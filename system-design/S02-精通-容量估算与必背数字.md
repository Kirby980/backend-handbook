# 精通容量估算与必背数字

> 容量估算（Capacity Estimation / Back-of-the-envelope）是系统设计的"地基"。没有它，所有架构决策都是空中楼阁——你凭什么说"要加缓存"？凭什么说"单库扛不住要分片"？答案都藏在估算里。
>
> 这一篇给你两样东西：一套**可复用的估算套路**，和一组**必背的数量级数字**。目标不是算得精确，而是建立"数量级直觉"——面试官问"这个系统要几台机器"，你能在 30 秒内给出一个站得住脚的区间。

---

## 一、为什么估算是系统设计的地基

估算的价值，在于**把模糊的"大概很多"变成可决策的数字**。看一个例子：

> 题目：设计一个短链系统。

如果不估算，你只能含糊地说"用数据库存映射，加 Redis 缓存"。如果估算：

- 假设每天新增 1 亿条短链 → 写 QPS ≈ 1e8 / 1e5 ≈ **1000/s**（均值），峰值 3 倍 ≈ 3000/s。
- 读写比按 10:1 → 读 QPS ≈ **1万/s**（均值），峰值 ≈ 3万/s。
- 存一条约 100 字节，5 年 ≈ 1e8 × 365 × 5 × 100B ≈ **18 TB**。

有了这三个数，结论立刻清晰：写 3000/s 单库能扛，**不必一上来分片**；读 3万/s 必须缓存；18TB 单机磁盘放得下但要考虑副本和增长。**估算直接驱动了"先不分片、重点做读缓存"这个架构决策**——这就是面试官想看到的因果链。

记住一句话：**估算是为决策服务的，不是为了算出一个漂亮数字。** 每算一个数，都要紧跟一句"所以……"。

## 二、必背 Latency Numbers（2026 校准版）

Jeff Dean 那张经典 "Latency Numbers Every Programmer Should Know" 需要按当代硬件（NVMe、100GbE、DDR5）校准。下面是 2026 年的量级参考——**记数量级，不要背精确值**：

| 操作 | 量级 | 直觉 |
|---|---|---|
| L1 缓存引用 | ~1 ns | 基准单位 |
| 分支预测失败 | ~3 ns | |
| L2 缓存引用 | ~4 ns | |
| 互斥锁加解锁 | ~15 ns | |
| 内存随机读 | ~80–100 ns | 比 L1 慢 ~100 倍 |
| 内存顺序读 1MB | ~50 μs | |
| **NVMe SSD 随机读** | ~20–100 μs | 比 2010 年代 SATA SSD（~150μs）快一个量级 |
| **Redis 读（同机房往返）** | ~0.2–0.5 ms | 含网络 RTT，主要是网络开销 |
| SSD 顺序读 1MB | ~50–200 μs | |
| **同机房网络 RTT** | ~0.5 ms | |
| **同城机房 RTT** | ~0.5–2 ms | |
| 磁盘（HDD）寻道 | ~5–10 ms | 仍用于冷存储/归档 |
| **跨城 RTT（如京沪）** | ~25–35 ms | 受光速物理限制，无法优化 |
| **跨国 RTT（如中美）** | ~150–200 ms | |

**会用比会背更重要**。两个关键推论：

1. **内存比磁盘快 ~1000 倍，跨城比同城慢 ~30 倍**——这解释了为什么要缓存、为什么强一致跨地域同步很贵。
2. **跨城 RTT 是光速决定的物理下限**：北京到上海直线 ~1100km，光纤里光速约 20万 km/s，单程 ~5.5ms，往返 + 设备转发 ≈ 30ms。**这个数字优化不掉**，所以异地多活的强一致写必然慢，只能靠就近 + 最终一致绕开。

## 三、单位与 2 的幂速查

估算时单位换算出错是低级但致命的失误。背熟下面这张表，心算才快：

### 3.1 2 的幂 → 十进制近似

| 2 的幂 | 近似值 | 字节单位 |
|---|---|---|
| 2^10 | ~1 千 (1.02e3) | 1 KB |
| 2^20 | ~1 百万 (1.05e6) | 1 MB |
| 2^30 | ~10 亿 (1.07e9) | 1 GB |
| 2^32 | ~43 亿 | 4 GB（int32 上限，雪花 ID 常考） |
| 2^40 | ~1 万亿 | 1 TB |
| 2^50 | — | 1 PB |

### 3.2 时间速查

- 一天 = 86,400 秒 ≈ **1e5 秒**（估算时直接用 10万，误差 15% 可接受）。
- 一个月 ≈ 2.6e6 秒；一年 ≈ 3.15e7 秒 ≈ **3e7 秒**。

### 3.3 数据类型大小

| 类型 | 大小 | 备注 |
|---|---|---|
| char / int8 | 1 B | |
| int / int32 | 4 B | |
| long / int64 / 时间戳 | 8 B | |
| UUID | 16 B | |
| 一个中文字符 (UTF-8) | 3 B | |
| 一条典型业务记录 | ~100 B – 1 KB | 估算常用基准 |

## 四、QPS 估算套路

QPS（Queries Per Second）是几乎所有题的起点。标准流程：

### 4.1 从 DAU 到平均 QPS

```
平均 QPS = DAU × 人均每日请求数 / 86400(≈1e5)
```

例：DAU 1000 万、人均每天刷 20 次 Feed：
平均读 QPS = 1e7 × 20 / 1e5 = **2000/s**。

### 4.2 峰值放大

真实流量不均匀（白天高、晚高峰尖）。**峰值 QPS = 平均 QPS × 放大倍数**，倍数按场景：

| 场景 | 峰值/均值 |
|---|---|
| 流量平稳的工具类 | 2–3× |
| 有明显晚高峰的社交/电商 | 3–5× |
| 秒杀/抢票等脉冲场景 | 10–100×+ |

上例按社交 5 倍：峰值读 QPS ≈ **1万/s**。

### 4.3 读写比

读写比决定优化方向。社交/内容类常见 **读:写 = 100:1 甚至更高**，所以读侧重缓存、写侧相对从容；而日志/IM/秒杀是写密集，重点在削峰和分片。**务必主动向面试官确认读写比**，它是选型的分水岭。

---

## 五、存储估算

```
存储 = 单条大小 × 每日新增条数 × 保留天数 × 副本数
```

逐项确认假设，再相乘。例：设计一个评论系统，每天 5000 万条评论，单条含文本 + 元数据 ≈ 500B，保留永久按 5 年算，副本 3 份：

```
5e7 × 500B × 365 × 5 × 3 ≈ 1.37e14 B ≈ 137 TB
```

要点：
- **副本数别忘**：通常 ×3（主 + 两从，或对象存储 3 副本）。
- **冷热分离**：算总量后说一句"其中近 30 天热数据约 X GB 放 SSD/缓存，历史冷数据归档到对象存储"，体现成本意识。
- **加索引/冗余开销**：实际占用比裸数据大 1.5–3 倍，估算时可乘个系数或口头说明。

---

## 六、带宽估算

```
带宽 = QPS × 单次传输大小
```

分**入向（ingress）**和**出向（egress）**分别算。例：图片服务峰值 1万 QPS，平均每张图 200KB：

```
出向带宽 = 1e4 × 200KB = 2e9 B/s = 2 GB/s ≈ 16 Gbps
```

参照物：**万兆网卡 ≈ 1.25 GB/s（10 Gbps）**。所以上例单机网卡扛不住，必须多机 + CDN 分摊——又一个由估算驱动的结论。25GbE / 100GbE 在 2026 已是数据中心标配，但 CDN 仍是图片/视频出向的第一选择。

---

## 七、内存与缓存容量估算

要不要缓存、缓存要多大内存，也靠估算。核心是**二八定律**：通常 **20% 的热数据承载 80% 的访问**。

流程：
1. 估算需要缓存的对象总量与单个大小。
2. 取热数据比例（常用 20%）。
3. 算出缓存内存预算，对照单机 Redis 容量（几十 GB 量级）决定要几个分片。

例：1 亿个用户会话，每个 1KB，缓存全部需 100GB；若只缓存活跃 20%，则 20GB，单 Redis 实例可放下，留增长空间可上 3 节点集群。

**命中率**是缓存设计的核心指标：命中率从 90% 提到 99%，意味着回源 DB 的请求量降到 1/10。讲方案时给出目标命中率（如"做到 95%+"）并说明它如何把后端压力降下来。

## 八、Little 定律与并发度

估算"需要多少并发/连接/线程/机器"时，用 **Little 定律**：

```
并发数 L = 到达率 λ (QPS) × 平均处理时间 W (秒)
```

例：某接口 QPS 5000，单次平均耗时 200ms（0.2s）：

```
并发数 = 5000 × 0.2 = 1000
```

即任意时刻约有 1000 个请求在途。推论：
- **连接池/线程池**：需要约 1000 的并发处理能力（视模型而定）。
- **机器数**：若单机能稳定处理 200 并发，则需 ≈ 5 台 + 冗余。
- **优化延迟即降并发**：把 W 从 200ms 降到 50ms，同 QPS 下并发降到 250——这就是为什么降延迟能省机器。

Little 定律也解释了**线程池打满**：当下游变慢（W 变大）而 QPS 不变，在途请求 L 暴涨，线程/连接被占满，进而雪崩。所以要配超时 + 限流，见 [B21 背压与限流](../backend/B21-精通背压与限流.md)。

## 九、完整示例·估算一个微博级系统

把上面的套路串起来，估算一个微博级系统。**先亮假设**：

- DAU 2 亿；人均每天发帖 0.1 次、刷 Feed 50 次（读）。
- 单条微博：文本 + 元数据 ≈ 1KB（不含图片，图片走对象存储）。
- 读写比因此约 500:1（典型社交）。

### 9.1 QPS

```
写 QPS(均) = 2e8 × 0.1 / 1e5 = 200/s     峰值 ×5 ≈ 1000/s
读 QPS(均) = 2e8 × 50  / 1e5 = 10万/s     峰值 ×5 ≈ 50万/s
```

**结论**：写 1000/s 单库可扛但要留余量；读 50万/s 是核心挑战，必须多级缓存 + 读副本 + CDN。

### 9.2 存储

```
每日新增文本 = 2e8 × 0.1 × 1KB = 2e7 KB = 20 GB/天
一年 ≈ 7.3 TB，三副本 ≈ 22 TB/年
```

**结论**：文本数据量不大，单集群可承载；真正的存储大头是图片/视频，放对象存储 + CDN。

### 9.3 带宽

```
读出向(峰) = 50万/s × 1KB = 5e8 B/s = 500 MB/s ≈ 4 Gbps（纯文本）
```

**结论**：纯文本带宽可控；算上图片（每次刷可能带几十张缩略图），出向轻松到几十 Gbps，CDN 是刚需。

### 9.4 缓存内存

```
热数据按近 3 天活跃微博 + 热门：约 20 GB × 3 + 热门常驻 ≈ 百 GB 量级
Feed 时间线缓存（每用户收件箱）：活跃用户 × 每人缓存若干 feed_id，又是几十~上百 GB
```

**结论**：需要 Redis 集群（多分片，TB 级总内存量级）。

### 9.5 机器规模

读服务按单机 1万 QPS 估，50万峰值 → ~50 台 + 冗余 ≈ 70 台；写服务流量小，10 台足够。**给出量级即可**，面试官要的是"几十台"还是"几千台"这个数量级判断，不是精确台数。

## 陷阱清单

- **单位错位**：把 86400 当 8640 或 864000，QPS 直接差一个量级。记死 ≈1e5。
- **忘记峰值放大**：用均值 QPS 选型，真到晚高峰就挂。一定乘 3–10×。
- **忘记副本数**：存储只算裸数据，实际 ×3 起。
- **读写比不问就假设**：默认读多写少，遇到 IM/日志这种写密集场景就翻车。
- **算完不用**：估出数字却不接"所以要/不要 X"，估算就白做了。
- **过度精确**：纠结"到底是 47万还是 52万 QPS"。系统设计只看数量级，给区间即可。
- **忽略物理下限**：承诺跨城强一致还低延迟——跨城 RTT ~30ms 是光速决定的，做不到。

## 2026 现状

- **硬件基线上移**：NVMe SSD 随机读进入几十微秒级、DDR5、25/100GbE 普及，使"内存数据库 + SSD 兜底"的架构更激进可行；很多过去必须分库的场景，单机性能已能覆盖。
- **NewSQL 改变存储估算**：TiDB / CockroachDB / Spanner 等把分片做进存储层，应用层估算更多关注"总量与副本"，而非"如何手工分库"，见 [S04 数据层扩展](./S04-精通-数据层扩展设计.md)。
- **延迟数字仍是面试硬通货**：硬件在变，但"内存 ns、SSD μs、同机房 ms、跨城几十 ms"的量级关系稳定，仍是必背。
- **可观测体系给真实数字**：生产中用 Prometheus / OTel 拿到真实 QPS、p99、命中率，比拍脑袋准；面试可提"上线后用监控验证估算并调整容量"。

## 练习题

1. 设计一个全球 IM 系统，DAU 5 亿、人均每天收发 40 条消息。估算消息写入的平均与峰值 QPS、每年消息存储量（单条 200B、三副本）。

<details><summary>参考答案</summary>

写均值 QPS = 5e8 × 40 / 1e5 = **20 万/s**；峰值按 ×5 ≈ **100 万/s**。年存储：每天消息数 = 5e8 × 40 = 2e10 条，一年 = 2e10 × 365 ≈ 7.3e12 条，× 200B = 1.46e15 B ≈ **1.46 PB**（裸数据），× 3 副本 ≈ **4.4 PB/年**。结论：消息量和存储都是海量级，写 100 万/s 远超单库，必须分片 + 写聚合/异步；PB 级存储需冷热分离（热数据内存/SSD、历史归档）。报数时先亮假设（DAU、人均条数、单条大小、副本），再给量级。

</details>

2. 某图片社交 App 峰值 2万 QPS，平均每次响应返回 5 张缩略图各 50KB。估算出向带宽，并判断需要多少张万兆网卡 / 是否必须上 CDN。

<details><summary>参考答案</summary>

出向带宽 = 2e4 QPS × 5 张 × 50KB = 2e4 × 250KB = 5e9 B/s = **5 GB/s ≈ 40 Gbps**。万兆网卡 ≈ 1.25 GB/s（10 Gbps），纯算需 5/1.25 ≈ **4 张**。但实际**必须上 CDN**：①单机/单机房网卡和上行带宽扛不住这么大出向；②图片是静态内容、全国/全球用户分布，CDN 就近返回能卸载绝大部分出向带宽，源站只承担边缘未命中的回源。所以结论不是"堆网卡"，而是"CDN 承担主要出向，源站压力降到很小"。

</details>

3. 用 Little 定律：一个下游 RPC 平均耗时 100ms，上游 QPS 3000，问连接池至少要多大？如果下游劣化到 500ms 会发生什么？

<details><summary>参考答案</summary>

Little 定律：并发数 = QPS × 平均耗时 = 3000 × 0.1s = **300**，所以连接池至少要 ~300（实际加余量）。若下游劣化到 500ms：并发 = 3000 × 0.5 = **1500**，在途请求暴涨到 1500。若连接池仍是 300，则请求排队等连接 → 等待超时 → 上游线程/连接被占满 → 拒绝服务甚至雪崩。这说明下游变慢会按倍数放大在途请求数，所以必须配超时 + 限流，防止下游劣化拖垮上游（见 B21）。

</details>

4. 一个系统读 QPS 20万，你打算用缓存抗。若目标命中率 98%，回源 DB 的 QPS 是多少？命中率掉到 90% 呢？这说明了什么？

<details><summary>参考答案</summary>

命中率 98% → 回源 DB = 20万 × (1−0.98) = **4000/s**；命中率 90% → 回源 = 20万 × 0.1 = **2万/s**。命中率从 98% 掉到 90%（看似只差 8 个百分点），回源 QPS 却从 4000 涨到 2 万、翻了 5 倍。这说明缓存命中率对后端压力是**非线性放大**——越接近 100%，每提升一点都极大降低回源；反之略微下降就可能压垮 DB。因此要努力保高命中率，并防缓存击穿/雪崩导致命中率骤降。

</details>

5. 解释为什么"北京机房写、上海机房同步强一致确认"的接口 p99 很难低于 60ms。

<details><summary>参考答案</summary>

因为跨城 RTT 是光速决定的物理下限：京沪直线约 1100 km，光在光纤中速度约 20 万 km/s，单程 ≈ 5.5ms，往返加上中间设备转发、排队，实测约 30ms 左右。同步强一致确认要求写操作必须等上海机房确认后才返回，至少包含一个跨城往返（~30ms），加上两端的处理时间、可能的多次交互（如两阶段），累积下来 p99 很难压到 60ms 以下。关键认知：这个延迟是物理规律，无法靠优化代码消除，只能通过就近写 + 最终一致 + 单元化来绕开跨城同步。

</details>

6. 给定 DAU 1 亿的短视频 Feed，人均每天看 30 个视频，每个视频平均 5MB。估算视频出向总流量（按天），并说明为什么这类系统的成本大头是带宽而非计算。

<details><summary>参考答案</summary>

每天播放次数 = 1e8 × 30 = 3e9 次，× 5MB = 1.5e16 B/天 = **15 PB/天** 的出向流量。成本大头是带宽而非计算的原因：①每次播放要传输 MB 级的大文件，而服务端的计算（鉴权、返回播放地址、推荐排序）相对很轻；②15 PB/天的出向带宽 + CDN 分发费用是巨额且持续的，远超服务器计算成本。所以短视频/直播这类系统的核心成本与优化重点都在带宽（CDN 计费、P2P 分发、码率自适应、热点预热），计算反而不是瓶颈。

</details>

7. 你估算出某写入场景峰值 8万 QPS，而单 MySQL 主库约 5000 TPS。请写出从这个数字推导出的两条架构结论。

<details><summary>参考答案</summary>

8万 / 5000 ≈ 16，写入需求是单库能力的约 16 倍。两条结论：①**单库扛不住，必须分库分表**——至少需要约 16 个以上的写分片把写入打散（留余量更多），或②**前置缓冲削峰 + 异步写**——用消息队列把瞬时 8万 QPS 缓冲，消费者按单库可承受的速率（几千 TPS）平稳写入，把同步写改成异步写。实践中两者常结合（分片 + 异步）。核心是估算出"写需求 ≫ 单库能力"这一数量级差，直接推导出"分片或异步削峰"的架构决策——这就是估算驱动设计。

</details>
