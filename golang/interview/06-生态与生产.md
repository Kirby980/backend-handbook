## §1 net/http

### Q1 ⭐⭐⭐⭐⭐ net/http server 的"四个超时"各覆盖什么阶段？生产推荐怎么设？

**答**：

`http.Server` 的四个超时字段对应连接生命周期的不同阶段，缺一个就可能被慢攻击拖垮：

| 超时 | 覆盖阶段 | 不设的风险 |
|---|---|---|
| `ReadHeaderTimeout` | accept → 读完请求 header | Slowloris 攻击：攻击者每秒发一个字节 header，连接耗尽 |
| `ReadTimeout` | accept → 读完整个请求（header + body） | 慢上传/大 body 攻击 |
| `WriteTimeout` | 开始写响应 → 写完 response | 客户端慢读，goroutine 卡在 `Write` |
| `IdleTimeout` | keep-alive 期间两次请求间的空闲 | 闲置连接占用 FD、内存 |

生产推荐配置（对一般 API 服务）：

```go
srv := &http.Server{
    Addr:              ":8080",
    Handler:           mux,
    ReadHeaderTimeout: 5 * time.Second,   // 必设，防 Slowloris
    ReadTimeout:       30 * time.Second,  // 含 body
    WriteTimeout:      30 * time.Second,  // 含响应写出
    IdleTimeout:       120 * time.Second, // keep-alive 空闲
    MaxHeaderBytes:    1 << 20,           // 1MB 防超大 header
}
```

注意三点：

1. **`ReadTimeout` 包含 `ReadHeaderTimeout`**，只设 `ReadTimeout` 等于两者都生效，但单独的 `ReadHeaderTimeout` 更细粒度。
2. **`WriteTimeout` 从开始写响应算起**，对长轮询 / SSE / 流式响应要单独用 `http.ResponseController.SetWriteDeadline` 调整，否则 30s 就被掐断。
3. **不要把超时设成 0**（零值表示"无限制"），这是 Go 1.0 至今最坑的"安全默认值"问题。

📎 **深入阅读**: [G27-精通-Go-net-http](../G27-精通-Go-net-http.md)

**常见追问**：
- Q: 为什么 Go 默认 `http.Server{}` 所有超时都是 0？ A: 历史原因，标准库不知道你的业务场景，但今天这是 CVE 级别的坑。
- Q: 上传文件场景 `ReadTimeout` 怎么设？ A: 用 `http.ResponseController.SetReadDeadline(handler 内动态延长)`，或者拆成独立的上传服务设大超时。
- Q: `WriteTimeout` 触发了客户端会看到什么？ A: 连接 RST，response 可能写到一半被截断；如果 header 还没写，客户端可能看到 EOF。

**陷阱**：很多团队照搬 `http.ListenAndServe(":8080", nil)`，等于把所有超时都关了，QA 流量没问题，公网一上就被慢连接打爆 FD。

### Q2 ⭐⭐⭐⭐ Go 1.22+ ServeMux 增强带来了什么？方法前缀 + PathValue 是怎么用的？

**答**：

Go 1.22 之前的 `http.ServeMux` 只支持前缀路由，方法分发、路径参数都得自己写或上 chi/gin。1.22 把它升级成了"够用的路由器"：

```go
mux := http.NewServeMux()

// 方法 + 路径 + 通配符
mux.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id")
    fmt.Fprintf(w, "user %s", id)
})

mux.HandleFunc("POST /users/{id}/posts", createPost)

// 路径末尾 {path...} 捕获剩余路径
mux.HandleFunc("GET /files/{path...}", serveFile)

// 优先级：精确路径 > 带参数 > 通配符
mux.HandleFunc("GET /users/me", currentUser) // 比 /users/{id} 优先级高
```

核心特性：

1. **方法前缀**：`"GET /users/{id}"` 中的 `GET ` 是 method matcher，未匹配返回 405。
2. **路径参数**：`{id}` 通过 `r.PathValue("id")` 取，类型只有 string。
3. **末尾通配**：`{path...}` 捕获多段路径。
4. **优先级规则**：更具体的模式优先（精确 > 参数 > 通配），冲突会在注册时 panic。
5. **`{$}` 锚定**：`"/users/{$}"` 表示精确 `/users/` 不含子路径。

对比第三方路由：性能略低于 chi/gin（少量正则），但够用，且零依赖。新项目内部服务可以直接用，C 端高 QPS 场景仍推荐 chi。

📎 **深入阅读**: [G27-精通-Go-net-http](../G27-精通-Go-net-http.md)

**常见追问**：
- Q: 优先级冲突怎么报错？ A: 注册时直接 panic，避免运行时歧义。
- Q: PathValue 没找到返回什么？ A: 空字符串 `""`，没有 ok 返回值。
- Q: 性能比 chi 差多少？ A: 简单路由差不到 2 倍，复杂正则可能差 3-5 倍，但对绝大多数 API 服务无感。

**陷阱**：`{id}` 不支持正则约束（chi 支持 `{id:[0-9]+}`），需要自己在 handler 里校验类型。

### Q3 ⭐⭐⭐⭐ middleware 链式调用是怎么实现的？洋葱模型怎么理解？

**答**：

middleware 本质是高阶函数：接收 `http.Handler` 返回新的 `http.Handler`，外层包裹内层，形成"洋葱"。

```go
type Middleware func(http.Handler) http.Handler

func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)  // 调用内层
        log.Printf("%s %s %v", r.Method, r.URL.Path, time.Since(start))
    })
}

func Recover(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if err := recover(); err != nil {
                http.Error(w, "internal error", 500)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

// 链式组合
func Chain(h http.Handler, mws ...Middleware) http.Handler {
    for i := len(mws) - 1; i >= 0; i-- {
        h = mws[i](h)
    }
    return h
}

handler := Chain(myHandler, Logging, Recover, Auth)
// 执行顺序：Logging → Recover → Auth → myHandler → Auth → Recover → Logging
```

**洋葱模型**：每个 middleware 包成一层，请求从外往内"穿过"每一层（pre-处理），到核心 handler 后再从内往外"返回"（post-处理）。`next.ServeHTTP(w, r)` 这一行就是穿透点：之前是 pre，之后是 post。

关键设计点：

1. **顺序敏感**：Recover 必须在最外层（捕获后面所有 panic），Logging 一般也靠外（记录完整耗时）。Auth 靠近业务。
2. **wrap ResponseWriter**：想拿到 status code、字节数，需要自定义 `responseWriter` 把 `WriteHeader` 包一层。
3. **context 传递**：在前层注入数据用 `r = r.WithContext(context.WithValue(...))`，注意 key 用自定义类型避免冲突。

📎 **深入阅读**: [G27-精通-Go-net-http](../G27-精通-Go-net-http.md)

**常见追问**：
- Q: 怎么拿到 response 的 status code？ A: wrap `http.ResponseWriter`，重写 `WriteHeader(code int)` 记录到字段。
- Q: middleware 在哪做 trace_id 生成？ A: 最外层，注入到 context，后续 logger / db / rpc 都能取到。
- Q: Go 1.22 ServeMux 支持子路由组吗？ A: 不支持（gin/chi 才有 group），需要自己写或用 `http.StripPrefix`。

**陷阱**：在 middleware 里写 `r.Body`，再调 `next.ServeHTTP` 时 body 已读完，下游拿不到。需要 `io.ReadAll` 后用 `bytes.NewReader` 重置。

### Q4 ⭐⭐⭐⭐⭐ graceful shutdown 怎么完整实现？

**答**：

优雅停机的目标：**新请求拒绝、旧请求处理完、超时后强杀**。完整模板：

```go
package main

import (
    "context"
    "errors"
    "log"
    "net/http"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    srv := &http.Server{
        Addr:              ":8080",
        Handler:           mux,
        ReadHeaderTimeout: 5 * time.Second,
        ReadTimeout:       30 * time.Second,
        WriteTimeout:      30 * time.Second,
        IdleTimeout:       120 * time.Second,
    }

    // 1. 启动 server（异步）
    serverErr := make(chan error, 1)
    go func() {
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            serverErr <- err
        }
    }()

    // 2. 监听信号（Go 1.16+ signal.NotifyContext）
    ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
    defer stop()

    select {
    case err := <-serverErr:
        log.Fatalf("server error: %v", err)
    case <-ctx.Done():
        log.Println("shutdown signal received")
    }

    // 3. 给 in-flight 请求 30 秒处理时间
    shutdownCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()

    // 4. Shutdown：停 accept、关 idle 连接、等 active 连接处理完
    if err := srv.Shutdown(shutdownCtx); err != nil {
        log.Printf("graceful shutdown failed, force close: %v", err)
        _ = srv.Close() // 兜底强杀
    }

    log.Println("server exited cleanly")
}
```

`srv.Shutdown(ctx)` 做的事：

1. 关闭所有 listener（停止 accept 新连接）
2. 关闭所有处于 idle 状态的 keep-alive 连接
3. 等待 in-flight handler 完成；ctx 超时则返回 `context.DeadlineExceeded`，**但不会强杀正在执行的 handler**

所以需要：handler 自己监听 `r.Context().Done()`，在 ctx 取消时尽快返回（用 `select` 在 channel 操作里检查）。

**外围还要做的事**（生产）：

- **k8s 场景**：preStop hook 先 `sleep 5s` 等 endpoint 摘除，再发 SIGTERM，避免 readiness 切换有窗口期。
- **健康检查**：收到信号后先把 `/health` 返回 503，让 LB 早摘流。
- **依赖清理**：DB 连接池 `db.Close()`、消息队列 consumer 停止、缓存 flush 等，都在 Shutdown 之后做。

📎 **深入阅读**: [G27-精通-Go-net-http](../G27-精通-Go-net-http.md)

**常见追问**：
- Q: 为什么需要 `signal.NotifyContext` 而不是直接 `signal.Notify`？ A: 1.16+ 标准库语法糖，ctx 自动被信号取消，写起来更简洁。
- Q: handler 内的长循环怎么响应 shutdown？ A: 必须 `select` 监听 `r.Context().Done()`，否则 Shutdown 永远等不到它结束。
- Q: WebSocket / SSE 怎么处理？ A: Shutdown 不会主动关长连接，需要自己维护连接表，收到关停信号后向所有连接发关闭帧。

**陷阱**：`Shutdown(ctx)` 不传超时（用 `context.Background()`）会无限等慢请求；服务永远停不下来。一定要带 deadline。

### Q5 ⭐⭐⭐⭐ http.Client 有哪些常见陷阱？

**答**：

`http.Client` 看着简单，生产坑特别多：

**1. 不要每次新建 Client**

```go
// ❌ 每次新建 Client → Transport 也是新的 → 连接池失效，每次都是新 TCP/TLS
for _, url := range urls {
    resp, _ := http.Get(url) // 内部 DefaultClient，但很多人手写 &http.Client{}
}

// ✅ Client 复用，Transport 内置连接池
var client = &http.Client{
    Timeout: 10 * time.Second,
    Transport: &http.Transport{
        MaxIdleConns:        100,
        MaxIdleConnsPerHost: 20,
        IdleConnTimeout:     90 * time.Second,
    },
}
```

**2. Body 必须读完才能复用连接**

```go
// ❌ 没读完 body 就 Close → 连接被丢弃，下次重新建立
resp, _ := client.Get(url)
defer resp.Body.Close()
if resp.StatusCode != 200 {
    return // body 没读，连接复用失败
}

// ✅ 不需要 body 也要 drain
defer func() {
    io.Copy(io.Discard, resp.Body)
    resp.Body.Close()
}()
```

**3. 默认 Transport 的陷阱**

`http.DefaultTransport` 的 `MaxIdleConnsPerHost` 是 2（！），高 QPS 调用同一域名时大部分连接都被新建，性能很差。

**4. 超时分层**

```go
client := &http.Client{
    Timeout: 30 * time.Second, // 端到端总超时
    Transport: &http.Transport{
        DialContext: (&net.Dialer{
            Timeout:   5 * time.Second, // TCP 连接
            KeepAlive: 30 * time.Second,
        }).DialContext,
        TLSHandshakeTimeout:   5 * time.Second,
        ResponseHeaderTimeout: 10 * time.Second, // 收到 response header
        ExpectContinueTimeout: 1 * time.Second,
        IdleConnTimeout:       90 * time.Second,
    },
}
```

**5. 取消请求用 `context`**

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
resp, err := client.Do(req)
```

不要用 `client.Timeout` 控制单个请求，那是全局的。

**6. Proxy / TLS 验证**

测试环境关闭 TLS 验证：`Transport.TLSClientConfig = &tls.Config{InsecureSkipVerify: true}`，生产绝对不要忘了打开。

📎 **深入阅读**: [G27-精通-Go-net-http](../G27-精通-Go-net-http.md)

**常见追问**：
- Q: Transport 复用为什么不能跨 Client？ A: 可以跨 Client，但每个 Client 持有的 Transport 是独立的连接池，跨 Client 必须共享同一 Transport 实例才行。
- Q: HTTP/2 的连接复用规则？ A: 一个连接多路复用多个 stream，连接池层面单个 host 通常只需 1-2 个连接。
- Q: 怎么定位连接没复用？ A: `httptrace.ClientTrace` 的 `GotConn` 回调，看 `info.Reused` 字段。

**陷阱**：忘记 `defer resp.Body.Close()` 不仅泄漏 fd，还会让连接进入 limbo 状态被 transport 丢弃。

## §2 gRPC

### Q6 ⭐⭐⭐⭐ gRPC 四种 RPC 模式各适合什么场景？

**答**：

gRPC 基于 HTTP/2 stream 设计四种调用模式：

| 模式 | proto 写法 | 场景 |
|---|---|---|
| Unary | `rpc Get (Req) returns (Resp);` | 普通 RPC：查询、写入、命令 |
| Server streaming | `rpc List (Req) returns (stream Resp);` | 大结果集分批返回、日志推送、订阅广播 |
| Client streaming | `rpc Upload (stream Req) returns (Resp);` | 上传、批量写入、聚合统计 |
| Bidi streaming | `rpc Chat (stream Req) returns (stream Resp);` | 聊天、双向同步、控制流交互 |

具体场景例子：

- **Unary**：90% 的内部 RPC 都是这类，类似 REST GET/POST。低延迟、单次往返。
- **Server streaming**：拉一个大文件分块返回；订阅 K8s 资源变更（`Watch`）；实时行情推送。客户端读完所有 `Recv()` 看到 `io.EOF` 表示结束。
- **Client streaming**：上传日志批次（每条一个 message，server 聚合后返回总数）；指标上报。
- **Bidi streaming**：客户端和服务端都长连接，互相推消息；典型是聊天系统、IoT 双向控制、协同编辑。

streaming 模式注意点：

1. **不能在多个 goroutine 同时 Send 或同时 Recv**（同方向非线程安全），但一个 goroutine Send、另一个 Recv 是安全的。
2. **流的生命周期等同 ctx**，ctx 取消整个流也取消。
3. **流量控制**：HTTP/2 自带 flow control，但应用层也要小心 server 推得快 client 处理不过来 → 内存涨。
4. **错误传播**：流中途出错通过 `Recv()` 返回 `error`，不会用 trailers 之外的方式通知。

📎 **深入阅读**: [G28-精通-Go-gRPC-与-Protobuf](../G28-精通-Go-gRPC-与-Protobuf.md)

**常见追问**：
- Q: server streaming 怎么实现客户端取消？ A: client 端 `ctx.Cancel()`，server 的 stream `Context().Done()` 收到信号。
- Q: 一个 bidi stream 能不能同时跑两个 goroutine 一个 send 一个 recv？ A: 可以，方向独立，但同方向并发 panic。
- Q: streaming 跟普通 unary 性能差距？ A: 流式建立有额外的 HTTP/2 stream 开销，但 message 多时摊销很低；单次 unary 1-2 ms，流式 message 走在已有 stream 上几十微秒。

**陷阱**：忘记调用 `stream.CloseSend()`（client streaming），server 端 `Recv()` 永远拿不到 EOF，goroutine 泄漏。

### Q7 ⭐⭐⭐⭐ gRPC interceptor 两类怎么写？

**答**：

gRPC 的中间件叫 interceptor，分 unary 和 stream 两类，client / server 端各自独立：

**Server-side unary interceptor**：

```go
func LoggingUnaryInterceptor(
    ctx context.Context,
    req interface{},
    info *grpc.UnaryServerInfo,
    handler grpc.UnaryHandler,
) (resp interface{}, err error) {
    start := time.Now()
    resp, err = handler(ctx, req) // 调下游
    log.Printf("method=%s dur=%v err=%v", info.FullMethod, time.Since(start), err)
    return
}

srv := grpc.NewServer(grpc.UnaryInterceptor(LoggingUnaryInterceptor))
```

**Server-side stream interceptor**：

```go
func LoggingStreamInterceptor(
    srv interface{},
    ss grpc.ServerStream,
    info *grpc.StreamServerInfo,
    handler grpc.StreamHandler,
) error {
    start := time.Now()
    err := handler(srv, ss)
    log.Printf("method=%s dur=%v err=%v", info.FullMethod, time.Since(start), err)
    return err
}

srv := grpc.NewServer(grpc.StreamInterceptor(LoggingStreamInterceptor))
```

**多个 interceptor 链**：用 `grpc.ChainUnaryInterceptor(a, b, c)`，洋葱模型同 http middleware。

**典型用途**：

1. **日志**：记录方法名、耗时、status code
2. **认证**：从 metadata 取 token 校验
3. **trace**：从 metadata 取 trace_id 注入 context，调下游时再透传
4. **限流 / 熔断**：在 handler 前判断
5. **panic recover**：handler panic 时转成 `codes.Internal`
6. **指标**：Prometheus method label 上报

**Client 端**写法对称：`grpc.UnaryClientInterceptor` / `grpc.StreamClientInterceptor`，签名略不同（带 method 名、cc、opts）。

📎 **深入阅读**: [G28-精通-Go-gRPC-与-Protobuf](../G28-精通-Go-gRPC-与-Protobuf.md)

**常见追问**：
- Q: stream interceptor 怎么拿到具体的 message？ A: 包一层 `grpc.ServerStream`，重写 `SendMsg` / `RecvMsg`，否则 interceptor 只能在 handler 进出时观察。
- Q: client interceptor 怎么注入 trace？ A: 在 `invoker` 调用前用 `metadata.AppendToOutgoingContext(ctx, "trace-id", id)`。
- Q: 多个 interceptor 的执行顺序？ A: ChainUnaryInterceptor(a, b, c) → a 最外，c 最内，handler 在最里面。

**陷阱**：把 panic recover 放在 chain 中间而不是第一个（最外层），后面的 interceptor panic 就没法捕获。

### Q8 ⭐⭐⭐ gRPC vs REST 怎么选？

**答**：

不是 either-or，而是分场景：

| 维度 | gRPC | REST/JSON |
|---|---|---|
| 协议 | HTTP/2 + Protobuf | HTTP/1.1 或 HTTP/2 + JSON |
| 性能 | 序列化快 5-10x，体积小 3-5x | 文本，易读但慢 |
| Schema | proto 强约束 | OpenAPI（可选） |
| 浏览器 | 需要 grpc-web 代理 | 原生支持 |
| 流式 | 原生支持 | SSE/WebSocket 自己搭 |
| 工具链 | protoc 生成多语言 stub | 生态成熟，curl/Postman 友好 |
| 可观测 | metadata + 工具集成 | 调试简单 |

**选 gRPC**：

- 内部服务间调用，团队都用 gRPC
- 高 QPS（>1k）、低延迟（<10ms）要求
- 需要双向流（聊天、推送、IoT）
- 跨语言（Go/Java/Python 都生成 stub）
- 接口契约强，proto 当文档

**选 REST**：

- 对外 API（合作伙伴、浏览器、移动端）
- 接口频繁变更、参数不固定
- 团队没 protoc 工具链
- 调试便利重要（curl/Postman）

**实践**：很多团队是"内部 gRPC + 外部 REST"，前端层用 gRPC-Gateway 自动生成 REST 反向代理。

📎 **深入阅读**: [G28-精通-Go-gRPC-与-Protobuf](../G28-精通-Go-gRPC-与-Protobuf.md)

**常见追问**：
- Q: 浏览器为什么用不了 gRPC？ A: 浏览器不能控制 HTTP/2 trailers，需要 grpc-web 转发到 HTTP/1.1 + base64。
- Q: protobuf 比 JSON 快多少？ A: 序列化 5-10x，反序列化 3-5x，CPU 占用差距更大。
- Q: gRPC 怎么做 API 版本？ A: package 名带版本（`pkg.v1`, `pkg.v2`），proto 文件目录分版本。

**陷阱**：对外服务直接暴露 gRPC，需要专门 SDK 才能调，门槛高、生态差，慎选。

### Q9 ⭐⭐⭐⭐ gRPC status code 几个常用怎么用？

**答**：

gRPC 用 `codes.Code` 枚举表达错误类型，对应 HTTP 状态语义化更细：

| Code | 含义 | 典型场景 |
|---|---|---|
| `OK` | 成功 | - |
| `Canceled` | 客户端取消 | client 主动 cancel ctx |
| `Unknown` | 未知错误 | panic 兜底 |
| `InvalidArgument` | 参数错误 | 入参校验失败 |
| `DeadlineExceeded` | 超时 | ctx deadline 到期 |
| `NotFound` | 资源不存在 | 查询的 ID 不在 |
| `AlreadyExists` | 资源已存在 | 创建冲突 |
| `PermissionDenied` | 无权限 | 鉴权过但无权限 |
| `Unauthenticated` | 未认证 | token 缺失/过期 |
| `ResourceExhausted` | 资源耗尽 | 限流、配额超 |
| `FailedPrecondition` | 前置条件不满足 | 状态机不允许该操作 |
| `Aborted` | 中止（一般可重试） | 乐观锁冲突 |
| `Unavailable` | 服务不可用（**应重试**） | 下游挂了、连接断 |
| `Internal` | 内部错误（不应重试） | bug、空指针 |
| `Unimplemented` | 未实现 | 协议字段对方不认 |

**写法**：

```go
import (
    "google.golang.org/grpc/codes"
    "google.golang.org/grpc/status"
)

func GetUser(ctx context.Context, req *pb.GetUserReq) (*pb.User, error) {
    if req.Id == "" {
        return nil, status.Errorf(codes.InvalidArgument, "id is required")
    }
    u, err := db.Find(req.Id)
    if errors.Is(err, sql.ErrNoRows) {
        return nil, status.Errorf(codes.NotFound, "user %s not found", req.Id)
    }
    if err != nil {
        return nil, status.Errorf(codes.Internal, "db error: %v", err)
    }
    return u, nil
}

// client 端判断
_, err := client.GetUser(ctx, req)
if st, ok := status.FromError(err); ok {
    switch st.Code() {
    case codes.NotFound:
        // ...
    case codes.Unavailable:
        // 重试
    }
}
```

**重试策略**：`Unavailable` / `Aborted` / `DeadlineExceeded`（如果 ctx 还有时间）通常可以重试；`InvalidArgument` / `NotFound` / `Internal` 重试无意义。

**结构化错误细节**：`status.Error` 支持 `WithDetails(...)` 携带 protobuf 详情，业务可自定义错误码。

📎 **深入阅读**: [G28-精通-Go-gRPC-与-Protobuf](../G28-精通-Go-gRPC-与-Protobuf.md)

**常见追问**：
- Q: `Canceled` vs `DeadlineExceeded`？ A: 前者是主动取消，后者是超时；server 端区分意义不大，client 端日志要分清。
- Q: 怎么把 HTTP 状态码映射到 gRPC？ A: grpc-gateway 内置映射表（404→NotFound, 401→Unauthenticated 等）。
- Q: server panic 默认是什么 code？ A: 没有 recover 时连接被关，client 看到 `Unavailable`；有 recover 通常转成 `Internal`。

**陷阱**：误用 `Internal` 表达业务错误（如"余额不足"），导致客户端误重试；业务错误应该用 `FailedPrecondition` 或自定义 details。

### Q10 ⭐⭐⭐⭐ Protobuf 兼容性规则有哪些？

**答**：

protobuf 设计的核心目标就是**向前向后兼容**，关键规则：

**1. 字段编号是契约，绝对不能改**

```proto
message User {
    string name = 1;   // 编号 1 永久绑定 name
    int64  age  = 2;
    // 编号 3 删除了？ 用 reserved 占位
    reserved 3;
    reserved "old_field"; // 保留字段名也防止冲突
}
```

改编号 = 改协议，老 client 解析新数据时把 `string` 当成新字段的类型读，全乱套。

**2. 字段类型兼容范围**

| 旧类型 | 可改成 |
|---|---|
| `int32` | `int64` `uint32` `uint64` `bool` (wire 兼容，但语义可能截断) |
| `sint32` | `sint64` |
| `string` | `bytes` (bytes 是 valid UTF-8 时) |
| `enum` | `int32` |
| `repeated T` (packed) | `repeated T` (non-packed)，反向兼容 |

不兼容：`int32` → `string`（wire 不同）；`message` → `int32`。

**3. 增删字段都向前向后兼容**

- 新增字段：旧 client 解析新数据时未知字段会被保留（proto3 默认 preserve unknown fields），不影响。
- 删除字段：等同于添加 `reserved`，旧 client 写的数据 server 收到忽略。

**4. proto2 vs proto3**

| 维度 | proto2 | proto3 |
|---|---|---|
| required | 支持（但**强烈反对**） | 移除 |
| optional | 支持 | 1.0 移除，3.15 重新加回（带 has_xxx） |
| 默认值 | 可自定义 | 类型零值，不可改 |
| unknown fields | 默认保留 | 3.5+ 默认保留 |

`required` 不兼容修改：一旦写了 required，永远不能改成 optional（旧二进制会拒绝缺字段）。所以**生产 proto 永远不用 required**。

proto3 早期问题：无法区分"字段没传"vs"字段是零值"。3.15+ 用 `optional` 恢复，编译出 `HasXxx()` 方法。

**5. enum 规则**

- 新 enum 值添加到末尾
- 不要删除已有值（reserved）
- enum 默认值（0）保留给"未指定"语义

📎 **深入阅读**: [G28-精通-Go-gRPC-与-Protobuf](../G28-精通-Go-gRPC-与-Protobuf.md)

**常见追问**：
- Q: 把 `repeated int32` 改成 `repeated int64` 安全吗？ A: wire 兼容，但 packed 编码下要小心 message size 变化。
- Q: 字段从 `optional` 改成 `repeated` 行吗？ A: 不行，wire type 不同。
- Q: proto3 怎么知道字段是否被设置？ A: 用 `optional` 关键字（3.15+），编译出 `HasXxx() bool`。

**陷阱**：直接复用已删除的字段编号给新字段——最经典翻车，建议养成习惯每次删都加 `reserved N;`。

### Q11 ⭐⭐⭐⭐ database/sql 连接池怎么配？

**答**：

`database/sql` 暴露三个核心参数：

| 参数 | 默认 | 含义 |
|---|---|---|
| `SetMaxOpenConns(n)` | 0（无限制） | 同时打开的最大连接数 |
| `SetMaxIdleConns(n)` | 2 | 空闲连接池容量 |
| `SetConnMaxLifetime(d)` | 0（永久） | 连接最长生命，超时强制关 |
| `SetConnMaxIdleTime(d)` | 0（永久） | 空闲多久后关 |

**生产配置思路**：

```go
db, err := sql.Open("postgres", dsn)
db.SetMaxOpenConns(50)        // 看 DB 端 max_connections / 服务实例数 算
db.SetMaxIdleConns(10)        // 一般 = MaxOpen 的 20%-50%
db.SetConnMaxLifetime(30 * time.Minute) // 防止连接老化（DNS 漂移、防火墙超时）
db.SetConnMaxIdleTime(5 * time.Minute)  // 低峰期收缩
```

**MaxOpen 怎么算**：

- 单实例：`MaxOpen × 实例数 < DB 的 max_connections × 0.8`（留余量）
- PostgreSQL：默认 max_connections=100，部署 10 个实例每个 MaxOpen=8 比较稳
- MySQL：默认 151，但通常调大到 500-1000

**MaxIdle 不能太小**：默认 2 是大坑，QPS 高时每次都要新建连接，TLS 握手开销大。一般 = MaxOpen 的 20-50%。

**ConnMaxLifetime 必须设**：

- 云数据库 / RDS 经常有空闲连接强制断开（5-10 分钟无活动）
- 服务后面的 LB 也可能 timeout
- 不设的话连接会 stale，下次用报 "connection reset"

**指标监控**：

```go
stats := db.Stats()
// MaxOpenConnections、OpenConnections、InUse、Idle
// WaitCount、WaitDuration（等连接的次数和总时间，>0 表示池不够大）
```

`WaitCount` 持续增长就该扩 MaxOpen，或者优化慢查询释放连接。

📎 **深入阅读**: [G29-精通-Go-数据库访问](../G29-精通-Go-数据库访问.md)

**常见追问**：
- Q: MaxIdle > MaxOpen 会怎样？ A: 库内部自动截断 MaxIdle = MaxOpen。
- Q: 怎么判断连接池小了？ A: `db.Stats().WaitDuration` 持续大于 0，或者 P99 延迟主要在等连接。
- Q: 连接被 DB 端断开 Go 这边能感知吗？ A: 不能立即感知，下次 Query 时报错；用 `ConnMaxLifetime` 主动轮换。

**陷阱**：MaxOpenConns 设太大（如 1000），DB 端总连接数被打爆，所有服务都连不上。

### Q12 ⭐⭐⭐⭐ pgx 相比 database/sql 优势是什么？

**答**：

`database/sql` 是 Go 的标准 DB 抽象，但它是 LCD（最小公共子集），PostgreSQL 的很多特性表达不出来。`pgx` 是 Postgres 原生 driver，有两种用法：

1. **作为 database/sql driver**：`import _ "github.com/jackc/pgx/v5/stdlib"` —— 跟标准库一致，但用不到 pgx 高级特性。
2. **直接用 pgx API**：跳过 database/sql，直接调 `pgx.Connect()` / `pgxpool.New()`，解锁所有特性。

**核心优势**：

| 特性 | database/sql | pgx 原生 |
|---|---|---|
| 协议 | 通过 driver 走 lib/pq 或 pgx | 原生 Postgres binary protocol |
| 类型支持 | 基础类型 | UUID、JSONB、Array、Range、Hstore、复合类型全支持 |
| 批量插入 | `INSERT VALUES (?), (?), ...` 拼 | `COPY FROM` 接口（10x 快） |
| Batch 协议 | 不支持 | 多条 query 合并一次网络往返 |
| LISTEN/NOTIFY | 不支持 | 原生支持订阅 |
| Prepared Statement | 部分支持 | 完整 + 自动缓存 |
| 性能 | 基线 | 序列化快 2-3x，无中间反射 |

**COPY 批量**：

```go
rows := [][]any{
    {1, "a"},
    {2, "b"},
    // ...10w 行
}
n, err := conn.CopyFrom(ctx, pgx.Identifier{"users"}, []string{"id", "name"}, pgx.CopyFromRows(rows))
// 10 万行：INSERT 30s，COPY 2s
```

**Batch**：

```go
batch := &pgx.Batch{}
batch.Queue("INSERT INTO logs(msg) VALUES($1)", "a")
batch.Queue("INSERT INTO logs(msg) VALUES($1)", "b")
br := conn.SendBatch(ctx, batch)
defer br.Close()
// 一次网络往返跑两条 SQL
```

**JSONB 直接绑定**：

```go
type Config struct {
    Name string
    Tags []string
}
var c Config
conn.QueryRow(ctx, "SELECT data FROM configs WHERE id=$1", id).Scan(&c)
// pgx 自动 json.Unmarshal
```

**什么时候用 pgx 原生 vs database/sql + pgx driver**：

- 只跑 Postgres + 需要 COPY / JSONB / Array → pgx 原生
- 需要 driver 抽象（多 DB 支持、ORM 兼容）→ pgx 当 driver
- 用 sqlc → 默认就是 pgx

📎 **深入阅读**: [G29-精通-Go-数据库访问](../G29-精通-Go-数据库访问.md)

**常见追问**：
- Q: pgx 怎么处理连接池？ A: `pgxpool.Pool`，跟 `*sql.DB` 类似，但配置项更多（最小连接数、健康检查等）。
- Q: 为什么 COPY 比 INSERT 快这么多？ A: COPY 是流式协议，无 SQL 解析、无 prepared statement、无 round-trip per row。
- Q: pgx 支持 MySQL 吗？ A: 不支持，纯 Postgres driver。

**陷阱**：用 pgx driver 但 dsn 写错（`?` vs `$1` 占位符），database/sql 抽象层会迷惑。

### Q13 ⭐⭐⭐⭐⭐ N+1 问题怎么识别？怎么修？

**答**：

**症状**：查 N 个主对象，触发 N 次子对象查询，总共 N+1 次 DB 调用。

```go
// ❌ N+1
users, _ := db.QueryUsers() // 1 次：拿 100 个 user
for _, u := range users {
    posts, _ := db.QueryPostsByUserID(u.ID) // 100 次：每人查一次 posts
}
// 总：101 次 DB 查询，延迟 = N × RTT
```

**识别方法**：

1. **慢查询日志**：发现某个端点 DB 调用次数随用户数线性增长。
2. **APM/Trace**：trace span 里数据库调用次数特别多。
3. **代码 review**：for 循环里有 DB 调用 → 立刻警惕。
4. **测试**：在测试里 mock db 计数 query 次数。

**修法**：

**方法 1：JOIN（最简单）**

```go
rows, _ := db.Query(`
    SELECT u.id, u.name, p.id, p.title 
    FROM users u 
    LEFT JOIN posts p ON p.user_id = u.id
    WHERE u.org_id = $1`, orgID)
// 1 次查询，应用层组装
```

但 JOIN 在 user 有多 post 时会 duplicate user 数据，传输放大。

**方法 2：批量 IN 查询（最常用）**

```go
users, _ := db.QueryUsers() // 1 次
userIDs := extractIDs(users)
posts, _ := db.Query("SELECT * FROM posts WHERE user_id = ANY($1)", userIDs) // 1 次
// 应用层 groupBy 拼回
postsByUser := groupBy(posts, func(p Post) int { return p.UserID })
for i := range users {
    users[i].Posts = postsByUser[users[i].ID]
}
// 总：2 次查询
```

**方法 3：DataLoader 模式**

适合 GraphQL / RPC 场景：在 request scope 内攒一批 ID，一次性查。开源库如 `graph-gophers/dataloader`：

```go
loader := dataloader.NewBatchedLoader(func(ctx context.Context, keys []dataloader.Key) []*dataloader.Result {
    ids := toIDs(keys)
    posts, _ := db.Query("SELECT * FROM posts WHERE user_id = ANY($1)", ids)
    return mapBack(posts, keys)
})

// 各业务并发调用，dataloader 自动 batch
postsForUser1 := loader.Load(ctx, dataloader.StringKey("1"))
postsForUser2 := loader.Load(ctx, dataloader.StringKey("2"))
```

**方法 4：ORM 的 Preload / Eager Loading**

GORM 的 `db.Preload("Posts").Find(&users)`、ent 的 `client.User.Query().WithPosts().All(ctx)`，都是对方法 2 的封装。

**预防**：

- code review 警惕 for 循环内 DB / RPC
- 测试覆盖关键端点的 query 次数（断言不超过 K 次）
- 慢端点用 trace 看 DB span 数量

📎 **深入阅读**: [G29-精通-Go-数据库访问](../G29-精通-Go-数据库访问.md)

**常见追问**：
- Q: GraphQL 怎么天然遇到 N+1？ A: resolver 嵌套调用，每层默认独立查询。DataLoader 是标准解法。
- Q: ANY($1) 比 IN(?,?,...) 好在哪？ A: 参数固定一个，避免 SQL 文本变化导致 prepared statement cache miss。
- Q: 一次查询返回 10w 行内存爆了怎么办？ A: 分页 / 游标 / 流式。

**陷阱**：用 ORM 的人最容易栽 N+1，因为对象关联看起来"自然"访问，背后 N 次查询不可见。

### Q14 ⭐⭐⭐⭐ 事务管理 best practice？

**答**：

**标准模板**：

```go
func TransferMoney(ctx context.Context, db *sql.DB, from, to int64, amount int) error {
    tx, err := db.BeginTx(ctx, &sql.TxOptions{
        Isolation: sql.LevelReadCommitted,
    })
    if err != nil {
        return fmt.Errorf("begin tx: %w", err)
    }

    // 注意：defer rollback 在 commit 成功后是 no-op，不冲突
    defer func() {
        _ = tx.Rollback()
    }()

    if _, err := tx.ExecContext(ctx,
        "UPDATE accounts SET balance = balance - $1 WHERE id = $2", amount, from); err != nil {
        return fmt.Errorf("debit: %w", err)
    }

    if _, err := tx.ExecContext(ctx,
        "UPDATE accounts SET balance = balance + $1 WHERE id = $2", amount, to); err != nil {
        return fmt.Errorf("credit: %w", err)
    }

    if err := tx.Commit(); err != nil {
        return fmt.Errorf("commit: %w", err)
    }
    return nil
}
```

要点：

1. **`defer tx.Rollback()`** 保证任何 return / panic 都回滚。Rollback 在 Commit 之后调是 no-op，安全。
2. **永远传 `ctx`** 给 `BeginTx` / `ExecContext`，链路超时能取消事务。
3. **明确隔离级别**：默认是数据库默认（PG ReadCommitted，MySQL RepeatableRead），生产推荐显式声明。
4. **事务里只做事务的事**：不要在事务中发外部 HTTP 调用、不要 sleep、不要长时间持锁。
5. **错误包装**：用 `%w` 让上层能 `errors.Is`。

**封装 helper**（更通用）：

```go
func WithTx(ctx context.Context, db *sql.DB, fn func(*sql.Tx) error) (err error) {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer func() {
        if p := recover(); p != nil {
            _ = tx.Rollback()
            panic(p)
        }
        if err != nil {
            _ = tx.Rollback()
        } else {
            err = tx.Commit()
        }
    }()
    return fn(tx)
}

// 业务用
err := WithTx(ctx, db, func(tx *sql.Tx) error {
    // ... 多条 SQL
    return nil
})
```

**嵌套事务**：

`database/sql` **不支持真正嵌套**（PostgreSQL/MySQL 都没有 nested transaction），但有 **savepoint** 模拟：

```go
tx.Exec("SAVEPOINT sp1")
// ... 子操作
if err != nil {
    tx.Exec("ROLLBACK TO sp1")
} else {
    tx.Exec("RELEASE SAVEPOINT sp1")
}
```

一些 ORM（sqlx / pgx）封装了 savepoint 自动管理。**反模式**：业务层方法 A 开事务、调 B 也开事务 → 真的开了两个连接的两个事务，互相不可见。正确做法：传 `*sql.Tx`（或定义 `Querier` 接口让 sql.DB / sql.Tx 都满足）。

📎 **深入阅读**: [G29-精通-Go-数据库访问](../G29-精通-Go-数据库访问.md)

**常见追问**：
- Q: 事务隔离级别什么时候用 Serializable？ A: 强一致性要求高的金融场景，但性能损失大，多用 RC + 应用层乐观锁。
- Q: 事务里 read 后再 update 怎么避免覆盖？ A: SELECT FOR UPDATE 加行锁，或者 version 字段乐观锁。
- Q: tx 没 commit 也没 rollback 会怎样？ A: 连接归还池时未提交事务被自动 rollback（PG），但是个坏习惯。

**陷阱**：在事务中调用 `db.Query`（用错对象，没用 tx），SQL 在另一个连接执行，看不到事务里的修改。

### Q15 ⭐⭐⭐ sqlc 的核心思想是什么？

**答**：

**sqlc**（[sqlc.dev](https://sqlc.dev)）的思路简单粗暴：**写 SQL，生成 Go 代码**。

工作流：

1. 写 schema.sql（DDL）
2. 写 query.sql（每条 query 带 `-- name: QueryName :one/:many/:exec` 注释）
3. 跑 `sqlc generate` → 生成强类型 Go 函数

例子：

```sql
-- query.sql
-- name: GetUser :one
SELECT id, name, email FROM users WHERE id = $1;

-- name: ListUsersByOrg :many
SELECT id, name FROM users WHERE org_id = $1 ORDER BY id;

-- name: CreateUser :exec
INSERT INTO users (name, email) VALUES ($1, $2);
```

生成：

```go
type Queries struct { db DBTX }

func (q *Queries) GetUser(ctx context.Context, id int64) (User, error) { ... }
func (q *Queries) ListUsersByOrg(ctx context.Context, orgID int64) ([]User, error) { ... }
func (q *Queries) CreateUser(ctx context.Context, arg CreateUserParams) error { ... }
```

**核心价值**：

1. **Type Safety**：SQL → Go 类型映射在编译期确定，列名打错编译报错。
2. **零 ORM 抽象**：没有 `.Where(...).Order(...).Limit(...)` 链式调用，直接写 SQL，DBA review 友好。
3. **性能**：生成的代码用 `database/sql` 或 pgx，没有反射开销。
4. **可读性**：业务代码 `q.GetUser(ctx, id)`，SQL 在 .sql 文件里集中维护。

**和 ORM (GORM / ent) 的区别**：

| 维度 | ORM | sqlc |
|---|---|---|
| 学习曲线 | DSL 学习 | 会 SQL 就行 |
| 灵活度 | 复杂查询 fallback raw SQL | 100% SQL |
| 性能 | 反射 / 中间层开销 | 接近 raw |
| 重构 | 改 struct 自动迁移 | 改 SQL 后 regenerate |

**适合场景**：

- 团队 SQL 熟练，不想被 ORM 限制
- 查询比较复杂（聚合、CTE、window function）
- 想要 DB schema migration 和代码强同步

**不适合**：

- 多 DB（sqlc 是 driver-specific，主要支持 PG/MySQL/SQLite）
- 极动态查询（query 是文件里写死的）

📎 **深入阅读**: [G29-精通-Go-数据库访问](../G29-精通-Go-数据库访问.md)

**常见追问**：
- Q: sqlc 怎么处理动态 WHERE？ A: 用 `coalesce($1, column)` 或者写多个 query，复杂动态确实是 sqlc 弱项。
- Q: sqlc 和 pgx 怎么配合？ A: sqlc 默认就是 pgx driver，生成的代码已经用 pgx pool。
- Q: schema 迁移用什么？ A: sqlc 不做 migration，搭配 golang-migrate / atlas / goose。

**陷阱**：sqlc 生成的代码默认不能改（再次 generate 覆盖），所有"自定义逻辑"应该在外层 service 包装。

## §4 结构化日志

### Q16 ⭐⭐⭐⭐ slog vs zap vs zerolog 对比

**答**：

三大 Go 结构化日志库，定位有差：

| 维度 | slog (1.21+ stdlib) | zap (uber) | zerolog (rs) |
|---|---|---|---|
| 性能 | 接近 zap | 业内顶尖 | 略高于 zap |
| 零分配 | 大部分场景 | 提供 zero-alloc API (`zap.Field`) | 默认 zero-alloc |
| API 人体工学 | 简洁、官方 | 略繁琐（SugaredLogger 缓解） | 链式调用顺手 |
| Handler 扩展 | 标准接口（slog.Handler） | encoder + core 自定义 | 受限 |
| 标准库集成 | 原生 | 需 adapter | 需 adapter |
| 上下文传递 | `slog.With(key, val)` | `logger.With(zap.String(...))` | `log.With().Str(...).Logger()` |
| trace 集成 | 通过 Handler 注入 | 通过 hook | 通过 hook |

**性能数据**（参考量级，简单字段 + JSON 输出，单位 ns/op）：

```
zerolog       ~40
zap (Field)   ~50
slog          ~80
zap (Sugared) ~180
logrus        ~3000
```

slog 比 zap 慢 1.5x 左右，但是**标准库**，开箱即用，没有第三方依赖：

```go
import "log/slog"

logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
    Level: slog.LevelDebug,
}))
slog.SetDefault(logger)

slog.Info("user created", "uid", 42, "name", "alice")
// {"time":"2026-05-...","level":"INFO","msg":"user created","uid":42,"name":"alice"}

// 带上下文的 child logger
log := logger.With("trace_id", "abc123", "service", "api")
log.Info("processing")
```

**选型建议**：

- **新项目 / 不追求极致性能**：直接用 slog，没有依赖、API 标准化
- **超高 QPS / 日志成本敏感**：zap 或 zerolog
- **已有项目 zap / logrus**：保持不动，可以用 `slog-zap` adapter 桥接到 slog 接口

**slog 的关键设计**：

1. **Attr 而非 map**：`slog.Int("k", 1)` 避免 interface boxing。
2. **Handler 抽象**：JSON / Text / 自定义都通过 Handler 实现，可叠加（多目的地）。
3. **Group**：`slog.Group("user", "id", 1, "name", "x")` 输出 nested JSON。
4. **LogValuer 接口**：自定义类型实现 `LogValue() slog.Value` 控制序列化。

**常见追问**：
- Q: slog 比 zap 慢能接受吗？ A: 日均日志 < 10w 条/服务 完全不感知；超高 QPS（>10k/s）才看得出差距。

### Q17 ⭐⭐⭐ 怎么把日志和 trace_id 关联？

**答**：

**目标**：分布式 trace 的每个 span 产生的日志都能带上 `trace_id` / `span_id`，便于在 Jaeger/Tempo 等 trace 系统点击跳到 Loki/ES 看完整日志。

**OpenTelemetry 集成思路**：

1. **入口注入**：每个请求/事件，在 OTel SDK 创建 span 时把 `trace_id` 写入 `context.Context`。
2. **logger 从 ctx 取值**：日志库的 Handler 在每条 log 输出时从 ctx 取 trace_id 加到 fields。
3. **传播**：跨服务调用时，OTel 的 propagator 自动通过 HTTP header (`traceparent`) / gRPC metadata 透传。

**slog 实现**：

```go
type TraceHandler struct{ slog.Handler }

func (h TraceHandler) Handle(ctx context.Context, r slog.Record) error {
    if span := trace.SpanFromContext(ctx); span.SpanContext().IsValid() {
        r.AddAttrs(
            slog.String("trace_id", span.SpanContext().TraceID().String()),
            slog.String("span_id", span.SpanContext().SpanID().String()),
        )
    }
    return h.Handler.Handle(ctx, r)
}

logger := slog.New(TraceHandler{slog.NewJSONHandler(os.Stdout, nil)})
slog.SetDefault(logger)

// 业务代码（必须用 InfoCtx 等带 ctx 的 API）
slog.InfoContext(ctx, "processing", "uid", 42)
// 输出: {"msg":"processing","trace_id":"4bf92f...","span_id":"00f06...","uid":42}
```

**zap 实现**：用 `zap.Field` + custom logger wrapper：

```go
func LoggerFromCtx(ctx context.Context) *zap.Logger {
    fields := []zap.Field{}
    if span := trace.SpanFromContext(ctx); span.SpanContext().IsValid() {
        fields = append(fields,
            zap.String("trace_id", span.SpanContext().TraceID().String()),
            zap.String("span_id", span.SpanContext().SpanID().String()),
        )
    }
    return baseLogger.With(fields...)
}
```

**`otelslog` 现成包**（Go 1.21+）：[`go.opentelemetry.io/contrib/bridges/otelslog`](https://pkg.go.dev/go.opentelemetry.io/contrib/bridges/otelslog) 直接提供 handler，省去手写。

**关键约束**：

- 业务必须用 `slog.XxxContext(ctx, ...)`（带 ctx 的方法），否则 handler 拿不到 trace。
- middleware 必须在 ctx 上下文用 OTel 注入 span，否则 SpanContext 是 invalid。

📎 **深入阅读**: [G30-精通-Go-结构化日志](../G30-精通-Go-结构化日志.md)

**常见追问**：
- Q: 日志和 metric 怎么关联到 trace？ A: metric 上报 exemplar（OTel 1.0+ 支持），exemplar 带 trace_id。
- Q: trace_id 标准是什么？ A: W3C Trace Context: `traceparent: 00-<trace-id>-<span-id>-<flags>`。
- Q: 同一个 span 多条 log 怎么排序？ A: 看时间戳；同一个 service 内通常 monotonic，跨服务靠 trace 视图。

**陷阱**：忘了用 `InfoContext` / `ErrorContext`，依然调 `slog.Info(...)`，trace_id 注入失败但报错不明显。

### Q18 ⭐⭐⭐⭐ 日志采样的几种策略

**答**：

为什么要采样：高 QPS 服务全量日志成本（存储 + 检索）爆炸，但每条都丢又会漏问题。常见策略：

**1. 按级别采样**

```
ERROR / WARN：100% 不采样（罕见，全部留）
INFO：10% 采样
DEBUG：1% 采样或线上关掉
```

实现：handler 在 emit 前掷骰子：

```go
type LevelSampler struct{ slog.Handler; rate map[slog.Level]float64 }

func (s LevelSampler) Handle(ctx context.Context, r slog.Record) error {
    rate, ok := s.rate[r.Level]
    if ok && rand.Float64() > rate {
        return nil // 丢弃
    }
    return s.Handler.Handle(ctx, r)
}
```

**2. 按 QPS 采样（Tail-based）**

每秒第 1-N 条全留，第 N+1 条开始按比例采样。zap 的 `Sampler` 就是这种：

```go
core := zapcore.NewSamplerWithOptions(baseCore,
    time.Second, // 时间窗口
    100,         // 前 100 条全留
    100)         // 之后每 100 条留 1 条
```

效果：突发流量峰值的日志被压平，但不会完全丢；常规情况几乎全留。

**3. 头部 / 尾部采样（基于 trace）**

**头部采样**：在请求入口决定是否记录整条 trace 的日志（一般 1%-10%），决定后整条链路统一记录。简单但可能漏 anomaly。

**尾部采样**：先收集所有 trace，请求结束后根据条件（耗时 > 1s、出现 error、status >= 500）决定是否保留。能精准保留有意义的日志，但需要中转聚合（OTel Collector 的 tail sampling processor）。

**4. 错误优先采样**

任何 request 出现 error / panic → 该 request 的所有日志（debug/info 也）全部保留；正常 request 大幅采样。需要在 request scope 缓存日志，结束时决定提交还是丢弃。

**5. 配额型**

每个 service / endpoint 给定每秒日志数额度，超出按比例丢。

**生产组合**：

- **入口标记**：请求 ctx 注入 `sampled` 标志
- **error / 慢请求强制留**：handler 检查 ctx 是否标记为 force-keep
- **常规按级别 + zap.Sampler 限流**
- **采集端二次处理**：OTel Collector 的 sampling processor 集中策略

📎 **深入阅读**: [G30-精通-Go-结构化日志](../G30-精通-Go-结构化日志.md)

**常见追问**：
- Q: 采样后调试找不到日志怎么办？ A: 出 incident 时可以临时调整采样率到 100%，或在 trace 头标记强制保留。
- Q: 不采样会怎样？ A: Loki / ES 存储成本随 QPS 线性增长；查询性能也下降。
- Q: 怎么验证采样实现正确？ A: 对照采样前后的日志总量 / 错误日志数量，确认错误没被采掉。

**陷阱**：采样规则把 ERROR 也按比例丢——线上看不到错误，等 SLO 报警才发现。ERROR 永远 100% 留。

## §5 CGO

### Q19 ⭐⭐⭐⭐ CGO 调用开销为什么大？Go 1.26 -30% 改善了什么？

**答**：

CGO 单次调用开销在 Go 1.25 大约 **200ns**（M1/AMD64 实测），Go 1.26 优化后降到 **~140ns**。比起纯 Go 函数（~1-2ns）依然贵 100 倍以上。

**开销来源**：

1. **栈切换**：Go 的 goroutine 栈是分段 / 可增长的小栈（初始 2KB），C 函数需要稳定的大栈。每次 CGO 调用要切换到 M 上的系统栈（`g0.stack`）执行，调用结束切回。
2. **TLS 设置**：C 库可能依赖 thread-local storage（errno、libc 状态），Go runtime 要保证 TLS 正确。
3. **信号屏蔽**：CGO 调用期间 Go runtime 抢占器不能直接抢占（C 代码不可中断），需要屏蔽并发抢占信号。
4. **scheduler 协作**：M 进入 syscall-like 状态，P 可能 handoff 给其他 M 跑 Go 代码（避免阻塞调度）。
5. **参数 marshal**：Go ↔ C 的指针类型、字符串、slice 转换有额外检查。

**Go 1.26 优化**（约 30% 提升）：

- **简化栈切换路径**：去除部分冗余的 g 状态切换
- **更轻量的 cgo prologue**：以前每次都执行一遍完整的 `cgocall` 包装，新版对简单 C 函数走 fast path
- **TLS 设置优化**：对部分平台 TLS 访问减少一次间接

**实践含义**：

- 单次调用从 200ns 降到 140ns，对热路径 CGO（如 SQLite、libxml、加密库）累计收益可观。
- **但仍不便宜**：每秒 100 万次 CGO = 200ms（旧）→ 140ms（新）纯 overhead。
- **不要在 hot loop 里 fine-grained CGO**：把多次 C 调用聚合成一次大调用（batch API），开销摊薄。

**对比**：

| 操作 | 大约耗时 |
|---|---|
| Go 函数调用 | 1-2 ns |
| Go interface dispatch | 3-5 ns |
| channel send/recv（无竞争） | 30-100 ns |
| Mutex Lock/Unlock | 20-50 ns |
| **CGO 调用 (1.25)** | **200 ns** |
| **CGO 调用 (1.26)** | **140 ns** |
| syscall（Linux） | 100-200 ns |

📎 **深入阅读**: [G26-精通-Go-CGO](../G26-精通-Go-CGO.md)

**常见追问**：
- Q: Go 1.26 之后还有进一步优化空间吗？ A: 有提案讨论"linkonce CGO"对简单签名做内联，但生态影响大，未确定。
- Q: 怎么测自己代码的 CGO 开销？ A: pprof CPU profile 里看 `runtime.cgocall` 总占比。
- Q: 用 cgo 跟用 syscall 哪个开销低？ A: syscall 通常更低（无栈切换），但 cgo 能用现成 C 库，trade-off。

**陷阱**：用 CGO 调 trivial 函数（比如简单数学运算），benchmark 时纯 Go 还更快。

### Q20 ⭐⭐⭐⭐⭐ CGO 内存所有权：C 分配 vs Go 分配，传指针怎么注意？

**答**：

CGO 内存管理是 CGO 最容易出 bug 的地方，规则如下：

**1. 谁分配谁释放**

- **C 分配的内存**（`C.malloc` / 库内部 alloc）→ 必须 C 释放（`C.free` 或对应库的 free 函数）。
- **Go 分配的内存**（`make`、字面量）→ GC 自动管理，但**不能让 C 代码长期持有指针**。

```go
// C 分配
p := C.malloc(100)
defer C.free(p)
// ... 用 p

// Go → C: 复制成 C 内存
goStr := "hello"
cStr := C.CString(goStr) // 内部 C.malloc + memcpy
defer C.free(unsafe.Pointer(cStr))
C.do_something(cStr)
```

**2. Go 指针传给 C 的规则**（cgo rule）

CGO 规则 #1：**Go 代码可以把 Go 指针传给 C 函数，但 C 代码不能在调用返回后保留该指针**。

```go
// ✅ 同步调用：C 用完就还
data := []byte{1, 2, 3}
C.process(unsafe.Pointer(&data[0]), C.int(len(data)))
// C.process 返回后，data 可以被 GC 移动 / 回收，但 C 已经用完了，安全
```

```c
// ❌ C 端保存了 Go 指针
static void* saved;
void process(void* p, int n) {
    saved = p; // ❌ Go GC 可能移动 / 回收，下次访问 saved 崩溃
}
```

**3. Go 指针中不能包含 Go 指针**

`C.foo(ptr)` 时 `ptr` 不能间接指向另一个 Go 指针。例如：

```go
type Inner struct{ x int }
type Outer struct{ p *Inner }

o := &Outer{p: &Inner{}}
C.bar(unsafe.Pointer(o)) // ❌ o 是 Go 指针，且 o.p 也是 Go 指针，违反规则
```

CGO 启动时 `GODEBUG=cgocheck=1`（默认开启，性能开销小）会检测此类违规，panic。

**4. 长期共享内存：用 C 分配**

如果 C 端需要长期持有，就让 C 端分配：

```go
buf := C.malloc(C.size_t(size))
defer C.free(buf)
C.register_buffer(buf, C.size_t(size)) // C 可以长期持有
```

**5. Pinning（Go 1.21+ runtime.Pinner）**

如果必须让 C 长期持有 Go 内存，用 `runtime.Pinner`：

```go
data := make([]byte, 1024)

var pinner runtime.Pinner
pinner.Pin(&data[0])
defer pinner.Unpin()

C.register_buffer(unsafe.Pointer(&data[0]), C.int(len(data)))
// data[0] 被 pin 住，GC 不会移动；C 端可以长期持有
```

**调试工具**：

- `GODEBUG=cgocheck=2` 启用更严格检查（性能开销大，仅 debug）
- `go build -race` race detector 也能发现部分 CGO 内存竞争

📎 **深入阅读**: [G26-精通-Go-CGO](../G26-精通-Go-CGO.md)

**常见追问**：
- Q: `C.CString` 为什么要 free？ A: 内部 `C.malloc`，Go GC 不管。
- Q: Go GC 真的会移动堆对象吗？ A: 当前 Go 的 GC 不移动对象（non-moving GC），但官方保留权利，所以规则按"可能移动"写。
- Q: cgo.Handle 是干嘛的？ A: 1.17+ 提供，传 Go 对象给 C 不用裸指针，用整数 handle 反查 Go 对象，规避指针规则。

**陷阱**：用 `unsafe.Pointer(&slice[0])` 传给 C，C 端保存指针；slice 在 Go 端被 append 触发扩容（底层数组换地址），C 端持有的指针变成野指针。

### Q21 ⭐⭐⭐⭐ runtime.Pinner（Go 1.21+）解决了什么问题？

**答**：

**问题背景**：

CGO 规则禁止 C 长期持有 Go 指针，因为 Go GC 在未来可能移动对象（虽然当前实现不移动）。但是有些场景必须让 C 端持有 Go 内存：

- **回调注册**：C 库要求传入回调函数 + user_data（指针），异步调用回回调。user_data 如果是 Go 对象，没法用。
- **零拷贝共享**：大 buffer 让 C 复用 Go 分配的内存，复制一遍代价大。
- **C 端构建数据结构指向 Go**：图形 API 把 Go vertex buffer 注册到 GPU。

**1.21 之前的解法**：

1. **复制到 C 内存**：`C.malloc` + `memcpy`，简单但有拷贝开销。
2. **`runtime.KeepAlive`**：只防 GC 回收，不防移动；调用周期短时勉强用，长持有不行。
3. **`cgo.Handle`**：1.17+ 提供，把 Go 对象注册到全局 map 拿到 `uintptr` handle，C 端持有 handle，回调时反查。但需要每次访问转换 + 全局 map 锁。

**1.21 引入 `runtime.Pinner`**：

```go
var pinner runtime.Pinner
defer pinner.Unpin() // 函数结束统一 unpin

data := make([]byte, 1024)
pinner.Pin(&data[0]) // 这块内存被 pin

// 现在可以安全地把 &data[0] 长期传给 C
C.register_buffer(unsafe.Pointer(&data[0]), C.int(len(data)))

// ... 长期使用 ...

// pinner.Unpin() 在 defer 中调用，data 重新参与 GC
```

**效果**：

- pin 住的对象 GC 不会移动（虽然现在不移动，但未来 moving GC 启用时也安全）
- 可以包含 Go 指针（绕过 CGO rule #1 的某些限制）
- 性能：Pin 操作约 50ns 量级，Unpin 类似；不影响其他 GC 行为
- 单个 Pinner 可以 pin 多个对象，Unpin 一次性释放

**典型场景**：

```go
type Callback struct {
    Done chan error
}

//export goCallback
func goCallback(userData unsafe.Pointer, status C.int) {
    cb := (*Callback)(userData)
    if status == 0 {
        cb.Done <- nil
    } else {
        cb.Done <- fmt.Errorf("err %d", status)
    }
}

func AsyncCall(ctx context.Context) error {
    cb := &Callback{Done: make(chan error, 1)}
    var pinner runtime.Pinner
    pinner.Pin(cb)
    defer pinner.Unpin()

    C.start_async(C.callback_t(C.goCallback), unsafe.Pointer(cb))

    select {
    case err := <-cb.Done:
        return err
    case <-ctx.Done():
        return ctx.Err()
    }
}
```

**vs cgo.Handle 对比**：

| 维度 | runtime.Pinner | cgo.Handle |
|---|---|---|
| 引入版本 | 1.21 | 1.17 |
| 性能 | Pin/Unpin 各 ~50ns | 注册/查询全局 map，更慢 |
| C 端拿到 | 真实指针，可解引用 Go 内存 | 整数 handle，需 callback 到 Go 查 |
| 适用 | 共享内存、回调 | 跨语言对象引用 |

📎 **深入阅读**: [G26-精通-Go-CGO](../G26-精通-Go-CGO.md)

**常见追问**：
- Q: Pinner 能 pin 多大的对象？ A: 没有 size 限制，单个对象一次 Pin 即可；多个对象多次 Pin 累加。
- Q: 未 Unpin 会泄漏吗？ A: 是的，pin 的对象 GC 不回收；务必 defer Unpin。
- Q: Pin 期间对象能被修改吗？ A: 可以，Pin 只防止移动 / 回收，不是只读锁。

**陷阱**：以为 Pin 之后可以随便给 C，但如果对象本身**包含 Go 指针字段**（如 string、slice header）那些内部指针没被 pin，CGO check 还是会报错。

## §6 部署与运维

### Q22 ⭐⭐⭐⭐ 容器化 Go 服务的常见坑

**答**：

**1. GOMAXPROCS 误认核数（Go 1.25 已修）**

老问题：容器限制 2 个 CPU（CFS quota），但 Go 1.24 之前 `GOMAXPROCS` 默认读 `runtime.NumCPU()`（看到的是宿主机核数，如 32）。结果：

- 调度器把 G 撒到 32 个 P
- 实际只有 2 个 CPU quota，被 throttle
- 大量 P 抢 CPU 引发 latency spike

**1.25 修复**：runtime 自动读 cgroup v2 的 CPU quota，正确算出有效核数（`ceil(quota / period)`）。

**老版本绕过**：用 [`automaxprocs`](https://github.com/uber-go/automaxprocs) 库，import 时自动设置：

```go
import _ "go.uber.org/automaxprocs"
```

**2. scratch / distroless 镜像缺 CA 证书**

```dockerfile
FROM scratch
COPY app /app
ENTRYPOINT ["/app"]
```

跑起来调 HTTPS 报：`x509: certificate signed by unknown authority` —— scratch 镜像没有任何 CA bundle。

**解法**：

```dockerfile
FROM alpine:latest AS certs
RUN apk add --no-cache ca-certificates

FROM scratch
COPY --from=certs /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY app /app
ENTRYPOINT ["/app"]
```

或者用 distroless（已带 CA + tzdata）：`gcr.io/distroless/static-debian12`。

**3. glibc / musl 不一致**

宿主或 builder 用 glibc（Ubuntu / Debian），目标镜像用 alpine（musl）→ CGO 二进制起不来：

```
not found
ld-linux.so.2 not found
```

**解法**：

- 纯 Go 程序：`CGO_ENABLED=0` 静态编译，不依赖 libc
- 必须 CGO：builder 也用 alpine 或者用 `golang:alpine` 镜像编译

**4. 时区缺失**

scratch / distroless static 镜像没有 tzdata，`time.LoadLocation("Asia/Shanghai")` 返回 error。

**解法**：

- Go 1.15+ 内嵌 tzdata：`import _ "time/tzdata"`
- 或镜像 COPY tzdata 文件

**5. /tmp 满**

某些镜像 `/tmp` 是 tmpfs（小），大文件下载 / DB driver 临时文件爆。
**解法**：挂卷或换路径。

**6. signal 处理 + PID 1**

容器内进程是 PID 1，没有 init 处理僵尸进程；CGO/exec 子进程可能成为僵尸。Go 服务自己一般不开子进程，问题不大。但 `kill -TERM` 等信号必须自己处理（默认 Go runtime 收信号不退出？实际 SIGINT/TERM 默认会终止程序，但应用层应主动 signal.Notify 做 graceful shutdown）。

**7. 文件描述符限制**

容器默认 ulimit 可能很低（如 1024），高 QPS 服务（连接 + DB 池 + http client 池）一会就爆。

**解法**：

- k8s spec 里调 `securityContext`
- 服务启动时 `syscall.Setrlimit` 自调

📎 **深入阅读**: [G27-精通-Go-net-http](../G27-精通-Go-net-http.md)

**常见追问**：
- Q: 1.25 之前 GOMAXPROCS 怎么显式设？ A: 环境变量 `GOMAXPROCS=2` 或 `runtime.GOMAXPROCS(2)`，automaxprocs 自动读 cgroup。
- Q: alpine vs distroless 怎么选？ A: alpine 小（5MB）但 musl 可能跟 glibc 行为有差异；distroless 稳定但稍大。
- Q: 静态二进制启动比动态快多少？ A: 几毫秒级别，差距不大；主要价值是部署简单、镜像小。

**陷阱**：以为 1.25 升级后就不用 automaxprocs 了——cgroup v1 + 老内核场景还是可能识别失败，automaxprocs 兜底更稳。

### Q23 ⭐⭐⭐⭐ Go 服务 OOM 怎么排查？GOMEMLIMIT 怎么用？

**答**：

**OOM 流程**：

1. **确认是 Go 进程被 kill**：`dmesg | grep -i oom`，看 oom-killer 杀的是不是 Go 进程。
2. **看曲线**：监控里 RSS 是缓慢增长还是突涨。
3. **拿 heap profile**：`/debug/pprof/heap` 或服务挂前自动 dump 到文件。

**heap profile 分析**：

```bash
go tool pprof http://localhost:6060/debug/pprof/heap
(pprof) top
(pprof) list <FunctionName>
(pprof) web   # 图形化
```

关注：

- `inuse_space`：当前活跃内存（推荐 OOM 排查用）
- `alloc_space`：累计分配（找分配热点）
- 哪个调用栈占大头？是否预期？

**常见 OOM 原因**：

1. **大 slice / map 缓存无淘汰**：缓存只塞不清。
2. **goroutine 泄漏**：goroutine 持有 stack + 局部变量。
3. **大 buffer 未释放**：HTTP body、文件读取一次性 ReadAll 大文件。
4. **string 滥用**：日志拼接超大字符串。
5. **CGO 内存泄漏**：C.malloc 后忘记 C.free。Go 的 heap profile 看不到 C 内存。
6. **GC 滞后**：低优先级 GC 在 burst 时来不及，瞬间 RSS 飙到 limit 触发 OOMKill。

**GOMEMLIMIT 是什么**：

Go 1.19+ 引入 `GOMEMLIMIT`（环境变量或 `debug.SetMemoryLimit`），给 runtime 一个软上限：

- runtime 看到 RSS 接近 limit 时主动触发 GC（不再等到 GOGC 比例触发）
- 防止"runtime 还没意识到要 GC 就被 kernel OOMKill"

**配置**：

```bash
GOMEMLIMIT=1800MiB  # 略小于 cgroup limit 的 90%
GOGC=100            # 默认值，让 GC 按比例 trigger；GOMEMLIMIT 兜底
```

**注意**：

1. **GOMEMLIMIT 不是 hard cap**，runtime 尽力但不保证不超。Go 会调高 GC 频率（占用更多 CPU），但如果 live set 真的超过 limit，依然会 OOM。
2. **配 cgroup limit 时 GOMEMLIMIT 要小于它**（一般 90%），留 buffer 给非 heap 内存（stack、CGO、内核态）。
3. **1.26 Green Tea GC** 在 GOMEMLIMIT 触发时的 CPU 占用比 1.25 少 30%，降低了"接近 limit 时 GC 抖动"的痛感。

**heap profile 周期性自动 dump**（便于 post-mortem）：

```go
import _ "net/http/pprof"
go http.ListenAndServe(":6060", nil)

// 或者：每分钟 dump 一次到磁盘
go func() {
    for range time.Tick(time.Minute) {
        f, _ := os.Create(fmt.Sprintf("/tmp/heap-%d.pb", time.Now().Unix()))
        pprof.WriteHeapProfile(f)
        f.Close()
    }
}()
```

**1.26 goroutineleak profile**：直接报告活跃 goroutine 数 + 堆栈分布，找 goroutine 泄漏特别方便。

📎 **深入阅读**: [G22-精通-Go-pprof-性能剖析](../G22-精通-Go-pprof-性能剖析.md)

**常见追问**：
- Q: GOGC 和 GOMEMLIMIT 同时设怎么生效？ A: 两者取触发条件更早的：GOGC 按 heap 增长比例，GOMEMLIMIT 按绝对内存。先到先 GC。
- Q: 怎么区分内存涨是泄漏还是高负载？ A: live set 持续增长不回落 = 泄漏；峰谷有起伏 = 负载。
- Q: heap profile 没看到的内存去哪了？ A: stack、CGO（C.malloc）、mmap（runtime 直接管理）。`runtime.ReadMemStats` 看 sys 总量。

**陷阱**：GOMEMLIMIT 设得太接近 cgroup limit（如 99%），瞬间分配突发依然 OOMKill；留 10-20% 余量。

### Q24 ⭐⭐⭐ build 优化的常用参数

**答**：

**核心三件套**：

```bash
CGO_ENABLED=0 go build -ldflags="-s -w" -trimpath -o app .
```

**`-ldflags="-s -w"`**：

- `-s`：strip 符号表
- `-w`：strip DWARF 调试信息
- 效果：二进制小 25-40%，无法 `go tool pprof` symbolize / `dlv` 调试
- 生产推荐：开启（小镜像、防泄漏内部符号）；debug 镜像不开

**`-trimpath`**：

- 编译时把绝对路径（`/home/user/project/...`）替换成 module path（`example.com/foo/...`）
- 好处：跨机器编译产物 deterministic，不泄漏 builder 路径
- 1.13+ 标准支持

**`CGO_ENABLED=0`**：

- 关闭 CGO，所有依赖纯 Go 实现
- 优点：静态链接，可塞 scratch 镜像，跨平台编译方便
- 缺点：用不了 sqlite3、glibc 优化、某些 cgo-only 库

**版本 / 构建信息嵌入**：

```bash
go build -ldflags "\
  -X main.Version=v1.2.3 \
  -X main.Commit=$(git rev-parse HEAD) \
  -X main.BuildTime=$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  -o app .
```

```go
// main.go
var (
    Version   = "dev"
    Commit    = "none"
    BuildTime = "unknown"
)
```

Go 1.18+ 内置 `runtime/debug.ReadBuildInfo()`，能拿到 VCS 信息（commit hash、dirty 标志）不用再手动 -X：

```go
info, _ := debug.ReadBuildInfo()
for _, s := range info.Settings {
    if s.Key == "vcs.revision" {
        commit = s.Value
    }
}
```

**其他常用**：

| 参数 | 用途 |
|---|---|
| `-race` | 启用 race detector（dev/test 用，生产慢 2-10x） |
| `-buildmode=pie` | 位置无关可执行文件（安全加固） |
| `-tags` | build constraint（如 `-tags "production"`） |
| `-mod=vendor` | 用 vendor 目录而非 module cache |
| `-buildvcs=false` | 不嵌入 VCS 信息（构建确定性） |
| `-gcflags="all=-l"` | 关闭内联（profile 调试用） |
| `-asmflags` | 汇编器参数 |

**多阶段 Dockerfile 例子**：

```dockerfile
FROM golang:1.26-alpine AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build \
    -ldflags="-s -w -X main.Version=$(git describe --tags)" \
    -trimpath \
    -o /out/app .

FROM gcr.io/distroless/static-debian12
COPY --from=builder /out/app /app
ENTRYPOINT ["/app"]
```

结果二进制几 MB，镜像 < 20MB。

📎 **深入阅读**: [G17-精通-Go-Modules](../G17-精通-Go-Modules.md)

**常见追问**：
- Q: -s -w 之后还能拿 stack trace 吗？ A: 能拿到函数名（PC 表保留），但行号信息丢失（无 DWARF）。
- Q: -trimpath 影响 go.sum？ A: 不影响。
- Q: 怎么生成最小镜像？ A: scratch + 静态二进制 + 必要 CA + tzdata，可到 5-8MB。

**陷阱**：CGO_ENABLED=0 默认是 1（如果系统有 C 工具链），跨平台编译时忘了设可能导致依赖 glibc，目标镜像跑不起来。

## 速记表

### http 四超时速查

| 字段 | 阶段 | 推荐值 | 关键风险 |
|---|---|---|---|
| `ReadHeaderTimeout` | 读完 header | 5s | Slowloris 攻击 |
| `ReadTimeout` | 读完 header + body | 30s | 慢上传攻击 |
| `WriteTimeout` | 开始写 → 写完 | 30s | 客户端慢读 |
| `IdleTimeout` | keep-alive 空闲 | 120s | 闲置连接堆积 |
| `MaxHeaderBytes` | header 总大小 | 1MB | 超大 header DoS |

### gRPC RPC 模式速查

| 模式 | proto 语法 | 场景 |
|---|---|---|
| Unary | `(Req) returns (Resp)` | 普通 RPC，类似 REST |
| Server stream | `(Req) returns (stream Resp)` | 大结果分批、订阅推送 |
| Client stream | `(stream Req) returns (Resp)` | 批量上传、聚合 |
| Bidi stream | `(stream Req) returns (stream Resp)` | 聊天、双向同步 |

### gRPC 常用 status code 速查

| Code | 何时用 | 重试 |
|---|---|---|
| `InvalidArgument` | 参数错误 | 否 |
| `NotFound` | 资源不存在 | 否 |
| `AlreadyExists` | 创建冲突 | 否 |
| `PermissionDenied` | 无权限 | 否 |
| `Unauthenticated` | token 无效 | 否 |
| `ResourceExhausted` | 限流 / 配额 | 是（带退避） |
| `FailedPrecondition` | 状态机不允许 | 否 |
| `Aborted` | 乐观锁冲突 | 是 |
| `DeadlineExceeded` | 超时 | 视情况 |
| `Unavailable` | 服务不可用 | **是** |
| `Internal` | 内部错误 | 否 |
| `Unimplemented` | 未实现 | 否 |

### 数据库连接池速查

| 配置 | 默认 | 生产推荐 |
|---|---|---|
| `MaxOpenConns` | 0（无限） | 服务实例数 × MaxOpen < DB max_connections × 0.8 |
| `MaxIdleConns` | 2 | MaxOpen 的 20-50% |
| `ConnMaxLifetime` | 0（永久） | 30 分钟 |
| `ConnMaxIdleTime` | 0（永久） | 5 分钟 |

### 日志库速查

| 库 | 性能（ns/op 量级） | 标准库 | 主要优点 |
|---|---|---|---|
| `log/slog` | ~80 | ✅ | 官方、零依赖、Handler 抽象 |
| `zap` | ~50 (Field) / ~180 (Sugared) | ❌ | 业内最强性能 |
| `zerolog` | ~40 | ❌ | 默认 zero-alloc，链式 API 顺手 |
| `logrus` | ~3000 | ❌ | 历史老牌，新项目不推荐 |

### CGO 开销速查

| 操作 | 量级 |
|---|---|
| Go 函数调用 | 1-2 ns |
| Mutex Lock/Unlock | 20-50 ns |
| **CGO 调用 (1.26)** | **~140 ns** |
| **CGO 调用 (1.25)** | **~200 ns** |
| syscall (Linux) | 100-200 ns |

### 容器化关键开关速查

| 问题 | 解法 |
|---|---|
| GOMAXPROCS 看不准 | Go 1.25+ 自动；老版本用 automaxprocs |
| 容器无 CA 证书 | distroless/static 或 COPY ca-certificates |
| 容器无 tzdata | `import _ "time/tzdata"` |
| OOMKill 频繁 | 设 `GOMEMLIMIT < cgroup limit × 90%` |
| 二进制太大 | `-ldflags="-s -w" -trimpath` |
| 跨平台编译报错 | `CGO_ENABLED=0` |

## 高频陷阱清单

1. **http.Server 不设超时** → Slowloris 攻击 / FD 耗尽。默认 0 等于无限制，生产必设四超时。

2. **http.Client 每次 new** → Transport 不复用，连接池失效，每请求一次 TCP+TLS。Client 应进程级单例。

3. **http response Body 没读完就 Close** → 连接无法复用，悄悄当成短连接，性能 -50%。`defer io.Copy(io.Discard, resp.Body)` 兜底。

4. **DefaultTransport.MaxIdleConnsPerHost=2** → 高 QPS 同域名调用大部分新建连接。务必显式配置 ≥20。

5. **graceful shutdown 不传 ctx 超时** → 慢请求让服务永远停不下来。`Shutdown(ctx)` 必须带 deadline。

6. **gRPC stream 忘记 CloseSend** → server `Recv()` 永不返回 EOF，goroutine 泄漏。

7. **gRPC interceptor 顺序** → panic recover 必须在 chain 最外层，否则后面 interceptor panic 漏掉。

8. **gRPC 业务错误用 Internal** → 客户端会重试（认为是 server bug），应该用 `FailedPrecondition` 或 details。

9. **proto 字段编号复用 / required 字段** → 永远不兼容，新老版本相互崩。删字段一律 `reserved`。

10. **database/sql MaxIdleConns 用默认 2** → QPS 一上来全部新建连接，TLS 握手延迟暴增。设 ≥ MaxOpen 的 20%。

11. **连接 ConnMaxLifetime 不设** → 云 DB / LB 静悄悄把空闲连接 reset，下次用报 connection reset by peer。

12. **for 循环里查 DB / RPC** → 经典 N+1，性能跟数据量线性下降。批量查询 + groupBy 拼回。

13. **事务里调外部 HTTP / 等慢操作** → 长持连接 + 长持锁，DB 连接池被打满。事务里只做事务的事。

14. **采样规则把 ERROR 也丢** → 线上没错误日志，事故后无法回溯。ERROR / WARN 永远 100% 留。

15. **slog 用了但忘 `slog.SetDefault`** → 包级 `slog.Info` 走默认 text handler，格式跟项目其他日志不一致。

16. **CGO 把 Go 指针长期保存到 C 端** → 违反 cgocheck，panic；或 Go GC 回收后 use-after-free。用 `runtime.Pinner` 或 `cgo.Handle`。

17. **CGO 用 C.CString 忘 C.free** → 经典 C 端内存泄漏，Go heap profile 看不到。

18. **scratch 镜像没 CA 证书** → HTTPS 请求 `x509: certificate signed by unknown authority`。COPY 一份 ca-certificates。

19. **time.LoadLocation("Asia/Shanghai") 报错** → distroless/static 无 tzdata。`import _ "time/tzdata"` 嵌入。

20. **GOMEMLIMIT 设到 cgroup limit 的 99%** → 突发分配依然 OOMKill。留 10-20% buffer。

21. **`-ldflags="-s -w"` 后还想 pprof 拿行号** → DWARF 已 strip，行号丢失，只剩函数名。生产+debug 双镜像策略。

22. **CGO 在 hot path 频繁调用** → 200ns/次（1.26 降到 140ns）但 1M QPS 累计 100ms+ 纯 overhead。聚合成批调用。
