## §1 Benchmark

### Q1 ⭐⭐⭐⭐ testing.B 的 b.N 是怎么决定的？为什么 benchmark 要循环 b.N 次

**答**：

`testing.B` 的核心思路是**让被测函数运行足够长的时间，使时间测量误差可忽略**。框架并不预先知道函数有多快，所以采用「逐步逼近」算法：

1. 首次调用 `f(b)` 时 `b.N = 1`，跑一次记录耗时；
2. 根据当前耗时估算需要多少次循环才能跑满 `-benchtime`（默认 1s）；
3. 把 `b.N` 按几何级数（×100 上限、向上取整到 1、2、3、5 序列）放大，重新跑一遍；
4. 重复直到累计耗时 ≥ benchtime，最终汇报 `ns/op = 总耗时 / b.N`。

所以**用户写的代码必须是 `for i := 0; i < b.N; i++ { ... }` 的循环**——框架要靠这个循环来控制采样次数。如果只跑一次，单次测量包含调度、缓存预热、CPU 频率波动等噪声，结果毫无意义。

```go
func BenchmarkFoo(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Foo()
    }
}
```

Go 1.24 起新增 `for b.Loop() { ... }` 写法，框架自动管理迭代次数，并且**保证 `b.Loop()` 内部的变量不会被编译器消除**（解决了 Q2 的痛点）。生产代码推荐用新写法。

📎 **深入阅读**: [G19-精通-Go-Benchmarking](../G19-精通-Go-Benchmarking.md)

**常见追问**：
- Q: `-benchtime=10x` 是什么含义？  A: 强制循环 10 次（而非按时间），用于固定负载对比。
- Q: 多次跑结果差别大怎么办？  A: 加 `-count=10` + benchstat 做统计检验，关闭 turbo / 固定 CPU。
- Q: `b.Loop()` 和 `b.N` 循环底层区别？  A: `b.Loop()` 内联了 KeepAlive 语义，循环体的输入输出参数都被视为「活跃」，不会被 DCE。

**陷阱**：在 `b.N` 循环外做的初始化（如建表）必须在 `b.ResetTimer()` 之后才不会被计入；新版本 `b.Loop()` 则会自动忽略循环外的耗时。

### Q2 ⭐⭐⭐⭐⭐ 防止编译器消除（dead code elimination）：runtime.KeepAlive、写到包级 sink 变量、b.ResetTimer 等技巧

**答**：

Go 编译器会做激进的死代码消除：如果一个函数的返回值未被使用、且函数本身无副作用，**整个调用都可能被优化掉**。这会让 benchmark 测出 0.5ns/op 之类的"假极速"。常见对抗技巧：

**1) 包级 sink 变量**：把结果赋值给一个外部变量，编译器无法证明该变量不会被读，于是保留计算。

```go
var sinkInt int
var sinkStr string

func BenchmarkHash(b *testing.B) {
    var local int
    for i := 0; i < b.N; i++ {
        local = hash("hello")
    }
    sinkInt = local // 防消除
}
```

**2) `runtime.KeepAlive`**：常用于 finalizer / cgo 场景，告诉编译器某对象在此处之前必须存活。也可用于 benchmark：

```go
for i := 0; i < b.N; i++ {
    r := compute(i)
    runtime.KeepAlive(r)
}
```

**3) `b.ResetTimer()` / `b.StopTimer()` / `b.StartTimer()`**：控制计时器，把建表、warmup 等开销排除在计量之外。

```go
data := buildLargeMap()
b.ResetTimer()
for i := 0; i < b.N; i++ {
    _ = data[i%len(data)]
}
```

**4) Go 1.24 `for b.Loop()`** ：官方提供的"全自动版"。循环体内引用的变量自动 KeepAlive，循环外建表自动不计时。是首选写法。

```go
func BenchmarkLookup(b *testing.B) {
    data := buildLargeMap() // 不计入
    for b.Loop() {
        _ = data[42]        // 不会被消除
    }
}
```

📎 **深入阅读**: [G19-精通-Go-Benchmarking](../G19-精通-Go-Benchmarking.md)

**常见追问**：
- Q: 为什么 `_ = result` 也可能被消除？  A: `_` 显式表示丢弃，编译器知道无副作用就敢删。
- Q: `runtime.KeepAlive` 和 `_ = x` 的区别？  A: 前者保证从程序入口到该语句对象都存活；后者只是赋值给空白，不阻止 DCE。
- Q: `b.Loop()` 内部还能用 `b.StopTimer()` 吗？  A: 可以，语义不变。

**陷阱**：把 `BenchmarkXxx` 测出 0.3ns/op 大概率是被编译器消除了，先怀疑自己的代码，而不是 Go 真这么快。

### Q3 ⭐⭐⭐⭐ benchstat 是什么？为什么要跑多次（-count=10）取统计

**答**：

`benchstat` 是 Go 官方提供的 benchmark 结果统计工具（`golang.org/x/perf/cmd/benchstat`）。单次 benchmark 的测量受 CPU 频率漂移、GC、操作系统调度影响，**任何两次结果差几个百分点都属于噪声**。直接比较 "old: 100ns vs new: 95ns" 没有统计意义。

正确流程：

```bash
# 跑 10 轮，落盘
go test -bench=. -count=10 -benchmem > old.txt
# 改完代码
go test -bench=. -count=10 -benchmem > new.txt
# 统计对比
benchstat old.txt new.txt
```

输出（节选）：
```
                 │   old.txt   │              new.txt              │
                 │   sec/op    │   sec/op     vs base              │
Foo-8              102.3n ± 2%   98.5n ± 1%  -3.71% (p=0.001 n=10)
Bar-8              512.1n ± 5%   515.0n ± 4%       ~ (p=0.789 n=10)
```

关键看两列：
- **±X%**：相对标准差（CV），衡量噪声幅度。>5% 说明环境不稳。
- **p=**：t-检验 p 值。p < 0.05 视为差异显著；`~` 表示无显著差异。

只有 p 值显著且变化幅度大于噪声水平，才能说"这个优化是真的"。否则你看到的 5% 提升可能只是另一次 GC 的偶然结果。

📎 **深入阅读**: [G19-精通-Go-Benchmarking](../G19-精通-Go-Benchmarking.md)

**常见追问**：
- Q: 为什么默认 `-count=10`？  A: 经验值，让 t-检验有足够样本量；对慢 benchmark 可降低到 5。
- Q: 如何降低噪声？  A: 关闭 turbo boost、关 SMT、`taskset` 固定核、关后台进程、用 `perflock` 加锁。
- Q: benchstat 还能比 allocs/op 吗？  A: 能，会对每一列指标都做统计检验。

**陷阱**：在 macOS 上跑 benchmark 噪声极大（thermal throttling），CI 跑 benchmark 几乎无意义，应当用专门的 perf runner。

### Q4 ⭐⭐⭐ -benchmem 输出的几列都是什么含义（B/op、allocs/op）

**答**：

加 `-benchmem` 后，benchmark 输出多两列：

```
BenchmarkFoo-8     1000000    1234 ns/op    256 B/op    3 allocs/op
```

| 列 | 含义 |
|---|---|
| `ns/op` | 每次迭代的平均耗时（纳秒） |
| `B/op` | 每次迭代分配的字节数（堆分配，不含栈） |
| `allocs/op` | 每次迭代触发的堆分配次数 |

**B/op vs allocs/op 哪个更重要？** 通常 `allocs/op` 更关键——分配次数直接影响 GC 压力和分配器锁竞争。1 次 1KB 分配通常比 100 次 10B 分配快得多。

**典型优化目标**：
- `allocs/op = 0`：纯栈分配 / 零分配 fast path（标准库 `strings.Builder.WriteByte` 等）
- 用 `sync.Pool` 把热点对象池化，allocs/op 从 N 降到 0
- 用 `bytes.Buffer` / `strings.Builder` 取代字符串拼接

注意 `B/op` 只统计**堆**分配。逃逸分析把对象留在栈上的话不会计入。可以加 `-gcflags="-m"` 查看逃逸结果。

```go
func BenchmarkConcat(b *testing.B) {
    b.ReportAllocs() // 等价于 -benchmem
    for b.Loop() {
        s := "hello" + ", " + "world" // 编译期常量折叠，0 alloc
        _ = s
    }
}
```

📎 **深入阅读**: [G19-精通-Go-Benchmarking](../G19-精通-Go-Benchmarking.md)

**常见追问**：
- Q: `b.ReportAllocs()` 和 `-benchmem` 区别？  A: 前者在代码里写死，后者命令行控制；混用以前者优先。
- Q: 为什么我看到 0 B/op 但 1 allocs/op？  A: 显示精度问题，实际分配 < 0.5B/op 被四舍五入。
- Q: `B/op` 大于真实大小怎么解释？  A: malloc 的 size class 上取整，一个 17B 分配实际占用 24B（mspan 最小粒度）。

**陷阱**：`-benchmem` 只看堆，看栈逃逸要靠 `-gcflags="-m=2"`；测出的"零分配"也可能因为编译器对你的代码做了内联消除。

## §2 pprof

### Q5 ⭐⭐⭐⭐ pprof 五种 profile：CPU / heap / goroutine / block / mutex，各采集什么

**答**：

| Profile | 采集对象 | 启用方式 | 默认开销 |
|---------|---------|---------|---------|
| **CPU** | 函数 CPU 时间（采样栈） | `pprof.StartCPUProfile` 或 `/debug/pprof/profile` | 启动期间约 1-3% |
| **heap** | 已分配/已使用的堆对象（采样） | `pprof.WriteHeapProfile` 或 `/debug/pprof/heap` | 默认每 512KB 采一次，几乎免费 |
| **goroutine** | 当前所有 goroutine 的栈快照 | `/debug/pprof/goroutine` | 仅快照瞬间，开销=goroutine 数 |
| **block** | 阻塞在 chan / sync 上的事件 | `runtime.SetBlockProfileRate(n)` | 取决于 rate，1ns=100% 抓 |
| **mutex** | 锁竞争事件（持锁者 / 等待者） | `runtime.SetMutexProfileFraction(n)` | 1/n 采样 |

**使用入口**：
```go
import _ "net/http/pprof" // 自动注册 /debug/pprof/*
go func() {
    log.Println(http.ListenAndServe("localhost:6060", nil))
}()
```

**采集示例**：
```bash
# 30s CPU profile
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30
# 当前堆快照
go tool pprof http://localhost:6060/debug/pprof/heap
# 所有 goroutine 栈
curl http://localhost:6060/debug/pprof/goroutine?debug=2
```

📎 **深入阅读**: [G22-精通-Go-pprof-性能剖析](../G22-精通-Go-pprof-性能剖析.md)

**常见追问**：
- Q: 还有哪些 profile？  A: `threadcreate`（OS 线程创建）、`allocs`（heap 的累计版本）。
- Q: 生产环境是否常开 pprof endpoint？  A: 推荐放在内部端口或加鉴权，公网暴露会有 RCE 风险（曾出过 CVE）。
- Q: 多种 profile 能同时采吗？  A: 可以，互不影响。

**陷阱**：CPU profile 不开启时几乎零成本，但 block/mutex profile rate 太高会严重拖慢；heap profile 永远是采样的，不要把它当作精确的内存账本。

### Q6 ⭐⭐⭐⭐⭐ CPU profile 是采样还是统计？采样频率 100Hz 怎么算

**答**：

Go 的 CPU profile 是**基于信号中断的采样剖析**，不是 instrumentation。原理：

1. `pprof.StartCPUProfile` 注册 `SIGPROF` 信号处理器；
2. 调用 `setitimer(ITIMER_PROF, ...)` 让操作系统每 10ms 给当前线程发一次 `SIGPROF`；
3. 信号到来时记录当前 goroutine 的栈；
4. 汇总每条调用栈出现的次数 → 推算 CPU 时间占比。

**默认频率 100Hz** 含义：1 秒采 100 个样本，**每个样本代表 10ms 的 CPU 时间**。例如某函数在 30 秒 profile 中出现 600 次，就估算它占用了 6 秒 CPU。

```
function_cpu_time ≈ sample_count × (1s / frequency)
                  ≈ 600 × 10ms = 6s
```

**为什么是 100Hz？**
- 太高（>500Hz）：信号开销自身污染 profile，本末倒置；
- 太低（<50Hz）：长尾函数采不到，统计偏差大；
- 100Hz 是开销（约 1-3%）与精度的折衷。

**修改频率**：
```go
runtime.SetCPUProfileRate(250) // 慎用，可能丢样本
```

**采样的副作用**：
1. **运行 <10ms 的函数有概率完全采不到**，profile 不会出现它。
2. **被 syscall 阻塞的 goroutine 不算 CPU**——syscall 期间线程在内核态，SIGPROF 不投递给用户态。要看这种"墙钟时间"占用得用 trace。
3. **多核机器上**：信号会均匀分给各 OS 线程，所以 profile 反映的是"总 CPU 时间"，1s 内可达 cores 秒。

📎 **深入阅读**: [G22-精通-Go-pprof-性能剖析](../G22-精通-Go-pprof-性能剖析.md)

**常见追问**：
- Q: profile 显示 `runtime.futex` 占 30% 正常吗？  A: 不正常，说明你在大量调度阻塞，看 mutex/block profile。
- Q: 容器里 SetCPUProfileRate 失效？  A: cgroup 的 cpu shares 不影响信号频率，但 throttle 会延后投递。
- Q: 比 100Hz 更高精度怎么办？  A: 用 `perf record` + `perf script` 直接看硬件 PMU。

**陷阱**：采样剖析对短路径敏感函数低估严重，把测试 case 跑得更久（增加 `-benchtime=30s`）能改善精度。

### Q7 ⭐⭐⭐⭐ heap profile 的 inuse vs alloc 区别？面试场景：内存涨但没泄漏怎么定位

**答**：

heap profile 提供四种视图：

| 视图 | 命令 | 含义 |
|------|------|------|
| `inuse_space` | 默认 | 当前**仍在使用**的对象总字节 |
| `inuse_objects` | `-inuse_objects` | 当前仍在使用的对象**个数** |
| `alloc_space` | `-alloc_space` | 进程启动以来**累计**分配的字节 |
| `alloc_objects` | `-alloc_objects` | 累计分配的对象个数 |

**区别本质**：
- `inuse_*`：当前活着的 = **泄漏检测视角**。GC 之后没被释放的、引用还在的，才出现在这里。
- `alloc_*`：累计分配的 = **GC 压力视角**。哪个函数频繁制造垃圾、即使及时回收也会拖慢 GC。

**面试经典场景：内存稳步上涨但没泄漏怎么定位？**

1. **第一步**：连续打两次 heap profile，比较 `inuse_space`：
   ```bash
   curl http://localhost:6060/debug/pprof/heap > h1.pb.gz
   sleep 600
   curl http://localhost:6060/debug/pprof/heap > h2.pb.gz
   go tool pprof -base h1.pb.gz h2.pb.gz
   ```
   `-base` 让 pprof 算差值。如果某条调用栈 inuse 持续增长 → 真泄漏。

2. **第二步**：如果 inuse 平稳但 RSS 在涨，看 `runtime.MemStats`：
   - `HeapInuse` 平稳 + `HeapIdle` 大：**碎片化**，等 GC 归还系统（Go 1.16+ 默认 `MADV_DONTNEED`）。
   - `Sys` 大但 `Heap*` 都小：goroutine 栈太多 / mmap 大对象 / cgo。

3. **第三步**：用 `alloc_space` 找高频分配源——即使没泄漏，每秒 100MB 的 churn 也会让 GC 频繁触发，间接抬升 RSS。

📎 **深入阅读**: [G22-精通-Go-pprof-性能剖析](../G22-精通-Go-pprof-性能剖析.md)

**常见追问**：
- Q: 为什么 RSS 远大于 heap inuse？  A: Go runtime 把回收的 span 缓存了，等 scavenger 渐进归还；调小 `GOGC` 或主动 `debug.FreeOSMemory()`。
- Q: heap profile 的采样精度？  A: 默认 `runtime.MemProfileRate = 512KB`，意味着每分配 ~512KB 采一次。
- Q: 怎么调高精度？  A: 设为 1 表示每次分配都采（极慢，只调试用）。

**陷阱**：`alloc_*` 的累计值只在长跑进程上稳定，单测里很可能误判；定位"持续增长"必须用 `-base` 取差。

### Q8 ⭐⭐⭐⭐ block profile / mutex profile 何时开（生产环境的开销）

**答**：

两者都是**事件采样**而非时间采样，因此默认关闭：

**block profile**：记录 goroutine 阻塞在 chan 收发、`sync.Mutex.Lock`、`sync.Cond.Wait`、`select` 等同步原语上的时间。

```go
// rate = 1ns 时 100% 抓；rate=10000 抓 1us 以上的事件
runtime.SetBlockProfileRate(10 * 1000) // 10us 起记录
```

**mutex profile**：记录 mutex 的"持有/等待"事件——谁拿着锁、谁在等。

```go
// 1/n 采样：1 = 全采，100 = 1% 采
runtime.SetMutexProfileFraction(100)
```

**开销评估**：
- block：每次阻塞采样要记录一个完整栈，对阻塞频率敏感。一个 producer/consumer 程序 rate=1 可能拖慢 30%+。生产环境推荐 10us~1ms。
- mutex：每次锁竞争失败时采样。锁争抢不严重的程序几乎免费；高竞争场景 fraction=100 较安全。

**用法示例**：
```go
func main() {
    // 5% mutex 采样
    runtime.SetMutexProfileFraction(20)
    // 仅记录阻塞 > 1ms 的事件
    runtime.SetBlockProfileRate(1_000_000)
    go http.ListenAndServe(":6060", nil)
    // ... 业务代码
}
```

```bash
go tool pprof http://localhost:6060/debug/pprof/block
go tool pprof http://localhost:6060/debug/pprof/mutex
```

**典型场景**：
- 生产偶发延迟尖刺：开 block profile rate=1ms 抓"被阻塞超过 1ms"的栈。
- 怀疑某全局锁热点：开 mutex fraction=100 看 contention top。

📎 **深入阅读**: [G22-精通-Go-pprof-性能剖析](../G22-精通-Go-pprof-性能剖析.md)

**常见追问**：
- Q: block profile 抓 chan 还是 mutex？  A: 都抓，所有 runtime 级的同步阻塞。
- Q: mutex profile 能看 RWMutex 的读锁竞争吗？  A: Go 1.18+ 可以，之前只看写锁。
- Q: 为什么默认关闭？  A: 防止生产环境意外开成全采样而拖垮系统。

**陷阱**：`SetBlockProfileRate(0)` 是关闭，`1` 是 **100% 采样**——记错值容易把生产打挂。

### Q9 ⭐⭐⭐⭐ pprof 怎么看火焰图？top / list / web 三种视角

**答**：

`go tool pprof` 交互式界面常用命令：

**1) `top` —— 找热点函数**
```
(pprof) top10
Showing nodes accounting for 8.50s, 85.00% of 10.00s total
      flat  flat%   sum%        cum   cum%
     3.00s 30.00% 30.00%      3.20s 32.00%  encoding/json.(*decodeState).object
     2.00s 20.00% 50.00%      2.00s 20.00%  runtime.mapaccess1_faststr
     ...
```
- `flat`：函数**自身**消耗的 CPU（不含被调用方）
- `cum`：函数 + 其所有子调用累计 CPU
- 优化"flat 大"的函数收益最直接；"cum 大但 flat 小"说明问题在它调用的下游。

**2) `list <regex>` —— 看到行级**
```
(pprof) list decodeState.object
Total: 10s
ROUTINE ======================== encoding/json.(*decodeState).object
     3s    3.2s (flat, cum) 32.00% of Total
       .          .   810:    for {
     50ms      50ms   811:        if d.scan.step(...)
     2.95s    3.15s   812:        v := d.value()
       .          .   813:    }
```
直接看到每一行消耗，立刻知道是哪条语句慢。

**3) `web` —— SVG 调用图 / `flame` —— 火焰图**

`web` 生成 graphviz SVG，节点大小=cum，边粗细=被调用次数。
`flame`（pprof 内置）/ 浏览器版 `-http :8080` 生成火焰图：
- 横轴：调用栈中各函数的 CPU 占比
- 纵轴：调用深度（栈顶在最上）
- 越宽的格子越费时；找最宽的、最不该宽的，就是优化目标。

```bash
# 启动 pprof Web UI（推荐）
go tool pprof -http=:8080 cpu.pb.gz
# 或者直接命令行
go tool pprof cpu.pb.gz
(pprof) flame
```

**视角选择**：
- 不知道从哪下手 → `top` 看大头
- 大头确定要继续钻 → `list` 看代码行
- 想理解调用关系 / 给同事讲 → `web` / `flame`

📎 **深入阅读**: [G22-精通-Go-pprof-性能剖析](../G22-精通-Go-pprof-性能剖析.md)

**常见追问**：
- Q: 火焰图横向相同函数会合并吗？  A: 默认会按栈完全相同合并；按调用路径区分要用 differential flame graph。
- Q: 怎么看反向火焰图？  A: pprof `-http` UI 有 "Inverted Flame Graph"，按 cum 倒序聚合，适合定位"被很多人调用"的底层函数。
- Q: 看不懂大量 `runtime.*` 怎么办？  A: `--ignore=runtime` 过滤；或在 web UI 里关闭 runtime 包。

**陷阱**：火焰图的横宽是**采样次数**而不是时间——profile 时间短 + 函数很短，可能根本采不到。

## §3 trace

### Q10 ⭐⭐⭐⭐ runtime/trace 与 pprof 的区别（采样 vs 全量）

**答**：

| 维度 | pprof | runtime/trace |
|------|-------|---------------|
| **采集方式** | 采样（信号 / 阈值） | 全量事件流（每个 goroutine 切换、syscall、GC 起止都记录） |
| **数据量** | KB ~ 几 MB | 30s 典型 100MB+ |
| **回答的问题** | "CPU 花在哪？谁分配最多？" | "为什么 P99 高？这个请求在等什么？" |
| **时间维度** | 聚合统计 | 时间线（precise timeline） |
| **开销** | 1-3% (CPU) | 10-30% (全量事件) |
| **看法** | `go tool pprof` | `go tool trace` Web UI |

**trace 记录哪些事件**：
- goroutine 创建 / 启动 / 阻塞 / 恢复 / 结束
- syscall 进入 / 退出
- GC start / mark / sweep
- network poller wake / sleep
- 用户 region / task（`runtime/trace.WithRegion` 等）

**何时用 trace 而非 pprof**：

| 现象 | 用 |
|------|----|
| 整体 CPU 高、想知道谁是 hot path | pprof CPU |
| 内存涨 | pprof heap |
| P99 偶发尖刺 | trace |
| 想知道某请求为什么慢 | trace + user region |
| GC 抖动定位 | trace（看 STW + mark 时长） |
| 调度延迟（goroutine 排队等 P） | trace |

**采集示例**：
```go
import "runtime/trace"

f, _ := os.Create("trace.out")
trace.Start(f)
defer trace.Stop()
// ... 运行 1~30s
```

```bash
go tool trace trace.out
```

打开 `http://localhost:xxx`，重点看：
- **View trace**：时间线（Chrome trace viewer）
- **Goroutine analysis**：每个 G 的存活 / 阻塞分布
- **Network blocking profile** / **Syscall blocking profile** / **Scheduler latency profile**

📎 **深入阅读**: [G23-精通-Go-runtime-trace](../G23-精通-Go-runtime-trace.md)

**常见追问**：
- Q: trace 文件能在线服务长期开吗？  A: 默认不行，太大；要么定时短抓，要么用 FlightRecorder（Q12）。
- Q: trace 能替代 pprof 吗？  A: 不能，trace 看不出"哪个函数 flat 占用最多"，pprof 是必要补充。
- Q: 时间线粒度多细？  A: 微秒级，能看清 GC 5ms STW 内部的执行情况。

**陷阱**：trace 开启会改变 runtime 行为（写 buffer、锁竞争），微基准 + trace 会让结果失真。

### Q11 ⭐⭐⭐⭐ go tool trace 主要看什么（goroutine 调度延迟、阻塞、GC 时长、syscall）

**答**：

`go tool trace` Web UI 几个最重要的页面：

**1) Goroutine analysis**
按函数聚合所有 goroutine 的生命周期，列出：
- **Execution time**：在 P 上真正执行的时间
- **Network wait** / **Sync wait** / **Block time**：分别等网络、等锁、等其他
- **GC pause** / **Sweep time**：被 GC 暂停的时间
- **Scheduler latency**：可运行但还没被调度上（runqueue 等 P）

> 面试金句：高 P99 一般 = scheduler latency 高 + sync wait 高。

**2) View trace**（核心时间线）
横轴时间、纵轴 P0/P1/...每个核。每个色块是一个 goroutine 时间片，悬停看栈。能直接看出：
- GC STW 的两段
- 所有 P 都空闲但 goroutine 在排队（调度异常）
- syscall 期间 G 被 detach 到 M

**3) Network blocking profile / Syscall blocking profile / Block profile / Scheduler latency profile**
四个聚合视图，类似 pprof 但维度不同。

**4) User-defined tasks/regions**
代码里用 `trace.WithRegion(ctx, "db.Query", func() { ... })` 标注关键路径，UI 里就能筛出每次 Query 的开销分布。

```go
import "runtime/trace"

ctx := r.Context()
trace.WithRegion(ctx, "handler.Decode", func() {
    json.NewDecoder(r.Body).Decode(&req)
})
trace.WithRegion(ctx, "db.Query", func() {
    rows, _ = db.QueryContext(ctx, sql)
})
```

**典型排查路径**：
1. 看 View trace 找毛刺时段
2. 鼠标圈选该时段 → 看 Goroutine analysis
3. 发现 Sync wait 异常高 → 用 pprof mutex profile 找具体锁
4. 或者发现 GC pause 多 → 用 pprof heap 找分配热点

📎 **深入阅读**: [G23-精通-Go-runtime-trace](../G23-精通-Go-runtime-trace.md)

**常见追问**：
- Q: trace 里如何看 GMP？  A: 每个 P 占一行；M（OS 线程）默认隐藏，可在 "Threads" 视图打开。
- Q: 怎么找 starvation？  A: View trace 看哪个 goroutine 的色块持续不在 P 上但又是 runnable。
- Q: 用 region 影响性能吗？  A: trace 关闭时几乎零成本；开启时每 region 几百 ns 开销。

**陷阱**：trace 文件太大时浏览器会卡，建议 trace 不超过 30 秒；超过则用 FlightRecorder 取片段。

### Q12 ⭐⭐⭐⭐⭐ Go 1.25 FlightRecorder（连续跟踪缓冲）解决了什么问题

**答**：

**问题**：以前的 trace 必须**事先开启**。线上偶发故障——比如 P99 每 10 分钟尖刺一次——你不可能 24h 一直开 trace（开销和文件大小都不行），所以**永远抓不到现场**。

**FlightRecorder 思路**（借鉴 Java 的 JFR / Linux 的 perf-rec circular buffer）：
- runtime 在内存里维护一个**环形缓冲区**，**永远在记录**最近 N 秒（默认 ~10s, 可配）的事件
- 旧事件被新事件覆盖
- 故障发生时，应用方主动调 `WriteTo(file)` 把当前缓冲区**dump 到磁盘**，得到"事故前最后 10s"的 trace

```go
import "runtime/trace"

fr := trace.NewFlightRecorder()
fr.SetPeriod(10 * time.Second) // 缓冲最近 10 秒
fr.Start()
defer fr.Stop()

// 业务循环：监控指标
for {
    select {
    case <-anomalyDetected:
        f, _ := os.Create(fmt.Sprintf("trace-%d.out", time.Now().Unix()))
        fr.WriteTo(f)
        f.Close()
    }
}
```

**关键收益**：
1. **常驻开启**：环形缓冲不写磁盘，开销远低于完整 trace（约 1-3%）
2. **抓得到偶发问题**：异常发生后再 dump，包含完整事故现场
3. **配合熔断 / 探针**：监测到 latency > 阈值 → 自动 dump trace + 发告警

**典型架构**：

```
[Prometheus alert] → [HTTP /debug/flightrecorder/dump] → [trace.out 上传到 S3]
                                                       ↓
                                                  开发拉下来 go tool trace
```

📎 **深入阅读**: [G23-精通-Go-runtime-trace](../G23-精通-Go-runtime-trace.md)

**常见追问**：
- Q: 缓冲区放在哪？  A: 进程内堆内存；越大越能回看更久，但内存占用越多。
- Q: 能配合 pprof 吗？  A: 可以，FR dump 出来的是标准 trace 格式，`go tool trace` 直接打开。
- Q: 1.25 以前怎么实现类似功能？  A: 社区有 `cloudwego/kitex-tracer` 等 hack，但需自行实现环形 buffer 抓 runtime 事件。

**陷阱**：FlightRecorder 的 buffer size 是软上限，事件密集（trace.WithRegion 调用频繁）时实际可回看时间会缩短；触发 dump 后建议 cooldown 一段时间避免反复 dump。

## §4 unsafe

### Q13 ⭐⭐⭐⭐⭐ unsafe.Pointer 的"六条合法转换规则"（go vet 的依据）

**答**：

`unsafe.Pointer` 是 Go 类型系统的"逃生舱"。Go spec 列出**六条且只有六条**合法用法，`go vet -unsafeptr` 就是按这六条来检查。

**规则 1**：`*T1 → unsafe.Pointer → *T2`，前提是 `sizeof(T2) ≤ sizeof(T1)` 且对齐兼容。

```go
var f float64 = 1.5
p := (*uint64)(unsafe.Pointer(&f)) // float64 ↔ uint64 重解释
```

**规则 2**：`unsafe.Pointer → uintptr` 用于显示（fmt / 打印）。**返回 uintptr 不再算作指针**，GC 不会更新它。

**规则 3**：`unsafe.Pointer` 与 `uintptr` 做**算术，在同一条表达式内完成**（指针运算）。

```go
// ✅ 合法：单条语句完成
p := unsafe.Pointer(uintptr(unsafe.Pointer(&arr[0])) + uintptr(i)*unsafe.Sizeof(arr[0]))

// ❌ 危险：拆成两步，中间 uintptr 不被 GC 跟踪，对象可能被移动
u := uintptr(unsafe.Pointer(&arr[0]))
u += offset // GC 在这里发生，u 已是过期地址
p := unsafe.Pointer(u)
```

**规则 4**：`syscall.Syscall` 的指针参数，可以临时转为 uintptr。runtime 特殊保证：传给 syscall 的 uintptr 参数在调用期间被视作活指针。

**规则 5**：`reflect.Value.Pointer` / `UnsafeAddr` 的返回值（uintptr）必须**立即转换**回 `unsafe.Pointer`。

```go
p := unsafe.Pointer(reflect.ValueOf(x).Pointer()) // ✅ 同一行
```

**规则 6**：`reflect.SliceHeader` / `reflect.StringHeader` 的 `Data` 字段——同样必须当作 uintptr 立即处理。**Go 1.20 起官方推荐改用 `unsafe.Slice` / `unsafe.String` / `unsafe.StringData` / `unsafe.SliceData`**，绕过这条规则。

**Go 1.20+ 新 API**：
```go
// 旧：通过 reflect.SliceHeader 强转
// 新：官方安全 API
b := unsafe.Slice(ptr, n)              // *T + n → []T
s := unsafe.String(byteptr, n)         // *byte + n → string
p := unsafe.SliceData(slice)           // []T → *T
p := unsafe.StringData(str)            // string → *byte
```

📎 **深入阅读**: [G25-精通-Go-unsafe-与-linkname](../G25-精通-Go-unsafe-与-linkname.md)

**常见追问**：
- Q: 为什么 uintptr 不算指针？  A: 它是数字，GC 扫描栈/寄存器时不当指针处理；对象被 mark/scan 阶段移动时不更新它（虽然目前 Go GC 不移动对象，但规则保留余地）。
- Q: `go vet` 全过就安全吗？  A: 不一定，vet 只查语法层面；语义错误（指针寿命、对齐）需要人为保证。
- Q: 怎么测试 unsafe 代码？  A: `go test -race -gcflags="all=-d=checkptr"`，runtime 会校验越界 / 对齐。

**陷阱**：把 `&slice[0]` 拿出来 `uintptr` 算偏移再放回去——只要中间发生过函数调用或 GC，地址就可能过期；现代 Go 用 `unsafe.Add(ptr, offset)` + `unsafe.Slice` 替代。

### Q14 ⭐⭐⭐⭐ 零拷贝 string ↔ []byte 的常见写法及风险

**答**：

Go 中 `string` 和 `[]byte` 互转默认会拷贝整段数据（语义上 string 不可变、[]byte 可变，必须复制）。零拷贝技巧能省去这次内存复制，热路径上很常见。

**Go 1.20+ 推荐写法**：

```go
// []byte → string（零拷贝）
func b2s(b []byte) string {
    return unsafe.String(unsafe.SliceData(b), len(b))
}

// string → []byte（零拷贝）
func s2b(s string) []byte {
    return unsafe.Slice(unsafe.StringData(s), len(s))
}
```

**旧写法（已不推荐）**：通过 `reflect.StringHeader` / `reflect.SliceHeader` 强转。新代码不要写。

**风险与限制**：

1. **写入零拷贝 string 转出的 []byte 是 UB**。`string` 内存可能位于只读段（编译期常量），写它会段错误。
   ```go
   b := s2b("hello") // 编译期字符串
   b[0] = 'H'        // 💥 SIGSEGV
   ```

2. **生命周期**：转换后两个变量共享底层数据，任何一个还活着就阻止 GC 回收。如果 `[]byte` 来自大 buffer，转 `string` 后切片虽小，GC 也不释放整段——可能造成"内存膨胀"。

3. **逃逸分析失效**：`unsafe.SliceData` 拿到的指针属于"外部引用"，编译器会保守把对象逃逸到堆。

4. **race detector 报警**：并发场景一方写 `[]byte`、另一方读零拷贝 `string`，race 工具会报 data race。

**何时值得用**：
- 高频 hot path（每请求 GB 级吞吐）
- 只读用途（log key、map 索引）
- 你能 100% 保证不写 + 生命周期短

```go
// 典型场景：把 HTTP body 当 key 查 map 而不分配新 string
key := b2s(body) // body 在函数返回前不会被 reuse
v := cache[key]
```

📎 **深入阅读**: [G25-精通-Go-unsafe-与-linkname](../G25-精通-Go-unsafe-与-linkname.md)

**常见追问**：
- Q: `string([]byte(...))` 真的会拷贝吗？  A: 编译器在部分场景会优化掉（如 `m[string(b)]` 取 map），但不是所有场景，靠不住。
- Q: 标准库自己用零拷贝吗？  A: 用，`strings.Builder.String()` 就用 `unsafe.String` 直接交出底层数组。
- Q: race detector 报错怎么办？  A: 那就不该零拷贝；如果是误报，加注释屏蔽 `// nolint:race`。

**陷阱**：千万不要对 string 零拷贝出的 []byte 写值，也不要在 cgo 传出后用——cgo 边界外可能复用内存。

### Q15 ⭐⭐⭐⭐ //go:linkname 是什么？什么场景合法（标准库自身、调试）

**答**：

`//go:linkname localName remoteName` 是一条**编译器指令**，用来给当前包的某个函数/变量起"别名"，让它在链接期指向另一个包（甚至 runtime 内部不导出的符号）。

```go
package myhack

import _ "unsafe" // 必须

//go:linkname nanotime runtime.nanotime
func nanotime() int64 // 没有函数体，链接器把它绑到 runtime.nanotime

func Now() int64 { return nanotime() }
```

**用途**：
1. **访问 runtime 内部未导出函数**：`runtime.nanotime`、`runtime.fastrand`、`runtime.procPin` 等。
2. **标准库内部跨包调用**：例如 `time` 包要调用 `runtime` 的低层函数。
3. **库作者绕过封装做极致优化**（如 `valyala/fastrand`、`bytedance/sonic`）。
4. **测试代码 hook 私有函数**。

**前置条件**：
- 必须 `import _ "unsafe"`（这是约定，编译器靠它识别你"知道在干嘛"）
- 函数体可以省略（纯转发）或填充自定义实现
- 需要在编译时开 `-gcflags=-d=linkname=*` 或同 module 内（受 Go 1.21+ 收紧的访问规则限制）

**Go 1.21+ 限制**：
- `runtime` 的非导出符号默认**禁止**被外部 module linkname
- 标准库内部已知 linkname 用法被加入白名单
- 外部库滥用 linkname 会触发警告甚至链接失败

**合法场景**：
- ✅ 你自己写 runtime 实验 / 调试器
- ✅ 你 fork 了 Go 源码做修改
- ✅ 标准库内部
- ⚠️ 高性能库（要做好兼容性测试，跨 Go 版本可能崩）
- ❌ 业务代码（一旦升级 Go 版本可能直接挂）

**典型例子（早年 fastrand）**：
```go
//go:linkname runtime_fastrand runtime.fastrand
func runtime_fastrand() uint32

func Fastrand() uint32 { return runtime_fastrand() } // 比 math/rand 快几十倍
```

📎 **深入阅读**: [G25-精通-Go-unsafe-与-linkname](../G25-精通-Go-unsafe-与-linkname.md)

**常见追问**：
- Q: linkname 能引用导出符号吗？  A: 能，但没意义——直接 import 就行。
- Q: 1.23+ runtime.fastrand 没了怎么办？  A: 改用 `math/rand/v2` 的 `Uint64()`，性能差距已很小。
- Q: linkname 用错了会怎样？  A: 链接成功但运行时崩（参数布局不匹配）/ panic / 数据损坏，调试极其困难。

**陷阱**：linkname 绑定的目标函数签名 / 调用约定不被编译器校验——目标改了你的代码会静默错乱。

## §5 Testing

### Q16 ⭐⭐⭐ table-driven test 的标准写法

**答**：

table-driven 是 Go 社区最主流的测试写法，核心思想：**把测试用例当数据**，循环驱动一份测试逻辑。

**标准模板**：
```go
func TestAdd(t *testing.T) {
    tests := []struct {
        name string
        a, b int
        want int
    }{
        {"zero", 0, 0, 0},
        {"positive", 1, 2, 3},
        {"negative", -1, -2, -3},
        {"overflow", math.MaxInt, 1, math.MinInt},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got := Add(tt.a, tt.b)
            if got != tt.want {
                t.Errorf("Add(%d, %d) = %d, want %d", tt.a, tt.b, got, tt.want)
            }
        })
    }
}
```

**为什么用 `t.Run` 子测试**：
1. 输出按 case 名字分组：`--- FAIL: TestAdd/overflow`
2. 可以单独 `-run TestAdd/positive` 跑一个
3. 每个子测试可独立 `t.Parallel()`
4. 一个失败不影响后续跑

**进阶变量**：
- `setup/teardown` 可放在子测试外或用 `t.Cleanup(fn)` 注册
- 用 `cmp.Diff(tt.want, got)` 替代 `!=`，错误信息更友好
- 需要错误检查时加 `wantErr error` 字段

```go
{
    name: "div by zero",
    a:   1, b: 0,
    wantErr: ErrDivZero,
}
// 校验
if !errors.Is(err, tt.wantErr) {
    t.Errorf("err = %v, want %v", err, tt.wantErr)
}
```

📎 **深入阅读**: [G18-精通-Go-测试](../G18-精通-Go-测试.md)

**常见追问**：
- Q: case 数据放外部 YAML / JSON 行不行？  A: 行，叫"golden file test"，常用于复杂结构断言。
- Q: 为什么不用 `assert` 库？  A: Go 社区偏好 `t.Errorf`，自由度高且无第三方依赖；用 `testify` 也不是不行。
- Q: Go 1.22 后 `t.Run` 内捕获循环变量还有坑吗？  A: 没了，1.22 起循环变量按每轮独立创建，老写法 `tt := tt` 不再必要。

**陷阱**：千万记得用 `t.Run(tt.name, ...)` 而不是直接 `func(t *testing.T)` 调一遍——后者所有 case 共享一个 t，输出无法定位。

### Q17 ⭐⭐⭐⭐ t.Parallel 的注意点：循环变量复用（Go 1.22 前后）、共享状态、t.Setenv 不兼容

**答**：

`t.Parallel()` 让当前子测试与其他声明了 Parallel 的子测试**并发执行**。注意点：

**1) Go 1.22 之前的循环变量陷阱**

```go
for _, tt := range tests {
    // ❌ 1.22 之前：所有并发子测试共享同一个 tt，最后 tt 是最后一个 case
    t.Run(tt.name, func(t *testing.T) {
        t.Parallel()
        check(t, tt.input) // 全部用最后一个 case 的 input
    })
}
```

修复（1.22 之前）：
```go
for _, tt := range tests {
    tt := tt // 每轮复制一份
    t.Run(tt.name, func(t *testing.T) {
        t.Parallel()
        check(t, tt.input)
    })
}
```

Go 1.22 起循环变量每次迭代是新变量，**该坑消失**。但许多老仓库还在用旧写法。

**2) 共享状态**

并发子测试共享：
- 全局变量
- 包级 mutex
- 文件系统（同名 tempfile）
- 网络端口

```go
var counter int
// ❌ 多个 t.Parallel 子测试 race 修改 counter
```

要么避免共享、要么显式加锁。`go test -race` 会立刻暴露。

**3) `t.Setenv` 不兼容 Parallel**

`t.Setenv` 修改进程级环境变量，调完会自动恢复。如果子测试既 `t.Parallel()` 又 `t.Setenv()`，会**直接 panic**（运行时检查）：

```go
t.Run("env", func(t *testing.T) {
    t.Setenv("DEBUG", "1") // ✅
    t.Parallel()           // 💥 panic: t.Parallel called after t.Setenv
})
```

需要并发 + 不同 env，只能 fork 子进程跑（`testscript` / `os/exec`）。

**4) `t.Cleanup` 的顺序**：每个并发子测试的 cleanup 在该子测试结束后立即执行，但父测试的 cleanup 要等所有并发子完成。

**5) 控制并发度**：`-parallel N` 控制最多多少 Parallel 子测试同时跑，默认 `GOMAXPROCS`。

📎 **深入阅读**: [G18-精通-Go-测试](../G18-精通-Go-测试.md)

**常见追问**：
- Q: TestMain 里能 t.Parallel 吗？  A: TestMain 没有 t，不适用。
- Q: 子测试 + Parallel + 表驱动的完整模板？  A: 见 Q16 加上 `t.Parallel()` 即可（Go 1.22+ 无需 shadow）。
- Q: 为什么 `t.TempDir` 在 Parallel 下安全？  A: 每个 t 独立创建唯一目录。

**陷阱**：在 CI 上 `-parallel=1` 跑通、本地多核挂掉，多半就是 1.22 以前的循环变量复用。

### Q18 ⭐⭐⭐⭐ fuzz testing：种子语料、corpus、最小化 reproducer

**答**：

Go 1.18+ 内置 fuzzing。原理：**自动生成大量随机输入**，把测试函数当成"输入→不 panic / 满足不变量"的属性测试。

**写法**：
```go
func FuzzParse(f *testing.F) {
    // 种子语料：保证基本路径覆盖
    f.Add("hello")
    f.Add("123")
    f.Add("")

    f.Fuzz(func(t *testing.T, s string) {
        v, err := Parse(s)
        if err != nil {
            return // 输入非法，正常错误不算 bug
        }
        // 不变量：parse 出来再 format 一次结果不变
        if got := Format(v); got != s {
            t.Errorf("roundtrip: %q → %q", s, got)
        }
    })
}
```

**关键概念**：

1. **种子语料（seed corpus）**：`f.Add(...)` 添加的初始用例 + `testdata/fuzz/FuzzParse/*` 下持久化的用例。fuzz 引擎以此为起点变异。
2. **生成语料（generated corpus）**：fuzz 引擎运行时基于覆盖反馈生成的新输入，保存在 `$GOCACHE/fuzz/`。
3. **最小化 reproducer**：发现 crash 后，引擎自动尝试缩小输入（删字符、二分），最后落盘到 `testdata/fuzz/FuzzParse/<hash>`。这个文件就是 bug 复现脚本，**直接 commit 进 git**，未来 `go test` 会自动跑（regression）。

**运行**：
```bash
# 普通跑：只执行种子 + testdata 下的回归 case
go test ./...

# 开始 fuzzing（默认无限跑）
go test -fuzz=FuzzParse -fuzztime=10m
```

**fuzz vs unit test**：

| 维度 | unit test | fuzz |
|------|-----------|------|
| 输入 | 人工指定 | 引擎生成 |
| 目标 | 验证已知 case | 找未知边界 |
| 运行时长 | 秒级 | 分钟到小时 |
| 适合场景 | 业务正确性 | 解析器 / 协议 / 安全敏感代码 |

**发现 crash 后的工作流**：
1. 引擎在 `testdata/fuzz/<FuzzName>/<hash>` 写入复现文件
2. `go test -run FuzzName/<hash>` 单独跑这个最小 case
3. 修 bug → 该文件留下作为永久回归测试

📎 **深入阅读**: [G18-精通-Go-测试](../G18-精通-Go-测试.md)

**常见追问**：
- Q: fuzz 能跑分布式吗？  A: 标准库内置不支持；社区有 `oss-fuzz` 集成，Google 帮你跑。
- Q: 怎么提升 coverage？  A: 加多样化的种子 + 让 Fuzz 函数尽量纯（不读全局状态）。
- Q: 输入类型限制？  A: 支持 string、[]byte、各种原生数值类型；复杂结构需要先解码。

**陷阱**：fuzz 跑出来的小输入容易"巧合通过"，必须用断言验证不变量；只检查"不 panic"等于白跑。

### Q19 ⭐⭐⭐⭐ fake / mock / stub 的区别？什么场景用 mock 库（gomock / mockery）

**答**：

Martin Fowler 的经典划分（test doubles）：

| 类型 | 行为 | 典型场景 |
|------|------|---------|
| **Dummy** | 占位对象，从不被调用 | 接口参数占位 |
| **Stub** | 返回写死的预设值 | "调 GetUser 永远返回 alice" |
| **Fake** | 简化但可工作的真实实现 | in-memory SQLite 替代 PostgreSQL |
| **Mock** | 验证调用次数 / 参数 / 顺序 | "确保 SendEmail 被调用 1 次，参数=xxx" |
| **Spy** | 录制调用，事后查 | wrapper 记录所有调用 |

**Go 中的选择**：

1. **优先 Fake**：写一个 `InMemoryRepo` 实现 `Repo` 接口，最贴近真实行为，测试逻辑更稳。
2. **次选手写 Stub**：简单接口直接闭包搞定，**不引入第三方依赖**。
   ```go
   type stubRepo struct { user User }
   func (s stubRepo) GetUser(id string) (User, error) { return s.user, nil }
   ```
3. **复杂接口 / 强调验证调用 → Mock 库**：
   - **gomock**（google/mock）：基于代码生成，强类型，最主流
   - **mockery**：基于 `testify/mock`，配置文件驱动
   - **moq**：matryer/moq，极简代码生成

**何时用 mock 库**：
- 接口方法多（>5）+ 频繁变化，手写 stub 太累
- 要严格断言"GetUser 被调用了 2 次，第二次参数是 X"
- 团队规范统一

```go
// gomock 示例
mockRepo := mock.NewMockRepo(ctrl)
mockRepo.EXPECT().
    GetUser("alice").
    Return(User{Name: "Alice"}, nil).
    Times(1)
```

**避免**：
- 不要 mock 自家没声明的接口（不要 mock 标准库的 *sql.DB）
- 不要"为了 100% mock 覆盖"导致测试和实现绑死，重构必断
- 集成测试用 fake / testcontainer 跑真组件，比 mock 健壮

📎 **深入阅读**: [G18-精通-Go-测试](../G18-精通-Go-测试.md)

**常见追问**：
- Q: gomock 已停止维护？  A: 2023 年 Google 转移到 `go.uber.org/mock`，API 兼容。
- Q: 怎么测 http handler？  A: 用 `httptest.NewServer` 起真服务 + `httptest.NewRecorder` 捕响应，不需要 mock。
- Q: testify 的 mock 和 gomock 区别？  A: testify 是运行时反射，写法松散；gomock 是代码生成，强类型 + 严格。

**陷阱**：mock 严格匹配参数会让测试脆弱；用 `gomock.Any()` / `mock.Anything` 时要注意"忘了断言"——折中：关键参数显式，无关参数 Any。

### Q20 ⭐⭐⭐⭐⭐ Go 1.25 testing/synctest 解决了什么问题（虚拟时间 + goroutine 等待）

**答**：

**问题**：测试涉及 `time.Sleep` / `time.After` / goroutine 调度的代码非常痛苦：
- 真的 sleep 让测试变慢（10s 超时测试要跑 10s）
- 用 `mockTime` 之类的包要侵入业务代码（替换 `time.Now`）
- 多 goroutine 协作的代码需要 `time.Sleep(100ms)` "估摸" 等它跑完——flaky test 的最大来源

**`testing/synctest`**（Go 1.24 实验性引入，需 `GOEXPERIMENT=synctest`；Go 1.25 起正式纳入标准库 GA，无需实验开关）提供两个核心 API：

```go
import "testing/synctest"

func TestTimeout(t *testing.T) {
    synctest.Run(func() {
        ch := make(chan int)
        go func() {
            time.Sleep(1 * time.Hour) // 虚拟时间，瞬间完成
            ch <- 42
        }()

        synctest.Wait() // 等所有 goroutine 阻塞
        // 此时虚拟时钟已经推进 1h，ch 有值了

        select {
        case v := <-ch:
            // ✅
        default:
            t.Fatal("no value")
        }
    })
}
```

**核心机制**：
1. **虚拟时钟**：`Run` 内部劫持 `time.Now / time.Sleep / time.After / time.NewTimer`，时间不真流逝。
2. **"durably blocked" 检测**：所有 goroutine 都阻塞在 chan / sleep / select 等"持久阻塞"上时，runtime 把虚拟时钟跳到下一个最近 timer。
3. **`synctest.Wait()`**：等待所有同协作组的 goroutine 都到达 durably blocked 状态，相当于一种"全栈静默点"。
4. **隔离泡（bubble）**：`Run` 内启动的 goroutine 属于同一个泡；离开泡（如真正网络 IO）会失败或被检测。

**实际应用场景**：

- **测试超时逻辑**：原本要等 30s 的 `context.WithTimeout(30*time.Second)` 测试现在毫秒完成。
- **测试调度公平性**：`synctest.Wait()` 让你能断言"两个 goroutine 都已 select 后再发信号"。
- **测试时间相关的 retry / backoff**：模拟"等 1 分钟再重试"无需真等。

**和 `clockwork` / `benbjohnson/clock` 等社区方案的区别**：
- 社区方案需要把 `time.Now` 通过 DI 注入业务，侵入式
- synctest 是 runtime 级劫持，**业务代码完全不改**

📎 **深入阅读**: [G18-精通-Go-测试](../G18-精通-Go-测试.md)

**常见追问**：
- Q: synctest 还是实验包吗？  A: 不再是。Go 1.24 实验性引入（`GOEXPERIMENT=synctest`），Go 1.25 起正式纳入标准库（GA），无需实验开关；旧的 GOEXPERIMENT 写法在 1.26 已弃用。
- Q: 真 IO 怎么办？  A: 测试里把 IO 抽象成接口注入 fake；synctest 不替代依赖注入。
- Q: 和 race detector 冲突吗？  A: 不冲突，`-race` 仍可用。

**陷阱**：synctest 内调用真 syscall / cgo / 网络会被检测为"非 durable 阻塞"导致死锁——只能用纯 Go + chan + time 组合。

## §6 Modules

### Q21 ⭐⭐⭐⭐ go.mod 的 require / replace / exclude / retract 各干什么

**答**：

`go.mod` 四个关键指令：

**1) `require`**：声明依赖。
```go.mod
require (
    github.com/gin-gonic/gin v1.10.0
    golang.org/x/sync v0.7.0
)
```

带 `// indirect` 注释的是**间接依赖**——你的代码没直接 import，但被你的依赖依赖。Go 1.17+ 把所有间接依赖也写入 go.mod（lazy loading 需要）。

**2) `replace`**：把某个版本（或所有版本）替换成本地路径或另一个 module。
```go.mod
// 把上游版本替换成本地分支调试
replace github.com/foo/bar => ../bar-fork

// 替换为另一个 module
replace github.com/foo/bar v1.2.3 => github.com/myorg/bar v1.2.4-patch
```

只在当前 module 的 go.mod 生效，**不会传递给下游**。常用于：
- 本地开发联调（指向本地路径）
- 上游有 bug，临时切私有 fork
- 强制升级被上游间接 require 的库

**3) `exclude`**：明确禁止某个版本被选中。
```go.mod
exclude github.com/foo/bar v1.2.5 // 这版本有严重 bug
```

实际项目用得很少，因为 `replace` 更灵活。

**4) `retract`**（Go 1.16+）：声明本模块的某些版本**已废弃**，提示下游别用。
```go.mod
module github.com/myorg/lib

retract (
    v1.5.0 // 严重 bug，请用 v1.5.1
    [v1.0.0, v1.0.5] // 区间撤回
)
```

发布者标记后，`go get` 默认跳过 retracted 版本，`go list -m -versions` 会标 `// retracted`。这是 Go 模块体系的"召回机制"——你不能从 proxy 删版本（不可变性原则），只能 retract。

📎 **深入阅读**: [G17-精通-Go-Modules](../G17-精通-Go-Modules.md)

**常见追问**：
- Q: replace 写在自己仓库里，下游 import 时生效吗？  A: 不生效，只对本 module 编译生效。
- Q: 怎么强制全员用某 replace？  A: 没办法；通过 vendoring 或自建 fork 路径。
- Q: retract 的版本如果还在生产怎么办？  A: 没事，已下载的不会失效，只是 `go get` 不会拿到。

**陷阱**：`replace` 留在生产 go.mod 里是常见问题源（本地路径绝对路径泄漏 / fork 失去维护）；上线前用 `go mod edit -dropreplace=...` 清理。

### Q22 ⭐⭐⭐⭐⭐ MVS (Minimum Version Selection) 算法和 npm/maven 的依赖解析有什么本质区别

**答**：

Go Modules 使用 **MVS（Minimum Version Selection）** 解析依赖，由 Russ Cox 设计。核心规则：**对每个依赖，选择所有 require 声明中"最高的最低要求"作为最终版本**。

**算法**：
1. 从 main module 出发，收集所有传递依赖（包括间接）的 require 声明
2. 对每个 module M：取所有声明它的 require 行中**最高的版本**作为选定版本
3. 不做 SAT 求解，不寻找"最优"组合

**示例**：
```
A requires B v1.2
A requires C v1.0
C v1.0 requires B v1.5
```

MVS 选 B v1.5（满足所有人的最低要求里最高的）。

**与 npm / maven 的本质区别**：

| 维度 | Go MVS | npm | Maven |
|------|--------|-----|-------|
| **目标** | 可重现 + 最低升级 | 最新满足 semver | 最近优先 |
| **是否需要 lockfile** | 不需要（go.sum 是哈希校验，不是版本锁） | 需要（package-lock.json） | 不需要（声明即锁） |
| **算法复杂度** | 线性 | NP-Hard（回溯求解） | 启发式 |
| **冲突处理** | 不允许同一 major 多版本共存 | 允许 nested node_modules | dependencyManagement 强制 |
| **可重现性** | 默认可重现（只看 go.mod） | 必须 lockfile | 受插件影响 |
| **是否选"最新"** | 否，选最低满足者 | 是，选最新 ≤ 区间上界 | 倾向最新 |

**Russ Cox 的设计哲学**：
> "依赖解析不应有惊喜。开发者升级一个库，不应导致另一个无关库被偷偷升级。"

MVS 做到了：
1. **稳定性**：除非你显式 `go get foo@latest`，没人会自动升你；
2. **可重现**：go.mod 完全确定构建结果，go.sum 只校验内容；
3. **易调试**：只要看每条 require 的版本就能算出最终选谁，不需要回溯。

**代价**：
- 不会自动给你"最新版"——你得手动 `go get -u ./...`
- 主版本变更（v2+）走 import path 改名（`/v2`），不能像 npm 同时跑多个 major

**对照 npm**：npm 解析时若 A 要 lodash@^1，B 要 lodash@^2，会在 node_modules 里同时安装两份。Go 不允许；同一 import path 同时只能一个版本，跨 major 必须改 path。

📎 **深入阅读**: [G17-精通-Go-Modules](../G17-精通-Go-Modules.md)

**常见追问**：
- Q: go.sum 是 lockfile 吗？  A: 不是，只是哈希数据库（校验下载内容未篡改）。go.mod 已经"锁"了版本。
- Q: 怎么看为什么某版本被选中？  A: `go mod why -m github.com/foo/bar` 显示导入链。
- Q: MVS 不会选不到最新？  A: 对，要主动 `go get -u`，团队靠定期统一升级。

**陷阱**：误以为 `go get foo` 会升级所有依赖；实际上只升级 foo 一个 + 它的依赖（按需）；批量升级要 `go get -u ./...`。

### Q23 ⭐⭐⭐⭐ Go 1.24 `tool` 指令解决了什么问题（vs 老的 tools.go pattern）

**答**：

**老问题**：Go 工程经常需要工具链上的辅助二进制（`stringer`、`mockgen`、`protoc-gen-go`、`golangci-lint`），但 `go.mod` 只管"代码依赖"，工具的版本管理一直靠 hack。

**老方案：tools.go pattern**：

```go
//go:build tools
// +build tools

package tools

import (
    _ "golang.org/x/tools/cmd/stringer"
    _ "github.com/golang/mock/mockgen"
)
```

- 一个空文件，build tag 隔离让生产构建忽略
- 通过 import 让 `go.mod` 收录工具的版本
- `go install golang.org/x/tools/cmd/stringer` 自己装

**痛点**：
1. 工具变成 indirect 依赖，go.mod 里看不出"它是工具"还是"运行时依赖"
2. 安装要单独 `go install ...@版本`，版本可能和 go.mod 不一致
3. 工具的传递依赖污染 main module 的依赖树

**Go 1.24 新指令 `tool`**：

```go.mod
go 1.24

require (
    github.com/foo/lib v1.2.3
)

tool (
    golang.org/x/tools/cmd/stringer
    github.com/golang/mock/mockgen
)
```

**新能力**：
1. `go tool` 直接运行：`go tool stringer -type=Color`，自动选 go.mod 里固定的版本
2. `go install tool` 批量安装工具
3. 工具的依赖**与 main module 隔离**，不会污染 go.sum 的关键部分
4. 工具的版本号写在 require 段（普通依赖那样），但 `tool` 段标记它是工具

**迁移**：
```bash
# 删 tools.go，直接编辑 go.mod
go get -tool golang.org/x/tools/cmd/stringer@latest
# 等价于
go mod edit -tool golang.org/x/tools/cmd/stringer
go mod tidy
```

**Makefile 简化**：
```makefile
# 老
generate:
	go install golang.org/x/tools/cmd/stringer@v0.20.0
	$(GOPATH)/bin/stringer -type=Color

# 新
generate:
	go tool stringer -type=Color
```

📎 **深入阅读**: [G17-精通-Go-Modules](../G17-精通-Go-Modules.md)

**常见追问**：
- Q: 团队还没全员 1.24 怎么办？  A: 维持 tools.go pattern；Go 1.24 是稳定后的现代写法。
- Q: tool 指令支持工具的版本独立升级吗？  A: 支持，`go get -tool foo@v1.2.3`。
- Q: 多个项目共享同一工具版本？  A: 把工具 module 抽成内部 module，各项目 require + tool 引用。

**陷阱**：`go tool` 找不到的工具是因为没 `go install tool` 过，新克隆仓库时记得跑一次。

### Q24 ⭐⭐⭐ GOPROXY / GOSUMDB / GOPRIVATE 怎么配私有仓库

**答**：

Go module 下载链路：

```
go get foo/bar
    ↓
GOPROXY (https://proxy.golang.org,direct)
    ↓ 拉取 zip / mod
GOSUMDB (sum.golang.org)
    ↓ 校验内容哈希
$GOPATH/pkg/mod
```

**关键环境变量**：

**GOPROXY**：module 代理列表，逗号分隔，按顺序尝试。
```bash
GOPROXY=https://proxy.golang.org,https://goproxy.cn,direct
```
- `direct` 表示"直接走 VCS"（git / hg）
- `off` 禁止下载，离线模式
- 公司内网常自建 Athens / JFrog / 七牛 goproxy

**GOSUMDB**：哈希数据库地址，用于校验下载内容未被篡改。
- `sum.golang.org`（默认）
- `off` 关闭校验（不推荐，私有 module 必关）

**GOPRIVATE**：通配符，**这些路径**绕过 GOPROXY 和 GOSUMDB。
```bash
GOPRIVATE=*.corp.example.com,github.com/myorg/*
```

**GONOPROXY** / **GONOSUMDB**：单独控制（一般直接用 GOPRIVATE 一把搞定）。

**典型企业配置**：

```bash
# ~/.netrc 或 git credential helper 处理认证
# 公司 GitLab + 公网开源
export GOPROXY=https://goproxy.corp.example.com,https://proxy.golang.org,direct
export GOSUMDB=sum.golang.org
export GOPRIVATE=*.corp.example.com,gitlab.corp.example.com/*
```

**写入 go env**：
```bash
go env -w GOPROXY=https://goproxy.cn,direct
go env -w GOPRIVATE=github.com/myorg/*
```

**私有仓库认证**：
- HTTPS：`~/.netrc` 或 `git config --global url."https://user:token@github.com/".insteadOf "https://github.com/"`
- SSH：在 `~/.gitconfig` 改 url 替换
```
[url "git@github.com:"]
    insteadOf = https://github.com/
```

**常见问题**：

1. **下载 401**：GOPRIVATE 没配，Go 试图通过公共 proxy 拉私仓 → 没权限。
2. **校验失败 `sumdb error`**：私仓没加 GOPRIVATE 又开了 GOSUMDB。
3. **下载慢**：海外开发用 `goproxy.cn` 加速。

📎 **深入阅读**: [G17-精通-Go-Modules](../G17-精通-Go-Modules.md)

**常见追问**：
- Q: GOPROXY 的 `direct` 必须放最后吗？  A: 一般放最后做兜底；放前面会让所有请求走 VCS。
- Q: 公司搭 goproxy 用什么？  A: Athens（开源）、JFrog Artifactory、阿里云 / 七牛企业版。
- Q: `GOFLAGS=-mod=mod/-mod=vendor` 啥关系？  A: 控制 build 是否用 vendor 目录；与 proxy 无关。

**陷阱**：把私有仓加进 GOPROXY 列表（错误）而不是 GOPRIVATE（正确）——前者只是当 proxy 备选，仍会走 sumdb。

## 速记表

### pprof 五种 profile 用途

| Profile | 看什么 | 开销 | 典型问题 |
|---------|-------|------|---------|
| **CPU** | 函数 CPU 时间 | 1-3% | 算法热点 / 业务慢 |
| **heap** | 当前/累计堆分配 | 几乎免费（采样） | 内存泄漏 / GC 压力 |
| **goroutine** | 所有 G 栈快照 | 一次性，O(G) | goroutine 泄漏 / 死锁 |
| **block** | chan/sync 阻塞 | 视 rate 而定 | 偶发延迟 / 等待瓶颈 |
| **mutex** | 锁竞争 | 视 fraction 而定 | 全局锁热点 |

### unsafe.Pointer 六条规则

| # | 规则 | 用途 |
|---|------|------|
| 1 | `*T1 ↔ *T2`（同/小尺寸） | 类型重解释 |
| 2 | `Pointer → uintptr` | 仅显示用 |
| 3 | 算术运算同行内完成 | 指针偏移 |
| 4 | syscall 参数 uintptr | runtime 特殊保证 |
| 5 | `reflect.Value.Pointer` 立即转回 | 反射拿地址 |
| 6 | `SliceHeader.Data` 立即处理 | 已被 `unsafe.Slice/String` 取代 |

### go.mod 指令速查

| 指令 | 作用 | 是否传递下游 |
|------|------|-------------|
| `require` | 声明依赖 | 是 |
| `replace` | 重定向 module 来源 | 否（仅当前 module） |
| `exclude` | 禁用某版本 | 否 |
| `retract` | 自家版本召回 | 是（影响下游 go get） |
| `tool` (1.24+) | 声明构建工具 | 否 |
| `go` | 语言版本要求 | 取最大 |
| `toolchain` (1.21+) | 自动选用 go 版本 | 由 main 决定 |

### 环境变量速查

| 变量 | 作用 |
|------|------|
| `GOPROXY` | module 代理列表 |
| `GOSUMDB` | 哈希校验数据库 |
| `GOPRIVATE` | 私有模块通配（绕过 proxy + sumdb） |
| `GONOPROXY` / `GONOSUMDB` | 细粒度控制 |
| `GOFLAGS` | 全局 go 命令默认参数 |
| `GOEXPERIMENT` | 启用实验特性（如 synctest） |

## 高频陷阱清单

1. **benchmark 测出 0.5ns/op 不是真快**：编译器消除了，加 sink 变量或用 `for b.Loop()`（Go 1.24+）。
2. **benchmark 不用 `-count=10` + benchstat**：单次结果误差大于优化幅度，结论无效。
3. **CPU profile 看不到 syscall 时间**：被阻塞的 G 不占 CPU，要用 trace 看墙钟。
4. **heap profile 累计 vs 当前混用**：`alloc_*` 看 GC 压力，`inuse_*` 看泄漏，别张冠李戴。
5. **block/mutex rate 写错**：`SetBlockProfileRate(1)` = 100% 采，不是关闭；生产环境推荐 1us~1ms 阈值。
6. **`uintptr` 中间持有指针**：GC 不跟踪 uintptr，对象可能失效；指针算术必须单条语句完成。
7. **零拷贝 string→[]byte 后写入**：string 可能位于只读段，写它直接 SIGSEGV；零拷贝只用于只读。
8. **t.Parallel + t.Setenv**：直接 panic；要并发 + 不同 env 只能 fork 进程。
9. **1.22 之前的循环变量 + Parallel**：所有子测试共享最后一个 case；记得 `tt := tt` 或升级 1.22+。
10. **生产 go.mod 留 replace 指向本地路径**：CI / 别人的机器编译失败；上线前 `go mod edit -dropreplace`。
11. **私有仓库没配 GOPRIVATE**：Go 尝试走公共 sumdb 校验 → 失败；GOPROXY 配进去是错的，要用 GOPRIVATE。
12. **fuzz 只检查 "不 panic"**：99% 的 bug 漏掉；必须断言不变量（round-trip / 单调 / 长度等）。
