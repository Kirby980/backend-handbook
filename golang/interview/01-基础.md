## §1 变量、常量、类型

### Q1 ⭐⭐⭐ var、:=、const 几种声明形式的区别（包级变量为什么不能用 :=）

**答**：

Go 有四种声明形式，各自定位不同：

- **`var x T`**：声明 + 零值初始化，类型显式。包级和函数级都能用。
- **`var x = expr`**：声明 + 推导类型。包级和函数级都能用。
- **`x := expr`**：**短变量声明**，等价于 `var x = expr`。**只能在函数内部使用**。
- **`const x = expr`**：编译期常量，必须由常量表达式初始化。

**包级为什么不能用 `:=`**：Go 语法规则上，`:=` 是 **`ShortVarDecl`**，只允许出现在函数体（更精确说是 `Block` 里）。包级声明必须显式声明关键字，方便编译器构造**包级变量初始化顺序图**——根据依赖关系决定 `init()` 之前的求值顺序。如果允许 `:=`，会引入解析歧义并破坏初始化顺序的可预测性。

```go
package main

var a = 10        // OK
var b int = 20    // OK
// c := 30        // 编译错误: non-declaration statement outside function body

func f() {
    d := 40       // OK
    _ = d
}
```

`:=` 还有个常用规则：左侧多变量时，**至少有一个是新变量**就合法，其他变量做重新赋值。

📎 **深入阅读**: [G01-精通-Go-变量-常量与-iota-习语](../G01-精通-Go-变量-常量与-iota-习语.md)

**常见追问**：
- Q: `var (a = 1; b = 2)` 这种分组声明和单独写有区别吗？  A: 没本质区别，只是组织代码用，编译后等价。
- Q: 函数内 `x := 1; x := 2` 报错吗？  A: 报错，第二个 `:=` 没有新变量。

**陷阱**：在 if/for 的初始化子句里用 `:=` 会创建**该语句作用域内的新变量**，可能 shadow 外层同名变量，go vet 会警告。

### Q2 ⭐⭐⭐ Go 的零值机制是什么？哪些类型零值是 nil？

**答**：

Go 规定**任何变量被声明但未显式初始化时，都会被赋予该类型的零值**——不存在 C 那种"未初始化内存"。这让代码不依赖初始化顺序、更安全。

零值对照表：

| 类型 | 零值 |
|---|---|
| bool | `false` |
| 数值（int/float/complex 等） | `0` |
| string | `""`（空串，但 len=0 且不是 nil） |
| pointer | `nil` |
| function | `nil` |
| interface | `nil`（type 和 value 都为 nil） |
| channel | `nil` |
| slice | `nil`（header 三元组全 0） |
| map | `nil` |
| struct | 每个字段递归零值 |
| array | 每个元素递归零值 |

**零值是 nil 的 6 种内建类型**：pointer、function、interface、channel、slice、map；`unsafe.Pointer` 同理但属 unsafe 包。背口诀：**"指函接、通切映"**。

零值能用的优势：`var mu sync.Mutex` 直接可用、`var buf bytes.Buffer` 直接 Write、`var b strings.Builder` 直接拼接。这是 Go API 设计的重要哲学——尽量让零值开箱即用。

📎 **深入阅读**: [G01-精通-Go-变量-常量与-iota-习语](../G01-精通-Go-变量-常量与-iota-习语.md)

**常见追问**：
- Q: nil map 能读吗？能写吗？  A: 能读（返回零值），写会 panic。
- Q: nil slice 能 append 吗？  A: 能，会分配新底层数组。
- Q: nil channel 读写会怎样？  A: 永久阻塞（select 里常用作禁用某 case 的手段）。

**陷阱**：`var m map[string]int; m["a"] = 1` 直接 panic，要先 `m = make(...)`。这是最经典的新手 bug。

### Q3 ⭐⭐⭐⭐ iota 习语：写一个 KB/MB/GB 常量组、写一个位掩码常量组

**答**：

`iota` 是 Go 中**编译期常量计数器**：在每个 `const (...)` 块里从 0 开始，每出现一行常量声明 +1（注意是**行**，不是每用一次 iota）。

**KB/MB/GB（左移技巧）**：

```go
const (
    _  = iota // 跳过 0
    KB = 1 << (10 * iota) // 1 << 10
    MB                    // 1 << 20
    GB                    // 1 << 30
    TB                    // 1 << 40
    PB                    // 1 << 50
    EB                    // 1 << 60
)
```

后面几行省略了表达式，会**复用上一行的表达式模板**，但 iota 值递增——这是 iota 最优雅的用法。

**位掩码（权限标志）**：

```go
type Permission uint8

const (
    Read    Permission = 1 << iota // 1 (0001)
    Write                          // 2 (0010)
    Execute                        // 4 (0100)
    Delete                         // 8 (1000)
)

// 组合
all := Read | Write | Execute
// 判断
has := all&Write != 0
// 移除
all &^= Execute  // AND NOT
```

**注意点**：
- iota 只在 `const (...)` 内有效，函数内裸用不行。
- 每个 const 块独立计数，从 0 开始。
- 跨行复用表达式需要严格相同的"模板"，多写少写一个操作数都不行。

📎 **深入阅读**: [G01-精通-Go-变量-常量与-iota-习语](../G01-精通-Go-变量-常量与-iota-习语.md)

**常见追问**：
- Q: `const (a=iota; b; c=iota+10; d)` 各是多少？  A: a=0, b=1, c=12, d=13。
- Q: 用 iota 生成自增枚举字符串怎么搞？  A: `//go:generate stringer -type=Color`。

**陷阱**：iota 计数是**按行**的，空行和注释行不算，但 `_` 占位行算。

### Q4 ⭐⭐⭐⭐ 无类型常量是什么？为什么 `const a = 1.0; var b int = a` 不报错？

**答**：

Go 的常量分两种：

- **typed constant**：`const x int = 1`，类型固定。
- **untyped constant（无类型常量）**：`const x = 1`，没有显式类型，只有**默认类型**（如整数字面量默认 int，浮点字面量默认 float64）。

无类型常量的特点是**保持高精度**且**赋值时按需转换**——它有自己的 **kind**（整型 kind / 浮点 kind / 复数 kind / 字符串 kind / 布尔 kind / rune kind），运算时按 kind 兼容。

回到题目：
```go
const a = 1.0      // 无类型浮点常量，但值在 int 表示范围内
var b int = a      // 编译期检查：1.0 可以无损转为 int，所以合法
```

如果换成 `const a = 1.5`，赋给 int 就会报 `constant 1.5 truncated to integer`。

更骚的例子：
```go
const Pi = 3.14159265358979323846264338327950288419716939937510 // 50 位精度
var f float64 = Pi   // 截断到 float64 精度，无错
var d float32 = Pi   // 截断到 float32，无错
```

无类型常量让 `1 << 60` 这种表达式不会因为 int 默认宽度而溢出——只在赋值或类型断言点才检查。

📎 **深入阅读**: [G01-精通-Go-变量-常量与-iota-习语](../G01-精通-Go-变量-常量与-iota-习语.md)

**常见追问**：
- Q: `var x = 1` 中 1 是什么类型？  A: 1 是无类型整型常量，赋值给 x 时被赋予默认类型 int。
- Q: 无类型常量能存在变量里吗？  A: 不能，一旦赋给变量就具备了类型。

**陷阱**：`var x int32 = 1; var y int64 = x + 1` 报错（int32 + 无类型 1 → int32，不能赋给 int64），但 `var y int64 = 1 + 1` 没事（纯常量表达式）。

### Q5 ⭐⭐⭐ new(T) 和 make(T) 的区别（含返回类型差异）

**答**：

两者都用来分配，但定位完全不同：

| 维度 | `new(T)` | `make(T, args...)` |
|---|---|---|
| 适用类型 | 任意类型 T | **仅 slice / map / channel** |
| 返回值 | `*T`（指针） | `T`（值，而非指针） |
| 初始化 | 分配并清零（T 的零值） | 分配并**初始化内部结构**（如 slice 的 header、map 的 hmap、chan 的 hchan） |
| 典型用法 | `p := new(int)` | `s := make([]int, 0, 10)` |

举例对比：
```go
// new
p := new(int)      // *int, 指向值为 0 的 int
*p = 42

s1 := new([]int)   // *[]int，指向一个 nil slice
// *s1 = append(*s1, 1) // 能用，但很别扭

// make
s2 := make([]int, 0, 10) // []int，len=0 cap=10 的可用 slice
m := make(map[string]int) // map[string]int，可直接写

// 注意：new(map) 出来的是 *map，且内部 map 是 nil，不能写
mp := new(map[string]int)
// (*mp)["a"] = 1 // panic: assignment to entry in nil map
```

实际工程中：

- **slice / map / chan 用 make**，几乎没有例外。
- **new(T) 用得不多**——`&T{}`、`&Foo{Name: "x"}` 更直观、还能初始化字段。

📎 **深入阅读**: [G01-精通-Go-变量-常量与-iota-习语](../G01-精通-Go-变量-常量与-iota-习语.md)

**常见追问**：
- Q: `new(int)` 和 `var x int; &x` 等价吗？  A: 语义上等价，编译器可能都做逃逸分析后分配在堆上。
- Q: make 一定堆分配吗？  A: 不一定，逃逸分析决定。比如 `make([]int, 4)` 在函数内闭包未捕获时可能栈上分配。

**陷阱**：把 `new(map[K]V)` 当 `make(map[K]V)` 用——返回的是 nil map 的指针，写入就 panic。

## §2 字符串与 byte/rune

### Q6 ⭐⭐⭐⭐ string 的底层结构？为什么不可变？

**答**：

Go 中 `string` 是一个**只读字节序列**，底层结构（`reflect.StringHeader`，注意 Go 1.20+ 已 deprecated 但模型不变）：

```go
type stringHeader struct {
    Data uintptr // 指向底层字节数组
    Len  int     // 字节数
}
```

64 位平台上一共 **16 字节**（指针 8 + int 8）。

**为什么不可变**：
1. **运行时保证**：没有任何标准库函数返回可写入的 `string`。`s[0] = 'A'` 编译期就拒绝（`cannot assign to s[0]`）。
2. **内存模型简化**：不可变 → 可以共享底层内存。字符串常量被池化在只读段；切片 `s[2:5]` 不复制底层，只改 Data/Len。
3. **并发安全**：多 goroutine 读同一个 string 永远安全，编译器和运行时无需插入同步。
4. **map key 友好**：哈希值可以缓存，不需要担心 key 中途被改。

**只读体现在哪儿**：
- 字符串字面量编译后放进只读数据段（`.rodata`），尝试写会段错误（Go 里因编译器拦截不会到那一步）。
- 函数传 string 是**值传递这个 16 字节 header**，但底层数据不复制——所以传 1MB 的 string 也很快。

不过这个"不可变"是**语言层面的**，用 `unsafe.Pointer` 是可以打破的，但属于自找麻烦（写一个被池化的字面量直接段错误）。

📎 **深入阅读**: [G02-精通-Go-数据类型-Rune-与字符串内幕](../G02-精通-Go-数据类型-Rune-与字符串内幕.md)

**常见追问**：
- Q: `s := "hello"; t := s` 复制了底层字节吗？  A: 没有，只复制了 16 字节 header。
- Q: string 比较是什么复杂度？  A: O(n) 字节比较，但短路：长度不等直接 false；指针相同直接 true（编译器优化）。

**陷阱**：用 `unsafe.String(unsafe.SliceData(b), len(b))` 把 `[]byte` 零拷贝转 string，必须保证之后绝不修改 b，否则违反不可变契约。

### Q7 ⭐⭐⭐⭐ len(s) 返回的是字节数还是字符数？怎么数字符？

**答**：

`len(s)` 返回 **string 的字节数**（即 StringHeader.Len 字段），不是"字符数"。

UTF-8 编码下，一个"字符"（更精确说是 **rune**，Unicode 码点）可能占 1-4 字节：
- ASCII 字符（如 `'A'`, `'1'`）：1 字节
- 拉丁扩展（如 `'é'`）：2 字节
- 常用汉字（如 `'中'`）：3 字节
- 表情符号（如 `'🎉'`）：4 字节

```go
s := "hello, 中国"
fmt.Println(len(s))                          // 13 (5 + 2 + 2*3)
fmt.Println(utf8.RuneCountInString(s))       // 9 (h,e,l,l,o,',',' ',中,国)
fmt.Println(len([]rune(s)))                  // 9，但有分配开销
```

**统计 rune 的几种方法**：

| 方法 | 是否分配 | 适用 |
|---|---|---|
| `utf8.RuneCountInString(s)` | 否 | **首选**，零分配 |
| `len([]rune(s))` | 是（转换分配） | 后续还要 indexing rune 才用 |
| `for range s` 计数 | 否 | 顺手做其他事 |

**注意 grapheme cluster**：用户视觉上的"一个字符"可能由多个 rune 组成，比如 `é` 可以是单 rune（U+00E9），也可以是 e + 组合用尖音符（U+0065 U+0301）。表情如 👨‍👩‍👧‍👦 由 7 个 rune 组成。要数视觉字符得用第三方库（如 `rivo/uniseg`），标准库目前没有。

📎 **深入阅读**: [G02-精通-Go-数据类型-Rune-与字符串内幕](../G02-精通-Go-数据类型-Rune-与字符串内幕.md)

**常见追问**：
- Q: `s[0]` 是 byte 还是 rune？  A: byte。`for i := 0; i < len(s); i++ { s[i] }` 是按字节遍历。
- Q: `for i, c := range s` 中 i 和 c 是什么？  A: i 是**字节索引**（不连续！），c 是 rune。

**陷阱**：截取中文 `s[:3]` 可能切到一个汉字的中间，得到无效 UTF-8。要截"前 3 个汉字"得用 rune 切。

### Q8 ⭐⭐⭐⭐ string 和 []byte 互转的代价？有哪些零拷贝场景（编译器优化）？

**答**：

通常 `string ↔ []byte` 互转**会复制底层数据**，复杂度 O(n)、伴随一次堆分配。原因是 string 不可变而 []byte 可变，所以默认必须复制以保证语义安全。

但编译器对几种**只读场景**做了零拷贝优化：

1. **map 查找 key**：`m[string(b)]`，编译器知道 string 临时值只用于查找，不会逃逸，直接用 b 的底层数据。
2. **string 比较**：`if string(b) == "foo"` 同理。
3. **`for range` 遍历**：`for i, c := range string(b)` 编译器优化为按字节解码。
4. **`+` 拼接的小段**：有时也会避免中间拷贝。
5. **`strings.Builder.Write([]byte)` + `String()`**：Builder 内部用 unsafe 复用 byte slice 的内存。

**显式零拷贝**（Go 1.20+ 提供安全 API）：

```go
import "unsafe"

// []byte → string 零拷贝
s := unsafe.String(unsafe.SliceData(b), len(b))

// string → []byte 零拷贝
b := unsafe.Slice(unsafe.StringData(s), len(s))
```

**用 unsafe 转换的红线**：
- 转换得到的 string 之后**不能修改原 []byte**（违反 string 不可变）。
- 转换得到的 []byte **不能写入**（如果 string 来自字面量，写入只读段直接 SIGSEGV）。
- 这俩 API 是 unsafe 的"次坏选择"——比纯 reinterpret 安全（明确传 data/len），但仍需自己保证不变量。

工程上：单次小转换不必优化（编译器都帮你做了）；如果是 **hot path 上的大块转换**（比如解析协议），用 `unsafe.String` / `unsafe.Slice` 可显著降分配。

📎 **深入阅读**: [G02-精通-Go-数据类型-Rune-与字符串内幕](../G02-精通-Go-数据类型-Rune-与字符串内幕.md)

**常见追问**：
- Q: `bytes.Equal(b, []byte(s))` 会分配吗？  A: 分配。换成 `bytes.Equal(b, []byte("foo"))` 编译器优化为 string 比较。
- Q: `json.Unmarshal` 拿到的 string 字段是 input []byte 的零拷贝引用吗？  A: 不是，是新分配的（避免持有大缓冲）。

**陷阱**：从一个 sync.Pool 拿出的 buffer，用 unsafe 拼出 string 返回出去，把 buffer 还回去后 string 内容会被复用——典型踩坑场景。

### Q9 ⭐⭐⭐ 字符串拼接的几种方式与性能权衡（+ / fmt.Sprintf / strings.Builder / bytes.Buffer）

**答**：

四种主流方式，按场景选：

| 方式 | 适用 | 性能 | 备注 |
|---|---|---|---|
| `s1 + s2` | 已知少量片段、编译期常量拼接 | 编译期常量拼接为 0 开销；运行期 n 段拼接 O(总长 × n) | 每次拼接生成新 string |
| `fmt.Sprintf` | 格式化输出（需要 %d / %v 等） | 慢，反射 + 接口装箱 | 别用来拼简单字符串 |
| `strings.Builder` | **首选**循环/未知段数 | O(总长) 摊销，避免重复复制 | Go 1.10+，Builder 不可拷贝 |
| `bytes.Buffer` | 需要 io.Writer 接口、中途读 | 比 Builder 慢一点（需要把 byte 转 string） | 历史包，能用 Builder 就用 Builder |
| `strings.Join` | 已经在 slice 里 | 一次性预算总长，最快 | 比手动循环 Builder 简洁 |

**代码对比**：

```go
// 烂：n 次拷贝
s := ""
for _, p := range parts {
    s += p
}

// 好：strings.Builder
var b strings.Builder
b.Grow(estimatedSize) // 重要！预分配避免多次扩容
for _, p := range parts {
    b.WriteString(p)
}
result := b.String()

// 已知列表：最简洁
result := strings.Join(parts, ",")
```

**Builder.Grow 的意义**：Builder 内部是一个 []byte，append 增长策略和 slice 一致。如果你知道总长，提前 Grow 能避免多次 2x 扩容，性能差可达 3-5 倍。

**Builder vs Buffer**：Builder 的 `String()` 用 `unsafe` 把 []byte 直接 reinterpret 为 string（因为之后承诺不再修改），零拷贝；Buffer.String() 必须复制。

📎 **深入阅读**: [G02-精通-Go-数据类型-Rune-与字符串内幕](../G02-精通-Go-数据类型-Rune-与字符串内幕.md)

**常见追问**：
- Q: Builder 为什么不能拷贝？  A: 拷贝后两个 Builder 共享底层 []byte，但 Builder 的 String() 用 unsafe 转换依赖独占，会出错。`go vet` 会报错。
- Q: 拼接 2 段 string 用什么？  A: 直接 `a+b`，编译器认得。

**陷阱**：`fmt.Sprintf("%s%s", a, b)` 比 `a+b` 慢一个数量级。简单拼接千万别用 Sprintf。

## §3 Slice

### Q10 ⭐⭐⭐⭐ slice 的底层结构（SliceHeader 三元组）？在 64 位上多大？

**答**：

slice 的底层是个 **header 三元组**（`runtime.slice` 在源码里）：

```go
type slice struct {
    array unsafe.Pointer // 指向底层数组
    len   int            // 当前长度
    cap   int            // 当前容量
}
```

64 位平台上：指针 8 + int 8 + int 8 = **24 字节**。

理解这个布局，很多行为就清晰了：

- **传 slice 是传 24 字节 header 的值拷贝**——所以函数内 `s = append(s, x)` 不会改外面的 slice header，但**可能改共享的底层数组**。
- **`s := []int{}` 和 `var s []int`**：前者 array 指向某个 0 长度的占位数组（非 nil），后者 array 为 nil。
- **`s[i]` 越界**：编译器/运行时插入 `0 <= i < len` 检查，越界 panic（`runtime error: index out of range`）。
- **`s[i:j]`**：生成新 header，array 指针偏移 i*sizeof(T)，新 len=j-i，新 cap=原 cap - i。

可视化：
```
slice header (24 bytes)        backing array
+-------+---+---+
| array | 3 | 5 |               [_, _, _, _, _]
+---+---+---+---+               ^
    |                           |
    +---------------------------+
```

slice 是 Go 里**最常见的 24 字节值**，理解它是后续 append、扩容、共享底层数组等所有问题的基础。

📎 **深入阅读**: [G03-精通-Go-切片-底层结构与扩容机制](../G03-精通-Go-切片-底层结构与扩容机制.md)

**常见追问**：
- Q: slice 的 0 值能 append 吗？  A: 能，append 检测 nil 会分配新底层数组。
- Q: `unsafe.Sizeof(s)` 返回多少？  A: 24（在 64 位平台），与底层数组长度无关。

**陷阱**：把 slice 传到协程然后在外层 append，可能造成数据竞争——header 是 24 字节的值，但底层数组是共享的。

### Q11 ⭐⭐⭐⭐⭐ slice 扩容机制？Go 1.18 前后阈值变化？为什么阈值从 1024 降到 256？

**答**：

slice 扩容发生在 `append` 超过 cap 时。运行时根据**新需要的 cap** 和**当前 cap** 计算新 cap，然后分配新底层数组、复制旧元素。

**算法演进**（按 Go 版本）：

- **Go 1.17 及之前**：cap < 1024 时翻倍；cap ≥ 1024 时按 1.25x 增长。
- **Go 1.18+**：**阈值降到 256**。具体公式（简化版）：
  - cap < 256：翻倍（2x）
  - cap ≥ 256：`newcap = oldcap + (oldcap + 3*256) / 4`（约 1.25x，但起点偏移以平滑过渡）

最终还会经过 **size class 对齐**：把字节数 round 到 `mallocgc` 的 size class，所以实际 cap 可能比公式算出来的还大一点。

**为什么从 1024 降到 256**：

1. **内存利用率**：旧策略下 1024 之前一直 2x，意味着持续到 1024 都翻倍，浪费大。降到 256 让"温和增长"更早接管。
2. **真实负载分析**：Google 内部测过大量 Go 服务，发现 slice 容量分布在 256-1024 这个区间最密集——把策略切换点放在 256 能让大部分 slice 走更省内存的路径。
3. **配合 size class**：mallocgc 的 size class 在中等大小区间粒度较细，1.25x 更容易命中相邻 class，减少内部碎片。

**示例**：
```go
s := make([]int, 0)
for i := 0; i < 1500; i++ {
    s = append(s, i)
    if cap(s) != prevCap {
        fmt.Println(len(s), cap(s)) // 观察增长曲线
        prevCap = cap(s)
    }
}
// Go 1.18+ 大致：1 2 4 8 16 32 64 128 256（之后温和）
// 注意 256 之后的 cap 会被 size class 拉齐，不是严格 1.25
```

工程实践：**已知最终 size 就用 `make([]T, 0, n)` 预分配**，避免多次扩容。批量 append 大块数据时这能差 3-5 倍性能。

📎 **深入阅读**: [G03-精通-Go-切片-底层结构与扩容机制](../G03-精通-Go-切片-底层结构与扩容机制.md)

**常见追问**：
- Q: `make([]int, 5)` 之后再 append 第 6 个元素，cap 变成多少？  A: 10（2x，因为 5 < 256）。
- Q: 一次 append 多个元素超过 cap，扩容算法还是 2x 吗？  A: 不是，会先取 max(needed, computed)，确保一次到位。

**陷阱**：依赖具体的扩容数字（"cap 从 100 涨到 200"）写测试，跨版本会坏。只能依赖"cap >= len"和"会增长"两个语义。

### Q12 ⭐⭐⭐⭐ nil slice vs empty slice 的差异（含 JSON 序列化）

**答**：

两者长度都为 0，但本质有差：

```go
var n []int            // nil slice: header = {nil, 0, 0}
e := []int{}           // empty slice: header = {<somePtr>, 0, 0}
e2 := make([]int, 0)   // empty slice，等价于上面

n == nil   // true
e == nil   // false
len(n)     // 0
len(e)     // 0
```

**行为一致的部分**：`len`、`cap`、`for range`、`append`——都一样。

**行为不同的部分**：

1. **`== nil` 判断**：业务里要不要区分 "没传" vs "传了空数组"，就用这个区分。
2. **JSON 序列化**：
   ```go
   json.Marshal(map[string][]int{"a": nil})      // {"a":null}
   json.Marshal(map[string][]int{"a": []int{}}) // {"a":[]}
   ```
   前端拿到 `null` 和 `[]` 处理逻辑可能完全不同。
3. **protobuf 序列化**：通常都序列化为空数组，但具体看实现。
4. **指针打印**：`%p` 输出 nil slice 是 `0x0`，empty slice 是某个堆地址（或编译器选的占位地址）。

**推荐风格**：

- 函数返回**没找到结果**或**真正没数据**时，返回 nil slice（更省内存，header 只有 24 字节也是 24 字节，但 backing array 不分配）。
- 调用方判断空用 `len(s) == 0`，**不要用 `s == nil`**——两种空都覆盖。
- 需要保证 JSON 输出 `[]` 而非 `null` 时，**显式初始化 `[]T{}`**。

📎 **深入阅读**: [G03-精通-Go-切片-底层结构与扩容机制](../G03-精通-Go-切片-底层结构与扩容机制.md)

**常见追问**：
- Q: nil slice append 之后还是 nil 吗？  A: 不是，append 会分配底层数组并返回新 header。
- Q: `reflect.DeepEqual(nil_slice, empty_slice)` 是 true 还是 false？  A: false，DeepEqual 区分 nil。

**陷阱**：前后端联调时返回 `null` 让前端报错——后端要么显式 `[]T{}`，要么改 JSON tag 加 omitempty 自洽。

### Q13 ⭐⭐⭐⭐⭐ slice 别名陷阱：append 何时返回新底层数组？三索引切片 `s[i:j:k]` 用途？

**答**：

**别名陷阱**：`s2 := s1[2:5]` 创建的 s2 与 s1 共享底层数组。改 s2 的元素会改 s1 看到的值。

```go
s1 := []int{1, 2, 3, 4, 5}
s2 := s1[1:3]      // [2, 3]，cap=4
s2[0] = 99
fmt.Println(s1)    // [1, 99, 3, 4, 5]  ← 改了！
```

**append 何时返回新底层数组**：当 `append` 添加的元素数让 `len > cap` 时，运行时分配新底层数组并复制旧元素。**没超 cap 时仍共享**：

```go
s1 := make([]int, 3, 5)         // cap=5
s2 := s1[:3]                    // 共享，cap=5
s2 = append(s2, 99)             // len=4 <= cap=5，仍写入共享数组！
fmt.Println(s1[:4])             // [..., ..., ..., 99]
```

这是无数 bug 的来源：s2 看似独立，append 之后悄悄改了 s1 可见的数据。

**三索引切片 `s[i:j:k]`**：

`s[i:j:k]` 中 i 是起点、j 是结尾（exclusive）、**k 是 cap 边界**。生成的 slice header 是：
- array = &s[i]
- len = j - i
- cap = k - i

要求 `i <= j <= k <= cap(s)`。

```go
s1 := []int{1, 2, 3, 4, 5}     // len=5 cap=5
s2 := s1[1:3:3]                // len=2 cap=2
s2 = append(s2, 99)            // cap 不够，触发扩容，新底层数组
fmt.Println(s1)                // [1, 2, 3, 4, 5] ← 没被改
```

**典型用途**：
1. **暴露子 slice 时防止使用者通过 append 越界写到父 slice 的后续元素**。
2. 限制 cap 让 append 必扩容（即"复制语义"slice）。
3. 协议库返回数据时，"截断"读权限。

工程口诀：**返回 slice 给外部时，三索引切片更安全**：`return data[start:end:end]`。

📎 **深入阅读**: [G03-精通-Go-切片-底层结构与扩容机制](../G03-精通-Go-切片-底层结构与扩容机制.md)

**常见追问**：
- Q: `s2 := s1; s2 = append(s2, 1)` 会影响 s1 吗？  A: 取决于 cap：cap 够则修改共享底层数组（s1 看不见新增的，因为它的 len 没变，但若后续 s1 也 append 会冲突）；cap 不够则 s2 走了新数组，互不影响。
- Q: copy 是深拷贝吗？  A: 元素值的浅拷贝。元素本身是引用类型时不递归。

**陷阱**：从大切片切出小切片返回（`return huge[i:j]`），底层 huge 不能 GC——长期持有泄漏。要 `make + copy` 或 `slices.Clone`（Go 1.21+）。

### Q14 ⭐⭐⭐⭐ 函数参数传 slice 是值传递还是引用传递？

**答**：

**Go 只有值传递**，slice 也不例外——传递的是那个 **24 字节的 slice header**（array 指针 + len + cap）的副本。

但因为副本里的 array 指针指向**同一块底层数据**，函数内修改元素会影响外部，所以行为上**看起来像引用传递**：

```go
func modify(s []int) {
    s[0] = 99          // 改的是共享底层数组，外部可见
    s = append(s, 1)   // 修改的是 s 的副本 header，外部不可见
}

s := []int{1, 2, 3}
modify(s)
fmt.Println(s)         // [99, 2, 3]，注意没有 1 被加进来
```

**关键区分**：

| 操作 | 外部可见？ |
|---|---|
| `s[i] = v` | ✅ 共享底层数组 |
| `copy(s, ...)` | ✅ 写底层数组 |
| `s = append(s, v)` | ❌ 改的是局部 header |
| `s = s[:n]` | ❌ 改的是局部 header |
| `s = nil` | ❌ 同上 |

**要让外部看到 header 变化**，两种做法：

1. 函数返回新 slice，调用方接住：`s = modify(s)`（标准库的 append 就是这模式）。
2. 传 `*[]T`：`func modify(s *[]int) { *s = append(*s, 1) }`。

第一种更 idiomatic。

**slice 作为函数参数的成本**：
- 拷贝 24 字节（slice header）——比 []int{} 数组按值拷贝便宜得多。
- 不分配（除非 escape 到堆）。

📎 **深入阅读**: [G03-精通-Go-切片-底层结构与扩容机制](../G03-精通-Go-切片-底层结构与扩容机制.md)

**常见追问**：
- Q: map 传参是值还是引用？  A: 也是值传递，但 map 内部是个指针（`*hmap`），所以函数内修改 map 外部可见。
- Q: chan 呢？  A: 同 map，chan 本身是 hchan 指针。

**陷阱**："切片是引用类型"这个说法不严谨——Go 没有"引用类型"概念，只是 slice 内部有指针所以表现像引用。

## §4 Map

### Q15 ⭐⭐⭐⭐ map 为什么遍历无序？

**答**：

Go 的 `map` 在 `for range` 时**故意打乱起始 bucket**，遍历顺序不可预测。这是**语言规范明确规定**的，不是实现 bug。

**原因**：

1. **防止用户依赖顺序**：如果某版本恰好按插入顺序遍历，用户会写出依赖这个顺序的代码，未来版本一改就坏。Go 团队从 1.0 就主动随机化，把"无序"刻进契约。
2. **底层不维护顺序**：Go map 是哈希表（开放寻址 + bucket，Go 1.24+ Swiss Tables），key 按 hash 散布在桶里——本来就没有"顺序"概念。维护顺序要额外内存。
3. **rehash 后位置变化**：扩容会重新映射 key 位置，"插入顺序"难以保留。

**实现细节**：运行时遍历开始时，从一个随机 bucket、随机 cell 开始扫——不是真"随机"，是用一个伪随机数偏移起始点。

**要有序怎么办**：

```go
// 排序 key
keys := make([]string, 0, len(m))
for k := range m {
    keys = append(keys, k)
}
sort.Strings(keys)
for _, k := range keys {
    fmt.Println(k, m[k])
}

// 或用 Go 1.21+ 的 maps.Keys + slices.Sorted
import "maps"; import "slices"
sortedKeys := slices.Sorted(maps.Keys(m))
```

要保留**插入顺序**：标准库没现成 OrderedMap，自己 struct{ m map; keys []K } 包一层，或用第三方库（如 `elliotchance/orderedmap`）。

📎 **深入阅读**: [G04-精通-Go-Map-哈希内幕与并发](../G04-精通-Go-Map-哈希内幕与并发.md)

**常见追问**：
- Q: 同一个 map 多次遍历顺序一样吗？  A: 不一样，每次都随机。
- Q: 遍历期间删除当前 key 安全吗？  A: 安全（语言规范允许），且不影响后续遍历。

**陷阱**：测试里 `for k := range m` 然后断言"第一个是 a"——稳挂。

### Q16 ⭐⭐⭐⭐ map 并发读写为什么 panic？sync.Map 的适用场景？

**答**：

**Go 原生 map 不是并发安全的**：并发读写会触发 runtime 的**写并发检测**，直接 `fatal error: concurrent map writes` / `concurrent map read and map write`，**不可 recover**。

```go
m := make(map[int]int)
go func() { for { m[1] = 1 } }()
go func() { for { m[2] = 2 } }()
// fatal error: concurrent map writes
```

**原因**：
1. map 写操作可能触发**渐进式扩容**，扩容期间结构在变（迁移 bucket），并发读可能读到中间态。
2. runtime 在 mapassign / mapaccess 里检查一个 `hashWriting` 标志位，发现并发就主动 fatal——这是**主动崩溃**而非内存损坏，更利于发现 bug。

**并发安全的三个选择**：

| 方案 | 适用 | 性能特点 |
|---|---|---|
| `sync.Mutex` + map | 读写均衡、key 数量可控 | 简单粗暴，竞争激烈时慢 |
| `sync.RWMutex` + map | 读多写少（10:1 以上） | 读不互斥，写需独占 |
| `sync.Map` | **读多写少** + **写后基本不删** + key 集合稳定 | 内部 read-only + dirty 双 map，读路径无锁 |

**sync.Map 适用场景（官方文档明确）**：
1. **缓存读多写少**：连接池、配置项、metric 计数器。
2. **多个 goroutine 写不同 key**：避免单一 Mutex 瓶颈。
3. **key 集合稳定**：偶尔新增，频繁查询。

**sync.Map 不适用**：
- 写多读少 → 内部 dirty map 频繁升级，比 Mutex+map 更慢。
- 需要 len()、range（API 不直接提供 len，range 通过 Range 闭包）。
- key 频繁变化（每次新 key 都升级 dirty）。

```go
var m sync.Map
m.Store("a", 1)
v, ok := m.Load("a")
m.Range(func(k, v any) bool { return true })
m.Delete("a")

// Go 1.20+ 新增的强类型读写
v, loaded := m.LoadOrStore("b", 2)
v, loaded = m.LoadAndDelete("b")
v, ok := m.Swap("b", 3)
```

📎 **深入阅读**: [G04-精通-Go-Map-哈希内幕与并发](../G04-精通-Go-Map-哈希内幕与并发.md)

**常见追问**：
- Q: 并发读（无写）会 panic 吗？  A: 不会，并发读是安全的。
- Q: 用 atomic.Pointer 包 map 怎么样？  A: Copy-on-Write 模式，写少读多极致优化方案，但每次写都要复制全 map。

**陷阱**：以为 RWMutex 一定比 Mutex 快——RWMutex 自身开销更大，读临界区很短时反而更慢。

### Q17 ⭐⭐⭐⭐⭐ map delete 后内存会释放吗？怎么真正释放？

**答**：

**不会**。`delete(m, k)` 只是标记 key 不存在、释放该 key/value 的引用（让其可被 GC），**但 map 占据的 bucket 数组、overflow buckets 不会缩容**。

```go
m := make(map[int][]byte, 1000)
for i := 0; i < 1_000_000; i++ {
    m[i] = make([]byte, 1024)
}
for k := range m {
    delete(m, k)
}
// len(m) == 0，但 m 仍占着大量 bucket 数组的内存
```

**底层原因**：Go map 的 bucket 数组是**只增不减**的——扩容会重新分配更大的，但没"缩容"操作。原因有二：
1. 缩容要重新 hash 所有 key，成本高。
2. 经验上 map 大小往往再涨回去，缩了又长更亏。

**真正释放的几种方法**：

1. **置 nil 让整张 map 被 GC**（如果整张 map 不需要了）：
   ```go
   m = nil  // 整张 map 包括 bucket 数组可被 GC
   ```

2. **新建 map 替换**（保留语义，释放 bucket）：
   ```go
   m = make(map[K]V, expectedSize)
   ```

3. **`clear(m)` （Go 1.21+）**：清空所有 entry，**但仍不释放 bucket 数组内存**——只是把 entry 数清零，等同于循环 delete 但更快。要释放还是得 make 新的。

**优化场景**：
- **map 作为短期工作集**：用完后 `m = nil` 让 GC 回收。
- **map 是长期容器但 size 波动大**：周期性 `m = newMap` 重建。
- **map 在对象池里**：清空但保留 capacity 复用——`clear(m)` 合适。

**Swiss Tables 后（Go 1.24+）**：底层结构变了（group 取代 bucket），但**"不主动缩容"的语义仍然成立**——下层内存管理策略没变。

📎 **深入阅读**: [G04-精通-Go-Map-哈希内幕与并发](../G04-精通-Go-Map-哈希内幕与并发.md)

**常见追问**：
- Q: 用 pprof 看 map 内存怎么看？  A: heap profile 看 `runtime.makemap` 和 `runtime.mapassign` 的分配点。
- Q: GC 跑完 map 内存还高怎么办？  A: 99% 是没释放 map 本身，或还有 goroutine 持有引用。

**陷阱**：监控系统里 `map[ts]value` 作为 sliding window，光 delete 旧 key 内存只增不减——必须周期性整张换。

### Q18 ⭐⭐⭐⭐ Go 1.24+ Swiss Tables 改了什么？性能影响？

**答**：

Go 1.24 把 map 的底层从经典 **bucket 数组 + overflow chain** 换成了 **Swiss Tables**（受 Google Abseil flat_hash_map 启发）。

**Swiss Tables 是什么**：
- 把哈希表分成固定大小的 **group**（通常 8 个 slot）。
- 每个 group 里每个 slot 存一个 **7-bit hash 摘要**（叫 "control byte"）。
- 查找时用 hash 找到 group，然后用 **SIMD 指令一次比对 8 个 control byte**（x86 上是 SSE2 / AArch64 上是 NEON），命中再去比 full key。
- overflow 用**开放寻址（探测下一个 group）**，不再链式。

**对 Go map 的影响**：

| 维度 | 旧实现（map） | 新实现（Swiss Tables） |
|---|---|---|
| 查找性能 | 链式比较 key | SIMD 并行比对，命中更快 |
| 缓存友好性 | bucket 内连续，overflow 跳跃 | 全连续 group |
| 小 map 性能 | 8 entry/bucket | 8 entry/group，类似但常数更小 |
| 大 map 性能 | overflow chain 拉长会慢 | 平摊更稳定 |

**实测影响**（官方 benchmark + 社区测试）：
- 小 map (< 100 entry)：性能持平或微涨。
- 中等 map (1k-100k entry)：**查找快 10%-30%**，插入差不多。
- 大 map (> 100k)：**查找 / 删除快 20%-50%**，写也更快。
- 内存占用：**降低 5%-20%**（control byte 比 overflow 指针省）。

**对开发者透明**：
- API 完全不变，`m[k]`、`delete`、`for range` 全部一样。
- **迭代仍然无序**；随机化语义与之前版本一致（自 Go 1.3 起小 map 也随机化、1.12 起每次迭代都随机），Swiss Tables 只改实现、不改可观察的迭代顺序语义。
- delete 不缩容的行为不变。

**注意**：
- 第三方库如果用 `unsafe` 戳 map 内部结构（极少见，但有些超低层库会），可能会坏。但官方 API 都兼容。

📎 **深入阅读**: [G04-精通-Go-Map-哈希内幕与并发](../G04-精通-Go-Map-哈希内幕与并发.md)

**常见追问**：
- Q: 我能强制用回旧 map 实现吗？  A: Go 1.24 之后没有官方开关，全切了。
- Q: Swiss Tables 让 map key 必须支持 hash 吗？  A: 还是原 hash 函数（runtime/alg 那套），只是上层组织变了。

**陷阱**：在跨版本（1.23 ↔ 1.24）做 microbenchmark 对比，要先确认 map size 落在哪个区间——小 map 看不出差异。

### Q19 ⭐⭐⭐ map 的 key 必须满足什么条件？

**答**：

map 的 key **必须可比较**（comparable），即支持 `==` / `!=`。

**可比较的类型**：
- 所有基本类型：bool / 数值 / string
- 指针 / channel
- 数组（如果元素类型可比较）
- struct（如果所有字段类型可比较）
- 接口（运行时比较动态类型 + 值）

**不可比较的类型**：
- **slice / map / function** —— 这三个用 `==` 直接编译错误（只能和 nil 比）。
- 含有上述类型字段的 struct / 数组也不可比较。

```go
m1 := make(map[[3]int]string)        // OK，数组 key
m2 := make(map[struct{ a, b int }]string) // OK
// m3 := make(map[[]int]string)      // 编译错误：invalid map key type
// m4 := make(map[map[string]int]int) // 编译错误
```

**接口作为 key 的坑**：
```go
var m = map[any]string{}
m[[]int{1, 2}] = "x"   // 编译通过（any 类型 key），但运行时 panic
// panic: runtime error: hash of unhashable type []int
```
Go 允许把不可比较的值装进 any 接口（编译通过），但运行时计算 hash / 比较时会 panic。**用 any 当 key 是反模式**。

**string key 的注意点**：
- string 比较是字节级，Unicode 等价的字符串（如组合字符）算两个不同 key。
- 用大字符串当 key 时 hash 开销 = O(len(s))，热点路径要警惕。

**自定义 hash**：Go map 不允许用户传 hash 函数（不像 C++ unordered_map），key 类型决定一切。要自定义 hash，得自己包成 string（如 hex / json）或用第三方库。

📎 **深入阅读**: [G04-精通-Go-Map-哈希内幕与并发](../G04-精通-Go-Map-哈希内幕与并发.md)

**常见追问**：
- Q: float64 能当 key 吗？  A: 能，但 `NaN != NaN`，存进去就再也找不到——所以 NaN 永远查不到自己。
- Q: 含 slice 字段的 struct 能当 key 吗？  A: 不能。

**陷阱**：定义 `type ID struct { Name string; Tags []string }` 当 key，编译就报 invalid map key。

## §5 Struct

### Q20 ⭐⭐⭐⭐⭐ struct 字段对齐：给一个 `{bool, string, int32, []byte, bool, int64}` 算 sizeof。怎么优化字段顺序？

**答**：

64 位平台、64-bit alignment：

| 类型 | 大小 | 对齐 |
|---|---|---|
| bool | 1 | 1 |
| int32 | 4 | 4 |
| int64 | 8 | 8 |
| string | 16 (data + len) | 8 |
| []byte | 24 (data + len + cap) | 8 |

**按声明顺序 `{bool, string, int32, []byte, bool, int64}` 算**：

```
offset
 0: bool      (1B)  + pad 7B  →  对齐到 8
 8: string   (16B)              →  offset 24
24: int32     (4B)  + pad 4B   →  对齐到 8
32: []byte   (24B)              →  offset 56
56: bool      (1B)  + pad 7B   →  对齐到 8
64: int64     (8B)              →  offset 72

总大小：72 字节（72 % 8 == 0，刚好对齐）
```

**优化顺序：按对齐大→小排列**：

```go
struct {
    s    string   // 16
    b    []byte   // 24
    n    int64    //  8
    m    int32    //  4
    f1   bool     //  1
    f2   bool     //  1
    // 末尾 pad 2 字节到 8 对齐
}
// 16 + 24 + 8 + 4 + 1 + 1 + pad 2 = 56 字节
```

**节省 16 字节**（72 → 56），约 22%。

**对齐规则**：
1. 每个字段对齐到自己 alignof 的倍数偏移。
2. struct 整体对齐 = max(字段 alignof)。
3. struct sizeof 必须是其 alignof 的整数倍（末尾可能 pad）。

**判断工具**：
```go
import (
    "fmt"
    "unsafe"
)
fmt.Println(unsafe.Sizeof(MyStruct{}))
fmt.Println(unsafe.Alignof(MyStruct{}))
fmt.Println(unsafe.Offsetof(MyStruct{}.field))
```

也可以用 [maligned](https://github.com/mdempsky/maligned) 或 [fieldalignment](https://pkg.go.dev/golang.org/x/tools/go/analysis/passes/fieldalignment) 这种 linter 自动建议字段顺序。

**工程取舍**：
- 一般 struct 字段少、不在 hot path，不必抠对齐。
- **高频分配的对象**（每秒百万级、或大 slice 元素）：手工排一下能省 20%-50% 内存。
- 字段顺序也要兼顾**可读性**——业务相关的字段聚在一起，比强行按大小排更好维护。

📎 **深入阅读**: [G05-精通-Go-Struct-内存布局与嵌入](../G05-精通-Go-Struct-内存布局与嵌入.md)

**常见追问**：
- Q: 32 位平台计算有何不同？  A: int / uintptr / 指针都是 4 字节，对齐也是 4。
- Q: bool 占 1 字节为什么？  A: Go 规定 bool 是 1 字节（不是位）。

**陷阱**：以为字段紧凑就一定快——访问跨 cache line 字段也可能更慢。对齐优化通常是为了**省内存**而非速度。

### Q21 ⭐⭐⭐⭐ 嵌入（embedding）和继承的区别？方法提升规则？

**答**：

Go 没有继承，**只有嵌入（embedding）**。语法上：

```go
type Animal struct {
    Name string
}
func (a Animal) Speak() { fmt.Println(a.Name) }

type Dog struct {
    Animal       // 匿名字段（embedded）
    Breed string
}

d := Dog{Animal: Animal{Name: "Rex"}, Breed: "Husky"}
d.Speak()        // 调用 Dog 的"提升方法"
d.Name           // 提升字段，等价于 d.Animal.Name
```

**与继承的本质区别**：

| 维度 | 继承（OOP） | 嵌入（Go） |
|---|---|---|
| 关系 | is-a | **has-a** |
| 方法集 | 子类拥有父类方法 | 外层结构能"调用"内层方法（语法糖） |
| 多态 | 通过虚函数表 / vtable | 通过 interface 满足 |
| override | 子类可重写父类方法 | 外层定义同名方法**遮蔽**内层方法，但内层仍可访问 |
| 类型转换 | 子类 → 父类隐式 | Dog 不能赋给 Animal 变量 |

**方法提升规则**：

1. 嵌入字段（匿名字段）的所有方法都被"提升"到外层 struct。
2. 提升的方法**接收者仍是内层类型**——内层值什么，外层访问后还是什么。
3. 同名方法在外层定义时**遮蔽**内层方法，但 `d.Animal.Speak()` 仍可显式调。
4. 多层嵌入按**最浅原则**：哪一层先有同名方法，外层就用哪个；同深度冲突要显式指定。

**指针 vs 值嵌入**：
- 嵌入 `Animal`：内层值复制到外层。
- 嵌入 `*Animal`：外层只持有指针，可 nil。

**接口嵌入**：
```go
type ReadWriter interface {
    io.Reader
    io.Writer
}
```
等价于把方法签名集合在一起，没有运行时开销。

**典型使用**：
- 装饰器：`type Logger struct { http.Handler }`——拦截 `ServeHTTP` 加日志。
- mock：`type MockDB struct { *sql.DB }`——只 override 想 mock 的方法。
- 复用：`type Service struct { Repo; Cache }`——多组合而非多继承。

📎 **深入阅读**: [G05-精通-Go-Struct-内存布局与嵌入](../G05-精通-Go-Struct-内存布局与嵌入.md)

**常见追问**：
- Q: 嵌入冲突怎么处理？  A: 同层同名直接调用编译错误，需要显式 `d.A.Foo()` 或 `d.B.Foo()`。
- Q: 嵌入 interface 和嵌入 struct 区别？  A: 嵌入 interface 把方法签名加进来；嵌入 struct 把字段和方法都加进来。

**陷阱**：嵌入 sync.Mutex 把内部 Lock/Unlock 暴露成 public 方法——外部能直接 lock/unlock，破坏封装。一般用具名字段 `mu sync.Mutex` 更稳。

### Q22 ⭐⭐⭐ 空结构体 `struct{}` 大小是 0 吗？地址相同吗？什么场景用？

**答**：

**大小是 0**：`unsafe.Sizeof(struct{}{}) == 0`。

**地址行为**：Go 规范说**所有 zero-size 值的地址可能相同**——runtime 通常用一个特殊的占位地址 `runtime.zerobase`。但具体实现可变化，**不要依赖**。

```go
var a, b struct{}
fmt.Println(&a == &b) // 通常 true，但不保证
```

**经典使用场景**：

1. **set 数据结构**（map 的零成本 value）：
   ```go
   set := make(map[string]struct{})
   set["a"] = struct{}{}
   _, exists := set["a"]
   ```
   value 不占内存——比 `map[string]bool` 省。

2. **信号 channel**：
   ```go
   done := make(chan struct{})
   go func() {
       defer close(done)
       // ...
   }()
   <-done
   ```
   信号本身不携带数据，struct{} 是最小的"语义占位"。比 `chan bool` 表意更清晰。

3. **方法接收者**（无状态类型）：
   ```go
   type Handler struct{}
   func (Handler) ServeHTTP(...) { ... }
   ```

4. **嵌入 unexported 让 struct 不可直接初始化**：
   ```go
   type Foo struct {
       _ struct{}     // 防止外部用 Foo{} 初始化（需要走 NewFoo）
       Name string
   }
   // Foo{Name: "x"}  // 编译错误：implicit assignment of unexported field
   ```
   不过更常见的做法是把字段全 unexported，构造函数返回值。

**注意 `[0]T` 和 `[0]func()`**：
- `[0]T` 也是 zero-size，常用于**禁止比较**：`type Foo struct { _ [0]func() }` 让 Foo 不可比较，防止误用。

📎 **深入阅读**: [G05-精通-Go-Struct-内存布局与嵌入](../G05-精通-Go-Struct-内存布局与嵌入.md)

**常见追问**：
- Q: struct{} 数组占多少？  A: `[1000]struct{}{}` 还是 0 字节。
- Q: chan struct{} 比 chan bool 真的更快吗？  A: 无明显速度差异，但更省内存（4 字节 vs 0 字节 buffered 时）+ 语义更清晰。

**陷阱**：`return &struct{}{}` 拿地址回传——可能不同调用返回同一个地址，做指针等值比较会得到诡异结果。

## §6 函数、defer、闭包

### Q23 ⭐⭐⭐⭐ defer 执行顺序？defer + 命名返回值的"小坑"代码题

**答**：

**defer 执行顺序：LIFO（后进先出）**。多个 defer 按声明逆序执行。defer 的**参数在声明时求值**（不是执行时），但函数体在 `return` 后才执行。

```go
func main() {
    defer fmt.Println(1)
    defer fmt.Println(2)
    defer fmt.Println(3)
}
// 输出：3 2 1
```

**经典坑题：defer + 命名返回值**：

```go
func f1() int {
    x := 5
    defer func() { x++ }()
    return x
}
// 返回 5 还是 6？答：5
// 因为 return x 是 "把 x 赋给隐藏的返回值"，之后 defer 改的是局部 x
```

```go
func f2() (x int) {  // 命名返回值
    x = 5
    defer func() { x++ }()
    return x
}
// 返回 5 还是 6？答：6
// 命名返回值就是返回变量本身，defer 修改它 → 影响返回结果
```

```go
func f3() (result int) {
    defer func() { result *= 2 }()
    return 5
}
// return 5 等价于 result = 5; defer 改 result → return 10
```

**defer 求值的小坑**：

```go
func f() {
    i := 1
    defer fmt.Println(i) // 立即捕获 i 的值 1
    i = 2
    return
}
// 输出 1

func f2() {
    i := 1
    defer func() { fmt.Println(i) }() // 闭包，捕获 i 的引用
    i = 2
    return
}
// 输出 2
```

`defer fmt.Println(i)` 中 i 在 defer 声明时被 evaluate（拷贝实参）；`defer func() { ... }()` 是闭包，运行时才读 i。

**总结口诀**：
- **return 三步走**：① 返回值赋值（含命名返回值的"赋"）→ ② 执行 defer 列表 → ③ 真正返回。
- defer 直接传参：声明时拷贝。
- defer 闭包引用：执行时读。

📎 **深入阅读**: [G06-精通-Go-函数-闭包与-defer-机制](../G06-精通-Go-函数-闭包与-defer-机制.md)

**常见追问**：
- Q: defer 里 panic 会发生什么？  A: 当前 defer 链继续，panic 会向上冒泡；defer 链中可 recover。
- Q: defer 一个 nil 函数会怎样？  A: defer 声明时不 panic，**执行到时 panic**（nil func call）。

**陷阱**：循环里 `defer file.Close()` 会堆积大量 defer 直到函数返回——大循环要立刻关 / 用立即调用的函数包一层。

### Q24 ⭐⭐⭐⭐ defer 性能：Go 1.14+ 开放编码优化是什么？什么时候不开

**答**：

Go 早期 defer 用**链表式的 deferred record**（heap 分配 `_defer` 结构 + push 到 g.defer 链表），单次开销几十到几百纳秒——hot loop 里很伤。

**Go 1.13 引入了 stack-allocated defer**：把 _defer 分配在栈上，省掉了堆分配。但仍要操作链表。

**Go 1.14 引入 open-coded defer（开放编码）**：编译器把 defer 调用**直接展开**到函数末尾，配合一个位图标记哪个 defer 应该被执行。零运行时开销——一次 defer ≈ 一次普通函数调用。

**条件**（Go 1.14+ 同时满足才开 open-coded）：

1. 函数中的 **defer 数 ≤ 8**。
2. 没有 defer 在循环里（loop 内的 defer 数无法编译期确定）。
3. 函数没禁用优化（`//go:noinline` 等可能影响）。

**性能对比**（粗略数据，实际差异看场景）：

| 方式 | 单次 defer 开销 |
|---|---|
| Go 1.12 heap defer | ~50 ns |
| Go 1.13 stack defer | ~35 ns |
| Go 1.14+ open-coded | ~1-3 ns |
| 内联手写 (无 defer) | ~0.5 ns |

**性能敏感场景的取舍**：

- **绝大多数代码**：defer 性能没问题，照用——可读性 / 异常安全更重要。
- **极致 hot path**（每次调用纳秒级要求，比如 RPC 解码热点）：手动 close、避免 defer。
- **循环内**：defer 会回到链表式，hot loop 里慎用——`for { f, _ := os.Open(...); defer f.Close() }` 累积 defer 直到外层函数返回，**既慢又泄漏**，要么循环体抽函数、要么循环内显式 close。

**怎么验证**：用 `go tool compile -m -m main.go` 看，会输出 `open-coded defer` 之类的标记；或者直接 `go build -gcflags="-d=defer=2"`。

📎 **深入阅读**: [G06-精通-Go-函数-闭包与-defer-机制](../G06-精通-Go-函数-闭包与-defer-机制.md)

**常见追问**：
- Q: 为什么阈值是 8？  A: 位图用 8-bit byte 一个比特表示一个 defer，正好 8 个。
- Q: defer 在递归函数怎么算？  A: 每次调用都是新的栈帧，互不影响。

**陷阱**：循环内 defer 资源不仅性能差，更大问题是**资源累积释放延迟到外层函数返回**，常导致文件句柄 / 连接耗尽。

### Q25 ⭐⭐⭐⭐ 闭包捕获是值还是引用？Go 1.22 前后 for-range 变量复用问题

**答**：

**Go 中闭包捕获变量是按引用捕获**——闭包持有变量的**地址**，外部修改闭包能看到。

```go
func main() {
    x := 1
    f := func() { fmt.Println(x) }
    x = 2
    f() // 输出 2
}
```

实现上：编译器分析闭包捕获了哪些外部变量，把这些变量提升到堆上（逃逸），闭包内是这些堆变量的指针。

**经典 for-range 坑（Go 1.22 之前）**：

```go
// Go 1.21 及之前
fns := []func(){}
for i := 0; i < 3; i++ {
    fns = append(fns, func() { fmt.Println(i) })
}
for _, f := range fns { f() }
// 输出：3 3 3 ← 闭包都引用同一个 i，循环结束时 i=3
```

原因：**循环变量 i 在整个 for 中只有一个**（每次迭代复用同一个 i 的内存位置），三个闭包都捕获了同一个 i 的指针。

**Go 1.22+ 改变**：

`for i := 0; i < N; i++` 和 `for i, v := range xs` 中**循环变量每次迭代是新的**（per-iteration scope）。

```go
// Go 1.22+
fns := []func(){}
for i := 0; i < 3; i++ {
    fns = append(fns, func() { fmt.Println(i) })
}
for _, f := range fns { f() }
// 输出：0 1 2 ← 每次循环新建 i
```

**修复手段（兼容旧版本）**：

```go
for i := 0; i < 3; i++ {
    i := i // 创建新的 i shadow 外层
    fns = append(fns, func() { fmt.Println(i) })
}

// 或参数捕获
for i := 0; i < 3; i++ {
    fns = append(fns, func(i int) func() {
        return func() { fmt.Println(i) }
    }(i))
}
```

**怎么知道用哪个版本的行为**：看 `go.mod` 里 `go 1.22` 或更高时新行为生效；旧版本仍是共享变量。

**协程启动场景同样适用**：
```go
// Go 1.22+ 终于不踩坑
for _, x := range xs {
    go process(x)  // 每次 x 都是新的
}
```

📎 **深入阅读**: [G06-精通-Go-函数-闭包与-defer-机制](../G06-精通-Go-函数-闭包与-defer-机制.md)

**常见追问**：
- Q: 1.22 之前为什么不直接修复？  A: 修了等于破坏旧代码语义，Go 1 兼容承诺。1.22 通过 go.mod 版本控制做了平滑切换。
- Q: 改了 for 之后，性能有影响吗？  A: 极小——只在闭包/取地址等"逃逸"路径多个堆对象，多数循环没差异。

**陷阱**：跨版本写库代码时，循环变量 + goroutine / 闭包还是要显式 `x := x`——既兼容老版本，又让阅读者一眼看出意图。

### Q26 ⭐⭐⭐ recover 的作用域：能跨 goroutine 吗？必须在 defer 中调用吗？

**答**：

**recover 必须在 defer 函数中直接调用**，且**只能 recover 当前 goroutine 的 panic**。

**规则细节**：

1. **必须在 defer 函数体内直接调用**：
   ```go
   defer func() {
       if r := recover(); r != nil {
           log.Println("recovered:", r)
       }
   }()
   ```
   `recover` 直接放在函数体里、defer 包了别的函数再调用 recover 都没用——runtime 检查调用栈，只在 `defer 直接调用` 的形式下生效。

2. **跨 goroutine 不可恢复**：
   ```go
   defer func() { recover() }() // 这里的 recover
   go func() {
       panic("oops")  // 这个 panic 不会被外层 recover
       // 不被 recover 的 panic → 整个程序 crash
   }()
   ```
   每个 goroutine 必须自己有 defer + recover 才能拦截自己的 panic。

3. **recover 只在当前 defer 链中**：
   ```go
   func f() {
       g()       // g 中 panic，h 的 recover 抓不到
   }
   func h() {
       defer func() { recover() }()
       f()       // 这里 panic 会传到 h，被 h 的 recover 抓到
   }
   ```
   panic 沿调用栈向上冒泡，每层 defer 都有机会 recover。但是 goroutine 是独立栈，跨 G 不传递。

4. **recover 返回值**：panic 携带的值（任意 interface{}）。没 panic 时返回 nil。

**工程实践**：
- **库代码不要 recover**——让调用方决定怎么处理。
- **网络服务的 handler 层**包一层 recover，避免单个请求挂掉整个进程（`net/http` 自带）。
- **每个 goroutine 入口都要 recover**——尤其是从池子里取出来的 worker、定时任务、消息消费协程。

```go
func safeGo(fn func()) {
    go func() {
        defer func() {
            if r := recover(); r != nil {
                log.Printf("goroutine panic: %v\n%s", r, debug.Stack())
            }
        }()
        fn()
    }()
}
```

📎 **深入阅读**: [G10-精通-Go-错误处理-与-panic-recover](../G10-精通-Go-错误处理-与-panic-recover.md)

**常见追问**：
- Q: recover 后能继续执行 panic 之前的代码吗？  A: 不能，recover 之后函数当前流程结束，控制权回到 defer 调用者；但程序可继续运行（不 crash）。
- Q: panic 里 panic 怎么办？  A: 新 panic 替换旧的，最终 recover 拿到的是最后一个 panic 的值。

**陷阱**：`go func() { fn() }()` 不加 recover——fn 内部 panic 直接拉爆进程。生产环境要么禁裸 go，要么用 safeGo 包装。

## §7 错误处理

### Q27 ⭐⭐⭐⭐ error 接口的定义？哨兵错误 vs 自定义类型 vs %w wrap

**答**：

**error 接口的定义极简**：

```go
type error interface {
    Error() string
}
```

任何实现了 `Error() string` 方法的类型都是 error。

**三种主流错误风格**：

1. **哨兵错误（sentinel errors）**：

   ```go
   var ErrNotFound = errors.New("not found")

   if err := db.Get(k); err == ErrNotFound {
       // ...
   }
   ```

   - 优点：简单，调用方好判断。
   - 缺点：跨包暴露符号、不能携带上下文。
   - 适用：标准化的几种错误（io.EOF, sql.ErrNoRows）。

2. **自定义错误类型**：

   ```go
   type NotFoundError struct {
       Key string
   }
   func (e *NotFoundError) Error() string {
       return fmt.Sprintf("key %q not found", e.Key)
   }

   if e, ok := err.(*NotFoundError); ok {
       log.Println("missing key:", e.Key)
   }
   ```

   - 优点：携带结构化信息（key、status code 等）。
   - 缺点：调用方要做类型断言，耦合。
   - 适用：需要根据错误细节做差异化处理。

3. **wrap with %w（Go 1.13+）**：

   ```go
   if err := callAPI(); err != nil {
       return fmt.Errorf("fetch user %d: %w", uid, err)
   }
   ```

   - 优点：保留原错误链，配合 `errors.Is/As` 解包。
   - 缺点：堆叠太深可读性下降。
   - **现代 Go 的事实标准**。

**最佳实践**：

- 内层错误用**自定义类型或哨兵**，外层逐层 `%w` 包裹添加上下文。
- 调用方用 **`errors.Is`** 判等、**`errors.As`** 解包类型。
- 错误消息**小写开头、无标点结尾**（Go 风格指南）。

```go
// 错
return errors.New("Failed to do X.")
// 对
return errors.New("failed to do X")
```

📎 **深入阅读**: [G10-精通-Go-错误处理-与-panic-recover](../G10-精通-Go-错误处理-与-panic-recover.md)

**常见追问**：
- Q: `*MyErr` 还是 `MyErr` 实现 Error()？  A: 看是否需要修改字段——通常 *MyErr，nil 安全检查也方便。
- Q: 错误链怎么打印？  A: `fmt.Printf("%+v", err)`（取决于实现）或自己写 traverse。

**陷阱**：`if err != nil { return err }` 不加上下文——出问题时只看到底层错误，调用链不知道哪个层级出问题，加 `fmt.Errorf("doing X: %w", err)` 至少加一行栈信息。

### Q28 ⭐⭐⭐⭐ errors.Is、errors.As、errors.Join 的区别

**答**：

三个函数解决错误链处理的不同需求：

**`errors.Is(err, target) bool`**：沿着 err 的 Unwrap 链找有没有等于 target 的错误。判等用 `==`（或自定义 `Is` 方法）。

```go
if errors.Is(err, sql.ErrNoRows) {
    // 即使 err 被 wrap 过 n 层，只要链里有 sql.ErrNoRows 就匹配
}
```

适合**哨兵错误**判断。

**`errors.As(err, target *T) bool`**：沿着 Unwrap 链找第一个能赋给 `*target` 的错误，赋值并返回 true。

```go
var pathErr *fs.PathError
if errors.As(err, &pathErr) {
    log.Println(pathErr.Path) // 拿到结构化字段
}
```

适合**自定义错误类型**取信息。注意 target 是**指向 error 类型的指针**。

**`errors.Join(errs ...error) error` (Go 1.20+)**：把多个 error 合并成一个，新 error 的 Error() 是各个 error 字符串用 `\n` 连接；支持 `errors.Is/As` 遍历所有子 error。

```go
err := errors.Join(err1, err2, err3)
if errors.Is(err, ErrNotFound) {
    // 子里只要有一个 Is ErrNotFound 就 true
}
```

适合 **fan-out 后聚合错误**（并发任务收集所有失败、批量操作记所有错）。

**对比表**：

| 函数 | 关心什么 | 返回 |
|---|---|---|
| `errors.Is` | 错误链里有没有目标错误（按值） | bool |
| `errors.As` | 错误链里有没有目标类型，并提取出来 | bool |
| `errors.Join` | 把多个错误打包 | error |

**自定义 Is / Unwrap 协议**：

```go
type StatusErr struct {
    Code int
    Err  error
}
func (s *StatusErr) Error() string { return fmt.Sprintf("%d: %v", s.Code, s.Err) }
func (s *StatusErr) Unwrap() error { return s.Err }
func (s *StatusErr) Is(target error) bool {
    t, ok := target.(*StatusErr)
    return ok && t.Code == s.Code
}
```

提供 `Unwrap()` 让 Is/As 能穿透；提供 `Is(error)` 让自定义判等规则生效。

**Unwrap() []error**（Go 1.20+）：与 Join 配套，让一个 error 能 Unwrap 出多个子 error。

📎 **深入阅读**: [G10-精通-Go-错误处理-与-panic-recover](../G10-精通-Go-错误处理-与-panic-recover.md)

**常见追问**：
- Q: errors.As 的 target 为什么是 `*T`？  A: 函数要写入 target，Go 没引用必须用指针。
- Q: 一个 error 实现了 Is 又有 Unwrap，调用顺序？  A: 先调当前 error 的 Is，false 则 Unwrap 继续。

**陷阱**：拿到 wrapped error 用 `err == sql.ErrNoRows` 直接判等——wrap 后用 == 永远 false，必须 errors.Is。

### Q29 ⭐⭐⭐ panic 与 error 的边界：什么场景该 panic？

**答**：

**核心原则：可预期的错误用 error 返回，不可恢复的程序异常才 panic**。

**该用 error 的场景**：

- IO 失败（文件不存在、网络断）
- 输入校验（用户参数错）
- 业务规则不满足（余额不足、权限不够）
- 资源耗尽（DB 连接满、内存超 limit）

这些都是**调用方可预期、需要处理**的情况。

**该 panic 的场景**：

- **程序员错误（bug）**：不可能为真的不变量被打破。
  ```go
  if x < 0 { panic("invariant violation: x should be non-negative") }
  ```
- **不可恢复的初始化失败**：`init()` 里读不到必需的配置 → panic，让进程起不来比起来后报错好。
- **第三方库的 must-style API**：`template.Must(...)`、`regexp.MustCompile(...)`——参数是编译期已知的字面量，运行时挂掉等于代码有 bug。
- **数组 / slice / map 内置操作触发**：越界、nil map 写——runtime 自己 panic，不是用户主动选择。

**panic 的边界规则**：

1. **库的公共 API 不应 panic**（除非文档明确说，如 Must 系列）。让调用方决定怎么处理 error。
2. **服务入口处加 defer recover**：HTTP handler、RPC handler、消息消费 goroutine——把意外 panic 转成 500 错误响应，而不是 crash 进程。
3. **panic 别滥用做异常控制流**：用 panic 跳出多层函数（"我懒得逐层 return err"）是反模式，不可读、性能差、易出错。

**举例对比**：

```go
// 业务函数（应该返回 error）
func Withdraw(account *Account, amount Money) error {
    if amount > account.Balance {
        return ErrInsufficientFunds
    }
    // ...
    return nil
}

// 内部不变量（panic 合理）
func (q *Queue) pop() Item {
    if q.len == 0 {
        panic("pop on empty queue") // 调用方违反了使用契约
    }
    // ...
}

// 编译期已知合法的常量（Must 风格）
var validHost = regexp.MustCompile(`^[a-z0-9.-]+$`)
```

📎 **深入阅读**: [G10-精通-Go-错误处理-与-panic-recover](../G10-精通-Go-错误处理-与-panic-recover.md)

**常见追问**：
- Q: panic 比 return err 慢吗？  A: 慢得多。panic 要 unwind 栈、跑 defer 链，纳秒级 vs 微秒级。hot path 千万别用 panic 做控制流。
- Q: 业务里硬要 panic 然后 recover，有什么风险？  A: 隐藏 bug、性能损耗、错误信息丢失（panic 携带的是 interface{}，类型断言一次又一次容易错）。

**陷阱**：第三方库里 panic（未文档化），调用方没 recover 直接拖崩服务——所以**用 panic 是契约级别的决定**，写出来要慎重。

## 高频陷阱清单

- **nil map 写入直接 panic**：`var m map[string]int; m["x"]=1` —— 必须 `m = make(map...)`。
- **map delete 不释放底层 bucket**：长生存 map 退化成内存泄漏，要么整张换、要么用 `clear` + 接受 cap 不缩。
- **大 slice 切小 slice 返回**：底层数组被引用整体无法 GC——`return data[i:j]` 慎用，必要时 `slices.Clone`。
- **append 共享底层数组的隐式修改**：`s2 := s1[:3]; s2 = append(s2, x)` 当 s1 的 cap 还有空间时，悄悄改了 s1 看到的元素。
- **JSON 输出 null vs []**：nil slice 输出 `null`，前端可能崩；显式 `[]T{}` 或换 omitempty 协议。
- **for-range 闭包变量复用（Go 1.21 及之前）**：`for _, x := range xs { go f(x) }` 全是最后一个 x —— 加 `x := x` 或升 Go 1.22+。
- **循环里 defer**：资源不立即释放、open-coded defer 失效，要么改循环结构、要么循环体抽函数。
- **goroutine 没 recover**：单个 panic 拖崩进程。所有 `go` 入口包一层 `safeGo`。
- **`if err == sql.ErrNoRows` 直接判等被 wrap 打破**：用 `errors.Is`，永远别直接 `==` 比较跨包错误。
- **struct 字段顺序随手排**：高频分配对象，按对齐大小重排可省 20-50% 内存。
