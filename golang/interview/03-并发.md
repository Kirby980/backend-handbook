## §1 Goroutine 与 GMP

### Q1 ⭐⭐⭐ goroutine 和 thread 的区别？为什么 Go 能创建几十万 goroutine

**答**：

goroutine 是 Go runtime 在用户态管理的"轻量级线程"，与操作系统线程 (OS thread) 有本质差异：

| 维度 | OS Thread | Goroutine |
|------|-----------|-----------|
| **调度方** | 操作系统内核 | Go runtime（用户态） |
| **初始栈大小** | 1~8 MB（固定） | 2 KB（可动态伸缩，最大 1 GB） |
| **创建/销毁开销** | μs 级，涉及系统调用 | ns 级，纯用户态分配 |
| **上下文切换** | 内核切换，~1μs，刷新 TLB/寄存器 | runtime 切换，~100ns，只保存少量寄存器 |
| **数量级** | 几千就吃力 | 几十万乃至百万级 |
| **通信方式** | 共享内存 + 锁 | channel（推荐）/ 共享内存 |

Go 能创建几十万 goroutine 的关键原因：

1. **栈极小且按需增长**：每个 goroutine 起步 2 KB（vs 线程 MB 级），100 万 goroutine 仅需 ~2 GB 栈空间，且大多数 goroutine 实际只用几 KB。
2. **M:N 调度**：N 个 goroutine 复用 M 个 OS 线程（通常 M = CPU 核数），切换无需陷入内核。
3. **runtime 整合 I/O 与调度**：网络 I/O 通过 netpoller (epoll/kqueue) 异步化，阻塞的 goroutine 不占线程。

📎 **深入阅读**: [G11-精通-Goroutines-与-GMP-调度](../G11-精通-Goroutines-与-GMP-调度.md)

**常见追问**：
- Q: goroutine 切换为什么比线程快？  A: 不进内核态，只切换 PC/SP/BP 等少量寄存器（约 100ns vs 线程 1μs+），且不刷新 TLB。
- Q: goroutine 能取消吗？  A: 没有内置 kill API，必须通过 channel 或 context 协作式退出。
- Q: 一个 goroutine 占多少内存？  A: 栈 2KB 起 + g 结构体约 2KB，合计起步 ~4KB。

**陷阱**：goroutine 廉价不等于免费——海量 goroutine 也会带来 GC 扫描、调度排队、栈拷贝等开销，生产仍推荐 worker pool 限制并发度。

### Q2 ⭐⭐⭐⭐⭐ 简述 GMP 调度模型

**答**：

GMP 是 Go 调度器的三个核心抽象：

- **G (Goroutine)**：用户协程，保存执行栈、PC、状态等。
- **M (Machine)**：OS 线程，真正执行 G 的载体。M 必须绑定一个 P 才能跑用户代码。
- **P (Processor)**：逻辑处理器，持有一个**本地 G 队列**（256 容量）和缓存（mcache、defer 池等）。`GOMAXPROCS` 决定 P 的数量。

**调度流程**：

```
                       ┌──── Global Run Queue ────┐
                       │  G  G  G  G  G  G  G  G  │
                       └──────────────────────────┘
                                 ▲
                                 │ 偷取/补给
        ┌───────────┐    ┌───────────┐    ┌───────────┐
        │    P0     │    │    P1     │    │    P2     │
        │ local rq  │    │ local rq  │    │ local rq  │
        │  G G G    │    │  G G G G  │    │  G G      │
        └────┬──────┘    └─────┬─────┘    └─────┬─────┘
             │                 │                │
        ┌────▼────┐       ┌────▼────┐      ┌────▼────┐
        │   M0    │       │   M1    │      │   M2    │
        │ thread  │       │ thread  │      │ thread  │
        └─────────┘       └─────────┘      └─────────┘
```

**调度循环 `schedule()` 的简化逻辑**：

```go
func schedule() {
    // 1) 每 61 次调度优先从全局队列取（防止全局队列饥饿）
    if p.schedtick%61 == 0 && len(globalq) > 0 {
        gp = globalq.pop()
    }
    // 2) 本地队列取
    if gp == nil {
        gp = p.localq.pop()
    }
    // 3) 全局队列 + netpoller
    if gp == nil {
        gp = findRunnable() // 包含从其他 P steal、检查 netpoll、GC 等
    }
    execute(gp)
}
```

**关键机制**：

1. **Work Stealing**：P 本地队列空时，会从其他 P 偷取一半 G。
2. **Hand-off**：M 陷入系统调用阻塞时，runtime 把 P 解绑给其他 M 使用（避免 P 闲置）。
3. **Sysmon 监控线程**：每 20μs ~ 10ms 巡检，处理长时间阻塞的 G（异步抢占）、网络 poll、GC 触发。
4. **Network Poller**：网络 IO 不阻塞 M，G 被挂起到 netpoller，事件就绪后重新入队。

**G 的状态**：`_Gidle → _Grunnable → _Grunning → _Gsyscall/_Gwaiting → _Grunnable → ...`

📎 **深入阅读**: [G11-精通-Goroutines-与-GMP-调度](../G11-精通-Goroutines-与-GMP-调度.md)

**常见追问**：
- Q: 为什么不是 GM 两层？  A: 早期 Go 1.0 就是 GM，全局锁竞争严重。P 的引入相当于把"待运行 G 队列"分片，本地队列无锁，全局队列只在补给时碰。
- Q: M 数量有上限吗？  A: 默认 10000（`runtime/debug.SetMaxThreads` 可调）。M 数 ≠ P 数，syscall 阻塞时 M 会膨胀。
- Q: 主 goroutine 退出会怎么样？  A: `main` 返回后整个进程退出，所有其他 goroutine 强制终止，没机会执行 defer。

**陷阱**：把"GMP"当成静态架构图背诵是不够的，面试官会追问"P 本地队列满了怎么办"（一半移到全局队列）、"Sysmon 怎么发现长时间运行的 G"（基于 schedtick 时间戳）。

### Q3 ⭐⭐⭐⭐ P 数量为什么默认 = CPU 核数？什么时候应该调大 GOMAXPROCS

**答**：

P 数量决定**同时执行 Go 代码的并行度**（不是并发度——并发由 goroutine 数决定）。默认 `runtime.NumCPU()` 是因为：

- P 多于核数 → M 之间频繁抢核，上下文切换损失大于收益。
- P 少于核数 → 浪费 CPU。

**应该调大 GOMAXPROCS 的场景几乎不存在**，但有几种情况要警惕：

1. **大量 CGO 调用**：CGO 期间 P 会 hand-off，但 M 阻塞在 C 代码里，可能导致 G 排队。可适当调大或改用异步。
2. **大量阻塞型 syscall**：同上，M 频繁阻塞。但通常 runtime hand-off 已能处理。
3. **CPU 限制 < 整机核数**（容器场景）：Go 1.25 之前 `NumCPU()` 看到的是宿主机核数，需要手动按 cgroup CPU quota 调小（用 `automaxprocs` 库）。**Go 1.25 已原生支持容器感知**，会按 `cpu.cfs_quota_us / cfs_period_us` 自动设定。

**调小的情形**：批处理任务希望让出 CPU 给其他进程；调试时把 `GOMAXPROCS=1` 复现某些时序 bug。

**典型代码**：

```go
// 容器中显式按 cgroup 配置（Go < 1.25）
import _ "go.uber.org/automaxprocs"

// Go 1.25+ 默认就是容器感知，无需该库
```

📎 **深入阅读**: [G11-精通-Goroutines-与-GMP-调度](../G11-精通-Goroutines-与-GMP-调度.md)

**常见追问**：
- Q: GOMAXPROCS=1 时还有并发吗？  A: 有！多个 goroutine 可以在唯一的 P 上交替执行（time-slice），但**没有并行**。
- Q: 在 32 核机器上设 64 会发生什么？  A: 调度损耗增加、cache miss 增加，benchmark 通常会变慢 5-15%。
- Q: 怎么动态调整？  A: `runtime.GOMAXPROCS(n)` 可运行时设置，但会触发 STW。

**陷阱**：K8s 里跑 Go 服务而忘记容器感知，会导致 P 数远超实际 CPU 限制，sysmon 误判抢占，GC STW 暴涨。Go 1.25 之前必须配 `automaxprocs`。

### Q4 ⭐⭐⭐⭐ Work Stealing 怎么工作？P 本地队列空了的处理顺序

**答**：

当某个 P 的本地运行队列空了，它不会立即让 M 进入休眠，而是按以下顺序"找活干"：

```go
// runtime/proc.go: findRunnable() 简化版
func findRunnable() *g {
    // 1) 本地队列 pop
    if gp := runqget(_p_); gp != nil { return gp }

    // 2) 全局队列取一批（不超过 len/GOMAXPROCS+1）
    if gp := globrunqget(_p_, 0); gp != nil { return gp }

    // 3) netpoller 非阻塞查询（有就绪的网络 G 吗？）
    if list := netpoll(0); !list.empty() { return list.pop() }

    // 4) Work Stealing: 随机选一个 P，偷它队列的一半
    for i := 0; i < 4; i++ {
        if gp := runqsteal(_p_, randomP); gp != nil {
            return gp
        }
    }

    // 5) 再查全局队列、GC worker、再 steal 一轮…

    // 6) 都没有 → M 解绑 P，park (休眠等被唤醒)
    stopm()
}
```

**Work Stealing 细节**：

- **随机起点**：避免所有空闲 P 都去偷 P0，造成 thundering herd。
- **偷一半**：`n = runqlen(victim) / 2`，平衡两边队列长度。
- **从 victim 队尾偷**：本地 P 自己从队头消费，偷者从队尾，减少 cache 争用。
- **跳过 runnext**：每个 P 有个 `runnext` 槽（保存"刚 ready 的 G"），优先执行不被偷，提高局部性。

**为什么这套设计有效**：
- 本地队列无锁 → 大多数 push/pop 走快速路径。
- 全局队列加锁，但只在 steal/补给时碰，开销低。
- netpoller + steal 双重保险，CPU 利用率高。

📎 **深入阅读**: [G11-精通-Goroutines-与-GMP-调度](../G11-精通-Goroutines-与-GMP-调度.md)

**常见追问**：
- Q: 为什么要偷一半而不是一个？  A: 偷一个会频繁触发 steal（每次只够干一会儿），偷一半摊薄成本。
- Q: 所有 P 都空闲时怎么唤醒？  A: 新 goroutine 创建或 netpoll 事件就绪时，调度器会 `wakep()` 唤醒一个 M+P。
- Q: runnext 是什么？  A: 一个特殊槽位，存"当前 G 用 `go` 启动的第 0 个子 G"，强提高 channel ping-pong 类场景的性能。

**陷阱**：写 benchmark 时如果只有一个 goroutine 在跑，其他 P 全在 steal 循环，会看到 CPU 100% 但实际啥也没干。开 `GODEBUG=schedtrace=1000` 排查。

### Q5 ⭐⭐⭐⭐⭐ Go 1.14+ 异步抢占解决了什么问题？怎么实现的

**答**：

**痛点：协作式抢占的盲区**。Go 1.14 之前，调度器依靠**函数调用时的栈检查**来抢占——每次函数序言 (prologue) 都会检查 `g.stackguard0`，如果被置为 `0xfffffade`（抢占标记），就跳到 `runtime.morestack` 触发让出。

这套机制的致命缺陷：**没有函数调用的紧密循环里，永远不会被抢占**。

```go
// 这个循环在 Go 1.13 上会让一个 P 永远卡住，连 GC STW 都进不去
func busy() {
    for i := 0; i < 1e10; i++ {
        // 没有函数调用、没有内存分配 → 没有抢占点
    }
}
```

后果：GC 等待这个 G 进入安全点，全部 STW 卡住整个进程，可能几秒甚至超时。

**Go 1.14 异步抢占的实现**：

1. **Sysmon 检测**：监控线程每 ~10ms 巡检，发现某 G 跑超过 10ms 还没让出。
2. **发送信号**：`signalM(mp, sigPreempt)` → SIGURG。
3. **信号处理**：M 进入 `runtime.sighandler` → `doSigPreempt` → 修改被中断的 PC，让 G 返回时跳转到 `runtime.asyncPreempt`。
4. **`asyncPreempt`**：保存所有寄存器（异步抢占要保存全套，不像协作式只保存部分），调用 `mcall(gopreempt_m)` 让出 P。

**为什么用 SIGURG**：相对冷门，几乎没人会在 Go 程序里用它，避免与用户代码冲突。

**安全点限制**：不是所有 PC 都能被抢占，编译器会标注"不安全点"（持有写屏障、栈无法解析的位置），在这些点收到信号会延迟到下一个安全点再抢占。

📎 **深入阅读**: [G11-精通-Goroutines-与-GMP-调度](../G11-精通-Goroutines-与-GMP-调度.md)

**常见追问**：
- Q: GC STW 时间从此就 < 1ms 了？  A: 是的，Go 1.14 后 STW 通常 < 100μs。但抢占信号不是免费的，密集发送会有性能影响。
- Q: 异步抢占在所有平台都支持吗？  A: 主流 Linux/macOS/Windows 都支持，部分嵌入式平台（如 plan9）回退到协作式。
- Q: 用户能感知到吗？  A: 一般不能。但用 `runtime.LockOSThread` 后信号交付路径变化，要小心。

**陷阱**：CGO 调用期间不能被异步抢占（在 C 代码里发信号不安全），所以长时间 CGO 仍可能拖慢 GC。把重计算放回 Go 侧。

### Q6 ⭐⭐⭐⭐ 一个 goroutine 阻塞会发生什么

**答**：

按阻塞**类型**分类，调度器的处理完全不同：

**1. 系统调用 (read/write/未注册 fd 等)**：

```
G 进入 _Gsyscall 状态 → entersyscall()
   ├─ M 与 P 解绑（hand-off）
   ├─ 如果 syscall 时间长（>20μs），sysmon 把 P 交给空闲 M 或新建 M
   └─ syscall 返回 → exitsyscall()
       ├─ 尝试获取原 P；获取失败则尝试任一空闲 P
       └─ 都失败 → G 入全局队列，M 休眠
```

P 不被白白占用，但 M 数量可能膨胀。

**2. Channel / sync.Mutex / sync.Cond 阻塞**：

```
G 进入 _Gwaiting 状态 → gopark()
   ├─ G 从 P 摘除，挂到等待队列（hchan.recvq、Mutex 等）
   ├─ P 调用 schedule() 选下一个 G 执行
   └─ 唤醒方调用 goready() → G 重新入 P 的本地队列
```

完全用户态切换，M 一直忙别的，开销最小。

**3. 网络 I/O (TCP/HTTP)**：

```
G 调用 conn.Read → 底层 epoll_wait（非阻塞 fd）
   ├─ 没数据 → G _Gwaiting，挂到 netpoller
   ├─ M 继续跑其他 G
   ├─ epoll 事件就绪 → netpoll() 返回 G 列表
   └─ G 重新入运行队列
```

这是 Go 网络框架的精髓——同步 API 实现异步 I/O。

**4. CGO 调用**：

```
进入 C 代码前 → entersyscall（同 syscall 路径）
   ├─ P 被 hand-off
   └─ C 代码执行期间 M 阻塞，不能被异步抢占
```

**5. 持有锁的死循环（Q5 的场景）**：

Go 1.14+ 由 sysmon 异步抢占；之前会卡死整个进程。

📎 **深入阅读**: [G11-精通-Goroutines-与-GMP-调度](../G11-精通-Goroutines-与-GMP-调度.md)

**常见追问**：
- Q: 为什么网络 I/O 不会让 M 阻塞？  A: Go runtime 把 socket fd 设为 `O_NONBLOCK`，统一交 netpoller (epoll/kqueue) 管理，G 是被挂起到 runtime 而不是内核。
- Q: 大量 syscall 会有什么问题？  A: M 数量膨胀（默认上限 10000），线程切换开销变大，sysmon 压力上升。
- Q: 怎么观测一个 G 阻塞在哪？  A: `pprof goroutine?debug=2` 看完整栈 + 阻塞原因，或用 `runtime/trace`。

**陷阱**：误以为所有阻塞都"释放 P"——Mutex 阻塞确实立刻 yield，但持有 Mutex 时 G 不会被抢占的窗口需要注意。

### Q7 ⭐⭐⭐⭐ goroutine 栈是怎么伸缩的？初始多大

**答**：

**初始栈大小**：Go 1.4+ 是 **2 KB**（更早是 8KB 甚至 4MB 段栈）。

**伸缩机制：连续栈 (Contiguous Stack)** ——Go 1.3 后采用：

1. **栈不够时扩容**：
   ```
   函数序言检查 SP < stackguard0
      ├─ 是 → runtime.morestack
      │   ├─ 分配双倍大小的新栈
      │   ├─ 拷贝旧栈所有数据（包括所有局部变量）
      │   ├─ 调整所有指向旧栈的指针（栈上变量地址变了！）
      │   └─ 释放旧栈，切换到新栈继续执行
      └─ 否 → 正常执行
   ```

2. **栈空闲时收缩**：GC 时检测，如果使用量 < 1/4，缩到一半。

**为什么扩容代价能接受**：
- 拷贝是按页粒度，benchmark 显示对应用透明（除非极端栈使用模式）。
- 调整指针靠**栈帧元数据**：编译器为每个函数生成 stackmap，标注哪些是指针，runtime 据此遍历修正。
- 栈上指针必须**只指向自己这个 G 的栈**——这就是为什么 channel 传递大值时编译器会自动逃逸到堆。

**栈大小上限**：默认 **1 GB**（64-bit），可通过 `debug.SetMaxStack` 调整。超出 → `runtime: goroutine stack exceeds 1000000000-byte limit`，进程直接挂。

**代码示例（验证栈拷贝后地址会变）**：

```go
func depth(n int, prev *int) {
    var x int = n
    if prev != nil && prev != &x {
        fmt.Printf("栈地址变了! prev=%p new=%p\n", prev, &x)
    }
    if n > 0 {
        depth(n-1, &x)
    }
}

func main() {
    depth(10000, nil) // 深递归触发栈扩容
}
```

📎 **深入阅读**: [G11-精通-Goroutines-与-GMP-调度](../G11-精通-Goroutines-与-GMP-调度.md)

**常见追问**：
- Q: 段栈 (segmented stack) 为什么被废弃？  A: "hot split" 问题：栈刚扩容又缩，缩了又扩，循环抖动。
- Q: 怎么避免栈扩容开销？  A: 避免极深递归、避免大局部数组（让它逃逸到堆）、bench profile `runtime.MemStats.StackInuse`。
- Q: defer 在哪里？  A: Go 1.14+ open-coded defer 直接放栈上；老式 defer 链放堆上。

**陷阱**：`unsafe.Pointer` 缓存了栈上变量的地址，goroutine 触发栈拷贝后这个指针指向了已释放内存——这是最阴险的 unsafe 误用之一。

### Q8 ⭐⭐⭐⭐ Go 1.25 容器感知 GOMAXPROCS：在 K8s 里有什么影响

**答**：

**问题背景**：Go 1.25 之前，`runtime.NumCPU()` 和默认 `GOMAXPROCS` 都读 `/proc/cpuinfo`（即宿主机物理核数）。在 K8s 容器里：

```yaml
resources:
  limits:
    cpu: "2"     # 容器限制 2 核
# 但 Go 看到的是宿主机 64 核！
```

后果：
- Go 启动 64 个 P，CFS 调度器（容器 cgroup）会频繁限流 → throttling。
- 64 个 P 抢 2 个核的 quota，cache miss 暴增，p99 延迟飙升。
- GC worker 数量也按 GOMAXPROCS 算，STW 更长。

**Go 1.25 解决方案**：runtime 启动时读取：

```
/sys/fs/cgroup/cpu.max          # cgroup v2: "200000 100000" → 2 core
/sys/fs/cgroup/cpu/cpu.cfs_quota_us   # cgroup v1
/sys/fs/cgroup/cpu/cpu.cfs_period_us
```

计算 `ceil(quota / period)`，作为默认 GOMAXPROCS。如果是 cgroup v1 且没读到，回退到 `NumCPU()`。

**影响**：

| 场景 | Go 1.24 行为 | Go 1.25 行为 |
|------|--------------|--------------|
| 容器 cpu=2，宿主 64 核 | GOMAXPROCS=64，throttle 严重 | GOMAXPROCS=2，刚好 |
| 容器 cpu=0.5 | GOMAXPROCS=64 | GOMAXPROCS=1（向上取整） |
| 无 CPU 限制 | GOMAXPROCS=宿主核数 | 同 1.24 |
| 显式 `GOMAXPROCS=N` env | 用 env 值 | 同上，优先级最高 |

**迁移建议**：

```go
// Go 1.25 前必须显式引入这个库
import _ "go.uber.org/automaxprocs"

// Go 1.25 后可以移除，但保留也无害（库会检测原生支持）
```

升级到 Go 1.25 时观察指标：
- CPU throttle 比例（应该显著下降）
- p99 延迟（应改善）
- GC pause（应下降）
- goroutine 排队时间（可能略增——因为 P 少了，需要适当调大业务侧并发参数）

📎 **深入阅读**: [G11-精通-Goroutines-与-GMP-调度](../G11-精通-Goroutines-与-GMP-调度.md)

**常见追问**：
- Q: 用 CPU 亲和性 (taskset) 怎么算？  A: Go 1.25 用 cgroup quota 不是 cpuset，亲和性需要单独看 `sched_getaffinity`。新版本会综合两者取最小。
- Q: cpu.max 是 `max` 怎么办？  A: 无限制，回退到宿主核数。
- Q: 旧服务升级 1.25 后吞吐下降？  A: 之前可能误打误撞用满了 64 个 P 跑 IO 密集型；现在只剩 2 个，需要业务层提高 goroutine 并发数或 worker pool 大小。

**陷阱**：升级 Go 1.25 后某些"吃 throttle 不报错"的指标会变（throttle 下降→实际延迟下降→QPS 上升→可能撑爆下游），灰度上线务必看全链路。

## §2 Channel

### Q9 ⭐⭐⭐⭐ channel 底层数据结构（hchan）？sendq/recvq 是什么

**答**：

channel 在运行时是一个 `hchan` 结构体（`runtime/chan.go`）：

```go
type hchan struct {
    qcount   uint           // 当前缓冲区元素数
    dataqsiz uint           // 缓冲区容量
    buf      unsafe.Pointer // 指向环形数组（只有有缓冲 channel 才有）
    elemsize uint16         // 元素大小
    closed   uint32         // 是否已关闭
    elemtype *_type         // 元素类型
    sendx    uint           // 发送索引（环形数组）
    recvx    uint           // 接收索引
    recvq    waitq          // 等待接收的 G 队列
    sendq    waitq          // 等待发送的 G 队列
    lock     mutex          // 保护整个 hchan
}

type waitq struct {
    first *sudog
    last  *sudog
}
```

`sudog`（pseudo-g）是 G 在等待队列中的包装，含指向 G 的指针、数据地址、释放回调等。

**核心机制**：

**1. 发送 `ch <- v` 的快速路径与慢速路径**：

```
有缓冲 + 缓冲未满
   → 直接写入 buf[sendx]，sendx++，qcount++
   → 立即返回

有缓冲 + 缓冲满 / 无缓冲 + 没人在 recvq
   → 当前 G 包装成 sudog，挂到 sendq
   → gopark（让出 P）

无缓冲 + recvq 有等待者
   → 直接把 v 拷贝到等待者的接收地址（绕过 buf）
   → goready 唤醒接收者
   → 自己继续运行
```

**2. 接收 `<-ch` 镜像对称**：

```
有缓冲 + 缓冲非空
   → 从 buf[recvx] 读出，recvx++，qcount--
   → 如果 sendq 有等待者：把它的数据搬进 buf 末端，唤醒它

有缓冲 + 缓冲空 / 无缓冲 + 没人 sendq
   → 当前 G 入 recvq，gopark

无缓冲 + sendq 有等待者
   → 直接从等待者拷贝数据
   → goready 它，自己继续
```

📎 **深入阅读**: [G12-精通-Go-Channels-与-select](../G12-精通-Go-Channels-与-select.md)

**常见追问**：
- Q: 无缓冲 channel 有 buf 吗？  A: 没有，`dataqsiz=0`，发送和接收必须同步配对。
- Q: 锁的粒度多大？  A: 整个 hchan 一把锁，单条 send/recv 都要拿。所以高并发场景 channel 不是无锁的，比 atomic 慢 5-10 倍。
- Q: 为什么 send/recv 时不走 buf 直接拷贝？  A: 减少一次内存拷贝（buf→变量），等价但更快。

**陷阱**：把 channel 当"无锁高性能队列"是误解。频繁 send/recv 场景下，hchan.lock 是单点瓶颈，更适合用 atomic、ringbuffer (如 `container/ring`) 或者 sharding。

### Q10 ⭐⭐⭐⭐ 有缓冲 vs 无缓冲 channel 的区别

**答**：

|  | 无缓冲 `make(chan T)` | 有缓冲 `make(chan T, N)` |
|------|---------------------|----------------------|
| **通信语义** | 同步：send 等到 recv 才完成 | 异步：缓冲未满直接 send |
| **happens-before** | send 与 recv 同步点 | send 与对应的 recv 同步 |
| **buf 是否分配** | 否（dataqsiz=0） | 是（环形数组） |
| **典型用法** | 信号量、握手、保证顺序 | 解耦生产/消费、削峰、worker pool |

**同步通信例子**：

```go
done := make(chan struct{})
go func() {
    doWork()
    done <- struct{}{} // 阻塞直到主 goroutine 接收
}()
<-done // 这之后 doWork 一定完成
```

无缓冲 channel 等价于"我把这件事亲手交给你"，建立**强同步**。

**异步通信例子**：

```go
jobs := make(chan int, 100)
for i := 0; i < 10; i++ {
    go worker(jobs) // 10 个消费者
}
for i := 0; i < 1000; i++ {
    jobs <- i // 前 100 个不阻塞，后续等消费
}
```

有缓冲 channel 是"放在桌上等你来拿"，**解耦**了生产消费节奏。

**关键差异**：

1. **happens-before**：
   - 无缓冲：第 N 次 send **同步于** 第 N 次 recv 的完成。
   - 有缓冲：第 N 次 send **同步于** 第 N 次 recv 的**开始**（即 send 完成不代表 recv 开始）。
   - 关闭：close **同步于** 所有 recv 看到 zero-value。

2. **内存开销**：有缓冲 channel 起步多了 buf 的 `N * elemsize` 字节。

3. **常见 bug**：
   - 无缓冲：`go func() { ch <- 1 }()` 没人接 → 永久泄漏。
   - 有缓冲：`ch <- 1; ch <- 2` 缓冲只有 1 → 第二次阻塞。

**选择原则**：
- 需要"对方确认收到"用无缓冲。
- 需要"我先写到一边继续"用有缓冲。
- 不要靠 buffer 大小做流控——那是限流器的职责（rate.Limiter）。

📎 **深入阅读**: [G12-精通-Go-Channels-与-select](../G12-精通-Go-Channels-与-select.md)

**常见追问**：
- Q: `make(chan int, 1)` 和 `make(chan int)` + goroutine 哪个开销小？  A: 前者，省一个 sudog 分配。
- Q: buffer 设多少合适？  A: 没有银弹。worker pool 通常设 `2 * workers` 或 `0`（强反压）。生产消费节奏一致用 0~1，节奏不稳用大值。
- Q: 满了能扩容吗？  A: 不能，channel 大小创建后固定。

**陷阱**：缓冲设大不等于性能更好——大缓冲会**隐藏背压**，生产者一直猛灌，消费者跟不上时表现为延迟暴涨而非吞吐降低，更难排查。

### Q11 ⭐⭐⭐⭐⭐ channel 关闭的"原则"：谁负责关闭？关闭后读/写各发生什么

**答**：

**官方原则（Go FAQ）**：
- channel 应该由**发送方**关闭，且只关闭一次。
- 关闭的目的是**通知接收方"不会再有数据"**，不是清理资源。

**关闭后的行为**：

| 操作 | closed channel | 后果 |
|------|----------------|------|
| `<-ch`（缓冲有剩余） | 正常读，元素被消费 | 直到清空后返回 zero-value |
| `<-ch`（缓冲空） | 立即返回 zero-value | `v, ok := <-ch` 的 `ok` 为 `false` |
| `ch <- v` | **panic: send on closed channel** | 致命 |
| `close(ch)` 二次关闭 | **panic: close of closed channel** | 致命 |
| `close(nil)` | **panic: close of nil channel** | 致命 |

**正确关闭模式**：

**模式 1：单 sender，多 receiver** —— sender 直接关：

```go
func producer(ch chan<- int) {
    defer close(ch)
    for i := 0; i < 10; i++ {
        ch <- i
    }
}

func consumer(ch <-chan int) {
    for v := range ch { // close 后 range 自动退出
        fmt.Println(v)
    }
}
```

**模式 2：多 sender，单 receiver** —— receiver 不能关 channel（违反"sender 负责"），改用"中介 channel"：

```go
done := make(chan struct{})
ch := make(chan int)

// receiver 想停止：close(done)
go func() {
    for {
        select {
        case <-done:
            return
        case v := <-ch:
            handle(v)
        }
    }
}()

// 多 sender：每次发送前检查 done
go func() {
    for {
        select {
        case <-done:
            return
        case ch <- compute():
        }
    }
}()
```

**模式 3：多 sender，多 receiver** —— 引入"协调者 goroutine"或 `sync.Once`：

```go
var once sync.Once
closeCh := func() { once.Do(func() { close(ch) }) }
```

或更常见的：用 context 做退出信号，所有方监听 `ctx.Done()`，channel 不显式关闭（GC 自然回收）。

**为什么不能多次关闭**：close 操作会唤醒所有等待者并把 `closed` 标志设为 1，第二次 close 检测到已置位 → panic。这是设计选择，强制"恰好一次"语义。

**判断 channel 是否关闭的安全方法**：

```go
// 错误：竞态
// if !isClosed(ch) { ch <- v }  // 中间可能被 close

// 正确：用 recover 或 select default
select {
case ch <- v:
default:
    // channel 满 或 已 close（区分不了，所以这模式只在不关心错误时用）
}

// 真正的"安全发送"
defer func() { recover() }() // 防止 panic
ch <- v
```

📎 **深入阅读**: [G12-精通-Go-Channels-与-select](../G12-精通-Go-Channels-与-select.md)

**常见追问**：
- Q: 关闭 channel 会唤醒等待的发送者吗？  A: 会，但它们随即 panic（send on closed）。
- Q: 关闭 channel 会唤醒等待的接收者吗？  A: 会，全部唤醒，每个都收到 zero-value 和 `ok=false`。
- Q: 不 close 会内存泄漏吗？  A: 不会，GC 会回收无人引用的 channel，但等待在它上的 G 会永久挂起 → goroutine 泄漏。

**陷阱**：用 `len(ch) == 0` 判断"没数据了"是错的——并发场景下下一行立刻可能有 send；用 `close + range` 或 `select + done` 才是正确退出协议。

### Q12 ⭐⭐⭐⭐ nil channel 在 select 中的妙用

**答**：

**nil channel 的行为**：

| 操作 | nil channel |
|------|-------------|
| `<-ch` | **永久阻塞** |
| `ch <- v` | **永久阻塞** |
| `close(ch)` | **panic** |

看起来全是负面，但放进 `select` 里成了"动态关闭分支"的法宝——**select 会跳过 nil channel 分支**，相当于这个 case 不存在。

**经典应用：根据状态启用/禁用某个分支**：

```go
// 场景：处理一个慢生产者，但偶尔需要暂停消费

func consumer(input <-chan int, pause <-chan bool) {
    var data <-chan int = input // 初始启用
    paused := false

    for {
        select {
        case v := <-data:
            fmt.Println(v)
        case p := <-pause:
            paused = p
            if paused {
                data = nil    // 禁用 data 分支
            } else {
                data = input  // 重新启用
            }
        }
    }
}
```

这里关键：`data = nil` 后 `case v := <-data` 永远不会被选中，select 只剩 `pause` 分支生效。

**另一个例子：multiplexer 一边关闭后停止处理**：

```go
func merge(a, b <-chan int, out chan<- int) {
    for a != nil || b != nil {
        select {
        case v, ok := <-a:
            if !ok { a = nil; continue } // a 关闭后置 nil
            out <- v
        case v, ok := <-b:
            if !ok { b = nil; continue }
            out <- v
        }
    }
    close(out)
}
```

不置 nil 的话，关闭后的 channel 会立刻可读（返回 zero-value），select 会一直选中它形成死循环。

**第三种：发送侧动态启用**：

```go
var out chan<- int // 初始 nil，发送分支禁用
for {
    if hasData {
        out = realOut
    } else {
        out = nil
    }
    select {
    case out <- data:    // hasData=false 时这分支跳过
    case <-ctx.Done():
        return
    }
}
```

📎 **深入阅读**: [G12-精通-Go-Channels-与-select](../G12-精通-Go-Channels-与-select.md)

**常见追问**：
- Q: 全部 case 都是 nil 会怎么样？  A: select 永久阻塞；若有 `default` 则走 default。
- Q: 这种写法常见吗？  A: 在 fan-in、状态机、生产消费节流场景非常常用。
- Q: 怎么调试 nil channel 的死锁？  A: `pprof goroutine?debug=2` 看 G 阻塞在 `chanrecv (nil chan)`。

**陷阱**：`var ch chan int` 默认就是 nil，新手常以为是"空 channel 待初始化"，对它读写就死锁。要么 `make` 要么明确不打算用。

### Q13 ⭐⭐⭐ 列举几种 channel 死锁场景

**答**：

**1. 主 goroutine 直接读空 channel**：

```go
func main() {
    ch := make(chan int)
    <-ch // fatal error: all goroutines are asleep - deadlock!
}
```
runtime 检测到所有 G 都阻塞 → 报死锁。

**2. 无缓冲 channel 单 goroutine 自发送**：

```go
ch := make(chan int)
ch <- 1 // 主 G 阻塞，没有接收者
```

**3. 死循环发送 + 接收者退出**：

```go
ch := make(chan int)
go func() {
    for { ch <- compute() } // 接收者 break 后 → 永远阻塞
}()
for v := range ch {
    if v > 100 { break }
}
// goroutine 泄漏（runtime 检测不到，只有部分 G 阻塞）
```

**4. 循环依赖 (ABBA)**：

```go
a := make(chan int)
b := make(chan int)
go func() { a <- (<-b) }() // 等 b
go func() { b <- (<-a) }() // 等 a
// 互等死锁
```

**5. close 与 send race**：

```go
ch := make(chan int)
go func() { ch <- 1 }()  // 可能在 close 后执行
close(ch)
// → panic: send on closed channel（不是死锁但同样致命）
```

**6. select 全部分支阻塞且无 default**：

```go
select {
case <-c1: // c1 没人发
case <-c2: // c2 没人发
} // 卡死
```

**7. 持有锁同时操作 channel**：

```go
var mu sync.Mutex
ch := make(chan int)
go func() {
    mu.Lock()
    defer mu.Unlock()
    <-ch
}()
mu.Lock() // 永远拿不到，因为对方拿着锁等 ch
ch <- 1
mu.Unlock()
```

**8. WaitGroup 与 channel 顺序错乱**：

```go
var wg sync.WaitGroup
ch := make(chan int)
wg.Add(1)
go func() {
    defer wg.Done()
    ch <- 1
}()
wg.Wait()   // 等 Done，但 Done 要等 ch 被接收
<-ch        // 永远到不了
```
顺序应为：先 `<-ch` 再 `wg.Wait()`，或用有缓冲 channel。

**调试技巧**：
- `GOTRACEBACK=all` 触发死锁时打印所有 G 栈。
- 单 goroutine 死锁会被 runtime 自动检测；多 goroutine 死锁需要 `pprof`。
- `go test -race` 可发现部分时序问题。

📎 **深入阅读**: [G12-精通-Go-Channels-与-select](../G12-精通-Go-Channels-与-select.md)

**常见追问**：
- Q: runtime 怎么检测死锁？  A: 调度器在 schedule 时如果发现所有 M 都 park 且无 netpoll 事件，触发 `throw("all goroutines are asleep - deadlock!")`。
- Q: 部分死锁能检测吗？  A: 不能。runtime 只能检测"全部 G 都阻塞"。漏写消费者导致一两个 G 泄漏要靠 pprof。
- Q: 怎么从架构层面避免？  A: context 替代手工同步、有缓冲 channel + select default、显式超时、layered ownership（谁创建谁关闭）。

**陷阱**：单 goroutine 测试通过不代表生产无死锁——加上并发压测才能暴露 ABBA、close-race 等问题。

## §3 Select

### Q14 ⭐⭐⭐ select 的随机性是怎么实现的？为什么要随机

**答**：

**实现**：runtime 在执行 `select` 时：

1. 收集所有 case 的 channel 操作（send/recv）。
2. 用 `fastrand` 生成一个**随机排列**（Fisher-Yates 洗牌）。
3. 按这个随机顺序检查每个 case 是否可立即执行。
4. 有可执行 → 选一个；都不可 → 按顺序入等待队列，然后 park。

```go
// runtime/select.go 简化
func selectgo(cases []scase) {
    norder := make([]uint16, ncases)
    // ... 初始化为 0..n-1
    for i := 1; i < ncases; i++ {
        j := fastrandn(uint32(i + 1))
        norder[i], norder[j] = norder[j], norder[i]
    }
    // 按 norder 顺序遍历 cases
    for _, idx := range norder {
        c := cases[idx]
        if /* 可立即执行 */ {
            return idx
        }
    }
    // 入等待队列、park
}
```

**为什么要随机**：

1. **公平性**：如果按代码顺序固定，永远优先匹配第一个 case，可能导致其他分支饿死。

   ```go
   select {
   case v := <-fast: // 一直有数据
       handle(v)
   case v := <-slow: // 永远轮不到
       handle(v)
   }
   ```

   随机化保证两个分支被选中的期望概率相同。

2. **避免病态时序**：固定顺序会让某些时序触发同步性 bug，随机化能在多次运行中暴露问题。

3. **简化语义**：用户不应依赖 case 顺序，否则代码可读性差且易出错。

**注意：随机 ≠ 平均**：如果两个 case 都立即可执行，各 50% 概率；但如果一个 case 长期"刚好就绪"（生产快），另一个偶尔就绪，长期看仍偏向第一个，因为它每次进入 select 都可执行。

**default 的优先级**：default 不参与随机，**只有所有非 default case 都不可立即执行时**才走 default。

```go
select {
case <-ch:    // 不可执行
case <-ch2:   // 不可执行
default:      // 走这里
}
```

📎 **深入阅读**: [G12-精通-Go-Channels-与-select](../G12-精通-Go-Channels-与-select.md)

**常见追问**：
- Q: nil channel 参与随机吗？  A: 不参与。selectgo 会先剔除 nil case（永远不可执行）。
- Q: 随机用什么算法？  A: 早期 `nanotime` xor，新版本 `fastrand` (基于 PRNG)。
- Q: 能优先某个 case 吗？  A: 不行，select 不支持优先级。变通：嵌套 select + default，先单独检查高优先级。

**陷阱**：写测试时如果用 `time.Sleep` 配合 select，可能因为随机性偶发失败。改成强制时序（用 channel 同步）或 mock 时间。

### Q15 ⭐⭐⭐⭐ for-select 优雅退出的几种写法

**答**：

**模式 1：done channel + close**（最经典）：

```go
func worker(done <-chan struct{}, jobs <-chan int) {
    for {
        select {
        case <-done:
            return
        case j, ok := <-jobs:
            if !ok { return } // jobs 关闭也退出
            process(j)
        }
    }
}

// 外部调用
done := make(chan struct{})
go worker(done, jobs)
// ...
close(done) // 广播退出
```

`close(done)` 是广播信号：所有 select 监听者立刻被唤醒。

**模式 2：context.Context**（推荐，标准化）：

```go
func worker(ctx context.Context, jobs <-chan int) error {
    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case j, ok := <-jobs:
            if !ok { return nil }
            if err := process(ctx, j); err != nil {
                return err
            }
        }
    }
}

ctx, cancel := context.WithCancel(context.Background())
defer cancel()
go worker(ctx, jobs)
// 外部：cancel() 触发退出
```

context 还能传递超时、deadline、value，是 Go 1.7+ 的标准退出协议。

**模式 3：哨兵值 + 关闭 jobs channel**：

```go
func worker(jobs <-chan int) {
    for j := range jobs { // jobs close 后自动退出
        process(j)
    }
}
```

简洁但只适用于 sender 控制退出的场景。

**模式 4：errgroup + ctx**（推荐用于多 worker 一损俱损）：

```go
g, ctx := errgroup.WithContext(context.Background())
for i := 0; i < 10; i++ {
    g.Go(func() error {
        return worker(ctx, jobs)
    })
}
if err := g.Wait(); err != nil {
    log.Fatal(err)
}
```

任一 worker 返回 error → ctx 自动 cancel → 其他 worker 退出。

**模式 5：双层 select 优先级**：

```go
for {
    // 优先检查退出
    select {
    case <-ctx.Done(): return ctx.Err()
    default:
    }

    select {
    case <-ctx.Done(): return ctx.Err()
    case j := <-jobs: process(j)
    }
}
```

避免 jobs 一直有数据时 ctx.Done 被随机延迟到达。

**模式 6：超时退出**：

```go
timer := time.NewTimer(timeout)
defer timer.Stop()

select {
case <-ctx.Done(): return
case <-timer.C: return errors.New("timeout")
case j := <-jobs: process(j)
}
```

📎 **深入阅读**: [G12-精通-Go-Channels-与-select](../G12-精通-Go-Channels-与-select.md) · [G14-精通-Go-context-包](../G14-精通-Go-context-包.md)

**常见追问**：
- Q: done channel vs context 哪个好？  A: context 是社区共识，跨包传递更顺。done channel 适合简单场景或不能传 ctx 的库 API。
- Q: 多 worker 怎么等所有退出？  A: errgroup.Wait 或 sync.WaitGroup（Go 1.25 用 `wg.Go(fn)`）。
- Q: 退出时还有未处理任务怎么办？  A: 业务决定——丢弃（直接 return）、消费完（range 剩余）、持久化（写回队列）。

**陷阱**：在循环里 `defer timer.Stop()` 会在循环结束才生效，热循环每次创建 timer 会泄漏。要么 `timer.Reset`、要么循环外创建。

### Q16 ⭐⭐⭐⭐ select + time.After 的坑

**答**：

**坑**：`time.After(d)` 每次调用都创建一个新的 timer + channel，**timer 在 d 到达前不会被 GC**。在热循环里：

```go
for {
    select {
    case v := <-ch:
        handle(v)
    case <-time.After(5 * time.Minute): // 每次循环创建一个 5 分钟 timer
        return
    }
}
```

如果 `ch` 频繁有数据，5 分钟的超时 timer 来不及 fire 就被丢弃，但 timer 对象仍挂在 runtime 的 timer heap 上，**每次循环泄漏一个**。高 QPS 下数小时就能堆出几十万 timer，影响 timer wheel 性能 + 增加 GC 扫描。

**Go 1.23+ 改进**：`time.After` 现在能在被 GC 时及时清理 timer（不再等 fire），但**还是建议手动 Stop**，因为：
1. 旧 Go 版本仍受影响。
2. Stop 是立即释放，GC 触发有延迟。
3. timer.C 中可能还有未消费的 tick 占内存。

**正确写法 1：复用 timer**：

```go
timer := time.NewTimer(5 * time.Minute)
defer timer.Stop()

for {
    timer.Reset(5 * time.Minute) // 重置而不是新建
    select {
    case v := <-ch:
        handle(v)
        if !timer.Stop() {
            <-timer.C // 清空可能已 fire 的值
        }
    case <-timer.C:
        return
    }
}
```

注意 `Stop` 返回 false 表示 timer 已 fire，channel 里有值需要排空，否则下次 Reset 会和旧值竞争。

**Go 1.23+ 简化**：`Reset` 已能正确处理 race，`Stop` 后不需要手动排空 channel：

```go
// Go 1.23+
timer := time.NewTimer(5 * time.Minute)
defer timer.Stop()

for {
    timer.Reset(5 * time.Minute)
    select {
    case v := <-ch:
        handle(v)
    case <-timer.C:
        return
    }
}
```

**正确写法 2：context.WithTimeout**：

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Minute)
defer cancel()

for {
    select {
    case v := <-ch: handle(v)
    case <-ctx.Done(): return
    }
}
```

context 内部会做正确的 timer 管理，是最简洁的方式。

**正确写法 3：固定 deadline 而非每次重置超时**：如果超时是"整体最长 5 分钟"，用 `context.WithDeadline`；如果是"两次消息之间不能超过 5 分钟"，必须 Reset 模式。

📎 **深入阅读**: [G12-精通-Go-Channels-与-select](../G12-精通-Go-Channels-与-select.md)

**常见追问**：
- Q: time.After 在低频场景有问题吗？  A: 没有。每秒一次以下的循环用 time.After 完全 OK，可读性最好。
- Q: Stop + Reset 的正确顺序是？  A: Go 1.23+ 直接 Reset 即可；旧版本：`if !timer.Stop() { <-timer.C }; timer.Reset(d)`。
- Q: timer.C 是带缓冲的吗？  A: Go 1.23 之前是带缓冲的（cap=1），fire 后值留在 channel 里直到被消费，可能收到陈旧值；Go 1.23 起改为无缓冲（cap=0）的同步 channel，Stop/Reset 返回后不会再观察到旧配置对应的值。

**陷阱**：把"timer 泄漏"和"goroutine 泄漏"混为一谈。前者只是 timer 对象多，不会阻止程序退出；后者会让进程永远跑下去。但 timer 多了会让 sysmon 巡检变慢，间接影响延迟。

## §4 sync 包

### Q17 ⭐⭐⭐⭐⭐ Mutex 实现：自旋 + 饥饿模式

**答**：

`sync.Mutex` 是 Go 中最核心的并发原语，其实现经历过多次演进。当前实现要点：

```go
type Mutex struct {
    state int32  // 复合字段：locked/woken/starving/waiterCount
    sema  uint32 // 信号量，等待者 park 在这上面
}

const (
    mutexLocked      = 1 << 0  // 锁状态位
    mutexWoken       = 1 << 1  // 唤醒标记
    mutexStarving    = 1 << 2  // 饥饿模式
    mutexWaiterShift = 3       // 等待者计数从第 3 位开始
)
```

**Lock 路径**：

```
1. Fast path: CAS(state, 0, mutexLocked)
   成功 → 直接返回（无锁竞争）
2. Slow path: lockSlow
   循环:
   a) 普通模式 + 锁被持有 + 自旋次数 < 4
      → runtime.procyield 自旋（30 个 PAUSE 指令）
   b) 重试 CAS 加锁
      失败 → 增加 waiter 计数，semacquire park
      成功 → 退出
   c) 被唤醒后检查饥饿（等待时间 > 1ms）→ 进入饥饿模式
```

**普通模式 vs 饥饿模式**：

| 维度 | 普通模式 (Normal) | 饥饿模式 (Starving) |
|------|------------------|--------------------|
| **新 goroutine 来抢** | 与队首老 G 公平竞争（可能抢赢） | 直接排队，老 G 优先 |
| **唤醒后** | 与抢者竞争，可能再次失败 | 直接交付，无竞争 |
| **何时进入** | 等待者排队 > 1ms | （从普通切换） |
| **何时退出** | （从饥饿切换回） | 队列空 / 当前 G 等待 < 1ms |
| **吞吐** | 高（自旋 + 局部性好） | 低（无自旋） |
| **延迟尾巴** | 可能很长（unfair） | 有界（队列 FIFO） |

**饥饿模式的设计动机**：普通模式下"新来 G 偏袒"导致老等待者可能无限延迟（尾延迟 p99 > 1s）。1ms 是 trade-off：进入饥饿后吞吐下降但 p99 可控。

**Unlock 路径**：

```
1. Fast path: state -= mutexLocked
2. 检查 waiter 数：
   有等待者 → unlockSlow → semrelease 唤醒一个
3. 饥饿模式下：直接把锁"传递"给被唤醒的 waiter（runtime_Semrelease handoff=true）
```

**为什么自旋有用**：临界区通常很短（< 1μs），自旋 30 次（约 100ns）能避免昂贵的 park/unpark（约 1μs+）。但自旋仅在多核 + 可能很快释放时才划算，所以条件严格：
- `GOMAXPROCS > 1`
- 当前没有其他 G 在自旋
- P 本地队列非空（说明 P 还在干活）
- 当前已自旋 < 4 次

📎 **深入阅读**: [G13-精通-Go-sync-包](../G13-精通-Go-sync-包.md)

**常见追问**：
- Q: Mutex 是可重入的吗？  A: **不是**！同一 G 二次 Lock 会死锁。Go 故意不提供可重入锁，鼓励重新设计 API。
- Q: TryLock 什么时候加的？  A: Go 1.18 加了 `TryLock`，但官方明确"不建议常规使用"，主要用于死锁检测、监控等场景。
- Q: Mutex 的内存对齐有要求吗？  A: state 字段必须是 4 字节对齐（atomic 操作要求）。结构体里嵌入 Mutex 通常没问题。

**陷阱**：把 Mutex 当 struct 值传递会复制状态，导致两份锁互不影响 + race detector 报错。永远用指针传递。`go vet` 能检测大多数 Mutex 复制错误。

### Q18 ⭐⭐⭐⭐ RWMutex 的适用场景与陷阱

**答**：

`sync.RWMutex` 支持多个读者并发、单写者独占。语义：
- 多个 `RLock` 可共存
- 一个 `Lock` 排斥所有 `RLock`/`Lock`
- 等待中的 `Lock` 会阻塞**新来的** `RLock`（防止 reader 饥饿写者）

**适用场景**：**读远多于写**（10:1 以上）且**临界区相对长**（μs 级以上）。典型：
- 配置缓存
- 路由表
- 频繁查询、偶尔更新的字典

**不适用场景**：
- 读写比接近 → Mutex 更快（RWMutex 内部需要原子操作维护 reader 计数，开销大）
- 临界区极短（< 100ns）→ atomic 或 Mutex 更佳
- 写频繁 → 写者饥饿 + RLock 抖动 → 退化

**陷阱 1：写者饥饿（旧版本）**：Go 1.0 早期，连续 reader 会让 writer 永远等不到锁。当前实现已修复：一旦有 `Lock` 等待，新 `RLock` 必须排队。

**陷阱 2：嵌套 RLock 死锁**：

```go
var rw sync.RWMutex

func read() {
    rw.RLock()
    defer rw.RUnlock()
    deeper() // 又调用 read 风格的函数
}

func deeper() {
    rw.RLock()
    defer rw.RUnlock()
    // ... 看起来没事
}
```

单 reader 时正常；但如果中间有 writer 等待：
```
G1: RLock() → 进入 deeper
G2: Lock() → 等待（要求当前 reader 退出）
G1: RLock() → 等待（writer 排在前面）
→ 死锁
```

**RWMutex 不可重入**！

**陷阱 3：把 RLock 当作"只读保证"**：RLock 保护的临界区里**修改数据**是 race：

```go
rw.RLock()
m["key"] = value // 多个 reader 同时写 → race!
rw.RUnlock()
```

RWMutex 只保证 reader 之间不互斥，不保证只读语义。

**陷阱 4：RWMutex 比 Mutex 慢**：基准测试常见结果（无竞争场景）：
```
BenchmarkMutex/Lock-8      300ns
BenchmarkRWMutex/RLock-8   400ns
BenchmarkRWMutex/Lock-8    500ns
```
因为 RLock 需要 atomic.AddInt32 + 检查 writer 等待状态，比 Mutex 的 CAS 复杂。竞争场景下读者并发收益才显现。

**替代方案**：
- `sync.Map`：键值场景
- `atomic.Pointer`：整体不可变结构的 copy-on-write
- 双缓冲 + atomic swap：高频读、低频写

📎 **深入阅读**: [G13-精通-Go-sync-包](../G13-精通-Go-sync-包.md)

**常见追问**：
- Q: 升级锁（RLock → Lock）能做吗？  A: 不能直接升级，必须先 RUnlock 再 Lock，期间状态可能变化要重新检查。
- Q: 怎么知道当前持有写锁？  A: 没有公开 API。需要自己用额外变量记录。
- Q: RWMutex 的内存模型？  A: `Lock` 同步于 `RLock/Lock`，`RLock` 同步于对应 `Lock`。

**陷阱**：性能优化误用——把所有锁都换成 RWMutex 期望提升吞吐，实际多数场景反而变慢。先 benchmark。

### Q19 ⭐⭐⭐⭐ sync.Once 的实现关键点

**答**：

`sync.Once` 保证某函数**恰好执行一次**，即使多 goroutine 并发调用。简化实现：

```go
type Once struct {
    done atomic.Uint32 // Go 1.21+ 用 atomic.Uint32
    m    Mutex
}

func (o *Once) Do(f func()) {
    if o.done.Load() == 0 {  // 1) 快速路径：atomic 检查
        o.doSlow(f)
    }
}

func (o *Once) doSlow(f func()) {
    o.m.Lock()                // 2) 加锁
    defer o.m.Unlock()
    if o.done.Load() == 0 {   // 3) double-check
        defer o.done.Store(1) // 4) 标记完成（defer 保证 panic 也置位？不！见下文）
        f()
    }
}
```

**关键设计点**：

**1. Double-check 模式**：

- 第一次检查无锁，多数调用快速返回（hot path）。
- 第二次检查在锁内，避免 race（两个 G 同时通过第一次检查）。
- 必须用 atomic 而非普通 read，否则编译器/CPU 重排会破坏 happens-before。

**2. 为什么不用 CAS 替代 Mutex**：

CAS 版本看似可行：

```go
// 错误示例！
func (o *Once) DoBad(f func()) {
    if o.done.CompareAndSwap(0, 1) {
        f() // 谁 CAS 成功谁执行
    }
}
```

问题：CAS 成功后 f 还没执行完，另一个 G 检查 done==1 就直接返回 → 误以为初始化完了 → 读取到未初始化数据。

正确版本必须让"其他 G 等待 f 完成"，Mutex 提供这个语义（其他 G park 在 Mutex 上）。

**3. f panic 怎么办**：

```go
var once sync.Once
func() {
    defer func() { recover() }()
    once.Do(func() { panic("oops") })
}()

once.Do(func() { fmt.Println("again") }) // 不会执行！
```

panic 后 `done` **仍然被置为 1**（早期实现使用 defer 设置；Go 1.x 后改为先标记后调用，避免遗留 race，但语义保持："Do 调用 f 一次，无论 f 是否成功"）。

实际查 Go 1.21+ 源码：

```go
func (o *Once) doSlow(f func()) {
    o.m.Lock()
    defer o.m.Unlock()
    if o.done.Load() == 0 {
        defer o.done.Store(1) // 实际是 defer
        f()
    }
}
```

注意 `defer o.done.Store(1)`：如果 f panic，defer 仍执行，done 置 1。所以**panic 视为完成**，下次 Do 不再调用 f。

这是有意为之：避免"持续重试" → 同一资源被反复初始化失败的雪崩。如果想重试，要自己实现：

```go
type ResettableOnce struct {
    done atomic.Bool
    m    sync.Mutex
}

func (o *ResettableOnce) DoTry(f func() error) error {
    if o.done.Load() { return nil }
    o.m.Lock()
    defer o.m.Unlock()
    if o.done.Load() { return nil }
    if err := f(); err != nil { return err }
    o.done.Store(true)
    return nil
}
```

**4. Go 1.21+ 新增 `sync.OnceFunc`/`OnceValue`/`OnceValues`**：

```go
var loadConfig = sync.OnceValue(func() *Config {
    return doExpensiveLoad()
})

cfg := loadConfig() // 自动 Once 化
```

减少样板代码。

📎 **深入阅读**: [G13-精通-Go-sync-包](../G13-精通-Go-sync-包.md)

**常见追问**：
- Q: 为什么 done 用 uint32 而不是 bool？  A: 老版本 atomic 包没有 atomic.Bool（Go 1.19 才有），用 uint32 是历史包袱。Go 1.21+ 改为 atomic.Uint32。
- Q: 同一个 Once 可以传不同 f 吗？  A: 可以但只有第一次的 f 会执行，其他 f 直接跳过。语义是"Do 一次"，不是"每个 f 一次"。
- Q: Once 能复位吗？  A: 标准库不能。需要复位用上面的自定义 ResettableOnce。

**陷阱**：递归调用 Once.Do 自己 → 死锁（Mutex 不可重入）：

```go
once.Do(func() {
    once.Do(...) // 死锁
})
```

### Q20 ⭐⭐⭐⭐ sync.Pool 用途和陷阱

**答**：

`sync.Pool` 是一个**对象池**，用来复用短生命周期对象，减少 GC 压力。典型用法：

```go
var bufPool = sync.Pool{
    New: func() any {
        return new(bytes.Buffer)
    },
}

func Handle(w http.ResponseWriter, r *http.Request) {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset()
    defer bufPool.Put(buf)
    // 使用 buf...
}
```

**实现要点**：

每个 P 持有 local pool（无锁），加上 victim cache（上轮 GC 残留）：

```
Get:
  1. P.local 有 → 直接取
  2. P.local 空 → victim 取（上一轮 GC 没回收的）
  3. 都空 → 从其他 P steal（一半）
  4. 都没有 → 调用 New()

Put:
  放回当前 P.local
```

**关键性质**：

1. **GC 时清空**：每次 GC，pool 中所有对象都会被释放（实际是 local 变 victim，victim 直接丢）。这保证 pool 不会无限增长。
2. **无大小上限**：调用方只 Put 多少存多少（直到 GC）。
3. **不保证存活**：Put 进去的对象**可能立即被 GC 回收**，所以 Pool 只用于"性能优化"，不用于"对象注册表"。

**陷阱 1：Pool 不是缓存**：

```go
// 错误用法
var dbConnPool = sync.Pool{
    New: func() any { return openConn() }, // 每次 GC 都丢 → 频繁建连
}
```

数据库连接、文件句柄这类**有状态、获取昂贵**的对象应该用专用池（database/sql 的连接池、自定义 LRU），而不是 sync.Pool。

**陷阱 2：放入大对象+少使用 → 内存浪费**：

```go
var pool = sync.Pool{
    New: func() any { return make([]byte, 10<<20) }, // 10MB
}
// 偶尔 Get 几次 → 每个 P 都 cache 一份 → 占用 P*10MB
```

GOMAXPROCS=64 时光 Pool 就吃 640MB。控制 Pool 的对象大小，或加上"大小过滤"（Put 时检查是否过大，过大不放回）。

**陷阱 3：不 Reset 状态**：

```go
b := bufPool.Get().(*bytes.Buffer)
// 忘了 b.Reset() → 残留之前的数据
b.WriteString("new")
```

Pool 复用的是**对象**，状态需要使用方清理。

**陷阱 4：放入逃逸到堆的对象**：sync.Pool 的优势是减少堆分配；但 Pool 本身的对象总是在堆上（Get 返回 interface{}）。所以如果对象本来就在栈上分配（小 buf 没逃逸），用 Pool 反而更慢。先 escape analysis。

**陷阱 5：放回不同类型**：interface{} 没有类型检查，断言失败 panic。建议每个 Pool 只放一种类型。

**适用场景**：
- `bytes.Buffer`、`gzip.Writer` 这类有 Reset 方法的对象
- protobuf 序列化对象（每次 RPC 新建一个）
- json encode 的临时 buffer

**不适用**：
- 长生命周期对象
- 需要"恰好 N 个实例"的场景（用 channel 实现的信号量 + slice）
- 异步释放（Put 后还要用）

📎 **深入阅读**: [G13-精通-Go-sync-包](../G13-精通-Go-sync-包.md)

**常见追问**：
- Q: Pool 里的对象什么时候 GC？  A: GC 周期开始时把 local 移到 victim，victim 上一轮的直接释放，相当于活两轮 GC。
- Q: 多 GOMAXPROCS 性能影响？  A: P 多 → local 多 → cache miss 少，但 GC 释放的总量大。GOMAXPROCS=64 比 4 时 Pool 命中率高，但 GC 后释放更多。
- Q: 怎么观测 Pool 效果？  A: pprof allocs 看是否减少；自定义 hit/miss 计数器。

**陷阱**：把 sync.Pool 当作"性能银弹"——很多场景下逃逸分析已经把对象放栈上，再用 Pool 反而引入开销（Put 时拷贝到堆）。先 profile 再优化。

### Q21 ⭐⭐⭐⭐ WaitGroup 的注意事项 + Go 1.25 `WaitGroup.Go`

**答**：

`sync.WaitGroup` 用于等待一组 goroutine 完成。经典用法：

```go
var wg sync.WaitGroup
for i := 0; i < 10; i++ {
    wg.Add(1)
    go func(i int) {
        defer wg.Done()
        work(i)
    }(i)
}
wg.Wait()
```

**陷阱 1：Add 必须在 Wait 之前**：

```go
// 错误
for i := 0; i < 10; i++ {
    go func() {
        wg.Add(1)        // 可能在 Wait 之后才执行
        defer wg.Done()
        work()
    }()
}
wg.Wait()
```

修复：在 goroutine 外面 Add。

**陷阱 2：Add 的参数是 delta**：负数会触发 panic（counter < 0）。`Add(-1)` 等价于 `Done()`，但建议用 `Done()` 更清晰。

**陷阱 3：复用 WaitGroup 的注意事项**：

```go
var wg sync.WaitGroup
for batch := 0; batch < N; batch++ {
    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func() { defer wg.Done(); work() }()
    }
    wg.Wait()
    // 这里可以再次使用，因为 Wait 返回时 counter 已归零
}
```

可以复用，但**不能并发 Add/Wait**——必须等 Wait 返回后再 Add 新一轮。

**陷阱 4：WaitGroup 不能复制**：嵌入到 struct 时一定要用指针：

```go
type Worker struct {
    wg sync.WaitGroup // OK，但传递 Worker 必须用 *Worker
}

func (w *Worker) Run() {
    w.wg.Add(1)
    go func() { defer w.wg.Done(); ... }()
}

func (w Worker) Bad() { // 接收者是值！wg 被复制 → 错误
    w.wg.Wait() // 等的是新拷贝
}
```

`go vet` 会检测大多数复制错误。

**Go 1.25 新方法 `WaitGroup.Go`**：

```go
// 老写法
var wg sync.WaitGroup
for _, item := range items {
    wg.Add(1)
    go func(it Item) {
        defer wg.Done()
        process(it)
    }(item)
}
wg.Wait()

// Go 1.25 新写法
var wg sync.WaitGroup
for _, item := range items {
    item := item // Go 1.22+ 不需要这行了
    wg.Go(func() {
        process(item)
    })
}
wg.Wait()
```

`wg.Go(fn)` 等价于 `wg.Add(1); go func() { defer wg.Done(); fn() }()`。优势：
- 减少样板代码
- 避免忘记 `defer wg.Done()`
- 避免 Add 在 goroutine 内的常见错误

**适用与不适用**：
- 适合：知道任务数、不需要传递错误、不需要 cancel。
- 不适合：需要错误传递 → `errgroup.Group`（也有 `errgroup.Go`，Go 1.25 之前就有）；需要并发控制 → `errgroup.SetLimit` 或 worker pool。

📎 **深入阅读**: [G13-精通-Go-sync-包](../G13-精通-Go-sync-包.md)

**常见追问**：
- Q: WaitGroup 怎么实现的？  A: 一个 64 位字段，高 32 位是 counter，低 32 位是 waiter 数。Add 用 atomic.AddInt64，Done 等价 Add(-1)。Wait 用信号量 park。
- Q: counter 溢出怎么办？  A: 设计上不会，超过 int32 max 算未定义行为。实际单进程几十亿 goroutine 也吃不消。
- Q: WaitGroup 能取消吗？  A: 不能。它只能等所有 Done。需要取消用 context + errgroup。

**陷阱**：`wg.Wait()` 之后还要再 `wg.Add()` 必须确保**没有任何 G 在 Wait**——并发 Add 和 Wait 是 race，runtime 会 panic。复用 WaitGroup 时要谨慎。

### Q22 ⭐⭐⭐⭐ atomic vs Mutex：什么场景该用 atomic

**答**：

**atomic 适用条件**（同时满足）：

1. **单变量**：只更新一个字段。多字段必须用 Mutex 保证组合一致性。
2. **无复合操作**：不需要"读-决策-写"中间不能被打断。
3. **简单类型**：int32/int64/uintptr/uint32/uint64/Pointer。复杂结构体不行。
4. **不需要等待**：atomic 不能"阻塞直到条件满足"。

**性能对比**（无竞争）：

```
atomic.AddInt64  ~5 ns
Mutex.Lock+Unlock ~25 ns
```

竞争激烈时差距可能拉大到 10-100x（Mutex 涉及 park/unpark）。

**典型用法**：

```go
// 1) 计数器
var counter atomic.Int64
counter.Add(1)
val := counter.Load()

// 2) 标志位
var done atomic.Bool
done.Store(true)
if done.Load() { ... }

// 3) 单生产者/消费者状态机
var state atomic.Int32 // 0=idle, 1=running, 2=stopped
if state.CompareAndSwap(0, 1) { /* 抢到执行权 */ }

// 4) 指针快照（copy-on-write）
var configPtr atomic.Pointer[Config]
configPtr.Store(newConfig)
cfg := configPtr.Load()

// 5) seqlock 风格的低争用读多写少
```

**Mutex 必须用的场景**：

```go
// 多字段必须一致
mu.Lock()
balance = balance - amount
log = append(log, tx)
mu.Unlock()

// 条件等待
mu.Lock()
for !ready {
    cond.Wait()
}
mu.Unlock()

// 复合操作（读改写）
mu.Lock()
if m[k] == nil { m[k] = newVal() }
mu.Unlock()
```

虽然最后一个例子也可以用 CAS 改写，但代码可读性骤降，且要小心 ABA。

**atomic 高级用法**：

**1. CAS 循环（无锁更新）**：

```go
for {
    old := ptr.Load()
    new := compute(old)
    if ptr.CompareAndSwap(old, new) { break }
    // CAS 失败说明有人抢先，重试
}
```

**2. atomic.Pointer[T]** (Go 1.19+) 类型安全的指针 atomic：

```go
var p atomic.Pointer[MyStruct]
p.Store(&MyStruct{...})
v := p.Load() // 返回 *MyStruct
```

替代了不安全的 `unsafe.Pointer` 用法。

**3. 内存序问题**：Go 的 atomic 是 **sequentially consistent**（最强内存序），不像 C++ 还有 relaxed/acquire/release。简单但慢。

**陷阱 1：atomic 不能跨平台保证 8 字节对齐**（32 位平台）。Go 1.19 之前需要：

```go
type S struct {
    count int64  // 32 位平台可能未对齐 → atomic 操作 panic
}
```

修复：把 int64 放结构体首位，或用 Go 1.19+ 的 `atomic.Int64`（runtime 保证对齐）。

**陷阱 2：CAS 的 ABA**：值从 A→B→A，CAS 仍能成功，但中间发生过变化。Go 没有内置 versioned pointer，需要自己加版本号。

**陷阱 3：误以为 atomic 字段就线程安全**：单字段 atomic ≠ 整个对象线程安全。如果对象有多个字段交叉读写，仍需 Mutex 或精心设计。

📎 **深入阅读**: [G13-精通-Go-sync-包](../G13-精通-Go-sync-包.md)

**常见追问**：
- Q: atomic.Int64 和直接用 int64 + atomic.AddInt64 哪个好？  A: Go 1.19+ 优先 `atomic.Int64`，类型安全 + 自动对齐。
- Q: atomic.Value 和 atomic.Pointer 的区别？  A: atomic.Value 早期方案（interface{} 包装），需要类型一致。atomic.Pointer 是泛型版本，更安全。新代码用 Pointer。
- Q: atomic 操作是 CPU 原子吗？  A: 是。底层用 LOCK 前缀（x86）或 LDREX/STREX（ARM）等原子指令。

**陷阱**：滥用 atomic 实现"无锁队列"——CAS 循环在高竞争下退化（live-lock），不如直接 Mutex。Go 标准库的 sync.Pool 内部就用 Mutex + 分片，而不是无锁数据结构。

## §5 Context

### Q23 ⭐⭐⭐⭐ context 的树形结构？cancel 信号怎么传播

**答**：

**结构**：Context 是树形 —— 父 → 子的单向引用，子记录父（用于继承 deadline/value），父记录子（用于级联 cancel）。

```go
type cancelCtx struct {
    Context             // 父 ctx
    mu        sync.Mutex
    done      atomic.Value // chan struct{}
    children  map[canceler]struct{}
    err       error
}
```

**创建关系**：

```go
ctx := context.Background()                          // 根
ctx1, cancel1 := context.WithCancel(ctx)             // 子
ctx2, cancel2 := context.WithTimeout(ctx1, 5*time.Second) // ctx1 的子
ctx3 := context.WithValue(ctx2, "key", "v")          // ctx2 的子
```

**传播规则**：

1. **cancel 向下传播**：cancel 父 → 所有子（递归）的 Done channel 关闭、Err 返回。
2. **deadline 取最严格**：子的 deadline 不能晚于父，否则被截断。
3. **value 向上查询**：`ctx.Value(k)` 沿父链查找，找到第一个匹配返回。

**cancel 实现要点**：

```go
func (c *cancelCtx) cancel(removeFromParent bool, err error) {
    c.mu.Lock()
    c.err = err
    close(c.done.Load().(chan struct{}))
    for child := range c.children {
        child.cancel(false, err) // 递归 cancel 子
    }
    c.children = nil
    c.mu.Unlock()
    if removeFromParent {
        removeChild(c.Context, c) // 从父的 children 集合移除
    }
}
```

**为什么要 `removeFromParent`**：避免子 ctx 在父还活着时挂着，造成内存泄漏。`cancel()` 调用时必为 true；级联触发时为 false（父正在遍历 children，避免并发修改）。

**cancel 何时触发**：
- 显式调用返回的 `cancel()`
- `WithTimeout`/`WithDeadline` 到期（内部启动 timer）
- 父 ctx 被 cancel（级联）

**Done channel 何时返回**：
- `Background`/`TODO`：返回 nil（永不关闭）
- `cancelCtx`：返回内部 channel，cancel 时关闭
- `valueCtx`：透传父的 Done

**为什么 Done 用 channel 而不是 bool**：可以放进 select，统一退出协议：

```go
select {
case <-ctx.Done():
    return ctx.Err()
case v := <-ch:
    process(v)
}
```

**Go 1.21 新增 `WithoutCancel`**：派生一个不受父 cancel 影响的 ctx（但保留 value）。用于发起后台清理任务：

```go
func handler(ctx context.Context) {
    // 请求 ctx 取消后立即返回，但后台异步上报仍要做完
    go report(context.WithoutCancel(ctx))
}
```

**Go 1.21 新增 `AfterFunc`**：注册一个回调，ctx cancel 时异步执行：

```go
stop := context.AfterFunc(ctx, func() {
    cleanup()
})
defer stop() // ctx 没 cancel 也可以主动取消注册
```

📎 **深入阅读**: [G14-精通-Go-context-包](../G14-精通-Go-context-包.md)

**常见追问**：
- Q: cancel 必须调用吗？  A: 是的。即使 ctx 自然到期（timeout），也应 defer cancel() 释放资源（子 ctx 引用、timer 句柄）。`go vet` 会检测未调用的 cancel。
- Q: 同一 ctx 多次 cancel 安全吗？  A: 是的，幂等。但 `WithCancel` 返回的 cancel 函数内部有 once 保护。
- Q: 怎么观察 ctx 树？  A: 没有内置 API，需要自己包装。pprof 不显示 ctx 关系。

**陷阱**：把 ctx 当成全局变量传递（如放进 sync.Map）——ctx 设计是请求生命周期内的，存活久了的 ctx 持有大量 value 不释放就是泄漏。

### Q24 ⭐⭐⭐ context.WithValue 适合放什么？不适合放什么

**答**：

**官方建议**：`WithValue` 仅用于**跨 API 边界的请求范围数据**，不应用于函数参数。

**适合放**：

1. **请求 ID / Trace ID**：用于日志关联、分布式追踪。
2. **用户身份**：认证后的 user ID/角色。
3. **租户 ID**：多租户场景。
4. **日志元数据**：requestSource、IP 等。
5. **金丝雀标识**：灰度路由信息。

```go
type ctxKey int
const (
    keyRequestID ctxKey = iota
    keyUser
)

ctx = context.WithValue(ctx, keyRequestID, uuid.New().String())
reqID := ctx.Value(keyRequestID).(string)
```

**不适合放**：

1. **函数参数**：`process(ctx, userID)` 优于 `process(WithValue(ctx, "uid", userID))`。
2. **可选参数 / 业务对象**：DB 连接、配置等应该显式注入。
3. **可变状态**：context 应该是只读的，可变状态用 channel/mutex。
4. **大量数据**：每个 Value 都新建一个 ctx 节点，链长查询 O(n)。

**为什么用自定义类型作为 key**：

```go
// 错误
ctx = context.WithValue(ctx, "userID", 42)

// 正确
type ctxKey int
const keyUserID ctxKey = 1
ctx = context.WithValue(ctx, keyUserID, 42)
```

字符串 key 会和其他包冲突（不同包都用 "userID"）。自定义类型（特别是非导出类型）天然唯一。

**Value 查询的性能**：

```go
// 链：root → ctx1 → ctx2 → ctx3
// ctx3.Value(k) → ctx3 没有 → ctx2 没有 → ctx1 有 → 返回
// O(n) 链长
```

链不长（< 10）影响可忽略，但极端情况（深嵌套、热路径）要小心。

**Go 风格的封装**：

```go
package logctx

type ctxKey struct{}

func WithLogger(ctx context.Context, logger *slog.Logger) context.Context {
    return context.WithValue(ctx, ctxKey{}, logger)
}

func From(ctx context.Context) *slog.Logger {
    if l, ok := ctx.Value(ctxKey{}).(*slog.Logger); ok {
        return l
    }
    return slog.Default()
}
```

key 类型用 `struct{}` 是更现代的写法，零内存占用 + 类型唯一。

📎 **深入阅读**: [G14-精通-Go-context-包](../G14-精通-Go-context-包.md)

**常见追问**：
- Q: ctx.Value 是 thread-safe 吗？  A: 是的，ctx 是不可变的（每次 WithValue 创建新节点），并发读安全。
- Q: 怎么传递可变上下文？  A: 把指针放进 Value（如 `*RequestState`），但内部修改要自己加锁，且这破坏了 ctx 的"只读"约定。
- Q: WithValue 会有 ABI 兼容问题吗？  A: 不会，但跨进程（RPC）必须显式序列化，不能依赖 ctx 自动传递（gRPC 用 metadata）。

**陷阱**：在 HTTP middleware 链里反复 WithValue → ctx 链很深，每次 Value 查询 O(n)。如果是同一 key 不同 layer，考虑合并成一个结构体。

### Q25 ⭐⭐⭐⭐ 自定义 context.Context 实现的注意点

**答**：

`context.Context` 是 interface：

```go
type Context interface {
    Deadline() (deadline time.Time, ok bool)
    Done() <-chan struct{}
    Err() error
    Value(key any) any
}
```

理论上可以自定义实现，但有不少坑。

**典型自定义场景**：
1. **包装第三方 ctx**：把别的 cancel 机制（如 channel）适配成 ctx。
2. **添加跟踪/度量**：拦截 Value 查询做埋点。
3. **测试 mock**：注入特定 deadline 或 err。
4. **多源 cancel 合并**：等任一源 cancel。

**核心要点**：

**1. 一定要嵌入或代理父 ctx**：

```go
type myCtx struct {
    context.Context // 嵌入：免费获得四个方法
    // 重写你需要定制的
}

func (m *myCtx) Value(key any) any {
    if key == myKey {
        return m.myVal
    }
    return m.Context.Value(key) // 透传到父
}
```

不嵌入会丢失 deadline / cancel 传播。

**2. Done() 必须满足"once close"**：

```go
type bothCancelled struct {
    context.Context
    ch chan struct{}
    once sync.Once
}

func (b *bothCancelled) Done() <-chan struct{} { return b.ch }
func (b *bothCancelled) cancel() {
    b.once.Do(func() { close(b.ch) })
}
```

关闭 ch 必须幂等。

**3. Err() 与 Done() 一致**：Done 关闭后 Err 必须返回非 nil；Done 未关闭时 Err 必须返回 nil。

**4. 多源合并的官方模式（Go 1.20+ 推荐用 `WithCancelCause` + 自己包装）**：

```go
// 老式实现
func MergeCancel(ctxs ...context.Context) (context.Context, context.CancelFunc) {
    mergedCtx, cancel := context.WithCancel(context.Background())
    for _, c := range ctxs {
        go func(c context.Context) {
            select {
            case <-c.Done():
                cancel() // 任一源完成就 cancel
            case <-mergedCtx.Done():
                return
            }
        }(c)
    }
    return mergedCtx, cancel
}
```

这种实现每个父 ctx 一个监听 goroutine，注意泄漏：调用方必须 cancel 这个 mergedCtx 才能停掉所有 goroutine。

**5. Go 1.21+ 推荐方式**：

`context.AfterFunc(parent, fn)` 注册回调，避免显式 goroutine：

```go
func MergeCancel(parent context.Context, others ...context.Context) (context.Context, context.CancelFunc) {
    ctx, cancel := context.WithCancel(parent)
    for _, other := range others {
        stop := context.AfterFunc(other, cancel)
        _ = stop // 调用方 cancel 主 ctx 时会自动解除
    }
    return ctx, cancel
}
```

**6. WithCancelCause / Cause** (Go 1.20+)：

允许携带 cancel 的原因：

```go
ctx, cancel := context.WithCancelCause(parent)
cancel(errors.New("client disconnected"))

// 下游
if err := ctx.Err(); err != nil {
    cause := context.Cause(ctx) // "client disconnected"
}
```

自定义 ctx 实现时如果要支持 Cause，需要嵌入 cancelCtx 而非自己实现。

**7. 别忘了 race 检测**：自定义 Done channel 关闭和 Err 设值必须 happens-before，不然 race detector 会告警。

📎 **深入阅读**: [G14-精通-Go-context-包](../G14-精通-Go-context-包.md)

**常见追问**：
- Q: 为什么 context 不能自己 cancel 父？  A: 设计上是单向：父 cancel 子，子不能 cancel 父。否则会造成所有权混乱。
- Q: nil context 能用吗？  A: 不能。函数参数中传 nil 会 panic（Done 等 nil deref）。用 context.TODO()。
- Q: emptyCtx 能 cancel 吗？  A: 不能。Background/TODO 的 Done 返回 nil，永不关闭。

**陷阱**：自定义 ctx 时把 `Done` 实现成"每次返回新 channel"——这破坏了 select 在 `<-ctx.Done()` 上的稳定性，且 race detector 检测不到。Done 必须始终返回同一个 channel。

## §6 Race 与内存模型

### Q26 ⭐⭐⭐⭐ `-race` 检测怎么工作？开销多大

**答**：

**底层原理**：Go race detector 基于 Google 的 **ThreadSanitizer (TSan)** 算法，编译时插桩 + 运行时记录每次内存访问的"happens-before 关系"。

**实现要点**：

1. **编译插桩**：`go build -race` 让编译器在每个内存读写指令前插入运行时调用：

   ```
   // 原始代码
   x = 42

   // 插桩后（伪代码）
   __tsan_write8(&x)
   x = 42
   ```

   每次访问都会上报到 race runtime。

2. **运行时影子内存**：每 8 字节的程序内存对应 32 字节的 **shadow memory**，记录最近 4 个访问（goroutine ID + 时钟戳 + 读/写）。

3. **Vector clock**：每个 goroutine 维护一个向量时钟，跟踪它对其他 goroutine 的"已知最新事件"。

4. **同步事件更新时钟**：channel send/recv、Mutex Lock/Unlock、atomic 操作等"同步原语"会更新双方的向量时钟，建立 happens-before。

5. **检测竞争**：每次访问 X，检查影子内存中最近的访问，如果两次访问之间没有 happens-before 关系 + 至少一次是写 → 报告 race。

**开销**：

- **CPU**：通常 **2-20 倍**慢，热路径插桩多的极端情况可达 100x。
- **内存**：**5-10 倍**，因为 shadow memory + 元数据。
- **二进制大小**：增加 ~20%。

所以 race detector **不适合生产**，只在测试 + 灰度环境运行。

**使用建议**：

```bash
# 所有测试都开 race
go test -race ./...

# 关键服务在 CI 跑长稳压测
go test -race -run TestStress -count=100

# 灰度环境少量实例开 race（金丝雀）
go build -race -o myservice
```

**race detector 的局限**：

1. **运行时检测**：必须代码实际执行到 race 才发现。100% 覆盖率才能保证发现所有 race。
2. **假阴性**：没跑到的代码不报。
3. **几乎无假阳性**：TSan 算法理论上不会误报，所以一旦报了就是真的（除非有黑魔法绕过插桩，如 cgo、`go:nocheckptr`）。
4. **不能检测 unsafe**：直接用 unsafe.Pointer 绕过的访问可能漏检。
5. **不检测死锁**：单 goroutine 全部阻塞由 runtime 检测，多 goroutine 死锁要靠 pprof。

**报告格式示例**：

```
==================
WARNING: DATA RACE
Write at 0x00c0000180a8 by goroutine 7:
  main.increment()
      /tmp/main.go:10 +0x44

Previous read at 0x00c0000180a8 by goroutine 6:
  main.read()
      /tmp/main.go:15 +0x44

Goroutine 7 (running) created at:
  main.main()
      /tmp/main.go:21 +0x95
==================
```

包括两个冲突访问的位置、goroutine 创建点，定位很快。

📎 **深入阅读**: [G16-精通-Go-Race-Detection](../G16-精通-Go-Race-Detection.md)

**常见追问**：
- Q: race detector 能查到 happens-before 吗？  A: 它就是用 happens-before 算法工作的，但不会"显示"关系，只在出错时报。
- Q: 开 race 后程序更慢，能优化吗？  A: 减少同步原语使用、避免热路径上的锁、用 atomic 替代 Mutex（atomic 也会插桩但开销小）。
- Q: 怎么屏蔽某段已知"benign race"？  A: 标准做法是修复（没有真正 benign 的 race）。需要绕过用 `runtime.NoEscape` 或直接关 race。

**陷阱**：开发本地通过 race test 不代表生产无 race。CI 上跑高并发 stress test 才能暴露概率事件。

### Q27 ⭐⭐⭐⭐⭐ happens-before 关系

**答**：

**定义**：在两个 goroutine 之间，事件 A "happens-before" 事件 B，意味着 A 的所有写入对 B 可见，且 A 在 B 之前完成。这是 Go 内存模型的核心。

**没有 happens-before 关系的读写就是 data race**。

**Go 内存模型规定的 happens-before 关系**：

**1. 单 goroutine 内**：程序顺序天然 happens-before（编译器/CPU 重排不能违反单线程语义）。

**2. goroutine 创建**：

```go
x := 1
go func() {
    fmt.Println(x) // 一定看到 x=1
}()
```

`go` 语句**之前**的所有写入 happens-before 新 goroutine 的开始。

**3. goroutine 退出**：goroutine 退出不保证 happens-before 任何 goroutine 的执行（除非有显式同步）：

```go
var x int
go func() { x = 1 }() // 主 goroutine 不能保证看到 x=1
// 这里读 x 是 race
```

**4. channel send/recv**：

**无缓冲 channel**：

```go
ch := make(chan int)
go func() {
    x = 1
    ch <- 0   // (A)
}()
<-ch          // (B)
fmt.Println(x) // x=1 保证可见
```

发送 (A) happens-before 对应的接收 (B) **完成**。

**有缓冲 channel**：

```go
ch := make(chan int, 1)
ch <- 0       // (A)
go func() {
    <-ch      // (B)
    fmt.Println(x) // x=1 保证可见（如果 A 前写了 x=1）
}()
```

第 N 次接收 happens-before 第 (N + capacity) 次发送的完成。换句话说，"接收到第 N 个值" → "看到发送方第 N 次 send 前的所有写"。

**关闭 channel**：

```go
ch := make(chan int)
x = 1
close(ch)    // (A)
go func() {
    <-ch     // (B) 收到 zero value
    fmt.Println(x) // x=1 可见
}()
```

close happens-before 因 close 而返回 zero-value 的接收。

**5. sync.Mutex**：

```go
mu.Lock()
x = 1
mu.Unlock()    // (A)

mu.Lock()      // (B)
fmt.Println(x) // x=1 可见
mu.Unlock()
```

第 N 次 Unlock happens-before 第 (N+1) 次 Lock。

**6. sync.RWMutex**：

`Unlock` happens-before 后续 `Lock`/`RLock`；`RUnlock` happens-before 后续 `Lock`（但**不**对其他 `RLock` 建立 hb，因为 reader 之间不互斥）。

**7. sync.Once**：

`once.Do(f)` 第一次调用的 `f` 返回 happens-before 任何其他 `once.Do` 调用的返回。所以：

```go
var x int
var once sync.Once
go func() {
    once.Do(func() { x = 1 })
    fmt.Println(x) // x=1 可见
}()
go func() {
    once.Do(func() { x = 1 }) // 实际不会执行
    fmt.Println(x) // x=1 可见（hb 通过 once 传递）
}()
```

**8. atomic 操作**（Go 1.19+ 写入内存模型）：

所有 atomic 操作按全局顺序排列（sequentially consistent），相互之间建立 hb。

```go
var ready atomic.Bool
var data int

// G1
data = 42
ready.Store(true)

// G2
if ready.Load() {
    fmt.Println(data) // 42 可见
}
```

Store happens-before 后续 Load 看到这个值的执行。

**9. timer**：`time.Now` 返回的时间 + timer fire 不建立 hb。需要通过 channel 显式同步。

**口诀**：
- **同步操作两端有 hb**：channel send/recv、Mutex Lock/Unlock、Once.Do、atomic ops。
- **无同步操作就是 race**：哪怕你"看起来"逻辑上合理。

📎 **深入阅读**: [G16-精通-Go-Race-Detection](../G16-精通-Go-Race-Detection.md) · [G13-精通-Go-sync-包](../G13-精通-Go-sync-包.md)

**常见追问**：
- Q: `for ready { }` 这种忙等是 race 吗？  A: 是。`ready` 没用 atomic 或 mutex 保护，编译器可能优化成"读一次永远循环"。改 `for !ready.Load() { runtime.Gosched() }`。
- Q: print 函数有 hb 吗？  A: fmt.Print 内部有锁（os.Stdout 是 *File，Write 加锁），所以两次 Print 之间有 hb，但这不是你应该依赖的行为。
- Q: WaitGroup.Wait 返回有 hb 吗？  A: 有。所有 Done() 调用 happens-before Wait() 的返回。

**陷阱**：把"我电脑上跑了一万遍都对"当作没有 race 的证据——race 在弱内存模型 CPU（如 ARM）上更容易显现。x86 强内存模型可能掩盖 bug 多年。

## §7 并发模式

### Q28 ⭐⭐⭐⭐ worker pool 设计：怎么优雅退出？怎么处理 panic

**答**：

**基础 worker pool**：

```go
type Pool struct {
    jobs    chan Job
    workers int
    wg      sync.WaitGroup
}

func New(n int, queueSize int) *Pool {
    p := &Pool{
        jobs:    make(chan Job, queueSize),
        workers: n,
    }
    for i := 0; i < n; i++ {
        p.wg.Add(1)
        go p.worker(i)
    }
    return p
}

func (p *Pool) worker(id int) {
    defer p.wg.Done()
    defer func() {
        if r := recover(); r != nil {
            log.Printf("worker %d panic: %v\n%s", id, r, debug.Stack())
            // 重启 worker 还是让它死？业务决定。
        }
    }()

    for job := range p.jobs {
        job.Run()
    }
}

func (p *Pool) Submit(j Job) error {
    select {
    case p.jobs <- j:
        return nil
    default:
        return errors.New("queue full")
    }
}

func (p *Pool) Shutdown() {
    close(p.jobs)
    p.wg.Wait()
}
```

**关键设计点**：

**1. 优雅退出的几种语义**：

- **stop accepting + drain**（推荐）：close(jobs) 让 worker 处理完队列里的再退。
- **immediate cancel**：用 context，正在处理的也 cancel。
- **deadline-based**：给个最大等待时间，超时就强退。

```go
// 带超时的优雅退出
func (p *Pool) ShutdownWithTimeout(d time.Duration) error {
    close(p.jobs)
    done := make(chan struct{})
    go func() { p.wg.Wait(); close(done) }()
    select {
    case <-done:
        return nil
    case <-time.After(d):
        return errors.New("shutdown timeout, some jobs may be lost")
    }
}
```

**2. Panic 处理**：

```go
func (p *Pool) worker(id int) {
    defer p.wg.Done()
    for {
        select {
        case job, ok := <-p.jobs:
            if !ok { return }
            p.runSafely(job, id)
        case <-p.ctx.Done():
            return
        }
    }
}

func (p *Pool) runSafely(job Job, id int) {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("worker %d panic on job %v: %v\n%s",
                id, job, r, debug.Stack())
            metrics.WorkerPanics.Inc()
        }
    }()
    job.Run()
}
```

注意：defer recover 要在循环内（针对每个 job），而不是 worker 启动时——后者 panic 一次 worker 就死了。

**3. 错误传递**：

```go
type Result struct {
    Job Job
    Err error
}

type Pool struct {
    jobs    chan Job
    results chan Result
}

// worker 把错误写到 results
func (p *Pool) worker() {
    for j := range p.jobs {
        err := j.Run()
        p.results <- Result{j, err}
    }
}
```

或用 errgroup：

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(N) // Go 1.21+ 限制并发数
for _, j := range jobs {
    g.Go(func() error {
        return j.Run(ctx)
    })
}
if err := g.Wait(); err != nil {
    // 第一个 error，其他 G 已通过 ctx 收到 cancel
}
```

**4. 反压（backpressure）**：

- **有界队列 + 阻塞 Submit**：生产者会被自然反压。
- **有界队列 + reject**：满了直接拒绝（上面 `default` 分支）。
- **无界队列**：危险，OOM 风险。

**5. 监控指标**：
- 当前队列长度 `len(jobs)`
- worker 利用率（busy / total）
- 处理延迟 P50/P99
- panic 计数
- reject 计数

📎 **深入阅读**: [G15-精通-Go-并发模式](../G15-精通-Go-并发模式.md)

**常见追问**：
- Q: worker pool 还是 unbounded goroutine？  A: 高 QPS 服务用 pool 限并发；批处理任务用 unbounded + errgroup 简单。看 goroutine 创建频率。
- Q: 队列要不要持久化？  A: 进程内 channel 重启丢失。重要任务用 Redis/Kafka/MQ + 消费者池。
- Q: 怎么处理 head-of-line blocking？  A: 多 channel 分类（按优先级或类型），select 多路读。

**陷阱**：worker 数等于 CPU 核数是 CPU 密集场景的最优解；I/O 密集应该远大于核数（10-100x），但要注意下游能力。

### Q29 ⭐⭐⭐⭐ errgroup 与 context 配合

**答**：

`golang.org/x/sync/errgroup` 是并发 goroutine 管理的标准库选择，核心解决"第一个 error 取消其他 goroutine"。

**基础用法**：

```go
import "golang.org/x/sync/errgroup"

g, ctx := errgroup.WithContext(parent)
for _, url := range urls {
    g.Go(func() error {
        return fetch(ctx, url)
    })
}
if err := g.Wait(); err != nil {
    return err // 第一个非 nil error
}
```

**关键机制**：

**1. WithContext 派生**：`errgroup.WithContext(parent)` 返回的 ctx 是 `parent` 的子，**任一 g.Go 返回 error 时自动 cancel 这个 ctx**。

```go
// 简化内部实现
type Group struct {
    cancel func(error) // Go 1.20+ 用 cancelCause
    wg     sync.WaitGroup
    errOnce sync.Once
    err    error
}

func (g *Group) Go(f func() error) {
    g.wg.Add(1)
    go func() {
        defer g.wg.Done()
        if err := f(); err != nil {
            g.errOnce.Do(func() {
                g.err = err
                if g.cancel != nil { g.cancel(err) }
            })
        }
    }()
}
```

`errOnce` 保证只记录第一个 error，且只 cancel 一次。

**2. 子 goroutine 必须监听 ctx**：cancel 是"通知"，不是"强制终止"。子 goroutine 需要主动检查：

```go
g.Go(func() error {
    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case v := <-input:
            if err := process(v); err != nil {
                return err
            }
        }
    }
})
```

或在阻塞调用中传 ctx：

```go
g.Go(func() error {
    req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
    return httpClient.Do(req) // 自动响应 cancel
})
```

**3. 限制并发数（Go errgroup 0.10+）**：

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(10) // 最多 10 个 goroutine 同时执行
for _, item := range items {
    g.Go(func() error { return process(ctx, item) })
}
g.Wait()
```

`SetLimit` 内部用信号量；G.Go 满了会**阻塞**。如果想 reject 而非阻塞，用 `g.TryGo`。

**4. 不同错误语义**：

- **fail-fast**（默认）：第一个 error 触发 ctx cancel，其他尽快退出。
- **collect-all errors**：需要收集所有错误，不能用 errgroup，要自己实现：

```go
var mu sync.Mutex
var allErrs []error
var wg sync.WaitGroup
for _, item := range items {
    wg.Add(1)
    go func() {
        defer wg.Done()
        if err := process(item); err != nil {
            mu.Lock()
            allErrs = append(allErrs, err)
            mu.Unlock()
        }
    }()
}
wg.Wait()
return errors.Join(allErrs...) // Go 1.20+
```

**5. 嵌套 errgroup**：

```go
g, ctx := errgroup.WithContext(parent)
g.Go(func() error {
    subg, subctx := errgroup.WithContext(ctx)
    for _, sub := range subTasks {
        subg.Go(func() error { return doSub(subctx, sub) })
    }
    return subg.Wait()
})
g.Wait()
```

任何层级出错都会传播到根。

**6. WaitGroup vs errgroup 选哪个**：

| 场景 | 推荐 |
|------|------|
| 不需要 error | sync.WaitGroup（Go 1.25 用 `wg.Go`） |
| 需要 error | errgroup |
| 第一个错误就停 | errgroup（自动） |
| 收集所有错误 | 手动 + errors.Join |
| 限制并发 | errgroup.SetLimit |

📎 **深入阅读**: [G15-精通-Go-并发模式](../G15-精通-Go-并发模式.md)

**常见追问**：
- Q: ctx cancel 后 g.Go 还能继续 Add 吗？  A: 可以，但新 goroutine 一进去就看到 ctx 已 cancel，应立即返回。
- Q: g.Wait 内部怎么处理 panic？  A: 不处理！panic 会让 worker goroutine 直接退出，但 wg.Done 仍在 defer 里被调用。错误**不会被 errgroup 捕获**。需要业务自己 recover。
- Q: errgroup vs conc 库哪个好？  A: errgroup 是 x/sync 的，最稳定。`sourcegraph/conc` 提供更强类型（泛型 + 自动 panic recover），是较新的选择。

**陷阱**：以为 g.Wait() 返回时所有 goroutine 都干干净净——只是它们都返回了，但中间产生的副作用（开了文件、连了数据库）必须由它们自己 defer 清理。

### Q30 ⭐⭐⭐⭐ 实现一个限流器：channel 版 vs `golang.org/x/time/rate` 对比

**答**：

**Token Bucket 算法**：桶里以恒定速率 R 加 token（上限 B），请求消耗 token，没 token 等待或拒绝。

**Channel 版（教学用）**：

```go
type ChanLimiter struct {
    tokens chan struct{}
    stop   chan struct{}
}

func NewChanLimiter(rate int, burst int) *ChanLimiter {
    l := &ChanLimiter{
        tokens: make(chan struct{}, burst),
        stop:   make(chan struct{}),
    }
    // 预填 burst 个 token
    for i := 0; i < burst; i++ { l.tokens <- struct{}{} }
    // 后台填充
    go func() {
        t := time.NewTicker(time.Second / time.Duration(rate))
        defer t.Stop()
        for {
            select {
            case <-l.stop:
                return
            case <-t.C:
                select {
                case l.tokens <- struct{}{}: // 非阻塞放
                default:                     // 桶满丢弃
                }
            }
        }
    }()
    return l
}

func (l *ChanLimiter) Allow() bool {
    select {
    case <-l.tokens:
        return true
    default:
        return false
    }
}

func (l *ChanLimiter) Wait(ctx context.Context) error {
    select {
    case <-l.tokens:
        return nil
    case <-ctx.Done():
        return ctx.Err()
    }
}

func (l *ChanLimiter) Close() { close(l.stop) }
```

**优点**：直观，无依赖。
**缺点**：
- 一个 ticker goroutine 持续占用，QPS 高时 ticker 频率太高（rate=10000 → 100μs 一次 tick，调度抖动大）。
- rate 不能动态调整（要重建）。
- 没法表达"取多个 token"（要循环取）。

**`golang.org/x/time/rate` 版**（生产推荐）：

```go
import "golang.org/x/time/rate"

// rate.Limit 是 token/秒（float64），第二个参数是 burst
limiter := rate.NewLimiter(rate.Limit(100), 200) // 100 QPS，突发 200

// 非阻塞
if !limiter.Allow() {
    return errors.New("rate limited")
}

// 阻塞等待
if err := limiter.Wait(ctx); err != nil {
    return err
}

// 取 N 个 token（大请求）
if err := limiter.WaitN(ctx, 5); err != nil { ... }

// 动态调整
limiter.SetLimit(rate.Limit(200))
limiter.SetBurst(500)
```

**实现原理**：基于"上次填充时间 + 当前已积累 token 数"**懒计算**，没有后台 goroutine。

```go
// 简化逻辑
type Limiter struct {
    mu     sync.Mutex
    limit  rate.Limit
    burst  int
    tokens float64
    last   time.Time // 上次更新时间
}

func (l *Limiter) reserveN(now time.Time, n int) Reservation {
    l.mu.Lock()
    defer l.mu.Unlock()
    elapsed := now.Sub(l.last).Seconds()
    l.tokens = math.Min(float64(l.burst), l.tokens + elapsed*float64(l.limit))
    l.last = now
    if l.tokens >= float64(n) {
        l.tokens -= float64(n)
        return Reservation{ok: true}
    }
    // 计算需要等多久
    wait := time.Duration((float64(n) - l.tokens) / float64(l.limit) * float64(time.Second))
    l.tokens = float64(n) // 预扣
    return Reservation{ok: true, wait: wait}
}
```

**优点**：
- 无后台 goroutine，更轻量。
- 支持小数 rate（如 0.5 QPS）。
- 支持 WaitN、ReserveN。
- 可动态调整。
- 数学上精确（基于时间）。

**缺点**：
- 抽象更高，调试稍麻烦。
- 锁开销略高于 channel 的 atomic 路径（但场景已足够）。

**进阶：分布式限流**：单机限流器不够时：
- **Redis + Lua**：原子计数器，cluster 部署。
- **滑动窗口**：精确但内存大。
- **Sentinel / Envoy**：中间件层限流。

**漏桶 vs 令牌桶**：
- 令牌桶（上述）：允许突发，平均速率限制。
- 漏桶：严格匀速输出，不允许突发。
- 大多数 API 限流用令牌桶（API gateway 默认）。

**与限流相关的其他模式**：
- **熔断器** (`sony/gobreaker`)：错误率超阈值 → 直接返回错误。
- **重试 + 退避**：429 响应配合指数退避。
- **优先级队列**：高优先级请求优先获取 token。

📎 **深入阅读**: [G15-精通-Go-并发模式](../G15-精通-Go-并发模式.md)

**常见追问**：
- Q: rate.Limiter 性能瓶颈？  A: 一把全局 Mutex。Hot path 上 1M+ QPS 时考虑分片限流器。
- Q: 怎么实现"每秒 N，每分钟 M"？  A: 嵌套两个 Limiter，每个请求都过两遍。
- Q: 限流应该在哪一层？  A: gateway > 业务网关 > 单服务 > 单 handler。越外层越好。

**陷阱**：限流配置过紧导致正常流量被拒，过松导致下游被打爆。一定要配 metrics 看 reject rate 和 wait latency，逐步调优。

## 速记表

### GMP 状态机

| 状态 | 含义 | 进入条件 | 退出条件 |
|------|------|----------|----------|
| `_Gidle` | 刚创建 | newproc | 初始化完成 |
| `_Grunnable` | 可运行 | go 启动、唤醒 | 被调度 |
| `_Grunning` | 正在执行 | execute | yield/block |
| `_Gsyscall` | 系统调用 | entersyscall | exitsyscall |
| `_Gwaiting` | 阻塞 | gopark | goready |
| `_Gdead` | 已退出 | goexit | （复用） |

### channel 操作矩阵

| 操作 | nil | 空 | 非空 | 满 | closed |
|------|-----|----|----|----|--------|
| send | 阻塞 | 直接送对方 | 入 buf | 阻塞 | **panic** |
| recv | 阻塞 | 阻塞 | 取 buf | 取 buf+让 sender | zero, ok=false |
| close | **panic** | OK | OK | OK | **panic** |

### sync 工具速查

| 工具 | 适用 | 关键陷阱 |
|------|------|----------|
| Mutex | 短临界区 | 不可重入、不能复制 |
| RWMutex | 读 >> 写 | 嵌套死锁、不可升级 |
| Once | 一次性初始化 | panic 也算"已完成" |
| Pool | 临时对象复用 | GC 时清空，不是缓存 |
| WaitGroup | 等多 G 完成 | Add 必须在 Wait 前 |
| Cond | 条件等待 | 需配合 Mutex，必须 for + Wait |
| atomic | 单变量原子 | 32 位平台对齐 |

### context 传播规则

| 规则 | 方向 |
|------|------|
| cancel | 父 → 子（级联） |
| deadline | 父 → 子（取最严） |
| Value | 子 → 父（链式查找） |
| 错误 | 子 cancel 不影响父 |

### 内存模型 happens-before

| 同步原语 | hb 关系 |
|----------|---------|
| `go` 语句 | 之前所有写 hb goroutine 启动 |
| channel send (unbuf) | send hb recv 完成 |
| channel send (buf=N) | 第 K 次 recv hb 第 K+N 次 send 完成 |
| close(ch) | close hb 因 close 返回的 recv |
| Mutex Unlock | 第 N 次 Unlock hb 第 N+1 次 Lock |
| Once.Do | 首次 f 返回 hb 任何 Do 返回 |
| atomic Store | Store hb 看到该值的 Load |

## 高频陷阱清单

1. **循环变量捕获**（Go 1.22 修复）：旧版本 `for i := range items { go func() { use(i) }() }` 所有 G 看到同一个 i。Go 1.22+ 默认每轮新建变量。

2. **goroutine 泄漏**：channel 没人收 / context 没传 / 阻塞调用不退出。生产用 pprof 定期排查 goroutine 数。

3. **defer 在循环里**：每次循环 defer 推迟到函数末才执行，资源堆积。要么改用闭包包装，要么显式 close。

4. **`time.After` 在热循环**：每次循环创建新 timer 泄漏（Go 1.23 已大幅缓解，但仍建议 NewTimer + Reset 模式）。

5. **errgroup 没接 ctx**：goroutine 不监听 ctx.Done，cancel 信号失效。

6. **Mutex 复制**：值传递 struct 嵌入 Mutex 会复制状态。永远用指针。

7. **关闭已关闭的 channel**：双 sender 没协调好，第二次 close panic。用 sync.Once 或单 sender 原则。

8. **WaitGroup.Add 在 goroutine 内**：Add 在 Wait 之后执行 → 还没 +1 就开始 Wait → counter=0 立即返回。

9. **race 在 32 位平台**：int64 没对齐 → atomic 操作 panic。Go 1.19+ 用 atomic.Int64 避免。

10. **context.Value 传业务参数**：违反设计意图，类型不安全，可读性差。用显式参数。

11. **持有锁同时发送/接收 channel**：极易 ABBA 死锁。锁内只做内存操作，IO 和 channel 在锁外。

12. **for range channel 没退出协议**：channel 不 close → goroutine 永远卡在 range。
