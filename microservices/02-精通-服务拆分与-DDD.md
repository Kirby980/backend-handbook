# 精通服务拆分与 DDD：限界上下文、聚合、上下文映射、事件风暴

> 关联章节：[M01 微服务架构总览](./01-精通-微服务架构总览.md)、[M03 单体到微服务演进](./03-精通-单体到微服务演进.md)、[M22 反模式与重构](./22-精通-反模式与重构.md)

## 引言：为什么"拆分"是微服务里最难的一步

如果说微服务的难度有 100 分，分布式事务占 30 分、可观测占 20 分、网关与韧性各占 10 分——那"如何拆"这一件事，单独占 30 分以上。

为什么？

- 拆错了，怎么补救都补不齐——你后续做再好的限流、熔断、链路追踪，也救不回来一个"分布式单体"
- 拆错了，要花 6-12 个月才能发现错（业务跑久了才显形）
- 拆错了，纠正成本是当初拆分成本的 5-10 倍

更糟糕的是，市面上"拆服务"的教程大多停留在"按业务模块拆" 这一层——告诉你"订单 / 商品 / 用户" 是不同的服务，然后就结束了。但真正的问题是：

- "订单服务" 里到底放什么？订单创建？支付？退款？物流跟踪？
- "用户服务" 和"账号服务" 是同一个吗？"用户中心" 和"用户档案" 呢？
- 订单要查商品，是直接调商品服务的 API，还是订单存一份商品快照？
- 一个订单跨越库存、支付、物流——它的"主"在哪里？

这些问题没有简单答案，但有方法论——这就是 **DDD（领域驱动设计）**。Eric Evans 在 2003 年提出 DDD 时主要为单体服务，但 2014 年微服务兴起后，DDD 反而成为"如何拆服务"最有效的理论框架。

这一章就是要把 DDD 战略设计与战术设计完整讲清楚，让你读完能：

- 区分子域（Subdomain）与限界上下文（Bounded Context）
- 用 4 个不变量规则设计聚合（Aggregate）
- 画出 7 种上下文映射关系
- 用事件风暴（Event Storming）3 阶段方法做拆分
- 拿一个电商系统做完整拆分演练
- 识别 5 种最常见的拆分反模式

## 第一章：DDD 的核心问题与基本术语

### 1.1 DDD 要解决什么问题

软件复杂度的来源分两种：

- **本质复杂度（Essential Complexity）**：业务本身的复杂——退货的 18 种状态、订单的多种支付方式、不同国家的税务规则
- **偶然复杂度（Accidental Complexity）**：技术选型造成的复杂——分布式事务、性能调优、序列化

DDD **不解决** 偶然复杂度（那是技术问题），它解决**本质复杂度**——让代码与业务概念对齐，让架构反映业务边界。

### 1.2 DDD 的两大组成

```
                  DDD
                   │
        ┌──────────┴──────────┐
        │                     │
   战略设计                战术设计
   (Strategic)            (Tactical)
        │                     │
   ──────────              ─────────
   - 子域                   - 实体 (Entity)
   - 限界上下文             - 值对象 (Value Object)
   - 上下文映射             - 聚合 (Aggregate)
   - 通用语言               - 领域事件 (Domain Event)
                            - 仓储 (Repository)
                            - 领域服务 / 应用服务
                            - 工厂 (Factory)
```

**战略设计**：大尺度的、关于"如何切分系统" 的设计——直接决定你拆几个服务、每个服务负责什么。

**战术设计**：每个服务内部的代码结构——决定单个服务里实体怎么建、聚合怎么定。

对微服务来说，**战略设计是 80% 的价值**，战术设计是 20%。

### 1.3 通用语言（Ubiquitous Language）

DDD 的隐性基础是**通用语言**：

- 业务专家说"订单"，开发说"Order"，产品说"销售单据"——这是一团乱麻
- DDD 要求团队（业务 + 开发 + 测试 + 运维）使用同一套术语
- 这套术语在代码、文档、会议、需求里都一致

**通用语言不是全公司的全局术语，而是"每个限界上下文内"的术语**——这就引出了下一节。

### 1.4 术语速查

| 术语 | 中文 | 简要解释 |
|---|---|---|
| Domain | 领域 | 整个业务范围 |
| Subdomain | 子域 | 领域的划分（按业务功能） |
| Bounded Context | 限界上下文 | 模型边界（按术语含义） |
| Ubiquitous Language | 通用语言 | 上下文内统一术语 |
| Context Map | 上下文映射 | 上下文之间的关系图 |
| Entity | 实体 | 有唯一标识、生命周期 |
| Value Object | 值对象 | 无标识、不可变、按值比较 |
| Aggregate | 聚合 | 一组实体+VO 的事务边界 |
| Aggregate Root | 聚合根 | 聚合的对外入口 |
| Domain Event | 领域事件 | 业务上有意义的状态变化 |
| Repository | 仓储 | 聚合的持久化抽象 |
| Domain Service | 领域服务 | 跨多个聚合的领域逻辑 |
| Application Service | 应用服务 | 编排领域逻辑、对接外部 |
| Factory | 工厂 | 复杂聚合的创建逻辑 |
| ACL | 防腐层 | Anti-Corruption Layer |

## 第二章：战略设计——子域

### 2.1 子域是什么

**子域（Subdomain）= 业务功能的逻辑划分**。

如果你的领域是"电商"，子域可能是：

- 商品管理
- 订单处理
- 支付
- 库存
- 物流
- 营销
- 客服
- 数据分析
- ...

子域之间的边界由业务功能决定——不是由代码、技术、团队决定。**子域是业务视角，不是技术视角**。

### 2.2 子域的 3 种分类

DDD 把子域分成 3 类，这个分类直接影响你的工程投入：

| 类型 | 英文 | 特征 | 投入策略 |
|---|---|---|---|
| **核心子域** | Core Domain | 业务差异化、竞争优势所在 | 投入最强工程师，自研 |
| **支撑子域** | Supporting | 必要但不差异化 | 投入中等，可自研或外包 |
| **通用子域** | Generic | 行业通用解决方案存在 | 用现成的，不要自研 |

### 2.3 怎么识别核心子域

核心子域的判断标准：

- 公司核心营收来自这里
- 业务专家在这里花最多时间
- 这里的规则最复杂、变化最快
- 这里的代码是"商业秘密"

例子：

- **淘宝**：搜索推荐、营销引擎、支付风控 = 核心；用户登录 = 通用
- **滴滴**：路径规划、动态定价、司机匹配 = 核心；短信通知 = 通用
- **B 站**：内容审核、推荐、视频编解码 = 核心；客服系统 = 支撑

### 2.4 通用子域：永远先看市场再决定

通用子域有现成产品时，**自研几乎总是错的**：

- 身份认证 → Keycloak / Auth0
- 邮件发送 → 阿里云邮件服务 / SendGrid
- 短信 → 腾讯云短信 / Twilio
- 支付 → 支付宝 / Stripe（如果不是金融公司）
- 客服工单 → Zendesk
- 报表 → Metabase / Superset

自研通用子域 = 用一流工程师做三流产品（因为你的资源远比 SaaS 厂商少）。

### 2.5 子域 ≠ 微服务

**最常见误区**：以为"一个子域 = 一个服务"。

实际上：

- 一个子域可能拆成多个服务（比如"订单"子域拆成订单创建、订单查询、订单退款 3 个服务）
- 一个服务可能覆盖多个子域（比如"用户中心"服务覆盖注册、登录、个人资料 3 个子域）

**子域是业务视角的划分，服务是技术部署的划分**，两者只是有相关性，不是 1:1。

那什么才是"应该 1:1"的？答案是**限界上下文**——下一章。

## 第三章：战略设计——限界上下文（Bounded Context）

### 3.1 限界上下文的定义

> A description of a boundary (typically a subsystem, or the work of a particular team) within which a particular model is defined and applicable.
>
> —— Eric Evans

**限界上下文（Bounded Context）= 模型的边界**。在这个边界内：

- 术语（通用语言）的含义统一
- 模型一致
- 团队一致

跨过边界，同一个词可能意思不同。

### 3.2 经典例子：电商里的"商品"

在电商系统里，"商品" 这个词在不同上下文里意思完全不同：

| 上下文 | "商品" 的含义 |
|---|---|
| **商品管理** | SKU、SPU、品类、属性、参数 |
| **库存** | 库存单位、可用数量、占用、安全库存 |
| **订单** | 下单时的快照（名称、价格、规格） |
| **物流** | 包裹、重量、体积、危险品标识 |
| **营销** | 活动商品池、可参与活动 |
| **搜索推荐** | 标题、描述、tag、向量嵌入 |
| **财务** | 商品成本、营收归属、税率 |

如果你试图建一个"全局商品模型"，你就要把所有字段塞进去——SKU + 库存数量 + 价格快照 + 重量 + 活动 tag + 向量 ......得到一个无人能维护的怪物。

**正确做法**：每个上下文有自己的"商品" 模型，只包含自己关心的字段，通过 ID 关联。

### 3.3 限界上下文 vs 子域

| 维度 | 子域 | 限界上下文 |
|---|---|---|
| 视角 | 业务视角 | 模型视角 |
|edges| 业务功能边界 | 通用语言/模型边界 |
| 数量 | 一般较少（5-15） | 通常更多或相同 |
| 与团队 | 不直接绑定 | 一般 1 团队 1 上下文 |
| 与服务 | 不是 1:1 | **更接近 1:1**（但不绝对） |

### 3.4 子域与限界上下文的关系——4 种可能

理论上"一个子域 = 一个限界上下文"是理想，但实际：

1. **1:1 理想**：商品子域 ↔ 商品上下文（最简单情况）
2. **1:N（一个子域拆多个上下文）**：订单子域 拆成 订单创建上下文 + 订单履约上下文（事务模型差异大）
3. **N:1（多个子域合一个上下文）**：早期的"用户子域"+"账号子域" 合为"用户中心"上下文
4. **遗留集成（最常见）**：你接手了一个老系统，它的"上下文" 跨越多个子域，你只能在 ACL 后慢慢拆

### 3.5 限界上下文是微服务划分的"最佳近似"

经验法则：**一个微服务 ≈ 一个限界上下文**。

但不是绝对：

- 大型限界上下文可能拆成多个服务（按数据量 / 性能 / 团队）
- 小型限界上下文可能合并到一个服务

记住：拆分粒度由**部署独立性 + 团队 ownership + 性能/扩展需求**共同决定，限界上下文给你边界基础，不是机械标准。

### 3.6 上下文的命名规则

好的上下文命名应该：

- **业务术语**：用业务方听得懂的词，不用"OrderApiService"
- **名词**：用名词性的描述，不用动词
- **范围明确**：让人一眼看出边界

例子：

```
✅ 好
  - 订单履约（Order Fulfillment）
  - 商品目录（Product Catalog）
  - 支付清算（Payment Settlement）

❌ 不好
  - 业务中台（太宽）
  - OrderProcessor（技术化）
  - 通用服务（无边界）
```

## 第四章：战术设计——核心积木

### 4.1 实体（Entity）

**实体 = 有唯一标识 + 有生命周期**。

- "用户 ID=42" 和"用户 ID=43" 是两个不同的实体，即使其他字段全相同
- 实体的属性可变（用户名可以改），但 ID 不变
- 实体可以经历多个状态（注册 → 激活 → 注销）

代码体现：

```java
public class User {
    private final UserId id;            // 不可变
    private String name;                // 可变
    private Email email;                // 值对象
    private UserStatus status;          // 枚举状态

    // 业务方法：状态转换
    public void activate() {
        if (this.status != UserStatus.PENDING) {
            throw new IllegalStateException("Only PENDING user can activate");
        }
        this.status = UserStatus.ACTIVE;
    }
}
```

### 4.2 值对象（Value Object）

**值对象 = 无标识 + 不可变 + 按值比较**。

- "100 元" 和"100 元" 是同一个值对象（即使是两个 Java 对象）
- 值对象一旦创建不能修改（要改就 new 一个新的）
- equals() 比较所有字段

例子：

```java
// 值对象：金额
public final class Money {
    private final BigDecimal amount;
    private final Currency currency;

    public Money(BigDecimal amount, Currency currency) {
        this.amount = amount;
        this.currency = currency;
    }

    // 计算返回新对象，不修改自己
    public Money add(Money other) {
        require(this.currency.equals(other.currency));
        return new Money(this.amount.add(other.amount), this.currency);
    }

    // 按值比较
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money)) return false;
        Money m = (Money) o;
        return amount.equals(m.amount) && currency.equals(m.currency);
    }
}
```

值对象的常见例子：

- 金额 (Money)
- 地址 (Address)
- 时间区间 (TimeRange)
- 经纬度 (GeoCoordinate)
- 邮箱、手机号、身份证号
- 颜色、尺寸

**经验法则**：先用值对象，必要时升级为实体。值对象比实体简单 10 倍。

### 4.3 聚合（Aggregate）与聚合根（Aggregate Root）

**聚合 = 一组紧密相关的实体和值对象组成的"事务边界"**。

聚合的目的是**保护不变量（invariants）**——业务规则不能被打破。

例子：订单聚合

```
Order (聚合根)
  ├── OrderItem[]              (实体)
  │     ├── productId
  │     ├── quantity
  │     └── price (Money)
  ├── shippingAddress (VO)
  ├── totalAmount (VO)         不变量：=  sum(items.price * quantity)
  └── status

  不变量：
  1. 订单金额 = 所有 item 金额之和
  2. 已支付订单不能修改 item
  3. items.size > 0
```

**聚合根（Aggregate Root）= 聚合的对外入口**。外部代码只能拿到聚合根，通过它访问聚合内的其他对象。

```java
// 错：直接修改聚合内的对象
order.getItems().add(new OrderItem(...));   // 绕过聚合根，不变量可能被破坏

// 对：通过聚合根的业务方法
order.addItem(productId, quantity, price);  // 聚合根内部维护不变量
```

### 4.4 聚合的 4 个不变量规则（Vernon's Rules）

Vaughn Vernon 在《实现领域驱动设计》提出 4 条聚合设计规则。微服务里这 4 条**几乎等于"如何拆数据"**：

#### 规则 1：保持聚合尽量小

**理由**：聚合越大，锁竞争越严重，加载性能越差。

```
❌ 大聚合：Order 包含 1000 个 OrderItem
   每次加载 1000 个 item，锁的范围大

✅ 小聚合：Order 只包含订单元信息 + 引用 OrderItem 的 ID
   OrderItem 是另一个聚合
```

经验：**一个聚合一般包含 1-5 个实体**。超过就要考虑拆。

#### 规则 2：通过 ID 引用其他聚合

**理由**：直接对象引用导致"加载一个聚合连带加载半个数据库"。

```java
// ❌ 直接引用
public class Order {
    private User customer;        // 加载 Order 时连带加载 User
    private Product[] products;   // 还要加载所有 Product
}

// ✅ ID 引用
public class Order {
    private UserId customerId;          // 只存 ID
    private List<ProductId> productIds; // 只存 ID
}
```

要查 User 信息时，单独通过 UserRepository 查。

#### 规则 3：最终一致性跨聚合

**理由**：单一事务只能保证一个聚合的强一致；跨聚合用领域事件做最终一致。

```
❌ 一个事务跨多个聚合
  begin
    update Order
    update User
    update Product
  commit

✅ 单聚合事务 + 领域事件
  begin
    update Order
    save OrderCreated event
  commit
  
  // 异步处理事件
  on OrderCreated → 更新 User 统计
  on OrderCreated → 扣减 Product 库存
```

这条规则是 Saga / Outbox / Event-Driven 整套微服务异步模式的根基。

#### 规则 4：一个事务一个聚合

**理由**：保证强一致性的边界就是聚合边界。跨聚合的操作必须是事件驱动 + 最终一致。

```java
@Transactional
public void placeOrder(OrderCommand cmd) {
    Order order = new Order(cmd);    // ✅ 一个聚合
    orderRepository.save(order);
    eventBus.publish(new OrderCreated(order.id));
}

// ❌ 错误：一个事务里改两个聚合
@Transactional
public void placeOrder(OrderCommand cmd) {
    Order order = new Order(cmd);
    orderRepository.save(order);
    
    User user = userRepository.findById(cmd.userId);
    user.incrementOrderCount();        // 改了第二个聚合
    userRepository.save(user);
}
```

### 4.5 领域事件（Domain Event）

**领域事件 = 业务上有意义的状态变化**。

- 命名规则：**过去时**（OrderCreated, PaymentFailed, UserActivated）
- 包含足够信息让消费方处理（但不要塞整个聚合）
- 一旦发布，事实不可改

```java
public class OrderCreated {
    public final OrderId orderId;
    public final UserId customerId;
    public final Money totalAmount;
    public final Instant occurredAt;
    // 注意：不要塞整个 Order 对象
}
```

领域事件是微服务异步通信的"自然单位"——一个聚合发布事件，其他服务订阅。

### 4.6 仓储（Repository）

**仓储 = 聚合的持久化抽象**。

- 一个聚合根 = 一个 Repository
- 接口在领域层，实现在基础设施层
- 屏蔽底层是 PostgreSQL / MongoDB / Elasticsearch

```java
public interface OrderRepository {
    Optional<Order> findById(OrderId id);
    void save(Order order);
    List<Order> findByCustomer(UserId customerId);
}
```

### 4.7 领域服务 vs 应用服务

| 类型 | 职责 | 例子 |
|---|---|---|
| **领域服务** | 跨多个聚合的纯业务逻辑 | 计算多个账户的总余额、调用规则引擎 |
| **应用服务** | 编排领域逻辑 + 处理事务/事件/外部调用 | OrderApplicationService.placeOrder() |

应用服务是 Controller 和领域之间的桥梁。它的典型职责：

1. 接收命令（DTO）
2. 加载聚合
3. 调用聚合的业务方法
4. 保存聚合
5. 发布领域事件
6. 返回结果

```java
@Service
public class OrderApplicationService {
    public OrderId placeOrder(PlaceOrderCommand cmd) {
        // 1. 接收命令
        // 2. 加载/创建聚合
        Order order = Order.create(cmd.customerId, cmd.items);
        // 3. 调用业务方法
        order.validateInventory(inventoryService);
        // 4. 保存
        orderRepository.save(order);
        // 5. 发布事件
        eventPublisher.publish(new OrderCreated(order.id));
        // 6. 返回
        return order.id;
    }
}
```

## 第五章：上下文映射——7 种关系

上下文不是孤立的，它们之间有关系。Eric Evans 定义了 7 种主要的上下文映射模式，这些模式是**微服务间集成的所有可能形态**。

### 5.1 关系图速览

```
┌─────────────────────────────────────────────────┐
│                                                 │
│  Partnership ←──────────────→  Partnership      │
│       (合作)                                    │
│                                                 │
│  Shared Kernel ◄─►  Shared Kernel               │
│       (共享内核)                                │
│                                                 │
│  Customer ─────────► Supplier                   │
│   (客户)              (供应商)                  │
│                                                 │
│  Conformist ─────────► Upstream                 │
│   (跟随者)              (上游主导)               │
│                                                 │
│  Anti-Corruption Layer (ACL)                    │
│   下游用 ACL 隔离上游模型                       │
│                                                 │
│  Open Host Service (OHS)                        │
│   上游提供开放协议                              │
│                                                 │
│  Separate Ways                                  │
│   两上下文完全无关                              │
└─────────────────────────────────────────────────┘
```

### 5.2 Partnership（合作关系）

两个上下文的团队**共同成功 or 共同失败**——必须同步演进。

**特征**：

- 没有明确的上下游
- 任一方的变化都需要双方协调
- 沟通成本高

**例子**：订单上下文与支付上下文——下单和支付必须协同设计，否则用户体验破碎。

**警告**：Partnership 是**所有关系中风险最高**的——耦合最紧。能用别的关系就别用 Partnership。

### 5.3 Shared Kernel（共享内核）

两个上下文**共享一部分模型**（一段共同代码 + 数据库）。

**特征**：

- 共享内核必须严格审查变更
- 修改要双方同意
- 一般用 Git Submodule / 内部包发布

**例子**：身份认证模型（User、Permission）被多个上下文共享。

**警告**：Shared Kernel **越多越糟糕**——它本质上是被规范化了的耦合。能小就小，能不用就不用。

### 5.4 Customer / Supplier（客户/供应商）

下游（Customer）依赖上游（Supplier），但**下游有发言权**——可以向上游提需求。

**特征**：

- 上下游明确
- 下游的需求会进入上游的 backlog
- 上游对下游负责

**例子**：订单上下文依赖商品上下文。订单团队可以向商品团队提"我们需要 SKU 的 weight 字段" 这种需求。

### 5.5 Conformist（跟随者）

下游**完全跟随**上游的模型——上游不在乎下游需求。

**特征**：

- 上游强势（通常是大组织 / 外部系统）
- 下游被动接受
- 任何上游变化都要下游适配

**例子**：你接入支付宝、微信支付——你必须按它们的 API 来，不能让它们配合你。

### 5.6 Anti-Corruption Layer / ACL（防腐层）

下游**用一层翻译层**把上游模型转换成自己的模型——保护自己不被上游污染。

**特征**：

- 上下游解耦
- 上游变化由 ACL 吸收
- 自己的领域模型保持纯净

**结构**：

```
  下游服务
    │
    │  本地模型
    ▼
  Anti-Corruption Layer
    │
    │  上游模型
    ▼
  上游服务
```

**例子**：你的"会员中心" 需要从遗留 CRM 系统获取客户信息，但 CRM 字段乱七八糟。你写一个 ACL 把它转换成你想要的 Customer 模型。

**重要**：ACL 是**微服务里最常用、最有价值的模式之一**——尤其在和遗留系统集成时。

### 5.7 Open Host Service / OHS（开放主机服务）

上游**提供标准化协议** 让所有下游都好对接。

**特征**：

- 上游开放、向后兼容
- 协议稳定（OpenAPI / Protobuf / Schema Registry）
- 一对多

**例子**：你的"商品服务" 用 OpenAPI + gRPC 暴露统一接口，所有下游（订单、营销、推荐）都用同一份契约。

### 5.8 Separate Ways（各行其道）

两个上下文**完全没集成**——独立工作，无关。

**例子**：HR 系统和电商订单系统——没必要集成（即使在同一公司）。

### 5.9 7 种关系的选择决策树

```
两个上下文要不要集成？
    │
    NO ──→ Separate Ways
    │
    YES
    │
    是同一团队/小团队吗？
    │
    YES ──→ Partnership
    │
    NO
    │
    上游愿意配合下游吗？
    │
    YES                       NO
    │                         │
    上游愿意标准化吗？        强势上游
    │                         │
    YES ──→ Open Host         │
    │                         │
    NO ──→ Customer/Supplier  上下游需要解耦吗？
                              │
                              YES ──→ ACL
                              │
                              NO ──→ Conformist
```

## 第六章：事件风暴（Event Storming）

### 6.1 事件风暴是什么

事件风暴是 Alberto Brandolini 在 2013 年提出的**协作式建模工作坊**——把业务专家、产品、开发、测试拉到一面墙前，用便利贴梳理整个业务流。

**为什么是事件**？因为事件是业务专家和开发都听得懂的语言——"订单创建了"、"支付成功了"、"库存扣减了"。

### 6.2 事件风暴的 3 阶段

#### 阶段 1：Big Picture（全景图）

**目的**：把整个业务流"画"出来——一面墙、几百张便利贴。

**参与者**：业务专家 + 产品 + 开发 + 测试，10-20 人。

**步骤**：

1. 每人写"业务上发生的事件"（橙色便利贴），过去时
2. 全部贴到墙上
3. 沿时间轴排序
4. 找出**热点**（多人有疑问、有冲突的地方）

**产出**：一张"事件全景图"——是后续战略设计的输入。

```
墙上的样子：
[用户注册]──[邮箱验证]──[加入购物车]──[提交订单]──[支付]──[发货]──[签收]──[评价]
            ↓                              ↓               ↓
       [发送欢迎邮件]              [冻结库存]      [生成快递单]
```

#### 阶段 2：Process Modeling（流程建模）

**目的**：细化每个事件——是什么触发它、它导致什么。

**新增便利贴**：

- 命令（Command，蓝色）：用户/系统的动作。例："提交订单"
- 策略（Policy，紫色）：业务规则。例："订单超 200 元免运费"
- 用户/系统（Actor，黄色）：谁发起的
- 视图（View，绿色）：用户看到什么

**布局**：

```
[Actor] ──→ [Command] ──→ [Aggregate] ──→ [Event] ──→ [Policy] ──→ [Command]
                                              │
                                              ▼
                                          [View]
```

例子：

```
[用户] ──→ [提交订单] ──→ [Order 聚合] ──→ [OrderCreated]
                                              │
                                              ├──→ Policy: 自动扣减库存
                                              │      └──→ [ReserveInventory] ──→ [Inventory]
                                              │
                                              └──→ Policy: 发送通知
                                                     └──→ [SendNotification] ──→ [Notification]
```

#### 阶段 3：Software Design（软件设计）

**目的**：识别聚合 + 限界上下文。

**步骤**：

1. 把高频出现的实体名词圈出来 → 候选聚合
2. 找出术语含义切换的位置 → 候选上下文边界
3. 给每个上下文起名字
4. 标注上下文间的关系（参考第五章 7 种关系）

**产出**：

- 聚合列表
- 限界上下文图
- 上下文映射图

### 6.3 事件风暴的实操要点

- **物理墙优先**：用大房间 + 便利贴，比线上工具效率高 3 倍
- **业务专家必到场**：缺业务方的事件风暴只是开发自嗨
- **时间限制**：Big Picture 半天到一天，Process 一天，Design 一到两天
- **照片归档**：每次结束拍照存档，作为下次起点

## 第七章：完整案例——电商系统拆分

下面用一个中型电商系统做完整拆分演练。假设规模：300 万 SKU、日 100 万订单、50 工程师。

### 7.1 业务流总览

```
注册 → 浏览 → 加购 → 下单 → 支付 → 履约 → 物流 → 签收 → 评价 → 售后
```

### 7.2 子域识别

按业务功能划分子域：

| 子域 | 类型 | 说明 |
|---|---|---|
| 商品 | 核心 | 商品信息、分类、属性 |
| 订单 | 核心 | 订单生命周期 |
| 支付 | 核心 | 支付路由、结算、对账 |
| 库存 | 核心 | 商品库存、占用、释放 |
| 营销 | 核心 | 优惠券、活动、价格策略 |
| 推荐搜索 | 核心 | 个性化推荐、搜索 |
| 用户 | 支撑 | 注册、登录、个人资料 |
| 购物车 | 支撑 | 购物车持久化 |
| 物流 | 支撑 | 发货、配送跟踪 |
| 客服 | 支撑 | 工单、咨询 |
| 评价 | 支撑 | 商品评价、晒单 |
| 通知 | 通用 | 短信、邮件、推送 |
| 风控 | 核心 | 反欺诈、信用 |
| 数据分析 | 支撑 | BI、报表 |

### 7.3 限界上下文识别

根据"通用语言一致" 原则，把子域细化为限界上下文。**关键判断：'商品' 这个词在这里和那里意思是否一样**。

| 限界上下文 | 包含子域 | "商品" 含义 | "订单" 含义 |
|---|---|---|---|
| **商品目录** | 商品 | SKU/SPU/类目 | n/a |
| **库存** | 库存 | 库存单位、可用量 | n/a |
| **购物车** | 购物车 | 选购项 | n/a |
| **订单履约** | 订单 | 订单快照 | 完整订单 |
| **支付清算** | 支付 | n/a | 支付流水 |
| **物流配送** | 物流 | 包裹明细 | 关联运单 |
| **营销活动** | 营销 | 活动商品池 | 折扣订单 |
| **会员中心** | 用户 | n/a | 历史订单 |
| **推荐搜索** | 推荐搜索 | 召回项、向量 | 用户行为 |
| **风控** | 风控 | 黑名单 | 异常订单 |
| **客服工单** | 客服 | 咨询商品 | 售后订单 |
| **评价晒单** | 评价 | 被评商品 | 关联订单 |
| **通知中心** | 通知 | n/a | n/a |
| **数据分析** | 数据分析 | 全量分析 | 全量分析 |

注意"商品" 的含义在每个上下文里都不同：

- 商品目录里："商品" = 完整 SKU 模型，几百个字段
- 订单履约里："商品" = 快照（名称 / 价格 / 规格），下单瞬间冻结
- 物流里："商品" = 包裹明细（重量、体积、危险品标识）
- 推荐里："商品" = embedding 向量 + 召回 tag

### 7.4 关键聚合设计

#### 商品目录上下文

```
Product (聚合根)
  ├── ProductId
  ├── Name
  ├── Category (VO)
  ├── Attributes (VO[])
  ├── SKU[] (实体)
  │     ├── SkuId
  │     ├── Specs (VO)
  │     └── Price (Money)
  └── Status

不变量：
- 至少 1 个 SKU
- 所有 SKU 的 spec 维度一致
```

#### 订单履约上下文

```
Order (聚合根)
  ├── OrderId
  ├── CustomerId            (引用，不是嵌入)
  ├── OrderItem[] (实体)
  │     ├── ProductSnapshot (VO) ← 来自商品目录的快照
  │     ├── Quantity
  │     ├── Price (Money)
  │     └── PromotionId (引用)
  ├── ShippingAddress (VO)
  ├── PaymentMethod
  ├── Status
  └── TotalAmount (VO)

不变量：
- TotalAmount = sum(item.price * quantity)
- 已支付订单不可修改 item
- items.size > 0
```

#### 库存上下文

```
InventoryItem (聚合根)
  ├── SkuId
  ├── Warehouse (引用)
  ├── AvailableQuantity
  ├── ReservedQuantity      // 占用（如下单待支付）
  ├── SafetyStock           // 安全库存
  └── Status

不变量：
- AvailableQuantity >= 0
- ReservedQuantity >= 0
```

### 7.5 上下文映射

```
                        商品目录 (OHS via gRPC)
                              ▲
                              │ Customer/Supplier
                              │
         购物车 ─────────────►│
                              │
         订单履约 ────────────┤── ACL ──→ (法律变化时隔离)
                              │
                              ▼
         推荐搜索 (Conformist 接收商品事件)


         订单履约 ◄── Partnership ──► 支付清算
         (订单创建必须和支付协同)

         订单履约 ──→ 库存 (Customer/Supplier，订单要锁库存)
         订单履约 ──→ 营销 (Customer/Supplier，订单要查折扣)
         订单履约 ──→ 物流 (Customer/Supplier，订单转发运单)

         评价晒单 ◄── Conformist ── 订单履约
         (评价依赖订单，订单不在乎评价)

         所有上下文 ──→ 通知中心 (Open Host Service via Kafka)

         数据分析 ◄── Separate Ways（异步抽数，不影响实时）
```

### 7.6 关键决策

#### 决策 1：商品快照放在订单聚合里

**原因**：订单一旦生成，商品信息要"凝固"。商品改名/改价不能影响历史订单。

```java
// 订单 item 里的商品信息是 VO snapshot，不是引用
public class OrderItem {
    private final ProductSnapshot productSnapshot;  // 冻结
    // private final ProductId productId;  ← 仅作为关联键
}
```

#### 决策 2：库存"占用" 走 Saga，不放在订单事务里

**原因**：订单和库存是两个聚合。订单创建瞬间扣库存属于强一致跨聚合，违反聚合规则。

正确做法：

```
Order Saga:
  1. CreateOrder → 订单 = PendingInventory
  2. ReserveInventory → 库存占用
     成功：→ 订单 = WaitingPayment
     失败：→ 订单 = Cancelled (补偿)
  3. ProcessPayment
     ...
```

#### 决策 3：推荐用 Conformist 模式接收商品事件

**原因**：推荐服务消费"商品上架/下架/改价" 事件，但不能要求商品服务为它定制——商品改 schema 推荐就跟。

#### 决策 4：会员中心和用户认证是同一个上下文吗？

**讨论**：

- 用户认证（登录、token）几乎所有上下文都用
- 会员中心（积分、等级、营销画像）只有营销/推荐用

**结论**：拆成两个上下文。"账号" 上下文做认证（generic 子域，可用 Keycloak）；"会员中心" 做营销画像（核心子域，自研）。

## 第八章：拆分反模式——5 个常见错误

### 8.1 反模式 1：按 CRUD 拆

**症状**：拆成 "User Service 只做 user 表的 CRUD"、"Order Service 只做 order 表的 CRUD"。

**问题**：

- 没有业务边界，只有数据边界
- 业务逻辑被打散：下单要调 5 个服务才能完成
- 是"分布式数据库" 不是"微服务"

**纠正**：按业务能力拆。"订单履约" 服务包含订单、订单项、订单状态机、订单事件——所有订单相关的业务在一处。

### 8.2 反模式 2：按技术层拆

**症状**：拆成 "DAO Service"、"Service Service"、"Controller Service"——按 MVC 层拆。

**问题**：

- 一个业务请求要穿透所有层服务
- 改一个业务功能要改 3 个服务

**纠正**：按业务能力拆，每个服务内部仍是分层架构。

### 8.3 反模式 3：忽视业务边界（按数据库表拆）

**症状**：现有数据库有 50 张表，"那就拆 50 个服务"。

**问题**：

- 表之间的关联变成网络调用
- 一个简单 JOIN 变成跨服务查询

**纠正**：按聚合拆，**一个聚合 = 一些相关的表**。

### 8.4 反模式 4：实体即服务（Entity Service）

**症状**：每个 DDD 里的实体都搞一个服务。

**问题**：

- 实体粒度远小于聚合
- 服务无法独立完成有意义的业务
- 任何业务都要跨多个服务编排

**纠正**：以聚合（或者限界上下文）为最小服务单位，不要按实体。

### 8.5 反模式 5：大泥球微服务

**症状**：服务是拆了，但每个服务都共享同一份数据库 schema；改一个表所有服务一起改；服务间疯狂相互调用。

**问题**：

- 数据耦合 = 失去了"独立部署" 这个最大收益
- 是分布式单体，最糟糕的反模式

**纠正**：

- 一个服务独占自己的数据库 schema
- 服务间通过 API 或事件交互，不直接共享表
- 数据冗余可以接受（订单存商品快照）

## 第九章：拆分的常见困难与对策

### 9.1 困难：跨服务查询

**问题**：

```
查询：用户最近 10 个订单，每个订单包含商品名称
→ 涉及订单服务和商品服务
→ N+1 调用？10 个订单 × 每个 5 个商品 = 50 次商品服务调用
```

**对策**：

1. **冗余字段**：订单里存商品名称快照（最常用）
2. **批量查询**：一次性查 50 个商品 ID（减少 RT，但还是跨服务）
3. **CQRS + 物化视图**：维护一个"订单详情" 读模型，包含商品信息
4. **API 网关聚合**：BFF 层做并发调用合并

### 9.2 困难：跨服务事务

详见 [M08 分布式事务](./08-精通-分布式事务.md)。简要：

- **Saga**：编排或编排+补偿
- **Outbox**：保证消息发布与本地事务原子性
- **TCC**：两阶段，金融场景

### 9.3 困难：数据一致性

- 接受最终一致（默认）
- 业务上能容忍多久不一致？设计延迟容忍
- 真正需要强一致的，重新审视边界（可能拆错了）

### 9.4 困难：服务间循环依赖

**症状**：A 调 B，B 又调 A。

**对策**：

- 改成事件驱动（A 发事件，B 订阅；不要 A 调 B 调 A）
- 把共同依赖抽出来成第三方
- 重新审视边界（90% 的循环依赖是因为边界画错了）

## 第十章：判断你的拆分是否合理——10 个体检题

拆分完成后，用以下 10 题做自检。任何一个"否"都意味着边界可能需要调整。

1. 每个服务有自己独立的数据库 schema 吗？（不共享表）
2. 改一个服务的代码，能不通知别人就发布吗？
3. 跨服务的"事务" 控制在 3 个以内？
4. 服务名是业务术语，不是技术术语？
5. 服务的 API 是稳定的（半年内不大改）？
6. 每个服务有明确的 owner 团队？
7. 任意两个服务之间的调用 < 3 次（不是 chatty）？
8. 服务的代码量在合理区间（5k-100k 行）？
9. 服务的领域模型独立（不依赖其他服务的 entity）？
10. 出现新业务时，能找到清晰的"归属服务"？

## 生产实践

### 实践 1：拆分先做事件风暴

不要让架构师一个人画图——拉业务方一起做事件风暴。事件风暴**比任何文档都有效**，因为它强迫所有人在同一个语境下讨论。

实操：找一个大会议室，准备便利贴和 A0 卷纸，2 天工作坊，所有关键人到场。

### 实践 2：用聚合规则保护数据边界

第四章的 4 条聚合规则是**铁律**，违反它就是埋雷：

- 小聚合
- ID 引用
- 最终一致跨聚合
- 一事务一聚合

任何"为了性能"或"为了方便" 违反规则的设计，6 个月后都会反噬。

### 实践 3：用 ACL 隔离遗留系统

接手老系统时不要直接对接旧 API。**在你的服务和老系统之间加一层 ACL**，把老模型翻译成你的领域模型。这一层让你能慢慢替换底层而不污染上层。

### 实践 4：拆分后保留单体作为"剩余服务"

不要追求"100% 拆分"。**保留一个"单体服务" 容纳所有还没拆的功能**，新功能逐步外迁。这比"一次拆完" 安全得多。

### 实践 5：用 Schema Registry 管理跨服务契约

服务间通信的 schema（Protobuf / Avro / JSON Schema）要进**Schema Registry**：

- Confluent Schema Registry（Kafka 生态）
- Apicurio
- Buf Schema Registry（gRPC）

破坏性变更必须通过 Registry 审批，避免野生 schema 漂移。

### 实践 6：每个服务一份"上下文画布"

每个服务建一个文档（上下文画布 / Bounded Context Canvas）：

- 名称、目的
- 战略分类（核心/支撑/通用）
- 角色（上下游关系）
- 通用语言（关键术语表）
- 业务规则与不变量
- 主要事件
- 关键聚合
- Owner 团队

放在服务根目录的 README 或 Backstage 里。新人 1 小时上手。

## 陷阱清单

### 陷阱 1：把子域当限界上下文

子域是业务划分，限界上下文是模型边界。两者不是 1:1。把它们混为一谈会导致"商品服务"塞 100 个字段——因为"商品" 这个业务概念被无限放大。

### 陷阱 2：聚合做得太大

把"用户" 和"用户的所有订单" 放在一个聚合里——加载用户要加载几千条订单，性能爆炸。聚合越小越好。

### 陷阱 3：跨聚合直接引用

聚合 A 引用聚合 B 的对象（不是 ID）——加载 A 必然加载 B，事务边界混乱。必须用 ID 引用。

### 陷阱 4：领域事件包含整个聚合

事件里塞了整个 Order 对象——消费方依赖你的内部结构，破坏封装。事件只放消费方需要的最小信息。

### 陷阱 5：缺失通用语言

代码里叫 Order，文档里叫订单，需求文档里叫"销售单据"——不同名字指同一物。开会一半时间在搞清楚谁说的什么。必须统一术语。

### 陷阱 6：上下文映射只画一次就不维护

上下文映射要**随着业务演进持续更新**。一年前的图和现在的真实状况差异巨大——按图施工 = 按过期地图打仗。

### 陷阱 7：把 ACL 当成"翻译层而已"

ACL 不只是 DTO 转换。它应该**主动拒绝**上游不合理的概念入侵。比如上游有"客户分类" 但你不需要——ACL 里直接 drop，不要传到领域层。

### 陷阱 8：忽视 Partnership 的成本

把所有相关上下文都做成 Partnership——结果两个团队天天开会同步。Partnership 是最贵的关系，能用别的就别用。

## 练习题

### 题 1：子域 vs 限界上下文

请用一句话区分子域和限界上下文，并各举一个例子。

**答案要点**：子域是业务功能划分（如"订单子域"），限界上下文是模型边界（如"订单履约上下文" + "订单查询上下文"）。子域 1 个，限界上下文可能多个。

### 题 2：聚合设计

设计一个"购物车" 聚合，包含哪些实体/VO？4 个不变量规则在你的设计里是怎么体现的？

**答案要点**：
- Cart 为聚合根，包含 CartItem 实体（小聚合）
- CartItem 用 productId 引用商品（ID 引用，不嵌入 Product）
- 加购、改数量、删除都在 Cart 内部（一事务一聚合）
- 合并到订单时通过事件，不在同一事务（最终一致跨聚合）

### 题 3：上下文映射

下列场景应该用哪种上下文关系？请说明理由。

A. 内部订单服务和内部支付服务  
B. 你的会员服务和阿里云短信服务  
C. 你的电商系统和遗留 CRM 系统  
D. 商品服务和推荐服务（推荐消费商品事件）  
E. HR 系统和电商订单系统

**答案要点**：
- A. Partnership（紧密协作）或 Customer/Supplier
- B. Conformist（阿里云不会为你改）
- C. ACL（保护新系统不被老模型污染）
- D. Open Host Service / Conformist（推荐订阅事件，无定制要求）
- E. Separate Ways（无关）

### 题 4：识别反模式

下面的拆分有什么问题？请改进。

> 把电商单体拆成 8 个服务：UserDAO、UserService、UserAPI、OrderDAO、OrderService、OrderAPI、ProductDAO、ProductService

**答案要点**：按技术层拆（反模式 2）+ 按 CRUD 拆（反模式 1）。改进：按业务能力拆为"用户中心、订单履约、商品目录" 3 个服务，每个内部仍是分层架构。

### 题 5：事件风暴流程

某团队第一次做事件风暴。请你列出 3 阶段及每阶段的关键产出。

**答案要点**：
- 阶段 1 Big Picture：产出事件全景图（事件按时间排）
- 阶段 2 Process Modeling：产出命令-聚合-事件-策略链
- 阶段 3 Software Design：产出聚合列表 + 限界上下文图 + 上下文映射

### 题 6：商品快照辨析

订单里要不要冗余商品名称和价格？为什么？

**答案要点**：要冗余。订单是历史记录，必须保留"下单瞬间" 的商品状态。商品改价/改名不能追溯影响历史订单。这是商品快照（VO）的典型应用。

### 题 7：聚合规则应用

某项目里订单和库存放在同一事务里更新（强一致）。请用聚合 4 规则评估是否合适。

**答案要点**：违反"一事务一聚合" 和"最终一致跨聚合"。订单和库存是两个聚合，必须用 Saga 或事件驱动达成最终一致。强一致跨聚合在分布式下不可持续。

### 题 8：拆分粒度判断

某服务有 200KB 代码、3 个聚合、1 个团队 owner。是否需要继续拆？

**答案要点**：不需要。判断标准：（1）部署独立性已满足（一个服务一个团队）；（2）代码量适中（远小于 1MB）；（3）3 个聚合在同一上下文内合理。继续拆会引入网络/事务/运维成本而无明显收益。
