## 引言：为什么"分布式事务"是微服务最难的章

一旦你把"用户下单"拆成 OrderService + PaymentService + InventoryService + ShippingService，"一笔下单"就不再是一个数据库事务能搞定的事。这时摆在你面前的问题是：

- 库存扣了，但支付失败了，怎么把库存退回去？
- 支付成功了，但物流单创建失败了，订单状态怎么回滚？
- 4 个服务同时操作，怎么保证它们要么全成功、要么全失败？
- 如果"全失败"做不到，至少要保证"最终一致"，可"最终"是多久？业务能接受吗？

这就是**分布式事务**的核心命题。它不只是一个技术问题——它是 **"一致性、可用性、性能、复杂度"** 的四方博弈。学完这一章你应能：

- 区分 ACID 与 BASE，理解 CAP 在事务场景的含义
- 解释 2PC、3PC、XA 各自的死亡原因
- 用 TCC（Try-Confirm-Cancel）实现一个金融级业务
- 用 Saga（Orchestration / Choreography）实现长事务的补偿
- 用 Outbox 模式 + CDC（Debezium）实现"业务表 → 事件"零丢失
- 给出"Saga + Outbox + Idempotent Consumer + Inbox"的端到端架构
- 识别并修复 Dual Write 这类常见反模式
- 在不同业务场景下做出合理的事务模型选型

## 第一章：ACID、BASE 与 CAP 三视角

### 1.1 ACID（单机事务的黄金标准）

| 字母 | 含义 |
|---|---|
| **A**tomicity | 原子性：事务内所有操作要么全部成功，要么全部回滚 |
| **C**onsistency | 一致性：事务前后业务规则被保持（如借贷平衡） |
| **I**solation | 隔离性：并发事务互不干扰（多种隔离级别） |
| **D**urability | 持久性：事务提交后数据落盘不丢 |

在单机数据库（PostgreSQL / MySQL / Oracle）里，ACID 由 WAL + MVCC + 锁 + fsync 协同保证。但**一旦数据跨节点跨数据库**，ACID 的实现就变成了 2PC（两阶段提交）——而 2PC 在工程上几乎已死。

### 1.2 BASE（分布式事务的现实主义）

BASE 是 ACID 的"妥协版本"：

| 字母 | 含义 |
|---|---|
| **B**asically **A**vailable | 基本可用：允许部分功能降级，整体可用 |
| **S**oft state | 软状态：允许中间态存在（如"处理中"） |
| **E**ventually consistent | 最终一致：在一个可接受的时间窗口后，所有副本达到一致 |

BASE 的核心放弃是 **C**：放弃强一致，换取**可用性 + 分区容错 + 可扩展性**。这是绝大多数微服务架构的实际工作模型。

### 1.3 CAP 视角

CAP 三选二是常见误解。在分布式系统里 **P 是必然存在**（网络一定会分区），剩下的选择是 C 还是 A：

- **CP**：分区时拒绝服务直到一致性恢复（如 etcd、ZooKeeper）。
- **AP**：分区时允许各分区独立服务，事后协调（如 DynamoDB、Cassandra、绝大多数微服务）。

事务模型映射：

| 模型 | C/A 偏好 | 典型 |
|---|---|---|
| 2PC / XA | CP（强一致，牺牲可用） | 银行同库分布式事务 |
| TCC | C（业务级强一致） | 金融分布式事务 |
| Saga | AP（最终一致） | 电商订单流程 |
| Outbox + Saga | AP（最终一致，但保证发布） | 现代微服务事实标准 |

### 1.4 "强一致"是不是必要的？

工程上 80% 业务**不需要**强一致：

- 下单后 200ms 内积分入账延迟 → 用户无感知。
- 商品评分 5 秒后更新 → 用户能接受。
- 通知 1 秒后推送 → 完全没问题。

剩下 20% 需要强一致的（如金融交易、库存扣减），也可以用**业务级强一致**（TCC / 同步确认 + 异步补偿）代替**数据库级强一致**（2PC）。

判断"是否真的需要强一致"问题：

1. 业务上能接受 100ms / 1s / 10s 的不一致窗口吗？
2. 如果暂时不一致，用户感知是什么？影响金额上限是多少？
3. 通过 UI 兜底（"处理中"状态）能否消除用户疑虑？
4. 监控 + 对账能否在窗口期内发现不一致？

绝大多数情况下，答案会让你倒向 BASE / 最终一致。

## 第二章：2PC 与 XA 的死亡

### 2.1 2PC 的工作原理

```
Coordinator (协调器)
    │
    ├── Phase 1: Prepare
    │      ├─→ Participant-A: "你能 commit 吗？" ─→ "Yes（已锁资源）"
    │      ├─→ Participant-B: "你能 commit 吗？" ─→ "Yes"
    │      └─→ Participant-C: "你能 commit 吗？" ─→ "Yes"
    │
    └── Phase 2: Commit
           ├─→ A: "commit!" ─→ "Done"
           ├─→ B: "commit!" ─→ "Done"
           └─→ C: "commit!" ─→ "Done"
```

如果 Phase 1 中任一参与者回 No，协调器在 Phase 2 发 abort。

### 2.2 XA 协议

XA 是 X/Open 组织定义的 2PC 标准接口（`xa_prepare` / `xa_commit` / `xa_rollback`）。Java JTA、Spring `JtaTransactionManager`、Atomikos、Narayana 都是 XA 实现。

### 2.3 为什么 2PC 在微服务里死了

#### 致命问题 1：阻塞 + 长锁

Phase 1 prepare 之后到 Phase 2 commit 之前，参与者**必须锁住相关资源**——锁可能持续数百毫秒到数秒。

```
T+0     prepare(A) → 锁住 user_balance 行
T+5ms   prepare(B) → 锁住 inventory 行
T+10ms  prepare(C) → 锁住 order 行
T+...    协调器写日志 + 决策
T+50ms  commit ALL → 锁释放
```

50ms 的锁，对 OLTP 系统是**灾难性的**。生产环境 QPS 跌 10-20 倍。

#### 致命问题 2：协调器单点

协调器在 Phase 1 完成后崩溃 → 所有参与者**永久阻塞**（不知道该 commit 还是 abort）。

补救：协调器要 HA（如 Raft 三副本）+ 持久化日志 → 复杂度暴涨、性能进一步降低。

#### 致命问题 3：网络分区

prepare 阶段一个参与者超时无响应 → 协调器决定 abort → 但参与者其实成功了 → **不一致**。

#### 致命问题 4：跨异构系统不可行

XA 要求所有参与者支持同一协议。Kafka、Redis、MongoDB、HTTP 外部 API、SaaS（Stripe / Twilio）几乎都不支持 XA。在异构架构里 XA 失效。

#### 致命问题 5：性能

数倍 round-trip + 写日志 + 锁等待 → 整体延迟是单机事务的 5-20 倍。

#### 2PC 死亡时间线

| 年份 | 事件 |
|---|---|
| 1990s | XA 兴起，企业级 JTA 标准 |
| 2000s | EJB / Java EE 推广 XA，但被诟病性能差 |
| 2010s | 微服务兴起，XA 几乎被弃用 |
| 2015+ | Saga / TCC 模式流行，Outbox + CDC 成新标杆 |
| 2026 | XA 仅在传统单机系内（Oracle RAC、SQL Server 同库分布式）少量遗留 |

### 2.4 3PC：失败的尝试

3PC 在 2PC 基础上加了一个 "CanCommit" 阶段，缓解阻塞：

```
CanCommit → PreCommit → DoCommit
```

理论上避免协调器崩溃导致永久阻塞（参与者可超时自决）。

**但**：

- 仍假设网络可靠 → 极端分区下仍可能不一致。
- 多一个阶段 → 性能更差。
- 几乎没有工业级实现。

3PC 是教科书上的"知识"，不是工程上的"答案"。

### 2.5 什么场景下 2PC 仍合理

- **同一数据库的多个实例**（如 Oracle RAC 内部跨节点事务，DBMS 自己处理）。
- **强监管金融场景** + 性能可忍受 + 参与者全是 XA 兼容数据库。
- **批处理任务**而非在线 OLTP（延迟不敏感）。

除此之外：**不要在新系统里上 2PC**。

## 第三章：TCC（Try-Confirm-Cancel）

### 3.1 TCC 的核心思想

把每个分布式参与者的操作拆成 **3 个业务接口**：

| 阶段 | 含义 | 示例（扣余额） |
|---|---|---|
| **Try** | 资源预留（业务级"软锁"） | 冻结余额 100 元（balance -= 100, frozen += 100） |
| **Confirm** | 真正生效（idempotent） | 冻结额转扣减（frozen -= 100，余额已扣） |
| **Cancel** | 释放预留（idempotent） | 取消冻结（frozen -= 100, balance += 100） |

TCC 把"事务"从数据库层提到业务层：**不再用数据库锁**，而是**用业务字段（frozen / pending）做软锁**。

### 3.2 TCC 流程

```
Coordinator (TM)
    │
    ├── Phase 1: Try
    │   ├─→ AccountSvc.tryDebit(orderId, amount) → OK
    │   ├─→ InventorySvc.tryReserve(orderId, sku, qty) → OK
    │   └─→ ShippingSvc.trySchedule(orderId, addr) → OK
    │
    └── Phase 2 (Confirm if all OK)
        ├─→ AccountSvc.confirmDebit(orderId)
        ├─→ InventorySvc.confirmReserve(orderId)
        └─→ ShippingSvc.confirmSchedule(orderId)

    Phase 2 (Cancel if any failed)
        ├─→ AccountSvc.cancelDebit(orderId)
        ├─→ InventorySvc.cancelReserve(orderId)
        └─→ ShippingSvc.cancelSchedule(orderId)
```

### 3.3 TCC 的关键设计点

#### 1. Try 必须"业务可逆"

Try 不能做不可逆操作（如发邮件、调外部支付）。这些必须放在 Confirm。

#### 2. Confirm / Cancel 必须幂等

Coordinator 会重试，必须用 orderId 作为幂等 key（见 M09）。

#### 3. 空回滚（Empty Rollback）

如果 Try 因网络问题没到达，但 Cancel 到了 → 必须识别"没有 Try 过的事务"并跳过 Cancel。
做法：建 `tcc_transaction` 表，Cancel 时检查"是否存在 Try 记录"。

#### 4. 防悬挂（Hanging）

Try 超时后 Coordinator 已 Cancel，但 Try 的请求迟到 → 不能再 Try。
做法：Cancel 在 `tcc_transaction` 写"已取消"标记，Try 看到标记后直接拒绝。

#### 5. 冻结字段 vs 预留表

两种实现：

- **冻结字段**：余额表加 `frozen_amount` 字段，Try 时 balance -= X, frozen += X。
- **预留表**：单独 `reservations` 表，Try 时插入预留记录。

预留表更灵活、易扩展；冻结字段更简单、性能高。

### 3.4 TCC 代码骨架（Go）

```go
// AccountService
type AccountService struct { db *sql.DB }

func (s *AccountService) TryDebit(ctx context.Context, txID, userID string, amount int64) error {
    tx, _ := s.db.BeginTx(ctx, nil)
    defer tx.Rollback()

    // 1. 写 TCC 事务记录（用于空回滚 + 防悬挂）
    _, err := tx.ExecContext(ctx, `
        INSERT INTO tcc_transactions(tx_id, branch, state) VALUES ($1, 'account', 'TRYING')
        ON CONFLICT (tx_id, branch) DO NOTHING
    `, txID)
    if err != nil { return err }

    // 2. 冻结资金
    res, err := tx.ExecContext(ctx, `
        UPDATE accounts SET balance = balance - $1, frozen = frozen + $1
        WHERE user_id = $2 AND balance >= $1
    `, amount, userID)
    if err != nil { return err }
    if n, _ := res.RowsAffected(); n == 0 { return ErrInsufficientFunds }

    return tx.Commit()
}

func (s *AccountService) ConfirmDebit(ctx context.Context, txID string) error {
    tx, _ := s.db.BeginTx(ctx, nil)
    defer tx.Rollback()

    // 幂等检查
    var state string
    err := tx.QueryRowContext(ctx, `
        SELECT state FROM tcc_transactions WHERE tx_id=$1 AND branch='account' FOR UPDATE
    `, txID).Scan(&state)
    if err == sql.ErrNoRows { return nil }                 // 防悬挂：无 Try 记录
    if state == "CONFIRMED" || state == "CANCELED" { return nil }  // 幂等

    // 解冻 → 实际扣减
    _, err = tx.ExecContext(ctx, `
        UPDATE accounts SET frozen = frozen - (SELECT amount FROM tcc_transactions WHERE tx_id=$1 AND branch='account')
        WHERE user_id = (SELECT user_id FROM tcc_transactions WHERE tx_id=$1 AND branch='account')
    `, txID)
    if err != nil { return err }

    _, err = tx.ExecContext(ctx, `UPDATE tcc_transactions SET state='CONFIRMED' WHERE tx_id=$1 AND branch='account'`, txID)
    if err != nil { return err }
    return tx.Commit()
}

func (s *AccountService) CancelDebit(ctx context.Context, txID string) error {
    // 空回滚 + 幂等 + 解冻 + 回滚余额
    // ... 类似 ConfirmDebit
}
```

### 3.5 TCC 适用与不适用

适合：

- 金融交易（资金、积分、票券）。
- 库存（业务模型清晰能加预留字段）。
- 需要业务级强一致（一致窗口 < 1 秒）。

不适合：

- 业务接口无法改造成 Try/Confirm/Cancel 三段式（如外部 SaaS 无预留 API）。
- 长流程（数十秒到数分钟，Try 的资源占用太久）。
- 跨多个团队 / 公司（每个参与方都要实现 3 接口，协作成本高）。

### 3.6 框架

- **Seata**（阿里开源）：AT / TCC / Saga / XA 多模式，国内主流。
- **DTM**（开源 Go 实现）：TCC / Saga / 二阶段消息，轻量。
- **Hmily** / **TCC-Transaction**（国内 Java）。

国内金融 / 电商体系里 Seata + DTM 是事实标准。

## 第四章：Saga——长事务的补偿模型

### 4.1 Saga 的核心思想

> Saga 是把一个长事务拆成一系列**本地事务（local transactions）**，每个本地事务都有对应的**补偿事务（compensating transaction）**。如果某步失败，则执行已完成步骤的补偿，回退整体状态。

```
T1 → T2 → T3 → T4   (Forward)
                  失败
C3 ← C2 ← C1        (Compensate)
```

Saga 名字来自 1987 年 Hector Garcia-Molina 的论文（同名作者）。

### 4.2 Saga vs TCC vs 2PC

| 维度 | 2PC / XA | TCC | Saga |
|---|---|---|---|
| 强一致 | 数据库强一致 | 业务级强一致 | 最终一致 |
| 锁 | DB 锁 | 业务软锁（frozen） | 无锁 |
| 中间状态 | 不可见 | "处理中"可见 | "各种业务状态"可见 |
| 性能 | 差 | 中 | 好 |
| 业务改造 | 几乎无 | 大（3 接口） | 中（补偿接口） |
| 长流程支持 | 极差 | 差 | 好 |
| 跨异构系统 | 差 | 中 | 好 |
| 典型时长 | < 1s | < 几秒 | 秒级到数小时 |
| 典型场景 | 同库分布式 | 金融、库存 | 电商订单、工作流 |

### 4.3 Saga 的两种实现：编排 vs 编舞

#### Orchestration（编排）：中央编排器

```
       OrderSaga (编排器)
            │
   ┌────────┼─────────────┬────────────────┐
   │        │             │                │
   ▼        ▼             ▼                ▼
PaymentSvc InvSvc      ShippingSvc      NotifySvc
   │        │             │                │
   └────────┴─────────────┴────────────────┘
            状态机：CREATED → PAID → RESERVED → SHIPPED → DONE
```

编排器是一个独立的服务（或库），用状态机驱动各参与方：

```
state CREATED:
    call Payment.charge → on success: state=PAID
                       → on failure: state=FAILED
state PAID:
    call Inventory.reserve → on success: state=RESERVED
                          → on failure: compensate(Payment.refund), state=COMPENSATED
state RESERVED:
    call Shipping.create → on success: state=SHIPPED
                        → on failure: compensate(Inventory.release, Payment.refund), state=COMPENSATED
state SHIPPED:
    call Notify.send → state=DONE
```

#### Choreography（编舞）：纯事件驱动

```
OrderSvc → publish OrderPlaced
PaymentSvc consumes OrderPlaced → charges → publish PaymentSucceeded / PaymentFailed
InventorySvc consumes PaymentSucceeded → reserves → publish InventoryReserved / ...
ShippingSvc consumes InventoryReserved → ships → publish OrderShipped / ...
```

没有中央编排器，每个服务订阅自己关心的事件、发布自己产生的事件。补偿通过订阅"失败事件"触发：

```
PaymentSvc consumes InventoryReserveFailed → refunds → publish PaymentRefunded
```

### 4.4 编排 vs 编舞对比

| 维度 | 编排 | 编舞 |
|---|---|---|
| 流程可见性 | 高（编排器一目了然） | 低（散落各服务） |
| 加新参与者 | 改编排器 | 增订阅，无需改他人 |
| 单点风险 | 编排器需要 HA | 无中心，各服务独立 |
| 调试 | 容易（看编排器状态机） | 难（链路追踪还原） |
| 服务耦合 | 编排器知道所有服务 | 服务彼此不知 |
| 适合 | 流程稳定、参与方较多、需要可视化 | 流程灵活、订阅方动态变化 |
| 典型框架 | Temporal / Camunda / Conductor / Cadence / Seata Saga | Kafka + 各服务自治 |

**实务建议**：

- 强业务流程（订单、支付、KYC、风控）→ 编排（流程可视、可调）。
- 弱业务流程、事件广播为主 → 编舞（耦合最低）。
- 混合：大流程用编排，细枝末节用编舞。

### 4.5 Saga 的补偿设计

#### 1. 补偿必须幂等

补偿可能被重试。同一笔订单 refund 被调用 N 次，结果应等同一次。

#### 2. 补偿必须可重试（最终成功）

如果补偿失败，编排器要持续重试（指数退避），直到成功或人工介入。

#### 3. 补偿不可"undo 一切"

某些操作天然不可补偿：

- 发出去的邮件不能 unsent。
- 已确认的物流不能假装没发。

应对：

- **避免**：流程设计时把不可逆操作放最后（"先扣款再发邮件"）。
- **缓解**：把"邮件"改成"发送 + 后续 retract 通知"。

#### 4. 同时支持"语义补偿"

不是数据上的回滚，而是业务上的"反向操作"：
- 已发货 → 退货流程（非"删订单"）。
- 已通知 → 发"撤回通知"邮件（非删邮件）。

#### 5. Saga 不保证隔离性

Saga 是非原子的，中间步骤对其他事务可见。可能出现"看见中间状态"：

- 用户已扣款但订单未完成 → UI 看到"处理中"是关键。
- 商品已扣库存但订单未支付 → 其他用户可能看到"无库存"短暂错误。

应对：
- UI 显示"处理中"中间状态。
- 业务上接受短窗口不一致。
- 关键业务用 **锁定 + 信号量**（"已预留"标记）。

### 4.6 Saga 状态机持久化

编排器必须持久化每个 Saga 实例的当前状态，否则崩溃后无法续跑：

```sql
CREATE TABLE saga_instances (
    saga_id UUID PRIMARY KEY,
    saga_type VARCHAR(64),
    state VARCHAR(32),          -- CREATED / PAID / RESERVED / SHIPPED / DONE / COMPENSATING / COMPENSATED / FAILED
    context JSONB,              -- 业务上下文
    current_step INT,
    created_at TIMESTAMPTZ,
    updated_at TIMESTAMPTZ,
    completed_at TIMESTAMPTZ
);

CREATE TABLE saga_steps (
    saga_id UUID,
    step INT,
    action VARCHAR(64),
    state VARCHAR(32),          -- PENDING / SUCCESS / FAILED / COMPENSATED
    request JSONB,
    response JSONB,
    started_at TIMESTAMPTZ,
    finished_at TIMESTAMPTZ,
    PRIMARY KEY (saga_id, step)
);
```

Temporal / Cadence 等专用框架内置了状态持久化、定时器、重试、补偿，免去自研。

## 第五章：Outbox 模式——Dual Write 的解药

### 5.1 Dual Write 问题

最常见的微服务反模式：**在一个本地事务里，先改 DB，再发消息（或反过来）**。

```go
tx, _ := db.Begin()
tx.Exec("UPDATE orders SET status='PAID' WHERE id=?", orderID)
tx.Commit()
producer.Send("OrderPaid", orderID)   // 这一步独立，可能失败
```

问题：

- DB commit 成功 → 消息发送失败：下游永远缺这条事件。
- 消息发送成功 → DB commit 失败（极端：commit 时 OOM）：下游收到不存在的事件。

两个步骤不在同一个事务里，无法原子保证。这就是 **Dual Write**。

### 5.2 Outbox 模式原理

把"发消息"也变成"写 DB"——业务表和 outbox 表在**同一本地事务**里：

```sql
BEGIN;
UPDATE orders SET status='PAID' WHERE id=$1;
INSERT INTO outbox(event_type, aggregate_id, payload, created_at)
VALUES ('OrderPaid', $1, $2::jsonb, now());
COMMIT;
```

事务原子保证：业务变更 + 事件记录"同生死"。

然后用**独立的发布器（Publisher）异步把 outbox 表的事件搬到消息总线**：

```
[Application] → [DB: orders + outbox (same tx)] → [Publisher] → [Kafka]
```

### 5.3 Outbox 表设计

```sql
CREATE TABLE outbox (
    id BIGSERIAL PRIMARY KEY,
    event_id UUID NOT NULL UNIQUE,             -- 幂等 key
    aggregate_type VARCHAR(64) NOT NULL,       -- 'Order'
    aggregate_id VARCHAR(64) NOT NULL,         -- '12345'
    event_type VARCHAR(64) NOT NULL,           -- 'OrderPaid'
    payload JSONB NOT NULL,
    headers JSONB,                             -- traceparent / source / etc.
    created_at TIMESTAMPTZ DEFAULT now(),
    published_at TIMESTAMPTZ                   -- NULL 表示未发布
);

CREATE INDEX idx_outbox_unpub ON outbox(id) WHERE published_at IS NULL;
```

### 5.4 Publisher 实现的两条路

#### 路 A：轮询式 Publisher（Polling Publisher）

应用启动一个后台线程，定时查未发布事件，发出去后更新 published_at：

```python
def publish_loop():
    while True:
        rows = db.query("""
            SELECT id, event_id, aggregate_id, event_type, payload, headers
            FROM outbox WHERE published_at IS NULL
            ORDER BY id LIMIT 1000 FOR UPDATE SKIP LOCKED
        """)
        for r in rows:
            kafka.produce(topic=route(r), key=r.aggregate_id, value=encode(r))
            db.exec("UPDATE outbox SET published_at=now() WHERE id=$1", r.id)
        time.sleep(0.1)
```

优点：

- 应用层全控，简单。
- 不依赖 DB 复制能力。

缺点：

- 轮询延迟（100ms~1s）。
- 大表查询慢，需要好索引。
- 多实例并发要 `FOR UPDATE SKIP LOCKED`（PG）。

#### 路 B：CDC（Change Data Capture）—— Debezium + Kafka Connect

利用数据库的逻辑复制能力，监听 outbox 表的 INSERT 事件，自动发到 Kafka。**无需应用层 publisher**。

```
[App] → [DB outbox INSERT]
           │  (logical replication / WAL)
           ▼
       [Debezium connector]
           │
           ▼
       [Kafka topic]
```

优点：

- **近实时**（毫秒级）。
- 应用代码无需任何 publisher 逻辑。
- 高可靠（CDC 是 DB 的一等公民）。

缺点：

- 多了 Debezium / Kafka Connect 运维。
- DB 必须支持逻辑复制（PG ≥ 10、MySQL binlog ROW）。

**2026 推荐默认是路 B**——Debezium + Kafka Connect 已经非常成熟。

### 5.5 Debezium Outbox Event Router

Debezium 提供一个内置的 SMT（Single Message Transform）专门处理 outbox 表：

```yaml
# Kafka Connect config
name: outbox-connector
config:
  connector.class: io.debezium.connector.postgresql.PostgresConnector
  database.hostname: pg.example.com
  database.port: 5432
  database.user: cdc_user
  database.dbname: orders
  topic.prefix: orderdb
  table.include.list: public.outbox

  # Outbox Event Router SMT
  transforms: outbox
  transforms.outbox.type: io.debezium.transforms.outbox.EventRouter
  transforms.outbox.route.by.field: aggregate_type
  transforms.outbox.route.topic.replacement: events.${routedByValue}
  transforms.outbox.table.field.event.id: event_id
  transforms.outbox.table.field.event.key: aggregate_id
  transforms.outbox.table.field.event.payload: payload
```

效果：

- INSERT into outbox(aggregate_type='Order', ...) → 自动发到 topic `events.Order`，key = aggregate_id。
- event_id 进 Kafka header → 消费方用它做幂等。

### 5.6 Outbox 的几个工程要点

#### 1. Outbox 表清理

无限增长是问题。两种清理：

- 定时 `DELETE FROM outbox WHERE published_at < now() - interval '7 days'`。
- 用分区表，按 day 分区，到期 `DROP PARTITION`（推荐）。

#### 2. Outbox 是否包含载荷？

两种风格：

- **Thick payload**：outbox 直接存完整事件体（推荐）。优点：消费方自治；缺点：DB 写入量大。
- **Thin payload**：只存 event_id + aggregate_id，消费方回查。问题：回查时数据可能已变 → 不一致。

选 thick payload，并配合 `compression` / 分区。

#### 3. Outbox 表和业务表必须同库

跨库就没了"同一事务"原子性。如果业务库与 outbox 必须分开，那只能退化成 saga / 二阶段消息。

#### 4. Outbox 不解决"消费方幂等"

Outbox 解决"发布方零丢失"，但消息可能因 CDC 重启、网络重试而重复。消费方仍需幂等。

### 5.7 二阶段消息（Eventual Message）

RocketMQ 的"事务消息"、DTM 的"二阶段消息"是另一种解决方案：

```
1. send half message → MQ holds it (not visible to consumer)
2. execute local tx
3. commit / rollback the half message
```

MQ 还会回调应用查询本地 tx 状态以兜底。

特点：

- 不需要 DB 支持 CDC。
- 但需要 MQ 支持半消息 + 回调（仅 RocketMQ / DTM）。

总体而言 Outbox + CDC 已是行业默认，二阶段消息留给"已用 RocketMQ"团队。

## 第六章：Inbox 模式与端到端幂等

### 6.1 Inbox 模式

Outbox 解决发布端；Inbox 解决消费端的"重复消费"问题。

```sql
CREATE TABLE inbox (
    event_id UUID PRIMARY KEY,
    consumer_group VARCHAR(64) NOT NULL,
    aggregate_id VARCHAR(64) NOT NULL,
    payload JSONB,
    processed_at TIMESTAMPTZ DEFAULT now()
);
```

消费方在**同一本地事务**里：

```go
tx, _ := db.Begin()
defer tx.Rollback()

// 1. 检查 + 标记 inbox
_, err := tx.Exec(`
    INSERT INTO inbox(event_id, consumer_group, aggregate_id, payload)
    VALUES ($1, $2, $3, $4)
`, event.ID, "payment-svc", event.OrderID, event.Payload)
if isUniqueViolation(err) {
    return tx.Rollback()       // 已处理过，幂等跳过
}
if err != nil { return err }

// 2. 业务处理（在同一事务）
_, err = tx.Exec(`UPDATE payments SET status='PAID' WHERE order_id=$1`, event.OrderID)
if err != nil { return err }

// 3. 如果有下游事件，写自己的 outbox
_, err = tx.Exec(`INSERT INTO outbox(...) VALUES (...)`, ...)
if err != nil { return err }

return tx.Commit()
```

**Outbox（发布零丢失） + Inbox（消费零重复）** 组合就是"端到端 exactly-once"的工程实现。

### 6.2 完整链路

```
[Service A: 业务 + Outbox]
      │   ↑
      │   │ (same tx)
      ▼   │
   [DB: orders + outbox]
      │
      ▼ (CDC)
   [Debezium]
      │
      ▼
   [Kafka topic]
      │
      ▼
[Service B: Inbox 去重 + 业务 + 自身 Outbox]
      │   ↑
      │   │ (same tx)
      ▼   │
   [DB: payments + inbox + outbox]
      │
      ▼ (CDC)
   ...
```

每个跨服务边界都用 Outbox + Inbox 组合，整体得到**端到端可靠 + 幂等**。

### 6.3 Inbox 表的清理

按 `consumer_group` + `processed_at` 分区或 TTL 清理。原则：保留到"上游不会再重试"为止（通常 7-30 天）。

## 第七章：最终一致性的业务约束

### 7.1 "最终"是多久？

"最终一致"是个工程概念，不是数学上的"无穷大时间"。生产环境的"最终"通常：

| 场景 | 期望窗口 |
|---|---|
| UI 状态刷新 | < 1 秒 |
| 业务通知 | < 5 秒 |
| 财务对账 | < 1 分钟 |
| 离线报表 | < 1 小时 |
| 数据归档 | < 24 小时 |

> **关键问题**：业务能接受多大的不一致窗口？这是设计的起点。

### 7.2 如何向业务方表达"最终一致"

很多业务方会说"我必须立即一致"，但他们的"立即"往往指：

- UI 显示不能有"错乱"（其实可以显示"处理中"）。
- 用户感受不到"我钱付了但订单没生效"（其实可以加占位/loading）。
- 财务上能对账（用对账机制兜底而非实时）。

技术上：

- 把"中间状态"做成 UI 一等公民（"处理中" 旋转图标）。
- 用 SSE / WebSocket / 长轮询主动推送最终状态。
- 用对账作为 fallback：T+1 跑对账脚本，发现异常 → 告警 → 修复。

### 7.3 对账系统的必要性

任何 BASE 架构都需要对账兜底：

- 每小时跑 reconciliation：业务表 vs 事件流 vs 下游状态，发现差异告警。
- 关键账户每日对账：余额、库存、订单数。
- 告警阈值：差异 > 10 条或 > 0.01% 就 PagerDuty。

对账不是"备份"，而是**架构正确性的最后一道防线**。

## 第八章：完整案例——电商订单的 Saga 设计

### 8.1 业务流程

下单后需要：

1. **Payment**：扣款（外部支付网关，10-30s 可能完成）。
2. **Inventory**：扣库存（本地 DB，毫秒级）。
3. **Shipping**：建运单（外部物流系统，可能数秒）。
4. **Loyalty**：加积分（本地，毫秒级）。
5. **Notify**：发推送/邮件（多通道，秒级）。

如果中间任何一步失败，需要：

- 退款（如果 Payment 已成功）。
- 释放库存（如果 Inventory 已扣减）。
- 取消运单（如果 Shipping 已创建）。
- 撤销积分（如果 Loyalty 已加）。
- 撤回通知（如果可撤回）。

### 8.2 选择：编排 + Outbox + Inbox

考虑：

- 流程稳定（电商订单流程是核心业务）。
- 参与服务多（5 个）。
- 需要可视化、可重放、可干预。

→ **编排式 Saga + 每个服务用 Outbox/Inbox 保证可靠**。

### 8.3 状态机设计

```
状态：CREATED → PAID → RESERVED → SHIPPED → AWARDED → DONE
                       │
        失败 → COMPENSATING_INVENTORY → COMPENSATING_PAYMENT → CANCELED
```

```sql
CREATE TABLE order_saga (
    saga_id UUID PRIMARY KEY,
    order_id VARCHAR(64) UNIQUE,
    state VARCHAR(32),
    user_id VARCHAR(64),
    total NUMERIC(18,2),
    items JSONB,
    addr JSONB,
    payment_id VARCHAR(64),
    shipping_id VARCHAR(64),
    failure_reason TEXT,
    started_at TIMESTAMPTZ DEFAULT now(),
    updated_at TIMESTAMPTZ DEFAULT now(),
    completed_at TIMESTAMPTZ
);

CREATE TABLE order_saga_steps (
    saga_id UUID,
    step_no INT,
    step_name VARCHAR(64),
    state VARCHAR(32),       -- PENDING / SUCCESS / FAILED / COMPENSATED
    request JSONB,
    response JSONB,
    started_at TIMESTAMPTZ,
    finished_at TIMESTAMPTZ,
    PRIMARY KEY (saga_id, step_no)
);
```

### 8.4 编排器伪代码

```go
func (o *OrchestratorSvc) RunOrderSaga(ctx context.Context, sagaID uuid.UUID) {
    saga := o.repo.Load(sagaID)

    for {
        switch saga.State {
        case "CREATED":
            if err := o.charge(ctx, saga); err != nil {
                o.transit(saga, "FAILED", err.Error())
                return
            }
            o.transit(saga, "PAID", "")

        case "PAID":
            if err := o.reserve(ctx, saga); err != nil {
                o.transit(saga, "COMPENSATING_PAYMENT", err.Error())
                continue
            }
            o.transit(saga, "RESERVED", "")

        case "RESERVED":
            if err := o.createShipping(ctx, saga); err != nil {
                o.transit(saga, "COMPENSATING_INVENTORY", err.Error())
                continue
            }
            o.transit(saga, "SHIPPED", "")

        case "SHIPPED":
            o.awardLoyalty(ctx, saga)       // best effort
            o.notify(ctx, saga)              // best effort
            o.transit(saga, "DONE", "")
            return

        // 补偿分支
        case "COMPENSATING_INVENTORY":
            o.releaseReserve(ctx, saga)
            o.transit(saga, "COMPENSATING_PAYMENT", "")

        case "COMPENSATING_PAYMENT":
            o.refund(ctx, saga)
            o.transit(saga, "CANCELED", "")
            return

        case "DONE", "CANCELED", "FAILED":
            return
        }
    }
}
```

每个 step 内部都用 Outbox 写消息、消费方用 Inbox 去重。

### 8.5 端到端架构图

```
                    ┌───────────────────────────────┐
                    │       Orchestrator Svc         │
                    │  - state machine               │
                    │  - retries + compensations     │
                    │  - persisted in order_saga     │
                    └──────┬────────────┬────────────┘
                           │            │
              (CMD via Kafka or RPC)    │ (state events via Kafka)
                           │            │
        ┌──────────┬───────┼────────────┼──────────────┬─────────────┐
        ▼          ▼       ▼            ▼              ▼             ▼
   PaymentSvc  InventorySvc ShippingSvc  LoyaltySvc   NotifySvc
   ├ DB        ├ DB         ├ DB         ├ DB          ├ DB
   ├ outbox    ├ outbox     ├ outbox     ├ outbox      ├ outbox
   ├ inbox     ├ inbox      ├ inbox      ├ inbox       ├ inbox
   │           │            │            │             │
   ▼           ▼            ▼            ▼             ▼
  [Debezium]→[Kafka topics: events.Payment / events.Inventory / ...]
                  │
                  ▼
              [Orchestrator subscribes to all events → drive state]
```

### 8.6 关键设计点

- **Saga 不锁资源**：库存用"预留"软锁（reserved_qty 字段），不锁物理库存。
- **超时与重试**：每个 step 有 timeout，超时进重试队列；N 次失败进 DLQ + 人工介入。
- **补偿幂等**：refund / releaseReserve 用 saga_id 作幂等 key。
- **不可补偿步骤后置**：通知、积分这种不可逆的放最后，前面失败不影响它们。
- **可视化**：Saga 状态机 + 各 step 状态都打到监控（Grafana），运营可看每笔订单的进度。
- **熔断**：上游失败率超阈值 → 暂停新订单（保护下游不雪崩）。

## 第九章：决策树——什么场景用什么

```
                         需要事务跨服务/系统?
                         ┌───┴──────────┐
                         否              是
                         │               │
                         本地事务         │
                                         │
                              强一致是否必要?
                              ┌─────┴───────┐
                              是              否
                              │               │
                              │              最终一致 + Saga
                              │              ┌────┴─────┐
                              │              业务流程稳定?
                              │              ┌──┴──┐
                              │              是    否
                              │              │     │
                              │            编排  编舞
                              │
                       一致窗口 < 1 秒?
                       ┌─────┴──────┐
                       是             否
                       │              │
                       TCC            Saga (短) / TCC + Saga 混合
                                      ┌─────┴─────┐
                                      参与方都自家?
                                      ┌──┴──┐
                                      是    否
                                      │     │
                                  跨异构    跨第三方
                                  TCC      Saga (无法 TCC 化)
```

简化决策：

| 业务特征 | 选择 |
|---|---|
| 单服务内 | 本地事务 |
| 跨服务 + 短流程 + 金融级一致 | TCC |
| 跨服务 + 长流程 + 最终一致 | Saga（编排） |
| 事件驱动、订阅方动态 | Saga（编舞） |
| 任何跨服务发布事件 | **必须 Outbox** |
| 任何跨服务消费事件 | **必须 Inbox / 业务幂等** |
| 老系统遗留 + 同库 | 可以 2PC（最后选择） |

## 第十章：反模式与陷阱

### 10.1 反模式 1：Dual Write

```go
// 错误
db.Commit()
producer.Send(...)
```

修复：Outbox 模式。

### 10.2 反模式 2：Saga 不持久化中间状态

崩溃后不知道走到哪了 → 业务"卡住"或"重复执行"。

修复：每步状态 + saga_steps 表持久化。

### 10.3 反模式 3：补偿假设"反向操作总能成功"

如果 refund 调外部支付网关失败了呢？

修复：补偿要重试到成功，N 次失败转人工。

### 10.4 反模式 4：用 Saga 替代所有事务

简单单服务事务用 Saga → 复杂度爆炸。

修复：单服务内用本地事务。

### 10.5 反模式 5：消费者不去重

Outbox 保证发布零丢失，但消费方可能重复消费同一事件。

修复：Inbox + 业务唯一约束。

### 10.6 反模式 6：编排器变成"分布式单体"

编排器知道所有业务逻辑、所有服务 API、所有错误处理 → 改一个服务要改编排器 → 强耦合。

修复：编排器只管"流程编排"，业务逻辑在各服务；用事件驱动减少 RPC 调用。

### 10.7 反模式 7：Outbox 不分区/不清理

百亿条历史事件堆在一张表 → 索引爆炸 → 发布慢。

修复：分区表 + 自动清理 + 监控表大小。

### 10.8 反模式 8："最终一致"无窗口监控

没有对账机制 → 不一致永久存在但无人发现。

修复：定时对账 + 差异告警。

### 10.9 反模式 9：跨多个 DB 用本地事务（自欺欺人）

```go
tx1, _ := db1.Begin()
tx2, _ := db2.Begin()
tx1.Exec(...)
tx2.Exec(...)
tx1.Commit()   // 成功
tx2.Commit()   // 失败 → 不一致
```

修复：要么 2PC，要么改成 Saga + Outbox。

### 10.10 反模式 10：Saga 步骤之间共享内存状态

```go
var pendingOrders = map[string]*Order{}   // 进程内状态
// orchestrator 崩溃 → 状态全丢
```

修复：状态机必须在 DB 持久化，每次重启从 DB 恢复。

## 陷阱清单

1. **2PC 在异构系统不可行**：Kafka / Redis / 外部 API 不支持 XA。
2. **TCC 忘记空回滚 / 防悬挂**：Cancel 在 Try 之前到达 → 业务错乱。
3. **Saga 补偿不幂等**：编排器重试 → 多次退款。
4. **补偿失败无兜底**：refund 调网关失败后不再重试 → 钱永久卡住。
5. **Outbox 表和业务表不在同库**：失去原子性。
6. **Outbox 用 thin payload + 回查**：回查时数据已变。
7. **Inbox 不和业务在同一事务**：先 insert inbox 再业务 → 业务失败但 inbox 已写 → 永久跳过该事件。
8. **状态机分支没覆盖完**：某条边界路径走向"未知状态"，Saga 卡死。
9. **编排器单点**：用 K8s StatefulSet + 持久化状态 + leader election。
10. **不可补偿的步骤放在中间**：发邮件后失败 → 邮件已发，订单未成。
11. **多 Saga 并发同一业务实体**：用户重复点击下单 → 两个 Saga 同时扣库存。要在 Saga 启动前用幂等 key 拦截。
12. **跨服务用本地事务自欺欺人**：不是事务，只是顺序执行。
13. **CDC 慢 → outbox 堆积**：DB 磁盘满 → 业务写入卡。要监控 Outbox lag。
14. **Saga 状态机版本升级不兼容**：老 Saga 跑到新代码上找不到状态。需要 saga_version 字段 + 兼容老版本。
15. **业务"最终一致窗口"无对账**：不一致永久存在。
16. **TCC 与 Saga 混用没想清楚边界**：金融分支用 TCC，长流程外层用 Saga 包，注意接口契约一致。
17. **Outbox 表不索引 unpublished**：全表扫描，DB 拖垮。
18. **Saga 补偿动作改变了正向数据**：导致幂等检查失败、二次重试出错。

## 参考答案

1. **2PC**
   - 五条死亡原因（按严重度）：① 跨异构系统不可行——Kafka/Redis/MongoDB/外部 SaaS 几乎都不支持 XA，微服务架构天然异构，这是根本性硬伤；② 阻塞 + 长锁——prepare 到 commit 之间参与者必须锁住资源数百毫秒到数秒，OLTP 系统 QPS 跌 10-20 倍；③ 协调器单点——Phase 1 后协调器崩溃则所有参与者永久阻塞，HA 化又使复杂度与性能进一步恶化；④ 网络分区导致不一致——prepare 超时协调器 abort 但参与者实际成功；⑤ 性能——数倍 round-trip + 写日志 + 锁等待，延迟是单机 5-20 倍。
   - **Oracle RAC + XA 可保留**：RAC 是同一数据库的多实例跨节点事务，由 DBMS 自身处理，属于 2PC 仍合理的场景（同库分布式、强监管金融、参与者全 XA 兼容、延迟可忍受）。迁移到 Saga 的代价：需为每个本地事务设计补偿动作、引入编排器/事件总线、放弃数据库级强一致改为业务级最终一致并接受中间状态可见、新增 Outbox/Inbox 与对账系统、改造所有调用方处理"处理中"状态——代价高且引入新的一致性窗口风险，若现状性能可接受不建议为迁移而迁移。

2. **TCC**
   - **A→B 转账 TCC**：Try——A 账户冻结金额（`balance -= X, frozen += X`，余额不足则失败），B 账户预入账（可记 pending）；写 `tcc_transactions(tx_id, branch, state='TRYING')`。Confirm——A 解冻并真实扣减（`frozen -= X`），B 真实入账（`balance += X`），用 `SELECT ... FOR UPDATE` 检查状态做幂等，已 CONFIRMED/CANCELED 直接返回。Cancel——A 回滚冻结（`frozen -= X, balance += X`），B 撤销预入账。空回滚——Cancel 时若无 Try 记录（`sql.ErrNoRows`）直接跳过；防悬挂——Cancel 写"已取消"标记，迟到的 Try 看到标记直接拒绝；幂等——Confirm/Cancel 均以 tx_id + branch 作幂等 key、靠状态判断。
   - **跨 Stripe 不可用原因**：TCC 要求每个参与者实现 Try/Confirm/Cancel 三段式业务接口（资源预留 + 确认 + 取消），但第三方 SaaS 如 Stripe 不提供"预冻结/可逆预留"的 API，无法把支付改造成可回滚的 Try。混合方案——内部参与者（账户、库存）用 TCC 保证业务级强一致，外部 Stripe 调用包在外层 Saga 里作为不可补偿步骤后置，失败时对内部 TCC 分支执行补偿（refund 用语义补偿即发起退款而非撤销），即"TCC 内部 + Saga 外部"。

3. **Saga 编排 vs 编舞**
   - **编排式**：OrderSaga 编排器用状态机依次 RPC/命令调 Payment.charge → Inventory.reserve → Shipping.create，每步成功推进状态（CREATED→PAID→RESERVED→SHIPPED），失败则按逆序触发补偿（如 Shipping 失败 → releaseReserve + refund → COMPENSATED）。**编舞式**：OrderSvc 发 `OrderPlaced` → PaymentSvc 订阅扣款发 `PaymentSucceeded` → InventorySvc 订阅扣库存发 `InventoryReserved` → ShippingSvc 订阅建运单；失败路径靠订阅"失败事件"触发补偿（如 `InventoryReserveFailed` → PaymentSvc 退款发 `PaymentRefunded`）。
   - 三个评估维度：① 流程可见性/可调试性（编排高、编舞低，需链路追踪还原）；② 加新参与者的耦合（编排要改编排器、编舞只需新增订阅）；③ 单点风险（编排器需 HA、编舞无中心）。选择：流程稳定、参与方多、需可视化可干预的核心业务用编排；流程灵活、订阅方动态、追求最低耦合用编舞；大流程编排 + 细枝末节编舞混合。

4. **Outbox**
   - **Dual Write**：在一个本地事务外先 commit DB 再发消息（或反之），两步不在同一事务无法原子保证——DB 成功消息失败则下游永久缺事件，消息成功 DB 失败则下游收到幽灵事件。Outbox 解法：把业务 UPDATE 和 `INSERT INTO outbox(...)` 放进**同一本地事务**，原子保证"业务变更 + 事件记录同生死"，再由独立 Publisher 异步把 outbox 搬到消息总线。
   - **对比**：Polling Publisher 应用层全控、不依赖 DB 复制能力、简单，但有轮询延迟（100ms~1s）、大表查询慢、多实例需 `FOR UPDATE SKIP LOCKED`；Debezium CDC 近实时（毫秒级）、应用无需 publisher 逻辑、高可靠，但多了 Debezium/Kafka Connect 运维且要求 DB 支持逻辑复制。新项目选 Debezium + CDC（2026 推荐默认），已非常成熟且配合 Outbox Event Router SMT 可零代码路由。

5. **Inbox + 端到端幂等**
   - **三服务事件链**：A（业务表 + outbox，同一事务）→ Debezium → Kafka → B（inbox 去重 + 业务表 + 自身 outbox，同一事务）→ Debezium → Kafka → C（inbox + 业务表）。每个服务在同一本地事务里：先 `INSERT INTO inbox(event_id...)`（唯一约束冲突即幂等跳过）→ 业务处理 → 写自己的 outbox。
   - **Kafka EOS 不能替代**：EOS 作用域仅限 Kafka 内部（producer 幂等 + 事务，Kafka→Kafka），一旦消费后写入业务 DB 就跨出了 Kafka 事务边界；而 Outbox 解决"业务写库与事件发布的原子性"（防 Dual Write），Inbox 解决"消费写库的去重幂等"，二者覆盖的是 Kafka 管不到的应用-DB 边界。Outbox + Inbox 组合才是端到端 exactly-once 的工程实现。

6. **完整案例**（要点）
   - 状态机表 `order_saga`（saga_id/order_id UNIQUE/state/context...）+ `order_saga_steps`（每步 PENDING/SUCCESS/FAILED/COMPENSATED）持久化。状态机 CREATED→PAID→RESERVED→SHIPPED→AWARDED→DONE，失败走 COMPENSATING_INVENTORY→COMPENSATING_PAYMENT→CANCELED。5 step 伪代码：charge→reserve→createShipping→awardLoyalty(best effort)→notify(best effort)。三种失败补偿：支付失败→FAILED 直接结束；库存失败→补偿 refund；物流失败→补偿 releaseReserve + refund。补偿用 saga_id 幂等、重试到成功转人工，不可补偿步骤（积分/通知）后置。监控：saga_completed_total{state}、saga_step_failure_total、compensation_failure_total、saga_duration_seconds。
   - **秒杀优化**：库存预扣到 Redis（lua 原子扣减）削峰、下单异步化只写 outbox 不同步 RPC；支付/物流/积分/通知全异步由编排器后续驱动；积分、通知做懒触发（best effort、可延迟）；用熔断在上游失败率超阈值时暂停新订单；Saga 不锁物理库存用 reserved_qty 软锁；用幂等 key 拦截用户重复点击避免并发多 Saga 扣同一库存。

7. **运维**
   - **Outbox 5TB + lag 30s 根因**：① 未分区/未清理导致表与索引膨胀全表扫描慢；② Debezium connector 故障或重启、replication slot 落后；③ Kafka 写入瓶颈/broker 慢使发布吞吐跟不上写入；④ 业务写入激增超过发布速率；⑤ 缺 unpublished 索引导致 Polling 全表扫描；⑥ DB 主从复制延迟或磁盘 IO 饱和。排查：查 Debezium lag/失败率与 replication slot 滞后、看 outbox 表大小与索引、对比 outbox 写入速率 vs 发布速率、检查 Kafka 端到端延迟、确认分区与清理任务是否运行。
   - **编排器不启动新 Saga 诊断角度**：① 编排器进程崩溃/未拉起（K8s pod 状态）；② leader election 卡住无 leader；③ 状态持久化 DB 不可达或连接池耗尽；④ 入口事件/命令未到达（上游 Kafka topic、消费 lag）；⑤ Saga 状态机版本升级不兼容老状态卡死；⑥ 编排器消费者 rebalance 风暴；⑦ 幂等拦截误判把新 Saga 当重复跳过；⑧ 下游全部熔断触发"暂停新订单"保护逻辑。

8. **决策**
   - a) 改头像 + CDN：跨服务最终一致可接受 → Saga（编舞）/ 简单事件驱动 + Outbox，UI 显示"处理中"。
   - b) 银行内部转账（强一致 + 异构 DB）：业务级强一致、一致窗口 < 1 秒、参与方都自家 → TCC（账户冻结/确认/取消）。
   - c) 跨境支付（多个第三方 SaaS）：参与方含无法 TCC 化的第三方 → Saga（无法 TCC，用语义补偿如退款），不可补偿步骤后置。
   - d) 内部审批工作流（多 step 长流程）：流程稳定、step 多、需可视化可干预 → 编排式 Saga（Temporal/Camunda）。
   - e) IoT 设备状态上报 + 聚合（最终一致 OK）：弱业务流程、事件广播为主 → Saga（编舞）/ 事件驱动，按时间戳最后写入策略聚合。
