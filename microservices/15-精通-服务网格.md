## 引言：从应用层看 Service Mesh 到底解决什么

云原生章节的 C10 是从"基础设施层"讲网格：怎么部署 Istio、怎么调 Envoy 配置、怎么和 K8s 网络栈打通。

这一章是 **应用层视角**——你是写业务代码的工程师 / 架构师 / Tech Lead，要决定：

- 我的 100 个微服务，该不该上 Mesh？
- 上了之后，业务代码要不要改？
- 治理逻辑（mTLS / 重试 / 限流 / 灰度）从 SDK 搬到 Mesh，怎么搬？
- Sidecar 还是 Ambient？eBPF（Cilium）值不值？
- 不上 Mesh 的话，还有什么选择？

**Service Mesh 在一句话里**：把跨进程通信的治理（mTLS / 重试 / 限流 / 可观测 / 灰度）从业务进程下沉到独立的"网格层"，让应用专心写业务。

```
   传统模式（SDK 模式）:
   ┌────────────────────────────────────┐
   │   业务进程                          │
   │   ├─ 业务代码                        │
   │   ├─ Resilience4j（熔断重试）        │
   │   ├─ Sentinel（限流）                │
   │   ├─ Micrometer（指标）              │
   │   ├─ OpenTelemetry SDK（链路）       │
   │   ├─ mTLS 证书加载逻辑                │
   │   └─ ... 这些都要随语言版本升级       │
   └────────────────────────────────────┘

   Service Mesh 模式:
   ┌────────────────────────────────────┐
   │   业务进程（只剩业务代码）           │
   └─────────────┬──────────────────────┘
                 │ 透明拦截
   ┌─────────────▼──────────────────────┐
   │   网格数据面（Envoy / ztunnel / eBPF）│
   │   ├─ mTLS 自动协商                   │
   │   ├─ 重试 / 超时 / 熔断              │
   │   ├─ 限流                            │
   │   ├─ 指标 + 链路自动注入             │
   │   └─ 流量切分（灰度）                │
   └────────────────────────────────────┘
                 ↑
   ┌─────────────┴──────────────────────┐
   │   网格控制面（Istiod / Cilium）       │
   │   监听 K8s CRD，下发配置              │
   └────────────────────────────────────┘
```

## 第一章：数据面 vs 控制面——网格的二分法

每个 Service Mesh 都由两层组成：

```
┌─────────────────────────────────────────────────┐
│   Control Plane (控制面)                          │
│   - 监听 K8s CRD（VirtualService、Gateway 等）    │
│   - 计算每个数据面节点的配置                       │
│   - 下发配置（xDS / 自有协议）                    │
│   代表：Istiod / Linkerd Control Plane / Cilium  │
└─────────────────────────┬───────────────────────┘
                          │ xDS over gRPC
                          │
┌─────────────────────────▼───────────────────────┐
│   Data Plane (数据面)                             │
│   - 实际转发流量                                  │
│   - 实施 mTLS / 重试 / 限流                       │
│   - 暴露 metrics                                  │
│   代表：Envoy / linkerd2-proxy / ztunnel / Cilium│
└─────────────────────────────────────────────────┘
```

**为什么要分层**：

- 控制面**集中决策**——一处改、全网生效
- 数据面**分布式执行**——每个节点本地决定流量去哪
- 哪怕控制面挂了，数据面用上次的配置**继续工作几小时**

这就是为什么 mesh 升级时数据面不会瞬间瘫——配置已经本地缓存，控制面短暂不可用没事。

### 1.1 xDS 协议

Envoy 和 Istio 之间用 **xDS** 协议同步配置：

```
LDS  Listener Discovery Service     监听器（"我要监听哪些端口"）
RDS  Route Discovery Service        路由规则（"path /a → 后端 A"）
CDS  Cluster Discovery Service      集群（"后端 A 是哪些 IP"）
EDS  Endpoint Discovery Service     端点（具体 IP/端口）
SDS  Secret Discovery Service       证书
```

实际通信是 ADS（Aggregated Discovery Service）——把 5 个流合一，避免顺序问题。

xDS 是 CNCF 标准，**任何代理只要实现 xDS 就能被 Istiod 控制**。Cilium 的 L7 代理也用 xDS。

### 1.2 控制面性能瓶颈

```
1000 个服务 × 10 实例 = 10000 个数据面节点
  每次配置变更，控制面要给 10000 个节点推送

如果不优化：
  控制面 CPU 爆炸、节点同步慢

实际优化（Istio 1.20+）：
  - 增量 xDS（只推变化）
  - sidecar resource（限定 sidecar 只关心一部分服务）
  - 调度延迟（合并连续变更）
```

**关键事实**：Istiod 单实例上限大约是 **3-5k 节点**。超过这个数要么拆控制面，要么减少 sidecar 数量（Ambient 是好答案）。

## 第二章：Sidecar 模式——经典 Istio 的代价

### 2.1 Sidecar 拦截原理

经典 Istio：

```
Pod 内部：
  ┌──────────────────────────────────┐
  │  Container A (业务)               │
  │    ↓ syscall                      │
  │  127.0.0.1:9080 →                 │
  ├──────────────────────────────────┤
  │  iptables NAT (istio-init 改的)   │
  │  REDIRECT to 15001（出站）        │
  │  REDIRECT to 15006（入站）        │
  ├──────────────────────────────────┤
  │  istio-proxy (Envoy sidecar)     │
  │  做：mTLS / 路由 / 重试 / 指标    │
  │    ↓                              │
  │  eth0 (Pod 网络)                  │
  └──────────────────────────────────┘
```

业务代码**完全无感**——它以为自己直连了目标，实际所有出入流量都过 sidecar。

### 2.2 Sidecar 的好处

- **零代码改造**：业务不感知 mTLS
- **跨语言一致**：Go / Java / Python 同一套治理
- **强大功能**：Envoy 是工业级 L7 代理
- **故障隔离**：sidecar 挂只影响一个 Pod

### 2.3 Sidecar 的代价（Ambient 出现的根本原因）

| 代价 | 典型数字 | 解释 |
|---|---|---|
| **资源开销** | 每 Pod +100MB 内存 +0.1-0.5 CPU | 1000 Pod = 100GB 内存 |
| **冷启动延迟** | Pod 启动多 1-3s | 弹性扩容、灰度时累加 |
| **数据路径** | 每跳 +2 hop | +0.5-2ms 延迟 |
| **运维复杂** | 注入失败、版本错位、容器顺序 | SRE 持续维护 |
| **升级困难** | 升级 Istio 要重启所有 Pod | 业务窗口 |

### 2.4 Sidecar 启动顺序坑

K8s 1.33 之前的经典问题：

```yaml
# 应用容器启动时 sidecar 还没就绪 → 应用调外部 API 失败
# 应用容器先退出但 sidecar 还在 → Pod 永远不 terminate
```

**K8s 1.28 alpha → 1.29 beta → 1.33 GA 的 Sidecar Container**（`restartPolicy: Always` 的 initContainer）解决了这个问题：

```yaml
spec:
  initContainers:
  - name: istio-proxy
    restartPolicy: Always   # 1.33 GA：让 init 容器变成"sidecar"
```

Istio 1.20+ 支持 native sidecar；Istio 1.27+ 默认启用。但**升级前的存量集群仍要小心**，这也是 Ambient 模式彻底绕开这层坑的原因。

### 2.5 应用层视角的开发体验

业务代码改动**理论上为零**。实际上有几个常见坑：

1. **健康检查端点**：sidecar 注入后，K8s livenessProbe 经 sidecar，业务必须实现就绪和探活，且确保 sidecar 就绪后才接流量
2. **直连 IP 不行**：sidecar 拦截基于 K8s Service。如果你的代码直接连 Pod IP，Mesh 没法治理
3. **跨语言客户端**：业务不要再用 Resilience4j / Sentinel 这种 SDK 做熔断重试，让 mesh 做（避免双层重试导致雪崩）

## 第三章：Istio Ambient Mesh——2024-11 GA 的革命

### 3.1 为什么需要 Ambient

Ambient 设计目标一句话总结：

> **L4 mTLS 和 L7 治理拆开——大多数服务只需要 L4，按需上 L7。**

经典 Sidecar 的问题在于 **"全有全无"**——一旦注入 sidecar，所有流量都过 Envoy，哪怕你只想要 mTLS。Ambient 把这层撕开：

```
经典 Sidecar：              Ambient：
  每 Pod 一个 Envoy          每 Node 一个 ztunnel (L4)
  (重)                       按需 waypoint (L7)
                             (按需 + 轻)
```

### 3.2 ztunnel + waypoint 双层架构

```
     Node 1                              Node 2
  ┌─────────────────────┐           ┌─────────────────────┐
  │  App Pod 1 (无 sidecar) ─┐       │  App Pod 3 (无 sidecar)│
  │  App Pod 2 (无 sidecar) ─┤       │                       │
  │                      │   │       │                       │
  │  ztunnel (DaemonSet) ┼   │       │  ztunnel (DaemonSet)  │
  │   - L4 mTLS          │   │       │   - L4 mTLS           │
  │   - HBONE 隧道       └───┼───────┼─→                     │
  └─────────────────────┘   │       └─────────────────────┘
                             │
                  按需 L7 ↓ │
                             ▼
                  ┌─────────────────────┐
                  │  waypoint Pod        │  ← 按 namespace / 按服务部署
                  │  (Envoy)             │
                  │  - 重试 / 限流 / L7  │
                  └─────────────────────┘
```

**ztunnel**：

- Rust 写的轻量 L4 代理，DaemonSet（每节点一个）
- 只做 mTLS + L4 路由（不解析 HTTP）
- 用 **HBONE 协议**（HTTP/2 CONNECT 隧道）传输 mTLS 流量
- 资源开销极低（典型 < 50MB / 节点）

**waypoint**：

- 标准 Envoy，但部署模式不同——按命名空间或按服务部署
- 只有需要 L7 治理（重试、超时、HTTPRoute、AuthorizationPolicy on L7）时才走 waypoint
- 普通 mTLS 流量直接 ztunnel → ztunnel，不经过 waypoint

### 3.3 HBONE 协议

HBONE = HTTP-Based Overlay Network Encapsulation。

```
  原始 mTLS 流量需要的能力：
  - 加密（mTLS）
  - 携带客户端身份（SPIFFE ID）
  - 多路复用（多业务共享一个隧道）

  HBONE 做法：
  - 用 HTTP/2 CONNECT 建隧道
  - 隧道头携带 SPIFFE ID
  - HTTP/2 stream 天然多路复用
```

为什么用 HTTP/2 而不是原始 TCP？

- 多路复用（一条 TCP 连接承载多个业务流）
- 标准协议，易调试
- 防火墙友好（看起来就是普通 HTTPS）

### 3.4 启用 Ambient

```bash
# 安装 Ambient
istioctl install --set profile=ambient --skip-confirmation

# 给一个 namespace 启用 Ambient
kubectl label namespace prod istio.io/dataplane-mode=ambient

# 验证：Pod 没有 sidecar，但流量自动走 ztunnel
kubectl get pods -n prod
# NAME      READY   STATUS
# myapp-x   1/1     Running     ← 1/1，不是 2/2
```

加 namespace label 后**已运行的 Pod 不需要重启**——ztunnel 通过节点级流量重定向接管。这是 Ambient 相对 Sidecar 的运维优势之一。

### 3.5 按需启用 L7（waypoint）

```bash
# 给 namespace 部署一个 waypoint
istioctl waypoint apply --namespace prod --enroll-namespace
```

部署后：

```
某 prod 服务请求 → ztunnel → waypoint（Envoy）→ 目标 ztunnel → 目标 Pod
```

如果你只想给某个特定服务做 L7：

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: order-svc-waypoint
  namespace: prod
spec:
  gatewayClassName: istio-waypoint
  listeners:
  - name: mesh
    port: 15008
    protocol: HBONE
```

### 3.6 Ambient 的代价与适用场景

Ambient 不是完美的：

| 维度 | Sidecar | Ambient |
|---|---|---|
| 资源 | 每 Pod 100MB | 每 Node 50MB（DaemonSet） |
| 故障隔离 | 强（Pod 内） | 弱（node 级，影响该 node 全部 Pod） |
| 功能完整度 | 强（满血 Envoy） | L4 时简单；L7 还是 Envoy |
| 升级 | 重启所有 Pod | 升级 ztunnel DaemonSet 即可 |
| 生态成熟度 | 极成熟 | 2024-11 GA，仍在演进 |
| 多租户隔离 | 强（Pod 边界） | ztunnel 在 node 上共享 |

**Ambient 适合**：

- 中大型集群（1000+ Pod，sidecar 资源不划算）
- 大量服务只需要 mTLS、不需要 L7 治理
- 想降低运维负担

**仍选 Sidecar 的场景**：

- 需要满血 Envoy 功能
- 多租户强隔离场景
- 已经在生产稳定跑 sidecar，没动力换

## 第四章：Linkerd——Rust 写的轻量 Sidecar

### 4.1 Linkerd 的差异化定位

Linkerd 2.x 是用 **Rust** 写的 sidecar：

| 维度 | Istio (Envoy) | Linkerd (linkerd2-proxy) |
|---|---|---|
| 数据面语言 | C++ | Rust |
| 性能 | 强 | 略快（Rust 零成本抽象） |
| 内存 | 每 Pod ~100MB | 每 Pod ~20-40MB |
| 功能丰富度 | 极丰富 | 精选（够用就好） |
| 学习曲线 | 陡峭 | 平缓 |
| 中文社区 | 大 | 小 |

Linkerd 的产品哲学：**"不是把所有功能都给你，而是把核心做到极致简单"**。

### 4.2 Linkerd 适合谁

- **中小团队**：不需要 Envoy 的全部高级功能
- **追求简单**：Linkerd 几乎"装上就工作"
- **资源敏感**：sidecar 内存只有 Istio 的 1/3
- **不在意中文生态**

### 4.3 Linkerd 的 sidecar-less 路线

Linkerd 团队对 Ambient 路线保持观望，他们的回答是：**Linkerd 的 sidecar 已经够轻，不需要彻底干掉**。但社区已经开始讨论是否引入类似 ztunnel 的 node-level 代理。

## 第五章：Cilium Service Mesh——eBPF 替代 Sidecar

### 5.1 eBPF 是什么

eBPF（extended Berkeley Packet Filter）允许在 **Linux 内核态**运行受限的程序，不需要修改内核源码。

```
   传统数据面（Envoy sidecar）:
   网络包 → 网卡 → 内核 → 用户态（Envoy）→ 内核 → 业务 socket
                     ↓ 多次 user/kernel 切换、复制 ↑

   eBPF 数据面:
   网络包 → 网卡 → 内核（eBPF 程序直接处理） → 业务 socket
                     ↓ 零拷贝、零上下文切换
```

### 5.2 Cilium Service Mesh 架构

```
┌─────────────────────────────────────────────────┐
│   Node                                            │
│                                                   │
│   App Pod 1   App Pod 2   App Pod 3              │
│      │           │           │                    │
│      ▼           ▼           ▼                    │
│   ┌───────────────────────────────────────────┐  │
│   │ Cilium eBPF programs                      │  │
│   │ - 网络策略                                │  │
│   │ - L4 负载均衡                             │  │
│   │ - mTLS (kTLS) - 部分实验                  │  │
│   └───────────────┬───────────────────────────┘  │
│                   │                                │
│   ┌───────────────▼───────────────────────────┐  │
│   │ Cilium Envoy (per-Node, 按需 L7)          │  │
│   │ - L7 路由 / HTTPRoute                    │  │
│   └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

### 5.3 Cilium 的优势

- **零 sidecar 资源开销**（L4 全靠 eBPF 内核态做）
- **低延迟**（少了用户态切换）
- **L7 仍用 Envoy**，但 per-Node 不是 per-Pod
- **同一套技术栈做 CNI + NetworkPolicy + Mesh + Observability**

### 5.4 Cilium 的代价

- **需要较新内核**（5.10+）
- **mTLS 仍部分依赖用户态 Envoy**（纯 eBPF mTLS 还在试验）
- **L7 功能不如 Istio 完整**
- **生态较 Istio 小**

### 5.5 Cilium 适合谁

- 已经用 Cilium 做 CNI 的集群（顺势升 Mesh）
- 性能敏感场景（金融交易、低延迟）
- 中等规模集群

## 第六章：Consul Connect

HashiCorp 的 Mesh 方案，定位是**多云、与 Vault 强集成**。

```
   Consul Server (3 节点 Raft 集群)
        │
        ├─ Consul Connect 控制面

        ▼
```

- HashiCorp 全家桶（Consul / Vault / Terraform / Nomad）

## 第七章：mTLS 自动注入——零信任的基石

### 7.1 为什么 mTLS 必须

零信任原则：**网络不可信，每次通信都要验证身份**。

```
传统：
  内网默认信任 → 拿到 IP 就能调任何服务
        ↓
  一个 Pod 被攻陷 → 横向移动整个集群

零信任 + mTLS：
  每次通信双向身份验证
        ↓
  一个 Pod 被攻陷 → 它能调的只是它本来就有权限调的
```

但**手动管 mTLS** 痛苦：

- 100 个服务要 100 张证书
- 证书 30 天过期要轮转
- 私钥分发到每个 Pod
- 证书撤销

Mesh 自动解决了这些。

### 7.2 Istio 的自动 mTLS 流程

```
1. Pod 启动
2. istio-agent 向 Citadel/Istiod 请求证书
   - 凭证：K8s ServiceAccount JWT
3. Istiod 验证 JWT → 给出 SPIFFE 身份证书
   - SPIFFE ID: spiffe://cluster.local/ns/prod/sa/order-svc
4. 证书写入 sidecar 内存（SDS 协议）
5. Pod 之间通信时，sidecar 自动完成 mTLS 握手
6. 证书每 24h 自动轮转
```

业务**零感知**。

### 7.3 SPIFFE：跨 Mesh 身份标准

SPIFFE（Secure Production Identity Framework For Everyone）是 CNCF 项目，定义了**服务身份的统一标准**：

```
SPIFFE ID 格式：
  spiffe://<trust-domain>/<workload-identifier>

示例：
  spiffe://acme.com/ns/prod/sa/order-svc

  acme.com         信任域（公司）
  ns/prod          namespace
  sa/order-svc     ServiceAccount
```

每个 Mesh 实现（Istio、Linkerd、Consul）都把这个 SPIFFE ID 写到 X.509 证书的 SAN URI 里。

**SPIRE** 是 SPIFFE 的参考实现，可以独立部署给非 Mesh 应用用。Istio 1.14+ 可与 SPIRE 集成做联邦身份。

### 7.4 mTLS 模式

Istio 提供三种 mTLS 模式：

```yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: prod
spec:
  mtls:
    mode: STRICT      # 只接受 mTLS（拒绝明文）
    # mode: PERMISSIVE  # 同时接受 mTLS 和明文（迁移期）
    # mode: DISABLE     # 关闭 mTLS
```

迁移路径：

```
Phase 1: DISABLE     现状
Phase 2: PERMISSIVE  新流量走 mTLS，老的不强制
Phase 3: STRICT      只接受 mTLS
```

不要直接从 DISABLE 跳 STRICT——会瞬间断流量。

### 7.5 授权策略（AuthorizationPolicy）

mTLS 只解决"谁在调用"，授权解决"它能调用什么"。

```yaml
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: order-svc-allow-frontend
  namespace: prod
spec:
  selector:
    matchLabels:
      app: order-svc
  rules:
  - from:
    - source:
        principals:
        - "cluster.local/ns/prod/sa/frontend-bff"
        - "cluster.local/ns/prod/sa/admin-portal"
    to:
    - operation:
        methods: ["GET", "POST"]
        paths: ["/api/v1/orders/*"]
```

这条规则的语义：**只有 frontend-bff 和 admin-portal 这两个服务账号可以调用 order-svc 的 `/api/v1/orders/*`**。即使其他 Pod 拿到了网络可达性，没有正确身份照样被拒。

## 第八章：流量治理——VirtualService 与 DestinationRule

### 8.1 经典 Istio 配置三件套

```
Gateway          流量入口（南北流量）
   ↓
VirtualService   路由规则（把请求分发到哪个版本/子集）
   ↓
DestinationRule  目的地策略（连接池、熔断、子集定义）
```

### 8.2 流量切分（灰度发布）

```yaml
# 把 95% 流量给 v1，5% 给 v2
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: order-svc
spec:
  hosts:
  - order-svc
  http:
  - route:
    - destination:
        host: order-svc
        subset: v1
      weight: 95
    - destination:
        host: order-svc
        subset: v2
      weight: 5
---
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: order-svc
spec:
  host: order-svc
  subsets:
  - name: v1
    labels:
      version: v1
  - name: v2
    labels:
      version: v2
```

### 8.3 基于 header 的路由（A/B / 内部灰度）

```yaml
spec:
  http:
  - match:
    - headers:
        x-canary-user:
          exact: "true"
    route:
    - destination:
        host: order-svc
        subset: v2
  - route:
    - destination:
        host: order-svc
        subset: v1
```

公司内部测试加 header `x-canary-user: true` 就走新版本，普通用户走老版本。

### 8.4 故障注入（混沌工程）

```yaml
spec:
  http:
  - fault:
      delay:
        percentage:
          value: 10
        fixedDelay: 5s
      abort:
        percentage:
          value: 1
        httpStatus: 503
    route:
    - destination:
        host: order-svc
```

10% 请求加 5s 延迟、1% 请求返回 503。用于演练下游对延迟和错误的韧性。

### 8.5 重试和超时

```yaml
spec:
  http:
  - route:
    - destination:
        host: order-svc
    timeout: 2s
    retries:
      attempts: 3
      perTryTimeout: 500ms
      retryOn: 5xx,reset,connect-failure
```

**关键**：mesh 做重试时，业务代码就**不要**再做重试，否则会指数放大（业务重试 3 次 × mesh 重试 3 次 = 9 次）。

### 8.6 熔断（OutlierDetection + ConnectionPool）

```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: order-svc
spec:
  host: order-svc
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 100
      http:
        http1MaxPendingRequests: 50
        maxRequestsPerConnection: 10
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 30s
      baseEjectionTime: 30s
      maxEjectionPercent: 50
```

效果：

- 单个上游实例连续 5 次 5xx → 从负载均衡池移除 30s
- 最多移除 50% 实例（避免全打挂）

## 第九章：与 Gateway API 整合——南北 + 东西流量统一

### 9.1 Gateway API 是什么

Gateway API（v1.0 GA 2023-10，v1.1 2024-05）是 K8s 官方下一代流量入口标准，**取代 Ingress**。

```
   Ingress (老):                Gateway API (新):
   - 角色不分                    - GatewayClass（基础设施）
   - 注解魔法                    - Gateway（流量入口）
   - 厂商各家方言                - HTTPRoute / TCPRoute（路由）
                                  - 角色分明、跨厂商
```

### 9.2 Mesh + Gateway API 一统江湖

Istio 1.24 起，Gateway API 既管南北流量（外部 → 集群）也管东西流量（集群内）：

```yaml
# 南北：外部 → Gateway → order-svc
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: ext-gw
spec:
  gatewayClassName: istio
  listeners:
  - name: https
    port: 443
    protocol: HTTPS
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: order-route
spec:
  parentRefs:
  - name: ext-gw
  hostnames: ["api.example.com"]
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /orders
    backendRefs:
    - name: order-svc
      port: 80
```

```yaml
# 东西：在 mesh 内做服务间路由
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: order-svc-mesh
spec:
  parentRefs:
  - kind: Service
    name: order-svc       # 直接挂在服务上（mesh 内）
  rules:
  - matches:
    - headers:
      - name: x-canary
        value: "true"
    backendRefs:
    - name: order-svc-v2
  - backendRefs:
    - name: order-svc-v1
```

### 9.3 VirtualService 还是 HTTPRoute

**2026 年方向**：HTTPRoute 取代 VirtualService。新项目优先 Gateway API。

- VirtualService 是 Istio 私有 CRD，只 Istio 能解析
- HTTPRoute 是社区标准，Istio / Linkerd / Cilium / Envoy Gateway 都支持

## 第十章：多集群 Mesh——3 种拓扑

### 10.1 为什么要多集群 Mesh

- **跨地域容灾**：上海挂了，自动切北京
- **跨云**：AWS + GCP 混合部署
- **业务隔离**：不同业务线不同集群，但跨集群服务调用

### 10.2 三种拓扑

#### A：单控制面，多数据面（Single Primary）

```
                ┌────────────────┐
                │  Istiod (主集群) │
                └────┬───────┬───┘
                     │       │
        ┌────────────▼─┐  ┌──▼────────────┐
        │ Cluster A    │  │ Cluster B      │
        │ (远程数据面) │  │ (远程数据面)   │
        └──────────────┘  └────────────────┘
```

- 优点：控制面集中，配置一致
- 缺点：主集群挂全网瘫

#### B：多控制面（Multi-Primary）

```
   ┌──────────────┐         ┌──────────────┐
   │ Cluster A    │ ←─sync─→│ Cluster B    │
   │ Istiod + 数据│         │ Istiod + 数据│
   └──────────────┘         └──────────────┘
```

- 每个集群独立控制面，通过 ServiceEntry 或东西网关跨集群
- 优点：故障域隔离
- 缺点：配置同步复杂

#### C：External Control Plane（外部控制面）

```
   ┌──────────────────────┐
   │ Istiod （独立部署）   │  ← 不在任何业务集群
   └─────┬──────────┬─────┘
         │          │
   ┌─────▼────┐  ┌──▼─────┐
   │ Cluster A│  │Cluster B│
   └──────────┘  └─────────┘
```

- Istiod 完全独立部署，每个集群只是数据面
- 适合超大规模

### 10.3 跨集群通信

```yaml
# 在 cluster-a 声明 "我要调 cluster-b 的 service-x"
apiVersion: networking.istio.io/v1beta1
kind: ServiceEntry
metadata:
  name: service-x-remote
spec:
  hosts:
  - service-x.prod.svc.cluster.local
  location: MESH_EXTERNAL
  resolution: DNS
  addresses:
  - 240.0.0.1   # 虚拟 IP
  endpoints:
  - address: cluster-b-east-west-gw.example.com
    network: cluster-b
```

跨集群 mTLS：依赖共享根 CA（或证书联邦）。

## 第十一章：何时不要上 Mesh——8 个反对信号

Mesh 不是银弹。以下场景**先不要**上：

### 11.1 服务数 < 10

5 个微服务用 SDK（Resilience4j + Sentinel + OpenTelemetry）做治理够用。Mesh 的固定成本（学习、运维、资源）摊不下来。

### 11.2 团队没有 K8s 经验

Mesh 是 K8s 上的高阶玩法。如果团队 K8s 都还在踩坑，叠 Mesh 是双重灾难。

### 11.3 没有专人维护

Mesh 不是装上就完事——升级、调优、排障都需要懂的人。**没有专人就别上**。

### 11.4 业务对延迟极度敏感

Sidecar 模式 +0.5-2ms 延迟。Ambient + ztunnel 也有几百微秒。如果你的业务是 < 1ms 的高频交易、广告竞价，慎重。

### 11.5 单语言、SDK 成熟

如果全公司就是 Java、Resilience4j + Sentinel 用得很好，硬上 Mesh 收益小。

### 11.6 已经有 API Gateway，并且都是南北流量

如果服务间几乎不互调（典型的"网关 → 业务 → DB"扁平架构），Mesh 主要价值（东西流量治理）用不上。

### 11.7 集群规模 < 50 Pod

Mesh 控制面、CRD、监控的运维成本对小集群不划算。

### 11.8 多云但不打算统一

如果各云独立运营、不互通服务，多集群 Mesh 没必要。

### 11.9 什么时候上 Mesh

```
✅ 服务 > 30，且持续增长
✅ 多语言（Java + Go + Python）
✅ 强 mTLS / 零信任合规要求
✅ 团队有 K8s 经验、能投入 1-2 人专职
✅ 服务间互调频繁（东西流量为主）
✅ 已经感受到 SDK 模式的"运维债"
```

## 生产实践

### 1. 选型决策矩阵

| 场景 | 推荐 |
|---|---|
| 100+ 服务、强治理、有专人 | Istio Ambient |
| 30-100 服务、追求简单、资源敏感 | Linkerd |
| 已用 Cilium CNI、性能敏感 | Cilium Service Mesh |
| HashiCorp 全家桶、混合云 | Consul Connect |
| < 30 服务 | 暂不上 mesh |

### 2. 渐进式落地路径

```
Step 1: 部署 mesh 控制面（不注入任何 Pod）
        - 让团队熟悉
        - 检验监控

Step 2: 选 1 个低风险服务（非核心、有流量但不致命）
        - 注入 sidecar / 加 ambient label
        - 监控延迟、错误率

Step 3: 启用 mTLS（PERMISSIVE 模式）
        - 不强制
        - 观察证书签发是否正常

Step 4: 扩展到所有非核心服务

Step 5: 切到 STRICT mTLS
        - 这一步可能出问题，提前演练

Step 6: 把流量治理（重试 / 限流）从 SDK 搬到 mesh
        - 业务代码逐步移除 Resilience4j 等

Step 7: 启用灰度发布
        - VirtualService / HTTPRoute
```

每一步**至少观察 1-2 周**。

### 3. 监控核心指标

```
Sidecar / ztunnel:
- istio_requests_total （RED 指标）
- istio_request_duration_milliseconds_bucket
- envoy_cluster_upstream_rq_retry （重试次数，警惕雪崩）
- envoy_cluster_upstream_rq_timeout

控制面:
- pilot_xds_pushes_total
- pilot_proxy_convergence_time （配置下发延迟，目标 < 1s）

证书:
- citadel_secret_controller_csr_err_count
- 证书过期前 N 天告警
```

### 4. 灰度发布配合 Argo Rollouts

```
Argo Rollouts (策略)
   ↓ 调用
Istio VirtualService (流量切分)
   ↓
观察 Prometheus 指标
   ↓ 自动判断
继续 / 暂停 / 回滚
```

### 5. 避免双重重试

业务 SDK 重试 3 次 × Mesh 重试 3 次 = 9 次。这种放大在故障时**会要命**。

原则：**只在一处重试**。Mesh 上 mesh 做，下了 mesh SDK 做，不能两边都做。

### 6. mTLS 迁移演练

切 STRICT 之前，**先在 staging 演练**：

```
1. staging 切 STRICT
2. 跑端到端测试
3. 检查所有调用是否成功
4. 检查是否有遗漏的非 mTLS 入口（如外部探活）
5. 通过后再 prod 切
```

### 7. 控制面 HA

- Istiod 至少 3 副本
- 监控 xDS push 延迟
- 控制面挂时数据面照常工作几小时（依赖本地缓存）

### 8. 排障常用命令

```bash
istioctl proxy-status                  # 查所有 Envoy 状态
istioctl proxy-config cluster <pod>    # 看下发的集群配置
istioctl analyze                       # 静态检查 CRD
istioctl experimental ambient list     # Ambient 模式查看
```

## 陷阱清单

| # | 陷阱 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 业务 SDK 重试 + Mesh 重试 | 雪崩 | 只在一处重试 |
| 2 | mTLS 直接从 DISABLE 切 STRICT | 瞬间断流 | 经过 PERMISSIVE 过渡 |
| 3 | 小集群（5 服务）上 Mesh | 学习/运维成本 ROI 负 | 用 SDK 即可 |
| 4 | 团队没人懂就上 | 出事没法排障 | 至少 1 人专职 |
| 5 | sidecar 启动顺序坑 | 应用拉不到外部 | 用 native sidecar (K8s 1.29+) |
| 6 | 直连 Pod IP 而非 Service | mesh 治理失效 | 通过 Service / DNS |
| 7 | 给所有 namespace 自动注入 | 系统 namespace 也注入引发问题 | 显式 opt-in |
| 8 | 控制面单点 | 升级期数据面无法更新配置 | 多副本 + 滚动 |
| 9 | 不监控控制面延迟 | 配置下发慢都不知道 | pilot_proxy_convergence_time 告警 |
| 10 | 多集群联邦 CA 没设好 | 跨集群 mTLS 失败 | 共享根 CA 或证书联邦 |
| 11 | VirtualService 改完忘了 DestinationRule subsets | 流量切分失败 | 一起改 |
| 12 | 不演练 mTLS 切 STRICT | prod 切完瞬间挂 | staging 演练 |
| 13 | 升级 Istio 不灰度 | 全集群波动 | 按 namespace 灰度 |
| 14 | 故障注入打到 prod | 真挂 | 只在 dev/test 用 |
| 15 | Mesh + Gateway 重复治理 | 行为冲突 | 明确边界（南北 / 东西） |
| 16 | 没做容量评估，控制面被 1w 节点拖挂 | 全网瘫 | 单 Istiod < 3-5k Pod，拆分 |
| 17 | 把 mesh 当配置中心存业务参数 | 滥用 | 用 Apollo / Nacos |
| 18 | Ambient 模式下还想用 sidecar 的所有 feature | 部分 L7 功能要 waypoint | 看清能力差异 |
