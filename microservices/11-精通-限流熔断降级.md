## 引言：稳定性的"三件套"

微服务架构里，单机时代的"扛不住就崩"在分布式语境下被放大成"一个服务挂全链路雪崩"。限流、熔断、降级是大多数生产事故里"能不能止血"的分水岭：

- **限流（Rate Limiting）**：流量进来之前先过秤，超过就丢、就排队、就 429。保护**自己**的资源不被打穿。
- **熔断（Circuit Breaker）**：调用下游时发现下游不健康，就**立刻拒绝**，不再去敲那扇正在崩的门。保护**自己**不被下游拖死。
- **降级（Fallback / Degradation）**：在限流或熔断触发后，**返回一个"次优但可用"的结果**而非简单的 500。保护**用户体验**。

三件套不是三个独立按钮，而是一条流水线：

```
请求 → [限流 → 通过率超阈值就拒绝] → [调下游 → 熔断器判断要不要调] → [失败 → 降级返回兜底]
```

这一章把这三件套从算法、参数、工具到生产实践讲透。读完之后你应该能：

- 在 Token Bucket / Leaky Bucket / 滑动窗口 / 固定窗口里给一个场景做选型
- 用 Redis + Lua 写一个分布式限流器并解释为什么需要 Lua
- 解释自适应限流（BBR / Vegas / Sentinel 流控）为什么比固定阈值更鲁棒
- 画出 Circuit Breaker Closed → Open → Half-Open 的完整状态机和关键参数
- 设计一个 4 层（CDN → 网关 → 服务 → DB）的限流分层方案
- 在全链路压测里验证你的熔断器真的会跳

## 第一章：为什么要限流——三个根本目的

### 1.1 保护资源

任何系统都有"承载上限"：单机 QPS、连接池大小、CPU、内存、IO、下游依赖容量。**限流的第一目的是让系统永远工作在"承载上限以下"**——超过的部分宁可拒绝也不让它进。

一个未做限流的服务在突发流量下的典型行为：

```
正常 RT 50ms，QPS 1k → 一切正常
QPS 突增到 5k → 线程池打满，RT 升到 500ms
请求继续涌入 → 队列堆积，RT 升到 5s
客户端超时重试 → QPS 实际翻倍 = 10k
服务 OOM 或 GC 不停 → 完全无响应
```

有限流：QPS 一过 2k 立即 429，RT 永远不超过 100ms，挂掉的只是"被拒绝的那部分流量"，**核心容量稳定**。

### 1.2 防止雪崩

雪崩 = 一个组件出问题导致整条链路全挂。机制：

```
DB 慢 → 服务 A 大量请求堆积 → A 的连接池打满
→ 上游服务 B 调 A 全部超时 → B 的线程池也堵
→ 网关调 B 全部超时 → 网关线程池堵
→ 用户请求全部失败
```

雪崩传播的本质是**同步等待 + 资源耗尽**。限流在每一层切断这个传播链：B 调 A 时如果发现 A 在限流，B 立刻拿到 429，不会"卡住等"。

### 1.3 公平性

多租户场景（一个 SaaS API 服务多个客户）下，没有限流 = 一个坏租户能吃光资源。**Per-Tenant 限流**保证一个客户的流量不影响别人。

公平性也包含"防刷"：一个 IP 一分钟最多 100 次登录，防止暴力破解；一个用户 5 秒内最多发一条评论，防止刷屏。

### 1.4 限流的三个维度

| 维度 | 例子 | 工具 |
|---|---|---|
| **入口** | 网关层全局 QPS、CDN 防刷 | CDN、网关 |
| **业务** | 用户级（per-uid）、租户级（per-tenant）、接口级（per-api）| 服务内部 |
| **资源** | 连接数、并发数、内存占用 | 容器、JVM、信号量 |

## 第二章：限流算法——四大经典

### 2.1 固定窗口（Fixed Window）

最简单：每分钟最多 N 个请求。

```
                          每分钟计数器
  00:00-00:59  →  counter = 60   ✓
  01:00-01:59  →  counter = 0（重置） → 80  ✓
```

**实现**：

```go
type FixedWindow struct {
    mu       sync.Mutex
    count    int
    limit    int
    windowAt time.Time
    window   time.Duration
}

func (f *FixedWindow) Allow() bool {
    f.mu.Lock()
    defer f.mu.Unlock()
    now := time.Now()
    if now.Sub(f.windowAt) >= f.window {
        f.windowAt = now
        f.count = 0
    }
    if f.count >= f.limit {
        return false
    }
    f.count++
    return true
}
```

**致命缺陷——边界突刺**：

```
窗口 60 秒、限额 100：
00:00:59 来 100 个请求 → 全过
00:01:00 又来 100 个 → 也全过
=> 1 秒内实际放过了 200 个，是限额的 2 倍
```

适用：要求极简、对突刺不敏感的场景。

### 2.2 滑动窗口（Sliding Window）

固定窗口的修正：把大窗口切成 N 个小格子，按时间滑动。

```
60 秒切成 6 个 10 秒桶：
[10s][10s][10s][10s][10s][10s]
sum = 当前所有桶的累计

每过 10 秒：丢掉最老的桶，开新桶
```

**优点**：边界突刺被分摊，平滑很多。

**Sliding Window Log**（精确版）：记录每个请求的时间戳，查询"过去 60 秒内有几条" → 精确但内存大。

**Sliding Window Counter**（折中版）：当前桶 + 上一桶按"已过时间比例加权"：

```
count = curr_bucket + prev_bucket * (1 - elapsed_in_curr / window)
```

Redis Cell 模块（GCRA 算法）就是这个思路的极简实现。

### 2.3 Token Bucket（令牌桶）

**核心模型**：

```
桶容量 = burst
速率   = rate（每秒往桶里放 rate 个令牌）
请求来 → 从桶里取 1 个令牌 → 没有就拒绝/排队
```

```
+------------+   rate tokens/sec
|   leaky    | <-------- token source
|   bucket   |
| [● ● ● ●] |  burst 容量
+-----------|------+
            v
         请求消费
```

**特点**：

- 允许"短时突发"：桶里攒了 100 个令牌，可以瞬间放 100 个请求
- 长期速率不会超过 `rate`
- 通过调节 `burst` 和 `rate` 可以独立控制"突发能力"和"平均速率"

**Go 标准库 golang.org/x/time/rate 实现**：

```go
limiter := rate.NewLimiter(rate.Limit(100), 200)  // 100 QPS、突发 200

if !limiter.Allow() {
    return http.StatusTooManyRequests
}
// 或者阻塞等待
if err := limiter.Wait(ctx); err != nil { ... }
```

**为什么 Token Bucket 是事实标准**：AWS API Gateway、nginx limit_req（其实是 Leaky Bucket，但接口几乎等价）、Envoy Rate Limit、Stripe API、几乎所有云厂商的限流，底层都是 Token Bucket。

### 2.4 Leaky Bucket（漏桶）

```
请求 → 进桶（FIFO 队列） → 桶以恒定速率"漏"出去 → 处理
桶满 → 拒绝
```

**与 Token Bucket 的核心区别**：

| 维度 | Token Bucket | Leaky Bucket |
|---|---|---|
| 突发支持 | ✓ 允许桶满时放过 burst 个 | ✗ 严格匀速 |
| 输出节奏 | 时快时慢 | 严格恒定 |
| 应用场景 | API 限流、客户端突发友好 | 整形（traffic shaping）、给下游恒定压力 |

Leaky Bucket 更像"出口流量整形"，Token Bucket 更像"入口流量控制"。**面试时不要把它们说反**。

### 2.5 算法选型矩阵

| 算法 | 实现复杂度 | 内存 | 精度 | 突刺 | 适用 |
|---|---|---|---|---|---|
| Fixed Window | 极低 | O(1) | 低 | ✗ 有 | 内部调用、对精度要求低 |
| Sliding Log | 高 | O(N) | 最高 | ✓ 无 | 安全审计、精确计数 |
| Sliding Counter | 中 | O(1) | 中高 | ✓ 弱 | 网关、通用 API |
| Token Bucket | 中 | O(1) | 高 | ✓ 允许 | API 限流主流方案 |
| Leaky Bucket | 中 | O(N) 队列 | 高 | ✗ 不允许 | 流量整形、给下游恒压 |

## 第三章：单机限流 vs 分布式限流

### 3.1 为什么单机限流不够

一个服务 10 个实例，每个限 1k QPS → 总 10k QPS。问题来了：

- 流量倾斜：负载均衡哈希不均，实际有的实例 2k 有的 200
- 灰度发布：1 个实例承担 100% 流量、剩下 9 个跑新版本
- **下游的限额是 5k**：你 10k 进来 5k 被拒，下游崩

**结论**：当你要保护的资源是**全局共享**（DB、外部 API、共享缓存）时，限流必须**全局**。

### 3.2 Redis + Lua 实现分布式 Token Bucket

```lua
-- KEYS[1] = bucket key
-- ARGV[1] = rate        每秒令牌数
-- ARGV[2] = capacity    桶容量
-- ARGV[3] = now         当前时间戳（毫秒）
-- ARGV[4] = requested   本次请求要消耗的令牌数

local rate     = tonumber(ARGV[1])
local capacity = tonumber(ARGV[2])
local now      = tonumber(ARGV[3])
local requested= tonumber(ARGV[4])

local bucket = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(bucket[1])
local ts     = tonumber(bucket[2])

if tokens == nil then
    tokens = capacity
    ts     = now
end

-- 按时间差补充令牌
local delta = (now - ts) / 1000.0 * rate
tokens = math.min(capacity, tokens + delta)
ts     = now

local allowed = 0
if tokens >= requested then
    tokens = tokens - requested
    allowed = 1
end

redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', ts)
redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate) + 60)

return {allowed, math.floor(tokens)}
```

**为什么必须 Lua**：Token Bucket 的 read-modify-write 必须原子。如果用 GET / SET 两个命令，并发场景下两个客户端会读到同一个 token 值，都"以为"自己取到了，**实际超发**。

Lua 在 Redis 单线程模型里串行执行，保证整个过程原子。

### 3.3 调用端用 Go：

```go
//go:embed token_bucket.lua
var tokenBucketScript string

var script = redis.NewScript(tokenBucketScript)

func Allow(ctx context.Context, key string, rate, capacity int) (bool, int, error) {
    now := time.Now().UnixMilli()
    res, err := script.Run(ctx, rdb, []string{key}, rate, capacity, now, 1).Result()
    if err != nil {
        // Redis 不可用 → fail-open 还是 fail-close？见 3.5
        return true, 0, err
    }
    arr := res.([]interface{})
    allowed := arr[0].(int64) == 1
    remain  := int(arr[1].(int64))
    return allowed, remain, nil
}
```

### 3.4 Sentinel cluster mode（集群限流）

阿里 Sentinel 的集群限流走的是"客户端 → token server"的中心化模式：

```
+---------+      +---------+      +---------+
| Service1| ---> |         |      |Service2 |
+---------+      | Token   | <--- +---------+
                 | Server  |
+---------+      |         |      +---------+
| Service3| ---> |         | <--- |Service4 |
+---------+      +---------+      +---------+
```

每个服务实例调用 Token Server 申请令牌，Token Server 维护全局视图。

**优势**：算法跑在内存里、不依赖 Redis、与 Sentinel Dashboard 深度集成。
**代价**：多了一跳网络、Token Server 是单点（需要主备 + Raft）。

### 3.5 Fail-Open vs Fail-Close

**Redis 挂了，限流器怎么办？**

| 选择 | 含义 | 适用 |
|---|---|---|
| Fail-Open | Redis 不可用就放行所有请求 | 用户面 API：限流不是为了拒绝，是为了保护 |
| Fail-Close | Redis 不可用就拒绝所有请求 | 防刷、安全场景：宁可拒错不能漏过 |

通用做法：**Fail-Open + 单机兜底**——Redis 挂了走单机限流，每实例独立兜底，全局总量虽不准但不会让下游被打穿。

## 第四章：自适应限流——固定阈值的死亡

### 4.1 固定阈值的问题

线上限额 QPS=2000——这个数字从哪儿来？

- 压测得来：今天的代码、今天的数据量、今天的依赖响应
- 明天代码改了 / 数据涨了 / 下游慢了 → **2000 不再合适**
- 高峰期 CPU 满了，QPS 2000 系统已经濒死，但限流器还在放
- 低峰期 CPU 闲着，QPS 1800 已经触发限流，**浪费容量**

固定阈值的根本缺陷：**它表达的是"昨天的容量"，不是"现在的容量"**。

### 4.2 自适应限流的思路

不看 QPS，看**信号**：

| 信号 | 含义 | 工具 |
|---|---|---|
| **CPU 利用率** | 超过 80% 就降级 | 简单粗暴 |
| **响应时间（RT）** | RT 飙升 = 系统在排队 | Sentinel 的 RT 限流 |
| **在途请求数（in-flight）** | 当前并发量 | BBR、Vegas |
| **Load Average** | 单位时间排队任务数 | Linux load |
| **GC 频率** | Full GC 频繁 = 内存压力 | Java 应用 |

### 4.3 BBR 思路（借自 TCP）

Google BBR 是 TCP 拥塞控制算法，核心思想：

```
带宽 × 延迟 = 在途数据量（BDP, Bandwidth-Delay Product）
```

应用到限流：

```
最大允许并发 = MaxQPS × MinRT
```

- **MaxQPS**：滑动窗口内观察到的最大 QPS
- **MinRT**：滑动窗口内观察到的最小响应时间

当 `in-flight > MaxQPS × MinRT` 时拒绝请求。

**B 站开源的 kratos/aegis 就是这个思路**：

```go
limiter := aegis.NewBBR()
if !limiter.Allow() {
    return ErrLimit
}
defer limiter.Done()  // 完成后归还
```

**为什么自适应更好**：系统能力变化（GC、网络抖动、依赖变慢）时，MaxQPS 和 MinRT 自动跟着变，**永远工作在"刚好不过载"的状态**。

### 4.4 Netflix concurrency-limits（Vegas）

Netflix 在 2018 年开源的 concurrency-limits 项目用的是 TCP Vegas 算法的思路：

```
estimatedLimit = α + (1 - α) × (currentLimit × minRT / currentRT)
```

简化版：响应时间变长 → 限额下降；响应时间变短 → 限额上升。

**核心区别**：BBR 看"能力上限"，Vegas 看"响应时间退化"。生产环境两者效果接近。

### 4.5 Sentinel 流控的几种模式

Sentinel（阿里开源）流控不止 QPS，还包括：

| 模式 | 说明 |
|---|---|
| **QPS 模式** | 普通限流 |
| **并发线程数** | 限制同一时刻在跑的线程 |
| **关联模式** | 资源 A 流量大时限流资源 B（防资源竞争） |
| **链路模式** | 只对来自特定入口的流量限流 |
| **基于 RT** | 平均 RT 超过阈值就限流 |
| **基于 CPU** | CPU 使用率超过阈值就限流 |
| **基于 Load** | 系统 Load > 阈值就限流 |

**复合规则**：实践中往往"QPS 上限 + 自适应底线"两条规则同时配——QPS 防极端突发，自适应防容量退化。

## 第五章：限流工具对比

### 5.1 主流工具横评

| 工具 | 部署位置 | 算法 | 集群限流 | 自适应 | 适用 |
|---|---|---|---|---|---|
| **nginx limit_req** | 入口层 | Leaky Bucket | ✗（per-instance） | ✗ | 入口防刷 |
| **nginx limit_conn** | 入口层 | 并发数 | ✗ | ✗ | 限制连接数 |
| **Envoy Rate Limit** | Sidecar / 网关 | Token Bucket | ✓（外接 ratelimit service）| ✗ | 服务网格、网关 |
| **Apisix limit-req** | 网关 | Token / Leaky | ✓（基于 Redis）| 部分 | 网关 |
| **Sentinel** | 应用内 | 多种 | ✓（Token Server） | ✓ | Java 应用 |
| **Resilience4j RateLimiter** | 应用内 | Token Bucket | ✗ | ✗ | Java 函数式 |
| **kratos/aegis** | 应用内 | BBR | ✗（设计如此） | ✓ | Go 应用 |
| **golang.org/x/time/rate** | 应用内 | Token Bucket | ✗ | ✗ | Go 标准 |
| **Redis + Lua 自实现** | 应用内 + Redis | 任选 | ✓ | 可加 | 通用 |

### 5.2 nginx limit_req 实战

```nginx
http {
    limit_req_zone $binary_remote_addr zone=ip:10m rate=10r/s;
    limit_req_zone $http_authorization zone=user:10m rate=100r/s;

    server {
        location /api/ {
            limit_req zone=ip burst=20 nodelay;       # IP 维度 10r/s 突发 20
            limit_req zone=user burst=200;            # 用户维度 100r/s 突发 200
            proxy_pass http://backend;
        }
    }
}
```

- `burst`：允许的突发上限
- `nodelay`：超过 rate 但在 burst 内的请求直接放行（不延迟），超过 burst 才拒绝

### 5.3 Envoy Rate Limit

Envoy 自身不存限流状态，调用外部 ratelimit service（Go 写的）：

```yaml
# envoy.yaml
http_filters:
  - name: envoy.filters.http.ratelimit
    typed_config:
      domain: api
      rate_limit_service:
        grpc_service:
          envoy_grpc:
            cluster_name: ratelimit_cluster

# ratelimit service 的 config
domain: api
descriptors:
  - key: user_id
    rate_limit:
      unit: minute
      requests_per_unit: 1000
  - key: api_endpoint
    value: /v1/search
    rate_limit:
      unit: second
      requests_per_unit: 500
```

服务网格里几乎所有限流都走这个模式：Envoy 拦截 → 调 ratelimit service → 拒/放。

## 第六章：熔断器（Circuit Breaker）

### 6.1 三态状态机

熔断器借自电路工程：保险丝跳了，电路就断开了。

```
        失败率 > threshold
+----------+    在窗口内    +----------+
|          | -------------> |          |
|  Closed  |                |   Open   |
| (正常)   | <------------- |  (熔断)  |
+----------+    一段时间    +----------+
     ^                          |
     |                          | sleep window 后
     | 试探通过                  v
     |                      +----------+
     +--------------------- |Half-Open |
        试探失败            | (半开)   |
                            +----------+
```

| 状态 | 行为 | 转换条件 |
|---|---|---|
| **Closed** | 正常调用，统计失败率 | 失败率超阈值 → Open |
| **Open** | 直接 fail，不调下游 | sleep window 到了 → Half-Open |
| **Half-Open** | 放过少量试探请求 | 成功 → Closed；失败 → Open |

### 6.2 关键参数

| 参数 | 典型值 | 含义 |
|---|---|---|
| **failure threshold** | 50% | 失败率超过这个就跳闸 |
| **min requests** | 20 | 至少要这么多请求才计算失败率（防小样本误判） |
| **sliding window** | 10s | 统计失败率的时间窗口 |
| **sleep window** | 30s | Open 状态保持多久 |
| **half-open trials** | 5 | Half-Open 放过几个试探请求 |
| **slow call duration** | 5s | RT 超过这个算"慢调用"（也计入失败） |
| **slow call ratio** | 50% | 慢调用比例超过这个也跳闸 |

### 6.3 Resilience4j 配置

```yaml
resilience4j.circuitbreaker:
  instances:
    paymentService:
      failureRateThreshold: 50
      slowCallRateThreshold: 50
      slowCallDurationThreshold: 2s
      slidingWindowType: COUNT_BASED
      slidingWindowSize: 100
      minimumNumberOfCalls: 20
      waitDurationInOpenState: 30s
      permittedNumberOfCallsInHalfOpenState: 5
      automaticTransitionFromOpenToHalfOpenEnabled: true
```

```java
@CircuitBreaker(name = "paymentService", fallbackMethod = "payFallback")
public PayResult pay(PayRequest req) {
    return paymentClient.pay(req);
}

private PayResult payFallback(PayRequest req, Exception e) {
    return PayResult.pending();  // 标记"待支付"，让用户稍后重试
}
```

### 6.4 Go 实现 gobreaker

```go
import "github.com/sony/gobreaker"

cb := gobreaker.NewCircuitBreaker(gobreaker.Settings{
    Name:        "paymentService",
    MaxRequests: 5,        // Half-Open 时放过的请求数
    Interval:    10 * time.Second,
    Timeout:     30 * time.Second,
    ReadyToTrip: func(c gobreaker.Counts) bool {
        return c.Requests >= 20 && float64(c.TotalFailures)/float64(c.Requests) >= 0.5
    },
})

resp, err := cb.Execute(func() (interface{}, error) {
    return paymentClient.Pay(req)
})
if err != nil {
    return fallback()
}
```

### 6.5 熔断器陷阱

**陷阱 1：所有请求共享一个熔断器**

服务 A 调下游有 10 个接口，全部走同一个熔断器 → 接口 X 挂了，接口 Y 也被熔了。**正确做法：每个下游接口（甚至每个下游实例）一个熔断器**。

**陷阱 2：min requests 太小**

minRequests=5、threshold=50% → 5 个请求里 3 个失败就跳闸，**很容易误判**。生产至少 20-50。

**陷阱 3：sleep window 太长**

下游已经恢复，但你的熔断器还要等 60 秒才探 → 影响恢复速度。一般 30s 内。

**陷阱 4：Half-Open 的并发问题**

Half-Open 允许 N 个试探请求并发，如果 N 设太大 → 一旦下游还没好就被这 N 个请求再次打挂。**N 一般 1-5**。

## 第七章：降级（Fallback / Degradation）

### 7.1 降级 ≠ 失败

熔断或限流触发后，**直接返回错误**和**返回兜底**对用户的影响天差地别：

```
[用户搜索商品]
没降级：500 Internal Server Error → 用户重试 → 还是失败 → 走人
有降级：返回"近期热门商品" → 用户至少看到东西 → 可能继续操作
```

降级的核心是**"次优但可用"**。

### 7.2 降级策略分类

#### 7.2.1 静态兜底

```go
func GetRecommend(userId int) ([]Item, error) {
    items, err := recoService.Get(userId)
    if err != nil {
        return getHotItemsFromCache(), nil  // 走缓存的热门榜
    }
    return items, nil
}
```

#### 7.2.2 缓存兜底

调用前先有缓存：

```go
func GetUserInfo(userId int) (*User, error) {
    u, err := userService.Get(userId)
    if err != nil {
        if cached, ok := localCache.Get(userId); ok {
            return cached, nil  // 返回稍微过期的数据
        }
        return nil, err
    }
    localCache.Set(userId, u, 1*time.Hour)
    return u, nil
}
```

#### 7.2.3 异步降级

强一致变弱一致——把同步调用改为发消息：

```
正常：扣库存 → 同步调用 → 失败回滚整单
降级：扣库存 → 写消息队列异步处理 → 用户看到"订单已提交，稍后处理"
```

#### 7.2.4 业务降级

砍掉非关键路径：

```
正常下单：扣库存 + 写订单 + 发优惠券 + 记积分 + 推送通知 + 风控审核
降级下单（双 11 高峰）：扣库存 + 写订单 + 异步队列处理其他
```

把**非核心链路从同步链路里摘出来**——故障窗口期专门保护核心。

#### 7.2.5 读写分离降级

写降级：禁止写，只读
读降级：从主库读 → 从库读（接受秒级延迟）

### 7.3 降级的"开关化"

降级不应该是"出问题才触发"，而应该是**可手动操作的开关**：

```yaml
features:
  recommendation_v2: false    # 关掉 v2 推荐，走 v1
  enable_coupon_calc: false   # 关掉优惠券计算，走默认无券
  enable_risk_check: true     # 风控审核
```

配置中心（Apollo / Nacos）一键改 → 应用收到事件 → 立即生效。这就是 **Feature Flag 在降级上的应用**——见 [M19 灰度发布](./19-精通-灰度发布.md)。

### 7.4 降级的边界

**不能降级的事情**：

- 钱：扣款不能"降级为不扣"
- 库存：超卖比卖空更难解释
- 合规：风控、KYC、审计不能省

**判断标准**：如果"降级后用户/业务方/法务任何一方接受不了"，那这个点不能降级。

## 第八章：限流分层——电商促销系统案例

### 8.1 分层模型

```
互联网用户
   |
+--v---------------+
|     CDN          |  L1: 全球边缘限流 / 防 DDOS / 防爬
+--+---------------+
   |
+--v---------------+
| 高防 / WAF       |  L2: IP 限流、异常流量识别
+--+---------------+
   |
+--v---------------+
|   API 网关       |  L3: 全局 QPS、用户级、接口级限流 + 鉴权
+--+---------------+
   |
+--v---------------+
|  业务服务        |  L4: 服务内部限流 + 熔断 + 自适应
+--+---------------+
   |
+--v---------------+
|  DB / 缓存       |  L5: 连接池限流、慢查询保护
+------------------+
```

每一层的限流目的不同：

| 层 | 目的 | 维度 | 典型工具 |
|---|---|---|---|
| L1 CDN | 抗 DDOS、防爬 | IP、UA、地域 | Cloudflare、Akamai |
| L2 WAF | 业务级防护 | IP、用户、签名 | 阿里云 WAF、自建 |
| L3 网关 | 业务总量控制 | 接口、用户、租户 | Kong、Envoy Gateway |
| L4 服务 | 单服务能力保护 | 接口、依赖 | Sentinel、aegis |
| L5 DB | 资源保护 | 连接、慢查询 | DB Proxy、连接池 |

### 8.2 电商秒杀场景的限流设计

**业务背景**：1 件商品 1 万件库存，预估 100 万人抢购。

```
100w 用户进入活动页
  ↓ [L1 CDN] 静态页面命中 99.5%，回源 5000 QPS
[L2 WAF] 异常 IP 拦截、机器流量识别（验证码）
  ↓ 真实请求量：约 50w 用户进入"立即抢购"
[L3 网关] 限流：
  - 接口级：/seckill/order 最大 5000 QPS
  - 用户级：每个 uid 1 秒最多 1 次
  ↓ 通过率约 5%（其他全部 429）
[L4 服务] 限流：
  - 单实例 2000 QPS
  - 库存余量为 0 时直接返回（业务级降级）
  ↓
[L5 DB] 库存扣减用 Redis 预扣 + DB 异步落库
```

**关键设计**：

1. **越前置的层，丢请求成本越低**——CDN 丢一个请求几乎零成本；DB 丢一个请求已经做了很多工作
2. **用户维度限流防"刷单脚本"**：一个 uid 1 秒 1 次 → 脚本起 1000 个号才能 1k QPS
3. **库存到 0 后立即降级**：网关层下发"已售罄"标志，根本不走业务服务
4. **熔断保护下游 DB**：Redis 预扣失败立即降级返回"系统繁忙"

### 8.3 多机房 + 多 region 限流

```
region-A (国内主)         region-B (海外灾备)
+----------------+       +----------------+
| Gateway × 10   |       | Gateway × 5    |
| 限流配额 70%   |       | 限流配额 30%   |
+----------------+       +----------------+
          ↓                       ↓
+----------------------------------------+
|  Token Server（跨 region 全局视图）    |
+----------------------------------------+
```

集群限流跨 region 时延高（30-100ms），通常做法：

- **本地限额预分**：region-A 拿到全局 70%，自己内部走分布式限流
- **定期再平衡**：region-B 流量低时把 quota 让一部分给 region-A

## 第九章：全链路压测中验证熔断

### 9.1 为什么生产里需要"主动验证"

熔断器最大的悖论：**写好了但从来没真正跳过**。生产事故时才发现：

- 配置参数错了
- 上游调用没接 fallback
- 熔断后用户体验比直接错还差

**全链路压测**是验证熔断的唯一可靠手段。

### 9.2 验证步骤

```
Step 1: 选定目标
  - 目标服务：order-service
  - 目标依赖：payment-service
  - 验证目标：order-service 调 payment 失败率 > 50% 时熔断器跳闸

Step 2: 注入故障
  - 用 Chaos Mesh 给 payment 注入"50% 请求延迟 5s"
  - 见 M20 契约测试与混沌工程

Step 3: 加压
  - 用 k6 / wrk 给 order-service 加 1000 QPS

Step 4: 观察
  - 看 order 调 payment 的失败率：是否从 0 → 50%+
  - 看熔断器状态：从 Closed → Open
  - 看 fallback 是否被触发
  - 看 user 端的实际响应：5xx 是否被限制在某个比例

Step 5: 恢复验证
  - 停止注入
  - 看熔断器：sleep window 后是否进入 Half-Open
  - 看是否回到 Closed
```

### 9.3 关键指标

```promql
# 熔断器状态
circuit_breaker_state{service="payment"}     # 0=Closed, 1=Open, 2=HalfOpen

# 拒绝率
rate(circuit_breaker_rejected_total[1m])
  / rate(circuit_breaker_calls_total[1m])

# Fallback 调用率
rate(circuit_breaker_fallback_total[1m])

# 上游接口的实际 5xx 率
rate(http_requests_total{status=~"5.."}[1m])
  / rate(http_requests_total[1m])
```

### 9.4 混沌工程范式

按 Netflix Principles of Chaos：

```
1. 定义稳态（steady state）——熔断器跳闸前后用户层 5xx ≤ X%
2. 假设系统能维持稳态
3. 注入真实事件（下游慢、宕机、网络丢包）
4. 观察是否还维持稳态
5. 不维持 → 找到改进点 → 修复 → 再压
```

详见 [M20 契约测试与混沌工程](./20-精通-契约测试与混沌工程.md)。

## 第十章：限流与熔断的协同

### 10.1 上下游协议

设想三层服务调用：

```
Gateway → ServiceA → ServiceB
```

- Gateway 限流 5000 QPS
- ServiceA 限流 4000 QPS（自己单机能力 4k）
- ServiceB 限流 3000 QPS（依赖 DB，只能 3k）

谁应该限谁？

**核心原则**：**入口层限"业务总量"，每层服务限"自己能扛多少"，下游不应该承担上游限流的责任**。

如果 ServiceA 没做限流、ServiceB 限到 3k：
- 5k 流量进来 ServiceA 全转发
- ServiceB 限到 3k，剩 2k 拒绝
- **ServiceA 调 ServiceB 的失败率突然到 40%**
- ServiceA 的熔断器跳闸 → 5k 全部 fail
- 实际能服务的请求 = 0，而不是 3k

**正确做法**：

```
Gateway 限 5000 → 给业务总量定调
   ↓
ServiceA 限 4000 → 单机能力 + 留给下游空间
   ↓
ServiceA 调 ServiceB 时：
   - 设熔断器（不依赖 B 的限流回包）
   - 给 B 留余量，自己也不超 3000
```

### 10.2 调用方还是被调方做限流？

被调方（接收方）必须做——保护自己。
调用方可以做——更好，提前拒绝，省一次网络。

**一般建议**：双方都做，被调方为主。

### 10.3 熔断 + 限流 + Fallback 完整流程

```go
func GetUserProfile(ctx context.Context, uid int64) (*Profile, error) {
    // 1. 本地限流：防止本机过载
    if !localLimiter.Allow() {
        return nil, ErrLocalLimit
    }

    // 2. 熔断器：保护下游
    return userService.Execute(func() (*Profile, error) {
        // 3. 远程调用 + 超时
        ctx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
        defer cancel()
        return userClient.GetProfile(ctx, uid)
    }, func(err error) (*Profile, error) {
        // 4. Fallback：缓存兜底
        if cached, ok := profileCache.Get(uid); ok {
            return cached, nil
        }
        return defaultProfile, nil
    })
}
```

## 生产实践

### 限流参数推荐

| 场景 | rate | burst | 维度 |
|---|---|---|---|
| 网关接口级 | 压测峰值 × 1.2 | rate × 2 | 接口 |
| 用户级（普通 API）| 100 r/s | 200 | uid |
| 用户级（安全敏感，如登录）| 5 r/min | 10 | uid + IP |
| 防爬 | 30 r/min | 60 | IP |
| 内部服务间 | 单实例上限 × 实例数 × 1.2 | rate × 1.5 | service |

### 熔断器参数推荐

| 场景 | failure_threshold | min_requests | sliding_window | sleep_window |
|---|---|---|---|---|
| 核心强依赖（如支付）| 50% | 50 | 10s | 30s |
| 旁路依赖（如推荐）| 30% | 20 | 10s | 60s |
| 边缘依赖（如审计）| 80% | 10 | 30s | 60s |

### 监控告警必备

| 指标 | 告警条件 |
|---|---|
| `limiter_rejected_qps` | > 0 持续 1 分钟 |
| `limiter_pass_rate` | < 50% 持续 5 分钟 |
| `circuit_breaker_state` | = Open 持续 1 分钟 |
| `circuit_breaker_open_total` | 1 小时内 > 3 次（频繁跳闸 = 阈值不合适） |
| `fallback_total` | > 调用总量 5% |

### 灰度上线限流

**永远不要直接全量上线一个新限流配置**：

1. 影子模式：跑限流逻辑但**不真拒绝**——只打日志看会拒多少
2. 1% 灰度：1% 流量真拒
3. 看用户层 5xx、业务指标是否异常
4. 逐步放大到 100%

### 限流文案

429 不要只返回 `"Too Many Requests"`：

```json
{
  "code": 429,
  "message": "请求过于频繁，请稍后再试",
  "retry_after": 3,
  "trace_id": "abc123"
}
```

`Retry-After` HTTP header 让客户端知道**多久后可以重试**。

## 陷阱清单

1. **限流配置写死在代码里**：每次调阈值都要发版，事故时无法快速止损。永远走配置中心。

2. **限流没分维度**：所有请求都用一个全局桶，导致一个客户的突发吃光整个配额。至少分接口 + 维度（uid/IP/tenant）。

3. **熔断器开太敏感**：threshold=20%、min=5 → 网络抖一下就跳。生产先保守，再根据数据收紧。

4. **熔断后还重试**：调用层熔断了，但客户端代码继续 retry 3 次 → 雪上加霜。**熔断 = fail fast，不要再重试**。

5. **Fallback 比正常还慢**：Fallback 查缓存超时 5s，还不如直接 fail。Fallback 必须**比正常路径更快、更简单**。

6. **限流器自己挂了**：Redis 不可用、Sentinel TokenServer 挂了 → 整个集群限不住。永远有单机兜底。

7. **限流单位错**：QPS 限的是请求数，但有些请求很重（一次查 1000 条）一些请求很轻（查 1 条），按请求数限流不准。**复杂场景按"计算成本"加权**。

8. **共享熔断器**：A 调 B 的 10 个接口共用一个熔断器 → 接口 X 挂全断。每个调用点一个。

9. **熔断 sleep window 配置错**：sleep=300s（5 分钟）→ 下游恢复了还要等 5 分钟才探。一般 30-60s。

10. **没做演练**：上线了，没在测试环境验证过熔断真的会跳。100% 会在生产第一次故障时发现配置错了。

11. **Fallback 没记录**：触发 fallback 时没记日志/metric → 出问题时不知道有多少请求走了降级路径。

12. **限流过严，影响 SLA**：业务诉求 99.9% SLA，但限流误杀 5%。**限流前先算清楚 SLA 预算**。

13. **重试和限流互相打架**：上游限流给下游 30% 错误率 + 上游开 3 次重试 = 实际 3 倍流量打到下游。**重试要先看错误码**——429 / 503 不重试。

14. **集群限流时延高**：每个请求都查一次 Redis，增加 1-2ms。高频接口要批量预取（一次拿 10 个令牌）。

## 2026 现状

- **自适应限流**已成主流：Sentinel 1.8+、kratos/aegis、Netflix concurrency-limits 都在大规模生产用。固定阈值在新系统里几乎不再被单独使用。
- **服务网格层限流**借助 Envoy + RateLimit Service 成熟，配置可以由 SRE 在网格层下发，**应用代码完全不感知**。Istio Ambient（2024-11 GA）让这件事更轻量（无 sidecar 也能限流）。
- **eBPF 限流**：Cilium 在 L4 层用 eBPF 直接限流，绕过用户态，性能极高。
- **Resilience4j** 取代了 Hystrix 成为 Java 生态默认（Hystrix 2018 停止维护）。
- **Token Bucket** 几乎统一了限流算法选择，Leaky Bucket 仅在流量整形场景出现。
- **AI 服务限流的新挑战**：LLM 请求按 token 数计费 + 推理时间不固定，传统 QPS 限流不够，**改按 token-per-second + 并发限流**。OpenAI、Anthropic API 都采用 RPM（每分钟请求数）+ TPM（每分钟 token 数）双指标。
- **Feature Flag 与降级一体化**：LaunchDarkly、GrowthBook 既做灰度也做降级开关，配置统一。
- **混沌工程平台化**：Chaos Mesh 在生产 K8s 集群常态化运行，每周固定时间注入故障验证熔断器。

8. **故障复盘**：某天线上熔断器疯狂跳闸（一天 200 次），看监控发现下游服务实际只是网络抖动几次（每次几秒）。请分析可能的原因和修复方案。
