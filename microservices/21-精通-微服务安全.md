## 引言：当边界消失，安全从何谈起

让我们先抛几个真实的、能让架构师彻夜难眠的问题：

1. 你的微服务集群有 30 个服务，A 服务调用 B 服务时，B 凭什么相信 A 真的是 A，而不是被攻入内网的攻击者伪装的？
2. 一个用户登录后，请求经过 Gateway → BFF → Order → Payment → Risk → Account 共 6 跳，**用户身份**如何在 6 跳中正确传递、又不被中间任意一跳冒用？
3. 你的服务证书是怎么发的？怎么轮转的？过期了怎么办？开发同学是不是把私钥直接 commit 到 Git 了？
4. 当一个内部服务被攻陷，攻击者能不能横向移动到数据库、配置中心、消息队列？你怎么阻止？
5. 你说"我们有 WAF 和防火墙"，那进了内网之后呢？内网是不是默认全通？这就是经典的"咬壳硬糖"——**外面硬，里面软**。

传统单体时代，安全约等于"把边界守好"——一道防火墙 + 一个 WAF + 一套 RBAC，足够应付 80% 的场景。但微服务时代，边界**消失**了：

- 服务运行在 K8s Pod 里，IP 随时变；
- 一个业务请求穿过 10 个服务、3 个网络分区、2 个 Region；
- 内部攻击面急剧膨胀，任何一个被入侵的容器都可能成为跳板；
- 合规要求（GDPR、SOC 2、等保 2.0、PCI-DSS）要求"数据流动全程加密+审计"。

于是工业界共识转向 **Zero Trust（零信任）**：永远不要信任任何一个调用方，即使它来自内网。本章我们就把"微服务安全"这棵庞大的树，从根（服务身份）讲到叶（审计日志），用 30+ 真实落地经验把你武装成一个真正能 Hold 住生产安全的架构师。

## 第 1 章：微服务安全的 4 个维度

我们先把"安全"这个泛词，**拆**成 4 个工程上可操作的维度。这 4 个维度构成了本章的脊柱：

| 维度 | 解决什么问题 | 典型实现 | 类比 |
| --- | --- | --- | --- |
| **1. Service Identity（服务身份）** | 我是谁？我能向其他服务证明吗？ | SPIFFE / SPIRE / Istio Citadel / X.509 | 工牌 |
| **2. 传输加密（mTLS）** | 链路上的数据不能被窃听/篡改 | mTLS、TLS 1.3、Wireguard | 加密信封 |
| **3. 授权（Authz）** | 你有权限做这个操作吗？ | RBAC / ABAC / ReBAC / OPA | 门禁系统 |
| **4. 审计（Audit）** | 出事之后能追溯吗？ | 结构化日志 + SIEM + 不可篡改链 | 监控录像 |

```
        │                    微服务安全四维度                       │
        ├─────────────────────────────────────────────────────────┤

        │     谁           安全通道          权限         留痕      │
        │      │              │               │            │      │
        │   SPIFFE          mTLS           OPA/RBAC     OpenTele- │
        │   SPIRE          TLS 1.3         JWT/OIDC     metry +   │
        │   Citadel        Wireguard       Zanzibar     SIEM      │
        │                                                         │
        └─────────────────────────────────────────────────────────┘
                              │
                              ▼
                  全部基于 Zero Trust 原则
```

## 第 2 章：边界安全的失败 —— "咬壳硬糖"模型

在讲 Zero Trust 之前，必须先解释**为什么传统模型必然失败**。

### 2.1 经典模型：Perimeter Security（边界安全）

```
   外部 Internet                内部网络
   ─────────────                ─────────────────────
                 │              │
                 │   防火墙     │  ┌──────┐  ┌──────┐  ┌──────┐
   攻击者 ──────►│   WAF      │  │ Svc A│←─│ Svc B│←─│ Svc C│
                 │   IDS      │  └──────┘  └──────┘  └──────┘
                 │              │   全部明文 HTTP，无认证
                 │              │   IP 白名单 = "认证"
                 ──────────────
                 一道墙挡天下
```

这个模型的假设是：**只要墙足够厚，内部就是安全的。** 所以内部服务之间：

- 明文 HTTP；
- 没有任何认证（最多 IP 白名单）；
- 数据库连接字符串直接写在配置文件；
- 谁能调谁，靠"君子协议"。

### 2.2 为什么失败？—— 5 个真实的攻击路径

1. **供应链投毒**：开发同学装了一个被植入后门的 npm 包，攻击者拿到 dev 笔记本，VPN 进入内网；
2. **横向移动**：攻击者攻破一个低价值服务（如内部 Wiki），用它作为跳板访问高价值服务（如支付）；
3. **凭据泄露**：数据库密码在 Slack 群里被截图分享，攻击者通过被劫持的员工账号拿到；
4. **内鬼**：被开除的运维带走了一份 `~/.kube/config`；
5. **K8s 误配置**：一个 NodePort 暴露到公网，里面是一个无认证的内部 admin API。

每一种都让"边界安全"瞬间崩塌。这个模型有个形象比喻：**M&M 巧克力豆（咬壳硬糖）**——**外面一层硬糖壳，里面是软软的巧克力**。一旦壳破，全是软的。

### 2.3 Zero Trust 的诞生

2010 年 Forrester 的 John Kindervag 首次提出 Zero Trust 概念，核心一句话：

> **"Never trust, always verify."**（永不信任，始终验证）

无论请求来自内网、外网、Pod 内、Pod 外，都必须：

- 验证身份（你是谁）；
- 验证权限（你能做什么）；
- 加密传输（链路防窃听）；
- 记录审计（事后能追）。

2020 年 NIST 发布 SP 800-207 标准，Zero Trust 从概念走向工程。2024 年起，主流云厂商（AWS、Azure、GCP）的内部架构以及一线互联网公司（Google BeyondCorp、Netflix、Cloudflare）已全面落地 Zero Trust，**Service Mesh 成为最自然的承载体**。

## 第 3 章: Zero Trust 七大原则与落地映射

NIST 800-207 定义了 Zero Trust 的 7 个原则。我们逐条解读，并映射到微服务场景的工程实现：

| # | 原则（英文） | 通俗解释 | 微服务落地 |
| --- | --- | --- | --- |
| 1 | All data sources and computing services are considered resources | 所有数据/算力都是资源，都要保护 | 每个服务、每个 DB、每个 Topic 都要认证 |
| 2 | All communication is secured regardless of network location | 不分内网外网，全部加密 | mTLS 全网；K8s 默认 deny-all |
| 3 | Access to resources is granted on a per-session basis | 每次会话单独授权 | JWT 短 TTL；mTLS 证书短期 |
| 4 | Access is determined by dynamic policy | 策略动态评估而非静态白名单 | OPA / Cedar 实时决策 |
| 5 | Monitor and measure integrity & security posture | 持续监控完整性 | 镜像签名（Cosign）、运行时（Falco） |
| 6 | Authentication & authorization are strictly enforced before access | 访问前强制 AuthN+AuthZ | Sidecar 强制拦截 |
| 7 | Collect as much info as possible to improve security posture | 全量收集行为数据，喂入决策 | 审计日志 → SIEM → UEBA |

```
NIST Zero Trust 落地映射:

  原则                    工程实现                     2026 主流工具
  ─────                  ──────────                  ──────────────
  ② 全部加密       →    自动 mTLS                →    Istio / Linkerd / Cilium
  ⑥ 强制认证       →    Sidecar / eBPF 拦截      →    Envoy / Cilium
  ④ 动态策略       →    Policy as Code           →    OPA / Cedar / OpenFGA
  ① 资源全保护     →    NetworkPolicy / IAM      →    Calico / Cilium / IAM
  ③ 短会话         →    Token 5min / Cert 24h    →    SPIRE / Vault
  ⑦ 全量行为       →    OTel + SIEM + UEBA       →    Tempo / Splunk / Chronicle
  ⑤ 完整性         →    SBOM + 签名 + Falco      →    Cosign / Trivy / Falco
```

接下来我们就深入"骨架"：服务身份（Identity）。

## 第 4 章：服务身份 —— SPIFFE / SPIRE 与 Istio Citadel

### 4.1 为什么服务需要"身份"

回到开篇问题 1：A 调 B，B 凭什么相信对方是 A？

朴素方案：
- **IP 白名单**：错。Pod IP 频繁变化、可被伪造（同节点容器）；
- **共享 Token**：错。Token 泄露即满盘皆输；
- **API Key**：错。难轮转、难撤销、易被记到日志。

工业界共识：**给每个服务一张可验证的"工牌"**，由可信第三方（CA）签发，且短期有效、自动轮转。这就是 **Service Identity（服务身份）**。

### 4.2 SPIFFE：服务身份的开放标准

**SPIFFE**（Secure Production Identity Framework For Everyone）是 CNCF 孵化的开放标准，2016 年提出、2018 年进入 CNCF，已成 Service Mesh 事实标准。

核心概念：

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| **SPIFFE ID** | 一个 URI 形式的全局唯一身份标识 | `spiffe://prod.company.com/ns/payments/sa/order-service` |
| **Trust Domain** | 信任域，类似"公司" | `prod.company.com` |
| **SVID** | SPIFFE Verifiable Identity Document，可验证的身份凭证 | X.509 或 JWT 形态 |
| **Workload API** | 工作负载用来获取自己 SVID 的本地 API | Unix Socket：`/run/spire/sockets/agent.sock` |

SPIFFE ID 的结构：

```
spiffe://[Trust Domain]/[Workload Selector]
        │              │
        │              └──── 一般编码 namespace + service account
        │
        └──── 信任域名（DNS 风格）

例:
  spiffe://prod.example.com/ns/orders/sa/order-svc
  spiffe://staging.example.com/ns/payments/sa/payment-svc
```

### 4.3 SVID 两种形态：X.509 vs JWT

SPIFFE 定义了两种 SVID 载体：

| 维度 | X.509 SVID | JWT SVID |
| --- | --- | --- |
| 形态 | 标准 X.509 证书 + 私钥 | 标准 JWT (header.payload.sig) |
| 主体字段 | SAN URI: `spiffe://...` | `sub` claim |
| 适用场景 | mTLS 服务间通信（首选） | HTTP/gRPC Header 透传、消息队列 |
| 验证方式 | 证书链 + 公钥 | 公钥 + JWKS |
| 是否能跨 Mesh | 不方便（需信任 CA） | 方便（公钥可分发） |
| 默认 TTL | 1 小时（可配） | 5-15 分钟 |

**最佳实践**：服务间用 X.509 SVID 做 mTLS，跨域/异构系统传递用 JWT SVID。

### 4.4 SPIRE：SPIFFE 的参考实现

**SPIRE**（SPIFFE Runtime Environment）是 SPIFFE 的官方参考实现，架构：

```
                     ┌──────────────────────────┐
                     │      SPIRE Server        │
                     │  - 根 CA / 中间 CA       │
                     │  - 节点注册表             │
                     │  - 工作负载注册表         │
                     └──────────┬───────────────┘
                                │ 节点认证（K8s SA Token / AWS IAM / GCP IID）
                ┌───────────────┼────────────────┐
                ▼               ▼                ▼
        ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
        │ SPIRE Agent │  │ SPIRE Agent │  │ SPIRE Agent │
        │  (Node 1)   │  │  (Node 2)   │  │  (Node 3)   │
        └──────┬──────┘  └──────┬──────┘  └──────┬──────┘
               │ Workload API   │                │
               ▼                ▼                ▼
        ┌──────────┐      ┌──────────┐      ┌──────────┐
        │ Pod: A   │      │ Pod: B   │      │ Pod: C   │
        │ ← SVID   │      │ ← SVID   │      │ ← SVID   │
        └──────────┘      └──────────┘      └──────────┘
```

工作流程：

1. SPIRE Server 启动，生成根 CA；
2. SPIRE Agent 在每个节点启动，通过 K8s SA Token 向 Server 证明"我是某节点上的合法 Agent"；
3. 业务 Pod 通过本地 Unix Socket 向 Agent 索取 SVID；
4. Agent 检查工作负载的属性（K8s namespace、SA、Pod label…），匹配预先注册的 SPIFFE ID 规则，返回 SVID；
5. SVID 在 TTL 过期前自动轮转（默认 1h）。

### 4.5 Istio Citadel：Service Mesh 内置 CA

如果你用 Istio，恭喜，Istio 内置的 **Citadel**（现已合并入 istiod）就是一个 SPIFFE 兼容的 CA：

- 自动为每个 Pod 注入 Sidecar（Envoy）；
- 自动签发 X.509 SVID，证书 SAN 字段为 `spiffe://cluster.local/ns/<ns>/sa/<sa>`；
- 默认证书 TTL 24 小时，到期前自动轮转；
- 全 mesh 内 mTLS，业务代码 0 感知。

```yaml
# Istio: 强制全 namespace mTLS
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: production
spec:
  mtls:
    mode: STRICT          # 必须 mTLS，否则 reject
```

这一招打开后，整个 namespace 内东西流量全部加密 + 强身份，业务代码零改动。**这就是 Service Mesh 之于 Zero Trust 的核心价值。**

## 第 5 章：mTLS —— 服务间双向认证加密

### 5.1 TLS 与 mTLS 的差异

|  | TLS（单向） | mTLS（双向） |
| --- | --- | --- |
| 客户端验证服务端 | ✅ | ✅ |
| 服务端验证客户端 | ❌ | ✅ |
| 适用场景 | 浏览器访问网站 | 服务间互信 |
| 性能开销 | 一次握手 ~5ms | 一次握手 ~7ms |
| 部署复杂度 | 中 | 高（手动）/ 低（Mesh 自动） |

### 5.2 手动 mTLS：那些年踩过的坑

如果不用 Mesh，手动实现 mTLS 你需要：

1. **CA 体系**：建立根 CA + 中间 CA，制定证书申请流程；
2. **证书签发**：为每个服务生成 CSR、签发证书、分发私钥；
3. **证书轮转**：定期重发，业务无感知重启或 hot reload；
4. **证书撤销**：CRL 或 OCSP，被入侵服务立即撤销；
5. **客户端验证**：每个服务端配置"允许哪些客户端 CN 调用我"；
6. **应用集成**：每种语言/框架都要对接（Java / Go / Python / Node…）。

我们在 2021 年某金融客户落地过手动 mTLS，**结论：极其痛苦**。一个 50 服务的集群，团队投入 2 个全职 SRE 用了 4 个月才稳定运行。任何一个新服务上线、任何一个证书过期，都可能引发故障。

### 5.3 Mesh 自动 mTLS：解放业务

Service Mesh（Istio / Linkerd / Cilium Service Mesh）把上面 6 步全都接管：

```
业务 Pod                              业务 Pod
┌──────────┐                          ┌──────────┐
│ App 容器 │ ───── 明文 localhost ──► │ Sidecar  │ ◄── 明文 localhost ─── 业务调用
│ (业务)   │ ◄──── 明文 localhost ─── │ (Envoy)  │ ───────► [上游服务]
└──────────┘                          └────┬─────┘
                                           │ mTLS（自动）
                                      ┌────▼──────────────────┐
                                      │  跨节点加密链路        │
                                      │  证书自动注入 + 轮转    │
                                      └────┬──────────────────┘
                                           │
                                      ┌────▼─────┐
                                      │ Sidecar  │
                                      │ (Envoy)  │
                                      └────┬─────┘
                                           │ 明文 localhost
                                      ┌────▼─────┐
                                      │ App 容器 │
                                      └──────────┘
```

业务收益：

- **业务代码不变**：客户端依然写 `http://payment-service/api/v1/pay`；
- **零配置加密**：Sidecar 自动 mTLS；
- **证书自动轮转**：Citadel 默认 24h（生产推荐 1-4h）；
- **零信任默认**：开启 STRICT 模式，未携带客户端证书直接 reject。

### 5.4 证书轮转：24h 还是 5min？

证书 TTL 越短越安全（被泄露的窗口越短），但越短对 CA 压力越大。常见配置：

| 场景 | 推荐 TTL | 原因 |
| --- | --- | --- |
| Istio 默认 | 24h | 兼顾性能与安全 |
| 金融生产 | 1-4h | 合规要求 |
| 顶级零信任（Google） | 5-30min | BeyondCorp 实践 |
| Vault 动态证书 | 1h-7d 可配 | 由策略决定 |

轮转流程（Istio 为例）：

```
T-0:        证书签发，TTL=24h
T-12h:      Citadel 在 TTL 一半时触发预轮转
T-12h+1s:   新证书签发，Sidecar 加载到内存
T-12h+2s:   新证书生效，旧证书继续支持已有连接到 TTL 结束
T-24h:      旧证书失效，被吊销
```

**关键陷阱**：业务代码自己缓存了 TLS Context（如 Java 的 `SSLContext` 单例），导致 Sidecar 切换证书后业务无感知、连接超时。**解决：始终通过 Sidecar 出站，业务代码不要持有 TLS 状态。**

## 第 6 章：用户身份 vs 服务身份 —— 两个世界的桥梁

mTLS 解决了**服务身份**问题（服务 A 调用服务 B 时，B 知道是 A），但还有一个完全不同的问题：**用户身份**（B 知道这是哪个**用户**发起的请求）。

### 6.1 两种身份的混淆

很多团队第一次做安全设计时容易犯一个错误：**用 JWT 同时充当服务身份和用户身份**。我们见过：

```
错误示例（金融客户 2022）:
  Gateway 拿用户 JWT，原封不动塞 header；
  Order 服务用同一个 JWT 调用 Payment 服务；
  Payment 服务以为这是用户在直接调用自己，把"user_id"当成"调用方身份"用于审计；
  → 一旦 Order 服务被攻陷，攻击者可以用任意用户 JWT 调用 Payment。
```

正确的心智模型：

| | 服务身份 | 用户身份 |
| --- | --- | --- |
| 主体 | 哪个服务（Workload） | 哪个人（User） |
| 载体 | X.509 SVID（mTLS 证书） | JWT / OIDC ID Token |
| 寿命 | 24h 或更短 | Access Token 15min，Refresh 30 天 |
| 信任来源 | 集群内 CA（Citadel/SPIRE） | IDP（Auth0 / Keycloak / Cognito） |
| 谁颁发 | 控制平面 | IDP（Identity Provider） |
| 何时验证 | 每次 mTLS 握手（Sidecar） | 业务层 / 网关层（OPA / 中间件） |

**两条线，不能混。** 一个请求里，两个 token 同时存在：

```
              ┌─── X.509 SVID (mTLS 客户端证书) → 验证服务身份
HTTP 请求 ────┤
              └─── Authorization: Bearer <JWT>   → 验证用户身份
```

### 6.2 OAuth 2.1 / OIDC 简明指南

OAuth 2.0（RFC 6749）仍是现行标准；**OAuth 2.1** 截至 2026 年仍是 Internet-Draft（draft-ietf-oauth-v2-1），尚未定稿，旨在合并安全最佳实践、淘汰 Implicit/ROPC。当下推荐流程：

| 场景 | 推荐流程 | 关键点 |
| --- | --- | --- |
| Web 应用（SPA + Backend） | Authorization Code + PKCE | 不要把 token 留在 SPA 内存外 |
| 移动 APP | Authorization Code + PKCE | App 内置浏览器 |
| 机器到机器（M2M） | Client Credentials | 服务自己有 client_id/secret |
| 设备登录（电视） | Device Code Flow | 用户扫码授权 |

OIDC = OAuth 2.0 + 身份信息层（ID Token）。颁发的 token 是 JWT，包含：

```json
{
  "iss": "https://auth.example.com",     // 颁发者
  "sub": "user-9527",                     // 用户 ID
  "aud": "order-service",                 // 受众
  "exp": 1717032000,                      // 过期
  "iat": 1717028400,                      // 颁发时间
  "scope": "order:read order:write",     // 权限
  "tenant_id": "t-1234",                  // 自定义 claim
  "roles": ["customer"]                   // 自定义 claim
}
```

### 6.3 User Context 在跨服务调用中的传递

```
                  Browser
                     │
                     │ Authorization: Bearer <user_jwt>
                     ▼
                  Gateway ── 验证 JWT 签名 / aud / exp
                     │
                     │ 注入：
                     │   x-user-id: 9527
                     │   x-tenant-id: t-1234
                     │   x-trace-id: abc-123
                     │ （以及原始 JWT 透传到 metadata）
                     │
                     ▼
                Order Service ─── mTLS 客户端证书：spiffe://.../sa/gateway
                     │            （服务身份）
                     │
                     │ 透传 x-user-id 等 + 原 JWT
                     ▼
              Payment Service ─── mTLS：spiffe://.../sa/order-svc
                     │
                     │ 再次验证 JWT
                     ▼
                   Database
```

**最佳实践**：

1. **Gateway 验签**：用户 JWT 验签放在网关，下游不重复验签（仅复用 claims）。除非有合规要求"端到端验签"。
2. **propagate 而非 trust**：下游服务不要"无脑信任"上游传来的 user_id，应该**仍然校验 JWT** 或 **用 trusted header + service identity 双重验证**。
3. **不要在 URL / log / 错误信息里裸露 token**：JWT 一旦进了日志，全员都能拿到，等于密码泄露。

## 第 7 章：授权 —— RBAC / ABAC / ReBAC

### 7.1 三种授权模型的边界

| 模型 | 决策依据 | 典型场景 | 表达能力 |
| --- | --- | --- | --- |
| **RBAC** | 角色 → 权限 | 后台管理系统 | 简单：粗粒度 |
| **ABAC** | 属性（user/resource/env） | 多租户、动态规则 | 中：基于条件 |
| **ReBAC** | 主体与对象间的"关系图" | 协作类（如 Google Docs） | 强：图遍历 |

### 7.2 RBAC：经典也最常被滥用

```
用户 → 角色 → 权限
1)  Alice 是 "admin"
2)  admin 拥有 "order:read, order:write, refund"
3)  Alice 因此能 read order, write order, refund
```

实现：一张 `user_role` 表 + `role_permission` 表 + 中间件拦截。

**典型陷阱**：

- 角色爆炸：50 个用户，硬生生发明出 200 个角色（"客服-华南-级别 2-退款 50 以下"）；
- 越权风险：忘记限制"数据范围"（admin 能读所有租户的数据）；
- 难审计：角色变动没记录，事后无法回溯"那一天 Alice 为什么有 X 权限"。

### 7.3 ABAC：更灵活，但配置心智重

```
决策：(user, action, resource, environment) → permit / deny

例:
  IF user.department == resource.owner_department
     AND environment.time BETWEEN 9:00 AND 18:00
     AND environment.network IN ("office", "vpn")
  THEN ALLOW
```

ABAC 通常用 **OPA**（Open Policy Agent）+ Rego DSL：

```rego
package authz

default allow = false

allow {
    input.user.tenant_id == input.resource.tenant_id
    input.action == "read"
    input.user.role[_] == "viewer"
}

allow {
    input.user.tenant_id == input.resource.tenant_id
    input.action in {"read", "write", "delete"}
    input.user.role[_] == "admin"
}
```

部署：OPA 作为 Sidecar 或集中服务，业务代码统一调用 `opa.eval(input)`。

### 7.4 ReBAC：协作类系统的最佳选择

2019 年 Google 公开 **Zanzibar 论文**（YouTube/Drive 的授权系统），开启 ReBAC 时代。核心思想：把权限建模为**关系图**：

```
(document:doc-42, owner, user:alice)
(document:doc-42, viewer, group:team-eng)
(group:team-eng, member, user:bob)

→ "Bob 能看 doc-42 吗？" 等价于图遍历：
   doc-42 → viewer → team-eng → member → bob   ✓
```

主流开源实现：

| 项目 | 出处 | 特点 |
| --- | --- | --- |
| **SpiceDB** | authzed | 直接对标 Zanzibar，最成熟 |
| **OpenFGA** | Auth0 / CNCF | 易用，文档好，2025-10 进入 Incubating |
| **Permify** | Permify Co | 后起之秀，社区活跃 |
| **Ory Keto** | Ory | Go 生态老牌 |

2025 年起，**OpenFGA 已成为协作型 SaaS 产品的默认选择**（Vercel、Linear、Notion 风格的产品）。

### 7.5 双层防护：网关 + 服务

```
                        网关层（粗粒度）
                  ┌────────────────────────────┐
                  │ - JWT 验签                  │
                  │ - 路径白名单 / 黑名单        │
                  │ - 用户角色基础检查           │
                  │ - 限流、IP 黑名单            │
                  └────────────┬───────────────┘
                               │
                               ▼
                       业务服务层（细粒度）
                  ┌────────────────────────────┐
                  │ - 资源级权限（only own）     │
                  │ - 状态机检查（订单必须是 X 态）│
                  │ - 多租户隔离                 │
                  │ - 业务规则                   │
                  └────────────────────────────┘
```

**规则**：

- 网关层做"宁可错过、不可错放"的快速过滤；
- 业务层做"精确判断"，因为它最懂业务语义；
- 不要把全部授权塞到网关 —— 网关不懂"这个订单是不是这个用户的"。

## 第 8 章：密钥管理 —— Vault 与 KMS

服务里总会有些"长期密钥"绕不开：数据库密码、第三方 API Key、加密用主密钥…

### 8.1 反模式：硬编码

```yaml
# ❌ 永远不要这样
spring:
  datasource:
    password: SuperSecret123!
```

或者：

```bash
# ❌ 也别这样
export DB_PASSWORD="SuperSecret123!"
docker run -e DB_PASSWORD=$DB_PASSWORD ...
```

理由：

- 进 Git → 全员可见；
- 进环境变量 → 进程列表、`/proc` 可见；
- 进容器镜像 → 镜像泄露即密码泄露；
- 难轮转 → 改密码 = 重发布。

### 8.2 正解：动态密钥 + 短期凭证

主流方案：

| 工具 | 出处 | 特色 |
| --- | --- | --- |
| **HashiCorp Vault** | HashiCorp | 开源 / 商业，最成熟 |
| **AWS Secrets Manager** / **KMS** | AWS | 与 IAM 深度集成 |
| **GCP Secret Manager** / **Cloud KMS** | GCP | 与 Workload Identity 集成 |
| **Azure Key Vault** | Azure | 与 Managed Identity 集成 |
| **External Secrets Operator** | CNCF | 把上述同步到 K8s Secret |

**Vault 动态数据库密码**示例：

```
应用 ─→ Vault Agent（Sidecar）
             │ 用 SPIFFE / K8s SA 认证
             ▼
         Vault Server
             │ 向数据库实时创建临时账号（TTL=1h）
             ▼
        生成账号：app-abc, 密码：xxxx
             │
             ▼
       应用拿到的密码 1h 后失效，Agent 自动续期
```

每次应用启动拿到一个**新创建的、1h 失效的、专属账号**。即使账号泄露，1 小时后失效；即使数据库被攻陷，无法溯源到具体的开发同学（因为是 Vault 创建的虚拟账号）。

### 8.3 K8s Secret 不够吗？

K8s 原生 Secret：

- 默认是 base64 编码（**不是加密**）；
- 存在 etcd，etcd 默认不加密；
- 所有命名空间下有 RBAC 权限的人都能 `kubectl get secret -o yaml`；

可选改进：

- 启用 **etcd encryption at rest**（K8s 1.13+）；
- 启用 **External Secrets Operator**，让真密钥留在 Vault/KMS；
- 启用 **Sealed Secrets** / **SOPS**，让密钥能安全进 Git。

但终极方案仍是：**让密钥不要进 K8s Secret，由 Workload Identity 直接到 Vault/KMS 拿。**

## 第 9 章：限流与 DoS 防护 —— 安全的一部分

很多人把"限流"归到可用性，其实它也是安全的关键防线。常见安全场景：

| 场景 | 攻击形态 | 限流策略 |
| --- | --- | --- |
| 撞库登录 | 暴力枚举密码 | 单 IP / 单账号 1 分钟 5 次 |
| 短信轰炸 | 调用 send-sms 接口刷别人手机 | 单手机号 1 小时 5 条 |
| 爬虫 | 高频拉商品 | 单 IP QPS 限制 |
| 慢攻击 | Slowloris、Slow POST | 连接数 + 超时双限 |
| 重放攻击 | 截获后重发 | 请求加 nonce + 时间戳 |
| API 滥用 | 拿到 Key 后狂调 | 按 API Key 限流 |

实现层级：

```
       L7 网关（Kong / APISIX / Envoy / Cloudflare）
            │  按 IP / Token / Path / 用户层级限流
            │  全局并发数
            │  WAF 规则（OWASP Top 10）
            ▼
       Service Mesh（可选）
            │  服务到服务的限流
            ▼
       业务服务内部
            │  Bucket / Token Bucket
            │  业务语义限流（"这个用户今天已发 3 条短信"）
```

详见 [精通限流熔断降级](./11-精通-限流熔断降级.md)。

## 第 10 章：审计日志 —— 出事时能不能追

合规的核心要求之一就是：**任何敏感操作必须有审计**。审计日志至少包含：

| 字段 | 示例 |
| --- | --- |
| timestamp | `2026-05-15T10:23:45.123Z` |
| actor.type | `user / service / system` |
| actor.id | `user:9527` / `service:order-svc` |
| actor.ip | `10.0.1.34` |
| service_identity | `spiffe://prod.x.com/ns/order/sa/order-svc` |
| action | `order.refund` |
| resource | `order:o-8800` |
| result | `success / denied` |
| reason | （若 denied）`tenant_mismatch` |
| trace_id | `abc-123-...` |
| request_id | `r-9527` |

**关键设计**：

1. **结构化**：JSON，避免日志里塞自然语言；
2. **不可篡改**：审计日志写入只追加（append-only）的存储或带 hash 链；
3. **集中**：所有服务写到 SIEM（Splunk / Elastic / Chronicle / Datadog Security）；
4. **保留周期**：等保 2.0 要求 ≥ 180 天，PCI-DSS ≥ 1 年；
5. **告警联动**：异常模式（如同账号 5 分钟登录失败 20 次）实时告警。

```
   各服务 ─── OTel Logs ───►  Collector ──►  Kafka  ──►  SIEM
                                                          │
                                                          ▼
                                                  规则引擎（UEBA）
                                                          │
                                                          ▼
                                                  告警 / 阻断
```

## 第 11 章：镜像与运行时安全

### 11.1 供应链：从源码到镜像

2024 年起，"软件供应链安全"（Software Supply Chain Security）成为头号关注。SLSA 框架定义了 4 个等级，主流工具：

| 阶段 | 工具 | 作用 |
| --- | --- | --- |
| 源码扫描 | **Semgrep / SonarQube** | 静态代码审计 |
| 依赖扫描 | **Dependabot / Renovate / OSV-Scanner** | 已知漏洞 |
| SBOM 生成 | **Syft** | 软件物料清单 |
| 镜像扫描 | **Trivy / Grype / Snyk** | CVE 检测 |
| 镜像签名 | **Cosign / Notation** | 防篡改 |
| 镜像准入 | **Kyverno / Gatekeeper / Connaisseur** | 拒绝未签名镜像 |

CI 中典型流水线：

```
Code ─► Lint ─► Test ─► Build ─► Trivy Scan ─► Cosign Sign ─► Push
                                       │
                                       └─ 高危 CVE → 阻断
```

K8s 准入：

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-signed-images
spec:
  validationFailureAction: Enforce
  rules:
    - name: verify-signature
      match:
        any:
          - resources:
              kinds: ["Pod"]
      verifyImages:
        - imageReferences:
            - "registry.company.com/*"
          attestors:
            - entries:
                - keys:
                    publicKeys: |-
                      -----BEGIN PUBLIC KEY-----
                      ...
                      -----END PUBLIC KEY-----
```

### 11.2 运行时：Falco / Tetragon

镜像扫得再干净，跑起来后被攻击者植入怎么办？**运行时安全**登场：

| 工具 | 实现 | 出处 |
| --- | --- | --- |
| **Falco** | eBPF + 内核审计 | CNCF Graduated |
| **Tetragon** | eBPF | Isovalent |
| **Sysdig Secure** | 商业 | Sysdig |

Falco 规则示例：

```yaml
- rule: Shell in Container
  desc: Detect shell spawn in a container
  condition: >
    container.id != host
    and shell_procs
    and proc.tty != 0
  output: >
    Shell spawned in container (user=%user.name container_id=%container.id
    container_name=%container.name shell=%proc.name)
  priority: WARNING
```

任何容器里被人开了 shell（无论入侵还是误操作），立刻告警。

## 第 12 章：完整案例 —— 30 服务集群从 0 到 1 落地安全

某 SaaS 客户，30 个微服务、3 个 K8s 集群（dev/stage/prod）、120 工程师。落地时间线如下：

### 阶段一（第 1 个月）：基线与方向

- 现状审计：mTLS 0 覆盖，95% 服务明文 HTTP；数据库密码硬编码 60%；无审计日志；
- 立项：3 个月内达到"Zero Trust 基本盘"；
- 选型：Istio（已有 mesh 经验）+ Vault（已有 secret 管理需求）+ OPA + Falco；

### 阶段二（第 2 个月）：mTLS 全覆盖

- 第 1 周：dev 环境开 `PERMISSIVE` 模式，允许 mTLS 与明文并存；
- 第 2-3 周：业务侧适配，把所有跨服务调用都过 Sidecar；
- 第 4 周：dev 切 `STRICT`，验证全部业务正常；
- 同步推进 stage 和 prod；

**踩坑**：
- Java 应用启动慢，Sidecar 比业务先 ready 才能让出口流量过去 → 用 `holdApplicationUntilProxyStarts: true`；
- 一些 legacy 系统（如 mainframe）不在 mesh 里 → 用 Egress Gateway 做边界 mTLS；

### 阶段三（第 3 个月）：JWT + RBAC + 审计

- 引入 Keycloak 做 IDP，统一管理用户身份；
- 网关层（Kong）做 JWT 验签 + 路由级 RBAC；
- 业务层用 OPA Sidecar 做细粒度授权；
- 所有服务接入 OTel Logs，统一打到 Splunk + 自建 SIEM；
- Falco 部署到所有节点，规则 50+；

### 阶段四（第 4-6 个月）：成熟度提升

- Trivy + Cosign 接入 CI/CD，未签镜像 K8s 拒绝；
- Vault 接管 80% 数据库账号，TTL 1h 自动轮转；
- 渗透测试，发现 2 个高危（一处未授权接口、一处 SSRF），修复；
- 通过 SOC 2 Type II 审计；

### 最终成果

| 指标 | 落地前 | 落地后 |
| --- | --- | --- |
| 服务间 mTLS 覆盖率 | 0% | 100%（STRICT） |
| 硬编码密钥 | 60% 服务 | 0% |
| 平均证书 TTL | N/A | 24h（自动轮转） |
| 平均检测攻击时间 | 不可知 | 30s（Falco + SIEM） |
| 合规认证 | 无 | SOC 2 + 等保 2.0 三级 |
| 安全相关 P1 故障 | 年 5 起 | 年 0 起 |

## 生产实践

1. **不要在 0 day 就上 STRICT mTLS**：先 PERMISSIVE 跑 2 周，观察日志里是否还有明文流量。
2. **JWT 不要塞太多业务数据**：保持 < 4KB，更多上下文走专门的 user-info 服务。
3. **服务身份和用户身份分两条线**：不要混用，更不要让下游"信任"上游传的 user_id 而不再验签。
4. **证书轮转必须可观测**：暴露 metric `certificate_expiry_seconds`，距离过期 < 2h 立刻告警。
5. **审计日志和业务日志分流**：审计日志单独写、不和业务 INFO 日志混在一起，便于合规拉取。
6. **OPA Policy 必须有单元测试**：Rego 是图灵完备的，错一个 `not` 整个 deny → allow，必须 `opa test`。
7. **Vault 必须 HA + 灾备**：Vault 挂了等于所有服务拿不到密码，必须 3 节点 Raft + 跨 AZ + 定期 snapshot。
8. **mTLS 不替代 WAF**：mTLS 解决"机密性+服务身份"，但 SQL 注入、XSS 还是要靠 WAF。
9. **不要给运维 Vault root token**：用 SSO + 短期 token + 双人复核。
10. **任何 namespace 默认 NetworkPolicy deny-all**：再按需开白。

---

## 陷阱清单

1. **以为开了 mTLS 就等于零信任**：mTLS 只解决"机密性+服务身份"，授权和审计还是要做。
2. **JWT 当成不可被滥用的"白纸"**：JWT 可被记到日志、可被中间人窃取（如果没 HTTPS），不是万能盾。
3. **共享同一个 JWT 通过整条调用链**：一旦某个服务被攻陷，攻击者拿到 JWT 可冒充用户。
4. **证书轮转后业务连接断**：业务代码自己缓存了 TLS Context，没用 Sidecar，证书一换就断。
5. **OPA 性能黑洞**：Policy 写得递归过深，每次决策耗时 100ms+，QPS 上不去。
6. **K8s Secret 当成保险柜**：base64 ≠ 加密，必须配合 etcd 加密 + Vault。
7. **审计日志写到本地磁盘**：节点挂了日志没了，必须实时打到中心化存储。
8. **没有 break-glass 账号**：所有人都通过 SSO，SSO 挂了运维进不来，必须留一个本地 emergency 账号。
9. **Vault 跑在自己保护的 K8s 集群里**：Vault 挂了等于密钥拿不到，K8s 又依赖 Vault 起不来，死锁。
10. **以为 Istio AuthorizationPolicy 默认 deny**：默认是 allow，必须显式加 deny-all + 按需 allow。
11. **服务被攻陷后没有"撤销"机制**：必须能 1 分钟内吊销证书 + 撤销 JWT + 撤销 DB 账号。
12. **跨域 mTLS 信任问题**：多集群、多 mesh 互通时，互信关系（TrustBundle）配置极易出错。

---

## 2026 现状

1. **Spiffe/Spire 成 CNCF Graduated**：服务身份标准已稳定，Istio/Linkerd/Consul/Cilium 全兼容。
2. **eBPF 成为新一代 mTLS 载体**：Cilium Service Mesh 用 eBPF 做透明 mTLS，性能比 Envoy Sidecar 高 30%+。
3. **零信任成为合规默认**：SOC 2、PCI-DSS、等保 3.0 已把 Zero Trust 作为隐含要求。
4. **OpenFGA / SpiceDB 进入主流**：Notion、Linear、Vercel 风格的产品几乎都用 ReBAC。
5. **AI 模型的服务身份**：LLM 也作为一种 workload，被纳入 SPIFFE 体系，限制其能调的下游 API。
6. **Confidential Computing 起飞**：AWS Nitro Enclaves、Intel TDX、AMD SEV-SNP 让内存也加密，敏感数据可在云上端到端加密。
7. **WASM 沙箱成为新边界**：插件化系统（如 Envoy、Kong）大量使用 WASM，沙箱内做加密计算。
8. **AI 辅助安全运营**：SIEM + LLM 自动生成检测规则、自动总结告警，SOC 工程师工作量大幅下降。
9. **Vault Enterprise 与 OpenBao 分裂**：HashiCorp 转 BSL 协议后社区 fork 出 OpenBao，2025 进入 Linux Foundation。
10. **多云身份联邦**：跨 AWS/GCP/Azure 的 Workload Identity Federation 已成标准。

## 参考答案

1. **从登录到下单的全链路安全机制**
   - 浏览器→IDP：OIDC Authorization Code + PKCE 获取用户 JWT（用户身份）。去掉则任何人可冒充登录。
   - 浏览器→Gateway：HTTPS/TLS + 网关 JWT 验签（aud/exp/签名）+ 登录/下单限流。去掉验签则伪造 token 直接进；去掉限流则撞库/刷单。
   - Gateway→Order→Payment 等各跳：mTLS（X.509 SVID 服务身份）+ 透传 user 上下文，下游仍校验 JWT 或 trusted-header + 服务身份双验。去掉 mTLS 则内网可窃听/伪装横向移动；无脑信任上游 user_id 则一个服务被攻陷即可冒充任意用户。
   - 各跳：RBAC/ABAC 资源级授权（订单属于该用户、租户隔离）。去掉则越权访问他人订单。
   - 全程：结构化审计日志写 SIEM。去掉则出事无法追溯。

2. **20 服务集群的身份设计要点**
   - Trust Domain：按环境隔离，如 `prod.company.com` / `stage.company.com` / `dev.company.com`，跨域不互信。
   - SPIFFE ID 命名：`spiffe://<trust-domain>/ns/<namespace>/sa/<service-account>`，按 namespace + SA 编码。
   - 证书 TTL：dev 24h、prod 1-4h（金融更短），到期前自动轮转。
   - PeerAuthentication 设 `mtls.mode: STRICT`（先 PERMISSIVE 过渡）；AuthorizationPolicy 默认 deny-all 再按 principal（SPIFFE ID）显式 allow 调用关系。

3. **用户 JWT 泄露的应急**
   撤销：将该用户 refresh token 失效、对 access token 加入黑名单/降低 TTL，强制重新登录；通知：告知用户、安全团队，触发 incident；审计：用 trace_id/user_id 在 SIEM 回溯该 token 的所有调用，评估是否已被滥用；防后续：缩短 access token TTL、引入 token binding（DPoP/mTLS-bound token）、对异常行为（异地、UEBA）实时告警与阻断。

4. **服务 A 的 SPIFFE 私钥被窃**
   攻击者可冒充 A 发起 mTLS，调用 A 被授权的下游。发现：SIEM/审计中 A 的身份出现异常来源 IP、异常调用模式，Falco 检测容器内异常进程。撤销：吊销该 SVID（短 TTL 让其快速失效）、重签、轮换私钥。防横向移动：AuthorizationPolicy 最小授权（A 只能调它该调的）+ NetworkPolicy deny-all + 各下游仍独立鉴权，使拿到 A 身份也无法越权访问 DB/其他高价值服务。

5. **多租户 SaaS 三种授权模型对比**
   - RBAC：用户→角色→权限 + 租户隔离字段。落地最简单、性能高，但角色易爆炸、细粒度（资源级/数据范围）弱。
   - ABAC：基于 (user, action, resource, env) 属性用 OPA/Rego 决策，适合动态规则与租户隔离；落地配置心智重、策略需单测、复杂策略有性能开销。
   - ReBAC：用关系图（Zanzibar/OpenFGA/SpiceDB）建模，适合协作/共享类资源；表达力最强、可做图遍历，但引入额外授权服务、运维与一致性成本最高。

6. **高危依赖 `is-promise@2.2.2` 的评估与应对**
   评估：看该 CVE 的可达性（项目是否真的调用了脆弱代码路径）、严重程度、是否有补丁版本、是直接依赖还是传递依赖。应对：能升级则升级到修复版（用 Renovate/Dependabot）；无补丁则评估替换包、加缓解措施或临时 pin + 加 CI 抑制并记录例外；高危且可达且无解时阻断构建。配合 SBOM（Syft）确认影响面。

7. **Vault 崩溃导致全断的事后改造**
   - Vault HA：3 节点 Raft + 跨 AZ 部署，定期 snapshot 灾备。
   - 解耦死锁：Vault 不部署在它所保护、且 K8s 又依赖它才能启动的集群里（避免循环依赖）。
   - 客户端弹性：应用本地缓存上一次有效凭证并在 Vault 不可用时续用到 TTL，Agent 自动续期重试。
   - 应急：保留 break-glass 机制与离线 unseal key 分片（多人持有）。

8. **5 条 Falco 规则（要点）**
   - 容器内起 shell：`container.id != host and proc.name in (bash,sh,zsh) and proc.tty != 0`。
   - 读取 /etc/shadow：`open_read and fd.name = /etc/shadow and container.id != host`。
   - 写入 /etc/cron：`open_write and fd.name startswith /etc/cron and container.id != host`。
   - 出站到非白名单 IP：`outbound and not fd.sip in (allowed_ips)`。
   - 加载内核模块：`evt.type in (init_module, finit_module)`。
   每条配 output（带 user/container/proc）+ priority。

9. **未鉴权 `/admin/dump-users` 一周加固（分层）**
   - 立即（网络层）：用 NetworkPolicy/防火墙把该接口限制到内网/运维网段，或先下线该路由止血。
   - 网关层：加 JWT 验签 + 路径级 RBAC（仅 admin 角色），并加限流与审计。
   - 业务层：接口内做细粒度授权（校验角色 + 租户范围）、对敏感数据脱敏/分页，记录审计日志。
   - 收尾：渗透验证、加自动化测试防回归。

10. **8 周渐进式零信任路线图（单体小团队）**
    - 第1周：现状审计（明文流量、硬编码密钥、无审计点）+ 制定目标与选型。
    - 第2周：全链路启用 HTTPS/TLS，对外接口统一走网关。
    - 第3周：引入 IDP（如 Keycloak），统一用户登录与 JWT 验签（网关层）。
    - 第4周：清理硬编码密钥，接入 Vault/Secret 管理，密钥短期化。
    - 第5周：网关层加 RBAC + 限流（撞库/短信轰炸防护）。
    - 第6周：接入结构化审计日志到集中存储/SIEM，关键操作留痕。
    - 第7周：CI 引入依赖/镜像扫描（Trivy/OSV）+ 镜像签名。
    - 第8周：部署运行时安全（Falco）+ NetworkPolicy deny-all 按需开白，复盘并做一次渗透测试。
