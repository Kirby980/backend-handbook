## 引言：韧性是组合艺术

2007 年 Michael Nygard 写《Release It!》时，提出了一组应对分布式故障的"稳定模式"。十几年过去了，这些模式没有过时——反而成了每一个微服务工程师的"工具腰带"。

韧性设计模式不是一个模式能解决问题，**是一组模式按规则组合在一起才能解决问题**：

```
   一次远程调用 = Timeout + Retry + Circuit Breaker + Bulkhead + Fallback + Deadline + ...
```

如果说 [M11](./11-精通-限流熔断降级.md) 讲的是"如何防自己/防下游被打挂"，**这一章讲的是"如何把一次脆弱的远程调用变成一次可生还的调用"**。

读完之后你应该能：

- 给"一个调用 5 个下游"的核心接口设计一套完整的韧性策略
- 解释为什么 Timeout 必须存在、上下游 timeout 怎么排
- 用 Retry + Backoff + Jitter 而不是裸 Retry
- 区分 Bulkhead 的三种实现（连接池、线程池、信号量）
- 用 Hedged Request 压低 P99 latency
- 解释 Deadline 在 gRPC 链路上为什么必须自动传播

## 第一章：韧性的 8 大模式全景

### 1.1 模式清单

Nygard 的原书有 11+ 个，但工业界共识的"必知 8 个"如下：

| 模式 | 一句话 | 防的是 |
|---|---|---|
| **Timeout** | 任何远程调用必须有超时 | 下游卡死把自己拖死 |
| **Retry** | 失败后用指数退避 + 抖动重试 | 瞬时故障 |
| **Circuit Breaker** | 失败率高就断开调用 | 下游持续不可用把自己打爆 |
| **Bulkhead** | 资源隔离 | 一个慢调用占光所有资源 |
| **Fallback** | 失败时返回兜底 | 用户看到 5xx |
| **Steady State** | 自我清理 | 资源累积 OOM |
| **Fail Fast** | 早失败胜过慢失败 | 不必要的等待占资源 |
| **Hedged Request** | 双发请求，谁快用谁 | 尾延迟 |

### 1.2 模式之间的关系

```
                   一次请求生命周期
   开始 →  [Fail Fast 检查]  →  [Bulkhead 获取资源]
              ↓ 失败                ↓ 失败
          直接拒绝               拒绝（资源耗尽）
              ↓                     ↓
        [Circuit Breaker 检查]   [Timeout 启动]
              ↓ Open                ↓
          走 Fallback           [Retry 包裹]
              ↓                     ↓
                              [Hedged Request 双发]
                                    ↓
                                调用下游
                                    ↓
                               成功 → 返回
                                    ↓
                              失败 → Fallback
```

每个模式是一道关卡，组合在一起构成"远程调用的防御工事"。

### 1.3 8 个模式的核心配比

不是每个调用都要用全 8 个：

| 调用类型 | Timeout | Retry | CB | Bulkhead | Fallback | Hedged |
|---|---|---|---|---|---|---|
| 核心强依赖（支付）| 必须 | 仅幂等 | 必须 | 必须 | 必须 | 视场景 |
| 旁路弱依赖（推荐）| 必须 | 必须 | 必须 | 必须 | 必须 | 可选 |
| 内部 RPC | 必须 | 视场景 | 必须 | 视场景 | 视场景 | 不需要 |
| 第三方 API | 必须 | 必须 | 必须 | 必须 | 必须 | 不需要 |

## 第二章：Timeout — 一切韧性的根基

### 2.1 没 Timeout 的代价

任何远程调用没有 Timeout = 调用者把"是否完成"的决定权完全交给被调者。被调者卡住 → 调用者卡住 → 一传十、十传百 → 雪崩。

**真实案例**：2014 年 Cassandra Java Driver 默认 socket timeout = 12 秒。一次 Cassandra 慢查询 → 调用方所有线程被卡 12 秒 → 服务彻底瘫痪。

### 2.2 Timeout 的三个层次

```
+--------------------------------+
| Application Timeout            |  业务定义"最多等多久"
+--------------------------------+
| Library / HTTP Client Timeout  |  库级别（连接、读、写、整体）
+--------------------------------+
| OS / Socket Timeout            |  操作系统 TCP 层
+--------------------------------+
```

**必须三层都配**——任何一层没配就可能卡死。

### 2.3 HTTP Client 的四种 Timeout

| Timeout | 含义 | 典型值 |
|---|---|---|
| **Connect Timeout** | TCP 三次握手最长时间 | 1-3s |
| **TLS Handshake Timeout** | TLS 握手 | 1-3s |
| **Read Timeout** | 单次读阻塞最长时间 | 5-30s |
| **Total Timeout** | 整个请求最长时间 | 业务决定 |

Go 示例：

```go
client := &http.Client{
    Timeout: 10 * time.Second,          // total
    Transport: &http.Transport{
        DialContext: (&net.Dialer{
            Timeout:   2 * time.Second,  // connect
            KeepAlive: 30 * time.Second,
        }).DialContext,
        TLSHandshakeTimeout:   3 * time.Second,
        ResponseHeaderTimeout: 5 * time.Second,
        ExpectContinueTimeout: 1 * time.Second,
        IdleConnTimeout:       90 * time.Second,
    },
}
```

**陷阱**：`http.Client.Timeout` 是整体超时，但 `http.DefaultClient` 默认 = 0（无超时）。Go 代码里经常一行 `http.Get(url)`，**默认就是无超时**。

### 2.4 上下游 Timeout 排序原则

**核心规则**：上游 timeout ≥ 下游 timeout + 该层处理时间。

```
   User → Gateway → ServiceA → ServiceB → DB
          10s        9s         5s         2s
```

为什么？如果上游 timeout < 下游：

```
   User → Gateway (5s timeout) → ServiceA (10s timeout) → ServiceB → DB
```

- Gateway 5 秒后超时返回用户 504
- 但 ServiceA 还在等 ServiceB（最长 10s）
- ServiceA 的连接还占着 → 浪费资源
- ServiceA 处理完结果谁也不要 → "无用功"

**正确做法**：下游 timeout 略小于上游剩余时间，让下游"知道自己已经没意义"提前 abort。

### 2.5 Deadline Propagation（最优解）

更优雅的方案：不传 timeout 值，传 **deadline**（绝对时间戳）。

gRPC 自动做这件事：

```go
// Gateway
ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
serviceAClient.Process(ctx, req)
// gRPC 把 deadline = now+10s 编码到 metadata "grpc-timeout"

// ServiceA 收到时
// ctx 自带 deadline，调 ServiceB 时传同一个 ctx
ctx, _ := context.WithTimeout(ctx, 5*time.Second)
// 实际生效时间 = min(剩余 deadline, 5s)
serviceBClient.Compute(ctx, req2)
```

整个调用链每一跳都能看到"还剩多少时间"，到期立刻 abort。

**HTTP 没原生 deadline，需要手动注入 header**：

```
X-Deadline-Ms: 1716800000000  (UNIX 毫秒)
```

下游服务读这个 header 算自己的 budget。

### 2.6 Timeout 与重试的相互作用

```
total budget = 1s
retry = 3 次

如果每次都用 total budget = 1s
→ 第一次跑了 1s 失败 → 重试 → 第二次跑了 1s 失败 → ...
→ 实际耗时最长 3s，违反 budget

正确做法：
total budget = 1s
single attempt timeout = 300ms
retry = 3 次（最多 900ms < 1s）
```

**重试时 timeout 要算 budget**。

## 第三章：Retry — 不只是简单的循环

### 3.1 何时可以重试

| 场景 | 能重试吗 |
|---|---|
| 网络超时 | ✓ |
| 503 / 502 | ✓ |
| 429（限流）| ✓ 但要看 Retry-After |
| 504 | ✓ |
| 4xx（业务错误）| ✗ |
| 500（语义不明）| 视情况，一般 ✗ |
| 写操作 + 不幂等 | ✗ |

**第一原则**：不幂等的操作不能盲目重试。见 [M09 幂等与去重](./09-精通-幂等与去重.md)。

### 3.2 退避策略

#### 3.2.1 固定间隔（最差）

```
fail → wait 1s → retry → wait 1s → retry → ...
```

问题：N 个客户端同时失败，N 个同时重试 → **羊群效应（thundering herd）**

#### 3.2.2 指数退避（Exponential Backoff）

```
fail → wait base × 2^0 → retry
fail → wait base × 2^1 → retry
fail → wait base × 2^2 → retry
...
```

base=100ms：100ms → 200ms → 400ms → 800ms → 1.6s → ...

问题：N 个客户端**同步指数退避** → 还是同时重试 → 羊群效应缓解但没消除。

#### 3.2.3 指数退避 + 抖动（Jitter）

AWS 在 2015 年总结的最佳实践：

```
sleep = random(0, base × 2^attempt)
```

```python
import random

def backoff(attempt, base_ms=100, cap_ms=20000):
    return random.uniform(0, min(cap_ms, base_ms * (2 ** attempt))) / 1000
```

**为什么 Jitter 重要**：把"所有人同时重试"打散成"在区间内均匀分布"——下游被均匀分摊。

#### 3.2.4 Decorrelated Jitter（去相关抖动）

更进一步——下次 sleep 基于上次 sleep：

```python
def decorrelated_jitter(prev_sleep_ms, base_ms=100, cap_ms=20000):
    return min(cap_ms, random.uniform(base_ms, prev_sleep_ms * 3))
```

避免连续多次都抽到小值的尾部风险。

### 3.3 Go 实现完整 Retry

```go
type RetryOpts struct {
    MaxAttempts int
    BaseDelay   time.Duration
    MaxDelay    time.Duration
    Retryable   func(error) bool
}

func Retry(ctx context.Context, opts RetryOpts, fn func() error) error {
    var err error
    for attempt := 0; attempt < opts.MaxAttempts; attempt++ {
        if err = fn(); err == nil {
            return nil
        }
        if !opts.Retryable(err) {
            return err
        }
        if attempt == opts.MaxAttempts-1 {
            break
        }
        // Jittered exponential backoff
        max := time.Duration(math.Min(
            float64(opts.MaxDelay),
            float64(opts.BaseDelay)*math.Pow(2, float64(attempt)),
        ))
        sleep := time.Duration(rand.Int63n(int64(max)))
        select {
        case <-time.After(sleep):
        case <-ctx.Done():
            return ctx.Err()
        }
    }
    return err
}

// 使用
err := Retry(ctx, RetryOpts{
    MaxAttempts: 3,
    BaseDelay:   100 * time.Millisecond,
    MaxDelay:    2 * time.Second,
    Retryable: func(err error) bool {
        if errors.Is(err, context.DeadlineExceeded) {
            return false  // deadline 到了不重试
        }
        var httpErr *HTTPError
        if errors.As(err, &httpErr) {
            return httpErr.Code == 503 || httpErr.Code == 504
        }
        return true
    },
}, func() error {
    return callService(ctx)
})
```

### 3.4 Retry 失控的经典场景

```
   A → B → C
```

- A 调 B 重试 3 次
- B 调 C 重试 3 次
- C 调 DB 重试 3 次

C 挂了 → DB 没回 → C 重试 3 次失败 → B 收到一次失败 → B 重试 3 次 → 每次又重试 3 次 = 9 次 → A 收到一次失败 → A 重试 3 次 → 每次 9 次 = **27 次**

**结论**：链路上每层都重试 = 倍数级放大。

**修复**：

1. **重试预算（retry budget）**：每条链路只允许 1 层重试（一般在最接近问题源头的那层）
2. **退避协调**：重试时带 `Retry-Attempt-Count` header，下游知道这是第 N 次重试 → 不再重试
3. **Token Bucket 限制重试速率**：客户端总重试不超过总请求的 10%

gRPC 内置 retry policy 支持 `attempts` 上限 + 集群侧 RetryThrottling：

```json
{
  "methodConfig": [{
    "name": [{"service": "Payment"}],
    "retryPolicy": {
      "maxAttempts": 3,
      "initialBackoff": "0.1s",
      "maxBackoff": "1s",
      "backoffMultiplier": 2.0,
      "retryableStatusCodes": ["UNAVAILABLE"]
    }
  }],
  "retryThrottling": {
    "maxTokens": 10,
    "tokenRatio": 0.1
  }
}
```

### 3.5 Idempotency Key 与 Retry 的组合

不幂等的写操作怎么安全重试？

```
client → 生成 idempotency_key = uuid
       → 请求 header: Idempotency-Key: <key>
       → 服务端：
            - 看到这个 key 已存在 → 返回上次结果（不重复执行）
            - 没看到 → 执行 + 存储 key 与结果（24h TTL）
```

Stripe 的 API 全部支持 `Idempotency-Key` header，客户端可以放心重试。详见 [M09 幂等与去重](./09-精通-幂等与去重.md)。

## 第四章：Circuit Breaker — 与 Bulkhead 配合

熔断器的原理在 [M11 第六章](./11-精通-限流熔断降级.md) 已经讲过状态机和参数。**这一节聚焦"从应用视角怎么用"**。

### 4.1 熔断器粒度

```
                wrong                    right
[App] -[CB]- [Service B]    [App] -[CB-1]- [Service B endpoint X]
                            [App] -[CB-2]- [Service B endpoint Y]
                            [App] -[CB-3]- [Service C endpoint Z]
```

**粒度原则**：每个"下游故障域"一个熔断器。最细到下游的 endpoint，至少到下游的 service。

### 4.2 熔断器 + 重试的顺序

```
请求 → 熔断器检查 →（Closed）→ 重试包裹 → 调用
                              ↘ 重试也走熔断器吗？
```

**关键判断**：重试**算不算**给熔断器贡献一次"失败"？

**Resilience4j 的做法**：默认每次重试都进入熔断器统计——3 次重试都失败 = 熔断器看到 3 次失败。
**优点**：失败更快被熔断
**缺点**：放大失败率

**推荐做法**：把 Retry 放在熔断器**外面**：

```go
err := Retry(ctx, opts, func() error {
    return cb.Execute(func() error { return call() })
})
```

- 熔断器跳了 → Retry 看到 ErrCircuitOpen → 不应该再 retry（fail fast）
- 修改 Retryable：`err == ErrCircuitOpen` 返回 false

### 4.3 Half-Open 试探请求

Half-Open 时允许少量"试探请求"过去：

- 允许并发？通常 1-5 个，**不允许 100 个**（避免下游刚恢复又被打挂）
- 试探请求是真实业务请求还是合成请求？通常用真实请求（更准）；金融场景可能用合成请求避免影响用户

### 4.4 共享熔断器陷阱

```go
// 错误：一个 service 共用一个熔断器
var paymentCB = gobreaker.NewCircuitBreaker(...)

func PayCard(req) {
    paymentCB.Execute(...)
}
func PayWallet(req) {
    paymentCB.Execute(...)
}
// 卡支付挂了 → 钱包支付也被熔
```

**正确**：

```go
var (
    payCardCB   = gobreaker.NewCircuitBreaker(... name="pay-card")
    payWalletCB = gobreaker.NewCircuitBreaker(... name="pay-wallet")
)
```

## 第五章：Bulkhead — 资源隔离

### 5.1 名字的由来

Bulkhead = 船舶的水密舱壁。一个舱进水，其他舱不受影响 → 船不沉。

软件里：一个调用慢了 / 一个依赖卡住了，**不要把所有的资源（线程、连接、内存）都搭上**——给每个故障域分独立的"资源池"。

```
   错误：所有调用共享一个线程池
   +---------+
   | 100 线程|
   +---------+
   | 调用 A  |  ← A 慢了，占了 90 个线程
   | 调用 A  |
   | 调用 B  |  ← B 只能用剩下的 10 个 → B 也变慢
   +---------+

   正确：每个依赖独立
   +-------+  +-------+  +-------+
   | A: 40 |  | B: 40 |  | C: 20 |
   +-------+  +-------+  +-------+
   A 慢只占自己的 40 个，B、C 不受影响
```

### 5.2 Bulkhead 的三种实现

#### 5.2.1 线程池隔离（Thread Pool）

每个依赖一个独立的线程池。调用走该线程池，线程池满 = 该依赖请求被拒。

**优点**：完全隔离，A 的慢不影响 B。
**缺点**：线程是昂贵资源（每个 1MB 栈 + 上下文切换开销），创建很多线程池开销大。

Hystrix 历史包袱：Hystrix 默认每个依赖独立线程池，最多几百个。一台 8C 机器跑 1000 个线程池 → CPU 全在做上下文切换 → **业务还没跑性能就掉了**。Hystrix 2018 停止维护与此有关。

#### 5.2.2 信号量隔离（Semaphore）

不用独立线程，用计数器：

```java
Semaphore sem = new Semaphore(50);  // 允许 50 并发
if (!sem.tryAcquire()) {
    return fallback();  // 满了，拒绝
}
try {
    return call();
} finally {
    sem.release();
}
```

**优点**：开销极小。
**缺点**：调用还是在调用方线程里同步执行 → 如果调用慢，调用方线程还是被阻塞。

适用：调用是**非阻塞的**（异步 HTTP / 协程）；或者主要目的是**计数限流**而非完全隔离。

#### 5.2.3 连接池隔离（Connection Pool）

每个下游一个独立的 HTTP / DB 连接池：

```go
var (
    paymentHTTP = &http.Client{Transport: &http.Transport{MaxIdleConnsPerHost: 50}}
    userHTTP    = &http.Client{Transport: &http.Transport{MaxIdleConnsPerHost: 50}}
)
```

**优点**：天然隔离，每个连接池独立耗尽。
**缺点**：连接池满时新请求要等（默认行为）—— 必须配 `MaxConns` + 满时 fail fast。

### 5.3 Resilience4j Bulkhead

```java
BulkheadConfig config = BulkheadConfig.custom()
    .maxConcurrentCalls(50)
    .maxWaitDuration(Duration.ofMillis(100))
    .build();

Bulkhead bulkhead = Bulkhead.of("payment", config);

Try.ofSupplier(Bulkhead.decorateSupplier(bulkhead, () -> paymentService.pay()))
   .recover(throwable -> fallback());
```

`maxWaitDuration` = 满了愿意等多久——一般 0（立即拒），避免堆积。

### 5.4 Go 协程池实现 Bulkhead

Go 协程便宜（栈 2KB），但下游连接还是有限的：

```go
type Bulkhead struct {
    sem chan struct{}
}

func New(max int) *Bulkhead {
    return &Bulkhead{sem: make(chan struct{}, max)}
}

func (b *Bulkhead) Do(ctx context.Context, fn func() error) error {
    select {
    case b.sem <- struct{}{}:
        defer func() { <-b.sem }()
        return fn()
    case <-ctx.Done():
        return ctx.Err()
    default:
        return ErrBulkheadFull  // 立即拒
    }
}

// 使用
paymentBulkhead := New(50)
err := paymentBulkhead.Do(ctx, func() error {
    return callPayment(ctx)
})
```

### 5.5 连接池配置最佳实践

| 参数 | 推荐 | 说明 |
|---|---|---|
| `MaxIdleConnsPerHost` | 50-200 | 单个目标 host 空闲连接池 |
| `MaxConnsPerHost` | = MaxIdleConnsPerHost × 2 | 总连接上限（含活跃）|
| `IdleConnTimeout` | 90s | 空闲多久关闭 |
| `KeepAlive` | 30s | TCP keepalive |

DB 连接池（Go database/sql）：

```go
db.SetMaxOpenConns(100)
db.SetMaxIdleConns(20)
db.SetConnMaxLifetime(30 * time.Minute)
db.SetConnMaxIdleTime(5 * time.Minute)
```

`MaxOpenConns` 必须配——否则突发会创建无数连接打爆 DB。

## 第六章：Fallback — 降级返回

Fallback 的核心策略在 [M11 第七章](./11-精通-限流熔断降级.md) 已经讲过。**本节聚焦工程实现**。

### 6.1 Fallback 链式

通常不是只有一个 fallback，而是层层降级：

```
真实调用 → 失败 → 本地缓存 → 失败 → 静态默认值 → 失败 → 兜底错误
```

```go
func GetUser(ctx context.Context, uid int64) (*User, error) {
    // 1. 远程
    u, err := userClient.Get(ctx, uid)
    if err == nil {
        cache.Set(uid, u, 1*time.Hour)
        return u, nil
    }

    // 2. 本地缓存
    if u, ok := cache.Get(uid); ok {
        metric.Inc("user.fallback.cache")
        return u, nil
    }

    // 3. 静态默认
    metric.Inc("user.fallback.default")
    return &User{ID: uid, Name: "Guest"}, nil
}
```

### 6.2 Fallback 必须比正常路径更快

**反例**：Fallback 查另一个数据库表，结果那个表也慢 → Fallback 比正常调用还慢 → 雪上加霜。

**原则**：Fallback 路径必须**纯内存**或**确定快**的：

- 内存缓存（命中即返回）
- 静态文件 / 常量
- 本地 SQLite 或 BoltDB 镜像数据

### 6.3 Fallback 的可观测

```go
metric.Inc("call.fallback", "service", "user", "type", "cache")
logger.Warn("fallback triggered",
    "service", "user",
    "reason", err.Error(),
    "trace_id", traceID,
)
```

仪表盘上应该有"fallback 比例"，超过阈值告警。

### 6.4 Fallback 的副作用

**警告**：Fallback 路径如果有副作用（写库、发消息），事故时被频繁触发会**放大问题**。

**反例**：

```go
// fallback 把请求写到本地队列待处理
func GetUser(ctx context.Context, uid int64) (*User, error) {
    u, err := remoteCall(ctx, uid)
    if err != nil {
        localQueue.Push(uid)  // 副作用！
        return cache.Get(uid)
    }
    return u, nil
}
// 下游挂了 → 100w 请求 → 100w 条 push 到 localQueue → 队列爆了
```

Fallback 应该是**只读、无副作用、O(1)**。

## 第七章：Steady State — 自我清理

### 7.1 资源累积的"癌症"

Nygard 强调：很多系统不是被流量打爆的，是被自己慢慢积累的"垃圾"撑死的：

- 日志文件越写越大 → 磁盘满
- 缓存只进不出 → OOM
- 长连接没清理 → 文件句柄耗尽
- 临时文件没删 → inode 耗尽
- 数据库历史数据没归档 → 慢查询
- 死连接没关 → 连接池被占

### 7.2 清理机制

每一个"可能累积"的资源都要有自动清理：

| 资源 | 清理策略 |
|---|---|
| 日志 | logrotate + 保留 N 天 |
| 缓存 | LRU + TTL |
| 临时文件 | 后台 cron 删 |
| 历史数据 | 分区表 + 自动 drop 旧分区 |
| 死连接 | TCP keepalive + 连接池空闲超时 |
| Goroutine 泄漏 | 监控 `goroutine_count` |
| 文件句柄 | 监控 `fd_count` |

### 7.3 健康检查与自愈

Steady State 的现代实现 = Kubernetes 的健康检查：

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 60
  periodSeconds: 10
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /readyz
    port: 8080
  periodSeconds: 5
```

`/healthz` 失败 → kubelet 重启 Pod → "脏"的进程被替换。这是 **Steady State 的容器化版本**——不指望应用永远稳，而是出问题就重启。

### 7.4 真实案例

某金融服务有个 bug：异常路径下 `*sql.Rows` 没 `Close()`。低频路径，每天泄漏几十个连接。

- 第 1 天：连接池 100/100 健康
- 第 7 天：连接池 200/250 警告
- 第 30 天：连接池打满 → DB 拒绝新连接 → 服务挂

Steady State 的修复：

1. 每个 `Query()` 必须 `defer rows.Close()`（代码规范 + linter）
2. DB 连接池配 `ConnMaxLifetime` = 30 分钟，强制定期换新连接
3. 监控 `db_open_connections`，达到 80% 告警

## 第八章：Fail Fast — 早失败胜于慢失败

### 8.1 哲学

"如果你早晚要失败，请尽早失败。"

**慢失败 = 占资源 + 用户等待 + 调用链上下游连带受影响。**
**早失败 = 立即返回错误，资源立即释放，用户立即知道。**

### 8.2 Fail Fast 的实现

```
请求来了 → 立即检查"我能不能处理" → 不能 → 立即拒绝
                                  → 能 → 进入处理流程
```

检查项：

| 检查 | 失败 |
|---|---|
| 输入参数校验 | 400 立即返回 |
| 鉴权 | 401 立即返回 |
| 限流器 | 429 立即返回 |
| 熔断器 Open | fallback 立即返回 |
| Bulkhead 满 | 503 立即返回 |
| 连接池满 | 503 立即返回 |
| 关键依赖 ping 不通 | 503 立即返回（健康检查） |

### 8.3 与 Bulkhead 的协同

Bulkhead 的 `maxWaitDuration=0` 就是 Fail Fast——满了立即拒，**不要等**。

```java
BulkheadConfig.custom()
    .maxConcurrentCalls(50)
    .maxWaitDuration(Duration.ZERO)  // fail fast
    .build();
```

### 8.4 Fail Fast 与重试的协同

```
fail fast 拒绝（503 或 429） → 上游客户端按指数退避重试 → 5s 后再试
```

比起"卡 30s 才超时" → 资源被占 30s + 用户等 30s + 上游连接占 30s，**fail fast 后等下次** 显然更友好。

### 8.5 服务启动期的 Fail Fast

应用启动时：

- 依赖 DB / Redis ping 不通 → **直接退出**（exit code != 0）
- 配置文件读取失败 → 直接退出
- 端口被占用 → 直接退出

**不要**默默启动、靠后续请求才发现错。Kubernetes 会按 restart policy 重启或调度到别的节点。

## 第九章：Hedged Request — 降低尾延迟

### 9.1 P99 问题

线上服务平均延迟 50ms 看起来很好。但：

- P50 = 30ms
- P99 = 500ms
- P99.9 = 3s

**1% 的用户体验是 500ms+，0.1% 的用户体验是 3s+**。对于高并发场景（1M 请求/天 → 1000 个 3s+ 用户）这是不可接受的。

P99 的"长尾"来自：

- GC pause
- 偶发慢磁盘
- 网络抖动
- 临时高 CPU
- 节点正在被换出

### 9.2 Hedged Request 思路

来自 Jeff Dean 2013 论文 "The Tail at Scale"：

```
发请求到 Replica1
等 P95 时间（例如 50ms）
还没回 → 发请求到 Replica2
谁先回用谁
```

```
t=0    : send to R1
t=50ms : R1 still pending → also send to R2
t=70ms : R2 returns first → use R2's response, cancel R1
```

### 9.3 实战效果

Google 论文中 BigTable 的实验：

- 没 hedge：P99.9 = 1800ms
- 有 hedge（在 P95 时发副本）：P99.9 = 74ms

**降低 20 倍**。

代价：约 5% 的请求会发两次（多 5% 的 backend 负载）。

### 9.4 实现要点

```go
func HedgedCall(ctx context.Context, after time.Duration, calls ...func(context.Context) (T, error)) (T, error) {
    ctx, cancel := context.WithCancel(ctx)
    defer cancel()

    type result struct {
        v   T
        err error
    }
    ch := make(chan result, len(calls))

    // 立刻发第一个
    go func() {
        v, err := calls[0](ctx)
        ch <- result{v, err}
    }()

    var hedgeTimer *time.Timer
    if len(calls) > 1 {
        hedgeTimer = time.AfterFunc(after, func() {
            for _, c := range calls[1:] {
                go func(call func(context.Context) (T, error)) {
                    v, err := call(ctx)
                    ch <- result{v, err}
                }(c)
            }
        })
    }

    select {
    case r := <-ch:
        if hedgeTimer != nil {
            hedgeTimer.Stop()
        }
        cancel()  // 取消其他
        return r.v, r.err
    case <-ctx.Done():
        return *new(T), ctx.Err()
    }
}
```

### 9.5 Hedged Request 的前提

| 前提 | 说明 |
|---|---|
| 请求是**幂等读** | 写请求 hedge = 双重写，灾难 |
| 后端可以**取消** | 否则取消失效，资源浪费 |
| 后端有多副本 | 单副本 hedge 没意义 |
| 多副本之间**数据一致** | 否则两个副本回不同结果 |

### 9.6 何时不要 hedge

- 后端容量不足时 hedge = 雪上加霜（多 5% 请求量）
- 写操作或非幂等读
- 延迟不稳定的根本原因是后端整体问题（hedge 解决不了）

### 9.7 gRPC 内置 Hedging

gRPC 在 2020+ 内置 hedging 策略（注意：默认关闭）：

```json
{
  "methodConfig": [{
    "name": [{"service": "Storage", "method": "Read"}],
    "hedgingPolicy": {
      "maxAttempts": 3,
      "hedgingDelay": "0.05s",
      "nonFatalStatusCodes": ["UNAVAILABLE"]
    }
  }]
}
```

## 第十章：组合案例

### 10.1 案例 1：电商订单创建

```
[Web] → POST /order → [order-service]
                          ├─ 调 [user-service]    （读用户）
                          ├─ 调 [stock-service]   （扣库存）
                          ├─ 调 [coupon-service]  （核销优惠券）
                          ├─ 调 [risk-service]    （风控）
                          └─ 调 [payment-service] （下单支付）
```

**给每个下游设计韧性策略**：

| 下游 | Timeout | Retry | CB | Bulkhead | Fallback |
|---|---|---|---|---|---|
| user | 100ms | 1（幂等读）| ✓ | 50 并发 | 本地缓存 → guest 用户 |
| stock | 500ms | ✗（不幂等扣减）| ✓ | 30 并发 | 失败 → 直接拒单 |
| coupon | 200ms | 1（用 idempotency-key）| ✓ | 20 并发 | 不用优惠券继续 |
| risk | 300ms | ✗ | ✓ | 30 并发 | 标记"待人工审" |
| payment | 2s | ✗（用 idempotency-key 退而求其次）| ✓ | 50 并发 | 标记"待支付"，让用户重试 |

**整体 Deadline 编排**：

```
HTTP gateway: 3s budget
  ↓
order-service: 2.8s budget（自己处理预留 200ms）
  ↓
并行调 user + stock + coupon + risk: 500ms budget
  ↓
拿到结果后调 payment: 剩余约 2s
```

**用 gRPC 的 ctx 自动 propagation**，每跳都看到剩余 budget。

### 10.2 案例 2：用 Hedged Request 降低搜索 API 的 P99

```
搜索 API 调 4 个 Elasticsearch 副本之一
平均 RT 50ms，P99 = 800ms（GC/IO 抖动）
```

不做 hedge：用户体验 P99 800ms。

**实施 hedge**：

```go
result, err := HedgedCall(ctx, 100*time.Millisecond,
    func(ctx context.Context) ([]Doc, error) { return es1.Search(ctx, q) },
    func(ctx context.Context) ([]Doc, error) { return es2.Search(ctx, q) },
)
```

第一次请求 100ms 没回 → 发第二个副本 → 哪个先回用哪个。

**结果**：

- P50 = 50ms（基本没变）
- P99 = 130ms（从 800ms 降下来）
- 额外负载 = 约 1% 请求触发 hedge（因 P99 触发率约 1%）

### 10.3 案例 3：第三方支付 API 的"组合拳"

调用支付宝/Stripe 的 charge API：

```go
// 1. 生成幂等 key（重试时复用）
idempotencyKey := uuid.New().String()

// 2. 熔断器保护
err := paymentCB.Execute(func() error {
    // 3. Retry 包裹（仅可重试错误）
    return Retry(ctx, RetryOpts{
        MaxAttempts: 3,
        BaseDelay:   200 * time.Millisecond,
        MaxDelay:    2 * time.Second,
        Retryable:   isRetryableHTTPError,
    }, func() error {
        // 4. Bulkhead 限制并发
        return paymentBulkhead.Do(ctx, func() error {
            // 5. Timeout 限制单次
            ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
            defer cancel()
            // 6. 实际调用（带 idempotency-key）
            return stripeClient.Charge(ctx, req, idempotencyKey)
        })
    })
})

// 7. 失败 fallback：写入"待重试"队列
if err != nil {
    pendingQueue.Push(req, idempotencyKey)
    return PendingResult, nil
}
```

完整 8 个模式中用到 7 个（除了 Hedged，因为支付不能双发）。

## 生产实践

### 配置 Checklist

- [ ] **每个**远程调用都有 Timeout（HTTP / RPC / DB / Redis / Kafka producer）
- [ ] **每个**写操作有 Idempotency Key（或确认是天然幂等）
- [ ] **每个**外部依赖有独立 Bulkhead（连接池 + 并发限制）
- [ ] **每个**关键依赖有 Circuit Breaker
- [ ] **每个**Fallback 比正常路径快 + 无副作用
- [ ] Retry 是 Exponential + Jitter，不是固定间隔
- [ ] Deadline 在 gRPC 链路上自动传播
- [ ] 健康检查（liveness + readiness）已配
- [ ] Goroutine count / FD count / 连接池 监控 + 告警
- [ ] 全链路压测验证过熔断和降级
- [ ] Retry 总量受控（gRPC retry throttling 或客户端 budget）

### 默认值速查

| 场景 | Timeout | Retry | CB threshold | Bulkhead |
|---|---|---|---|---|
| 内部 RPC（幂等读）| 200ms | 2 次 | 50% / 20 req | 50 |
| 内部 RPC（写）| 500ms | 0 | 50% / 20 req | 30 |
| 跨数据中心调用 | 1-3s | 0 | 40% / 20 req | 20 |
| 第三方 API | 2-5s | 3 次 | 30% / 30 req | 20 |
| DB 查询（OLTP）| 1s | 1 次 | 60% / 50 req | 100 |
| DB 查询（分析）| 30s | 0 | 不开 | 5 |

## 陷阱清单

1. **裸 HTTP 调用没 Timeout**：Go `http.Get()` 默认无超时；Python requests 默认无超时。生产代码每一个调用都必须显式设。

2. **Timeout 倒挂**：下游 timeout > 上游 timeout，下游做无用功。

3. **重试盲目**：不区分错误类型一律重试，4xx 也重试 → 加重下游负担。

4. **重试无退避或固定间隔**：羊群效应。

5. **多层重试叠加**：链路 A → B → C 每层都 retry 3 次 = 27 倍流量。

6. **不幂等的写操作直接重试**：导致重复扣款、重复发货。

7. **Bulkhead 用线程池但池子太多**：Hystrix 时代教训，1000 个线程池在 8C 机器上跑得很慢。

8. **连接池没配上限**：突发把 DB 连接打满。

9. **Fallback 比正常慢**：fallback 路径走数据库或网络，事故时雪上加霜。

10. **Fallback 有副作用**：把请求 push 到队列，结果队列也爆了。

11. **熔断器粒度太粗**：一个 service 一个熔断器，一个 endpoint 挂全断。

12. **熔断器参数太敏感**：min_requests=5 → 偶发失败就跳。

13. **Hedged Request 用于写操作**：双重写 = 灾难。

14. **Goroutine 泄漏**：context 没传或没 cancel，goroutine 永远在等。监控 goroutine 数。

15. **健康检查检查得太重**：`/healthz` 里去 ping DB / Redis 等，结果 DB 慢一下 → 整个 Pod 被 kill。**健康检查要轻**。

16. **Steady State 资源没归还**：rows 没 close、文件句柄没关、临时文件没删。

17. **超时设得太长不敢调**：怕影响业务，设了 30s。结果一旦下游慢 → 全部卡死。**Fail Fast > 等到下个世纪**。

## 2026 现状

- **gRPC** 已成微服务内部通信主流，**Deadline Propagation** 默认开启。HTTP 仍需手动注入 deadline header。
- **Resilience4j** 取代 Hystrix 在 Java 生态成为默认，函数式风格 + 模块化（CircuitBreaker / Retry / Bulkhead / RateLimiter / TimeLimiter 各自独立）。
- **Hystrix 2018 停止维护**——它的"线程池隔离"思路在性能上的代价让现代框架转向"信号量 + 自适应限流"。
- **Go 生态** 没有统一的"韧性框架"，社区方案：sony/gobreaker（熔断）、kratos/aegis（限流）、自研 Bulkhead，组合使用。
- **服务网格层面韧性**（Istio / Linkerd / Envoy）让"每个调用自动具备 retry / timeout / CB"，应用代码可以更薄。Istio Ambient（2024-11 GA）让这件事不再依赖 sidecar。
- **Hedged Request** 进入主流：gRPC 内置支持、AWS SDK 多数支持、DynamoDB / Spanner 客户端默认开启。
- **OpenTelemetry** 让 Bulkhead / CB / Retry 状态全可观测，仪表盘和告警标准化。
- **AI 时代的韧性新挑战**：LLM 调用延迟在几百毫秒到几十秒之间，传统 timeout 不适用；Streaming response 让 retry 不适用；需要新的模式（partial result fallback、token 级别 budget）。
- **混沌工程**：每周自动注入故障验证韧性策略是否生效，详见 [M20](./20-精通-契约测试与混沌工程.md)。
