## 引言：为什么必须把"异步"学透

在一份典型的微服务架构里，**同步调用是表象，异步消息是骨架**。

- 用户下单：API 网关同步返回订单号 → 库存扣减、风控审核、物流调度、积分入账、推送通知，全是异步。
- 一笔支付成功：账户余额扣减是同步的；但对账、清算、通知商户、生成发票、给推荐系统打信号，全是异步。
- 一次评论审核：审核服务调用 NLP 模型同步返回是否通过；但落库、广播给关注者、更新评分、触发风控规则，全是异步。

异步消息的本质，是用 **"时间解耦 + 空间解耦 + 失败隔离"** 来换 **"端到端一致性窗口 + 排查难度 + 运维复杂度"**。
做得好它是平台的稳定基石；做得差它是 P0 事故的高发区。

读完本章你应能：

- 区分**消息**（Message）和**事件**（Event）的语义本质差异
- 解释 Pub-Sub 与 Point-to-Point 两种模型的工程含义
- 在 Kafka / RabbitMQ / NATS / Pulsar / Redpanda 中为给定场景做技术选型
- 准确说出 Kafka 的 at-most-once / at-least-once / exactly-once 各自的限制条件
- 实现业务幂等消费（业务 key + 唯一约束 / 状态机）
- 设计死信队列（DLQ）、重试与隔离消费的完整链路
- 给出顺序保证（同 partition / 同 key）的工程约束
- 监控消费者组的 lag、rebalance、消费分布健康度
- 识别"用消息当 RPC"、"消息体过大"、"不幂等消费"等反模式

## 第一章：消息与事件的本质差异

### 1.1 一对最容易被混用的术语

中文圈把这两个词混着用，英文圈也好不到哪儿去——Kafka 文档里"record"、"message"、"event"三个词随意切换。但在架构语义层面，它们有清晰的差别：

| 维度 | 消息 (Message) | 事件 (Event) |
|---|---|---|
| 语义 | "请你做某件事"（命令/请求） | "某件事已经发生了"（事实陈述） |
| 时态 | 祈使句 / 将来时 | 完成时 |
| 命名 | `SendEmailCommand` / `ChargeOrderCommand` | `OrderPlaced` / `PaymentSucceeded` |
| 接收者 | 通常 1 个（消费方负责执行） | 0..N 个（订阅方各自反应） |
| 耦合方向 | 发送方知道接收方"应做的事" | 发送方不关心谁会订阅 |
| 路由 | 队列 / RPC-over-MQ | Topic / 事件流 |
| 失败语义 | 失败需要重试或返回错误 | 失败由订阅方各自处理，不回流 |
| 典型中间件 | RabbitMQ / SQS / NATS Core | Kafka / Pulsar / EventBridge |

一句话：**消息是"任务"，事件是"事实"**。

### 1.2 用一个订单流程看差别

**消息思维（命令式）**：

```
OrderService → SendCommand("ChargeOrder", orderId, amount) → PaymentService
                                                          → InventoryService.SendCommand("Reserve", ...)
                                                          → ShippingService.SendCommand("Schedule", ...)
```

OrderService 是上帝视角，明确知道下一步要触发哪些动作。耦合在编排者这里。

**事件思维（事实广播）**：

```
OrderService → Publish(OrderPlaced{orderId, items, amount, userId, ...})
              │
              ├→ PaymentService 订阅，自己决定扣款
              ├→ InventoryService 订阅，自己决定扣库存
              ├→ ShippingService 订阅，自己决定建运单
              ├→ LoyaltyService 订阅，自己决定加积分
              └→ RiskService 订阅，自己决定打风控信号
```

OrderService 只发布"订单创建了"这个**事实**，谁愿意做什么、做不做、做几次，OrderService 不关心。这是**事件驱动**的核心。

### 1.3 两种思维的取舍

| 维度 | 命令（消息） | 事件 |
|---|---|---|
| 加新订阅方 | 改编排者 | 不改发布方 |
| 端到端可追溯 | 编排者一目了然 | 需要依赖链路追踪还原 |
| 流程编排清晰度 | 高（编排者集中） | 低（散落各服务） |
| 演化灵活性 | 低 | 高 |
| 调试难度 | 低 | 高（事件 → 谁反应了？） |
| 适合场景 | 工作流明确、参与方稳定 | 业务边界清晰、订阅方多变 |

**实务建议**：

- 跨**限界上下文**（Bounded Context）的通信用 **事件**。
- **限界上下文内部**、需要编排的流程，可以用 **消息（命令）** 甚至 RPC。
- 不要在事件名里写"动作"（如 `OrderCreating`、`OrderToBeCharged`），事件名应是 **过去时事实**。

### 1.4 文档事件 vs 通知事件 vs 事件溯源事件

事件本身还分三种风格（Martin Fowler 的分类）：

| 类型 | 数据载荷 | 用途 |
|---|---|---|
| **通知事件**（Event Notification） | 仅 ID 与最小信息 | "X 发生了，详情自己查" → 订阅方回查 |
| **状态传递事件**（Event-Carried State Transfer） | 完整业务状态快照 | 订阅方无需回查，自己缓存 |
| **事件溯源事件**（Event Sourcing） | 业务领域事件 | 系统状态本身由事件序列重建（见 M10） |

工程上选择：

- **通知事件**：消息体小，但订阅方需要回查 → 回查会形成"事件雪崩"风险，且容易因数据已变化而读到不一致版本。
- **状态传递事件**：消息体大，但订阅方完全自治、可离线消费。**多数微服务事件用这个**。
- **事件溯源事件**：只在业务模型适合 Event Sourcing 时用，见 M10。

### 1.5 为什么本章不直接讲 Event Sourcing

事件驱动 ≠ Event Sourcing。

- **事件驱动**：服务之间用事件通信，但每个服务内部仍可用传统 CRUD 持久化。
- **Event Sourcing**：服务**内部**的状态本身由事件序列构成，是一种领域建模选择。

绝大多数生产系统是"事件驱动 + CRUD"，少数是"事件驱动 + ES"。M10 专门讲后者。

## 第二章：两种核心模型——Point-to-Point 与 Pub-Sub

### 2.1 Point-to-Point（点对点 / 队列模型）

```
Producer ──> [ Queue ] ──> Consumer-1 (一条只被一个消费者拿走)
                    │
                    └─── Consumer-2 (与 C1 竞争消费)
```

- **一条消息只被一个消费者处理**（消费者之间是"竞争消费"）。
- 多消费者用于扩容吞吐，不是用于广播。
- 典型实现：RabbitMQ Queue、AWS SQS、Redis BLPOP、NATS Queue Group。

### 2.2 Pub-Sub（发布订阅 / 主题模型）

```
Producer ──> [ Topic ] ──┬──> Subscriber-A (拿到所有消息)
                         ├──> Subscriber-B (拿到所有消息)
                         └──> Subscriber-C (拿到所有消息)
```

- **一条消息被所有订阅者各拿到一份**。
- 订阅者之间独立，互不干扰。
- 典型实现：Kafka Topic + 不同 Consumer Group、RabbitMQ Fanout Exchange、NATS Subject、Redis Pub/Sub。

### 2.3 Kafka 同时是两种

Kafka 是 Pub-Sub 的实现，但**通过 Consumer Group 同时实现了 Queue 语义**：

- 同一个 group 内：每个 partition 只被一个 consumer 处理 → 等价于 Queue（竞争消费）。
- 不同的 group 之间：每个 group 各自从头消费 → 等价于 Pub-Sub（广播）。

```
Topic: orders (3 partitions)

Consumer Group: "payment-svc"      Consumer Group: "shipping-svc"
  ├ consumer-1 ← partition-0          ├ consumer-1 ← partition-0
  ├ consumer-2 ← partition-1          └ consumer-2 ← partition-1, 2
  └ consumer-3 ← partition-2
```

一个 topic 多个 group 各自消费 = Pub-Sub；同 group 多 consumer 共享 partition = Queue。

### 2.4 选型速查

| 需求 | 模型 | 推荐 |
|---|---|---|
| 任务队列、worker 池 | Point-to-Point | RabbitMQ / SQS / NATS JetStream |
| 业务事件广播 | Pub-Sub | Kafka / Pulsar |
| 临时通知（断线即丢） | 轻量 Pub-Sub | NATS Core / Redis Pub/Sub |
| 持久化事件 + 回放 | 持久 Pub-Sub | Kafka / Pulsar |
| 跨地域复制 | 持久 Pub-Sub + 复制 | Kafka MirrorMaker / Pulsar Geo |

## 第三章：主流中间件对比矩阵

### 3.1 整体对比表（2026 视角）

| 维度 | Kafka 4.x | RabbitMQ 4.x | NATS JetStream | Pulsar 3.x | Redpanda |
|---|---|---|---|---|---|
| **核心范式** | 持久日志 | 队列 + Exchange 路由 | 主题 + 流 | 持久日志 + 队列 | 持久日志（Kafka 兼容） |
| **存储模型** | 顺序日志（segment） | 队列（mnesia / Quorum Queue） | File / Memory + RAFT | 分层存储（BookKeeper + 对象） | 顺序日志（Raft） |
| **协议** | Kafka 协议 | AMQP / MQTT / STOMP | NATS Wire | Pulsar / Kafka 兼容 | Kafka 协议（C++ 实现） |
| **协调** | KRaft（无 ZK） | Quorum Queue（Raft） | RAFT | ZK（迁移中）/ Oxia | Raft |
| **吞吐** | 极高（百万 msg/s） | 中（万级 msg/s） | 高 | 极高 | 极高（号称低延迟） |
| **延迟** | 5-30ms | 1-10ms | <1ms（核心） | 5-30ms | 1-10ms |
| **顺序保证** | 同 partition 内 | 同 queue | 同 subject | 同 partition / Key_Shared | 同 partition |
| **Exactly-Once** | 支持（事务） | 不支持 | 不支持 | 支持（事务） | 支持（Kafka 兼容） |
| **死信** | 应用层实现 | 内置 DLX | 内置 | 内置 | 应用层 |
| **路由能力** | 弱（仅 topic + key） | 极强（Direct/Topic/Fanout/Headers） | 强（subject 通配） | 中 | 弱 |
| **消息保留** | 时间 / 大小（可永久） | 消费即删 / TTL | 流可保留 | 分层永久 | 时间 / 大小 |
| **多租户** | 无（靠 namespace 约定） | vhost | account | 一等公民 | 无 |
| **运维门槛** | 中（KRaft 后降低） | 低 | 低 | 高 | 低 |
| **JVM** | 是 | Erlang | 否（Go） | 是 | 否（C++） |
| **典型场景** | 数据管道、事件流、CDC | 工作队列、RPC | 微服务通信、IoT | 多租户企业平台 | 低延迟 Kafka 替代 |

### 3.2 一对一对比详解

#### Kafka vs RabbitMQ

| 你想要 | 选 Kafka | 选 RabbitMQ |
|---|---|---|
| 事件流、CDC、数据管道 | ✓ | ✗ |
| 工作任务分发、RPC-over-MQ | ✗ | ✓ |
| 灵活路由（Header / Topic 通配） | ✗ | ✓ |
| 永久保留 + 回放 | ✓ | ✗（设计上消费即删） |
| 单条吞吐 100 万+ | ✓ | ✗ |
| 优先级队列、延时队列 | 应用层实现 | 原生支持 |

经典误用：用 Kafka 当任务队列（每条任务都需要 ack、retry、DLQ、优先级）→ 累死自己。
反之：用 RabbitMQ 跑数据管道（百万级吞吐）→ 把它打挂。

#### Kafka vs Pulsar

Pulsar 是"理论更优、生态略弱"的存在：

- 计算与存储分离（broker 无状态，数据在 BookKeeper）→ 扩缩容快、迁移容易。
- 多租户、命名空间是一等公民。
- 同时支持 Topic 与 Queue 两种语义（Key_Shared / Shared / Failover）。
- 分层存储（热数据本地、冷数据 S3）原生。
- 缺点：架构复杂，生态（Connect / Streams 等）落后 Kafka。
- 2026 现状：Pulsar 在企业级多租户场景增长，但 Kafka 仍是默认选择。

#### Kafka vs NATS JetStream

NATS 强在 **轻量 + 低延迟**：

- 核心二进制小、单节点 < 20MB 内存可跑。
- 微秒级延迟（核心 Pub-Sub），事件流 JetStream 也是亚毫秒级。
- Subject 通配符路由强（`orders.>` 订阅所有订单事件）。
- 内置 KV、对象存储、请求-响应模型。
- 但生态远不如 Kafka，企业级数据管道仍优先 Kafka。

#### Kafka vs Redpanda

Redpanda = "Kafka 协议 + C++ 重写 + 无 JVM"：

- 完全兼容 Kafka 客户端。
- 单 broker 即可、无 ZK / KRaft 元数据集群。
- 性能（特别是 P99 延迟）声称优于 Kafka。
- 商业开源混合模式（部分企业功能闭源）。
- 适合中小规模、对延迟敏感的团队；超大规模生态仍是 Kafka。

### 3.3 选型决策树

```
                  需要持久化 + 回放?
                   ┌─────┴─────┐
                   是          否
                   │           │
        ┌──────────┴──┐    ┌──┴───────────┐
        最大吞吐?       临时通知 / RPC?
        ┌─────┴───┐    ┌──┴────────────┐
        极高     高    NATS Core     RabbitMQ RPC
        │       │
        │     需要 Kafka 兼容?
        │     ┌──┴──┐
        │     是    否
        │     │     │
        Kafka Redpanda NATS JetStream
        │
     多租户 + 分层存储?
     ┌──┴───┐
     是     否
     │      │
     Pulsar Kafka
```

简化版的一句话指引：

- **业务事件流 / CDC / 数据管道**：Kafka 默认。
- **任务队列 / 复杂路由**：RabbitMQ。
- **微服务内部通信 / 低延迟**：NATS。
- **大企业多租户 / 跨地域**：Pulsar。
- **小规模 + Kafka 协议 + 低延迟**：Redpanda。

## 第四章：投递语义——At-most-once / At-least-once / Exactly-once

### 4.1 三种语义的定义

| 语义 | 含义 | 重复? | 丢失? |
|---|---|---|---|
| At-most-once | 最多一次 | 不可能 | 可能 |
| At-least-once | 至少一次 | 可能 | 不可能 |
| Exactly-once | 恰好一次 | 不可能 | 不可能 |

直觉上 Exactly-once 最香，但工程上它是"**特定假设下的端到端保证**"，绝大多数业务该追求 **at-least-once + 业务幂等**。

### 4.2 At-most-once（不推荐）

实现极简：发送后不重试、消费后立即 commit 再处理。

```
[ Producer.send → 不管失败 ]
[ Consumer poll → commit offset → process（处理时崩了就丢） ]
```

适用场景：纯指标上报、可容忍丢失的日志。**业务消息几乎不用**。

### 4.3 At-least-once（默认 & 推荐）

实现：

- Producer：失败重试，`acks=all`、`retries` 充分大、`enable.idempotence=true`（防 broker 端重复）。
- Consumer：**先处理成功，再 commit offset**；若处理后未 commit 就崩了，下次会重投。

```
[ Producer.send → 失败重试 → broker 持久化成功才 ack ]
[ Consumer poll → 业务处理 → commit offset ]
                  │
                  └ 若中途崩溃，offset 未 commit → 下次重投
```

代价：**消息可能重复** → 业务必须幂等（见第六章）。

### 4.4 Exactly-once 的真相

#### Kafka Exactly-once 的两层

Kafka 的 EOS（Exactly-Once Semantics）有两个层次：

**第一层：Idempotent Producer**（`enable.idempotence=true`）

- 给每条消息加 `(producerId, epoch, sequence)`。
- broker 根据序号去重，**单 partition、单会话**内不会重复。
- 默认从 Kafka 3.0 起开启。

**第二层：Transactional Producer + Read-Committed Consumer**

- producer 用 `transactional.id` 把多条 send + commit offset 包成事务。
- broker 标记事务 commit / abort，consumer 配置 `isolation.level=read_committed` 只读到 committed 数据。
- 用于 **Kafka → Kafka** 流处理（Kafka Streams / Flink），保证"读 → 处理 → 写 + commit offset"原子。

#### Exactly-once 不是银弹

它的**严格限制**：

1. **作用域**：Kafka 内部。一旦你把消息消费后写到 MySQL、Redis、外部 API，Kafka 的 EOS 管不到 → 仍需业务幂等。
2. **吞吐代价**：事务 commit 引入额外的 marker write 与等待，吞吐降低 20-50%。
3. **延迟代价**：read_committed 消费者只能读到 committed 之前的消息，端到端延迟增加（事务超时窗口）。
4. **复杂度**：transactional.id 必须稳定，否则 fencing 失败；producer 崩溃恢复要正确处理 epoch。
5. **跨外部系统不保证**：Sink 必须接受幂等写入或支持事务（如 Kafka Connect 的某些 sink），否则只能至少一次。

#### 工程指南

- **流处理 Kafka 内部传递**（如 Kafka Streams、Flink Kafka source/sink）：开 EOS 是合理的。
- **业务消费写外部 DB**：用 at-least-once + 业务幂等（强烈推荐）。
- **要"端到端 EOS"**：必须自己加业务幂等层，Kafka 的 EOS **只是其中一环**，不是全部。

### 4.5 三种语义参数总结

```yaml
# Producer at-least-once（+ idempotent，推荐默认）
acks: all
retries: 2147483647       # Integer.MAX_VALUE
max.in.flight.requests.per.connection: 5
enable.idempotence: true   # Kafka 3.0+ 默认
delivery.timeout.ms: 120000

# Producer exactly-once（事务）
acks: all
enable.idempotence: true
transactional.id: "order-svc-instance-1"   # 必须稳定

# Consumer at-least-once（推荐默认）
enable.auto.commit: false
isolation.level: read_committed   # 配合事务 producer
# 处理成功后手动 commit
```

## 第五章：消费幂等——业务层的最后一道防线

### 5.1 为什么"消费幂等"是必修课

回顾上一章：在 at-least-once 下，消息**一定**会重复。重复来源：

1. Producer 重试：broker 写成功但 ack 丢失 → producer 重发。
2. Consumer 处理后未 commit offset 即崩 → rebalance 后重投。
3. 上游业务因网络问题重发（最常见！）。
4. Rebalance 期间 in-flight 消息被重新分配。

所以**消费方必须幂等**，这是异步消息架构的**生死线**。

### 5.2 幂等三板斧

#### 板斧一：业务唯一 key + DB 唯一约束

最简单也最常用。每条消息必须带一个**业务幂等 key**（如 `event_id`、`order_id + step`、`request_id`）：

```sql
CREATE TABLE order_payment (
    id BIGSERIAL PRIMARY KEY,
    event_id VARCHAR(64) NOT NULL UNIQUE,   -- 幂等 key
    order_id VARCHAR(64) NOT NULL,
    amount NUMERIC(18,2),
    status VARCHAR(16),
    created_at TIMESTAMPTZ DEFAULT now()
);
```

消费代码：

```go
func handlePaymentEvent(ctx context.Context, e PaymentEvent) error {
    _, err := db.ExecContext(ctx, `
        INSERT INTO order_payment(event_id, order_id, amount, status)
        VALUES ($1, $2, $3, 'PAID')
        ON CONFLICT (event_id) DO NOTHING
    `, e.EventID, e.OrderID, e.Amount)
    if err != nil { return err }

    // 副作用（外部调用）必须放在 insert 之后，且自身幂等
    return notifyShipping(ctx, e.OrderID)
}
```

要点：

- **INSERT 是幂等性的锚点**：唯一约束保证重复消息被静默忽略。
- 副作用（调外部）放 INSERT 之后，且本身要幂等（用同一 event_id 透传到下游）。
- `ON CONFLICT DO NOTHING` 是 Postgres 写法；MySQL 用 `INSERT IGNORE` 或 `INSERT ... ON DUPLICATE KEY UPDATE`。

#### 板斧二：状态机驱动

业务实体本来就有状态机（如订单 `CREATED → PAID → SHIPPED → DELIVERED`），用状态约束保证操作不重复：

```sql
UPDATE orders
SET status = 'PAID', paid_at = now()
WHERE order_id = $1 AND status = 'CREATED';
-- affected_rows = 1 → 真的扣款了
-- affected_rows = 0 → 已扣款（重复消息），忽略
```

```go
result, err := db.ExecContext(ctx, `
    UPDATE orders SET status='PAID', paid_at=now()
    WHERE order_id=$1 AND status='CREATED'
`, e.OrderID)
if err != nil { return err }
n, _ := result.RowsAffected()
if n == 0 {
    log.Info("payment event ignored, order not in CREATED state",
        "order_id", e.OrderID)
    return nil
}
return notifyShipping(ctx, e.OrderID)
```

状态机的好处：天然描述合法转移。坏处：**前提是业务真的有干净的状态机**——很多业务实体没有。

#### 板斧三：去重表 / 去重缓存

如果业务模型不好嵌入唯一约束，可以单独维护去重表：

```sql
CREATE TABLE consumed_events (
    consumer_group VARCHAR(64),
    event_id       VARCHAR(64),
    consumed_at    TIMESTAMPTZ DEFAULT now(),
    PRIMARY KEY (consumer_group, event_id)
);
```

消费逻辑：

```go
tx, _ := db.BeginTx(ctx, nil)
defer tx.Rollback()

// 1. 标记已消费（重复则唯一约束冲突）
_, err := tx.ExecContext(ctx, `
    INSERT INTO consumed_events(consumer_group, event_id) VALUES ($1, $2)
`, "payment-svc", e.EventID)
if isUniqueViolation(err) {
    return nil  // 已消费过
}
if err != nil { return err }

// 2. 业务处理
if err := businessLogic(ctx, tx, e); err != nil { return err }

return tx.Commit()
```

去重缓存版本（性能高、可能漏，需要 fallback 到 DB）：

- Redis SET event:{id} 1 NX EX 86400 → 若已存在则跳过。
- 适合短窗口去重（24h），长窗口仍需 DB。

### 5.3 复合幂等 key 的设计

简单的 event_id 不一定够，常见复合 key：

| 场景 | key 构成 |
|---|---|
| 订单支付 | `order_id + payment_attempt_n` |
| 账户加钱 | `from + to + business_id + business_type` |
| 库存扣减 | `order_id + sku_id` |
| 推送通知 | `user_id + template_id + content_hash` |

原则：**业务上"重复发起就该幂等"的最小标识** 都进 key。

### 5.4 幂等 vs 重入

注意区分两个相关但不同的概念：

- **幂等（Idempotent）**：同一操作执行 N 次效果等于 1 次。
- **重入安全（Re-entrant）**：同一资源被并发操作时正确（用锁 / CAS / 事务隔离）。

消费幂等是前者；并发消费同一 key 需要后者（用 DB 行锁或分布式锁）。

### 5.5 幂等存储清理

去重表会无限增长。两种清理策略：

| 策略 | 说明 | 适用 |
|---|---|---|
| TTL 删除 | event_id 留 N 天后删 | 上游业务保证 N 天后不会再重发 |
| 业务上下文绑定 | event_id 与业务实体一起删（如订单归档时） | 长周期业务 |

清理方法：

```sql
-- 配合 Postgres 分区表，按 month 分区，到期 DROP PARTITION
DROP TABLE consumed_events_2025_11;
```

## 第六章：死信队列、重试与隔离消费

### 6.1 为什么消息会"消费失败"

消费失败的原因谱系：

| 类型 | 示例 | 重试有用? |
|---|---|---|
| 瞬时错误 | 网络抖动、DB 短暂不可用 | 是（指数退避） |
| 限流被拒 | 下游 429 | 是（更长退避） |
| 资源不足 | OOM、连接池耗尽 | 是 |
| 数据错误 | JSON 解析失败、字段缺失 | 否（重试也错） |
| 业务规则错误 | 订单已退款，不能再退 | 否 |
| 上下游不一致 | 引用的实体不存在 | 看情况 |

**关键**：可重试错误和不可重试错误的策略完全不同。

### 6.2 重试策略

#### 指数退避 + 抖动

```python
# Pseudocode
def backoff(attempt):
    base = min(60s, 2^attempt * 100ms)
    return base * random.uniform(0.5, 1.5)
```

第 1 次 100-150ms、第 2 次 200-300ms、…、上限 60s + 抖动。
**抖动很重要**：避免大批消费者同时重试打雷下游。

#### 三种重试位置

| 位置 | 实现 | 优劣 |
|---|---|---|
| 进程内重试 | 消费方 `for attempt in 1..N: retry` | 简单，但阻塞 worker、影响其他消息 |
| 重试 topic（recycling） | 失败消息发到 `orders.retry.5s` topic 等待消费 | 不阻塞，需要 N 个延迟 topic |
| 单独 retry 服务 | 用 DB / Redis 排程，到点再投 | 灵活，复杂度高 |

**推荐**：进程内重试 1-3 次（短瞬时错误）→ 失败发到 retry topic（中等错误）→ 多次失败送 DLQ（持久失败）。

```
[main topic] → consumer → fail × 3 → publish to [retry.5s]
[retry.5s] → 等 5s → 重消费 → fail → publish to [retry.30s]
[retry.30s] → 等 30s → 重消费 → fail → publish to [retry.5m]
...
最终 [DLQ] → 人工或修复后回灌
```

#### Kafka 实现延迟重试

Kafka 没有原生延迟队列，常见三种实现：

1. **延迟 topic + 时间戳判定**：消费时检查 `processAt > now()` 则不 commit、sleep（不优雅）。
2. **N 个固定延迟 topic**（5s / 30s / 5m / 1h），按需路由（业界标准做法）。
3. **外部调度器**（如 Temporal、自研）控制再投递时机。

推荐做法 2，结构清晰、运维可见。

### 6.3 死信队列（DLQ）

#### 什么消息进 DLQ

- 重试次数耗尽仍失败。
- 反序列化失败（poison pill）。
- 业务校验明确不通过（"订单不存在"）且不应阻塞后续消息。

#### DLQ topic 命名约定

```
orders.placed                     # 业务 topic
orders.placed.retry.5s            # 重试 5s
orders.placed.retry.30s
orders.placed.retry.5m
orders.placed.dlq                 # 死信
```

#### DLQ 消息必带元数据

```json
{
  "original_topic": "orders.placed",
  "original_partition": 3,
  "original_offset": 87654321,
  "original_timestamp": "2026-05-28T08:14:23Z",
  "consumer_group": "payment-svc",
  "error_class": "BizValidationError",
  "error_message": "order not found: order_id=12345",
  "stacktrace": "...",
  "retry_attempts": 5,
  "first_failure_at": "2026-05-28T08:10:01Z",
  "last_failure_at": "2026-05-28T08:14:23Z",
  "payload": { ... 原消息体 ... }
}
```

没有这些上下文，DLQ 就是个黑洞——救出来也不知道为啥失败。

### 6.4 隔离消费：防止"毒消息"打垮整个消费者

一个反复失败的消息会让消费者卡在同一 offset 反复重试，**阻塞同 partition 的所有后续消息**。这就是"队头阻塞"。

防御办法：

- **N 次失败必送 DLQ + commit**：放走，不让它阻塞别人。
- **隔离 worker pool**：把"高失败率 key"路由到专用 worker。
- **bulkhead 化**：按业务 tenant / VIP 等级分独立消费者组。

```go
// Kafka 单 partition 内的隔离消费
for msg := range partition {
    err := handleWithRetry(msg, 3)
    if err != nil {
        // 关键：不要在这里 panic / 阻塞
        // 1. 发到 DLQ
        sendToDLQ(msg, err)
        // 2. commit offset 放行
        commit(msg.Offset + 1)
        continue
    }
    commit(msg.Offset + 1)
}
```

### 6.5 DLQ 后续处理

DLQ 不是终点。运维流程：

1. **告警**：DLQ 流入速率 > 阈值 → PagerDuty。
2. **分析**：日志 + DLQ 消息分类。
3. **修复**：代码 bug 修复、上下游数据修复、限流参数调整。
4. **回灌**：把 DLQ 消息**带上"已修复"标记**重新投入 main topic（或专用 reinject topic）。
5. **复盘**：为什么这类消息进了 DLQ，是否应在 producer 端拦截。

回灌工具：自研脚本 / Kafka Tools / Confluent Replicator 都能用。**回灌前一定要确认幂等**——多次回灌不能造成业务重复。

## 第七章：消息顺序保证

### 7.1 顺序问题的本质

很多业务依赖顺序：

- 用户余额：先 +100 后 -50 与 先 -50 后 +100 含义不同（后者可能透支）。
- 订单状态机：`CREATED → PAID → SHIPPED`，不能乱。
- 库存增减：先入库后出库 vs 反向，可能拒发或超卖。

但**全局顺序**几乎不可能在分布式消息系统里高效实现——会退化成单线程。

### 7.2 Kafka 的顺序保证

Kafka 提供**单 partition 内的强顺序**：

- 同一个 partition 的消息，按 producer 写入顺序持久化。
- 消费者按 offset 递增读取。
- **跨 partition 不保证顺序**。

由此推出工程做法：**把"需要保序"的消息发到同一个 partition**。

### 7.3 如何路由到同一 partition

```
partition = hash(key) % num_partitions
```

只要给同一**业务实体**用同一 key，所有相关消息就会进同一 partition：

| 业务 | 推荐 key |
|---|---|
| 订单事件 | `order_id` |
| 用户行为 | `user_id` |
| 账户流水 | `account_id` |
| 设备数据 | `device_id` |

```go
// Go: sarama
msg := &sarama.ProducerMessage{
    Topic: "orders",
    Key:   sarama.StringEncoder(orderID),  // 关键
    Value: sarama.ByteEncoder(payload),
}
```

### 7.4 顺序的脆弱点

即使按 key 路由，仍有几处"顺序失效"陷阱：

#### 陷阱 1：生产端 in-flight 重试乱序

`max.in.flight.requests.per.connection > 1` + `retries > 0` + 关闭 idempotence → 重试可能把后发的消息插到前发之前。

修复：

```yaml
enable.idempotence: true   # 内部会限制并保证有序
max.in.flight.requests.per.connection: 5  # 配合 idempotence 安全
```

#### 陷阱 2：消费端多线程并行处理乱序

为了吞吐，消费者常把消息扔给线程池处理：

```
poll → 100 条消息 → 丢给 worker pool（10 线程） → 同 key 消息可能被不同线程并行处理
```

修复（**按 key 路由到固定 worker**）：

```go
workerIdx := hash(msg.Key) % workerCount
workers[workerIdx].Submit(msg)  // 同 key 总是同一 worker → 顺序
```

#### 陷阱 3：rebalance 引发跨 partition 重处理

rebalance 时 partition 重分配，正在处理中的消息可能被另一个消费者重读，且与原 owner 的处理交叉。

修复：处理逻辑必须幂等（见第五章）。

#### 陷阱 4：DLQ + 回灌打乱顺序

一条 retry 5 次后进 DLQ，半小时后回灌 → 它跑到了"未来"。后续修复的顺序约束。

修复：

- 同 key 阻塞机制：进 DLQ 后，**同 key 的后续消息暂停消费**直到修复（复杂，慎用）。
- 容忍业务上"补丁"：让业务模型容忍少量乱序（如对账系统按时间戳重排）。

### 7.5 何时不要追求顺序

顺序约束越严，扩展性越差。如果业务允许，**重新设计成"顺序无关"**：

- 把 `余额 += 10`、`余额 -= 5` 改成"流水记账 + 实时聚合"。
- 把 `订单状态变更` 改成"事件溯源 + 物化视图"（M10）。
- 把 `device 读数` 改成"按时间戳为准 + 最后写入策略"。

工程上 80% 的"顺序问题"都能通过这种重设计消失。

## 第八章：消费者组、Rebalance 与 Lag 监控

### 8.1 Consumer Group 模型

一个 Consumer Group：

- 由若干消费者实例组成。
- 协调器（Coordinator，是某个 broker）负责 partition 分配。
- 同 group 内 **每个 partition 至多被一个 consumer 拥有**。

```
Topic orders (P0, P1, P2, P3)
Consumer Group "payment-svc"
  ├ consumer-A → P0, P1
  └ consumer-B → P2, P3
```

加 consumer-C 后 → 重新分配 → A=P0、B=P2,P3、C=P1（具体看 assignor）。

### 8.2 Rebalance 的类型与代价

Rebalance 触发：

- 消费者加入 / 退出 / 崩溃（心跳超时）。
- 订阅 topic 的 partition 数变化。
- 配置 `session.timeout.ms` / `heartbeat.interval.ms` 不匹配心跳频率。

#### Stop-the-world Rebalance（默认，但越来越少见）

整个 group 暂停消费、所有 partition 重分配 → 数秒到数十秒"消费冰冻"。
对吞吐 / 延迟敏感的业务是灾难。

#### Cooperative Rebalance（Incremental，2.4+ 推荐）

- `CooperativeStickyAssignor`：只移动"必须移动"的 partition，其他 partition 持续消费。
- 大幅缩短 rebalance 影响时间（从数十秒降到亚秒级）。

```yaml
partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor
```

#### KIP-848（Kafka 3.7+）

服务端协调的下一代 rebalance 协议，消费者不再参与协调状态机，进一步降低 rebalance 抖动。**在 Kafka 4.0 已 GA（broker 端默认开启），但消费者客户端默认仍是旧协议，需显式 opt-in（`group.protocol=consumer`）**。详见 kafka/04。

### 8.3 心跳与会话超时

```yaml
session.timeout.ms: 45000        # 协调器多久没收到心跳判定 consumer 死亡
heartbeat.interval.ms: 3000      # 心跳间隔（一般 = session/3）
max.poll.interval.ms: 300000     # 两次 poll 最大间隔（处理耗时 > 这个会被踢）
```

最常见的 rebalance 病因：

- 消费者处理慢，超过 `max.poll.interval.ms` → 被踢出 → 不停 rebalance。
- 修复：缩小 batch、把慢操作异步化、加大 `max.poll.interval.ms`（不是根治）。

### 8.4 消费 Lag（滞后）监控

Lag = `latest offset` - `committed offset`，意为"还有多少条未消费"。

```bash
kafka-consumer-groups.sh --bootstrap-server kafka:9092 \
  --describe --group payment-svc
```

输出：

```
TOPIC          PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
orders.placed  0          1234567         1234890         323
orders.placed  1          5678123         5678125         2
orders.placed  2          9876543         9990000         113457   ← 异常
```

#### Lag 的可观测指标

| 指标 | 含义 | 报警阈值参考 |
|---|---|---|
| Lag (rec) | 未消费记录数 | > 业务可接受值（如 10k）即告警 |
| Lag (time) | 最早未消费记录与当前时间差 | > SLA（如 5 分钟）即告警 |
| Rebalance rate | 单位时间 rebalance 次数 | > 0.1 / min 即可疑 |
| Consumer fetch rate | 单 consumer 拉取速率 | 突降即可疑 |

`Lag (time)` 比 `Lag (rec)` 更直观——10 万条 lag 在低峰可能 10 秒能追上，在高峰可能要 1 小时。**告警优先用时间 lag**。

#### 工具

- Burrow（LinkedIn 开源，Kafka 专用 lag 监控）。
- Prometheus kafka_exporter（暴露 consumer lag metrics）。
- 各云厂商托管 Kafka 内置面板。

### 8.5 消费扩缩容

```
N partitions, M consumers in group
  M < N  : 部分 consumer 拥有多个 partition
  M = N  : 每个 consumer 一个 partition（理想）
  M > N  : 多出的 consumer idle，浪费
```

**结论**：消费者扩容上限 = partition 数。设计 topic 时要前瞻性预估 partition 数（参见 kafka/01-精通-Topic-Partition-Offset.md）。

## 第九章：与 Event Sourcing 的区别（与 M10 划界）

很多人混淆"事件驱动微服务"与"Event Sourcing"。M10 会详谈 ES，这里只划清边界：

| 维度 | 事件驱动微服务（本章） | Event Sourcing（M10） |
|---|---|---|
| 主张 | 服务间用事件通信 | 服务内部状态由事件序列构成 |
| 持久化 | 各服务自由（CRUD / ES 都行） | 必须 append-only event log |
| 重建状态 | 不需要（CRUD 表自带状态） | 状态 = replay events |
| 主要工具 | Kafka / Rabbit / NATS | Event Store / Kafka / Axon / Marten |
| 复杂度 | 中 | 高 |
| 适用 | 几乎所有微服务 | 审计严苛、状态历史重要的领域（金融、合规） |

简单判别：

- "用 Kafka 发 `OrderPlaced` 给下游订阅" → 事件驱动。
- "OrderService 自己**不存订单表**、只存 `OrderPlaced/OrderPaid/OrderShipped` 事件流，订单状态 = 事件 replay" → Event Sourcing。

事件驱动是异步通信的一种模式；ES 是领域建模 + 持久化的一种模式。两者可独立，也可组合。

## 第十章：模式总结与反模式

### 10.1 推荐模式

| 模式 | 简述 | 适用 |
|---|---|---|
| 事件通知 | 发布"事实"，订阅方各自反应 | 跨上下文通信 |
| 状态传递事件 | 事件载荷含完整业务状态 | 订阅方需要自治 |
| Outbox 模式 | 业务 + 事件入库同一事务，CDC 异步发布 | 防 Dual Write（详见 M08） |
| Inbox 模式 | 消费侧把 event_id 入库去重 | 业务无唯一约束时 |
| DLQ + 隔离消费 | 异常消息进 DLQ 不阻塞主流程 | 所有生产消费 |
| 按 key 路由 | 同 key 进同 partition 保序 | 业务实体内有序需求 |
| Saga | 跨服务最终一致（编排 / 编舞） | 跨服务事务（详见 M08） |

### 10.2 反模式

#### 反模式 1：用消息当 RPC

```
A → publish("GetUserInfo", userId) → B
B → publish("GetUserInfoResponse", userInfo) → A
A 同步等待响应（轮询或临时订阅）
```

为什么错：

- 异步消息加了一层延迟（10-100ms）。
- 失败语义不明（B 没响应是挂了？是繁忙？）。
- 让 broker 成了 RPC 中介，broker 拥塞会让所有调用都慢。
- 同步语义被异步基础设施承载，运维复杂度暴涨。

修复：**RPC 用 gRPC / HTTP**（M04），消息留给真异步场景。

#### 反模式 2：消息体过大

把一份 5MB 的图片塞进 Kafka 消息。

后果：

- 内存占用爆炸（一个 batch 几百条 = GB 级）。
- 拖慢 broker 复制（ISR 同步慢）。
- 触发 producer / broker 的 `message.max.bytes` 拒绝。
- consumer 单 poll 易 OOM。

修复：**Claim-Check 模式**——大对象传 OSS / S3，消息只带 URL + 元数据。

```json
{
  "event_id": "...",
  "asset_url": "s3://bucket/images/abcdef.jpg",
  "asset_size": 5242880,
  "asset_sha256": "..."
}
```

#### 反模式 3：消费不幂等

消费方写："如果消息来了就 +1"。
重试一次余额 +2，再重试 +3。
线上事故现场之一。

修复：见第五章。

#### 反模式 4：Dual Write（先 DB 后消息）

```
tx.commit()        ← DB 成功
producer.send(...) ← 消息发送失败
```

DB 改了但事件没出去 → 下游永远缺这条事件。

```
producer.send(...) ← 消息发送成功
tx.commit()        ← DB 失败
```

事件出去了但 DB 没改 → 下游消费幽灵事件。

修复：**Outbox 模式**（详见 M08）。

#### 反模式 5：广播命令

把 `ChargeOrder` 这种命令发到 fanout topic 让所有人都看。
后果：多个服务可能都尝试扣款 → 双重扣款。

修复：命令应该 P2P 路由，事件才广播。

#### 反模式 6：跨服务共享 Topic 语义

OrderService 发 `OrderPlaced` 到 topic，PaymentService 也往同一 topic 发 `PaymentRequested`。Schema 不一致、订阅方混乱。

修复：**一个 topic = 一个事件类型 + 一个发布者**（或一个聚合根的所有事件）。Schema Registry 强制 Schema 演化兼容（M20）。

#### 反模式 7：事件名是动词不是事实

错：`SendingEmail`, `ChargingUser`, `OrderToBeShipped`。
对：`EmailSent`, `UserCharged`, `OrderShipped`。

事件 = 已发生的事实，名字用**过去时**。

#### 反模式 8：事件载荷依赖外部一致状态

事件只带 `userId`，订阅方需要回查 `UserService` 才能拿到地址。
但回查时用户已迁移地址，发送的发票寄到错的地址。

修复：用"状态传递事件"——载荷里带需要的字段快照。

### 10.3 设计 Checklist

新增一个事件流时检查：

- [ ] 这是事件还是命令？命名是过去时事实吗？
- [ ] Schema 注册了吗？有版本兼容策略吗？
- [ ] 业务幂等 key 在哪里？消费方能用它去重吗？
- [ ] 顺序保证需要吗？按什么 key 路由？
- [ ] 消息体多大？需要 Claim-Check 吗？
- [ ] DLQ topic 建了吗？告警接了吗？
- [ ] Lag 监控加了吗？SLA 阈值是什么？
- [ ] 消费者处理耗时 < `max.poll.interval.ms` 吗？
- [ ] 跨服务的最终一致窗口是多少？业务方接受吗？

    for msg := range c.Messages() {

    }

## 陷阱清单

1. **以为 Kafka EOS = 端到端 EOS**：EOS 只管 Kafka 内，跨外部系统仍需业务幂等。
2. **以为 acks=all 就不丢消息**：还要 ISR 副本数 > 1、`min.insync.replicas >= 2`。
3. **以为顺序按 key 路由就 OK**：还有重试乱序、worker pool 乱序、rebalance 乱序。
4. **消费者处理慢被踢出 group**：超 `max.poll.interval.ms` → 不停 rebalance → 越踢越慢。
5. **rebalance 期间业务暂停**：用 CooperativeStickyAssignor + KIP-848（KIP-848 在 Kafka 4.0 已 GA，但客户端需显式设 `group.protocol=consumer` 启用）。
6. **DLQ 没人看**：流入但无告警、无修复、不回灌 → 等同于丢消息。
7. **大消息打爆 broker**：用 Claim-Check 模式。
8. **消费方调外部 API 不带幂等 key**：上游重试 → 下游重复扣款。
9. **状态机消费没用 affected_rows 判断**：每次都"成功"，业务上重复执行了。
10. **Topic schema 自由演化**：今天加字段、明天删字段 → 消费方批量解析失败。要用 Schema Registry + 兼容性策略（M20）。
11. **混用命令与事件 topic**：导致跨上下文耦合，订阅方混乱。
12. **同 group 既消费又生产相关 topic**：易死循环 / 自我放大。
13. **Lag 报警用记录数不用时间**：低峰 10k 不算事、高峰 1k 已要救火。
14. **忘了清理去重表**：DB 爆磁盘。
15. **`auto.offset.reset=latest` 在新建消费者**：上线即丢历史数据，业务方没意识到。
16. **跨集群事件复制忘了去重**：MirrorMaker 把 DLQ 也复制过去，回灌时双倍。

## 参考答案

1. **概念辨析**
   - **消息 vs 事件**：消息是"请你做某件事"的命令/请求（祈使句、将来时），通常只有 1 个接收者负责执行，发送方知道接收方"应做的事"、失败需重试或返回错误；事件是"某件事已经发生了"的事实陈述（完成时），有 0..N 个订阅方各自反应，发送方不关心谁订阅、失败由订阅方各自处理不回流。一句话：消息是"任务"，事件是"事实"。不可混用的例子：`ChargeOrderCommand`（命令，必须有且仅有一个支付服务执行，重复执行会双重扣款）与 `OrderPlaced`（事件，库存/物流/积分/风控各自订阅反应）。把 `ChargeOrder` 当事件广播会导致多个服务都尝试扣款。
   - **三类事件**：通知事件只带 ID 与最小信息，订阅方需回查详情——消息体小，但有"事件雪崩"风险且可能读到已变化的不一致版本；状态传递事件载荷含完整业务状态快照，订阅方无需回查、可完全自治离线消费——消息体大，是多数微服务事件的选择；事件溯源事件是业务领域事件，系统状态本身由事件序列重建，只在业务模型适合 Event Sourcing（审计严苛、状态历史重要）时用。

2. **选型**
   - **点击流场景选 Kafka**。理由：每天 50 亿条属于超大吞吐（百万 msg/s 级），Kafka 持久日志范式是事件流/数据管道的默认选择；8 个下游分析服务用 8 个不同 Consumer Group 实现 Pub-Sub 广播，互不干扰；24h 回放靠基于时间/大小的消息保留策略天然支持；生态（Connect/Streams、Schema Registry）成熟。RabbitMQ 设计上消费即删、吞吐万级会被打挂；NATS 生态弱不适合企业数据管道；Pulsar 理论可行但此场景无多租户需求，Kafka 仍是默认。
   - **OA 工作流选 RabbitMQ**。理由：每小时 1 万任务吞吐很低，但需要优先级队列、延时队列、复杂路由（Direct/Topic/Fanout/Headers）——这些都是 RabbitMQ 原生支持而 Kafka 需应用层实现的能力；工作任务分发是典型的 Point-to-Point/竞争消费场景，且内置 DLX 死信支持。

3. **语义**
   - **EOS 两层**：第一层 Idempotent Producer（`enable.idempotence=true`，Kafka 3.0+ 默认开），给每条消息加 `(producerId, epoch, sequence)`，broker 按序号去重，作用域是单 partition、单会话内防重；第二层 Transactional Producer + Read-Committed Consumer，用稳定的 `transactional.id` 把多条 send + commit offset 包成事务，broker 标记 commit/abort，消费者 `isolation.level=read_committed` 只读 committed 数据，作用域是 Kafka → Kafka 的流处理（保证"读→处理→写+commit offset"原子）。
   - **为什么管不到外部 MySQL**：Kafka 的 EOS 作用域仅限 Kafka 内部，一旦把消息消费后写到 MySQL、Redis 或外部 API，事务边界就跨出了 Kafka，broker 无法把"外部写入"纳入它的事务 marker 机制。工程上等价"端到端 EOS"的思路：用 at-least-once + 业务幂等——消费方以业务唯一 key + DB 唯一约束（或状态机、去重表）保证重复消息被静默忽略，副作用本身也透传同一幂等 key；写出侧用 Outbox 模式避免 Dual Write。Kafka EOS 只是其中一环，业务幂等层才是端到端保证的核心。

4. **幂等**
   - **充值幂等方案**：① 幂等 key 用复合 key，如 `from + to + business_id + business_type`（"重复发起就该幂等"的最小标识全进 key），消息体带 `event_id`；② DB 表带 `event_id VARCHAR(64) NOT NULL UNIQUE` 唯一约束的充值流水表，或在余额表用状态机；③ 消费代码以 `INSERT ... ON CONFLICT (event_id) DO NOTHING`（PG）/ `INSERT IGNORE`（MySQL）作为幂等锚点，唯一约束保证重复消息被静默忽略，加钱副作用放在 INSERT 之后并在同一事务内，并发同 key 用 DB 行锁保证重入安全；④ 清理用 TTL 删除（上游保证 N 天后不再重发）或按月分区表到期 DROP PARTITION。
   - **1TB 去重表清理**：① TTL 删除——event_id 保留 N 天后删，前提是上游业务保证 N 天后不会再重发同一消息；② 业务上下文绑定——event_id 与业务实体一起删（如订单归档时清理），适用长周期业务；③ 分区表 + DROP PARTITION——按月分区，到期直接 `DROP TABLE consumed_events_2025_11`，比 DELETE 高效不产生大事务，适合持续高写入场景。

5. **DLQ 与重试**
   - **完整链路**：`order.placed`（主 topic，进程内重试 1-3 次处理短瞬时错误）→ 失败发 `order.placed.retry.5s`（等 5s 重消费，处理中等错误）→ 仍失败发 `order.placed.retry.30s` → `order.placed.retry.5m`（N 个固定延迟 topic 按需路由，业界标准做法）→ 多次失败送 `order.placed.dlq`（重试耗尽/反序列化失败 poison pill/业务明确不通过）→ 人工分析修复后带"已修复"标记回灌主 topic。命名约定为 `<domain>.<entity>.<event>.retry.Ns` / `.dlq`；DLQ 消息必带 original_topic/partition/offset、error_class、retry_attempts 等元数据，否则就是黑洞。
   - **毒消息阻塞排障**：根因——一条反复失败的消息让消费者卡在同一 offset 反复重试，阻塞同 partition 所有后续消息（队头阻塞）。紧急止血——N 次失败后立即把该消息发到 DLQ 并 commit offset+1 放行（关键是不要在处理处 panic/阻塞），让后续 10 万条恢复消费。长期修复——分析 DLQ 消息分类定位是数据错误还是代码 bug；用隔离 worker pool 把高失败率 key 路由到专用 worker、按 tenant/VIP 做 bulkhead；接 DLQ 流入速率告警；从 producer 端拦截这类必然失败的消息。

6. **顺序**
   - **余额端到端保序**：producer 侧用 `account_id` 作 key，`partition = hash(key) % num_partitions` 保证同账户消息进同一 partition；开 `enable.idempotence=true`（配合 `max.in.flight.requests.per.connection=5` 安全），broker 内单 partition 按写入顺序持久化；consumer 按 offset 递增读取，多线程处理时按 `hash(msg.Key) % workerCount` 路由到固定 worker。四个失效陷阱：① 生产端 in-flight 重试乱序（关 idempotence + retries>0 + in-flight>1）→ 开 idempotence；② 消费端线程池并行处理同 key 乱序 → 按 key 路由固定 worker；③ rebalance 跨 partition 重处理交叉 → 处理逻辑幂等；④ DLQ 回灌把消息推到"未来" → 同 key 阻塞机制或业务容忍乱序（按时间戳重排）。
   - **评论系统**：用 `post_id`（帖子 ID）作分区 key，保证同帖子下所有评论进同一 partition 严格保序，跨帖子无序要求所以可分散到不同 partition 并行。partition 数推算依据：上限决定消费者扩容上限（M consumers ≤ N partitions 才不浪费），需按峰值写入吞吐 / 单 partition 吞吐上限、以及预估的最大并行消费者数前瞻性预留，topic 创建后增 partition 会改变 hash 路由破坏既有保序，故应一次预估到位。

7. **Rebalance**
   - **两种 Rebalance**：Stop-the-world（默认旧机制）整个 group 暂停消费、所有 partition 重分配，造成数秒到数十秒"消费冰冻"，对延迟敏感业务是灾难；Cooperative/Incremental（2.4+，`CooperativeStickyAssignor`）只移动必须移动的 partition、其余持续消费，影响时间从数十秒降到亚秒级。Kafka 3.x → 4.x 演化：KIP-848 服务端协调协议，消费者不再参与协调状态机，3.7 引入、4.0 broker 端 GA 默认开启，但客户端默认仍是旧协议，需显式设 `group.protocol=consumer` opt-in。
   - **每分钟 5 次 rebalance 排障**：可能根因——① 消费者处理慢超 `max.poll.interval.ms` 被踢出（最常见）；② `session.timeout.ms`/`heartbeat.interval.ms` 配置与心跳频率不匹配；③ 消费者频繁崩溃重启/扩缩容；④ 用了 stop-the-world assignor 而非 CooperativeSticky；⑤ 订阅 topic 的 partition 数变化或 GC 停顿导致心跳超时。诊断步骤：查 `consumer_rebalance_count` 与 `consumer_processing_duration_p99`，对比处理耗时与 max.poll.interval；查实例日志有无心跳超时/OOM/重启；缩小 `max.poll.records` batch、把慢操作异步化、切 CooperativeStickyAssignor、按需调大超时（治标）。

8. **架构题**（要点）
   - **架构图**：OrderService 发布 `order.placed`（状态传递事件，载荷含 items/amount/userId 完整快照）→ Payment/Inventory/Shipping 各用独立 Consumer Group 订阅；各服务处理后再发布各自事实事件（`PaymentSucceeded`、`InventoryReserved`、`ShipmentScheduled`）形成事件链，用 Saga（编舞）串联跨服务最终一致；写出侧统一用 Outbox + Debezium CDC 防 Dual Write。
   - **事件流图**：`order.placed` → Payment 订阅扣款 → 发 `payment.succeeded` → Inventory 订阅扣库存 → 发 `inventory.reserved` → Shipping 建运单。失败路径走各 topic 的 retry.5s/30s/5m → dlq。
   - **DB 表设计**：各服务有 `event_id UNIQUE` 幂等约束或状态机（`UPDATE ... WHERE status='CREATED'` 用 affected_rows 判断），加 outbox 表（业务 + 事件入库同一事务）与 consumed_events 去重表（按月分区）。
   - **顺序保证**：所有事件用 `order_id` 作 key 保证同订单进同 partition、状态机变更有序；消费端按 key 路由固定 worker。
   - **Schema 演化**：每个 topic = 一个事件类型 + 一个发布者，注册到 Schema Registry，用向后/向前兼容策略，只加可选字段不删字段。
   - **监控面板**：各消费组 lag（优先时间维 lag）、rebalance rate、dlq_rate、处理 P99；DLQ 流入速率超阈值告警。
   - **故障演练矩阵**：支付超时重试、库存不足业务拒绝进 DLQ、消费者批量重启 rebalance、毒消息阻塞、Schema 不兼容、上游重发幂等等场景的预期表现与恢复手段。
