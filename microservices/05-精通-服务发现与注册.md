# 精通服务发现与注册：Consul、etcd、K8s Service 与健康检查

> 关联章节：[精通 API 网关与 BFF](./06-精通-API-网关与-BFF.md)、[精通同步通信](./04-精通-同步通信.md)、[精通服务网格](./15-精通-服务网格.md)

---

## 引言：单体没有服务发现，微服务没法没有它

单体时代不存在"服务发现"——所有"服务调用"都是进程内函数调用，地址就是函数名。

到了微服务：服务有 N 个实例（HA + 扩容），实例的 IP 和端口随部署变化，实例随时可能挂掉或新增。**调用方怎么知道"现在能用哪些实例"**——这就是服务发现要解决的核心问题。

读完这一章你应该能：

- 解释客户端发现和服务端发现的取舍
- 说出 Consul / etcd / Eureka / K8s Service 各自的最佳场景
- 设计一套优雅下线流程（drain + preStop + readiness）
- 配置 gRPC 客户端的负载均衡策略
- 在跨集群 / 跨地域场景下选合适的服务发现拓扑

---

## 第 1 章：服务发现要解决的 3 个问题

### 1.1 服务注册（Registration）

服务实例启动后，要让"发现系统"知道：

- 我是谁（服务名 `order-service`）
- 我在哪（IP + Port）
- 我健康吗（健康检查）
- 我有哪些 metadata（版本、机房、权重等）

### 1.2 服务发现（Discovery）

客户端要知道：

- 服务 `order-service` 有哪些可用实例
- 这些实例的负载、健康、地域
- 一旦某实例挂掉，立刻知道

### 1.3 健康检查（Health Check）

发现系统要持续验证实例可用：

- 主动探测：定期 HTTP/TCP/gRPC 请求
- 被动检测：从调用结果推断（连续 N 个失败 = 不健康）
- 实例自报（heartbeat）

这三个职责合起来 = "服务发现系统"。

## 第 2 章：客户端发现 vs 服务端发现

### 2.1 客户端发现（Client-Side Discovery）

```
Client --查询--> Registry（实例列表）
       --直接调用--> ServiceInstance
```

客户端拉取实例列表，自己做负载均衡。**Eureka / Consul SDK / gRPC + DNS resolver** 都属此类。

**优点**：
- 客户端可定制负载均衡策略（EWMA / 一致性 hash 等）
- 少一跳网络（直连）
- 客户端可拿到丰富的实例 metadata（版本、地域、权重）

**缺点**：
- 客户端依赖服务发现 SDK，多语言需多份实现
- 客户端缓存可能滞后（脏数据）
- 大量客户端给 Registry 压力大

### 2.2 服务端发现（Server-Side Discovery）

```
Client --调用 LB VIP--> LoadBalancer --选实例--> ServiceInstance
                       (LB 查 Registry)
```

客户端调一个稳定地址（VIP / 域名），中间件负责路由。**K8s Service / AWS ELB / Consul + HAProxy** 都属此类。

**优点**：
- 客户端不感知发现机制，跨语言 0 成本
- 集中式控制，统一限流 / 熔断 / 加密
- 客户端不依赖 Registry

**缺点**：
- 多一跳延迟（LB 转发）
- LB 本身是单点（必须 HA）
- 负载均衡策略受 LB 限制

### 2.3 对比矩阵

| 维度 | 客户端发现 | 服务端发现 |
|---|---|---|
| 客户端依赖 | SDK（多语言要适配） | 无（用标准 DNS） |
| 网络跳数 | 1 跳 | 2 跳 |
| 负载均衡 | 客户端控制 | LB 控制 |
| 实例 metadata | 丰富 | 受 LB 限制 |
| 适合规模 | 中小（< 万实例） | 大（任意） |
| 典型代表 | Eureka, gRPC+SDK | K8s Service, AWS ELB |

**2026 主流：服务端发现（K8s Service）**。原因：跨语言友好 + 与服务网格天然结合。

## 第 3 章：DNS-based vs API-based

### 3.1 DNS-based 服务发现

K8s Service 是 DNS-based 的代表：

```bash
# 客户端只需要：
curl http://order-service.default.svc.cluster.local/api/orders

# DNS 解析：
order-service.default.svc.cluster.local. → 10.96.123.45 (ClusterIP / VIP)
```

K8s 通过 kube-proxy（iptables/IPVS）把 ClusterIP 流量转发到 Pod IP。

**优点**：
- 跨语言（任何能解析 DNS 的语言都能用）
- 极简（应用代码不需要服务发现库）
- 与 K8s 生态深度集成

**缺点**：
- DNS 缓存 TTL 导致实例变更感知慢
- 看不到实例细节（实际转发由 kube-proxy 处理）
- 自定义负载均衡难（只能用 LB 提供的策略）

### 3.2 API-based 服务发现

Consul / Eureka / etcd 都提供 HTTP / gRPC API 查询实例：

```bash
# Consul
curl http://consul:8500/v1/catalog/service/order-service

# 返回：
[
  {"Address": "10.0.1.5", "Port": 8080, "ServiceTags": ["v2", "us-west"]},
  {"Address": "10.0.1.6", "Port": 8080, "ServiceTags": ["v1", "us-west"]}
]
```

客户端可以拿到完整实例列表 + metadata。

**优点**：
- 实时（无 DNS TTL 问题）
- 丰富的 metadata
- 支持灵活的过滤（按 tag / metadata）
- 客户端控制负载均衡

**缺点**：
- 需要客户端 SDK
- 跨语言要维护多套库

### 3.3 混合方案

K8s 上可以用 `headless service`（ClusterIP=None）让 DNS 直接返回 Pod IP 列表，得到 API-based 的部分优势：

```bash
nslookup order-service-headless.default.svc.cluster.local
# 返回多个 Pod IP，不经过 kube-proxy
```

gRPC + DNS Resolver 就用这种方式做客户端负载均衡。

## 第 4 章：Consul 深度

### 4.1 Consul 架构

```
            ┌────────────────────────┐
            │   Consul Server (3-5)  │
            │   Raft 一致性          │
            └───┬────────────────┬───┘
                │                │
        ┌───────▼───┐    ┌──────▼──────┐
        │ Client    │    │ Client      │
        │ (每节点)   │    │ (每节点)    │
        └───┬───────┘    └────┬────────┘
            │                 │
       ┌────▼────┐       ┌────▼────┐
       │ Service │       │ Service │
       └─────────┘       └─────────┘
```

- **Server**（3 或 5）：Raft 一致性，存所有数据
- **Client**：每个节点一个 agent，转发请求，做本地 health check
- **Service**：业务进程，通过本地 Consul Client 注册

### 4.2 服务注册

```hcl
# /etc/consul.d/order-service.hcl
service {
  name = "order-service"
  port = 8080
  tags = ["v2", "us-west-2"]
  meta {
    version = "v2.3.1"
  }
  check {
    http = "http://localhost:8080/healthz"
    interval = "10s"
    timeout = "2s"
    deregister_critical_service_after = "30s"
  }
}
```

发布到本地 Consul Client：`consul reload`。

### 4.3 多数据中心（WAN Federation）

Consul 原生支持多 DC：

```
DC1 (us-west) ←─WAN gossip─→ DC2 (eu-east)
   Server×3                   Server×3
```

跨 DC 查询：

```bash
curl http://consul:8500/v1/catalog/service/order-service?dc=dc2
```

WAN gossip 用 LAN gossip 的不同端口（默认 8302），延迟容忍性更高。

### 4.4 健康检查

Consul 常见 5 种 check：

| 类型 | 例子 | 适用 |
|---|---|---|
| HTTP | `GET /healthz`，期望 200 | Web 服务 |
| TCP | 探测端口 | TCP 服务 |
| Script | 跑脚本，exit 0=passing | 自定义 |
| TTL | 服务主动 ping `PUT /v1/agent/check/pass/...` | 应用层心跳 |
| gRPC | gRPC Health Checking Protocol | gRPC 服务 |

`deregister_critical_service_after`：服务连续 critical 超过该时间，自动注销。生产建议 30s-1min。

## 第 5 章：etcd 作为服务发现

### 5.1 etcd 的角色

etcd 是 Raft KV，**本身不是服务发现框架**，但提供原语让应用自己实现：

- KV 存实例信息：`/services/order-service/instance-1` → `{"ip":"10.0.1.5","port":8080}`
- **Lease（租约）**：实例注册 KV 绑定 lease，lease 失效 KV 自动删除
- **Watch**：客户端 watch `/services/order-service/` 前缀，实例变更立即通知

### 5.2 实战：用 etcd lease 注册

```go
import (
    clientv3 "go.etcd.io/etcd/client/v3"
)

cli, _ := clientv3.New(clientv3.Config{Endpoints: []string{"etcd:2379"}})

// 创建 10s 租约
lease, _ := cli.Grant(ctx, 10)

// 注册实例
cli.Put(ctx, "/services/order-service/instance-1",
    `{"ip":"10.0.1.5","port":8080}`,
    clientv3.WithLease(lease.ID))

// 启动心跳（每 5s 续约）
ch, _ := cli.KeepAlive(ctx, lease.ID)
go func() {
    for range ch {} // drain
}()
```

进程崩溃 → 心跳停 → 10s 后 KV 自动删 → 客户端 watch 立即感知。

### 5.3 etcd vs Consul

| 维度 | etcd | Consul |
|---|---|---|
| 设计目标 | 通用 KV（K8s 用作配置存储） | 服务发现 + KV + 多 DC |
| 服务发现层 | 应用自实现 | 内置 |
| 健康检查 | 应用层心跳（lease） | 多种内置 check |
| 多 DC | 不支持原生联邦 | 原生 WAN |
| 学习曲线 | 简单 | 中 |
| 体量 | 轻 | 重 |
| 生产用途 | 多见于 K8s 内部、自研 | 多见于独立服务发现 |

经验：**K8s 集群内 → 直接用 Service**；**多集群 / 多语言 / 复杂 metadata → Consul**；**自研控制面 → etcd**。

## 第 6 章：Eureka（历史与现状）

Netflix 早期开源（2012），AP 模型：

- 注册中心多节点之间**最终一致**（不强一致）
- 网络分区时各 AZ 独立运行，避免脑裂导致服务"全死"
- 客户端缓存 + 自我保护机制（实例下线超过 15% 不再自动清理）

**2026 现状**：Eureka 1.x 已停止维护，Eureka 2.x 被取消。在 Spring Cloud 生态仍有遗存，但新项目几乎都迁到 Consul / Nacos / K8s Service。

历史教训：CAP 选 AP 是优势，但"自我保护"机制让"实际已挂的实例"长期留在列表，造成调用方误判。Consul 选 CP 路线（牺牲分区可用换强一致）。

## 第 7 章：K8s Service / EndpointSlice 深度

### 7.1 K8s Service 5 种类型

| 类型 | 用途 |
|---|---|
| ClusterIP | 集群内部 VIP（默认） |
| NodePort | 通过 Node IP + Port 暴露 |
| LoadBalancer | 云厂商 LB 自动创建 |
| ExternalName | DNS CNAME |
| Headless（ClusterIP=None） | 直接返回 Pod IP，跳过 kube-proxy |

### 7.2 Service / Endpoint / EndpointSlice

```
Service (虚拟 IP)
   │
   └─ Endpoint Slices（Pod IP 列表，K8s 1.21+ 默认）
        ├── EndpointSlice 1: [10.0.1.5, 10.0.1.6, ...]（最多 100 个）
        ├── EndpointSlice 2: [10.0.1.7, 10.0.1.8, ...]
```

EndpointSlice 取代老的 Endpoint（单对象太大）。K8s 控制器维护 Pod IP → Slice 的映射。

### 7.3 kube-proxy 转发模式

| 模式 | 原理 | 性能 |
|---|---|---|
| iptables | iptables 规则随机选 backend | 中（规则数 = Pod 数） |
| IPVS | 内核哈希表 + 多种算法 | 高 |
| eBPF（Cilium） | 内核 eBPF 程序 | **最高** |

大集群（10000+ Service）建议切 IPVS 或 Cilium，iptables 规则爆炸严重影响连接建立。

### 7.4 Headless Service + 客户端负载均衡

```yaml
apiVersion: v1
kind: Service
metadata:
  name: order-headless
spec:
  clusterIP: None  # ★ headless
  selector:
    app: order
  ports:
    - port: 8080
```

DNS 查询返回所有 Pod IP（A 记录列表）。gRPC 客户端用 `dns:///order-headless.default.svc.cluster.local:8080`，自动获取所有 IP 做客户端 LB。

## 第 8 章：健康检查模型深度

### 8.1 主动 vs 被动

**主动健康检查**：定期发探针：

- HTTP `GET /healthz`
- TCP `connect`
- gRPC `grpc.health.v1.Health/Check`
- 自定义脚本

**被动健康检查**：从实际请求结果统计：

- 连续 N 个 5xx → 暂时摘除
- P99 latency 超过阈值 → 降权

服务网格（Istio）和 Envoy 都支持被动检查（outlier detection）。

### 8.2 Readiness vs Liveness

K8s 区分两种探针：

| 探针 | 失败后果 | 何时用 |
|---|---|---|
| **Liveness** | Pod 重启 | 进程死锁、不可恢复异常 |
| **Readiness** | 从 Service 摘除（不重启） | 初始化中、暂时不可服务 |
| **Startup**（1.20+） | 启动期失败不杀 Pod | 慢启动应用 |

**陷阱**：把"依赖 DB 不通"放进 liveness → DB 抖动一下所有 Pod 重启 → 雪崩。应该放进 readiness。

### 8.3 健康检查的反模式

- **过于宽松**：只检查"进程在跑"，不检查"实际能服务"
- **过于严格**：检查所有依赖（DB / 缓存 / 下游 RPC），任何一个抖动整个服务摘除
- **检查路径需要鉴权**：探针打不通
- **检查路径自己出错**：返回 200 但实际服务挂了（缓存 / mock 路径）

经验：`/healthz`（liveness）只检查进程；`/readyz`（readiness）检查"我能干活"（已加载配置、可连数据库、依赖服务可达）。

## 第 9 章：服务优雅下线

### 9.1 错误的下线流程

```
kill -9 Pod  →  正在处理的请求全部失败  →  客户端立即看到错误
```

### 9.2 正确的下线流程

```
1. 收到 SIGTERM
2. /readyz 返回 503  →  从 Service 摘除（k8s 几秒后才生效）
3. preStop hook 等 10-30s（让流量从 Service 摘除生效 + 处理已收到的请求）
4. 优雅关闭：停止接新请求 + 等已有请求完成（grace period）
5. 关闭依赖（DB pool / Redis / 文件）
6. 进程退出
```

### 9.3 K8s 配置

```yaml
spec:
  terminationGracePeriodSeconds: 60  # 总宽限时长
  containers:
  - name: order
    lifecycle:
      preStop:
        exec:
          command: ["sh", "-c", "sleep 20"]  # 等待 endpoint 同步
    readinessProbe:
      httpGet:
        path: /readyz
        port: 8080
      periodSeconds: 5
```

### 9.4 应用代码

```go
sigCh := make(chan os.Signal, 1)
signal.Notify(sigCh, syscall.SIGTERM, syscall.SIGINT)
<-sigCh

// 1. 标记 not ready
ready.Store(false)

// 2. 等待 endpoint 摘除（K8s readiness 同步）
time.Sleep(20 * time.Second)

// 3. 优雅关闭 HTTP server
shutdownCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
server.Shutdown(shutdownCtx)

// 4. 关闭依赖
db.Close()
redis.Close()
```

## 第 10 章：客户端负载均衡算法

### 10.1 常见算法

| 算法 | 原理 | 适用 |
|---|---|---|
| Round Robin | 轮询 | 实例同构 |
| Weighted RR | 加权轮询 | 实例异构（不同配置） |
| Random | 随机 | 简单 |
| Least Connections | 选连接最少的 | 长连接 / 不均衡负载 |
| EWMA / P2C | 选 P2C 中响应快的 | 实例性能波动大 |
| Consistent Hash | 同 key 同实例 | 缓存 / sticky session |
| Power of Two Choices | 随机 2 个选最忙小 | 兼具简单与公平 |

### 10.2 gRPC 客户端 LB

```go
conn, err := grpc.Dial(
    "dns:///order-service:8080",
    grpc.WithDefaultServiceConfig(`{
        "loadBalancingConfig": [{"round_robin": {}}]
    }`),
    grpc.WithTransportCredentials(insecure.NewCredentials()),
)
```

gRPC-go 内置 `round_robin` / `pick_first`。xDS resolver 让 gRPC 直接对接 Istio 控制面（不需要 sidecar）。

### 10.3 P2C（Power of Two Choices）

```
随机选两个实例 A 和 B
若 A 的 active_request < B 的 active_request
   选 A
否则选 B
```

简单算法但效果接近 least connections（理论：随机 2 选 1 已经接近最优）。Envoy、gRPC、Linkerd 都用。

## 第 11 章：多集群 / 多地域服务发现

### 11.1 拓扑选择

| 拓扑 | 描述 | 适用 |
|---|---|---|
| **单集群** | 一个 K8s 集群内 | 单数据中心 |
| **多集群 + 中央 Registry** | Consul WAN / 中央 DNS | 跨地域，强一致 |
| **多集群 + 网格** | Istio multi-cluster / Cilium ClusterMesh | 跨地域，K8s 原生 |
| **多集群 + 联邦 DNS** | KubeFed / 自建 | 简单跨集群 |
| **边缘 + 中央** | Submariner / 自研 | 边缘计算 |

### 11.2 Cilium ClusterMesh

```yaml
# 两个集群直接通信
# Cluster A 的 Pod 可以解析 Cluster B 的 Service
# 通过共享的 Service Mesh + ClusterMesh

apiVersion: v1
kind: Service
metadata:
  name: order-service
  annotations:
    service.cilium.io/global: "true"  # 开启跨集群发现
```

### 11.3 Istio Multi-cluster

- 主从（Primary-Remote）：单控制面管多集群
- 多主（Multi-Primary）：每集群一控制面，跨集群信任
- 混合：复杂场景

## 生产实践

1. **K8s 集群内默认用 Service**：跨语言友好、与生态集成、零应用代码
2. **多集群 / 多语言 / 复杂 metadata 用 Consul**：成熟、稳定、社区活跃
3. **健康检查必须有 readyz 和 healthz 之分**：避免依赖抖动导致大批 Pod 重启
4. **优雅下线必须做**：terminationGracePeriodSeconds + preStop sleep + 应用 SIGTERM handling
5. **大集群用 IPVS / Cilium 替代 iptables**：iptables 规则数与 Service × Pod 成正比，10000+ 严重影响性能
6. **gRPC 用 DNS resolver + 客户端 LB**：避免 kube-proxy 转发跳数
7. **headless service + gRPC + P2C** 是高性能内部 RPC 推荐配置
8. **Consul 服务自动注销窗口**：`deregister_critical_service_after = "30s"` 防"僵尸实例"
9. **跨 DC 不要用强一致**：Consul WAN 是 gossip，能容忍延迟
10. **客户端缓存 + 兜底**：服务发现挂了不能让业务挂，本地缓存上次实例列表

---

## 陷阱清单

1. **DNS 缓存 TTL 太长** → 实例下线后客户端还在调老 IP；JVM 用户特别注意 `networkaddress.cache.ttl`
2. **K8s `/healthz` 检查 DB 连接** → DB 抖动整个 Pod 重启雪崩；应该放 `/readyz`
3. **优雅下线缺 preStop sleep** → Pod 收到 SIGTERM 立即关闭 HTTP，但 endpoint 同步还需几秒，正在分发的流量失败
4. **客户端不缓存实例列表** → Registry 挂导致业务挂
5. **服务注册的端口写死** → 多副本端口冲突
6. **健康检查接口路径需要 auth** → 探针打不通，K8s 杀 Pod
7. **iptables 规则爆炸** → 大集群 kube-proxy CPU 100%；切 IPVS
8. **跨集群用 ExternalName** → DNS 解析依赖外部，故障域扩大
9. **Eureka 自我保护机制** → 实例已挂但还在列表，调用失败
10. **服务注册了但缺 metadata** → 不能按版本 / 地域 / 权重路由
11. **L4 LB 做长连接负载均衡** → 不公平（已建连不会迁移），新连接才生效，老 Pod 杀掉前会持续接收流量
12. **混淆 Readiness 和 Liveness** → 后果差异巨大

## 练习题

1. 客户端发现和服务端发现的根本取舍是什么？给一个适合各自的场景。

   **答案**：客户端发现"灵活但耦合 SDK"，适合性能敏感、多策略 LB；服务端发现"通用但多一跳"，适合多语言、跨团队。K8s Service（服务端）+ gRPC headless（客户端）是常见组合。

2. K8s Pod 下线时大量请求 502。可能原因？

   **答案**：(1) 没有 readinessProbe，endpoint 同步前请求还在；(2) 没有 preStop sleep，SIGTERM 后立即关 HTTP；(3) 应用没处理 SIGTERM；(4) terminationGracePeriodSeconds 太短。

3. Consul WAN federation 和 K8s ClusterMesh 各自适合什么？

   **答案**：Consul WAN 适合多语言 / 异构基础设施（VM + K8s 混合）；ClusterMesh 适合纯 K8s + Cilium，性能更好但依赖单一厂商。

4. gRPC 客户端用 `dns:///service:8080` 但发现请求总打到同一个 Pod。为什么？

   **答案**：(1) Service 是 ClusterIP（VIP）而非 headless，DNS 只返回一个 IP；(2) 没配置 `round_robin` 负载均衡策略。改 headless service + `loadBalancingConfig: round_robin`。

5. 客户端发现 SDK 缓存了实例列表，但实例已下线 30 秒后客户端还在调它。怎么改？

   **答案**：(1) 服务端缩短 lease/TTL；(2) 客户端订阅变更（watch / long polling）；(3) 客户端被动检测（连续失败摘除）。

6. K8s 一个 Service 后面 100 个 Pod，部分 Pod CPU 100% 但还在 ready 状态。流量怎么避开这些 Pod？

   **答案**：K8s Service 不感知性能，需用服务网格（Istio outlier detection / 被动健康检查）或客户端 LB（P2C / EWMA）。

7. 优雅下线时 preStop 该 sleep 多久？

   **答案**：取决于 K8s endpoint 同步时间 + 客户端 DNS 缓存。经验：10-30 秒。K8s 1.21+ endpoint 一般 < 5s 同步，加缓冲到 15-20s。

8. 设计一个跨 3 个地域（US / EU / APAC）的服务发现方案，要求"本地优先 + 故障跨域 fallback"。

   **答案**：(1) 每地域独立 Consul DC，本地服务本地注册；(2) WAN federation 让 DC 互通；(3) 客户端先查本 DC，若实例不足或本地故障切到远 DC；(4) 用 metadata `region` 做权重，本地权重高，跨域权重低。Istio locality LB / Cilium service affinity 都能实现。
