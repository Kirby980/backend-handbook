## 引言：当一次请求穿过 12 个服务，瓶颈在哪一段？

```text
[client]
  └─> [api-gateway]  20ms
        └─> [auth]   8ms
        └─> [order-svc]   2300ms  ← 慢
              ├─> [user-svc]      12ms
              ├─> [inventory-svc] 18ms
              ├─> [pricing-svc]   2200ms ← 真正的慢点
              │     └─> [cache]   1ms
              │     └─> [db]      2180ms ← 最深处
              └─> [kafka publish] 5ms
```

2026 年一个"看起来正常"的电商订单接口，背后实际穿过 8-15 个微服务。客户端报"P99 超过 2 秒"——光看一台机器的 CPU、内存、QPS 都没问题。只有把同一次请求在所有服务里走过的轨迹"穿"起来，画成一棵调用树，才能一眼看出"2.2 秒里有 2.18 秒卡在 pricing-svc 的某条 SQL 上"。

这条"轨迹"就是 **Trace**。能把它正确拼起来、零侵入嵌入到代码、跨进程跨语言跨异步消息全程传递，是分布式系统**最重要的可观测能力**。

链路追踪的核心难点不在"打 Span"，而在三件事：

1. **跨进程上下文传播**：HTTP/gRPC/消息队列/异步任务，每跨一次进程边界都要把 trace-id 带过去
2. **采样**：100% 采样会把后端打爆（10K QPS × 50 Span = 50 万 Span/s），如何只采"有价值"的轨迹
3. **关联**：把 Trace 和 Metrics、Logs、Profile 在同一个 trace-id 上对齐，才能闭环排查

2026 年这件事已经标准化：**OpenTelemetry**（CNCF Graduated，2023 年毕业）统一了 API/SDK/Protocol/Collector，Jaeger / Tempo / Zipkin 都只是"后端展示"。本章把它从原理到落地讲清楚。

| 主题 | 2026 现状 |
|---|---|
| 上下文标准 | **W3C TraceContext**（traceparent + tracestate）正式 RFC，Level 2 |
| 协议 | **OTLP**（OpenTelemetry Protocol）gRPC/HTTP，CNCF Graduated |
| SDK | OTel SDK 已覆盖 Go / Java / Python / JS / Rust / .NET / PHP / Ruby（11 种语言 Stable） |
| 后端 | **Tempo 2.x**（Grafana）/ **Jaeger 2.x**（已重构基于 OTel Collector）/ Honeycomb / Datadog |
| 自动埋点 | Java agent / .NET / Python / Node 已稳定；Go 通过 eBPF / 编译时注入逐步成熟 |
| 采样 | Tail-based sampling 成主流（OTel Collector tail_sampling processor） |
| eBPF auto-trace | Pixie / Beyla（Grafana）/ Coroot 等无需改代码 |
| 关联 | Exemplars（Prom + Trace）/ trace_id 注入日志，已成默认 |

## 第一章：链路追踪的基本概念——Trace、Span、SpanContext

### 1.1 一张图看懂三个核心抽象

```text
                Trace (trace_id = abc123…)
   ┌──────────────────────────────────────────────────────┐
   │  Span A: api-gateway /order                          │
   │  span_id=001  parent=null  duration=420ms            │
   │    ┌──────────────────────────────────────────────┐  │
   │    │ Span B: order-svc CreateOrder               │  │
   │    │ span_id=002  parent=001  duration=400ms     │  │
   │    │   ┌──────────────────────────────────────┐  │  │
   │    │   │ Span C: pricing-svc Calculate       │  │  │
   │    │   │ span_id=003  parent=002  dur=380ms   │  │  │
   │    │   │   ┌──────────────────────────────┐    │  │  │
   │    │   │   │ Span D: pg SELECT pricing    │    │  │  │
   │    │   │   │ span_id=004  parent=003 360ms│    │  │  │
   │    │   │   └──────────────────────────────┘    │  │  │
   │    │   └──────────────────────────────────────┘  │  │
   │    └──────────────────────────────────────────────┘  │
   └──────────────────────────────────────────────────────┘
```

三个抽象的精确含义：

| 抽象 | 含义 | 关键字段 |
|---|---|---|
| **Trace** | 一次端到端的请求轨迹，由多个 Span 组成的有向无环图（通常是树） | `trace_id`（128bit 全局唯一） |
| **Span** | 一段"有开始有结束"的工作单元（一次 HTTP 调用、一次 SQL、一次函数） | `span_id` / `parent_span_id` / `start_time` / `end_time` / `attributes` / `events` / `status` / `kind` |
| **SpanContext** | 跨进程**传播**的最小上下文（只带"指向当前 Span 的引用 + 采样标志"） | `trace_id` + `span_id` + `trace_flags` + `trace_state` |

记住一句口号：**Trace 是树，Span 是节点，SpanContext 是过线时塞给下游的"通行证"**。

### 1.2 Span 模型详解

OpenTelemetry 规范定义的 Span 必备字段：

```go
type Span struct {
    // 标识
    TraceID      [16]byte   // 全局唯一，16 字节
    SpanID       [8]byte    // 单 Trace 内唯一，8 字节
    ParentSpanID [8]byte    // 父 Span（根 Span 为全零）
    TraceFlags   byte       // 采样标志位（0x01 = sampled）
    TraceState   string     // 厂商自定义 K/V（最多 32 个）

    // 内容
    Name      string                 // Span 名（操作名）
    Kind      SpanKind               // CLIENT/SERVER/PRODUCER/CONSUMER/INTERNAL
    StartTime time.Time
    EndTime   time.Time
    Attributes map[string]any        // 业务/技术标签，如 http.method
    Events    []Event                // 时间点事件，如 "cache miss"
    Links     []Link                 // 跨 Trace 引用（异步 fan-in 用）
    Status    Status                 // OK / ERROR + message
    Resource  Resource               // 进程级标签：service.name 等
}
```

#### SpanKind 详解

| Kind | 含义 | 典型例子 |
|---|---|---|
| `SERVER` | 收到入站调用 | HTTP server 收到请求 |
| `CLIENT` | 发出出站调用 | 调用下游 HTTP/gRPC |
| `PRODUCER` | 发布异步消息 | 向 Kafka publish |
| `CONSUMER` | 消费异步消息 | 从 Kafka consume |
| `INTERNAL` | 进程内一段工作 | 调用内部函数、库 |

**Kind 决定了后端 UI 的可视化方式**：CLIENT-SERVER 配对组成 RPC，PRODUCER-CONSUMER 配对组成消息流。

#### Attributes（属性） vs Events（事件） vs Links（链接）

```go
// 属性：描述"这段工作"是什么（在 Span 整个生命周期成立）
span.SetAttributes(
    attribute.String("http.method", "POST"),
    attribute.String("http.url", "/api/order"),
    attribute.Int("http.status_code", 200),
    attribute.String("db.statement", "SELECT * FROM order WHERE id=$1"),
    attribute.String("user.id", "u_4521"),
)

// 事件：Span 内某个"时间点"发生了什么（一次性）
span.AddEvent("cache_miss", trace.WithAttributes(
    attribute.String("key", "user:4521"),
))
span.AddEvent("retry", trace.WithAttributes(
    attribute.Int("attempt", 2),
))

// 链接：指向另一个 Trace 的 Span（异步 fan-in 时常用）
span := tracer.Start(ctx, "batch_process",
    trace.WithLinks(trace.Link{SpanContext: originalSpanContext}))
```

**Attribute** = "这段调用是 POST /api/order"；**Event** = "在 220ms 时发生了 cache_miss"；**Link** = "这次批处理由 [trace=xxx, span=yyy] 触发"。

#### Status

```go
span.SetStatus(codes.Error, "user not found")
// 或
span.SetStatus(codes.Ok, "")
```

注意：**HTTP 4xx 是否算错误**取决于 SpanKind：
- SERVER 端：HTTP 4xx **不算** Span 错误（客户端问题）
- CLIENT 端：HTTP 4xx **算** Span 错误（我调用对方失败了）

这是 OTel 语义约定（Semantic Conventions）的细节，2026 年生产环境必须配置正确，否则告警全是误报。

### 1.3 Span 树 vs Span DAG

99% 的场景 Span 构成树（每个 Span 只有一个 parent）。但**异步消息 fan-in / 批处理**场景下需要 DAG，用 `Links` 实现：

```text
Trace A (订单 1)  ─┐
Trace B (订单 2)  ─┼─> 定时任务批量处理（用 Link 指回 3 个原 Trace）
Trace C (订单 3)  ─┘
```

Link 不算 parent-child 关系，后端 UI 通常用虚线表示。

## 第二章：W3C TraceContext 标准——跨进程的"通行证"

### 2.1 为什么需要标准

2010-2018 年的链路追踪是各家私有协议的"诸侯混战"：

| 厂商/系统 | Header 格式 | 字段 |
|---|---|---|
| Google Dapper（论文 2010） | 内部 | trace_id, span_id |
| Zipkin / B3 | `X-B3-TraceId` / `X-B3-SpanId` / `X-B3-ParentSpanId` / `X-B3-Sampled` | 4 个 header（或 1 个 `b3:` 简写） |
| Jaeger | `uber-trace-id: {trace-id}:{span-id}:{parent-span-id}:{flags}` | 1 个组合 header |
| Google Cloud Trace | `X-Cloud-Trace-Context: TRACE_ID/SPAN_ID;o=OPTIONS` | 1 个 header |
| AWS X-Ray | `X-Amzn-Trace-Id: Root=1-...;Parent=...;Sampled=1` | 1 个 header |
| 阿里 Eagle Eye | `EagleEye-TraceID` 等 | 多个 header |

后果：跨厂商系统的调用链直接断掉。同一个公司接入了阿里 SLS 和自建 Jaeger，链路在网关层断成两截。

### 2.2 W3C TraceContext 规范

2020 年 W3C 发布 [Trace Context](https://www.w3.org/TR/trace-context/) RFC（2022 年 Level 2）。所有主流厂商已全部支持，**2026 年新项目无脑选 W3C**。

规范只有两个 HTTP header：

```http
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
             │  │                                │                │
             │  │                                │                └─ trace-flags (1 字节, 01=sampled)
             │  │                                └────────────────── parent-id / span-id (8 字节)
             │  └────────────────────────────────────────────────── trace-id (16 字节)
             └─ version (1 字节, 当前 00)

tracestate: rojo=00f067aa0ba902b7,congo=t61rcWkgMzE
            │                       │
            │                       └─ congo 厂商的扩展键值
            └─ rojo 厂商的扩展键值
```

`traceparent` 各字段（hex 编码）：

| 字段 | 字节数 | 说明 |
|---|---|---|
| version | 1 | `00` 当前版本 |
| trace-id | 16 | 全局 Trace ID，不能全 0 |
| parent-id | 8 | 当前父 Span ID（即将进入下游时的发送方 Span），不能全 0 |
| trace-flags | 1 | bit 0 = sampled；其余保留 |

`tracestate` 是厂商扩展，给特定 vendor 加附加信息（如 Datadog `dd=...`、Honeycomb `hc=...`）。规则：
- 最多 32 个键值对
- 总长度 ≤ 512 字节
- 顺序有意义（**最左**是最近的厂商）

### 2.3 propagation 注入与提取

发送端（CLIENT Span）注入：

```go
// HTTP 出站：在 request header 注入
propagator := otel.GetTextMapPropagator()
propagator.Inject(ctx, propagation.HeaderCarrier(req.Header))
// 此时 req.Header 已包含 traceparent + tracestate
```

接收端（SERVER Span）提取：

```go
// HTTP 入站：从 request header 提取
ctx := propagator.Extract(r.Context(), propagation.HeaderCarrier(r.Header))
// 用提取出的 ctx 启动 SERVER Span，会自动成为对方 CLIENT Span 的子 Span
_, span := tracer.Start(ctx, "handle_order", trace.WithSpanKind(trace.SpanKindServer))
```

### 2.4 老格式兼容（B3 / Jaeger / X-Cloud-Trace）

迁移期间需要同时识别新老格式。OTel 支持 **多 propagator 组合**：

```go
otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(
    propagation.TraceContext{},   // W3C（首选）
    propagation.Baggage{},        // W3C Baggage
    b3.New(b3.WithInjectEncoding(b3.B3MultipleHeader)),  // B3 兼容
    // 如有需要：jaegerpropagator.Jaeger{}, gcppropagator.CloudTraceFormatPropagator{}
))
```

注入时**每种都注入**，提取时**任何一种命中即可**。生产环境推荐策略：

| 阶段 | 注入 | 提取 |
|---|---|---|
| 全新项目 | W3C only | W3C only |
| 迁移期 | W3C + B3 | W3C + B3 + 老格式 |
| 完全切完 | W3C only | W3C only（关闭老格式提取） |

### 2.5 Baggage：另一个独立通道

`baggage` 是 W3C 另一个 header，**与 trace 独立**，用来跨进程传递业务级 K/V（如用户 ID、Tenant、A/B 实验组）。

```http
baggage: userId=4521,tenant=acme,experiment=variant-b
```

```go
// 写入
ctx = baggage.ContextWithValues(ctx,
    attribute.String("userId", "4521"),
    attribute.String("tenant", "acme"))

// 读取（任意下游服务）
mem := baggage.FromContext(ctx).Member("tenant")
fmt.Println(mem.Value())  // "acme"
```

Baggage 的典型用途：**全链路染色**（让一个测试用户的所有 Span 都打上 `test=true` 标签，方便后台过滤）。注意：**Baggage 会原样传递到所有下游**，不要塞敏感信息（PII、token）。

## 第三章：跨进程与跨异步消息的上下文传播

### 3.1 HTTP 传播

最简单。所有主流 HTTP 库（Go `net/http`、Java OkHttp/Spring、Node Express/Fetch、Python requests）都有 OTel instrumentation：

```go
import "go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp"

// 服务端：包一层 middleware，自动提取 + 启动 SERVER Span
handler := otelhttp.NewHandler(myHandler, "order-svc")
http.ListenAndServe(":8080", handler)

// 客户端：用包装后的 Transport，自动注入 + 启动 CLIENT Span
client := &http.Client{Transport: otelhttp.NewTransport(http.DefaultTransport)}
resp, _ := client.Do(req)
```

### 3.2 gRPC 传播

gRPC 的元数据（metadata）类似 HTTP header，OTel 有内置 interceptor：

```go
import "go.opentelemetry.io/contrib/instrumentation/google.golang.org/grpc/otelgrpc"

// Server
server := grpc.NewServer(
    grpc.StatsHandler(otelgrpc.NewServerHandler()),
)

// Client
conn, _ := grpc.Dial(addr,
    grpc.WithStatsHandler(otelgrpc.NewClientHandler()),
)
```

注意 2024 年起 OTel Go 已废弃 `UnaryClientInterceptor`/`StreamClientInterceptor` 改用 `StatsHandler`（统一支持 unary + streaming）。

### 3.3 Kafka 传播

Kafka 消息的 header（KIP-82，2017 引入）是天然的 carrier。生产者注入：

```go
// 生产者
msg := &kafka.Message{Topic: "order-events", Value: payload}

// 把当前 ctx 的 trace 注入到 msg.Headers
carrier := NewKafkaCarrier(&msg.Headers)
otel.GetTextMapPropagator().Inject(ctx, carrier)

// 启动 PRODUCER Span
ctx, span := tracer.Start(ctx, "kafka.publish",
    trace.WithSpanKind(trace.SpanKindProducer),
    trace.WithAttributes(
        attribute.String("messaging.system", "kafka"),
        attribute.String("messaging.destination.name", msg.Topic),
    ))
defer span.End()

producer.Produce(msg, nil)
```

消费者提取：

```go
// 消费者
msg := <-consumer.Events()

carrier := NewKafkaCarrier(&msg.Headers)
ctx := otel.GetTextMapPropagator().Extract(context.Background(), carrier)

// 用提取的 ctx 启动 CONSUMER Span
ctx, span := tracer.Start(ctx, "kafka.consume",
    trace.WithSpanKind(trace.SpanKindConsumer),
    trace.WithAttributes(
        attribute.String("messaging.system", "kafka"),
        attribute.String("messaging.destination.name", msg.Topic),
    ))
defer span.End()

// 业务处理...
```

Carrier 接口实现：

```go
type kafkaCarrier struct{ h *[]kafka.Header }

func (c kafkaCarrier) Get(key string) string {
    for _, hdr := range *c.h {
        if hdr.Key == key { return string(hdr.Value) }
    }
    return ""
}
func (c kafkaCarrier) Set(key, val string) {
    for i, hdr := range *c.h {
        if hdr.Key == key { (*c.h)[i].Value = []byte(val); return }
    }
    *c.h = append(*c.h, kafka.Header{Key: key, Value: []byte(val)})
}
func (c kafkaCarrier) Keys() []string { /* ... */ }
```

### 3.4 异步任务 / 定时任务的特殊处理

**坑**：HTTP 处理函数把任务丢到 goroutine pool / 异步队列后，原 Trace 已经结束，但任务还在跑。两种正确做法：

**做法 A：用 Link 关联**（推荐）

```go
// HTTP handler
func handler(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context()
    spanContext := trace.SpanContextFromContext(ctx)

    // 异步任务时关联原 Trace（不是 parent，而是 link）
    go runAsync(spanContext)

    w.WriteHeader(202)
}

func runAsync(originalCtx trace.SpanContext) {
    _, span := tracer.Start(context.Background(), "async_work",
        trace.WithLinks(trace.Link{SpanContext: originalCtx}),
        trace.WithNewRoot())
    defer span.End()
    // ...
}
```

新 Trace 通过 Link 指回原 Trace。在 UI 上能看到"这个异步任务由 trace-id=xxx 触发"。

**做法 B：复用原 ctx**（仅适用于短任务）

```go
go func(ctx context.Context) {
    _, span := tracer.Start(ctx, "quick_async")
    defer span.End()
    // ...
}(r.Context())
```

但 `r.Context()` 在 HTTP 响应完成后会被 cancel，长任务会被打断——所以仅适合<1 秒的小任务。

### 3.5 跨语言传播的坑

| 坑 | 现象 | 解决 |
|---|---|---|
| Header 大小写 | Java HTTP 库把 `traceparent` 改成 `Traceparent`，某些代理不一致 | HTTP header 本来不区分大小写，但代码读取时要 case-insensitive |
| Underscore 被 nginx 拒绝 | nginx 默认会忽略带下划线的 header（`X_B3_TraceId`） | nginx 配置 `underscores_in_headers on;`，或改用 dash |
| 多次注入 | 重复注入 `traceparent`，header 变成数组 | 注入前先删，或用 `Set` 而非 `Add` |
| 大小写敏感的网关 | API Gateway 把 header 全部小写化后转发 | 检查网关 header 处理策略 |

## 第四章：OpenTelemetry 架构全景

### 4.1 OTel 项目分层

```text
┌──────────────────────────────────────────────────────────┐
│  应用代码                                                  │
│  ├─ Manual：tracer.Start() / span.SetAttributes()        │
│  └─ Auto：Java agent / Python autoinstrument / Go eBPF   │
├──────────────────────────────────────────────────────────┤
│  OTel API（稳定的接口）                                    │
│  ├─ tracer / meter / logger                              │
│  └─ propagator / baggage                                 │
├──────────────────────────────────────────────────────────┤
│  OTel SDK（实现）                                         │
│  ├─ Sampler（采样器）                                     │
│  ├─ Processor（BatchSpanProcessor / SimpleSpanProcessor）│
│  └─ Exporter（OTLP / Jaeger / Zipkin / Console）        │
├──────────────────────────────────────────────────────────┤
│  OTel Collector（独立进程，可选但强烈推荐）                  │
│  ├─ Receivers（OTLP / Jaeger / Zipkin / Prometheus）    │
│  ├─ Processors（batch / tail_sampling / attributes）    │
│  └─ Exporters（Tempo / Jaeger / Honeycomb / DataDog）   │
├──────────────────────────────────────────────────────────┤
│  后端 / 存储                                               │
│  └─ Tempo / Jaeger / Zipkin / SkyWalking / 商业 APM      │
└──────────────────────────────────────────────────────────┘
```

### 4.2 OTel Collector 三层：Receiver → Processor → Exporter

Collector 是**独立的、与语言无关的**数据处理网关。所有 SDK 推数据到 Collector，Collector 处理后导出到后端。

```yaml
# otel-collector-config.yaml
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }
  jaeger:
    protocols: { grpc: {} }     # 兼容老的 Jaeger client
  zipkin:
    endpoint: 0.0.0.0:9411      # 兼容老的 Zipkin client

processors:
  batch:
    timeout: 5s
    send_batch_size: 1024
  attributes:
    actions:
      - key: env
        value: prod
        action: insert
      - key: password
        action: delete            # 脱敏
```

### 4.3 部署模式：Agent vs Gateway

**Agent 模式**（DaemonSet 每个节点一份）：

```text
Pod ─┐
Pod ─┼─> Local Collector (Agent) ─> Central Collector (Gateway) ─> Backend
Pod ─┘
```

优点：本地批量、低网络开销、本地降级缓存
缺点：每节点占资源（CPU 100m / Mem 200Mi 起）

**Gateway 模式**（Deployment 集群级别 N 副本）：

```text
Pod ──┐
Pod ──┼─> Central Collector ─> Backend
Pod ──┘
```

优点：集中策略（采样、过滤）、节省节点资源
缺点：所有流量绕一道、网关挂全挂

**生产推荐**：**Agent + Gateway 两层**。Agent 做轻量批处理与本地降级，Gateway 做 tail sampling 与导出。

### 4.4 Resource：进程级标签

每个 SDK 实例启动时声明 `Resource`（进程级、不变的标签），后续所有 Span/Metric/Log 自动带上：

```go
res, _ := resource.Merge(
    resource.Default(),
    resource.NewWithAttributes(
        semconv.SchemaURL,
        semconv.ServiceName("order-svc"),
        semconv.ServiceVersion("v3.2.1"),
        semconv.DeploymentEnvironmentName("prod"),
        attribute.String("region", "ap-southeast-1"),
        attribute.String("k8s.cluster.name", "prod-1"),
        attribute.String("k8s.namespace.name", "shop"),
        attribute.String("k8s.pod.name", os.Getenv("HOSTNAME")),
    ),
)
```

K8s 部署时通过 Downward API 注入：

```yaml

  - name: OTEL_RESOURCE_ATTRIBUTES
    value: "service.name=order-svc,service.version=v3.2.1,deployment.environment=prod"
  - name: OTEL_SERVICE_NAME

  - name: K8S_POD_NAME
```

### 4.5 OTel Semantic Conventions（语义约定）

OTel 规定一套**标准 Attribute 名**，所有 SDK / 后端都按这个约定来。一些必背的：

| 类别 | Attribute | 示例 |
|---|---|---|
| 资源 | `service.name` | `order-svc` |
| 资源 | `service.version` | `v3.2.1` |
| HTTP | `http.request.method` | `POST` |
| HTTP | `http.response.status_code` | `200` |
| HTTP | `url.full` | `/api/order/123` |
| RPC | `rpc.system` | `grpc` |
| RPC | `rpc.service` | `order.v1.OrderService` |
| RPC | `rpc.method` | `CreateOrder` |
| DB | `db.system.name` | `postgresql` |
| DB | `db.query.text` | `SELECT * FROM order WHERE id=$1` |
| 消息 | `messaging.system` | `kafka` |
| 消息 | `messaging.destination.name` | `order-events` |
| 异常 | `exception.type` | `NullPointerException` |

**重要**：2024 年起 OTel 把许多 attribute 重命名（如 `http.method` → `http.request.method`），生产环境的 dashboard 要兼容新旧两套或固定一套。

## 第五章：手动埋点 vs 自动埋点

### 5.1 Auto Instrumentation 概览

**Auto Instrumentation** = 不改业务代码即可生成 Span。各语言机制不同：

| 语言 | 机制 | 成熟度 |
|---|---|---|
| Java | OTel Java Agent（javaagent JAR + bytecode 改写） | Stable，覆盖率最高（200+ 库） |
| .NET | OTel .NET Auto Instrumentation（CLR Profiler API） | Stable |
| Python | `opentelemetry-instrument` 命令（Monkey patch） | Stable |
| Node.js | `--require @opentelemetry/auto-instrumentations-node` | Stable |
| Ruby | `opentelemetry-instrumentation-all` | Stable |
| Go | **编译时**注入（`otel build`）或 eBPF（如 Beyla） | 2024 后渐成熟，但仍弱于 Java |
| Rust | 几乎没有 Auto，靠手动 | Manual |
| PHP | OTel PHP Auto Instrumentation | Stable |

Java agent 用法（最丝滑）：

```bash
# 下载 agent
curl -L -O https://github.com/open-telemetry/opentelemetry-java-instrumentation/releases/latest/download/opentelemetry-javaagent.jar

# 启动
java -javaagent:./opentelemetry-javaagent.jar \
     -Dotel.service.name=order-svc \
     -Dotel.exporter.otlp.endpoint=http://collector:4317 \
     -jar app.jar
```

**0 行业务代码改动**即可：Spring MVC / JDBC / Kafka / Redis / gRPC 全部自动出 Span。

### 5.2 Manual Instrumentation：什么时候必须手动

Auto 解决不了的场景：

1. **业务级 Span**：一段重要的业务逻辑（如"风控决策"、"价格计算"），需要手动标记
2. **业务级属性**：把 `user.id` / `order.id` / `tenant.id` 等业务字段加到 Span 上
3. **未支持的库**：自研 RPC 框架、小众消息中间件
4. **细粒度控制**：跨函数 Span（一个函数太大要拆）

```go
ctx, span := tracer.Start(ctx, "RiskEvaluation",
    trace.WithAttributes(
        attribute.String("user.id", userID),
        attribute.Float64("transaction.amount", amount),
        attribute.String("transaction.currency", "USD"),
    ))
defer span.End()

score, err := evaluateRisk(ctx, userID, amount)
if err != nil {
    span.RecordError(err)
    span.SetStatus(codes.Error, err.Error())
    return err
}
span.SetAttributes(attribute.Float64("risk.score", score))
```

### 5.3 混用策略

生产推荐：**Auto 打底 + 手动加业务关键 Span/属性**。

```text
auto: HTTP/RPC/DB/Cache/MQ 的 Span 全部自动
  +
manual: 业务关键节点（"提交订单"、"扣库存"、"风控通过"）+ 业务属性
```

## 第六章：采样策略——Head-based vs Tail-based

### 6.1 为什么需要采样

10K QPS × 平均 50 Span/请求 = **50 万 Span/秒**。一条 Span ~ 500 字节，每秒 250MB，每天 21TB——**全采的存储成本无法接受**。

但简单的 1% 采样会丢掉 99% 的错误链路（错误不是均匀分布的，反而是越罕见的请求越值得保留）。这就需要"聪明的采样"。

### 6.2 Head-based Sampling（头采样）

**决策点**：源头第一个 Span 生成时。
**决策依据**：随机、或基于 trace-id 哈希、或基于 attribute（如 user-id）。
**传播**：决策通过 `traceparent` 的 `trace-flags` 传给所有下游，全链路一致。

```go
// 头采样：1% 随机
provider := sdktrace.NewTracerProvider(
    sdktrace.WithSampler(sdktrace.TraceIDRatioBased(0.01)),
)
```

```go
// 父决策优先（兼容下游被采样的情况）
sampler := sdktrace.ParentBased(
    sdktrace.TraceIDRatioBased(0.01),    // 自己作为根时 1%
    sdktrace.WithRemoteParentSampled(sdktrace.AlwaysSample()),
    sdktrace.WithRemoteParentNotSampled(sdktrace.NeverSample()),
)
```

优点：
- 决策快（每个 Span 启动时一次随机数）
- 全链路一致（要么全采，要么全弃）
- 各服务可独立做（无需中心化协调）

缺点：
- **错过错误**：罕见的错误请求大概率被丢弃（错误率 0.1% × 采样 1% = 万分之一概率被采到）
- **错过慢请求**：99 分位慢请求大概率不在 1% 采样里

### 6.3 Tail-based Sampling（尾采样）

**决策点**：Trace 所有 Span 完成后（或超时）。
**决策依据**：基于整个 Trace 的特征（是否有 error、是否 > 1 秒、是否含某属性）。
**位置**：必须在 Collector（Gateway）端集中决策——SDK 端做不到。

```yaml
processors:
  tail_sampling:
    decision_wait: 30s           # 等 Trace 收齐多少秒做决策
    num_traces: 100000           # 内存里 buffer 多少 Trace
    expected_new_traces_per_sec: 10000

    policies:
      # 1) 所有错误 Trace 100% 保留
      - name: errors-100pct
        type: status_code
        status_code: { status_codes: [ERROR] }

      # 2) 所有慢 Trace（> 1s）100% 保留
      - name: slow-100pct
        type: latency
        latency: { threshold_ms: 1000 }

      # 3) 关键 user 100% 保留（如 VIP）
      - name: vip-100pct
        type: string_attribute
        string_attribute:
          key: user.tier
          values: [vip, enterprise]

      # 4) 其余 1% 抽样保留
      - name: baseline-1pct
        type: probabilistic
        probabilistic: { sampling_percentage: 1 }
```

优点：
- **能保住所有错误 + 所有慢请求** + 1% 基线，存储节省 95% 以上
- 决策依据可任意复杂

缺点：
- 需要 Collector buffer Trace 30 秒（**所有** Span 必须经过同一个 Collector 实例！）
- 跨 Collector 部署需要"按 trace-id 做 consistent hashing 路由"（OTel Collector 的 `load-balancing exporter` 已支持）

### 6.4 推荐架构：Tail Sampling + 路由

```text
┌─ Agent (each node)
│  └─ batch + forward (no sampling)
│
└─> Load-balancing Exporter
       │  按 trace-id hash 路由
       ▼
    Gateway Collector (N 副本)
       │  tail_sampling
       ▼
    Tempo / Jaeger
```

```yaml
# Agent 端：不采样，按 trace-id hash 路由到 Gateway
exporters:
  loadbalancing:
    resolver:
      dns:
        hostname: otel-gateway.observability.svc.cluster.local
    protocol: { otlp: {} }
    routing_key: traceID
```

### 6.5 头采样 + 尾采样组合

实际生产推荐组合：

| 阶段 | 策略 | 目的 |
|---|---|---|
| SDK | **head 100%**（不采样） | 不丢任何信号源 |
| Collector | **tail sampling**：error+slow+random | 控存储成本 |

如果应用流量极大（如百万 QPS），可以再加一层 SDK 端的 head 10%（先丢 90%）+ Collector tail 10%，最终保留 1%。

## 第七章：后端选型——Jaeger / Tempo / Zipkin / SkyWalking / 商业

### 7.1 主流后端对比

| 后端 | 创立 | 协议 | 存储 | 查询能力 | 2026 现状 |
|---|---|---|---|---|---|
| **Jaeger 2.x** | Uber（2017）| OTLP / Jaeger thrift | Cassandra / ES / Badger / **OTel Collector backbone** | TraceQL | 2024 重构为 v2，**基于 OTel Collector**，与 OTel 完全融合 |
| **Tempo** | Grafana（2020） | OTLP / Jaeger / Zipkin | 对象存储（S3/GCS/MinIO） | TraceQL（强，类似 PromQL） | **Grafana 默认 trace 后端**，与 Loki/Mimir/Pyroscope 集成度最高 |
| **Zipkin** | Twitter（2012） | Zipkin v1/v2 / OTLP | ES / Cassandra / MySQL | 简单过滤 | 仍维护，但增长停滞，新项目少用 |
| **SkyWalking** | Apache（2017） | SkyWalking / OTLP | ES / TiDB / BanyanDB | OAL（自有 DSL） | 中国主流，自带 APM/告警/拓扑图，有 BanyanDB 自研存储 |
| **Honeycomb** | 商业（2016） | OTLP | 列式专有 | 强大（BubbleUp、Heatmap） | High-cardinality 之王 |
| **Datadog APM** | 商业 | OTLP / DD agent | 专有 | 强大 | 老牌 SaaS，价格贵 |
| **Lightstep / ServiceNow Cloud Observability** | 商业 | OTLP | 专有 | 极强（meta-data driven） | OTel 项目主要发起方 |

### 7.2 Jaeger vs Tempo 怎么选

| 维度 | Jaeger 2.x | Tempo 2.x |
|---|---|---|
| 存储 | ES/Cassandra（贵） | 对象存储 S3（便宜 10-100 倍） |
| 查询 | TraceQL（v2 引入） | TraceQL（更成熟） |
| 索引 | 全字段索引（快但贵） | 仅按 trace-id 索引 + 流式扫描 |
| 适合场景 | 中小规模，查询模式多变 | 大规模，按 trace-id / service 查 |
| Grafana 集成 | 支持 | 原生最佳 |

**2026 推荐**：
- 新项目、PB 级链路、用 Grafana 栈 → **Tempo**
- 中小规模、需要丰富过滤查询 → **Jaeger 2**
- 自带 APM 需求、不想搭 Prom + Loki + Tempo → **SkyWalking**

### 7.3 TraceQL 示例

TraceQL 是 Tempo/Jaeger 2 的查询语言，类似 PromQL 但操作的是 Trace：

```traceql
# 找所有 order-svc 错误的 Trace
{ resource.service.name = "order-svc" && status = error }

# 找慢的（>1s）pricing 调用
{ resource.service.name = "pricing-svc" && duration > 1s }

# 找 VIP 用户的所有 Trace（用 attribute）
{ .user.tier = "vip" }

# 链路结构查询：order-svc -> pricing-svc 这一段慢
{ resource.service.name = "order-svc" } >> { resource.service.name = "pricing-svc" && duration > 500ms }

# 聚合：按 service 统计错误率
{ status = error } | rate() by (resource.service.name)
```

`>>` 是"后代"（含跨多层），`>` 是"直接子"。

## 第八章：Trace + Metric + Log 联动——Exemplars

### 8.1 三者关联的关键：trace_id

可观测三支柱（M18 详细讲）能"打通"靠两根线：
1. **trace_id** 在 Metric / Log / Trace 三者中作为关联键
2. **Exemplars**：Prometheus 直方图样本附带 trace_id

### 8.2 Log 注入 trace_id

让所有结构化日志都带上 `trace_id` + `span_id`：

```go
// 在 logger 里包一层
func logger(ctx context.Context) *slog.Logger {
    span := trace.SpanContextFromContext(ctx)
    return slog.With(
        "trace_id", span.TraceID().String(),
        "span_id", span.SpanID().String(),
    )
}

// 使用
logger(ctx).Error("payment failed", "user_id", userID, "amount", amount)
```

输出（JSON 格式）：

```json
{
  "ts": "2026-05-28T10:23:14Z",
  "level": "ERROR",
  "msg": "payment failed",
  "user_id": "u_4521",
  "amount": 99.99,
  "trace_id": "0af7651916cd43dd8448eb211c80319c",
  "span_id": "b7ad6b7169203331"
}
```

Grafana 仪表板中点这条日志 → 跳到 Tempo 的对应 Trace（**Loki / Datadog / Honeycomb 都支持这个跳转**）。

### 8.3 Exemplars：Prometheus 直方图链回 Trace

Prometheus 2.26+ 支持 **Exemplars**：直方图的某个样本可以附带一个 trace_id：

```go
// 在记录 metric 时附带 trace 信息
histogram, _ := meter.Float64Histogram("http_request_duration_seconds")
histogram.Record(ctx, 0.234,
    metric.WithAttributes(
        attribute.String("method", "POST"),
        attribute.Int("status", 200),
    ),
)
// OTel SDK 自动从 ctx 提取 trace_id 作为 Exemplar
```

Grafana 中看到 P99 直方图的高分位点 → 点击 → 直接跳到代表那个慢请求的 Trace。这是**从指标找根因**的最快路径。

### 8.4 端到端联动场景

**案例**：Prometheus 告警 P99 > 1s
1. **指标侧**：告警面板显示 P99=2.3s，按 service 切发现 `pricing-svc` 飙高
2. **Exemplar**：直方图 P99 桶里附带几个 trace_id，点开
3. **Trace 侧**：在 Tempo 中看 Trace 树，发现 `pricing-svc` 的 `pg.query` Span 占 95% 时间
4. **日志侧**：从 Span 点 trace_id 跳到 Loki，看到 `SELECT * FROM pricing WHERE ... ORDER BY created DESC LIMIT 10` 这条 SQL 出现 N 次
5. **Profile 侧**：从该服务的 Pyroscope flame graph 看到 CPU 大量花在 JSON 序列化
6. **定位**：业务代码每次查询返回 10MB 大字段，需要分页或字段裁剪

整条链路无需切换 5 个不同系统，**只在 Grafana 一个界面里完成**。

### 9.2 通用初始化代码

```go
package otelinit

import (
    "context"
    "os"
    "time"

    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc"
    "go.opentelemetry.io/otel/propagation"
    "go.opentelemetry.io/otel/sdk/resource"
    sdktrace "go.opentelemetry.io/otel/sdk/trace"
    semconv "go.opentelemetry.io/otel/semconv/v1.26.0"
)

func InitTracer(ctx context.Context, serviceName, version string) (func(context.Context) error, error) {
    // 1) Resource：进程标签
    res, err := resource.Merge(resource.Default(), resource.NewWithAttributes(
        semconv.SchemaURL,
        semconv.ServiceName(serviceName),
        semconv.ServiceVersion(version),
        semconv.DeploymentEnvironmentName(os.Getenv("ENV")),
        attribute.String("k8s.pod.name", os.Getenv("HOSTNAME")),
    ))
    if err != nil { return nil, err }

    // 2) Exporter：往 Collector 推 OTLP/gRPC
    exp, err := otlptracegrpc.New(ctx,
        otlptracegrpc.WithEndpoint(os.Getenv("OTEL_EXPORTER_OTLP_ENDPOINT")),
        otlptracegrpc.WithInsecure(),
    )
    if err != nil { return nil, err }

    // 3) Provider：BatchSpanProcessor + ParentBased sampler
    bsp := sdktrace.NewBatchSpanProcessor(exp,
        sdktrace.WithMaxQueueSize(10000),
        sdktrace.WithMaxExportBatchSize(1024),
        sdktrace.WithBatchTimeout(5*time.Second),
    )
    tp := sdktrace.NewTracerProvider(
        sdktrace.WithResource(res),
        sdktrace.WithSpanProcessor(bsp),
        // head 100%，让 collector tail sampling 决定
        sdktrace.WithSampler(sdktrace.ParentBased(sdktrace.AlwaysSample())),
    )
    otel.SetTracerProvider(tp)
    otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(
        propagation.TraceContext{}, propagation.Baggage{},
    ))

    return tp.Shutdown, nil
}
```

### 9.3 HTTP gateway

### 9.4 gRPC order-svc

```go
import (
    "go.opentelemetry.io/contrib/instrumentation/google.golang.org/grpc/otelgrpc"
)

func main() {
    ctx := context.Background()
    shutdown, _ := otelinit.InitTracer(ctx, "order-svc", "v3.2.1")
    defer shutdown(context.Background())

    s := grpc.NewServer(
        grpc.StatsHandler(otelgrpc.NewServerHandler()),
    )
    pb.RegisterOrderServiceServer(s, &OrderServer{})
    lis, _ := net.Listen("tcp", ":50051")
    s.Serve(lis)
}

type OrderServer struct {
    pb.UnimplementedOrderServiceServer
    kafka *kafka.Producer
    db    *sql.DB
}

func (s *OrderServer) CreateOrder(ctx context.Context, req *pb.CreateOrderReq) (*pb.CreateOrderResp, error) {
    tracer := otel.Tracer("order-svc")
    ctx, span := tracer.Start(ctx, "CreateOrder",
        trace.WithAttributes(attribute.String("user.id", req.UserId)))
    defer span.End()

    // 1) 写 DB
    if err := s.insertOrder(ctx, req); err != nil {
        span.RecordError(err)
        return nil, err
    }

    // 2) 发 Kafka
    if err := s.publishEvent(ctx, req); err != nil {
        span.RecordError(err)
        return nil, err
    }

    orderID := genID()
    span.SetAttributes(attribute.String("order.id", orderID))
    return &pb.CreateOrderResp{OrderId: orderID}, nil
}

func (s *OrderServer) insertOrder(ctx context.Context, req *pb.CreateOrderReq) error {
    tracer := otel.Tracer("order-svc")
    ctx, span := tracer.Start(ctx, "pg.insert.order",
        trace.WithSpanKind(trace.SpanKindClient),
        trace.WithAttributes(
            semconv.DBSystemNamePostgreSQL,
            attribute.String("db.query.text", "INSERT INTO order ..."),
        ))
    defer span.End()

    _, err := s.db.ExecContext(ctx, "INSERT INTO order(user_id) VALUES ($1)", req.UserId)
    if err != nil { span.RecordError(err) }
    return err
}

func (s *OrderServer) publishEvent(ctx context.Context, req *pb.CreateOrderReq) error {
    tracer := otel.Tracer("order-svc")
    ctx, span := tracer.Start(ctx, "kafka.publish.order-events",
        trace.WithSpanKind(trace.SpanKindProducer),
        trace.WithAttributes(
            semconv.MessagingSystemKafka,
            attribute.String("messaging.destination.name", "order-events"),
        ))
    defer span.End()

    headers := []kafka.Header{}
    otel.GetTextMapPropagator().Inject(ctx, &kafkaHeaderCarrier{&headers})

    return s.kafka.Produce(&kafka.Message{
        Topic:   "order-events",
        Value:   []byte(req.UserId),
        Headers: headers,
    }, nil)
}
```

### 9.5 Kafka consumer

```go
func main() {
    ctx := context.Background()
    shutdown, _ := otelinit.InitTracer(ctx, "order-consumer", "v1.0")
    defer shutdown(context.Background())

    consumer, _ := kafka.NewConsumer(&kafka.ConfigMap{
        "bootstrap.servers": "kafka:9092",
        "group.id":          "order-consumer-grp",
    })
    consumer.Subscribe("order-events", nil)

    for {
        msg, err := consumer.ReadMessage(-1)
        if err != nil { continue }
        handleMessage(msg)
    }
}

func handleMessage(msg *kafka.Message) {
    // 从 Kafka header 提取
    ctx := otel.GetTextMapPropagator().Extract(
        context.Background(),
        &kafkaHeaderCarrier{&msg.Headers},
    )

    tracer := otel.Tracer("order-consumer")
    ctx, span := tracer.Start(ctx, "kafka.consume.order-events",
        trace.WithSpanKind(trace.SpanKindConsumer),
        trace.WithAttributes(
            semconv.MessagingSystemKafka,
            attribute.String("messaging.destination.name", "order-events"),
        ))
    defer span.End()

    // 业务处理（继续被 Trace 串联）
    processOrder(ctx, msg.Value)
}
```

## 第十章：性能开销与采样率权衡

### 10.1 OTel SDK 性能开销

实测数据（Go 1.22，Linux，单核 c6i.large）：

| 操作 | 开销 |
|---|---|
| `tracer.Start()` + `span.End()`（不导出） | ~250 ns |
| 添加 5 个 attribute | ~600 ns |
| BatchSpanProcessor 后台导出（10000 span/批） | <1% CPU |
| 内存：每 Span ~ 800 字节（含属性） |

**结论**：100% 采样下，CPU 开销 < 3%，内存 < 200MB，是可以接受的。**头采样降低导出量，而 SDK 端创建 Span 的开销是省不掉的**。

### 10.2 网络与存储开销

| 项目 | 估算 |
|---|---|
| 单 Span 大小（含 5 个 attr） | 400-800 字节 |
| 50K Span/s 全采 | 25 MB/s ≈ 80 GB/小时 ≈ 2 TB/天 |
| 经 tail sampling 1% | 20 GB/天 |
| Tempo（S3）存储成本 | $0.023/GB·月 ≈ 每天 $0.50 |
| Jaeger（ES）存储成本 | 10-100 倍 Tempo |

### 10.3 采样率推荐

| 流量级别 | SDK head | Collector tail | 最终采样率 |
|---|---|---|---|
| < 100 QPS | 100% | 100% | 100%（全采） |
| 100-1K QPS | 100% | error+slow+10% | ~15% |
| 1K-10K QPS | 100% | error+slow+1% | ~5% |
| 10K-100K QPS | 10% head | error+slow+0.1%（在 10% 里） | ~0.5% |
| > 100K QPS | 1% head + dynamic | error+slow+0.01% | ~0.1% |

**永远全保 error 和 slow**——这两个绝对值小，不会撑爆存储。

## 生产实践

### 实践 1：从零起步的 instrumentation 顺序

不要一上来就 100% 改造所有服务，按价值排序：

1. **入口层先 Auto**：所有 HTTP/gRPC server 自动起 SERVER Span（用 Java agent / `otelhttp` / `otelgrpc`）
2. **下游调用 Auto**：HTTP client / gRPC client / DB client 自动起 CLIENT Span
3. **消息中间件 Auto + Manual**：Kafka header 注入（要自己写 Carrier）
4. **关键业务 Manual**：风控、定价、库存等业务节点
5. **业务属性 Manual**：user_id / tenant_id / order_id 等

### 实践 2：service.name 命名规范

所有 service.name 写死在配置中心，不允许代码硬编码。规范：

```text
{org}.{domain}.{service-name}
```

例：
- `acme.shop.order-svc`
- `acme.shop.payment-svc`
- `acme.platform.auth-svc`

避免重名（Tempo 按 service.name 索引，重名会让两个无关服务的 Trace 混在一起）。

### 实践 3：错误必须 RecordError + SetStatus

OTel 规定**两个动作必须都做**才算"标记错误"：

```go
if err != nil {
    span.RecordError(err)                           // 把异常作为 Event 记录
    span.SetStatus(codes.Error, err.Error())        // 把 Span 状态设为 Error
    return err
}
```

只调 `RecordError` 而不设 status，**后端不会认为这个 Span 是错的**，告警会漏。

### 实践 4：高 cardinality 属性的"暴力陷阱"

不要把以下东西作为 attribute 直接打到 Span：

| 不要做 | 原因 |
|---|---|
| `http.url` 含 query string 全打 | URL 数量爆炸（每个用户参数不同），Tempo 索引爆 |
| 把整个 JSON request 当作 attribute | 单个 Span 几 MB，Collector 内存爆 |
| 把 stack trace 当 attribute | 该用 `RecordError`（作为 Event） |
| 把 user.id 作为 metric label | 应作为 Span attribute（trace 不索引则 OK，metric 维度爆炸） |

**记住**：Span 的 attribute 容量约束远比 Metric label 宽松（OTel 默认每 Span 128 attr，每 attr 长度 256），但**也别滥用**——单个 Trace 太大也会拖慢传输和查询。

### 实践 5：Collector 部署 SOP

```yaml
# Agent (DaemonSet)
resources:
  requests: { cpu: 100m, memory: 256Mi }
  limits:   { cpu: 500m, memory: 512Mi }
config:
  receivers: { otlp: { protocols: { grpc: {}, http: {} } } }
  processors:
    memory_limiter: { limit_mib: 400, check_interval: 1s }
    batch: { send_batch_size: 1024, timeout: 5s }
  exporters:
    loadbalancing:
      resolver: { dns: { hostname: otel-gateway.observability } }

# Gateway (Deployment, N>=3)
resources:
  requests: { cpu: 1, memory: 2Gi }
  limits:   { cpu: 4, memory: 8Gi }
config:
  processors:
    tail_sampling: { ... }
  exporters:
    otlp/tempo: { ... }
```

关键点：**memory_limiter 必须配**（Collector OOM 会丢全集群信号），**Gateway 至少 3 副本**做高可用。

### 实践 6：本地降级与丢失保护

Collector / 后端不可用时，SDK 默认会丢弃 Span（避免 OOM）。需要"丢但要告警"：

```go
// 自定义错误处理器
otel.SetErrorHandler(otel.ErrorHandlerFunc(func(err error) {
    // 上报到 metric（不要直接打日志，量太大会刷屏）
    droppedSpanCounter.Add(1)
}))
```

或者用 Collector 端的 `persistent queue`（OTel Collector contrib 提供）做本地落盘缓冲，后端恢复后回放。

### 实践 7：用 Resource Attribute 而非 Span Attribute 表达"静态信息"

```go
// 不要这样：每个 Span 都打
span.SetAttributes(attribute.String("k8s.pod.name", podName))

// 应该这样：在 Resource 里声明一次
resource.NewWithAttributes(semconv.SchemaURL,
    attribute.String("k8s.pod.name", podName),
)
```

Resource attribute 只在导出时附加一次，节省 90% 网络/存储开销。

## 陷阱清单

1. **忘记关闭 SDK**：`tp.Shutdown(ctx)` 不调用 → BatchSpanProcessor 队列里的 Span 全丢。任何 main 函数末尾必须 `defer tp.Shutdown(ctx)`
2. **同步 Exporter**：用 `SimpleSpanProcessor` 上生产 → 每条 Span 同步推送，阻塞业务请求。生产必须 `BatchSpanProcessor`
3. **采样不一致**：服务 A 用 head 1%、服务 B 用 100% → 跨服务的 Trace 会有"洞"。应在 source 决定，下游 `ParentBased`
4. **trace_flags 没传**：手写 carrier 时漏传 `01` → 下游以为是 unsampled，整条链路丢
5. **HTTP header 大小写敏感**：自研 RPC 框架按大小写匹配 `Traceparent` → 失败。要 case-insensitive 处理
6. **nginx 默认拒下划线 header**：W3C 没下划线问题，但老 B3 的 `X_B3_*` 会被 nginx 过滤。换 dash 或 `underscores_in_headers on;`
7. **goroutine 不传 ctx**：`go func() { ... }()` 不传 ctx → 异步任务和上层 Trace 断开。要么传 ctx，要么显式 Link
8. **defer span.End() 在 return err 之前**：在 helper 函数里 span 已 end 又被使用 → panic
9. **大 Span**：把整个 request body / response body 当 attribute → Collector OOM、查询慢
10. **PII 泄漏到 Trace**：用户密码、token、身份证号当 attribute 进了 Tempo → 合规事故。Collector 加 `attributes` processor 脱敏
11. **service.name 重名**：两个独立部门的 `gateway` 服务同名 → Trace 混淆。强制 `{org}.{domain}.{service}` 命名
12. **采样后看不到 Trace**：Tail sampling decision_wait=30s，刚发的请求 30 秒后才出现在 Tempo → 别急着 F5
13. **Collector 没 memory_limiter**：突发流量 OOM → 信号全丢。**必配 memory_limiter processor**
14. **Tail sampling 跨节点路由错**：Collector 多副本部署但没用 loadbalancing exporter → 同一 Trace 的 Span 分散到多个 Collector，tail 决策只能看到部分 Span。**必须用 trace-id 做一致性路由**
15. **Baggage 塞 PII**：把用户 token 塞 baggage → 全部下游都能拿到 → 安全事故。Baggage 只放业务标识
16. **traceparent 被 CDN/WAF 剥离**：Cloudflare / Akamai 某些规则会去掉未知 header → 用 W3C 标准 + 显式 allowlist
17. **Span 数量爆炸**：循环里每次迭代 start 一个 Span（如 10000 行 DB 行迭代）→ Trace 几 MB。批量操作只起一个 Span，用 events 标记进度
18. **没设 sampler 默认 100%**：本地 dev 设 100%，忘记改 prod → 流量大时全采撑爆
19. **多版本 OTel 库混用**：Java agent v1.32 + 业务依赖 SDK v1.20 → instrumentation 不兼容、属性命名不一致

## 2026 现状

### CNCF Graduated 与生态格局

OpenTelemetry 在 2023 年从 Incubating 升级为 **Graduated**，是继 K8s / Prometheus / Envoy 之后的"重量级毕业生"。2026 年的事实状态：

| 信号类型 | OTel 状态 |
|---|---|
| Traces | **Stable**（所有 11 种主流语言 SDK Stable） |
| Metrics | Stable（Prometheus 端原生支持 OTLP）  |
| Logs | Stable（2024 年 GA） |
| Profiling | **GA**（2025 年 GA，新加入第四支柱）|

### 重要里程碑

| 年份 | 事件 |
|---|---|
| 2019 | OpenTracing + OpenCensus 合并为 OpenTelemetry |
| 2021 | Trace API/SDK GA |
| 2023 | CNCF Graduated；Metrics GA |
| 2024 | Logs GA；Jaeger 2 重构基于 OTel Collector |
| 2025 | Profiling GA（OTel pprofiles）；OTLP/Arrow 协议高效编码上线 |
| 2026 | eBPF auto-instrumentation 进入 Beta（Beyla / Coroot / Pixie 推动） |

### 主流栈与商业 APM

2026 年的世界两条主线：

**开源 Grafana 栈**：
- Mimir（Metrics）+ Loki（Logs）+ Tempo（Traces）+ Pyroscope（Profiling），统一在 Grafana UI 里
- 数据接入全部 OTLP
- 适合自建、对成本敏感的场景

**商业 APM**：
- Datadog / New Relic / Dynatrace / AppDynamics 已全部支持 OTLP 接入
- 优势：开箱即用、UI 强、AI 异常检测
- 价格：每月 $15-30/Host，规模大成本爆炸

**OTel 让两条路融合**：业务代码用 OTel SDK，可以**先发 Datadog，明年换 Grafana**，零代码改动。这是 OTel 最大价值。

### eBPF auto-trace 兴起

2024-2026 年，eBPF 让"零侵入 + 无 SDK"的链路追踪成为可能：

| 工具 | 厂商 | 机制 |
|---|---|---|
| **Pixie** | New Relic | eBPF 内核 hook + HTTP/gRPC/MySQL 协议解码 |
| **Beyla** | Grafana | eBPF + 自动生成 OTel Span |
| **Coroot** | 独立 | eBPF + 服务拓扑自动发现 |
| **Hubble** | Cilium | eBPF + L3/L4/L7 流量 |
| **Inspektor Gadget** | Inspektor Gadget | 通用 eBPF 工具集 |

**优点**：完全零代码改动、跨语言、跨容器
**缺点**：信号粒度粗（只能看到协议层调用，看不到业务级语义；如 "/api/order/{id}" 在 eBPF 看是 "/api/order/123"，cardinality 高）

**2026 推荐**：业务关键服务仍用 OTel SDK（细粒度 + 业务属性），外围服务用 eBPF 兜底（零侵入获取拓扑）。

### OTLP/Arrow 与压缩

OTLP 默认 gRPC + protobuf。2024 年推出 OTLP/Arrow（基于 Apache Arrow 列式编码），压缩率提升 5-10 倍，CPU 开销下降 50%。Collector 之间用 Arrow 传输已是大规模部署标准。

### Trace 与 AI 异常检测

商业 APM 利用 LLM 做"Trace 自动诊断"——给定一条慢 Trace，AI 直接说"瓶颈在 pricing-svc 的 pg.query 上，看起来是表锁等待"。这是 2025-2026 年的新热点。开源侧 Grafana Sift 和 Tempo metrics-generator 也在做类似事。
