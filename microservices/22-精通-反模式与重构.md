> 关联章节：[精通微服务架构总览](./01-精通-微服务架构总览.md)、[精通服务拆分与 DDD](./02-精通-服务拆分与-DDD.md)、[精通单体到微服务演进](./03-精通-单体到微服务演进.md)

## 引言：为什么要专门讲"反模式"？

让我们先抛几个让架构师"心头一紧"的问题：

1. 你的 30 个微服务，每次发布都必须**同步上线**才能用，否则会出 Bug —— 这是微服务，还是把单体拆碎了又粘回去？
2. 上线一个新功能，需要改 8 个服务、协调 6 个团队、开 3 次跨团队会议、等 2 周窗口 —— 这是微服务的"独立部署"承诺吗？
3. 你有 200 个服务，但工程师只有 50 个 —— 平均每个工程师维护 4 个服务，还要轮岗、还要写需求、还要 oncall —— 你确定不是过度拆分？
4. 一个业务请求从入口到完成要经过 12 跳 RPC，p99 时延 3 秒，每天 10 几个偶发超时 —— 服务边界是不是切错了？
5. 两个服务共享同一个数据库表，A 写、B 读，A 改字段必须通知 B，否则 B 解析失败 —— 这还能叫"服务"吗？

如果上面任何一条让你点头，那你大概率已经身陷一种或多种**微服务反模式**。微服务不是"拆得越多越好"，更不是"用了 K8s 就是微服务"。本章我们就把工业界过去十年踩过的所有大坑，按"识别 → 危害 → 改造 → 反向演进"四步系统讲清楚，让你既能避坑，又能在已经掉进坑的项目里**爬出来**。

## 第 2 章：分布式单体 —— 一切反模式的"集大成者"

### 2.1 什么叫"分布式单体"

**Distributed Monolith**：表面上是微服务（多服务、多仓库、多容器），实际上耦合度堪比单体。是工业界**最常见**的微服务反模式，相当大比例的"微服务转型"最终都走到了这里（业界普遍观察，缺乏权威统计口径，不宜引用精确数字）。

它有一个核心特征：**失去了微服务的好处，却继承了微服务的所有缺点**。

### 2.2 识别：5 大症状

| 症状 | 描述 | 严重度 |
| --- | --- | --- |
| **1. 必须同步部署** | 服务 A 和 B 必须一起发布，否则报错 | ⭐⭐⭐⭐⭐ |
| **2. 链式同步调用** | A → B → C → D → E 一条直链 | ⭐⭐⭐⭐ |
| **3. 共享数据库** | 多服务直接读写同一张表 | ⭐⭐⭐⭐⭐ |
| **4. 共享代码强耦合** | 共享 model / DTO 库，改一行所有服务重发布 | ⭐⭐⭐⭐ |
| **5. 统一发布窗口** | 全公司每周三晚上集体发布 | ⭐⭐⭐⭐⭐ |

任意命中 2 条以上，恭喜，你已经在分布式单体里了。我们来逐项详细看。

#### 症状 1：必须同步部署

```
错误版本组合矩阵：

           Order-v1    Order-v2
Pay-v1       ✓          ✗  ← 报错
Pay-v2       ✗          ✓
```

含义：Order 服务和 Pay 服务必须版本**一一对应**，任何错配都会出错。这等于说"它们其实是一个东西"。

#### 症状 2：链式同步调用

```
Gateway ─► Order ─► Payment ─► Risk ─► Account ─► Notify
                                                      │
                                                      └─► User
                                                      
任何一跳超时，全链路超时。
p99 = max(各跳 p99) 而不是平均。
任何一跳挂了，全链路挂。
```

链越长越脆弱，详细分析见 [精通容错与混沌工程](./12-精通-容错与混沌工程.md)。

#### 症状 3：共享数据库

```
   ┌──────────┐         ┌──────────┐         ┌──────────┐
   │ Order    │         │ Payment  │         │ Refund   │
   │ Service  │         │ Service  │         │ Service  │
   └────┬─────┘         └────┬─────┘         └────┬─────┘
        │                    │                    │
        └─────────────┬──────┴──────┬─────────────┘
                      ▼             ▼
              ┌───────────────────────────┐
              │   shared_database         │
              │     orders 表             │  ← 三个服务直接读写
              │     payments 表           │
              │     refunds 表            │
              └───────────────────────────┘
```

危害：

- DDL 变更牵一发动全身，任何字段改动都要协调所有服务；
- 一个慢查询能拖垮所有服务；
- 无法独立横向扩展；
- 数据所有权不清（谁说了算？）；
- 测试时无法独立 mock 数据。

#### 症状 4：共享代码强耦合

```java
// shared-models.jar (大家都依赖)
public class Order {
    private String id;
    private BigDecimal amount;
    // ... 30 个字段
}
```

某天财务团队往 Order 加一个 `taxRate` 字段，发版 shared-models v2.0。问题来了：

- 谁先升级？
- 不升级的会不会反序列化失败？
- v1.0 还在 prod 跑，v2.0 客户端能不能解析？

**实际结果**：所有团队被迫同步升级，每次都开"shared-models 升级协调会"，沦为新的"瓶颈"。

#### 症状 5：统一发布窗口

"周三晚上发版日"听起来很正规，但本质是：

- 我们不敢小步迭代；
- 我们没信心独立发布；
- 我们必须看着彼此发布。

这等于退回到了瀑布开发，微服务的"持续交付"承诺彻底破产。

### 2.3 危害量化

我们看过一个真实案例（电商客户，2023）：

| 指标 | 名义微服务（实为分布式单体） | 真正解耦后 |
| --- | --- | --- |
| 平均发布周期 | 2 周 | 2 小时 |
| 平均发布参与人数 | 8 人 | 1 人 |
| 一次发布回滚率 | 18% | 2% |
| MTTR（平均故障恢复） | 90 min | 15 min |
| 新功能上线周期 | 4-6 周 | 3-7 天 |

简单结论：**分布式单体既慢又脆**。

### 2.4 改造路线：4 步走

```
Step 1: 识别 → 量化
  - 服务依赖图 (谁调谁，是否同步)
  - 数据库表的所有权矩阵
  - 共享代码库的使用方
  - 发版协调成本

Step 2: 解耦数据
  - 共享表 → 各服务专属表 + 通过事件/API 同步
  - 物理隔离（一库一服务）

Step 3: 解耦发布
  - 引入契约测试（Pact）
  - 引入 API 版本（v1 / v2 并存）
  - 引入 Feature Flag（先功能再发版）

Step 4: 解耦组织
  - 按 BC 重新划分团队
  - 每个服务必须有明确 owner
  - 取消统一发版日
```

我们在第 13 章用一个完整案例展开。

## 第 3 章：共享数据库 —— 分布式单体的"母体"

为什么单独把"共享数据库"拎出来？因为它是 90% 分布式单体的**根本原因**。

### 3.1 为什么会发生

历史上从单体拆出来的项目几乎都经历过这个阶段：

```
   阶段 0：单体
   ┌─────────────────┐
   │     monolith    │ ──► one_database
   └─────────────────┘

   阶段 1：拆分代码（共享 DB 阶段，最危险）
   ┌──────┐  ┌──────┐  ┌──────┐
   │ Svc A│  │ Svc B│  │ Svc C│ ──► one_database  ← 数据库还没拆！
   └──────┘  └──────┘  └──────┘

   阶段 2：才是真正的微服务
   ┌──────┐  ┌──────┐  ┌──────┐
   │ Svc A│  │ Svc B│  │ Svc C│
   └──┬───┘  └──┬───┘  └──┬───┘
      │         │         │
     db_A     db_B      db_C
```

很多团队**停在阶段 1 三五年**。表面上服务多了，实际上"分布式单体"成形。

### 3.2 三种共享 DB 的形态

| 形态 | 描述 | 危害 |
| --- | --- | --- |
| **直接共享表** | 多服务 INSERT/UPDATE 同一张表 | ⭐⭐⭐⭐⭐ 最严重 |
| **读写分离** | A 写，B、C 直接 SELECT | ⭐⭐⭐⭐ |
| **共享视图/存储过程** | 通过视图或 SP "封装" | ⭐⭐⭐ 仍然耦合 schema |

### 3.3 拆分方案

**关键原则**：每个表只能有**一个**服务作为 owner，其他服务必须通过 API 或事件访问。

```
                 改造路线图
   
   Phase 1: 数据所有权清算
     用 Excel 列出所有表，每张表标注 owner
   
   Phase 2: 物理隔离前的逻辑隔离
     - 加 db_user_per_service，权限只到自己的表
     - 别人访问必须走 API
   
   Phase 3: 物理拆库
     - 各服务建独立 schema → 独立实例
   
   Phase 4: 数据同步
     - 需要读他人数据时：CDC（Debezium）+ 本地读模型
     - 需要写他人数据时：通过 API 或异步事件
```

详细方案见 [精通分布式数据管理](./04-精通-分布式数据管理.md)。

## 第 4 章：过细拆分 —— 服务数量大于工程师

### 4.1 识别症状

| 症状 | 阈值 |
| --- | --- |
| 服务数 / 工程师数 | > 1.5 危险，> 3 灾难 |
| 服务平均代码量 | < 500 行（大概率是 CRUD 包装） |
| 一个业务流程经过的服务数 | > 7 |
| 团队拥有的服务数 | 一个团队负责 > 10 个 |
| 服务变更频率 | 6 个月没动 → 大概率不该独立存在 |

### 4.2 典型坏味道

**坏味道 1：CRUD 包装服务**

```java
// User Service 的全部代码
@RestController
public class UserController {
    @Autowired UserRepository repo;
    
    @GetMapping("/users/{id}")
    public User get(@PathVariable Long id) { return repo.findById(id).get(); }
    
    @PostMapping("/users")
    public User create(@RequestBody User u) { return repo.save(u); }
    
    @PutMapping("/users/{id}")
    public User update(...) { ... }
    
    @DeleteMapping("/users/{id}")
    public void delete(@PathVariable Long id) { repo.deleteById(id); }
}
```

如果这就是 User Service 的全部，**它就是个数据库 + HTTP 接口**。没有业务逻辑，没有不变式（invariant）守护，没有领域意义。它应该是某个聚合的一部分，不是独立服务。

**坏味道 2：一个业务流程 10+ 跳**

```
Gateway → Order → Inventory → Pricing → Discount → Tax → 
Payment → Risk → Notification → Account → Audit  

11 跳，每跳 30ms，光网络就 330ms。
```

**坏味道 3：服务之间互相 RPC**

A 调 B，B 同时调 A 拿数据，A 又调 C，C 再回头查 A …… 这种"互相调用"几乎 100% 是切错了边界。

### 4.3 改造：合并

合并服务的指导原则：

| 信号 | 含义 |
| --- | --- |
| 两服务总是一起改 | 它们是一个业务 → 合并 |
| 两服务共享 90% 数据 | 数据所有权应该统一 → 合并 |
| 调用频率极高且同步 | 拆开成本远高于收益 → 合并 |
| 两服务都没业务逻辑 | 都是 CRUD → 合并到所属聚合 |

详见第 13 章案例 2。

## 第 5 章：Chatty Services —— RPC 风暴

### 5.1 什么是 Chatty Services

服务间互相**频繁、细粒度**地 RPC 调用，造成网络风暴。常见形态：

#### N+1 RPC 问题

```python
# Order Service
orders = order_repo.list(user_id=user_id)  # 拿 100 个订单
for order in orders:
    item = item_service.get(order.item_id)  # 调 100 次 RPC！
    order.item_name = item.name
```

p99 时延 = 1 次主查询 + 100 次 RPC（每次 50ms）= 5050ms ≈ 5 秒。

#### 大对象序列化

每次 RPC 都把整个 1MB 的 User 对象 JSON 传过去，光序列化反序列化就 30ms。

#### 同步链过长

业务上一个 click 触发 12 跳同步调用，任意一跳挂掉整条链路完蛋。

### 5.2 解决方案

| 问题 | 解决方案 | 代价 |
| --- | --- | --- |
| N+1 RPC | 批量接口 `getByIds([1,2,3...])` | 改 API |
| N+1 RPC | 在 caller 侧做本地缓存 / 物化视图 | 一致性 |
| 大对象 | 只传 id + 字段筛选（GraphQL / 自定义 fields） | API 重设计 |
| 同步链过长 | 改异步事件 / 编排 | 一致性变弱 |
| 通用减负 | 边缘缓存（Gateway 层） | 失效策略复杂 |

**批量化 + 异步化** 是最常用的两大武器。

### 5.3 案例

某社交客户的 feed 接口：

```
原版：
  Feed 服务 ─► User 服务 (N 次：拿每个 author)
            ─► Like 服务 (N 次：拿点赞数)
            ─► Comment 服务 (N 次：拿评论数)
            ─► Image 服务 (N 次：拿图片 url)
  
  100 条 feed × 4 个服务 = 400 次 RPC，p99 = 4 秒。

改造后：
  Feed 服务 ─► User 服务 batchGet([id1...idN])
            ─► Like 服务 batchGet
            ─► Comment 服务 batchGet  
            ─► Image 服务 batchGet
  
  4 次 RPC，p99 = 200ms。

进一步改造：
  把 user/like/count/image 等冷热数据，
  按 fanout-on-write 预写到 feed 物化视图，
  Feed 服务一次本地查询搞定，p99 = 50ms。
```

## 第 6 章：Dual Write —— 双写不一致

### 6.1 反模式描述

业务代码同时写两个独立的"系统"（DB + Cache、DB + MQ、DB + ES），任意一边失败就不一致。

```java
// ❌ 反模式
@Transactional
public void createOrder(Order o) {
    orderRepo.save(o);           // 写 DB
    redis.set(o.id, o);          // 写 Cache  ← 一致性炸弹
    kafka.send("order", o);      // 发消息    ← 一致性炸弹
}
```

故障点：

- DB 成功 + Cache 失败 → Cache 永远是旧数据；
- DB 成功 + MQ 失败 → 下游永远收不到事件；
- DB 失败 + MQ 成功 → 下游收到了一个根本不存在的订单；
- 应用 Crash 在 DB 和 MQ 之间 → 永远不一致。

### 6.2 解决方案：Outbox / CDC

**Transactional Outbox 模式**：

```sql
-- 在同一个 DB 事务里同时写业务表和 outbox 表
BEGIN;
INSERT INTO orders (...) VALUES (...);
INSERT INTO outbox (event_type, payload, status) 
       VALUES ('OrderCreated', '{...}', 'PENDING');
COMMIT;
```

然后用一个独立的 publisher 进程（或 Debezium CDC）扫 outbox 表，把事件发到 MQ：

```
┌──────────┐  事务 │ ┌──────────┐
│   App    │ ────► │ │ orders   │
└──────────┘       │ │ outbox   │
                   │ └────┬─────┘
                           │ CDC / 轮询
                           ▼
                     ┌──────────┐
                     │  Kafka   │ ──► 下游
                     └──────────┘
```

详细见 [精通分布式数据管理](./04-精通-分布式数据管理.md) 的 Outbox 章节。

### 6.3 Cache 的 Dual Write 怎么解？

| 方案 | 一致性 | 复杂度 |
| --- | --- | --- |
| Cache-Aside（懒失效） | 弱一致 | 低 |
| Write-Through（同步双写） | 强但有 Dual Write 问题 | 中 |
| Write-Behind（异步） | 弱 | 高 |
| **CDC 驱动 Cache 刷新** | 最终一致 | 中（推荐） |

## 第 7 章：Big Ball of Mud 微服务版

### 7.1 形态

经典"泥球"在单体里指代码混乱无章。**微服务版的泥球**则是：

- 100 个服务，每个都自己一套技术栈（Spring/Express/FastAPI/Go），无统一规范；
- 服务间随意互相调用，没有任何分层；
- 服务命名混乱（`user-service-v2-final-prod-2024`）；
- 一个功能不知道该归哪个服务；
- 共享代码库散落在 N 个仓库；
- CI/CD 各自为政；
- 监控、日志、链路追踪缺失或混乱；
- 没人能说清"系统全貌"。

### 7.2 识别

"画不出系统架构图" 就是 Big Ball of Mud 微服务版。任何一个工程师只能讲清自己负责的 2-3 个服务，组合到一起就 happy hour。

### 7.3 改造

无法一蹴而就，路线图：

1. **梳理服务清单**（人工 + 服务注册中心 + API 文档）；
2. **绘制依赖图**（自动化工具：Linkerd / Istio Topology / SkyWalking Topology）；
3. **识别核心域 vs 支撑域**（详见 [服务拆分与 DDD](./02-精通-服务拆分与-DDD.md)）；
4. **建立技术栈准入清单**（最多 3 种语言 + 5 种存储）；
5. **强制服务必须有 owner**（孤儿服务下线或归并）；
6. **逐步合并/重构**（每季度一个里程碑）。

## 第 8 章：错误的服务边界

### 8.1 三种典型错误切分

| 切分依据 | 例子 | 问题 |
| --- | --- | --- |
| **按 CRUD** | UserCreateService / UserUpdateService / UserDeleteService | 同一聚合被打散，事务难做 |
| **按技术层** | ControllerService / ServiceLayer / DAOService | 退化为分布式 N 层架构 |
| **按表** | OrderTableService / OrderItemTableService | 数据库 schema 主导业务 |

### 8.2 正确切分的标准

**Bounded Context（限界上下文）**是唯一靠谱标准：

- 一个 BC = 一组语义一致的业务概念；
- 不同 BC 中的同名概念可以有完全不同的含义（如"用户"在销售 BC 和客服 BC 不一样）；
- BC 与 BC 之间通过 **明确契约**（API / Event）通信；
- BC 内部数据封装、不允许外部直接访问。

参考 [精通服务拆分与 DDD](./02-精通-服务拆分与-DDD.md)。

### 8.3 切错了怎么办

**反向演进**（第 12 章详述）。先承认错误，再重构。

## 第 9 章：缺乏治理 —— 没有契约、没有版本、没有观测

### 9.1 没有契约测试

接口随便改，下游一发版就挂。

正解：**Consumer-Driven Contract Tests**，工具 **Pact** / **Spring Cloud Contract**。

```
   Consumer 写期望         Provider CI 跑契约
   ───────────────         ──────────────────
   Pact 文件 ────► Broker ─────► Provider 拉取 ─► 验证
                                       │
                                       ▼
                                  通过/失败
```

详见 [精通契约测试](./16-精通-契约测试.md)（若已有）。

### 9.2 没有 API 版本策略

接口断流升级，下游集体崩溃。

正解：

- URL 版本：`/v1/orders`、`/v2/orders`；
- 灰度并存窗口 ≥ 90 天；
- Deprecation 标记 + 日志告警；
- gRPC 用 reserved 字段保留兼容性。

### 9.3 没有可观测性

线上出问题，三个团队互相 ping：

> "你们服务是不是挂了？" "没挂，可能是网络。" "网络好好的。" "再看看你们 DB？"

正解：日志 + Metrics + Trace + Alert 全栈接入，详见 [精通可观测性](./08-精通-可观测性-metrics-tracing-logging.md)。

### 9.4 没有 SLA / SLO / Error Budget

服务承诺什么没人知道，挂了多久也没人定义。

正解：每个服务必须有 SLI/SLO 文档（如 "p99 < 200ms，可用性 99.9%"）。

## 第 10 章：跨服务事务滥用

### 10.1 反模式：本来一个服务的事务被拆成 Saga

某客户案例：

```
"订单 + 订单明细" 被拆成两个服务：
  - Order Service (orders 表)
  - OrderItem Service (order_items 表)

下单流程被迫做成 Saga：
  1. Order Service 创建 order，状态 = PENDING
  2. 调 OrderItem Service 创建 items
  3. 如果 items 创建失败 → 回滚 order

问题：
  - 本来一个 DB 事务的事，搞成 2 跳 RPC + 补偿；
  - p99 时延 3 倍；
  - 失败概率 5 倍；
  - 异常处理代码爆炸。
```

**根因**：错把"同一聚合的两张表"当成"两个 BC"拆了。

### 10.2 判定原则

| 场景 | 该用什么 |
| --- | --- |
| 同一聚合（强一致不变式） | **本地事务**（不要拆服务） |
| 不同聚合，同一 BC | 本地事务 / Domain Event |
| 不同 BC，业务流程 | Saga / Outbox |
| 不同 BC，最终一致即可 | 异步事件 |

如果你发现 90% 的"跨服务事务"用 Saga，说明大概率是拆错了，不是 Saga 用得不熟。

详见 [精通分布式事务](./05-精通-分布式事务-saga-tcc-outbox.md)。

## 第 11 章：康威定律错位

### 11.1 康威定律

> 任何组织设计的系统都会复制该组织的沟通结构。
> —— Melvin Conway, 1968

简单说：**组织结构会决定系统架构**。

### 11.2 错位形态

| 形态 | 描述 | 后果 |
| --- | --- | --- |
| **一个团队管 30 个服务** | 团队太大，服务粒度太碎 | 没人专精，bug 多 |
| **一个服务跨多个团队** | 谁都不是 owner | 推卸责任 |
| **核心域被边缘团队负责** | 业务优先级与人力错配 | 关键服务质量低 |
| **服务边界跨团队** | 一个 RFC 要 5 个团队签字 | 决策极慢 |

### 11.3 正解：逆康威定律

**主动调整组织结构来匹配理想架构**，详见 [团队拓扑](./19-精通-服务所有权与团队拓扑.md)（若已有）。

Team Topologies 的 4 种基础团队类型：

- **Stream-Aligned Team**（业务流团队）：1 个团队 1-3 个紧密相关服务；
- **Platform Team**（平台团队）：基础设施、中间件；
- **Enabling Team**（赋能团队）：帮其他团队落地新实践；
- **Complicated Subsystem Team**（专家团队）：处理复杂子系统（推荐算法、风控）。

## 第 12 章：反向演进 —— 何时合并服务

微服务社区谈"拆"很多，谈"合"很少。但合并服务往往**是更难也更勇敢**的决策。

### 12.1 合并的信号

| 信号 | 阈值 |
| --- | --- |
| 两服务总是一起改 | 一年 > 20 次共改 |
| 两服务共享同一聚合 | 强一致需求多 |
| 两服务都是 CRUD | 业务逻辑 < 20% |
| 两服务之间同步 RPC > 90% 流量 | 几乎没异步通信 |
| 两服务都由一个团队维护 | 拆分没带来组织收益 |

### 12.2 合并步骤

```
Phase 1: 暂停拆分动力，达成合并共识
  - 写 RFC 列出问题
  - 量化数据（RPC 频率、共改次数、bug 数）
  - 与团队/owner/管理层对齐

Phase 2: 接口层合并
  - 新服务暴露并集 API
  - 老服务通过 facade 转发到新服务（兼容老调用方）

Phase 3: 代码与数据合并
  - 把两个仓库代码合到一个
  - 数据库表迁移到统一 schema
  - 旧服务保留只读模式过渡

Phase 4: 切流量
  - 灰度切到新服务
  - 老服务下线

Phase 5: 清理
  - 删除老仓库
  - 删除旧 API 路由
  - 更新文档
```

### 12.3 工具

- **代码合并**：`git subtree merge`、自动化迁移脚本；
- **数据库合并**：Flyway / Liquibase 多 schema 合并；
- **API 兼容**：API Gateway 路由重写（老路径 → 新服务）；
- **流量切换**：Service Mesh VirtualService 按比例路由。

## 第 13 章：完整案例 1 —— 30 服务分布式单体的 6 个月重构

### 背景

某 B2B SaaS 公司，2019 年从单体拆出 30 个服务，2023 年我们介入时：

- 服务数：30
- 工程师：35
- 共享数据库：1 个（所有服务都接）
- 平均发布时间：每周三晚上，全员 oncall
- 平均上线一个新功能：4 周
- 客户反馈最大痛点："你们怎么连个按钮都改这么慢"

### 第 1 个月：诊断与共识

- 跑工具梳理依赖图（Istio + 静态扫描）；
- 输出现状报告："你们是分布式单体"；
- 拉管理层和 Tech Lead 开 3 次会，达成共识；
- 制定 6 个月路线图。

### 第 2 个月：数据所有权清算

- 整理共享 DB 的 80 张表，每张表标注 owner；
- 28 张表无明确 owner → 业务专家研讨会确定；
- 给每个服务建 DB User，权限仅限自己的表；
- 跑业务回归，发现 12 处偷偷跨表的 SQL → 改成 API 调用。

### 第 3 个月：物理拆库

- 每个服务建独立 schema（仍同一个 MySQL 实例，先逻辑拆）；
- 一些高频跨服务 JOIN → 在调用方建本地物化视图，CDC 同步；
- 引入 Debezium，搭事件总线。

### 第 4 个月：解耦发布

- 引入 Pact，每个服务消费方写期望、提供方 CI 验证；
- 引入 API 版本策略：`/v1`、`/v2` 灰度并存 90 天；
- 引入 Feature Flag（LaunchDarkly），把"发版"和"功能上线"解耦。

### 第 5 个月：拆库 + 解耦组织

- 高负载服务先迁到独立 MySQL 实例；
- 取消周三发版日，鼓励"今天写完今天上"；
- 重新划分团队，每个服务有明确 owner。

### 第 6 个月：观测 + 治理收尾

- OTel 全栈接入；
- 每个服务建 SLO 看板；
- 跑混沌实验验证解耦效果；
- 复盘、文档化、培训。

### 成果对比

| 指标 | 改造前 | 改造后 |
| --- | --- | --- |
| 平均发布周期 | 1 周 | 1 天 |
| 一次发布参与人 | 8 人 | 1-2 人 |
| 上线一个新功能 | 4 周 | 5 天 |
| 服务间共改频率 | 平均 12 次/月 | 1.5 次/月 |
| 故障 MTTR | 90 min | 25 min |
| 团队 NPS | -10 | +35 |

## 第 14 章：完整案例 2 —— 10 个 CRUD 合并为 3 个有业务意义的服务

### 背景

某中型电商，2022 年"激进拆分"，把订单域拆成：

```
- order-create-service
- order-update-service  
- order-query-service
- order-cancel-service
- order-refund-service
- order-item-service
- order-coupon-service
- order-tax-service
- order-history-service
- order-notification-service
```

10 个服务，每个 < 800 行代码。

### 问题诊断

- 一个下单流程要经过 7 跳 RPC；
- 任何订单字段变更要改 5+ 服务；
- 10 个服务共用同一张 `orders` 表（共享 DB）；
- 没有任何独立部署收益；
- 团队只有 6 人维护 10 个服务，平均每人 1.6 个；
- bug 修复要协调多个仓库 PR。

### 合并方案

按 DDD 重新划分边界：

```
原 10 服务                   合并后 3 服务

order-create-service ┐
order-update-service ├──► Order-Lifecycle-Service
order-cancel-service │      (订单聚合的生命周期)
order-history-service┘

order-query-service  ──►  Order-Query-Service (CQRS 读端)

order-refund-service ┐
order-coupon-service ├──► Order-Pricing-Service
order-tax-service    │      (订单计价与退款)
order-item-service   ┘

order-notification-service → 合并到通用 notification-service
```

### 合并过程（4 个月）

1. **第 1 月**：写 RFC、对齐共识、设计目标架构；
2. **第 2 月**：建 3 个新服务的脚手架，迁移核心代码；
3. **第 3 月**：API Gateway 把老路径双写到新服务，灰度对比；
4. **第 4 月**：切量 100%，下线老服务，删代码删仓库。

### 成果

| 指标 | 拆得太碎前 | 合并后 |
| --- | --- | --- |
| 服务数 | 10 | 3 |
| 一次下单 RPC 跳数 | 7 | 2 |
| 平均 p99 时延 | 800ms | 250ms |
| 月度 bug 数 | 28 | 9 |
| 团队心智负担 | 高 | 中 |
| 发版协调时长 | 平均 4 小时 | 平均 30 分钟 |

## 第 15 章：恰到好处的服务粒度判定

### 15.1 没有银弹

服务粒度没有标准答案，但有原则：

```
"恰到好处"的服务粒度判定矩阵
                                                 
            高耦合 ───────────────────► 低耦合
              │                              │
   高变更频率 │                              │
              │                              │
              │                              │
   低变更频率 │                              │
              │                              │
              ▼ 高内聚                    低内聚
```

**判断公式（经验法则）**：

```
一个候选服务 S 是否值得独立存在 = 
    业务自治价值 + 独立部署价值 + 团队边界价值 
  - 网络代价 - 数据同步代价 - 运维代价 - 测试代价
> 0
```

### 15.2 粒度决策清单

提出一个新服务前，问自己 10 个问题：

1. 它是一个 Bounded Context 吗？还是只是某 BC 的一部分？
2. 它有独立的不变式（business invariant）吗？
3. 它的数据是否完全自治？
4. 它有独立的可变化节奏吗？（如果总和别人一起改，就别拆）
5. 它有独立的扩展需求吗？（如果总跟另一个服务一起扩，就别拆）
6. 它有 1+ 个明确 owner 团队吗？
7. 拆出来之后，团队/工程师数是否还撑得住？
8. 调用模式是否能容忍异步？（如果必须 100% 同步链调用，先想想）
9. 数据一致性需求是否能容忍最终一致？
10. 你能 5 分钟讲清楚它的职责吗？讲不清就别拆。

任何一项答"否"，谨慎拆分。

### 15.3 一个简单的标尺

| 信号 | 该拆 | 别拆 |
| --- | --- | --- |
| 它有独立的变更节奏 | ✅ | ❌ |
| 它有独立的扩展需求 | ✅ | ❌ |
| 它有独立的团队/owner | ✅ | ❌ |
| 它能容忍最终一致 | ✅ | ❌ |
| 它有清晰的业务边界 | ✅ | ❌ |
| 它和别人共享一个聚合 | ❌ | ✅ |
| 它只是几个 CRUD 接口 | ❌ | ✅ |
| 它和另一服务总是一起改 | ❌ | ✅ |

## 生产实践

1. **每季度做一次"反模式审查"**：跑依赖图、跑共改频率、跑 RPC topology，主动检测分布式单体迹象。
2. **新服务必须过"5 问 RFC"**：为什么独立？数据归谁？谁是 owner？SLA 是什么？退路是什么？
3. **共享代码库（shared-models）严格限制**：只放纯数据结构（如 protobuf gen 代码），禁止业务逻辑。
4. **API Gateway 强制版本化**：所有外部入口必须带版本（v1/v2），90 天最少灰度期。
5. **Contract Test 是必备**：消费方写 Pact 期望，提供方 CI 跑通才能合并 PR。
6. **数据库账号一服务一用户**：用 DB 层权限强制数据所有权，从根上杜绝偷偷跨表。
7. **依赖图必须可视化**：每周生成依赖图，新增依赖必须 RFC 评审。
8. **拆分前先合并代码库做"模块化单体"**：很多团队跳过这一步直接拆，是过细拆分的根源。
9. **服务 Owner 必须公开可查**：服务注册中心必须有 owner 字段，孤儿服务下线或归并。
10. **混沌实验验证解耦**：定期随机挂掉一个服务，看其他服务是否被波及。
11. **保留"反向演进"勇气**：当一个微服务越走越像分布式单体，不要硬撑，敢于合并。
12. **拒绝技术驱动的拆分**："这个用 Go 写更好"不是拆分服务的理由。

---

## 陷阱清单

1. **把"拆得多"当成微服务成熟度**：实际可能是分布式单体。
2. **共享数据库被认为"过渡期"，然后过渡了 5 年**：永远停不下来。
3. **shared-models 库被业务逻辑塞满**：所有服务被迫同步升级。
4. **没有契约测试就敢改接口**：下游集体崩溃。
5. **同步调用链超过 5 跳**：可用性是各跳之积，p99 是各跳之和。
6. **每个聚合拆 5 个 CRUD 服务**：你失去了聚合，得到的是噩梦。
7. **跨服务事务到处用 Saga**：可能是拆错边界的征兆。
8. **服务命名带技术词（如 `*-controller-service`）**：基本可以确定切错了。
9. **服务发布必须按既定顺序**：典型的"必须同步部署"分布式单体症状。
10. **K8s 用得很高级但服务边界一团糟**：再好的运维平台救不了错的架构。
11. **新成员入职 3 个月还搞不清服务全貌**：你已经是 Big Ball of Mud。
12. **拆出来发现没有任何独立部署需求**：拆错了，合回去。
13. **认为"反向演进"是失败**：恰恰相反，敢于合并是高级架构师的标志。
14. **数据一致性出问题用更多 Saga 解决**：往往应该是合并服务而不是增加补偿。
15. **服务比工程师还多**：组织撑不住，必然走向无人维护。

---

## 2026 现状

1. **Modular Monolith 复兴**：业界主流认知回归"先模块化单体，再按需拆"，避免一开始就过度微服务。
2. **AI 辅助识别反模式**：Backstage / SourceGraph / GitHub Copilot 已能自动扫共改频率、依赖图、识别分布式单体。
3. **Macro-Service 概念兴起**：在微服务和单体之间，承认存在"中等粒度服务"是合理选择。
4. **"Right-sized service" 取代 "micro-service"**：业界讨论焦点从"够不够小"转向"合不合适"。
5. **服务合并工具成熟**：自动化代码合并、数据库迁移、API facade 转发等工具链已成熟。
6. **Team Topologies 普及**：组织设计与架构同步规划成为最佳实践。
7. **DDD 复兴**：与早期微服务"轻 DDD"不同，现在大家越来越重视战略 DDD（Bounded Context 划分）。
8. **平台工程视角**：内部开发者平台（IDP）让"开新服务"的成本变低，但也带来"是否真的需要"的反思。
9. **Service Weaver / 单进程多服务方案**：Google 等开源 Service Weaver，允许"一个二进制内多服务"，运行时再决定是否拆。
10. **观测先行成为共识**：拆分之前先有可观测性，避免拆出来盲飞。

   - 《Building Microservices》第 2 版（Sam Newman）—— 反模式与演进章节
   - 《Monolith to Microservices》（Sam Newman）—— 完整方法论
   - 《Software Architecture: The Hard Parts》（Neal Ford et al.）—— 服务粒度专章
   - 《Domain-Driven Design》（Eric Evans）—— 战略 DDD
   - 《Team Topologies》（Matthew Skelton / Manuel Pais）
2. **论文与文章**：
   - "Microservices: a definition of this new architectural term"（Martin Fowler / James Lewis）
   - "Distributed Monolith Antipattern"（Microservices.io）
   - "MonolithFirst"（Martin Fowler）
   - "How to Detect, Assess, and Remediate Anti-Patterns"（Google Cloud Architecture Center）
3. **工具**：
   - Backstage（Spotify 开源）：服务目录与 owner 治理
   - Pact / Spring Cloud Contract：契约测试
   - SourceGraph：跨仓库代码搜索
   - Istio / Linkerd Topology：依赖图自动绘制
4. **课程**：
   - Pluralsight: "Microservices Architecture Patterns and Antipatterns"
   - O'Reilly: "Software Architecture: The Hard Parts" 录播
5. **演讲**：
   - "Don't build a distributed monolith" (Jonathan Tower, NDC)
   - "Modular Monoliths" (Simon Brown, GOTO)
   - "Monolith Decomposition Patterns" (Sam Newman)

---

> 至此，本系列从"如何切微服务"讲到了"哪里别瞎切"。微服务不是目的，**让业务以可持续速度演进**才是目的。你既要会拆，也要会合。希望本章能让你在下一次"要不要拆服务"决策前，多停一秒、多问一句。
