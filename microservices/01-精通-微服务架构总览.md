# 精通微服务架构总览：单体的真正问题、何时拆、康威定律与 Microservices Premium

> 关联章节：[M02 服务拆分与 DDD](./02-精通-服务拆分与-DDD.md)、[M03 单体到微服务演进](./03-精通-单体到微服务演进.md)、[M22 反模式与重构](./22-精通-反模式与重构.md)

## 引言：先把"要不要做微服务"想清楚

微服务在 2014 年由 Martin Fowler 和 James Lewis 在博客上正式命名之后，到 2026 年已经过了 12 年。这 12 年里发生了三件事：

1. **早期狂热**（2014-2018）：所有公司争先恐后把单体拆成几十甚至几百个服务，"微服务" 成了简历加分项。
2. **现实回潮**（2019-2022）：分布式事务、运维成本、网络故障、调试痛苦让大量公司意识到自己拆错了。Segment 等公司公开把微服务合并回单体。
3. **理性沉淀**（2023-2026）：业界形成共识——微服务不是"必然演进的下一步"，而是"组织/业务/技术在某个临界点上的工程选择"。"先单体再拆" 几乎成了主流。

如果你正准备启动一个微服务项目，或者正在被 Tech Lead 反复追问"我们要不要拆"，这一章就是为你写的。读完之后你应该能：

- 准确说出单体到底有哪些真实问题（而不是道听途说）
- 给出至少 5 个"不要做微服务"的信号
- 解释康威定律的两个方向（组织 → 架构、架构 → 组织）
- 解释 "Microservices Premium" 这个概念以及它的代价构成
- 区分微服务、SOA、Macroservices 的历史与本质差异
- 用 3 个信号判断"何时该拆"
- 拿出一个清晰的"收益 vs 代价"对照表，去和老板谈

## 第一章：单体到底有什么真实问题

### 1.1 单体不是"罪恶"，但它会随规模累积四类负债

很多新工程师以为"单体 = 落后 = 必须拆"，这是错的。**单体是工程上的默认起点**，问题在于当代码量、团队规模、业务复杂度同时增长时，单体会累积四类负债，最终拖垮交付速度。

| 负债类型 | 表现 | 后果 |
|---|---|---|
| 组织扩展负债 | 多团队抢同一个仓库 | 合并冲突、谁先合谁先赢 |
| 部署耦合负债 | 改一个按钮要全量发布 | 发布频率被最慢模块卡死 |
| 技术栈锁定负债 | 全工程绑死在某语言/框架版本 | 想升级 = 全公司停摆 |
| 故障爆炸半径 | 一个内存泄漏拖垮整个进程 | 99.9% 都做不到 |

### 1.2 组织扩展负债：合并冲突的诅咒

当一个仓库被 50+ 工程师同时维护，**合并冲突的频率是工程师数量的平方级别增长**。

- 5 个人：冲突偶尔出现，几分钟解决
- 20 个人：每天都有冲突，半小时一次的 rebase 成日常
- 50 个人：合并大型 PR 时要协调多个团队，一个 PR 卡两周不罕见
- 100+ 人：单仓库已经"事实上不可维护"，团队开始建立各种"主干保护流程"——其实就是延缓崩盘

更隐蔽的问题是 **代码所有权稀释**。当所有人都能改所有代码，结果就是没人对任何代码负责。Bug 来了找不到主人，重构没人愿意做，技术债像雪球一样滚大。

### 1.3 部署耦合负债：发布频率被最慢的模块卡死

单体的"原子性部署" 听起来是好事——一致性强、回滚简单。但当业务复杂到一定程度，这个"原子性" 反而变成枷锁。

```
单体部署链：
  改一行 CSS → 走完整 CI/CD → 跑全量回归 → 部署 → 2 小时上线
                                              ↓
                                         如果回归挂了
                                              ↓
                                         所有人停工等修
```

更糟糕的是**发布频率被"最危险的模块"决定**。如果你的支付模块每周只能发一次（因为风险高），那即使你的营销模块每天能发 10 次，它也只能跟着每周一次的节奏。营销团队会怎么想？

- **方案 A**：等支付团队，业务节奏被拖慢
- **方案 B**：堆 feature flag，结果代码里到处是开关，更乱
- **方案 C**：拆成独立服务，各自发布

最后大部分公司会走到 C。

### 1.4 技术栈锁定：升级一次 = 全公司停摆

单体里所有模块共享同一个 runtime：

- Java 8 想升到 21 → 所有模块同时改，光测试就要 3 个月
- Spring Boot 2.x 想升到 3.x → 所有依赖一起改，一个旧库阻塞全局
- 想引入一个新框架（比如响应式编程）→ 不可能局部试水

**技术栈锁定的本质是"风险耦合"**——任何变动的风险都被放大到全局。结果就是公司在技术栈选型上变得极度保守，新人来了一看："你们还在用 Spring Boot 2？"

### 1.5 故障爆炸半径：一个泄漏拖垮一切

单体进程内的所有模块共享同一份资源：

- 内存：一个模块内存泄漏，整个进程 OOM
- CPU：一个模块的死循环，整个进程卡死
- 数据库连接池：一个慢查询打满连接，所有功能瘫痪
- ClassLoader：一个 jar 冲突，整个应用启不起来

这就是 **故障爆炸半径** 问题——任何小故障都可能导致整站不可用。SLO 想做到 99.9% 都很难，更别说 99.99%。

### 1.6 但单体也有真正的优势——别忘了

| 优势 | 说明 |
|---|---|
| **本地调用 0 网络成本** | 函数调用 ≈ 10 ns，gRPC 跨进程 ≈ 1 ms，差 5 个数量级 |
| **强类型 + 编译期检查** | 改接口，编译器立刻报错；微服务里要靠契约测试 |
| **事务简单** | 一个 DB connection，一句 begin/commit，没有 Saga 没有 Outbox |
| **调试简单** | 一个 IDE 起进程，断点全在；微服务要跨服务 trace |
| **运维简单** | 一个二进制文件，一份配置，一个监控仪表盘 |

**单体不是问题，问题是"在不该用单体的规模下还在用单体"**。同理，"在不该用微服务的规模下用微服务"也是问题。

## 第二章：何时不要做微服务——5 个明确信号

### 2.1 信号一：团队规模 < 10 工程师

业界经验法则：**"每个微服务由 1 个 2-pizza team（6-8 人）拥有"**。如果整个公司只有 10 个工程师，拆成 10 个服务意味着每个服务"无主"，运维、文档、值班全没人做。

- 3-5 工程师：模块化单体（modular monolith）
- 6-10 工程师：单体 + 个别独立服务（如风控、推送）
- 10-30 工程师：可以拆 3-6 个核心服务
- 30+ 工程师：完整微服务架构开始有意义
- 100+ 工程师：微服务几乎是必然

### 2.2 信号二：业务边界还在快速变

DDD 的核心前提是**业务边界相对稳定**——你能识别出"订单"和"支付"是两个不同的子域。但如果你的产品还在"上周做电商、这周做内容、下周做社交"的早期阶段，**任何拆分都会很快被打脸**。

业务边界变化的代价：
- 单体里改边界 = 改包路径，IDE 一键搞定
- 微服务里改边界 = 拆/合服务，迁移数据，改 API 契约，几周到几月

### 2.3 信号三：组织没准备好（最常被忽视）

微服务**首先是一个组织问题**，其次才是技术问题。如果没有以下任何一项，技术上拆成功也没用：

- DevOps 文化：开发要能看监控、写告警、自己上线
- 测试自动化：契约测试、集成测试、混沌测试
- 可观测平台：Prometheus + Grafana + Jaeger + Loki
- CI/CD 流水线：每个服务独立流水线、独立环境
- 服务网格或同等流量治理能力
- 容器化与 K8s 经验

很多公司"先拆了再说"，结果拆出来的服务部署还要靠 SCP + nohup，监控只有一份服务器 CPU 图——这就是"分布式单体" 的温床。

### 2.4 信号四：没有真正的扩展瓶颈

如果你的整个应用 QPS 只有 100，DB 也才 50 GB，那 "我们要做微服务来支撑高并发" 就是个借口。**单体在合理设计下能撑到 1 万 QPS、TB 级数据**——大多数公司一辈子也到不了这个门槛。

真正的"扩展瓶颈" 应该有明确数据：
- 某个模块 CPU 持续 80%+，但其他模块只用 10%
- 某个表数据增长是其他表的 100 倍
- 某个 API 流量是其他 API 的 50 倍

如果数据上看不出明显的"不均衡"，单体加机器就够。

### 2.5 信号五：还没把单体做模块化

**没有做好模块化的团队，几乎不可能做好微服务。** 因为：

- 模块化要求清晰边界 → 微服务也要
- 模块化要求依赖管理 → 微服务的 API 契约更严
- 模块化要求职责单一 → 微服务的"高内聚低耦合" 一脉相承

如果你的单体里 `OrderService` 直接调用 `userRepository.findById()`、`paymentDao.charge()`、`inventoryClient.lock()`，那你根本没有"边界"概念。先把单体做成"模块化单体"，再考虑拆分。

### 2.6 5 个信号合在一起的判断表

| 维度 | 强烈不要 | 谨慎考虑 | 适合 |
|---|---|---|---|
| 团队规模 | < 10 | 10-30 | 30+ |
| 业务稳定性 | 频繁 pivot | 边界初稳 | 模型成熟 |
| 组织准备 | 无 DevOps | 部分到位 | 完整 SRE/DevOps |
| 扩展瓶颈 | 无明确瓶颈 | 局部瓶颈 | 多模块独立扩 |
| 模块化基础 | 一锅粥 | 分模块 | 模块化单体 |

5 项里 3 项以上是"强烈不要"，就不要拆。

## 第三章：微服务 vs SOA vs Macroservices——历史脉络与本质差异

### 3.1 历史脉络

```
1980s   面向过程 / 模块化
   ↓
1990s   面向对象 / EJB / 分布式对象 (CORBA, DCOM)
   ↓
2000s   SOA (Service-Oriented Architecture) + ESB
   ↓
2010s   Microservices (2014 命名)
   ↓
2020s   Macroservices / 模块化单体 反思
```

### 3.2 SOA vs 微服务：不只是"粒度更小"

很多人以为微服务是 SOA 的"细粒度版本"，这是简化的说法。真正区别在于**思想哲学**：

| 维度 | SOA | 微服务 |
|---|---|---|
| 通信 | ESB（智能中介）| 哑管道（HTTP/MQ），逻辑在端 |
| 数据 | 共享数据库 / 联邦 | Database per Service |
| 治理 | 集中式（治理委员会）| 去中心化（团队自治） |
| 协议 | SOAP / XML / WS-* | REST / JSON / gRPC / Protobuf |
| 部署 | 应用服务器 + 共享中间件 | 独立容器 / K8s pod |
| 团队 | 跨服务的横向团队（DBA、运维等）| 垂直跨功能团队（you build it, you run it） |
| 服务发现 | UDDI 注册表 | DNS / Consul / K8s Service |
| 失败哲学 | 中央协调避免失败 | 设计为可失败，拥抱故障 |

**核心区别一句话**：SOA 把智能放在 ESB 里，微服务把智能放在端点里。

### 3.3 Macroservices——理性回潮的产物

2020 年后，业界开始反思"过细拆分"。**Macroservices** 这个词被 Cindy Sridharan 等人提出，意思是"比微服务粗的服务"：

- 一个 Macroservice 可能包含 5-10 个相关的限界上下文
- 通常 5 万到 50 万行代码
- 由一个 8-15 人团队拥有
- 部署独立，但内部仍是模块化的

例子：
- "订单中心" Macroservice = 订单 + 购物车 + 收藏夹 + 优惠券
- "用户中心" Macroservice = 注册 + 登录 + 个人资料 + 三方授权

Macroservice 的好处：
- 网络调用 << 微服务
- 数据库依赖 << 微服务
- 团队边界 ≈ 微服务
- 但内部仍有清晰模块边界

很多"先单体后微服务" 的公司，最后停在 macroservices 这一层，不再继续细拆。

### 3.4 三种架构的尺度对照

```
代码行数         100K          500K         5M
                  │             │           │
模块化单体  ──────●─────────────│           │
Macroservice      │  ●──────────●           │
微服务            │             │  ●────────●
                  │             │           │
                  10人          50人        300人
```

## 第四章：康威定律与 Inverse Conway Maneuver

### 4.1 康威定律原文

> "Any organization that designs a system... will produce a design whose structure is a copy of the organization's communication structure."
>
> —— Melvin Conway, 1968

翻译：**任何组织设计出来的系统，其架构都是该组织沟通结构的镜像。**

例子：
- 3 个团队（前端、后端、DBA）→ 系统就是三层架构
- 5 个产品线团队 → 系统就是 5 个垂直业务系统
- 1 个大团队 → 系统就是单体

**康威定律不是预测，是经验定律**——50 多年的工程实践反复验证。

### 4.2 微服务对组织的隐含要求

如果你想要"自治的微服务"，你必须先有"自治的团队"。微服务的组织设计原则：

| 微服务特性 | 组织要求 |
|---|---|
| 每个服务独立部署 | 团队拥有独立的 CI/CD 权限 |
| 每个服务独立数据库 | 团队拥有数据库 schema 修改权限 |
| 服务 API 是契约 | 团队间通过文档/契约沟通，不靠开会 |
| 失败隔离 | 团队对自己服务的可用性负全责（SRE 心智） |
| 技术栈自由 | 团队有技术选型权 |

如果你的组织里：
- 数据库改 schema 要 DBA 审批两周
- 上线要运维同事帮你部署
- 选型要走 CTO 评审

那拆微服务=自欺欺人——你拆出来的"服务" 仍然是被集中化流程牢牢拴住的，效率不会提升。

### 4.3 Inverse Conway Maneuver——主动改组织来塑造架构

既然组织结构决定架构，那要不要"先动组织来塑造想要的架构"？这就是 **Inverse Conway Maneuver**（逆康威机动）的思路：

1. **目标架构**：先想清楚你想要的微服务架构（比如 8 个核心服务）
2. **设计组织**：按目标架构组建 8 个 2-pizza team
3. **赋予权力**：给每个团队完整的 ownership（开发 + 测试 + 部署 + 运维）
4. **建立平台**：建立中央平台团队，提供 K8s / CI/CD / 可观测的 "Internal Developer Platform"

Netflix、Amazon、Spotify、Capital One 都做过类似的组织重塑。

### 4.4 平台工程团队（Platform Engineering）

伴随 Inverse Conway 而生的是"平台团队"概念：

- **业务团队**：拥有微服务的业务逻辑、API、数据
- **平台团队**：提供 K8s、CI/CD、监控、链路、服务网格、CDN 这些"基础设施即服务"

平台团队的价值不是"代为运维"，而是**通过抽象，让业务团队不需要懂底层就能享受底层能力**。Backstage（Spotify 开源）就是平台工程的代表产物。

## 第五章：Microservices Premium——拆分的真实代价

### 5.1 Martin Fowler 提出的 "Premium" 概念

2015 年 Martin Fowler 发表《MicroservicePremium》一文，核心观点：

> 微服务有真实的好处，但它要求你付出一笔"溢价"（premium）。如果你的项目复杂度低，这笔溢价就吃掉了你所有的收益，让你的生产力反而下降。

```
生产力
  ▲
  │              微服务收益曲线 ╱
  │                          ╱
  │                       ╱
  │     单体    ────────●────  临界点：复杂度 C*
  │          ╱
  │       ╱
  │    ╱
  │ ╱
  └──────────────────────────────►  复杂度
        简单         复杂        非常复杂
```

**关键洞察**：在复杂度 C* 以下，单体的生产力总是高于微服务。微服务只有在突破临界点后才反超。

### 5.2 Premium 包含什么——5 类代价

#### 代价 1：网络成本

进程内函数调用 ~10 ns；进程间 gRPC ~1 ms（10^5 倍差距）；跨可用区调用 ~5-10 ms（10^6 倍）。

```
单体里的 1 行调用：
  user = userRepository.findById(id);  // 10 ns ~ 1 μs

微服务里同样的逻辑：
  序列化请求 ──→ 网络 ──→ 反序列化 ──→ DB ──→ 序列化响应 ──→ 网络 ──→ 反序列化
  ~10 μs       ~500 μs   ~10 μs        ~500 μs ~10 μs       ~500 μs    ~10 μs
  总计 ~1-2 ms
```

任何一次跨服务调用都比本地调用慢 100-10000 倍。如果你的业务里有"每请求要调 10 个服务"的链路，延迟就到了 10ms+。

#### 代价 2：复杂度爆炸

```
单体的关注点：
  - 业务逻辑
  - 单库事务

微服务的关注点：
  - 业务逻辑
  - 服务发现
  - 网络重试
  - 熔断降级
  - 限流
  - 幂等
  - 分布式事务（Saga / Outbox）
  - 数据一致性
  - 跨服务调试 / Trace
  - 服务间认证 (mTLS)
  - 版本兼容
  - 部署编排
```

每个关注点都是一个学习和维护的负担。

#### 代价 3：分布式系统陷阱

著名的 **L. Peter Deutsch 的"分布式 8 大谬误"**：

1. 网络是可靠的
2. 延迟为零
3. 带宽无限
4. 网络是安全的
5. 拓扑结构不变
6. 只有一个管理员
7. 传输成本为零
8. 网络是同构的

**单体里你可以全部假设是真的，微服务里全部是假的**。

#### 代价 4：运维成本

| 维度 | 单体 | 微服务 |
|---|---|---|
| 部署单元 | 1 | N（10-100+） |
| CI/CD 流水线 | 1 | N |
| 监控仪表盘 | 1 | N + 全局 |
| 告警规则 | ~20 | ~20 × N |
| 数据库 | 1 | N |
| 日志聚合 | 单机 | 集中式 (ELK/Loki) |
| 链路追踪 | 不需要 | 必须 (OTel + Tempo) |
| 配置中心 | 1 个文件 | 配置中心服务 |
| 发布协调 | 简单 | 灰度 + 兼容 + 回滚 |

运维团队人数大约要乘以 1.5-3。

#### 代价 5：组织成本

- 跨团队会议数量爆炸：A 服务改 API → 通知 B/C/D
- 新人 onboarding 成本：要懂 10 个服务才能 fix 一个 bug
- 文档维护：API、依赖图、On-Call SOP，全要写

### 5.3 Premium 的可视化对比

```
单体项目 100 人月：
  业务逻辑 70 人月
  基础设施 20 人月
  运维 10 人月

同等微服务项目：
  业务逻辑 60 人月（多了 API 设计、契约测试）
  基础设施 50 人月（多了网关、网格、可观测）
  运维 30 人月（多了部署编排、告警维护）
  ──────────────────────
  合计 140 人月（+40%）
```

40% 是常见数字。如果你的项目还没复杂到需要它，那这 40% 就是纯亏。

## 第六章：Monolith First 原则

### 6.1 Martin Fowler 的两条经验法则

Fowler 提出两条经验法则：

1. **几乎所有成功的微服务故事都是从单体演进而来。**
2. **几乎所有从零开始就上微服务的项目都遇到了重大麻烦。**

为什么？

- 一开始你不知道边界在哪——业务还在变
- 一开始你的团队规模不需要拆
- 一开始你的复杂度还在 C* 以下——拆了反而拖慢

### 6.2 Monolith First 的实操路径

```
阶段 1：单体（0-10 人）
  ↓
阶段 2：模块化单体（10-30 人）
  ↓
阶段 3：拆出 1-3 个独立服务（30-50 人）
  ↓
阶段 4：完整微服务架构（50+ 人）
  ↓
阶段 5：可能反向合并（如果发现过细）
```

每一步都是基于"当下的痛点"而不是"未来的可能"。

### 6.3 模块化单体（Modular Monolith）

阶段 2 是关键。模块化单体的目标：

- 每个模块有清晰边界（package / namespace 隔离）
- 模块间只能通过公开 API 交互（私有方法不能跨模块调用）
- 模块各自有数据访问层（不能跨模块直接查表）
- 模块各自的领域模型独立（不共享 entity）

如果你做到这一点，将来拆微服务时**几乎只是"把进程内调用换成 RPC"**。反过来如果模块边界混乱，拆出来也是分布式单体。

```java
// 反例：跨模块调用私有 DAO
public class OrderService {
  @Autowired UserRepository userRepo;     // 跨模块直接访问
  @Autowired ProductRepository productRepo;
  // ...
}

// 正例：通过公开 API
public class OrderService {
  @Autowired UserModule userModule;       // 模块级 API
  @Autowired ProductModule productModule;

  public Order createOrder(Long userId, Long productId) {
    User user = userModule.findById(userId);     // 公开方法
    Product product = productModule.findById(productId);
    // ...
  }
}
```

## 第七章：何时拆——3 个信号

如果你已经在单体上跑了一段时间，怎么判断"现在该开始拆了"？看这 3 个信号。

### 7.1 信号一：部署矛盾

**症状**：发布频率被某一两个"高危模块"卡死。其他团队天天等。

**度量**：
- 某模块发布失败率 > 5%
- 整体平均发布周期超过团队期望的 3 倍
- 每月有 > 3 次"因 A 模块问题导致 B 团队回滚"的事件

**判断**：把"高变更率 + 低风险" 模块拆出去。

### 7.2 信号二：团队矛盾

**症状**：多个团队改同一份代码导致频繁冲突；ownership 模糊。

**度量**：
- 单个 PR 平均合并时长 > 1 天
- 30%+ 的 PR 涉及多团队代码
- 出现"我以为你改了" / "我没敢改怕影响你" 的对话

**判断**：按团队 ownership 划分边界，拆成各自负责的服务。

### 7.3 信号三：性能矛盾

**症状**：某个模块的资源消耗远高于其他模块，但被绑死无法独立扩容。

**度量**：
- 某模块 CPU 占比 > 50%
- 某 API 流量是平均的 10 倍
- 想给某模块加机器，结果要给整个应用加

**判断**：把高负载模块独立成服务，单独水平扩展。

### 7.4 3 个信号一起出现 = 拆分时机到了

```
                   部署矛盾
                      │
                      │  ◄── 1 个信号：还能忍
                      │  ◄── 2 个信号：开始规划
                      │  ◄── 3 个信号：必须行动
                      │
       团队矛盾 ──────┼────── 性能矛盾
```

只满足 1 个不要急；2 个开始做规划；3 个齐全已经晚了，赶紧动手。

## 第八章：微服务的核心收益——4 个真实优势

如果代价这么大，为什么大公司还是义无反顾地拆？因为收益足够大。

### 8.1 收益一：独立部署 → 加快交付节奏

每个服务独立 CI/CD、独立发布，发布频率不再被其他模块卡死。

```
单体：每周 1-2 次发布，每次 100+ 人协同
微服务：每天每团队 2-3 次发布，互不影响
```

业界数据：Amazon 公开说他们每秒钟有一次部署（thousands per day）。这不是单体能做到的。

### 8.2 收益二：技术栈自由 → 局部演进

每个服务可以选最合适的技术：

- 推荐服务用 Python（生态好）
- 高并发支付用 Go 或 Rust
- 复杂业务流程用 Java（生态成熟）
- 实时计算用 Scala + Akka

更重要的是**可以局部升级**——某个服务升 JDK 21，不影响别人。

### 8.3 收益三：故障隔离 → 提高整体可用性

```
单体：1 模块宕机 → 整站不可用
微服务：1 服务宕机 → 只影响相关功能

99% × 99% × 99% × ... × 99% 听起来在下降
但实际上：每个服务 99.9% + 韧性设计（熔断/降级）→ 整体 99.95%
```

关键是"故障被隔离" 让你能针对性优化最关键的服务。

### 8.4 收益四：独立扩展 → 节省资源

高负载服务单独水平扩，低负载服务保持 1-2 实例。

```
单体：要扩就全扩，10 倍流量 = 10 倍机器
微服务：只扩流量大的，10 倍流量 = 2 倍机器 + 网关 + DB
```

成本节省常见 30-50%。

## 第九章：微服务的代价——4 个真实负担

### 9.1 负担一：分布式调试地狱

单体里 stack trace 就够。微服务里你需要：

- Trace ID 跨服务传递（W3C TraceContext）
- 集中式 Trace 存储（Jaeger / Tempo）
- 跨服务日志聚合（Loki / ELK）
- 服务间的请求关联（OpenTelemetry SDK）

如果没有这些，"为什么这个请求慢" 这个问题就无法回答。

### 9.2 负担二：数据一致性问题

```
单体：begin; update orders; update inventory; commit;     // 1 个事务

微服务：
  1. order-service 创建订单
  2. inventory-service 扣库存
     如果失败怎么办？
     补偿 order-service 吗？
     补偿的请求又失败了怎么办？
```

这就引入了 Saga、Outbox、TCC、最终一致性的整套复杂度（[详见 M08](./08-精通-分布式事务.md)）。

### 9.3 负担三：版本兼容与契约管理

服务 A 改了 API，调用方 B、C、D 怎么办？

- 必须 backward compatible（加字段、不删字段、不改字段类型）
- 必须有契约测试（Pact / Spring Cloud Contract）
- 必须有 Schema Registry（Avro / Protobuf）

破坏性变更（breaking change）几乎要走"加新 API → 灰度迁移 → 退役旧 API"的多步流程。

### 9.4 负担四：运维基础设施投入

最低门槛：

- K8s 集群（或同等容器平台）
- 服务发现（K8s Service / Consul）
- 配置中心（Apollo / Nacos）
- 消息中间件（Kafka / RabbitMQ）
- 监控告警（Prometheus + Alertmanager）
- 链路追踪（OpenTelemetry + Jaeger）
- 日志聚合（Loki / ELK）
- API 网关（Kong / Envoy Gateway）
- CI/CD（Jenkins / GitHub Actions / ArgoCD）
- 服务网格（Istio / Linkerd，可选）

每一项都是几人月的搭建 + 持续运维。

## 生产实践

### 实践 1：用"3 个信号 + 5 个反信号"做最终决策

启动微服务项目前，把第七章的 3 个拆分信号和第二章的 5 个"不要做" 信号同时对照。如果反信号有 2 项以上，**坚决不拆**。这不是怯懦，是工程负责。

### 实践 2：先做模块化单体 6-12 个月

不要直接从"单体" 跳到"微服务"。中间过渡是"模块化单体"——同一进程，但模块边界清晰、模块间只走公开 API。这一步是后续拆分的演练，也是判断边界是否正确的试金石。

### 实践 3：第一刀拆"最容易的服务"

拆分新手最常见错误是从核心业务下手——结果出问题影响巨大、回滚困难。正确做法：

- 选一个"边界清晰 + 业务次要 + 团队意愿强" 的模块（通知、文件上传、报表等）
- 完整走一遍：拆代码 → 拆数据 → 上 CI/CD → 上监控 → 上线
- 团队积累经验后，再拆核心服务

### 实践 4：建立 Service Catalog 与 Ownership

每个服务必须有：

- 明确的 Owner Team（不能"我们部门"，要具体到团队）
- 明确的 On-Call 轮值
- 明确的 SLO（可用性 / 延迟）
- 一份对外 API 文档
- 一份 Runbook（出问题怎么办）

用 Backstage 或类似工具管理。没有 catalog 和 ownership，服务长出来无人认领，迟早成"僵尸服务"。

### 实践 5：先建平台团队，再拆业务服务

平台先行 6-12 个月：

- K8s 集群（生产 + 预发）
- CI/CD 模板
- 监控/链路/日志统一接入
- 网关 + 服务发现
- 服务模板（脚手架）

业务团队"开箱即用"，否则每个业务团队各搭一套，重复造轮子还都不专业。

### 实践 6：避免"大爆炸式重构"

不要"一次性把单体拆成 20 个服务"。用绞杀者模式（见 M03）渐进式拆分，每次只拆一个，跑稳了再下一个。3 年完成迁移是健康节奏，3 个月完成的多半是灾难。

## 陷阱清单

### 陷阱 1：以为微服务必然更快

**错误**：拆完之后接口响应更慢，因为多了网络跳数和序列化。
**真相**：单次请求几乎总是变慢。微服务的"快"是**整体团队交付速度**的快，不是单次请求的快。

### 陷阱 2：分布式单体（最常见陷阱）

**症状**：服务拆了，但所有服务都依赖同一个数据库；改一个表所有服务一起改；部署还是要按顺序。
**根因**：拆了进程，没拆数据；拆了代码，没拆 ownership。
**后果**：兼具单体和微服务的所有缺点，没有任何一个的优点。

### 陷阱 3：先拆服务，后做平台

**错误**：业务团队各自硬造 CI/CD 和监控，标准不一，运维灾难。
**正确**：先用 6-12 个月建立平台和标准，业务团队基于平台拆。

### 陷阱 4：服务边界跟着技术分（DAO 服务、API 服务）

**错误**：拆成"用户 DAO 服务、用户 API 服务、用户 BFF 服务"——按技术层拆。
**正确**：按业务域拆——"用户中心" 是一个服务，内部包含 DAO/Service/Controller。

### 陷阱 5：忽视组织一致性

**错误**：技术拆了 20 个服务，但开发流程还要 CTO 一周一审。
**结果**：服务自治变成笑话，发布速度反而下降。

### 陷阱 6：过度拆分（Nano-Services）

**错误**：每个 CRUD 操作一个服务。
**后果**：100+ 服务，每个只有几百行代码，但运维成本爆炸。Segment 在 2018 年公开把自己的 100+ 服务合并回单体，就是这个陷阱的反面教材。

### 陷阱 7：以为只是技术问题

**错误**：CTO 拍板"我们做微服务"，没动组织、没做培训。
**真相**：微服务是组织变革 + 技术变革，缺一不可。

### 陷阱 8：忘了反向退路

**错误**：拆了就回不去——没有合并预案。
**真相**：微服务也可能拆错。能合并回去的架构才是真正灵活的架构。Segment、Istio（control plane 合并）、InVision 都做过反向操作。

## 练习题

### 题 1：判断信号

某创业公司，12 名工程师，业务是 SaaS 销售管理工具，已上线 8 个月，PMF 还在摸索，每月发版 6-8 次，单体跑在 2 台机器上，QPS 100。CTO 想拆微服务。

请用本章学到的判断标准评估，并给出建议。

**答案要点**：5 个反信号里至少满足"团队规模小（12 < 临界 30）" + "业务边界未稳（PMF 摸索）" + "无明确扩展瓶颈（100 QPS）" + "组织准备不足（创业公司大概率无 SRE）" 4 项。强烈建议**不要拆**，先做模块化单体。

### 题 2：康威定律应用

公司想从单体演进到微服务，目标拆 6 个服务。当前组织是"前端组、后端组、DBA 组、测试组" 4 个横向团队。请基于 Inverse Conway Maneuver 设计组织调整方案。

**答案要点**：把 4 个横向团队改成 6 个垂直跨功能团队，每个团队有自己的前后端 + DBA 兼任 + 测试。DBA 转为"平台数据团队" 角色，做 DB 标准化工具而不是为每个团队改 schema。

### 题 3：3 个拆分信号

A 公司有以下情况：每月发版 4 次，每次涉及全员协调；某个推荐模块 CPU 占比 60%，其他模块都不忙；ownership 清晰，开发协作顺畅。是否该拆？拆什么？

**答案要点**：满足"部署矛盾 + 性能矛盾" 2 个信号，不满足"团队矛盾"。可以先拆 **推荐模块** 成独立服务以独立扩容，同时部分缓解发布耦合。不需要立即全面拆分。

### 题 4：Microservices Premium 计算

如果一个 100 人月的单体项目，按 40% premium 估算，对应微服务版本需要多少人月？这个 premium 主要花在哪里？

**答案要点**：100 × 1.4 = 140 人月。Premium 主要花在：基础设施搭建（网关、网格、链路追踪）、运维成本（多个 CI/CD、监控）、复杂度处理（分布式事务、契约测试、版本兼容）。

### 题 5：辨析

下面哪些是"分布式单体"的特征？  
A. 服务各自独立部署但共享一个数据库  
B. 改一个服务的 API 需要同时改 5 个调用方  
C. 服务间用 gRPC 通信  
D. 所有服务的发布必须按固定顺序进行  
E. 每个服务有独立的数据库

**答案要点**：A、B、D 是分布式单体特征。C 是中性（gRPC 本身不导致分布式单体）。E 是真正微服务的标志。

### 题 6：何时不要拆

列出至少 5 个"不要做微服务" 的信号，并解释为什么每个信号都是 stop sign。

**答案要点**：参见第二章 5 个信号。每个信号的本质：团队规模不够 → 服务无主；业务不稳 → 边界总改；组织没准备 → 拆了等于自残；无扩展瓶颈 → 拆了纯亏；模块化基础差 → 拆出来就是分布式单体。

### 题 7：单体的真实问题

为什么单体在团队规模超过 50 人后几乎必然出问题？请列出至少 3 个机制。

**答案要点**：（1）合并冲突频率 O(N²) 增长；（2）发布耦合让发布频率被最危险模块卡死；（3）代码 ownership 稀释，无人负责；（4）单一技术栈无法满足不同场景。

### 题 8：架构选择

某公司有以下情况：50 工程师，4 年历史的电商单体，最近 1 年内出现 2 次"全站宕机" 事故（均因单个模块 OOM），有完整 DevOps 流程。Tech Lead 提议拆微服务。请给出你的方案。

**答案要点**：满足拆分条件（规模够、业务稳、组织有 DevOps、有故障爆炸半径问题）。建议：（1）先做模块化单体，明确边界 6 个月；（2）按"3 信号" 选 2-3 个最痛的模块先拆（如曾经 OOM 的模块、高变更率模块）；（3）平台先行，建好 K8s/监控/网关；（4）渐进式 12-18 个月拆完核心服务；（5）保留单体作为"剩余服务"容器，不要追求 100% 拆分。
