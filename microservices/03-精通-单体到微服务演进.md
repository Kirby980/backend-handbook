# 精通单体到微服务演进：绞杀者模式、影子流量、数据库拆分、迁移路线图

> 关联章节：[M01 微服务架构总览](./01-精通-微服务架构总览.md)、[M02 服务拆分与 DDD](./02-精通-服务拆分与-DDD.md)、[M22 反模式与重构](./22-精通-反模式与重构.md)

## 引言：为什么"演进"比"重写"更难也更靠谱

读完 M01 你知道了"何时该拆"，读完 M02 你知道了"该怎么拆"。但还有一个最关键的问题没回答：**你已经有一个 100 万行代码的老单体了，怎么把它变成微服务？**

业界历史上有两种思路：

### 思路 A：大爆炸式重写（Big Bang Rewrite）

- 凑齐一支新团队
- 用 12-18 个月平行开发新版微服务
- 某天上线，老系统下线

**失败率 > 80%**。著名失败案例：

- **Netscape 6（1998-2000）**：把 Navigator 重写，期间被 IE 抢光市场份额，公司被卖
- **Friendster**：重写期间被 MySpace 和 Facebook 超越
- 国内某电商把订单中心重写一年，上线后导致全站事故，被迫回滚

为什么会失败？Joel Spolsky 2000 年那篇著名博文《[Things You Should Never Do, Part I](https://www.joelonsoftware.com/2000/04/06/things-you-should-never-do-part-i/)》总结得最清楚：

> 你以为旧代码丑陋是因为之前的工程师笨。其实那些丑陋的代码里藏着 10 年的 bug 修复、特殊处理、边缘 case。重写会把所有这些经验全部丢掉。

### 思路 B：渐进式演进（Incremental Evolution）

- 不重写，逐步替换
- 一次只拆一个模块
- 12-36 个月走完整迁移
- **失败率 < 30%**

业界共识：**永远选思路 B**。这一章讲的就是思路 B 的整套方法论。

读完这一章你应该能：

- 用绞杀者模式（Strangler Fig）的 3 步法启动迁移
- 用并行运行（Parallel Run）+ 影子流量（Shadow Traffic）验证新服务
- 用 CDC（Change Data Capture）拆分共享数据库
- 用 ACL 保护新服务不被老模型污染
- 画出一份 12 个月迁移路线图
- 识别"应该退回单体" 的反向演进信号
- 准备完整的回滚预案

## 第一章：绞杀者模式（Strangler Fig Pattern）

### 1.1 名字的由来

Martin Fowler 2001 年从澳洲热带雨林里看到一种植物——绞杀榕（Strangler Fig），2004 年成文命名了这个模式。这种植物的生长过程是：

1. 鸟把种子带到一棵宿主树上
2. 种子在树枝上发芽，根向下延伸到地面
3. 绞杀榕的根慢慢包裹住宿主树
4. 几十年后宿主树枯死、腐烂、消失
5. 留下的是一个中空但完整的绞杀榕

Fowler 觉得这个比喻太贴切了：

- 宿主树 = 老单体
- 绞杀榕 = 新微服务
- 包裹过程 = 渐进替换
- 宿主消失 = 老单体退役

```
阶段 1：种子萌芽          阶段 2：根系蔓延         阶段 3：宿主消失
                         
   单体(完整)              单体(部分还在)            单体(已退役)
       │                    新服务 ●                  新服务 ●●●●●
       │                    新服务 ●                  新服务 ●●●●●
       │                                              新服务 ●●●●●
```

### 1.2 绞杀者模式的 3 步

#### 第 1 步：建立转发层（Façade / Proxy）

**在单体前面放一个反向代理**，作为所有外部流量的入口。所有请求先到代理，代理决定路由到老单体还是新服务。

```
                    ┌──────────────────┐
                    │  Strangler Façade │
   客户端 ────────►│  (Nginx/Envoy)    │
                    └────────┬──────────┘
                             │
                  ┌──────────┴──────────┐
                  ▼                     ▼
            ┌─────────┐          ┌────────────┐
            │ 老单体  │          │ 新服务      │
            │         │          │ (空的，待替) │
            └─────────┘          └────────────┘
```

**关键**：在还没有任何新服务时，**先把这个代理上线**——所有流量都转发到老单体。这一步不改变任何业务，但为后续切换打基础。

#### 第 2 步：替换逻辑（一次替换一个）

每次选**一个 API / 一个模块** 从老单体移到新服务。代理的路由规则更新：

```
路由表:
  GET  /api/users/*           ──→ 新用户服务
  POST /api/orders            ──→ 老单体  (还没拆)
  GET  /api/products/*        ──→ 新商品服务
  *                            ──→ 老单体  (默认)
```

**渐进过程**：

- 第 1 次：拆"用户注册" API
- 第 2 次：拆"商品查询" API
- 第 3 次：拆"购物车" API
- ...

每次只拆 1-2 个 API，跑稳后再下一个。**失败可以单点回滚**，不影响其他模块。

#### 第 3 步：退役老路径

当所有 API 都迁移完成，老单体里这部分代码就死了：

- 删除老单体里对应的 controller / service / DAO
- 删除路由表中的 fallback 规则
- 删除数据库里的相关表（如果数据也迁完了）

**最终状态**：老单体逐渐变薄，直到所有功能都迁出，整个老单体退役。

### 1.3 绞杀者的关键优势

| 优势 | 说明 |
|---|---|
| **风险可控** | 每次只动一小块，问题可单点回滚 |
| **持续交付** | 不停服、不影响业务 |
| **学习曲线平滑** | 团队边做边学，不是一夜要换技能栈 |
| **可中止** | 半路发现拆错了，立刻停下重新规划 |

### 1.4 路由层选型

| 工具 | 适用场景 | 难度 |
|---|---|---|
| **Nginx** | 简单路径路由 | 低 |
| **Envoy / Envoy Gateway** | 复杂规则、灰度、可观测 | 中 |
| **Kong** | 需要插件生态（认证、限流） | 中 |
| **API 网关（Apisix / Kong）** | 全功能企业级 | 中 |
| **Spring Cloud Gateway** | Java 技术栈、与微服务集成 | 中 |
| **Istio Ingress** | 已有 K8s + Istio | 高（但功能最强）|

经验：**早期用 Nginx 起步够用**，复杂度上来再升 Envoy 或网关。

### 1.5 转发层的关键能力清单

转发层不只是"转发"——它要支持几个关键能力：

- **基于路径的路由**：`/api/users/*` 走新服务
- **基于 Header 的路由**：`X-User-Group: beta` 走新服务（灰度）
- **流量复制（Shadow）**：请求同时发往老和新，对比结果
- **超时与重试**：新服务挂了能 fallback 回老单体
- **链路追踪注入**：Trace ID 跨服务传递
- **可观测**：路由流量分布、新老延迟对比

## 第二章：并行运行（Parallel Run）+ 影子流量（Shadow Traffic）

### 2.1 并行运行的意义

绞杀者的核心是"逐步替换"，但替换前怎么知道新服务和老逻辑等价？答案是**并行运行**：

```
                              ┌─→ 老单体逻辑 ─→ 结果 A
                              │
   请求 ──→ Façade ───────────┤
                              │
                              └─→ 新服务   ─→ 结果 B

   对比器（Diff）：A 和 B 是否一致？
```

阶段：

1. **完全并行 + 用老的结果**：两边都跑，但返回老的；后台对比 A 和 B
2. **完全并行 + 用新的结果**：跑稳了切换，返回新的；老的继续跑做对照
3. **下线老逻辑**：新的稳定，老的彻底关闭

### 2.2 影子流量（Shadow Traffic）

**影子流量** = 把请求复制一份发给新服务，但**新服务的响应被丢弃**——不影响生产，只用于验证。

```
   请求 ──→ Façade ──→ 老单体 ──→ 客户端
                │
                └─→ 新服务 (复制) → 日志 + 对比 → 监控
```

#### 影子流量的好处

- **零风险验证**：新服务挂了客户无感
- **真实流量压测**：用生产流量验证容量
- **正确性验证**：对比新老响应找 bug

#### 工具

- **Envoy 的 request_mirror_policies**：原生支持流量镜像
- **Istio 的 mirror**：服务网格层
- **Diffy（Twitter 开源）**：专门做新老服务 diff 的工具
- **Linkerd 的 traffic split + mirror**

Envoy 配置例子：

```yaml
route:
  cluster: old-monolith
  request_mirror_policies:
    - cluster: new-service
      runtime_fraction:
        default_value:
          numerator: 100   # 100% 镜像
          denominator: HUNDRED
```

### 2.3 Diff 测试（结果对比）

光发流量不够，还要**自动对比新老响应**：

```python
# 简化的 Diff 测试器
def diff_test(request):
    old_response = call_old_monolith(request)
    new_response = call_new_service(request)
    
    if not deep_equal(old_response, new_response):
        log_diff(request, old_response, new_response)
        metrics.inc("diff_count")
    
    return old_response   # 始终返回老的
```

**关键技巧**：

- 忽略不重要字段（时间戳、ID、随机值）
- 容忍可接受差异（如金额精度 +/- 0.01）
- 把 diff 按 endpoint 聚合，找模式

GitHub 开源了 **Scientist**（Ruby）库做这件事，其他语言有对应实现。

### 2.4 灰度切换

影子流量跑稳后，开始真实切换。**永远用百分比逐步切换**：

```
第 1 天：1% 流量到新服务
第 2 天：5%
第 3 天：10%
第 7 天：25%
第 14 天：50%
第 21 天：100%
```

切换工具：

- **Envoy weighted clusters**：按权重分流
- **Istio VirtualService**：精细化流量切分
- **特性开关（Feature Flag）**：基于业务规则切（如某品类、某地域）

### 2.5 自动回滚

切换过程中必须有自动回滚：

```yaml
# 简化的自动回滚规则
rollback_when:
  - new_service_error_rate > 1%        # 错误率超阈值
  - new_service_p99_latency > 500ms    # 延迟超阈值
  - diff_test_failure_rate > 0.1%      # diff 失败率超阈值
```

**指标关联回滚** 是渐进式交付（Progressive Delivery）的核心——见 M19 灰度发布。

## 第三章：数据库拆分——最难的一步

### 3.1 为什么数据库拆分这么难

代码层面的"拆分服务" 相对简单：写新代码、改路由。但**数据库拆分**碰到的问题完全不同：

- 数据有 **状态**——不能简单"切换"
- 数据有 **关联**——JOIN、外键、事务
- 数据有 **历史**——几年的数据要不要迁
- 数据 **不停在变**——迁移期间新数据不断进来

业界一个共识：**数据库拆分的工作量 = 代码拆分工作量的 3-5 倍**。

### 3.2 共享数据库模式与目标

```
当前（共享 DB）：
  ┌──────────┐     ┌──────────┐    ┌──────────┐
  │ 服务 A   │     │ 服务 B   │    │ 服务 C   │
  └────┬─────┘     └────┬─────┘    └────┬─────┘
       │                │               │
       └───────┬────────┴──────┬────────┘
               ▼               ▼
        ┌─────────────────────────┐
        │  共享数据库 (含 50 张表) │
        └─────────────────────────┘

目标（Database per Service）：
  ┌──────────┐     ┌──────────┐    ┌──────────┐
  │ 服务 A   │     │ 服务 B   │    │ 服务 C   │
  └────┬─────┘     └────┬─────┘    └────┬─────┘
       ▼                ▼               ▼
  ┌─────────┐     ┌─────────┐     ┌─────────┐
  │ DB A    │     │ DB B    │     │ DB C    │
  └─────────┘     └─────────┘     └─────────┘
```

### 3.3 数据库拆分的 5 步走

#### 步骤 1：分组表归属

把现有表按"属于哪个服务" 分组：

```
共享 DB:
  - users          → 用户服务
  - user_profiles  → 用户服务
  - orders         → 订单服务
  - order_items    → 订单服务
  - products       → 商品服务
  - product_skus   → 商品服务
  - inventory      → 库存服务
  - payments       → 支付服务
```

**重点**：处理跨服务的表（如 `order_items` 既被订单查也被推荐查）——决定主归属，其他服务通过 API 取。

#### 步骤 2：解除跨表 JOIN

找出所有跨服务的 JOIN，逐一改造：

```sql
-- 改造前（跨服务 JOIN）
SELECT o.*, u.name, p.title
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN products p ON o.product_id = p.id;

-- 改造方案 1：API 调用聚合
1. 查 orders（订单服务自己的 DB）
2. 批量查 users（调用用户服务）
3. 批量查 products（调用商品服务）
4. 应用层组装

-- 改造方案 2：冗余字段
ALTER TABLE orders ADD COLUMN user_name VARCHAR(100);
ALTER TABLE orders ADD COLUMN product_title VARCHAR(200);
-- 下单时填充快照

-- 改造方案 3：CQRS 物化视图
新建 order_view 表（消费 orders + users + products 事件维护）
```

#### 步骤 3：解除外键约束

外键是跨服务拆分的死敌。**逐步删除外键**：

```sql
-- 删除外键
ALTER TABLE orders DROP CONSTRAINT fk_orders_user;

-- 用应用层校验代替
public Order createOrder(OrderCommand cmd) {
    // 应用层校验 user 存在
    if (!userService.exists(cmd.userId)) {
        throw new UserNotFoundException();
    }
    // ...
}
```

**接受弱一致**：删除外键后，理论上可能存在"订单引用了不存在的用户"。在分布式系统里这是常态——通过对账脚本周期性检测。

#### 步骤 4：物理迁移

表归属确定后，物理上把表移到新 DB：

```
方案 A：停机迁移（适合数据少 < 10GB）
  1. 停服 5-30 分钟
  2. 把表 dump 到新 DB
  3. 修改服务连接串
  4. 启动

方案 B：双写迁移（适合数据多）
  1. 老 DB 和新 DB 都有这张表
  2. 应用同时写两边
  3. 后台对比新老一致性
  4. 切换读到新 DB
  5. 停止写老 DB

方案 C：CDC 同步（推荐，详见下一节）
```

#### 步骤 5：数据所有权移交

迁移完成后：

- 老 DB 删除已迁走的表
- 新 DB 上加完整索引、权限
- 服务的 DB 权限收回到最小（只能访问自己的 DB）
- 监控告警迁移

### 3.4 数据库拆分的难点：跨服务事务

老单体里你可以这样：

```sql
begin;
update orders set status = 'paid' where id = 100;
update inventory set quantity = quantity - 1 where sku_id = 200;
commit;
```

拆分后这两张表分别在不同 DB 里。怎么办？

**绝对不要用 XA / 2PC**。详见 M08。**用 Saga 或 Outbox**：

```
Saga 模式：
  1. 订单服务：update orders set status = 'pending_inventory'
                publish event OrderPendingInventory
  2. 库存服务：consume event
                update inventory（成功或失败）
                publish event InventoryReserved/Failed
  3. 订单服务：consume event
                update orders set status = 'paid' or 'cancelled'
```

详细 Saga 实现在 M08，这里只指出：**数据库拆分必然带来跨服务事务问题，必须提前规划补偿逻辑**。

## 第四章：CDC（Change Data Capture）保持数据同步

### 4.1 为什么需要 CDC

数据库拆分是渐进过程。中间会有"老 DB 还在用、新 DB 也在写"的并存期。这时需要让两边的数据**实时同步**。

CDC 的本质：**监听数据库的变更日志（binlog/WAL），把变更转成事件**。

```
   老 DB (MySQL)
       │
       │  binlog（INSERT/UPDATE/DELETE）
       ▼
   ┌────────────┐
   │  Debezium  │  CDC 工具
   └─────┬──────┘
         │  Kafka 消息
         ▼
   ┌─────────────┐
   │   Kafka     │  Topic: db.orders.cdc
   └─────┬───────┘
         │
   ┌─────┴─────┐
   ▼           ▼
新 DB    其他服务消费
```

### 4.2 Debezium——CDC 的事实标准

**Debezium** 是 Red Hat 开源的 CDC 工具，支持 MySQL / PostgreSQL / SQL Server / Oracle / MongoDB 等。

部署形态：**Debezium Connector 跑在 Kafka Connect 上**。

```yaml
# Debezium MySQL Connector 配置
name: mysql-connector-monolith
config:
  connector.class: io.debezium.connector.mysql.MySqlConnector
  database.hostname: monolith-db
  database.port: 3306
  database.user: debezium
  database.password: ${secret}
  database.server.id: 184054
  database.server.name: monolith
  table.include.list: monolith.orders,monolith.order_items
  database.history.kafka.bootstrap.servers: kafka:9092
  database.history.kafka.topic: schema-changes.monolith
```

数据流：

```
orders 表 INSERT
   ↓
binlog: INSERT INTO orders VALUES (...)
   ↓
Debezium 读 binlog
   ↓
Kafka topic monolith.orders 收到消息:
{
  "before": null,
  "after": {"id": 100, "user_id": 42, "amount": 199},
  "op": "c",
  "ts_ms": 1700000000000
}
```

### 4.3 CDC 在拆分中的 3 个核心用法

#### 用法 1：双向同步（迁移期）

老 DB → CDC → Kafka → 新 DB；同时新 DB → CDC → Kafka → 老 DB。

这样不论哪边写，最终两边都一致。**适合渐进式迁移期**。

风险：**双向 CDC 容易循环**——A 写到 B，B 又传回 A。要加循环检测（标记来源）。

#### 用法 2：Outbox 模式（保证事件可靠发布）

服务在自己的 DB 里写一张 `outbox` 表，CDC 监听这张表并发布到 Kafka：

```sql
-- 服务的本地事务
begin;
insert into orders ...;
insert into outbox (event_type, payload) values ('OrderCreated', '{...}');
commit;

-- CDC 读 outbox 表
-- 自动发布到 Kafka topic orders.events
```

好处：业务表写入和事件发布在**一个本地事务里**，保证 "写了数据库就一定发了事件"。详见 M08。

#### 用法 3：Read Model / 物化视图

新服务从老 DB 的 CDC 流构建自己的"只读副本"：

```
老 DB (orders 表)
   │
   │ CDC
   ▼
Kafka (db.orders)
   │
   ▼
新订单服务（消费事件，维护自己的本地 orders 表）
```

新服务有自己的数据库 schema，但内容由老 DB 通过 CDC 同步——逐步替换老的读路径。

### 4.4 CDC 的常见坑

| 坑 | 说明 | 对策 |
|---|---|---|
| **binlog 配置** | 必须 ROW format | 改 my.cnf: `binlog_format=ROW` |
| **大事务** | 一个事务几十万行，CDC 卡死 | 分批操作，避免巨型事务 |
| **schema 变更** | DDL 变更要 Debezium 也跟 | 用 schema registry 管理 |
| **延迟** | CDC 有 100ms-数秒延迟 | 接受最终一致，不要做强一致 |
| **数据回放** | 历史数据初始化 | Debezium snapshot 功能 |
| **数据丢失** | Kafka 满了或 Connect 挂了 | 监控 lag，告警 |

## 第五章：第一个要拆的服务怎么选

### 5.1 第一刀不能选错——成本与收益的平衡

第一个拆分的服务**几乎决定了整个迁移的成败**。它要：

- 拆出来能验证整套基础设施（CI/CD、监控、网关、服务注册）
- 团队能积累经验和信心
- 失败时不会重伤业务

### 5.2 4 个判断维度

#### 维度 1：变更频率高

变更频率高 = 拆出来收益大（解开发布耦合）。

```
SELECT module, count(*) as commits
FROM git_commits
WHERE date > '2024-01-01'
GROUP BY module
ORDER BY commits DESC;

-- 输出
-- products       1532   ← 候选
-- orders          876   
-- payments        421
-- shipping        128
-- admin            89
```

#### 维度 2：业务边界清晰

DDD 分析过的限界上下文里**边界最清晰** 的优先：

- 输入输出明确
- 与其他模块依赖少
- 通用语言独立

例：通知模块（输入：事件、输出：发送）几乎和其他模块解耦。

#### 维度 3：性能瓶颈点

某个模块 CPU/内存/DB 占比远高于其他——拆出去单独扩容。

```
监控指标：
  推荐服务 CPU: 45%
  其他所有模块 CPU 总和: 30%
  → 推荐模块是性能瓶颈，拆出去能独立扩
```

#### 维度 4：团队意愿与能力

- 有团队主动 own 这个模块
- 团队有 DevOps 能力
- 团队接受加班和试错

**没有 own 的服务=没人负责**，拆出来也是僵尸服务。

### 5.3 推荐的"第一刀" 候选

按经验，以下模块是最常见的 "first slice"：

| 候选 | 原因 |
|---|---|
| **通知中心**（短信/邮件/推送） | 边界清晰、与业务弱耦合、失败影响小 |
| **文件存储 / OSS** | 边界清晰、可独立扩展 |
| **报表分析** | 异步、对实时性要求低、容错高 |
| **搜索** | 与主业务异步、独立扩展、可用 ES |
| **认证 / SSO** | 通用子域，可用 Keycloak 直接换 |
| **风控 / 反欺诈** | 独立模型、对接外部系统多 |

### 5.4 不要从这些模块开始

| 反例 | 原因 |
|---|---|
| **订单 / 支付** | 核心业务，故障影响巨大 |
| **库存** | 强一致性要求高 |
| **核心数据流（如交易主链）** | 跨服务调用必然变多，风险大 |

## 第六章：ACL（Anti-Corruption Layer）保护新服务

### 6.1 ACL 的核心价值

拆出新服务时，最大的风险不是"功能错"——而是**老系统的烂模型污染新服务**。

老单体里可能有：

- 字段名乱七八糟（`status1`, `status2`, `flag`, `is_x_y_z`）
- 枚举值混乱（"1=有效，2=无效，3=待定，9=异常，0=未知"）
- 业务规则散落（A 表的字段含义还要查 B 表的 flag）
- 历史 hack（某老板要的特殊逻辑，写死在代码里）

如果新服务直接接老 API / 老表，这些"复杂度" 会全部被搬到新服务里——新服务从第一天起就是污染的。

**ACL 就是用一层翻译挡住这些污染**：

```
新服务（干净的领域模型）
      │
      │  ↕  调用 ACL
      ▼
ACL 层（翻译 + 过滤）
      │
      │  ↕  调用老 API / 老 DB
      ▼
老单体
```

### 6.2 ACL 实操

```java
// 老系统的 user 数据（污染源）
class LegacyUser {
    String userId;           // "U_00000042"，特殊前缀
    String userType;         // "1"/"2"/"3"/"9"，含义要查文档
    String statusFlag;       // "Y"/"N"/"P"，老板钦定
    String extraJson;        // 一个塞了 30 个字段的 JSON
    Date createTime;         // 时区？据说是 UTC+8 但有些是 UTC
    // ... 还有 50 个奇怪字段
}

// 新服务的领域模型（干净）
class User {
    UserId id;               // 强类型 ID
    UserStatus status;       // enum: ACTIVE/INACTIVE/PENDING
    Instant createdAt;       // 标准化时间
}

// ACL 翻译层
class UserLegacyAcl {
    User translate(LegacyUser legacy) {
        return new User(
            parseUserId(legacy.userId),         // 去掉前缀
            translateStatus(legacy.statusFlag), // Y→ACTIVE, N→INACTIVE...
            normalizeTime(legacy.createTime)    // 强制 UTC
        );
        // userType 直接 drop（新模型不需要）
        // extraJson 按需提取
    }
}
```

### 6.3 ACL 的部署位置

ACL 可以放在几个不同位置：

- **新服务内部** 一个 acl 包/模块：简单，但污染了新代码库
- **独立的 ACL 服务**：彻底隔离，但多一跳网络
- **API 网关插件**：在网关层翻译，所有下游受益

我的推荐：**ACL 作为新服务的独立模块**——既不污染领域代码，也不增加部署复杂度。

### 6.4 ACL 何时拆除

ACL 不是永久的——它的目的是"在老系统还在时保护新服务"。当：

- 老系统下线
- 老 API 全部由新服务替代
- 没有其他下游依赖老格式

就可以删 ACL。中间一段时间 ACL 内部代码会越来越简单，最终归零。

## 第七章：12 个月迁移路线图模板

下面是一份适合 50-100 人团队、单体规模 50 万-100 万行代码的标准 12 个月路线图。

### 7.1 路线图总览

```
M01-M02  准备阶段：组织、平台、培训
M03      启动阶段：第一个服务（通知/搜索之类的"小试牛刀"）
M04-M06  扩展阶段：支撑域服务（认证、文件、报表）
M07-M09  攻坚阶段：核心域服务之一（商品 / 订单 / 库存 取一个）
M10-M11  攻坚阶段：核心域服务之二
M12      收尾阶段：剩余清理、文档、回顾
```

### 7.2 详细月度计划

#### M01-M02 准备阶段（2 个月）

**组织准备**：

- 任命迁移负责人（架构师 + Tech Lead，组队 + 全职）
- 各业务团队任命迁移 owner
- 建立 weekly 同步会议

**平台准备**：

- K8s 集群上线（生产 + 预发 + 测试）
- CI/CD 流水线模板
- 监控（Prometheus + Grafana）+ 日志（Loki）+ 链路（Jaeger）
- 服务网格（可选：Istio Ambient）
- 配置中心、服务注册
- 服务模板（脚手架）

**架构准备**：

- 完整 DDD 战略设计输出（参考 M02）
- 上下文映射图
- 服务拆分顺序与依赖图
- 数据库拆分方案

**培训**：

- 全员 DDD 培训 1-2 天
- 平台使用培训
- 拆分演练（用 demo 项目）

#### M03 启动阶段（1 个月）

**目标**：完整走通一个"低风险服务"。

**任务**：

- 选定首拆服务（推荐"通知中心"）
- 上 Strangler Façade（哪怕只对这一个 API 生效）
- 新服务开发完成（包含 ACL）
- 双跑期 2 周（影子流量）
- 灰度切换 100%
- 老代码退役

**验收标准**：

- 新服务 SLO 达标（99.9% 可用、p99 < 200ms）
- 监控/告警/链路全打通
- 团队对工具链熟练

#### M04-M06 扩展阶段（3 个月）

**目标**：拆 3-4 个支撑域服务。

候选：

- 认证服务（可考虑 Keycloak）
- 文件存储服务
- 报表分析服务
- 搜索服务

**任务**：

- 每月 1-2 个服务
- 巩固平台工具链
- 数据库局部拆分（这些服务的数据相对独立）

#### M07-M09 攻坚阶段一（3 个月）

**目标**：拆出一个核心域服务（推荐"商品中心"——读多写少，相对容易）。

**任务**：

- 商品上下文 + 库存上下文一起规划
- CDC 接入老 DB
- 商品读路径完全迁到新服务
- 商品写路径迁移（伴随 outbox 事件）
- 老 DB 商品表退役

**特殊关注**：

- 商品事件订阅方（订单、推荐、营销）的同步
- 商品快照机制（订单要冻结商品）

#### M10-M11 攻坚阶段二（2 个月）

**目标**：拆出订单 / 支付（最难的核心域）。

**任务**：

- Saga 编排器搭建（用 Camunda / Temporal / 自研）
- 订单状态机迁移
- 支付链路独立
- 跨服务事务用 Outbox + Saga

**重要**：这个阶段**进度可能拖延 1-3 个月**——这是正常的。订单/支付的复杂度不能压缩。

#### M12 收尾阶段（1 个月）

**任务**：

- 清理剩余的老代码
- 文档完整化（每个服务一份上下文画布 + 上下文映射图）
- 写技术 retro
- 对比拆分前后的指标（发布频率、可用性、故障数）

### 7.3 风险与缓冲

12 个月路线图**总是有 30%-50% 的偏差**——这是行业经验。给自己留缓冲：

- 关键里程碑预留 1 个月缓冲
- 每月做 retro 调整下个月计划
- 不要"为了节点而上线"——稳了再上

## 第八章：反向演进——什么时候该退一步

### 8.1 反向演进的真实性

业界有真实的反向演进案例：

| 公司 | 反向演进 | 原因 |
|---|---|---|
| **Segment** (2018) | 100+ 微服务 → 单体 | 微服务运维成本太高 |
| **InVision** | 部分微服务回单体 | 性能 + 复杂度 |
| **Istio control plane** (2020) | 多组件 → istiod 单体 | 部署运维复杂度 |
| **Amazon Prime Video** (2023) | 微服务 → 单体 | 成本降 90% |

**反向演进不是失败，是工程理性**。当数据告诉你"拆错了"，承认并改正比硬撑更负责。

### 8.2 5 个反向演进信号

#### 信号 1：服务调用 chatty

一个业务请求要调 10+ 个服务才能完成——延迟爆炸、错误率累积。

数据：

```
某 API: 调用 12 个下游服务
p99 延迟: 4500ms
错误率: 2.3%（每个下游 0.2% × 12 累加近似）
```

**对策**：合并强相关服务。

#### 信号 2：分布式事务超过 50%

业务流里"涉及跨服务事务" 的比例 > 50%——说明拆错了边界。

**对策**：把高频跨事务的服务合并。

#### 信号 3：运维成本 > 业务价值

某些服务每月运维成本（人力 + 基础设施）远超它带来的业务价值——尤其常见于"过细拆分" 的 nano-service。

**对策**：合并低价值服务。

#### 信号 4：团队 < 服务数

10 个工程师维护 30 个服务——每个服务都"半死不活"，更新缓慢、文档过时。

**对策**：合并到团队能维护的数量（一般每 1.5-2 工程师一个服务）。

#### 信号 5：性能持续退化

拆分后 p99 延迟比单体高 5-10 倍，业务方持续抱怨。

**对策**：识别热点路径合并。

### 8.3 怎么合并回去

合并是"反向绞杀者"：

```
1. 在合并目标服务里建一个 module，包含被合并服务的代码
2. 部署双跑（请求同时发两边，验证一致）
3. 灰度切换到合并版本
4. 下线原服务
5. 清理 API
```

注意：**数据库不一定要合并**——可以保留独立 DB，只合并代码。这比合数据库简单 10 倍。

## 第九章：真实案例研究

### 9.1 Amazon 的演进史

**1995-2001：单体（Obidos）**

亚马逊最早是个巨型单体（C++ 写的，代号 Obidos），随着规模增长，部署一次要协调几十个团队。

**2002：Bezos API Mandate**

Jeff Bezos 给所有工程师发邮件，5 条命令：

1. 所有团队必须通过服务接口对外暴露数据和功能
2. 团队之间必须通过这些接口通信
3. 不允许其他形式的进程间通信（不能直接读对方数据库、不能共享内存、不能"后门"）
4. 用什么技术不管
5. 所有服务接口必须从一开始就设计为可以对外（外部化）

邮件结尾还加了一句威胁：**不遵守者直接开除**。

这条 Mandate 是**业界微服务的起源之一**——它先做了组织上的强制隔离。

**2002-2010：渐进拆分**

接下来近 10 年，Amazon 把单体逐步拆成数千个微服务。期间发明了：

- AWS（最早是内部工具，后来对外）
- 两披萨团队
- "You build it, you run it"

**2023：Prime Video 反向演进**

Prime Video 的 audio/video monitoring 服务原本是 Step Functions + Lambda 微服务架构，2023 年合并回单体后**成本降 90%**。但这不是"微服务错了"——是这个特定场景下"微服务的过度使用"。

### 9.2 Netflix 的演进史

**2008 灾难性故障**

Netflix 原本是 Oracle 数据库 + 大单体，2008 年一次数据库损坏导致 3 天 DVD 邮寄业务瘫痪。这个事故触发了向微服务的转型。

**2009-2012：迁移到 AWS + 微服务**

- 用 7 年时间把数据从 Oracle 迁到 Cassandra
- 业务逻辑逐步从单体拆出，形成 500+ 微服务
- 开源 OSS：Eureka（服务发现）、Hystrix（熔断）、Ribbon（客户端 LB）、Zuul（网关）

**2015-2020：扩展与优化**

- 灰度发布工具 Spinnaker
- 混沌工程（Chaos Monkey 起源）
- 引入 Istio 和服务网格

**2020+：成熟稳定**

Netflix 现在的微服务数量稳定在 1000+，重点从"拆" 转向"治理与可观测"。

### 9.3 Uber 的演进史

**2010-2013：单体（PHP + Node.js）**

Uber 早期是 PHP 写的，调度系统是 Node.js。

**2013-2015：早期拆分**

业务爆发期，单体扛不住，开始拆分。但**早期拆得太细**——一度有 2000+ 微服务（业界最高之一）。

**2016-2018：反思与重构**

意识到过度拆分：

- 服务依赖图太复杂
- 跨服务调用延迟高
- 运维成本爆炸

Uber 提出"DOMA"（Domain-Oriented Microservice Architecture）——按领域聚合而不是按粒度拆。**类似 macroservice 思路**。

**2018+：服务数下降**

约 2200 个微服务经 DOMA 归类到约 70 个领域（domain），核心业务服务数量明显减少和合并。

**经验教训**：

> 不要追求服务数量。每个服务都要有明确 owner 和价值。

## 第十章：风险与回滚预案

### 10.1 拆分项目的 6 大风险

| 风险 | 表现 | 概率 |
|---|---|---|
| 进度延期 | 12 个月计划做 24 个月 | 高 |
| 性能退化 | p99 比单体差 3-10 倍 | 中 |
| 数据一致性问题 | 跨服务数据不一致 | 中 |
| 业务事故 | 拆分上线导致功能错误 | 中低 |
| 团队疲惫 | 工程师抱怨"做的都是基础设施" | 高 |
| 半途而废 | 拆到一半停了，落得分布式单体 | 高 |

### 10.2 回滚预案

**每次切换前都要有回滚预案。** 不是"如果失败怎么办"，是"失败时第一步做什么"。

```
回滚预案模板：

服务: 商品中心
切换日期: 2026-06-01
切换比例: 0% → 5% → 25% → 100%

回滚触发条件：
  - 新服务错误率 > 0.5%（持续 5 分钟）
  - 新服务 p99 > 300ms（持续 5 分钟）
  - 业务方报告 > 5 个客诉
  - 数据 diff 失败率 > 1%

回滚步骤：
  1. SRE 立刻在 Façade/网关把流量切回老单体（< 1 分钟）
  2. 通知业务方
  3. 暂停所有相关变更
  4. 分析根因
  5. 修复后从 0% 重新灰度

回滚后果评估：
  - 用户感知：无（流量自动切回）
  - 数据影响：检查是否有不一致需补偿
  - 时间损失：~ 1-2 周延期

负责人：
  - 切换执行：架构师 + Tech Lead
  - 回滚决策：架构师（5 分钟决策窗口）
  - 业务沟通：产品 Owner
```

### 10.3 心态调整

拆分项目**几乎一定会出问题**——准备好以下心态：

- 进度延误是常态，不要硬冲节点
- 反向演进不是失败，是修正
- 老系统的"丑陋代码" 都有它的理由，慢慢理解
- 新基础设施学习曲线陡峭，给团队时间
- 业务一定会有"为什么这件事这么慢" 的质疑——准备好数据回应

## 生产实践

### 实践 1：先做"绞杀者 Façade"，再做服务拆分

错误顺序：先把新服务做出来，再想"怎么路由"。
正确顺序：先在单体前面放反向代理，所有流量过代理；再拆服务。

理由：代理上线是低风险的，先有这个基础，后续每次切换都简单。

### 实践 2：影子流量是必经之路

不要直接灰度切流量——一定先跑影子流量 2-4 周，验证新服务的正确性和性能。

实操工具链：Envoy mirror + 自定义 diff 工具 + 监控告警。

### 实践 3：用 CDC 而不是双写

迁移期数据同步**永远用 CDC**，不要应用层双写。

理由：应用层双写有 N 个坑（应用挂了导致一边写一边没写、事务边界问题、性能开销），CDC 是从 DB 层捕获，可靠性高得多。

### 实践 4：每个新服务有"上下文画布"

服务上线时必须有：

- README 包含上下文画布（参考 M02）
- API 文档（OpenAPI/gRPC）
- Runbook（出问题怎么办）
- 依赖图
- SLO 定义

没有这些不允许上线——避免半年后"这服务谁做的？"

### 实践 5：每次拆分后做 retro

拆完一个服务，**全员 retro 1 小时**：

- 哪里超期了？为什么？
- 哪些假设错了？
- 下次怎么改进？

把经验沉淀进"迁移 playbook"。

### 实践 6：保留"撤回选项" 6 个月

新服务上线 100% 后，**老代码保留 6 个月**——保留快速回滚能力。6 个月稳定运行后再删。

### 实践 7：发布频率作为成功指标

迁移成功的最直接指标：**发布频率提升**。

- 单体时代：每周 1-2 次
- 迁移后目标：每周 5-10 次（不同服务独立频率）

如果迁移 1 年后发布频率没明显提升——拆分可能没真正解决问题。

## 陷阱清单

### 陷阱 1：大爆炸式重写

最常见也最致命的陷阱。永远渐进，永远不重写。

### 陷阱 2：拆代码不拆数据

服务拆了 10 个，但所有服务连同一个数据库——分布式单体的标准配方。

### 陷阱 3：在没有平台的情况下拆服务

K8s 没有、监控没有、CI/CD 没有，先拆 5 个服务——结果业务全瘫。**平台先行 6-12 个月**。

### 陷阱 4：拆了又不删老代码

新服务上线了，但老代码也没删——结果两份代码并行维护，bug 修一处忘一处。**老代码必须有明确退役日期**。

### 陷阱 5：忽视事件溯源 / Outbox

业务表写完就调下游 API——失败时数据已写但事件没发。**用 Outbox 保证原子性**。

### 陷阱 6：业务方不知情

技术团队闷头拆，业务方某天突然报"为什么这功能慢了"——沟通失败。**业务方必须是迁移利益相关方，每月汇报进度**。

### 陷阱 7：忽视性能退化

拆分后单次请求一定会慢——但慢多少要监控。**SLO 不能只看可用性，必须看延迟**。

### 陷阱 8：技术债越拆越多

为了赶进度，新服务里也写烂代码——"反正以后再重构"。**新服务必须比老代码质量更高，否则白拆**。

### 陷阱 9：低估文化变革

工程师习惯了"看着别人写代码"，突然要求"你 own 这个服务、自己运维、自己值班"——抵触情绪强。**文化变革要花 1-2 年**。

### 陷阱 10：忽视回滚预案

切换时只想着成功，没想失败怎么办。**每次切换前都要写回滚预案并演练**。

## 练习题

### 题 1：绞杀者模式 3 步

请列出 Strangler Fig Pattern 的 3 个步骤，并解释每步的关键产物。

**答案要点**：
- 步骤 1 建立转发层：所有流量过 Façade，路由表全部指向老单体（产物：可路由的代理）
- 步骤 2 替换逻辑：逐个 API 切到新服务，每次只拆 1-2 个（产物：渐进切换的路由表）
- 步骤 3 退役老路径：所有 API 迁移完成后删除老代码（产物：薄到零的单体）

### 题 2：第一个拆的服务

你接手一个 80 万行代码的电商单体，10 工程师，要开始拆微服务。请给出第一个拆什么的判断及理由。

**答案要点**：选支撑域且边界清晰的服务，如通知中心、文件存储、搜索。理由：边界清晰、与主业务弱耦合、失败影响小、能验证整个工具链。不要选订单/支付/库存这类核心域。

### 题 3：影子流量

什么是影子流量？它解决什么问题？请描述用 Envoy 配置一个影子流量的关键配置。

**答案要点**：影子流量 = 把请求复制一份发到新服务但丢弃响应；解决"新服务正确性验证 + 真实流量压测"。Envoy 配置：在 route 里加 `request_mirror_policies` 指定 mirror cluster 和 fraction。

### 题 4：CDC 与双写对比

迁移期需要保持新老 DB 同步，应用层双写和 CDC（Debezium）哪个更好？为什么？

**答案要点**：CDC 更好。原因：（1）应用层双写有事务边界问题（业务事务和双写不在同一事务）；（2）双写有性能开销；（3）CDC 从 binlog 捕获，可靠性高；（4）CDC 不侵入业务代码。双写适用场景几乎只有"完全无法接受异步延迟" 的极端情况。

### 题 5：数据库拆分难点

老单体的 `orders` 和 `users` 表有外键 + JOIN。拆分时怎么处理？请给出 3 个候选方案。

**答案要点**：
- 方案 1：删外键 + API 调用聚合（应用层 join）
- 方案 2：删外键 + 冗余字段（订单存 user_name 快照）
- 方案 3：CQRS 物化视图（订单服务消费 user 事件维护本地副本）

### 题 6：反向演进信号

列出至少 3 个"应该把微服务合并回去" 的信号。

**答案要点**：
- 服务调用过 chatty（一个业务调 10+ 服务）
- 分布式事务占比超 50%
- 运维成本 > 业务价值
- 团队规模 < 服务数 × 1.5
- 性能持续退化无法接受

### 题 7：迁移路线图

设计一个 12 个月的迁移路线图，假设 50 工程师的电商团队。请列出关键阶段和里程碑。

**答案要点**：
- M01-M02 准备（组织、平台、培训、DDD 设计）
- M03 启动（第一个低风险服务）
- M04-M06 支撑域服务（认证、文件、报表）
- M07-M09 核心域之一（商品 + 库存）
- M10-M11 核心域之二（订单 + 支付，含 Saga）
- M12 收尾（清理、文档、retro）

### 题 8：回滚预案

某团队明天要把订单服务从老单体切到新服务（5% 灰度）。请帮他设计完整回滚预案。

**答案要点**：
- 回滚触发条件（错误率/延迟/客诉/diff 失败率阈值）
- 回滚步骤（5 分钟内切回老单体）
- 数据一致性检查方案
- 业务沟通分工
- 决策人与决策窗口（5 分钟决策）
