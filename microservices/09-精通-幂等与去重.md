## 引言：为什么"幂等"是分布式系统的底层公理

在单机的世界里，一次 SQL `UPDATE accounts SET balance = balance - 100 WHERE id = 1` 要么成功要么失败，几乎不存在"既不是成功也不是失败"的中间态。但是在跨进程、跨网络、跨服务、跨消息中间件的分布式系统里，"我以为我已经处理了"和"对方以为我没处理"会同时存在——这就是著名的 **两将军问题** 的工程化版本：**网络无法被信任**。

而**幂等**（Idempotency）就是对这个不可信网络的工程化回答：**无论一个操作被执行一次还是一万次，业务结果都和"执行一次"完全相同**。

学完这一章你应能回答：

- 什么是幂等？数学定义和业务定义有什么区别？
- `PUT /users/1` 一定是幂等的吗？什么情况下它不是？
- 网络抖动、客户端重试、消息中间件 At-Least-Once 投递……怎么让"重试"安全？
- 消费者侧拿到重复消息怎么办？Inbox 模式怎么和 Outbox 模式配对？
- Stripe / AWS / GitHub 是怎么实现 `Idempotency-Key` 头的？
- 幂等 key 存哪里？Redis 还是 DB？要不要 TTL？多久过期？
- 状态机 + CAS 为什么是幂等的"自然实现"？
- 在 gRPC / Kafka / HTTP 中怎么跨服务传递幂等上下文？

本章会用 5 种实现模式 + 1 个完整的支付服务案例，把幂等从"概念"变成"工程肌肉记忆"。

## 第一章：幂等的精确定义

### 1.1 数学视角

在数学上，函数 `f` 是**幂等的（idempotent）**当且仅当：

```
f(f(x)) = f(x)        对一切 x 成立
```

也就是说，把 `f` 的结果再喂给 `f` 一次，结果不变。例如：

- `abs(abs(x)) = abs(x)` —— 取绝对值是幂等的
- `max(max(x, y), max(x, y)) = max(x, y)` —— max 是幂等的
- `f(x) = x + 1` —— 不是幂等的（每次加 1）

### 1.2 业务视角

在工程上幂等的定义稍宽：**重复调用 `n` 次（n >= 1）和调用 1 次产生相同的业务可见结果**。

| 视角 | 关注点 |
|---|---|
| 数学幂等 | 函数输入输出严格相等 |
| HTTP 幂等 | 重复请求服务器状态最终相同（响应体可不同） |
| 业务幂等 | 重复请求业务效果一致（余额、订单状态、库存数量都不变） |

实际工程中，我们更看重**业务幂等**：

- 同一笔支付重复提交 3 次，**用户账户只被扣一次款**
- 同一个发货请求 retry 5 次，**只发一次货**
- 同一条消息消费 100 次，**积分只发一次**

### 1.3 幂等 vs 重入 vs 并发安全

很多人把这三个概念搅在一起，必须分清：

| 概念 | 关注点 | 例子 |
|---|---|---|
| **幂等**（Idempotent） | 重复执行同一操作的结果一致 | 重试网络请求 |
| **重入**（Reentrant） | 一个线程可重复进入同一锁 | `ReentrantLock` |
| **并发安全**（Thread-safe） | 多线程同时执行不出错 | `ConcurrentHashMap` |

幂等不要求并发安全（虽然实现幂等常常需要并发安全的存储），并发安全也不蕴含幂等（一个并发安全的计数器递增显然不幂等）。

### 1.4 一个反直觉的例子

```sql
-- 操作 A：扣减库存
UPDATE inventory SET stock = stock - 1 WHERE sku_id = 'A001';
```

它**不幂等**。重试一次就再扣一次。

```sql
-- 操作 B：设置库存为指定值
UPDATE inventory SET stock = 10 WHERE sku_id = 'A001';
```

它**幂等**——但前提是中间没有其它操作改变库存。在并发场景下，这种"绝对值赋值"也可能产生业务上的不一致。

**幂等不是免费的，它需要在数据模型、API 设计、存储、协议四个层面共同配合。**

## 第二章：HTTP 方法的幂等性

HTTP 规范（RFC 9110，2022 年取代旧的 RFC 7231）对方法的幂等性有明确定义：

| 方法 | 幂等？ | 安全？（不修改状态） |
|---|---|---|
| GET | 是 | 是 |
| HEAD | 是 | 是 |
| OPTIONS | 是 | 是 |
| PUT | 是 | 否 |
| DELETE | 是 | 否 |
| POST | **否** | 否 |
| PATCH | **不强制** | 否 |

### 2.1 GET / HEAD 的幂等性

读操作天然幂等。但要小心：

- 计数类副作用（"被点赞 +1"）的 GET 实质上不是幂等的，违反 HTTP 语义
- 缓存层的副作用（命中率统计、回源标记）不算业务幂等问题

### 2.2 PUT 的幂等性

`PUT /users/1` 携带完整资源体被认为是幂等的：

```
PUT /users/1
{ "name": "Alice", "email": "a@x.com" }
```

无论调用 1 次还是 100 次，资源 `/users/1` 都是同样的状态。

**但 PUT 不一定幂等的反例：**

```
PUT /users/1
{ "name": "Alice", "version_history": APPEND("update-1") }
```

如果服务端把 `version_history` 当作追加列表（而不是覆盖），那么 PUT 就不再幂等了。**幂等是服务端语义决定的，不是方法名决定的。**

### 2.3 DELETE 的幂等性

`DELETE /orders/123` 是幂等的：

- 第一次：删除成功，返回 200
- 第二次：资源已不存在，返回 404 或 200（视实现）

虽然**响应不同**，但**服务器状态一致**（资源都不存在），所以仍然是幂等的。

但下面这种不幂等：

```
DELETE /orders/oldest    # 删除最老的订单
```

每次删除不同的资源，服务器状态每次都变。

### 2.4 POST 的非幂等性

POST 默认不幂等：

```
POST /payments
{ "amount": 100, "to": "merchant-A" }
```

重复 POST 会产生多笔支付。**这正是为什么 POST 需要 Idempotency-Key 来"伪造幂等性"。**

### 2.5 PATCH 不强制幂等

PATCH 是部分更新，其幂等性取决于 patch 语义：

```http
PATCH /counter
{ "op": "set", "value": 10 }       # 幂等
{ "op": "increment", "value": 1 }   # 不幂等
```

JSON Patch（RFC 6902）的 replace/add/remove 一般幂等，move/copy/test 也幂等；但自定义的 patch 语义就不一定了。

### 2.6 工程小结

不要**只依据 HTTP 方法判断幂等性**——必须看服务端的实际语义。在 API 设计阶段就要明确：

- 这个端点是否声明为幂等？
- 是否接受 Idempotency-Key 头？
- 幂等的窗口是多久？

## 第三章：Idempotency-Key Header（Stripe 标准）

Stripe 在 2015 年提出 `Idempotency-Key` HTTP 头，现在已经成为行业事实标准（AWS、GitHub、Square、Shopify、PayPal 都遵循类似设计）。

### 3.1 基本协议

客户端为每次"逻辑请求"生成一个唯一 key，并在请求头中携带：

```http
POST /v1/charges HTTP/1.1
Host: api.stripe.com
Idempotency-Key: a1b2c3d4-e5f6-7890-abcd-ef1234567890
Content-Type: application/json

{
  "amount": 2000,
  "currency": "usd",
  "source": "tok_visa"
}
```

服务端的处理逻辑：

1. 提取 `Idempotency-Key`
2. 在幂等存储（Redis / DB）中查找该 key
3. **如果找到**：
   - 该 key 对应的请求**已完成** → 直接返回缓存的响应
   - 该 key 对应的请求**正在处理** → 返回 409 Conflict 或者等待
4. **如果未找到**：
   - 记录 key 与当前请求的指纹（method + path + body hash）
   - 执行业务逻辑
   - 把响应缓存到幂等存储
   - 返回响应

### 3.2 请求生命周期时序图

```
Client                Server               Idempotency Store     Business Logic
  │                     │                         │                      │
  │  POST /charges      │                         │                      │
  │  Idempotency-Key:X  │                         │                      │
  ├────────────────────>│                         │                      │
  │                     │  SETNX key=X            │                      │
  │                     ├────────────────────────>│                      │
  │                     │                  ok(first time)                │
  │                     │<────────────────────────┤                      │
  │                     │                         │                      │
  │                     │  process payment                               │
  │                     ├────────────────────────────────────────────────>│
  │                     │                                       charge ok│
  │                     │<───────────────────────────────────────────────┤
  │                     │                         │                      │
  │                     │  SET key=X result=...   │                      │
  │                     ├────────────────────────>│                      │
  │                     │                         │                      │
  │   200 OK + result   │                         │                      │
  │<────────────────────┤                         │                      │
  │                     │                         │                      │
  │  (网络抖动，重试)    │                         │                      │
  │  POST /charges      │                         │                      │
  │  Idempotency-Key:X  │                         │                      │
  ├────────────────────>│                         │                      │
  │                     │  GET key=X              │                      │
  │                     ├────────────────────────>│                      │
  │                     │            found(cached result)                │
  │                     │<────────────────────────┤                      │
  │   200 OK + result   │                         │                      │
  │<────────────────────┤                         │                      │
```

### 3.3 中间态处理：In-Flight 请求

最棘手的情况是：客户端 0.5 秒后重试，但**第一次请求还在处理中**。

三种处理策略：

| 策略 | 优点 | 缺点 |
|---|---|---|
| **拒绝**（返回 409） | 实现简单 | 客户端要再重试 |
| **等待**（阻塞返回） | 客户端体验好 | 占用服务端资源 |
| **去重队列** | 集中调度，可观测 | 实现复杂 |

Stripe 的实际做法是**返回 409**，并要求客户端使用指数回退再次重试。

### 3.4 Body 指纹校验

如果客户端**用同一个 key 提交不同的 body**，服务端要返回 422，避免"用同一个 key 蒙混过关"：

```go
fingerprint := sha256(method + path + body)
stored := store.Get(idempotencyKey)
if stored != nil && stored.Fingerprint != fingerprint {
    return 422, "Idempotency-Key reused with different payload"
}
```

### 3.5 Key 的生命周期

- **生成时机**：客户端在第一次发起请求之前生成
- **复用范围**：仅在重试同一逻辑请求时使用
- **过期时间**：通常 24h（Stripe）、48h（GitHub），过期后服务端可清理
- **唯一性范围**：通常是（账户 + 端点 + key）三元组组成的命名空间

## 第四章：5 种幂等实现模式

下面是工程上最常用的 5 种模式，从简单到复杂排序。

### 4.1 模式一：唯一 ID + 数据库唯一约束

**思路**：把"幂等 key"直接落到一张业务表，用数据库唯一约束兜底。

```sql
CREATE TABLE payments (
    id           BIGSERIAL PRIMARY KEY,
    request_id   VARCHAR(64) NOT NULL,
    user_id      BIGINT NOT NULL,
    amount       NUMERIC(18, 2) NOT NULL,
    status       VARCHAR(16) NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (request_id)            -- 唯一约束
);
```

```go
func CreatePayment(ctx context.Context, req PayRequest) error {
    _, err := db.ExecContext(ctx,
        `INSERT INTO payments(request_id, user_id, amount, status)
         VALUES ($1, $2, $3, 'CREATED')`,
        req.RequestID, req.UserID, req.Amount)
    if err != nil {
        if isUniqueViolation(err) {
            // 已经创建过，直接读取已有记录返回
            return nil
        }
        return err
    }
    return nil
}
```

| 优点 | 缺点 |
|---|---|
| 实现极简，强一致 | 仅在写入瞬间生效，无法处理"业务执行中崩溃后重试" |
| 数据库自带 | 唯一约束失败也是事务回滚的成本 |
| 适合"创建型"接口 | 不适合"更新型"接口 |

### 4.2 模式二：状态机 + CAS（Compare-And-Swap）

**思路**：业务对象天然有状态，每次状态迁移用 `WHERE status = 当前状态` 守护。

```sql
-- 把订单从 CREATED 推进到 PAID
UPDATE orders
SET status = 'PAID', paid_at = now()
WHERE id = $1 AND status = 'CREATED';
```

- 影响行数 = 1：迁移成功
- 影响行数 = 0：当前状态不是 `CREATED`（可能已经是 PAID、CANCELED，等等）→ 业务上视为"已处理"

```go
func MarkPaid(ctx context.Context, orderID int64) (bool, error) {
    res, err := db.ExecContext(ctx,
        `UPDATE orders SET status='PAID', paid_at=now()
         WHERE id=$1 AND status='CREATED'`, orderID)
    if err != nil {
        return false, err
    }
    n, _ := res.RowsAffected()
    return n == 1, nil   // true=本次迁移成功, false=已经被处理过
}
```

| 优点 | 缺点 |
|---|---|
| 业务状态自带幂等语义 | 必须有明确的状态机 |
| 没有额外存储 | 状态迁移不能"重复"或"回退" |
| 与 DB 事务无缝集成 | 不能跨服务直接复用 |

### 4.3 模式三：Token 模式（前置申请 → 使用消费）

**思路**：用户先调用一次"申请 token"，再用 token 提交业务请求；服务端在消费 token 后立即作废。

```
Step 1: POST /payments/tokens          → { "token": "tk_abc123" }
Step 2: POST /payments/charge          → header: Idempotency-Token: tk_abc123
        body: { "amount": 100 }
Step 3: 重复 Step 2 → 服务端发现 token 已消费 → 返回原结果
```

```go
// Step 1: 颁发 token
token := uuid.NewString()
redis.SetEx(ctx, "token:"+token, "issued", time.Hour)
return token

// Step 2: 消费 token
res, err := redis.Eval(ctx, `
    local v = redis.call('GET', KEYS[1])
    if v == 'issued' then
        redis.call('SET', KEYS[1], ARGV[1], 'EX', 3600)
        return 1
    elseif v == nil then
        return -1   -- token 不存在
    else
        return 0    -- 已被消费
    end
`, []string{"token:" + token}, currentRequestID).Int()
```

| 优点 | 缺点 |
|---|---|
| 防御"客户端重复提交按钮" | 多了一次往返 |
| 把幂等性"前置"到客户端 | Token 管理复杂 |
| 适合表单提交、银行转账 | 不适合机器对机器调用 |

银行 / 证券类业务（如"提交转账"按钮）非常喜欢用这个模式，因为它能彻底杜绝"用户手抖双击"。

### 4.4 模式四：去重表（Dedup Table）

**思路**：在数据库或 Redis 中维护一张"已处理 key"的表，记录所有已经处理过的请求。

```sql
CREATE TABLE idempotency_records (
    key            VARCHAR(64) PRIMARY KEY,
    fingerprint    VARCHAR(64) NOT NULL,
    response_body  TEXT,
    response_code  INT,
    status         VARCHAR(16) NOT NULL,   -- IN_FLIGHT / DONE
    created_at     TIMESTAMPTZ NOT NULL,
    expires_at     TIMESTAMPTZ NOT NULL
);
CREATE INDEX ON idempotency_records (expires_at);
```

```go
func WithIdempotency(ctx context.Context, key, fingerprint string,
        do func() ([]byte, int, error)) ([]byte, int, error) {

    // 尝试插入 IN_FLIGHT
    _, err := db.ExecContext(ctx, `
        INSERT INTO idempotency_records(key, fingerprint, status, created_at, expires_at)
        VALUES ($1, $2, 'IN_FLIGHT', now(), now() + interval '24 hours')`,
        key, fingerprint)
    if err != nil {
        if isUniqueViolation(err) {
            // 已存在：检查指纹、状态
            return loadCached(ctx, key, fingerprint)
        }
        return nil, 0, err
    }

    // 首次：执行业务
    body, code, bizErr := do()

    // 写回结果
    _, _ = db.ExecContext(ctx, `
        UPDATE idempotency_records
        SET response_body=$1, response_code=$2, status='DONE'
        WHERE key=$3`, body, code, key)

    return body, code, bizErr
}
```

定期清理任务：

```sql
DELETE FROM idempotency_records WHERE expires_at < now();
```

| 优点 | 缺点 |
|---|---|
| 通用，可适配任意接口 | 多一次存储读写 |
| 可以缓存原始响应 | 需要选型存储（DB/Redis） |
| 适合 RESTful API 中间件 | 需要清理任务 |

### 4.5 模式五：业务版本号 / 乐观锁

**思路**：每次更新时携带"客户端看到的版本号"，服务端比对：

```sql
UPDATE accounts
SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 7;
```

如果客户端的 `version=7` 和数据库当前 version 一致，更新成功；否则更新失败。

```go
type AccountUpdate struct {
    ID      int64
    Delta   int64
    Version int64  // 客户端传入
}

res, _ := db.ExecContext(ctx,
    `UPDATE accounts SET balance=balance+$1, version=version+1
     WHERE id=$2 AND version=$3`,
    upd.Delta, upd.ID, upd.Version)
n, _ := res.RowsAffected()
if n == 0 {
    // 版本不匹配：要么已经被别人改了，要么重试碰到旧版本号
    return ErrVersionConflict
}
```

注意：**乐观锁本身不是幂等，它是并发控制**。但配合"客户端只有失败才重试，重试用最新版本号"的语义，可以达到幂等效果。

### 4.6 5 种模式对比

| 模式 | 强一致 | 实现复杂度 | 通用性 | 适用场景 |
|---|---|---|---|---|
| 唯一 ID + DB 约束 | 强 | 极低 | 仅创建 | 创建型接口（订单、用户） |
| 状态机 + CAS | 强 | 低 | 仅迁移 | 状态推进型接口 |
| Token | 强 | 中 | 一次性 | 表单、按钮 |
| 去重表 | 强 | 中 | 通用 | RESTful API 中间件 |
| 乐观锁 | 弱 | 低 | 通用 | 并发更新 |

实际工程中**最常组合使用**：

- API 层：去重表 / Idempotency-Key（粗粒度）
- DB 层：唯一约束 + 状态机 CAS（细粒度兜底）

## 第五章：幂等存储选型

幂等存储是"幂等机制的基础设施"——选型不好会成为系统瓶颈或单点故障。

### 5.1 三种主流选型

#### 选型 A：Redis

```go
ok, _ := redis.SetNX(ctx, "idem:"+key, "in_flight", 24*time.Hour).Result()
if !ok {
    return cachedResponse(key)
}
defer redis.Set(ctx, "idem:"+key, "done:"+result, 24*time.Hour)
```

| 优点 | 缺点 |
|---|---|
| 极快（μs 级） | 持久性弱（AOF/RDB 可能丢失 1-2s 数据） |
| 自带 TTL | 主从切换时可能丢数据 |
| 支持原子操作（SETNX） | 与业务 DB 不在一个事务里 |

#### 选型 B：业务 DB

```sql
INSERT INTO idempotency_records(key, ...) VALUES (...)
ON CONFLICT (key) DO NOTHING;
```

| 优点 | 缺点 |
|---|---|
| 与业务事务原子 | 多一次写入 |
| 100% 可靠 | 长期堆积需要清理 |
| 易于跨服务对账 | 性能不如 Redis |

#### 选型 C：应用内存（如 ConcurrentHashMap / Guava Cache）

```java
LoadingCache<String, Response> cache = CacheBuilder.newBuilder()
    .expireAfterWrite(1, TimeUnit.HOURS)
    .maximumSize(100_000)
    .build();
```

| 优点 | 缺点 |
|---|---|
| 零延迟 | **多实例不共享，幂等性失效** |
| 实现简单 | 重启即丢失 |
| 适合单机服务 | **生产严禁用于多实例** |

### 5.2 选型决策表

| 业务场景 | 推荐选型 | 理由 |
|---|---|---|
| 金融、扣款、提现 | DB 唯一约束 + 状态机 | 强一致、可对账 |
| 高 QPS RESTful API（>1k qps） | Redis + DB 兜底 | 性能 + 可靠 |
| 内部低频管理 API | 仅 DB | 简单 |
| Webhook 接收端 | DB 去重表 | 持久化、可重放 |
| 消息消费幂等 | DB Inbox 表 | 与业务事务原子 |

### 5.3 双层存储：Redis + DB

工业级方案常用**双层**：

```
请求
  │
  ├─→ 查 Redis（μs 级）→ 命中 → 直接返回
  │
  └─→ 查 DB（ms 级）→ 命中 → 回填 Redis → 返回
                  └─→ 未命中 → 执行业务 → 写 DB（事务内）→ 异步回填 Redis
```

要点：**最终一致性必须由 DB 兜底**，Redis 仅做加速。

## 第六章：幂等 key 设计

### 6.1 谁来生成 key？

| 生成方 | 优点 | 缺点 |
|---|---|---|
| 客户端 | 端到端可重试 | 客户端可能生成重复 |
| 服务端 | 集中控制 | 不能在网络失败后重试 |

**最佳实践：客户端生成，使用 UUIDv4 或 UUIDv7。**

### 6.2 key 的好结构

```
{tenant}:{endpoint}:{client_request_id}
example: tenant-1:POST/payments:a1b2c3d4-...
```

- `tenant`：多租户隔离
- `endpoint`：避免不同接口的 key 撞车
- `client_request_id`：客户端生成的 UUID

### 6.3 用什么生成 client_request_id？

| 方案 | 长度 | 唯一性 | 排序友好 |
|---|---|---|---|
| UUIDv4（随机） | 36 | 极强 | 否 |
| UUIDv7（时间序） | 36 | 强 | 是（前缀有时间） |
| Snowflake | 19 | 强 | 是 |
| 业务 ID（订单号） | 不定 | 强 | 看设计 |
| Hash(body) | 64 | 强 | 否 |

**推荐：UUIDv7**——它带时间戳前缀，便于按时间分区清理，又能保留 UUID 的全局唯一性。

```go
import "github.com/google/uuid"

id, _ := uuid.NewV7()    // UUIDv7
```

### 6.4 Hash(body) 的陷阱

有人会想"不让客户端生成 key，直接 Hash(body) 不就行了？"——这会带来两个问题：

1. **正常重复请求被错误去重**：用户连续 2 次给同一商户付 100 元（合理业务），body 相同，被去重成 1 次
2. **header / 时间相关字段**：客户端时间戳变化导致 hash 不同

**Hash(body) 只能作为"指纹校验"，不能作为唯一去重 key。**

## 第七章：幂等过期策略

幂等数据不能永久保留（会爆存储），但又不能太短（重试可能延迟到达）。

### 7.1 三种过期窗口

| 窗口 | 时长 | 场景 |
|---|---|---|
| 短期 | 1h | 实时性强的 API（搜索、下单） |
| 中期 | 24h | 标准 RESTful API（Stripe 默认） |
| 长期 | 7-30 天 | 异步业务（消息消费、对账） |
| 永久 | ∞ | 强审计场景（金融转账留痕） |

### 7.2 过期窗口的下限

幂等窗口必须 **≥ 客户端最大可能重试时长**。例如：

- 客户端最大重试间隔 10 分钟，最多重试 6 次 → 重试窗口约 1h
- 消息中间件最大重投递间隔 24h → 幂等窗口要 ≥ 24h

**经验法则：取客户端重试时长的 2-3 倍。**

### 7.3 清理策略

```sql
-- 按天分区表，删除整张分区
DROP TABLE idempotency_records_2026_05_25;
```

或者：

```sql
DELETE FROM idempotency_records
WHERE expires_at < now()
  AND created_at < now() - interval '7 days'
LIMIT 10000;
```

注意：**大表 DELETE 会锁表 / 膨胀 WAL**，分批 + 限速。

### 7.4 永久保留的特例

金融场景下，"曾经发起过的所有支付请求"需要永久留痕（审计 / 对账 / 反洗钱）。这时幂等表不能删，但可以归档：

```
idempotency_records          热数据（24h）
       │
       ├─→ archive cron       归档到冷存储（S3 / 对象存储）
       ▼
idempotency_records_archive
```

## 第八章：重试 + 幂等的协同

幂等只是"防御"，**真正决定整个系统行为的是重试策略**。

### 8.1 重试的金科玉律

1. **只有幂等的操作才能重试**
2. **指数回退（Exponential Backoff）**：1s → 2s → 4s → 8s
3. **加 jitter（抖动）**：避免重试风暴
4. **设置上限**：max retries + max elapsed time

### 8.2 Go 实现

```go
import "github.com/cenkalti/backoff/v4"

operation := func() error {
    return callRemoteService(ctx, request, idempotencyKey)
}

bo := backoff.NewExponentialBackOff()
bo.InitialInterval = 1 * time.Second
bo.MaxInterval = 30 * time.Second
bo.MaxElapsedTime = 5 * time.Minute

err := backoff.Retry(operation, backoff.WithContext(bo, ctx))
```

### 8.3 失败分类：可重试 vs 不可重试

| HTTP / 错误类型 | 可重试？ |
|---|---|
| 网络超时 / 连接错误 | 是 |
| 5xx（除 501、503） | 是 |
| 503 Service Unavailable | 是（看 Retry-After） |
| 429 Too Many Requests | 是（看 Retry-After） |
| 4xx（除 408/409/425/429） | **否**（业务错误，重试无意义） |
| 409 Conflict（in-flight） | 是（短等待后重试） |

### 8.4 重试风暴

如果一个下游服务降级，所有上游同时疯狂重试，会把它彻底打死。这就是著名的 **"重试风暴"**。

防御：

- **Jitter**：每次回退时间加随机抖动 0.5~1.5x
- **Circuit Breaker**：连续失败后快速短路
- **Token Bucket**：客户端侧限流自己的重试速率

详见 [精通限流熔断降级](./11-精通-限流熔断降级.md)。

## 第九章：异步消费幂等 —— Inbox 模式

异步消息（Kafka / RabbitMQ / Pulsar）几乎都是 **At-Least-Once**（至少一次）投递，意味着同一条消息**可能被消费多次**。消费端必须幂等。

### 9.1 Inbox 模式

Inbox 是 [Outbox 模式](./08-精通-分布式事务.md) 的对称设计：

```
                                            消费端
                                              │
消息中间件 ─→ Consumer ─→ INSERT INTO inbox  │
                                              ├─→ 是否已存在？
                                              │      │
                                              │   存在 → 跳过
                                              │      │
                                              │   不存在 → 业务处理 + 标记
                                              ▼
                                          业务表
```

### 9.2 表结构

```sql
CREATE TABLE inbox (
    message_id    VARCHAR(64) PRIMARY KEY,
    topic         VARCHAR(64) NOT NULL,
    payload       JSONB,
    received_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    processed_at  TIMESTAMPTZ
);
```

### 9.3 消费逻辑（事务内）

```go
func ConsumeMessage(ctx context.Context, msg Message) error {
    tx, _ := db.BeginTx(ctx, nil)
    defer tx.Rollback()

    // 1. 尝试 INSERT INBOX，唯一约束兜底
    _, err := tx.ExecContext(ctx,
        `INSERT INTO inbox(message_id, topic, payload) VALUES ($1, $2, $3)`,
        msg.ID, msg.Topic, msg.Payload)
    if err != nil {
        if isUniqueViolation(err) {
            // 已处理过，commit 后 ack
            tx.Commit()
            return nil
        }
        return err
    }

    // 2. 在同一事务中处理业务
    if err := handleBusiness(ctx, tx, msg); err != nil {
        return err  // rollback，等下次重投递
    }

    // 3. 标记完成
    _, _ = tx.ExecContext(ctx,
        `UPDATE inbox SET processed_at=now() WHERE message_id=$1`, msg.ID)

    return tx.Commit()
}
```

要点：

- **业务表 + inbox 表必须在同一个 DB 事务内**（否则会失去原子性）
- 唯一约束失败 = 已处理，直接 ack 消息
- 失败则 rollback，消息会被重投递

### 9.4 与 Outbox 的配对

完整链路：

```
Service A                Message Bus            Service B
  │                          │                     │
  │ tx { business; outbox }  │                     │
  ├──────────────┐           │                     │
  │              │           │                     │
  │              ▼           │                     │
  │           outbox table   │                     │
  │                          │                     │
  │  CDC / poller            │                     │
  ├─────────────────────────>│                     │
  │                          │                     │
  │                          ├────────────────────>│
  │                          │     deliver         │
  │                          │  (At-Least-Once)    │
  │                          │                     │
  │                          │                     │ tx { inbox; business }
  │                          │                     ├──────────────┐
  │                          │                     │              ▼
  │                          │                     │           inbox table
  │                          │      ack            │
  │                          │<────────────────────┤
```

详见 [精通分布式事务 - Outbox 章节](./08-精通-分布式事务.md)。

### 9.5 Inbox 的清理

Inbox 表会无限增长，需要定期清理 / 归档：

```sql
DELETE FROM inbox WHERE received_at < now() - interval '30 days';
```

清理窗口必须 **≥ 消息中间件的最大重投递时间**。

## 第十章：跨服务幂等传递

在微服务调用链上，幂等 key 通常需要**端到端**透传，否则中间某一跳的重试就失去保护。

### 10.1 HTTP Header

```http
POST /v1/orders
X-Idempotency-Key: req-2026-05-28-abc123
```

中间件/网关要把这个 header 透传给下游：

```go
// Gin 中间件
func IdempotencyMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        key := c.GetHeader("X-Idempotency-Key")
        if key == "" {
            key = uuid.NewString()  // 兜底自动生成
        }
        c.Set("idempotency_key", key)
        c.Request.Header.Set("X-Idempotency-Key", key)  // 透传
        c.Next()
    }
}
```

### 10.2 gRPC Metadata

```go
import "google.golang.org/grpc/metadata"

md := metadata.New(map[string]string{
    "idempotency-key": "req-abc-123",
})
ctx := metadata.NewOutgoingContext(ctx, md)
resp, err := client.CreateOrder(ctx, req)
```

服务端读取：

```go
md, _ := metadata.FromIncomingContext(ctx)
keys := md.Get("idempotency-key")
```

### 10.3 消息 Header

Kafka / Pulsar 都支持消息头：

```go
msg := &sarama.ProducerMessage{
    Topic: "orders",
    Value: sarama.ByteEncoder(payload),
    Headers: []sarama.RecordHeader{
        {Key: []byte("idempotency-key"), Value: []byte(idemKey)},
        {Key: []byte("trace-id"), Value: []byte(traceID)},
    },
}
```

消费端：

```go
for _, h := range msg.Headers {
    if string(h.Key) == "idempotency-key" {
        idemKey = string(h.Value)
    }
}
```

### 10.4 透传链路图

```
Client ─[X-Idempotency-Key]─→ Gateway
                                  │ (透传)
                                  ▼
                              Order Service
                                  │ (透传 gRPC metadata)
                                  ▼
                            Payment Service
                                  │ (透传 Kafka header)
                                  ▼
                            Notification Service
```

任意一跳网络抖动 → 重试 → 因为 key 不变 → 全链路幂等。

## 第十一章：完整案例 —— 支付服务幂等设计

下面用一个**支付服务**的端到端例子，把前面所有模式串起来。

### 11.1 业务背景

商户调用支付服务发起代收款：

```
商户 ─→ 支付服务 ─→ 银行接口
                  ↓
              账户服务（扣减余额）
                  ↓
              对账服务（异步流水）
```

要求：

- 商户网络抖动重试不会重复扣款
- 银行接口超时重试安全
- 账户服务挂了不丢账
- 对账服务可以从消息流重建状态

### 11.2 表结构

```sql
-- 幂等表
CREATE TABLE payment_idempotency (
    request_id   VARCHAR(64) PRIMARY KEY,        -- 商户提交的幂等 key
    merchant_id  BIGINT NOT NULL,
    fingerprint  VARCHAR(64) NOT NULL,
    payment_id   BIGINT,                          -- 关联支付单
    status       VARCHAR(16) NOT NULL,            -- IN_FLIGHT / DONE / FAILED
    result       JSONB,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at   TIMESTAMPTZ NOT NULL DEFAULT now() + interval '7 days'
);

-- 支付单
CREATE TABLE payments (
    id            BIGSERIAL PRIMARY KEY,
    merchant_id   BIGINT NOT NULL,
    user_id       BIGINT NOT NULL,
    amount        NUMERIC(18, 2) NOT NULL,
    status        VARCHAR(16) NOT NULL,           -- CREATED / SUCCESS / FAILED
    bank_trace_id VARCHAR(64),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (merchant_id, request_id)
);

-- Outbox 表（用于发出"支付完成"事件）
CREATE TABLE outbox (
    id           BIGSERIAL PRIMARY KEY,
    aggregate_id BIGINT NOT NULL,
    event_type   VARCHAR(64) NOT NULL,
    payload      JSONB NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at TIMESTAMPTZ
);

-- Inbox 表（用于消费"账户扣款完成"事件）
CREATE TABLE inbox (
    message_id   VARCHAR(64) PRIMARY KEY,
    topic        VARCHAR(64) NOT NULL,
    received_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    processed_at TIMESTAMPTZ
);
```

### 11.3 创建支付的服务代码（Go）

```go
func (s *PaymentService) CreatePayment(ctx context.Context, req PayRequest) (*PayResult, error) {
    fingerprint := hashRequest(req)

    tx, _ := s.db.BeginTx(ctx, nil)
    defer tx.Rollback()

    // Step 1: 尝试占位幂等记录
    _, err := tx.ExecContext(ctx, `
        INSERT INTO payment_idempotency(request_id, merchant_id, fingerprint, status)
        VALUES ($1, $2, $3, 'IN_FLIGHT')`,
        req.RequestID, req.MerchantID, fingerprint)
    if err != nil {
        if isUniqueViolation(err) {
            tx.Rollback()
            return s.handleDuplicate(ctx, req, fingerprint)
        }
        return nil, err
    }

    // Step 2: 创建支付单（状态 CREATED）
    var paymentID int64
    err = tx.QueryRowContext(ctx, `
        INSERT INTO payments(merchant_id, user_id, amount, status)
        VALUES ($1, $2, $3, 'CREATED')
        RETURNING id`,
        req.MerchantID, req.UserID, req.Amount).Scan(&paymentID)
    if err != nil {
        return nil, err
    }

    // Step 3: 关联 paymentID 到幂等记录
    _, err = tx.ExecContext(ctx, `
        UPDATE payment_idempotency SET payment_id=$1 WHERE request_id=$2`,
        paymentID, req.RequestID)
    if err != nil {
        return nil, err
    }

    // Step 4: 同事务写 outbox（"PaymentCreated" 事件）
    _, err = tx.ExecContext(ctx, `
        INSERT INTO outbox(aggregate_id, event_type, payload)
        VALUES ($1, 'PaymentCreated', $2)`,
        paymentID, mustJSON(req))
    if err != nil {
        return nil, err
    }

    if err := tx.Commit(); err != nil {
        return nil, err
    }

    // Step 5: 异步调用银行接口（带幂等）
    go s.callBank(ctx, paymentID, req)

    return &PayResult{PaymentID: paymentID, Status: "PROCESSING"}, nil
}

func (s *PaymentService) handleDuplicate(ctx context.Context,
        req PayRequest, fingerprint string) (*PayResult, error) {

    var stored struct {
        Fingerprint string
        Status      string
        Result      []byte
    }
    err := s.db.QueryRowContext(ctx, `
        SELECT fingerprint, status, result FROM payment_idempotency
        WHERE request_id=$1`, req.RequestID).Scan(
            &stored.Fingerprint, &stored.Status, &stored.Result)
    if err != nil {
        return nil, err
    }

    if stored.Fingerprint != fingerprint {
        return nil, ErrIdempotencyKeyConflict
    }
    if stored.Status == "IN_FLIGHT" {
        return nil, ErrInFlight   // 客户端短等待后重试
    }
    var r PayResult
    _ = json.Unmarshal(stored.Result, &r)
    return &r, nil
}
```

### 11.4 调用银行接口（外部幂等）

```go
func (s *PaymentService) callBank(ctx context.Context, paymentID int64, req PayRequest) {
    // 用支付单 ID 作为银行接口的 Idempotency-Key
    bankKey := fmt.Sprintf("pay-%d", paymentID)

    bo := backoff.NewExponentialBackOff()
    bo.MaxElapsedTime = 5 * time.Minute

    err := backoff.Retry(func() error {
        return s.bankClient.Charge(ctx, BankRequest{
            IdempotencyKey: bankKey,
            Amount:         req.Amount,
            UserID:         req.UserID,
        })
    }, backoff.WithContext(bo, ctx))

    // 推进状态机
    if err == nil {
        _, _ = s.db.ExecContext(ctx, `
            UPDATE payments SET status='SUCCESS', updated_at=now()
            WHERE id=$1 AND status='CREATED'`, paymentID)
    } else {
        _, _ = s.db.ExecContext(ctx, `
            UPDATE payments SET status='FAILED', updated_at=now()
            WHERE id=$1 AND status='CREATED'`, paymentID)
    }
}
```

| PayService 进程崩溃 | outbox 表事件仍在，CDC 重新推送 |

## 第十二章：生产实践

### 12.1 一定要做的

- 所有"创建型"接口都强制要求 `Idempotency-Key`，缺失则返回 400
- 幂等 key 至少 16 字符的可识别熵
- 幂等表必须有 TTL / 归档策略
- 幂等记录与业务表必须在同一事务（或者用 outbox + 异步对账）
- 任何"重试"的代码路径，都要在 PR review 时检查"对端幂等性是否就绪"

### 12.2 一定要监控的

| 指标 | 含义 |
|---|---|
| `idempotency_key_hit_rate` | 命中率（重试占比） |
| `idempotency_in_flight_count` | 当前 in-flight 请求数 |
| `idempotency_key_collision` | 同 key 不同 fingerprint（攻击 / bug） |
| `inbox_lag_seconds` | inbox 处理延迟 |
| `outbox_publish_lag` | outbox 发布延迟 |

### 12.3 一定要测试的

- 单元测试：相同 key 重试 100 次结果一致
- 集成测试：注入网络抖动 / 消息重投
- 压测：幂等存储是否成为热点
- 混沌测试：随机 kill 服务进程

## 第十三章：陷阱清单

| 序号 | 陷阱 | 修复 |
|---|---|---|
| 1 | "PUT 一定幂等"的误信 | 仔细审视服务端语义，PUT 也可能不幂等 |
| 2 | Hash(body) 当 key | 改用客户端 UUIDv7 |
| 3 | 幂等表与业务表跨库 | 改用同库同事务 |
| 4 | Redis 当唯一幂等存储 | 双层：Redis 加速 + DB 兜底 |
| 5 | 幂等 key 无 TTL，永久膨胀 | 加 TTL + 分区归档 |
| 6 | 用 ConcurrentHashMap 做幂等（多实例失效） | 改用分布式存储 |
| 7 | 状态机 UPDATE 不加 WHERE status | 加 CAS 守护 |
| 8 | Inbox / Outbox 跨事务 | 必须同一 DB 事务 |
| 9 | 失败的请求也缓存为成功 | 区分 IN_FLIGHT / DONE / FAILED |
| 10 | 客户端重试间隔无 jitter | 加 0.5x-1.5x 随机抖动 |
| 11 | 没有"已处理但响应丢失"的兜底（要重发 ack） | 幂等记录中保存原响应 |
| 12 | 幂等 key 太短 / 容易撞车 | UUID / 至少 22 字符的 entropy |

## 第十四章：2026 现状

### 14.1 行业事实标准

- **Stripe-style `Idempotency-Key`**：几乎所有支付 / SaaS 平台都遵循
- **AWS SDK**：内置 `ClientRequestToken`（DynamoDB、SQS、Lambda）
- **GitHub API**：`Idempotency-Key` 已在 GA（2024）
- **OpenAI / Anthropic API**：`Idempotency-Key` 头已成为默认（2025 起）

### 14.2 标准化进展

`Idempotency-Key` 已进入 IETF Draft（`draft-ietf-httpapi-idempotency-key-header`），预计 2026 年成为 RFC，届时所有 HTTP API 框架都会原生支持。

### 14.3 工具生态

- **Go**：`github.com/stripe/stripe-go` 内置 Idempotency 重试；`go-resty` 支持 backoff
- **Java**：Spring Retry + Spring Cloud Stream Inbox 模块
- **Node**：`bullmq` 内置 idempotency
- **数据库**：PostgreSQL 17 增强 `MERGE`（新增 `RETURNING`、`WHEN NOT MATCHED BY SOURCE`），可用 `MERGE ... WHEN NOT MATCHED THEN DO NOTHING` 简化幂等 SQL（注：`ON CONFLICT DO NOTHING` 是 INSERT 的子句，属 PG 9.5，与 MERGE 是两套语法）
- **消息中间件**：Kafka 3.x 支持 Exactly-Once Semantics（EOS），但生产消费端仍建议自实现 Inbox（EOS 限制太多）

### 14.4 AI / Agent 系统的新挑战

LLM Agent 大量调用 tool / API，重试和并发更激烈。2026 年的一个共识是：**所有给 Agent 调用的 API 都必须设计为幂等**。Anthropic / OpenAI 在它们的工具调用规范里已经把 `Idempotency-Key` 标记为推荐参数。

## 第十五章：练习题

### 题 1（基础）：判断幂等性

下面哪些是幂等的？

```
A. UPDATE users SET name='Alice' WHERE id=1
B. UPDATE counter SET value = value + 1 WHERE id=1
C. INSERT INTO logs(msg) VALUES ('event-X')
D. DELETE FROM cart_items WHERE user_id=1
E. UPDATE accounts SET status='FROZEN' WHERE id=1 AND status='ACTIVE'
```

**答案要点**：A 幂等；B 不幂等（每次 +1）；C 不幂等（每次新行）；D 幂等（最终状态都是"该用户购物车空"）；E 幂等（CAS 守护）。

### 题 2（设计）：朋友圈点赞

设计一个"点赞接口"，要求：用户对同一帖子点赞 N 次只算一次；客户端可能重试；高 QPS。

**答案要点**：

- 数据模型：`likes(user_id, post_id, created_at)` 加 `UNIQUE(user_id, post_id)`
- 写入：`INSERT ... ON CONFLICT DO NOTHING`
- 不需要 Idempotency-Key（业务 PK 天然幂等）
- 高 QPS：Redis 写入 + 异步落库 + 定期对账

### 题 3（落地）：Webhook 接收

你的服务接收第三方 Webhook，可能被对方重投递。怎么保证幂等？

**答案要点**：

- 用 webhook 自带的 event_id 作为 inbox 表主键
- `INSERT ... ON CONFLICT DO NOTHING` + 业务处理
- 即使重投递，业务不会执行多次
- 永远先 ack（避免对方继续重投）

### 题 4（分析）：In-Flight 响应丢失

客户端发了 `Idempotency-Key=K1`，服务端处理完了，但响应在网络上丢了。客户端重试 K1，你的服务怎么处理？

**答案要点**：

- 幂等记录中应保存原响应
- 重试时直接返回缓存响应
- 关键：必须区分"in-flight"和"done"两种状态
- in-flight 返回 409 让客户端等待

### 题 5（陷阱）：Hash(body) 作为 key

某团队提议："让我们用 body 的 SHA256 作为 idempotency-key，省去客户端管理"。会出什么问题？

**答案要点**：

- 用户连续 2 次给同一商户付 100 元的合理业务被误去重
- 客户端 / 服务端 / 时间戳的细微差异导致 hash 不一致
- 攻击者可以预测 key 并提前抢占
- 正确：客户端 UUID + 服务端可选 Hash(body) 作为 fingerprint 校验

### 题 6（架构）：Saga + Inbox + Outbox 完整链路

请画出"下单 → 扣库存 → 扣余额 → 通知"的完整端到端架构，标出所有幂等点。

**答案要点**：

- API Gateway 处 Idempotency-Key 中间件
- Order Service：DB 唯一约束 + outbox
- Inventory Service：inbox + 状态机 CAS（库存扣减）
- Account Service：inbox + 唯一约束（流水表）
- Notification Service：inbox + 去重表（避免重复推送）

### 题 7（性能）：幂等表成为热点

发现幂等表的写入成为系统瓶颈。怎么优化？

**答案要点**：

- 按 `request_id` 哈希分库分表
- Redis 加速 + DB 兜底
- 高频请求走 Redis SETNX，DB 仅做异步落库
- 用 partition by hash 分散写入压力

### 题 8（实战）：消息重投递 + 客户端重试同时发生

消费端拿到一条重复消息，同时商户在重试同一 key，会有什么问题？怎么解决？

**答案要点**：

- 两者会**同时**写幂等表 / inbox 表
- DB 唯一约束兜底，一个成功，一个失败
- 失败方读取已有结果，返回幂等响应
- 注意：业务事务必须有明确的隔离级别（Read Committed 或更高）
