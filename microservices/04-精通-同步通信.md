## 引言：为什么"协议选型"是微服务架构的第一道分叉

微服务的"分布式特性"，第一现场就是**服务之间怎么说话**。把单体里一行函数调用 `userService.GetUser(id)` 变成跨进程、跨网络、跨语言、跨可用区的远程调用——通信协议是这层抽象的载体。

工程师对"协议选型"的态度通常分两个极端：

1. **不假思索全用 REST**：因为"熟悉"。结果在内部服务调用上吃 JSON 序列化和 HTTP/1.1 的双重亏，P99 莫名其妙地高。
2. **新潮全用 gRPC**：因为"高性能"。结果对外暴露的 API 调试困难、浏览器调不通、前端要额外配 gRPC-Web 代理。

更深的问题是：很多工程师把 REST / gRPC / GraphQL 当作"协议替代品"在选，**忽略了它们其实是不同抽象层级的工具**：

- REST 是**资源抽象**——"我有什么资源、你能对它做什么操作"
- gRPC 是**过程调用抽象**——"我有什么动作、参数是什么、返回什么"
- GraphQL 是**查询抽象**——"我要什么数据、不要什么、怎么聚合"

读完这一章你应该能：

- 在 REST / gRPC / GraphQL 之间为具体场景做有理有据的选型
- 解释 gRPC 4 种 RPC 模式（unary / server-stream / client-stream / bidi）各自的最佳场景
- 写一个标准的 Idempotency-Key 实现（Stripe 风格）
- 设计向后兼容的 Protobuf schema 演进策略
- 用 Apollo Router 部署一个 GraphQL Federation

## 第 1 章：同步通信的基础约束

### 1.1 同步 vs 异步的本质

**同步调用**：调用方阻塞等待被调用方返回。语义模型类似单体内函数调用——简单、直观、调用栈清晰。

**异步通信**：调用方发出消息后不等待结果。语义模型是事件流——解耦、有韧性、但调试复杂。

| 维度 | 同步 RPC | 异步消息 |
|---|---|---|
| 调用方阻塞 | ✅ | ❌ |
| 双方必须在线 | ✅ | ❌（生产者发完即返） |
| 响应可获取 | ✅ 直接拿 | 需 callback / poll |
| 错误定位 | 容易（一条调用链） | 困难（事件因果链） |
| 流量峰值削峰 | ✗ | ✅（消息队列缓冲） |

**90% 的微服务通信都是同步**——因为业务逻辑天然是"我请求你→你返回"。但同步意味着**耦合**：

- 上游必须知道下游地址（→ 服务发现 P05）
- 上游必须等待下游返回（→ 超时 / 韧性 P12）
- 上游必须信任下游可用性（→ 熔断 / 限流 P11）

### 1.2 同步通信的三个隐式约束

1. **延迟可观测**：本地 vs 跨进程 vs 跨可用区差几十到几百倍——本地 < 100ns；跨进程 ~10μs；跨主机 ~100μs；跨 AZ ~1ms；跨地域 ~50ms+
2. **网络可失败**：8 大谬论之首——"网络是可靠的"。重试、超时、熔断都是因此存在
3. **上下文必须传递**：trace_id、user_id、tenant_id、deadline、locale 在每跳调用中显式传递（→ M17 链路追踪）

## 第 2 章：REST API 深度

### 2.1 Richardson 成熟度模型（4 个级别）

| 级别 | 名称 | 特征 |
|---|---|---|
| Level 0 | "RPC over HTTP" | 单个 URL + POST，HTTP 仅作传输 |
| Level 1 | 资源 | 多个资源 URL，但仍只用 GET/POST |
| Level 2 | HTTP 动词 | 正确使用 GET/POST/PUT/DELETE/PATCH + 状态码 |
| Level 3 | HATEOAS | 响应里返回相关资源链接（self-describing） |

**生产实践**：绝大多数"REST API"实际只达到 Level 2。HATEOAS（Level 3）几乎从未被工业界采用——因为客户端通常已知 API 结构，链接发现的价值不抵成本。

### 2.2 OpenAPI 3.x 与自动化

OpenAPI（前身 Swagger）是 REST API 的描述标准：

```yaml
openapi: 3.1.0
info:
  title: Order API
  version: 1.0.0
paths:
  /orders/{id}:
    get:
      operationId: getOrder
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
      responses:
        '200':
          description: OK
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Order'
```

OpenAPI 的工程价值：

- **客户端代码生成**：用 `openapi-generator` 一键生成 Java / Go / Python / TypeScript 客户端
- **文档自动化**：Swagger UI / Redoc 直接渲染
- **mock 服务器**：Prism、wiremock 让前端不等后端
- **契约测试**：Schemathesis 用 OpenAPI 自动生成测试用例

### 2.3 REST 错误模型（RFC 7807 Problem Details）

不要返回纯字符串 error。用 RFC 7807 标准结构：

```json
{
  "type": "https://example.com/probs/out-of-credit",
  "title": "You do not have enough credit.",
  "status": 403,
  "detail": "Your current balance is 30, but that costs 50.",
  "instance": "/account/12345/transactions/abc",
  "balance": 30,
  "accounts": ["/account/12345", "/account/67890"]
}
```

`Content-Type: application/problem+json`。`type` 是错误类型的 URI（可解引用），`title` 给人看，`detail` 给开发者看，`instance` 是出错的具体资源。

### 2.4 REST 的死穴

- **多次往返**：要 100 个用户的最新订单 → 100 个 GET /orders/?user=xxx（→ 用 GraphQL 或 BFF 解决）
- **过度获取**：客户端只要 name，服务端返回 50 个字段（→ GraphQL / fieldmask）
- **N+1 问题**：列表页加载后逐条获取详情
- **版本管理乱**：URL v1/v2 / Accept header / 自定义 header 三种风格并存

## 第 3 章：gRPC 深度

### 3.1 gRPC 的本质优势

不是"性能快"那么简单。gRPC 的工程价值：

1. **强 Schema（Protobuf）**：编译期类型检查 vs JSON 运行时检查
2. **HTTP/2 多路复用**：一条 TCP 连接并发多个 RPC，避免 HTTP/1.1 队头阻塞
3. **二进制序列化**：典型场景比 JSON 小 30-50%、快 5-10 倍
4. **跨语言代码生成**：proto 文件 → 任意语言客户端，无需手写 DTO
5. **流式 RPC**：原生支持 server-stream / client-stream / bidi
6. **deadline propagation**：超时自动跨服务传递
7. **Interceptor 模型**：日志 / 监控 / auth / 限流 横切关注点

### 3.2 4 种 RPC 模式

```protobuf
service OrderService {
  // Unary：一请求一响应
  rpc GetOrder(GetOrderRequest) returns (Order);

  // Server streaming：一请求多响应（流）
  rpc StreamOrderEvents(WatchRequest) returns (stream OrderEvent);

  // Client streaming：多请求（流）一响应
  rpc BulkCreateOrders(stream CreateOrderRequest) returns (BulkCreateResponse);

  // Bidi streaming：双向流
  rpc OrderChat(stream ChatMessage) returns (stream ChatMessage);
}
```

| 模式 | 典型场景 |
|---|---|
| Unary | 99% 的业务 RPC：查询、更新、删除 |
| Server stream | 推送、订阅事件、长任务进度回报 |
| Client stream | 批量上传、流式数据采集 |
| Bidi stream | 实时通信、协作编辑、游戏状态同步 |

### 3.3 gRPC 在 Go 的最小实战

```protobuf
// order.proto
syntax = "proto3";
package order.v1;
option go_package = "example.com/api/order/v1;orderv1";

service OrderService {
  rpc GetOrder(GetOrderRequest) returns (Order);
}

message GetOrderRequest {
  string id = 1;
}

message Order {
  string id = 1;
  string user_id = 2;
  int64 amount_cents = 3;
  enum Status {
    UNKNOWN = 0;
    PENDING = 1;
    PAID = 2;
    SHIPPED = 3;
  }
  Status status = 4;
}
```

```go
// 服务端
type orderServer struct {
    orderv1.UnimplementedOrderServiceServer
}

func (s *orderServer) GetOrder(ctx context.Context, req *orderv1.GetOrderRequest) (*orderv1.Order, error) {
    if req.Id == "" {
        return nil, status.Error(codes.InvalidArgument, "id is required")
    }
    // 模拟查数据库
    return &orderv1.Order{
        Id:          req.Id,
        UserId:      "u123",
        AmountCents: 9900,
        Status:      orderv1.Order_PAID,
    }, nil
}

func main() {
    lis, _ := net.Listen("tcp", ":50051")
    srv := grpc.NewServer(
        grpc.ChainUnaryInterceptor(loggingInterceptor, recoveryInterceptor),
    )
    orderv1.RegisterOrderServiceServer(srv, &orderServer{})
    srv.Serve(lis)
}
```

```go
// 客户端
conn, _ := grpc.Dial("order:50051",
    grpc.WithTransportCredentials(insecure.NewCredentials()),
    grpc.WithDefaultCallOptions(grpc.UseCompressor(gzip.Name)),
)
defer conn.Close()

client := orderv1.NewOrderServiceClient(conn)
ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
defer cancel()

order, err := client.GetOrder(ctx, &orderv1.GetOrderRequest{Id: "o123"})
```

### 3.4 Status Code（与 HTTP 区分）

gRPC 有自己的 17 个 status code（编号 0-16），不要混淆 HTTP status：

| Code | 含义 | HTTP 类比 |
|---|---|---|
| OK | 成功 | 200 |
| InvalidArgument | 参数错 | 400 |
| NotFound | 资源不存在 | 404 |
| AlreadyExists | 资源已存在 | 409 |
| PermissionDenied | 无权 | 403 |
| Unauthenticated | 未认证 | 401 |
| ResourceExhausted | 超限 | 429 |
| FailedPrecondition | 状态不对 | 409 / 412 |
| Aborted | 并发冲突（如乐观锁失败） | 409 |
| Unavailable | 暂时不可用 | 503 |
| DeadlineExceeded | 超时 | 504 |
| Internal | 服务端 bug | 500 |
| Unimplemented | 未实现 | 501 |

### 3.5 Deadline Propagation

gRPC 的杀手特性。一旦在调用方设了 `WithTimeout`，deadline 会**自动跨进程传递**：

```
Client (deadline=500ms)
  └─→ Service A (200ms used)
       └─→ Service B (remaining 300ms automatic)
            └─→ Service C (remaining 250ms)
```

服务端 `ctx.Done()` 一旦触发，立即放弃工作。这种"端到端 deadline"是同步 RPC 链路稳定性的基石——避免了"上游已经超时返回，下游还在傻干"的资源浪费。

## 第 4 章：gRPC 周边生态

### 4.1 gRPC-Web

浏览器不能直接说 HTTP/2 二进制 gRPC（需要 trailer 等浏览器 fetch API 不支持的特性）。gRPC-Web 在浏览器 ↔ 代理之间用类 HTTP/1.1，代理 ↔ 后端走标准 gRPC。

```
Browser  --HTTP/1.1+ProtoBuf--> Envoy/grpc-web --HTTP/2 gRPC--> Backend
```

代理由 Envoy（推荐）或 grpc-web 自带的代理实现。

### 4.2 gRPC-Gateway

让一份 proto 同时暴露 gRPC 和 REST 两套 API：

```protobuf
service OrderService {
  rpc GetOrder(GetOrderRequest) returns (Order) {
    option (google.api.http) = {
      get: "/v1/orders/{id}"
    };
  }
}
```

用 `protoc-gen-grpc-gateway` 生成 REST → gRPC 转换层。**强烈推荐用于"内部 gRPC + 外部 REST"双协议场景**。

### 4.3 Connect-RPC（2022 兴起）

Buf 团队推出，让 gRPC 完全兼容浏览器（不需要 Envoy 代理）。同一份 proto 同时支持 gRPC / gRPC-Web / Connect 三种协议。Go / TypeScript 生态完善，2026 已经在大量新项目中替代 gRPC-Gateway。

## 第 5 章：GraphQL 与 Federation

### 5.1 GraphQL 解决什么

REST 的"过度获取 / 不足获取 / 多次往返"问题在 BFF 层尤其痛：

```graphql
query DashboardData {
  me {
    id
    name
    orders(last: 5) {
      id
      total
      items { name price }
    }
    notifications(unread: true) {
      id
      message
    }
  }
}
```

一个请求返回前端所需的全部数据。客户端要什么字段说什么字段，多余的字段不会被返回。

### 5.2 Federation（联邦）

单一 GraphQL Server 难以扩展到大型微服务架构（每加一个服务都要改总 schema）。**Apollo Federation** 让多个 Subgraph 合并成一个 Supergraph：

```
                    Apollo Router
                   /     |      \
              UserSvc  OrderSvc  ProductSvc
              (subgraph) (subgraph) (subgraph)
```

每个服务声明自己拥有的类型和与其他类型的关系（`@key`、`@external`、`@requires`）：

```graphql
# Order Service Subgraph
type Order @key(fields: "id") {
  id: ID!
  total: Float!
  user: User
}

extend type User @key(fields: "id") {
  id: ID! @external
  orders: [Order!]!
}
```

Router 在运行时把跨服务查询拆解执行、合并响应。

### 5.3 Apollo Router 2.x（2026）

Apollo Router 是用 Rust 重写的 Federation 网关，相比早期 Node.js 版 Gateway 性能提升 10 倍以上。2026 年它已成 BFF 层的事实标准之一，对标 REST 网关。

### 5.4 N+1 与 DataLoader

GraphQL 最常见性能陷阱。`orders { user { name } }` 100 个订单可能触发 100 次 User 查询。**DataLoader** 做请求合并 + 缓存：

```javascript
const userLoader = new DataLoader(async (ids) => {
  const users = await User.findByIds(ids);
  return ids.map(id => users.find(u => u.id === id));
});

// resolver
user: (order) => userLoader.load(order.userId);
```

100 次 `load(id)` 自动批合并成 1 次 `findByIds([...])`。

## 第 6 章：协议选型矩阵

| 场景 | 推荐协议 | 理由 |
|---|---|---|
| 外部公开 API | REST + OpenAPI | 生态成熟、浏览器友好、调试方便 |
| 浏览器/移动端 → 后端 | REST 或 GraphQL | 浏览器友好 |
| 内部服务 ↔ 内部服务 | **gRPC** | 性能、Schema、流式 |
| 前端聚合层（BFF） | GraphQL Federation | 客户端按需取数 |
| 流式数据（监控、日志） | gRPC server-stream / WebSocket | 推送语义 |
| 实时双向（聊天、游戏） | gRPC bidi / WebSocket | 双工 |
| 移动端弱网 | gRPC（HTTP/2 多路复用） | 单连接复用 |
| 公开 SDK 给第三方 | REST | 用户技术栈未知 |
| 跨语言异构服务 | gRPC（Protobuf 跨语言） | 类型一致 |
| 大数据吞吐 | gRPC stream / Kafka（异步） | 高吞吐 |

经验法则："**内部 gRPC + 外部 REST + BFF GraphQL**"是 2026 的主流组合。

## 第 7 章：Schema 兼容性与演进

### 7.1 Protobuf 兼容性规则

**安全操作**（向后向前兼容）：
- 添加新字段（用新 tag number）
- 添加新 enum 值（注意客户端要兼容 unknown）
- 删除字段时**保留 tag number**（标 `reserved`）
- 把单字段改成 `oneof` 中的一个

**危险操作**（破坏兼容）：
- 修改字段类型
- 修改字段 tag number
- 删除字段而不 reserve（后续新字段可能复用 number 造成数据错乱）
- 把 required 改 optional（proto2，proto3 无 required 概念）

```protobuf
// 演进前
message Order {
  string id = 1;
  int64 amount = 2;
  string status = 3;
}

// 演进后（安全）
message Order {
  string id = 1;
  int64 amount = 2;
  reserved 3;            // 旧 status 字段废弃，禁止复用
  reserved "status";
  OrderStatus status_v2 = 4;  // 新字段用新 tag
  string idempotency_key = 5;
}

enum OrderStatus {
  ORDER_STATUS_UNKNOWN = 0;   // 必有 0 兜底
  ORDER_STATUS_PENDING = 1;
  ORDER_STATUS_PAID = 2;
}
```

### 7.2 REST API 版本策略

3 种风格：

| 风格 | 例子 | 优劣 |
|---|---|---|
| URL 路径 | `/v1/orders` / `/v2/orders` | 直观、易调试、CDN 友好 |
| Accept Header | `Accept: application/vnd.example.v2+json` | URL 不变 / 调试不友好 |
| 自定义 Header | `X-API-Version: 2` | 简单 / 非标准 |

**推荐 URL 路径**——可读性、可缓存性、可监控性都好。

### 7.3 字段演进的实战清单

- 新字段必须可选 + 默认值兜底
- 删字段先标 deprecated 一个版本，下个版本再删
- 老客户端不认识新字段时要忽略（proto3 unknown fields 默认保留）
- enum 添加新值，老客户端要 fallback 到 UNKNOWN
- 接口删除前给所有调用方提 PR / 告警 / deadline

## 第 8 章：Idempotency-Key Header（Stripe 标准）

### 8.1 为什么需要

网络重试是同步 RPC 的常态。客户端超时后不知道服务端是否处理了——重试可能造成重复扣款、重复发货。

### 8.2 Stripe 风格实现

```
POST /v1/charges
Idempotency-Key: 8e0a2c7b-...-UUIDv4
Content-Type: application/json
```

服务端：

1. 检查 key 是否存在于幂等存储（Redis TTL=24h）
2. 不存在 → 执行业务 + 缓存"key + 响应"
3. 存在 + 业务未完成 → 返回 409 / 直接等待
4. 存在 + 业务已完成 → 直接返回缓存响应

### 8.3 最小实现（Go + Redis）

```go
func IdempotencyMiddleware(rdb *redis.Client) gin.HandlerFunc {
    return func(c *gin.Context) {
        key := c.GetHeader("Idempotency-Key")
        if key == "" {
            c.Next()
            return
        }
        cacheKey := "idem:" + key

        // 检查是否有缓存响应
        cached, err := rdb.Get(c, cacheKey).Bytes()
        if err == nil {
            var resp CachedResp
            json.Unmarshal(cached, &resp)
            c.Data(resp.Status, resp.ContentType, resp.Body)
            c.Abort()
            return
        }

        // 用 SET NX 防止并发重复执行
        locked, _ := rdb.SetNX(c, cacheKey+":lock", "1", 30*time.Second).Result()
        if !locked {
            c.JSON(409, gin.H{"error": "request in progress"})
            c.Abort()
            return
        }

        // 用 ResponseWriter 拦截写入
        bw := &bodyWriter{ResponseWriter: c.Writer}
        c.Writer = bw
        c.Next()

        // 缓存响应（24h）
        cached, _ = json.Marshal(CachedResp{
            Status:      bw.status,
            ContentType: bw.Header().Get("Content-Type"),
            Body:        bw.body.Bytes(),
        })
        rdb.Set(c, cacheKey, cached, 24*time.Hour)
        rdb.Del(c, cacheKey+":lock")
    }
}
```

详见 [M09 精通幂等与去重](./09-精通-幂等与去重.md)。

## 第 9 章：长连接、Keepalive、HTTP/2

### 9.1 短连接 vs 长连接

- HTTP/1.1 短连接：每请求一次 TCP 握手 + TLS 握手（典型 100ms+），高延迟
- HTTP/1.1 keepalive：复用 TCP，但仍有队头阻塞
- HTTP/2：单 TCP 多路复用，无队头阻塞
- gRPC（HTTP/2）：默认长连接 + keepalive ping

### 9.2 gRPC Keepalive 配置

```go
import "google.golang.org/grpc/keepalive"

server := grpc.NewServer(
    grpc.KeepaliveParams(keepalive.ServerParameters{
        Time:    30 * time.Second,  // 30s 没流量发 ping
        Timeout: 10 * time.Second,  // ping 10s 不回响应则断连
    }),
    grpc.KeepaliveEnforcementPolicy(keepalive.EnforcementPolicy{
        MinTime:             10 * time.Second,
        PermitWithoutStream: true,
    }),
)
```

经验：长连接的"死链"检测靠 keepalive ping。配置不当会出现"连接还在但请求一直 hang"。

## 第 10 章：超时、Deadline、背压

### 10.1 超时设置原则

**核心法则：下游 timeout 必须小于上游 timeout 减去预期网络开销**。

```
Client timeout = 1s
   └─→ Gateway timeout = 900ms
        └─→ Service A timeout = 800ms
             └─→ Service B timeout = 600ms
                  └─→ DB timeout = 400ms
```

留余地避免"上游超时返回，下游还在处理"。

### 10.2 Deadline Propagation 的正确实践

在 gRPC：客户端设了 deadline，服务端用 `ctx.Done()` 监听。

```go
func (s *Server) DoWork(ctx context.Context, req *Req) (*Resp, error) {
    if deadline, ok := ctx.Deadline(); ok {
        log.Printf("deadline in %v", time.Until(deadline))
    }

    select {
    case <-ctx.Done():
        return nil, ctx.Err()  // DeadlineExceeded / Canceled
    case result := <-doAsyncWork(ctx, req):
        return result, nil
    }
}
```

### 10.3 背压（Backpressure）

流式 RPC（client-stream / bidi）下，生产者可能比消费者快。gRPC HTTP/2 的 flow control 自动反压——但如果应用层 channel 不做限流，仍会内存堆积。

实战：流式接收时用 buffer chan + worker pool，buffer 满了主动减速。

## 第 11 章：性能对比基准

典型场景（小消息 / 高 QPS）：

| 协议 | 序列化 | 平均 RT | QPS（4 核） | CPU |
|---|---|---|---|---|
| REST + JSON | 200B → 200B | 0.8ms | 50k | 高 |
| gRPC + Protobuf | 200B → 80B | 0.3ms | 200k | 低 |
| GraphQL + JSON | 任意 | 1.5ms（含解析） | 20k | 中 |
| Connect + Protobuf | 200B → 80B | 0.4ms | 180k | 低 |

数据仅供参考——真实场景受序列化大小、复杂度、网络拓扑影响大。

**结论**：内部高频调用 gRPC 收益显著。外部 API 性能不是主要约束，可读性 / 兼容性更重要。

## 生产实践

1. **"内部 gRPC + 外部 REST + BFF GraphQL"** 是 2026 主流配置——三个工具各司其职
2. **proto 文件单独仓库**：所有服务依赖同一份 proto，禁止本地修改
3. **proto 演进必须 review**：删除字段、改类型属于破坏性变更，强制走 schema review 流程
4. **gRPC 默认配 keepalive ping**：避免连接"死链"
5. **deadline propagation 全链路打开**：客户端必设 timeout，服务端必查 ctx.Done()
6. **错误码标准化**：用 gRPC status code（内部）或 RFC 7807（外部 REST）
7. **Idempotency-Key 在所有写 API 强制**：客户端生成 UUID v4，服务端缓存 24h
8. **gRPC-Gateway 双协议暴露**：内部 gRPC + 自动生成 REST，开发期调试方便
9. **OpenAPI 文档自动化**：CI 校验 spec 与代码一致；自动发布 Redoc
10. **GraphQL 必配 DataLoader + 复杂度限制**：防 N+1 + 防恶意查询
11. **流式 RPC 默认不用**：除非确实需要推送或大数据传输；unary 满足 95% 场景
12. **健康检查标准化**：gRPC Health Checking Protocol（`grpc.health.v1.Health/Check`）

## 陷阱清单

1. **gRPC status code 与 HTTP status 混用** → 服务端返 HTTP 500 但 gRPC 调用方拿到 Unavailable，调试困惑
2. **proto 字段 tag number 复用** → 删除字段后没 reserve，新字段复用造成历史数据反序列化错乱
3. **enum 新增值客户端不兼容** → 老客户端拿到新值 panic；必须有 UNKNOWN=0 兜底 + 客户端 default-case 处理
4. **gRPC 客户端不复用连接** → 每次 RPC 新建 conn，连接池爆炸，性能崩
5. **不设 deadline** → 下游 hang 住，上游全 hang，雪崩
6. **timeout 设置倒挂** → 下游 timeout > 上游 timeout，上游已超时返回但下游继续工作
7. **HTTP/2 over single TCP** → 一条连接掉了所有流全断；生产至少 2-3 条连接做客户端负载均衡
8. **gRPC-Web 直接暴露给浏览器** → 浏览器 fetch API 不支持 trailer，需 Envoy / Connect 代理
9. **REST API 用 GET 提交大量数据** → URL 过长被代理截断；改 POST
10. **PUT 用了非幂等的"upsert + 自增 ID"** → 重试造成 ID 漂移
11. **GraphQL 暴露给公网无复杂度限制** → 攻击者写嵌套 100 层查询打垮服务
12. **proto3 默认值不可区分"未设置" vs "设值为零值"** → 用 wrapper 类型或 `optional`（proto3.15+）

## 练习题

1. 一个内部服务用 REST API 暴露给其他内部服务，调用频率 10 万 QPS，P99 50ms。怎么改善？

   **答案**：迁移到 gRPC。Protobuf 序列化能减 50% 体积，HTTP/2 多路复用避免连接瓶颈，典型场景 P99 可降到 5-10ms。

2. proto 文件里把字段 `optional string foo = 3` 删除了，发布后老客户端崩溃。哪里错了？

   **答案**：删除字段必须 `reserved 3; reserved "foo";` 防止 tag 3 被复用造成数据错乱。客户端是否崩溃取决于实现（默认应该兼容 unknown fields），但稳妥做法是先 deprecated 一个版本再删。

3. 设计一个跨 5 个服务的查询（用户 → 订单 → 商品 → 库存 → 物流），用什么协议组合？

   **答案**：内部全 gRPC，BFF 层用 GraphQL Federation 把 5 个服务的 schema 合并成一个 Supergraph，前端一次查询。或者写专门 BFF 服务做聚合。

4. 客户端调 gRPC server 设了 `WithTimeout(1*time.Second)`，但下游 DB 查询经常 800ms。怎么链路超时？

   **答案**：从最外层 deadline 开始扣减预算。客户端 1s → 服务 A 设 850ms → 服务 B 设 700ms → DB 500ms。每跳留 50-100ms 缓冲网络抖动。

5. 用 Idempotency-Key 实现支付接口的幂等。给出"两次相同 key 的并发请求"处理方案。

   **答案**：服务端用 Redis `SETNX` 加分布式锁。第二个请求看到 lock 存在直接返回 409 conflict 或"请重试"。详见 [P09 幂等](./09-精通-幂等与去重.md)。

6. GraphQL 暴露给浏览器，攻击者发出 100 层嵌套查询。怎么防？

   **答案**：(1) 查询复杂度分析（每个字段权重打分，超过阈值拒绝）；(2) 查询深度限制；(3) 持久化查询（Persisted Queries）—— 只允许预注册的查询；(4) 限流 + 鉴权。

7. gRPC 服务用 HTTP/2 单 TCP 连接，发现高峰期偶尔全断。可能是什么原因？

   **答案**：单连接故障导致所有 stream 中断。生产应该用 gRPC client-side load balancing（用 multiple subchannels），或者用服务网格（sidecar 自动多连接）。

8. 同一个 proto 文件，一份给内部 gRPC 用，一份给外部 REST 用。怎么做？

   **答案**：proto 里加 `google.api.http` annotation，用 grpc-gateway 自动生成 REST。一份 proto 同时暴露两个协议。
