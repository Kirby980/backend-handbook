## 引言：分布式锁是被错用最多的工具

"我需要一个分布式锁"——这句话在面试里说出来就过半数；在生产代码里看到则要警惕：

- 你确定**真的需要锁**？很多场景是"幂等"或"乐观并发"就能解决（[M09](./09-精通-幂等与去重.md)）
- 你确定锁的**正确性边界**？锁过期了但业务还在跑怎么办？
- 你听过 Redlock 大辩论吗？Antirez vs Martin Kleppmann 谁对？
- 你的锁能扛**网络分区**吗？还是只能扛"健康 Redis"？

分布式锁是分布式系统里**最容易写错的组件之一**。本章把它从需求、算法、实现、争议、替代方案讲完。读完后你应该能：

- 给一个业务场景判断"要不要用锁"或"用什么协调原语"
- 用 SET NX PX + Lua 写出**正确**的 Redis 锁（多数人写的版本是错的）
- 解释 Redlock 算法 + Martin Kleppmann 的攻击场景
- 用 etcd Lease + Watch 实现一把"正确的"分布式锁
- 用 Fencing Token 防止"持锁过期但还在执行"的脏写
- 用 etcd 或 Raft 库实现 Leader Election
- 在"定时任务多机部署"和"秒杀库存"两个真实场景里做出正确选型

## 第一章：分布式锁的核心需求

### 1.1 需求清单

任何分布式锁实现都要至少满足前三条：

| 需求 | 含义 | 决定性 |
|---|---|---|
| **互斥（Mutual Exclusion）** | 同一时刻只有一个客户端持锁 | 锁的本质 |
| **防死锁（Deadlock-Free）** | 持锁客户端崩了，锁能自动释放 | 容错必备 |
| **容错（Fault Tolerance）** | 锁服务部分节点挂了，锁仍可用 | 高可用 |
| **公平性（Fairness）** | 按申请顺序获得锁 | 多数场景不强求 |
| **可重入（Reentrancy）** | 同一客户端可以再次拿锁 | Java 习惯，分布式较少做 |
| **Fencing** | 持锁者过期后的旧请求被拒 | 强一致写场景必需 |

### 1.2 为什么"防死锁"是难点

最简单实现：SETNX（如果不存在就设置）：

```
client A: SETNX lock 1 → 成功 → 持锁
client A: 业务跑一半，崩了
锁永远留在 Redis 里 → 死锁
```

加 EXPIRE：

```
SETNX lock 1
EXPIRE lock 30
```

新问题：SETNX 和 EXPIRE **不原子**——SETNX 成功后还没来得及 EXPIRE 就崩了 → **又死锁了**。

Redis 2.6.12+ 解决：

```
SET lock <unique_value> NX PX 30000
```

一条命令搞定。但 **30 秒后业务还没跑完怎么办？**——这是后面"看门狗"要解决的问题。

### 1.3 互斥的"强度"

- **AP 锁**（如 Redis 单实例）：网络分区时可能两个客户端同时持锁
- **CP 锁**（如 etcd / ZK）：网络分区时优先保证一致性，少数派不能拿锁

**用锁前先问自己**：双重持锁会造成多大损失？

- 多扣一次款？不能容忍 → 必须 CP + Fencing
- 多发一份缓存更新？无所谓 → AP 够用

## 第二章：Redis 分布式锁的演变

### 2.1 第一代：SETNX + EXPIRE（错）

```python
if redis.setnx('lock', '1'):
    redis.expire('lock', 30)
    try:
        do_work()
    finally:
        redis.delete('lock')
```

**致命错误**：

1. SETNX 后未 EXPIRE 就崩 → 死锁
2. 业务超过 30s，锁过期，别的客户端拿到了 → A 完了 → A 还在 finally 里 delete 锁 → **删了 B 的锁**

### 2.2 第二代：SET NX PX + Token（接近对）

```python
import uuid
token = str(uuid.uuid4())

# 一条命令完成"设置 + 过期"
if redis.set('lock', token, nx=True, px=30000):
    try:
        do_work()
    finally:
        # 必须用 Lua 保证"先检查值再删除"原子
        redis.eval("""
            if redis.call('get', KEYS[1]) == ARGV[1] then
                return redis.call('del', KEYS[1])
            else
                return 0
            end
        """, 1, 'lock', token)
```

修复点：

- 用 unique token（UUID）防止"删了别人的锁"
- 用 Lua 让"先 GET 比对 + DEL"原子
- 用 SET NX PX 让"设值 + 过期"原子

**还有什么问题**：

- 业务执行超时（>30s）锁过期 → 另一个客户端拿到锁 → 两个客户端同时执行 → 互斥被破坏
- Redis 主从切换：主写入了锁但还没同步到从就挂 → 从被选主 → 别人拿到同一把锁 → 互斥被破坏

### 2.3 第三代：续期（看门狗 / Lease Renewal）

```python
def acquire_with_watchdog(key, token, ttl_ms):
    if not redis.set(key, token, nx=True, px=ttl_ms):
        return False
    # 启动后台续期线程
    stop = threading.Event()
    def watchdog():
        while not stop.is_set():
            time.sleep(ttl_ms / 3 / 1000)
            redis.eval("""
                if redis.call('get', KEYS[1]) == ARGV[1] then
                    return redis.call('pexpire', KEYS[1], ARGV[2])
                end
                return 0
            """, 1, key, token, ttl_ms)
    t = threading.Thread(target=watchdog, daemon=True)
    t.start()
    return token, stop
```

**Redisson（Java）的默认实现就是这个**——锁 TTL = 30s，每 10s 续期一次。锁拿走的客户端只要还活着，锁就一直续。

**新问题**：

- 进程假死（GC 长 stop the world / OS swap） → 续期线程也卡 → 锁过期 → 别人拿走 → 进程恢复继续执行 → **双持锁**
- 这就是 Martin Kleppmann 著名攻击场景

### 2.4 第四代：Fencing Token（正确）

见第六章。

## 第三章：Redlock 算法

### 3.1 Antirez 的设计

2014 年 Antirez（Redis 作者）提出 Redlock 解决"主从切换丢锁"：

```
有 N 个独立的 Redis master（典型 N=5）
客户端请求 quorum（N/2+1）个 master 都获取到锁
所有 master 都用 SET NX PX 同一个 token
拿到 quorum 才算"持锁成功"
```

### 3.2 算法步骤

```
1. 记录当前时间 T1
2. 顺序向 N 个 Redis master 请求 SET key token NX PX TTL
   - 每个请求有短超时（如 50ms），失败立即跳过
3. 拿到 quorum 个 master 的 OK + 总耗时 < TTL
   → 锁获取成功
   → 实际锁有效期 = TTL - (T2 - T1)
4. 否则在所有 master 上 release（delete with token check）
```

### 3.3 释放

```
向所有 N 个 master（包括没拿到的）都执行 release Lua 脚本
原因：可能某个 master 因网络原因没回但实际写入成功了
```

### 3.4 Redlock 的设计权衡

- 5 个独立 master（不是主从）→ 一个挂还有 4 个 → 容错 2 节点失效
- 不依赖 Redis 主从同步 → 避开"主写入但从没同步"问题
- 仍是 AP（强调"多数派"而非 Raft 的"提交"语义）

### 3.5 Antirez 给的注意事项

- 5 个 master 之间**时钟漂移**不能太大
- 网络分区时，少数派的客户端可能仍然认为自己持锁（但实际过期）
- 推荐使用 unique token + Lua release

## 第四章：Redlock 大辩论

### 4.1 Martin Kleppmann 2016 文章

Kleppmann（《Designing Data-Intensive Applications》作者）发文 "How to do distributed locking" 指出 Redlock 在两类场景下不安全：

#### 4.1.1 进程 Pause（GC / Swap）

```
T0: client A acquired lock (TTL=30s)
T1: client A starts work, GC pauses for 60s
T31: lock expired in Redis
T32: client B acquires the same lock
T33: client B starts work
T60: client A resumes from GC, "thinks" it still holds lock, writes data
=> A 和 B 同时写！
```

不管锁服务是 Redis / ZK / etcd / 完美的 Raft，**这个场景都存在**——因为锁服务无法感知客户端的 GC pause。

#### 4.1.2 时钟跳变

Redlock 严重依赖墙上时钟（计算 TTL）。如果某个 master 的时钟突然跳了 30s（NTP 同步、VM live migration、人为修改），就会出现：

- 锁实际刚刚过期
- 但客户端按自己时钟以为锁还有 20s
- → 双持锁

### 4.2 Antirez 的回应

Antirez 2016 回应：

- "进程 pause" 问题不是 Redlock 独有，**任何 lease-based 系统都有**——ZK / etcd / Chubby 都一样
- 时钟问题的影响"有限"，正常运维下时钟漂移 < 50ms
- Redlock 的目标是"高效互斥"，不是"100% 正确"——对正确性极致敏感的场景应该用 ZK + 真正的 fencing

### 4.3 共识

业界目前共识：

| 场景 | 推荐 |
|---|---|
| "Efficiency"（高效）锁——多人同时跑没事，只是浪费资源 | Redis 单实例 / Redlock 够用 |
| "Correctness"（正确）锁——多人同时跑会造成数据错误 | 必须 etcd / ZK + Fencing Token |

**关键洞察**：Fencing Token 是"无论用什么锁服务都应该加"的额外保护层——它防的是客户端 GC pause 这类锁服务管不到的事。

## 第五章：Fencing Token

### 5.1 概念

锁服务每次发锁时，**附带一个单调递增的 token**（fencing token）。被锁保护的资源（存储 / API）拒绝"老 token"的请求。

```
T0: client A acquires lock → token = 1
T1: A writes to storage with token=1 → OK, storage now records last_token=1
T2: A's GC pause...
T3: lock expires, client B acquires → token = 2
T4: B writes to storage with token=2 → OK, storage records last_token=2
T5: A resumes, writes with token=1 → storage sees 1 < 2 → REJECT
```

### 5.2 实现

锁服务（必须支持单调计数）：

```python
# etcd: 用 revision 作 token
resp = etcd.put(lock_key, token, lease=lease_id)
fencing_token = resp.header.revision   # etcd 全局递增 revision
```

```python
# ZK: 临时顺序节点的序号本身就是 token
node = zk.create("/locks/lock-", ephemeral=True, sequence=True)
fencing_token = int(node.split("-")[-1])
```

存储侧：

```python
def write(resource_id, data, fencing_token):
    last = db.get_last_token(resource_id) or 0
    if fencing_token < last:
        raise StaleTokenError()
    db.write(resource_id, data, last_token=fencing_token)
```

存储要在**同一事务**里检查 token + 更新 token + 写数据。

### 5.3 Redis 单机能不能做 Fencing？

Redis 没有内置单调递增。可以用 `INCR fencing_counter` 配合锁拿到 token：

```lua
-- 拿锁的同时拿 token
local ok = redis.call('SET', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2])
if ok then
    local token = redis.call('INCR', KEYS[2])
    return token
else
    return nil
end
```

但 Redis 主从切换时 token 计数器**可能丢失**或回退 → fencing 失效。这就是为什么严肃场景用 etcd / ZK 的根本原因。

### 5.4 Fencing 的成本

**资源方必须支持 token 校验**——很多场景做不到：

- 调用第三方支付 API 不能塞 token
- 写第三方数据库不能加 column
- 发邮件 API 没法校验

这种场景下：**接受"风险"+ 用幂等保护** 是更现实的选择。

## 第六章：etcd 实现分布式锁

### 6.1 etcd 锁的核心：Lease + Key

```
1. 客户端创建 Lease（TTL=30s）
2. 用 Lease 创建 key /locks/myresource，value 任意
3. 创建时用 transaction（mod_revision = 0 表示 key 不存在）
4. 成功 → 持锁
5. 后台 KeepAlive 续 lease
6. 释放 → revoke lease（key 自动消失）
```

### 6.2 Go etcd 客户端

etcd 官方提供 `concurrency` 包：

```go
import (
    "go.etcd.io/etcd/client/v3"
    "go.etcd.io/etcd/client/v3/concurrency"
)

cli, _ := clientv3.New(clientv3.Config{
    Endpoints:   []string{"etcd:2379"},
    DialTimeout: 5 * time.Second,
})
defer cli.Close()

// 创建 session（带 TTL 的 lease）
session, err := concurrency.NewSession(cli, concurrency.WithTTL(30))
if err != nil { return err }
defer session.Close()

// 创建 mutex
mutex := concurrency.NewMutex(session, "/locks/order-job")

ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
if err := mutex.Lock(ctx); err != nil {
    return err
}
defer mutex.Unlock(context.Background())

// 业务逻辑
doWork()
```

### 6.3 etcd 锁的内部实现

实际上 etcd `concurrency.Mutex` 使用的也是"临时顺序 key"：

```
/locks/order-job/{lease-id}-{revision}
```

每个客户端创建自己的临时 key，看自己的 key 是不是最小的：

- 是 → 持锁
- 否 → watch 比自己小的那个 key，等它消失

这其实是 **ZooKeeper recipe 的 etcd 版本**。

### 6.4 etcd 锁的优势

| 优势 | 解释 |
|---|---|
| **真正 CP** | 基于 Raft，多数派写入才确认 |
| **Lease 续期是内置原子** | 不依赖客户端定时器 |
| **Fencing Token 天然有** | etcd 全局 revision 就是 |
| **Watch 等待** | 没拿到锁时不需要轮询 |

### 6.5 etcd 锁的代价

- 比 Redis 慢（写入要走 Raft quorum，~5-10ms）
- 不适合极高频锁场景（每秒上万次锁竞争）

## 第七章：ZooKeeper 实现分布式锁

### 7.1 临时顺序节点 Recipe

ZK 经典实现：

```
1. 在 /locks/myresource 下创建临时顺序节点 lock-0000001
2. 列出 /locks/myresource 下所有节点，按序号排序
3. 自己是最小的 → 持锁
4. 否则 watch 紧邻的前一个节点
5. 前一个节点删除（释放 / 客户端断连） → 自己变成最小 → 持锁
```

### 7.2 Curator 库

Apache Curator 是 ZK 官方推荐的客户端库，封装了锁 recipe：

```java
CuratorFramework client = CuratorFrameworkFactory.newClient(...);
client.start();

InterProcessMutex lock = new InterProcessMutex(client, "/locks/order-job");
if (lock.acquire(5, TimeUnit.SECONDS)) {
    try {
        doWork();
    } finally {
        lock.release();
    }
}
```

### 7.3 ZK 锁的特性

| 特性 | 说明 |
|---|---|
| **公平** | 严格按申请顺序（顺序节点）|
| **CP** | ZAB 协议，多数派 |
| **临时节点** | 客户端断连自动删除 → 防死锁 |
| **Fencing Token** | 顺序节点序号天然是 |
| **可重入** | Curator 的 InterProcessMutex 支持 |

### 7.4 ZK vs etcd

| 维度 | ZooKeeper | etcd |
|---|---|---|
| 协议 | ZAB（自家） | Raft |
| 语言 | Java | Go |
| API | 树形节点 + Watch | KV + Watch + Lease |
| 性能 | 中 | 中 |
| 生态 | Hadoop / Kafka / Curator | K8s / 云原生 |
| 学习曲线 | 较陡 | 较平 |

**选型**：纯 K8s 生态用 etcd；Hadoop 生态或已有 ZK 用 ZK。功能上两者基本等价。

## 第八章：锁的粒度

### 8.1 粗粒度 vs 细粒度

```
粗：全局只有一把锁 → 互斥强 / 并发低
细：每个资源一把锁 → 并发高 / 复杂度高
```

电商库存案例：

- 粗：`SETNX global_stock_lock` → 全部商品扣减串行，性能差
- 细：`SETNX stock:{sku_id}` → 不同 SKU 并行，**热门 SKU 还是串行**
- 分段：`SETNX stock:{sku_id}:{segment}`，把单个 SKU 库存分成 N 段，每段独立锁 → 热门 SKU 也能并行

### 8.2 分段锁（Striped Lock）

Redisson、Java ConcurrentHashMap、Go sync 都有"分段"思路。分布式版本：

```go
func stockLockKey(skuId int64) string {
    segment := skuId % 16  // 16 段
    return fmt.Sprintf("stock:%d:%d", skuId, segment)
}
```

扣减时同时锁这个段的库存子记录。**总并发 = 16 倍**。

### 8.3 业务对象 vs 数据库行

- 业务对象锁：`SETNX order:create:{user_id}` → 防止用户重复下单
- 数据库行锁：`SELECT ... FOR UPDATE` → DB 原生

**永远优先考虑数据库行锁**：

- 数据库自己懂死锁检测
- 事务自动解锁
- 不需要看门狗

只有"跨数据库 + 跨服务 + 跨进程"才上分布式锁。

## 第九章：锁超时与业务执行时间不可控

### 9.1 矛盾

- 锁超时长 → 客户端崩了，等很久才释放
- 锁超时短 → 业务跑久一点就过期，双持锁

### 9.2 看门狗（Watchdog / Auto-Renewal）

Redisson 默认策略：

```
- 锁 TTL = 30s
- 每 10s 后台续期一次（lease 续）
- 客户端主动 unlock 时取消续期 + 删除锁
- 客户端崩了 → 续期停了 → 30s 后锁自动释放
```

Go etcd `concurrency.Session` 也是这个机制——它自动 KeepAlive lease。

### 9.3 看门狗的死角

- **客户端 hang**（不是崩）→ 看门狗还在跑 → 锁一直续 → 永远不释放
- 排查难度大，所以**配合业务级超时**：业务最多跑 N 分钟，强制 cancel

### 9.4 业务可中断的关键

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Minute)
defer cancel()

if err := mutex.Lock(ctx); err != nil {
    return err
}
defer mutex.Unlock(context.Background())

if err := doWork(ctx); err != nil {  // ← doWork 必须感知 ctx 取消
    return err
}
```

业务代码必须**支持 context 取消**——卡在某个不响应取消的 IO 上 = 看门狗永远跑。

## 第十章：Leader Election（选主）

### 10.1 何时需要选主

- 定时任务多机部署：只能一台跑
- 主备模式服务：主挂了备顶上
- 缓存预热任务：一台预热完所有人共享
- 数据迁移 / Schema 升级：单点执行

### 10.2 etcd Leader Election

etcd `concurrency.Election`：

```go
session, _ := concurrency.NewSession(cli, concurrency.WithTTL(15))
defer session.Close()

election := concurrency.NewElection(session, "/election/job-coordinator")

// Campaign 阻塞直到当选 leader（或被打断）
ctx, cancel := context.WithCancel(context.Background())
go func() {
    if err := election.Campaign(ctx, hostname); err != nil {
        log.Error("campaign failed", err)
    }
}()

// 同时 watch 谁是 leader
ch := election.Observe(ctx)
for resp := range ch {
    log.Info("current leader", resp.Kvs[0].Value)
}
```

机制：

- 所有候选者写同一个 election key
- 写得早的（revision 小）的当 leader
- 当前 leader 的 session 失效 → key 消失 → 下一个 revision 最小的接管

### 10.3 Raft 库直接选主

如果你的应用本身要内嵌共识，用 Raft 库：

- Go: `hashicorp/raft`、`etcd/raft`
- Java: `apache/ratis`

```go
config := raft.DefaultConfig()
config.LocalID = "node1"

raftNode, err := raft.NewRaft(config, fsm, logs, stable, snaps, transport)
// Raft 内置选主，IsLeader() 检查
if raftNode.State() == raft.Leader {
    doLeaderWork()
}
```

但这意味着你的服务自己组成集群——通常仅在"自带状态的中间件"里用。

### 10.4 简单 Lease + 心跳选主

如果不想引入 etcd / Raft：

```
1. 候选者尝试 SET leader_key node_id NX PX 30s
2. 成功 → 自己是 leader → 每 10s 续期一次
3. 续期失败（key 不存在或值变了）→ 自己不再是 leader
4. 没拿到 → 每 5s 重试一次
```

**简单但不严谨**——网络分区时可能双 leader（同 Redlock 问题）。**接受双 leader 的容忍场景**才能用。

### 10.5 选主后 graceful 切换

```go
for {
    select {
    case <-ctx.Done():
        return
    case event := <-leadershipEvent:
        if event.IsLeader {
            startLeaderTasks()
        } else {
            // 立即 cancel 当前任务，让备机接管
            stopLeaderTasks()
        }
    }
}
```

**关键**：失去 leadership 时**立即停手**，不要再写共享资源。

## 第十一章：真实案例

### 11.1 案例 1：定时任务多机部署用 etcd 选主

**业务**：每小时跑一次"过期订单清理"，服务部署 5 个实例，只能 1 个跑。

**方案 A（不推荐）**：每个实例都 try-lock，谁拿到谁跑。
- 问题：拿锁时间和定时器对不齐，可能跨小时同时多个实例都在等

**方案 B（推荐）**：etcd 选主常驻 leader，cron 触发时 leader 跑：

```go
session, _ := concurrency.NewSession(cli, concurrency.WithTTL(15))
election := concurrency.NewElection(session, "/election/order-cleaner")

go election.Campaign(ctx, hostname)

c := cron.New()
c.AddFunc("@hourly", func() {
    leader, _ := election.Leader(ctx)
    if leader != nil && string(leader.Kvs[0].Value) == hostname {
        runCleanup()
    }
})
c.Start()
```

**优势**：

- 永远只有一个实例跑
- leader 挂了，30s 内自动 failover
- 实例重启不影响（备机接管）

### 11.2 案例 2：秒杀库存扣减用 Redis 分段锁

**业务**：秒杀 10000 件商品，预估 100w QPS。

**方案 A（不推荐）**：DB 行锁。
- 问题：行锁串行，单行 QPS 几百，撑不住

**方案 B（不推荐）**：Redis SETNX `stock:{sku}` + DB 扣减。
- 问题：单 SKU 锁串行，热点 SKU 仍然瓶颈

**方案 C（推荐）**：Redis 分段预扣 + 异步落库：

```lua
-- KEYS[1] = stock_segment_key (e.g. stock:1001:5)
-- ARGV[1] = qty
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock >= tonumber(ARGV[1]) then
    redis.call('DECRBY', KEYS[1], ARGV[1])
    return 1
else
    return 0
end
```

```go
// 10000 库存分 16 段
// 用户 hash 到一个段
segment := userId % 16
key := fmt.Sprintf("stock:%d:%d", skuId, segment)
ok, _ := redis.Eval(ctx, script, []string{key}, qty).Bool()
if !ok {
    // 当前段没了，可以"借段"（向其他段问）或直接拒绝
    return ErrSoldOut
}

// 异步落库（最终一致）
mq.Publish("stock.deducted", event)
```

**关键设计**：

- **没用锁**！因为 Redis 单线程，`EVAL` 本身原子，**不需要额外锁**
- 分段把热点打散
- 写 Redis + 异步落库 → 把 DB 压力降到几乎零

这是"用幂等 + 原子操作 + 异步化"绕开分布式锁的经典案例。**很多需要锁的场景其实不需要锁**。

### 11.3 案例 3：金融扣款用 ZK + Fencing

**业务**：用户余额扣款，绝对不能多扣。

```
1. 服务 A 申请锁 /locks/user/{uid} → 拿到顺序号 token=10
2. 服务 A 调风控、调内部账务系统
3. 账务系统的扣款 API 必须传 token
4. 账务系统校验 token > last_used_token
5. 通过 → 扣款 + 记 last_used_token=10
6. 不通过 → 拒绝
```

即使服务 A GC pause 60s 锁过期，等它恢复时账务系统的 last_used_token 已经 ≥ 11 → 拒绝它的请求。

## 第十二章：替代分布式锁的思路

很多"想用锁"的场景有更好的方案：

### 12.1 乐观锁（CAS）

数据库版本号或 etcd `mod_revision`：

```sql
UPDATE account SET balance = balance - 100, version = version + 1
WHERE user_id = 123 AND version = 5
```

- 影响 0 行 → 别人改过了 → 重试或失败
- 影响 1 行 → 成功

**适用**：冲突少的场景。冲突多 → CAS 失败率高 → 性能不如悲观锁。

### 12.2 幂等键

[M09 幂等与去重](./09-精通-幂等与去重.md) 详讲。客户端带 idempotency key，服务端去重 → 不需要锁。

### 12.3 队列串行化

把"需要互斥"的操作发到一个分区队列（Kafka 按 key 分区）。同 key 进同分区 → 单消费者顺序处理 → 天然串行。

```
user_id=123 → kafka topic order partition by user_id
consumer thread #5 sequentially handles partition 5
→ 同 user 的订单天然串行处理
```

**Kafka 单分区单消费者天然就是一把锁**。

### 12.4 数据库自身的锁

`SELECT ... FOR UPDATE`、PostgreSQL Advisory Lock、MySQL `GET_LOCK()`：

```sql
-- PostgreSQL
SELECT pg_advisory_xact_lock(123);  -- 事务级锁
-- 业务逻辑
COMMIT;  -- 自动释放
```

事务结束自动释放，**永远不会忘记 unlock**。

## 生产实践

### 选型决策树

```
要互斥控制 N 个客户端吗？
├─ N=1（同进程）→ sync.Mutex
├─ N=多（同DB）→ DB 行锁 / Advisory Lock
├─ N=多（跨服务）
│   ├─ 容忍极少数双持锁 → Redis SET NX PX + Token
│   ├─ 不能容忍双持锁 → etcd Lease + Fencing Token
│   ├─ 严格公平 → ZK / etcd 顺序节点
│   └─ 选主 → etcd / ZK Election Recipe
└─ 真的需要锁吗？
    ├─ 能用幂等吗？→ M09
    ├─ 能用 CAS 吗？→ 乐观锁
    └─ 能用队列吗？→ Kafka 分区
```

### Redis 锁参数

| 参数 | 推荐 |
|---|---|
| TTL | 业务执行时间 × 3，最低 10s |
| Token | UUID 或 host+pid+nonce |
| 续期间隔 | TTL / 3 |
| 释放 | 必须用 Lua 校验 token |
| 客户端超时 | TTL × 2（等锁的最长时间） |

### etcd 锁参数

| 参数 | 推荐 |
|---|---|
| Session TTL | 15-30s |
| KeepAlive 间隔 | TTL / 3，etcd 客户端默认 |
| Lock 超时 ctx | 业务可接受的最长等锁时间 |

### 监控告警

| 指标 | 告警 |
|---|---|
| 锁等待时间 P99 | > 5s |
| 锁获取失败率 | > 5% |
| 锁持有时间 P99 | > 业务平均的 3 倍（可能卡了）|
| 续期失败次数 | > 0（看门狗失效）|
| etcd / Redis 连接失败 | 任何 |

### Idempotency First 原则

**遇到"我要加锁"先问自己**：

1. 这个操作能改成幂等吗？→ 优先
2. 能用乐观锁 CAS 吗？→ 次优
3. 能用单分区队列吗？→ 次优
4. 不得不锁了，正确性要求多高？

## 陷阱清单

1. **SETNX + EXPIRE 两条命令**：非原子，SETNX 后崩 → 死锁。永远用 `SET NX PX`。

2. **DEL 不校验 token**：可能删别人的锁。永远用 Lua。

3. **客户端时钟参与判断**：客户端按本地时钟判断"锁还有多久"，时钟跳变就乱。所有 TTL 判断交给锁服务。

4. **看门狗不感知客户端 hang**：续期线程是 daemon，业务线程卡死时它还在续。**配业务级 timeout**。

5. **锁内做长 IO**：锁 + 调用外部 API（5s）→ 锁持有 5s+，并发上不去。**锁内只做最小临界区**。

6. **Redlock 用于强一致场景**：双持锁仍可能。强一致用 etcd + Fencing。

7. **没有 Fencing**：客户端 GC pause + 锁过期 + 新持锁者 + 旧客户端恢复写 = 数据损坏。

8. **公平锁误用**：用 ZK 顺序节点 → 几万 watch → ZK 集群被打爆。公平锁不要做太多并发。

9. **etcd lease 没续**：忘了 KeepAlive，30s 后锁莫名消失。

10. **ZK 节点不是临时**：客户端崩了节点不释放 → 死锁。临时节点是 recipe 的核心。

11. **锁粒度太粗**：全局一把锁 → 整个服务串行。按业务对象分锁。

12. **解锁前 ctx 已 cancel**：`defer mutex.Unlock(ctx)` 但 ctx 已取消 → Unlock 失败 → 锁靠 TTL 等死。**Unlock 用新的 context**。

13. **重试拿锁不退避**：N 个客户端同时抢同一把锁，全部退避 0 重试 → 风暴。指数退避 + jitter。

14. **以为 Redis 主从切换不丢锁**：默认 async 复制，主写入但还没同步就挂 → 选新主 → 锁丢。要么 Redlock 要么 WAIT 命令。

15. **以为"我用了 Redisson 就稳了"**：Redisson 基于 Redis，Kleppmann 的问题仍然存在。强一致场景换 etcd。

16. **滥用分布式锁**：DB 单库本来 `SELECT FOR UPDATE` 一行解决，硬塞分布式锁 → 多了一个依赖 + 复杂度。

## 2026 现状

- **etcd** 在 K8s 生态全面替代 ZK，新项目 etcd > ZK 选型。
- **Redis 集群（Redis Cluster + Sentinel）锁**：业界仍大量使用，Redisson 在 Java 生态默认，绝大多数场景"够用"。**Redlock 在生产里实际用得不多**——5 个独立 Redis 部署成本高，多数选 Redis 主从 + 容忍极少数风险。
- **Fencing Token** 被广泛认为是"严肃锁"的必备：金融、计费、扣减库存场景必加。
- **数据库 Advisory Lock**（PostgreSQL `pg_advisory_lock`）在中小规模"轻量协调"场景兴起——不引入新组件、事务集成、自动释放，简单可靠。
- **Service Mesh + Kubernetes Lease**：K8s 自己的 Lease 对象（用于 controller-manager 选主）开放给应用使用，无需引入 etcd 客户端（间接用 K8s API）。
- **NewSQL（TiDB / CockroachDB）**：内置乐观事务 + 分布式锁，应用层不用自己实现。
- **协调原语向云服务化**：AWS DynamoDB（带条件写）、Azure CosmosDB、GCP Firestore 都内置乐观并发控制，云时代越来越多场景"不需要单独的锁服务"。
- **Kleppmann vs Antirez 辩论**逐渐共识：根据"Efficiency"或"Correctness"做选型，Fencing 是必备保护。

## 参考答案

1. **正确性论证**：伪代码——① 生成 unique token（UUID）；② `SET lock token NX PX 30000`，一条命令原子完成"不存在才设值 + 设过期"，防止 SETNX/EXPIRE 两步之间崩溃导致死锁；③ 拿到锁执行临界区；④ 释放用 Lua 原子执行"GET 比对 token 相等才 DEL"。每步必要性：NX 保证互斥；PX 防客户端崩溃后死锁；unique token 防止误删别人的锁；Lua 把"判断 + 删除"合成原子操作。若省掉 Lua 释放（直接 GET 再 DEL 两步），在 GET 返回自己 token 后、DEL 之前若本锁恰好过期被他人获取，DEL 就会删掉别人的锁，破坏互斥。

2. **Redlock GC pause 双持锁**：T0 client A 拿锁（TTL=30s）→ T1 A 开始工作随即 GC pause 60s → T31 Redis 中锁过期 → T32 client B 获取同一把锁开始写 → T60 A 从 GC 恢复，自认为仍持锁也写入，A 与 B 同时写=数据损坏。Fencing 避免：锁服务发锁时附带单调递增 token，A 得 token=1、B 得 token=2，存储记录 last_token；A 恢复后用 token=1 写，存储发现 1 < 已记录的 2 → 拒绝。Fencing 防的正是锁服务感知不到的客户端 pause。

3. **etcd Mutex 排队**：`concurrency.Mutex` 内部为每个客户端在 `/locks/{name}/` 下创建带 lease-id 的临时顺序 key（key 名含全局递增 revision），然后比较自己是否是当前最小 revision——是则持锁，否则 **watch 紧邻自己前一个（比自己小的最近一个）key**，等它消失（释放或 lease 失效）再竞争。10 个客户端同时拿锁时第 7 个 watch 的是第 6 个客户端的 key（按 revision 排序紧邻其前一个），形成有序等待链而非全部轮询，避免惊群。

4. **看门狗 vs Lease（客户端 hang 但没崩）**：两者表现相同——都会"继续续期"。Redisson 看门狗是后台 daemon 线程定时 pexpire，etcd Session 是客户端 KeepAlive 定时续 lease；客户端进程 hang（GC/swap/死循环）但进程还活着时，只要续期线程/goroutine 仍在跑，锁就一直被续、不会释放，造成"业务卡死但锁不放"。两者都不安全，必须配业务级 timeout（context 超时强制中断）。真正崩溃（进程退出）时两者都能靠 TTL 自动释放。安全性差别不大，关键防护是 Fencing Token + 业务 ctx 超时。

5. **选型实战**：(a) 凌晨数据归档 10 实例跑 1 个 → etcd/ZK 选主（Leader Election），常驻 leader，cron 触发时仅 leader 执行，挂了自动 failover；(b) 用户提现扣余额（绝不能多扣）→ Correctness 锁，etcd/ZK + Fencing Token，或直接用 DB 行锁 `SELECT FOR UPDATE` / 乐观锁 version CAS，账务侧校验 token；(c) 缓存预热（只 1 个读 DB 其他等结果）→ 单飞/选主 + 共享结果，可用 Redis SET NX PX 选出预热者其余轮询结果（Efficiency 锁，重复预热只是浪费可容忍）；(d) 全局分布式 ID 生成器 → 不用锁，用号段模式（DB 批量取段本地分配）或 Snowflake（机器位+时间戳+序号），etcd 仅用于分配 workerId。

6. **不用锁防超卖（100 件 / 100w QPS）**：用 Redis 原子操作 + 分段 + 异步落库（见案例 11.2）。① 库存预加载到 Redis，分成 N 段（如 16 段）分散热点；② 扣减用 Lua 脚本 `GET → 比较 → DECRBY`，Redis 单线程使 EVAL 天然原子，无需额外锁；③ 用户 hash 到某段扣减，段空则拒绝或借段；④ 扣减成功后发消息异步落库（最终一致），DB 压力降到近零；⑤ 售罄后前置降级直接返回。核心：原子操作 + 分段打散 + 异步化绕开锁。

7. **etcd Fencing 锁**：① 获取锁——`NewSession(WithTTL)` 创建 lease，用 `concurrency.Mutex` 或事务在锁 key 不存在时写入并绑定 lease，取 `resp.Header.Revision` 作 fencing_token（etcd 全局单调递增 revision）；② 写资源——调用资源 API/存储时携带 fencing_token；③ 校验——存储侧在同一事务内 `last = get_last_token(resource); if token < last: reject; else write + set last_token=token`。即使持锁者 pause、锁过期被他人接管，旧 token 写入会因 `token < last` 被拒。

8. **选主切换不双跑**：监听 leadership 事件（`election.Observe`），失去 leadership 时**立即 cancel 当前任务的 context 并停手**（stopLeaderTasks），不再写共享资源；当选时才 startLeaderTasks。配合：① 任务逻辑必须感知 ctx 取消、可中断；② leader session lease 失效后 key 自动消失，下一 revision 最小者接管，etcd 的 Raft 保证同一时刻只有一个 leader 视图；③ 关键写操作加 Fencing Token，防止老 leader pause 恢复后还写；④ 新 leader 接手前确认上一个任务已结束或用幂等保证重叠窗口安全。
