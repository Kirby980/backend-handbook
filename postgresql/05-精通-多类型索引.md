# 精通多类型索引：GIN / GiST / SP-GiST / BRIN / Hash / Bloom

> 关联章节：[精通 B-tree 索引](./04-精通-B-tree-索引.md)、[精通 pgvector 与向量检索](./06-精通-pgvector-与向量检索.md)、[精通 JSONB 与全文检索](./12-精通-JSONB-与全文检索.md)

## 引言：为什么 PostgreSQL 是"索引最丰富的关系库"

如果让我用一句话区分 PostgreSQL 和 MySQL/Oracle 的索引设计，那就是：**PG 把"索引"做成了一个开放协议**。

MySQL 的索引清单很短：B+ 树、全文索引、（8.0 起的）空间索引、（8.0.36 起的）向量索引。基本全是引擎内置、不可扩展的。PG 不一样——`CREATE EXTENSION btree_gin` 一行命令就让 GIN 支持普通标量；`CREATE EXTENSION pg_trgm` 让 LIKE `'%foo%'` 也能走索引；写一个新的 opclass 就能让 GiST 支持你自定义的距离函数。**PG 的索引是"协议 + 用户函数"**，B-tree 只是其中一个实现。

这章不讲 B-tree（P04 讲完了），专攻其他 5 大类 + Bloom 扩展。读完之后你应该能：

- 解释 GIN 的 `entry tree + posting tree` 双层结构以及它为什么对 JSONB / 数组 / 全文检索几乎是"必选"
- 列出 GiST 的 7 个用户函数，理解为什么 PostGIS 用 GiST 而不是 GIN
- 说出 BRIN 为什么"10GB 表索引只要几 MB"——以及在什么数据分布下它瞬间失效
- 给一张 10 亿行的日志表设计合适的索引组合
- 决定 JSONB 列上是用 `jsonb_ops` 还是 `jsonb_path_ops`
- 给一个 5 列宽表的多列 OR 等值查询设计 Bloom 索引

PG 文档对索引类型只是"罗列",这里要做的是把每种索引的内部结构、代价模型、最佳场景全部摊开。

## 第 1 章：索引家族全景与选择决策树

### 1.1 PostgreSQL 6 大内置索引类型

| 索引类型 | 默认？ | 主要用途 | 内部结构 | 是否支持范围 | 是否支持排序 | 体积 |
|---|---|---|---|---|---|---|
| **B-tree** | ✅ | 等值 / 范围 / 排序 / 唯一约束 | 平衡多叉树 | ✅ | ✅ | 中 |
| **Hash** | ❌ | 仅等值 | 哈希表 | ❌ | ❌ | 中 |
| **GIN** | ❌ | 倒排：JSONB / 数组 / tsvector / 多值 | entry tree + posting list/tree | 部分 | ❌ | 大 |
| **GiST** | ❌ | 几何 / 范围类型 / k-NN / 全文 | 通用搜索树（R-tree 风格） | ✅（范围类型） | ✅（KNN <-> ） | 中 |
| **SP-GiST** | ❌ | 不平衡空间分区：电话 / IP 前缀 / 四叉树 | 空间分区树 | ✅ | 部分 | 中 |
| **BRIN** | ❌ | 超大顺序相关数据 | 块范围摘要 | ✅ | ❌ | **极小** |

外加扩展形态：
- **Bloom**（`CREATE EXTENSION bloom`）：多列任意子集等值
- **btree_gist** / **btree_gin**：让 GiST/GIN 也支持普通标量列（用于复合 opclass）
- **rum**（社区扩展）：GIN 的进化版，支持排序 / 距离 / 范围
- **vector**（pgvector，详见 P06）：HNSW / IVFFlat

### 1.2 选择决策树

```
你的查询是什么？
├── 等值 / 范围 / 排序（普通列）         → B-tree
├── 等值（仅，hash 偏好）              → Hash（实际很少选，因为 B-tree 等值也够快）
├── JSONB 包含 (@>) / 数组成员 / 全文   → GIN
├── 几何位置 / 范围类型重叠 / 最近邻     → GiST
├── 电话号码 / IP 前缀 / URL 前缀       → SP-GiST
├── 超大顺序相关数据（日志/时序/自增）   → BRIN
├── 宽表多列任意子集等值                → Bloom
├── 模糊 LIKE '%xxx%'                  → GIN + pg_trgm
└── 向量 cosine / L2 相似               → pgvector (HNSW)
```

每种索引都有自己的"舒适区"。生产中常见的错误是**在 JSONB 上加 B-tree**（这种索引几乎不会被使用）、**在乱序日志上加 BRIN**（索引摆设）、**在巨量 UPDATE 表上加 GIN**（写入崩溃）。

### 1.3 一个具体的拐点：JSONB 的索引选择

```sql
-- 建表
CREATE TABLE events (
    id        bigserial PRIMARY KEY,
    payload   jsonb,
    created_at timestamptz DEFAULT now()
);

-- 错误：B-tree 几乎用不上
CREATE INDEX bad_idx ON events (payload);

-- 正确选项 1：GIN with jsonb_ops（默认）
CREATE INDEX events_payload_gin ON events USING gin (payload);
-- 支持 @>, ?, ?|, ?&

-- 正确选项 2：GIN with jsonb_path_ops（更小更快，但只支持 @>）
CREATE INDEX events_payload_gin_path ON events USING gin (payload jsonb_path_ops);
-- 只支持 @>，体积小 30-50%

-- 正确选项 3：表达式 GIN（针对高频路径）
CREATE INDEX events_user_idx ON events ((payload->>'user_id'));
-- 支持 payload->>'user_id' = 'xxx' 的查询
```

> 💡 一个 200 GB 的 JSONB 表，加 `jsonb_path_ops` 索引可能是 40 GB，加 `jsonb_ops` 是 70 GB——选 path_ops 经常能省 30 GB 磁盘。

## 第 2 章：GIN（Generalized Inverted Index）倒排索引

### 2.1 GIN 的设计目标

GIN 解决的是这样一类问题：**一行包含多个 key，但你要按 key 反查行**。

举例：

- 文档里有多个词 → 按词找文档（全文检索）
- 数组列 `['php', 'go', 'python']` → 找包含 `'go'` 的行
- JSONB `{"tags": ["a", "b"]}` → 找 tags 包含 `'a'` 的行

B-tree 处理的是 1 key → 1 row 的映射；GIN 处理 N key → M row 的映射。这就是"倒排"——和搜索引擎（Lucene/ES）一样的思想。

### 2.2 GIN 的内部结构：双层树

```
            ┌─────────────────────────────────┐
            │  Entry Tree（B-tree on keys）   │
            │  存所有出现过的 key             │
            └─────────────────────────────────┘
                       │
            ┌──────────┼──────────┐
            ▼          ▼          ▼
       "apple"      "go"      "python"
            │          │          │
            ▼          ▼          ▼
       [posting]  [posting]  [posting tree]
       少量行号    少量行号    （太长改存 B-tree）
```

每个 key 对应一个 **posting list**（少量行号，inline 存）或 **posting tree**（行号太多时升级为独立 B-tree）。

- **Entry tree** 本质就是一个标准 B-tree，叶子结点是 (key, pointer to posting)
- **Posting list** 内联在 entry 叶子里，行号按 TID 排序压缩存储
- 当 posting list 大到放不下一页时，升级为 **posting tree**（独立的 B-tree，叶子存压缩 TID）

### 2.3 GIN 与 B-tree 的对比

| 维度 | B-tree | GIN |
|---|---|---|
| 一行可索引几个 key | 1（或复合视为 1） | N（数组、JSONB key、词项） |
| 查询语义 | 比较 key | 集合包含 |
| 写性能 | 快 | 慢（每个 key 都要落） |
| 读性能 | 快 | 极快（直接拿 TID 列表） |
| 索引大小 | 中 | 偏大（同 key 可能重复出现） |
| 排序支持 | ✅ | ❌（rum 扩展支持） |

GIN **慢在写**：插入一行 JSONB `{"tags": [a,b,c]}` 要在 entry tree 中维护 3 个 key 的 posting。这种写放大让 GIN 在高频 UPDATE 表上代价巨大。

### 2.4 fastupdate（pending list）权衡

为缓解写放大，GIN 引入 **pending list**：

```
INSERT → pending list（顺序追加，几乎免费）
                 │
                 └──── 定期合并 ──→ entry tree（昂贵）
```

参数：

```sql
ALTER INDEX events_payload_gin SET (fastupdate = on);
ALTER INDEX events_payload_gin SET (gin_pending_list_limit = '4MB');
```

- **fastupdate=on**（默认）：写入先进 pending list，查询时会顺带触发合并
- **gin_pending_list_limit**：pending list 大到一定阈值就自动合并

副作用：

- 写很爽（快几倍）
- 但**查询有时会突然变慢**（恰好触发合并的那次查询）
- pending list 越大，被它截胡的查询越慢

生产实践：在线服务通常 **关闭 fastupdate**（要查询稳定），批量 ETL 表可以打开。

```sql
-- 手动合并 pending list
SELECT gin_clean_pending_list('events_payload_gin');
```

### 2.5 jsonb_ops vs jsonb_path_ops

两种 GIN opclass 的取舍：

| opclass | 支持操作符 | 索引体积 | 查询性能 |
|---|---|---|---|
| `jsonb_ops`（默认） | `@>` `?` `?|` `?&` | 大（每个 key 和每个 value 各一个 entry） | 一般 |
| `jsonb_path_ops` | 只支持 `@>` | 小（每个完整路径 hash 成一个 entry） | 快 |

如果你的查询只用 `@>`（最常见），用 `jsonb_path_ops`——索引小 30-50%，查询还更快。

```sql
-- jsonb_ops 索引（默认）
CREATE INDEX idx_default ON events USING gin (payload);

-- jsonb_path_ops 索引（推荐）
CREATE INDEX idx_path_ops ON events USING gin (payload jsonb_path_ops);
```

### 2.6 GIN 索引大小估算

经验值：

- **数组列**：索引大小 ≈ 数据列大小 × 1.0-1.5
- **JSONB `jsonb_ops`**：索引大小 ≈ 数据列大小 × 0.5-1.0
- **JSONB `jsonb_path_ops`**：索引大小 ≈ 数据列大小 × 0.3-0.6
- **tsvector**：索引大小 ≈ tsvector 列大小 × 1.5-2.0

实际看一下：

```sql
SELECT pg_size_pretty(pg_relation_size('events')) AS table_size,
       pg_size_pretty(pg_relation_size('events_payload_gin')) AS index_size;
```

## 第 3 章：GiST（Generalized Search Tree）

### 3.1 GiST 是什么

如果说 GIN 是"倒排协议"，GiST 就是"**模板化的 R-tree**"——它定义了一组用户函数，你实现这些函数，就能让 GiST 支持你的数据类型。

PG 内置的 GiST 应用：

- **几何类型** `box / circle / polygon`：经典 R-tree 用途
- **范围类型** `int4range / tstzrange`：重叠 / 包含查询
- **全文检索** `tsvector`：相对 GIN 写更快但查更慢
- **网络地址** `inet`：CIDR 前缀
- **k-NN（最近邻）** ：`ORDER BY point <-> '(0,0)'` 取最近 N 个
- **PostGIS** `geometry / geography`：所有空间索引都是 GiST

### 3.2 GiST 的 7 个用户函数

实现一个新的 GiST opclass 要提供这 7 个函数（C 函数或 PL/pgSQL）：

| 函数 | 作用 |
|---|---|
| `consistent(entry, query, strategy)` | 给定一个节点和查询，判断是否"可能"包含匹配 |
| `union(entries[])` | 合并多个子节点的范围 |
| `compress(entry)` | 把原始数据压成索引内部表示 |
| `decompress(entry)` | 解压（很多 opclass 是 no-op） |
| `penalty(entry, new)` | 把新条目插入这个节点的"代价"（用于选最便宜的插入点） |
| `picksplit(entries)` | 节点满时如何分裂成两个子节点 |
| `same(entry1, entry2)` | 两个 entry 是否相同 |

注意：consistent 函数允许返回**假阳性**——这意味着 GiST 查询完后**必须回堆验证**。索引只是"过滤候选行"，不是"直接给答案"。

### 3.3 GiST 与 GIN 的取舍

经常被问的"全文检索用 GIN 还是 GiST"：

| 维度 | GIN | GiST |
|---|---|---|
| 查询速度 | **快 3-10 倍** | 慢 |
| 构建速度 | 慢 | 快 |
| 写入速度 | 慢（除非 fastupdate） | 中 |
| 索引大小 | 偏大 | 中 |
| 支持 ORDER BY 距离 | ❌ | ✅（k-NN） |
| 假阳性 | 无 | 有，必须 recheck |

经验法则：

- **以查为主、更新不频繁** → GIN
- **写多查少、需要 k-NN** → GiST
- **PostGIS** → **永远是 GiST**（GIN 不支持空间）

### 3.4 GiST 的 k-NN 查询

GiST 的杀手特性是支持"按距离排序"：

```sql
-- 找距离原点最近的 100 个点
CREATE INDEX pts_idx ON locations USING gist (geom);

SELECT name, geom <-> ST_MakePoint(0, 0) AS dist
FROM locations
ORDER BY geom <-> ST_MakePoint(0, 0)
LIMIT 100;
```

执行计划会显示 `Index Scan` + 直接走索引拿到 TOP-N，**不用全表算距离再排序**——这是 GiST 比 GIN 的根本优势。

### 3.5 Buffered GiST 构建

PG 9.4+ 引入的特性：在构建大 GiST 索引时使用 buffered 模式，把"哪些行该进哪个节点"先缓冲再批量插，速度快 2-3 倍。

```sql
-- 自动启用（满足条件时）
CREATE INDEX big_geo_idx ON huge_table USING gist (geom);
-- 通过 maintenance_work_mem 控制 buffer 大小
SET maintenance_work_mem = '2GB';
```

## 第 4 章：SP-GiST（Space-Partitioned GiST）

### 4.1 SP-GiST 是什么

SP-GiST 提供**不平衡的空间分区树**：四叉树、kd-tree、后缀树、基数树。和 GiST（平衡的 R-tree 风格）的区别：

| 维度 | GiST | SP-GiST |
|---|---|---|
| 树形状 | 平衡 | 不平衡（按数据分布） |
| 节点重叠 | 允许 | 不允许（严格分区） |
| 适用数据 | 范围 / 几何 / 任意 | "自然分区"型：前缀 / 离散点 |

### 4.2 SP-GiST 的最佳场景

- **电话号码 / 邮编**：前缀树
- **IP 地址 / CIDR**：基数树（`inet` 类型）
- **URL**：前缀匹配
- **二维点（稀疏）**：四叉树 / kd-tree
- **文本前缀搜索**：后缀树

```sql
-- 在 inet 列上建 SP-GiST 索引
CREATE INDEX ip_idx ON access_log USING spgist (client_ip inet_ops);

-- 查"属于 192.168.0.0/16 的所有记录"
SELECT * FROM access_log WHERE client_ip <<= '192.168.0.0/16';
```

### 4.3 GiST vs SP-GiST 决策

如果数据"自然分区"（很容易切成不重叠的子空间），用 SP-GiST，否则用 GiST。

- 二维稀疏点 → SP-GiST 四叉树
- 二维密集多边形 → GiST R-tree
- IP 段 → SP-GiST 基数树
- 时间范围 → GiST（范围类型 opclass）

## 第 5 章：BRIN（Block Range Index）块范围索引

### 5.1 BRIN 的核心思想

BRIN 不是"为每行建一个 entry"，而是"每 N 个连续 page 建一个摘要"。

```
表的物理布局（每个方框是一个 8KB page）：
[page 1][page 2][page 3] ... [page 128][page 129] ...
└────── range 1 ──────┘     └────── range 2 ──────┘

BRIN 索引存储：
range 1: min=2024-01-01, max=2024-01-03
range 2: min=2024-01-03, max=2024-01-05
...
```

查询 `created_at > '2024-01-04'`：

1. 扫 BRIN 找哪些 range 的 max >= '2024-01-04'
2. 直接扫这些 range 里的 page

### 5.2 适用场景：超大顺序相关数据

BRIN 在"**列的物理顺序与逻辑顺序高度相关**"时威力最大：

- **时序数据**（按 `created_at` 自然有序）
- **自增 ID**
- **日志类只追加（append-only）表**
- **按业务时间分区表的 created_at 列**

举例：10 亿行日志表，按 `created_at` 自然有序。

```sql
-- B-tree 索引：约 30 GB
CREATE INDEX log_btree ON logs (created_at);

-- BRIN 索引：约 2 MB
CREATE INDEX log_brin ON logs USING brin (created_at);
```

差距 **15000 倍**！这就是为什么时序场景几乎不用 B-tree 而用 BRIN。

### 5.3 关键参数：pages_per_range

```sql
CREATE INDEX log_brin ON logs USING brin (created_at)
WITH (pages_per_range = 128);  -- 默认 128
```

- 调小 → 索引更精确（每个 range 范围小）→ 索引体积变大、查询更精确
- 调大 → 索引更小但范围宽 → 查询过滤效果差

经验值：
- 写入完全有序：32-128
- 写入半有序：16-32
- 完全乱序：**不要用 BRIN**

### 5.4 PG 14+ 多范围 BRIN

PG 14 引入了新的 opclass：

```sql
-- minmax_multi：每个 range 不只 1 个 [min, max]，而是多个区间
CREATE INDEX log_brin_multi ON logs USING brin (
    created_at timestamptz_minmax_multi_ops
);

-- bloom：每个 range 用 bloom filter 表示有哪些值（适合等值查询）
CREATE INDEX status_brin_bloom ON logs USING brin (
    status text_bloom_ops
);
```

- `minmax_multi` 解决了数据"基本有序但偶尔乱序"的退化问题
- `bloom` 让 BRIN 支持等值查询（取代部分 Hash 索引场景）

### 5.5 BRIN 退化场景

```sql
-- BAD：created_at 完全乱序
INSERT INTO logs VALUES (1, '2024-05-01', ...);
INSERT INTO logs VALUES (2, '2020-01-15', ...);
INSERT INTO logs VALUES (3, '2025-12-31', ...);
INSERT INTO logs VALUES (4, '2022-08-20', ...);
```

每个 range 的 `[min, max]` 都接近 `[全局min, 全局max]`——索引等于没用，每次查询都扫全表。

### 5.6 维护 BRIN

```sql
-- 一些行被新写入或 VACUUM，BRIN 的 summary 可能过期
SELECT brin_summarize_new_values('log_brin');

-- 完整重建一个 range（PG 10+）
SELECT brin_desummarize_range('log_brin', 100);
SELECT brin_summarize_range('log_brin', 100);
```

`autosummarize` 参数（PG 10+）让 BRIN 在 VACUUM 时自动更新：

```sql
ALTER INDEX log_brin SET (autosummarize = on);
```

## 第 6 章：Hash 索引

### 6.1 Hash 索引为什么"长期边缘化"

PG 10 之前，Hash 索引**不写 WAL**，崩溃后必须重建，几乎没有生产价值。PG 10 起补上 WAL 支持后才"复活"，但：

- B-tree 在等值查询上已经够快（O(log N), N=10亿时 log N≈30）
- Hash 不支持范围、排序、唯一约束（PG 10+）、多列索引
- 实际生产几乎不会主动选 Hash

### 6.2 何时考虑 Hash

- 索引列**极长**（如 64 字节 UUID 文本）→ Hash 摘要小很多
- **只做等值查询、绝不需要排序**
- 高基数（每个 key 几乎唯一）

```sql
-- 一个 1 亿行表，url 列 256 字节
CREATE INDEX urls_hash ON pages USING hash (url);
-- B-tree 可能 25 GB，Hash 可能 8 GB
```

但即使如此，多数 DBA 还是会选 B-tree——稳定性、工具链支持。

### 6.3 Hash 的内部

```
Hash function → bucket
                 │
                 ├── overflow pages（冲突链）
```

固定 bucket 数 + linear hashing 扩展。冲突走 overflow page 链。

## 第 7 章：Bloom 扩展索引

### 7.1 Bloom 索引解决什么

考虑一张 10 列宽表，查询是**任意几列的等值组合**：

```sql
SELECT * FROM events
WHERE col1 = 'a' AND col5 = 'x';  -- 这次查 col1+col5

SELECT * FROM events
WHERE col2 = 'b' AND col3 = 'c' AND col7 = 'z';  -- 这次查 col2+col3+col7
```

如果用 B-tree，要为每种组合建索引——10 列任意子集 = 2^10 个组合，不可能全建。

**Bloom 索引**用 bloom filter 压缩所有列的等值信息到一个 bit array，可以快速排除"肯定不匹配"的行。

### 7.2 用法

```sql
CREATE EXTENSION bloom;

CREATE INDEX events_bloom ON events
USING bloom (col1, col2, col3, col4, col5, col6, col7, col8, col9, col10)
WITH (length = 80, col1 = 2, col2 = 2, col3 = 4, col4 = 2);
-- length: bloom filter 总 bit 数
-- col*: 每列分到几个 bit
```

### 7.3 Bloom 的取舍

| 维度 | 评价 |
|---|---|
| 假阳性 | **有**——索引返回的候选行必须回堆验证 |
| 不支持范围 | 仅等值 |
| 不支持排序 | 无 |
| 多列任意组合 | ✅ 核心优势 |
| 写性能 | 中（要算 hash） |
| 索引大小 | 小（bit array） |

### 7.4 适用场景

- 数据仓库 / OLAP 场景：宽表 + 任意维度过滤
- "我不知道用户会按哪些列过滤"——动态过滤
- 列基数高（重复少）

## 第 8 章：opclass 与 opfamily

### 8.1 opclass 是什么

PG 的索引是协议化的。每种"（索引类型 × 数据类型）"对应一个 **operator class（opclass）**，定义这种数据用这种索引怎么工作。

```sql
-- 查看一个表的索引用了哪些 opclass
SELECT
    c.relname AS index,
    a.attname AS column,
    op.opcname AS opclass
FROM pg_index i
JOIN pg_class c ON c.oid = i.indexrelid
JOIN pg_attribute a ON a.attrelid = c.oid
JOIN pg_opclass op ON op.oid = ANY(i.indclass::oid[])
WHERE c.relname = 'events_payload_gin';
```

### 8.2 常见 opclass

| 数据类型 | 索引类型 | 默认 opclass | 备选 opclass |
|---|---|---|---|
| `text` | B-tree | `text_ops` | `text_pattern_ops`（支持 LIKE） |
| `varchar` | B-tree | `varchar_ops` | `varchar_pattern_ops` |
| `jsonb` | GIN | `jsonb_ops` | `jsonb_path_ops`（更小） |
| `tsvector` | GIN | `tsvector_ops` | — |
| `tsvector` | GiST | `tsvector_ops` | — |
| `int4` | BRIN | `int4_minmax_ops` | `int4_bloom_ops`, `int4_minmax_multi_ops` (PG 14+) |
| `inet` | SP-GiST | `inet_ops` | — |

### 8.3 LIKE 索引的 opclass 陷阱

```sql
-- 默认 opclass：text_ops
CREATE INDEX users_email_idx ON users (email);

-- 这个查询用不上索引（locale 排序与 LIKE 不一致）
SELECT * FROM users WHERE email LIKE 'foo%';

-- 解决：用 text_pattern_ops
CREATE INDEX users_email_idx2 ON users (email text_pattern_ops);
-- 现在 LIKE 'foo%' 可以走索引（前缀匹配）

-- 或者用 C locale 建库
```

## 第 9 章：3 个完整生产案例

### 9.1 案例一：10 亿行日志表的索引组合

业务：电商订单审计日志，每天 1 亿行，保留 30 天，**只追加**。

**查询模式**：
1. 按 `created_at` 时间范围扫近 N 小时（高频）
2. 按 `order_id` 精确查（中频）
3. 按 `payload->>'event_type'` 等值过滤（高频）

**索引方案**：

```sql
-- 1. 时间扫：BRIN（极小，足够）
CREATE INDEX logs_ct_brin ON audit_logs USING brin (created_at)
  WITH (pages_per_range = 64);

-- 2. order_id 精确查：B-tree
CREATE INDEX logs_oid ON audit_logs (order_id);

-- 3. JSONB 路径：表达式 GIN
CREATE INDEX logs_event_type ON audit_logs (((payload->>'event_type')));

-- 整体：BRIN 几 MB + B-tree 几十 GB + 表达式索引几 GB
-- 而单纯用 B-tree on created_at 就要 30 GB
```

### 9.2 案例二：商品搜索（JSONB tags + 全文）

```sql
CREATE TABLE products (
    id        bigserial PRIMARY KEY,
    name      text,
    description text,
    tags      jsonb,
    price     numeric,
    created_at timestamptz DEFAULT now()
);

-- tags GIN：支持 tags @> '["promo"]'
CREATE INDEX products_tags ON products USING gin (tags jsonb_path_ops);

-- 全文 GIN：支持 to_tsvector('zh', name || ' ' || description) @@ ...
CREATE INDEX products_fts ON products USING gin (
    to_tsvector('simple', coalesce(name, '') || ' ' || coalesce(description, ''))
);

-- 价格 B-tree：常规
CREATE INDEX products_price ON products (price);
```

查询：

```sql
SELECT * FROM products
WHERE tags @> '["promo"]'::jsonb
  AND to_tsvector('simple', name || ' ' || description) @@ to_tsquery('shoe')
  AND price BETWEEN 100 AND 500;
```

EXPLAIN 会显示 `BitmapAnd` 把三个索引的位图相交。

### 9.3 案例三：地理位置最近邻（PostGIS）

```sql
CREATE EXTENSION postgis;

CREATE TABLE pois (
    id bigserial PRIMARY KEY,
    name text,
    geom geometry(Point, 4326)
);

-- GiST 空间索引
CREATE INDEX pois_geom ON pois USING gist (geom);

-- 找用户附近 1km 内的 POI，按距离排序取前 20
SELECT id, name,
       ST_Distance(geom::geography, 'SRID=4326;POINT(116.4 39.9)'::geography) AS dist_m
FROM pois
WHERE ST_DWithin(
    geom::geography,
    'SRID=4326;POINT(116.4 39.9)'::geography,
    1000
)
ORDER BY geom <-> ST_MakePoint(116.4, 39.9)
LIMIT 20;
```

GiST 同时支撑 `ST_DWithin` 过滤和 `<->` 排序。

## 第 10 章：索引诊断与维护

### 10.1 查未使用的索引

```sql
SELECT
    schemaname || '.' || relname AS table,
    indexrelname AS index,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size,
    idx_scan AS scans
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE 'pg_toast%'
ORDER BY pg_relation_size(indexrelid) DESC;
```

### 10.2 查"扫得多但收益少"的索引

```sql
SELECT
    relname AS table,
    indexrelname AS index,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch,
    CASE WHEN idx_scan > 0
         THEN round(idx_tup_read::numeric / idx_scan, 2)
         ELSE 0 END AS rows_per_scan
FROM pg_stat_user_indexes
WHERE idx_scan > 0
ORDER BY rows_per_scan DESC
LIMIT 20;
```

`rows_per_scan` 高 = 选择性差。

### 10.3 索引膨胀

```sql
-- 用 pgstatindex 看 B-tree 内部填充率
CREATE EXTENSION pgstattuple;
SELECT * FROM pgstatindex('events_payload_gin');
```

膨胀严重就重建：

```sql
REINDEX INDEX CONCURRENTLY events_payload_gin;
```

### 10.4 索引建议（hypopg）

```sql
CREATE EXTENSION hypopg;

-- 创建一个虚拟索引（不真建）
SELECT hypopg_create_index('CREATE INDEX ON events ((payload->>''user_id''))');

-- 看 planner 是否会选它
EXPLAIN SELECT * FROM events WHERE payload->>'user_id' = 'u123';

-- 用完清理
SELECT hypopg_reset();
```

## 生产实践

1. **JSONB 默认上 `jsonb_path_ops` GIN**：90% 的场景只用 `@>`，索引能省 30-50% 空间。
2. **时序表用 BRIN**：每天 GB 级写入的日志、监控、订单流水，BRIN 通常足够。配合声明式分区还能让 BRIN 永远聚焦活跃 range。
3. **PostGIS 用 GiST**：唯一选择。
4. **多列 OR 等值用 Bloom**：宽表 + 不可预测的过滤组合，远比为每种组合建 B-tree 高效。
5. **GIN 表生产关闭 fastupdate**：避免查询时间不稳定。批量导入前临时开。
6. **LIKE 'foo%' 加 `text_pattern_ops`**：locale 非 C 时是必需。
7. **CREATE INDEX CONCURRENTLY**：生产建索引一律用 CONCURRENTLY，避免锁表。失败要 DROP INVALID 索引重建。
8. **REINDEX CONCURRENTLY（PG 12+）**：处理索引膨胀的标准动作，无锁。
9. **用 pg_stat_user_indexes 月度审查**：删除未使用索引能省 10-30% 写入开销。
10. **hypopg 试索引**：上线前虚拟试试 planner 选不选。

---

## 陷阱清单

1. **JSONB 上加 B-tree** → 索引几乎用不到，纯粹浪费空间。
2. **乱序数据上加 BRIN** → 索引等于摆设，每次查询扫全表。
3. **生产环境 GIN 开 fastupdate** → 查询时间忽快忽慢，触发合并的请求 P99 飞涨。
4. **CREATE INDEX 不带 CONCURRENTLY** → 锁表写入，业务超时。
5. **CONCURRENTLY 失败留下 INVALID 索引** → 不会被 planner 使用，但占空间——记得 `DROP INDEX CONCURRENTLY`。
6. **多列索引列顺序错** → 等值列放前，范围列放后；选择性高的放前。
7. **GiST + GIN 并存在同一 tsvector 列** → 一般只需要一个；GiST 在更新频繁场景更友好，GIN 在查询为主场景必选。
8. **LIKE '%foo%' 期望走 B-tree** → 不可能。要走索引必须用 `pg_trgm` GIN。
9. **Hash 索引在 PG 9.x** → 没 WAL，崩溃后丢失。PG 10+ 才能用。
10. **BRIN 上加唯一约束** → 不支持，UNIQUE 只能 B-tree。
11. **JSONB 整列加 GIN 当万能搜索** → 索引大、写慢。**改用表达式索引**针对高频路径。
12. **忽视 INCLUDE 列** → 覆盖索引能省回堆，但很多人忘了在 B-tree 上加 INCLUDE。
13. **maintenance_work_mem 太小** → CREATE INDEX 慢得离谱。临时调大（如 4GB）能提速数倍。
14. **GIN 索引列 NULL 值多** → NULL 不会进 GIN entry tree，但行还在表里——某些查询走不上索引。
15. **Bloom 索引 length 调太小** → 假阳性率高，回堆开销超过收益。

## 2026 现状

| 主题 | 状态 |
|---|---|
| **BRIN minmax_multi / bloom（PG 14+）** | 成熟，时序场景几乎默认选 minmax_multi |
| **REINDEX CONCURRENTLY（PG 12+）** | 索引膨胀治理标准动作 |
| **GIN deduplication 改进** | PG 13+ 持续优化重复 key 存储 |
| **pg_trgm 全文模糊** | 中文场景配合 `gin_trgm_ops`，成熟可用 |
| **rum 扩展** | 仍是小众，但全文 + 排序场景比 GIN 强 |
| **hypopg** | 索引建议标准工具，AWS RDS / Aurora 都支持 |
| **pgvector**（详见 P06） | HNSW 已成 RAG 默认；与 GIN 全文一起做混合检索常见 |
| **多列扩展统计 CREATE STATISTICS（PG 10+）** | 帮 planner 估算相关列基数，间接影响索引选择 |
| **B-tree skip scan**（PG 17 部分） | 多列 B-tree 跳过前缀的能力进步，但仍不完全替代精心设计的多列索引 |
| **PG 18 异步 IO** | 对 bitmap heap scan / index-only scan 有性能改进 |

## 练习题

1. 一个 200 GB JSONB 表，主要查询是 `WHERE data @> '{"status": "active"}'::jsonb`。索引怎么选？给出建议和理由。

   **答案**：`CREATE INDEX ON t USING gin (data jsonb_path_ops)`。只支持 `@>` 但体积小 30-50%，匹配场景刚好。

2. 一张 10 亿行日志表，按 `created_at` 时序写入但偶尔有迟到 30 天的回填记录。BRIN 还能用吗？

   **答案**：经典 BRIN `minmax` 会退化（一个 range 的 max 被回填记录拉到当前，min 被拉到 30 天前）。PG 14+ 的 `minmax_multi` 能存多个区间，正是为这种场景设计的，选它。

3. 你给 PostGIS 表加了 GIN 索引，发现根本不用。为什么？

   **答案**：GIN 不支持空间类型。PostGIS 必须用 GiST。

4. 在线服务的 GIN 索引偶发查询 P99 飙到 500ms，平时 5ms。最可能的原因？怎么处理？

   **答案**：`fastupdate = on` 导致 pending list 累积，某次查询恰好触发合并。解决：`ALTER INDEX idx SET (fastupdate = off)` 关闭，或调小 `gin_pending_list_limit` + 用 `gin_clean_pending_list()` 定期人工合并。

5. 一个 5 列宽表，业务方说"我也不知道用户会按哪些列过滤"。怎么设计索引？

   **答案**：Bloom 索引 `CREATE EXTENSION bloom; CREATE INDEX ... USING bloom (c1, c2, c3, c4, c5)`。支持任意子集等值。代价是有假阳性，必须回堆验证；好处是省得为每种组合建 B-tree。

6. `CREATE INDEX CONCURRENTLY` 失败后，索引状态是 INVALID。可以用吗？怎么处理？

   **答案**：INVALID 索引不会被 planner 使用，但会被 INSERT/UPDATE 维护（拖慢写入）。处理：`DROP INDEX CONCURRENTLY idx_name; CREATE INDEX CONCURRENTLY ...` 重建。

7. 在 `email text` 列上建 B-tree 后，`SELECT * FROM users WHERE email LIKE 'foo%'` 仍走 Seq Scan。怎么修？

   **答案**：locale 非 C 时默认 `text_ops` opclass 与 LIKE 不兼容。改用 `CREATE INDEX ON users (email text_pattern_ops)`。

8. 你想知道某个表"如果加了 JSONB 表达式索引，planner 是否会选"。不想真建，怎么试？

   **答案**：`CREATE EXTENSION hypopg; SELECT hypopg_create_index('...'); EXPLAIN ...; SELECT hypopg_reset();` 用 hypopg 创建虚拟索引让 planner 评估。
