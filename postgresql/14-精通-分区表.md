# 精通分区表：PostgreSQL 大表切片的工业级方案

> 关联章节：[P02 堆表存储与 TOAST](./02-精通-堆表存储与-TOAST.md)、[P08 VACUUM 与表膨胀](./08-精通-VACUUM-与表膨胀.md)、[P18 扩展生态](./18-精通-扩展生态.md)

---

## 引言：为什么需要分区

当一张表突破 1 亿行 / 500 GB，传统单表会出现一系列病症：

- **VACUUM 越来越慢**——每次扫整张大表，autovacuum 跟不上写入
- **索引膨胀难处理**——重建索引锁表时间长
- **历史数据删除阻塞**——`DELETE FROM logs WHERE ts < ...` 一次删几百万行，锁、WAL 爆量
- **冷热混合 IO 差**——SSD 上的 90% 数据从不被访问
- **统计信息粗糙**——大表的直方图分辨率有限，planner 估算偏

**分区表（Table Partitioning）** 把一张逻辑表切成多个物理表（每个分区是真表），逻辑上还是一张表。带来的好处：

| 维度 | 收益 |
|---|---|
| 查询 | 分区裁剪（只扫相关分区） |
| 维护 | 单分区 VACUUM、REINDEX、TRUNCATE |
| 归档 | `DETACH PARTITION` 秒级把旧数据"摘下" |
| 数据生命周期 | DROP 整个分区比 DELETE 快 1000 倍 |
| 索引 | 每个分区独立索引，重建影响小 |
| 并行 | 分区维度天然并行 |

但分区也不是银弹——本章重点讲清楚 **PG 分区到底能做什么、不能做什么、什么场景值得切、什么场景反而拖累**。

读完之后你应该能：

- 区分 PG 三代分区方案（继承式 / 声明式 / TimescaleDB Hypertable）
- 选对 RANGE / LIST / HASH 三种策略
- 用声明式分区（PG 10+）建分区表、子分区、默认分区
- 解释分区裁剪的两个时机（plan-time / run-time）
- 评估"分区数量"对 planner 的影响
- 用 ATTACH/DETACH PARTITION 实现"无锁"维护
- 用 pg_partman 自动滚动管理
- 对比 PG 原生分区 vs TimescaleDB Hypertable
- 在 K8s / 云环境跑大型分区表的运维节奏

## 第一章：历史——从继承到声明式

### 1.1 第一代：表继承（古老）

PostgreSQL 早期没有"分区"概念，靠**表继承 + CHECK 约束 + 触发器**模拟：

```sql
CREATE TABLE logs (ts TIMESTAMPTZ, body TEXT);
CREATE TABLE logs_2024_01 (CHECK (ts >= '2024-01-01' AND ts < '2024-02-01')) INHERITS (logs);
CREATE TABLE logs_2024_02 (CHECK (ts >= '2024-02-01' AND ts < '2024-03-01')) INHERITS (logs);

-- 路由插入需要触发器/规则
CREATE TRIGGER ... BEFORE INSERT ON logs FOR EACH ROW EXECUTE FUNCTION route_insert();
```

问题：
- 路由代码维护成本巨大
- 唯一约束不能跨子表
- 优化器只能基于 `constraint_exclusion = on` 静态裁剪
- ATTACH/DETACH 不友好

### 1.2 第二代：声明式分区（PG 10+，主流）

PG 10 引入 `PARTITION BY`，由内核管理分区路由，工业可用：

```sql
CREATE TABLE logs (
  ts TIMESTAMPTZ NOT NULL,
  body TEXT
) PARTITION BY RANGE (ts);
```

PG 11+ 又补齐了大量短板：默认分区、Hash 分区、外键、行触发器、唯一索引、并行查询等。

PG 12-18 持续优化分区裁剪、ATTACH/DETACH CONCURRENTLY、运行时裁剪。

### 1.3 第三代：扩展分区（TimescaleDB / Citus）

- **TimescaleDB Hypertable**：自动创建 chunk、按时间 + 空间双维度分块、压缩、连续聚合（continuous aggregates）
- **Citus 分布式表**：跨节点 hash 分片，每节点本地仍是 PG 表

在 2026 年，**声明式分区（PG 内置）+ TimescaleDB Hypertable**（时序场景） 是两条最常用的路。

## 第二章：三种分区策略

### 2.1 RANGE 分区

按值范围切：时间、自增 ID、价格区间。

```sql
CREATE TABLE orders (
  id BIGSERIAL,
  created_at TIMESTAMPTZ NOT NULL,
  amount NUMERIC
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_01 PARTITION OF orders
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

CREATE TABLE orders_2026_02 PARTITION OF orders
  FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

注意：上界**不包含**（`[from, to)` 区间）。

**多列 RANGE**（PG 11+）：

```sql
CREATE TABLE t (a INT, b INT) PARTITION BY RANGE (a, b);
CREATE TABLE t_p1 PARTITION OF t FOR VALUES FROM (1, 1) TO (5, 10);
```

多列 RANGE 用字典序比较，常见于"year-month"双键。

### 2.2 LIST 分区

按枚举值切：region、tenant_id、category。

```sql
CREATE TABLE users (
  id BIGSERIAL,
  region TEXT NOT NULL,
  name TEXT
) PARTITION BY LIST (region);

CREATE TABLE users_cn PARTITION OF users FOR VALUES IN ('CN', 'HK', 'TW');
CREATE TABLE users_us PARTITION OF users FOR VALUES IN ('US', 'CA');
CREATE TABLE users_eu PARTITION OF users FOR VALUES IN ('DE','FR','UK','IT','ES');
```

适用：值集合明确、有限、查询常按这个字段过滤。

### 2.3 HASH 分区

按哈希切：user_id、device_id、order_id。

```sql
CREATE TABLE events (
  user_id BIGINT NOT NULL,
  ts TIMESTAMPTZ,
  payload JSONB
) PARTITION BY HASH (user_id);

CREATE TABLE events_0 PARTITION OF events FOR VALUES WITH (MODULUS 8, REMAINDER 0);
CREATE TABLE events_1 PARTITION OF events FOR VALUES WITH (MODULUS 8, REMAINDER 1);
-- ...到 events_7
```

适用：没有自然的范围/枚举切片维度，希望均匀分摊负载。

**HASH 分区的代价**：
- **不能** 做范围查询裁剪（只对等值查询）
- 新增分区需要 `MODULUS` 变化，意味着**全表数据搬迁**
- 一旦定下来很难改

经验：HASH 分区数定一次定终生，按未来 3-5 年规模一次给到位（如 32/64/128）。

### 2.4 三策略决策矩阵

```
              查询模式                      增长模式
              范围  /  等值                  渐进  /  突发
       ┌───────────┴───────────┐    ┌───────────┴───────────┐
RANGE  │  时间序列              │    │  按时间自然滚动         │
LIST   │  租户/区域/类别         │    │  固定枚举              │
HASH   │  纯负载分摊（等值）     │    │  一次性预切             │
```

经验：

- 日志/事件/订单/审计 → **RANGE by ts**
- 多租户 SaaS → **LIST by tenant_id** 或 **HASH by tenant_id**
- 用户/设备超大表 → **HASH by user_id**
- "时间 + 租户"双维 → **RANGE by ts → HASH by tenant_id** 子分区

## 第三章：子分区（多级分区）

```sql
CREATE TABLE orders (
  id BIGSERIAL,
  created_at TIMESTAMPTZ NOT NULL,
  region TEXT,
  amount NUMERIC
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_01 PARTITION OF orders
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01')
  PARTITION BY LIST (region);   -- 子分区

CREATE TABLE orders_2026_01_cn PARTITION OF orders_2026_01 FOR VALUES IN ('CN','HK','TW');
CREATE TABLE orders_2026_01_us PARTITION OF orders_2026_01 FOR VALUES IN ('US','CA');
```

子分区适合："按时间滚动 + 按区域/租户隔离"复合需求。

陷阱：**层级越深，分区数量爆炸**——3 层 × 每层 12 → 1728 个叶子分区，planner 压力大。

经验：层级 ≤ 2，叶子分区 ≤ 1000。

## 第四章：DEFAULT 分区

PG 11+ 引入"默认分区"——所有未匹配任何分区的数据落到这里：

```sql
CREATE TABLE orders_default PARTITION OF orders DEFAULT;
```

用途：
- 兜底，防止写入失败
- 还没建好的未来分区先临时收

**陷阱**：

1. **DEFAULT 存在时，新增 RANGE 分区可能要重新检查 DEFAULT 中的所有行**（确保它们不属于新分区）——慢
2. DEFAULT 不参与分区裁剪（除非 planner 能完全证明）
3. DEFAULT 累积太多数据 → 失去分区表意义

生产实践：**只把 DEFAULT 当作"应急容器"，应该尽快用脚本 `INSERT ... ON CONFLICT` 把里面的数据移到正常分区，然后 TRUNCATE DEFAULT**。

## 第五章：分区裁剪（Partition Pruning）

### 5.1 两代分区裁剪

| 代 | 名称 | 时期 | 触发方式 | 限制 |
|---|---|---|---|---|
| 1 | constraint_exclusion | PG 8.x | plan-time | 基于 CHECK 约束 |
| 2 | partition_pruning | PG 11+ | plan-time + run-time | 基于分区元数据，更聪明 |

关键参数：

```sql
SHOW enable_partition_pruning;        -- 默认 on，控制 plan-time + run-time
SHOW constraint_exclusion;            -- on/off/partition，主要给继承式
```

PG 10 的分区裁剪叫 "real partition pruning"，比早期的 constraint_exclusion 强很多——后者是基于 CHECK 谓词的通用机制（性能差、覆盖少），前者是分区表专用、O(log N) 找分区。

### 5.2 Plan-time 裁剪

WHERE 条件是**字面常量**时，planner 直接在生成计划时确定要扫哪些分区：

```sql
EXPLAIN SELECT * FROM orders WHERE created_at >= '2026-05-01' AND created_at < '2026-06-01';
-- Append
--   -> Seq Scan on orders_2026_05    <- 只扫 5 月分区
```

### 5.3 Run-time 裁剪

WHERE 条件是**参数 / 子查询结果 / 函数返回值**时，plan-time 不知道值，需要执行时再选择：

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE created_at = $1;
-- Append
--   Subplans Removed: 11    <- 执行时把 12 个分区裁剪到 1 个
--   -> Seq Scan on orders_2026_05 (filter: created_at = $1)
```

`Subplans Removed: N` 就是 run-time 裁剪生效的标志。

### 5.4 分区裁剪的"裁不到"陷阱

以下情况裁剪失效：

| 失效条件 | 原因 | 解决 |
|---|---|---|
| `WHERE date_trunc('month', ts) = '2026-05'` | 函数包装失去常量信息 | 改为 `ts >= '2026-05-01' AND ts < '2026-06-01'` |
| `WHERE ts::date = '2026-05-01'` | 类型转换 | 直接用 timestamptz 字面量 |
| `WHERE ts BETWEEN $1 AND $2`（极大范围） | 跨多分区 | 没办法，扫多分区 |
| 跨分区 JOIN | 不裁剪 | 看 5.5 |

### 5.5 Partition-wise Join / Aggregate（PG 11+）

如果两张分区表用**相同的分区键** JOIN，planner 可以"按分区一对一 JOIN"：

```sql
SET enable_partitionwise_join = on;
SET enable_partitionwise_aggregate = on;

SELECT * FROM orders o JOIN users u ON o.user_id = u.id;
-- 如果 orders 和 users 都按 user_id 分区，相同模数，则按分区配对 JOIN
```

效果显著：每个分区独立 hash join，能并行，能用更小的 work_mem。

要求严格：
- 两表分区键完全一致
- 分区边界匹配
- 默认关闭，需手动 enable_partitionwise_join = on

## 第六章：索引、约束、外键的现实

### 6.1 本地索引 vs 全局索引

PostgreSQL 分区表的索引是**本地索引**——每个分区一份独立 B-tree，不存在跨分区的"全局索引"。

```sql
CREATE INDEX idx_orders_user ON orders (user_id);
-- 实际：在每个子分区上自动建一个同名索引
```

含义：
- 索引体积 = 各分区索引之和
- 索引扫描会按分区分别走，结果通过 Append/MergeAppend 合并
- 不能跨分区强制顺序（除非用 MergeAppend，需要每个子索引有序）

### 6.2 唯一约束的限制

**PG 不支持跨分区唯一约束**——除非唯一约束包含分区键。

```sql
-- 报错
ALTER TABLE orders ADD CONSTRAINT u_order_no UNIQUE (order_no);

-- 可行（包含分区键）
ALTER TABLE orders ADD CONSTRAINT u_order_no UNIQUE (created_at, order_no);
```

含义：
- 业务全局唯一的 order_no 不能用 PG 分区表保证
- 需要用 UUIDv7（自带全局唯一性）或应用层去重

这是 PG 分区表**最大的限制**之一。Oracle 有全局索引，PG 没有。

### 6.3 外键

PG 11+ 支持外键，但有限制：

- 分区表**可以引用**普通表（FK 出去）
- 分区表**可以被引用**（FK 进来）—— PG 12+
- 引用方需要在每个分区上建索引（自动）

```sql
CREATE TABLE order_items (
  order_id BIGINT REFERENCES orders (id),
  ...
);
-- 等价于在 order_items 上加 FK，每个 orders 分区都被引用
```

性能注意：高频写入下外键检查 = 每次都查所有分区的索引，可能慢。常见做法是**业务层校验、不用 FK**。

### 6.4 唯一 vs 主键的实战取舍

| 业务需求 | 方案 |
|---|---|
| 主键全局唯一 | 用 UUIDv7（PG 18 内置） |
| 业务键全局唯一 | 应用层 + 唯一索引兜底（单分区内）+ 后台去重 |
| 主键 = 分区键 + 自增 | `PRIMARY KEY (created_at, id)`，丑但能用 |

## 第七章：分区维护操作

### 7.1 ATTACH PARTITION

把一个独立表"挂"成分区：

```sql
CREATE TABLE orders_2026_07_staging (LIKE orders INCLUDING ALL);
-- 写入数据、建索引...
ALTER TABLE orders_2026_07_staging ADD CONSTRAINT chk
  CHECK (created_at >= '2026-07-01' AND created_at < '2026-08-01') NOT VALID;
ALTER TABLE orders_2026_07_staging VALIDATE CONSTRAINT chk;

ALTER TABLE orders ATTACH PARTITION orders_2026_07_staging
  FOR VALUES FROM ('2026-07-01') TO ('2026-08-01');
```

要点：
- 加 `CHECK ... NOT VALID` + `VALIDATE` 避免 ATTACH 时锁表全扫
- PG 在 ATTACH 时会校验数据落在范围内（有 CHECK 就跳过全扫）

### 7.2 DETACH PARTITION

把分区"摘下"成独立表：

```sql
ALTER TABLE orders DETACH PARTITION orders_2024_01;
-- 现在 orders_2024_01 是独立表，可以归档、DROP 或单独查询
```

### 7.3 DETACH PARTITION CONCURRENTLY（PG 14+）

普通 DETACH 需要 `ACCESS EXCLUSIVE` 锁（短暂但是阻塞读写）。PG 14+ 提供并发版：

```sql
ALTER TABLE orders DETACH PARTITION orders_2024_01 CONCURRENTLY;
```

两阶段：
1. 短锁标记 "PENDING DETACH"
2. 等所有相关事务结束
3. 真正分离

适合 24×7 业务，避免分离冷分区时的瞬时阻塞。

### 7.4 DROP / TRUNCATE 分区

```sql
DROP TABLE orders_2024_01;          -- 比 DELETE 快 1000 倍
TRUNCATE TABLE orders_2024_01;      -- 保留分区元数据，清空数据
```

这是分区表的**核心价值之一**——历史数据生命周期管理。

### 7.5 滚动分区脚本（手动）

```sql
-- 每月 1 号执行
CREATE TABLE IF NOT EXISTS orders_2026_06 PARTITION OF orders
  FOR VALUES FROM ('2026-06-01') TO ('2026-07-01');

DROP TABLE IF EXISTS orders_2023_06;  -- 保留 36 个月
```

手动版的问题：人为操作，漏建 = 写入失败（除非有 DEFAULT 分区兜底）。

## 第八章：pg_partman 自动维护

### 8.1 是什么

`pg_partman` 是 PG 生态最成熟的分区维护扩展，社区维护，pg18 兼容。功能：

- 基于"模板表"自动创建未来分区（预建 N 个）
- 基于"保留策略"自动 DROP 旧分区
- 配合 `pg_cron` 定时执行

### 8.2 基本用法

```sql
CREATE EXTENSION pg_partman;

-- 创建分区表（手动建好基础）
CREATE TABLE logs (ts TIMESTAMPTZ NOT NULL, msg TEXT) PARTITION BY RANGE (ts);

-- 注册到 pg_partman
SELECT partman.create_parent(
  p_parent_table => 'public.logs',
  p_control => 'ts',
  p_type => 'native',          -- 声明式分区
  p_interval => '1 day',       -- 按天
  p_premake => 7               -- 预建 7 天
);

-- 配置保留：保留 90 天
UPDATE partman.part_config
SET retention = '90 days', retention_keep_table = false
WHERE parent_table = 'public.logs';

-- 跑维护（pg_cron 定时跑）
SELECT partman.run_maintenance('public.logs');
```

### 8.3 与 pg_cron 集成

```sql
CREATE EXTENSION pg_cron;
SELECT cron.schedule('partman-maintenance', '5 * * * *',
  $$ SELECT partman.run_maintenance(p_analyze := true) $$);
```

每小时 5 分跑一次：检查所有注册的分区表，预建未来分区，DROP 过期分区。

### 8.4 模板表

`pg_partman` 用一张"模板表"复制权限、索引、约束：

```sql
-- 修改模板表，新建的分区会继承
ALTER TABLE partman.template_public_logs ADD COLUMN level TEXT;
CREATE INDEX ON partman.template_public_logs (level);
```

新分区会自动带上模板表的索引（注意：**已有分区不变**，要手动同步）。

### 8.5 与原生分区的对比

| 维度 | 手动 SQL | pg_partman |
|---|---|---|
| 学习成本 | 低 | 中 |
| 复杂度 | 低（10 行脚本） | 中 |
| 出错风险 | 高（漏建分区） | 低 |
| 灵活性 | 高 | 中 |
| 与 pg_cron 集成 | 自己写 | 内置 |

经验：> 1 张分区表就上 pg_partman。

## 第九章：PG 分区 vs TimescaleDB Hypertable

TimescaleDB 是 PG 的扩展，提供 Hypertable——"自动分区的时序表"。两者关系：

```
TimescaleDB Hypertable
  └─ 内部用 PG 继承表机制实现（不是声明式分区）
     └─ chunk = 真正的物理表
```

| 维度 | PG 声明式分区 | TimescaleDB Hypertable |
|---|---|---|
| 内核 | PG 原生 | PG 扩展 |
| 分区创建 | 手动 / pg_partman | 自动 chunk |
| 分区维度 | RANGE/LIST/HASH | 时间 + 空间双维 |
| 压缩 | 无（需手动） | 内置列存压缩（10x） |
| 连续聚合 | 无 | 内置 continuous aggregates |
| 数据保留 | DROP TABLE | drop_chunks 策略 |
| 跨 chunk 索引 | 不支持 | 部分支持 |
| 许可证 | PostgreSQL | Timescale Community License（部分功能） |
| 厂商绑定 | 无 | Timescale 公司 |

经验：

- **纯时间序列大表（监控/IoT/日志）→ TimescaleDB**
- **业务表（订单/事件）→ PG 声明式分区**
- **未来想迁移到云中立 → PG 声明式分区**（避免锁定）

## 第十章：分区数量与 Planner 代价

### 10.1 分区不是越多越好

planner 在处理 N 个分区时，每个查询要：
- 加载 N 个分区元数据（pg_class / pg_index）
- 评估 N 个分区是否可裁剪
- 生成 Append 子计划

PG 12 之前对 1000+ 分区性能崩盘；PG 13-18 持续优化，1000+ 已可用，但还是有代价。

### 10.2 经验阈值

| 分区数 | 建议 |
|---|---|
| < 100 | 任何 PG 版本都没问题 |
| 100-1000 | PG 12+，注意 `enable_partition_pruning=on` |
| 1000-10000 | PG 14+，避免 partition-wise join 等高代价 |
| > 10000 | 重新审视分区粒度——按月而非按天 |

### 10.3 测量分区裁剪开销

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM huge_partitioned WHERE ts = '2026-05-01 12:00:00';

-- Planning Time: 35.2 ms        <- 这是 planner 处理分区的代价
-- Execution Time: 0.5 ms
```

如果 Planning Time >> Execution Time，分区太多。考虑：

- 合并细粒度分区为大粒度
- 用 prepared statement 让 plan 缓存
- 检查 `enable_partitionwise_*` 是否开了但没必要

### 10.4 数据局部性

每个分区是独立堆表，所以查询多分区时**buffer cache 命中率会下降**——访问模式从"集中"变"分散"。设计时尽量让 hot 数据集中在少数分区。

## 第十一章：完整案例

### 11.1 案例 A：按月分区日志表

```sql
-- 1. 基础表
CREATE TABLE app_logs (
  ts TIMESTAMPTZ NOT NULL,
  level TEXT NOT NULL,
  service TEXT NOT NULL,
  message TEXT,
  ctx JSONB
) PARTITION BY RANGE (ts);

-- 2. 默认分区兜底
CREATE TABLE app_logs_default PARTITION OF app_logs DEFAULT;

-- 3. 预建分区（pg_partman 自动）
SELECT partman.create_parent(
  p_parent_table => 'public.app_logs',
  p_control => 'ts',
  p_type => 'native',
  p_interval => '1 month',
  p_premake => 3
);

UPDATE partman.part_config
SET retention = '12 months', retention_keep_table = false
WHERE parent_table = 'public.app_logs';

-- 4. 索引（每个分区独立）
CREATE INDEX ON app_logs (ts);
CREATE INDEX ON app_logs (service, ts);
CREATE INDEX ON app_logs USING gin (ctx jsonb_path_ops);
CREATE INDEX ON app_logs USING brin (ts);  -- 时序天然适合 BRIN

-- 5. 查询示例（分区裁剪生效）
SELECT * FROM app_logs
WHERE ts >= '2026-05-01' AND ts < '2026-05-08'
  AND service = 'api'
  AND ctx @> '{"user_id": 42}';
```

EXPLAIN 输出片段：

```
Append
  -> Bitmap Heap Scan on app_logs_2026_05
       Recheck Cond: (...)
       -> BitmapAnd
            -> Bitmap Index Scan on app_logs_2026_05_service_ts_idx
            -> Bitmap Index Scan on app_logs_2026_05_ctx_idx
```

### 11.2 案例 B：按 HASH 分区用户表

```sql
-- 1. 基础表
CREATE TABLE users (
  id BIGINT NOT NULL,
  email TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now(),
  profile JSONB,
  PRIMARY KEY (id)              -- 注意：id 必须包含在 PK 中（同时是分区键）
) PARTITION BY HASH (id);

-- 2. 16 个分区
DO $$
BEGIN
  FOR i IN 0..15 LOOP
    EXECUTE format(
      'CREATE TABLE users_p%s PARTITION OF users FOR VALUES WITH (MODULUS 16, REMAINDER %s)',
      i, i);
  END LOOP;
END$$;

-- 3. 索引
CREATE INDEX ON users (email);
CREATE INDEX ON users (created_at);

-- 4. 查询（等值时分区裁剪）
EXPLAIN SELECT * FROM users WHERE id = 12345;
-- Bitmap Heap Scan on users_p11      <- 只扫一个分区

-- 5. 跨分区查询（无裁剪）
EXPLAIN SELECT * FROM users WHERE email = 'a@b.com';
-- Append
--   -> 16 个分区都扫
```

要点：HASH 分区的 email 查询要求**每个分区独立索引**，等值时仍快（16 次小索引扫总和接近一次大索引）。

### 11.3 案例 C：时序 + 租户双维

```sql
CREATE TABLE events (
  ts TIMESTAMPTZ NOT NULL,
  tenant_id BIGINT NOT NULL,
  user_id BIGINT,
  payload JSONB
) PARTITION BY RANGE (ts);

CREATE TABLE events_2026_05 PARTITION OF events
  FOR VALUES FROM ('2026-05-01') TO ('2026-06-01')
  PARTITION BY HASH (tenant_id);

-- 子分区
DO $$
BEGIN
  FOR i IN 0..7 LOOP
    EXECUTE format(
      'CREATE TABLE events_2026_05_t%s PARTITION OF events_2026_05 FOR VALUES WITH (MODULUS 8, REMAINDER %s)',
      i, i);
  END LOOP;
END$$;
```

查询 "tenant 42 在 5 月的数据" → 1 个月分区 × 1 个 hash 分区 = 1 个叶子分区。

## 第十二章：监控分区健康

### 12.1 查所有分区

```sql
SELECT
  schemaname || '.' || tablename AS partition,
  pg_size_pretty(pg_total_relation_size(schemaname || '.' || tablename)) AS size
FROM pg_tables
WHERE schemaname = 'public' AND tablename LIKE 'orders_%'
ORDER BY pg_total_relation_size(schemaname || '.' || tablename) DESC;
```

### 12.2 查分区元数据

```sql
SELECT
  c.relname AS partition,
  pg_get_expr(c.relpartbound, c.oid) AS range
FROM pg_class c
JOIN pg_inherits i ON i.inhrelid = c.oid
JOIN pg_class p ON p.oid = i.inhparent
WHERE p.relname = 'orders';
```

## 生产实践

### 实践 1：分区设计前先回答 5 个问题

1. 主要查询的 WHERE 是否包含分区键？
2. 分区键的值分布是否均匀？
3. 数据有保留期吗？多久 DROP 旧数据？
4. 单分区目标大小 10-100 GB（太小是浪费、太大失去意义）？
5. 全局唯一性需求是什么？（是否能接受 PG 的限制？）

### 实践 2：迁移路径

把已有大表迁到分区表：

1. 用相同 schema 创建分区表（不同表名 `orders_new`）
2. 后台批量插入旧数据到对应分区（按月切批）
3. 用 logical replication 或双写让两表保持同步
4. 在维护窗口里 `ALTER TABLE orders RENAME TO orders_old; ALTER TABLE orders_new RENAME TO orders;`
5. 验证后 DROP `orders_old`

### 实践 3：分区与 VACUUM

每个分区独立 vacuum。autovacuum 工作正常，但要注意：

- 历史分区（只读）→ `ALTER TABLE ... SET (autovacuum_enabled = false)`，节省资源
- 当前写入分区 → 监控 dead tuple 比例

### 实践 4：分区与索引重建

REINDEX 单个分区比 REINDEX 整张表快得多：

```sql
REINDEX INDEX CONCURRENTLY orders_2026_05_pkey;
```

### 实践 5：DEFAULT 分区的"垃圾房"风险

DEFAULT 分区是"应急用"。在 cron 里定期检查 DEFAULT 行数：

```sql
SELECT count(*) FROM orders_default;
```

> 0 就告警，手工把数据搬走 + TRUNCATE。

### 实践 6：分区数量"上限观察"

观察 pg_stat_statements 中分区表查询的 `mean_plan_time`：

```sql
SELECT query, mean_plan_time, mean_exec_time
FROM pg_stat_statements WHERE query LIKE '%orders%';
```

如果 `mean_plan_time` > `mean_exec_time` * 0.5 → 分区太多，合并粒度。

### 实践 7：pg_partman 上线 checklist

- [ ] pg_cron 已装并启动
- [ ] cron 跑 `partman.run_maintenance()` 每小时
- [ ] 模板表已配置好索引/权限
- [ ] retention 策略已设置
- [ ] 监控 pg_partman.part_config 表
- [ ] 有 DEFAULT 分区兜底（避免漏建）

### 实践 8：分区表的备份

`pg_dump` 默认会把整个分区表当一棵树 dump，恢复时也会恢复全部分区——OK 但慢。
要并行：`pg_dump -j 8 --section=data ...` 或分别 dump 各分区。

## 陷阱清单

| # | 陷阱 | 后果 | 解决 |
|---|---|---|---|
| 1 | 分区键被函数包装 | 不裁剪 | 改写 WHERE 用范围而非函数 |
| 2 | 没建 DEFAULT 分区 + 漏建未来分区 | 写入失败 | 加 DEFAULT 或预建足够分区 |
| 3 | DEFAULT 分区被堆满 | 失去意义 | 定期搬出 + TRUNCATE |
| 4 | 跨分区唯一约束 | 无法创建 | 把分区键加入 UNIQUE 列；或用 UUIDv7 |
| 5 | HASH 分区想扩容 | 全表重切 | 一次定 32/64/128，留余量 |
| 6 | 子分区层级过深 | 元数据爆炸 | 层级 ≤ 2 |
| 7 | 分区数太多（>1000） | Planning 慢 | 合并粒度（按月而非按天） |
| 8 | partition-wise join 默认关 | 大表 JOIN 慢 | `SET enable_partitionwise_join=on` |
| 9 | 历史分区一直跑 autovacuum | 浪费资源 | 关闭只读分区的 autovacuum |
| 10 | DETACH 阻塞业务 | 短暂锁 | PG 14+ 用 DETACH CONCURRENTLY |
| 11 | 把整张 GIN 建在大分区表 | 写入崩盘 | 用表达式 GIN，按分区独立 |
| 12 | 索引模板表改了但老分区没同步 | 老分区无新索引 | 显式 CREATE INDEX 在每个老分区 |
| 13 | 用 BRIN 但分区键和 BRIN 列不一致 | 选择性差 | BRIN 列应是物理顺序列 |
| 14 | 备份很慢 | pg_dump 单线程 | 并行 dump 或分区粒度备份 |
| 15 | pg_partman 维护任务漏跑 | 漏建未来分区 → 写入失败 | 监控 cron 任务状态 |

## 2026 现状

| 主题 | 2026 状态 |
|---|---|
| 声明式分区 | 工业可用（PG 10 至今 9 年） |
| DETACH CONCURRENTLY | PG 14+ 普及，几乎免锁分离 |
| ATTACH CONCURRENTLY | 还在社区讨论，尚未进入主线 |
| 全局唯一索引 | 仍是 PG 最大缺口；社区有 patch 但未合入 |
| 分区裁剪 | PG 17/18 持续优化 hash 分区裁剪 |
| 运行时裁剪 | 成熟，看 `Subplans Removed` |
| pg_partman | 5.x 主流，PG 18 兼容 |
| TimescaleDB | 时序压倒性首选；许可证争议持续 |
| Citus | 分布式分片成熟；PG 16/17 集成 |
| 云厂商分区 | AWS RDS / Aurora / GCP CloudSQL 全支持 |
| HypertableV3 | TimescaleDB 引入下一代，更接近 PG 原生分区 |
| 列存分区 | citus columnar / hydra 提供列存分区 |

   - (b) 多租户 SaaS，5000 个租户，业务严格隔离

   - (d) 历史价格表，按商品+时间双维度查询

2. **DEFAULT 陷阱**：以下顺序会发生什么？
   ```sql
   CREATE TABLE t (ts TIMESTAMPTZ) PARTITION BY RANGE (ts);
   CREATE TABLE t_default PARTITION OF t DEFAULT;
   INSERT INTO t VALUES ('2026-05-15');   -- 落到 t_default
   CREATE TABLE t_may PARTITION OF t FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');
   ```
   提示：DEFAULT 中的数据如何处理？

3. **分区裁剪诊断**：以下两个查询哪个走分区裁剪？
   ```sql
   SELECT * FROM orders WHERE date_trunc('month', created_at) = '2026-05-01';
   SELECT * FROM orders WHERE created_at >= '2026-05-01' AND created_at < '2026-06-01';
   ```
   用 EXPLAIN 验证。

6. **pg_partman 脚本**：写一个 pg_partman 配置，使得 `events` 表按天分区，预建 7 天，保留 30 天。

7. **DETACH CONCURRENTLY**：解释 DETACH PARTITION CONCURRENTLY 的两阶段过程，以及为何不能在事务里执行。

8. **partition-wise join**：写一个会触发 partition-wise join 的查询，并解释什么条件下 planner 会选择 partition-wise。
