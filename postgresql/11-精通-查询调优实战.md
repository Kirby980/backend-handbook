## 引言：从"会看 EXPLAIN"到"会调优"

P09 让你理解了 planner 怎么"想"，P10 教会你读 EXPLAIN 的每一行。但生产环境里 DBA / 后端工程师每天面对的是另一套问题：

- 早上一打开 Grafana，"接口 P99 从 80ms 涨到 1.2s"——是哪条 SQL？
- 凌晨发版后，某张表 CPU 飙到 95%——是哪条 SQL？
- 测试环境跑得飞快，生产慢 100 倍——是哪条 SQL？
- 老板拍着桌子问"分页到第 10000 页超时怎么办"——这是设计问题，不是数据库问题。

查询调优的本质从来不是"把 SQL 改得更花哨"，而是 **定位 → 解读 → 重写或加索引 → 验证**，并把这套循环工程化。这一章把整套流程拆开讲透：从 `pg_stat_statements` 怎么把"实例所有 SQL"聚合成 digest，到 `auto_explain` 怎么自动抓"偶发慢 SQL"的执行计划，到 8 种最常见的"慢 SQL 重写套路"，再到并行查询、JIT、prepared statement、`work_mem`、`CREATE STATISTICS` 等高级武器。

读完这一章你应该能：

- 用 `pg_stat_statements` 列出 top-10 高消耗 SQL 并解读字段含义
- 配置 `auto_explain` 自动落地慢查询的执行计划
- 准确识别覆盖索引、部分索引、表达式索引、多列索引顺序的适用场景
- 把 OFFSET 大分页、NOT IN、子查询、SELECT \* 等"经典反模式"重写为高效形式
- 控制并行查询的开启与关闭，理解 `parallel_setup_cost` 怎么影响选择
- 区分 prepared statement 的 custom plan 与 generic plan，看到 plan flip
- 给出针对单表的 `STATISTICS 1000` 与 `CREATE STATISTICS` 处理多列相关性
- 完整复盘 6 个真实生产案例

## 第一章：pg_stat_statements——digest 化的 SQL 仪表盘

### 1.1 它是什么

`pg_stat_statements` 是 PostgreSQL 官方 contrib 扩展，自 9.4 起趋于成熟，在 13 / 14 / 15 几个版本上又陆续补全了 `plan_time` / 多个 `_exec_time` 字段。它做的事一句话总结：**把所有跑过的 SQL 按"参数化后的指纹（query id）"聚合成统计行**，常驻共享内存。

举个例子，下面三条业务 SQL 在它眼里是同一行：

```sql
SELECT * FROM users WHERE id = 1;
SELECT * FROM users WHERE id = 42;
SELECT * FROM users WHERE id = 1024;
```

聚合后变成：

```sql
SELECT * FROM users WHERE id = $1
-- calls = 3, total_exec_time = 12ms, mean_exec_time = 4ms, ...
```

这就是"digest 化"，让你能跨千万次执行做统计聚合，而不是被字面值淹没。

### 1.2 安装

`pg_stat_statements` 是 contrib 扩展，默认已经随 `postgresql-contrib` 包发出，但需要两步才能用起来：

第一步，写入 `postgresql.conf`：

```conf
shared_preload_libraries = 'pg_stat_statements'

# 推荐配置
pg_stat_statements.max = 10000        # 跟踪的 digest 上限，超出 LRU 淘汰
pg_stat_statements.track = all        # all / top / none：all 跟踪含子语句的 SQL
pg_stat_statements.track_utility = on # 跟踪 DDL / VACUUM 等非 DML
pg_stat_statements.save = on          # 重启保留累计统计
```

由于 `shared_preload_libraries` 在 `postmaster` 启动时加载，**必须重启 PostgreSQL**：

```bash
sudo systemctl restart postgresql
```

第二步，在你要分析的库里建扩展（每个库都要建一次）：

```sql
CREATE EXTENSION pg_stat_statements;
-- 验证
\dx pg_stat_statements
```

如果云数据库（RDS / Cloud SQL / Aliyun RDS / 腾讯云 TDSQL-C 等）已经预启用，仅需第二步。

### 1.3 关键字段（PG 16/17/18 视角）

`pg_stat_statements` 视图字段非常多，按用途分组记忆：

| 字段 | 含义 | 典型用途 |
|---|---|---|
| `queryid` | digest 哈希 | join `pg_stat_activity` 找正在执行的 SQL |
| `query` | 参数化后的 SQL 文本（$1, $2...） | 显示 |
| `calls` | 调用次数 | 找热 SQL |
| `total_exec_time` | 累计执行时间（ms） | **真正的"贵 SQL"指标** |
| `mean_exec_time` | 平均执行时间 | 单次慢的 SQL |
| `min_exec_time` / `max_exec_time` / `stddev_exec_time` | 极值与抖动 | 找"偶尔很慢"的 SQL |
| `rows` | 累计返回行数 | 找"批量返回"型 |
| `shared_blks_hit` | 缓冲命中页数 | I/O 命中率 |
| `shared_blks_read` | 从磁盘读的页数 | I/O 压力来源 |
| `shared_blks_dirtied` | 标脏页数 | 写入热点 |
| `shared_blks_written` | 被 backend 直接写出的页数 | bgwriter / checkpoint 压力 |
| `local_blks_*` | 临时表 I/O | 大量临时表统计 |
| `temp_blks_read` / `temp_blks_written` | 溢出到磁盘的临时空间 | `work_mem` 不足的强信号 |
| `blk_read_time` / `blk_write_time` | I/O 等待时间（要 `track_io_timing=on`） | I/O 瓶颈定位 |
| `wal_records` / `wal_fpi` / `wal_bytes` | 产生的 WAL 量（PG 13+） | 大事务 / 频繁更新定位 |
| `total_plan_time` / `mean_plan_time`（PG 13+） | 规划耗时 | 复杂 SQL 频繁重规划 |
| `jit_*`（PG 15+） | JIT 编译统计 | JIT 是否值得开 |

> 关于"执行时间字段"：PG 13 之前叫 `total_time`，PG 13 拆成 `total_plan_time` + `total_exec_time`。后续示例统一用 PG 13+ 字段名。

### 1.4 找 top-N 慢 SQL 的常用 SQL

最常用的"五条武器 SQL"，建议存到一个 `slow.sql` 文件里随手 `\i`：

**1) 按累计执行时间 top-10**

```sql
SELECT
  substr(query, 1, 80)         AS query,
  calls,
  round(total_exec_time::numeric, 2) AS total_ms,
  round(mean_exec_time::numeric, 2)  AS mean_ms,
  rows,
  100.0 * shared_blks_hit / nullif(shared_blks_hit + shared_blks_read, 0) AS hit_pct
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

这条最能反映"消耗最多 CPU / I/O 时间的 SQL"。哪怕单次只有 5ms，调用一亿次也是巨头。

**2) 按平均执行时间 top-10**

```sql
SELECT
  substr(query, 1, 80) AS query,
  calls,
  round(mean_exec_time::numeric, 2) AS mean_ms,
  round(stddev_exec_time::numeric, 2) AS stddev_ms,
  round(max_exec_time::numeric, 2)   AS max_ms
FROM pg_stat_statements
WHERE calls > 100
ORDER BY mean_exec_time DESC
LIMIT 10;
```

加 `calls > 100` 过滤掉只跑过几次的 ad-hoc SQL，避免噪声。

**3) 按 I/O 找慢 SQL**

```sql
SELECT
  substr(query, 1, 80) AS query,
  shared_blks_read,
  shared_blks_hit,
  round(blk_read_time::numeric, 2) AS read_ms,
  round(100.0 * shared_blks_hit / nullif(shared_blks_hit + shared_blks_read, 0), 1) AS hit_pct
FROM pg_stat_statements
ORDER BY shared_blks_read DESC
LIMIT 10;
```

`shared_blks_read` 大意味着这条 SQL 经常从盘上读，是缓冲池效率低或表太大。需要 `track_io_timing = on` 才有 `blk_read_time`。

**4) 找产生 WAL 多的 SQL**

```sql
SELECT
  substr(query, 1, 80) AS query,
  calls,
  pg_size_pretty(wal_bytes) AS wal,
  wal_records,
  wal_fpi
FROM pg_stat_statements
WHERE wal_bytes > 0
ORDER BY wal_bytes DESC
LIMIT 10;
```

定位"主要 WAL 产生者"，对复制延迟、归档大小、磁盘写入 IOPS 都有意义。`wal_fpi` 是 full page image 数，说明 checkpoint 后修改了大量新页。

**5) 找临时文件溢出**

```sql
SELECT
  substr(query, 1, 80) AS query,
  calls,
  pg_size_pretty(temp_blks_read * 8192::bigint)    AS temp_read,
  pg_size_pretty(temp_blks_written * 8192::bigint) AS temp_written
FROM pg_stat_statements
WHERE temp_blks_written > 0
ORDER BY temp_blks_written DESC
LIMIT 10;
```

`temp_blks_written > 0` 说明 sort / hash 溢出到磁盘了——直接对应 `work_mem` 不足。

### 1.5 重置统计

调优一轮后想看"最近 1 小时"的状况：

```sql
SELECT pg_stat_statements_reset();           -- 重置全部
SELECT pg_stat_statements_reset(userid, dbid, queryid);  -- 只重置某条
```

业务脚本里也可以周期 reset，比如每 1 小时存一次 snapshot 进 `pg_stat_history` 表，做时序对比。

### 1.6 与 pg_stat_activity 联动

`pg_stat_activity` 有 `query_id` 字段（PG 14+ 默认开 `compute_query_id = auto`），可以把"正在执行的连接"与 `pg_stat_statements` 关联：

```sql
SELECT
  a.pid, a.usename, a.application_name,
  a.state, now() - a.xact_start AS xact_age,
  substr(s.query, 1, 60) AS query,
  s.calls, round(s.mean_exec_time::numeric, 2) AS mean_ms
FROM pg_stat_activity a
LEFT JOIN pg_stat_statements s ON a.query_id = s.queryid
WHERE a.state = 'active' AND a.pid <> pg_backend_pid();
```

这能在事故现场迅速回答："此刻最热的 SQL 是不是我担心的那条"。

## 第二章：auto_explain——自动抓现场的"慢查询黑匣子"

### 2.1 为什么需要它

`pg_stat_statements` 看的是"统计"，但调优需要看"那一次具体执行的 EXPLAIN ANALYZE"——参数不同，plan 可能完全不同（参考第八章 prepared statement plan flip）。光看聚合数字不够。

`auto_explain` 是另一个 contrib 扩展，能在 SQL 超过阈值时**自动 dump 它的 EXPLAIN ANALYZE 到日志**。它的角色相当于"慢查询行车记录仪"。

### 2.2 配置

```conf
shared_preload_libraries = 'pg_stat_statements, auto_explain'

# 阈值（ms），-1 表示不开
auto_explain.log_min_duration = 1000

# 类似 EXPLAIN (ANALYZE, BUFFERS, VERBOSE) 的开关
auto_explain.log_analyze = on        # 真实执行（开销稍高，生产建议配合采样）
auto_explain.log_buffers = on
auto_explain.log_verbose = off
auto_explain.log_settings = on       # PG 12+：把非默认 GUC 写入日志
auto_explain.log_wal = on            # PG 13+：记录 WAL 量
auto_explain.log_format = 'text'     # text / json / xml / yaml
auto_explain.log_nested_statements = on  # 函数内 SQL 也记
auto_explain.log_triggers = off

# 采样：只对 1% 的请求开 ANALYZE，避免高 QPS 下开销
auto_explain.sample_rate = 0.01
```

无需重启即可改大部分参数（`LOAD 'auto_explain';` 后通过 `ALTER SYSTEM SET ... ; SELECT pg_reload_conf();`），但首次启用 `shared_preload_libraries` 仍需重启。

### 2.3 日志样例

下面是一条典型输出（节选 + 注释）：

```
LOG:  duration: 2384.521 ms  plan:
  Query Text: SELECT u.id, u.name, count(o.id) FROM users u LEFT JOIN orders o ...
  GroupAggregate  (cost=0.86..245678.21 rows=12000 width=20)
    (actual time=15.221..2380.842 rows=11843 loops=1)
    Buffers: shared hit=18421 read=42193 dirtied=12
    ->  Merge Left Join  (cost=...) (actual time=...) loops=1
          Merge Cond: (u.id = o.user_id)
          ->  Index Scan using users_pkey on users u ...
                Buffers: shared hit=15321
          ->  Index Scan using idx_orders_user_id on orders o ...
                Buffers: shared hit=3100 read=42193
  Settings: work_mem = '32MB', random_page_cost = '1.1'
```

注意 `Buffers: shared read=42193` 这一行——表明读了 42193 个 page（约 328 MB），是这次慢的主要原因。

### 2.4 配合 pgBadger / pganalyze

`auto_explain` 输出的日志可以被 [pgBadger](https://pgbadger.darold.net/) 这类工具自动聚合，生成 HTML 报告。云厂商的 PG 服务（pganalyze、Datadog Database Monitoring）也会自动消费 `auto_explain` 日志生成"plan 变化时间轴"，对 plan flip 排查非常关键。

### 2.5 还有 log_min_duration_statement

`log_min_duration_statement = 1000`（写在 `postgresql.conf`）是更简单的方案，只记录 SQL 文本不带 plan。两者经常组合：

```conf
log_min_duration_statement = 200      # 200ms 以上记 SQL 文本
auto_explain.log_min_duration = 1000  # 1s 以上记 plan
```

200ms 的频次更高，仅用于趋势；1s 的会带 plan，用于精细分析。

## 第三章：索引选择实战——五种"高级"索引

P04 / P05 讲了索引类型（B-tree、GIN、GiST、SP-GiST、BRIN、Hash、Bloom）。这一章只讲"索引怎么用得更聪明"——很多 PG 用户从 MySQL 过来，只会"在列上建普通索引"，错过了 PG 真正强大的几把武器。

### 3.1 覆盖索引（INCLUDE 列）

**核心想法**：把"非过滤但需要返回"的列塞进索引的 leaf payload，避免 heap 回表（Index Only Scan）。

```sql
-- 痛点：order_id 是查询条件，但要返回 status / amount
SELECT status, amount FROM orders WHERE order_id = 'O-123';

-- 普通索引：每次都得回表读 status / amount
CREATE INDEX idx_orders_order_id ON orders(order_id);

-- 覆盖索引（PG 11+ 支持 INCLUDE）
CREATE INDEX idx_orders_order_id_inc ON orders(order_id) INCLUDE (status, amount);
```

INCLUDE 列**不参与排序**（只是 payload），所以不要把它放到索引顺序里去——那会增加 B-tree 的体积和写入成本。

**Index Only Scan 的另一个前提**：visibility map 中该 heap page 必须是 all-visible（最近 vacuum 过）。否则 PG 仍然要回表确认行可见性。所以——

```sql
VACUUM ANALYZE orders;  -- 更新 VM，让 Index Only Scan 真正"only"
```

EXPLAIN 中 `Heap Fetches` 行能告诉你回表次数：

```
Index Only Scan using idx_orders_order_id_inc on orders ...
  Heap Fetches: 0      ← 完美的覆盖
```

如果 `Heap Fetches` 比 `rows` 大，说明 VM 不新鲜，要么调高 autovacuum 频率，要么定期 `VACUUM`。

### 3.2 部分索引（Partial Index）

**核心想法**：只为部分行建索引——当筛选条件高度集中时，索引可以缩小 90%+。

最经典的场景：状态字段。多数业务的订单表里 99% 是 `completed`，只有 1% 是 `pending`，但你的后台界面天天扫 pending：

```sql
-- 普通索引：1 亿行的 B-tree
CREATE INDEX idx_orders_status ON orders(status);

-- 部分索引：只索引 100 万行，小 100 倍
CREATE INDEX idx_orders_pending
  ON orders(created_at)
  WHERE status = 'pending';

-- 查询
SELECT * FROM orders WHERE status = 'pending' ORDER BY created_at DESC LIMIT 100;
```

更妙的用法：唯一约束限制范围。

```sql
-- 每个用户只能有 1 个 active 订阅，但可以有多个过期订阅
CREATE UNIQUE INDEX uniq_active_subscription
  ON subscriptions(user_id)
  WHERE status = 'active';
```

部分索引的代价：**planner 必须证明你的 WHERE 条件能"蕴含"索引谓词**。`status = 'pending'` 能命中 `WHERE status = 'pending'`，但 `status IN ('pending', 'failed')` 就不行。条件越复杂，命中越脆弱，建索引时要保持谓词简单。

### 3.3 表达式索引（Functional / Expression Index）

**核心想法**：当 WHERE 用的是函数包过的列，普通索引失效；把"函数表达式"做成索引。

```sql
-- 痛点：lower() 包住列后，列上的索引失效
SELECT * FROM users WHERE lower(email) = 'alice@x.com';
--                       ↑ 普通 idx(email) 用不上

-- 表达式索引
CREATE INDEX idx_users_lower_email ON users(lower(email));

-- 此时上面查询能走索引
```

JSONB 的"高频路径"是表达式索引的另一个杀手锏：

```sql
-- JSONB 数据：{"tags": ["sale", "summer"], "price": 99.9, "vendor": {"id": 42}}

-- 高频路径：vendor.id
CREATE INDEX idx_products_vendor
  ON products((data->'vendor'->>'id'));

-- 数值化（JSONB 默认是 text）
CREATE INDEX idx_products_price
  ON products(((data->>'price')::numeric));

-- 数组：用 GIN
CREATE INDEX idx_products_tags
  ON products USING gin ((data->'tags'));
```

注意：

- **表达式必须 IMMUTABLE**。`now()`、`random()`、与时区相关的函数都不行。
- **查询里必须用一模一样的表达式**。`(data->>'price')::numeric` 建的索引，`((data->>'price')::int)` 用不上。
- 表达式索引相当于把表达式结果物化进索引，更新该列的"输入"会触发索引行重写——重的表达式注意写放大。

### 3.4 多列索引顺序：高选择性优先 vs 范围列后置

经典的"多列索引顺序"题，PG 与 MySQL 规则一致，但更宽容（PG 17+ 在某些场景能 skip scan 跳过前缀列）。**默认仍按这两条原则**：

**原则 1：等值列前，范围列后**

```sql
-- 业务：按时间倒序列出某个用户最近的订单
SELECT * FROM orders WHERE user_id = ? AND created_at > ? ORDER BY created_at DESC;

-- 正确：等值列前
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at);

-- 错误：范围列前，user_id 还得"跳跃"匹配
CREATE INDEX idx_orders_created_user ON orders(created_at, user_id);
```

**原则 2：高选择性列前（但仅在等值列里比较）**

```sql
-- region 有 7 个值，user_id 有千万级
SELECT * FROM events WHERE user_id = ? AND region = ?;

-- 正确
CREATE INDEX idx_events_user_region ON events(user_id, region);
```

但 PG 16+ 改进了 B-tree skip scan，对前缀列基数低的索引也能跳着走（叫"loose index scan"）。仍然推荐显式按高选择性排列，以兼容老版本。

**复合排序场景**：

```sql
-- 倒序混合升序的排序
ORDER BY created_at DESC, id ASC

-- 索引也要匹配方向才能避免 sort
CREATE INDEX idx ON orders(user_id, created_at DESC, id ASC);
```

### 3.5 BRIN 与时序大表

P05 详细讲过 BRIN（块范围索引）。这里再强调一句调优视角：**单调递增的 timestamp 列上的 1 亿行表，B-tree 索引 2 GB+，BRIN 索引 1 MB**。

```sql
CREATE INDEX idx_logs_ts_brin
  ON logs USING brin(ts)
  WITH (pages_per_range = 32);
```

代价：选择性远不如 B-tree。但配合 `WHERE ts BETWEEN '2026-05-01' AND '2026-05-02'` 这种范围扫描，能很快定位到几个 block range，比顺扫快几十倍。

### 3.6 一张索引选择速查表

| 场景 | 推荐索引 |
|---|---|
| 主键 / 唯一 / 等值 / 范围 | B-tree |
| 大量行中 5% 热点（状态 / 标志位） | B-tree + WHERE 部分索引 |
| 函数包列 / lower() / 时区转换 | 表达式索引（B-tree on expr） |
| JSONB 高频路径（`data->>'k'`） | 表达式索引（B-tree） |
| JSONB 任意键查询（`data @> '{...}'`） | GIN on JSONB |
| 全文检索（tsvector） | GIN（或 GiST 优化更新频繁场景） |
| 数组包含 / && | GIN |
| 几何 / 范围类型 / kNN | GiST |
| 单调递增的时序列 | BRIN |
| 高基数 + 等值 + 不需要排序 | Hash（PG 10+ 有 WAL） |
| INSERT 频繁、读极少（流水表） | 干脆不建索引 |

## 第四章：慢 SQL 重写 8 大套路

下面 8 种是生产里反复出现的"典型反模式"。每条都给出"反模式 → 重写 → 原理"。

### 4.1 OFFSET 大分页 → keyset pagination

**反模式**：

```sql
SELECT * FROM events
ORDER BY id DESC
OFFSET 100000 LIMIT 10;
```

PG 的 OFFSET 不能"跳过"——它必须**真的扫过前 100000 行再丢弃**。第 1000 页慢 1000 倍，第 10000 页慢一万倍。

**重写：keyset / cursor pagination**

```sql
-- 第一页
SELECT * FROM events ORDER BY id DESC LIMIT 10;
-- 客户端记下最后一行的 id = last_id

-- 第二页
SELECT * FROM events WHERE id < :last_id ORDER BY id DESC LIMIT 10;
```

直接走 B-tree 索引定位 `last_id`，复杂度从 `O(offset + limit)` 降到 `O(log N + limit)`。

**复合排序的 keyset**（按 created_at 然后 id）：

```sql
SELECT * FROM events
WHERE (created_at, id) < (:last_ts, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 10;
```

PostgreSQL 支持元组比较 `(a, b) < (x, y)`，等价于 `a < x OR (a = x AND b < y)`，能直接走 `(created_at, id)` 索引。

什么时候 keyset 不适用：必须跳到任意页（`LIMIT 10 OFFSET 5000` 这种"第 500 页"链接式分页）。但事实上几乎没有用户翻到第 500 页——前端改成无限滚动 / 「Load more」按钮即可。

### 4.2 NOT IN（含 NULL 陷阱）→ NOT EXISTS / LEFT JOIN

**反模式**：

```sql
SELECT * FROM users
WHERE id NOT IN (SELECT user_id FROM blocked);
```

两个问题：

1. **NULL 陷阱**：如果 `blocked.user_id` 含 NULL，整条 SQL 返回空集（因为 `id NOT IN (1, 2, NULL)` 在 SQL 三值逻辑下永远不为 true）。
2. **性能**：NOT IN 不能反半连接（anti-join），常退化为 hash 或 sort+merge 的形式，且 NULL 处理逻辑复杂。

**重写**：

```sql
-- 推荐：NOT EXISTS
SELECT *
FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM blocked b WHERE b.user_id = u.id
);

-- 或：LEFT JOIN + IS NULL（hash anti join 形式）
SELECT u.*
FROM users u
LEFT JOIN blocked b ON b.user_id = u.id
WHERE b.user_id IS NULL;
```

两种都能让 planner 走 **Hash Anti Join** 或 **Nested Loop Anti Join**，性能与 INNER JOIN 同一量级，且不受 NULL 影响。

### 4.3 子查询 → LATERAL JOIN（尤其 top-N per group）

**反模式：top-N per user**

```sql
-- "每个用户最近 5 条订单"——经典坑
SELECT *
FROM orders o
WHERE o.user_id IN (SELECT id FROM users WHERE region = 'CN')
  AND (
    SELECT count(*) FROM orders o2
    WHERE o2.user_id = o.user_id AND o2.created_at > o.created_at
  ) < 5;
```

这条子查询每行触发一次，巨慢。

**重写：LATERAL JOIN**

```sql
SELECT o.*
FROM users u
JOIN LATERAL (
  SELECT * FROM orders o
  WHERE o.user_id = u.id
  ORDER BY o.created_at DESC
  LIMIT 5
) o ON true
WHERE u.region = 'CN';
```

LATERAL 让子查询能引用外层的 `u.id`，每个用户独立执行一次 `ORDER BY ... LIMIT 5`，配合 `(user_id, created_at DESC)` 索引可以变成 5 行 index scan。复杂度从 `O(N*M)` 降到 `O(U * log N)`，U 是用户数。

另一种写法是窗口函数：

```sql
SELECT *
FROM (
  SELECT o.*, row_number() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
  FROM orders o
  JOIN users u ON u.id = o.user_id
  WHERE u.region = 'CN'
) t
WHERE rn <= 5;
```

窗口函数对所有匹配行排序，再过滤 rn，**不能短路在 5**，所以数据集巨大时 LATERAL 仍然胜出。但代码更简洁，中小数据量可以无脑用窗口。

### 4.4 SELECT \* → 指定列

**反模式**：

```sql
SELECT * FROM users WHERE id = ?;
```

问题：

- 把每行所有列读进 backend，包括 TOAST'd 的 jsonb、bytea。即使你只用 id 和 name，也付了全部传输的钱。
- **破坏 Index Only Scan**：只要 SELECT 列不全在索引里，就必须回表。
- **PG 网络协议按行序列化**，列数多增加 CPU 编码开销。
- ORM 生成的 SELECT * 在表结构变更（加列）后突然变慢。

**重写**：明确列名。

```sql
SELECT id, name, email FROM users WHERE id = ?;
```

加上 INCLUDE 覆盖索引：

```sql
CREATE INDEX idx_users_id_inc ON users(id) INCLUDE (name, email);
-- 这条 SELECT 现在可能走 Index Only Scan
```

### 4.5 DISTINCT → GROUP BY（部分场景）

**反模式**：

```sql
SELECT DISTINCT user_id FROM events WHERE created_at > now() - interval '1 day';
```

DISTINCT 会触发 HashAggregate 或 Sort+Unique，对大量行内存压力大。

**重写（部分场景）**：

```sql
-- 1) GROUP BY 等价，planner 通常更优
SELECT user_id FROM events WHERE created_at > now() - interval '1 day' GROUP BY user_id;

-- 2) 如果有 (user_id, created_at) 索引，可用 loose index scan 模拟
SELECT user_id FROM events e
WHERE created_at > now() - interval '1 day'
  AND NOT EXISTS (
    SELECT 1 FROM events e2
    WHERE e2.user_id = e.user_id AND e2.id < e.id
  );
-- 实际上这种"递归 keyset"在 PG 里推荐用 WITH RECURSIVE
```

**注意**：DISTINCT 和 GROUP BY 在新版本 planner 已经能产出相同 plan，"DISTINCT 慢"主要在老版本或特殊场景，不要无脑替换。

### 4.6 IN（大量值）→ JOIN 临时表 / VALUES / unnest

**反模式**：

```sql
SELECT * FROM users WHERE id IN (1, 2, 3, ..., 10000);
```

PG 解析数千个值的 IN 列表本身有 CPU 成本，且 planner 经常退化为 BitmapOr，性能下降。

**重写**：

```sql
-- 1) unnest 数组（推荐）
SELECT u.*
FROM users u
JOIN unnest(ARRAY[1,2,3,...,10000]::bigint[]) AS t(id) ON u.id = t.id;

-- 2) VALUES 子表
SELECT u.*
FROM users u
JOIN (VALUES (1), (2), ..., (10000)) AS t(id) ON u.id = t.id;

-- 3) 真正临时表（最稳）
CREATE TEMP TABLE tmp_ids(id bigint PRIMARY KEY) ON COMMIT DROP;
INSERT INTO tmp_ids VALUES (...);
ANALYZE tmp_ids;
SELECT u.* FROM users u JOIN tmp_ids t ON u.id = t.id;
```

`unnest` 最优雅，传参也方便（Go 的 pgx 直接传 `[]int64`）。临时表适合"上万 + 多次使用"，要 ANALYZE 才有统计信息。

### 4.7 UNION → UNION ALL（如果不需要去重）

```sql
-- 反模式：UNION 自动 DISTINCT
SELECT id FROM table_a WHERE x = 1
UNION
SELECT id FROM table_b WHERE x = 1;

-- 重写：UNION ALL
SELECT id FROM table_a WHERE x = 1
UNION ALL
SELECT id FROM table_b WHERE x = 1;
```

UNION 必须 sort + unique 去重，UNION ALL 直接拼接。**确保两个子集没有交集时**用 UNION ALL，速度可以是几倍。

### 4.8 LIKE 与 pg_trgm

```sql
-- 前缀匹配，B-tree 能用（必须 C locale 或 text_pattern_ops）
SELECT * FROM users WHERE email LIKE 'alice%';

-- 索引（C locale 直接 OK；非 C locale 需要专用 opclass）
CREATE INDEX idx_users_email ON users(email text_pattern_ops);

-- 中间匹配 / 后缀匹配 B-tree 无能为力
SELECT * FROM users WHERE email LIKE '%@x.com';

-- 解法：pg_trgm + GIN
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_users_email_trgm ON users USING gin(email gin_trgm_ops);

-- 现在中间 / 后缀都能走索引
SELECT * FROM users WHERE email LIKE '%@x.com';
SELECT * FROM users WHERE email ILIKE '%alice%';
```

`pg_trgm` 把字符串拆成三字符 trigram 做倒排，是 PG 模糊匹配的杀手锏。代价：索引体积大、写入慢，并且对中文这种"两字一词"语言效果一般（中文用全文检索 + 中文分词更好，见 P12）。

## 第五章：并行查询

### 5.1 触发条件

PG 9.6 起支持并行查询，到 16/17/18 已经覆盖大部分 plan 节点（Parallel Seq Scan / Index Scan / Bitmap Heap Scan / Hash Join / Merge Join / Aggregate / Append）。但默认参数下不是每条 SQL 都会并行。

planner 选并行的条件（任一不满足都不并行）：

1. 表大小 ≥ `min_parallel_table_scan_size`（默认 8 MB）或索引大小 ≥ `min_parallel_index_scan_size`（默认 512 kB）。
2. 估算成本下降 > `parallel_setup_cost`（默认 1000.0）+ `parallel_tuple_cost * 估算行数`（默认 0.1）。
3. 当前会话 `max_parallel_workers_per_gather` > 0（默认 2）。
4. 实例全局 worker 池有空闲（`max_worker_processes` 默认 8, `max_parallel_workers` 默认 8）。
5. SQL 不在 PARALLEL UNSAFE / RESTRICTED 函数内。

### 5.2 关键参数速查

| 参数 | 默认 | 含义 |
|---|---|---|
| `max_worker_processes` | 8 | 实例级 worker 总池 |
| `max_parallel_workers` | 8 | 并行查询专用池（≤ max_worker_processes） |
| `max_parallel_workers_per_gather` | 2 | 单 Gather 节点最多用几个 worker |
| `max_parallel_maintenance_workers` | 2 | 索引构建等 DDL 并行 |
| `min_parallel_table_scan_size` | 8MB | 表小于这个，不考虑并行 |
| `min_parallel_index_scan_size` | 512kB | 索引小于这个，不考虑并行索引扫 |
| `parallel_setup_cost` | 1000.0 | 启动 worker 的成本 |
| `parallel_tuple_cost` | 0.1 | 通过 Gather 传一行的成本 |
| `force_parallel_mode` (≤14) / `debug_parallel_query` (15+) | off | 调试用，强制并行 |

### 5.3 调优实战

**默认值的问题**：`max_parallel_workers_per_gather = 2` 在 16 / 32 / 64 核机器上极保守。OLAP 报表类负载常把它调到 4 / 8。

```sql
-- 仅本会话
SET max_parallel_workers_per_gather = 8;

-- 系统级（需 reload）
ALTER SYSTEM SET max_parallel_workers_per_gather = 4;
SELECT pg_reload_conf();
```

EXPLAIN 中并行计划长这样：

```
Finalize Aggregate  (cost=...)
  ->  Gather  (cost=... rows=4 width=8)
        Workers Planned: 4
        Workers Launched: 4    ← 注意 Planned vs Launched，pool 不够会少
        ->  Partial Aggregate  ...
              ->  Parallel Seq Scan on events  ...
```

`Workers Launched < Workers Planned` 时说明 `max_parallel_workers` 或 `max_worker_processes` 不够，需要扩容。

**反例：并行反而更慢**

```sql
-- 表只有 50MB，并行 + Gather 开销大于扫描节省
SELECT count(*) FROM small_t;
-- 关闭
SET max_parallel_workers_per_gather = 0;
```

对小查询临时关并行，避免"启动 4 个 worker、扫完 10ms 就退出"的浪费。

**parallel_setup_cost 调小**：SSD + 大量短并行查询的 OLAP 场景，可调到 200-500，让 planner 更愿意走并行。

## 第六章：JIT 编译（PG 11+）

### 6.1 它是什么

JIT（Just-in-Time compilation）通过 LLVM 把"表达式求值"和"元组解构"动态编译成 native code。**对长跑的复杂查询**（OLAP / 大量过滤表达式）可以 10-30% 提速；对短跑查询反而拖慢——因为编译本身要几十 ms。

### 6.2 三道门槛

```conf
jit = on                              # 默认 on
jit_above_cost = 100000               # 总成本超过这个，才开 JIT
jit_inline_above_cost = 500000        # 进一步：函数 inline
jit_optimize_above_cost = 500000      # 进一步：LLVM optimize pass
```

意思是：

- cost < 10w：不 JIT
- 10w ≤ cost < 50w：JIT 但不 inline / optimize
- cost ≥ 50w：全开

### 6.3 看 JIT 收益

PG 15+ 在 EXPLAIN ANALYZE 输出末尾有 JIT 块：

```
JIT:
  Functions: 12
  Options: Inlining true, Optimization true, Expressions true, Deforming true
  Timing: Generation 1.524 ms, Inlining 11.231 ms, Optimization 42.184 ms,
          Emission 31.142 ms, Total 86.081 ms
```

`Total 86ms` 是编译成本——如果整条 SQL 本身只跑了 100ms，JIT 一半成本浪费在编译上。

`pg_stat_statements` 在 PG 15+ 也加了 `jit_functions` / `jit_generation_time` 等列，能聚合判断"哪类 SQL 因为 JIT 受益 / 受损"。

### 6.4 调优经验

- **OLTP 短查询多**：把 `jit_above_cost` 调到 500000 甚至 1000000，避免误开 JIT。
- **报表查询主导**：保持默认或调低。
- **整库关闭 JIT**：`jit = off`——很多 OLTP 业务的"实战经验值"。
- 升级到 PG 16+ 后，JIT 编译并行化（与 worker 并行），单查询延迟有所改善，但 `jit_above_cost` 偏低仍是常见坑。

## 第七章：prepared statement 与 plan flip

### 7.1 custom plan vs generic plan

prepared statement 把 SQL 与参数解耦：

```sql
PREPARE q AS SELECT * FROM users WHERE region = $1 AND active = $2;
EXECUTE q('CN', true);
```

PG 头 5 次执行用 **custom plan**——每次基于实际参数生成 plan。从第 6 次起，如果 **generic plan**（不带参数特化）的预估成本 ≤ custom plan 的平均成本 + 一定边际，PG 切到 **generic plan**，省掉规划时间。

控制参数：

```sql
SET plan_cache_mode = 'auto';        -- 默认：上面的逻辑
SET plan_cache_mode = 'force_custom_plan';
SET plan_cache_mode = 'force_generic_plan';
```

`auto` 内部的 "5 次" 也叫 `custom_plan_tries`，从 PG 17 起可调（更早版本是硬编码）。

### 7.2 plan flip 的灾难

经典坑：

```sql
PREPARE q AS SELECT * FROM events WHERE user_id = $1;
```

数据分布严重倾斜：90% 的 events 属于 user_id = 7（运营帐号）。前 5 次 EXECUTE 都传 `user_id = 7`，custom plan 选 Seq Scan（合理）。第 6 次切 generic plan，planner 用"平均选择性"估计 → 选 Index Scan，结果传 `user_id = 7` 时还是扫了 90% 的表，但走索引 → 大量 random I/O，比 Seq Scan 慢 10 倍。

**症状**：`pg_stat_statements` 看 mean 不慢，`auto_explain` 偶尔抓到一次慢得吓人；重启 / 重连后第一次又快。

**应对**：

```sql
-- 短期：强制 custom plan
SET plan_cache_mode = 'force_custom_plan';

-- 中期：连接池里禁用 server-side prepared statement
-- PgBouncer 在 transaction pool mode 下不能用 server-side prepare（限制）
-- pgx 可设 default_query_exec_mode = "exec"

-- 长期：解决数据倾斜（运营帐号单独表 / 分区）
```

### 7.3 怎么观察

PG 14+ 提供 `pg_prepared_statements` 视图，但看不到当前 plan 类型。最实用的办法：

```sql
SET auto_explain.log_min_duration = 100;
-- 跑业务，看日志里 plan，对比 generic_plan / custom_plan 的差异
```

PG 16+ 还能跑 `EXPLAIN (GENERIC_PLAN) EXECUTE q;` 看 generic plan 长啥样。

## 第八章：work_mem 调优

### 8.1 它是什么

`work_mem` 是**每个排序 / 哈希 / 聚合操作**能用的内存上限。**注意是 per-operation per-backend**——一条复杂 SQL 用了 3 个 sort + 2 个 hash，那一条 SQL 就吃 5 × work_mem；并发 100 条这样的 SQL，瞬间就是 500 × work_mem。

默认值 4MB 在 2026 年的 PG 仍然是出厂保守值。OLAP / 报表负载普遍调到 64MB / 128MB。

### 8.2 调小了的症状：临时文件

```sql
-- pg_stat_statements 里 temp_blks_written > 0 的 SQL
-- EXPLAIN ANALYZE 里出现：
Sort  (cost=...) (actual time=...)
  Sort Method: external merge  Disk: 124800kB
                    ↑ 溢出到磁盘
```

或者 hash join 里：

```
Hash  (cost=...) (rows=10000000)
  Buckets: 65536  Batches: 16  Memory Usage: 6789kB
                    ↑ 多 batch 表示溢出
```

### 8.3 调大了的代价

work_mem × max_connections × 每条 SQL 的 ops 数 是潜在内存上限。计算式：

```
peak_work_mem_bytes ≈ work_mem * max_connections * avg_ops_per_query
```

举例：work_mem = 64MB, max_connections = 200, avg_ops = 2 → 25.6 GB。一台 32 GB 机器立刻 OOM。

### 8.4 实战策略

1. **全局保守**：`work_mem = 8MB` 或 `16MB`。
2. **按 role / 按 SQL 临时上调**：
   ```sql
   -- 报表角色全局
   ALTER ROLE report_user SET work_mem = '256MB';

   -- 单条 SQL
   SET LOCAL work_mem = '256MB';
   SELECT ... ;
   ```
3. **PG 13+ 还有 `hash_mem_multiplier`**（默认 2.0）：hash 类操作的内存 = `work_mem * multiplier`。可以让 hash join 单独享更大内存而不连累 sort。

## 第九章：ANALYZE 与统计信息

### 9.1 单列高 STATISTICS

```sql
-- 默认 default_statistics_target = 100
SELECT * FROM pg_settings WHERE name = 'default_statistics_target';

-- 看某列当前 stats_target
SELECT attname, attstattarget FROM pg_attribute
WHERE attrelid = 'orders'::regclass AND attnum > 0;

-- 单列上调
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;
```

`STATISTICS 1000` 意味着采样更多行、直方图桶数更多（最多 10000）。**对极倾斜或基数极高的列**有效，但 ANALYZE 时间变长、`pg_statistic` 也变大。

### 9.2 CREATE STATISTICS——多列相关性

PG 10+ 引入扩展统计，解决"两列高度相关 → 多列谓词被严重低估"的问题。

经典反例：

```sql
-- 表 sales: city, country。country = 'CN' 蕴含 city ∈ {北京, 上海, 深圳...}
-- planner 默认假设两列独立：
--   P(city='北京' AND country='CN') = P(city='北京') * P(country='CN')
-- 实际：P(city='北京' AND country='CN') ≈ P(city='北京')，相差几百倍

EXPLAIN SELECT * FROM sales WHERE city = '北京' AND country = 'CN';
-- Estimated rows: 50    ← 严重低估
-- Actual rows: 50000
```

**解法**：

```sql
CREATE STATISTICS stats_city_country (ndistinct, dependencies, mcv)
  ON city, country FROM sales;
ANALYZE sales;
```

三种 stats:

- `ndistinct`：(city, country) 组合的不同值数
- `dependencies`：函数依赖（city → country）
- `mcv`：多列 most common values（PG 12+，最强力，处理任意 AND/OR 谓词）

**查看效果**：

```sql
SELECT * FROM pg_stats_ext WHERE statistics_name = 'stats_city_country';
```

调优后再 EXPLAIN，估算行数应该接近实际值。

### 9.3 自动 ANALYZE 的触发

autovacuum 不仅 vacuum，还 analyze：

```
触发：n_mod_since_analyze > autovacuum_analyze_threshold +
                            autovacuum_analyze_scale_factor * reltuples
默认 autovacuum_analyze_scale_factor = 0.1
```

**大表上 0.1 太大**，1 亿行表要插入 / 修改 1000 万行才触发 analyze——这中间统计信息严重过期。对大表显式 override：

```sql
ALTER TABLE big_t SET (autovacuum_analyze_scale_factor = 0.01);
```

## 第十章：表膨胀对查询的影响

P08 已经讲过 VACUUM、autovacuum 和 wraparound。这里只补一句**对查询调优的视角**：

膨胀（dead tuple 占比高）会让以下变慢：

- Seq Scan：扫描的"垃圾页"变多
- Index Scan：B-tree page 含 dead tuple → bloat → cache 命中下降
- 统计信息失真：直方图基于 reltuples，dead tuple 不计但反映在物理 I/O 上

检查膨胀：

```sql
-- pgstattuple（contrib 扩展）
CREATE EXTENSION pgstattuple;
SELECT * FROM pgstattuple('orders');
-- dead_tuple_percent 持续 > 20% 是危险信号

-- 或简易估算
SELECT n_dead_tup, n_live_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct
FROM pg_stat_user_tables
WHERE relname = 'orders';
```

调优思路：

- autovacuum 调激进：`autovacuum_vacuum_scale_factor = 0.05`
- 大批量 UPDATE / DELETE 后**手动 ANALYZE**（不需要 VACUUM FULL，除非真的膨胀）
- 周期性 `pg_repack`（无锁，比 VACUUM FULL 友好）

详见 [P08 VACUUM 与表膨胀](./08-精通-VACUUM-与表膨胀.md)。

## 第十一章：完整案例 1——1 亿行表 OFFSET 100000 慢爆

### 11.1 现场

电商搜索结果页，URL 是 `?page=10000`，对应 SQL：

```sql
SELECT id, title, price, image_url
FROM products
WHERE category_id = 42
ORDER BY published_at DESC, id DESC
OFFSET 100000 LIMIT 20;
```

`products` 表 1.2 亿行，`category_id = 42` 命中 600 万行。生产 P99 = 5.4 秒，CPU 飙到 70%。

### 11.2 EXPLAIN

```
Limit  (cost=128471.21..128475.61 rows=20 width=84) (actual time=5421.12..5421.31 rows=20)
  ->  Sort  (...) (actual rows=100020 loops=1)
        Sort Key: published_at DESC, id DESC
        Sort Method: top-N heapsort  Memory: 32kB
        ->  Index Scan using idx_products_category on products
            (rows=600000) (actual rows=600000 loops=1)
            Index Cond: (category_id = 42)
            Buffers: shared hit=82193 read=384912
```

诊断：planner 走索引读了 60 万行，sort 后丢 100000 行只留 20 行——**典型 OFFSET 大分页**。

### 11.3 优化第一版：keyset

```sql
-- 不再支持"任意页跳转"，改为"加载更多"
SELECT id, title, price, image_url
FROM products
WHERE category_id = 42
  AND (published_at, id) < (:last_ts, :last_id)
ORDER BY published_at DESC, id DESC
LIMIT 20;
```

索引调整：

```sql
CREATE INDEX idx_products_cat_pub_id
  ON products(category_id, published_at DESC, id DESC);
```

新 EXPLAIN：

```
Limit  (cost=0.56..3.21 rows=20 width=84) (actual time=0.18..0.42 rows=20)
  ->  Index Scan using idx_products_cat_pub_id on products
        (actual rows=20 loops=1)
        Index Cond: ((category_id = 42) AND (...) < (:last_ts, :last_id))
        Buffers: shared hit=8
```

P99 从 5.4s → 1ms。前端把分页改成「加载更多」，业务 OK。

### 11.4 进阶：要"跳到第 N 页"怎么办

业务确实要任意页跳，三个备选：

- **cached offset**：后台周期算"每 1000 页第一行的 cursor"，存 Redis，跳转时查 cursor。
- **基数限制**：只允许前 100 页跳转，再深的折叠成"加载更多"。这是 Google 搜索的策略。
- **结果集预计算**：把当前 category 的所有 id 物化到 redis ZSet，按 score = published_at 排序，分页变成 ZRANGE。适合活跃 SKU 数有限。

## 第十二章：完整案例 2——大批量 UPDATE 锁等待与 WAL 暴涨

### 12.1 现场

凌晨任务：把 `orders.region` 从代码值改成 ISO code，3000 万行：

```sql
UPDATE orders SET region = iso_map[region] WHERE region IN ('cn', 'us', ...);
```

20 分钟后还在跑，复制延迟从 0 涨到 8 分钟，磁盘 IOPS 拉满，主库 connections 堆积。

### 12.2 问题分析

- **单事务 3000 万行 UPDATE**：表锁升级到 `RowExclusiveLock`，但行级锁 3000 万个，全在一个事务里没法释放。
- **WAL 暴涨**：PG 的 UPDATE = DELETE 旧 + INSERT 新，3000 万行至少 60 GB WAL。
- **复制延迟**：standby 接收 WAL 但 apply 是单线程（PG 14 起部分并行），跟不上。
- **HOT update 不生效**：UPDATE 的列有索引（idx_orders_region），所以每行都要更新索引，写放大严重。

### 12.3 优化方案：拆小批 + 并行客户端

```sql
-- 1) 临时去掉 region 列上的索引（如果业务允许短暂没索引）
DROP INDEX idx_orders_region;

-- 2) 按主键范围拆批，每批 10000 行
DO $$
DECLARE
  start_id BIGINT := 0;
  end_id BIGINT;
  batch_size INT := 10000;
BEGIN
  LOOP
    SELECT min(id), max(id)
      INTO start_id, end_id
      FROM (
        SELECT id FROM orders
        WHERE id > start_id AND region IN ('cn', 'us', ...)
        ORDER BY id LIMIT batch_size
      ) t;
    EXIT WHEN start_id IS NULL;

    UPDATE orders SET region = iso_map[region]
    WHERE id BETWEEN start_id AND end_id
      AND region IN ('cn', 'us', ...);

    COMMIT;
    PERFORM pg_sleep(0.05);  -- 减缓主库压力 & 给复制喘息

    start_id := end_id;
  END LOOP;
END$$;

-- 3) 重建索引
CREATE INDEX CONCURRENTLY idx_orders_region ON orders(region);
```

**关键改进**：

- 每批 10k 行小事务，行锁随每个事务释放，业务事务能穿插。
- 50ms sleep 给复制喘息，延迟可控。
- DROP/重建索引避免 UPDATE 时索引写放大。
- `CREATE INDEX CONCURRENTLY` 不锁读写。

### 12.4 还能更进一步：FILLFACTOR + HOT update

如果业务上 region 列没法不带索引（很多查询用），换思路：

```sql
ALTER TABLE orders SET (fillfactor = 70);
VACUUM FULL orders;  -- 重建以应用 fillfactor

-- 但 region 列上的索引让 HOT 失效，要么砍掉这个索引
-- 要么接受 UPDATE 时索引写放大
```

详见 [P02 堆表与 TOAST](./02-精通-堆表存储与-TOAST.md) 的 HOT update 一节。

## 第十三章：完整案例 3——JSONB 高频路径下推

### 13.1 现场

埋点表 `events`，1.8 亿行：

```sql
CREATE TABLE events (
  id BIGSERIAL PRIMARY KEY,
  ts TIMESTAMPTZ,
  user_id BIGINT,
  payload JSONB
);
-- payload 例：
-- {"event": "click", "page": "/home", "exp": "AB-2026-05", ...}
```

业务最常见的查询：

```sql
SELECT count(*) FROM events
WHERE ts > now() - interval '1 hour'
  AND payload->>'exp' = 'AB-2026-05';
```

EXPLAIN：

```
Aggregate ... (actual time=18234.12)
  ->  Index Scan using idx_events_ts on events (rows=8000000)
        Filter: (payload->>'exp' = 'AB-2026-05')
        Rows Removed by Filter: 7900000
```

诊断：`ts` 索引命中 800 万行，再 filter `payload->>'exp'` 留下 10 万行——99% 行被丢，巨慢。

### 13.2 解法 A：表达式 B-tree 索引

```sql
CREATE INDEX idx_events_ts_exp
  ON events(ts, (payload->>'exp'));
```

新 EXPLAIN：

```
Aggregate ... (actual time=421.18)
  ->  Index Only Scan using idx_events_ts_exp on events (rows=100000)
        Index Cond: ((ts > ...) AND ((payload->>'exp'::text) = 'AB-2026-05'))
```

20s → 0.4s，43 倍。

### 13.3 解法 B：物化为生成列（PG 12+ stored generated column）

如果 `exp` 是核心维度，干脆物化成普通列：

```sql
ALTER TABLE events
  ADD COLUMN exp TEXT GENERATED ALWAYS AS (payload->>'exp') STORED;

CREATE INDEX idx_events_ts_exp_col ON events(ts, exp);
```

好处：

- 索引更省（普通 text 列比 jsonb 表达式快）
- 可以加 NOT NULL / CHECK 约束
- 后续 ETL 友好

代价：表占用增加（PG 18 才有 virtual generated column，可不物化但只能在表达式里用，不能直接索引）。

### 13.4 解法 C：JSONB GIN 索引（适合任意路径查询）

如果业务不止查 `exp`，可能查 `payload @> '{"exp": "AB-2026-05"}'`：

```sql
CREATE INDEX idx_events_payload ON events USING gin(payload);
-- 或更紧凑的 jsonb_path_ops
CREATE INDEX idx_events_payload_pathops ON events USING gin(payload jsonb_path_ops);
```

查询用 `@>` 操作符走 GIN。详见 [P12 JSONB 与全文检索](./12-精通-JSONB-与全文检索.md)。

## 第十四章：完整案例 4——top-N per user 用 LATERAL

### 14.1 现场

社交 feed：每个用户最近 10 条动态。

```sql
-- 200 万用户，6 亿动态
SELECT user_id, posts.*
FROM users
JOIN posts ON posts.user_id = users.id
WHERE users.region = 'CN'
ORDER BY posts.created_at DESC
LIMIT 100;
```

业务真实要的是"per user 最近 10 条"，但写成上面那样意思变了。改成正确版：

```sql
SELECT *
FROM (
  SELECT p.*, row_number() OVER (PARTITION BY p.user_id ORDER BY p.created_at DESC) AS rn
  FROM posts p
  JOIN users u ON u.id = p.user_id
  WHERE u.region = 'CN'
) t
WHERE rn <= 10;
```

EXPLAIN ANALYZE 30 秒——窗口函数对所有 200 万 × 平均 300 条 = 6 亿行排序后过滤。

### 14.2 LATERAL 重写

```sql
SELECT p.*
FROM users u
JOIN LATERAL (
  SELECT p.* FROM posts p
  WHERE p.user_id = u.id
  ORDER BY p.created_at DESC
  LIMIT 10
) p ON true
WHERE u.region = 'CN';
```

配合索引 `(user_id, created_at DESC)`，每个用户 10 行 Index Scan，总成本 200 万 × log(300) × 10 ≈ 几千万次比较，亚秒级。

### 14.3 EXPLAIN 对比

| 方案 | actual time | rows |
|---|---|---|
| 窗口函数 | 30,124 ms | 20M |
| LATERAL | 824 ms | 20M |

40 倍提升。

## 第十五章：完整案例 5——ANALYZE 抽样不足

### 15.1 现场

`audit_log` 表 8 亿行，按 `tenant_id`（多租户）查最近事件：

```sql
SELECT * FROM audit_log
WHERE tenant_id = 'tnt_xxx' AND ts > now() - interval '1 day'
ORDER BY ts DESC LIMIT 100;
```

P99 时快时慢，慢的时候 5-10 秒，快的时候 50ms。

### 15.2 EXPLAIN（慢的那次）

```
Limit ...
  ->  Sort ...
        ->  Bitmap Heap Scan on audit_log  (rows=42  width=...)
              (actual rows=1241223 loops=1)        ← 估 42, 实际 124 万
              Recheck Cond: (tenant_id = 'tnt_xxx')
              Filter: (ts > now() - '1 day')
              ->  Bitmap Index Scan on idx_tenant ...
```

差 30000 倍！planner 选 Bitmap Scan 是因为它以为只有 42 行，实际有上百万，整个 plan 错了。

### 15.3 原因

`tenant_id` 极倾斜：500 个租户，但有 3 个超大租户占 80% 数据。default_statistics_target = 100 时，直方图前 100 个 MCV 已经把"小租户"覆盖全了，超大租户的真实频率被严重低估（因为采样很可能漏掉某个超大值或低估其频率）。

### 15.4 解法

```sql
-- 1) 提升 tenant_id 的 stats target
ALTER TABLE audit_log ALTER COLUMN tenant_id SET STATISTICS 5000;
ANALYZE audit_log;

-- 2) 同时加多列扩展统计
CREATE STATISTICS audit_tenant_ts (mcv, dependencies) ON tenant_id, ts FROM audit_log;
ANALYZE audit_log;
```

调完后 EXPLAIN：

```
->  Index Scan using idx_audit_tenant_ts on audit_log  (rows=1100000  width=...)
      (actual rows=1241223 loops=1)
```

估算与实际数量级一致，planner 走对了路径，稳定 50ms。

### 15.5 教训

- 倾斜数据列要单独 STATISTICS 1000-10000
- 多列相关性用 CREATE STATISTICS
- 大表 `autovacuum_analyze_scale_factor` 调小

## 第十六章：完整案例 6——pg_stat_statements + auto_explain 联合定位偶发慢 SQL

### 16.1 现场

某接口 P99 偶发 4-5 秒，但 P50 = 30ms，无规律。`pg_stat_statements` 看到该 SQL：

| 字段 | 值 |
|---|---|
| calls | 1,240,000 |
| mean_exec_time | 41ms |
| max_exec_time | 8,124ms |
| stddev_exec_time | 412ms |

mean 不慢，但 stddev / max 很大——典型"偶发慢"。

### 16.2 启用 auto_explain

```conf
auto_explain.log_min_duration = 1000   # 1s 以上 dump
auto_explain.log_analyze = on
auto_explain.log_buffers = on
auto_explain.sample_rate = 0.1         # 10% 采样
```

reload，等 30 分钟，日志里抓到 8 条慢的：

```
LOG: duration: 4231.41 ms  plan:
Query Text: SELECT * FROM orders WHERE user_id = $1 ORDER BY created_at DESC LIMIT 50
  Index Scan using idx_orders_user_id on orders
    (actual time=421.12..4231.21 rows=50)
    Index Cond: (user_id = 7)
    Buffers: shared hit=12342 read=98421
```

发现：慢的全是 `user_id = 7`（运营用户），数据严重倾斜，且走了 idx_orders_user_id 而不是 idx_orders_user_created。

### 16.3 排查

```sql
-- 用户 id=7 的订单数
SELECT count(*) FROM orders WHERE user_id = 7;
-- 4,200,000

-- 普通用户
SELECT count(*) FROM orders WHERE user_id = 42;
-- 50
```

数据倾斜 + prepared statement plan flip（参见第七章），planner 切到 generic plan 后选了次优索引。

### 16.4 解法

```sql
-- 短期：force_custom_plan
ALTER ROLE app SET plan_cache_mode = 'force_custom_plan';

-- 中期：建组合索引让 generic plan 也选对
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC);
DROP INDEX idx_orders_user_id;

-- 长期：把运营/超级用户单独表 / 单独路径，避免数据倾斜污染整张表
```

调完 P99 从 8.1s 降到 80ms。

## 生产实践

### 1) 每周固定的 5 分钟巡检

每周一早上花 5 分钟跑下面 5 段 SQL，存到一个 `pg_weekly.sql`：

```sql
-- a) Top 10 累计耗时
SELECT substr(query, 1, 80), calls,
       round((total_exec_time/1000)::numeric, 1) AS total_s,
       round(mean_exec_time::numeric, 2) AS mean_ms
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

-- b) Top 10 I/O
SELECT substr(query, 1, 80), shared_blks_read,
       round(blk_read_time::numeric, 2) AS read_ms
FROM pg_stat_statements ORDER BY shared_blks_read DESC LIMIT 10;

-- c) 未使用索引（候选删除）
SELECT relname, indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND pg_relation_size(indexrelid) > 1024*1024
ORDER BY pg_relation_size(indexrelid) DESC;

-- d) 膨胀严重表
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0*n_dead_tup/nullif(n_live_tup+n_dead_tup, 0), 1) AS dead_pct
FROM pg_stat_user_tables
WHERE n_dead_tup > 100000
ORDER BY dead_pct DESC LIMIT 20;

-- e) 缓存命中率
SELECT datname,
       round(100.0*blks_hit/nullif(blks_hit+blks_read, 0), 2) AS hit_pct
FROM pg_stat_database WHERE datname NOT IN ('template0', 'template1');
```

跑完截图发到团队群，每周对比趋势。

### 2) 索引"先 CONCURRENTLY 后 ANALYZE"

```sql
CREATE INDEX CONCURRENTLY idx_x ON t(c);
ANALYZE t;  -- 重要：CONCURRENTLY 不会自动更新统计
```

很多团队只做第一步，第二步漏掉，planner 拿不到新索引的统计，"建了索引但没用上"。

### 3) 开发环境也启用 pg_stat_statements

让开发同学在写 SQL 阶段就能看到自己 SQL 的执行计划与统计，比上线后再优化便宜 100 倍。脚手架里 `docker run postgres` 时直接：

```bash
docker run -d \
  -e POSTGRES_PASSWORD=pwd \
  -p 5432:5432 \
  postgres:18 \
  -c shared_preload_libraries=pg_stat_statements \
  -c pg_stat_statements.track=all
```

### 4) 上线变更前必做"explain diff"

发版前对将要部署的所有 SQL 在生产 read replica 上跑 `EXPLAIN`，对比上一版的 plan：

```bash
psql -h replica -c "EXPLAIN (FORMAT JSON, ANALYZE, BUFFERS) <new_sql>" > new.json
diff <(jq . old.json) <(jq . new.json)
```

很多 plan 退化是改了 SQL 顺序、加了一个 join、改了某个 WHERE 条件触发的，diff 能第一时间看到。

### 5) PgBouncer + 慢查询的"奇怪现象"

PgBouncer 在 transaction pool mode 下，PG 的 server-side prepared statement 跨事务失效，会导致每次都重新 parse / plan——`pg_stat_statements` 显示 `total_plan_time` 极高。要么换 session mode，要么用 protocol-aware 客户端（pgx 5.x 有 server-side prepare cache）。

### 6) 写运维脚本：从 pg_stat_statements 自动生成"建议"

```sql
-- 建议加 INCLUDE 覆盖的 SQL：mean > 50ms 且 shared_blks_read 大
SELECT queryid, query, mean_exec_time, shared_blks_read
FROM pg_stat_statements
WHERE mean_exec_time > 50 AND shared_blks_read > 1000
ORDER BY mean_exec_time DESC LIMIT 20;
```

把结果丢给团队，每周一个"优化候选清单"。

## 陷阱清单

1. **OFFSET 大分页**：从一开始就用 keyset，等用户反馈再改的成本指数级上升。
2. **`NOT IN` 撞上 NULL**：永远用 `NOT EXISTS`。
3. **SELECT \***：破坏 Index Only Scan，且加列时被动慢。
4. **prepared statement plan flip**：数据倾斜场景务必 `force_custom_plan`。
5. **`auto_explain.log_analyze = on` 在高 QPS 下开销大**：用 `sample_rate`。
6. **CREATE INDEX 漏掉 CONCURRENTLY**：阻塞业务写。
7. **CREATE INDEX CONCURRENTLY 之后忘 ANALYZE**：planner 用不上新索引的统计。
8. **`shared_preload_libraries` 拼写错误导致 PG 起不来**：变更前用临时 `psql -c "ALTER SYSTEM SET ..."` 加重启 dry-run。
9. **`work_mem` 全局调大**：与 `max_connections` 乘起来 OOM。
10. **JIT 在 OLTP 反慢**：根据负载调 `jit_above_cost` 或直接关。
11. **default_statistics_target = 100 不够**：倾斜列 / 高基数列单独上调。
12. **表达式索引必须 IMMUTABLE**：含 `now()` 之类的不行；时区相关函数小心。
13. **多列索引顺序错**：等值列前、范围列后；高选择性优先。
14. **partial index 谓词太复杂**：planner 无法证明蕴含，命中失败。
15. **JSONB GIN 索引很大**：考虑 `jsonb_path_ops` 减小体积。
16. **autovacuum_analyze_scale_factor 大表上失效**：大表单独覆盖。
17. **大事务 UPDATE 不分批**：行锁、WAL、复制延迟、autovacuum bloat 全炸。
18. **CTE 默认物化（PG 11-）vs inline（PG 12+）**：跨版本要意识到差异，老版本可 `WITH x AS NOT MATERIALIZED (...)`。
19. **CONCURRENTLY 失败留下 invalid 索引**：`SELECT relname FROM pg_index JOIN pg_class ON ... WHERE NOT indisvalid;` 检查并 DROP 重建。
20. **`pg_stat_statements.max` 太小**：digest 被 LRU 频繁淘汰，统计抖动。

## 练习题

**1）digest 化的边界**

下面两条 SQL 在 `pg_stat_statements` 里是一条还是两条？

```sql
SELECT * FROM users WHERE id = 1 AND status = 'active';
SELECT * FROM users WHERE id = 2 AND status = 'pending';
```

它们的 queryid 一样吗？再思考：把第二条改成 `WHERE status = 'pending' AND id = 2`，还是一条吗？

<details><summary>参考答案</summary>

第一组是同一条（参数化后 `WHERE id = $1 AND status = $2`），queryid 一样。

改了顺序后是不同的——`pg_stat_statements` 用解析后的查询树做 hash，AST 不同就不同。所以"换列序写 SQL"会导致 digest 分裂，统计不准。

</details>

**2）OFFSET 与 keyset 的 edge case**

下面 keyset SQL 有什么问题？

```sql
SELECT * FROM events WHERE id < :last_id ORDER BY created_at DESC, id DESC LIMIT 10;
```

<details><summary>参考答案</summary>

排序键是 `(created_at, id)` 但筛选只用了 `id < last_id`。当两行 `created_at` 不同但 `id` 单调递增时没问题；但 `created_at` 可能不严格单调（同毫秒），此时 keyset 错乱，可能漏行或重复。

正确写法：

```sql
WHERE (created_at, id) < (:last_ts, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 10;
```

</details>

**3）部分索引命中**

已建索引：

```sql
CREATE INDEX idx_orders_pending ON orders(created_at) WHERE status = 'pending';
```

下面哪些 SQL 能命中？

```sql
-- A
SELECT * FROM orders WHERE status = 'pending';
-- B
SELECT * FROM orders WHERE status = 'pending' AND created_at > now() - interval '1 hour';
-- C
SELECT * FROM orders WHERE status IN ('pending', 'failed');
-- D
SELECT * FROM orders WHERE status = 'pending' OR id = 42;
```

<details><summary>参考答案</summary>

- A、B 能命中（WHERE 子句蕴含索引谓词 `status='pending'`）
- C 不能（IN 包含其他值，planner 无法证明）
- D 不能（OR 让谓词不蕴含）

</details>

**4）NOT IN 改写**

下面 SQL 在 `blocked.user_id` 有 NULL 时会怎样？给出三种安全改写。

```sql
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM blocked);
```

<details><summary>参考答案</summary>

含 NULL 时返回空集。安全改写：

```sql
-- 1) NOT EXISTS
SELECT * FROM users u WHERE NOT EXISTS (SELECT 1 FROM blocked b WHERE b.user_id = u.id);

-- 2) LEFT JOIN + IS NULL
SELECT u.* FROM users u LEFT JOIN blocked b ON b.user_id = u.id WHERE b.user_id IS NULL;

-- 3) 显式 filter NULL（不推荐，仅在你 100% 控制 blocked 列时）
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM blocked WHERE user_id IS NOT NULL);
```

</details>

**5）work_mem 算账**

`max_connections = 200`, `work_mem = 64MB`, 假设每条 SQL 平均 3 个 sort/hash 操作，估算潜在内存上限。一台 32GB 机器是否安全？

<details><summary>参考答案</summary>

200 × 64MB × 3 = 38.4 GB，超 32GB。不安全。

合理方案：work_mem 调到 16MB（200×16×3=9.6GB），让"贵 SQL"按需 SET LOCAL 上调。

</details>

**6）prepared statement plan flip**

下面 SQL 在 `user_id = 7`（数据 90% 都是这个值）时变慢，怎么排查？

```sql
PREPARE q AS SELECT * FROM events WHERE user_id = $1 ORDER BY ts DESC LIMIT 10;
EXECUTE q(7);
```

<details><summary>参考答案</summary>

1. `EXPLAIN (GENERIC_PLAN, ANALYZE) EXECUTE q(7);` 看 generic plan
2. `EXPLAIN ANALYZE SELECT ... WHERE user_id = 7 ORDER BY ts DESC LIMIT 10;` 看 custom plan
3. 对比两者，差异大说明 plan flip
4. 解决：`SET plan_cache_mode = 'force_custom_plan'`；长期改数据分布或加 `(user_id, ts DESC)` 索引让两种 plan 都对

</details>

**7）EXPLAIN 解读**

```
Bitmap Heap Scan on events  (cost=... rows=42)
  (actual rows=1241223 loops=1)
  Recheck Cond: (tenant_id = 'tnt_xxx')
  Filter: (ts > now() - '1 day')
  ->  Bitmap Index Scan on idx_tenant ...
```

哪些信号说明 plan 错了？给出至少两个修复方向。

<details><summary>参考答案</summary>

信号：

- 估算 42 行，实际 124 万行——统计信息严重低估
- Bitmap Heap Scan 在大量行场景里通常输给 Index Scan + LIMIT，提示 planner 选错节点

修复：

- `ALTER TABLE events ALTER COLUMN tenant_id SET STATISTICS 5000; ANALYZE;`
- 建多列扩展统计：`CREATE STATISTICS (mcv) ON tenant_id, ts FROM events;`
- 加 `(tenant_id, ts DESC)` 索引，配合 LIMIT
- 临时 `SET enable_bitmapscan = off` 验证 plan 选择

</details>

**8）JSONB 索引选择**

业务有三种查询：

```sql
-- Q1: payload->>'exp' = 'AB-2026-05'  (高频，单一路径)
-- Q2: payload @> '{"region": "CN"}'   (中频，任意路径)
-- Q3: payload->>'page' LIKE '/home%'  (低频，前缀匹配)
```

设计索引。

<details><summary>参考答案</summary>

```sql
-- Q1：表达式 B-tree（最快、最省）
CREATE INDEX idx_events_exp ON events((payload->>'exp'));

-- Q2：GIN with jsonb_path_ops（@> 的最佳搭档）
CREATE INDEX idx_events_payload ON events USING gin(payload jsonb_path_ops);

-- Q3：表达式 + text_pattern_ops（前缀匹配）
CREATE INDEX idx_events_page ON events((payload->>'page') text_pattern_ops);
```

不要建一个"通用 GIN on payload" 想覆盖所有——Q1 的单路径查询用 GIN 比表达式 B-tree 慢且占空间。

</details>
