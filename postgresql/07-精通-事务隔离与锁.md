## 引言：PostgreSQL 的并发模型，与 MySQL 长得不一样

读完 [P03 MVCC](./03-精通-MVCC-与可见性.md) 你应该已经接受了一件事：PostgreSQL 不存在"undo log"。旧版本不是被存进 rollback segment 让查询去回放，而是**直接以独立 tuple 形式留在堆表里**，由 xmin/xmax + Snapshot 决定可见性。

这意味着锁与隔离级别的实现也走了与 InnoDB 不同的路线：

- **没有 gap lock，没有 next-key lock**。RR 默认不防幻读（理论上），但 PG 通过 Repeatable Read 的事务级快照让你看不见新行——这是"读"层面的防御，不是"锁"层面的防御。
- **真·可串行化（Serializable，SSI）**。PG 9.1 起，Serializable 不再是 SS2PL（严格两阶段锁），而是 **Serializable Snapshot Isolation（SSI）**：基于 predicate 的读写依赖追踪，能在不阻塞的前提下检测出"危险结构"并主动 abort 其中一个事务。后被 CockroachDB / YugabyteDB 借鉴。
- **行锁不在内存里**，而是把 xid 写进 tuple 的 `xmax` 字段。所以"持有行锁的事务"约等于"写过这一行的事务"——这是 PG 行锁可以**无限多**且**几乎零内存**的原因，但同时它把锁信息变成了 tuple 的一部分，所以 dead tuple 必须等 vacuum 清理。
- **表锁层级 8 等级**（Access Share … Access Exclusive），DDL 直接对应表锁等级，比 InnoDB 的 MDL 更显式更细。
- **Advisory Lock 是 PG 独有的杀手锏**——应用层任意 64 位 key 直接拿一个锁，session 级或 transaction 级，分布式互斥 / 任务调度 / 单例守护一行 SQL 搞定。

这一章把 PG 的事务与锁体系讲透。读完后你应该能：

- 解释 PG 的 4 个隔离级别每一级"能防什么、防不了什么"
- 画出 SSI 检测危险结构的读写依赖图（SIREAD predicate locking）
- 设计一个"用 SKIP LOCKED 消费的任务队列"
- 用 `pg_blocking_pids()` 画出生产环境的阻塞链
- 列出阻塞 vacuum 的三大杀手（idle in transaction / prepared txn / 未消费 slot）
- 用 advisory lock 写一个"分布式定时任务只在一台机器跑"的开关

## 第一章：事务基础与隔离级别

### 1.1 PG 事务的开始与结束

```sql
BEGIN;              -- 显式开启（START TRANSACTION 同义）
-- DML / DDL ...
COMMIT;             -- 提交
ROLLBACK;           -- 回滚

-- savepoint
BEGIN;
INSERT INTO t VALUES (1);
SAVEPOINT sp1;
INSERT INTO t VALUES (2);
ROLLBACK TO sp1;    -- 回到 sp1，只回滚第二条
COMMIT;             -- 提交第一条
```

PG 默认每条 SQL 都是**隐式事务**（autocommit），与 MySQL 一致。

事务的标识：

- `txid`（事务 ID）：32 位，从 3 开始递增（0/1/2 保留）；2026 年社区正在推进 64-bit xid，但生产仍是 32-bit。
- `virtualxid`（虚拟事务 ID）：只读事务不分配真实 xid，只用 `backend_id/local_xid` 形式的虚拟 id，节省 xid 消耗。**重要含义：只有写过数据的事务才"耗费"xid，纯只读事务不计入 wraparound 风险**。

```sql
-- 查看当前事务 id（如果未写入，会触发分配）
SELECT txid_current();

-- 查看当前事务的虚拟 id（不触发分配）
SELECT virtualxid FROM pg_stat_activity WHERE pid = pg_backend_pid();
```

### 1.2 4 个隔离级别（PG 的真实映射）

SQL 标准定义了 4 级隔离，PG 的实际实现如下：

| SQL 标准声明 | PG 实际行为 | 脏读 | 不可重复读 | 幻读 | 序列化异常 |
|---|---|---|---|---|---|
| READ UNCOMMITTED | ≡ READ COMMITTED | ✗ | 可能 | 可能 | 可能 |
| READ COMMITTED（默认） | READ COMMITTED | ✗ | 可能 | 可能 | 可能 |
| REPEATABLE READ | Snapshot Isolation | ✗ | ✗ | ✗（PG 不会幻读） | 可能（写偏序） |
| SERIALIZABLE | SSI（PG 9.1+） | ✗ | ✗ | ✗ | ✗ |

**关键 1**：PG 没有真正的 READ UNCOMMITTED——即使你写 `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;`，行为也是 READ COMMITTED。源码在 `src/backend/utils/time/snapmgr.c`，因为 MVCC 模型不允许读未提交版本（CLOG 显示未提交则不可见）。

**关键 2**：PG 的 Repeatable Read **不存在幻读**（read phenomena 维度）。原因是 RR 使用**事务开始时的快照**，整个事务期间所有读看到的都是同一个快照，新插入的行无论是否提交都不可见。MySQL InnoDB 的 RR 通过 next-key lock **阻止插入**来防幻读，PG 通过**看不见**来防——本质不同。

**关键 3**：PG 的 RR 仍可能出现"写偏序（write skew）"，这就是为什么需要 Serializable（SSI）。

### 1.3 设置隔离级别

```sql
-- 会话级（之后所有事务默认）
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 事务级（仅本事务）
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ...
COMMIT;

-- 等价写法
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

只读优化：

```sql
BEGIN READ ONLY;  -- 不分配真实 xid，不占 wraparound 配额
BEGIN READ ONLY DEFERRABLE;  -- 仅 Serializable 下，等到能拿到"一致快照"再开始，永不被 abort
```

`DEFERRABLE` 适合长时间报表：用 Serializable + ReadOnly + Deferrable，确保结果一致但不会被 SSI 杀死。

## 第二章：READ COMMITTED —— 默认级

### 2.1 工作原理

每条 SQL **执行前**重新获取一个 snapshot。意味着同一事务里：

```sql
BEGIN;
SELECT count(*) FROM t WHERE status = 'ACTIVE';  -- 第一次执行，snapshot S1
-- ... 其他事务 commit 了一些 ACTIVE 行
SELECT count(*) FROM t WHERE status = 'ACTIVE';  -- 第二次执行，snapshot S2，可能不同
COMMIT;
```

两次 count 可能不同——这就是**不可重复读**。

### 2.2 UPDATE / DELETE 的特殊行为：EvalPlanQual

RC 下的写操作很微妙。考虑：

```sql
-- T1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;   -- 锁住 id=1，balance 从 500 → 400

-- T2
BEGIN;
UPDATE accounts SET balance = balance * 0.9 WHERE id = 1;   -- 等 T1
```

T2 等 T1 提交后，PG 不会简单"按 T2 开始时的 snapshot"看见 balance=500，而是触发 **EvalPlanQual（EPQ）**：

1. 重新读 id=1 这一行的**最新版本**（balance=400）
2. 重新评估 WHERE 条件，如果仍满足，则在 400 基础上执行 `* 0.9` → 360
3. 如果 WHERE 不再满足（比如有 `WHERE status='ACTIVE'` 而别人改成了 INACTIVE），跳过这一行

EPQ 的好处：**RC 下并发 UPDATE 永远操作的是最新版本**，不会出现 InnoDB 在 RR 下那种"丢失更新"陷阱。
EPQ 的代价：WHERE 条件需要重新评估，可能让结果与你 SQL 直觉不符——具体见后面 Repeatable Read 的对比。

### 2.3 RC 的典型异常

```
不可重复读：
T1: SELECT balance FROM a WHERE id=1;  -- 100
T2: UPDATE a SET balance=200 WHERE id=1; COMMIT;
T1: SELECT balance FROM a WHERE id=1;  -- 200 （同一事务两次读不同）

幻读：
T1: SELECT count(*) FROM orders WHERE date='2026-05-28';  -- 50
T2: INSERT INTO orders ... date='2026-05-28'; COMMIT;
T1: SELECT count(*) FROM orders WHERE date='2026-05-28';  -- 51
```

## 第三章：REPEATABLE READ —— Snapshot Isolation

### 3.1 工作原理

**事务第一次执行 SQL 时**获取一个 snapshot，整个事务的所有读都基于这个 snapshot。

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM t WHERE status='ACTIVE';  -- snapshot S 在此刻确定
-- 其他事务 INSERT / UPDATE / DELETE 都不影响本事务的读
SELECT count(*) FROM t WHERE status='ACTIVE';  -- 仍是同一个数（基于 S）
COMMIT;
```

注意是"第一次执行 SQL"而不是 `BEGIN`。因为 `BEGIN` 之后还没动数据，PG 用虚拟 xid 占位，真正的 snapshot 是在第一条数据语句执行时才确定。

### 3.2 PG RR 与 MySQL InnoDB RR 的根本差异

| 维度 | PostgreSQL RR | MySQL InnoDB RR |
|---|---|---|
| 实现 | Snapshot Isolation（快照） | MVCC 读 + Next-Key Lock 写 |
| 防幻读手段 | "看不见"新行（snapshot 切走） | gap lock + next-key lock 阻止 INSERT |
| 防幻读结果 | 不会幻读 | 不会幻读 |
| 写偏序（write skew） | **可能发生** | 一定程度上避免（因为 gap lock 锁了不存在的行） |
| 并发写冲突 | 直接报错 `could not serialize access`（40001） | 用行锁 + gap lock 阻塞或死锁 |
| 性能 | 读不阻塞写（无 gap lock） | gap lock 影响并发插入 |

### 3.3 RR 下 UPDATE 的"first updater wins"

```sql
-- T1
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id=1;  -- 100，snapshot 锁定

-- T2
BEGIN; UPDATE accounts SET balance=200 WHERE id=1; COMMIT;

-- T1
UPDATE accounts SET balance=balance+50 WHERE id=1;
-- 报错：ERROR: could not serialize access due to concurrent update
-- SQLSTATE: 40001
```

PG RR 下，如果你试图更新一行被别的事务提交过的版本，**直接报错让你重试**——不会像 RC 那样静默地基于最新版本计算。这是 SI 的"乐观锁"哲学。

**应用层必须 retry**：

```go
for attempt := 0; attempt < 3; attempt++ {
    tx, _ := db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelRepeatableRead})
    _, err := tx.Exec("UPDATE accounts SET balance=balance+50 WHERE id=$1", 1)
    if err != nil {
        var pgErr *pgconn.PgError
        if errors.As(err, &pgErr) && pgErr.Code == "40001" {
            tx.Rollback()
            time.Sleep(time.Duration(rand.Intn(100)) * time.Millisecond)
            continue
        }
        return err
    }
    return tx.Commit()
}
```

### 3.4 写偏序（Write Skew）—— RR 的致命漏洞

经典的"医生值班"案例：

```sql
CREATE TABLE doctors (id int PRIMARY KEY, on_call boolean);
INSERT INTO doctors VALUES (1, true), (2, true);

-- 规则：至少要有 1 名医生在值班

-- T1（医生 1 想下班）
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM doctors WHERE on_call = true;  -- 2，可以下班
UPDATE doctors SET on_call = false WHERE id = 1;

-- T2（医生 2 想下班，同时执行）
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM doctors WHERE on_call = true;  -- 2，可以下班
UPDATE doctors SET on_call = false WHERE id = 2;

COMMIT; COMMIT;  -- 两个都成功，但现在没人值班！
```

**两个事务读了同一份快照、写了不同的行**——没有写写冲突，但破坏了不变量。这就是 write skew，RR 防不住。

只有 **Serializable** 能防。

## 第四章：SERIALIZABLE —— SSI 真·可串行化

### 4.1 SSI 的核心思想

传统的 Serializable 实现是 **SS2PL**（Strict 2PL）：读加共享锁、写加排他锁、commit 时释放——读阻塞写、写阻塞读，性能差。

PG 选择了一条更聪明的路：**Serializable Snapshot Isolation（SSI）**。

**核心断言**：如果两个事务的执行结果**等价于某种串行执行**，就不需要阻塞它们；只在检测到"会破坏可串行化"的危险结构时，**主动 abort 其中一个**。

发明人：Cahill, Röhm & Fekete（2008），ACM SIGMOD。PG 在 9.1（2011）将其落地，至今仍是数据库界最优雅的 Serializable 实现。

### 4.2 危险结构：rw-antidependency

SSI 追踪三种事务依赖：

- **wr**：T2 读了 T1 写过的数据（T2 在 T1 之后）
- **ww**：T2 写了 T1 写过的数据（T2 在 T1 之后）
- **rw**：T2 写了 T1 读过的数据（T2 反过来在 T1 之后；但 T1 看不见 T2 的写——这是 SI 的特点）

只有 **rw-antidependency** 是"危险的"——它意味着 T1 读到的快照已经"过时"。

SSI 的定理：**只要并发事务图里没有"两个连续的 rw 边形成环"**，就一定存在一种合法的串行顺序，可以安全提交。否则——必须 abort 一个事务破环。

```
Doctors 案例的依赖图：

  T1 -----rw----> T2     T1 写 d1，T2 读 doctors 表（包含 d1）
   ^               |
   |               v
  T2 -----rw----> T1     T2 写 d2，T1 读 doctors 表（包含 d2）

形成 rw → rw 环 → 危险结构 → SSI abort 一个
```

### 4.3 Predicate Locking（SIREAD）

为了追踪"T1 读了什么"，PG 引入 **predicate locks**（也叫 SIREAD locks）：

- 不像 InnoDB 那样在索引区间上加锁
- 而是一种**逻辑标记**："T1 读了表 t 的页 p / tuple ctid"
- **predicate lock 不阻塞任何人**——它只是给 SSI 检测器用的"读痕迹"

锁粒度分层：

```
tuple (CTID 粒度，最细)
  ↓ 升级
page (页粒度)
  ↓ 升级
relation (表粒度，最粗)
```

如果你在大表上做了全表扫描，PG 不会真的记 100 万条 tuple 的 predicate lock，会升级到 relation 级。代价：**误报概率上升**——更多事务会被"过度敏感地" abort。

参数：

- `max_pred_locks_per_transaction` (默认 64)：每事务的 predicate lock 上限，超过则升级粒度
- `max_pred_locks_per_relation` (默认 -2)：每表上限
- `max_pred_locks_per_page` (默认 2)：每页 tuple 数上限

### 4.4 SSI 的代价

```sql
ERROR:  could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during commit attempt.
HINT:  The transaction might succeed if retried.
SQLSTATE: 40001
```

应用层 **必须实现 retry**。SSI 在事务提交时才检测，所以错误可能在 COMMIT 时才抛出——你 UPDATE 一切正常，COMMIT 失败。

### 4.5 SSI vs MySQL InnoDB Serializable

| 维度 | PG SSI | MySQL InnoDB Serializable |
|---|---|---|
| 实现 | SSI（乐观，predicate lock 仅追踪） | SS2PL（悲观，next-key lock 锁区间） |
| 读阻塞写 | 否 | 是 |
| 写阻塞读 | 否 | 是 |
| 死锁 | 不会（直接 abort 不形成等待） | 可能死锁 |
| 误判 | 可能误 abort（粒度升级） | 不误判但阻塞多 |
| 性能 | 高并发优 | 低并发也优 |
| Retry | 必须 | 死锁时需要 |

## 第五章：表锁 —— 8 个等级

### 5.1 等级矩阵

PG 表锁有 8 个等级，从弱到强：

| 等级 | 取得场景 | 主要冲突 |
|---|---|---|
| ACCESS SHARE (AS) | SELECT | 仅 AccessExclusive |
| ROW SHARE (RS) | SELECT FOR UPDATE/SHARE | Exclusive、AccessExclusive |
| ROW EXCLUSIVE (RE) | INSERT/UPDATE/DELETE/MERGE | Share、ShareRowExclusive、Exclusive、AccessExclusive |
| SHARE UPDATE EXCLUSIVE (SUE) | VACUUM (非 FULL)、ANALYZE、CREATE INDEX CONCURRENTLY、部分 ALTER | 自身、Share 及更强 |
| SHARE (S) | CREATE INDEX (非 CONCURRENTLY) | RE、SUE、SRE、E、AE |
| SHARE ROW EXCLUSIVE (SRE) | CREATE COLLATION、CREATE TRIGGER、部分 ALTER | RE、SUE、S、SRE、E、AE |
| EXCLUSIVE (E) | REFRESH MATERIALIZED VIEW CONCURRENTLY | 除 AS 外全部冲突 |
| ACCESS EXCLUSIVE (AE) | DROP TABLE / TRUNCATE / VACUUM FULL / ALTER TABLE（多数）/ CLUSTER | 全部冲突，包括 SELECT |

### 5.2 兼容性矩阵（✓ 兼容，✗ 冲突）

|           | AS | RS | RE | SUE | S | SRE | E | AE |
|-----------|----|----|----|-----|---|-----|---|-----|
| **AS**    | ✓  | ✓  | ✓  | ✓   | ✓ | ✓   | ✓ | ✗   |
| **RS**    | ✓  | ✓  | ✓  | ✓   | ✓ | ✓   | ✗ | ✗   |
| **RE**    | ✓  | ✓  | ✓  | ✓   | ✗ | ✗   | ✗ | ✗   |
| **SUE**   | ✓  | ✓  | ✓  | ✗   | ✗ | ✗   | ✗ | ✗   |
| **S**     | ✓  | ✓  | ✗  | ✗   | ✓ | ✗   | ✗ | ✗   |
| **SRE**   | ✓  | ✓  | ✗  | ✗   | ✗ | ✗   | ✗ | ✗   |
| **E**     | ✓  | ✗  | ✗  | ✗   | ✗ | ✗   | ✗ | ✗   |
| **AE**    | ✗  | ✗  | ✗  | ✗   | ✗ | ✗   | ✗ | ✗   |

记忆要点：

1. **AS 与 AE 互斥**——这意味着 SELECT 与 DROP/TRUNCATE/VACUUM FULL/大部分 ALTER 互斥
2. **RE 与 S 冲突**——所以 `CREATE INDEX`（非 CONCURRENTLY）会阻塞所有 DML
3. **SUE 自相冲突**——同一时间一个表上只能跑一个 `VACUUM` 或一个 `CREATE INDEX CONCURRENTLY`
4. **AE 跟所有锁冲突**——DDL 会卡死所有人，所以生产 DDL 必须设 `lock_timeout`

### 5.3 显式表锁

```sql
LOCK TABLE accounts IN ACCESS EXCLUSIVE MODE;        -- 阻塞所有人
LOCK TABLE accounts IN SHARE MODE NOWAIT;            -- 拿不到立刻报错
LOCK TABLE accounts IN ROW EXCLUSIVE MODE;           -- 跟 INSERT/UPDATE/DELETE 等价的锁
```

事务结束自动释放，没有 `UNLOCK TABLE`。

### 5.4 在线 DDL 的关键技巧

```sql
-- 灾难写法：默认 ALTER TABLE 加 AccessExclusive，阻塞全表
ALTER TABLE big_table ADD COLUMN foo int;

-- 安全写法 1：先设 lock_timeout 避免雪崩
SET lock_timeout = '3s';
ALTER TABLE big_table ADD COLUMN foo int;   -- 拿不到锁 3 秒后报错而非无限等

-- 安全写法 2：PG 11+ 加列默认无 rewrite
ALTER TABLE big_table ADD COLUMN foo int DEFAULT 0;  -- PG 11+ 不再 rewrite 表（元数据级）

-- 安全写法 3：在线建索引
CREATE INDEX CONCURRENTLY idx_foo ON big_table(foo);  -- ShareUpdateExclusive，不阻塞 DML

-- 安全写法 4：分步式 DDL
ALTER TABLE big_table ADD COLUMN foo int;            -- 1. 加列
ALTER TABLE big_table ADD CONSTRAINT chk_foo CHECK (foo > 0) NOT VALID;  -- 2. 加约束但不验证
ALTER TABLE big_table VALIDATE CONSTRAINT chk_foo;   -- 3. 单独验证（只持 SUE）
```

## 第六章：行锁 —— 4 种强度

### 6.1 四种行锁

| 锁类型 | 关键字 | 强度 | 阻止 |
|---|---|---|---|
| FOR KEY SHARE | `SELECT ... FOR KEY SHARE` | 弱 | 仅阻止 key 变更（DELETE / 主键 UPDATE） |
| FOR SHARE | `SELECT ... FOR SHARE` | 中弱 | 阻止 UPDATE（任意列）、DELETE |
| FOR NO KEY UPDATE | （内部，无 key 的 UPDATE） | 中强 | 阻止 SHARE/UPDATE/DELETE，允许 KEY SHARE |
| FOR UPDATE | `SELECT ... FOR UPDATE` | 强 | 阻止所有其他行锁 |

### 6.2 兼容性矩阵

|                       | FOR KEY SHARE | FOR SHARE | FOR NO KEY UPDATE | FOR UPDATE |
|-----------------------|----------------|-----------|--------------------|-------------|
| **FOR KEY SHARE**     | ✓              | ✓         | ✓                  | ✗           |
| **FOR SHARE**         | ✓              | ✓         | ✗                  | ✗           |
| **FOR NO KEY UPDATE** | ✓              | ✗         | ✗                  | ✗           |
| **FOR UPDATE**        | ✗              | ✗         | ✗                  | ✗           |

PG 9.3 引入了 KEY SHARE / NO KEY UPDATE 的细分。原因是**外键场景**：

```sql
CREATE TABLE orders (id int, customer_id int REFERENCES customers(id));

-- 改 orders.customer_id（指向 customer_id=10）时，PG 内部对 customers 行加 FOR KEY SHARE
-- 这样如果有人想 UPDATE customers SET name='...' WHERE id=10（不改 key），不互相阻塞
-- 但 DELETE customers WHERE id=10（改 key/删除）会被阻塞
```

如果没有这个细分，外键场景下任何 UPDATE 父表都会阻塞所有引用它的子表写入——并发会非常差。

### 6.3 行锁存储方式

PG 行锁**不在内存里**，而是：

- **写锁（UPDATE/DELETE 自动 + FOR UPDATE / FOR NO KEY UPDATE）**：把当前事务的 xid 写进 tuple 的 `xmax` 字段，加上 infomask 标记 `HEAP_XMAX_LOCK_ONLY`（如果只是锁而非真改）
- **多事务持锁（共享 + KEY SHARE 等）**：MultiXact 机制——`xmax` 指向一个 multi-xact id，背后是一个 xid 列表

这就是为什么 PG 行锁可以"无限多"（不占共享内存里的 lock table）但需要 vacuum 清理 dead/locked tuple。

### 6.4 行锁与隔离级别的相互作用

```sql
-- RC 下
SELECT * FROM accounts WHERE id=1 FOR UPDATE;  -- 加 FOR UPDATE 行锁
-- 行锁立刻生效，其他事务的 UPDATE/SELECT FOR UPDATE 会阻塞

-- RR 下
SELECT * FROM accounts WHERE id=1 FOR UPDATE;
-- 同样加行锁；但如果该行在你 snapshot 之后被改过，会报 40001
```

## 第七章：SKIP LOCKED 与 NOWAIT —— 工程实战

### 7.1 SKIP LOCKED（PG 9.5+）

**任务队列消费场景**的最佳工具：

```sql
-- worker N 取一个未被其他 worker 抢走的任务
BEGIN;
SELECT id, payload
FROM job_queue
WHERE status = 'PENDING'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 1;

UPDATE job_queue SET status='RUNNING', worker=$1 WHERE id=$2;
COMMIT;

-- worker 处理完后
UPDATE job_queue SET status='DONE' WHERE id=$1;
```

**SKIP LOCKED 的语义**：碰到被别人锁住的行就**跳过**（而不是等），保证多个 worker 永不互相阻塞。

完整 worker 伪代码：

```go
func consume(ctx context.Context, db *pgxpool.Pool) error {
    tx, err := db.BeginTx(ctx, pgx.TxOptions{})
    if err != nil { return err }
    defer tx.Rollback(ctx)

    var jobID int64
    var payload []byte
    err = tx.QueryRow(ctx, `
        SELECT id, payload FROM job_queue
        WHERE status='PENDING' AND scheduled_at <= now()
        ORDER BY scheduled_at
        FOR UPDATE SKIP LOCKED
        LIMIT 1
    `).Scan(&jobID, &payload)
    if errors.Is(err, pgx.ErrNoRows) {
        return nil  // 没活
    }
    if err != nil { return err }

    if err := process(payload); err != nil {
        _, _ = tx.Exec(ctx, `UPDATE job_queue SET status='FAILED', error=$1, attempts=attempts+1 WHERE id=$2`, err.Error(), jobID)
    } else {
        _, _ = tx.Exec(ctx, `UPDATE job_queue SET status='DONE' WHERE id=$1`, jobID)
    }
    return tx.Commit(ctx)
}
```

为什么不用 Redis / RabbitMQ？因为 PG 队列具有：

- **ACID** 与业务表同事务（最关键的优势）
- **天然持久化**
- **任意 SQL 查询**（看待处理量、看失败原因）
- 中小规模够用（1000-10000 QPS 完全没问题）

### 7.2 NOWAIT

```sql
SELECT * FROM t WHERE id=1 FOR UPDATE NOWAIT;
-- 如果别人持锁，立刻报错 ERROR: could not obtain lock on row in relation "t"
-- SQLSTATE: 55P03
```

适合 UI 编辑冲突检测（不想用户等几秒）。

### 7.3 lock_timeout

```sql
-- 会话级超时
SET lock_timeout = '5s';
UPDATE accounts SET balance=... WHERE id=1;
-- 5 秒拿不到行锁 → 报错（不是死锁，是等不到）

-- 全局生产建议
ALTER SYSTEM SET lock_timeout = '5s';
SELECT pg_reload_conf();
```

## 第八章：死锁检测

### 8.1 PG 死锁检测机制

**deadlock_timeout**（默认 1s）：每个进程在等锁超过这个时间后，触发一次死锁检测。

为什么默认 1s 而不是立即？因为短锁等待是常态，频繁跑死锁算法浪费 CPU。

检测算法：等待图 + 环检测（Wait-for Graph + Cycle Detection）。

发现环时，**牺牲发起检测的进程**（不是最年轻——这点和 InnoDB 不同；InnoDB 牺牲 undo log 量最少的那个）。

```sql
ERROR:  deadlock detected
DETAIL:  Process 1234 waits for ShareLock on transaction 567; blocked by process 890.
         Process 890 waits for ShareLock on transaction 999; blocked by process 1234.
HINT:  See server log for query details.
```

### 8.2 死锁日志

`postgresql.conf`：

```
log_lock_waits = on             # 锁等待超过 deadlock_timeout 就记录
deadlock_timeout = '1s'         # 默认 1s
log_min_duration_statement = '500ms'  # 慢查询日志
```

日志样例（log_lock_waits = on 后）：

```
LOG:  process 1234 still waiting for ShareLock on transaction 567 after 1000.123 ms
DETAIL:  Process holding the lock: 890. Wait queue: 1234, 2345.
CONTEXT:  while updating tuple (10,5) in relation "accounts"
```

### 8.3 经典死锁场景

```sql
-- T1
BEGIN;
UPDATE accounts SET balance=balance-100 WHERE id=1;
UPDATE accounts SET balance=balance+100 WHERE id=2;

-- T2（并发）
BEGIN;
UPDATE accounts SET balance=balance-50 WHERE id=2;   -- 拿 id=2
UPDATE accounts SET balance=balance+50 WHERE id=1;   -- 等 T1 的 id=1
                                                      -- T1 同时等 T2 的 id=2 → 死锁
```

避免方法：**所有事务以同一顺序访问资源**（按 id 升序）。

## 第九章：监控阻塞与锁等待

### 9.1 三个核心视图

```sql
-- pg_locks：当前所有锁
SELECT locktype, relation::regclass, mode, granted, pid
FROM pg_locks
ORDER BY granted, pid;

-- pg_stat_activity：当前所有活动会话
SELECT pid, usename, state, query, wait_event_type, wait_event, query_start
FROM pg_stat_activity
WHERE state != 'idle';

-- pg_blocking_pids()（PG 9.6+）：找出阻塞某个 pid 的所有 pid
SELECT pg_blocking_pids(1234);   -- 返回 {890, 567}
```

### 9.2 阻塞链查询（生产必备）

```sql
SELECT
    blocked.pid           AS blocked_pid,
    blocked.usename       AS blocked_user,
    blocking.pid          AS blocking_pid,
    blocking.usename      AS blocking_user,
    blocked.query         AS blocked_query,
    blocking.query        AS blocking_query,
    blocking.state        AS blocking_state,
    age(now(), blocked.query_start)  AS blocked_age,
    age(now(), blocking.query_start) AS blocking_age
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE blocked.wait_event_type = 'Lock'
ORDER BY blocked_age DESC;
```

**输出解读**：

- blocked_user 等 blocking_user
- 如果 blocking_state = 'idle in transaction'，说明阻塞者是**僵尸事务**——开了事务没提交也没回滚（连接池常见）

-- 硬杀：让对方收到 SIGTERM，连接断开（事务也会回滚）

## 第十章：Advisory Lock —— PG 杀手锏

### 10.1 概念

Advisory Lock = **应用层任意 64-bit key 的锁**，不绑定任何表/行。

- 完全由应用决定 key 含义
- 不阻塞 vacuum、不阻塞 DML
- 极轻量（lock table 里一项）

### 10.2 API

```sql
-- 会话级（连接断开自动释放）
SELECT pg_advisory_lock(123);          -- 单 key，阻塞直到拿到
SELECT pg_try_advisory_lock(123);      -- 非阻塞，返回 boolean
SELECT pg_advisory_unlock(123);        -- 释放

-- 事务级（事务结束自动释放，无需 unlock）
SELECT pg_advisory_xact_lock(123);
SELECT pg_try_advisory_xact_lock(123);

-- 共享锁（多个可并发持有）
SELECT pg_advisory_lock_shared(123);

-- 双 key 版本（int4, int4），更灵活
SELECT pg_advisory_lock(1, 2);
```

### 10.3 场景 1：分布式单例任务

```go
// 多实例部署，但定时任务只能在一台跑
func runCronJob(ctx context.Context, db *pgxpool.Pool) {
    conn, _ := db.Acquire(ctx)
    defer conn.Release()

    var locked bool
    conn.QueryRow(ctx, "SELECT pg_try_advisory_lock($1)", LOCK_KEY_CRON).Scan(&locked)
    if !locked {
        return  // 别人已经在跑
    }
    defer conn.Exec(ctx, "SELECT pg_advisory_unlock($1)", LOCK_KEY_CRON)

    doCronWork(ctx)
}
```

**关键**：必须用同一个 connection 持锁，连接池 release 之前要确保 unlock。如果用 `pg_advisory_xact_lock` 在事务内拿，事务一结束就释放，更安全。

### 10.4 场景 2：业务级唯一资源锁

```go
// 用户余额扣款，避免同一用户并发扣款
func deductBalance(ctx context.Context, db *pgxpool.Pool, userID int64, amount int) error {
    tx, _ := db.BeginTx(ctx, pgx.TxOptions{})
    defer tx.Rollback(ctx)

    // 事务级 advisory lock（事务结束自动释放）
    if _, err := tx.Exec(ctx, "SELECT pg_advisory_xact_lock($1, $2)", LOCK_NAMESPACE_USER, userID); err != nil {
        return err
    }

    // 现在同一 user 的所有 deductBalance 串行
    var balance int
    tx.QueryRow(ctx, "SELECT balance FROM users WHERE id=$1", userID).Scan(&balance)
    if balance < amount { return errors.New("insufficient") }
    tx.Exec(ctx, "UPDATE users SET balance=balance-$1 WHERE id=$2", amount, userID)
    return tx.Commit(ctx)
}
```

比 `SELECT ... FOR UPDATE` 优势：

- 不在堆表上占 xmax 槽位（不产生 dead tuple）
- 不需要先查存在的行（advisory lock 对不存在的 userID 也能拿）
- 命名空间式管理：用 (namespace, id) 双 key 区分不同业务

### 10.5 场景 3：迁移 / 部署互斥

```sql
-- DBA 跑 schema migration
SELECT pg_advisory_lock(MIGRATION_LOCK_KEY);
-- 跑迁移 SQL
SELECT pg_advisory_unlock(MIGRATION_LOCK_KEY);
```

Flyway / Liquibase / golang-migrate 等工具内部都用 advisory lock 做多实例并发部署互斥。

### 10.6 监控 advisory lock

```sql
SELECT pid, locktype, classid, objid, mode, granted
FROM pg_locks
WHERE locktype = 'advisory';
```

## 第十一章：长事务与 idle in transaction —— 第一杀手

### 11.1 长事务危害

长事务（包括 idle in transaction）对 PG 是**致命**的：

1. **阻塞 vacuum**：因为它的 xmin 是 horizon，所有比它新的 dead tuple 都不能回收 → 表膨胀（[P08 详解](./08-精通-VACUUM-与表膨胀.md)）
2. **WAL 暴涨**：dead tuple 不回收 → autovacuum 跑得更慢 → 新增 WAL 不能 archive
3. **replication slot 堆积**：物理 slot 的 WAL 段不能删 → 主库磁盘暴满
4. **直接持锁**：长事务里如果做过 DML，xmax/multi-xact 上的行锁一直不释放

### 11.2 找出长事务

```sql
SELECT
    pid,
    usename,
    state,
    age(now(), xact_start) AS xact_age,
    age(now(), state_change) AS idle_age,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND age(now(), xact_start) > interval '5 minutes'
ORDER BY xact_start;
```

`state` 可能值：

- `active`：正在执行 SQL
- `idle`：连接空闲，无事务
- `idle in transaction`：**有事务但没在执行 SQL**——僵尸事务，最危险
- `idle in transaction (aborted)`：事务已 abort 但还没 rollback——同样阻塞 vacuum

### 11.3 防御参数（PG 9.6+ / 14+）

```ini
# 自动 kill idle in transaction 超过 N
idle_in_transaction_session_timeout = '10min'

# PG 14+：kill idle 连接（即使没有事务）
idle_session_timeout = '1h'

# 限制单事务总时长（PG 17+）
transaction_timeout = '30min'

# 限制单语句时长（一直存在）
statement_timeout = '30s'

# 锁等待超时
lock_timeout = '3s'
```

生产推荐配置：

```ini
statement_timeout = '60s'                          # OLTP 严格限
idle_in_transaction_session_timeout = '5min'       # 防僵尸事务
lock_timeout = '3s'                                # 防 DDL 雪崩
deadlock_timeout = '1s'                            # 默认即可
```

## 第十二章：综合实战案例

### 12.1 案例 1：SSI 实现银行转账无双花

```sql
-- 不变量：所有账户总余额 >= 0
CREATE TABLE accounts (id int PRIMARY KEY, balance numeric);
INSERT INTO accounts VALUES (1, 100), (2, 100);

-- 规则：A 给 B 转钱时，必须保证 A 余额 >= 转账金额（不能透支）
-- 多个并发转账可能导致同时检查再扣减 → 透支

-- 用 SSI 保证
DO $$ BEGIN END; $$;  -- 占位

-- 两个并发事务
-- T1: A 给 B 转 80
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT sum(balance) FROM accounts WHERE id=1;  -- 100
UPDATE accounts SET balance=balance-80 WHERE id=1;
UPDATE accounts SET balance=balance+80 WHERE id=2;
COMMIT;

-- T2: A 给 B 转 80（并发）
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT sum(balance) FROM accounts WHERE id=1;  -- 100（snapshot）
UPDATE accounts SET balance=balance-80 WHERE id=1;
UPDATE accounts SET balance=balance+80 WHERE id=2;
COMMIT;
-- SSI 检测到 rw-antidependency 环 → abort
-- ERROR: could not serialize access due to read/write dependencies
```

**为什么 RR 不行？** RR 下 T2 的 UPDATE 会基于"snapshot 时 balance=100"计算（first updater wins 触发：T2 在 T1 之后 commit，但 T1 已经把 A balance 改成 20，T2 应该看到 20 还是 100？答案是 PG 会让 T2 看到"T1 已提交的版本"，但 WHERE 不会重新评估——所以 T2 会成功 UPDATE，最终 balance = -60）。

实际：RR 在 UPDATE 阶段会触发 `could not serialize`，但这是因为**写写冲突**（两个 UPDATE 改同一行）；如果你测试用的是 UPDATE 不同行 + 读总和判断的场景，RR 防不住（典型 write skew）。SSI 通过 predicate locking 抓到读写依赖才能防。

### 12.2 案例 2：SKIP LOCKED 多 worker 队列消费

```sql
CREATE TABLE job_queue (
    id bigserial PRIMARY KEY,
    payload jsonb NOT NULL,
    status text DEFAULT 'PENDING',
    priority int DEFAULT 0,
    scheduled_at timestamptz DEFAULT now(),
    attempts int DEFAULT 0,
    last_error text,
    locked_by text,
    locked_at timestamptz,
    created_at timestamptz DEFAULT now()
);

CREATE INDEX idx_jobs_pending ON job_queue (priority DESC, scheduled_at)
WHERE status = 'PENDING';

-- worker 拉取
WITH next_job AS (
    SELECT id FROM job_queue
    WHERE status = 'PENDING' AND scheduled_at <= now()
    ORDER BY priority DESC, scheduled_at
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE job_queue j
SET status='RUNNING', locked_by=$1, locked_at=now(), attempts=attempts+1
FROM next_job n
WHERE j.id = n.id
RETURNING j.id, j.payload;
```

**为什么用部分索引 `WHERE status='PENDING'`？** 因为索引只需要覆盖 PENDING 的少数行（百万级队列里通常 PENDING < 1%），索引体积小、扫描快、不被 DONE/FAILED 干扰。

**为什么用 `FOR UPDATE SKIP LOCKED + UPDATE`？** SKIP LOCKED 保证 worker 之间不争抢；UPDATE 状态改为 RUNNING 后即使 worker 崩溃，定时任务可以根据 `locked_at` 超时把行重置回 PENDING。

### 12.3 案例 3：用 pg_blocking_pids 画阻塞链

线上告警："某 API 响应从 50ms 飙到 5s"，登上数据库：

```sql
SELECT pid, state, wait_event_type, wait_event, query_start, query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY query_start;
```

发现 30 个会话都在 `wait_event_type='Lock'`。挖阻塞链：

```sql
WITH RECURSIVE chain AS (
    SELECT pid, pg_blocking_pids(pid) AS blocked_by, 1 AS depth
    FROM pg_stat_activity
    WHERE pg_blocking_pids(pid) <> '{}'
    UNION ALL
    SELECT a.pid, pg_blocking_pids(a.pid), c.depth + 1
    FROM pg_stat_activity a
    JOIN chain c ON a.pid = ANY(c.blocked_by)
    WHERE c.depth < 10
)
SELECT * FROM chain;
```

输出形如：

```
pid     blocked_by   depth
1001    {2002}       1
1002    {2002}       1
...
2002    {}           1     ← 根
```

定位到 pid=2002，查它的状态：

```sql
SELECT state, query, age(now(), state_change) AS idle_age
FROM pg_stat_activity WHERE pid=2002;
```

发现：`state='idle in transaction'`，已经 idle 15 分钟——某段业务代码忘了 commit/rollback。

应急：`SELECT pg_terminate_backend(2002);`
长期：设 `idle_in_transaction_session_timeout = '5min'`。

## 生产实践

### 隔离级别选择

| 业务类型 | 推荐 |
|---|---|
| 普通 OLTP（API、CRUD） | READ COMMITTED（默认） |
| 金融账单、库存、配额扣减 | SERIALIZABLE + retry 重试逻辑 |
| 长报表 / 数据导出 | REPEATABLE READ + READ ONLY DEFERRABLE |
| ETL 批处理 | RR + 显式 advisory lock 保护资源 |
| 单一资源严格互斥 | RC + advisory lock |

### 必设参数（postgresql.conf）

```ini
deadlock_timeout = '1s'                              # 死锁检测间隔
log_lock_waits = on                                   # 锁等待记录
statement_timeout = '60s'                             # 单 SQL 时长
lock_timeout = '3s'                                   # 锁等待时长
idle_in_transaction_session_timeout = '5min'          # 僵尸事务克星
idle_session_timeout = '1h'                           # PG 14+
default_transaction_isolation = 'read committed'      # 默认隔离
max_pred_locks_per_transaction = 64                   # SSI predicate locks
```

### 应用层规范

1. **永远写 retry 循环**——RR/SSI 必须；RC 偶尔也会遇到（HOT chain 异常）
2. **事务尽可能短**：把网络 IO、外部调用挪到事务外
3. **统一资源访问顺序**：避免死锁
4. **连接池要 release 时 rollback**：避免遗留事务
5. **大表 DDL 必须 `SET lock_timeout`**：避免 MDL 雪崩
6. **CREATE INDEX 默认走 CONCURRENTLY**

### 监控告警

| 指标 | 阈值 | 告警 |
|---|---|---|
| `pg_stat_activity` 中 `idle in transaction` 超过 5 分钟 | 1 个 | 紧急 |
| `pg_locks` 中 `granted=false` | > 10 | 警告 |
| `pg_locks` 中 `granted=false` | > 50 | 紧急 |
| 单个事务 `xact_start` 超过 30 分钟 | 1 个 | 紧急（vacuum 危机） |
| 锁等待平均时长 | > 1s | 警告 |
| 死锁次数 / 5min | > 5 | 警告 |

## 陷阱清单

1. **READ UNCOMMITTED 形同 READ COMMITTED**——别以为能读到未提交数据。
2. **RR 防幻读 ≠ 防写偏序**——doctors 案例每年都坑人，必须用 SSI 或显式锁。
3. **SSI 可能在 COMMIT 时报错**——retry 必须从 BEGIN 开始重做整个事务。
4. **`SELECT FOR UPDATE` 在 RR 下也可能 40001**——不是只有写写冲突会触发。
5. **行锁不会释放给 vacuum**——长事务的 xmax 阻塞 dead tuple 回收。
6. **`CREATE INDEX`（无 CONCURRENTLY）持 SHARE 锁**——阻塞所有 INSERT/UPDATE/DELETE。
7. **`ALTER TABLE` 默认 AccessExclusive**——即使 PG 11+ 加列不 rewrite，也持 AE 几毫秒，足以让没设 lock_timeout 的 DDL 雪崩。
8. **`TRUNCATE` 持 AccessExclusive**——比 `DELETE FROM` 锁更强（DELETE 是 RowExclusive）。
9. **Advisory Lock 不跨连接**——必须同一 connection 持有，连接池一定要锁定 connection 范围。
10. **`pg_try_advisory_lock` 多次调用同一 key 会累加计数**——unlock 也要相同次数。
11. **VACUUM 不持表锁不代表"不影响业务"**——它和 ANALYZE 持 ShareUpdateExclusive，会阻塞另一个 VACUUM/CREATE INDEX CONCURRENTLY/部分 ALTER。
12. **`idle in transaction (aborted)`仍阻塞 vacuum**——必须显式 rollback。
13. **死锁告警未必是真死锁**：`deadlock_timeout` 内的锁等待会被记录为"still waiting"，超时后才检测。
14. **SKIP LOCKED 不能与 FOR SHARE 配合用**——会被忽略，必须 FOR UPDATE / FOR NO KEY UPDATE。
15. **`pg_cancel_backend` 不一定立即生效**——如果对方在 syscall（磁盘 IO），可能要几秒；用 `pg_terminate_backend` 更暴力但确定。
16. **MultiXact wraparound 危机**——共享行锁过多时，MultiXact ID 也会 wraparound（独立于 xid），罕见但发生过线上事故。
17. **PgBouncer transaction pool 模式下 advisory lock 不可靠**——因为连接被回收。需用 session pool 或事务级 advisory_xact_lock。
18. **`SELECT FOR UPDATE OF t1` 在 join 时**——只锁 t1 的行，t2 不锁；写 SQL 时要明确。

| **SSI 稳定性** | PG 9.1（2011）引入 SSI 至今稳定；CockroachDB、YugabyteDB、FoundationDB 均借鉴此思想；2025 学界仍在 SSI 上发论文（如 PolarDB SSI 改进） |
| **xid 64-bit** | 社区 2024-2025 持续讨论；EDB / Citus / GreenPlum 等商业版已实现；PG 19 可能进入 mainline |
| **PG 17 改进** | `transaction_timeout` 参数（限制单事务总时长）；改进的 pg_stat_activity 字段 |
| **PG 18 改进** | 异步 IO 让锁等待期间不阻塞内核（部分场景）；`pg_stat_locks` 视图增强 |
| **Logical replication 与锁** | PG 16+ 支持 standby 上的 logical decoding，slot 不再单点 |
| **死锁可观测性** | pgAnalyze / Datadog / SkySQL 等 SaaS 工具普遍支持死锁 trace；自研 Prometheus exporter 也都集成 |
| **连接池趋势** | pgcat（Rust，2024-2026 迭代活跃）、PgBouncer 1.22+ 支持 PG 17；CloudNativePG 自带 PgBouncer sidecar |
| **AI 辅助锁分析** | Datadog Watchdog / pganalyze Index Advisor 开始用 LLM 解读死锁日志，给出修复建议 |

## 练习题

1. 解释 PG 的 READ COMMITTED 下 UPDATE 触发 EvalPlanQual 的过程。如果你执行 `UPDATE t SET v=v+1 WHERE v > 10`，并发事务把 v 从 12 改成 5 并提交，你的 UPDATE 会做什么？

2. 写出 doctors 写偏序案例。手动模拟 RR 下两个事务交错，最终破坏不变量；然后切到 SERIALIZABLE 重做，观察 SSI 报错。提交时谁会被 abort？

3. 设计一个"用户每天最多发 5 条评论"的限流，要求绝对不超额。给出三种方案：(a) RC + advisory lock；(b) SERIALIZABLE + retry；(c) UPSERT + 唯一索引。分析各自优缺点。

4. 用一张 1000 万行的表，跑下面 SQL 时 PG 加什么锁？为什么？
   - `SELECT * FROM t`
   - `UPDATE t SET v=v+1 WHERE id=1`
   - `CREATE INDEX idx_v ON t(v)`
   - `CREATE INDEX CONCURRENTLY idx_v ON t(v)`
   - `ALTER TABLE t ADD COLUMN x int DEFAULT 0`
   - `VACUUM t`
   - `VACUUM FULL t`

5. 写出"PG advisory lock 实现一个全局 FIFO 队列"的伪代码。要求多进程消费且严格 FIFO（不能跳号）。如果不能严格 FIFO，分析为什么 SKIP LOCKED 不能保证 FIFO。

6. 解释为什么 PG 行锁可以"无限多"而不需要 lock table。如果你 UPDATE 一行 1 亿次（同一事务内），xmax 字段会变成什么？vacuum 后会怎样？

7. 一个会话长时间 `idle in transaction`，列出至少 5 个潜在后果（vacuum / WAL / slot / 锁 / 连接数）。如何配置参数 + 监控告警避免？

8. 给定如下阻塞链：
   ```
   pid=100 blocked by {200}
   pid=200 blocked by {300}
   pid=300 idle in transaction 30min
   pid=400 blocked by {200}
   ```
   描述应急处理顺序、SQL 命令、以及事后改进措施。
