# 精通逻辑复制：从 Logical Decoding 到 Debezium、跨大版本零停机升级

> 关联章节：[P15 WAL 与物理复制](./15-精通-WAL-与物理流复制.md)、[P03 MVCC](./03-精通-MVCC-与可见性.md)、[P17 高可用](./17-精通-高可用与连接池.md)、[P22 PG18/17 新特性](./22-精通-PG18-17-新特性.md)

## 引言：为什么物理复制不够用

P15 讲了 streaming replication（物理流复制）——主备**二进制完全一致**，足够支撑高可用和读扩展。但它有几个根本限制：

1. **整集群一刀切**：不能只复制一张表、一个库
2. **不能跨大版本**：PG 16 主 → PG 17 备，搭都搭不起来
3. **不能跨架构 / 跨字节序**：x86 ↔ ARM、Linux ↔ Windows 不行
4. **备库只读**：不能在备库写入然后再合并回主
5. **不能发到非 PG**：想把变化推到 Kafka / ES / ClickHouse？物理 WAL 给不了

逻辑复制（Logical Replication）解决以上所有问题。它的核心是 **Logical Decoding**（PG 9.4+）——把物理 WAL 解析成"逻辑变更"（INSERT 哪一行、UPDATE 哪些列），然后通过 **Publication / Subscription**（PG 10+）做表级订阅，或通过 **Debezium / wal2json** 等外部消费者发到任意下游。

读完本章你应该能：

- 区分物理复制和逻辑复制 5 个核心差异
- 解释 Logical Decoding 的 reorder buffer 和 output plugin 机制
- 配置 PG 内置 publication / subscription（含 PG 15+ 行/列过滤）
- 排查初始 COPY 慢、流式落后、订阅冲突三大常见故障
- 用 Debezium + Kafka Connect 把 PG 变化推到 Kafka
- 用逻辑复制做 PG 14 → PG 18 零停机升级（详细步骤）
- 知道 PG 16 双向、PG 17 failover slot 的能力边界

## 第 1 章：物理 vs 逻辑复制

### 1.1 对比表

| 维度 | 物理复制 (P15) | 逻辑复制 |
|---|---|---|
| **粒度** | 整集群 | 表级（甚至行/列） |
| **跨大版本** | ❌ 必须同版本 | ✅ PG 10 → PG 18 都行 |
| **跨字节序 / 平台** | ❌ | ✅ |
| **下游能写** | ❌ 只读 standby | ✅ subscriber 可写 |
| **同时多源** | ⚠️ 备库只能一个主 | ✅ subscriber 可订多 publisher |
| **DDL 复制** | ✅ 自动同步 | ❌ 不复制 DDL（需手动） |
| **序列同步** | ✅ | ⚠️ 仅订阅初始化时复制，之后不同步 |
| **TRUNCATE** | ✅ | ✅（默认）/可关 |
| **大事务** | ✅ 边写边 replay | ⚠️ 默认要等事务 COMMIT 才解码（PG 14+ 可流式） |
| **延迟** | 极低（ms） | 略高（reorder + 提交后才发） |
| **典型用途** | HA、读扩展、容灾 | 跨版本升级、CDC、表级订阅、聚合到分析库 |

### 1.2 选哪个

| 需求 | 选 |
|---|---|
| 主从同城高可用 | 物理 |
| 异地容灾 | 物理（async） |
| PG 14 → PG 18 在线升级 | **逻辑** |
| 同步部分表到分析库 | **逻辑** |
| 推送变更到 Kafka | **逻辑 + Debezium** |
| 整库读写分离 | 物理 |
| 多个业务库聚合到一个数仓 | **逻辑（多订阅）** |
| 双中心双活 | **逻辑双向**（PG 16+） |

## 第 2 章：Logical Decoding —— 一切的底座

### 2.1 它在做什么

物理 WAL 长这样（rmgr 视角）：

```
INSERT off=8 in rel 16384 blk 0  [tuple bytes...]
```

下游消费者看不懂——它只知道"某文件某块某 offset 改了"。Logical Decoding 把它翻译成：

```
table public.users: INSERT: id=42, name='Alice', email='a@x.com'
```

这种翻译需要表结构信息——PostgreSQL 在 backend 进程里跑 logical decoding，能查 catalog 拿到表定义。

### 2.2 关键前提：`wal_level = logical`

```ini
wal_level = logical    # 重启生效
max_wal_senders = 10
max_replication_slots = 10
```

`logical` 比 `replica` 在 WAL 中多写：

- **REPLICA IDENTITY** 信息：UPDATE/DELETE 的 OLD 行的关键列
- 一些额外的 catalog snapshot 信息

代价：WAL 量大 5-15%。

### 2.3 REPLICA IDENTITY

为了让下游知道 UPDATE 改了哪一行，PG 在 WAL 里要带"OLD 行的标识"。这个标识由 `REPLICA IDENTITY` 设置：

| 设置 | 行为 |
|---|---|
| `DEFAULT`（默认） | OLD 行只带主键列 |
| `USING INDEX idx_name` | OLD 行带指定唯一索引的列 |
| `FULL` | OLD 行带所有列（重的不得了） |
| `NOTHING` | 不带——UPDATE/DELETE 不能逻辑复制 |

```sql
ALTER TABLE orders REPLICA IDENTITY FULL;
ALTER TABLE products REPLICA IDENTITY USING INDEX products_sku_idx;
```

**陷阱**：没有主键、没有唯一索引的表，默认 `DEFAULT` 等于 `NOTHING`——这种表 UPDATE/DELETE 不能复制。**必须设 `REPLICA IDENTITY FULL`** 或加主键。

### 2.4 Reorder Buffer

PG 多事务并发提交，但 logical decoding 必须**按提交顺序**发给下游。reorder buffer 把每个事务的变更暂存在内存（超过 `logical_decoding_work_mem`，PG 13+，默认 64 MB 就溢出到 disk），COMMIT 时才一次性发出。

```
T1: INSERT a
T2: INSERT b
T1: INSERT c
T2: COMMIT  → 发: BEGIN; INSERT b; COMMIT
T1: COMMIT  → 发: BEGIN; INSERT a; INSERT c; COMMIT
```

副作用：**长事务会堵塞 logical replication**——T1 不 COMMIT，T2 后面所有事务的 WAL 都得在 buffer 里等着（因为 slot 不能 advance）。

PG 14+ 引入**流式逻辑解码**（streaming in-progress transactions）：长事务可以边解码边发，下游收到 STREAM 标识自己缓存到 COMMIT 应用，缓解大事务问题。需要订阅端 `streaming = on`。

### 2.5 Output Plugin

Logical Decoding 框架解析出"逻辑变更结构"后，转给 **output plugin** 序列化成具体格式：

| Plugin | 格式 | 主要场景 |
|---|---|---|
| `pgoutput`（内置） | PG 内部二进制协议 | PG 自带 logical replication |
| `wal2json` | JSON | Debezium 1.x 早期、轻量自研消费者 |
| `decoderbufs` | Protobuf | Debezium 默认（PG connector） |
| `wal2avro` | Avro | 大数据生态 |
| `test_decoding`（内置） | 文本（人类可读） | 调试用 |

`test_decoding` 是最快的"看一眼 WAL 在解码什么"的工具：

```sql
SELECT pg_create_logical_replication_slot('test_slot', 'test_decoding');

-- 主库另开会话做点 DML
INSERT INTO t VALUES (1, 'a');

-- 看解码结果
SELECT data FROM pg_logical_slot_peek_changes('test_slot', NULL, NULL);
/*
BEGIN 750
table public.t: INSERT: id[integer]:1 name[text]:'a'
COMMIT 750
*/

SELECT pg_drop_replication_slot('test_slot');
```

## 第 3 章：内置 Publication / Subscription（PG 10+）

### 3.1 整体架构

```
Publisher (PG 主)                      Subscriber (PG 另一实例)
  ├── walsender (用 pgoutput plugin)   ├── apply worker (类似备库的 startup)
  ├── logical replication slot         ├── (可选) parallel apply workers (PG 16+)
  └── PUBLICATION 定义                 └── SUBSCRIPTION 定义
        ↓ pgoutput 协议 ↓
  网络流（用 streaming protocol）
```

### 3.2 创建 Publication

```sql
-- 发布所有表
CREATE PUBLICATION pub_all FOR ALL TABLES;

-- 发布指定表
CREATE PUBLICATION pub_orders FOR TABLE orders, customers;

-- PG 15+：按 schema
CREATE PUBLICATION pub_app FOR TABLES IN SCHEMA app;

-- 只复制部分操作
CREATE PUBLICATION pub_audit FOR TABLE audit_log
    WITH (publish = 'insert, update');   -- 不发 DELETE / TRUNCATE
```

### 3.3 创建 Subscription

```sql
-- 在 subscriber 上执行
CREATE SUBSCRIPTION sub_orders
    CONNECTION 'host=publisher.example.com port=5432 user=repl dbname=app password=xxx'
    PUBLICATION pub_orders;
```

Subscription 立刻做两步：

1. **初始数据同步**：对每张被订阅表做 `COPY`（相当于全量快照）
2. **流式增量**：COPY 完后从某个 LSN 开始流式 apply 增量

第二步通过创建一个 logical slot 在 publisher 上保持位置。

### 3.4 看状态

```sql
-- subscriber
SELECT * FROM pg_subscription;
SELECT * FROM pg_stat_subscription;

-- 每张表的初始同步状态
SELECT srrelid::regclass, srsubstate, srsublsn
FROM pg_subscription_rel;
-- srsubstate:
--   i = initializing
--   d = data is being copied
--   s = synchronized (waiting for catchup)
--   r = ready (normal replication)
```

### 3.5 参数

```sql
CREATE SUBSCRIPTION sub
    CONNECTION '...'
    PUBLICATION pub
    WITH (
        copy_data = true,         -- 初始 COPY
        create_slot = true,       -- publisher 上自动建 slot
        slot_name = 'sub_slot',   -- slot 名（默认与 subscription 同名）
        synchronous_commit = off, -- subscriber apply 时的 commit 设置
        streaming = parallel,     -- PG 14+ 大事务流式（PG 16+ 设为 parallel 启用并行 apply）
        binary = true,            -- PG 14+ 二进制协议（少 30% 流量）
        two_phase = true,         -- PG 15+ 复制 prepared transactions
        origin = 'any',           -- PG 16+ 双向复制时用 'none' 过滤回环
        failover = true           -- PG 17+ 与物理 standby 关联以便 failover
    );
```

### 3.6 增减发布表（DDL 手动）

```sql
-- publisher
ALTER PUBLICATION pub_orders ADD TABLE order_items;

-- subscriber：必须先在本地建表（DDL 不会复制！）
CREATE TABLE order_items (...);

-- subscriber：刷新订阅
ALTER SUBSCRIPTION sub_orders REFRESH PUBLICATION;
```

**新加的表会触发初始 COPY**——和初次订阅一样的步骤。

## 第 4 章：PG 15+ 行过滤与列过滤

### 4.1 行过滤（Row Filter）

```sql
-- publisher
CREATE PUBLICATION pub_us_orders FOR TABLE orders
    WHERE (country = 'US' AND amount > 100);
```

只有满足条件的行会被发出去。

**陷阱**：

- `WHERE` 表达式只能用**不可变函数**（不能 `now()`、不能用其他表）
- UPDATE 时：旧值满足条件、新值不满足 → 发 DELETE；反之 → 发 INSERT；都满足 → 发 UPDATE；都不满足 → 不发
- UPDATE 同步策略需要表的 REPLICA IDENTITY 至少覆盖 WHERE 用到的列

### 4.2 列过滤（Column List）

```sql
-- publisher
CREATE PUBLICATION pub_users_public FOR TABLE users (id, name, created_at);
-- 不发 email, password_hash, phone 等敏感列
```

用途：

- 隐私：合规要求下游不能拿敏感字段
- 减少流量：宽表只订阅几列

**约束**：

- 必须包含主键（或 REPLICA IDENTITY 涉及的列）
- 一张表在不同 publication 中可以有不同列表，但是同一个订阅看到的列必须能合并

### 4.3 完整示例：脱敏推到分析库

```sql
-- 业务库（publisher）
CREATE PUBLICATION pub_analytics
    FOR TABLE users (id, country, signup_date),
        TABLE orders (id, user_id, amount, currency, created_at)
        WHERE (status = 'paid');

-- 分析库（subscriber）
CREATE SUBSCRIPTION sub_analytics
    CONNECTION '...'
    PUBLICATION pub_analytics;
```

只把已支付订单的非敏感列复制到分析库。

## 第 5 章：冲突处理

### 5.1 冲突来源

逻辑复制 **不是物理一致**——subscriber 是一个独立的 PG 实例，可以被本地写入。这就有冲突的可能：

1. **INSERT 主键冲突**：publisher 发 INSERT id=5，但 subscriber 上 id=5 已存在
2. **UPDATE 找不到行**：publisher 发 UPDATE WHERE id=5，但 subscriber 上没这行
3. **DELETE 找不到行**：同上
4. **数据类型不一致**：publisher 改成 BIGINT，subscriber 还是 INT，溢出

### 5.2 冲突的后果

默认行为：**apply worker 报错并退出**。订阅暂停在那个事务，所有后续 WAL 都堵着，直到人工介入。

```sql
-- subscriber 日志
LOG:  logical replication worker for subscription "sub" has finished
ERROR:  duplicate key value violates unique constraint "users_pkey"
DETAIL:  Key (id)=(5) already exists.
```

### 5.3 排错套路

```sql
-- 1. 看哪个事务卡住
SELECT * FROM pg_stat_subscription;
SELECT * FROM pg_replication_origin_status;

-- 2. 跳过该事务（最粗暴，PG 15+）
ALTER SUBSCRIPTION sub SKIP (lsn = '0/12345678');

-- 3. 或者人工解决冲突（删冲突的本地行 / 改 schema）
DELETE FROM users WHERE id = 5;
-- subscription 会自动重试
```

PG 15+ 的 `SKIP (lsn = ...)` 比之前安全多了——精确跳一个 LSN，不会误伤别的。

### 5.4 PG 18 解冲策略（实验性扩展）

PG 18 开始讨论"冲突策略选择"（`apply_error_callback_action`），允许配置 last-write-wins / keep-local / log-only 等，但生产规模化使用还要等几个版本。当前主流仍靠 schema 设计避免冲突（subscriber 不接受本地写、主键策略选 UUIDv7 等）。

## 第 6 章：双向逻辑复制（PG 16+）

### 6.1 历史

PG 14 之前要做双向复制（A↔B），用户自己写循环防护：每个事务带个 source tag，apply 时检查不是自己来源的才执行。第三方扩展 `pglogical`、`BDR`（EDB）做过商业实现。

PG 16 把"防回环"做进核心：**Replication Origin Filtering**。

### 6.2 配置

每个 subscription 有个 origin（标识来源）。订阅时可以选择只复制"来自特定 origin"的变更：

```sql
-- 节点 A 订阅 B
CREATE SUBSCRIPTION sub_from_b
    CONNECTION 'host=B ...'
    PUBLICATION pub_all
    WITH (origin = 'none');   -- 只复制 B 上"本地写入"的变更，不复制 B 从 C 等转发的

-- 节点 B 订阅 A
CREATE SUBSCRIPTION sub_from_a
    CONNECTION 'host=A ...'
    PUBLICATION pub_all
    WITH (origin = 'none');
```

`origin = 'none'` = 只接受没有 origin 标记的变更（即本地客户端写入），不接受其他订阅 apply 来的——这就阻止了 A→B→A 的回环。

`origin = 'any'`（默认）= 接受所有，包括转发的（用于级联场景）。

### 6.3 限制

- 不解决冲突（如双方同时改一行）——还是人工处理
- DDL 仍不复制——两边需要分别执行
- 不是真正的"多主"（multi-master）——PG 仍是单主架构，双向只是工程便利

主流用法：**主备双向准备好**，正常单方向使用；发生 failover 时立刻反向，减少切换复杂度。

## 第 7 章：PG 17 故障切换不中断订阅（Failover Slot）

### 7.1 痛点

逻辑 slot 只存在于主库。物理 standby 取代主库后，新主上没有这个 slot——所有 subscriber 都得重建，初始 COPY 一遍（可能上 TB）。

### 7.2 PG 17 方案

`failover = true` 的 slot 会自动同步到物理 standby：

```sql
CREATE SUBSCRIPTION sub
    CONNECTION '...'
    PUBLICATION pub
    WITH (failover = true);
```

主库 promote 新主后，subscriber 自动连到新主的同名 slot，几乎无缝继续。

要求：

- 主库 `synchronized_standby_slots` 配置同步给哪些 standby
- 物理 standby 上 `sync_replication_slots = on`（PG 17+）
- 物理复制必须开

### 7.3 适用场景

- HA 切换时不丢失 subscriber 进度
- 跨版本升级中途主库故障也能恢复

PG 17 之前，需要 `pg_failover_slots`（第三方）或者 PgBouncer/路由层做妥协。

## 第 8 章：CDC 与 Debezium

### 8.1 为什么不用 PG 内置订阅

PG 内置 publication/subscription 只能 PG → PG。如果你要：

- 推 PG 变更到 Kafka
- 再让多个消费者各自处理（Elasticsearch、Redis 缓存失效、风控）

那就要用 Debezium。

### 8.2 Debezium 架构

```
PostgreSQL ──→ Debezium PG Connector ──→ Kafka topics ──→ 各下游
            (logical slot + decoderbufs/                    ├── Elasticsearch
             pgoutput plugin)                                ├── Cache invalidation
                                                             ├── Risk engine
                                                             └── Data lake
```

Debezium 跑在 Kafka Connect 上。每个表对应一个 topic：

- `myhost.public.users`
- `myhost.public.orders`

消息格式（JSON 示例）：

```json
{
  "before": null,
  "after": {"id": 42, "name": "Alice", "created_at": "2026-05-28T10:00:00Z"},
  "source": {"db": "app", "schema": "public", "table": "users", "lsn": 12345678, "txId": 1001},
  "op": "c",
  "ts_ms": 1748428800000
}
```

`op`: `c` (create/insert), `u` (update), `d` (delete), `r` (read = 初始 snapshot)。

### 8.3 配置 PG 端

```ini
# postgresql.conf
wal_level = logical
max_replication_slots = 10
max_wal_senders = 10
```

```sql
CREATE ROLE debezium WITH REPLICATION LOGIN PASSWORD 'xxx';
GRANT CONNECT ON DATABASE app TO debezium;
GRANT USAGE ON SCHEMA public TO debezium;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO debezium;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO debezium;

-- 给 UPDATE/DELETE 复制做准备
ALTER TABLE users REPLICA IDENTITY DEFAULT;   -- 有主键即可
ALTER TABLE orders REPLICA IDENTITY FULL;     -- 无主键大表
```

### 8.4 Debezium Connector 配置

```json
{
  "name": "pg-cdc",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "pg.example.com",
    "database.port": "5432",
    "database.user": "debezium",
    "database.password": "xxx",
    "database.dbname": "app",
    "topic.prefix": "myhost",
    "plugin.name": "pgoutput",
    "slot.name": "debezium_slot",
    "publication.name": "dbz_publication",
    "publication.autocreate.mode": "filtered",
    "table.include.list": "public.users,public.orders",
    "snapshot.mode": "initial",
    "heartbeat.interval.ms": "10000",
    "key.converter": "org.apache.kafka.connect.json.JsonConverter",
    "value.converter": "org.apache.kafka.connect.json.JsonConverter"
  }
}
```

关键配置：

- `plugin.name`：`pgoutput`（推荐，PG 内置，零外部依赖）或 `wal2json`、`decoderbufs`
- `slot.name`：与 PG 上 slot 名一致；不存在会自动创建
- `publication.name` + `publication.autocreate.mode`：自动管理 publication
- `snapshot.mode`：`initial`（首次全量+增量）、`never`、`always`、`incremental`（DBZ 2.x+ chunked snapshot）
- `heartbeat.interval.ms`：极重要——空闲 slot 不发心跳，主库 WAL 不能回收

### 8.5 心跳的必要性

如果 PG 中很多事务都不在 Debezium 订阅的表上，slot 不前进，WAL 永久保留。

`heartbeat.interval.ms = 10000` 让 Debezium 每 10 秒写一条心跳到 PG 的某张心跳表，触发 slot 前进。

或者用 `heartbeat.action.query` 让 PG 端的某个状态表前进：

```json
"heartbeat.action.query": "INSERT INTO debezium_heartbeat (ts) VALUES (now()) ON CONFLICT DO NOTHING"
```

### 8.6 监控

```sql
-- PG 侧
SELECT slot_name, plugin, active, confirmed_flush_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS lag
FROM pg_replication_slots;
```

Debezium JMX metrics：`MilliSecondsBehindSource`、`NumberOfEventsProcessed`。

## 第 9 章：跨大版本零停机升级（PG 14 → PG 18）

### 9.1 选项对比

| 方案 | 停机 | 难度 | 适合 |
|---|---|---|---|
| pg_dump / pg_restore | 几小时 | 低 | 小库、能停机 |
| `pg_upgrade --link` | 几分钟 | 中 | 单实例、风险可控 |
| 物理复制 | ❌ 不能跨大版本 | - | - |
| **逻辑复制** | **几秒**（仅 DNS 切换） | 高 | 大库、生产、零停机 |

### 9.2 升级步骤（PG 14 → PG 18）

```
旧主 PG 14              新主 PG 18
   │                       │
   ├─── publication ──→ subscription（logical）
   │                       │
   │                       │ 初始 COPY + 增量 catchup
   │                       │
   │                       ↓
   │                  追平 LSN
   │                       │
   ↓                       ↓
   停写              切到新主，DNS 切换
   │
   废弃
```

详细步骤：

**1. 新主搭好 PG 18，建相同 schema**

```bash
pg_dump -h pg14 -d app --schema-only > schema.sql
psql -h pg18 -d app < schema.sql
```

注意手动检查：

- 扩展版本（pg_stat_statements、pgvector 等）
- 序列起始值（订阅不复制序列，下面会讲）
- 默认值、约束、触发器

**2. 旧主创建 publication**

```sql
-- pg14
ALTER SYSTEM SET wal_level = 'logical';
-- 重启
SELECT pg_reload_conf();

CREATE PUBLICATION migrate_all FOR ALL TABLES;
```

如果原本是物理复制 + `wal_level=replica`，升级到 logical 需要重启（计划好维护窗口）。

**3. 新主创建 subscription**

```sql
-- pg18
CREATE SUBSCRIPTION migrate
    CONNECTION 'host=pg14 user=migrator dbname=app password=xxx'
    PUBLICATION migrate_all
    WITH (copy_data = true, streaming = on, binary = true);
```

初始 COPY 阶段：

- 大表会很慢（几小时到几天）
- COPY 期间旧主写入持续，增量在 slot 里堆着
- 监控：`pg_subscription_rel` 看每张表状态从 `i → d → s → r`

**4. 等增量追平**

```sql
-- 新主
SELECT now() - pg_last_xact_replay_timestamp();   -- 接近 0 时切换

-- 或者比较 LSN
SELECT subname, latest_end_lsn FROM pg_stat_subscription;
```

**5. 同步序列**（订阅不复制序列！）

```sql
-- 旧主导出序列当前值
psql -h pg14 -d app -At -c "
  SELECT 'SELECT setval(' || quote_literal(schemaname || '.' || sequencename) ||
         ', ' || last_value || ');'
  FROM pg_sequences;
" > sync_seq.sql

-- 切换前在新主执行
psql -h pg18 -d app < sync_seq.sql
```

**6. 切换**

```bash
# 旧主停止接受写入
psql -h pg14 -c "ALTER SYSTEM SET default_transaction_read_only = on;"
psql -h pg14 -c "SELECT pg_reload_conf();"

# 等订阅完全追平
psql -h pg18 -c "SELECT pg_last_xact_replay_timestamp();"

# DNS / proxy 切到新主
# 应用重连

# 删订阅（让新主独立）
psql -h pg18 -c "DROP SUBSCRIPTION migrate;"
```

切换窗口可以做到 **10 秒以内**（DNS TTL 短一点）。

### 9.3 升级常见坑

1. **大字段表 COPY 长**——TOAST 大字段 + 索引重建。可以先建无索引的目标表，COPY 完再建索引。
2. **PG 18 默认 collation 变了**（glibc → ICU）——索引可能需要重建。先在 staging 跑。
3. **扩展不兼容**——pgvector、PostGIS 在 PG 18 的版本要先确认。某些扩展旧版根本装不上 PG 18。
4. **不复制 DDL**——升级期间禁止 DDL。
5. **序列忘了同步**——新主自增 ID 撞主库已存在的值。
6. **大事务卡 slot**——升级前先把异常长的事务都清掉。
7. **`max_replication_slots` / `max_wal_senders` 不够**——同时还有物理复制时容易爆。

### 9.4 实际案例：800 GB 库从 PG 12 升到 PG 17

- 总体时间：从启动 sub 到切完 4 天 6 小时
- 初始 COPY 阶段：3 天 18 小时（带宽 200 Mbps 限速）
- 追平增量：约 6 小时（业务低峰把 sub 重启并 parallel apply）
- 切换窗口：12 秒（DNS TTL 10s + 应用重连）
- 切换后 24h 内观察主库稳定，删订阅

## 第 10 章：监控

### 10.1 必须的视图

```sql
-- publisher 视角
SELECT slot_name, plugin, slot_type, active, restart_lsn, confirmed_flush_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS lag_bytes
FROM pg_replication_slots
WHERE slot_type = 'logical';

-- subscriber 视角
SELECT subname, received_lsn, last_msg_send_time, last_msg_receipt_time,
       latest_end_lsn, latest_end_time,
       now() - latest_end_time AS apply_lag
FROM pg_stat_subscription;

-- 初始 COPY 进度
SELECT srrelid::regclass AS table, srsubstate
FROM pg_subscription_rel
WHERE srsubstate <> 'r';
```

### 10.2 Prometheus 指标

`postgres_exporter` 暴露的关键指标：

| 指标 | 含义 |
|---|---|
| `pg_replication_slots_pg_wal_lsn_diff` | slot 落后字节数 |
| `pg_replication_slots_active` | slot 是否有人连 |
| `pg_stat_subscription_msg_lag_seconds` | subscription apply 延迟 |
| `pg_stat_activity_count{state="active"}` | walsender 数量 |

### 10.3 告警阈值参考

| 指标 | 告警 |
|---|---|
| slot lag bytes | > 10 GB warning, > 50 GB critical |
| subscription apply lag | > 30 秒 warning, > 5 分钟 critical |
| slot active = false（持续） | > 5 分钟 critical |
| Debezium MilliSecondsBehindSource | > 60000 warning |

## 第 11 章：性能调优

### 11.1 Publisher 侧

```ini
wal_level = logical
max_wal_senders = 20            # 物理 + 逻辑订阅都要够
max_replication_slots = 20
max_logical_replication_workers = 8
logical_decoding_work_mem = 256MB   # 大事务的 reorder buffer 内存
max_slot_wal_keep_size = 100GB      # 必须设，防 slot 卡死撑爆磁盘
```

### 11.2 Subscriber 侧

```ini
max_logical_replication_workers = 8
max_sync_workers_per_subscription = 4   # 初始 COPY 并行度
max_parallel_apply_workers_per_subscription = 4  # PG 16+ 并行 apply
```

### 11.3 初始 COPY 加速

- 临时删订阅端表上的非必需索引，COPY 完再建（特别是 GIN）
- `max_sync_workers_per_subscription = 4` 多表并行 COPY
- 网络足够宽

### 11.4 流式增量加速

- PG 14+ `streaming = on`：大事务边解码边发
- PG 16+ `streaming = parallel`：subscriber 多 worker 并行 apply
- PG 14+ `binary = true`：少 30% 流量

## 生产实践

### 实践 1：CDC 推 Kafka 完整拓扑

```
[PostgreSQL 主]
   │
   │ logical slot (debezium_slot)
   ↓
[Debezium PG Connector @ Kafka Connect cluster]
   │ snapshot mode = incremental
   │ heartbeat = 10s
   ↓
[Kafka topics: myhost.public.*]
   │
   ├──→ [Elasticsearch sink connector]   →  ES (商品检索)
   ├──→ [Redis cache invalidator]        →  缓存失效
   ├──→ [Flink job]                       →  实时计算
   └──→ [HDFS / Iceberg sink]             →  数据湖
```

要点：

- Connector 与 PG 不同机房时 `slot.drop.on.stop = false`，防止重启全量
- `snapshot.mode = incremental`（DBZ 2.x+）：大表分批 snapshot，不阻塞增量
- 心跳必开，否则 WAL 撑爆
- 多 connector 共享一份订阅库不可取，每个用独立 slot

### 实践 2：跨大版本升级路径（每年一次）

公司治理：每年升级一个大版本（PG 13 → 14 → 15 → 16 → 17 → 18），每次走逻辑复制，控制风险。

模板：
1. 提前 2 周搭新版本测试环境
2. 在测试环境用 logical replication 同步生产 30%-50% 数据
3. 跑应用回归测试 + 性能基准对比
4. 提交切换计划（含回滚步骤）
5. 维护窗口执行切换（凌晨 4 点低峰）
6. 留旧版本 7 天后再删

### 实践 3：双中心准双向

```
DC1 主 ←—— logical(origin=none) ——→ DC2 主
   │                                     │
   ├── 物理 standby（同城）              ├── 物理 standby（同城）
   └── 应用集群 1                         └── 应用集群 2
```

正常：DC1 主写、DC2 读；同时反向 publication 待命。
故障：DC1 挂 → DC2 升主 → 应用切换。DC1 恢复后反向追同步。

不是真双活——避免双方同时写同一记录。多用于"近就近读、写主回归"。

## 陷阱清单

1. **`wal_level = logical` 没设就建 publication**——publication 能建但订阅 apply 完全无效，悄无声息。
2. **REPLICA IDENTITY 缺失**——无主键表 UPDATE/DELETE 不复制，DBA 半年后才发现下游缺数据。
3. **`max_slot_wal_keep_size` 不设 + slot 死掉**——主库 WAL 累积撑爆磁盘 → 数据库 panic。
4. **DDL 不复制忘了**——`ALTER TABLE ADD COLUMN` 在 publisher 加了，subscriber 没加，apply 报错。
5. **序列不复制忘了**——升级切换后新主自增 ID 撞已有数据。
6. **大事务卡 reorder buffer**——长 ETL 事务跑 6 小时，subscriber 6 小时没数据更新。配 `streaming = on` 缓解。
7. **`SKIP (lsn = ...)` 跳错事务**——人工跳过冲突时跳到错误 LSN，下游永久缺数据。
8. **PG 升级后扩展不兼容**——pgvector / PostGIS 旧版连不上新版。升级前先验证。
9. **Debezium heartbeat 没开**——非订阅表的事务不让 slot 前进，WAL 累积。
10. **subscription 用了 superuser**——容易越权 + 安全风险。建专用 REPLICATION 角色。
11. **PG 16 双向复制误以为是多主**——不解决冲突，schema 不设计好仍然会脏数据。
12. **Failover 后逻辑 slot 丢失**（PG 17 之前）——subscriber 必须全量重做。建议 PG 17+ 用 failover slot。
13. **行过滤 WHERE 用了可变函数**——`WHERE created_at > now()` 创建时直接报错。
14. **初始 COPY 阶段把订阅 DROP 了再建**——重新全量，几 TB 流量白费。要重启用 `ALTER SUBSCRIPTION ... DISABLE; ENABLE`。

## 2026 现状

- **PG 17**：failover slot（`failover = true`）、PG 端 logical replication 平均吞吐继续优化，subscribe 端并行 apply 成熟
- **PG 18**：进一步降低 logical decoding 的 catalog 锁争用；增强 protocol 心跳
- **Debezium 2.6/3.0**：incremental snapshot（chunked）、parallel snapshot、ad-hoc snapshot 命令支持，原生 Avro/Protobuf 改进；广泛 K8s 化部署（Strimzi + Kafka Connect Operator）
- **CDC 主流栈**：Debezium + Kafka + Schema Registry，下游 Iceberg / Hudi / Delta Lake 实时入湖
- **替代方案**：Fivetran / Airbyte 内部封装 PG logical decoding；DataHub / OpenLineage 元数据追踪
- **行业实践**：
  - 大厂 CDC 量级 100+ GB/天，Debezium + Kafka 是事实标准
  - 跨大版本升级 90% 走逻辑复制（`pg_upgrade --link` 仍存在但敢用的越来越少）
  - 双向双中心 在 PG 16+ 用 origin 过滤 + UUIDv7（PG 18 内置）替代自增 ID，避免主键冲突
