## 引言：Planner 是 PostgreSQL 的灵魂

很多从 MySQL 切到 PostgreSQL 的工程师，第一周就会被一个反直觉的事实击中：**PostgreSQL 不支持 query hint**。`FORCE INDEX`、`STRAIGHT_JOIN`、`USE INDEX` 这些 MySQL 党的"祖传药方"在 PG 里全部消失。社区核心开发组多年的态度只有一句话："如果优化器选错了，那就修优化器、修统计、修参数——不是给 SQL 加补丁。"

这背后是 PostgreSQL 的整体设计哲学：**Planner 必须自适应**。一条 SQL 在数据量从 1 万跳到 1 亿、从 SSD 跑到 NVMe、从 8 核换到 64 核时，应该自动选择不同的执行计划，而不是被一行 hint 钉死。

但这个哲学也有它的代价：**当 Planner 估算偏差时，没有"一锤子"修复办法**。你必须理解它的工作流程——读什么统计、用什么 cost model、做了哪些重写、为什么对 12 张表以上的 join 改用遗传算法——才能在估算翻车时找到真正的根因。

读完这一章，你应该能：

- 画出 PG SQL 处理 5 个阶段（Parser → Analyzer → Rewriter → Planner → Executor）的数据流
- 用 `pg_stats` 读出某列的 MCV、histogram、correlation，并解释行数估算公式
- 调对 `random_page_cost` / `effective_cache_size` / `work_mem` 等 cost model 参数
- 区分动态规划 join 枚举（< 12 表）和 GEQO 遗传算法的不同输出
- 解释 PG 12+ CTE 默认 inline 的行为，以及 `MATERIALIZED` / `NOT MATERIALIZED` 的作用
- 用扩展统计 `CREATE STATISTICS` 修复关联列估算偏差（city + country 经典案例）
- 解释为什么 PG 不支持 hint，以及什么时候才该使用 `pg_hint_plan` 这种扩展
- 区分 prepared statement 的 custom plan 与 generic plan，看懂 `custom_plan_tries` 的作用

## 第一章：SQL 处理 5 阶段

### 1.1 总体数据流

PostgreSQL 处理一条 SQL，经历 5 个清晰可分的阶段。每个阶段的输入输出都是一棵不同的 AST/Plan 树，对应源码目录如下：

```
SQL 字符串
   │
   ▼
[ 1. Parser    ]  src/backend/parser/gram.y          → RawStmt 链表
   │
   ▼
[ 2. Analyzer  ]  src/backend/parser/analyze.c       → Query 树
   │
   ▼
[ 3. Rewriter  ]  src/backend/rewrite/rewriteHandler → Query 树（重写后）
   │
   ▼
[ 4. Planner   ]  src/backend/optimizer/plan/        → PlannedStmt（Plan 树）
   │
   ▼
[ 5. Executor  ]  src/backend/executor/              → 结果元组流
```

| 阶段 | 输入 | 输出 | 关键函数 |
|---|---|---|---|
| Parser | SQL 字符串 | RawStmt（语法树，列还是字符串） | `raw_parser()` |
| Analyzer | RawStmt | Query 树（列绑定到 OID） | `parse_analyze_fixedparams()` |
| Rewriter | Query 树 | Query 树（视图展开 / RULE） | `QueryRewrite()` |
| Planner | Query 树 | PlannedStmt（包含 Plan 树） | `standard_planner()` → `subquery_planner()` |
| Executor | PlannedStmt | Tuple 流 | `ExecutorRun()` |

### 1.2 Parser：纯语法

`gram.y` 是经典的 bison 语法描述。Parser 此时不知道任何 schema——你写 `SELECT foo FROM bar` 它都能解析，只要符合 SQL 语法。

```sql
EXPLAIN (PARSER true) SELECT 1;  -- 假想
-- 没有这个选项，但你可以用 debug_print_parse=on 看 raw parse tree
SET debug_print_parse = on;
SET client_min_messages = log;
SELECT 1;
```

### 1.3 Analyzer：语义分析

Analyzer 做的事：

- 把列名 `foo` 解析成 `(table_oid, attno)`
- 检查类型（`int + text` 报错的地方）
- 展开 `SELECT *` 为列列表
- 把 `Param` 占位符固定下来（prepared statement 在这里第一次"知道"参数类型）

输出 Query 树。可以用 `debug_print_rewritten=on` 看 rewriter 后的样子。

### 1.4 Rewriter：视图展开 + RULE

Rewriter 主要处理两件事：

1. **视图展开**：`SELECT * FROM user_view` 被替换成视图定义的子查询。这是 PG 实现视图的方式（不是缓存结果，每次重新生成 Query 树）。
2. **RULE 系统**：PG 独有的 RULE 重写。`CREATE RULE` 可以拦截 INSERT/UPDATE/DELETE 把它转成别的语句——视图的"INSERT 进视图"也是 RULE 实现的。

```sql
CREATE VIEW v_active_users AS
SELECT id, name FROM users WHERE deleted_at IS NULL;

EXPLAIN SELECT * FROM v_active_users WHERE id = 42;
-- Plan 里看不到 view，因为已被展开成 users WHERE deleted_at IS NULL AND id = 42
```

### 1.5 Planner：决策核心

Planner 是本章主角，它接收 Query 树后做：

1. **子查询提升**（pull-up）：能合并的子查询提升到外层
2. **常量折叠**（`WHERE 1=1` 这种）
3. **谓词下推**：把 WHERE 条件推到能用索引的地方
4. **生成 access path**：对每个表枚举可用的 scan（seq / index / bitmap）
5. **枚举 join 顺序与算法**：动态规划或 GEQO
6. **挑成本最小的整体 plan**

### 1.6 Executor：volcano 迭代器

Executor 用经典的 volcano 模型——每个 Plan node 实现 `ExecInit / ExecProcNode / ExecEnd`，上层 node 通过 `ExecProcNode()` 从下层"拉"一行。PG 11 加入了 JIT（LLVM 生成 native code 加速 tuple deform 和表达式求值）。

## 第二章：统计信息——pg_statistic 与 pg_stats

### 2.1 系统目录 pg_statistic

PG 把所有列的分布统计放在 `pg_statistic`——但这是个 superuser 才能读的系统表，因为它包含真实数据样本（暴露 MCV 等于暴露数据）。日常用 **`pg_stats` 视图**（同样的数据，但脱敏 + 字段更友好）。

```sql
SELECT
    schemaname, tablename, attname,
    null_frac,
    n_distinct,
    most_common_vals,
    most_common_freqs,
    histogram_bounds,
    correlation
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';
```

### 2.2 关键字段含义

| 字段 | 含义 | 用途 |
|---|---|---|
| `null_frac` | NULL 占比（0~1） | `WHERE col IS NULL` 估算 |
| `n_distinct` | 不同值个数；正数=具体值；负数=占行比（-0.1 表示 10% 都是 distinct） | `GROUP BY` / Hash 桶数估算 |
| `most_common_vals` (MCV) | 高频值数组 | `WHERE col = 'paid'` 直接命中 MCV，估算精准 |
| `most_common_freqs` | 与 MCV 对应的频率 | 配合 MCV 用 |
| `histogram_bounds` | 等深直方图边界（默认 100 个桶 + MCV 之外的部分） | 范围查询 / 不命中 MCV 时估算 |
| `correlation` | 物理顺序与逻辑顺序相关性（-1~1） | 决定 index scan 的 random IO 估算（接近 ±1 = 顺序，接近 0 = 随机） |

### 2.3 行数估算公式

以 `WHERE status = 'paid'` 为例：

```
if 'paid' ∈ most_common_vals:
    selectivity = most_common_freqs['paid' 的位置]
else:
    # 用 (1 - 所有 MCV 频率之和 - null_frac) 平均分到其他 n_distinct 个值上
    selectivity = (1 - sum(MCV freqs) - null_frac) / (n_distinct - len(MCV))

estimated_rows = reltuples * selectivity
```

`reltuples` 来自 `pg_class.reltuples`，由 ANALYZE 维护。

### 2.4 ANALYZE 采样原理

```sql
ANALYZE orders;                           -- 一张表
ANALYZE orders (status, created_at);      -- 只更新两列
ANALYZE;                                  -- 整个数据库
```

PG 用 **两阶段随机采样**：

1. **page sample**：从堆表中随机抽 N 页（N = `300 * default_statistics_target`，默认 30000 页）
2. **row sample**：在这些页里再均匀抽 row，组成最终样本

样本大小 = `300 * default_statistics_target`（默认 30000 行）。这是 ANALYZE 时长的根因——表越大、target 越高，扫的页越多。

### 2.5 default_statistics_target

```sql
SHOW default_statistics_target;  -- 默认 100
```

影响：

- 样本大小 = `300 * target`（target=100 → 30000 行）
- MCV 数组大小上限 ≈ `target`
- histogram bucket 数 ≈ `target`

**调优建议**：

| 列特征 | 建议 target |
|---|---|
| 默认（普通业务列） | 100 |
| 高基数（如 user_id 关联列） | 200-500 |
| 极端倾斜（status='paid' 占 95%） | 500-1000，让 MCV 把热点全列出来 |
| 主键 / 唯一索引列 | 默认即可（n_distinct=-1 已经够） |

可以按列设置：

```sql
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
ANALYZE orders;  -- 立即生效
```

代价：ANALYZE 更慢、pg_statistic 占空间更大、planner 用 MCV 时遍历更慢——但 1000 以下都可以接受。

### 2.6 一个真实的 pg_stats 样例

```
schemaname | public
tablename  | orders
attname    | status
null_frac  | 0
n_distinct | 5            ← 5 个状态值
most_common_vals  | {paid, pending, refunded, failed, cancelled}
most_common_freqs | {0.71, 0.15, 0.08, 0.04, 0.02}
histogram_bounds  | (null，所有值都在 MCV 里)
correlation       | 0.12   ← 物理顺序与 status 几乎无关
```

读出的信息：

- 5 个不同 status，全部进入 MCV，所有等值查询都能精准估算
- `status='paid'` 估算 = 71% × `reltuples`
- `correlation=0.12` 表示物理顺序与 status 几乎无关，走 status 索引会引发大量随机 IO

## 第三章：Cost Model 详解

### 3.1 总公式

Planner 给每个 plan 算两个数：

- **startup_cost**：返回第一行之前必须完成的代价（如 Sort 必须读完全部输入）
- **total_cost**：返回最后一行的代价

挑总成本最小的 plan。

### 3.2 七个核心参数

| 参数 | 默认值 | 含义 | 调优建议 |
|---|---|---|---|
| `seq_page_cost` | 1.0 | 顺序读一页的代价（基准 = 1） | 一般不动 |
| `random_page_cost` | 4.0 | 随机读一页的代价 | **SSD/NVMe 建议 1.1**；机械盘保持 4.0 |
| `cpu_tuple_cost` | 0.01 | 处理一行 CPU 代价 | 一般不动 |
| `cpu_index_tuple_cost` | 0.005 | 处理一个索引项 CPU | 一般不动 |
| `cpu_operator_cost` | 0.0025 | 执行一个表达式/操作符 CPU | 一般不动 |
| `parallel_setup_cost` | 1000 | 启动并行 worker 的固定代价 | 小机器调低；大批 OLAP 调低 |
| `parallel_tuple_cost` | 0.1 | 在 worker 间传一行的代价 | 一般不动 |

```sql
SHOW seq_page_cost;
SHOW random_page_cost;
SHOW cpu_tuple_cost;
SHOW parallel_setup_cost;
```

### 3.3 random_page_cost：SSD 时代必改的参数

PostgreSQL 8.x 时代设默认值 4.0，假设的是机械盘。SSD/NVMe 上随机读和顺序读差距很小，但 PG 默认仍然是 4.0——这意味着 planner **系统性地低估索引扫描的吸引力**，倾向于走顺序扫描。

```sql
-- SSD/NVMe 生产环境
ALTER SYSTEM SET random_page_cost = 1.1;
SELECT pg_reload_conf();
```

实测影响：很多原本走 Seq Scan 的查询会切换到 Index Scan / Bitmap Index Scan。

| 存储类型 | 建议 random_page_cost |
|---|---|
| HDD（少见了） | 4.0（默认） |
| SAS / SSD | 1.5-2.0 |
| NVMe / 云盘（gp3、pd-ssd） | 1.1 |
| 全内存数据集 | 1.0（与 seq 相等） |

### 3.4 Seq Scan 的 cost 计算

```
seq_scan_cost = relpages * seq_page_cost
              + reltuples * (cpu_tuple_cost + qual_cost)
```

例：表 100,000 行，1,000 页，没有 WHERE：

```
cost = 1000 * 1.0 + 100000 * 0.01 = 1000 + 1000 = 2000
```

EXPLAIN 输出大约会是 `Seq Scan ... (cost=0.00..2000.00 rows=100000)`。

### 3.5 Index Scan 的 cost 计算

公式（简化）：

```
index_scan_cost = startup
                + index_pages * random_page_cost
                + matched_rows * cpu_index_tuple_cost
                + heap_pages_fetched * random_page_cost   ← 回表
                + matched_rows * (cpu_tuple_cost + qual_cost)
```

`heap_pages_fetched` 的估算用 **Mackert-Lohman 公式**，结合 `correlation`：

- correlation 接近 ±1：物理顺序与索引一致，回表近似顺序读
- correlation 接近 0：每行可能在不同页，最坏情况每行一个 random IO

### 3.6 effective_cache_size：planner 的"白日梦"

```sql
SHOW effective_cache_size;  -- 默认 4GB
```

**这是 PostgreSQL 最容易被误解的参数**：

- 它**不分配任何内存**
- 它只告诉 planner "OS 大概有多少缓存可用"
- planner 用它修正 Mackert-Lohman 公式——cache 越大，估算的 heap fetch 次数越少

**建议值**：物理内存的 50%-75%（剩下给 shared_buffers、work_mem、OS）。

```sql
-- 64GB 机器
ALTER SYSTEM SET effective_cache_size = '48GB';
SELECT pg_reload_conf();
```

效果：planner 更愿意走 index scan（认为多次回表不会真的从磁盘读）。

### 3.7 work_mem 与 plan 选择

`work_mem` 是单个 sort / hash 操作可用的内存上限。planner 根据它判断：

- 输入数据预估 < `work_mem` → in-memory sort / in-memory hash
- 输入数据预估 > `work_mem` → external merge sort / hash with spill

```sql
SET work_mem = '256MB';
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM big_table ORDER BY name;
-- Sort Method: quicksort  Memory: 230MB    ← in-memory
```

work_mem 太小会逼 sort 落盘（`external merge Disk: 500MB`），慢一个数量级。

## 第四章：Join 顺序枚举

### 4.1 问题规模

N 张表 join 的可能顺序是 N! × Catalan 数量级——5 表已经几千种，12 表 8000 万。Planner 不能蛮力枚举，必须分情况：

| 表数 | 算法 |
|---|---|
| < `geqo_threshold`（默认 12） | **动态规划**（精确最优） |
| >= 12 | **GEQO**（遗传算法，近似最优） |

### 4.2 动态规划（System R 风格）

PG 实现的是经典的 **Selinger 算法**：

```
level 1: 每张表的最佳 access path（seq / index / bitmap）
level 2: 所有 2 表 join，对每对 (Ti, Tj) 保留最便宜的 plan
level 3: 所有 3 表 join，基于 level 2 结果扩展
...
level N: 所有 N 表 join
```

复杂度 O(2^N × N) 量级。N=10 大约 10240 个 subset、N=12 大约 49152——可接受。

### 4.3 GEQO：遗传算法

`src/backend/optimizer/geqo/`，开关：

```sql
SHOW geqo;                  -- on
SHOW geqo_threshold;        -- 12
SHOW geqo_effort;           -- 5 (1-10, 越大越细)
SHOW geqo_pool_size;        -- 0 = 自适应
SHOW geqo_generations;      -- 0 = 自适应
SHOW geqo_selection_bias;   -- 2.0
SHOW geqo_seed;             -- 0.0 (随机种子)
```

工作流：

1. 把 join 顺序编码成一个排列（基因组）
2. 初始化种群（随机若干个 join 顺序）
3. 评估每个 plan 的 cost（适应度）
4. 选择 / 交叉 / 变异 → 新种群
5. 多代演化后输出最优解

**注意**：GEQO 的结果**不稳定**——同一条 SQL 跑两次可能拿到不同 plan。在大数仓里这是个坑。

应对：

```sql
SET geqo_seed = 0.42;   -- 固定随机种子
-- 或
SET geqo = off;          -- 强制走动态规划（但 24 表+ 可能爆内存/CPU）
SET join_collapse_limit = 16;     -- 让动态规划处理更多表
SET from_collapse_limit = 16;
```

### 4.4 collapse_limit：扁平化阈值

```sql
SHOW join_collapse_limit;    -- 8
SHOW from_collapse_limit;    -- 8
```

- `from_collapse_limit`：FROM 子句中嵌套子查询能被"提升"到外层的最大数量
- `join_collapse_limit`：显式 JOIN 能被重新排序的最大数量

如果你写 `A JOIN B JOIN C JOIN D ... JOIN J`（10 表），且 `join_collapse_limit=8`，那么 planner 只重排前 8 张，后 2 张保持你写的顺序。

**用途**：当你比 planner 更懂 join 顺序，可以调低 `join_collapse_limit=1`，让 planner **完全尊重你写的顺序**：

```sql
SET join_collapse_limit = 1;
SELECT * FROM small_table a JOIN big_table b ON ... JOIN huge_table c ON ...;
-- planner 严格按 a → b → c
```

这是 PG 提供的"软 hint"——不是给单条 SQL 加注释，但用 SET 局部生效。

## 第五章：子查询、视图、CTE 行为

### 5.1 子查询提升（pull-up）

```sql
SELECT * FROM (SELECT * FROM users WHERE age > 30) u WHERE u.city = 'NYC';
```

Planner 把子查询提升成：

```sql
SELECT * FROM users WHERE age > 30 AND city = 'NYC';
```

可以走复合索引 `(age, city)` 或 `(city, age)`，性能与直接写一样。

不能提升的情况：

- 子查询有 LIMIT
- 子查询有 GROUP BY / DISTINCT
- 子查询是 LATERAL（必须保留）

### 5.2 视图展开

视图本质上是命名的子查询。Rewriter 把视图引用替换成定义体后，planner 当作普通子查询处理。

```sql
CREATE VIEW v_recent AS SELECT * FROM logs WHERE created_at > now() - interval '7 day';
EXPLAIN SELECT count(*) FROM v_recent WHERE level='ERROR';
-- 等价于直接查 logs WHERE created_at > ... AND level='ERROR'
```

### 5.3 CTE：PG 12 之前与之后

**PG 12 之前**：CTE 是**优化栅栏（optimization fence）**——CTE 体先独立物化，外层查询不能下推条件进去。这给写"复杂查询拆步骤"的人挖了无数坑。

```sql
-- PG 11 行为
WITH recent AS (SELECT * FROM logs WHERE created_at > now() - interval '7 day')
SELECT * FROM recent WHERE level='ERROR';
-- PG 11：先把 7 天日志全 materialize（可能上千万行），再过滤 ERROR
-- 行为像一个临时表
```

**PG 12+ 默认 inline**：如果 CTE 满足以下条件，就被内联（行为像子查询）：

- 不是 recursive
- 在外层查询中**只被引用一次**
- 没有副作用（不是 INSERT/UPDATE/DELETE 在 CTE 里）

```sql
-- PG 12+ 默认行为
WITH recent AS (SELECT * FROM logs WHERE created_at > now() - interval '7 day')
SELECT * FROM recent WHERE level='ERROR';
-- 等价于直接 SELECT * FROM logs WHERE created_at > ... AND level='ERROR'
```

### 5.4 MATERIALIZED / NOT MATERIALIZED

PG 12+ 提供显式控制：

```sql
-- 强制物化（恢复 PG 11 行为）
WITH recent AS MATERIALIZED (SELECT * FROM logs WHERE ...)
SELECT * FROM recent WHERE level='ERROR';

-- 强制内联（即使被引用多次）
WITH recent AS NOT MATERIALIZED (SELECT * FROM logs WHERE ...)
SELECT * FROM recent r1 JOIN recent r2 ON r1.id = r2.id;
```

**何时该用 MATERIALIZED**：

- CTE 体非常重（join 多表 + 聚合），且会被外层多次引用
- 想阻止 planner 做奇怪的下推
- 调试时锁定 plan

**何时该用 NOT MATERIALIZED**：

- 复用一段子查询的语义，但希望被下推优化
- 多次引用但每次条件不同，想让 planner 分别优化

### 5.5 LATERAL：相关子查询

```sql
SELECT u.*, recent.*
FROM users u
LEFT JOIN LATERAL (
    SELECT * FROM orders o WHERE o.user_id = u.id
    ORDER BY created_at DESC LIMIT 3
) recent ON true;
```

LATERAL 允许子查询引用外层列，对应"每行执行一次子查询"的语义，但 planner 可以选择高效的 Nested Loop + Memoize（PG 14+，详见 P10）。

## 第六章：Planner 开关参数（生产慎用）

### 6.1 全套开关

PG 提供一组 `enable_*` 参数来禁用特定的 plan node：

| 参数 | 默认 | 关闭的 plan node |
|---|---|---|
| `enable_seqscan` | on | Seq Scan |
| `enable_indexscan` | on | Index Scan |
| `enable_indexonlyscan` | on | Index Only Scan |
| `enable_bitmapscan` | on | Bitmap Scan |
| `enable_tidscan` | on | Tid Scan |
| `enable_nestloop` | on | Nested Loop Join |
| `enable_hashjoin` | on | Hash Join |
| `enable_mergejoin` | on | Merge Join |
| `enable_material` | on | Materialize |
| `enable_memoize` | on | Memoize (PG 14+) |
| `enable_sort` | on | Sort |
| `enable_hashagg` | on | Hash Aggregate |
| `enable_parallel_append` | on | Parallel Append |
| `enable_partitionwise_join` | off | 分区 wise join |
| `enable_partitionwise_aggregate` | off | 分区 wise 聚合 |
| `enable_gathermerge` | on | Gather Merge |
| `enable_partition_pruning` | on | 分区裁剪 |
| `enable_async_append` | on | 异步 Append（FDW） |

### 6.2 这些参数不是"hint"

**关键点**：关闭一个参数不是禁用，而是给该 plan node 加上一个巨大的 cost penalty（`disable_cost = 1.0e10`）。如果没有其他选择，PG 仍然可能用它。

```sql
SET enable_seqscan = off;
EXPLAIN SELECT * FROM users;  -- 没索引时仍然 Seq Scan，cost 加了 1e10
```

### 6.3 调试用法

```sql
-- 想验证"如果不走 Seq Scan 是不是更快"：
BEGIN;
SET LOCAL enable_seqscan = off;
EXPLAIN ANALYZE SELECT * FROM users WHERE name = 'Alice';
ROLLBACK;
```

`SET LOCAL` 只在当前事务有效，更安全。

### 6.4 生产环境的禁忌

**绝对不要**在 postgresql.conf 全局关闭这些参数。后果：

- 关 enable_seqscan 后小表（< shared_buffers）查询变慢——seq scan 在小表上是最快的
- 关 enable_hashjoin 强迫 merge join，但 merge join 需要先排序，可能更慢
- 不同 SQL 需要不同 plan，全局关闭破坏其他查询

合理用法：

1. 临时调试一条 SQL（SET LOCAL）
2. 写到函数/存储过程内部（SET 在函数体）
3. 通过 pg_stat_statements 找出 plan 偏差后，调整 cost 参数（如 random_page_cost）而非 enable_*

## 第七章：为什么 PG 不支持 Hint？

### 7.1 官方立场

PG 官方 FAQ 长期保留这条：

> Why doesn't PostgreSQL support optimizer hints?
>
> Because they hide bugs. If the optimizer makes the wrong choice, we want to fix the optimizer, not paper over it with hints.

### 7.2 设计哲学

**核心假设**：数据库不停演化，硬件、数据量、参数都会变。一行 SQL 写的 hint 在三年后可能从"救命药"变成"毒药"。

例子：

```sql
-- 2023 年加的 hint
SELECT /*+ INDEX(o idx_status) */ * FROM orders WHERE status='paid';
-- 2026 年：status='paid' 占 95% 了，走索引反而比 seq scan 慢 10 倍
-- 但 hint 永远在那里
```

PG 的态度：与其让用户写 hint，不如让用户：

1. **修统计**（ANALYZE / `default_statistics_target` / `CREATE STATISTICS`）
2. **修 cost 参数**（random_page_cost / effective_cache_size）
3. **修 SQL**（用更适合的写法，如 LATERAL 代替子查询）
4. **报告 bug**：如果 planner 在合理统计下仍然选错，社区会修

### 7.3 反方观点

业界对此一直有争论：

- **支持方**：自适应是对的，hint 是技术债。
- **反对方**：现实中你没时间也没权力去改全局参数。一条线上慢 SQL 你只想立刻让它走某个索引。

折中方案是社区扩展 **pg_hint_plan**（NTT OSS Center，日本起源）。

### 7.4 pg_hint_plan 扩展

```sql
CREATE EXTENSION pg_hint_plan;
LOAD 'pg_hint_plan';
```

支持的 hint：

```sql
/*+ SeqScan(t)           */  -- 强制 t 表 seq scan
/*+ IndexScan(t idx_t1)  */  -- 强制走指定索引
/*+ HashJoin(a b)        */  -- 强制 hash join
/*+ NestLoop(a b)        */  -- 强制 nested loop
/*+ Leading((a (b c)))   */  -- 强制 join 顺序
/*+ Rows(t #1000)        */  -- 修改某节点的行数估算（绝对）
/*+ Set(work_mem '256MB')*/  -- 局部设置 GUC
```

例：

```sql
/*+ IndexScan(orders idx_orders_status) */
SELECT * FROM orders WHERE status = 'paid';
```

**什么时候值得用 pg_hint_plan**：

1. 你确认 planner 错了，且短期内无法改统计
2. 某条查询的 plan 反复抖动（特别是用 GEQO 时）
3. 旧 ORM 生成的 SQL 无法手改，但可以在 hint 表里指定（pg_hint_plan 支持把 hint 存到 `hint_plan.hints` 表）

**不应该用**：

1. 全表慢查询——根本是设计问题
2. 没看 EXPLAIN ANALYZE 就加 hint
3. 临时业务需求，但 hint 永远留下来

## 第八章：扩展统计 CREATE STATISTICS

### 8.1 关联列估算偏差

经典案例：

```sql
CREATE TABLE addresses (
    id serial PRIMARY KEY,
    city text,
    country text
);

INSERT INTO addresses (city, country)
SELECT
    (ARRAY['Beijing','Tokyo','Paris','New York','London'])[(random()*5)::int + 1],
    (ARRAY['China','Japan','France','USA','UK'])[(random()*5)::int + 1]
FROM generate_series(1, 100000);
-- 但每个 city 只对应一个 country
UPDATE addresses SET country = CASE city
    WHEN 'Beijing' THEN 'China'
    WHEN 'Tokyo' THEN 'Japan'
    WHEN 'Paris' THEN 'France'
    WHEN 'New York' THEN 'USA'
    WHEN 'London' THEN 'UK'
END;

ANALYZE addresses;
```

查询：

```sql
EXPLAIN ANALYZE SELECT * FROM addresses WHERE city='Beijing' AND country='China';
-- Seq Scan ... (cost=... rows=4000 ... actual rows=20000 ...)
```

Planner 假设独立：`P(city=Beijing AND country=China) = P(city=Beijing) × P(country=China) = 0.2 × 0.2 = 0.04`，估算 4000 行。
**实际**：city 与 country 完全相关，命中 20000 行。**估算偏差 5 倍**。

后果：基于错误估算选错 plan（如认为输入 4000 行所以用 Nested Loop，实际 20000 行应该 Hash Join）。

### 8.2 CREATE STATISTICS（PG 10+）

```sql
CREATE STATISTICS stat_addr_city_country (dependencies, ndistinct, mcv)
    ON city, country FROM addresses;

ANALYZE addresses;
```

四种统计类型：

| 类型 | 用途 | 解决什么 |
|---|---|---|
| `dependencies` | 函数依赖（A → B） | 多列等值估算偏差 |
| `ndistinct` | 多列组合的 distinct 值数 | GROUP BY 多列时桶数估算 |
| `mcv` | 多列 MCV | 多列等值估算（最精确） |
| `expressions` (PG 14+) | 表达式统计 | `WHERE lower(col) = ...` 这类 |

```sql
EXPLAIN ANALYZE SELECT * FROM addresses WHERE city='Beijing' AND country='China';
-- Seq Scan ... rows=20000 ... actual rows=20000   ← 估算精准了
```

### 8.3 查看扩展统计

```sql
SELECT * FROM pg_stats_ext;
-- statistics_name     | stat_addr_city_country
-- attnames            | {city, country}
-- kinds               | {d, f, m}    ← dependencies / ndistinct / mcv
-- n_distinct          | "city, country": 5
-- dependencies        | "city => country": 1.000000, "country => city": 1.000000
```

`dependencies=1.0` 表示完全函数依赖（city 完全决定 country）。

### 8.4 expressions 统计（PG 14+）

```sql
-- 用户经常按 lower(email) 查询
CREATE STATISTICS stat_users_lower_email (expressions)
    ON (lower(email)) FROM users;
ANALYZE users;
```

让 planner 能估算 `WHERE lower(email)='x@y.com'` 的选择性。

### 8.5 实战建议

- 对于多列 WHERE 频繁出现且**估算明显偏差**的场景，加 `(dependencies, mcv)`
- 对于 GROUP BY 多列估算偏差导致 hash bucket 不合理的场景，加 `ndistinct`
- 不要盲目加——每个 statistics 都增加 ANALYZE 成本和 pg_statistic_ext 存储

## 第九章：Parallel Query 决策

### 9.1 触发条件

PG 9.6+ 支持并行查询，但 planner 要满足以下条件才生成并行 plan：

| 条件 | 参数 / 限制 |
|---|---|
| 输入表足够大 | `min_parallel_table_scan_size`（默认 8MB） |
| 输入索引足够大 | `min_parallel_index_scan_size`（默认 512kB） |
| 估算成本足够高 | `parallel_setup_cost` + `parallel_tuple_cost` 不能压倒收益 |
| 查询本身允许并行 | 非 PARALLEL UNSAFE 的函数、非 SELECT FOR UPDATE 等 |
| 集群配置允许 | `max_worker_processes` / `max_parallel_workers` / `max_parallel_workers_per_gather` |

### 9.2 关键参数

```sql
SHOW max_worker_processes;              -- 全局 worker 池（默认 8）
SHOW max_parallel_workers;              -- 给并行查询用的上限（默认 8）
SHOW max_parallel_workers_per_gather;   -- 单个查询可用 worker 数（默认 2）
SHOW parallel_leader_participation;     -- leader 是否参与扫描（默认 on）
```

### 9.3 并行 plan node

- `Gather` / `Gather Merge`：leader 收集 worker 结果（Gather Merge 保留有序）
- `Parallel Seq Scan` / `Parallel Index Scan` / `Parallel Bitmap Heap Scan`
- `Parallel Hash Join`（PG 11+，build 阶段也并行）
- `Partial Aggregate` + `Finalize Aggregate`：worker 局部聚合，leader 汇总

```sql
EXPLAIN SELECT count(*) FROM big_table WHERE status='paid';
-- Finalize Aggregate
--   -> Gather  Workers Planned: 2
--      -> Partial Aggregate
--         -> Parallel Seq Scan on big_table
```

### 9.4 调优建议

- OLTP 小表查询不需要并行（启动 worker 比扫描还慢）
- OLAP 大表全扫 / 聚合开 4-8 个 worker 收益明显
- `max_parallel_workers_per_gather` 建议 CPU 核数 / 4（给其他查询留出 worker）

## 第十章：Prepared Statement — Custom Plan vs Generic Plan

### 10.1 两种 plan

```sql
PREPARE stmt(int) AS SELECT * FROM orders WHERE user_id = $1;
EXECUTE stmt(42);
```

PG 在执行 prepared statement 时有两种 plan：

- **Custom Plan**：每次 EXECUTE 时知道参数具体值，重新 plan（能利用 MCV、histogram）
- **Generic Plan**：忽略参数具体值，用平均选择性 plan 一次后缓存（节省 plan 时间）

### 10.2 自适应决策（PG 9.2+）

PG 的默认策略：

```
前 5 次 EXECUTE：用 Custom Plan，每次记录 cost
第 6 次起：生成 Generic Plan，比较平均 custom_cost
   if generic_cost > avg(custom_cost) * 某阈值:
       继续用 Custom
   else:
       切到 Generic
```

`custom_plan_tries` 不是参数，是硬编码常量 5。

### 10.3 强制控制：plan_cache_mode

PG 12+：

```sql
SET plan_cache_mode = 'auto';            -- 默认，自适应
SET plan_cache_mode = 'force_custom_plan';
SET plan_cache_mode = 'force_generic_plan';
```

### 10.4 何时该强制 custom plan

当数据严重倾斜时：

```sql
-- orders: 99% 是 status='paid', 1% 是其他
PREPARE q(text) AS SELECT * FROM orders WHERE status = $1;

EXECUTE q('paid');     -- 走 seq scan 最佳
EXECUTE q('pending');  -- 走 index scan 最佳
```

generic plan 用平均选择性，会得到一个对两种情况都不优的 plan。这时应该：

```sql
SET plan_cache_mode = 'force_custom_plan';
```

或不用 prepared statement，直接每次发完整 SQL（PG 的 plan 缓存对短查询开销不大）。

### 10.5 EXPLAIN (GENERIC_PLAN)（PG 16+）

PG 16 新增——不执行就能看 generic plan：

```sql
EXPLAIN (GENERIC_PLAN) SELECT * FROM orders WHERE status = $1;
```

帮助诊断 prepared statement 的潜在问题。

## 第十一章：综合实战案例

### 11.1 案例：planner 估算偏差导致选错索引

```sql
-- 场景：orders 表 1 亿行，95% status='paid'
CREATE INDEX idx_status ON orders(status);
CREATE INDEX idx_user ON orders(user_id);

EXPLAIN ANALYZE
SELECT * FROM orders WHERE status='pending' AND user_id=42;
```

如果 planner 没有 `(status, user_id)` 的扩展统计，它假设独立：

```
P(status=pending) ≈ 0.03
P(user_id=42) ≈ 1/1000000 = 1e-6
P(both) ≈ 3e-8 → 估算 3 行
```

实际可能 100 行（这个用户 pending 状态较多）。

诊断步骤：

```sql
-- 1. 看实际偏差
EXPLAIN (ANALYZE, BUFFERS) ...;
-- rows=3 actual rows=100   ← 30 倍偏差

-- 2. 加扩展统计
CREATE STATISTICS stat_orders_status_user (mcv)
    ON status, user_id FROM orders;
ANALYZE orders;

-- 3. 再跑
EXPLAIN ANALYZE ...;   -- 估算精度提升，plan 可能改变
```

### 11.2 案例：CTE 行为变化导致升级翻车

PG 11 → PG 12 升级后，某个报表 SQL 慢 10 倍：

```sql
WITH active AS (
    SELECT * FROM users WHERE status='active'
)
SELECT a.id, count(*) FROM active a JOIN orders o ON o.user_id = a.id
GROUP BY a.id;
```

- PG 11：active CTE 物化（100 万 active 用户），再 join orders
- PG 12：CTE inline，等价于 `users WHERE status='active' JOIN orders`，planner 可能选择 hash join build 在 users 端——但如果 active 占大多数，反而慢

修复：

```sql
WITH active AS MATERIALIZED (   -- 强制恢复 PG 11 行为
    SELECT * FROM users WHERE status='active'
)
SELECT ...
```

或重新评估 SQL 让 planner 找到真正的最优。

### 11.3 案例：SSD 升级后未调 random_page_cost

某团队从 SAS 升级到 NVMe 后，整体查询性能"没变化"。原因：random_page_cost 仍是 4.0，planner 偏向 seq scan，大量本应走 index 的查询走了全表。

```sql
ALTER SYSTEM SET random_page_cost = 1.1;
ALTER SYSTEM SET effective_cache_size = '48GB';
SELECT pg_reload_conf();
```

第二天 pg_stat_statements 显示平均查询时间下降 60%。

### 11.4 案例：12 表 join GEQO 抖动

每天凌晨的报表查询，plan 时好时坏：

```sql
-- 涉及 14 张维度表 + 事实表 join
SELECT ... FROM fact f
JOIN dim_a a ON ...
JOIN dim_b b ON ...
... -- 共 14 张
```

诊断：14 > geqo_threshold=12，走 GEQO，结果不稳定。

修复选项：

```sql
-- 选项 1：固定 GEQO 种子
SET geqo_seed = 0.42;

-- 选项 2：禁 GEQO，让动态规划处理
SET geqo = off;
SET join_collapse_limit = 16;
SET from_collapse_limit = 16;
-- 但 plan 时间会显著上升（可能秒级）

-- 选项 3：拆 SQL，分别物化中间结果
```

### 11.5 案例：MCV 不够大造成"长尾"估算偏差

某 SaaS 多租户表 `tenant_id`，有 5 个超大客户（占 60% 流量）+ 几万个小客户。default_statistics_target=100 时，MCV 只列了前 100 个 tenant，第 101 名之后的全用"平均选择性"估算——但实际差异极大。

```sql
ALTER TABLE events ALTER COLUMN tenant_id SET STATISTICS 1000;
ANALYZE events;
-- MCV 现在容纳 1000 个最常见 tenant，长尾的小客户也能估算准确
```

## 生产实践

### 部署 checklist

| 项 | 推荐值 | 说明 |
|---|---|---|
| `random_page_cost` | SSD/NVMe: 1.1；HDD: 4.0 | 必改 |
| `effective_cache_size` | 物理内存 × 0.5~0.75 | planner 提示，不分配内存 |
| `default_statistics_target` | 100（默认）；倾斜列 500-1000 | 按列 ALTER 调整 |
| `work_mem` | 16MB-256MB，按并发调 | 单 sort/hash 内存 |
| `geqo_seed` | 0.42（固定种子） | 避免 12+ 表 plan 抖动 |
| `plan_cache_mode` | auto；倾斜场景 force_custom | 长连接 prepared statement |
| `enable_partitionwise_join` | on | 有分区表时显著加速 |
| `auto_explain` | 开启 + threshold 100ms | 慢查询自动记录 plan |

### 定期任务

- 每周 ANALYZE 关键大表（autovacuum 兜底，但显式跑更可控）
- 每月 review `pg_stat_statements` top 20 慢 SQL 的 plan
- 数据量翻倍 / 数据分布显著变化时，review 扩展统计是否需要更新

### 监控指标

```sql
-- 检测 plan 估算偏差 > 10x 的 SQL
SELECT
    query,
    calls,
    mean_exec_time,
    plans,
    total_plan_time / plans AS avg_plan_time
FROM pg_stat_statements
ORDER BY mean_exec_time DESC LIMIT 20;

-- 检测从未被 ANALYZE 的表
SELECT schemaname, relname, last_analyze, last_autoanalyze, n_live_tup, n_dead_tup
FROM pg_stat_user_tables
WHERE last_analyze IS NULL AND last_autoanalyze IS NULL
   AND n_live_tup > 10000;
```

## 陷阱清单

1. **生产 SET enable_seqscan = off**：全局关闭后小表查询变慢，且很多 plan 没替代品仍走 seq scan + 巨大 cost penalty。
2. **以为 effective_cache_size 会分配内存**：不会。它只是 planner 的"白日梦参数"。
3. **CTE 升级 PG 12 后不复现 plan**：默认从物化变成 inline，老 SQL 行为变了。
4. **大表 ANALYZE 太慢就跳过**：跳过后统计过时，所有估算都错。用 `default_statistics_target` 控制采样大小，或对超大表用 `ALTER TABLE ... SET STATISTICS` 按列调整。
5. **12 张表 join 的 plan 不稳定**：GEQO 默认随机。生产环境固定 `geqo_seed` 或关闭 GEQO（注意 plan 时间）。
6. **加完索引 EXPLAIN 还是 seq scan**：检查 `random_page_cost`（SSD 上 4.0 太高）、`effective_cache_size`（太小）、表是否还没 ANALYZE（新建索引不会自动统计）。
7. **pg_hint_plan 加完没生效**：要 `LOAD 'pg_hint_plan'` 或 `shared_preload_libraries` 配置；hint 的表名必须是 SQL 里实际写的（alias 优先）。
8. **prepared statement 拿到差 plan**：长连接 + 数据倾斜的典型问题，切 `plan_cache_mode='force_custom_plan'`。
9. **扩展统计加了不生效**：必须 `ANALYZE` 之后才会算；统计名在 schema 范围唯一。
10. **以为 ANALYZE 是 VACUUM 的副作用**：`VACUUM` 不更新统计，只有 `VACUUM ANALYZE` 或 `ANALYZE` 才会。autovacuum 会触发 autoanalyze，但阈值独立配置。

---

## 2026 现状

- **PG 16+** 改进的 parallel hash join：build 阶段也能并行，大表 join 显著加速
- **PG 16+ EXPLAIN (GENERIC_PLAN)**：不执行就能看 prepared statement 的 generic plan
- **PG 17** 改进的 incremental sort 选择条件，更主动用上 incremental sort（见 P10）
- **PG 18** 异步 IO（io_uring）影响 cost model 隐含假设——大型 OLAP / 顺序扫描进一步加速
- **pg_hint_plan** 仍是社区主力 hint 扩展，2025 年发布兼容 PG 17 版本；PG 18 兼容性社区跟进中
- **pganalyze / pgmustard** 等商业工具内置了 plan 偏差检测和自动建议——可以作为补充
- **CockroachDB / YugabyteDB** 借鉴 PG planner 架构，但加入了 hint 支持，反映了业界对 PG"无 hint"哲学的分歧
- **planner overhead 在 OLTP 仍是关注点**：长连接 + prepared statement + plan cache 是标配，不要每条 SQL 都走完整 plan
