# 精通 PostgreSQL 扩展生态：从 PostGIS、TimescaleDB 到 Citus 与自研扩展

> 关联章节：[P05 多类型索引](./05-精通-多类型索引.md)、[P06 pgvector 与向量检索](./06-精通-pgvector-与向量检索.md)、[P14 分区表](./14-精通-分区表.md)、[P19 FDW 与异构集成](./19-精通-FDW-与异构集成.md)

> PostgreSQL 区别于一切关系库的**杀手锏**是扩展（Extension）机制：一句 `CREATE EXTENSION postgis;` 把一个完整的 GIS 引擎挂进来；一句 `CREATE EXTENSION timescaledb;` 让 PG 变成一个时序数据库；一句 `CREATE EXTENSION citus;` 让 PG 变成分布式 OLAP 集群。本章把"必学的 16 个扩展"按场景过一遍，并讲清楚扩展机制本身、兼容性矩阵、云厂商白名单以及商业生态。

## 引言：为什么 PG 的扩展机制是"杀手锏"

一个关系数据库要不要"什么都内置"？Oracle / SQL Server 走的是"全家桶"路线——GIS、时序、列存、向量、机器学习都进内核。MySQL 大体走的是"内核精简，引擎抽象"路线，InnoDB/MyISAM 切换是其灵活性的体现。

PostgreSQL 走了第三条路：**内核稳定 + 扩展机制丰富**。任何具备 C 能力的开发者都可以写一个 `.so` 动态库，配上 `.control` 和 `.sql`，作为"扩展"挂进 PG。这个机制带来三件事：

1. **生态爆炸**：PGXN（PostgreSQL Extension Network）上有上千个扩展，覆盖 GIS、时序、向量、地理、机器学习、加密、审计、备份、监控、外部数据源。
2. **稳定性可控**：扩展跑在内核之外，崩了不影响核心引擎（只崩当前 backend）。
3. **升级解耦**：扩展可独立升级 `ALTER EXTENSION ... UPDATE;`，不必等 PG 主版本。

这章我们把"日常工作中真的会用到"的 16 个扩展挨个过一遍。它不是一份目录索引，而是一份**实战指南**——每个扩展讲清楚"它解决什么问题、怎么开、怎么用、怎么坑"。

读完之后你应该能：

- 解释扩展机制的三大文件（`.control` / `.sql` / `.so`）与加载流程
- 区分 `shared_preload_libraries` / `session_preload_libraries` / `local_preload_libraries`
- 用 PostGIS 完成一个"找最近 100 个 POI"的查询，并配 GiST 空间索引
- 用 TimescaleDB 把一个亿级 IoT 时序表压缩到 10:1
- 评估 Citus / pg_partman / pg_cron / pg_repack / hypopg 是否要进生产
- 知道 AWS RDS / Aurora / GCP CloudSQL / Azure Postgres 各自的扩展白名单
- 自己写一个最简单的 C 扩展并打包

## 第一章：扩展机制原理 —— 三个文件 + 三个 GUC

### 1.1 扩展的物理形态

一个 PostgreSQL 扩展由三类文件组成，安装目录大致如下（以 Debian/Ubuntu 为例）：

```text
$SHAREDIR/extension/
  postgis.control          # 元数据：版本、依赖、是否可重定位
  postgis--3.4.0.sql       # SQL 脚本：定义函数、类型、操作符、索引访问方法
  postgis--3.3.0--3.4.0.sql# 升级脚本（从 3.3.0 → 3.4.0）

$LIBDIR/
  postgis-3.so             # C 动态库：实现真正的逻辑（如 ST_Distance）
```

- `.control` 是元数据，PG 启动 `CREATE EXTENSION` 时第一个读它。常见字段：

```ini
default_version = '3.4.0'
comment = 'PostGIS geometry and geography spatial types and functions'
module_pathname = '$libdir/postgis-3'
relocatable = false       # 是否允许 ALTER EXTENSION SET SCHEMA
schema = public           # 默认 schema
requires = 'plpgsql'      # 依赖其它扩展
superuser = true          # 是否需要超管创建
trusted = false           # PG 13+ trusted 扩展可由普通用户创建
```

- `.sql` 文件在 `CREATE EXTENSION` 时被执行，定义所有 SQL 对象。
- `.so` 是 C 实现，通过 `CREATE FUNCTION ... AS '$libdir/xxx', 'symbol_name' LANGUAGE C` 在 `.sql` 文件里被引用。

### 1.2 安装、查询、卸载

```sql
-- 列出所有"机器上可用"的扩展（OS 已安装）
SELECT name, default_version, installed_version, comment
FROM pg_available_extensions
ORDER BY name;

-- 列出"当前数据库已启用"的扩展
SELECT extname, extversion, extnamespace::regnamespace, extrelocatable
FROM pg_extension;

-- 安装到当前数据库
CREATE EXTENSION postgis;
CREATE EXTENSION IF NOT EXISTS pg_stat_statements WITH SCHEMA public CASCADE;

-- 升级
ALTER EXTENSION postgis UPDATE TO '3.4.0';

-- 改 schema
ALTER EXTENSION pg_trgm SET SCHEMA myext;

-- 卸载（会删除扩展定义的所有对象）
DROP EXTENSION pg_trgm CASCADE;
```

注意：`pg_available_extensions` 只看"OS 装了哪些"。要让一个新扩展可用，先 `apt install postgresql-18-postgis-3` 之类，再回到 psql `CREATE EXTENSION`。

### 1.3 三种 preload 的差异

| GUC | 作用域 | 何时加载 | 典型扩展 |
|---|---|---|---|
| `shared_preload_libraries` | 实例级 | postmaster 启动时 | pg_stat_statements、pg_cron、citus、timescaledb、pgaudit、auto_explain |
| `session_preload_libraries` | 连接级 | 新连接建立时 | auto_explain、调试钩子 |
| `local_preload_libraries` | 用户级 | 用户登录后 | 受限制（仅 $libdir/plugins） |

`shared_preload_libraries` 是改了**必须重启**的参数；其余两个是 SIGHUP 即可。

```bash
# postgresql.conf
shared_preload_libraries = 'pg_stat_statements,auto_explain,timescaledb'
```

加载顺序要注意：**Citus 必须在最前**（它要 hook planner / executor）；TimescaleDB 也要 preload；pg_cron 需要 preload 并指定 `cron.database_name`。

### 1.4 trusted 扩展（PG 13+）

PG 13 起，一部分扩展被标记为 `trusted = true`，允许 **CREATEDB 权限的普通用户**创建（不必超管），例如：`pg_trgm`、`citext`、`hstore`、`btree_gin`、`btree_gist`、`fuzzystrmatch`、`pgcrypto`、`tablefunc`、`unaccent`、`uuid-ossp`。

```sql
-- 普通用户在自己拥有的库里执行
CREATE EXTENSION pg_trgm;   -- OK on PG 13+
```

云厂商（RDS、CloudSQL）大量利用了 trusted 机制，把"必装小扩展"开放给普通用户。

## 第二章：PostGIS —— GIS 事实标准

PostGIS 是 GIS（地理信息系统）领域**事实标准**的开源实现，几乎一切跟"地图、坐标、距离、范围"相关的需求最终都会指向它。它把 PG 变成一个完整的空间数据库引擎。

### 2.1 启用与基础类型

```sql
CREATE EXTENSION postgis;            -- 核心
CREATE EXTENSION postgis_topology;   -- 拓扑（可选）
CREATE EXTENSION postgis_raster;     -- 栅格（PG 16+ 独立扩展）
CREATE EXTENSION postgis_sfcgal;     -- 3D 高级几何
CREATE EXTENSION address_standardizer;
```

两大核心类型：

| 类型 | 适用 | 计算 | 索引 |
|---|---|---|---|
| `GEOMETRY` | 平面坐标 | 笛卡尔距离（快） | GiST |
| `GEOGRAPHY` | 地球椭球 | 大圆距离（精确、慢 ~2x） | GiST |

SRID（Spatial Reference IDentifier）是空间参考系编号。最常用的几个：

- **4326**：WGS84 经纬度（GPS、Google Maps）
- **3857**：Web Mercator（Bing/Google 切片）
- **2326**：北京 1954（中国遗留系统）
- **4490**：CGCS2000（中国国家标准）

`GEOGRAPHY` 类型默认就是 SRID 4326（球面）。`GEOMETRY` 必须显式指定。

### 2.2 建表：POI 与轨迹

```sql
-- POI（兴趣点）
CREATE TABLE poi (
  id BIGSERIAL PRIMARY KEY,
  name TEXT,
  category TEXT,
  location GEOGRAPHY(POINT, 4326) NOT NULL
);

CREATE INDEX idx_poi_location ON poi USING GIST (location);

INSERT INTO poi (name, category, location) VALUES
  ('天安门', 'attraction', ST_GeogFromText('SRID=4326;POINT(116.397428 39.90923)')),
  ('故宫', 'attraction', ST_GeogFromText('SRID=4326;POINT(116.397026 39.918058)'));
```

构造几何对象的常用函数：

```sql
ST_GeogFromText('SRID=4326;POINT(lon lat)')
ST_MakePoint(lon, lat)::geography
ST_GeomFromGeoJSON('{"type":"Point","coordinates":[116.4,39.9]}')
ST_GeomFromEWKB('\\x01...'::bytea)
```

### 2.3 案例：找最近 100 个 POI（KNN）

需求：给定用户位置，找最近的 100 个咖啡店，按距离升序。

```sql
WITH user_loc AS (
  SELECT ST_GeogFromText('SRID=4326;POINT(116.4 39.91)') AS pt
)
SELECT p.id, p.name,
       ST_Distance(p.location, u.pt) AS dist_m
FROM   poi p, user_loc u
WHERE  p.category = 'cafe'
ORDER  BY p.location <-> u.pt          -- KNN 操作符，走索引
LIMIT  100;
```

关键点：

- `<->` 是 GiST 提供的 **KNN 距离操作符**，直接在索引节点上排序，比 `ORDER BY ST_Distance(...)` 快几个量级。
- `ST_DWithin(geog, geog, meters)` 是"在半径内"判定，**会走索引**；用它替代 `ST_Distance(a,b) < 1000`（不走索引）。

```sql
-- 高效：1km 内的咖啡店
SELECT * FROM poi
WHERE category = 'cafe'
  AND ST_DWithin(location, ST_GeogFromText('SRID=4326;POINT(116.4 39.91)'), 1000);
```

### 2.4 空间分析全家桶

| 函数 | 含义 |
|---|---|
| `ST_Distance(a, b)` | 两几何最近距离 |
| `ST_DWithin(a, b, d)` | a 与 b 是否在 d 距离内（走索引） |
| `ST_Intersects(a, b)` | 两几何是否相交 |
| `ST_Contains(a, b)` | a 是否完全包含 b |
| `ST_Within(a, b)` | a 是否完全在 b 内 |
| `ST_Touches(a, b)` | a 与 b 边界相接但内部不相交 |
| `ST_Crosses(a, b)` | 两线/面交叉 |
| `ST_Union(a, b)` | 并集 |
| `ST_Intersection(a, b)` | 交集 |
| `ST_Difference(a, b)` | 差集 |
| `ST_Buffer(geom, d)` | 半径 d 的缓冲区 |
| `ST_Area(geog)` | 面积（平方米） |
| `ST_Length(geog)` | 长度（米） |
| `ST_AsGeoJSON(geom)` | 转 GeoJSON |
| `ST_AsMVT(...)` | 矢量切片（Mapbox Vector Tile） |

### 2.5 3D 与拓扑

PostGIS 3+ 支持 3D：

```sql
SELECT ST_3DDistance(
  ST_MakePoint(1,1,1),
  ST_MakePoint(4,5,6)
);
```

拓扑（`postgis_topology`）用于"区域不能重叠、共享边界"的复杂行政区划场景，国土、电网、燃气、轨道交通常用。

### 2.6 实战提示

- 大数据集（千万 POI）必须建 `GIST` 索引；不要用 BRIN，BRIN 对几何随机分布无效。
- 表面积优化：`GEOGRAPHY` 比 `GEOMETRY` 慢 ~2x，但精确。**地图渲染用 geometry+3857**，**业务半径搜索用 geography+4326**。
- `pg_dump` 默认不会备份 `spatial_ref_sys`；PostGIS 升级后需要重建。
- 大版本升级：`SELECT PostGIS_Extensions_Upgrade();`

## 第三章：TimescaleDB —— PG 上的时序引擎

TimescaleDB 是基于 PG 的时序数据库扩展，由 Timescale Inc. 出品。它的卖点是"用普通 SQL 就能享受时序优化"——自动分区（Hypertable）、列式压缩、连续聚合、保留策略一应俱全。2026 年它已经是 IoT / 监控 / 金融 tick 数据的主流方案之一。

### 3.1 Hypertable —— 自动按时间分区

```sql
CREATE EXTENSION timescaledb;

CREATE TABLE metrics (
  ts TIMESTAMPTZ NOT NULL,
  device_id BIGINT NOT NULL,
  metric_name TEXT NOT NULL,
  value DOUBLE PRECISION
);

-- 把普通表变成 Hypertable，按 ts 每天一个 chunk
SELECT create_hypertable('metrics', 'ts', chunk_time_interval => INTERVAL '1 day');

-- 二维分区（按 device_id 再哈希到 16 个 chunk）
SELECT add_dimension('metrics', 'device_id', number_partitions => 16);
```

Hypertable 在内部由许多 **chunk**（子表，PG 原生分区表实现）组成。查询时 Timescale 的 planner hook 会做"chunk 裁剪"，只扫相关的几个 chunk。

```sql
-- 查 chunk 列表
SELECT show_chunks('metrics');
SELECT chunk_schema, chunk_name, range_start, range_end
FROM timescaledb_information.chunks
WHERE hypertable_name = 'metrics';
```

### 3.2 列式压缩（10:1）

TimescaleDB 2.0+ 引入**列式压缩**，对老 chunk（已经不写入的）按列做字典编码 + delta + gorilla 等算法压缩，典型压缩比 5-20x。

```sql
-- 开启压缩 + segment-by 装置 ID（同设备的数据放一起）
ALTER TABLE metrics SET (
  timescaledb.compress,
  timescaledb.compress_segmentby = 'device_id',
  timescaledb.compress_orderby = 'ts DESC'
);

-- 自动压缩 7 天前的 chunk
SELECT add_compression_policy('metrics', INTERVAL '7 days');

-- 手动压缩某 chunk
SELECT compress_chunk('_timescaledb_internal._hyper_1_42_chunk');
```

压缩后的 chunk 是**只读**的（PG 17 + TS 2.14+ 改进了局部 UPDATE 支持），适合"近 7 天热数据未压缩，老数据压缩归档"模式。

### 3.3 连续聚合 —— 物化视图 + 增量刷新

时序场景常需要"按分钟/小时/天聚合"。Timescale 的 **continuous aggregate** 是带增量刷新的物化视图：

```sql
CREATE MATERIALIZED VIEW metrics_1h
WITH (timescaledb.continuous) AS
SELECT
  time_bucket('1 hour', ts) AS bucket,
  device_id,
  AVG(value) AS avg_v,
  MAX(value) AS max_v,
  MIN(value) AS min_v
FROM metrics
GROUP BY bucket, device_id;

-- 自动每 30 分钟增量刷新最近 2 小时数据
SELECT add_continuous_aggregate_policy('metrics_1h',
  start_offset => INTERVAL '2 hours',
  end_offset   => INTERVAL '30 minutes',
  schedule_interval => INTERVAL '30 minutes');
```

`time_bucket(interval, ts)` 是 Hyperfunctions 提供的"对齐到桶"函数，类似 `date_trunc` 但更灵活（可指定起点、时区）。

查询走聚合表 + 实时数据：

```sql
SELECT * FROM metrics_1h
WHERE bucket >= now() - INTERVAL '1 day'
  AND device_id = 12345;
```

### 3.4 保留策略 —— 自动删除老数据

```sql
-- 保留 90 天，自动 drop 老 chunk（极快，不走 DELETE）
SELECT add_retention_policy('metrics', INTERVAL '90 days');
```

`DELETE` 对时序大表是灾难（产生大量死元组 + 索引膨胀）；TimescaleDB 通过 `DROP TABLE` 整个 chunk 来"删除"老数据，**毫秒级**。

### 3.5 Hyperfunctions

TimescaleDB 提供一组时序专用函数（部分要 Toolkit 扩展）：

| 函数 | 用途 |
|---|---|
| `time_bucket('5 min', ts)` | 对齐到桶 |
| `first(value, ts)` / `last(value, ts)` | 按时间取首/末值 |
| `time_weight(...)` | 时间加权平均（计费类） |
| `histogram(value, lo, hi, nbuckets)` | 分布直方图 |
| `percentile_agg(value)` | 近似分位数（UDDSketch） |
| `lttb(ts, value, n)` | 大数据点降采样（图表用） |
| `gapfill(...) + locf()` | 时间填充 + 上一非空值 |

### 3.6 IoT 亿级监控案例

需求：1 万设备 × 100 指标 × 每 5 秒一条 = ~17 亿条/天。

设计：

1. Hypertable，1 天一个 chunk，按 device_id 二级哈希 16 份
2. 7 天前压缩，按 (device_id, metric_name) segmentby
3. 1m / 5m / 1h 三级连续聚合
4. 保留原始数据 30 天，聚合数据 2 年
5. `shared_preload_libraries = 'timescaledb'`，`max_worker_processes = 32`，`timescaledb.max_background_workers = 16`

结果（实测参考）：

- 原始数据从 850GB/天 压缩到 ~50GB/天（17x）
- 历史聚合查询（1 年）从分钟级降到秒级
- 写入吞吐 ~50 万行/秒（单节点 16C/64G NVMe）

### 3.7 Timescale Cloud vs OSS

注意 TimescaleDB 是 **TSL（Timescale License）** 双协议——开源版叫 Apache 2，企业版叫 TSL（不可作为 DBaaS 转售）。Hyperfunctions 部分高级算法、bitmap 压缩在 TSL 版本中。**AWS RDS 不提供** TimescaleDB；Timescale 自家云、Azure（部分）、Aiven 提供。

## 第四章：Citus —— PG 的水平分片

Citus 把 PG 变成一个分布式集群：一个 **coordinator** 节点 + N 个 **worker** 节点，按 shard key 分片，coordinator 把 SQL 重写并下发到 worker。它由 Citus Data 出品，2019 年被微软收购，2023 年 Citus 11/12 把更多特性开源，**PG 16+ 时代 Citus 进一步深度整合**。

### 4.1 概念三件套

| 概念 | 含义 |
|---|---|
| **distributed table** | 分布式表，按 distribution column 哈希到 shard |
| **reference table** | 引用表，每个 worker 都有完整副本（小维度表） |
| **local table** | 本地表，只在 coordinator 上（不参与分布式） |
| **shard** | 物理分片，本质是 worker 上的一个 PG 表（命名为 `tbl_<shardid>`） |
| **shard count** | 一张分布式表的 shard 数（默认 32） |
| **replication factor** | 每个 shard 的副本数（推荐 1，配合流复制做 HA） |

### 4.2 建集群与建表

```sql
-- 1. 所有节点加 shared_preload_libraries = 'citus'
-- 2. coordinator 上注册 worker
SELECT citus_add_node('worker-1', 5432);
SELECT citus_add_node('worker-2', 5432);
SELECT citus_add_node('worker-3', 5432);

CREATE EXTENSION citus;

-- 3. 建表 + 分布式化
CREATE TABLE orders (
  id BIGSERIAL,
  tenant_id BIGINT NOT NULL,
  user_id BIGINT,
  amount NUMERIC,
  created_at TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (tenant_id, id)
);

SELECT create_distributed_table('orders', 'tenant_id');

CREATE TABLE products (
  id BIGINT PRIMARY KEY,
  name TEXT,
  price NUMERIC
);
SELECT create_reference_table('products');
```

后续所有对 `orders` 的查询，只要 WHERE 带 `tenant_id = ?`，就只打到一个 shard（**single-shard query**，性能等同于本地 PG）；否则 fan-out 到所有 worker 并行执行。

### 4.3 跨 shard JOIN 的三种模式

1. **Co-located join**：两个分布式表按同一个 key 分布，相同 key 的 shard 在同一 worker → 本地 join，性能最佳。
2. **Reference join**：分布式表 join 引用表 → 引用表副本在每个 worker → 本地 join。
3. **Repartition join**：两个分布式表按不同 key → Citus 在 worker 间临时重分发数据 → 慢。

建模铁律：**所有需要 JOIN 的大表用同一个 distribution key**（如 tenant_id / user_id）。

### 4.4 PG 16+ 直接编译进 PG?

社区一直在讨论让 Citus 成为 PG 内核的一部分。截至 2026-05，Citus 仍是独立扩展，但与 PG 主版本的兼容矩阵越来越快：**Citus 13 ↔ PG 17、Citus 14 ↔ PG 18**（preview）。

### 4.5 适用场景与边界

| 场景 | 适合？ |
|---|---|
| 多租户 SaaS（按 tenant_id 分） | 非常合适 |
| 实时分析（OLAP） | 合适，配合列存（cstore_fdw / columnar） |
| 单实例顶不住的高 TPS 写 | 合适 |
| 强一致跨分片事务 | 不合适（2PC 性能差） |
| 想直接替代单机 PG | **不要** |

## 第五章：pg_partman —— 自动分区维护

PG 10+ 已经原生支持声明式分区，但**自动创建未来分区、自动删除过期分区**仍要手写脚本。`pg_partman` 把这件事自动化。

```sql
CREATE EXTENSION pg_partman;

CREATE TABLE events (
  id BIGSERIAL,
  event_time TIMESTAMPTZ NOT NULL,
  payload JSONB
) PARTITION BY RANGE (event_time);

SELECT partman.create_parent(
  p_parent_table => 'public.events',
  p_control      => 'event_time',
  p_type         => 'range',
  p_interval     => '1 day',
  p_premake      => 7      -- 提前创建未来 7 天
);

-- 配合 pg_cron 定时维护
SELECT cron.schedule('partman-maintenance', '*/5 * * * *',
  $$CALL partman.run_maintenance_proc()$$);

-- 保留策略（删除 90 天前）
UPDATE partman.part_config
SET retention = '90 days', retention_keep_table = false
WHERE parent_table = 'public.events';
```

实操要点：

- `premake` 不要设得太大（每个空分区也占元数据）；按日分区 7-14 就够。
- `retention_keep_table = true` 时不删表，只把它从父表 DETACH（保留备份/迁移机会）。
- 与 TimescaleDB 二选一：pg_partman 更原生 / 通用；TimescaleDB 更自动 / 含压缩。

## 第六章：pg_cron —— DB 内的 cron job

`pg_cron` 让 PG 自己跑定时任务，省掉外部 Airflow/Crontab。

```bash
# postgresql.conf
shared_preload_libraries = 'pg_cron'
cron.database_name = 'mydb'
```

```sql
CREATE EXTENSION pg_cron;

-- 每分钟跑一次
SELECT cron.schedule('refresh-stat', '* * * * *',
  $$REFRESH MATERIALIZED VIEW CONCURRENTLY mv_dashboard$$);

-- 每天 03:00
SELECT cron.schedule('nightly-vacuum', '0 3 * * *',
  $$VACUUM (ANALYZE) big_table$$);

-- 查看
SELECT * FROM cron.job;
SELECT * FROM cron.job_run_details ORDER BY start_time DESC LIMIT 20;

-- 取消
SELECT cron.unschedule('refresh-stat');
```

注意：

- pg_cron 调度器只在 `cron.database_name` 所在库工作；其它库要在 `cron.use_background_workers = on` 模式下用 `cron.schedule_in_database(...)`。
- 任务失败默认不重试，要自己写监控。
- AWS RDS 与 GCP CloudSQL 均支持 pg_cron。

## 第七章：pg_stat_statements —— 慢 SQL 的眼睛

这是**所有 PG 部署都应该装**的扩展。它对 SQL 做"参数化指纹"（digest），统计执行次数、累计耗时、平均行数、buffers 等。

```bash
# postgresql.conf
shared_preload_libraries = 'pg_stat_statements'
pg_stat_statements.track = all
pg_stat_statements.max = 10000
```

```sql
CREATE EXTENSION pg_stat_statements;

-- TOP 10 慢 SQL
SELECT substring(query, 1, 80) AS q,
       calls,
       round(total_exec_time::numeric, 2) AS total_ms,
       round(mean_exec_time::numeric, 2)  AS mean_ms,
       rows,
       100.0 * shared_blks_hit / nullif(shared_blks_hit + shared_blks_read, 0) AS hit_ratio
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- 重置统计
SELECT pg_stat_statements_reset();
```

PG 13+ 把 `total_time` 拆为 `total_exec_time` + `total_plan_time`，注意字段名。

## 第八章：pgaudit —— 审计日志

合规场景（金融、医疗、政企）经常要求"所有 DDL/DML 落日志"。

```bash
shared_preload_libraries = 'pgaudit'
pgaudit.log = 'ddl, role, write'   # ddl/read/write/role/function/misc/all
pgaudit.log_catalog = off
pgaudit.log_parameter = on
```

```sql
CREATE EXTENSION pgaudit;
```

之后所有命中的 SQL 会出现在 PG log 中：

```text
AUDIT: SESSION,1,1,WRITE,INSERT,TABLE,public.orders,"INSERT INTO orders ...",<none>
```

要把审计日志与业务日志分离，可配合 `log_directory` 单独输出，或 LogJSON + Filebeat。

## 第九章：pglogical —— 早期逻辑复制

PG 10 之前没有原生逻辑复制时，2ndQuadrant 出了 `pglogical`。**PG 10+ 后多数场景用原生 PUBLICATION/SUBSCRIPTION 即可**，pglogical 现在主要用在：

- 跨大版本（如 9.6 → 16）的零停机迁移（原生逻辑复制 PG 10 才有）
- 需要列级过滤 / 行级过滤 / 冲突解决策略（原生 PG 15+ 才追上）

```sql
CREATE EXTENSION pglogical;

-- 源端
SELECT pglogical.create_node('src', 'host=src dbname=mydb');
SELECT pglogical.create_replication_set('default');
SELECT pglogical.replication_set_add_all_tables('default', ARRAY['public']);

-- 目标端
SELECT pglogical.create_node('dst', 'host=dst dbname=mydb');
SELECT pglogical.create_subscription('sub_from_src', 'host=src dbname=mydb');
```

新项目建议直接用原生 [P16 逻辑复制](./16-精通-逻辑复制.md) 或 Debezium。

## 第十章：UUID 家族 —— uuid-ossp / pgcrypto / 内置 uuidv7

### 10.1 三种来源

| 扩展 / 函数 | 提供的 UUID 版本 |
|---|---|
| `uuid-ossp` | v1（MAC+时间）、v3（MD5）、v4（随机）、v5（SHA-1） |
| `pgcrypto` | `gen_random_uuid()` → v4 |
| **PG 18 内置** | `uuidv7()` → v7（时间有序，索引友好） |

```sql
CREATE EXTENSION "uuid-ossp";
SELECT uuid_generate_v1();
SELECT uuid_generate_v4();
SELECT uuid_generate_v5(uuid_ns_url(), 'https://example.com');

CREATE EXTENSION pgcrypto;
SELECT gen_random_uuid();

-- PG 18+ 内置（无需扩展）
SELECT uuidv7();
SELECT uuidv7(now() - INTERVAL '1 hour');  -- 指定时间戳
```

### 10.2 选哪个？

| 场景 | 推荐 |
|---|---|
| 一般主键 | **uuidv7**（PG 18+）或 ULID（外部生成） |
| 完全无序的安全令牌 | gen_random_uuid (v4) |
| 与遗留系统兼容 | uuid_generate_v1 |
| Hash 命名空间 | uuid_generate_v5 |

**为什么 v7 重要**：UUIDv4 是完全随机的，作为 B-tree 主键导致页随机写入 / 严重写放大；UUIDv7 前 48 位是 Unix 毫秒时间戳，**索引插入接近顺序**，磁盘友好。这是 PG 18 把它内置的根本动机。

## 第十一章：citext —— 大小写不敏感文本

存 email、用户名等"逻辑上忽略大小写"的字段，传统做法是 `LOWER(col)` 比较 + 表达式索引；用 `citext` 类型可让代码更简洁。

```sql
CREATE EXTENSION citext;

CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  email CITEXT UNIQUE NOT NULL
);

INSERT INTO users (email) VALUES ('Alice@Example.com');
SELECT * FROM users WHERE email = 'alice@example.com';   -- 命中

-- 唯一约束也自动忽略大小写
INSERT INTO users (email) VALUES ('alice@EXAMPLE.com');  -- 违反唯一
```

注意：

- 排序仍按字节序（取决于 collation）。
- 用 `citext` 后 `LIKE` 也大小写不敏感；要严格大小写比较得 `email::text = '...'`。
- 不能改善 `LIKE '%xxx%'` 的通配前缀问题，仍需 pg_trgm。

## 第十二章：pg_trgm —— 真正能"模糊搜索"的索引

PG 内置 LIKE 没法走索引"前缀通配"（`'%xxx%'` 完全无索引）。`pg_trgm` 把字符串切成三元组，建 GIN/GiST 索引后任意位置匹配都能走索引。

```sql
CREATE EXTENSION pg_trgm;

CREATE TABLE products (
  id BIGSERIAL PRIMARY KEY,
  name TEXT
);
CREATE INDEX idx_products_name_trgm ON products
  USING GIN (name gin_trgm_ops);

-- 任意位置 LIKE
EXPLAIN ANALYZE
SELECT * FROM products WHERE name ILIKE '%cola%';
-- → Bitmap Index Scan on idx_products_name_trgm

-- 相似度搜索（typo 容忍）
SELECT name, similarity(name, 'cocacola') AS sim
FROM products
WHERE name % 'cocacola'      -- % 操作符，默认阈值 0.3
ORDER BY sim DESC LIMIT 10;

SET pg_trgm.similarity_threshold = 0.5;
```

性能：

- 千万级商品名 `ILIKE '%xxx%'` 从全表扫降到几十毫秒
- 索引比 B-tree 大 3-5x，写入慢 ~2x
- 与 [P12 全文检索](./12-精通-JSONB-与全文检索.md) 互补：全文检索按词；pg_trgm 按字符 trigram，更适合英文名、商品 SKU、错别字。

## 第十三章：fuzzystrmatch —— Soundex / Levenshtein

英文姓名匹配场景常用：

```sql
CREATE EXTENSION fuzzystrmatch;

SELECT levenshtein('postgres', 'postgresql');     -- 2
SELECT levenshtein_less_equal('abc', 'abd', 2);   -- 1（有上限阈值，更快）

SELECT soundex('Robert'), soundex('Rupert');      -- R163 R163（音相似）
SELECT difference('Robert', 'Rupert');            -- 4（0-4，越大越像）

SELECT metaphone('PostgreSQL', 6);
SELECT dmetaphone('Schmidt');
```

Soundex / Metaphone 仅适合英语；中文场景要用拼音算法（外部）。

与 pg_trgm 区别：trgm 适合"大表上的索引查找"；fuzzystrmatch 适合"小集合上的算分排序"。

## 第十四章：pg_repack —— 在线 VACUUM FULL

`VACUUM FULL` 是重写整表的"原子炸弹"——锁表、阻塞所有读写。`pg_repack` 用另一种思路：

1. 创建一张临时表（结构相同）
2. 用触发器同步增量
3. 复制存量数据到临时表
4. 短暂排它锁 swap 文件

最终效果等同 VACUUM FULL，但**全程只在最后一瞬锁表**。

```bash
# 安装客户端工具
apt install postgresql-18-repack

pg_repack -d mydb -t public.big_table
pg_repack -d mydb -t public.big_table -k             # 不要超管，用 superuser bypass 也可
pg_repack -d mydb -T 60 -t public.big_table          # 等锁超时 60s
pg_repack -d mydb -t public.big_table --jobs=4       # 并行
```

注意：

- 需要 PRIMARY KEY 或 UNIQUE NOT NULL 索引
- 需要双倍磁盘空间
- 主备复制中：备库 WAL 流量瞬时暴增（整表重写都走 WAL）

## 第十五章：hypopg —— 虚拟索引

调优时常想"加这个索引能不能让 SQL 变快"——但建索引昂贵。`hypopg` 让你**虚拟创建索引**，planner 把它当真的来生成计划，不真的占用磁盘。

```sql
CREATE EXTENSION hypopg;

-- 假设建一个索引
SELECT * FROM hypopg_create_index(
  'CREATE INDEX ON orders (tenant_id, created_at DESC)'
);
-- 返回虚拟 indexrelid

EXPLAIN SELECT * FROM orders
  WHERE tenant_id = 42 ORDER BY created_at DESC LIMIT 10;
-- → 计划里会用到 <hypo_idx> 时，说明真建是有意义的

SELECT hypopg_reset();  -- 清理所有虚拟索引
```

与 [P10 EXPLAIN](./10-精通-EXPLAIN-与执行计划.md) 配合，是索引设计的强力工具。

## 第十六章：过程语言 plpython / plperl / plv8

PG 默认装 PL/pgSQL；其它语言以扩展形式存在。

| 扩展 | 语言 | trusted? |
|---|---|---|
| `plpgsql` | PL/pgSQL | 是（默认安装） |
| `plpythonu` / `plpython3u` | Python 3 | 否（untrusted，u 结尾） |
| `plperl` / `plperlu` | Perl | trusted / untrusted |
| `plv8` | JavaScript（V8） | 是 |
| `pljava` | Java | 否 |
| `plr` | R | 否 |
| `pllua` | Lua | 是 |

```sql
CREATE EXTENSION plpython3u;

CREATE FUNCTION pyhash(s text) RETURNS bigint
LANGUAGE plpython3u AS $$
import hashlib
return int(hashlib.md5(s.encode()).hexdigest()[:15], 16)
$$;

SELECT pyhash('hello');
```

适用场景：调机器学习库（sklearn）、字符串处理（regex 复杂）、HTTP 出网调用（**生产慎用**，会阻塞 backend）。

云厂商通常**不开放 untrusted 过程语言**（安全隐患）。Aurora 提供 plperl/plv8 但禁 plpythonu。

写一个最小扩展 `myadd`：

### 17.1 C 函数

```c
// myadd.c
#include "postgres.h"
#include "fmgr.h"

PG_MODULE_MAGIC;

PG_FUNCTION_INFO_V1(myadd_int4);

Datum
myadd_int4(PG_FUNCTION_ARGS)
{
    int32 a = PG_GETARG_INT32(0);
    int32 b = PG_GETARG_INT32(1);

}
```

```makefile
MODULES = myadd

PG_CONFIG = pg_config

include $(PGXS)
```

### 17.3 SQL 定义

```sql
-- myadd--1.0.sql
CREATE FUNCTION myadd_int4(int, int) RETURNS int
AS '$libdir/myadd', 'myadd_int4'

```

### 17.4 control 文件

```ini
# myadd.control
comment = 'My adder extension'

relocatable = true
```

## 生产实践

1. **shared_preload_libraries 顺序敏感**：`citus` 第一，`pg_stat_statements` 第二，再 `pg_cron`/`timescaledb`/`auto_explain`/`pgaudit`。改了必须重启实例，做变更窗口要预留。
2. **PostGIS / TimescaleDB 升级**：与 PG 大版本升级耦合。先用 `pg_upgrade --check` + 提前在测试库 `ALTER EXTENSION ... UPDATE`。
3. **pg_stat_statements 是底线**：所有 PG 实例都装。`pg_stat_statements_reset()` 不要乱跑，否则破坏长期趋势。
4. **pg_cron 不替代外部调度器**：DB 内任务只放"轻量、纯 SQL、与数据强耦合"的（refresh MV、维护分区、清理表）。复杂 DAG / 重试 / 报警仍交给 Airflow / Argo Workflows。
5. **hypopg 上线评估必备**：每次"想加索引"前，先 hypopg + EXPLAIN，确认 planner 会用，再真建。
6. **pg_repack 优于 VACUUM FULL**：除非维护窗口很长。但要预算双倍磁盘 + WAL 流量。
7. **TimescaleDB / Citus 二选一**：时序选 Timescale；多租户/分布式选 Citus。混合极少能跑通（compression 与 distributed table 兼容性差）。
8. **审计与监控对齐**：pgaudit 输出量大，必须有独立日志通道 + 集中化（Loki/Elasticsearch）。
9. **trust 扩展也要审计**：trusted 不代表"没风险"——pg_trgm 索引被恶意大字符串攻击仍可耗 CPU。
10. **扩展卸载会级联删对象**：`DROP EXTENSION ... CASCADE` 前用 `DROP EXTENSION ... RESTRICT` 看依赖。

---

## 陷阱清单

- **PostGIS 的 GEOMETRY vs GEOGRAPHY 混用**：直接 `ST_Distance(geom, geog)` 会隐式转换，性能崩盘；统一类型。
- **PostGIS 升级遗漏 `spatial_ref_sys`**：`pg_dump` 不带它，恢复后所有 SRID 解析失败。导出加 `--extension postgis` 或单独导 sys 表。
- **TimescaleDB compress 后不能 ALTER 列**：先 decompress chunk → ALTER → recompress。
- **TimescaleDB continuous aggregate 的 `start_offset` 必须 > 最近写入**，否则未刷新窗口的数据看不到。
- **Citus 跨 shard 唯一约束失效**：只在 distribution column 上的唯一索引能跨 shard；其它列的 UNIQUE 只在 shard 内有效。
- **Citus reference table 不能太大**：每个 worker 都存全量，~GB 级别上限。
- **pg_partman premake 太小**：写入到达未来分区时报"no partition found"。日表至少 7。
- **pg_cron 在备库不工作**：备库只读，schedule 表无法写；切主后任务自动恢复。
- **pgaudit 把 SELECT 也审计** → 日志爆炸。生产建议只 `write,ddl,role`。
- **pg_trgm 的 GiST vs GIN 选择**：GIN 查询快，写入慢；GiST 写入快，查询慢。在线场景多读少写选 GIN。
- **pg_repack 中途中断**：可能留下触发器和临时表，要手动清理 `pg_temp_xxx`。
- **hypopg 虚拟索引在 EXPLAIN ANALYZE 中不会真执行** → 估算 cost 但行数估计仍依赖 pg_statistic。
- **uuid_generate_v1 暴露 MAC 地址**：合规问题；选 v4 或 v7。
- **untrusted PL 跑外部命令** = 远程命令执行漏洞窗口；尽量不要装 plperlu / plpythonu。
- **扩展版本与 OS 包不一致**：`CREATE EXTENSION foo VERSION 'x.y'` 失败要先升 OS 包 (`apt install postgresql-18-foo`)。
- **shared_preload_libraries 写错名字**：实例无法启动，只能进 single-user 模式改 conf。
- **Citus 升级跨大版本**：必须按 11→12→13 一步步来，跳级会丢元数据。
- **TimescaleDB CE vs TSL** 协议混淆：CE 部分缺压缩 / 连续聚合；TSL 不能 SaaS 二次贩售。

---

## 2026 现状

- **PG 18 默认提供 `uuidv7()`**：很多场景可以下掉 `uuid-ossp` / `pgcrypto`。
- **pgvector 0.8（2025 Q4）**：HNSW 写入并发提升 3x，支持 INT8 量化，索引体积砍半。
- **pgvectorscale**（Timescale 开源，2024）：StreamingDiskANN 索引，亿级向量延迟降到毫秒级，部分场景超 HNSW。
- **TimescaleDB 2.18**：列存压缩支持局部 UPDATE/DELETE（写时复制），不再"压缩 = 只读"。
- **Citus 14（preview）**：与 PG 18 配套，logical replication 跨 shard 改进。
- **Supabase 全套**：默认装 ~40 个扩展（pgvector / pgjwt / pg_graphql / pg_net / pgsodium / wrappers），把 PG 当 BaaS 平台用。
- **Neon serverless**：扩展白名单逼近 RDS，分支 + 冷启 + Pricing 是杀手锏；AI 工作流主流选型。
- **CloudNativePG GA**（2024-Q3）：CNCF Incubation 路径明朗，K8s 上自建 PG 集群的事实标准；多数大厂自建 PG-on-K8s 都已弃 Zalando 转 CNPG。
- **DuckDB 风格分析压力**：duckdb_fdw / pg_duckdb（Hydra & MotherDuck 出品）让 PG 直接调 DuckDB 执行 OLAP，列存分析速度逼近原生 DuckDB（详见 [P19 FDW](./19-精通-FDW-与异构集成.md)）。
- **AI 扩展兴起**：pg_vectorize、pg_embedding、pgai（Timescale）封装"调 OpenAI / Ollama 生成 embedding 并插表"成一条 SQL。

## 练习题

1. **扩展机制**：解释 `CREATE EXTENSION pg_trgm` 在数据库内部触发了哪些步骤（涉及哪些目录文件、哪些系统表行被插入、SQL 脚本如何执行）。
2. **preload 区分**：在什么情况下你会把扩展放进 `session_preload_libraries` 而不是 `shared_preload_libraries`？给一个真实例子。
3. **PostGIS KNN**：写一个查询，找出"距离用户 5km 内、评分高于 4.5 的最近 20 个餐厅"。要求只用一次表扫，命中 GiST 索引。
4. **TimescaleDB 设计**：你有一个智能电表系统，1 亿台设备每 15 分钟一条读数，要求：实时查最近 24h 任意设备曲线、按区域聚合月度报表、保留原始 3 年。给出 Hypertable / 压缩策略 / 连续聚合 / retention 完整设计。
5. **Citus 建模**：电商订单表 `orders` 与商品表 `products`，需要按 `tenant_id` 分布。`products` 是商品维度（千条），怎么建模才能高效 JOIN？给出 DDL。
6. **pg_partman + pg_cron**：用这两个扩展实现"事件表按日分区，提前 14 天创建，保留 365 天，每 5 分钟维护一次"。给完整 SQL。
7. **pg_trgm vs 全文检索**：什么场景选 pg_trgm？什么场景选 tsvector？给出区分判据。
8. **pg_repack 决策**：一张 200GB 表，膨胀率 60%，业务 24x7。是用 pg_repack 还是用 pg_squeeze？说出理由与风险。
9. **hypopg 实战**：给定一个慢 SQL `SELECT * FROM orders WHERE tenant_id=? AND status='paid' ORDER BY created_at DESC LIMIT 20`，用 hypopg 评估是否要建 `(tenant_id, status, created_at DESC)` 复合索引。
