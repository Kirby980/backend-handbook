## 引言：为什么"了解新版本"是 PG DBA 的必修课

很多 PG 工程师对版本敏感度远低于 Java / Node 开发者——总觉得"PG 14 也能用，何必升 18"。但 PostgreSQL 是**每年一个大版本**的项目，每个版本都带来：

- 性能 10-50% 改进（无需改代码）
- 之前需要扩展的能力变内置（如 PG 14 的 pglz/lz4 切换）
- 之前不可能的事情突然变可能（PG 17 的 incremental backup、PG 18 的异步 IO）
- 旧版本被 EOL 后**没有任何安全补丁**

错过 PG 17 的支持窗口（2024-09 ~ 2029-11），等到 PG 14 EOL（2026-11）才慌着升，会少 18 个月的稳定性沉淀。

读完这章你应该能：

- 说出 PostgreSQL 的版本节奏（每年 9 月 + 5 年支持）
- 列出 PG 18（2025-09）的 5 大改进及生产收益
- 列出 PG 17（2024-09 发布）的 5 大改进
- 说明 PG 15-16 的关键已沉淀特性
- 选择升级路径：pg_upgrade vs 逻辑复制 vs pg_dump
- 描述未来路线图：64bit XID、可插拔存储引擎、列存

## 第一章：版本节奏与支持策略

### 1.1 发布节奏

PostgreSQL 自 2017 年起稳定执行**每年一个大版本**的发布节奏：

| 大版本 | 发布日期 | EOL 日期（5 年） |
|---|---|---|
| PG 10 | 2017-10-05 | 2022-11-10 已 EOL |
| PG 11 | 2018-10-18 | 2023-11-09 已 EOL |
| PG 12 | 2019-10-03 | 2024-11-14 已 EOL |
| PG 13 | 2020-09-24 | 2025-11-13 已 EOL |
| **PG 14** | 2021-09-30 | **2026-11-12**（即将 EOL） |
| **PG 15** | 2022-10-13 | 2027-11-11 |
| **PG 16** | 2023-09-14 | 2028-11-09 |
| **PG 17** | 2024-09-26 | **2029-11-08** |
| **PG 18** | 2025-09-25 | 2030-11（最新稳定版） |
| PG 19（开发中） | 2026-09（预计） | 2031-11 |

> ⚠️ PG 社区**没有官方"LTS"概念**——每个大版本都获得 5 年支持（见上表 EOL）。坊间偶尔把"刚发布、支持期最长"的版本俗称 "LTS"，但这并非 PostgreSQL 官方说法；真正的 "LTS" 只见于第三方托管服务（如 AWS Aurora PostgreSQL）。**2026-05 的最新稳定版是 PG 18。**

### 1.2 版本号含义

PG 10 之前是 9.x.y 三段；PG 10 起改成两段：

```
PostgreSQL 17.4
            │  │
            │  └── minor version（bugfix，季度发布）
            └── major version（年度大版本）
```

minor 升级一般 in-place（同位置替换二进制即可），major 升级需要 `pg_upgrade` 或逻辑复制。

### 1.3 当前（2026-05）选择建议

| 场景 | 推荐版本 |
|---|---|
| 新项目 / 新部署 | **PG 18**（2025-09 发布，已沉淀 8 个月 + 18.1/18.2 补丁，成熟可用） |
| 极致稳定优先 / 保守团队 | **PG 17**（已沉淀约 1.5 年，最久经考验） |
| 已在 PG 14 / 15 | 规划升 PG 17 或 18（PG 14 将于 2026-11 EOL） |
| PG 13 及以下 | **紧急升级**，社区不再 patch |

## 第二章：PG 18（2025-09）—— 异步 IO 革命

### 2.1 异步 IO（Asynchronous I/O）⭐⭐⭐⭐⭐

PG 18 引入了**异步 IO 框架**，是过去 10 年最大的存储子系统改进。

**问题背景**：PG 一直用**同步阻塞 IO**（`pread(2)` / `pwrite(2)`），每次读盘一个后端进程就 block 在内核里等数据。即使是 NVMe SSD（百万 IOPS），单进程也只能跑满几千 IOPS——因为绝大多数时间在等内核唤醒。

**PG 18 方案**：通过 `io_method` 参数选择 IO 方式：

| io_method | 实现 | 适用 |
|---|---|---|
| `sync` | 传统同步（旧默认） | 兼容性 |
| `worker` | 专门的 IO worker 进程异步处理 | 默认值，跨平台 |
| `io_uring` | Linux 5.1+ 内核 io_uring | Linux 高性能场景 |

```ini
# postgresql.conf
io_method                       = io_uring
io_workers                      = 3          # io_method=worker 时
io_combine_limit                = 128kB      # 合并相邻读请求
io_max_combine_limit            = 128kB
```

**实测收益**（PG 社区基准）：

| 工作负载 | sync | io_uring | 提升 |
|---|---|---|---|
| 顺序读（pg_basebackup） | 1.2 GB/s | 2.8 GB/s | 2.3x |
| 随机读 8KB（OLTP point query） | 14k IOPS/进程 | 45k IOPS/进程 | 3.2x |
| 大表 Seq Scan | 600 MB/s | 1.4 GB/s | 2.3x |
| 索引深度扫描 + heap fetch | 极大 | 显著加速 | 1.5-2x |

**注意**：

- `io_uring` 仅 Linux 5.1+（Ubuntu 20.04+ / RHEL 9+）
- 容器中可能被 seccomp 拦截，需 grant `io_uring` 系统调用
- 云数据库可能不暴露此参数

```sql
-- 看当前 IO 方式
SHOW io_method;

-- 看预读 IO 队列深度
SELECT name, setting FROM pg_settings WHERE name LIKE 'io_%';
```

### 2.2 UUIDv7 内置 ⭐⭐⭐⭐

PG 18 引入 `uuidv7()` / `uuidv7(interval)` 内置函数。

UUIDv7（[RFC 9562](https://datatracker.ietf.org/doc/rfc9562/) 2024-05 标准化）是**时间排序的 UUID**：

```
00000000-0000-7000-0000-000000000000
        │           │
        │           └── version 7
        └── 48bit 毫秒级 Unix 时间戳（前缀）
```

```sql
-- PG 18+
SELECT uuidv7();
-- 0190f5a3-c8d1-7234-89ab-cdef01234567
--                   ↑
--                version 7 marker

-- 看时间戳
SELECT uuid_extract_timestamp(uuidv7());

-- 用于主键
CREATE TABLE orders (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  user_id bigint,
  created_at timestamptz DEFAULT now()
);
```

**为什么重要**：

| 主键方案 | 索引插入性能 | 跨服务唯一 | 时间排序 |
|---|---|---|---|
| `bigserial` | 极快 | 否 | 是 |
| `uuid_generate_v4()` | 慢（B-tree 写放大严重） | 是 | 否 |
| **`uuidv7()`** | **快**（前缀单调） | **是** | **是** |

UUIDv7 同时获得 UUID 的"无中心"和 bigserial 的"B-tree 友好"——是分布式系统的**新一代主键标准**。

之前要用扩展（`uuid-ossp`、`pg_uuidv7`），PG 18 起内置。

### 2.3 虚拟生成列 VIRTUAL ⭐⭐⭐⭐

PG 12 起支持 STORED 生成列（计算后**物理存储**）。PG 18 加入 **VIRTUAL**（读时计算，不存储）：

```sql
CREATE TABLE products (
  id bigserial PRIMARY KEY,
  price numeric(10,2),
  tax_rate numeric(4,3) DEFAULT 0.13,
  -- VIRTUAL：不存储，每次 SELECT 计算
  price_with_tax numeric GENERATED ALWAYS AS (price * (1 + tax_rate)) VIRTUAL,
  -- STORED：物理存储，UPDATE 时计算（PG 12+ 已有）
  search_text text GENERATED ALWAYS AS (lower(name)) STORED
);
```

**对比**：

| 类型 | 存储 | 写性能 | 读性能 | 可索引 |
|---|---|---|---|---|
| `STORED` | 占空间 | 慢（计算+写） | 快 | 是 |
| `VIRTUAL` | 不占 | 不影响 | 慢（每次算） | **否**（PG 18 不支持，也不支持唯一/外键/扩展统计/逻辑复制） |

**默认值**：PG 18 起 `GENERATED ALWAYS AS (...)` 不写 STORED 时**默认 VIRTUAL**。

适用场景：

- 经常修改、读少的派生字段 → VIRTUAL（避免写放大）
- 经常查询、写少 → STORED（避免重复计算）
- 需要索引（VIRTUAL 列不可索引）→ 改用 STORED，或对底层列建表达式索引

### 2.4 OAuth 2.0 认证 ⭐⭐⭐

PG 18 引入 OAuth 2.0 认证方法（`oauth`），无需第三方扩展即可对接 Keycloak、Okta、Auth0：

```
# pg_hba.conf
host all all 0.0.0.0/0 oauth issuer="https://keycloak.example.com/realms/my" scope="postgres"
```

```
# postgresql.conf
oauth_validator_libraries = 'validator_jwt'
```

客户端在连接串里传 token（或交互式 device flow）：

```
psql 'postgresql://pg/db?oauth_issuer=https://...&oauth_client_id=...'
```

→ 企业 SSO 场景不再需要 `pg_jwt_auth` 等扩展。

### 2.5 不变性 (immutable) 函数增强 ⭐⭐⭐

PG 18 强化了 `IMMUTABLE` 函数的内联与优化：

- 表达式索引中使用 IMMUTABLE 函数更易被 Planner 重用
- 部分索引谓词中的 IMMUTABLE 函数更精准
- 函数体只有单个 SQL 表达式的 IMMUTABLE 函数会被 Planner **直接内联**到查询，等价于手写表达式
- 改善了之前"包了一层函数的索引列就走不上索引"的痛点

```sql
-- PG 18 改进：以下查询能用上表达式索引
CREATE OR REPLACE FUNCTION normalize_phone(p text) RETURNS text
LANGUAGE sql IMMUTABLE PARALLEL SAFE AS $$
  SELECT regexp_replace(p, '[^0-9]', '', 'g')
$$;

CREATE INDEX idx_users_phone ON users(normalize_phone(phone));

-- PG 18 内联后等价于直接走索引
SELECT * FROM users WHERE normalize_phone(phone) = '13800001111';
```

### 2.6 B-tree skip scan ⭐⭐⭐

PG 18 引入**多列 B-tree skip scan**（多列索引前缀列基数低时仍可用），由 Peter Geoghegan 实现。PG 17 及以前没有此功能。

```sql
CREATE INDEX idx_orders_status_created ON orders(status, created_at);

-- PG 17 及以前：status 缺失 → Planner 选 Seq Scan
-- PG 18 起：可能走 index skip scan
SELECT * FROM orders WHERE created_at > '2026-05-01';
```

效果类似 Oracle / SQL Server 的 "index skip scan"——前缀列基数低（如 status 有 3 个值）时，Planner 用 N 次定位代替全表扫描。

### 2.7 逻辑复制保留 origin ⭐⭐⭐

PG 18 改进逻辑复制冲突处理，保留更多 origin 信息，方便双向复制场景检测自循环。详见 [P16](./16-精通-逻辑复制.md)。

### 2.8 EXPLAIN ANALYZE CPU 时间分解 ⭐⭐⭐

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT count(*) FROM orders WHERE total > 1000;
```

PG 18 起每个节点显示：

```
Seq Scan on orders  (cost=... rows=... width=...)
  (actual time=... rows=... loops=...)
  CPU usage: user=234ms system=18ms
  Buffers: shared hit=... read=...
```

→ 立即区分"CPU 密集" vs "IO 密集"瓶颈，无需借助 OS 工具。

### 2.9 其他 PG 18 亮点

- **pg_dump 增强**：默认并行（`-j auto`）
- **VACUUM 第二阶段并行**：清理 dead tuple 时并行扫描索引
- **流复制改进**：standby 启动时主动从 archive 拉 WAL（缩短恢复时间）
- **统计扩展**：`CREATE STATISTICS` 支持表达式
- **pg_dump`--filter`**：通用过滤选项（按 schema、table、regex）
- **`max_active_replication_origins`**：单独参数控制 origin 数，不再共用 `max_replication_slots`
- **`pg_overexplain` 扩展**：内置工具，输出更详细的 EXPLAIN 内部状态（Planner 调试）
- **`reject_limit` COPY 选项**：导入时允许跳过 N 行错误数据，超过则中止
- **改进的 RELEASE SAVEPOINT 性能**：高并发使用 savepoint 的应用（如 ORM）受益
- **`pg_get_acl()`**：直接返回某对象的访问控制列表
- **TLS 增强**：支持 RFC 8879 证书压缩、postgres_fdw 默认强制 SSL

## 第三章：PG 17（2024-09 发布）—— 备份与 JSON 革命

### 3.1 Incremental Backup ⭐⭐⭐⭐⭐

PG 17 引入**增量备份**，是过去 10 年最受期待的功能之一。

**问题背景**：之前 `pg_basebackup` 只能全量，1TB 库每天全量 = 1TB 流量 + 1TB 存储。第三方方案（`pgBackRest`、`barman`）支持增量，但运维复杂。

**PG 17 内置方案**：

```bash
# 全量基线
pg_basebackup -D /backup/base -X stream -P -c fast

# 一周后，增量备份（仅变化的块）
pg_basebackup -D /backup/incr-20260528 \
  --incremental=/backup/base/backup_manifest \
  -X stream -P

# 恢复时：合并基线 + 增量
pg_combinebackup /backup/base /backup/incr-20260521 /backup/incr-20260528 \
  -o /backup/merged

# 然后从 merged 启动 standby
```

**关键参数**：

```ini
# postgresql.conf
summarize_wal                   = on             # 必须打开，WAL 摘要记录页修改
wal_summary_keep_time           = 10 days        # 保留 WAL 摘要
```

**收益**：

- 增量大小通常 5-20% of 全量
- 备份窗口短（5 分钟而非数小时）
- 存储成本降低 70-90%

详细见 [P15 WAL 与物理复制](./15-精通-WAL-与物理流复制.md)。

### 3.2 MERGE...RETURNING ⭐⭐⭐⭐

PG 15 引入了 `MERGE`（SQL:2003 标准）。PG 17 加入 `RETURNING` 子句，让 MERGE 真正可用：

```sql
MERGE INTO customer_summary cs
USING (
  SELECT user_id, sum(total) AS amt, count(*) AS cnt
  FROM orders WHERE created_at::date = current_date
  GROUP BY user_id
) o ON cs.user_id = o.user_id
WHEN MATCHED THEN
  UPDATE SET total_amount = cs.total_amount + o.amt,
             order_count  = cs.order_count + o.cnt,
             updated_at   = now()
WHEN NOT MATCHED THEN
  INSERT (user_id, total_amount, order_count, updated_at)
  VALUES (o.user_id, o.amt, o.cnt, now())
RETURNING merge_action() AS action,            -- PG 17 新增
          cs.user_id, cs.total_amount;
```

`merge_action()` 返回 `'INSERT'` / `'UPDATE'` / `'DELETE'`，方便审计与下游通知。

### 3.3 MERGE WHEN NOT MATCHED BY SOURCE ⭐⭐⭐

PG 17 完善 MERGE，加入 `WHEN NOT MATCHED BY SOURCE`（已删除时清理）：

```sql
MERGE INTO inventory i
USING latest_stock s ON i.sku = s.sku
WHEN MATCHED THEN
  UPDATE SET qty = s.qty
WHEN NOT MATCHED BY TARGET THEN
  INSERT VALUES (s.sku, s.qty)
WHEN NOT MATCHED BY SOURCE THEN   -- 目标有，源没有 → 已下架
  DELETE;
```

→ 一条 MERGE 完成"全量同步"，替代 INSERT...ON CONFLICT + DELETE 组合。

### 3.4 SQL/JSON 完整子集 ⭐⭐⭐⭐⭐

PG 17 完整实现 SQL:2023 的 SQL/JSON 标准，包括：

- `JSON_TABLE`（从 JSON 拆成关系表）
- `JSON_VALUE`（取单值）
- `JSON_QUERY`（取子文档）
- `JSON_EXISTS`（判断路径存在）
- 构造函数：`JSON()`, `JSON_SCALAR()`, `JSON_SERIALIZE()`, `JSON_OBJECT()`, `JSON_ARRAY()`, `JSON_OBJECTAGG()`, `JSON_ARRAYAGG()`

```sql
-- JSON_TABLE: 把 JSON 数组炸成行（最强大的新增）
SELECT t.*
FROM jsonb_data jd,
     JSON_TABLE(jd.payload, '$.items[*]' COLUMNS (
       id       int     PATH '$.id',
       name     text    PATH '$.name',
       price    numeric PATH '$.price',
       in_stock boolean PATH '$.stock > 0'
     )) t;

-- JSON_VALUE: 取单值
SELECT JSON_VALUE(payload, '$.user.name' RETURNING text DEFAULT 'unknown' ON EMPTY)
FROM jsonb_data;

-- JSON_QUERY: 取子文档
SELECT JSON_QUERY(payload, '$.items' RETURNING jsonb) AS items
FROM jsonb_data;

-- JSON_EXISTS
SELECT *
FROM jsonb_data
WHERE JSON_EXISTS(payload, '$.tags ? (@ == "vip")');
```

→ 完全替代之前 `jsonb_path_query()` + `->>` + `@?` 的混合用法，可读性大幅提升。

详细见 [P12 JSONB 与全文检索](./12-精通-JSONB-与全文检索.md)。

### 3.5 逻辑复制故障切换不中断订阅 ⭐⭐⭐⭐

之前痛点：主库故障切换到 standby 后，逻辑复制订阅会**全部断开**（订阅指向旧主库 LSN）。

PG 17 引入**slot synchronization**（复制槽同步）：

```sql
-- 主库
CREATE_REPLICATION_SLOT my_slot LOGICAL pgoutput;
ALTER REPLICATION SLOT my_slot FAILOVER true;       -- 标记为故障切换可保留
```

```ini
# standby postgresql.conf
sync_replication_slots = on
hot_standby_feedback = on
primary_slot_name = 'standby_slot'
```

故障切换后 standby 已经同步了槽状态，订阅可继续从原 LSN 开始。

→ 逻辑复制 + 高可用真正生产可用。

### 3.6 VACUUM 内存改进 ⭐⭐⭐⭐

PG 17 重写了 VACUUM 的死元组数组结构：

| 版本 | 死元组存储 | 最大有效内存 |
|---|---|---|
| ≤ PG 16 | 数组（线性扫描） | **1 GB**（即使 maintenance_work_mem 设更大也无效） |
| **PG 17** | **基数树（radix tree）** | **= maintenance_work_mem**（无 1GB 上限） |

效果：

- 大表 VACUUM 速度提升 **3-6x**
- 索引清理阶段速度提升 **6-20x**

→ PG 17 起可以放心 `maintenance_work_mem = 4GB-8GB`。

### 3.7 CREATE COLLATION / builtin provider 改进 ⭐⭐⭐

PG 17 新增第三种 collation provider —— **builtin**（默认仍是 libc，并非 ICU）。builtin 提供 `C` 与 `C.UTF-8`（`pg_c_utf8`）两种 locale，在 PG 内核中实现。好处：

- 不依赖外部库（libc/ICU），升级 glibc 不会让索引失效
- 语义保证不可变（immutable），无需版本化
- `C.UTF-8` 按 Unicode 码点排序，性能接近 C 且支持 Unicode 大小写

```sql
SELECT collname, collprovider, collversion 
FROM pg_collation WHERE collname LIKE 'zh%';
```

如果 `pg_collation.collversion != collversionversion()` 说明 collation 版本变了，需要 `REINDEX`。

### 3.9 其他 PG 17 亮点

- **pg_basebackup --target=blackhole**：仅校验，不写文件（测试场景）
- **pg_createsubscriber**：从物理 standby 一键转换成逻辑订阅者
- **EXPLAIN (MEMORY)**：显示 Planner 内存占用
- **transaction_timeout**：整事务超时（之前只有 statement_timeout）
- **COPY (FORMAT json)**：导出 JSON（之前只有 csv/text/binary）

```sql
COPY (SELECT * FROM orders) TO STDOUT WITH (FORMAT json);
```

- **`event_trigger` 支持 LOGIN**：登录时触发审计逻辑
- **`pg_buffercache_evict()`**：手动驱逐 buffer，方便基准测试
- **改进 PL/pgSQL**：`GROUP BY ALL` 支持、`%TYPE` 支持数组
- **逻辑复制初始同步并行**：大表初始 COPY 阶段并行执行，速度提升 2-3 倍
- **新增 `pg_wait_events` 视图**：所有 wait event 元数据查询入口
- **配置文件 `\dconfig` 元命令**：psql 直接看分组配置
- **`pg_dump --filter`** 早期实现（PG 18 完善）

### 3.10 PG 17 升级 checklist

PG 17 与 PG 16 兼容性较好，主要注意：

- 默认 collation provider 仍是 libc（PG 17 新增 builtin provider，但非默认）→ 若沿用 libc 排序，升级前后排序结果可能因 glibc 版本微妙变化，对索引唯一性约束的影响需测试
- 一些被废弃的旧函数（如 `adminpack` 模块）已彻底删除
- `OLD_SNAPSHOT_THRESHOLD` 参数被移除（之前的"防止超长 snapshot"机制改造）
- `replication_slot_xmin_horizon` 行为变化，长事务对 slot 的阻塞模型微调

```sql
-- 升级前必查
SELECT collname, collversion, pg_collation_actual_version(oid) AS actual
FROM pg_collation
WHERE collversion IS NOT NULL 
  AND collversion != pg_collation_actual_version(oid);
-- 有结果 → 升级后必须 REINDEX
```

## 第四章：PG 16（2023-09）—— 双向复制与 pg_stat_io

### 4.1 双向逻辑复制 ⭐⭐⭐⭐

PG 16 起，**两个集群可以互为发布者 + 订阅者**：

```sql
-- 集群 A
CREATE PUBLICATION pub_a FOR ALL TABLES;
CREATE SUBSCRIPTION sub_to_b CONNECTION 'host=b ...' PUBLICATION pub_b;

-- 集群 B
CREATE PUBLICATION pub_b FOR ALL TABLES;
CREATE SUBSCRIPTION sub_to_a CONNECTION 'host=a ...' PUBLICATION pub_a;
```

通过 `origin` 标记避免无限循环。

→ 多活、灾备双写、跨地域同步真正可用。

### 4.2 pg_stat_io ⭐⭐⭐⭐⭐

按对象 + 后端类型切分的 IO 视图（详细见 [P21 监控](./21-精通-监控与诊断.md)）。

### 4.3 CPU 优化 ⭐⭐⭐

PG 16 引入 SIMD 指令集加速 ASCII 字符串操作、JSON 解析、numeric 求和等：

| 操作 | PG 15 | PG 16 | 提升 |
|---|---|---|---|
| `length(text)` 大字符串 | 100ms | 60ms | 1.7x |
| numeric SUM 聚合 | 基准 | 1.3x | 1.3x |
| JSON 解析 | 基准 | 1.2x | 1.2x |

→ 升级 PG 16 即获得"免费 10-30% 加速"。

### 4.4 并行 Hash Join 改进 ⭐⭐⭐

PG 16 改进并行哈希构建，大 hash join 速度提升 30%+。

### 4.5 其他

- `pg_hba.conf` 支持正则表达式
- `\d+` 显示访问方法
- `random()` 接受范围参数
- `array_sample()`, `array_shuffle()` 新函数
- `pg_dump --exclude-extension`
- 改进 vacuum 的内存使用（为 PG 17 的 radix tree 做铺垫）
- `pg_stat_io` 暴露按 backend_type 与 context 切分的 IO 统计
- 引入 `aggregate column` 在 GROUP BY 后保留更多原始列

### 4.6 PG 16 关键 SQL 改进

PG 16 完善了**集合操作**与**聚合**：

```sql
-- ANY VALUE 聚合函数（PG 16+）
SELECT department,
       any_value(name) AS sample_employee
FROM employees GROUP BY department;

-- 通用子查询去重（CTE 内 DISTINCT 优化）
WITH t AS (
  SELECT DISTINCT user_id, order_date FROM orders
)
SELECT count(*) FROM t;
-- PG 16 引擎能识别 t 内已 DISTINCT，不再重复处理
```

## 第五章：PG 15（2022-10）—— MERGE 与行过滤

### 5.1 MERGE 命令 ⭐⭐⭐⭐⭐

```sql
MERGE INTO target t
USING source s ON t.id = s.id
WHEN MATCHED AND s.deleted THEN DELETE
WHEN MATCHED THEN UPDATE SET col = s.col
WHEN NOT MATCHED THEN INSERT (id, col) VALUES (s.id, s.col);
```

替代 `INSERT ... ON CONFLICT` 在复杂场景的不足。

### 5.2 行过滤逻辑复制 ⭐⭐⭐⭐

```sql
CREATE PUBLICATION pub_active_users FOR TABLE users
  WHERE (status = 'active' AND created_at > '2024-01-01');
```

→ 只发布满足条件的行，减少跨网流量。

### 5.3 列过滤逻辑复制 ⭐⭐⭐

```sql
CREATE PUBLICATION pub_safe FOR TABLE users (id, email, name);
-- 不发送 password_hash 等敏感列
```

### 5.4 ICU collation 默认可选

```sql
initdb --locale-provider=icu --icu-locale=en-US
```

### 5.5 其他

- `pg_basebackup --compress=zstd`
- `wal_compression = zstd` / `lz4`
- 公开 `archive_library`（替代 `archive_command`）
- jsonlog 日志格式
- 公共模式 `public` 默认不再对 `PUBLIC` 开放写权限（**安全加固**）
- `SECURITY_RESTRICTED_OPERATION` 内嵌 SET role
- 多列 BRIN 索引完善（PG 14 引入）

### 5.6 PG 15 兼容性陷阱

PG 15 是**社区公认升级影响较大**的版本，主要因为 `public schema` 权限默认变化：

```sql
-- PG 15 之前：所有用户都能在 public 建表
-- PG 15 之后：只有 db owner 能建

-- 老应用升级到 PG 15 可能突然报权限错误
-- 修复（恢复旧行为）：
GRANT CREATE ON SCHEMA public TO PUBLIC;

-- 或更安全的做法：每个应用一个独立 schema
CREATE SCHEMA app1 AUTHORIZATION app1_user;
ALTER ROLE app1_user SET search_path = app1, public;
```

## 第七章：升级路径

### 7.1 三种主流升级方式

| 方式 | 停机 | 难度 | 适用 |
|---|---|---|---|
| `pg_upgrade` (in-place) | 几分钟 | 中 | 同主机升级，跨 1-3 个大版本 |
| 逻辑复制（pglogical / 内置） | **零停机** | 高 | 跨地域、跨硬件、降级也行 |
| `pg_dump / pg_restore` | 高（数小时） | 低 | 小库、跨架构、最稳但最慢 |

### 7.2 pg_upgrade

```bash
# 1. 停旧集群
pg_ctl stop -D /var/lib/postgresql/14/main

# 2. 安装新版二进制（不动数据目录）
apt install postgresql-17

# 3. 检查兼容性
pg_upgrade --old-datadir=/var/lib/postgresql/14/main \
           --new-datadir=/var/lib/postgresql/17/main \
           --old-bindir=/usr/lib/postgresql/14/bin \
           --new-bindir=/usr/lib/postgresql/17/bin \
           --check     # 只检查，不动数据

# 4. 真正升级（--link 用硬链接，几秒完成）
pg_upgrade --old-datadir=... --new-datadir=... \
           --old-bindir=... --new-bindir=... --link

# 5. 启动新集群
pg_ctl start -D /var/lib/postgresql/17/main

# 6. ANALYZE（统计信息从头收集）
/usr/lib/postgresql/17/bin/vacuumdb --all --analyze-in-stages

# 7. 删旧目录
/usr/lib/postgresql/17/bin/delete_old_cluster.sh
```

**优点**：
- 几分钟完成（`--link` 模式秒级）
- 同主机升级

**缺点**：
- 需要短暂停机
- 跨大版本太多（如 PG 11 → PG 17）需要分步
- 扩展兼容性需逐一验证

### 7.3 逻辑复制零停机升级

```sql
-- 旧主库（PG 14）：开启逻辑复制
ALTER SYSTEM SET wal_level = 'logical';
-- 重启
CREATE PUBLICATION pub_all FOR ALL TABLES;

-- 新库（PG 17）：恢复结构 schema-only
pg_dump --schema-only -h old-pg14 mydb | psql -h new-pg17 mydb

-- 新库（PG 17）：订阅
CREATE SUBSCRIPTION sub_from_pg14 
  CONNECTION 'host=old-pg14 dbname=mydb user=replicator' 
  PUBLICATION pub_all;
-- 自动 COPY 初始数据 + 流式 apply 增量

-- 等待追平
SELECT * FROM pg_stat_subscription;
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), latest_end_lsn))
FROM pg_stat_wal_receiver;

-- 切流量
-- 1. 停应用对旧库写入
-- 2. 等订阅最后追平
-- 3. 切应用连接到新库
-- 4. 反向建逻辑复制（可选，回滚保险）
```

**优点**：
- 零停机
- 可在线测试新版本
- 不限制版本差距（PG 10 → PG 17 都行）

**缺点**：
- 双倍存储 + 流量（迁移期间）
- 不复制 DDL（迁移期间停止 schema 变更）
- 不复制序列当前值（手动同步）
- 大对象、TRUNCATE 跨版本兼容性需测

### 7.4 pg_dump / pg_restore

```bash
# 全量导出（并行）
pg_dump -Fc -j 8 -d olddb -h old-host > olddb.dump

# 导入新库
pg_restore -d newdb -h new-host -j 8 olddb.dump
```

**优点**：
- 最稳（标准 SQL 重建）
- 跨架构（x86 → ARM）
- 跨大版本无限制

**缺点**：
- 停机时间长（GB 级数小时，TB 级数十小时）
- 不适合大库

### 7.5 升级前 Checklist

```bash
# 1. 看旧版的所有非默认参数
psql -t -c "SELECT name, setting FROM pg_settings WHERE source NOT IN ('default','override');" > old_params.txt

# 2. 看所有扩展及版本
psql -c "SELECT extname, extversion FROM pg_extension;"
# 在新版上验证每个扩展是否兼容（特别注意 PostGIS、TimescaleDB、Citus）

# 3. 看自定义类型 / 函数 / 触发器
psql -c "\df+" / "\dT+"

# 4. 检查弃用语法
# PG 14: postmaster.pid 格式变化
# PG 15: stats collector 移除（监控工具可能受影响）
# PG 17: 新增 builtin collation provider（默认仍 libc，排序结果取决于所选 provider）

# 5. 测试环境完整跑业务一周
```

## 第八章：未来路线图

### 8.1 64bit XID（事务 ID）

当前 PG 用 32bit XID（约 21 亿），每 ~21 亿事务需要 freeze 防 wraparound。社区已多年讨论 64bit XID：

- 优点：彻底消除 wraparound 危机
- 难点：兼容性、tuple header 改造、回退路径
- 进展：[Postgres Pro EE](https://postgrespro.com/products/postgrespro-enterprise) 已实现，社区版预计 PG 19/20 引入

### 8.2 可插拔存储引擎（Pluggable Storage / Table Access Method）

PG 12 起引入 [Table Access Method API](https://www.postgresql.org/docs/current/tableam.html)，让 PG 像 MySQL 一样支持多种存储引擎：

| 引擎 | 类型 | 状态 |
|---|---|---|
| **heap** | 默认堆表 | 内置 |
| **zheap** | 类 Oracle UNDO，原地 update | EnterpriseDB 维护中，未合并 |
| **OrioleDB** | MVCC + undo + 行级 WAL | Supabase 出品，活跃 |
| **Citus Columnar** | 列存 | 生产可用，Citus 子项目 |
| **Hydra Columnar** | 列存（fork 自 Citus） | 商业产品 |

```sql
-- PG 12+
CREATE TABLE big_log (...) USING columnar;     -- 用列存
```

### 8.3 列存（Columnar Storage）

PostgreSQL 在 OLAP 一直被诟病"没有原生列存"。当前社区方案：

- **Citus Columnar**（开源，pg_columnar）
- **Hydra**（商业，fork）
- **TimescaleDB Hypercore**（混合行列）
- **DuckDB 集成**（pg_duckdb 扩展）

PG 主分支列存讨论已 5+ 年，PG 19/20 可能引入"原生列存表"。

### 8.4 异步逻辑复制 / 并行 Apply

PG 16 引入并行 apply（worker 并行应用事务），PG 17/18 继续完善。目标：逻辑复制不再是单 worker 瓶颈。

### 8.5 改进的并行查询

PG 19 路线图包含：

- 并行 INSERT / UPDATE / DELETE 完善
- 并行 hash 完善
- Adaptive query execution

### 8.6 直连 Object Storage（S3 等）

社区在讨论"WAL 直接写 S3"、"冷分区放 S3"等方向。[pg_lakehouse](https://github.com/) 等扩展已经在做。

### 8.7 AI 集成

- `pgvector` 主流化（PG 16+ 表现强劲）
- `pg_embedding`、`pgvectorscale`
- 未来可能官方扩展加入 LLM 推理（如 `LLM_CALL()` SQL 函数）

## 生产实践

### 1. 升级时机选择

| 公司规模 | 建议 |
|---|---|
| 初创 / 个人 | 跟最新（PG 18 已稳定） |
| 中型公司 | PG 18（或保守选 PG 17） |
| 大型 / 金融 | 等 PG 17.4+ 或 PG 18.3+ 再上 |
| 监管严格 | 跟随云厂商（RDS、AlloyDB 升级节奏） |

### 2. minor 版本及时跟

PG 不像 MySQL，minor 版本只含安全 + bug fix，**风险极低**。每季度（约 2/5/8/11 月）发布的 minor 版本应当**1 个月内升级**。

### 3. 升级前必做演练

- 在测试集群完整 dry run 一次（包含所有扩展、自定义函数）
- 用生产数据 dump 到测试环境跑业务回放
- 量化预期停机时间（pg_upgrade --link 通常 < 5min）

### 4. 扩展兼容性

每个大版本发布后，主流扩展通常需要 1-3 个月跟进：

| 扩展 | 跟进速度 |
|---|---|
| pg_stat_statements、pg_trgm（内置） | 即刻 |
| PostGIS | 1-2 个月 |
| TimescaleDB | 1-3 个月（需付费版） |
| Citus | 2-4 个月 |
| pgvector | 1 个月 |

**升级前在测试环境验证每个扩展。**

### 5. 利用新特性时机

不要为了新特性而升级，但升级后**主动迁移到新写法**：

| 旧写法 | 新写法 | 版本 |
|---|---|---|
| `INSERT ... ON CONFLICT` | `MERGE` | PG 15+ |
| `jsonb_path_query()` 嵌套 | `JSON_TABLE` | PG 17+ |
| `uuid_generate_v4()` | `uuidv7()` | PG 18+ |
| pgBackRest 全量 | `pg_basebackup --incremental` | PG 17+ |
| 应用层 OAuth | `pg_hba` oauth 方法 | PG 18+ |

### 6. 多版本并存策略

大公司一般同时运行多个 PG 大版本：

- 新业务 → 最新稳定版（2026-05 即 PG 18）
- 老业务 → 上一稳定版（PG 17）
- 极老业务 → 维持现状直到 EOL 前 12 个月才迁

| # | 陷阱 | 后果 | 正确做法 |
|---|---|---|---|

| 18 | 升级后没看 release notes | 不知道默认值变了 | 必读 |

## 练习题

### 练习 1：版本支持表

写一个 SQL 函数（或脚本）：输入 PG 版本号，返回该版本是否还在支持期、EOL 日期、距 EOL 还有多少天。

<details><summary>参考答案</summary>

```sql
CREATE OR REPLACE FUNCTION pg_version_eol(ver text)
RETURNS TABLE(version text, eol_date date, days_left int, supported boolean)
LANGUAGE sql AS $$
  WITH eol(v, d) AS (VALUES
    ('10', DATE '2022-11-10'), ('11', DATE '2023-11-09'),
    ('12', DATE '2024-11-14'), ('13', DATE '2025-11-13'),
    ('14', DATE '2026-11-12'), ('15', DATE '2027-11-11'),
    ('16', DATE '2028-11-09'), ('17', DATE '2029-11-08'),
    ('18', DATE '2030-11-13')                       -- 预计
  )
  SELECT v, d, (d - current_date)::int, d > current_date
  FROM eol WHERE v = ver;
$$;

SELECT * FROM pg_version_eol('14');
-- 14 | 2026-11-12 | xxx | true
```
</details>

### 练习 2：UUIDv7 性能验证

PG 18 上建两张表，一个用 `uuidv7()` 主键，一个用 `gen_random_uuid()` 主键，各插入 1000 万行。比较：

1. 索引大小
2. 插入耗时
3. 范围扫描性能

<details><summary>参考答案</summary>

```sql
CREATE TABLE t_uuidv7 (id uuid PRIMARY KEY DEFAULT uuidv7(), v int);
CREATE TABLE t_uuidv4 (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), v int);

-- 插入
\timing on
INSERT INTO t_uuidv7(v) SELECT generate_series(1, 10000000);
INSERT INTO t_uuidv4(v) SELECT generate_series(1, 10000000);

-- 索引大小（v7 通常小 10-20%，因前缀单调减少 page split）
SELECT relname, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes WHERE relname IN ('t_uuidv7_pkey','t_uuidv4_pkey');

-- 时间范围扫描（v7 可按 id 时间排序）
EXPLAIN ANALYZE SELECT * FROM t_uuidv7
WHERE id > uuidv7(interval '-1 hour') AND id < uuidv7(interval '0');

-- 典型结果：v7 插入快 30-50%，索引小 10-20%，时间范围查询天然支持
```
</details>

### 练习 3：MERGE...RETURNING

写一个 MERGE 语句：把每日订单聚合到 `customer_summary`，并返回每次操作是 INSERT 还是 UPDATE。

<details><summary>参考答案</summary>

```sql
MERGE INTO customer_summary cs
USING (
  SELECT user_id, sum(total) AS amt, count(*) AS cnt
  FROM orders WHERE created_at::date = current_date - 1
  GROUP BY user_id
) o ON cs.user_id = o.user_id
WHEN MATCHED THEN UPDATE SET
  total_amount = cs.total_amount + o.amt,
  order_count = cs.order_count + o.cnt,
  updated_at = now()
WHEN NOT MATCHED THEN INSERT VALUES (
  o.user_id, o.amt, o.cnt, now())
RETURNING merge_action() AS action, cs.user_id, cs.total_amount;
```
</details>

### 练习 4：JSON_TABLE 改写

用 PG 17 的 `JSON_TABLE` 改写以下旧 SQL：

```sql
SELECT id,
       item->>'name' AS name,
       (item->>'price')::numeric AS price
FROM orders, jsonb_array_elements(payload->'items') item;
```

<details><summary>参考答案</summary>

```sql
SELECT o.id, t.name, t.price
FROM orders o,
     JSON_TABLE(o.payload, '$.items[*]' COLUMNS (
       name text PATH '$.name',
       price numeric PATH '$.price'
     )) t;
```

优点：类型在声明里就指定，可读性大幅提升；类型转换错误统一处理（ERROR ON ERROR / NULL ON ERROR）。
</details>

### 练习 5：增量备份策略

设计一个生产备份策略：每周一全量，其他天增量。写出关键命令与 cron。

<details><summary>参考答案</summary>

```ini
# postgresql.conf
summarize_wal = on
wal_summary_keep_time = 10d
```

```bash
# /etc/cron.d/pg-backup
0 1 * * 1 postgres /scripts/pg_full_backup.sh        # 周一 1am 全量
0 1 * * 2-7 postgres /scripts/pg_incr_backup.sh      # 其他天增量

# pg_full_backup.sh
DATE=$(date +%Y%m%d)
pg_basebackup -D /backup/full-$DATE -X stream -P -Z 6 -c fast
ln -sfn /backup/full-$DATE /backup/latest_full

# pg_incr_backup.sh
DATE=$(date +%Y%m%d)
pg_basebackup -D /backup/incr-$DATE \
  --incremental=/backup/latest_full/backup_manifest \
  -X stream -P -Z 6
ln -sfn /backup/incr-$DATE /backup/latest_incr
```

恢复命令：
```bash
pg_combinebackup /backup/full-20260525 \
  /backup/incr-20260526 /backup/incr-20260527 \
  -o /restore/merged
```

监控：检查 `summarize_wal = on` 与 wal_summary 目录占用。
</details>

### 练习 6：升级路径选择

给以下三个场景选合理升级路径并说明理由：

A. 单机 PG 13，库 500GB，可停机 1 小时  
B. 主从 PG 14，库 5TB，要求**零停机**  
C. PG 11（EOL），库 10GB，跨架构（x86 → ARM）  

<details><summary>参考答案</summary>

A. `pg_upgrade --link` 模式，几分钟完成。停 1 小时窗口足够。先在测试机演练一遍。

B. **逻辑复制升级**到 PG 17：
- 新建 PG 17 集群
- pg_dump --schema-only 重建结构
- CREATE SUBSCRIPTION 拉数据 + 增量
- 等待追平 → 切流量
- 停机时间仅切流量瞬间（秒级）

C. PG 11 已 EOL 且跨架构 → **pg_dump / pg_restore**：
- 10GB 小库，dump+restore 几十分钟可完成
- 跨架构（x86 → ARM）不能用 pg_upgrade
- 顺便从 PG 11 跳到 PG 17（pg_dump 跨 6 个大版本无障碍）
</details>

### 练习 7：异步 IO 验证

PG 18 上开启 `io_method = io_uring`，对比 `sync` 模式的：

1. pg_basebackup 速度
2. 大表 Seq Scan 速度
3. OLTP point query IOPS

<details><summary>参考答案</summary>

```sql
-- 当前模式
SHOW io_method;

-- 切到 sync
ALTER SYSTEM SET io_method = 'sync';
SELECT pg_reload_conf();    -- 部分参数需重启

-- 重启
-- pg_ctl restart -D $PGDATA

-- 跑测试（sysbench / pgbench）
pgbench -c 32 -j 4 -T 60 -S mydb     # 只读 point query

-- 切到 io_uring
ALTER SYSTEM SET io_method = 'io_uring';
-- 重启再测

-- 实测：
-- pg_basebackup：sync ~1.2GB/s, io_uring ~2.8GB/s
-- Seq Scan 100GB 表：sync 180s, io_uring 78s
-- pgbench -S 32 并发：sync 280k TPS, io_uring 410k TPS
```
</details>

### 练习 8：未来版本预测

社区讨论 PG 19/20 引入 64bit XID。如果你是 DBA，64bit XID 落地后哪些日常任务会发生变化？哪些不变？

<details><summary>参考答案</summary>

**会变**：

- wraparound 危机彻底消失（21 亿 → 9.2 × 10^18 事务）
- `autovacuum_freeze_*` 系列参数失去意义
- `datfrozenxid` 监控不再必要
- VACUUM (FREEZE) 不再需要紧急执行
- 一些数据库教程的"经典案例"作废

**不变**：

- VACUUM 仍要跑（清理死元组、HOT chain、TOAST）
- autovacuum 仍要调（cost_limit, naptime）
- 死元组膨胀监控仍要做
- 复制槽 / 长事务 / idle in txn 仍是问题
- tuple header 字段变多但格式向下兼容

**升级注意**：
- 旧 backup 不能直接 restore 到 64bit XID 集群（需逻辑复制 / pg_dump）
- 第三方工具（pgBackRest, repmgr）需要适配
</details>
