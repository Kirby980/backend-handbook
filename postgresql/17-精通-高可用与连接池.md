## 引言：HA 与连接池为什么放在一起讲

PostgreSQL 的高可用（HA）和连接池（Connection Pool）是两件事，但生产部署里几乎永远绑在一起出现。原因：

- **HA 解决"主库挂了怎么办"**：探活、选举、故障切换、防 split-brain
- **连接池解决"backend 太重 + 连接太多"**：PG 每个连接 fork 一个进程，10MB+ 常驻；几千连接直接 OOM
- 切换后应用怎么找到新主？大多走 **连接池/代理层**统一抽象端点，应用只连 pgbouncer/HAProxy，不感知后端切换

这章把两件事讲透，从 Patroni 这种"标准答案"到 CloudNativePG（K8s 时代）、从 PgBouncer 老牌到 pgcat（Rust 2024 兴起）。

读完本章你应该能：

- 区分 HA 三大要素：探活、选举、防脑裂
- 配置一个 3 节点 Patroni + etcd + HAProxy + PgBouncer 集群
- 解释 PgBouncer 三种 pool_mode 的差异以及为什么 transaction 是主流
- 知道 PG 17 protocol-level prepared statement 对池化的影响
- 用 CloudNativePG 在 K8s 上部署 PG 集群
- 设计跨机房 HA + 读写分离 + 优雅故障切换的端到端拓扑

## 第 1 章：HA 的三大核心问题

### 1.1 探活（Liveness）

"主库还活着吗？" 看似简单：

- TCP ping？端口开着但 PG hang 死不响应。
- `SELECT 1`？连接数满了根本连不上。
- 进程存在？kernel 还能调度但磁盘 IO 100% block。

实际探活要多维度：

```
1. TCP 连通性（端口可连）
2. 应用层探活（SELECT 1 在某超时内返回）
3. 复制状态（standby 是否在追）
4. WAL 写入是否前进（pg_current_wal_lsn 变化）
5. 文件系统能写
```

任意一个失败都可能是真死，也可能是误判。**探活算法越激进越容易误切，越保守越延迟切换**——HA 设计的核心权衡。

### 1.2 选举（Leader Election）

主挂了，多个备库谁来接？必须**唯一性确认**——选出来的就是新主，没有第二个。

技术手段：

- **Raft / Paxos**：基于 etcd / consul / zookeeper 等分布式协调存储（DCS）
- **静态优先级**：repmgr / 早期 pg_auto_failover 用预设优先级 + 半自动
- **K8s lease**：CloudNativePG 用 K8s lease API 替代独立 DCS

需要"多数派可达"——3 节点至少 2 节点能通信才能选举，避免脑裂。

### 1.3 防脑裂（Split-Brain Prevention）

最危险的场景：网络分区导致两个节点都自认为是主，同时接受写入。后果：数据冲突无法自动合并，必须人工选一边丢数据。

防护手段（缺一不可）：

| 手段 | 原理 |
|---|---|
| **DCS quorum** | 选举必须多数派同意；少数派一方不能 promote |
| **Fencing**（STONITH） | 物理隔离旧主：拔电、ipmi 重启、网络封禁 |
| **Watchdog** | 主库进程检测自己异常时主动 demote/kill |
| **VIP/Proxy 切换** | 入口流量统一从一个层进，切换时只有一个能拿到 |

Patroni 同时用 DCS quorum + watchdog + 主动 demote，是工业级标杆。

### 1.4 RTO / RPO

| 指标 | 含义 | 典型值 |
|---|---|---|
| **RTO** Recovery Time Objective | 故障后多久恢复服务 | 异步：1-3 分钟；同步：30s-1min |
| **RPO** Recovery Point Objective | 故障最多丢多少数据 | 异步：可能 N 秒；同步：0（理论上） |

异步复制 RTO 短但 RPO > 0；同步 RPO=0 但故障切换会停顿（等不到同步备库 ACK）。生产常配 **同城 sync + 异地 async**。

## 第 2 章：Patroni —— 事实标准

### 2.1 Patroni 是什么

Patroni 是 Python 编写的 PostgreSQL HA 模板，作者 Zalando（开源后社区维护）。它不重新发明 WAL/复制——直接管理原生 streaming replication；它解决的只是 **谁是主、什么时候切、切给谁**。

```
┌──────────────────────────────────────────────────────┐
│            DCS（etcd / consul / zookeeper / k8s）    │
│   存放：current leader、members、cluster config       │
└────────────┬───────────────┬─────────────┬───────────┘
             │               │             │
       ┌─────┴───┐     ┌─────┴───┐   ┌─────┴───┐
       │ patroni │     │ patroni │   │ patroni │
       │   +     │     │   +     │   │   +     │
       │ postgres│     │ postgres│   │ postgres│
       │  (主)   │     │  (备)   │   │  (备)   │
       └─────────┘     └─────────┘   └─────────┘
```

每个节点跑一个 patroni 进程：

- 启动/停止本地 PG
- 周期性向 DCS 续约（leader lease）
- 监控本地健康度
- 主：续约 leader key
- 备：监听 leader key，过期就发起选举

### 2.2 DCS 选哪个

| DCS | 特点 | 选用场景 |
|---|---|---|
| **etcd** | Go 实现，CNCF，K8s 同款 | 90% Patroni 用户首选 |
| **Consul** | Hashicorp，DNS 友好 | 已有 Consul 生态 |
| **ZooKeeper** | Java，老牌 | 已有 Kafka/Hadoop ZK |
| **Kubernetes** | 直接用 K8s API（lease + configmap） | K8s 环境内部署 |
| **Exhibitor** | ZK 管理工具 | 几乎没人用了 |

etcd 一般 3 或 5 节点：

```
etcd1, etcd2, etcd3  (3 节点 quorum = 2)
```

5 节点容忍 2 节点同时挂；3 节点容忍 1 节点挂。**永远奇数**避免脑裂。

### 2.3 配置文件示例

`/etc/patroni/patroni.yml`：

```yaml
scope: pgcluster1
namespace: /service/
name: pg1

restapi:
  listen: 0.0.0.0:8008
  connect_address: 10.0.0.1:8008

etcd3:
  hosts: etcd1:2379,etcd2:2379,etcd3:2379

bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    retry_timeout: 10
    maximum_lag_on_failover: 1048576  # 1MB
    synchronous_mode: true
    synchronous_mode_strict: false
    postgresql:
      use_pg_rewind: true
      use_slots: true
      parameters:
        wal_level: replica
        hot_standby: "on"
        max_wal_senders: 10
        max_replication_slots: 10
        wal_keep_size: 1GB
        max_slot_wal_keep_size: 100GB
        synchronous_commit: "on"

  initdb:
  - encoding: UTF8
  - data-checksums

  pg_hba:
  - host replication replicator 10.0.0.0/24 scram-sha-256
  - host all all 10.0.0.0/24 scram-sha-256

  users:
    admin:
      password: admin
      options:
        - createrole
        - createdb

postgresql:
  listen: 0.0.0.0:5432
  connect_address: 10.0.0.1:5432
  data_dir: /var/lib/postgresql/18/main
  bin_dir: /usr/lib/postgresql/18/bin
  authentication:
    replication:
      username: replicator
      password: replpw
    superuser:
      username: postgres
      password: pgpw

  parameters:
    unix_socket_directories: /var/run/postgresql

watchdog:
  mode: required             # 推荐：requires watchdog 才能 promote
  device: /dev/watchdog
  safety_margin: 5

tags:
  nofailover: false
  noloadbalance: false
  clonefrom: false
  nosync: false
```

关键点：

- `ttl: 30`、`loop_wait: 10`、`retry_timeout: 10`：DCS 心跳和重试时间——理论 RTO ≈ ttl
- `synchronous_mode: true`：开启 Patroni 管理的 sync 模式
- `maximum_lag_on_failover: 1MB`：备库 lag 超过这个不参与选举
- `watchdog: mode: required`：开启 Linux watchdog，hang 死直接重启 → 防脑裂
- `use_pg_rewind: true`：自动用 pg_rewind 把旧主接回新主

### 2.4 操作 patronictl

```bash
# 集群状态
patronictl -c /etc/patroni/patroni.yml list

# 输出
+ Cluster: pgcluster1 ------+----+-----------+
| Member | Host     | Role    | State   | TL | Lag in MB |
+--------+----------+---------+---------+----+-----------+
| pg1    | 10.0.0.1 | Leader  | running | 12 |           |
| pg2    | 10.0.0.2 | Sync    | running | 12 |         0 |
| pg3    | 10.0.0.3 | Replica | running | 12 |         5 |
+--------+----------+---------+---------+----+-----------+

# 手动切换（无故障，运维窗口用）
patronictl switchover --leader pg1 --candidate pg2

# 强制故障切换（leader 真挂）
patronictl failover

# 重置某节点（reinit）
patronictl reinit pgcluster1 pg3

# 编辑集群配置
patronictl edit-config
```

### 2.5 故障切换过程

```
T0:  pg1 leader (TL 12)，pg2 sync standby，pg3 async standby
T1:  pg1 进程被 kill
T2:  pg1 上的 patroni 检测到 PG 死 → 试图重启，失败
T3:  pg1 不再续约 leader key
T10: leader key TTL 到期，pg2/pg3 上的 patroni 收到失效通知
T11: pg2（sync 优先级高）发起选举，写 DCS：candidate=pg2
T12: pg2 确认自己 lag 满足条件 + watchdog OK → 升级
T13: pg2 promote（pg_ctl promote），TL → 13
T14: 应用通过 HAProxy 重连 → 流量到 pg2
T15: pg3 重新接 pg2 为主，可能需要 pg_rewind
T120: pg1 恢复，patroni 启动它，确认自己不是 leader，pg_rewind 接回 pg2
```

整个过程典型 30-60 秒（取决于 ttl/loop_wait 设置）。

## 第 3 章：其他 HA 方案对比

### 3.1 repmgr

老牌方案（2ndQuadrant，现 EDB）。比 Patroni 早。

特点：
- 不强制 DCS，用 PG 自身存元数据（`repmgr` schema）
- 故障切换可半自动（手动确认）或全自动（`repmgrd`）
- 缺少 watchdog / fencing 内建，靠人工或脚本

何时选：legacy 项目；管理员熟悉 repmgr；不接受额外 etcd。

何时不选：新项目、追求强一致防脑裂。Patroni 已是主流。

### 3.2 pg_auto_failover

Citus（已被 Microsoft 收购）出品。核心思路：把 HA 责任放进一个独立的 **monitor** 节点。

```
Monitor (一个独立 PG 实例)
   │
   ↓ 监督
Primary ←——→ Standby
```

特点：
- 部署简单，3 节点（含 monitor）即可
- monitor 本身是单点（可以再做主备，但复杂）
- 适合中小规模 / Citus 集群

何时选：你已经在用 Citus；想要轻量；接受 monitor 这个额外组件。

### 3.3 stolon

Sorint.lab 出品，Go 实现。早期 K8s 上的方案。

```
stolon-sentinel  (决策)
stolon-keeper    (管 PG)
stolon-proxy     (流量入口)
```

特点：proxy 集成在套件里。一度流行，但 2022 后社区活跃度下降，现在让位给 CloudNativePG。

### 3.4 CloudNativePG（CNPG）

K8s 时代的新标准。CNCF Sandbox（2024）→ Incubation 路上。EnterpriseDB 主导。

特点：
- 纯 K8s Operator，没有外部 DCS（用 K8s lease）
- 主备一组 StatefulSet，按 Operator 调度
- 备份/恢复集成 `barman` / 物理备份到 S3
- 滚动升级、读写分离 Service 都内置
- 支持 PgBouncer Pooler CR

简单清单：

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: app-pg
spec:
  instances: 3
  postgresql:
    parameters:
      max_connections: "500"
      shared_buffers: "8GB"
  bootstrap:
    initdb:
      database: app
      owner: appuser
  storage:
    size: 200Gi
    storageClass: fast-ssd
  backup:
    barmanObjectStore:
      destinationPath: s3://my-backups/app-pg/
      s3Credentials:
        accessKeyId:
          name: aws-creds
          key: ACCESS_KEY_ID
        secretAccessKey:
          name: aws-creds
          key: SECRET_ACCESS_KEY
    retentionPolicy: "30d"
```

部署：

```bash
kubectl apply -f cluster.yaml
```

Operator 自动：
- 创建 3 个 PG pod（1 主 2 备）
- 配置 streaming replication + slot
- 创建 `app-pg-rw`（写）和 `app-pg-ro` / `app-pg-r`（读）Service
- 配置 S3 备份 + WAL 归档
- 滚动升级时自动 switchover

故障切换：K8s 重启失败 pod，Operator 检测主失败 → 选最新备 promote → 切 Service 指向。RTO 通常 < 30s。

### 3.5 选型决策树

```
是否 K8s 环境？
├── 是 ──→ CloudNativePG（首选）
│         或 Zalando postgres-operator（Patroni-based）
│         或 Crunchy PGO（商业支持）
└── 否 ──→ 规模？
          ├── 大型 / 强一致 ──→ Patroni + etcd + HAProxy + PgBouncer
          ├── 中型 / 简单 ──→ pg_auto_failover
          └── 传统 / legacy ──→ repmgr
```

## 第 4 章：流量入口 —— VIP / HAProxy / DNS

故障切换发生后，应用怎么知道新主在哪？三种思路：

### 4.1 VIP（Virtual IP）漂移

```
应用 → 10.0.0.100（VIP） → 实际指向当前主库
```

切换时 VIP 从 pg1 漂到 pg2（用 keepalived / pcs / awsenidetach + attach）。

- 优点：应用 0 改动
- 缺点：跨子网难、云上不方便、ARP 缓存可能要等

### 4.2 HAProxy + Patroni REST 探活

Patroni 每个节点暴露 HTTP `GET /` 返回 200 表示是主、503 表示是备/挂。

```
frontend pg_write
    bind *:5432
    default_backend pg_primary

backend pg_primary
    option httpchk GET /
    http-check expect status 200
    server pg1 10.0.0.1:5432 check port 8008
    server pg2 10.0.0.2:5432 check port 8008
    server pg3 10.0.0.3:5432 check port 8008

frontend pg_read
    bind *:5433
    default_backend pg_replicas

backend pg_replicas
    balance leastconn
    option httpchk GET /replica
    http-check expect status 200
    server pg1 10.0.0.1:5432 check port 8008
    server pg2 10.0.0.2:5432 check port 8008
    server pg3 10.0.0.3:5432 check port 8008
```

- 应用连 `haproxy:5432` 写、`haproxy:5433` 读
- Patroni 切换后 HAProxy 几秒内识别到新主
- HAProxy 本身要双活（VRRP / NLB）

### 4.3 Consul + consul-template

Consul 服务发现 + consul-template 动态生成 HAProxy/PgBouncer 配置。

### 4.4 K8s Service

CloudNativePG 自动创建 `cluster-rw`、`cluster-ro` Service，主备切换时 Endpoint 自动更新。应用通过 Service DNS 名称访问，完全感知不到切换。

## 第 5 章：连接池的必要性

### 5.1 PostgreSQL 连接成本

每个 PG 连接：

- **一个 backend 进程**（fork from postmaster）
- 私有内存约 5-15 MB（取决于 work_mem 等）
- catalog cache、prepared statement cache、planner 状态等

1000 个连接 → 10-15 GB 内存常驻 → 还没开始处理业务 RAM 就吃光了。

PG 16/17 持续优化连接成本，但相比 MySQL 仍重。

### 5.2 短连接 + 高并发的问题

PHP/CGI 时代每请求一个连接，几千 QPS 就是几千连接/秒：

- fork 进程几十毫秒
- 应用要复用难（线程模型不友好）
- PG 直接被 fork 风暴打死

Node.js / Go 长连接好一些，但单个 Pod 一般也只能维持几十连接；K8s 几百 Pod 直接乘出几万连接 → PG 撑不住。

### 5.3 连接池的本质

**让多个客户端复用一组到 PG 的物理连接**：

```
[App pod 1] ──┐
[App pod 2] ──┼──→ [PgBouncer]  ──→  [PG (50 backend)]
[App pod 3] ──┘     1000 client     50 server
              client conn          server conn
```

PgBouncer 接收 1000 个客户端连接（轻量级，每个几 KB），底下只维持 50 个到 PG 的真实连接。

## 第 6 章：PgBouncer 深入

### 6.1 三种 pool_mode

```ini
# pgbouncer.ini
pool_mode = transaction   # session / transaction / statement
```

| 模式 | 一个 server conn 服务一个 client 的范围 | 适用 | 限制 |
|---|---|---|---|
| **session** | 整个 session（连接到断开） | 短连接、不能跨连接的功能 | 复用率低（≈ 没池） |
| **transaction** | 一个事务（BEGIN→COMMIT） | **主流**，绝大多数 web 应用 | 不支持 session-level 状态（LISTEN/NOTIFY、SET、prepared stmt 有限制） |
| **statement** | 一条语句 | 极端只读、不支持事务 | 不能用事务！autocommit only |

#### transaction 模式不支持的功能

- `LISTEN` / `NOTIFY`（依赖 session 持续）
- session 级 `SET` 参数（事务结束就还原了）
- 客户端的 prepared statement（不同事务可能落到不同 server conn）
- `WITH HOLD` cursor、`temp table`（除非 ON COMMIT DROP）
- session-level advisory lock

#### PG 17 + PgBouncer 1.21+：协议级 prepared statement

历史上 transaction 模式不能用 prepared statement，是因为 PG 的 prepared statement 绑定在 session：第二个事务用不同 server conn 时找不到。

PgBouncer 1.21（2023）开始内置支持：拦截 `PARSE` / `BIND` / `EXECUTE`，跨 server conn 透明 re-PARSE。配置 `max_prepared_statements`。

PG 17 协议层进一步配合：支持更细粒度的 prepared statement 元数据传递，让池化更好兼容。

**实际效果**：现在 PgBouncer transaction 模式下用 prepared statement 大体可行（开 `max_prepared_statements = N`），驱动支持也在改进（pgx、JDBC）。

### 6.2 部署模式

```
模式 A：Sidecar（每应用 Pod 一个 PgBouncer）
   [App + PgBouncer container]  ──→  PG
   优点：网络近、隔离好
   缺点：复用率低（每个 Pod 自己的连接池）

模式 B：中央池（一个共享 PgBouncer 集群）
   [App pods] ──→ [PgBouncer pool (HA)]  ──→  PG
   优点：复用率高（全局视角）
   缺点：网络多一跳、PgBouncer 本身是瓶颈

模式 C：Per-app（按应用分组）
   [App A pods] ──→ [PgBouncer A]  ──→  PG
   [App B pods] ──→ [PgBouncer B]  ──→  PG
   优点：故障隔离
   缺点：管理复杂
```

主流：**中央池 HA**（2-4 个 PgBouncer 实例 + LB 在前）。K8s 上 CloudNativePG 的 Pooler CR 帮你跑这个。

### 6.3 关键参数

```ini
[databases]
app = host=pg-rw.example.com port=5432 dbname=app

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt

pool_mode = transaction

max_client_conn = 10000          # 接受多少客户端连接
default_pool_size = 25           # 每 (db, user) 对维持多少 server 连接
min_pool_size = 5                # 最少保持几个空闲（预热）
reserve_pool_size = 5            # 备用池（高负载时启用）
reserve_pool_timeout = 3         # 客户端等多久后启用备用池

server_idle_timeout = 600        # server conn 空闲多久关
server_lifetime = 3600           # server conn 最长存活（强制轮换）
query_timeout = 0                # 0=不超时（业务自己控）
query_wait_timeout = 120         # 等池的最大时间

max_prepared_statements = 200    # PgBouncer 1.21+ 协议级 prepared
ignore_startup_parameters = extra_float_digits,search_path

stats_period = 60
log_connections = 0              # 关掉减少日志
log_disconnections = 0
```

`default_pool_size` 调优经验：

- `default_pool_size` 大致设为 PG `max_connections` ÷ 用户数
- PG `max_connections` 一般 200-500 已足够（连接池在前，PG 不需要很多直接连接）
- 单个 backend 几乎能跑满一个 CPU，所以 pool size ≈ CPU 核数 × 1.5-2

### 6.4 监控

连进 PgBouncer 的 `pgbouncer` 库（特殊管理库）：

```bash
psql -h pgbouncer -p 6432 pgbouncer

pgbouncer=# SHOW POOLS;
pgbouncer=# SHOW STATS;
pgbouncer=# SHOW CLIENTS;
pgbouncer=# SHOW SERVERS;
pgbouncer=# RELOAD;
```

关键指标：

- `cl_waiting`：等池的客户端数 > 0 长时间 = 池子不够
- `sv_used` / `sv_idle`：server 使用 vs 空闲

### 6.5 PgBouncer 的局限

- C 单线程（PgBouncer 默认）—— 高吞吐场景 CPU 单核瓶颈
- 没有内置 HA（多实例 + 外部 LB 自己搞）
- 不支持读写分离（要在前面再加一层）
- prepared statement 历史包袱

PgBouncer 1.20+ 引入实验性多进程模式 / 提升性能；社区有 fork 在做。

## 第 7 章：新一代连接池

### 7.1 pgcat（Rust）

2022 年开源，Instacart 推动，2024 后社区活跃。

特点：

- **Rust 异步多线程**：吞吐显著高于 PgBouncer
- **内置读写分离**：通过 SQL 注释路由
- **内置分片**（试验性 sharding 路由）
- **故障切换感知**：可探活后端，主备切换无缝
- 协议兼容 PostgreSQL（应用无改动）

配置示例：

```toml
[general]
host = "0.0.0.0"
port = 6432
admin_username = "admin"
admin_password = "..."

[pools.app]
pool_mode = "transaction"
default_role = "any"
query_parser_enabled = true        # 解析 SQL 自动路由
primary_reads_enabled = false
sharding_function = "pg_bigint_hash"

[pools.app.users.0]
username = "appuser"
password = "..."
pool_size = 50

[pools.app.shards.0]
servers = [
    ["pg-primary", 5432, "primary"],
    ["pg-replica-1", 5432, "replica"],
    ["pg-replica-2", 5432, "replica"],
]
database = "app"
```

应用可以在 SQL 前加注释：

```sql
/* role: primary */ INSERT INTO orders ...
/* role: replica */ SELECT * FROM orders ...
```

不加则按 `default_role` 走。

何时选：
- 高吞吐（>100k QPS）让 PgBouncer 单核 CPU 100%
- 需要内置读写分离 + 自动路由
- Rust 友好的运维团队

### 7.2 Odyssey（Yandex）

Yandex 出品，C++ 多线程。性能介于 pgbouncer 和 pgcat 之间，俄国/欧洲项目常见。

特点：内置多线程、TLS 良好、稳定。配置和 PgBouncer 类似。

### 7.3 PgPool-II（不推荐做纯连接池）

老牌 PgPool-II 想做"连接池 + 读写分离 + 负载均衡 + 自动故障切换"——啥都做导致复杂、bug 多。生产用它做连接池不如 PgBouncer + 单独 HA 工具组合。

### 7.4 应用内池（不要重新发明）

Go 的 pgxpool、Java 的 HikariCP 都是"应用内连接池"——它管的是 app↔PgBouncer 的连接，仍然需要 PgBouncer 管 PgBouncer↔PG 的连接。

```
应用 ─[HikariCP / pgxpool 池: 20]─→ [PgBouncer 池: 25] ─→ PG
```

两层池都有意义：应用内池避免 socket 反复创建，PgBouncer 池跨 Pod 共享后端连接。

## 第 8 章：读写分离

### 8.1 客户端（应用）层

应用自己分两套连接：

```go
writeDB, _ := pgxpool.New(ctx, "host=pg-rw ...")
readDB, _  := pgxpool.New(ctx, "host=pg-ro ...")
```

业务代码显式选：

```go
user := readDB.QueryRow(...)  // 读
writeDB.Exec("INSERT ...")     // 写
```

优点：精确控制；可以做"读自己写过的数据走主"逻辑。
缺点：业务代码侵入；新人容易写错。

### 8.2 中间件层

PgBouncer 本身不支持，靠在前面再加一层（HAProxy 按 5432/5433 区分、pgcat 按注释路由、ProxySQL for PG）。

```
应用 ──→ Proxy（按 BEGIN/SELECT 判断）──→ 主 / 备
```

优点：业务零改动。
缺点：复杂度增加、SQL 解析不全（COMMIT 后是否切回主等）；事务内永远走主比较安全。

### 8.3 复制延迟带来的语义问题

经典 bug："我下单后立刻刷新看不到我的订单" —— 写主、读到了还没追上的备库。

解决：

- **写后短时间内强制读主**（session sticky N 秒）
- **使用 LSN 同步**：写完拿到 `pg_current_wal_lsn`，读时备库等 LSN 追到再返回（PG `synchronous_commit = remote_apply` + 应用配合）
- **关键场景一律读主**

## 第 9 章：完整生产拓扑

### 9.1 同城 1 主 2 备 + 异地 1 备

```
        [App pods (K8s)]
              │
        ┌─────┴─────┐
        ↓           ↓
   [HAProxy:5432]  [HAProxy:5433]
     写流量          读流量
        │           │
        ↓           ↓
   ┌──────────┴───────────┐
   │   PgBouncer cluster  │   (transaction mode)
   │   3 实例 + L4 LB     │
   └─────────┬────────────┘
             ↓
     ┌───────┴───────┐
     │   Patroni     │
     │ 3 节点集群    │ ──→ etcd 3 节点（独立部署）
     │  + watchdog   │
     └───────┬───────┘
             │
   ┌─────────┼─────────┐
   ↓         ↓         ↓
[pg1 主] [pg2 同步] [pg3 异步]  ← 同城 DC1
   │
   └──→ [pg4 异步] ← 异地 DC2（容灾）
   │
   └──→ WAL → S3 (wal-g 归档)
```

参数总结：

```ini
# pg1 主
synchronous_standby_names = 'ANY 1 (pg2, pg3)'    # 同城至少 1 个 ACK
synchronous_commit = on
wal_level = replica
archive_command = 'wal-g wal-push %p'
max_wal_size = 16GB
checkpoint_timeout = 15min
max_slot_wal_keep_size = 200GB
```

```ini
# PgBouncer
pool_mode = transaction
max_client_conn = 5000
default_pool_size = 25
reserve_pool_size = 10
```

```yaml
# Patroni（关键部分）
synchronous_mode: true
synchronous_mode_strict: false
maximum_lag_on_failover: 1048576
watchdog:
  mode: required
```

### 9.2 RTO/RPO 分析

| 场景 | RTO | RPO |
|---|---|---|
| pg1 主进程崩溃 | 30-45s（Patroni TTL + promote） | 0（sync 备库已 ACK） |
| pg1 整机宕（含磁盘） | 30-45s | 0 |
| 同城整 DC 失联 | 5-15min（人工干预异地 promote） | 几秒到几分钟（async lag） |
| 误删数据 | 看备份恢复（30 分钟到几小时） | 看 PITR 精度（秒级） |

## 第 10 章：故障演练

每季度演练（生产前先在 staging 跑）：

| 场景 | 操作 | 期望 |
|---|---|---|
| 主进程 kill | `pkill -9 postgres` on pg1 | 30s 内切到 pg2 |
| 主机网络隔离 | `iptables -A INPUT -j DROP` on pg1 | Patroni watchdog 触发 → 主动 demote |
| 同步备库挂 | 停 pg2 | `synchronous_standby_names = 'ANY 1 (pg2,pg3)'` 切到 pg3 sync，写入不卡 |
| etcd 整集群挂 | 停 etcd | 现有 leader 继续工作（只读 fallback 或继续写到 lease 到期）；新选举不可能；切回 etcd 后恢复 |
| PgBouncer 全挂 | 停所有 PgBouncer | 应用报错，HAProxy 显示 backend 全 down；快速恢复 |
| 整 DC 失联 | 模拟跨 DC 网络断 | 异地 standby 不该被升级（quorum 不足），人工介入决定 |

## 生产实践

### 实践 1：PgBouncer pool size 调优

公式：

```
default_pool_size ≈ CPU 核数 × 1.5 ~ 2
total server conn ≈ default_pool_size × 用户数 ≤ PG max_connections × 0.7
```

例：32 核 PG，`max_connections=400`：

- 单数据库 default_pool_size = 48
- 8 个用户/库 ⇒ 48 × 8 = 384，留 16 余量给监控/超管

监控：`SHOW POOLS;` 看 `cl_waiting` 是否长期 > 0，是的话提高 pool size 或拆库。

### 实践 2：prepared statement 在 PgBouncer transaction 模式

JDBC（HikariCP）+ PgBouncer 1.21+ 配置：

```properties
# pgbouncer.ini
max_prepared_statements = 200
```

```properties
# HikariCP DataSource
prepareThreshold=0       # 不用客户端 PREPARE（避开兼容问题）
# 或者
prepareThreshold=5       # 客户端自动 PREPARE 阈值
```

实测在 PG 17 + PgBouncer 1.22 + JDBC 42.7 上能正常 PREPARE/EXECUTE，规避 transaction 模式历史限制。

### 实践 3：滚动升级

CloudNativePG `primaryUpdateStrategy: unsupervised`：

- 升级备库 → switchover（自动）→ 升级旧主
- 业务体验：一次几秒的连接中断
- 失败自动回滚

Patroni：

```bash
# 1. 升级 pg2 的 PG 版本（minor）
systemctl stop patroni
apt upgrade postgresql-18
systemctl start patroni
# pg2 起来后追上主库

# 2. switchover 到 pg2
patronictl switchover --leader pg1 --candidate pg2

# 3. 升级 pg1
# 4. switchover 回 pg1（如果有偏好）
```

### 实践 4：应用层重试

故障切换 30-45s 内有连接错误，应用必须重试：

```go
func WithRetry(fn func() error) error {
    backoff := []time.Duration{100*ms, 500*ms, 1*s, 2*s, 5*s, 10*s}
    for _, d := range backoff {
        if err := fn(); err == nil {
            return nil
        } else if !isTransient(err) {
            return err
        }
        time.Sleep(d)
    }
    return errors.New("exhausted retries")
}
```

判断 transient：连接被关、`server closed the connection`、`canceling statement due to ...`、`SQLSTATE 57P03`（不可用）等。

## 陷阱清单

1. **PgBouncer transaction 模式用了 `SET` 不带 BEGIN** —— SET 在事务结束就失效，到下个事务可能用不同 server conn，配置丢。改用 connection-string 的 `options`。
2. **PgBouncer 不知道 prepared statement**（旧版本）—— 应用客户端开 prepared，跨事务路由失败。1.21+ 解决；旧版本要 `prepareThreshold=0`。
3. **`max_client_conn` 远大于 `max_connections`** —— PgBouncer 接受 10000 客户端但底层 PG 只能 200，正常；但要保证 pool size × user 不超 PG 限。
4. **Patroni `synchronous_mode_strict: true`** —— sync 备库全挂时主库写入会 hang。生产一般 false 让它降级。
5. **etcd 部署在 PG 同机** —— 同机故障一起挂，HA 失效。**etcd 独立 3 节点**。
6. **没有 watchdog** —— PG 进程假死时 Patroni 也可能假死 → 不 demote → split-brain。生产强制 `watchdog: required`。
7. **HAProxy 探活间隔过短** —— 100ms 探一次把 Patroni REST 打爆。建议 2-5s 间隔。
8. **应用没重试** —— 切换 30s 期间报错直接抛给用户。应用必须有指数退避重试。
9. **K8s pod 设置了过小的 `terminationGracePeriodSeconds`** —— PG pod 被 kill -9，下次启动 crash recovery 时间长。设大点（60s+）。
10. **连接池在 PG 同机** —— PG OOM 把 PgBouncer 一起带挂。建议分开。
11. **CloudNativePG `instances: 2`** —— 2 节点没法 quorum。**至少 3 个**。
12. **共享 superuser 给应用** —— 出了问题排查权限攻击面巨大。每个应用独立 role + 最小权限。
13. **pg_rewind 失败**（无 wal_log_hints / checksum）—— 故障转回旧主要全量重建，慢。永远开 `wal_log_hints=on` 或 data checksums。
14. **PgBouncer 单进程 CPU 100%** —— 单 PgBouncer 实例上限 ~50k TPS。横向扩 + L4 LB。

## 练习题

1. **pool_mode 选择**：你的应用大量使用 `LISTEN/NOTIFY` 做事件推送，能用 PgBouncer `transaction` 模式吗？不能怎么办？

2. **pool size 计算**：PG 32 核 64 GB，`max_connections=400`，4 个应用各自独立用户。给出 `default_pool_size` 建议和理由。

3. **prepared statement**：解释 PgBouncer 1.21 前后 transaction 模式对客户端 prepared statement 支持的差别。如果你用 JDBC + HikariCP，怎么配？
