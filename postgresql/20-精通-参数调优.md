## 引言：参数调优是 PostgreSQL 上线前的"最后一公里"

很多人装完 PostgreSQL 直接拿默认参数上线，然后抱怨"PG 慢"。事实是——**PostgreSQL 默认配置是为 1995 年的 64MB 内存机器设计的**，目标是"能在任何机器上启动"。在 2026 年的 64GB / 256GB 内存主机上，默认配置只用了硬件能力的 5-10%。

- 你用 64GB 物理内存，但 `shared_buffers` 还是 128MB
- 你的 SSD 能跑 50 万 IOPS，但 `random_page_cost = 4.0` 让 Planner 拒绝走索引
- 你跑了一个大查询，发现 ORDER BY 在磁盘上排序——因为 `work_mem` 只有 4MB
- 你的从库追主库追了 30 分钟才赶上——因为 `max_wal_size` 太小，checkpoint 风暴
- 你的 autovacuum 永远跟不上更新速度——因为它一次只处理 200 行就睡 20ms

读完这章你应该能：

- 区分 `postgresql.conf` / `ALTER SYSTEM` / `SET` 三种参数修改方式的生效级别
- 给一个 16C/64G/SSD 的 OLTP 实例写出**生产可用**的参数模板
- 解释 `shared_buffers` 为什么不能简单地 = 物理内存的 80%
- 解释 `work_mem × max_connections` 的"内存放大"陷阱
- 用 `pg_settings` / `pg_file_settings` 系统视图诊断当前生效的参数
- 解释 `random_page_cost = 1.1` 为什么是 SSD 的标准答案
- 区分 `synchronous_commit` 的 5 个档位与 RPO/性能的权衡
- 给出生产环境调整 `max_connections` 的天花板（提示：≤300）

## 第一章：三种参数修改方式

### 1.1 postgresql.conf —— 持久化的配置文件

PostgreSQL 的"主"配置文件，位于数据目录（`$PGDATA/postgresql.conf`）。

```bash
# 找到当前生效的 postgresql.conf 路径
psql -c "SHOW config_file;"
# /var/lib/postgresql/18/main/postgresql.conf
```

文件内每行一个参数：

```ini
# postgresql.conf
shared_buffers = 16GB
work_mem = 32MB
maintenance_work_mem = 2GB
max_wal_size = 8GB
```

修改后需要 `pg_ctl reload` 或对于部分参数需要 `restart`。

### 1.2 ALTER SYSTEM —— 推荐方式

PG 9.4+ 引入的"SQL 方式改配置"，写入 `postgresql.auto.conf`（**优先级高于** `postgresql.conf`）：

```sql
-- 不需要 SSH 登录服务器
ALTER SYSTEM SET work_mem = '64MB';
ALTER SYSTEM SET max_connections = 200;

-- 重新载入
SELECT pg_reload_conf();

-- 重置某个参数（删掉 auto.conf 里的对应行）
ALTER SYSTEM RESET work_mem;

-- 全部重置
ALTER SYSTEM RESET ALL;
```

`postgresql.auto.conf` 由 PG 管理，**不要手工编辑**。优势：

- 不需要文件系统访问（云数据库友好）
- 改完留痕（`pg_file_settings` 会列出 source = 'configuration file' 或 'override'）
- 不会被人误把 `postgresql.conf` 注释丢失

### 1.3 SET —— 会话级 / 事务级

只影响当前连接（或当前事务）：

```sql
-- 仅当前会话有效
SET work_mem = '256MB';

-- 仅当前事务有效（更精细）
BEGIN;
SET LOCAL work_mem = '512MB';
-- ... 跑一个大 ORDER BY
COMMIT;

-- 角色级（指定用户登录后默认）
ALTER ROLE analytics SET work_mem = '512MB';

-- 数据库级
ALTER DATABASE analytics_db SET work_mem = '512MB';
```

**优先级**（高 → 低）：

```
SET LOCAL > SET > ALTER ROLE/DATABASE > ALTER SYSTEM > postgresql.conf > 编译默认
```

### 1.4 生效级别（context）

不是所有参数都能动态生效。`pg_settings.context` 列出 6 种级别：

| context | 改完需要 | 例子 |
|---|---|---|
| `internal` | 重新编译 PG | `block_size` (默认 8KB) |
| `postmaster` | 重启服务 | `shared_buffers`、`max_connections`、`max_worker_processes` |
| `sighup` | `pg_reload_conf()`（SIGHUP） | `work_mem`、`maintenance_work_mem`、`autovacuum*`、`log_*` |
| `superuser-backend` | 新建连接（超级用户） | `log_connections` |
| `backend` | 新建连接 | `post_auth_delay` |
| `superuser` | `SET`（仅超级用户） | `session_replication_role` |
| `user` | `SET`（任何用户） | `work_mem`、`statement_timeout`、`search_path` |

查询某参数的 context：

```sql
SELECT name, setting, unit, context, source
FROM pg_settings
WHERE name IN ('shared_buffers', 'work_mem', 'max_connections', 'random_page_cost');
```

| name | setting | unit | context | source |
|---|---|---|---|---|
| max_connections | 200 | - | postmaster | configuration file |
| random_page_cost | 1.1 | - | user | configuration file |
| shared_buffers | 2097152 | 8kB | postmaster | configuration file |
| work_mem | 65536 | kB | user | configuration file |

### 1.5 系统视图：pg_settings 与 pg_file_settings

```sql
-- 看所有参数当前值
SELECT name, setting, unit, short_desc
FROM pg_settings
WHERE category = 'Resource Usage / Memory';

-- 看配置文件里写了什么（包括 auto.conf）
SELECT sourcefile, sourceline, name, setting, applied, error
FROM pg_file_settings
ORDER BY sourcefile, sourceline;

-- 看哪些参数被改过（非默认值）
SELECT name, source, setting, boot_val, reset_val
FROM pg_settings
WHERE source NOT IN ('default', 'override')
ORDER BY name;
```

`pg_file_settings.applied = false` 表示参数解析失败或需要重启——上线前必查。

### 1.6 include 与 include_dir

`postgresql.conf` 支持模块化：

```ini
include = 'tuning.conf'              # 单文件
include_dir = 'conf.d'               # 目录下所有 *.conf
include_if_exists = 'extra.conf'     # 文件不存在不报错
```

云数据库（如 AWS RDS）用 `include_dir` 把用户自定义参数隔离开。

## 第二章：内存类参数

PostgreSQL 的内存使用分两层：

```
┌────────────────────────────────────────────────────────────┐
│ 操作系统页缓存（Page Cache）  ← effective_cache_size 提示  │
├────────────────────────────────────────────────────────────┤
│ 共享内存                                                    │
│   ├─ shared_buffers（数据页缓存，最重要）                 │
│   ├─ wal_buffers                                          │
│   ├─ CLOG / SLRU 各种小缓存                                │
│   └─ Lock table / Shared catalog                          │
├────────────────────────────────────────────────────────────┤
│ 后端进程（per-backend）                                     │
│   ├─ work_mem（每个查询节点）                              │
│   ├─ maintenance_work_mem（VACUUM/CREATE INDEX）           │
│   ├─ temp_buffers（临时表）                               │
│   └─ catalog cache / plan cache / ...                     │
└────────────────────────────────────────────────────────────┘
```

### 2.1 shared_buffers —— 数据页缓存

**重要程度**：⭐⭐⭐⭐⭐  **context**：postmaster（必须重启）

PG 的数据页（默认 8KB）缓存。**所有的读写都先经过 shared_buffers**——但 PG 与 MySQL InnoDB 不同，它**也依赖操作系统页缓存做二级缓存**。

```sql
SHOW shared_buffers;
-- 默认 128MB（笑话级）
```

经验法则：

| 物理内存 | shared_buffers 推荐 |
|---|---|
| 1 GB（容器） | 256 MB |
| 4 GB | 1 GB |
| 16 GB | 4 GB |
| 64 GB | **16 GB**（25%） |
| 256 GB | 64 GB（25%）|
| 1 TB | 也建议封顶 **128 GB** |

**为什么 25%？**

- PG 没有 direct IO，OS Page Cache 是天然的二级缓存（不浪费）
- shared_buffers 内部的 ProcArray / Buffer Pin 在超大规模下会有锁竞争
- 留 75% 给 OS Page Cache、其他后端进程、外部工具（pgBouncer、备份、监控）

**误区**：直接设到 80%。结果 OS 没有缓存可用，pg_basebackup 时性能崩溃。

云数据库（RDS / Aurora / Cloud SQL）一般设 25%，社区共识。

### 2.2 work_mem —— 单查询节点的内存上限

**重要程度**：⭐⭐⭐⭐⭐  **context**：user（可会话级调整）

`work_mem` 控制**单个查询节点**（不是整个查询！）能用的内存：

- ORDER BY、DISTINCT、Hash Aggregate、Hash Join、Hash Build 等

超过 `work_mem` 会**溢出到临时文件**（性能断崖式下降）。

```sql
SHOW work_mem;
-- 默认 4MB（笑话级 ×2）
```

**陷阱：内存放大**

一条 SQL 可能有 N 个 work_mem 消耗点；一个用户可能有 M 个并发连接。**实际峰值内存 = work_mem × N × M**。

```
假设：
  work_mem = 64MB
  一条 SQL 有 3 个 Sort 节点 + 1 个 HashJoin = 4 个消耗点
  并发连接 100

最坏情况内存峰值 = 64MB × 4 × 100 = 25.6 GB
```

经验值：

| 场景 | work_mem |
|---|---|
| OLTP（短小查询为主） | 16-32 MB |
| 混合负载 | 32-64 MB |
| OLAP（少并发，大查询） | 256 MB - 1 GB |
| 数据仓库 / ETL 用户 | `ALTER ROLE etl SET work_mem = '2GB';` |

**最佳实践**：保守的全局 `work_mem`，按需会话级调高：

```sql
-- 默认 32MB
ALTER SYSTEM SET work_mem = '32MB';

-- 报表系统单独账户
ALTER ROLE reporting SET work_mem = '512MB';

-- 特殊查询用 SET LOCAL
BEGIN;
SET LOCAL work_mem = '1GB';
SELECT ... ORDER BY ... ;
COMMIT;
```

PG 13+ 引入 `hash_mem_multiplier`（默认 2.0，PG 16 起为 2.0），让 Hash 操作可以用 `work_mem × multiplier`，避免哈希节点过早溢出。

### 2.3 maintenance_work_mem —— 维护操作内存

**重要程度**：⭐⭐⭐⭐  **context**：user

供 `VACUUM`、`CREATE INDEX`、`ALTER TABLE ADD FOREIGN KEY`、`pg_restore` 使用。

```sql
SHOW maintenance_work_mem;
-- 默认 64MB
```

**调大它能加速建索引 / VACUUM 几倍**。autovacuum worker 用的是 `autovacuum_work_mem`（若 `-1` 则继承 `maintenance_work_mem`）。

经验值：

| 物理内存 | maintenance_work_mem |
|---|---|
| 4 GB | 256 MB |
| 16 GB | 1 GB |
| 64 GB | **2 GB**（多数场景上限）|
| 256 GB | 4 GB（不建议无脑加大）|

注意 PG 17 改进了 VACUUM 的内存管理，**不再受 1GB 上限限制**（之前最多有效使用 1GB）。

### 2.4 effective_cache_size —— Planner 提示

**重要程度**：⭐⭐⭐⭐  **context**：user

这**不是分配内存**，而是**告诉 Planner**："操作系统页缓存 + shared_buffers 大概能缓存多少数据"。Planner 用它估算 Nested Loop + Index Scan 的 IO 成本。

```sql
SHOW effective_cache_size;
-- 默认 4GB
```

经验值：**物理内存 × 75%**（如果是专用 PG 服务器）。

```
64GB 物理内存 → effective_cache_size = 48GB
```

设得太小：Planner 倾向 Seq Scan（不愿走索引），认为索引页很可能从磁盘读取。
设得太大：Planner 过分乐观，给出"看似最优实际慢"的计划。

### 2.5 temp_buffers —— 临时表缓存

**重要程度**：⭐⭐  **context**：user

每个会话首次访问临时表时分配，仅供该会话。

```sql
SHOW temp_buffers;
-- 默认 8MB
```

大量使用临时表（如 ETL）时可调到 64-256MB。设置时机：会话开始前 `SET temp_buffers = '256MB';`（首次访问后无法再改）。

### 2.6 wal_buffers —— WAL 写入缓冲

**重要程度**：⭐⭐⭐  **context**：postmaster

WAL 暂存区，事务提交时统一 fsync。

```sql
SHOW wal_buffers;
-- 默认 -1，表示 shared_buffers / 32（最大 16MB）
```

**规则**：

- `shared_buffers ≥ 512MB` 时 `wal_buffers = 16MB`（足够）
- 高写入负载、`-1` 不够时手动设 `64MB`

### 2.7 内存配置速查表（64GB 物理内存示例）

```ini
# 内存类参数（64GB 物理内存，专用 PG 服务器）
shared_buffers              = 16GB        # 25%
work_mem                    = 32MB        # 看并发情况
maintenance_work_mem        = 2GB         # 加速 VACUUM/CREATE INDEX
autovacuum_work_mem         = -1          # 继承 maintenance_work_mem
effective_cache_size        = 48GB        # 75%
temp_buffers                = 16MB
wal_buffers                 = 64MB        # 高写入负载
```

## 第三章：WAL 与持久化

WAL（Write-Ahead Log）是 PG 的"redo log"——所有数据修改先写 WAL 再改数据页。WAL 参数直接影响**性能**与**持久性**（RPO）。

### 3.1 wal_level —— WAL 详细程度

**重要程度**：⭐⭐⭐⭐⭐  **context**：postmaster

```sql
SHOW wal_level;
-- minimal / replica（默认） / logical
```

| wal_level | 内容 | 用途 |
|---|---|---|
| `minimal` | 仅崩溃恢复需要 | 单机、不做复制（极少用） |
| `replica` | 加入足够支持物理复制的信息 | **默认值**，物理流复制 / Hot Standby |
| `logical` | 加入逻辑解码所需信息（行 before/after image） | 逻辑复制 / CDC（Debezium） |

**生产几乎都用 `replica` 或 `logical`**。`logical` 比 `replica` 多写约 10-20% WAL。

### 3.2 synchronous_commit —— 提交持久化级别

**重要程度**：⭐⭐⭐⭐⭐  **context**：user（可会话级调整！）

5 个档位，权衡 RPO 与延迟：

| 取值 | 主库行为 | 从库行为 | RPO | 性能 |
|---|---|---|---|---|
| `on`（默认） | WAL 写入并 fsync | 等同步从库收到（如果有） | 同步从库收到为准 | 基准 |
| `remote_apply` | 等从库**应用**了 WAL | 等从库 redo 完成 | 从库可读到 | 最慢 |
| `remote_write` | 等从库**写入** OS（未 fsync） | OS 缓冲收到 | 从库 OS 收到 | 比 on 快 |
| `local` | 仅主库本地 fsync | 不等从库 | 主库本地 | 比 on 快 |
| `off` | WAL 写入后立即返回 | 不等 | **3 倍 wal_writer_delay**（默认 600ms）| 最快 |

**经典场景**：

- 金融、订单系统：`on` + 同步从库（`synchronous_standby_names`）
- 日志、监控、IoT：`off`（接受少量数据丢失换性能）
- 单笔大事务临时调：`SET LOCAL synchronous_commit = off;`

**坑**：`off` 不等于"不持久"，崩溃后仍有 99% 的提交在磁盘上——只丢最后约 0.6s。

### 3.3 wal_compression —— WAL 压缩

**重要程度**：⭐⭐⭐  **context**：user

```sql
ALTER SYSTEM SET wal_compression = 'lz4';  -- PG 15+
-- 旧版本：'on' / 'off'
SELECT pg_reload_conf();
```

PG 15+ 支持 `lz4` / `zstd` / `pglz`，压缩 full page write 内容。

| 算法 | CPU 开销 | 压缩率 |
|---|---|---|
| pglz（旧默认） | 低 | 一般 |
| **lz4**（PG 15+ 推荐） | 极低 | 好 |
| zstd（PG 15+） | 中 | 最好 |

经验：高写入场景开 `lz4`，WAL 体积省 30-50%，CPU 几乎无感。

### 3.4 max_wal_size / min_wal_size

**重要程度**：⭐⭐⭐⭐⭐  **context**：sighup

PG 13+ 默认 `max_wal_size = 1GB` / `min_wal_size = 80MB`。

**作用**：触发 checkpoint 的"软上限"——WAL 写满 max_wal_size 就触发 checkpoint。

```sql
SHOW max_wal_size;
SHOW min_wal_size;
```

**太小** → checkpoint 频繁 → 写放大（每个脏页可能反复刷）→ IO 抖动
**太大** → 崩溃恢复时间长 → 占磁盘

经验值：

| 写入负载 | max_wal_size |
|---|---|
| 轻（< 1MB/s） | 1-2 GB |
| 中（1-10MB/s） | **8-16 GB** |
| 重（> 10MB/s） | 32-64 GB |

**调整公式**：`max_wal_size ≈ 写入速率 × checkpoint_timeout × 2`。

### 3.5 checkpoint_timeout / checkpoint_completion_target

**重要程度**：⭐⭐⭐⭐  **context**：sighup

```sql
SHOW checkpoint_timeout;
-- 默认 5min
SHOW checkpoint_completion_target;
-- 默认 0.9（PG 14+）
```

- `checkpoint_timeout`：两次 checkpoint 之间最大间隔（默认 5min）
- `checkpoint_completion_target`：在多大比例的 `checkpoint_timeout` 时间内完成刷脏页（0.9 表示用 90% 的时间，平滑 IO）

**生产推荐**：

```ini
checkpoint_timeout               = 15min      # 减少 checkpoint 频率
checkpoint_completion_target     = 0.9        # 平滑刷盘
max_wal_size                     = 16GB
min_wal_size                     = 2GB
checkpoint_warning               = 30s        # 检查点 < 30s 间隔触发警告（异常）
```

**目标**：让 checkpoint 由 `checkpoint_timeout` 触发，而非 `max_wal_size` 触发。日志里出现 `checkpoint starting: time` 是正常，`checkpoint starting: wal` 表示 max_wal_size 太小。

### 3.6 fsync / full_page_writes / commit_delay

| 参数 | 默认 | 调整建议 |
|---|---|---|
| `fsync` | on | **永远不要关**，关了崩溃必丢数据 |
| `full_page_writes` | on | **永远不要关**，关了崩溃恢复可能数据损坏 |
| `commit_delay` | 0 | 高并发短事务可调 100-1000μs，让多个事务合并 fsync |
| `commit_siblings` | 5 | 至少有 N 个活跃事务才触发 commit_delay |

### 3.7 WAL 完整配置示例

```ini
# WAL / 持久化
wal_level                       = replica         # 物理复制
synchronous_commit              = on              # 默认即可
wal_compression                 = lz4             # PG 15+
wal_buffers                     = 64MB
max_wal_size                    = 16GB
min_wal_size                    = 2GB
checkpoint_timeout              = 15min
checkpoint_completion_target    = 0.9
checkpoint_warning              = 30s
wal_writer_delay                = 200ms
wal_writer_flush_after          = 1MB
```

## 第四章：Autovacuum 调优视角

详细的 VACUUM 原理见 [P08](./08-精通-VACUUM-与表膨胀.md)，本节聚焦"调优"。

### 4.1 默认 autovacuum 为什么"永远跟不上"

默认配置：

```ini
autovacuum                       = on
autovacuum_max_workers           = 3              # 太少
autovacuum_naptime               = 1min
autovacuum_vacuum_threshold      = 50
autovacuum_vacuum_scale_factor   = 0.2            # 表 20% 死元组才触发
autovacuum_vacuum_cost_limit     = 200            # 每轮"信用值"
autovacuum_vacuum_cost_delay     = 2ms            # 每轮间隔（PG 12+ 从 20ms 改为 2ms）
```

问题：

- `autovacuum_max_workers = 3`：高写入数据库（几百个表）肯定堵
- `scale_factor = 0.2`：一个 1TB 表要等 200GB 死元组——直接死
- `cost_limit = 200`：autovacuum 一轮只能消耗 200 IO 信用就睡 2ms

### 4.2 全局调优

```ini
# 生产推荐（16C/64G 服务器）
autovacuum_max_workers           = 6              # 与 CPU 核数有关
autovacuum_naptime               = 15s            # 检查频率
autovacuum_vacuum_cost_limit     = 2000           # 提升 10 倍
autovacuum_vacuum_cost_delay     = 2ms            # PG 12+ 默认即可
autovacuum_work_mem              = 1GB            # 加速死元组扫描
maintenance_work_mem             = 2GB
```

### 4.3 大表单独调

```sql
-- 1TB 表，10% 死元组就清理
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.05,
  autovacuum_vacuum_threshold    = 10000,
  autovacuum_analyze_scale_factor = 0.02,
  autovacuum_vacuum_cost_limit   = 4000,
  fillfactor = 90                                 -- 留 10% 给 HOT update
);
```

### 4.4 防 wraparound 紧急参数

```ini
autovacuum_freeze_max_age        = 200000000      # 默认 2 亿事务
autovacuum_multixact_freeze_max_age = 400000000
vacuum_freeze_min_age            = 50000000
vacuum_freeze_table_age          = 150000000
```

当 `datfrozenxid` 接近 `autovacuum_freeze_max_age` 时，PG 会触发**强制 freeze**（不可阻止）。生产中要监控：

```sql
SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;
```

`xid_age > 1.5 亿`时要警觉，`> 1.8 亿`要立即处理。

## 第五章：并行查询参数

PG 9.6 起支持并行查询，10+ 起并行 VACUUM/INDEX，11+ 支持并行 Hash Join、CREATE INDEX。

### 5.1 五个关键参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `max_worker_processes` | 8 | 全局后台进程上限（含并行、复制、扩展） |
| `max_parallel_workers` | 8 | 并行查询可用 worker 总数（≤ `max_worker_processes`） |
| `max_parallel_workers_per_gather` | 2 | 单查询最多 N 个并行 worker |
| `max_parallel_maintenance_workers` | 2 | CREATE INDEX、VACUUM 并行 worker |
| `parallel_setup_cost` | 1000 | Planner 启动并行的固定成本 |
| `parallel_tuple_cost` | 0.1 | worker 传 1 行到 leader 的成本 |
| `min_parallel_table_scan_size` | 8MB | 表小于 N 不并行 |
| `min_parallel_index_scan_size` | 512kB | 索引小于 N 不并行 |

### 5.2 设置建议（按 CPU 核数）

```ini
# 16 核 CPU
max_worker_processes              = 16
max_parallel_workers              = 12           # 留 4 核给其他
max_parallel_workers_per_gather   = 4            # 单查询最多 4 worker
max_parallel_maintenance_workers  = 4            # 加速 CREATE INDEX
```

```ini
# 32 核 CPU（OLAP）
max_worker_processes              = 32
max_parallel_workers              = 24
max_parallel_workers_per_gather   = 8
max_parallel_maintenance_workers  = 8
```

### 5.3 何时关掉并行？

- 短查询为主的 OLTP：`max_parallel_workers_per_gather = 0`（避免并行启动开销）
- 容器 + 严格 CPU limit：`max_parallel_workers ≤ limit - 1`
- 函数里跑查询（PG 一般不并行函数内 SQL）

### 5.4 看是否走了并行

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders WHERE created_at >= '2025-01-01';
```

输出包含 `Gather` / `Parallel Seq Scan` 即走了并行。

## 第六章：连接管理

### 6.1 max_connections 的天花板

```sql
SHOW max_connections;
-- 默认 100
```

**误区**："我有 200 个微服务，每个 50 连接，那 max_connections = 10000 吧？"

**真相**：PG 是**进程模型**——每个连接 fork 一个 backend 进程，每进程占 5-15MB。

```
1000 个连接 × 10MB = 10GB 内存只是基础
+ 每个连接缓存 catalog、plan cache、shared buffer pin
+ ProcArray、Lock table 在共享内存里随连接数线性增长
+ 上下文切换：1000 个进程在 16 核上抢 CPU
```

**经验天花板**：

| 场景 | max_connections |
|---|---|
| 单机 PG，应用直连 | **≤ 200** |
| 中型集群 | 300（极限） |
| 任何 > 300 的情况 | **强制走 PgBouncer / pgcat** |

PgBouncer 在 transaction 模式下，**前端 10000 连接 ↔ 后端 50 连接**完全可行。

### 6.2 连接相关参数

```ini
max_connections                  = 200
superuser_reserved_connections   = 5
listen_addresses                 = '*'
port                             = 5432
tcp_keepalives_idle              = 60            # 60s 没活动开始 keepalive
tcp_keepalives_interval          = 10
tcp_keepalives_count             = 6
idle_in_transaction_session_timeout = 5min       # 防止 idle in txn 占着行锁
idle_session_timeout             = 1h            # PG 14+
statement_timeout                = 0             # 慎用，会切断长查询
lock_timeout                     = 5s            # 锁等待超过 N 自动失败
```

`idle_in_transaction_session_timeout = 5min` 是**生产必设**——防止应用 BEGIN 后忘了 COMMIT，导致 VACUUM 无法清理。

### 6.3 PgBouncer 简介

```ini
; pgbouncer.ini
[databases]
mydb = host=127.0.0.1 dbname=mydb

[pgbouncer]
listen_addr = *
listen_port = 6432
pool_mode = transaction              ; session / transaction / statement
max_client_conn = 10000              ; 前端最大连接
default_pool_size = 50               ; 每库后端连接数
reserve_pool_size = 10
server_idle_timeout = 600
```

详细见 [P17 高可用与连接池](./17-精通-高可用与连接池.md)。

## 第八章：Planner 参数

### 8.1 IO 成本模型

```sql
SHOW seq_page_cost;
-- 默认 1.0
SHOW random_page_cost;
-- 默认 4.0  ← 这是 1995 年机械硬盘的假设
```

| 介质 | random_page_cost 推荐 |
|---|---|
| 机械硬盘 HDD | 4.0（默认） |
| **SATA SSD / NVMe** | **1.1** |
| Optane / 高性能 NVMe | 1.0 |
| 内存数据库（全内存命中） | 1.0 |

**为什么 1.1 不是 1.0？** 仍要让 Planner 略偏向顺序扫描（缓存友好）。

```sql
ALTER SYSTEM SET random_page_cost = 1.1;
SELECT pg_reload_conf();
```

**生产实测**：默认 4.0 → 1.1 后，某些 SQL 从 Seq Scan 切到 Index Scan，**查询时间从 5s 降到 50ms**。

### 8.2 CPU 成本

```sql
SHOW cpu_tuple_cost;        -- 0.01
SHOW cpu_index_tuple_cost;  -- 0.005
SHOW cpu_operator_cost;     -- 0.0025
```

一般不调，除非做精细调优。

### 8.3 enable_* 开关

PG 提供一组开关用于"逼"Planner 选某个算法（**只用于调试**，生产不建议长期开关）：

```sql
SET enable_seqscan = off;       -- 禁止顺序扫描
SET enable_indexscan = off;     -- 禁止索引扫描
SET enable_bitmapscan = off;    -- 禁止位图扫描
SET enable_nestloop = off;      -- 禁止 Nested Loop
SET enable_hashjoin = off;      -- 禁止 Hash Join
SET enable_mergejoin = off;     -- 禁止 Merge Join
SET enable_parallel_hash = off;
SET enable_partitionwise_join = on;     -- PG 11+，分区表 join 下推
SET enable_partitionwise_aggregate = on;
```

诊断技巧：怀疑 Planner 选错了，临时 `enable_seqscan = off;` 看看走索引是否真的快。

### 8.4 JIT 编译

PG 11+ 支持 LLVM JIT（编译 expression 加速）：

```sql
SHOW jit;                              -- 默认 on
SHOW jit_above_cost;                   -- 默认 100000，估算 cost > N 才 JIT
SHOW jit_inline_above_cost;            -- 500000
SHOW jit_optimize_above_cost;          -- 500000
```

**经验**：

- OLAP / 数据仓库：JIT 显著加速（30-50% 加速大查询）
- OLTP（短查询）：JIT 反而成开销（编译时间 > 节省时间）→ `SET jit = off`
- 默认参数对混合负载即可

### 8.5 统计信息

```sql
SHOW default_statistics_target;
-- 默认 100
```

控制 `ANALYZE` 收集的直方图桶数 + MCV 个数。

- 默认 100 → 通用够用
- 大表 / 复杂分布：**1000**（更精确直方图，ANALYZE 慢一些）
- 单列调整：`ALTER TABLE t ALTER COLUMN c SET STATISTICS 1000;`

PG 10+ 引入 `CREATE STATISTICS`（扩展统计），让 Planner 理解多列相关性：

```sql
CREATE STATISTICS s_city_state (dependencies, ndistinct, mcv)
ON city, state FROM addresses;
ANALYZE addresses;
```

## 第十一章：实战案例 —— 默认配置到优化的 QPS 提升

### 11.1 场景

某电商订单库：

- 硬件：32C / 128G / NVMe SSD
- 数据量：3TB（orders 表 1.5TB，order_items 1TB）
- 并发：300 个应用连接（直连 PG）
- QPS：6000（混合读写）
- 抱怨：P99 高峰期 800ms，autovacuum 永远跟不上，磁盘 IO 80%

### 11.2 默认配置下的"病象"

```sql
-- shared_buffers 仅 128MB
SHOW shared_buffers;       -- 128MB

-- 缓存命中率
SELECT sum(heap_blks_hit) * 100.0 / sum(heap_blks_hit + heap_blks_read) AS hit_pct
FROM pg_statio_user_tables;
-- 72%（极低）

-- 大量临时文件
SELECT temp_files, pg_size_pretty(temp_bytes) FROM pg_stat_database WHERE datname = 'shop';
-- temp_files = 1.2M, temp_bytes = 4.5TB

-- 死元组
SELECT relname, n_dead_tup, n_live_tup, 
       n_dead_tup * 100.0 / GREATEST(n_live_tup + n_dead_tup, 1) AS dead_pct
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 5;
-- orders: dead_pct = 45%（极度膨胀）
```

### 11.3 调优方案

```ini
# --- 内存 ---
shared_buffers                   = 32GB         # 128MB → 32GB (25%)
work_mem                         = 64MB         # 4MB → 64MB
maintenance_work_mem             = 4GB
effective_cache_size             = 96GB

# --- WAL/checkpoint ---
wal_compression                  = lz4
max_wal_size                     = 32GB
min_wal_size                     = 4GB
checkpoint_timeout               = 15min
checkpoint_completion_target     = 0.9

# --- 并行 ---
max_worker_processes             = 32
max_parallel_workers             = 16
max_parallel_workers_per_gather  = 4

# --- Planner ---
random_page_cost                 = 1.1          # 4.0 → 1.1
effective_io_concurrency         = 200

# --- Autovacuum（重灾区） ---
autovacuum_max_workers           = 8            # 3 → 8
autovacuum_naptime               = 15s
autovacuum_vacuum_cost_limit     = 4000         # 200 → 4000
autovacuum_vacuum_scale_factor   = 0.05         # 0.2 → 0.05

# 大表单独调
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_threshold    = 50000,
  fillfactor                     = 90
);

# --- 连接（最重要的架构调整） ---
max_connections                  = 200          # 300 → 200
# 前面加 PgBouncer transaction 模式
```

应用侧加 PgBouncer：

```ini
[databases]
shop = host=pg-primary dbname=shop
[pgbouncer]
pool_mode = transaction
max_client_conn = 2000
default_pool_size = 50
```

### 11.4 调优效果

| 指标 | 调优前 | 调优后 | 提升 |
|---|---|---|---|
| QPS | 6,000 | **31,000** | **5.2x** |
| P99 延迟 | 800ms | 45ms | 17.8x |
| 缓存命中率 | 72% | 99.6% | - |
| 临时文件 | 4.5TB/天 | 12GB/天 | - |
| dead_tup 比例（orders） | 45% | 4% | - |
| autovacuum 滞后 | 持续 30min | 实时 | - |

**关键收益来自**：

1. shared_buffers 128MB → 32GB（缓存命中率 72% → 99.6%，直接消灭大量磁盘 IO）
2. random_page_cost 4.0 → 1.1（Planner 终于愿意走索引）
3. autovacuum 全套调优 + 大表单独参数（膨胀消失）
4. PgBouncer 替代 300 直连（CPU 上下文切换骤降）

## 生产实践

### 1. 上线前必跑的"参数体检"

```sql
-- 检查所有非默认参数（人工审核）
SELECT name, source, setting, boot_val
FROM pg_settings
WHERE source NOT IN ('default', 'override')
  AND name NOT LIKE '%password%'
ORDER BY name;

-- 检查 auto.conf 与 postgresql.conf 冲突
SELECT sourcefile, name, setting, applied
FROM pg_file_settings
ORDER BY name, sourcefile;
```

### 2. 修改流程

**禁止**直接 SSH 改 `postgresql.conf` 然后 reload——没痕迹、易冲突。

推荐：

```sql
-- 1. 测试环境验证
ALTER SYSTEM SET work_mem = '128MB';
SELECT pg_reload_conf();

-- 2. 验证生效
SHOW work_mem;
SELECT name, setting, pending_restart FROM pg_settings WHERE name = 'work_mem';

-- 3. 生产应用同样命令（CI/CD pipeline）
```

### 3. 重启前必查 pending_restart

```sql
SELECT name, setting, pending_restart
FROM pg_settings
WHERE pending_restart = true;
```

如果有结果，意味着你改了一个 `postmaster` context 参数（如 shared_buffers），需要重启才生效。

### 4. 配套监控

```sql
-- 缓存命中率（每分钟采样）
SELECT sum(heap_blks_hit)::float / nullif(sum(heap_blks_hit + heap_blks_read), 0)
FROM pg_statio_user_tables;

-- checkpoint 触发原因
SELECT * FROM pg_stat_bgwriter;
-- checkpoints_timed 应远大于 checkpoints_req

-- 临时文件
SELECT datname, temp_files, pg_size_pretty(temp_bytes)
FROM pg_stat_database;
```

## 陷阱清单

| # | 陷阱 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | `shared_buffers` 设到物理内存 80% | OS Page Cache 没空间，pg_basebackup / 大查询性能崩盘 | **25%**，最多 40% |
| 2 | `work_mem` 全局调到 1GB | `1GB × N_op × 并发` 内存爆炸 → OOM | 全局 32MB，按用户/查询调 |
| 3 | `max_connections = 1000` 直连 | 进程切换雪崩，TPS 下降 | ≤ 200 + PgBouncer |
| 4 | `random_page_cost` 用默认 4.0（在 SSD 上） | Planner 拒绝走索引 | **SSD 设 1.1** |
| 5 | `fsync = off` 提升性能 | 崩溃必丢数据，可能损坏 | 永远 `on` |
| 6 | `synchronous_commit = off` 没告知业务 | 崩溃丢失最近 600ms 数据 | 业务确认 RPO 后再设 |
| 7 | `max_wal_size` 太小（1GB） | checkpoint_req 频发，IO 抖动 | 8-32GB |
| 8 | 改完 postgresql.conf 没 reload | 不生效，以为生效了 | `SELECT pg_reload_conf();` |
| 9 | 改 `shared_buffers` 后没重启 | `pending_restart = true`，下次重启才生效 | 立即重启 |
| 10 | autovacuum 默认参数跑大表 | 永远跟不上，wraparound 危险 | 全局 + 大表单独调 |
| 11 | `default_statistics_target = 10000` | ANALYZE 极慢，规划器选择不一定更好 | 默认 100，特定列 1000 |
| 12 | 容器 PG 不调 max_parallel | 看到宿主机 CPU 数，过度并行 | 按容器 limit 显式设 |
| 13 | `log_min_duration_statement = 0` | 记录所有 SQL，日志爆盘 | ≥ 1000ms |
| 14 | `log_statement = 'all'` | 同上 | 'ddl' 或 'mod' 即可 |
| 15 | 改了 `wal_level` 没重启 | 不生效 | postmaster context 必须重启 |
| 16 | 把 `autovacuum = off` | 死元组永不清理 → wraparound 必死 | 永远 on，只调 worker / 频率 |
| 17 | 没设 `idle_in_transaction_session_timeout` | 应用 BEGIN 忘了 COMMIT，VACUUM 失败 | **必设 5min** |
| 18 | `checkpoint_completion_target = 1.0` | checkpoint 还没完下一个就来 | **0.9** |
| 19 | 关 `jit` 但是 OLAP 场景 | 大查询慢 30-50% | OLAP 必开 |
| 20 | 用 `SET` 调 `shared_buffers` | 报错"requires restart" | 区分 context |

## 2026 现状

### 1. PG 18 异步 IO 改变参数语义

PG 18（2025-09）引入了 `io_uring` 异步 IO（Linux 5.1+）：

```ini
# PG 18 新参数
io_method                        = 'io_uring'    # sync / worker / io_uring
io_workers                       = 3             # io_method=worker 时的 worker 数
io_max_combine_limit             = 128kB
```

- `io_method = io_uring`：随机 IO 性能显著提升（30-100%）
- 之前对 `effective_io_concurrency` 的依赖减弱（变成提示）
- `shared_buffers` 大小经验不变，但**冷启动加载更快**

### 2. PG 17 的 VACUUM 内存改进

PG 17 之前，VACUUM 的死元组数组**最多 1GB**（即使 `maintenance_work_mem = 4GB`）。PG 17 引入了基数树（radix tree）结构，**完全使用 maintenance_work_mem**，大表 VACUUM 速度可提升 6 倍。

→ PG 17+ 把 `maintenance_work_mem` 调到 4-8GB 是值得的。

### 3. pgtune 已经支持 PG 18

[pgtune.leopard.in.ua](https://pgtune.leopard.in.ua) 在 2025-Q4 加入了 PG 18 模板。

### 4. 云数据库的特殊性

- **AWS Aurora PostgreSQL**：`shared_buffers` 由 Aurora 内部管理（75% 内存），WAL/Buffer Pool 与磁盘解耦
- **Google AlloyDB**：列存加速分析查询，参数集自带 OLAP 倾向
- **Neon / Supabase / Crunchy**：按 instance class 自动选模板
- 通用建议：云数据库默认参数大部分接近最佳，**重点调 work_mem / autovacuum / pg_stat_statements**

### 5. PgBouncer vs pgcat vs Supavisor

- **PgBouncer 1.22**（2024）：稳定首选
- **pgcat**（Rust，2024 起兴起）：支持 sharding、read/write split、QUERY ROUTING
- **Supavisor**（Supabase 出品，Elixir）：多租户场景

→ 高并发 PG 部署，**连接池必备**。

### 6. CloudNativePG 的参数模板

K8s 上的 PG Operator（CNCF Incubation 路上），自带按 instance size 的参数模板。

```yaml
spec:
  postgresql:
    parameters:
      shared_buffers: "1GB"
      work_mem: "32MB"
      max_connections: "100"
```

### 7. 监控驱动调参成为主流

旧时代：拍脑袋 → 上线 → 抱怨
2026 模式：**Prometheus + postgres_exporter + Grafana**（看 [P21](./21-精通-监控与诊断.md)）→ 根据 wait events 与缓存命中率反向调参 → A/B 验证。

## 练习题

### 练习 1：参数生效级别

下面哪些参数**可以**通过 `SELECT pg_reload_conf()` 生效？哪些必须重启？

a. `shared_buffers`  
b. `work_mem`  
c. `max_connections`  
d. `random_page_cost`  
e. `wal_level`  
f. `autovacuum_max_workers`  
g. `log_min_duration_statement`  

<details><summary>参考答案</summary>

可 reload 生效（sighup / user context）：b、d、f、g
必须重启（postmaster context）：a、c、e

可用 `SELECT name, context FROM pg_settings WHERE name IN (...);` 验证。
</details>

### 练习 2：内存放大计算

服务器 32GB 物理内存，PG 配置：

- shared_buffers = 8GB
- work_mem = 256MB
- max_connections = 200
- maintenance_work_mem = 1GB
- autovacuum_max_workers = 5

假设业务高峰所有连接都在跑 SQL，每条 SQL 平均 2 个内存操作节点。问：最坏情况下 PG 可能用多少内存？是否会 OOM？

<details><summary>参考答案</summary>

```
shared_buffers              = 8 GB
work_mem 峰值（user 连接）   = 256MB × 2 × 200 = 100 GB
maintenance_work_mem 峰值    = 1GB × 5 = 5 GB
其他（catalog cache 等）     ≈ 2 GB
合计                        ≈ 115 GB ≫ 32 GB
```

**结论**：极度过配，OOM 风险高。修复：
- 降 work_mem 到 16MB（全局），按用户/会话调高
- 用 PgBouncer 把直连限制到 50
- 或者升级到 128GB+ 内存
</details>

### 练习 3：synchronous_commit 选档

业务场景：

A. 银行核心账户系统  
B. 用户登录会话存储（Redis 兜底）  
C. 实时大屏指标（每秒万条）  
D. 文档编辑器自动保存  

为每个场景推荐 `synchronous_commit` 档位并说明理由。

<details><summary>参考答案</summary>

- A: `on` + 同步从库（`synchronous_standby_names = 'standby1'`，要求至少一个从库 ack）
- B: `local`（主库本地 fsync 即可，Redis 已经是缓存层）
- C: `off`（接受最多 600ms 数据丢失换性能）
- D: `on`（默认）即可
</details>

### 练习 4：autovacuum 调优诊断

```sql
SELECT relname, n_dead_tup, n_live_tup, 
       n_dead_tup * 100.0 / GREATEST(n_live_tup + n_dead_tup, 1) AS dead_pct,
       last_autovacuum
FROM pg_stat_user_tables
WHERE relname = 'orders';
```

结果：

| relname | n_dead_tup | n_live_tup | dead_pct | last_autovacuum |
|---|---|---|---|---|
| orders | 12,000,000 | 50,000,000 | 19.4% | 2026-05-25 03:12 |

今天是 2026-05-28，距上次 autovacuum 3 天。问：为什么 autovacuum 没触发？该如何调？

<details><summary>参考答案</summary>

默认 `autovacuum_vacuum_scale_factor = 0.2`，触发阈值 = `0.2 × 50M = 10M`。当前死元组 12M > 10M，**应该已触发**——但 last_autovacuum 是 3 天前，可能：

1. autovacuum 正在跑，被中断（lock 冲突 / 长事务挡住）
2. autovacuum worker 都被其他大表占用
3. 表上有长 transaction snapshot 阻止清理

调优：
```sql
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.05,
  autovacuum_vacuum_threshold = 100000,
  fillfactor = 90
);
-- 全局加 worker
ALTER SYSTEM SET autovacuum_max_workers = 6;
ALTER SYSTEM SET autovacuum_vacuum_cost_limit = 4000;
SELECT pg_reload_conf();
-- 检查长事务
SELECT pid, xact_start, query FROM pg_stat_activity 
WHERE state IN ('active','idle in transaction')
  AND xact_start < now() - interval '10 min';
```
</details>

### 练习 5：SSD 上的 Planner

EXPLAIN 显示某个 1000 万行表的查询走 Seq Scan，预计 800ms，实际跑 2.3s。表上有合适的索引，强制 `enable_seqscan = off;` 后走索引仅 35ms。Planner 为什么选错？

<details><summary>参考答案</summary>

最常见原因：`random_page_cost = 4.0`（默认，机械盘假设）让 Planner 认为索引扫描 IO 成本远高于实际（SSD 上随机/顺序差异极小）。

修复：
```sql
ALTER SYSTEM SET random_page_cost = 1.1;
ALTER SYSTEM SET effective_io_concurrency = 200;
SELECT pg_reload_conf();
```

二级原因：`effective_cache_size` 设太小（默认 4GB），Planner 认为索引块大概率不在内存。

三级原因：统计信息陈旧，`ANALYZE table;` 重新采样。
</details>

### 练习 6：max_connections 决策

业务方说："我有 500 个微服务实例，每个实例 50 个连接，总共 25000 连接，PG 能扛吗？"

写一份给业务方的回复，说明你的方案。

<details><summary>参考答案</summary>

**直连 PG**：25000 连接 = 25000 进程 ≈ 250GB 内存（仅基础），还没算 catalog cache、上下文切换雪崩、ProcArray 锁竞争。**PG 撑不住**。

**方案**：
1. PG 后端固定 `max_connections = 200`
2. 前面放 PgBouncer（transaction 模式），`max_client_conn = 25000`、`default_pool_size = 100`（每库后端 100 个连接）
3. PgBouncer 多实例 + HAProxy 做负载（避免单点）
4. 每应用连接保持短小事务（< 100ms），避免事务级 pool 失效

预期能支撑 25000 前端 + 200 后端，CPU 上下文切换从 100k/s 降到 5k/s。
</details>

### 练习 7：参数模板撰写

公司要部署一个**时序监控数据库**：

- 8C / 32G / 普通 SSD
- 写入 5000 条/秒，读取 200 QPS
- 数据保留 90 天，旧数据按天分区
- 容忍 1s 数据丢失

写出 `postgresql.conf` 核心 20 项参数。

<details><summary>参考答案</summary>

```ini
# 内存
shared_buffers                   = 8GB           # 25%
work_mem                         = 32MB
maintenance_work_mem             = 1GB
effective_cache_size             = 24GB          # 75%
wal_buffers                      = 64MB

# WAL（写密集 + 容忍丢失）
wal_level                        = replica
synchronous_commit               = off           # 容忍 1s 丢失
wal_compression                  = lz4
max_wal_size                     = 16GB
min_wal_size                     = 2GB
checkpoint_timeout               = 15min
checkpoint_completion_target     = 0.9

# Autovacuum（高写入加强）
autovacuum_max_workers           = 4
autovacuum_naptime               = 15s
autovacuum_vacuum_cost_limit     = 2000

# Planner
random_page_cost                 = 1.1
effective_io_concurrency         = 200

# 连接
max_connections                  = 100

# 并行
max_worker_processes             = 8
max_parallel_workers             = 4
max_parallel_workers_per_gather  = 2
```

附加建议：分区表 + pg_partman 自动删过期 + BRIN 索引（时序友好）。
</details>

### 练习 8：紧急调优场景

凌晨 3 点告警：从库延迟 30 分钟。检查发现：

```sql
SELECT * FROM pg_stat_bgwriter;
-- checkpoints_timed = 50, checkpoints_req = 1200
```

主库 checkpoint 大量由 WAL 触发（req）。同时主库磁盘 IO 持续 90%。问：

1. 根本原因？
2. 紧急可调哪个参数（不重启）？
3. 长期修复？

<details><summary>参考答案</summary>

1. **根本原因**：`max_wal_size` 太小，WAL 不断触发紧急 checkpoint，刷脏页风暴，IO 饱和，WAL 应用慢，从库追不上。

2. **紧急调整**（sighup，无需重启）：
   ```sql
   ALTER SYSTEM SET max_wal_size = '32GB';   -- 假设原 4GB
   ALTER SYSTEM SET checkpoint_completion_target = 0.9;
   ALTER SYSTEM SET checkpoint_timeout = '15min';
   SELECT pg_reload_conf();
   ```

3. **长期修复**：
   - 评估写入速率，max_wal_size = 写入速率 × 30min × 2
   - 评估磁盘 IOPS 是否本身就不够（升级 NVMe / 增加 IOPS）
   - 考虑 wal_compression = lz4 减小 WAL 量
   - 从库网络延迟检查（区域内还是跨区域）
   - 监控 checkpoints_timed vs checkpoints_req 比值，正常应 > 95%
</details>
