## 引言：可观测性是 DBA 的眼睛

调优做完，参数定好，监控才刚开始。

- 凌晨 3 点告警"连接数飙升到 500"——你看 `pg_stat_activity` 还是只能看到当前快照
- 慢查询日志写了 100GB，pgBadger 还没跑完——你不知道从哪开始
- 主从延迟 10 分钟，但 Prometheus 上看不出来——`pg_stat_replication` 的 `replay_lag` 你没采
- autovacuum "好像"没在跑，wraparound 警告 `datfrozenxid age > 1.5 亿`——你没监控这个指标
- 一个会话卡住所有更新——你不会写 `pg_blocking_pids()` 查阻塞链

监控的核心不是"装一个 Grafana"，而是**理解 PG 暴露的每个 `pg_stat_*` 视图各自能回答什么问题**，并把它们组合成"事前预警 - 事中诊断 - 事后归因"的闭环。

读完这章你应该能：

- 列出 `pg_stat_*` 视图全家桶（10+ 个）及各自用途
- 用 `pg_stat_activity` 找出当前长事务、阻塞链、wait event
- 解释 9 大类 wait event（Lock / LWLock / IO / BufferPin / Activity / Client / IPC / Timeout / Extension）
- 用 `pg_stat_statements` 找出 TOP SQL 并按维度排序
- 用 `pg_stat_user_tables` / `pg_stat_user_indexes` 找无用索引 / 死元组膨胀
- 用 `pg_stat_replication` / `pg_stat_wal_receiver` 监控主备延迟
- 用 `pg_stat_io`（PG 16+）按对象 / 后端类型看 IO 分布
- 部署 `postgres_exporter` + Grafana 标准面板
- 给出 8 个生产**必设**告警阈值

## 第一章：pg_stat 视图全家桶

PG 内置一组累积型统计视图，由 `stats collector`（PG 14 前）/ shared memory stats（PG 15+）维护。

> **PG 15 重大变化**：统计信息从临时文件迁移到 shared memory，**性能提升**且**重启清零**（之前会持久化）。可用 `pg_stat_reset()` 主动清零。

### 1.1 视图分类速查

| 视图 | 一句话 | 重要程度 |
|---|---|---|
| `pg_stat_activity` | 当前会话快照 | ⭐⭐⭐⭐⭐ |
| `pg_stat_database` | 库级累积（commit/rollback/blks/tuples/deadlock） | ⭐⭐⭐⭐⭐ |
| `pg_stat_user_tables` | 表级（seq_scan/idx_scan/n_dead_tup/vacuum 时间） | ⭐⭐⭐⭐⭐ |
| `pg_stat_user_indexes` | 索引（idx_scan/idx_tup_read） | ⭐⭐⭐⭐⭐ |
| `pg_statio_user_tables` | 表 IO（heap_blks_read/hit） | ⭐⭐⭐⭐ |
| `pg_statio_user_indexes` | 索引 IO | ⭐⭐⭐⭐ |
| `pg_stat_replication` | 主库视角的复制状态 | ⭐⭐⭐⭐⭐ |
| `pg_stat_wal_receiver` | 备库视角的 WAL 接收 | ⭐⭐⭐⭐ |
| `pg_stat_wal` | WAL 写入统计（PG 14+） | ⭐⭐⭐ |
| `pg_stat_bgwriter` | 后台写、checkpoint | ⭐⭐⭐⭐ |
| `pg_stat_io` | IO 分类（PG 16+） | ⭐⭐⭐⭐ |
| `pg_stat_progress_vacuum` | VACUUM 进度（PG 9.6+） | ⭐⭐⭐⭐ |
| `pg_stat_progress_create_index` | 建索引进度（PG 12+） | ⭐⭐⭐ |
| `pg_stat_progress_analyze` | ANALYZE 进度（PG 13+） | ⭐⭐⭐ |
| `pg_stat_progress_basebackup` | basebackup 进度（PG 13+） | ⭐⭐⭐ |
| `pg_stat_progress_copy` | COPY 进度（PG 14+） | ⭐⭐⭐ |
| `pg_stat_statements` | TOP SQL（扩展） | ⭐⭐⭐⭐⭐ |
| `pg_stat_user_functions` | 函数调用统计 | ⭐⭐ |
| `pg_stat_archiver` | WAL 归档状态 | ⭐⭐⭐ |
| `pg_stat_subscription` | 订阅状态（逻辑复制） | ⭐⭐⭐⭐ |
| `pg_stat_replication_slots` | 复制槽统计（PG 14+） | ⭐⭐⭐⭐ |

### 1.2 累积值 vs 增量

`pg_stat_*` 大多是**累积值**（自启动或上次 reset），监控时需要按时间窗口做差：

```promql
# Prometheus
rate(pg_stat_database_xact_commit{datname="shop"}[5m])
```

或 SQL 自采：

```sql
-- 每分钟存一次快照
INSERT INTO mon.pg_stat_database_snap
SELECT now() AS ts, * FROM pg_stat_database;

-- 计算增量
SELECT ts, datname, xact_commit - lag(xact_commit) OVER (PARTITION BY datname ORDER BY ts) AS commits
FROM mon.pg_stat_database_snap;
```

## 第二章：pg_stat_activity —— 当前活动

**核心字段**：

```sql
SELECT pid, usename, datname, application_name, client_addr, 
       backend_start, xact_start, query_start, state_change,
       wait_event_type, wait_event, state, backend_xid, backend_xmin,
       query, backend_type
FROM pg_stat_activity;
```

| 字段 | 含义 |
|---|---|
| `pid` | 后端进程 PID |
| `usename` | 数据库用户 |
| `datname` | 当前数据库 |
| `application_name` | 客户端设置（连接串 `application_name=foo`） |
| `client_addr` | 客户端 IP |
| `backend_start` | 进程建立时间 |
| `xact_start` | 当前事务开始时间 |
| `query_start` | 当前 / 最近 SQL 开始时间 |
| `state` | active / idle / idle in transaction / idle in transaction (aborted) / fastpath function call / disabled |
| `wait_event_type` | 等待事件大类（IO / Lock / LWLock / ...） |
| `wait_event` | 具体等待事件名 |
| `backend_xid` | 当前事务分配的 XID（写事务才有） |
| `backend_xmin` | 最旧事务 ID（影响 VACUUM） |
| `query` | 当前/最近 SQL 文本 |
| `backend_type` | client backend / autovacuum worker / walsender / walreceiver / background worker / checkpointer / ... |

### 2.1 找长事务

```sql
SELECT pid, usename, application_name, state, 
       now() - xact_start AS xact_duration,
       now() - query_start AS query_duration,
       wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE state != 'idle'
  AND xact_start < now() - interval '5 min'
ORDER BY xact_start;
```

`xact_duration > 5min` 通常是问题——长事务持有 snapshot 阻止 VACUUM，可能引发 wraparound。

### 2.2 找 idle in transaction

最容易忽略也最危险的状态——客户端 `BEGIN` 后没 `COMMIT` 也没断开。

```sql
SELECT pid, usename, application_name, client_addr,
       now() - state_change AS idle_duration, query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND state_change < now() - interval '10 min';
```

**生产必设**：`idle_in_transaction_session_timeout = 5min`（PG 9.6+），自动 kill 这些会话。

### 2.3 找阻塞链 pg_blocking_pids

```sql
SELECT pid, usename, query_start, state,
       pg_blocking_pids(pid) AS blocked_by,
       query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

输出：

| pid | usename | query_start | state | blocked_by | query |
|---|---|---|---|---|---|
| 4521 | app | 10:12:34 | active | {3920} | UPDATE orders SET ... |
| 4522 | app | 10:12:35 | active | {3920} | UPDATE orders SET ... |

→ 4521、4522 都被 3920 阻塞。

完整的阻塞链可视化（适用于多层阻塞）：

```sql
WITH RECURSIVE block_chain AS (
  SELECT pid, pg_blocking_pids(pid) AS blockers, query, 1 AS depth
  FROM pg_stat_activity
  WHERE cardinality(pg_blocking_pids(pid)) > 0
  UNION
  SELECT a.pid, pg_blocking_pids(a.pid), a.query, bc.depth + 1
  FROM pg_stat_activity a, block_chain bc
  WHERE a.pid = ANY(bc.blockers)
)
SELECT * FROM block_chain;
```

### 2.4 终止会话

```sql
SELECT pg_cancel_backend(4521);    -- 取消当前查询（温和）
SELECT pg_terminate_backend(4521); -- 杀进程（连接断开）
```

### 2.5 wait_event_type 全分类

PG 9.6+ 暴露 wait event，分类为：

| 大类 | 含义 | 典型事件 |
|---|---|---|
| **LWLock** | 轻量锁（内部数据结构保护） | BufferContent / WALInsert / ProcArray / LockManager / XidGen |
| **Lock** | 表级 / 行级锁 | relation / transactionid / tuple / virtualxid |
| **BufferPin** | 等待 pin buffer | BufferPin |
| **Activity** | 后台进程空闲 | AutoVacuumMain / BgWriterMain / WalSenderMain （正常） |
| **Client** | 等待客户端 | ClientRead / ClientWrite |
| **Extension** | 扩展自定义 | 取决于扩展 |
| **IPC** | 进程间通信 | ParallelFinish / MessageQueueReceive |
| **Timeout** | 等待超时 | PgSleep / VacuumDelay |
| **IO** | 磁盘 IO | DataFileRead / DataFileWrite / WALWrite / WALSync |

完整列表见 [pg_wait_events 视图](https://www.postgresql.org/docs/current/monitoring-stats.html#WAIT-EVENT-TABLE)（PG 17+）。

**诊断套路**：

```sql
-- 等待事件 TOP 10（按当前快照）
SELECT wait_event_type, wait_event, count(*)
FROM pg_stat_activity
WHERE state != 'idle' AND wait_event IS NOT NULL
GROUP BY 1, 2
ORDER BY count(*) DESC LIMIT 10;
```

或采样型（每秒采一次，看 wait 分布）：

```sql
-- 创建采样表
CREATE TABLE mon.wait_samples (
  ts timestamptz, pid int, wait_event_type text, wait_event text, query text
);

-- cron 每秒
INSERT INTO mon.wait_samples
SELECT now(), pid, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE state = 'active' AND pid != pg_backend_pid();

-- 分析最近 10 分钟
SELECT wait_event_type, wait_event, count(*) AS samples
FROM mon.wait_samples
WHERE ts > now() - interval '10 min'
GROUP BY 1, 2
ORDER BY samples DESC LIMIT 20;
```

## 第三章：pg_stat_database —— 库级健康

```sql
SELECT datname, xact_commit, xact_rollback,
       blks_read, blks_hit,
       round(blks_hit * 100.0 / nullif(blks_hit + blks_read, 0), 2) AS cache_hit_pct,
       tup_returned, tup_fetched, tup_inserted, tup_updated, tup_deleted,
       temp_files, pg_size_pretty(temp_bytes) AS temp,
       deadlocks, conflicts,
       stats_reset
FROM pg_stat_database
WHERE datname NOT IN ('template0', 'template1');
```

**关键指标**：

| 指标 | 健康线 | 异常含义 |
|---|---|---|
| `xact_commit + xact_rollback` 速率 | TPS | 业务流量基线 |
| `xact_rollback / xact_commit` 比例 | < 1% | 大量回滚 = 业务异常或死锁 |
| `cache_hit_pct` | OLTP > 99%，OLAP > 95% | < 90% = shared_buffers 不够 |
| `tup_returned / tup_fetched` | 接近 1 | 远大于 1 = 大量行被 Planner 拿到却抛弃（Seq Scan + Filter） |
| `temp_files` 增长 | 缓慢 | 飙升 = work_mem 不够，大量溢出 |
| `deadlocks` | 0 | > 0 = 业务设计问题，需查日志 |
| `conflicts` | 0（主库） | 备库 > 0 = 流复制冲突 |

### 3.1 缓存命中率

```sql
SELECT datname,
       sum(blks_hit) * 100.0 / nullif(sum(blks_hit + blks_read), 0) AS hit_pct
FROM pg_stat_database
GROUP BY datname;
```

注意：这个 hit 是 `shared_buffers` 命中率，**OS Page Cache 命中算 read**。所以 PG 表面命中率 90% 可能实际整体（含 OS Cache）99%——配合系统层 `iostat` 看真实磁盘 IO。

### 3.2 临时文件激增

```sql
SELECT datname, temp_files, pg_size_pretty(temp_bytes)
FROM pg_stat_database
ORDER BY temp_bytes DESC;
```

配合 `log_temp_files = 10MB` 在日志里看哪些 SQL 创建大临时文件，调高这些 SQL 的 `work_mem`。

## 第四章：pg_stat_user_tables —— 表的"体检报告"

```sql
SELECT schemaname, relname,
       seq_scan, seq_tup_read,
       idx_scan, idx_tup_fetch,
       n_tup_ins, n_tup_upd, n_tup_del, n_tup_hot_upd,
       n_live_tup, n_dead_tup,
       round(n_dead_tup * 100.0 / GREATEST(n_live_tup + n_dead_tup, 1), 2) AS dead_pct,
       last_vacuum, last_autovacuum,
       last_analyze, last_autoanalyze,
       vacuum_count, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 20;
```

**关键场景**：

### 4.1 找膨胀的表

```sql
SELECT schemaname, relname, n_dead_tup, n_live_tup,
       round(n_dead_tup * 100.0 / GREATEST(n_live_tup + n_dead_tup, 1), 2) AS dead_pct,
       pg_size_pretty(pg_total_relation_size(format('%I.%I', schemaname, relname)::regclass)) AS size,
       last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY dead_pct DESC LIMIT 10;
```

`dead_pct > 20%` 且表 > 1GB → 需要专门调整 autovacuum 参数或 `VACUUM FULL`。

### 4.2 全表扫描的表

```sql
SELECT schemaname, relname, seq_scan, idx_scan,
       seq_tup_read, idx_tup_fetch,
       round(seq_scan * 100.0 / GREATEST(seq_scan + idx_scan, 1), 2) AS seq_pct,
       pg_size_pretty(pg_relation_size(format('%I.%I', schemaname, relname)::regclass)) AS size
FROM pg_stat_user_tables
WHERE seq_scan > 0
ORDER BY seq_scan * pg_relation_size(format('%I.%I', schemaname, relname)::regclass) DESC
LIMIT 20;
```

`seq_pct > 50%` 且表 > 100MB → 检查是否缺索引（用 `pg_stat_statements` 找具体 SQL）。

### 4.3 HOT update 比例

```sql
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(n_tup_hot_upd * 100.0 / GREATEST(n_tup_upd, 1), 2) AS hot_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 1000
ORDER BY n_tup_upd DESC LIMIT 10;
```

HOT 比例低（< 50%）= 更新太多影响了索引列，或 FILLFACTOR 太满。调整：

```sql
ALTER TABLE orders SET (fillfactor = 90);
```

### 4.4 autovacuum 滞后

```sql
SELECT relname,
       now() - last_autovacuum AS since_last_vacuum,
       autovacuum_count, vacuum_count,
       n_dead_tup
FROM pg_stat_user_tables
WHERE last_autovacuum < now() - interval '1 day'
   OR last_autovacuum IS NULL
ORDER BY n_dead_tup DESC LIMIT 10;
```

## 第五章：pg_stat_user_indexes —— 找无用索引

```sql
SELECT schemaname, relname, indexrelname,
       idx_scan, idx_tup_read, idx_tup_fetch,
       pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE '%_pkey'             -- 主键不能删
  AND NOT EXISTS (                                -- 排除唯一约束
    SELECT 1 FROM pg_constraint 
    WHERE conindid = indexrelid AND contype IN ('p','u'))
ORDER BY pg_relation_size(indexrelid) DESC
LIMIT 30;
```

`idx_scan = 0` 且非主键 / 唯一约束 → **大概率可删**。注意：

- 仅在统计窗口内未使用，需 `stats_reset` 之后已运行足够时间（≥ 1 周）
- 部分索引（partial index）可能仅在特定查询使用
- 主从切换后从库统计独立，新主库需要重新观察

```sql
-- 看 stats 重置时间
SELECT stats_reset FROM pg_stat_database WHERE datname = current_database();

-- 删索引（先 INVALID 测试，再 DROP）
DROP INDEX CONCURRENTLY idx_orders_unused;
```

**重复索引检测**：

```sql
-- 同表同列的索引（可能重复）
SELECT pg_size_pretty(SUM(pg_relation_size(idx))::bigint) AS size,
       (array_agg(idx))[1] AS idx1, (array_agg(idx))[2] AS idx2,
       (array_agg(idx))[3] AS idx3, (array_agg(idx))[4] AS idx4
FROM (
  SELECT indexrelid::regclass AS idx,
         (indrelid::text || E'\n' || indclass::text || E'\n' ||
          indkey::text || E'\n' || coalesce(indexprs::text,'') || E'\n' ||
          coalesce(indpred::text,'')) AS key
  FROM pg_index) sub
GROUP BY key HAVING count(*) > 1
ORDER BY SUM(pg_relation_size(idx)) DESC;
```

## 第六章：pg_stat_replication / pg_stat_wal_receiver

### 6.1 主库视角：pg_stat_replication

```sql
SELECT pid, usename, application_name, client_addr,
       state, sync_state, sync_priority,
       sent_lsn, write_lsn, flush_lsn, replay_lsn,
       write_lag, flush_lag, replay_lag,
       pg_size_pretty(pg_wal_lsn_diff(sent_lsn, replay_lsn)) AS replay_diff
FROM pg_stat_replication;
```

| 字段 | 含义 |
|---|---|
| `state` | streaming / catchup / startup |
| `sync_state` | sync / async / quorum / potential |
| `sent_lsn` | 主库已发送到从库的 WAL 位置 |
| `write_lsn` | 从库已写到 OS（未必 fsync） |
| `flush_lsn` | 从库已 fsync 到磁盘 |
| `replay_lsn` | 从库已 redo 完成 |
| `write_lag / flush_lag / replay_lag` | 各阶段时间延迟（interval） |

**生产关注**：

```sql
-- 复制延迟（按字节）
SELECT application_name,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS lag_bytes,
       replay_lag
FROM pg_stat_replication;
```

`replay_lag > 30s` 或 `lag_bytes > 100MB` → 告警。

### 6.2 备库视角：pg_stat_wal_receiver

```sql
SELECT status, receive_start_lsn, written_lsn, flushed_lsn,
       latest_end_lsn, latest_end_time,
       conninfo, slot_name
FROM pg_stat_wal_receiver;
```

备库直接查"我延迟多少":

```sql
-- 备库执行
SELECT now() - pg_last_xact_replay_timestamp() AS lag,
       pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();
```

### 6.3 pg_replication_slots / pg_stat_replication_slots（PG 14+）

```sql
SELECT slot_name, slot_type, database, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag_size,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS lag_confirm
FROM pg_replication_slots;
```

**警告**：失活的复制槽 (`active = false`) 会让 WAL 永不删除 → 磁盘爆满。

```sql
-- 巡检：找超过 1GB 的滞后槽
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag
FROM pg_replication_slots
WHERE pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) > 1024*1024*1024;
```

发现失效的废弃槽 → `SELECT pg_drop_replication_slot('orphan_slot');`

PG 13+ 可设 `max_slot_wal_keep_size`（如 `100GB`）限制槽最多保留多少 WAL，避免无限增长。

## 第七章：pg_stat_progress_* —— 长操作进度

PG 9.6+ 起逐渐暴露长操作进度，避免"VACUUM 跑了 6 小时了不知道还有多久"。

### 7.1 VACUUM 进度

```sql
SELECT pid, datname, relid::regclass AS table, phase,
       heap_blks_total, heap_blks_scanned, heap_blks_vacuumed,
       index_vacuum_count,
       max_dead_tuples, num_dead_tuples
FROM pg_stat_progress_vacuum;
```

`phase` 取值：
- `initializing`
- `scanning heap`（扫描堆）
- `vacuuming indexes`（清理索引）
- `vacuuming heap`（清理堆）
- `cleaning up indexes`
- `truncating heap`
- `performing final cleanup`

进度估算：`heap_blks_scanned / heap_blks_total`。

### 7.2 CREATE INDEX 进度（PG 12+）

```sql
SELECT pid, datname, relid::regclass, command, phase,
       blocks_total, blocks_done,
       tuples_total, tuples_done,
       partitions_total, partitions_done
FROM pg_stat_progress_create_index;
```

### 7.3 ANALYZE 进度（PG 13+）

```sql
SELECT pid, relid::regclass, phase,
       sample_blks_total, sample_blks_scanned,
       ext_stats_total, ext_stats_computed,
       child_tables_total, child_tables_done
FROM pg_stat_progress_analyze;
```

### 7.4 BASEBACKUP 进度（PG 13+）

```sql
SELECT pid, phase, backup_total, backup_streamed,
       round(backup_streamed * 100.0 / NULLIF(backup_total, 0), 2) AS pct
FROM pg_stat_progress_basebackup;
```

### 7.5 COPY 进度（PG 14+）

```sql
SELECT pid, datname, relid::regclass, command, type,
       bytes_processed, bytes_total,
       tuples_processed, tuples_excluded
FROM pg_stat_progress_copy;
```

## 第八章：pg_stat_io（PG 16+）

PG 16 引入的"按对象 + 后端类型"切分的 IO 视图，**是过去十年最重要的监控改进之一**。

```sql
SELECT backend_type, object, context,
       reads, read_time, writes, write_time,
       writebacks, writeback_time, extends, extend_time,
       hits, evictions, reuses, fsyncs, fsync_time
FROM pg_stat_io
WHERE object IS NOT NULL;
```

| 字段 | 含义 |
|---|---|
| `backend_type` | client backend / autovacuum worker / walsender / checkpointer / bgwriter / startup / ... |
| `object` | relation / temp relation |
| `context` | normal / vacuum / bulkread / bulkwrite |
| `reads / writes` | 块数 |
| `read_time / write_time` | 毫秒（需开 `track_io_timing = on`） |

### 8.1 典型分析

```sql
-- 按后端类型看 IO 占比
SELECT backend_type,
       sum(reads) AS reads,
       pg_size_pretty(sum(reads) * 8192::bigint) AS read_size,
       sum(writes) AS writes,
       pg_size_pretty(sum(writes) * 8192::bigint) AS write_size
FROM pg_stat_io
GROUP BY backend_type
ORDER BY sum(reads) + sum(writes) DESC;
```

可能发现：

- `autovacuum worker` 写入巨大 → 调整 autovacuum cost
- `checkpointer` 写入暴涨 → checkpoint 风暴，调大 `max_wal_size`
- `client backend` 在 `bulkread` context 大量读 → 大查询频繁

### 8.2 开 track_io_timing

```sql
-- 先测开销（getrusage 调用）
SELECT pg_test_timing();
-- < 100 ns 安全开

ALTER SYSTEM SET track_io_timing = on;
SELECT pg_reload_conf();
```

开启后 `read_time` / `write_time` 才有数据，能算 IO 延迟：

```sql
SELECT backend_type, context,
       sum(read_time) / nullif(sum(reads), 0) AS avg_read_ms,
       sum(write_time) / nullif(sum(writes), 0) AS avg_write_ms
FROM pg_stat_io
WHERE reads + writes > 0
GROUP BY backend_type, context
ORDER BY avg_read_ms DESC;
```

## 第九章：pg_stat_statements —— TOP SQL

**头号慢 SQL 定位工具**。安装：

```sql
-- postgresql.conf
shared_preload_libraries = 'pg_stat_statements'
pg_stat_statements.max = 10000
pg_stat_statements.track = all       -- all / top / none
pg_stat_statements.track_utility = on
pg_stat_statements.save = on

-- 创建扩展
CREATE EXTENSION pg_stat_statements;
```

### 9.1 关键字段

```sql
SELECT queryid, calls,
       total_exec_time, mean_exec_time, max_exec_time, stddev_exec_time,
       rows,
       shared_blks_hit, shared_blks_read,
       shared_blks_dirtied, shared_blks_written,
       temp_blks_read, temp_blks_written,
       blk_read_time, blk_write_time,
       wal_records, wal_fpi, wal_bytes,
       query
FROM pg_stat_statements;
```

PG 13+ 区分 `plan_time` 与 `exec_time`：

| 字段 | 含义 |
|---|---|
| `total_plan_time` | 累计规划时间 |
| `total_exec_time` | 累计执行时间 |
| `mean_exec_time` | 平均单次 |
| `wal_records` | 产生 WAL 记录数 |
| `wal_bytes` | 产生 WAL 字节 |

### 9.2 按多维度排序

```sql
-- 总耗时 TOP 10
SELECT round(total_exec_time::numeric, 2) AS total_ms,
       calls, round(mean_exec_time::numeric, 2) AS mean_ms,
       round(100 * total_exec_time / sum(total_exec_time) OVER (), 2) AS pct,
       left(query, 100) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 10;
```

```sql
-- 平均最慢 TOP 10
SELECT round(mean_exec_time::numeric, 2) AS mean_ms,
       calls, round(total_exec_time::numeric, 2) AS total_ms,
       left(query, 100) AS query
FROM pg_stat_statements
WHERE calls > 100
ORDER BY mean_exec_time DESC LIMIT 10;
```

```sql
-- 产生 WAL 最多 TOP 10
SELECT pg_size_pretty(wal_bytes) AS wal, wal_records, calls,
       left(query, 100) AS query
FROM pg_stat_statements
ORDER BY wal_bytes DESC LIMIT 10;
```

```sql
-- 临时文件最多 TOP 10
SELECT temp_blks_written * 8 AS temp_kb, calls,
       left(query, 100) AS query
FROM pg_stat_statements
WHERE temp_blks_written > 0
ORDER BY temp_blks_written DESC LIMIT 10;
```

### 9.3 重置统计

```sql
SELECT pg_stat_statements_reset();
-- 或仅清除某 query
SELECT pg_stat_statements_reset(0, 0, 4567890);
```

生产建议**每周自动重置**，避免老数据干扰。

### 9.4 与 auto_explain 配合

`pg_stat_statements` 只给"哪个 SQL 慢"，`auto_explain` 给"这次为什么慢"的实际执行计划：

```sql
-- postgresql.conf

auto_explain.log_min_duration = 1000
auto_explain.log_analyze = on
auto_explain.log_buffers = on
auto_explain.log_format = 'json'
auto_explain.sample_rate = 0.1
```

日志中会出现：

```

{
  "Query Text": "SELECT ...",
  "Plan": {
    "Node Type": "Seq Scan",
    "Relation Name": "orders",
    ...
  }
}
```

## 第十章：表 / 索引大小与膨胀检测

### 10.1 大小函数家族

| 函数 | 返回 |
|---|---|
| `pg_relation_size(oid)` | 主 fork 大小（堆/索引数据） |
| `pg_table_size(oid)` | 表 + TOAST + FSM + VM |
| `pg_indexes_size(oid)` | 该表所有索引合计 |
| `pg_total_relation_size(oid)` | 表 + 所有索引 + TOAST |
| `pg_database_size(name)` | 单库 |
| `pg_tablespace_size(name)` | 表空间 |

```sql
-- TOP 10 大表
SELECT schemaname, relname,
       pg_size_pretty(pg_total_relation_size(format('%I.%I', schemaname, relname)::regclass)) AS total,
       pg_size_pretty(pg_relation_size(format('%I.%I', schemaname, relname)::regclass)) AS table_only,
       pg_size_pretty(pg_indexes_size(format('%I.%I', schemaname, relname)::regclass)) AS indexes,
       pg_size_pretty(pg_total_relation_size(format('%I.%I', schemaname, relname)::regclass) -
                      pg_relation_size(format('%I.%I', schemaname, relname)::regclass) -
                      pg_indexes_size(format('%I.%I', schemaname, relname)::regclass)) AS toast
FROM pg_stat_user_tables
ORDER BY pg_total_relation_size(format('%I.%I', schemaname, relname)::regclass) DESC
LIMIT 10;
```

### 10.2 表膨胀检测

简单版（pg_stat_user_tables）：

```sql
SELECT relname, n_live_tup, n_dead_tup,
       round(n_dead_tup * 100.0 / GREATEST(n_live_tup + n_dead_tup, 1), 2) AS dead_pct
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY dead_pct DESC;
```

精确版（`pgstattuple` 扩展）：

```sql
CREATE EXTENSION pgstattuple;

SELECT * FROM pgstattuple('orders');
-- table_len, tuple_count, tuple_len, tuple_percent,
-- dead_tuple_count, dead_tuple_len, dead_tuple_percent,
-- free_space, free_percent

-- 不锁表的近似版（PG 9.5+）
SELECT * FROM pgstattuple_approx('orders');
```

### 10.3 索引膨胀检测

```sql
-- pgstattuple 看 B-tree 内部状态
SELECT * FROM pgstatindex('idx_orders_userid');
-- version, tree_level, index_size, root_block_no,
-- internal_pages, leaf_pages, empty_pages, deleted_pages,
-- avg_leaf_density, leaf_fragmentation
```

`avg_leaf_density < 50` 或 `leaf_fragmentation > 30` → 重建索引：

```sql
REINDEX INDEX CONCURRENTLY idx_orders_userid;
```

PG 12+ 支持 `REINDEX CONCURRENTLY`，不阻塞 DML。

### 10.4 社区膨胀检测脚本

[ioguix/pgsql-bloat-estimation](https://github.com/ioguix/pgsql-bloat-estimation) 是基于统计信息估算膨胀的著名脚本，**不需要扫描整表**：

```sql
-- 节选：表膨胀估算
SELECT current_database(), schemaname, tblname,
       bs * tblpages AS real_size,
       (tblpages - est_tblpages_ff) * bs AS bloat_size,
       CASE WHEN tblpages - est_tblpages_ff > 0
            THEN 100 * (tblpages - est_tblpages_ff) / tblpages::float
            ELSE 0 END AS bloat_ratio
FROM (...);
```

## 第十四章：告警阈值

生产 8 个**必设**告警：

| # | 告警项 | 阈值 | 严重度 |
|---|---|---|---|
| 1 | 实例不可用（`pg_up == 0`） | 任何 | P0 |
| 2 | 连接数 | > 80% of max_connections | P1 |
| 3 | 复制延迟（bytes） | > 1GB | P1 |
| 4 | 复制延迟（time） | > 60s | P1 |
| 5 | wraparound age | > 1.5 亿 | P1（> 1.8 亿 P0） |
| 6 | 磁盘剩余 | < 20% | P1（< 10% P0） |
| 7 | 长事务 | > 30min | P2 |
| 8 | 死锁速率 | > 1/min | P2 |

进阶告警（视场景）：

| # | 告警项 | 阈值 |
|---|---|---|
| 9 | 缓存命中率 | OLTP < 95% |
| 10 | 锁等待会话 | > 10 |
| 11 | 临时文件速率 | > 100MB/min |
| 12 | autovacuum 落后表数 | > 5（dead_pct > 30%） |
| 13 | checkpoint_req / checkpoint_timed 比例 | > 0.5 |
| 14 | WAL 生成速率突变 | > 历史 3 倍 |
| 15 | 复制槽失活 | active = false 且 > 1GB lag |

Prometheus 告警规则示例：

```yaml
groups:
- name: postgres
  rules:
  - alert: PostgresDown
    expr: pg_up == 0
    for: 1m
    labels:
      severity: critical
    annotations:
      summary: "PostgreSQL {{ $labels.instance }} 不可达"

  - alert: PostgresTooManyConnections
    expr: sum(pg_stat_activity_count) by (instance) > 
          on(instance) (pg_settings_max_connections * 0.8)
    for: 5m
    labels: { severity: warning }

  - alert: PostgresReplicationLag
    expr: pg_replication_lag_seconds > 60
    for: 5m
    labels: { severity: warning }

  - alert: PostgresWraparoundDanger
    expr: pg_wraparound_age > 150000000
    for: 5m
    labels: { severity: warning }

  - alert: PostgresWraparoundCritical
    expr: pg_wraparound_age > 180000000
    for: 1m
    labels: { severity: critical }
```

## 生产实践

### 1. 监控的"四象限"

| | 实时（< 5s 延迟） | 周期采样（分钟级） |
|---|---|---|
| **快照** | `pg_stat_activity` / `pg_locks` / `pg_blocking_pids()` | `pg_stat_user_tables` 全量 |
| **累积** | Prometheus rate() | pg_stat_statements 周报 |

### 2. 监控用户最小权限

```sql
CREATE USER monitor WITH PASSWORD 'xxx';
GRANT pg_monitor TO monitor;        -- 一次给全
-- 或细粒度：
-- GRANT pg_read_all_stats TO monitor;
-- GRANT pg_read_all_settings TO monitor;
```

不要给 superuser！

### 3. log_min_duration_statement 怎么设

| 场景 | 阈值 |
|---|---|
| 调试期、低流量 | 0（全记） |
| 生产初期 | 100ms |
| 高 QPS 生产 | 1000ms |
| 极高 QPS 生产 | 5000ms + 抽样 |

抽样：

```ini
log_min_duration_sample          = 100ms        # 100ms 以上抽样
log_statement_sample_rate        = 0.1          # 10% 抽样
log_transaction_sample_rate      = 0            # 关
```

### 4. 监控覆盖优先级

不要追求"监控一切"。优先级：

1. **可用性**（pg_up）→ 30s 内告警
2. **资源**（CPU、内存、磁盘）→ 5min 趋势
3. **连接 / 锁**（pg_stat_activity）→ 1min 快照
4. **复制 / WAL**（pg_stat_replication / pg_replication_slots）→ 30s
5. **wraparound** → 1h 即可（演变慢）
6. **TOP SQL**（pg_stat_statements）→ 每日报告
7. **表健康**（dead_tup / seq_scan）→ 每日报告

### 5. 数据保留策略

| 数据 | 保留期 |
|---|---|
| Prometheus 原始指标 | 15 天 |
| Prometheus 聚合（5min） | 90 天 |
| pgBadger 报告 | 永久 |
| 慢查询日志 | 7 天 |
| pg_stat_statements snapshot | 30 天 |

### 6. 演练：故障注入

定期演练（每季度）：

- 拔网线，看从库切换
- kill 主库进程，看 Patroni 选主
- 关掉 autovacuum 跑 1 周，看膨胀监控是否告警
- 制造长事务，看告警时延

监控如果在演练时不响、不准——它不是监控，是装饰。

## 陷阱清单

| # | 陷阱 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 只看 `pg_stat_activity`，不看历史 | 错过周期性问题 | 周期采样存历史 |
| 2 | 监控 CPU / 内存而不监控 PG 内部 | "机器没事，但用户慢" | 必看 wait events |
| 3 | `pg_stat_statements` 没启用 | 慢 SQL 全靠日志大海捞针 | 必装 |
| 4 | 不监控复制槽 lag | 槽失活 → WAL 爆磁盘 | 必告警 |
| 5 | 不监控 wraparound age | 突然到 21 亿强制只读 | 1.5/1.8 亿告警 |
| 6 | `log_min_duration_statement = 0` 在高 QPS | 日志爆盘 / IO 翻倍 | 1000ms + 抽样 |
| 7 | 用 superuser 跑 exporter | 安全风险 | 用 `pg_monitor` |
| 8 | 监控只覆盖主库 | 备库读慢、复制断不知道 | 主备都装 exporter |
| 9 | 没有 `idle_in_transaction_session_timeout` | 应用 bug → VACUUM 全失败 | 必设 5min |
| 10 | 死锁告警阈值太高 | 频繁死锁不报警 | > 1/min |
| 11 | 不监控临时文件 | 大查询溢出磁盘不知道 | `log_temp_files = 10MB` |
| 12 | `pg_stat_io` 用了但没开 `track_io_timing` | 看不到 IO 延迟 | 开 |
| 13 | autovacuum 监控只看次数 | 不看"是否真清掉了" | 看 n_dead_tup 趋势 |
| 14 | 没有阻塞链监控 | 一个会话卡死全库不知道 | `pg_blocking_pids()` 告警 |
| 15 | `pg_stat_statements` 不定期重置 | 老数据混淆趋势 | 周重置 |
| 16 | 用 `count(*) FROM pg_stat_user_tables` 而非视图字段 | 性能差 / 误读 | 直接查字段 |
| 17 | 监控间隔 60s | 错过 30s 内的尖峰 | 关键指标 10-15s |
| 18 | 备库不查 `pg_stat_database_conflicts` | 复制冲突累积 | 必看 |
| 19 | 备份不监控 | 静默失败，恢复时崩 | 必告警 `pg_stat_archiver.last_failed_time` |
| 20 | 告警风暴时无静默机制 | DBA 麻木 | Alertmanager 抑制规则 |

## 2026 现状

### 1. PG 17 暴露更多 wait event

PG 17 把内部多个 LWLock 命名暴露到 `pg_wait_events` 系统视图，让"等啥锁"更清晰。诊断套路：

```sql
SELECT * FROM pg_wait_events WHERE type = 'LWLock' ORDER BY name;
```

### 2. PG 16 的 pg_stat_io 已成标配

绝大多数 2024 后建的监控栈都默认收 `pg_stat_io`。看 `bgwriter` vs `checkpointer` vs `client backend` 写入占比，能立即诊断 checkpoint 风暴 / autovacuum 风暴 / 大 SQL 写。

### 3. EXPLAIN ANALYZE 增加 CPU/IO 细分（PG 18）

PG 18 的 `EXPLAIN (ANALYZE, BUFFERS)` 在每个节点显示 CPU 时间分解（user / system），辅助判断是 CPU 瓶颈还是 IO 瓶颈。

### 4. pganalyze、Datadog、New Relic 全面支持 PG 18

主流 SaaS 监控都已支持 PG 18 的新视图字段。

### 5. CloudNativePG 标配 Prometheus + Grafana

K8s 上的 PG 部署，CloudNativePG Operator 自带 `PodMonitor` + Grafana ConfigMap，开箱即用。

### 6. pgwatch3（2024）替代 pgwatch2

pgwatch3 重写了存储后端（默认 Postgres），更轻量，支持 Kubernetes Operator 部署。

### 7. eBPF 加入工具链

`bpftrace` / `bcc` 工具可以在内核层观察 PG 进程：

```bash
# 看 PG backend 的 syscalls
bpftrace -e 'tracepoint:syscalls:sys_enter_*{ @[pid] = count(); }' -p $(pgrep postgres)
```

社区 [pgsnap-ebpf](https://github.com/cybertec-postgresql) 等工具崛起。

### 8. AI 辅助诊断

pganalyze 已经接入 LLM 给出"问题摘要 + 修复建议"。社区有 [pgwatch-ai](https://github.com/) 类项目把指标喂 LLM 生成自然语言报告。

## 练习题

### 练习 1：找阻塞元凶

下午 14:30 收到告警："大量 UPDATE 等待"。写一个 SQL 找出**根源会话**（处于最顶层、被多个会话等待的 PID）。

<details><summary>参考答案</summary>

```sql
WITH blocking AS (
  SELECT a.pid AS blocker_pid,
         a.usename, a.application_name,
         now() - a.xact_start AS xact_duration,
         a.state, a.query AS blocker_query,
         array_agg(b.pid) AS blocked_pids,
         count(b.pid) AS blocked_count
  FROM pg_stat_activity a
  JOIN pg_stat_activity b ON a.pid = ANY(pg_blocking_pids(b.pid))
  WHERE NOT cardinality(pg_blocking_pids(a.pid)) > 0  -- a 本身不被阻塞
  GROUP BY a.pid, a.usename, a.application_name, a.xact_start, a.state, a.query
)
SELECT * FROM blocking ORDER BY blocked_count DESC;
```

输出最顶层的"罪魁祸首"——它阻塞了多少会话。
</details>

### 练习 2：缓存命中率诊断

`SELECT sum(blks_hit)*100.0/sum(blks_hit+blks_read) FROM pg_stat_database;` 返回 85%。

a. 这正常吗？  
b. 还需要看什么辅助判断？  
c. 优化方向有哪些？  

<details><summary>参考答案</summary>

a. **OLTP 不正常**（应 > 99%）；**OLAP 偏低但可接受**。需结合业务类型判断。

b. 辅助：
   - 看 `pg_statio_user_tables.heap_blks_hit` vs `heap_blks_read`，找哪个表读盘最多
   - 看系统层 `iostat -x 1` 实际磁盘 IO（PG 的 read 可能命中 OS Page Cache）
   - 看 `shared_buffers` 大小 vs 库总大小

c. 优化：
   - shared_buffers 加大（25% 物理内存）
   - 增加内存
   - 删除/合并冷数据（分区 + 归档）
   - 大查询用 effective_io_concurrency 加并行预取
   - 用 BRIN / 部分索引减少索引页占用
</details>

### 练习 3：复制槽炸盘

主库磁盘告警 90% 使用，发现 `pg_wal` 占了 200GB。怎么排查？

<details><summary>参考答案</summary>

```sql
-- 1. 看复制槽
SELECT slot_name, slot_type, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag
FROM pg_replication_slots
ORDER BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC;

-- 2. 看归档
SELECT * FROM pg_stat_archiver;
-- last_archived_wal vs last_failed_wal
-- 如果 archive_command 失败 → WAL 不会被清

-- 3. 看 WAL 配置
SHOW wal_keep_size;       -- PG 13+
SHOW max_slot_wal_keep_size;
SHOW archive_mode;
SHOW archive_command;
```

修复：
- 失活槽 → `pg_drop_replication_slot('xxx')`
- 归档失败 → 检查 archive_command 脚本（如 S3 上传脚本）
- 设 `max_slot_wal_keep_size = 100GB` 防止再爆
</details>

### 练习 4：无用索引清理

写 SQL 找出"过去 30 天未使用、非主键非唯一、大于 100MB"的索引。

<details><summary>参考答案</summary>

```sql
SELECT s.schemaname, s.relname AS table_name, s.indexrelname AS index_name,
       s.idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS index_size,
       d.stats_reset
FROM pg_stat_user_indexes s
JOIN pg_stat_database d ON d.datname = current_database()
WHERE s.idx_scan = 0
  AND pg_relation_size(s.indexrelid) > 100 * 1024 * 1024
  AND s.indexrelname NOT LIKE '%_pkey'
  AND NOT EXISTS (
    SELECT 1 FROM pg_constraint 
    WHERE conindid = s.indexrelid AND contype IN ('p','u'))
  AND d.stats_reset < now() - interval '30 days'
ORDER BY pg_relation_size(s.indexrelid) DESC;
```

注意 `stats_reset` 判断：必须有足够长统计窗口才能下"无用"结论。
</details>

### 练习 5：wraparound 紧急处置

`SELECT datname, age(datfrozenxid) FROM pg_database;` 显示某库 `xid_age = 195000000`（1.95 亿），距 2.1 亿强制只读还有 15M XID。怎么紧急处理？

<details><summary>参考答案</summary>

1. 立即停长事务（最重要）：
   ```sql
   SELECT pid, xact_start, query FROM pg_stat_activity
   WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 10;
   -- 必要时 pg_terminate_backend()
   ```

2. 查找老复制槽（也会阻 freeze）：
   ```sql
   SELECT slot_name, xmin, age(xmin) FROM pg_replication_slots;
   ```

3. 找出最老 xid 的表：
   ```sql
   SELECT c.oid::regclass AS table, age(c.relfrozenxid) AS xid_age
   FROM pg_class c WHERE c.relkind IN ('r','t','m')
   ORDER BY age(c.relfrozenxid) DESC LIMIT 10;
   ```

4. 紧急 freeze（手动）：
   ```sql
   VACUUM (FREEZE, VERBOSE) old_table;
   ```

5. 调高 autovacuum 信用：
   ```sql
   ALTER SYSTEM SET autovacuum_vacuum_cost_limit = 10000;
   ALTER SYSTEM SET autovacuum_max_workers = 8;
   SELECT pg_reload_conf();
   ```

6. 监控 `age(datfrozenxid)` 直到回落到安全值（< 1 亿）。
</details>

### 练习 6：pg_stat_statements 维度

写出三个 SQL，分别按"总耗时"、"产生 WAL 最多"、"临时文件最多"找 TOP 10 SQL。

<details><summary>参考答案</summary>

```sql
-- 总耗时
SELECT round(total_exec_time::numeric, 2) AS total_ms, calls,
       round(mean_exec_time::numeric, 2) AS mean_ms,
       round(100*total_exec_time/sum(total_exec_time) OVER (), 2) AS pct,
       left(query, 100) AS q
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

-- WAL
SELECT pg_size_pretty(wal_bytes) AS wal, wal_records, calls,
       round((wal_bytes/calls)::numeric, 0) AS wal_per_call,
       left(query, 100) AS q
FROM pg_stat_statements WHERE wal_bytes > 0
ORDER BY wal_bytes DESC LIMIT 10;

-- 临时文件
SELECT pg_size_pretty((temp_blks_written*8192)::bigint) AS temp,
       calls, left(query, 100) AS q
FROM pg_stat_statements WHERE temp_blks_written > 0
ORDER BY temp_blks_written DESC LIMIT 10;
```
</details>

### 练习 7：wait event 分析

某时段 P99 延迟突增。`pg_stat_activity` 抽样显示 80% 会话 `wait_event_type = 'IO'`、`wait_event = 'DataFileRead'`，20% 是 `LWLock / WALWrite`。诊断方向？

<details><summary>参考答案</summary>

`IO.DataFileRead` 占 80% → 大量缓存未命中读盘。可能原因：

1. shared_buffers 太小或冷启动
2. 业务突然访问冷数据（如运营推送）
3. 大查询挤掉热点（用 `pg_buffercache` 看）

`LWLock.WALWrite` 占 20% → WAL 写入瓶颈：

1. WAL 磁盘 IOPS 不够（单独 SSD？）
2. `wal_buffers` 太小
3. `synchronous_commit = on` 且 fsync 慢

诊断步骤：

- `pg_stat_io` 看 reads / writes 大头是谁
- `pg_stat_statements` 看是否新 SQL 涌入
- `pg_buffercache` 看 buffer pool 内容
- iostat / dstat 看磁盘 utilization 与延迟
- 临时 `SET work_mem` 测试是否大查询挤热数据
</details>

### 练习 8：监控用户最小化

写 SQL 创建一个仅用于 `postgres_exporter` 的最小权限用户。

<details><summary>参考答案</summary>

```sql
CREATE USER monitor WITH PASSWORD 'secret_change_me' 
  NOSUPERUSER NOCREATEDB NOCREATEROLE LOGIN;

-- 核心：PG 10+ 内置的 pg_monitor 角色
GRANT pg_monitor TO monitor;

-- 连接权限
GRANT CONNECT ON DATABASE postgres TO monitor;
GRANT CONNECT ON DATABASE shop TO monitor;

-- pg_stat_statements
GRANT SELECT ON pg_stat_statements TO monitor;
-- PG 14+ 自动包含在 pg_monitor 中

-- 自定义视图（如有）
GRANT USAGE ON SCHEMA mon TO monitor;
GRANT SELECT ON ALL TABLES IN SCHEMA mon TO monitor;
```

pg_hba.conf 限定来源：

```
host    all    monitor    10.0.0.0/8    scram-sha-256
```

绝对不要给 `superuser`、`CREATEROLE`、`REPLICATION`。
</details>
