# 精通 Python 对象内存优化

> Python 对象"贵"——一个 `int` 不止 4 字节、一个空对象也占上百字节。海量对象场景(几百万条记录)内存能轻易爆掉。本篇讲清对象的内存开销与优化手段:`__slots__`、缓存/intern、紧凑结构。依赖 [P09 __slots__](./P09-精通-Python-类与属性查找.md)、[P16 内存](./P16-精通-Python-内存管理与GC.md)。
>
> **📅 基准:2026 年 6 月,CPython 3.13 / 3.14。**

---

## 一、Python 对象很"贵"

Python 一切皆对象(见 [P01](./P01-精通-Python-数据模型与对象.md)),每个对象都带额外开销:

- **对象头**:每个对象至少有引用计数(`ob_refcnt`)+ 类型指针(`ob_type`),几十字节起步。
- **一个 `int` 不是 4 字节**:`sys.getsizeof(0)` 约 24-28 字节(含对象头 + 值);大整数更多。
- **普通实例有 `__dict__`**:每个实例自带一个字典存属性,字典本身开销不小。

```python
import sys
sys.getsizeof(0)            # ≈ 24-28
sys.getsizeof([])          # 空 list ≈ 56
sys.getsizeof({})          # 空 dict ≈ 64
```

所以"几百万个小对象"的内存可能远超直觉——优化内存就是减少**每对象的固定开销**和**避免冗余对象**。

---

## 二、`__slots__`:去掉实例字典

最有效的单对象优化:用 `__slots__`(见 [P09](./P09-精通-Python-类与属性查找.md))声明固定属性,让实例**不再有 `__dict__`**,改用紧凑的定长槽位存储:

```python
class PointDict:                 # 普通类:每实例一个 __dict__
    def __init__(self, x, y): self.x, self.y = x, y

class PointSlots:
    __slots__ = ("x", "y")       # 无 __dict__,省内存
    def __init__(self, x, y): self.x, self.y = x, y
# 海量实例时 PointSlots 能省 ~40-50% 内存
```

- **省内存 + 略快**:去掉 dict 开销,属性走固定偏移。
- **代价**:不能动态加属性、无 `__dict__`/`__weakref__`(需显式加)、不被子类自动继承、多继承受限(见 [P09](./P09-精通-Python-类与属性查找.md))。
- 适合**字段固定、数量巨大**的类;`@dataclass(slots=True)`(3.10+)自动加。

---

## 三、小整数缓存与字符串 intern

CPython 复用一些不可变对象,减少重复创建:

- **小整数缓存**:**-5 ~ 256** 的整数对象被**预先创建并缓存**,这个范围的整数字面量复用同一对象(所以 `256 is 256` 为 True、`257 is 257` 可能 False,见 [P01](./P01-精通-Python-数据模型与对象.md))。
- **字符串 intern(驻留)**:相同内容字符串共享同一对象;**像标识符的字符串**(变量名样式)会被**自动 intern**;可用 `sys.intern(s)` **手动驻留**高频重复字符串(如解析大量重复 key 时),省内存 + 加速 `==`(先比身份)。

```python
import sys
keys = [sys.intern(k) for k in raw_keys]   # 大量重复 key:intern 后只存一份
```

这是"减少冗余对象"的优化,但**不要据此用 `is` 比较值**(缓存/intern 是优化、不是语义保证)。

## 四、`sys.getsizeof` 的真相

`sys.getsizeof(obj)` 返回对象**自身**的浅层大小,**不递归计算它引用的对象**:

```python
sys.getsizeof([1, 2, 3])    # 只算 list 容器本身(指针数组),不含 1/2/3 的大小
```

所以一个"装了一堆大对象的 list",`getsizeof` 看着小,实际占用大。要算**深层总占用**得递归(或用 `pympler.asizeof`、`tracemalloc`)。内存分析别只看 `getsizeof`。

## 五、紧凑数据结构

对**大量同质数据**,用紧凑结构替代"list of 对象"能省几个数量级:

| 场景 | 别用 | 改用 |
|---|---|---|
| 大量同类型数字 | `list[int]`(每个 int 是对象,几十字节) | `array.array("i", ...)`、**NumPy `ndarray`**(连续原始字节,几字节/元素) |
| 二进制数据 | `list[int]` 表示字节 | `bytes`/`bytearray` |
| 固定结构二进制 | 对象 | `struct` 打包 |
| 海量小记录 | 普通类实例 | `__slots__` 类、`namedtuple`、或列式存储(NumPy/pandas) |

```python
import numpy as np
data = np.zeros(10_000_000, dtype=np.int32)   # 4 字节/元素,连续内存
# 等价的 list 会是它的 5-10 倍内存(每个 int 都是独立 Python 对象)
```

NumPy 不仅省内存,还能**向量化**计算(见 [P19](./P19-精通-Python-性能剖析与优化.md)),是数据/科学计算的内存与性能基石。

## 六、其他省内存手段

- **生成器/惰性**(见 [P05](./P05-精通-Python-迭代器与生成器.md)):流式处理大数据,不一次性装进内存(`(x for x in ...)` 而非 `[...]`)。
- **`__slots__` + 海量实例**:ORM 结果、缓存条目等用 slots 类。
- **及时释放引用**:大对象用完 `del` 或让其离开作用域,助引用计数即时回收(见 [P16](./P16-精通-Python-内存管理与GC.md));注意全局缓存/闭包别意外长期持有。
- **`functools.lru_cache` 设上限**:无界缓存会持续涨(见 [P06](./P06-精通-Python-装饰器与上下文管理器.md))。
- **列式存储 / 分块处理**:大数据用 pandas/Polars/分批读取,而非全量加载。

---

## 陷阱清单

- **以为 Python int/对象很小**:一个 int ≈ 24+ 字节,空对象上百字节;海量对象内存爆炸。
- **海量同质数字用 list**:每个数字是独立对象,比 array/NumPy 多耗几倍内存;用 NumPy。
- **`__slots__` 不被子类继承**:子类不声明就又有 `__dict__`,优化失效。
- **只看 `sys.getsizeof`**:它是浅层大小,不含引用对象;深层占用要递归/工具测。
- **依赖小整数缓存/intern 用 `is` 比值**:是优化不是语义,结果不可靠(见 [P01](./P01-精通-Python-数据模型与对象.md))。
- **全局缓存无上限**:内存持续增长(隐性泄漏);设上限或用弱引用(见 [P16](./P16-精通-Python-内存管理与GC.md))。
- **过早内存优化**:先测真实占用再优化;`__slots__`/NumPy 用在真正的内存热点上。

## 2026 现状

- **`@dataclass(slots=True)`** 是定义省内存数据类的便捷方式;海量对象场景广泛用 slots。
- **NumPy / pandas / Polars** 是处理大规模数值/表格数据的标准,列式 + 紧凑 dtype 大幅省内存且向量化快。
- **`tracemalloc`** 是定位内存增长来源的首选工具(对比快照);`pympler`、`objgraph` 辅助分析对象图。
- **free-threading(见 [P17](./P17-精通-Python-GIL原理.md))** 下"不朽对象(immortal objects)"等机制也涉及对象内存布局的调整。
- 与 Java 对照([J20](../java/INDEX.md)):Java 有对象头/压缩指针/逃逸分析等;Python 的 `__slots__` 类似"去掉动态字段表"、NumPy 类似"原始数组/堆外紧凑存储",思路相通——海量小对象都要避免每对象的固定开销。

## 练习题

1. 为什么说 Python 对象"很贵"?一个 int 占多少内存?

<details><summary>参考答案</summary>

因为 Python 中**一切皆对象**(见 P01),每个值——哪怕是一个整数、一个布尔——都是一个完整的**堆上对象**,带有固定的"对象头"开销,而不是像 C/Java 基本类型那样紧凑的几字节原始值。每个 CPython 对象至少包含:**引用计数字段 `ob_refcnt`**(用于内存管理,见 P16)和**类型指针 `ob_type`**(指向它的类型对象),再加上该类型自己的数据。所以即使一个很小的值,对象头就已经占了不少空间。具体到 **int**:`sys.getsizeof(0)` 在 64 位 CPython 上约为 **24-28 字节**(对象头 + 存储数字的字段),而且 Python 的 int 是**任意精度**的,数值越大占用越多(按需扩展);相比之下 C 的 `int` 只有 4 字节。其他例子:空 `list` 约 56 字节、空 `dict` 约 64 字节、一个普通自定义类的实例还要额外带一个 `__dict__`(实例属性字典,又是几十上百字节)。**含义**:当你需要创建**几百万个**小对象(如几百万条记录、几百万个坐标点、把大文件每个数字都做成 Python int)时,光是"每对象的固定开销"累加起来就可能占用远超数据本身的内存,轻易就把内存撑爆。这正是内存优化的出发点——要么**减少每个对象的固定开销**(如用 `__slots__` 去掉实例 dict)、要么**用紧凑结构避免"一值一对象"**(如用 `array`/NumPy 把上百万个数字存成连续的原始字节,每个只占几字节而非几十字节)、要么**用惰性/流式处理避免同时持有海量对象**(生成器)。理解"对象贵"才能解释为什么 Python 处理大规模数值数据要依赖 NumPy 而非原生 list。

</details>

2. `__slots__` 为什么能省内存?用它有什么代价?

<details><summary>参考答案</summary>

**省内存原理**:默认情况下,Python 每个实例都拥有一个 **`__dict__`(实例字典)**来存放它的属性,这让对象可以动态添加任意属性,但字典本身有可观的内存开销(哈希表结构、预留空间等),每个实例都要带一份。当类定义了 **`__slots__`**(一个固定的属性名序列)后,CPython **不再为实例创建 `__dict__`**,而是为这些声明的属性在对象内部分配**固定的、紧凑的槽位**(类似 C 结构体字段,通过描述符按固定偏移访问)。这样每个实例省掉了整个字典的开销,只为确定的几个属性留出紧凑空间,**对于需要创建大量实例的场景能节省相当可观的内存**(常见可省 40%-50% 甚至更多),属性访问也略快。**代价/限制**:①**不能动态添加未声明的属性**——给实例赋一个不在 `__slots__` 里的属性会报 `AttributeError`(这也带来一个好处:能捕获拼错属性名的 bug);②**实例没有 `__dict__`**——一些依赖 `__dict__` 的功能(如 `vars(obj)`、某些序列化/调试工具、给实例随意挂属性)受影响;③**默认没有 `__weakref__`**——实例不能被弱引用,需要的话要把 `"__weakref__"` 也写进 slots;④**不被子类自动继承**——如果子类没有定义自己的 `__slots__`,子类实例又会获得 `__dict__`,省内存效果消失;要让继承链都省内存,每层都要声明 slots;⑤**多继承限制**——多个基类都有非空 `__slots__` 时会冲突;⑥与 `@cached_property` 等需要写实例 dict 的特性冲突。**适用场景**:字段固定、数量巨大、对内存/性能敏感的数据类(如海量记录、缓存条目、坐标点)。现代可用 `@dataclass(slots=True)`(3.10+)自动生成带 slots 的数据类,省去手写。

</details>

3. 什么是小整数缓存和字符串 intern?它们为了什么?能用 `is` 比较吗?

<details><summary>参考答案</summary>

二者都是 CPython **复用不可变对象以节省内存、加速比较**的优化。**小整数缓存(small int cache)**:CPython 在解释器启动时**预先创建并缓存了 -5 到 256 之间的所有整数对象**,程序中这个范围内的整数字面量都**复用同一个缓存对象**,而不是每次新建。原因是这些小整数极其常用(循环计数、索引、小数值),复用它们能避免大量重复的对象创建、节省内存和分配开销。这导致 `a=256; b=256; a is b` 为 True(同一缓存对象),而 `257 is 257` 可能为 False(超出缓存范围、是不同对象)。**字符串 intern(驻留)**:CPython 让**内容相同的某些字符串共享同一个对象**;特别是**看起来像标识符的字符串**(只含字母数字下划线、像变量名的)会被**自动 intern**,此外可以用 `sys.intern(s)` **手动驻留**一个字符串。目的:①**省内存**——大量重复出现的字符串(如解析数据时反复出现的字段名/键名)只在内存里存一份;②**加速比较**——intern 后相等的字符串是同一对象,`==` 可以先做身份(指针)比较快速判定。所以处理有大量重复字符串的场景(如 JSON 解析、列名)时,`sys.intern` 能优化内存和速度。**关键警告:绝对不能依赖小整数缓存/intern,用 `is` 来比较"值是否相等"**——这些都是**实现层面的优化,不是语言语义保证**:缓存范围、是否被 intern、在不同上下文/编译单元/Python 实现下都可能不同,`is` 比较值的结果是不可靠、不可移植的。值相等永远用 `==`;`is` 只用于判断"是否同一对象"或与单例(None 等)比较(见 P01)。

</details>

4. `sys.getsizeof` 返回的是对象的真实总占用吗?

<details><summary>参考答案</summary>

**不是**。`sys.getsizeof(obj)` 返回的是对象**自身的浅层(shallow)大小**——即这个对象本体在内存中占用的字节数,**但它不会递归地把该对象所引用的其他对象的大小也算进去**。例如 `sys.getsizeof([1, 2, 3])` 只统计这个 list 容器对象本身的大小(对象头 + 它内部那个存放元素指针的数组的容量),而**不包含**它所指向的整数对象 1、2、3 的大小;同理 `sys.getsizeof(一个含大对象的 dict)` 只算 dict 容器结构,不算里面 key/value 对象的大小。这意味着:一个"装了很多大对象的容器",用 `getsizeof` 看可能很小(因为只是一堆指针),但其**深层实际占用**可能很大。所以做内存分析时**不能只用 `sys.getsizeof`** 来判断一个复杂/嵌套数据结构到底占了多少内存。要得到**深层总占用**,需要:①**递归地**对容器及其所有引用的对象累加 `getsizeof`(自己写递归并用集合记录已访问对象,避免重复计数和循环引用);②或使用现成工具——`pympler` 的 `asizeof.asizeof(obj)`(递归计算)、`tracemalloc`(跟踪内存分配、对比快照、定位是哪段代码分配了多少内存,是定位内存增长/泄漏的首选)、`objgraph`(分析对象引用图)。另外 `__sizeof__` 是 `getsizeof` 的底层实现(`getsizeof` 还会加上 GC 头部开销)。总之:`getsizeof` 适合看单个对象本体大小;评估整个数据结构占用要用递归或专门的内存分析工具。

</details>

5. 处理上百万个数字时,为什么用 NumPy/array 比 list 省内存得多?

<details><summary>参考答案</summary>

因为 `list` 存的是**指向独立 Python 对象的指针**,而 `array`/NumPy 存的是**连续的原始数值**。具体来说:一个 `list[int]` 在内存里是一个**指针数组**——list 本身存的是一串指针,每个指针指向一个**独立的 Python int 对象**;而每个 Python int 对象都是完整的堆对象,带对象头(引用计数、类型指针)+ 数值字段,占 **24-28 字节甚至更多**(见前面)。所以一百万个数字用 list 存,要 = 一百万个 int 对象(各 ~28 字节)+ 一百万个指针(各 8 字节)≈ 几十 MB,而且这些 int 对象在内存里**分散**(缓存不友好)。相比之下,**`array.array("i", ...)`** 把数字按指定类型(如 32 位整数)**紧密地、连续地**存成原始字节,每个元素只占 **4 字节**(没有每元素的对象头,也没有指针),没有"一值一对象"的开销;**NumPy 的 `ndarray`** 同理——它是一块连续的、按 `dtype`(如 `int32`/`float64`)紧凑存放原始数据的内存缓冲区,每个元素只占其 dtype 的字节数(int32 是 4 字节),整体内存可能只有等价 list 的 **1/5 到 1/10**。所以上百万级别的同质数值数据,NumPy/array 能省几倍到一个数量级的内存。**额外好处**:①**缓存友好 + 向量化**——连续内存让 CPU 缓存命中率高,NumPy 还能把整个数组的运算下推到底层 C/SIMD 实现做**向量化**,比 Python 循环快几十上百倍(见 P19);②可与 C 库零拷贝交互。**代价/适用**:array/NumPy 要求元素**同质**(同一种数值类型),适合数值计算;不适合存放异质对象或需要频繁任意增删的场景。结论:大规模数值数据用 NumPy(或 array、pandas/Polars 列式存储),而不要用原生 list of int/float。

</details>

6. 有哪些常见的 Python 内存优化手段?

<details><summary>参考答案</summary>

按"减少每对象开销、避免冗余对象、不同时持有海量对象"几条思路:①**`__slots__`**——给字段固定、数量巨大的类加 `__slots__`(或 `@dataclass(slots=True)`),去掉每实例的 `__dict__`,省可观内存(见 P09);②**用紧凑/列式结构存同质数据**——大量数字用 `array.array` 或 **NumPy ndarray**(连续原始字节,省几倍内存且能向量化);二进制数据用 `bytes`/`bytearray`、固定结构用 `struct`;大规模表格用 pandas/Polars 列式存储;避免"一值一对象"的 list；③**生成器/惰性流式处理**——用生成器、生成器表达式、`itertools`、逐行/分块读取(见 P05)来处理大数据,**一次只在内存里保留少量元素**,而不是一次性 `list()` 全量加载(把内存从 O(n) 降到 O(1));④**及时释放引用**——大对象用完让它离开作用域或 `del`,助引用计数即时回收(见 P16);**警惕全局变量、模块级缓存、闭包、循环引用意外长期持有对象**导致的隐性内存增长;⑤**给缓存设上限**——`functools.lru_cache(maxsize=...)` 而非无界 `@cache`,或用 `weakref.WeakValueDictionary` 做"不阻止回收"的缓存(见 P06/P16);⑥**字符串 intern**——大量重复字符串(如解析出的重复键名)用 `sys.intern` 去重共享;⑦**避免不必要的中间大列表**——用生成器表达式喂给 `sum`/`join` 等,而非先建完整 list;⑧**用 `tracemalloc` 定位真正的内存热点**——先测量(快照对比、看分配源)再针对性优化,不要凭感觉过早优化。原则同性能优化:**先用工具(tracemalloc/pympler)找到真正占内存的地方,再施加 `__slots__`/NumPy/惰性/释放引用等手段**,把功夫花在刀刃上。

</details>
