# 精通 CPython 执行模型与字节码

> "Python 是解释型语言"只说对了一半——它先编译成**字节码**,再由虚拟机解释执行。理解这条链路,才能看懂 GIL、性能、`.pyc`、JIT。面试问:"Python 是编译还是解释?""字节码是什么?"本篇拆解 CPython 执行模型,为 [P16 内存](./P16-精通-Python-内存管理与GC.md)、[P17 GIL](./P17-精通-Python-GIL原理.md)、[P19 性能](./P19-精通-Python-性能剖析与优化.md)打底。
>
> **📅 基准:2026 年 6 月,CPython 3.13(实验 JIT)/ 3.14。**

---

## 一、从源码到执行

CPython 执行一段 `.py` 的链路:

```
源码 .py
  → 词法分析(tokenize)
  → 语法分析 → AST(抽象语法树)
  → 编译(compile)→ 字节码(bytecode,存于 code object)
  → 解释器循环(ceval.c 的 eval loop)逐条执行字节码
```

所以 Python **既编译又解释**:先把源码**编译**成字节码(不是机器码),再由**虚拟机解释**执行字节码。这区别于 C(编译成机器码直接跑)和纯解释(逐行翻译源码)。

```python
import dis
def add(a, b):
    return a + b
dis.dis(add)        # 反汇编看字节码
# LOAD_FAST a / LOAD_FAST b / BINARY_OP + / RETURN_VALUE
```

---

## 二、字节码与 code object

编译产物是 **code object**(`add.__code__`),里面有字节码指令(`co_code`)、常量(`co_consts`)、变量名(`co_varnames`)、参数信息等。

```python
add.__code__.co_consts      # 常量
add.__code__.co_varnames    # ('a', 'b')
dis.dis(add)                # 人类可读的字节码
```

- **字节码是 CPython 的实现细节**,不同版本指令会变(`BINARY_OP` 在 3.11 替代了旧的 `BINARY_ADD`),**不要依赖具体字节码编程**。
- `dis` 模块是理解 Python 行为、排查性能、看清"一行代码背后做了多少事"的利器。

---

## 三、栈式虚拟机

CPython 虚拟机是**基于栈**的(不是基于寄存器):用一个**操作数栈**做计算——`LOAD_*` 把值压栈,运算指令弹出操作数、算完压回结果。

```
return a + b 大致:
  LOAD_FAST  a        # 把 a 压栈
  LOAD_FAST  b        # 把 b 压栈
  BINARY_OP  +        # 弹出 a、b,算 a+b,结果压栈
  RETURN_VALUE        # 弹出栈顶返回
```

解释器循环(eval loop)就是一个大循环:取下一条字节码 → 按指令操作操作数栈/调用函数 → 继续。**GIL(见 [P17](./P17-精通-Python-GIL原理.md))保护的就是这个解释器状态**——同一时刻只有一个线程在执行字节码。

---

## 四、.pyc 与 __pycache__

为避免每次都重新编译,CPython 把模块的字节码缓存到 **`__pycache__/模块.版本.pyc`**:

- 导入模块时,若 `.pyc` 比源码新且版本匹配,直接加载字节码、跳过编译;否则重新编译并更新 `.pyc`。
- **`.pyc` 只是编译缓存,不是"保护源码"**——能轻易反编译回近似源码;别指望它隐藏代码。
- 直接运行的主脚本(`python main.py`)不生成 `.pyc`(只缓存被 import 的模块)。

---

## 五、CPython 与其他实现

"Python"是语言规范,有多个实现:

| 实现 | 特点 |
|---|---|
| **CPython** | 官方、C 写的参考实现,**有 GIL**,生态最全(我们说的"Python"默认指它) |
| **PyPy** | 带 **JIT 编译器**,纯 Python 计算密集代码可快数倍;兼容性好但 C 扩展支持稍弱 |
| Jython / IronPython | 跑在 JVM / .NET 上(较小众) |
| GraalPy | GraalVM 上的 Python |

GIL、引用计数等是 **CPython 的实现细节**,不是语言规范——PyPy 等可能不同。本系列默认讲 CPython。

---

## 六、Faster CPython 与 JIT

近年 CPython 性能大幅提升(Faster CPython 项目):

- **3.11(2022):专门化自适应解释器(PEP 659)**——运行时观察类型,把通用字节码"专门化"成更快的特化指令(如确定是 int 加法就走快路径),整体提速 **10-60%**,且不改变语义。
- **3.12**:更多内联与优化、per-interpreter GIL(PEP 684)。
- **3.13(2024):实验性 JIT(PEP 744)**——copy-and-patch 技术,把热点字节码即时编译成机器码(默认关闭,需特殊构建启用),是迈向更高性能的一步;同期还有实验性 **free-threading**(见 [P17](./P17-精通-Python-GIL原理.md))。

这些优化让"Python 慢"的刻板印象逐步改善,但 CPython 仍以易用、生态优先,极致计算性能仍靠 C 扩展/NumPy/PyPy(见 [P19](./P19-精通-Python-性能剖析与优化.md))。

## 陷阱清单

- **以为"Python 是纯解释,不编译"**:它先编译成字节码再解释;只是不编译成机器码。
- **依赖具体字节码**:字节码是 CPython 实现细节,版本间会变;别基于 `dis` 输出写逻辑。
- **以为 `.pyc` 能保护/加密源码**:它只是编译缓存,可反编译;隐藏源码要别的手段(且都不可靠)。
- **混淆 Python 语言与 CPython 实现**:GIL、引用计数是 CPython 的,PyPy/其他实现可能不同。
- **指望 JIT 默认加速**:3.13 的 JIT 是实验性、默认关闭;别假设代码已被 JIT。
- **`eval`/`exec` 跑不可信代码**:能执行任意字节码/代码,巨大安全风险。

---

## 2026 现状

- **Faster CPython 持续推进**:3.11 的自适应解释器已带来可观提速,3.13 实验 JIT、3.14 继续优化,"Python 慢"在改善。
- **`dis`** 仍是理解行为、教学、性能分析的利器;`sys._getframe`/`inspect` 用于内省。
- **极致性能路线**:计算密集仍优先 NumPy 向量化、C 扩展(Cython/PyO3 Rust)、或 PyPy(见 [P19](./P19-精通-Python-性能剖析与优化.md))。
- 与 Java 对照([J21](../java/INDEX.md)):都先编译成字节码 + 虚拟机执行;但 JVM 的 JIT(C1/C2)成熟且默认,CPython 的 JIT 还在早期、且有 GIL——这是两者性能与并发模型的根本差异之一。

## 练习题

1. Python 是编译型还是解释型语言?描述源码到执行的完整过程。

<details><summary>参考答案</summary>

Python(指 CPython 实现)**既不是纯解释、也不是像 C 那样编译成机器码,而是"先编译成字节码、再由虚拟机解释执行"**——可以说它兼有两者。完整过程:①**词法分析(tokenize)**——把源码 `.py` 文本切分成一个个 token(关键字、标识符、运算符、字面量等);②**语法分析(parse)**——把 token 流按语法规则构建成 **AST(抽象语法树)**,表示程序的结构;③**编译(compile)**——把 AST 编译成 **字节码(bytecode)**,封装在 **code object** 中(包含字节码指令序列、常量表、变量名表等);字节码是一种与平台无关的中间表示,**不是 CPU 能直接执行的机器码**;④**解释执行**——CPython 的**虚拟机(解释器循环,即 ceval 中的 eval loop)逐条读取并执行字节码指令**,在一个基于栈的虚拟机上完成实际计算。所以"Python 是解释型语言"只对了一半:它确实有"编译"步骤(产出字节码),只是编译的目标是字节码而非机器码,然后这些字节码由解释器解释运行。这与 C/C++(编译成机器码,直接由 CPU 执行)不同,也与最朴素的"逐行翻译源码"的解释器不同。为加速,编译产物会缓存为 `.pyc` 文件(放在 `__pycache__`),下次导入若未过期就直接加载字节码、跳过前面的编译步骤。可以用 `dis` 模块查看任意函数编译出的字节码。

</details>

2. 什么是字节码和 code object?`dis` 模块有什么用?

<details><summary>参考答案</summary>

**字节码(bytecode)**是 CPython 把 Python 源码编译后得到的**中间表示**——一串紧凑的指令(每条指令是操作码 opcode + 可选参数),面向 CPython 的虚拟机而非真实 CPU。例如 `a + b` 会编译成类似 `LOAD_FAST a`、`LOAD_FAST b`、`BINARY_OP +`、`RETURN_VALUE` 这样的指令序列。**code object** 是承载字节码及其相关元数据的对象(可通过函数的 `__code__` 属性访问),里面包含:字节码本身(`co_code`)、常量表(`co_consts`)、局部变量名(`co_varnames`)、参数个数、所需栈大小、所属文件名/行号映射等——它是"可执行单元"的完整描述,函数、模块、类体、推导式、lambda 都各有自己的 code object。**`dis` 模块**用于**反汇编**:`dis.dis(func)` 把函数的字节码以人类可读的形式打印出来(指令名、参数、对应源码行)。它的用途:①**理解 Python 的实际行为**——看清"一行代码背后到底做了哪些操作",比如 `a = b = c` 的赋值顺序、`+=` 与 `=` 的区别、闭包变量怎么被捕获、`for` 怎么调用迭代协议;②**性能分析/优化**——对比两种写法编译出的字节码量,理解为什么某种写法更快(如局部变量访问 `LOAD_FAST` 比全局 `LOAD_GLOBAL` 快);③**教学和排查诡异行为**。注意:**字节码是 CPython 的实现细节,不同 Python 版本的指令集会变化**(例如 3.11 用 `BINARY_OP` 取代了旧版的 `BINARY_ADD` 等,3.11+ 还引入了自适应专门化指令),所以 `dis` 输出仅供理解和分析,**绝不要依赖具体字节码来编写逻辑**(那样跨版本会坏掉)。

</details>

3. `.pyc` 文件是什么?它能保护源码吗?

<details><summary>参考答案</summary>

`.pyc` 文件是 CPython 缓存的**编译后字节码**,存放在模块所在目录的 **`__pycache__`** 子目录里,文件名形如 `模块名.cpython-313.pyc`(包含解释器版本标识)。它的作用是**避免重复编译、加快导入**:当你 `import` 一个模块时,CPython 会检查是否已有对应的、未过期(基于源码修改时间/大小或哈希,且解释器版本匹配)的 `.pyc`——如果有,就直接加载其中的字节码,**跳过"源码→AST→字节码"的编译步骤**;如果没有或已过期,则重新编译并(尽量)写入更新 `.pyc`。注意:只有**被 import 的模块**会生成 `.pyc`,**直接运行的主脚本**(`python main.py` 的 main.py)通常不生成。**它不能保护/加密源码**:`.pyc` 只是字节码的序列化,**很容易被反编译**回与源码高度近似的代码(有现成的反编译工具如 uncompyle/decompyle 系列,字节码里还保留了变量名、常量、行号等信息),所以**用只分发 `.pyc`(删掉 `.py`)来隐藏或保护源代码是不可靠的**——任何拿到 `.pyc` 的人都能还原出可读代码。真要保护知识产权,通常的手段是:把核心逻辑写成编译好的 C 扩展(机器码,反编译难得多)、做服务端化(代码不下发到客户端)、商业混淆/加密方案(但纯 Python 层面都难以真正防住)。总之 `.pyc` 是**性能缓存,不是安全机制**。

</details>

4. CPython、PyPy 有什么区别?GIL 是 Python 语言的特性吗?

<details><summary>参考答案</summary>

"Python"是一门**语言规范**,有多个**实现**。**CPython** 是官方的、用 C 语言编写的参考实现,也是绝大多数人说"Python"时默认指的那个——它最成熟、生态/C 扩展支持最全,采用**引用计数 + 分代 GC** 做内存管理,并且**有 GIL(全局解释器锁)**。**PyPy** 是另一个实现,用 RPython 编写,最大特点是带 **JIT(即时编译)**——它在运行时把热点代码编译成机器码,对**纯 Python 的计算密集型代码**通常能比 CPython 快数倍(有时一个数量级);它高度兼容 CPython,但对一些依赖 CPython C-API 的 C 扩展支持稍弱、启动和内存特性也不同。此外还有 Jython(跑在 JVM 上)、IronPython(.NET)、GraalPy(GraalVM)等更小众的实现。**GIL 不是 Python 语言规范的一部分,而是 CPython 这个实现的特性**——语言规范并没有要求"必须有一个全局解释器锁"。这意味着:①其他实现可以没有 GIL(例如 Jython 跑在 JVM 上、就没有 CPython 式的 GIL,可以多线程并行;PyPy 也长期有无 GIL 的探索);②引用计数同理也是 CPython 的实现细节(Jython 用 JVM 的 GC)。所以谈论 GIL、引用计数这些时要明确"这是 CPython 的行为",而不是"Python 语言天生如此"。本课程默认讨论 CPython(因为它是事实标准),但理解"语言 vs 实现"的区别能避免把实现细节误当语言语义,也有助于理解为什么 free-threading(去 GIL)是在改 CPython 实现、而非改语言。

</details>

5. 什么是 Faster CPython?3.11 的自适应解释器和 3.13 的 JIT 分别是什么?

<details><summary>参考答案</summary>

**Faster CPython** 是 CPython 官方推动的一系列**性能优化项目**(由包括 Guido 在内的团队主导),目标是在**不改变语言语义、保持兼容**的前提下显著提升 CPython 的执行速度,扭转"Python 慢"的局面。其代表性成果:①**3.11(2022)的"专门化自适应解释器"(Specializing Adaptive Interpreter,PEP 659)**——核心思想是**运行时观察 + 指令专门化**:解释器在执行时会观察某条通用字节码实际操作的对象类型,如果发现某处总是对特定类型操作(比如某个 `BINARY_OP` 总是两个 int 相加),就把这条通用指令**动态替换成针对该类型优化过的"专门化"快速指令**(走更短的代码路径,省去通用的类型分派和检查);若后续类型变了再"去专门化"回退。这种自适应专门化对热点代码效果显著,使 3.11 相比 3.10 整体**提速约 10%-60%**(视工作负载),且对用户完全透明。②**3.13(2024)的实验性 JIT(PEP 744)**——引入了一个基于 **copy-and-patch** 技术的 JIT 编译器,能把热点的字节码(经过中间表示)**即时编译成机器码**执行,进一步突破解释执行的开销上限。它目前是**实验性的、默认关闭**(需要用特定选项构建 CPython 才启用),是 CPython 迈向"自带高性能 JIT"的早期一步,未来版本会持续成熟。同期 3.13 还有另一个重磅实验特性 **free-threading(去 GIL)**(见 P17)。**意义与边界**:这些优化让 Python 越来越快、缩小与编译型语言的差距,但 CPython 仍以易用性和生态为先,**追求极致计算性能**时主流做法仍是用 NumPy 向量化、写 C/Cython/Rust 扩展、或改用带成熟 JIT 的 PyPy(见 P19)。

</details>

6. CPython 的执行模型和 JVM 有什么相似与不同?(可对比 Java)

<details><summary>参考答案</summary>

**相似点**:两者都不是"源码直接编译成机器码运行",而是采用"**先编译成字节码、再由虚拟机执行**"的两段式模型。Java 把 `.java` 编译成 `.class`(JVM 字节码),由 **JVM** 执行;CPython 把 `.py` 编译成字节码(缓存为 `.pyc`),由 **CPython 虚拟机(解释器循环)** 执行。两者的虚拟机都基于**栈式架构**(用操作数栈做计算),都有各自的字节码指令集和 code/class 结构,都做内存自动管理(GC),都有"一次编写、跨平台运行"的特性(字节码与具体 CPU 无关)。**不同点**:①**JIT 成熟度**——**JVM 拥有成熟、默认开启的 JIT 编译器(HotSpot 的 C1/C2,见 J21)**,会把热点字节码编译成高度优化的机器码,使 Java 运行时性能接近原生;而 **CPython 长期是纯解释执行**(无 JIT),性能较低,直到 3.11 才有自适应专门化解释器、3.13 才引入**实验性、默认关闭**的 JIT,远不如 JVM 成熟。②**并发模型**——**CPython 有 GIL**,同一进程同一时刻只有一个线程在执行字节码,多线程无法在多核上并行跑 CPU 密集的 Python 代码(见 P17);而 **JVM 没有这种全局锁,线程可真正并行**,这是两者并发能力的根本差异。③**类型与编译期检查**——Java 是静态强类型、编译期做大量检查和优化;Python 动态类型,字节码编译期检查很少。④**优化与运行时**——JVM 有逃逸分析、内联、分层编译等重度运行时优化;CPython 优化相对轻量(虽在快速进步)。总之:模型骨架相似(字节码+VM),但 JVM 在 JIT 和真并行上远比 CPython 成熟,这也解释了为什么 Java 计算密集和多核场景性能强、而 Python 这类场景要靠 C 扩展/多进程/NumPy 弥补。

</details>
