# 精通 Python 内存管理与垃圾回收

> Python 内存管理是"引用计数为主 + 分代 GC 兜底"的双机制——引用计数即时回收,分代 GC 专门处理循环引用。面试高频:"Python 怎么 GC?""循环引用怎么办?""`__del__` 有什么坑?"本篇讲透,串起 [P01 对象](./P01-精通-Python-数据模型与对象.md)、[P15 PyObject](./P15-精通-Python-执行模型与字节码.md)、[P18 内存优化](./P18-精通-Python-对象内存优化.md)。
>
> **📅 基准:2026 年 6 月,CPython 3.13 / 3.14。**

---

## 一、引用计数:主力机制

CPython 每个对象(`PyObject`)都有一个**引用计数 `ob_refcnt`**,记录有多少个引用指向它。引用 +1(被赋值/传参/放进容器)、-1(名字销毁/重新绑定/容器移除)。**计数减到 0 立即回收**该对象内存。

```python
import sys
a = []
print(sys.getrefcount(a))   # 比实际多 1(getrefcount 的参数本身算一个临时引用)
b = a                       # 引用 +1
del b                       # 引用 -1
```

特点:**即时性**——对象一旦没人用立刻释放(不像追踪式 GC 要等下一轮)。代价:每次引用变动都要改计数(有开销),且**无法处理循环引用**(见下)。这也是 GIL 存在的原因之一——保护引用计数的并发安全(见 [P17](./P17-精通-Python-GIL原理.md))。

---

## 二、循环引用:引用计数的盲区

引用计数处理不了**循环引用**——两个对象互相引用,即使外部已无人引用它们,各自的计数也不为 0,永远不会被引用计数回收:

```python
a = {}; b = {}
a["b"] = b      # a 引用 b
b["a"] = a      # b 引用 a —— 循环!
del a, b        # 外部名字没了,但 a、b 互相引用,计数仍 >0 → 引用计数无法回收
```

这就需要第二套机制:**分代垃圾回收器**来发现并清理这种"孤岛"。

---

## 三、分代垃圾回收

CPython 用一个**追踪式、分代的垃圾回收器**(`gc` 模块)专门处理循环引用。核心思想:

- **可达性分析**:从根(全局、栈等)出发能到达的对象是活的;循环引用的"孤岛"虽互相引用但整体不可达,可被回收。
- **分代假设**:"大多数对象很快就死"。GC 把对象分**三代(0/1/2)**:新对象在第 0 代,**第 0 代回收最频繁**;熬过一轮回收的对象**晋升**到下一代;老对象(第 2 代)很少被扫描。这样把精力集中在"最可能是垃圾"的年轻对象上,减少全堆扫描开销。
- GC 只需追踪**容器类对象**(可能形成循环的,如 list/dict/对象实例);纯不可变标量(int/str)不参与(它们不会形成循环)。

```python
import gc
gc.collect()        # 手动触发一次回收
gc.disable()        # 关闭分代 GC(引用计数仍工作)——某些场景调优用
gc.get_threshold()  # 看触发阈值(默认 (700, 10, 10))
```

**分工**:引用计数负责绝大多数即时回收,分代 GC 只负责"打扫"引用计数处理不了的循环垃圾。

## 四、`__del__` 与循环引用

`__del__`(析构方法)在对象被回收时调用。但它和循环引用结合有历史坑:

- 早期(3.4 前):若循环引用里的对象定义了 `__del__`,GC **不知道按什么顺序调用析构**,会把它们放进 `gc.garbage` **不回收**(造成泄漏)。
- **3.4+(PEP 442)** 改进:能正确处理带 `__del__` 的循环引用了。但仍建议:**不要依赖 `__del__` 做关键清理**——它的调用时机不确定(取决于何时被回收)、异常被忽略、解释器退出时未必调用。
- **资源清理用 `with`/上下文管理器**(见 [P06](./P06-精通-Python-装饰器与上下文管理器.md))或显式 `close()`,而非 `__del__`。

---

## 五、弱引用 weakref

**弱引用**引用一个对象但**不增加其引用计数**——所以不会阻止对象被回收。用于**缓存、观察者、避免循环引用**:

```python
import weakref
class Node: pass
n = Node()
r = weakref.ref(n)      # 弱引用
print(r())              # 拿到 n(还活着)
del n                   # 唯一强引用没了 → n 被回收
print(r())              # None —— 弱引用自动失效
```

用途:①**缓存**(`WeakValueDictionary`:value 没别人用了就自动从缓存消失,不阻止回收);②**打破循环引用**(父子互引时,子对父用弱引用,避免孤岛);③观察者/回调注册表(不想因注册而让对象无法回收)。

---

## 六、内存池与调优

- **pymalloc**:CPython 为**小对象(≤512 字节)**用专门的内存池分配器(arena/pool/block 分层),减少频繁向操作系统 malloc/free 的开销、降低碎片。大对象走系统 malloc。
- **对象不一定立刻还给 OS**:释放的内存可能留在 Python 的内存池里复用,所以进程 RSS 不一定随对象释放下降(这常被误判为"内存泄漏")。
- **调优**:①CPU 敏感、对象多且确定无循环引用的批处理,可临时 `gc.disable()` 减少 GC 开销(结束再开);②长生命周期服务警惕"意外的强引用"(全局缓存、闭包、循环引用)导致内存增长;③用 `tracemalloc`、`objgraph`、`gc` 排查泄漏(见 [P19](./P19-精通-Python-性能剖析与优化.md))。

---

## 陷阱清单

- **以为只有 GC、没有引用计数**:CPython 主力是引用计数(即时回收),GC 只补充处理循环引用。
- **循环引用 + 长生命周期**:大对象循环引用若 GC 没及时跑,内存涨;必要时 `gc.collect()` 或用弱引用打破。
- **依赖 `__del__` 做清理**:调用时机不定、退出时未必调、异常被吞;用 `with`/`close()`。
- **`sys.getrefcount` 的 +1**:它的参数本身是一个临时引用,读数比"真实引用数"多 1。
- **把"RSS 不降"当内存泄漏**:释放的内存可能留在内存池复用,未必还给 OS。
- **全局缓存/闭包意外持有对象**:导致对象一直可达、无法回收(隐性泄漏);用弱引用缓存或限制大小。
- **多线程下手动改计数(C 扩展)不持 GIL**:破坏引用计数,崩溃(见 [P17](./P17-精通-Python-GIL原理.md))。

## 2026 现状

- **引用计数 + 分代 GC** 仍是 CPython 内存模型核心;**free-threading 构建(见 [P17](./P17-精通-Python-GIL原理.md))下引用计数改用了线程安全的方案(偏向引用计数等)**,是去 GIL 的关键工程。
- **`tracemalloc`(标准库)** 是定位内存增长/泄漏的首选(对比快照、看分配源)。
- **`weakref` + `WeakValueDictionary`/`WeakSet`** 在缓存、事件系统中常用,避免无意延长对象寿命。
- 与 Java/Go 对照:Java/Go 是**纯追踪式 GC**(无引用计数,见 [J17](../java/INDEX.md)/[G20](../golang/INDEX.md)),靠并发标记清除/整理;Python 是**引用计数为主**(即时、确定性强,但有计数开销且需 GC 补漏循环引用)。各有取舍。

## 练习题

1. CPython 主要靠什么做内存管理?引用计数是怎么工作的?

<details><summary>参考答案</summary>

CPython 的内存管理是**"引用计数(reference counting)为主 + 分代垃圾回收(generational GC)为辅"**的双机制,其中**引用计数是主力**。**引用计数的工作方式**:每个 Python 对象(底层的 PyObject)内部都有一个字段 **`ob_refcnt`**,记录当前有多少个引用指向该对象。当对象被新的名字绑定、被作为参数传递、被放入容器等时,引用计数 **+1**;当某个引用消失时——名字被 `del`、变量离开作用域、被重新赋值指向别的对象、从容器中移除等——引用计数 **-1**。**一旦某个对象的引用计数减到 0**(意味着再也没有任何引用指向它、无法被访问),CPython 就**立即回收**它占用的内存(并相应地把它所引用的其他对象计数也 -1,可能引发连锁回收)。这种机制的最大优点是**即时性/确定性**:对象一旦不再被使用就马上释放,不需要等待某个 GC 周期(对比 Java/Go 的纯追踪式 GC 是"过段时间才回收")。代价是:①**每次引用增减都要修改计数**,带来一定运行时开销;②**计数字段本身占内存**;③最关键的——**引用计数无法处理"循环引用"**(两个对象互相引用时,即使外部无人引用,它们的计数也不为 0,永远回收不掉),所以才需要第二套机制(分代 GC)来兜底。还有一点:引用计数的增减必须是线程安全的,这正是 CPython 用 GIL 保护的原因之一(见 P17)。可以用 `sys.getrefcount(obj)` 查看引用数(注意结果会比实际多 1,因为把 obj 传给该函数本身又制造了一个临时引用)。

</details>

2. 为什么引用计数处理不了循环引用?Python 怎么解决?

<details><summary>参考答案</summary>

**引用计数处理不了循环引用**的原因:循环引用是指两个(或多个)对象**互相引用**,形成一个环——例如 `a` 引用 `b`、`b` 又引用 `a`。当外部不再需要它们、`del a; del b` 之后,虽然没有任何"外部"引用指向这个环了,但**环内部对象之间的相互引用依然存在**:`a` 的引用计数因为还被 `b` 引用着而 ≥1,`b` 的引用计数也因为还被 `a` 引用着而 ≥1。两者的引用计数都**永远减不到 0**,所以引用计数机制**永远不会回收它们**——这块内存就泄漏了(成了"虽然不可达、但计数非 0"的孤岛)。**Python 的解决办法**是引入第二套机制:一个**追踪式(tracing)、分代(generational)的垃圾回收器**(由 `gc` 模块管理),专门用来发现并回收这种循环引用垃圾。它的原理是**可达性分析**——周期性地从根对象(全局变量、调用栈等)出发遍历,找出哪些对象是真正"可达(活)"的;那些虽然内部互相引用、但整体从根**不可达**的对象环,就被判定为垃圾并回收。为降低开销,它采用**分代**策略(基于"大多数对象很快死亡"的假设):对象分 0/1/2 三代,新对象在第 0 代、最频繁被扫描,熬过回收的晋升到更老的代、扫描频率更低,从而把回收精力集中在最可能是垃圾的年轻对象上,避免每次都全堆扫描。而且这个 GC **只需要追踪可能形成循环的容器类对象**(list、dict、自定义对象等),不可变标量(int、str)不参与。所以分工是:**引用计数负责绝大多数对象的即时回收,分代 GC 负责定期清理引用计数处理不掉的循环引用**。可用 `gc.collect()` 手动触发、`gc.disable()` 关闭(引用计数仍工作)。

</details>

3. 什么是分代垃圾回收?为什么要分代?

<details><summary>参考答案</summary>

**分代垃圾回收(generational GC)**是 CPython 的追踪式垃圾回收器(用于回收循环引用)采用的一种优化策略。它把所有被追踪的对象按"存活时间"分成**三代:第 0 代、第 1 代、第 2 代**。新创建的(容器类)对象先放入**第 0 代**;垃圾回收器**最频繁地扫描第 0 代**,在一次回收中**存活下来(仍可达)的对象会被"晋升"到第 1 代**;第 1 代积累到一定程度被扫描时,存活者再晋升到**第 2 代**;第 2 代是"老年代",**扫描频率最低**。每代有各自的触发阈值(默认约 `(700, 10, 10)`,可用 `gc.get_threshold()` 查看)。**为什么要分代**:核心依据是**"分代假设(generational hypothesis)"——绝大多数对象的生命周期都很短(创建后很快就变成垃圾),而少数熬过来的对象往往会存活很久**。基于这个经验规律:①**年轻对象最可能是垃圾**,所以频繁扫描第 0 代能以较小的代价回收掉大量短命垃圾;②**老对象大概率还活着**,频繁扫描它们大多是"白扫"(扫了也回收不了),纯属浪费,所以让老年代很少被扫描;③这样把垃圾回收的**精力集中在"投入产出比最高"的年轻代上**,避免每次都做昂贵的**全堆扫描**,显著降低 GC 的整体开销、减少停顿。换句话说,分代是一种"按对象年龄区别对待、把扫描成本花在刀刃上"的优化。补充:这套分代追踪 GC 只负责处理**循环引用**(非循环的垃圾由引用计数即时回收了),且只追踪可能产生循环的容器对象;Java/Go 等也广泛采用分代(或类似)思想做 GC。

</details>

4. `__del__` 方法有什么坑?为什么不推荐用它做资源清理?

<details><summary>参考答案</summary>

`__del__` 是对象的"析构方法",在对象**即将被销毁时**被调用。它的坑和不可靠性主要有:①**调用时机不确定**——`__del__` 何时被调用取决于对象**何时被回收**,而这依赖引用计数归零或 GC 运行的时机;在有其他引用(包括意外的全局引用、循环引用、异常 traceback 持有的引用)时,对象可能长时间不被回收,`__del__` 迟迟不执行,无法保证资源被及时释放;②**解释器退出时不保证调用**——程序结束时,残留对象的 `__del__` 不一定会被执行,所以靠它做"程序结束前的清理"不可靠;③**历史上与循环引用冲突**——在 Python 3.4 之前,如果循环引用中的对象定义了 `__del__`,GC 因为不知道按什么顺序安全析构,会把它们丢进 `gc.garbage` 列表而**不回收**(导致泄漏);PEP 442(3.4)改进后能正确处理带 `__del__` 的循环引用了,但这段历史说明 `__del__` 与 GC 的交互很微妙;④**`__del__` 中的异常会被忽略**(只打印到 stderr),错误难以察觉;⑤在 `__del__` 里访问其他对象/模块可能因解释器关闭阶段而已不可用。**因此不推荐用 `__del__` 做关键的资源清理**(关闭文件/网络连接/释放锁等)。**推荐做法**是使用**上下文管理器(`with` 语句)**(见 P06)——它保证 `__exit__` 在离开代码块时**确定性地、及时地**执行清理,无论是否发生异常;或者提供显式的 `close()`/`release()` 方法由调用方(或 `try/finally`、`contextlib.closing`)管理。简言之:确定性清理用 `with`/显式 close;`__del__` 至多作为"最后兜底"且不能依赖其时机。

</details>

5. 弱引用(weakref)是什么?有什么典型用途?

<details><summary>参考答案</summary>

**弱引用(weak reference)**是一种**引用对象但不增加其引用计数**的特殊引用——因此它**不会阻止所引用的对象被垃圾回收**。普通引用(强引用)会让对象的引用计数 +1、使对象保持存活;而弱引用"指向"对象却不"持有"它:只要对象的所有**强引用**都消失了,对象就会被回收,此时该弱引用会自动**失效**(变成指向 None)。用 `weakref.ref(obj)` 创建,调用 `r()` 取回对象(还活着返回对象,已回收返回 None)。**典型用途**:①**缓存**——用 `weakref.WeakValueDictionary`(或 `WeakKeyDictionary`)做缓存时,当某个被缓存的对象在别处已无人使用(无强引用),它会自动从缓存中消失、被回收,从而**缓存不会阻止对象被回收、避免缓存无限增长占内存**;这区别于普通 dict 缓存(会强引用、使对象一直存活造成内存泄漏);②**打破循环引用**——在父子/双向关联结构中(如树的子节点引用父节点、观察者引用主体),让其中一个方向用弱引用,就能**避免形成强引用环**导致的回收困难,父对象无人引用时能正常被回收;③**观察者模式/回调注册表**——注册回调或监听者时用弱引用持有它们,这样"注册"这个动作本身不会延长这些对象的生命周期(对象该回收时回收,自动从注册表失效),避免"只是注册了一下就再也回收不掉"的泄漏;④**关联额外数据**——给不能加属性的对象附加信息(WeakKeyDictionary)。注意:不是所有对象都支持被弱引用(如默认的 int、tuple、以及定义了 `__slots__` 但没加 `__weakref__` 的对象不支持)。总之弱引用让你"引用一个对象但不影响它的生死",是缓存和解循环引用的利器。

</details>

6. Python 的内存管理和 Java/Go 的垃圾回收相比有什么不同?

<details><summary>参考答案</summary>

**最根本的区别:CPython 以"引用计数"为主,Java/Go 是"纯追踪式 GC",不用引用计数。** ①**回收时机/确定性**:CPython 的引用计数让对象在**引用归零的那一刻即时、确定地**被回收(对循环引用之外的绝大多数对象),具有较强的确定性——这也是为什么 Python 里很多资源能"及时"释放;而 Java(见 J17)和 Go(见 G20)使用追踪式垃圾回收(标记-清除/标记-整理/分代/并发等),对象**不会在不可达的瞬间被回收,而是等到下一次 GC 运行时**才回收,时机不确定。②**循环引用**:引用计数处理不了循环引用,所以 CPython 额外配了一个**分代追踪 GC** 专门清理循环垃圾(双机制);而 Java/Go 的追踪式 GC 本身就基于可达性分析,**天然能处理循环引用**(不可达就回收,无需特别处理)。③**开销分布**:引用计数把开销**分摊到每次引用增减**上(频繁但小),并需要为计数加锁保证线程安全(CPython 用 GIL,见 P17);追踪式 GC 把开销集中在**GC 周期**(可能造成停顿,因此 Java 的 G1/ZGC、Go 的并发三色标记都在努力降低停顿)。④**并发/并行**:CPython 的引用计数+GIL 限制了多线程并行(改引用计数要线程安全),这与去 GIL/free-threading 的工程难点直接相关;Java/Go 的 GC 与运行时为真并行设计。⑤**内存归还**:CPython 有 pymalloc 内存池,释放的内存常留在池中复用、未必立刻还 OS;JVM/Go 运行时也管理自己的堆。**取舍**:引用计数=即时确定、实现相对简单、但有持续计数开销且要处理循环引用+并发计数难题(催生 GIL);纯追踪式 GC=无每次引用开销、自然处理循环引用、利于并行,但回收不即时、需要应对停顿。理解这点能解释很多现象:为什么 Python 资源释放较"准时"、为什么去 GIL 这么难(引用计数线程安全)、以及为什么 Java/Go 更适合高并发多核。

</details>
