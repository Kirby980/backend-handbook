# 精通 Python 内置容器底层

> `list`/`dict`/`set`/`tuple` 是 Python 用得最多的四个容器,但很多人不知道它们底层怎么实现、各操作复杂度多少。面试高频:"dict 为什么 O(1)、为什么 3.7 后有序?""list 头部插入为什么慢?""什么时候用 deque?"本篇深入 CPython 实现,串起 [P01 对象](./P01-精通-Python-数据模型与对象.md)、[P18 内存优化](./P18-精通-Python-对象内存优化.md)。
>
> **📅 基准:2026 年 6 月,Python 3.13 / 3.14。**

## 一、list:动态数组

CPython 的 `list` 是**动态数组**(不是链表):底层是一块连续的、存放**对象指针**的内存(`PyObject*` 数组),不直接存对象本身。

- **随机访问 `lst[i]` 是 O(1)**:按下标算偏移直接取指针。
- **`append` 均摊 O(1)**:list 会**预分配(over-allocate)**多余空间;满了才扩容(申请更大内存、拷贝旧指针过去)。增长是几何级的(约 1.125 倍递增),所以 N 次 append 总拷贝代价均摊到每次是 O(1)。
- **`insert(0, x)` / `pop(0)` 是 O(n)**:头部增删要移动后面所有元素(指针)。
- **`in` 成员测试是 O(n)**:线性扫描。频繁判断成员该用 set。

```python
import sys
lst = []
for i in range(5):
    lst.append(i)
    print(len(lst), sys.getsizeof(lst))  # 容量阶梯式增长,不是每次 +1
```

list 存的是**引用**:`a = [obj]` 不复制 obj。所以 `[[0]*3]*3` 会得到三行**共享同一内层列表**的坑(都是同一引用,见陷阱)。

## 二、dict:紧凑哈希表

`dict` 是**哈希表**,平均 O(1) 的增删查。CPython 3.6+ 用**紧凑布局(compact dict)**:分成两块——一个紧凑的、按插入顺序排列的 `entries` 数组(存 hash/key/value),和一个较小的 `indices` 数组(存到 entries 的下标)。

- **3.7 起 dict 保证插入有序**:这是紧凑布局的副产品,已写进语言规范(不再是实现细节)。
- **省内存**:紧凑布局比旧版省约 20-25% 内存。
- **查找过程**:`hash(key)` → 取低位定位 indices 槽 → 处理冲突(开放寻址 + 扰动探测)→ 到 entries 比较 key(先比 hash 再 `==`)。
- **负载因子超过 2/3 触发扩容**:重建更大的表(rehash),所以 key 顺序不变但容量翻倍。

```python
d = {"b": 1, "a": 2, "c": 3}
print(list(d))          # ['b', 'a', 'c'] —— 保持插入顺序
```

**key 必须可哈希(通常即不可变,见 [P01](./P01-精通-Python-数据模型与对象.md))**:`list` 不能作 key,`tuple`(元素均不可变时)可以。`hash(key)` 在对象生命周期内必须稳定,且相等对象哈希必须相等。

## 三、set / frozenset:哈希集合

`set` 本质是"只有 key 没有 value 的 dict"——同样基于哈希表:

- **成员测试 `x in s`、增删都是平均 O(1)**(对比 list 的 O(n))。
- 元素必须**可哈希**;`set` 本身可变(不可哈希),`frozenset` 不可变(可作 dict key / 放进另一个 set)。
- 集合运算:`|` 并、`&` 交、`-` 差、`^` 对称差。
- **去重**和**快速成员判断**首选 set。

```python
nums = [1, 2, 2, 3, 3, 3]
print(set(nums))            # {1, 2, 3} 去重
print(2 in set(nums))       # O(1)
```

---

## 四、tuple:不可变序列

`tuple` 是不可变序列,比 list 更轻量:

- **不可变 → 可哈希(元素也都可哈希时)**:能作 dict key / set 元素。
- 内存更省、可被解释器缓存/优化;适合"一组固定字段"(坐标、记录、多返回值)。
- ⚠️ **"不可变"指 tuple 结构不可变,不代表元素不可变**:`t = ([1,2], 3)` 里的列表仍可改 `t[0].append(4)`;而 `hash(t)` 会因含可变元素而报错。

`namedtuple`/`@dataclass`/`NamedTuple` 给 tuple 式数据加上字段名,可读性更好(见 [P14](./P14-精通-Python-类型注解与typing.md))。

## 五、操作复杂度速查

| 操作 | list | dict | set | deque |
|---|---|---|---|---|
| 索引 `[i]` | O(1) | — | — | O(n) |
| 按 key 查/改 | — | O(1) | — | — |
| `x in c` | O(n) | O(1) | O(1) | O(n) |
| 尾部 append | O(1)均摊 | — | — | O(1) |
| 头部 insert/pop | **O(n)** | — | — | **O(1)** |
| 末尾 pop | O(1) | — | — | O(1) |
| add / 删除 | — | O(1) | O(1) | — |

记忆:**要随机下标用 list;要键值/去重/成员判断用 dict/set;要两端高效进出用 deque。**

## 六、collections 常用容器

标准库 `collections` 补齐了内置容器的短板:

- **`deque`**:双端队列,**两端 append/pop 都是 O(1)**(底层是分块双向链表)。做队列/滑动窗口别用 `list.pop(0)`(O(n)),用 deque。
- **`defaultdict`**:访问缺失 key 时自动用工厂建默认值,省去 `setdefault`/判断。
- **`Counter`**:计数神器,`Counter(seq).most_common(k)` 取 Top-K。
- **`OrderedDict`**:3.7 后普通 dict 已有序,它现在主要用于需要 `move_to_end`、按顺序相等比较的场景(如手写 LRU)。
- **`namedtuple`**:带字段名的不可变 tuple。

```python
from collections import deque, Counter
q = deque([1, 2, 3]); q.appendleft(0)   # O(1) 头部插入
print(Counter("mississippi").most_common(2))  # [('i', 4), ('s', 4)]
```

## 陷阱清单

- **`[[0]*3]*3` 行共享同一列表**:`*` 复制的是引用,改一行全变。用推导式 `[[0]*3 for _ in range(3)]`。
- **用 `list` 做队列**:`pop(0)`/`insert(0,…)` 是 O(n);用 `collections.deque`。
- **频繁 `x in list`**:O(n);需要反复成员判断转成 `set`/`dict`(O(1))。
- **拿可变对象做 dict key / set 元素**:`list`/可变对象不可哈希,报 `TypeError`。
- **以为 dict 无序**:3.7+ 已保证插入有序;但别依赖"排序",有序≠排序。
- **迭代 dict/set 时增删**:`RuntimeError: dictionary changed size during iteration`。先收集再改,或迭代副本。
- **tuple "不可变"误解**:含可变元素的 tuple 元素仍可改,且这种 tuple 不可哈希。
- **大量字符串拼接用 list 累加再 join**:别用 `+=`(见 [P03](./P03-精通-Python-字符串与编码.md))。

## 2026 现状

- **紧凑有序 dict** 是现代 Python 的基石,`**kwargs`、JSON 往返、`dataclass` 字段顺序都依赖它。
- **`dict`/`set` 推导式**(见 [P07](./P07-精通-Python-推导式与函数式.md))是构造容器的主流写法。
- **`@dataclass` / `NamedTuple` / Pydantic** 在"结构化数据"场景大量取代裸 tuple/dict,兼顾可读与类型(见 [P14](./P14-精通-Python-类型注解与typing.md))。
- **性能敏感的同质数值数据**用 `array`、`numpy`、`struct` 紧凑存储,比 list of int 省大量内存(见 [P18](./P18-精通-Python-对象内存优化.md))。
- free-threading 构建下(见 [P17](./P17-精通-Python-GIL原理.md)),容器的并发安全需重新审视——CPython 在为内置容器加内部锁保证基本操作安全。

## 练习题

1. CPython 的 list 底层是什么结构?为什么 append 是均摊 O(1) 而 insert(0, x) 是 O(n)?

<details><summary>参考答案</summary>

CPython 的 `list` 底层是**动态数组**——一块连续内存,里面存放的是指向各元素对象的**指针(PyObject*)**数组,而不是元素本身、也不是链表。①**append 均摊 O(1)**:list 采用**预分配(over-allocation)**策略——当容量不足时,不是只多分配 1 个位置,而是按几何级数申请一块更大的内存(增长约 1.125 倍并带一定基数),把旧的指针数组拷贝过去。这样虽然单次扩容是 O(n)(要拷贝),但扩容不是每次 append 都发生,而是越来越稀疏;把 N 次 append 的总代价(包括偶尔的扩容拷贝)平摊到每次,均摊复杂度是 O(1)。②**insert(0, x) / pop(0) 是 O(n)**:因为数组是连续存储、靠下标定位,在**头部**插入或删除一个元素,必须把后面所有元素整体向后/向前移动一位(移动的是指针,但仍是 O(n) 次移动)以保持连续性,所以与列表长度成正比。推论:需要频繁在头部进出元素时,应使用 `collections.deque`(双端队列,两端操作 O(1));而随机下标访问 `lst[i]` 因为是按偏移直接取指针,是 O(1)。

</details>

2. dict 为什么平均 O(1)?为什么 Python 3.7 后 dict 保证有序?

<details><summary>参考答案</summary>

`dict` 是**哈希表**,所以平均 O(1):插入/查找时,先对 key 计算 `hash(key)`,用哈希值映射到表中的一个槽位,从而**不需要遍历**就能直接(或经过少量冲突探测)定位到目标,平均时间与表大小无关、为 O(1)(最坏情况下哈希严重冲突会退化,但实际极少)。查找一个 key 的过程:计算 hash → 用低位定位 indices 槽 → 若冲突则按扰动序列开放寻址探测 → 在 entries 中比较 key(先比 hash 值再用 `==` 确认)。当元素数超过容量的约 2/3(负载因子)时会扩容并 rehash。**3.7 后有序的原因**:CPython 3.6 引入了**紧凑字典(compact dict)**实现——把数据拆成两部分:一个**按插入顺序紧密排列**的 `entries` 数组(依次存每个 entry 的 hash/key/value),和一个独立的、较小的 `indices` 数组(哈希定位时存的是指向 entries 的下标)。由于真正的数据是按插入顺序追加进 entries 的,迭代时自然按插入顺序输出。这一开始(3.6)只是 CPython 的实现细节,因为太有用,**3.7 起被正式写入 Python 语言规范**,成为所有实现都必须保证的语义。附带好处是紧凑布局还节省了约 20-25% 的内存。注意"保持插入有序"不等于"排序"。

</details>

3. list、set、dict 在成员测试(`x in c`)上的复杂度分别是多少?这对写代码有什么指导?

<details><summary>参考答案</summary>

`x in lst`(list)是 **O(n)**——因为 list 是数组,没有基于值的索引,只能从头到尾逐个用 `==` 比较,平均要扫描一半元素。`x in s`(set)和 `key in d`(dict)是平均 **O(1)**——因为 set/dict 是哈希表,通过 `hash(x)` 直接定位槽位即可判断是否存在,与容器大小基本无关。**指导意义**:当代码里需要**反复进行成员判断**(例如在循环里频繁判断"某元素是否在集合中""是否已见过")时,如果用 list 存这些元素,整体复杂度会是 O(n×m)(外层循环 n 次、每次 in 扫描 m),很容易成为性能瓶颈;改用 **set 或 dict** 存放,可把每次成员判断降到 O(1),整体降到 O(n)。典型场景:去重(用 set)、查重/已访问标记(用 set)、按 key 查关联数据(用 dict)、统计计数(用 dict/Counter)。代价是 set/dict 比 list 占用更多内存、且元素必须可哈希、不保留可索引性。所以原则是:只需顺序存储和下标访问用 list;需要快速判断"在不在"或"按键取值"就用 set/dict。

</details>

4. 为什么 `[[0]*3]*3` 会有坑?正确写法是什么?

<details><summary>参考答案</summary>

`[[0]*3]*3` 的本意是创建一个 3×3 的二维列表,但它有一个共享引用的坑。先看内层:`[0]*3` 没问题,得到 `[0, 0, 0]`(因为 0 是不可变的 int,复制值没影响)。问题出在外层 `[...]*3`:序列的 `*` 重复操作**复制的是元素的引用,而不是创建新的副本**。所以 `[inner]*3` 得到的三个"行"实际上是**指向同一个内层列表对象**的三个引用,而非三个独立的列表。结果:`m = [[0]*3]*3` 后,执行 `m[0][0] = 1` 会发现 `m` 变成 `[[1,0,0],[1,0,0],[1,0,0]]`——三行一起变了,因为它们本就是同一个对象(`m[0] is m[1]` 为 True)。这与赋值不复制对象、`*` 只复制引用的语义一致(见 P01)。**正确写法**是用列表推导式,每次循环都新建一个独立的内层列表:`m = [[0]*3 for _ in range(3)]`——这里每次迭代都执行一次 `[0]*3` 生成一个全新的列表对象,三行互相独立,`m[0] is m[1]` 为 False,修改某行不影响其他行。同理,任何"重复包含可变对象的结构"都不要用 `*`,要用推导式逐个新建。

</details>

5. 什么时候该用 collections.deque 而不是 list?它的优势在哪?

<details><summary>参考答案</summary>

当需要**频繁在序列两端(尤其是头部)进行添加或删除**时,应使用 `collections.deque`(双端队列)而不是 `list`。原因在底层结构:`list` 是连续动态数组,尾部 append/pop 是均摊/O(1),但**头部** `insert(0, x)` 和 `pop(0)` 是 **O(n)**(要移动其余所有元素);而 `deque` 底层是**分块的双向链表**结构,**两端的 append/appendleft/pop/popleft 都是 O(1)**。所以典型场景:①实现**队列(FIFO)**——一端进另一端出,用 list 的 `pop(0)` 会很慢,deque 的 `popleft` 是 O(1);②实现**栈**两者都行(尾部操作 list 也 O(1));③**滑动窗口**——需要不断从一端加入、另一端移除;④需要**固定长度的环形缓冲**——`deque(maxlen=n)` 满了自动挤掉另一端,非常方便;⑤双向遍历/两端频繁操作的算法(如 BFS 队列、单调队列)。deque 还是线程安全的(append/pop 等单步操作),适合简单的多线程生产消费(不过更完整的用 `queue.Queue`)。代价/取舍:deque **不支持高效的随机下标访问**(`dq[i]` 是 O(n),因为要从端点走链),所以如果需要频繁按下标随机访问中间元素,还是用 list。一句话:两端进出选 deque,随机下标选 list。

</details>

6. dict 的 key 有什么要求?为什么 list 不能做 key 而 tuple 可以?

<details><summary>参考答案</summary>

dict 的 key 必须是**可哈希(hashable)**的对象。可哈希意味着:①对象实现了 `__hash__()` 且在其生命周期内哈希值**保持不变**;②实现了 `__eq__()` 用于在哈希冲突时比较相等;③遵守契约"相等的对象哈希值必须相等"。这是因为 dict 用哈希表存储:它靠 `hash(key)` 定位槽位、靠 `==` 确认 key——如果一个对象的哈希值会变化(比如它是可变的、改了内容后哈希也跟着变),那么放进去之后就再也找不到它了(它跑到了"原哈希对应的槽",但现在算出的是新哈希),哈希表会失效。所以 Python 规定:**通常只有不可变对象才可哈希**。`list` 是**可变**的,它没有 `__hash__`(被设为 None),因为它的内容随时可变、无法保证哈希稳定,所以不能作 key,作 key 会报 `TypeError: unhashable type: 'list'`。`tuple` 是**不可变**的,只要它的所有元素也都是可哈希的(如全是数字/字符串/其他不可变 tuple),它就是可哈希的,因此可以作 key(它的哈希由各元素的哈希组合而来)。但要注意:如果 tuple 里**包含了可变元素**(如 `(1, [2, 3])`),那么这个 tuple 也变得不可哈希、不能作 key——因为它的某个元素的"值"可变,无法保证整体哈希稳定。同理 set 的元素、需要作 key 的场景都要求可哈希;需要不可变集合作 key 时用 `frozenset`。

</details>
