## 引言：在 Linux 里，进程和线程是同一种东西

你大概背过这样一句"面试标准答案"：进程是资源分配的单位，线程是 CPU 调度的单位。这句话在抽象层面没错，但它会让你对 Linux 内核产生一个根本性的误解——以为内核里存在两种不同的对象，一种叫"进程"，一种叫"线程"。

事实是：**Linux 内核里只有一种执行实体，叫 `task`（任务），由 `struct task_struct` 描述。** 内核调度器调度的是 `task`，`ps` 看到的一行也是 `task`，`/proc/[pid]` 对应的还是 `task`。所谓"进程"和"线程"，只是同一种 `task` 在**共享多少资源**上的不同配置：

- 你 `fork()` 出一个"子进程"——内核创建了一个新 `task`，它**拷贝**（写时复制）了父亲的地址空间、文件表、信号处置等；
- 你 `pthread_create()` 出一个"线程"——内核同样创建了一个新 `task`，只不过它**共享**了同一个地址空间（`mm_struct`）、同一张文件表（`files_struct`）、同一套信号处置（`sighand_struct`）。

两者走的都是同一个内核函数：`kernel_clone()`（历史上叫 `do_fork`）。区别只在于传进去的一组 `CLONE_*` 标志位。`fork` 几乎不带共享标志，`pthread_create` 带上 `CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | ...`。**"线程"这个词在内核源码里几乎不出现，出现的是"共享了 `CLONE_THREAD` 的 task"。**

```
        一句话总结这一篇：
        进程 = 一组共享 mm 的 task（一个线程组 thread group）
        线程 = 线程组里的一个 task
        内核调度的最小单位 = task（不是进程）
```

理解这一点，后面所有"诡异现象"都会变得自然：

- 为什么多线程程序里 `getpid()` 在所有线程返回同一个值，而 `gettid()` 各不相同？——因为 `getpid()` 返回 `tgid`（线程组 ID），`gettid()` 返回 `pid`（task 自己的 ID）。
- 为什么 `top` 默认看到 8 个 CPU 跑满但只有一个进程？——因为那是一个进程里的 8 个 task。
- 为什么一个线程崩溃（段错误）整个进程都没了？——因为致命信号默认对整个线程组生效。
- 为什么 `kill -9` 杀不掉一个 `D` 状态的 task？——因为它根本没在"可被信号唤醒"的睡眠里。

本篇分六章把这套模型彻底拆开：第一章解剖 `task_struct`；第二章讲进程怎么被创造出来（`fork` / `vfork` / `clone` / `clone3` 与 COW、`exec`）；第三章讲线程模型（NPTL、`CLONE_THREAD`、`tgid` vs `pid`）；第四章讲进程状态机（R/S/D/T/Z/X，重点死磕 `D` 不可中断态与 load average 的关系）；第五章讲进程关系与终止（进程组/会话/控制终端、僵尸与孤儿、subreaper、daemon 化、`pidfd`）；第六章带你逐文件读穿 `/proc/[pid]`。

## 第一章 task_struct 解剖：一个 task 的全部身家

`task_struct` 是 Linux 里最大、最重要的结构体之一，定义在 `include/linux/sched.h`，字段有几百个，编译后实例往往上 KB。我们不逐字段背，只抓后端/SRE 真正会用到的几组。

### 1.1 身份：pid、tgid 与那串"命名空间敏感"的 ID

很多人以为 `task_struct` 里有个字段直接叫 `pid` 就是你 `ps` 看到的 PID。这里有两层坑。

第一层坑：**内核里的 `task->pid` 是"线程 ID"，`task->tgid` 才是用户口中的"进程 ID"。**

```c
struct task_struct {
    pid_t pid;     // 内核视角：这个 task 自己的 ID（= 用户态 gettid()）
    pid_t tgid;    // 线程组 ID（= 用户态 getpid()）；线程组 leader 的 tgid == pid
    ...
};
```

- 单线程进程：`pid == tgid`。
- 主线程：它是 thread group leader，`pid == tgid`。
- 子线程：`tgid` 等于主线程的 `pid`，但自己的 `pid` 是新分配的。

所以 `getpid()` 实现是返回 `tgid`，`gettid()` 返回 `pid`。

第二层坑：**在有 PID namespace 的世界里（容器、`unshare --pid`），一个 task 同时拥有多个 PID 值**——在每个它所属的命名空间里看到的数字都不同。`task_struct` 里其实不直接存那个数字，而是存一个指向 `struct pid` 的指针（通过 `task->thread_pid` / `pids[]`），`struct pid` 内含一个 `upid[]` 数组，记录它在每一层 namespace 里的数值。容器里 PID 1 的进程，在宿主机上可能是 PID 47821。这块详见 [L16 Namespace](./L16-精通-Namespace.md)，本篇只需记住：**"PID 是一个数字"是错觉，它是相对某个命名空间的。**

### 1.2 状态：state 与那个让人头疼的 D

```c
    unsigned int   __state;   // 6.x 改名为 __state（曾叫 state）
```

取值是一组位标志，常见的有 `TASK_RUNNING`(0)、`TASK_INTERRUPTIBLE`、`TASK_UNINTERRUPTIBLE`、`__TASK_STOPPED`、`__TASK_TRACED`。这是第四章的主角，这里先记住：**state 决定了调度器是否会把它放进运行队列，以及信号能否唤醒它。**

退出相关的状态（`EXIT_ZOMBIE` / `EXIT_DEAD`）放在另一个字段 `exit_state` 里。

### 1.3 地址空间：mm_struct 与那个意味深长的 NULL

```c
    struct mm_struct  *mm;         // 进程的地址空间
    struct mm_struct  *active_mm;  // 内核线程"借用"的地址空间
```

`mm_struct` 描述一个进程的整个虚拟地址空间：代码段/数据段/堆/栈/各种 mmap 区域（一串 `vm_area_struct`，6.1 起 VMA 查找用 maple tree 取代了旧红黑树）、页表根（`pgd`）、`mmap` 起始地址、`brk` 等。

两个关键事实：

1. **同一进程的所有线程共享同一个 `mm`**（指针相等）。这正是"线程共享内存"的本质——不是某种魔法，就是 `task->mm` 指向同一个 `mm_struct`。`fork` 出的子进程则是新的 `mm`（COW 拷贝）。
2. **内核线程（kthread，如 `kswapd`、`ksoftirqd`）的 `task->mm == NULL`**——它们没有自己的用户地址空间。但 CPU 任何时刻都需要一套页表，所以内核线程被调度上来时会"借用"上一个用户进程的页表，记在 `active_mm`。这就是为什么 `ps` 里那些 `[kxxx]`（中括号）进程的内存看起来很特殊。

### 1.4 打开的文件：files_struct 与 fs_struct

```c
    struct files_struct  *files;  // fd 表：fd -> struct file
    struct fs_struct     *fs;     // cwd、root、umask
```

`files_struct` 里是那张 **fd 数组**，下标是文件描述符，元素指向 `struct file`。线程默认共享同一张 `files`（`CLONE_FILES`），所以一个线程 `open` 得到 fd=7，另一个线程能直接用 fd=7。`fork` 的子进程则**拷贝**这张表（拷贝的是指针数组，`struct file` 仍共享，所以父子的 fd 指向同一个打开文件、共享同一个文件偏移）。fd 的完整机制见 [L08 I/O 多路复用](./L08-精通-IO-多路复用.md)。

`fs_struct` 存当前工作目录、根目录、umask——这也解释了为什么一个线程 `chdir()` 会影响同进程其他线程（默认共享 `CLONE_FS`）。

### 1.5 信号：三块结构与"对线程组还是对线程"

信号相关有三个结构，新手最容易混：

| 结构 | 作用 | 线程间是否共享 |
|---|---|---|
| `sighand_struct` | 信号处置表（每个信号的 handler / SIG_IGN / SIG_DFL） | 共享（`CLONE_SIGHAND`） |
| `signal_struct` | 线程组级共享状态：共享待决信号队列、资源限制 rlimit、计时器、tty 等 | 整个线程组共享 |
| `sigpending`（task 内） | **每个 task 私有**的待决信号队列 | 不共享 |

记住一条规则：**`kill(pid, sig)` 发给的是进程（线程组），信号会被随便挑一个"没屏蔽它"的线程处理；`tgkill`/`pthread_kill` 才能精确投递给某个线程。** 致命信号（如未捕获的 `SIGSEGV`、`SIGKILL`）会终结整个线程组——这就是"一个线程崩了整个进程都没了"的内核依据。信号细节见 [L14 信号与 IPC](./L14-精通-信号与IPC.md)。

### 1.6 亲缘指针：谁是我爹

```c
    struct task_struct __rcu *real_parent;  // 真正创建我的那个 task
    struct task_struct __rcu *parent;       // 接收我退出信号/被 ptrace 时的"父"
    struct list_head children;              // 我的孩子链表
    struct list_head sibling;               // 把我挂到父亲 children 上的兄弟链
    struct list_head ptraced;               // 被我 ptrace 的 task
    struct task_struct *group_leader;       // 线程组 leader（进程"主"task）
```

`real_parent` 是真正的生身父亲；`parent` 通常等于 `real_parent`，但被 `strace`/调试器 ptrace 时，`parent` 会临时变成调试器。父亲退出后，孩子会被"重新认领"（reparent），默认认给 init/subreaper（第五章详述）。

### 1.7 内核栈、thread_info 与 current

每个 task 有一块**独立的内核栈**（x86-64 上通常 16KB，`THREAD_SIZE`），它在 task 进入内核态（系统调用、中断）时使用，和用户栈完全分离。栈的一端（现代内核里 thread_info 已内嵌进 `task_struct`，不再放栈顶）关联着这个 task。

内核里随处可见的 `current` 宏，就是"当前正在这个 CPU 上运行的 task 的 `task_struct` 指针"。x86-64 上它通过 per-CPU 变量 `current_task` 取得，几乎零成本。你读内核源码时，`current->pid`、`current->mm` 满天飞，指的都是"现在跑着的这个 task"。

```
task_struct（堆上分配）
   ├── pid / tgid / __state / exit_state / flags / comm[16]
   ├── mm ───────────────► mm_struct（地址空间：VMA / pgd / brk ...）
   ├── files ────────────► files_struct（fd 表）
   ├── fs ───────────────► fs_struct（cwd / root / umask）
   ├── sighand ──────────► sighand_struct（信号处置表）
   ├── signal ───────────► signal_struct（线程组共享：rlimit / 待决信号 ...）
   ├── real_parent / parent / children / sibling / group_leader
   ├── sched_entity se（vruntime 等，见 L03）
   ├── cred（uid/gid/capabilities）
   └── 关联一块独立内核栈（约 16KB）
```

## 第二章 进程创建：fork / vfork / clone / clone3 与 COW

### 2.1 一切的源头：kernel_clone()

`fork()`、`vfork()`、`clone()`、`clone3()`、`pthread_create()` 在用户态看起来天差地别，在内核里却都汇聚到同一个函数 `kernel_clone(struct kernel_clone_args *)`，它负责：分配新的 `task_struct`、按 `CLONE_*` 标志决定**拷贝还是共享**各个资源、分配 PID、把新 task 挂上调度器运行队列。

差异全在那组标志位上：

| 系统调用 | 典型 CLONE 标志 | 语义 |
|---|---|---|
| `fork()` | 几乎无（仅 `SIGCHLD`） | 拷贝地址空间（COW）、拷贝 fd 表，全新进程 |
| `vfork()` | `CLONE_VM \| CLONE_VFORK` | 共享地址空间，父挂起直到子 `exec`/`exit` |
| `pthread_create()` | `CLONE_VM\|CLONE_FILES\|CLONE_FS\|CLONE_SIGHAND\|CLONE_THREAD\|CLONE_SETTLS\|...` | 共享一切，成为同一线程组的新线程 |
| `clone()/clone3()` | 由调用者任意组合 | 容器、运行时自定义共享粒度 |

### 2.2 COW 写时复制：fork 为什么"很快"

朴素想象里 `fork` 要把父进程几个 GB 的内存全拷一份——那会慢到不可用。真实机制是**写时复制（Copy-On-Write）**：

`fork` 时，内核**不拷贝物理内存页**，只拷贝**页表**，并把父子双方所有可写页的页表项标记为**只读**，同时在页描述符上增加引用计数。父子此刻共享同一批物理页，`fork` 因此只需处理页表，开销与地址空间大小近似线性但常数极小。

当父或子**任何一方尝试写**某个共享页时，CPU 发现页表项只读 → 触发**缺页异常（page fault）** → 内核的缺页处理发现这是 COW 页 → 真正分配一张新物理页、拷贝内容、把写入方的页表项改回可写。**"拷贝"被推迟到第一次写的那一刻，且只拷被写的那一页。**

```
fork 后（尚未写入）：              某一方写入页 P 后：
  父 PTE ─┐                         父 PTE ──► 物理页 P   （原页，可写）
          ├─► 物理页 P (只读)        子 PTE ──► 物理页 P'  （拷贝，可写）
  子 PTE ─┘                         （触发一次 minor page fault 完成拷贝）
```

实测验证 COW 的存在——`fork` 后立即看子进程的缺页计数随写入增长：

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    size_t N = 256UL * 1024 * 1024;     // 256MB
    char *buf = malloc(N);
    memset(buf, 1, N);                   // 先 touch 一遍，确保真实分配
    printf("parent pid=%d, buf=%p\n", getpid(), buf);

    pid_t c = fork();
    if (c == 0) {
        // 子进程：此刻还没拷贝任何数据页，只拷了页表
        printf("child pid=%d sees buf[0]=%d\n", getpid(), buf[0]);
        // 写入将逐页触发 COW，子进程 RSS 随之上涨
        memset(buf, 2, N);
        printf("child after write buf[0]=%d (父进程仍是 1)\n", buf[0]);
        _exit(0);
    }
    wait(NULL);
    printf("parent after child exit buf[0]=%d\n", buf[0]); // 仍是 1
    return 0;
}
```

观察缺页：`/usr/bin/time -v ./a.out` 看 "Minor (reclaiming a frame) page faults"，或在子进程里读 `/proc/self/stat` 的 `min_flt` 字段。COW 也解释了一个生产现象：**`fork` 一个占用大量内存的进程后，即便子进程立刻 `exec`，瞬间内存也可能因为大量写入 COW 而暴涨**——Redis 的 `bgsave` 就是典型，父进程持续写入会触发 COW，内存膨胀（见第五章/陷阱清单）。

### 2.3 vfork：一个"危险但快"的历史优化

`vfork` 共享父进程地址空间（`CLONE_VM`），并**挂起父进程**直到子进程 `exec` 或 `_exit`。它的存在意义是：在没有 COW 或 COW 还很贵的年代，`fork+exec` 模式下连页表都不想拷。子进程在 `exec` 前**不能修改任何内存、不能 `return`、只能调用 `_exit` 或 `exec` 系列**——否则会破坏父进程栈。现代有了 COW，`vfork` 价值大减，但仍被某些 `posix_spawn` 实现使用。**应用层基本不应直接用 `vfork`。**

### 2.4 clone3 与 struct clone_args：现代接口

老 `clone()` 用一长串位置参数传 flag、栈指针、TLS、ptid、ctid，扩展性差。Linux 5.3 引入 `clone3(struct clone_args *, size_t size)`，把参数收进一个结构体，且通过 `size` 实现**前向兼容**（内核按自己认识的字段长度解析，多出来的留给未来）：

```c
struct clone_args {
    __u64 flags;        // CLONE_* 标志（64 位，比老 clone 的 int 更宽）
    __u64 pidfd;        // 若设 CLONE_PIDFD，内核在此写回 pidfd
    __u64 child_tid;    // CLONE_CHILD_SETTID / CLEARTID 的地址
    __u64 parent_tid;   // CLONE_PARENT_SETTID 的地址
    __u64 exit_signal;  // 子进程退出时给父进程的信号（fork 用 SIGCHLD）
    __u64 stack;        // 子进程栈基址
    __u64 stack_size;
    __u64 tls;
    __u64 set_tid;      // 指定子进程 PID（容器恢复/CRIU 用）
    __u64 set_tid_size;
    __u64 cgroup;       // 配合 CLONE_INTO_CGROUP：直接生在指定 cgroup
};
```

两个对后端/容器很重要的能力：

- **`CLONE_PIDFD`**：创建子进程的同时拿到一个指向它的 **pidfd**（文件描述符），彻底解决 PID 回收复用导致的"误杀"竞争（第五章详述）。
- **`CLONE_INTO_CGROUP`**：直接把新进程生在某个 cgroup v2 目录里，省掉"先 fork 再写 cgroup.procs"的窗口。容器运行时（runc 等）受益明显，详见 [L17 Cgroup v2](./L17-精通-Cgroup-v2.md)。

### 2.5 exec：把"灵魂"换掉，"身份证"不变

`fork` 造了个新 task 但内容还是父亲的副本；要跑别的程序，得 `exec`。`execve()`（及 `execveat()`）做的是：**保留 `task_struct`（PID/tgid 不变、父子关系不变、未设 `O_CLOEXEC` 的 fd 保留），但把整个用户地址空间替换成新程序的镜像**——丢弃旧的 VMA，按 ELF 文件建立新的代码段/数据段/堆/栈，加载动态链接器，最后跳到新程序入口。

所以经典的 "fork + exec" 范式是：`fork` 复制出一个躯壳，子进程在里面 `exec` 换上新程序的"灵魂"，PID 不变方便父进程 `wait`。这也解释了 `exec` 失败为何不返回——成功就再也回不到调用点了（地址空间都没了），只有失败才返回 -1。`exec` 如何按 ELF 建立地址空间，详见 [L04 虚拟内存与分页](./L04-精通-虚拟内存与分页.md)。

## 第三章 线程模型：NPTL 与"共享 mm 的 task"

### 3.1 从 LinuxThreads 到 NPTL：1:1 模型

早年 Linux 的 LinuxThreads 实现问题重重（信号语义不符 POSIX、需要一个管理线程）。2003 年起的 **NPTL（Native POSIX Thread Library）** 成为标准实现，核心理念就是本篇开头那句话——**1:1 模型：一个 pthread 对应一个内核 task**，调度完全交给内核，用户态不再维护线程调度。`pthread_create` 底层就是带特定 `CLONE_*` 标志的 `clone`，线程同步（mutex/cond）则靠 **futex**（见 [L15 内核同步与 futex](./L15-精通-内核同步与futex.md)）。

### 3.2 哪些标志把一个 task 变成"线程"

`pthread_create` 创建线程时，glibc 大致传入这组标志：

```
CLONE_VM        共享地址空间（同一个 mm_struct）—— 线程能看到彼此的内存
CLONE_FS        共享 cwd / umask
CLONE_FILES     共享 fd 表 —— 一个线程开的 fd 别人能用
CLONE_SIGHAND   共享信号处置表
CLONE_THREAD    加入同一个线程组（tgid 相同）—— 这是"算同一进程"的关键
CLONE_SETTLS    设置线程本地存储（TLS）
CLONE_PARENT_SETTID / CLONE_CHILD_CLEARTID  glibc 维护 tid，线程退出时清零 + futex 唤醒 join
CLONE_SYSVSEM   共享 System V 信号量 undo
```

其中 **`CLONE_THREAD` 是分水岭**：带它，新 task 加入现有线程组（`tgid` 不变），退出时不向父进程发 `SIGCHLD`、`getpid()` 返回相同值；不带它（如 `fork`），就是一个全新进程（全新 `tgid`）。

### 3.3 tgid vs pid：一张图说清

```
进程（线程组 tgid = 1000）
┌───────────────────────────────────────────────┐
│  task A  pid=1000  tgid=1000   ← group_leader   │  getpid()=1000 gettid()=1000
│  task B  pid=1001  tgid=1000                    │  getpid()=1000 gettid()=1001
│  task C  pid=1002  tgid=1000                    │  getpid()=1000 gettid()=1002
│  共享：mm / files / fs / sighand / signal       │
└───────────────────────────────────────────────┘
   ps -e 默认按 tgid 折叠，只显示一行 (PID=1000)
   ps -eLf / top -H / ls /proc/1000/task 才能看到 B、C
```

用 Go 验证（Go runtime 的 M 就是内核线程）：

```go
package main

import (
	"fmt"
	"sync"
	"syscall"
)

func main() {
	pid := syscall.Getpid() // 返回 tgid，所有线程相同
	var wg sync.WaitGroup
	for i := 0; i < 3; i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			// runtime.LockOSThread 保证这个 goroutine 绑定在一个 OS 线程上
			// gettid 没有现成封装，直接走 syscall（x86-64: SYS_GETTID=186）
			tid, _, _ := syscall.Syscall(syscall.SYS_GETTID, 0, 0, 0)
			fmt.Printf("goroutine %d: pid(tgid)=%d tid=%d\n", i, pid, tid)
		}(i)
	}
	wg.Wait()
}
```

注意 Go 的 goroutine 不是 1:1 内核线程——它是 M:N 的，多个 goroutine 复用少量 OS 线程（M）。所以上面打印的 `tid` 数量取决于 runtime 调度，不一定恰好是 3 个不同值。但底层每个 M 仍是一个 `CLONE_THREAD` 的内核 task。用 C/pthread 写则 tid 严格各不相同。

### 3.4 线程与信号的微妙交互

- **进程定向信号**（`kill`、终端 `Ctrl+C` 的 `SIGINT`）：投给线程组，内核挑一个**没屏蔽该信号**的线程处理。所以多线程程序要小心：你可能不知道哪个线程会收到 `SIGTERM`。
- **线程定向信号**（`pthread_kill` → `tgkill`）：精确投给某个 tid。
- 常见最佳实践：用一个专门线程 `sigwait` 同步处理信号，其余线程全部 `pthread_sigmask` 屏蔽，避免不确定性。

## 第四章 进程状态机：R / S / D / T / Z / X 与 load average

`ps`、`top` 里那个单字母状态，是 `task_struct` 状态字段的人类可读映射。把它彻底搞懂，是排查"负载高但 CPU 不忙"这类问题的基本功。

### 4.1 状态全表

| 字母 | 内核状态 | 含义 | 信号能否唤醒 | 计入 load avg |
|---|---|---|---|---|
| `R` | `TASK_RUNNING` | 正在 CPU 上跑 或 在运行队列里等 CPU | —（在跑） | 是 |
| `S` | `TASK_INTERRUPTIBLE` | 可中断睡眠（等 I/O、锁、事件，能被信号叫醒） | 能 | 否 |
| `D` | `TASK_UNINTERRUPTIBLE` | 不可中断睡眠（通常等磁盘/某些内核锁） | **不能** | **是** |
| `T` | `__TASK_STOPPED` | 被 `SIGSTOP`/`SIGTSTP` 暂停（`Ctrl+Z`） | — | 否 |
| `t` | `__TASK_TRACED` | 被调试器 ptrace 停住 | — | 否 |
| `Z` | `EXIT_ZOMBIE` | 已退出，等父进程 `wait` 回收 | — | 否 |
| `X` | `EXIT_DEAD` | 正在被彻底销毁（瞬态，几乎看不到） | — | 否 |
| `I` | `TASK_IDLE` | 空闲内核线程的不可中断睡眠（`TASK_UNINTERRUPTIBLE \| TASK_NOLOAD`） | 不能 | **否** |

```
        ┌─────────── 被调度上 CPU ───────────┐
        │                                    │
  (新建) ──► R (就绪/运行) ──时间片用尽/被抢占──► R
        │       │  ▲                          │
   等待事件      │  │ 事件到达/被唤醒            │ 退出 exit()
   (可中断)      ▼  │                          ▼
        └────► S ───┘                      Z (僵尸) ──父 wait──► X (销毁)
                │
   等待磁盘/内核锁(不可中断)
                ▼
                D ──I/O 完成──► R
        SIGSTOP/Ctrl+Z
   R/S ──────────────► T ──SIGCONT──► R
```

### 4.2 D 状态：为什么 kill -9 都杀不动

`S`（可中断睡眠）和 `D`（不可中断睡眠）的唯一区别是：**`D` 状态下，信号无法唤醒这个 task。** `kill -9` 投递了 `SIGKILL`，但 task 压根不会在这个睡眠点检查信号，于是"杀不动"，必须等它睡眠的那个条件满足（通常是底层 I/O 完成）才会醒来、然后才处理那个早就排队的 `SIGKILL`。

为什么内核要设计这么个"信号都叫不醒"的状态？因为有些睡眠**正处在不能被打断的临界区**：比如一个 task 提交了磁盘读、正在等 DMA 完成，此时若被信号中途唤醒返回用户态，内核里那次 I/O 的状态机就会处于不一致——有些资源拿了一半、有些回调还没跑。用 `D` 保证"这段睡眠必须走完"。

**正常的 `D` 是一瞬间的事**（一次磁盘 I/O 几百微秒到几毫秒），你 `ps` 几乎抓不到。**长时间 `D`（几秒、几十秒）才是病**，常见病因：

- 底层存储卡住：坏盘、NFS server 不可达（经典的 NFS hang）、iSCSI/网络存储断链、过载的磁盘队列。
- 内核某把锁长期持有，task 在等。

`D` 状态的 task **无法被杀死**，连 `kill -9` 都没用，唯一的彻底办法往往是**修复底层（恢复存储/网络）或重启机器**。诊断时看它卡在哪个内核函数：

```bash
# 查所有 D 状态进程
ps -eo pid,stat,wchan,comm | awk '$2 ~ /^D/'

# 看某个 D 进程卡在哪个内核函数（wchan）+ 内核调用栈
cat /proc/<pid>/wchan        # 例如 io_schedule
sudo cat /proc/<pid>/stack   # 完整内核栈，一眼看出卡在 NFS 还是 blk 层
```

### 4.3 TASK_KILLABLE：D 状态的"温柔版"

纯 `D`（信号完全无效）太刚，于是内核引入 **`TASK_KILLABLE`**（`TASK_UNINTERRUPTIBLE | TASK_WAKEKILL`）：平时和 `D` 一样不可中断、忽略普通信号，**但仍可被致命信号（如 `SIGKILL`）唤醒**。很多原本用纯 `D` 的等待点（尤其 NFS）逐步改用 `killable` 睡眠，于是"NFS 卡死的进程现在有时能 `kill -9` 掉了"。但并非所有不可中断睡眠都升级了，所以"杀不掉的 D 进程"在 2026 年依然存在。`ps` 里 `TASK_KILLABLE` 仍显示为 `D`，肉眼无法区分。

### 4.4 D 状态与 load average：被误解最深的指标

很多人以为 **load average 是"CPU 使用率"**。错。Linux 的 load average 统计的是 **"处于 `TASK_RUNNING`（R）+ `TASK_UNINTERRUPTIBLE`（D）的 task 数量"的指数移动平均**（1/5/15 分钟）。

关键就在那个 **`D`**：**等磁盘 I/O 的进程也算进 load**。这是 Linux 特有的设计（其他 Unix 的 load 多只算 CPU 就绪队列）。后果是：

- 一台 8 核机器，CPU 几乎空闲，但有一块盘卡了、几十个进程在 `D` 等 I/O —— **load average 照样飙到几十**。这时你盯着 CPU 利用率会一脸懵，而 load 高得吓人。
- 所以"load 高"不能直接等于"CPU 不够"，必须结合状态分解：到底是 R 多（CPU 真忙/就绪排队）还是 D 多（I/O 等待）。

快速分解当前 R / D：

```bash
# 实时统计各状态 task 数
ps -eo stat --no-headers | cut -c1 | sort | uniq -c
# 或用 vmstat 看 r（运行队列）和 b（不可中断阻塞）两列
vmstat 1
#  r  b   ...   r 高 = CPU 就绪排队；b 高 = D 状态阻塞（多半 I/O）
```

注意：`TASK_IDLE`（状态 `I`，即 `TASK_UNINTERRUPTIBLE | TASK_NOLOAD`）是给空闲内核线程用的，**带 `NOLOAD` 标志，不计入 load**——这是内核为了避免一堆空闲 kworker 虚高 load 而专门引入的。load average 的完整方法论见 [L18 诊断](./L18-精通-性能诊断方法论与工具.md)，更现代的替代是 PSI（压力失速信息）。

## 第五章 进程关系与终止：进程组、会话、僵尸、孤儿、subreaper、daemon、pidfd

### 5.1 进程组与会话：为什么 Ctrl+C 能停掉整条管道

`task_struct`（经 `signal_struct`）记录三层归属：**会话（session）→ 进程组（process group）→ 进程**。

- **进程组**：一组相关进程，有个 PGID（通常是组长 PID）。`kill -SIGINT -PGID`（负号）能一次发给整组。你在 shell 里跑 `a | b | c`，这三个进程组成一个进程组。
- **会话**：一组进程组的集合，通常对应一次登录/一个终端。会话有个会话首进程（session leader），可关联一个**控制终端（controlling terminal）**。
- **控制终端**：你按 `Ctrl+C`，终端驱动把 `SIGINT` 发给**前台进程组**的所有成员——这就是为什么 `a | b | c` 整条管道一起停。`Ctrl+Z` 发 `SIGTSTP`（停），`Ctrl+\` 发 `SIGQUIT`。

```bash
# 看进程的 session、进程组、控制终端
ps -eo pid,ppid,pgid,sid,tty,stat,comm
#                  │    │    │
#                  PGID SID  控制终端（? 表示无控制终端，如 daemon）
```

### 5.2 僵尸进程（Z）：尸体要人收

进程 `exit()` 后并不会立刻从系统消失。内核要保留它的**退出状态**（exit code、被什么信号杀的、资源使用统计 rusage），直到**父进程调用 `wait`/`waitpid` 取走**。这段"已死但状态没被取走"的时期，task 就是**僵尸（zombie，`Z`）**。

僵尸几乎不占资源（地址空间、fd 全释放了，只剩一个 `task_struct` 骨架占个 PID 槽位）。但**大量僵尸会耗尽 PID**（`/proc/sys/kernel/pid_max`，64 位默认可达约 4 百万）。僵尸的成因永远是：**父进程不 `wait`。** 你 `kill` 僵尸是没用的——它已经死了，要消灭它只能让父进程去 `wait`，或者父进程退出（僵尸被 reparent 给 subreaper/init，由后者 `wait` 收尸）。

正确收尸：父进程用 `SIGCHLD` 处理器 + `waitpid(-1, ..., WNOHANG)` 循环，或直接 `signal(SIGCHLD, SIG_IGN)`（POSIX 下子进程退出即自动回收、不产生僵尸）。

```c
#include <signal.h>
#include <sys/wait.h>
#include <unistd.h>

void reaper(int sig) {
    (void)sig;
    // 一个 SIGCHLD 可能对应多个子进程退出（信号不排队），必须循环
    while (waitpid(-1, NULL, WNOHANG) > 0) { }
}

int main(void) {
    struct sigaction sa = {0};
    sa.sa_handler = reaper;
    sa.sa_flags = SA_RESTART | SA_NOCLDSTOP;
    sigaction(SIGCHLD, &sa, NULL);
    // ... fork 子进程、干活 ...
    pause();
    return 0;
}
```

### 5.3 孤儿进程与 subreaper：爹死了谁管

如果父进程先于子进程退出，子进程就成了**孤儿（orphan）**。孤儿不会变僵尸，它会被**重新认领（reparenting）**。传统上认领给 PID 1（init/systemd），由 init 负责 `wait` 收尸。

但现代有了 **subreaper** 机制（`prctl(PR_SET_CHILD_SUBREAPER, 1)`）：一个进程可以声明自己为"子收割者"，于是它的后代进程成为孤儿时，**不再 reparent 到 PID 1，而是 reparent 到最近的祖先 subreaper**。这对进程管理器（如 systemd 的用户实例、容器运行时、`tini`/`dumb-init`）至关重要——它们想自己掌管整棵子进程树的生命周期，而不是把孤儿丢给系统 init。容器里 PID 1 也天然承担 subreaper 角色，这正是"容器 PID 1 必须会收尸"的由来（否则容器内僵尸堆积）。

### 5.4 daemon 化：脱离终端的标准动作

写一个后台服务（daemon），传统 double-fork 套路是为了**彻底脱离控制终端、自成会话、且永不重新获得终端**：

```c
// 经典 double-fork daemon 化（现代多数交给 systemd，但理解原理仍必要）
pid_t pid = fork();
if (pid > 0) _exit(0);        // 父退出，子在后台
setsid();                     // 子成为新会话 leader + 新进程组，脱离原控制终端
pid = fork();                 // 第二次 fork：子不再是 session leader，
if (pid > 0) _exit(0);        //   从此无法意外获得控制终端
chdir("/");                   // 不占用任何挂载点
umask(0);
// 关闭 / 重定向 stdin/stdout/stderr 到 /dev/null
```

2026 年的现实：**绝大多数服务不该自己 daemon 化，而是作为前台进程交给 systemd 管理**（`Type=simple`/`exec`）。systemd 用 cgroup 精确跟踪整棵进程树，比 double-fork + PID 文件可靠得多。详见 [L20 systemd](./L20-精通-systemd-与启动流程.md)（本系列）。

### 5.5 pidfd：终结 PID 复用竞争

经典 `kill(pid, sig)` 有个古老的隐患：**PID 会被复用**。你拿到一个 pid=4242 想杀它，但在你 `kill` 之前它退出了、4242 被分配给一个无辜的新进程——你的 `kill` 就误杀了别人。这是分布式/进程管理代码里真实存在的竞态。

**pidfd（5.x 起逐步完善）** 解决之：它是一个**指向具体进程实例的文件描述符**，即使 PID 数字被复用，pidfd 仍唯一绑定原来那个进程实例。三种获取/使用方式：

```c
#define _GNU_SOURCE
#include <sys/syscall.h>
#include <sys/wait.h>
#include <unistd.h>
#include <poll.h>
#include <signal.h>

// 1) 对已存在的进程开 pidfd
int pidfd = syscall(SYS_pidfd_open, target_pid, 0);

// 2) 通过 pidfd 发信号（不会误杀复用的 PID）
syscall(SYS_pidfd_send_signal, pidfd, SIGTERM, NULL, 0);

// 3) pidfd 可被 poll/epoll：进程退出时变为可读 —— 用 fd 等待子进程
struct pollfd pfd = { .fd = pidfd, .events = POLLIN };
poll(&pfd, 1, -1);   // 子进程退出后返回
// 还可 waitid(P_PIDFD, pidfd, &info, WEXITED) 取退出状态
```

更好的是创建时直接拿：`clone3` 带 `CLONE_PIDFD`（或老的 `clone(CLONE_PIDFD, ...)`）在创建子进程的**同一瞬间**返回 pidfd，从根上消除竞态窗口。pidfd 还能跨进程传递（通过 `SCM_RIGHTS`），让 sidecar/管理进程安全地持有目标进程句柄。这是 2026 年进程管理代码（含容器运行时、systemd）的现代基础设施。

## 第六章 /proc/[pid] 全解：把一个 task 摊在桌上看

`/proc` 是内核暴露 task 内部状态的伪文件系统，每个 task 一个目录。读懂它，等于不写代码也能解剖任意进程。

### 6.1 status：人类可读的概览

```bash
cat /proc/<pid>/status
```

关键行：

| 字段 | 含义 |
|---|---|
| `Name` / `State` | 进程名 / 当前状态（如 `S (sleeping)`、`D (disk sleep)`） |
| `Tgid` / `Pid` / `PPid` | 线程组 ID（用户 PID）/ 本 task ID / 父 PID |
| `Threads` | 该进程的线程数（线程组内 task 数） |
| `VmRSS` / `VmSize` | 常驻内存 / 虚拟内存大小 |
| `RssAnon` / `RssFile` / `RssShmem` | RSS 细分（匿名/文件映射/共享内存） |
| `voluntary_ctxt_switches` / `nonvoluntary_ctxt_switches` | 主动/被动上下文切换次数（被动多 = 被抢占多 = CPU 竞争激烈） |
| `SigQ` / `SigPnd` / `SigBlk` / `SigCgt` | 信号队列/待决/屏蔽/捕获的位掩码 |
| `NSpid` | 该进程在各层 PID namespace 中的 PID（容器排障神器） |

### 6.2 stat：机器可读，load 计算的源头

`/proc/<pid>/stat` 是一行空格分隔的数字，`ps`/`top` 解析它。重要位（按字段序）：`state`（第 3）、`ppid`（4）、`pgrp`（5）、`session`（6）、`tty_nr`（7）、`minflt`（10，minor 缺页）、`majflt`（12，major 缺页 = 真读盘）、`utime`/`stime`（14/15，用户/内核 CPU 时间，单位 tick）、`num_threads`（20）、`starttime`（22）、`rss`（24）。`major fault` 持续高，说明在频繁换页/读盘，往往是内存不足的信号。

### 6.3 maps / smaps：地址空间布局

```bash
cat /proc/<pid>/maps          # 每个 VMA 一行：地址区间 权限 偏移 设备 inode 路径
# 555... r-xp ... /usr/bin/app   ← 代码段（可执行）
# 7f...  rw-p ... [heap]/[stack]/匿名/共享库
cat /proc/<pid>/smaps_rollup  # RSS/PSS/USS 汇总（容器内存归因常用，见 L06）
```

`maps` 直观展示 [L04](./L04-精通-虚拟内存与分页.md) 讲的地址空间分段。线程共享 `mm`，所以同进程所有线程的 `maps` 完全一样。

### 6.4 fd：打开的文件描述符

```bash
ls -l /proc/<pid>/fd
# 0 -> /dev/pts/3   1 -> /dev/null   3 -> socket:[12345]   4 -> /var/log/app.log
```

每个 fd 是个符号链接，指向它打开的文件/socket/pipe/eventfd。**排查"fd 泄漏 / Too many open files"** 的第一现场：`ls /proc/<pid>/fd | wc -l` 数量 vs `cat /proc/<pid>/limits` 里的 `Max open files`。`lsof -p <pid>` 是更友好的封装。

### 6.5 task：线程的真身

```bash
ls /proc/<pid>/task            # 每个子目录是一个线程（tid），结构与 /proc/[pid] 相同
cat /proc/<pid>/task/<tid>/status   # 单个线程的状态/CPU 时间
```

这就是"进程是 task 容器"的最直接体现——`/proc/<pid>/task/` 下每个目录是一个 tid，里面还有自己的 `stat`/`status`/`stack`。`top -H`、`ps -eLf` 本质都在读这里。排查"哪个线程吃满了一个核"，就是遍历 `task/*/stat` 看各线程 `utime+stime` 增量。

### 6.6 其它高频文件

| 文件 | 用途 |
|---|---|
| `wchan` / `stack` | task 正卡在哪个内核函数 / 完整内核调用栈（查 D 状态利器） |
| `limits` | 该进程的各项 rlimit（fd 数、栈大小、core 大小等） |
| `cgroup` | 它属于哪些 cgroup（容器归属，见 L17） |
| `ns/` | 各 namespace 的标识（同链接 = 同 namespace，见 L16） |
| `comm` / `cmdline` | 进程名（可写，最长 15 字符）/ 完整命令行（NUL 分隔） |
| `environ` | 启动时的环境变量（NUL 分隔） |
| `oom_score` / `oom_score_adj` | OOM 评分 / 人为调整（见 L06） |

## 生产实践

1. **永远给 `fork` 的子进程收尸。** 服务里 `fork` 后必须 `wait`/处理 `SIGCHLD`，否则僵尸累积、PID 耗尽。容器场景下确保 PID 1 会收尸（用 `tini`/`dumb-init`，或应用本身处理 `SIGCHLD`）。

2. **多线程程序统一管理信号。** 用一个专职线程 `sigwait`，其余线程 `pthread_sigmask` 全屏蔽，避免"不知道哪个线程收到 `SIGTERM`"导致的优雅退出失灵。

3. **进程管理代码用 pidfd 取代裸 PID。** 凡是"拿到 PID 后过一会儿再 `kill`"的逻辑，都有 PID 复用误杀风险。新代码用 `pidfd_open` + `pidfd_send_signal`，或 `clone3(CLONE_PIDFD)`。

4. **服务交给 systemd，别自己 double-fork。** 前台运行（`Type=exec`），让 systemd 用 cgroup 跟踪进程树、做重启与资源限制；PID 文件方案在崩溃/复用场景下不可靠。

5. **fork 大内存进程要算 COW 账。** Redis `bgsave`、JVM `fork` 外部命令等：子进程虽是 COW，但父进程持续写会逐页触发拷贝，瞬时内存可能接近翻倍。生产上要么预留足够内存 + 关闭 THP（避免大页放大 COW 单位），要么改用 `vfork`/`posix_spawn` 仅为 `exec`。

6. **排查高 load 先分 R/D。** `vmstat 1` 看 `r`（CPU 就绪）和 `b`（D 阻塞）两列：r 高加 CPU/优化计算，b 高查存储/网络存储。别看见 load 高就盲目扩 CPU。

7. **用 `/proc/<pid>/task` 定位"忙线程"。** 进程整体 CPU 高时，遍历 `task/*/comm` + `stat`（或直接 `top -H -p <pid>`）找出真正吃 CPU 的那个线程，再 `pstack`/`perf` 看它在干嘛。

## 陷阱清单

1. **现象**：`ps` 看到大量 `<defunct>`（Z）进程，越积越多，最终 `fork` 报 `EAGAIN`。
   **原因**：父进程不 `wait`，子进程退出状态无人回收，僵尸耗尽 PID（`pid_max`）。
   **修法**：父进程注册 `SIGCHLD` 处理器循环 `waitpid(-1,...,WNOHANG)`；或 `signal(SIGCHLD, SIG_IGN)`；容器内确保 PID 1 收尸。

2. **现象**：某进程 `D` 状态卡死，`kill -9` 完全无效，机器 load 飙到几十而 CPU 空闲。
   **原因**：`TASK_UNINTERRUPTIBLE` 不响应任何信号，多为底层存储/NFS hang；D 计入 load 故 load 虚高。
   **修法**：`cat /proc/<pid>/stack`/`wchan` 看卡在哪（`io_schedule`/NFS）；恢复底层存储或网络；纯 D 往往只能重启机器。

3. **现象**：多线程程序 `kill -TERM` 后行为不确定，有时优雅退出有时直接死。
   **原因**：进程定向信号被内核随机投给某个未屏蔽线程，而该线程可能没装 handler。
   **修法**：主线程统一装信号处理或专线程 `sigwait`，其余线程 `pthread_sigmask(SIG_BLOCK,...)` 屏蔽。

4. **现象**：进程管理器偶发"杀错进程"，杀掉了一个无关服务。
   **原因**：PID 复用竞态——记录的 PID 在 `kill` 前已退出并被复用。
   **修法**：改用 pidfd（`pidfd_open`/`clone3(CLONE_PIDFD)` + `pidfd_send_signal`），绑定进程实例而非 PID 数字。

5. **现象**：Redis/大内存进程在 `bgsave`/`fork` 期间内存暴涨甚至触发 OOM。
   **原因**：COW 下父进程持续写入，按页触发物理页拷贝；开启 THP 时拷贝单位是 2MB 大页，放大膨胀。
   **修法**：预留内存余量；`echo never > /sys/kernel/mm/transparent_hugepage/enabled` 关 THP；设置合理 `vm.overcommit_memory`。

6. **现象**：容器里 `getpid()` 返回 1，但宿主 `ps` 上是个大数字，跨层排障对不上号。
   **原因**：PID namespace——同一 task 在不同 namespace 有不同 PID 值。
   **修法**：看 `/proc/<pid>/status` 的 `NSpid` 行（列出各层 PID）；用 `lsns`/`nsenter` 对应（见 L16）。

7. **现象**：服务"明明退出了"但端口仍被占用 / 资源没释放，新实例起不来。
   **原因**：daemon 化不彻底，残留子进程或孤儿仍持有 fd；double-fork/PID 文件方案在异常退出时残留。
   **修法**：交给 systemd 用 cgroup 管理整棵进程树（`systemctl stop` 会清干净）；自管理时用 subreaper + pidfd 跟踪后代。

8. **现象**：`top` 显示某进程 CPU 800%，但代码看着没那么多并发。
   **原因**：那是线程组里多个 task 的 CPU 之和（按 tgid 折叠显示）。
   **修法**：`top -H -p <pid>` 或读 `/proc/<pid>/task/*/stat` 按线程拆分，定位真正的热点线程。

## 2026 现状

- **clone3 已成现代创建接口主力**：`struct clone_args` + `size` 的可扩展设计让新能力（`set_tid`、`CLONE_INTO_CGROUP`）平滑加入。容器运行时（runc/crun）与 systemd 在 6.x 上广泛使用 `CLONE_INTO_CGROUP` + `CLONE_PIDFD`，把"创建进程、放进 cgroup、拿到可靠句柄"合并为一步，消除中间窗口。
- **pidfd 成为进程管理事实标准**：`pidfd_open` / `pidfd_send_signal` / `pidfd_getfd` / `waitid(P_PIDFD)` 一整套接口稳定，Go（`os.Process` 在新版本内部用 pidfd 避免复用竞态）、systemd、容器栈普遍采用。"裸 PID 发信号"在新代码里被视为反模式。
- **D 状态仍是 SRE 头号迷思**：`TASK_KILLABLE` 让部分（尤其 NFS）等待可被 `SIGKILL` 打断，但并非全部；纯 `D` 卡死仍可能只能重启。现代诊断更多转向 **PSI**（`/proc/pressure/io` 等）量化 I/O 失速，而非只盯 load average。
- **load average 的局限被普遍认知**：因为 D 计入 load，社区长期推荐用 PSI + 按状态分解（R vs D）替代"唯 load 论"。`TASK_NOLOAD`（`TASK_IDLE`）确保空闲内核线程不污染 load。
- **Go/Rust 等运行时之下仍是 task**：无论 goroutine 还是 async task，落到内核都是 `CLONE_THREAD` 的 task 在被 EEVDF 调度（见 [L03 调度](./L03-精通-CPU-调度-CFS-到-EEVDF.md)）。理解 task 模型仍是看懂任何高级运行时的地基。

## 练习题

1. 用 C 写一个程序，`fork` 后父子都打印 `getpid()`、`getppid()`、`gettid()`（用 `SYS_gettid`），解释为什么父进程的 `getpid()` 等于子进程的 `getppid()`，而父子的 `gettid()` 与各自 `getpid()` 又分别相等。

2. 写一个多线程程序（pthread），3 个线程各打印 `getpid()` 和 `gettid()`，用 `ls /proc/<pid>/task` 验证线程数，并解释为什么 `getpid()` 全相同。

3. 复现 COW：`malloc` 并 touch 512MB，`fork` 后子进程只读不写，对比父子 `VmRSS`（`/proc/<pid>/status`）；再让子进程逐页写入，观察其 `RssAnon` 与 `min_flt`（`/proc/<pid>/stat`）如何上涨。解释每一步。

4. 制造一个僵尸：父进程 `fork` 后 `sleep(60)` 且不 `wait`，子进程立即 `exit`。用 `ps -el` 找到 `Z` 状态那行，解释为什么 `kill -9` 杀不掉僵尸，以及让父进程退出后僵尸去了哪里。

5. 制造一个 `D` 状态（提示：可对一个慢速/挂起的存储做大 I/O，或读一个 hang 的 NFS 挂载）。用 `cat /proc/<pid>/wchan` 和 `/proc/<pid>/stack` 看它卡在哪个内核函数，并解释 `kill -9` 为何无效。

6. 用 `clone3` + `CLONE_PIDFD` 创建子进程拿到 pidfd，用 `poll` 等待它退出，再用 `waitid(P_PIDFD, ...)` 取退出码。说明这相比"记录 PID 再 `kill`"消除了什么竞态。

7. 写一个正确的 daemon：double-fork + `setsid` + `chdir("/")` + 重定向标准流。然后用 `ps -eo pid,ppid,pgid,sid,tty,comm` 验证它的 PPID 为 1、有独立 SID、`tty` 为 `?`。再说明为什么生产环境更应交给 systemd。

8. 在一台 load average 高的机器上，用 `vmstat 1` 的 `r`/`b` 两列和 `ps -eo stat | cut -c1 | sort | uniq -c` 判断瓶颈是 CPU 就绪排队还是 I/O 阻塞，并结合 `/proc/pressure/{cpu,io}`（PSI）给出更细的归因。

## 参考答案

1. 内核里 `getpid()` 返回 `tgid`，`gettid()` 返回 task 自己的 `pid`，`getppid()` 返回父进程的 `tgid`。`fork` 出的子进程是单线程新进程，所以子进程 `pid == tgid`，即它的 `gettid() == getpid()`；父进程同理。子进程的父亲就是那个父进程（线程组 leader），所以子进程 `getppid()` 取的就是父进程的 `tgid`，即父进程的 `getpid()`。父子各自都是单线程进程，故各自 `gettid() == getpid()`。

2. 程序里 3 个 pthread 各自是带 `CLONE_THREAD` 的 task，加入同一线程组，`tgid` 都等于主线程的 pid，所以 `getpid()`（返回 tgid）三者全相同；而每个线程自己的 `pid`（即 `gettid()`）各不相同。`ls /proc/<pid>/task` 下会看到 4 个目录（主线程 + 3 个，或按实现 3+1），数量等于线程组内 task 数。`getpid()` 相同的本质是它们共享同一个线程组（同一 `signal_struct`/同一 tgid），而非各自独立进程。

3. (1) malloc + touch 512MB：父进程 `VmRSS` 增加约 512MB（真实分配了物理页）。(2) fork 后子进程只读：内核只拷页表、把可写页标只读、共享物理页，子进程此刻 RSS 几乎为 0 增量（共享父页），父子 RSS 在统计上各自计入共享页但物理页只有一份。(3) 子进程逐页写入：每写一个之前共享的只读页就触发一次 COW minor fault——内核分配新物理页、拷贝、改回可写。于是子进程 `RssAnon` 随写入页数线性上涨（最终接近 512MB），`min_flt`（minor 缺页计数）同步增长，每页一次。这直观证明"拷贝被推迟到第一次写，且只拷被写的那一页"。

4. 子进程 `exit` 后变僵尸（Z），内核保留它的 `task_struct` 骨架与退出状态，等父进程 `wait` 取走；父进程 `sleep(60)` 不 wait，僵尸就一直在。`kill -9` 杀不掉僵尸是因为它已经死了——地址空间、fd 都释放了，没有可被信号作用的执行实体，信号对一具"尸体"无意义；要消除它只能让父进程去 `wait` 取走状态。父进程退出后，僵尸（孤儿化）被 reparent 给最近的 subreaper 或 PID 1（init/systemd），由后者 `wait` 收尸，僵尸随即消失。

5. 用 `cat /proc/<pid>/wchan` 看它阻塞在哪个内核函数（如 `io_schedule`、NFS 相关函数），`cat /proc/<pid>/stack` 看完整内核调用栈，一眼区分卡在块层还是 NFS/网络存储层。`kill -9` 无效是因为 `D`（`TASK_UNINTERRUPTIBLE`）状态下 task 根本不会在睡眠点检查信号，必须等它睡眠的条件满足（底层 I/O 完成）才会醒，然后才处理排队的 SIGKILL；若底层永久 hang，纯 D 往往只能修复存储或重启机器。

6. 用 `clone3` 设 `CLONE_PIDFD`，内核在创建子进程的同一瞬间把 pidfd 写回 `clone_args.pidfd`；pidfd 绑定的是具体进程实例而非 PID 数字。`poll` 该 pidfd（`POLLIN`），子进程退出时变为可读返回；再 `waitid(P_PIDFD, pidfd, &info, WEXITED)` 取退出码。相比"记录 PID 再 kill"，它消除了 PID 复用竞态：传统做法中目标进程可能在你操作前退出、PID 被复用给无辜新进程，导致误杀/误等；pidfd 始终唯一指向原实例，复用的新 PID 不会被它命中。

7. daemon 步骤：第一次 `fork` 后父退出（让子在后台、脱离调用 shell 的进程组）；`setsid()` 使子成为新会话 leader + 新进程组，脱离原控制终端；第二次 `fork` 后父退出，使最终进程不再是 session leader，从此无法意外重新获得控制终端；`chdir("/")` 不占挂载点；重定向 stdin/stdout/stderr 到 `/dev/null`。验证：`ps -eo pid,ppid,pgid,sid,tty,comm` 中该进程 PPID 为 1（原父都退出后被 reparent 到 init）、有独立 SID、tty 列为 `?`（无控制终端）。生产更应交给 systemd 的原因：systemd 以 cgroup 跟踪整棵进程树，重启/资源限制/收尸都可靠，而 double-fork + PID 文件在崩溃或 PID 复用时不可靠。

8. 先看 `vmstat 1`：`r` 列是运行队列长度（R 状态、等 CPU），`b` 列是不可中断阻塞（D 状态、多为 I/O）。`r` 持续 > CPU 核数说明 CPU 就绪排队、瓶颈在 CPU；`b` 高说明大量进程在等 I/O。再用 `ps -eo stat | cut -c1 | sort | uniq -c` 统计 R 与 D 的数量印证。最后看 PSI：`/proc/pressure/cpu` 的 some/full avg 高 = CPU 竞争导致的失速；`/proc/pressure/io` 高 = I/O 失速。结论：load 高但 io PSI 高、cpu PSI 低、b 多，则是存储/网络存储瓶颈，扩 CPU 无用；反之 cpu PSI 高、r 多才是真 CPU 不足。
