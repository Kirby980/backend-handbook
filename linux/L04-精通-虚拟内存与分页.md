## 引言：malloc 1GB 不占物理内存？

先做一个实验。下面这段 C 程序申请 1 GB 内存，但只往里写一个字节：

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(void) {
    size_t n = 1UL << 30;        // 1 GB
    char *p = malloc(n);
    if (!p) { perror("malloc"); return 1; }
    p[0] = 'A';                  // 只触碰第一个字节
    printf("pid=%d, p=%p, 按回车退出\n", getpid(), p);
    getchar();
    return 0;
}
```

编译运行，另开终端看它的内存：

```bash
$ ./a.out &
pid=12345, p=0x7f...

$ grep -E 'VmSize|VmRSS' /proc/12345/status
VmSize:  1052800 kB     # ≈ 1 GB —— 虚拟内存
VmRSS:       1536 kB    # ≈ 1.5 MB —— 真正占用的物理内存
```

`VmSize`（即 `ps` 里的 **VSZ**）显示我们"拥有"1 GB，而 `VmRSS`（即 **RSS**，Resident Set Size）显示真正落到物理内存的只有 1.5 MB。这就是虚拟内存的核心把戏：**malloc 给你的是一张"地址支票"，不是现金；只有你真正写入某一页时，内核才会把一页物理内存"兑现"给你。**

这不是 bug，是设计。它解释了一连串后端工程师天天遇到的现象：

- 为什么 `top` 里 Java/Go 进程的 VSZ 动辄几十 GB，机器却没爆？
- 为什么 fork 一个 10 GB 的进程"瞬间"完成、不复制 10 GB？（COW，见 [L02 进程与线程模型](./L02-精通-进程与线程模型.md)）
- 为什么数据库重启后第一次查询慢（major fault），第二次就快（page cache 命中）？
- 为什么 THP 会带来"莫名其妙的延迟毛刺"，PostgreSQL/Redis 文档却建议关掉它？

本章把虚拟内存从最上层的地址空间布局，一路拆到 MMU 硬件做地址翻译、TLB 缓存翻译结果、缺页中断把虚拟页"接"到物理页。读完你应该能：

- 画出 64 位进程的虚拟地址空间布局，解释 VSZ 与 RSS 的差异
- 说清 4 级 / 5 级页表如何把一个 48/57 位虚拟地址翻译成物理地址
- 解释 TLB miss、TLB shootdown，以及大页为什么能省 TLB
- 区分 minor / major fault，并跟踪一次缺页的内核路径
- 讲清 `mmap` 文件映射 vs `read/write`、`MAP_SHARED` vs `MAP_PRIVATE`
- 判断什么场景该开 HugePage，什么场景该关 THP

## 第一章 虚拟地址空间

### 1.1 为什么需要虚拟内存

如果进程直接用物理地址，会有三个致命问题：

| 问题 | 没有虚拟内存 | 有虚拟内存 |
|---|---|---|
| **隔离** | 进程 A 能写进程 B 的内存 | 每个进程独立地址空间，互不可见 |
| **重定位** | 程序必须知道自己被加载到哪 | 每个进程都以为自己独占从 0 开始的地址 |
| **超额分配** | 物理内存 = 可用内存上限 | 虚拟空间远大于物理，按需兑现（demand paging） |

虚拟内存的本质是一层**间接（indirection）**：CPU 发出的每一个地址都是虚拟地址（Virtual Address，VA），经过 MMU（Memory Management Unit）查页表翻译成物理地址（Physical Address，PA）才真正访问内存。这层间接由硬件（MMU）+ 软件（内核页表）共同维护。

### 1.2 64 位地址空间布局

x86-64 在传统 4 级页表下使用 **48 位有效虚拟地址**（5 级页表下 57 位）。48 位即 256 TB 的虚拟空间，被劈成两半：

```
0xFFFFFFFFFFFFFFFF ┌─────────────────────────┐ ← 内核空间（所有进程共享同一份内核映射）
                   │   kernel space          │   128 TB（48 位规范地址高半区）
0xFFFF800000000000 ├─────────────────────────┤
                   │                         │
   非规范地址空洞   │   non-canonical hole    │   （48 位下，bit47 必须符号扩展，
                   │                         │     中间这段地址非法，访问触发 GP）
0x00007FFFFFFFFFFF ├─────────────────────────┤ ← 用户空间上限
                   │   [stack] ↓向下增长      │
                   │   ...                   │
                   │   [mmap region] ↓        │   动态库、匿名大块、文件映射
                   │   ...                   │
                   │   [heap] ↑ brk 向上增长   │
                   ├─────────────────────────┤
                   │   .bss   未初始化数据     │
                   │   .data  已初始化数据     │
                   │   .text  代码（只读+执行） │
0x0000000000400000 ├─────────────────────────┤ ← 典型 ELF 加载基址（无 PIE）
0x0000000000000000 └─────────────────────────┘ ← 第 0 页不可访问（NULL 解引用 → SIGSEGV）
```

关键点：

- **高半区（kernel space）是所有进程共享的同一份映射**。这就是为什么进入内核态不需要切页表（除非 KPTI / Meltdown 缓解开启，那是另一回事）。
- **非规范地址空洞**：48 位有效地址要求 bit[63:47] 全部等于 bit[47]（符号扩展），否则 CPU 视为非规范地址，访问触发 #GP。这避免了"中间那一大段"被误用。
- **第 0 页永远不映射**，所以解引用 NULL 指针必然 SIGSEGV——这是设计，不是巧合。

用 `/proc/[pid]/maps` 可以直接看一个真实进程的布局：

```bash
$ cat /proc/self/maps
55a3c0e00000-55a3c0e01000 r--p 00000000 fd:01 ...  /usr/bin/cat   # .text 前的只读段
55a3c0e01000-55a3c0e05000 r-xp 00001000 fd:01 ...  /usr/bin/cat   # 代码段 r-x
55a3c0e05000-55a3c0e07000 r--p 00005000 fd:01 ...  /usr/bin/cat   # 只读数据
55a3c0e07000-55a3c0e08000 r--p 00006000 fd:01 ...  /usr/bin/cat   # .data 前
55a3c0e08000-55a3c0e09000 rw-p 00007000 fd:01 ...  /usr/bin/cat   # .data/.bss rw
55a3c2a1f000-55a3c2a40000 rw-p 00000000 00:00 0    [heap]
7f8e4a000000-7f8e4a028000 r--p 00000000 fd:01 ...  /usr/lib/libc.so.6
...
7ffd3c5a0000-7ffd3c5c1000 rw-p 00000000 00:00 0    [stack]
7ffd3c5f0000-7ffd3c5f4000 r--p 00000000 00:00 0    [vvar]    # vDSO 数据
7ffd3c5f4000-7ffd3c5f6000 r-xp 00000000 00:00 0    [vdso]    # vDSO 代码（见 L01）
ffffffffff600000-ffffffffff601000 --xp 00000000 00:00 0 [vsyscall]
```

每一行是一个 **VMA**（虚拟内存区域）。第二列 `r-xp` 是权限：读/写/执行/(私有 p 或共享 s)。

### 1.3 ASLR：地址空间布局随机化

注意上面 heap、mmap、stack 的起始地址是随机的——这是 **ASLR**（Address Space Layout Randomization），让攻击者无法预测关键数据/代码的地址。

```bash
$ cat /proc/sys/kernel/randomize_va_space
2        # 0=关闭  1=mmap+stack+vdso 随机  2=再加上 heap/brk（默认）
```

调试时常临时关掉以获得稳定地址：`setarch $(uname -m) -R ./prog` 或 `echo 0 > /proc/sys/kernel/randomize_va_space`。生产**绝不可关**——这是基础的纵深防御。PIE（Position Independent Executable）编译的程序连 .text 基址都随机化。

### 1.4 mm_struct 与 vm_area_struct

内核里，每个进程的整个地址空间由一个 `mm_struct` 描述；线程组内的线程共享同一个 `mm_struct`（这正是"线程共享地址空间"的本质，见 [L02](./L02-精通-进程与线程模型.md)）。

```c
// 简化自 include/linux/mm_types.h
struct mm_struct {
    struct maple_tree mm_mt;     // VMA 的容器：6.1 起用 maple tree 取代红黑树
    pgd_t *pgd;                  // 顶级页表基址（写入 CR3 的就是它）
    atomic_t mm_users;           // 多少线程在用
    atomic_t mm_count;           // 引用计数
    unsigned long start_code, end_code, start_data, end_data;
    unsigned long start_brk, brk, start_stack;
    unsigned long mmap_base;     // mmap 区起始
    unsigned long total_vm;      // 总虚拟页数 → 对应 VSZ
    unsigned long hiwater_rss;   // RSS 峰值
    ...
};
```

每个 VMA 是一个 `vm_area_struct`，描述一段连续、权限相同的虚拟地址区间：

```c
// 简化
struct vm_area_struct {
    unsigned long vm_start;          // 区间起始 VA
    unsigned long vm_end;            // 区间结束 VA
    pgprot_t vm_page_prot;           // 权限（rwx）
    unsigned long vm_flags;          // VM_READ/VM_WRITE/VM_EXEC/VM_SHARED ...
    struct file *vm_file;            // 文件映射时指向文件；匿名映射为 NULL
    unsigned long vm_pgoff;          // 文件内偏移
    const struct vm_operations_struct *vm_ops;  // 含 .fault 缺页回调
};
```

> **6.1 的重要变化**：管理 VMA 的数据结构从红黑树 + 链表换成了 **maple tree**（一种 RCU 友好的 B 树变体），查找、插入更高效，且大幅降低了 mmap 锁竞争。这是 folio 之外内存子系统近年的一项基础重构。你在老资料里看到的 `mm->mmap` 链表头已不存在。

`mm_struct` 是连接"虚拟"与"物理"的总枢纽：`total_vm`（页数 × 页大小）对应 VSZ；真正映射了物理页的部分构成 RSS。

## 第二章 分页与页表

### 2.1 页与页框

虚拟内存以**页（page）**为单位管理，物理内存以**页框（page frame）**为单位管理，二者大小相同，x86-64 默认 **4 KB**。

```
虚拟地址 (48 位) = | 页号 VPN (36 位) | 页内偏移 (12 位) |
                               ↓ 查页表翻译
物理地址        = | 页框号 PFN        | 页内偏移 (12 位，原样照搬) |
```

偏移 12 位 = 4096，正好一页。翻译只需把"虚拟页号 VPN → 物理页框号 PFN"，偏移直接照抄。这个 VPN→PFN 的映射表就是**页表（page table）**。

问题来了：48 位地址有 2^36 ≈ 680 亿个页，每个页表项 8 字节，单级页表要 512 GB——荒谬。解法是**多级页表**：稀疏地址空间下只为用到的部分建表。

### 2.2 4 级页表

x86-64 把 48 位地址中的 36 位 VPN 切成 4 段，每段 9 位（2^9 = 512 项），逐级索引：

```
虚拟地址 48 位：
┌────────┬────────┬────────┬────────┬──────────────┐
│ PGD(9) │ PUD(9) │ PMD(9) │ PTE(9) │  offset(12)  │
└────────┴────────┴────────┴────────┴──────────────┘
   bit47-39 bit38-30 bit29-21 bit20-12   bit11-0

CR3 ─→ PGD ─[idx]→ PUD ─[idx]→ PMD ─[idx]→ PTE ─[idx]→ PTE 项含 PFN
       (一页512项)  ...                              ↓
                                          PFN<<12 | offset = 物理地址
```

Linux 内核里这四级叫 **PGD → P4D → PUD → PMD → PTE**（注意中间多了 P4D，为 5 级做准备；4 级时 P4D 被"折叠"成与 PGD 同级）：

| 级别 | Linux 名 | x86 术语 | 覆盖范围/项 |
|---|---|---|---|
| 顶级 | PGD (Page Global Dir) | PML4 | 512 GB |
| 第 4 | P4D | — (4 级时折叠) | 512 GB |
| 第 3 | PUD (Page Upper Dir) | PDPT | 1 GB |
| 第 2 | PMD (Page Middle Dir) | PD | 2 MB |
| 叶子 | PTE (Page Table Entry) | PT | 4 KB |

每级表本身占一页（512 × 8B = 4 KB）。**多级的精髓**：只有真正用到的子树才分配下级表。一个只用了几 MB 的进程，整个页表可能就几页。

### 2.3 5 级页表

随着内存规模膨胀，48 位（256 TB）虚拟空间不够用了（尤其是巨型机和持久内存场景）。Intel 引入 **5 级页表**（LA57），在 PGD 之上再加一级 **PGD（PML5）**，把虚拟地址扩到 **57 位 = 128 PB**，物理地址扩到 52 位。

```
57 位虚拟地址：
┌──────┬──────┬──────┬──────┬──────┬──────────┐
│PGD(9)│P4D(9)│PUD(9)│PMD(9)│PTE(9)│offset(12)│
└──────┴──────┴──────┴──────┴──────┴──────────┘
```

到 2026 年，5 级页表在主流服务器 CPU 与发行版内核中已普遍可用，但**默认仍按需启用**：内核在地址超过 47 位时才使用第 5 级（避免无谓的一次额外内存访问）。可用 `grep la57 /proc/cpuinfo` 看硬件是否支持。绝大多数应用感知不到差异——这正是分页抽象的价值。

### 2.4 PTE 标志位

每个 PTE 除了存 PFN，低位还有一串控制标志：

| 位 | 名称 | 含义 |
|---|---|---|
| P | Present | 1=该页在内存中；0=缺页（可能被换出/未分配/COW） |
| R/W | Writable | 0=只读（写触发缺页 → 可能 COW） |
| U/S | User/Supervisor | 0=仅内核可访问，用户态访问 → SIGSEGV |
| A | Accessed | 被访问过则硬件置 1（回收算法据此判断冷热，见 [L05](./L05-精通-物理内存管理与回收.md)） |
| D | Dirty | 被写过则硬件置 1（回写脏页的依据） |
| PS/PSE | Page Size | 在 PMD/PUD 级置 1 表示这是大页（2 MB / 1 GB），不再下钻 |
| NX | No-eXecute | 1=该页不可执行（DEP/W^X 防御的硬件基础） |

`A` 和 `D` 位是**硬件自动维护、软件读取并清除**的——内存回收和脏页回写两大机制都依赖它们。`P=0` 是缺页中断的触发开关，第四章详述。

### 2.5 地址翻译全流程

把上面拼起来，一次访问 `mov rax, [vaddr]` 的完整翻译：

```
1. CPU 发出虚拟地址 vaddr
2. MMU 先查 TLB（见第三章）；命中 → 直接得到 PFN，结束（快路径，~1 cycle）
3. TLB miss → page table walk（硬件页表遍历器 walker 自动做）：
   读 CR3 → PGD[idx] → (P4D) → PUD → PMD → PTE
   每一级都是一次内存访问（可能再次 cache miss）
4. PTE.P == 1 → 取 PFN，组装物理地址，填回 TLB，访问内存
   PTE.P == 0 → 触发 #PF 缺页中断，进内核 do_page_fault（见第四章）
5. 顺带检查权限：写只读页 / 用户访问内核页 → 也走缺页（可能是 COW 或 SIGSEGV）
```

注意第 3 步：**一次 TLB miss 在 4 级页表下要 4 次访存**（5 级下 5 次）。这就是 TLB 为何如此重要，也是大页的核心价值。

## 第三章 TLB

### 3.1 TLB 是什么

**TLB**（Translation Lookaside Buffer）是 MMU 内部缓存"VPN→PFN"翻译结果的小型高速缓存（几十到上千项）。它直接决定地址翻译走快路径还是慢路径：

```
            ┌── TLB 命中 ──→ 直接拿 PFN（~1 cycle）        ★ 快
虚拟地址 ──→ TLB
            └── TLB miss ──→ page walk（4~5 次访存）── 填 TLB ── 慢
```

TLB 通常分级（L1 dTLB/iTLB + L2 STLB），并区分数据/指令、4K/2M/1G 页大小。可以用 `perf` 直接量 TLB miss：

```bash
$ perf stat -e dTLB-load-misses,dTLB-loads,iTLB-load-misses ./your_app
       1,234,567      dTLB-load-misses    #    2.31% of all dTLB cache accesses
      53,456,789      dTLB-loads
          45,678      iTLB-load-misses
```

TLB miss 率高的程序（大堆、随机访问、指针追逐）会在 page walk 上耗掉惊人的周期。

### 3.2 TLB shootdown

TLB 是 per-CPU 的。当一个 CPU 修改了页表（比如 munmap、change protection、迁移页），**其它 CPU 的 TLB 里可能还缓存着旧翻译**，必须让它们失效——这叫 **TLB shootdown**。

```
CPU0: munmap(addr)  →  改页表，清自己 TLB
   │
   └─ 发 IPI（处理器间中断）→ CPU1, CPU2, CPU3
                              每个 CPU 在中断里 invlpg / flush 本地 TLB
   │
   └─ 等所有 CPU 确认完成 ← 同步点，CPU0 在此自旋等待
```

shootdown 是**同步、跨核、走 IPI** 的，核越多越贵。它是很多"munmap/madvise 慢"、"多线程频繁改内存映射卡顿"问题的隐藏元凶。诊断：

```bash
# 看 TLB shootdown 中断计数
$ grep TLB /proc/interrupts
TLB:  ...  per-cpu counts ...  TLB shootdowns

# 用 bpftrace 抓 shootdown 热点（需内核支持对应 tracepoint）
$ bpftrace -e 'tracepoint:tlb:tlb_flush { @[args->reason] = count(); }'
```

减少 shootdown 的思路：减少页表改动频率（别频繁 mmap/munmap，用内存池）、用大页（同样地址范围、更少页表项要刷）、绑核减少跨核共享。

### 3.3 PCID / ASID

每次切换进程要换 CR3（换页表），传统做法是**整个 TLB 全刷**——切回来又得重新 page walk，开销巨大。**PCID**（Process Context ID，ARM 上叫 ASID）给 TLB 项打上"属于哪个地址空间"的标签，切换地址空间时**无需全刷**，各进程的 TLB 项可共存：

```
没有 PCID：切进程 → flush 全部 TLB → 切回来全是 miss
有   PCID：每个 TLB 项带 PCID 标签 → 切换只换 CR3，旧项保留，切回来仍命中
```

到 2026 年，PCID 在 x86-64 上是标配并默认启用（尤其 KPTI/Meltdown 缓解开启后，PCID 能极大减少用户态/内核态页表切换的 TLB 损失）。`grep pcid /proc/cpuinfo` 确认硬件支持。这是个对延迟敏感服务很重要、却常被忽视的特性。

### 3.4 大页对 TLB 的意义

一个 TLB 项能覆盖多大内存，取决于页大小：

| 页大小 | 一个 TLB 项覆盖 | 覆盖 1 GB 数据需要的 TLB 项 |
|---|---|---|
| 4 KB | 4 KB | 262144 项（远超 TLB 容量 → 频繁 miss） |
| 2 MB（PMD 大页） | 2 MB | 512 项 |
| 1 GB（PUD 大页） | 1 GB | 1 项 |

**大页让单个 TLB 项覆盖更大范围**，TLB 命中率飙升，page walk 也少一级（PMD 大页省掉 PTE 级）。对大内存、访问局部性差的负载（数据库 buffer pool、JVM 堆、Redis），TLB 收益可能高达百分之几到十几的吞吐提升。这就是 HugePage 和 THP 的根本动机（第六章详述）。

## 第四章 缺页中断

### 4.1 缺页是常态，不是异常

"缺页中断"（page fault）名字唬人，其实是虚拟内存**正常工作的核心机制**——绝大多数缺页是预期的、廉价的。它由 PTE.P==0 或权限不符触发，CPU 把出错地址（CR2）和错误码压栈，进内核 `do_page_fault` / `handle_mm_fault`。

按是否需要磁盘 I/O 分两类：

| 类型 | 含义 | 代价 | 例子 |
|---|---|---|---|
| **minor fault**（次缺页） | 物理页已在内存，只需建立映射 | 微秒级，无 I/O | demand zero、COW、page cache 已有该页 |
| **major fault**（主缺页） | 数据不在内存，需从磁盘/swap 读入 | 毫秒级，有 I/O | 首次访问文件映射、访问被换出的页 |

```bash
$ /usr/bin/time -v ./your_app
    Major (requiring I/O) page faults: 23        # ← 这些是慢的，越少越好
    Minor (reclaiming a frame) page faults: 12456

# 实时观察某进程
$ ps -o min_flt,maj_flt -p <pid>
# 或
$ cat /proc/<pid>/stat   # 第 10、12 字段是 minflt/majflt
```

**性能口诀**：minor fault 多无妨，major fault 多说明在跟磁盘较劲（冷启动、内存不足换页、文件未缓存）。延迟敏感服务要盯紧 major fault。

### 4.2 demand paging：按需分页

回到引言的 malloc 1GB。`malloc` 大块内存时 glibc 调 `mmap` 建立一个**匿名 VMA**，但**不分配任何物理页**——所有 PTE 都是 P=0。直到你写 `p[0]='A'`：

```
1. CPU 访问 p[0] → MMU 发现 PTE.P=0 → #PF
2. do_page_fault → 查 VMA：地址合法、是匿名可写映射 → 合法缺页
3. 分配一个物理页框（首次写匿名页 → 给一个清零页 zero page 的可写副本）
4. 填 PTE：PFN | P=1 | RW=1
5. 返回用户态，重新执行那条写指令 → 这次命中
```

只有被触碰的那 4 KB 才真正"兑现"成物理内存——这就是 VSZ 1GB 而 RSS 1.5MB 的真相。glibc 还有个优化：未写过的匿名页全部映射到同一个**只读零页（zero page）**，读它们零成本，第一次写才触发 COW 分配真页。

### 4.3 COW：写时复制

`fork` 不复制父进程的物理内存，而是把父子的页表项**都标记为只读**，共享同一批物理页。任意一方**写**某页时触发缺页，内核才复制那一页：

```
fork 后：
  父 PTE: PFN=100, RW=0(只读)  ─┐
                                ├─→ 同一物理页 100（共享）
  子 PTE: PFN=100, RW=0(只读)  ─┘

子进程写该页：
  1. 写只读页 → #PF（错误码标明是写保护错误）
  2. do_wp_page：这页被多方共享 → 分配新页 200，复制内容
  3. 子 PTE: PFN=200, RW=1   父 PTE 若变独占也恢复 RW=1
```

COW 让 fork 几乎免费，也是 Redis BGSAVE、PostgreSQL fork worker 等"复制进程"操作快的原因（详见 [L02](./L02-精通-进程与线程模型.md)）。代价：父子之一大量写入时，COW 缺页会成批发生（Redis 持久化期间 RSS 上涨正源于此，见 [redis 内存](../redis/02-精通-Redis-内存与过期.md)）。

### 4.4 do_page_fault 路径

把一次缺页的内核路径串起来（x86-64，函数名随版本微调）：

```
硬件 #PF（出错 VA 在 CR2，错误码在栈）
   ↓
exc_page_fault()                 // arch/x86/mm/fault.c
   ↓
do_user_addr_fault()             // 用户地址；内核地址走另一支
   ↓
find_vma(mm, addr)               // 这地址落在哪个 VMA？
   ├─ 没有 VMA / 越权     → bad_area → SIGSEGV（段错误）
   └─ 合法
       ↓
handle_mm_fault()                // mm/memory.c：分页核心
   ↓
__handle_mm_fault → 逐级走/建页表 → handle_pte_fault()
   ├─ PTE 为空、匿名     → do_anonymous_page（demand zero）
   ├─ PTE 为空、有文件   → do_fault → vma->vm_ops->fault（读文件/page cache）
   ├─ 写只读、需 COW     → do_wp_page
   └─ PTE present 但被换出 → do_swap_page（从 swap 读回，major fault）
       ↓
   建立/更新 PTE → 返回 → CPU 重执行出错指令
```

错误码（page fault error code）的几个关键位帮你判断原因：P（缺页 vs 保护错）、W/R（读还是写）、U/S（用户还是内核）。`dmesg` 里段错误日志的 `error 4`/`error 6` 就是这几位的组合。

## 第五章 mmap

### 5.1 mmap 把文件/匿名内存映射进地址空间

`mmap` 是虚拟内存的"用户接口"，在进程地址空间建立一个 VMA：

```c
void *mmap(void *addr, size_t len, int prot, int flags, int fd, off_t off);
```

两个正交维度：

```
            匿名（fd=-1, MAP_ANONYMOUS）   文件（fd=文件）
MAP_PRIVATE  普通堆/栈内存（malloc 大块）    私有文件映射（改动不回写，COW）
MAP_SHARED   进程间共享内存（无文件）         共享文件映射（改动回写文件，进程间共享）
```

- **匿名映射**：没有后备文件，内容初始为零。`malloc` 大块、线程栈、`MAP_SHARED|MAP_ANONYMOUS` 的进程间共享内存都属此类。
- **文件映射**：以文件为后备。读取触发 major fault 从文件读入 page cache；`MAP_SHARED` 写改动最终回写文件，`MAP_PRIVATE` 写触发 COW、改动只在内存、不回写。

### 5.2 mmap vs read/write

mmap 读文件 vs 传统 `read()`：

| 维度 | read/write | mmap |
|---|---|---|
| 数据路径 | 磁盘 → page cache → **拷贝到用户 buffer** | 磁盘 → page cache → **直接映射进地址空间（零拷贝）** |
| 系统调用开销 | 每次 read 一次 syscall | 映射一次，之后直接访存（缺页除外） |
| 随机访问 | 需 lseek + read | 直接当数组下标访问，天然随机 |
| 小文件大量读 | syscall 开销占比高 | 缺页开销 + 页表开销可能更高 |
| 顺序大文件 | 配合预读很高效 | 也行，但 mmap 的 readahead 不如 read 直观 |
| 写一致性 | write 即进 page cache，fsync 落盘 | 改内存 → msync/munmap 回写（语义更微妙） |
| 出错处理 | read 返回 -1/errno | 访问坏块 → SIGBUS（更难处理） |

经验：**随机访问大文件、需要多进程共享、想省拷贝** → mmap；**顺序流式读写、需要明确的 I/O 控制** → read/write。数据库各有取舍——早期某些库用 mmap 管理数据文件，后来不少回退到自管 buffer pool + pread/pwrite，因为 mmap 的回写时机、SIGBUS 处理、与 page cache 回收的耦合很难精确控制（这也是著名论文 *"Are You Sure You Want to Use MMAP in Your DBMS?"* 的论点）。

### 5.3 一个 mmap 共享内存的例子

```c
#include <sys/mman.h>
#include <string.h>
#include <unistd.h>
#include <stdio.h>

int main(void) {
    size_t sz = 4096;
    // 匿名共享映射：fork 后父子都能看到对方的写
    char *shm = mmap(NULL, sz, PROT_READ | PROT_WRITE,
                     MAP_SHARED | MAP_ANONYMOUS, -1, 0);
    if (shm == MAP_FAILED) { perror("mmap"); return 1; }

    if (fork() == 0) {              // 子进程
        strcpy(shm, "hello from child");
        return 0;
    }
    wait(NULL);
    printf("parent sees: %s\n", shm);   // parent sees: hello from child
    munmap(shm, sz);
    return 0;
}
```

`MAP_SHARED` 让父子映射到**同一批物理页**（不 COW），所以子进程的写父进程立刻可见。把 `MAP_SHARED` 改成 `MAP_PRIVATE`，子进程的写会 COW 出私有副本，父进程看不到。

### 5.4 回写

`MAP_SHARED` 文件映射的脏页何时落盘？

- 内核后台 writeback（flusher 线程）按 `dirty_ratio` 等策略异步回写（见 [L05](./L05-精通-物理内存管理与回收.md) page cache 一章）；
- `msync(addr, len, MS_SYNC)` 强制同步回写；
- `munmap` 时回写脏页。

注意 mmap 写的"持久化点"不如 `write + fsync` 直观——这是用 mmap 做存储引擎的一大坑。

## 第六章 大页

### 6.1 为什么要大页

回顾第三章：4 KB 页下，覆盖大内存需要海量 TLB 项，必然频繁 TLB miss，每次 miss 又是 4~5 次访存。大页把页大小提到 **2 MB（PMD 级）或 1 GB（PUD 级）**，一举：

1. **TLB 覆盖范围暴增**（一项管 2 MB/1 GB），命中率飙升；
2. **page walk 少一级**（2 MB 页在 PMD 就是叶子，省掉 PTE 级）；
3. **页表本身更省内存**（少了大量 PTE 表页）。

Linux 提供两条路：**显式 HugePage（hugetlbfs）** 和 **透明大页（THP）**。

### 6.2 显式 HugePage（hugetlbfs）

需要管理员预留一池大页，应用显式申请。预留与查看：

```bash
# 预留 1024 个 2MB 大页（共 2GB）
$ echo 1024 > /proc/sys/vm/nr_hugepages
$ grep -i huge /proc/meminfo
HugePages_Total:    1024
HugePages_Free:     1024
Hugepagesize:       2048 kB
Hugetlb:         2097152 kB

# 1GB 巨页（需内核启动参数 default_hugepagesz=1G hugepagesz=1G）
$ ls /sys/kernel/mm/hugepages/
hugepages-1048576kB  hugepages-2048kB
```

应用用 `mmap(..., MAP_HUGETLB, ...)` 或挂载 hugetlbfs 申请。优点：**确定性强、无运行时碎片整理、无延迟毛刺**；缺点：需预留（占用内存即使没用满）、应用需改造。数据库、DPDK、KVM 大页内存常走这条路。

### 6.3 THP：透明大页

THP（Transparent HugePage）让内核**自动、透明地**把连续的 4 KB 匿名页"合并"成 2 MB 大页，应用无感。三种模式：

```bash
$ cat /sys/kernel/mm/transparent_hugepage/enabled
always [madvise] never
```

| 模式 | 行为 |
|---|---|
| `always` | 尽可能给所有匿名映射用 THP |
| `madvise` | 仅对显式 `madvise(MADV_HUGEPAGE)` 的区域用 THP（**2026 多数发行版默认**） |
| `never` | 完全关闭 |

THP 的两个来源：分配时直接给大页，或后台 **khugepaged** 线程异步扫描并把小页"塌缩（collapse）"成大页。

### 6.4 THP 的延迟毛刺与数据库为何常关

THP 听起来全是好处，为什么 PostgreSQL、Redis、MongoDB、Oracle 等都建议关掉（至少设 madvise）？根子在 `always` + 同步分配的几个副作用：

1. **直接回收/compaction 阻塞**：分配 2 MB 连续物理页需要内存规整（compaction，见 [L05](./L05-精通-物理内存管理与回收.md)）。内存碎片时，缺页路径上可能**同步**做规整，造成几十毫秒级的延迟毛刺——对 P99 敏感的服务是灾难。
2. **写放大 / 内存浪费**：COW 一个 2 MB 大页比 COW 一个 4 KB 页贵 512 倍。Redis fork 持久化期间，THP 会让 COW 复制以 2 MB 为单位，RSS 暴涨、延迟升高——所以 **Redis 明确要求关闭 THP**（`never`）。
3. **碎片化加剧**：大页拆分/合并增加管理开销。

> **量化对比**：开 `always` THP 的数据库，常见症状是平时吞吐略升，但 P99/P999 延迟出现无规律的毫秒级尖刺，`perf` 能看到 `compaction_alloc` / `khugepaged` 的热点。

`defrag` 子项控制分配时是否同步规整：

```bash
$ cat /sys/kernel/mm/transparent_hugepage/defrag
always defer [defer+madvise] madvise never
# defer+madvise（默认）：不阻塞缺页，后台异步规整——比 always 友好得多
```

**生产建议**：

- **延迟敏感的数据库/缓存（Redis 必须、PG/Mongo 推荐）**：`enabled=never` 或至少 `madvise`，`defrag` 不要 `always`。
- **吞吐型大内存计算（HPC、某些 JVM 大堆）**：可评估 `madvise` + 应用主动 `MADV_HUGEPAGE`，按需吃到 TLB 红利又不全局开。

到 2026 年，主流发行版默认 `enabled=madvise`，正是这个权衡的体现：默认不激进，把"要不要大页"的决定权交给应用。folio 重构也在持续改善大页/小页统一管理的开销。

```bash
# 查某进程吃了多少 THP
$ grep -i AnonHugePages /proc/<pid>/smaps_rollup
AnonHugePages:    524288 kB
# 系统级
$ grep AnonHugePages /proc/meminfo
```

## 生产实践

1. **冷启动慢？看 major fault**。服务刚起跑得慢、跑热后变快，多半是首次访问触发 major fault 把代码/数据从磁盘读进 page cache。可在部署后用 `vmtouch` 或主动顺序读把热文件预热进 page cache，把 major fault 提前到不计入 SLA 的预热阶段。

2. **VSZ 大不等于内存泄漏**。监控告警别盯 VSZ，盯 RSS（更准的是 PSS，见 [L06](./L06-精通-OOM-与内存诊断.md)）。Go/Java runtime 预留大块虚拟地址是常态。

3. **Redis/PG 部署清单第一条：关 THP**。Redis 不关 THP 会在 BGSAVE 期间触发大量 2 MB 粒度 COW，延迟飙升。systemd 服务可加 `ExecStartPre` 写 `never`，或在节点 tuned profile 里统一关。

4. **大堆服务考虑 PCID + 显式大页**。延迟敏感、大内存、随机访问的服务（数据库 buffer pool、L4 LB），确认 PCID 已启用，并评估 hugetlbfs 显式大页换取 TLB 收益。

5. **频繁 mmap/munmap 是反模式**。每次 munmap 触发 TLB shootdown（跨核 IPI）。用内存池/arena 复用映射，别把 mmap 当 malloc 频繁调。

6. **诊断 TLB 瓶颈用 perf**。`perf stat -e dTLB-load-misses,iTLB-load-misses` 看占比；若 dTLB miss 率高且是大内存随机访问负载，大页可能立竿见影。

## 陷阱清单

1. **现象**：`top` 显示进程 VSZ 50 GB，运维以为要 OOM 紧急扩容。
   **原因**：VSZ 是虚拟地址空间大小，包含未兑现的匿名映射、保留区、动态库映射，与真实物理占用无关。
   **修法**：看 RSS/PSS（`/proc/[pid]/smaps_rollup`），监控告警基于 RSS 或 cgroup `memory.current`，而非 VSZ。

2. **现象**：服务 P99 延迟无规律出现 20~80 ms 毛刺，CPU/IO 都不高。
   **原因**：`THP=always` 在缺页路径上同步做 compaction 凑 2 MB 连续页，阻塞了请求线程。
   **修法**：`enabled` 设 `madvise` 或 `never`，`defrag` 避免 `always`（用 `defer+madvise`）；用 `perf record` 确认 `compaction_alloc` 热点。

3. **现象**：Redis 持久化（BGSAVE）期间 RSS 翻倍、客户端延迟飙升。
   **原因**：fork 后写入触发 COW，开了 THP 时 COW 以 2 MB 为单位，放大 512 倍。
   **修法**：`echo never > /sys/kernel/mm/transparent_hugepage/enabled`；这是 Redis 官方启动告警明确要求的。

4. **现象**：多线程程序在大量 `munmap`/`mprotect` 后整体卡顿，核越多越明显。
   **原因**：每次改页表都触发 TLB shootdown，向所有相关核发 IPI 并同步等待，核多则风暴。
   **修法**：减少映射改动频率（内存池复用）、绑核降低共享、用大页减少需刷新的项；`grep TLB /proc/interrupts` 观察 shootdown 计数。

5. **现象**：mmap 一个文件后程序偶发 SIGBUS 崩溃。
   **原因**：访问的页对应的文件区域不存在（文件被截断）或磁盘坏块——文件映射访问错误以 SIGBUS 而非返回值报告。
   **修法**：映射前确保文件大小覆盖映射范围；对可能截断的文件用 `read/pread` 或安装 SIGBUS handler；别把 mmap 当万能 I/O。

6. **现象**：预留了 `nr_hugepages` 大页但应用申请失败，或内存"凭空少了一截"。
   **原因**：hugetlbfs 大页是**预留即占用**，即使没被应用使用也从可用内存中扣除；且大页一旦碎片化后很难再凑出，运行中调大 `nr_hugepages` 常失败。
   **修法**：启动早期（内存未碎片化时）预留；用 `hugepages-...kB` 节点核对 Free/Total；按实际用量预留，避免过度预留挤占普通内存。

7. **现象**：关掉 ASLR 后程序"更稳定"，于是想在生产保留。
   **原因**：关 ASLR 移除了关键的内存防护，地址可预测使 ROP/缓冲区溢出攻击大幅容易。
   **修法**：ASLR 仅在调试时临时关（`setarch -R`），生产 `randomize_va_space=2`，并以 PIE 编译关键服务。

## 2026 现状

- **5 级页表已普及但按需启用**：主流服务器 CPU 与发行版内核支持 LA57（57 位/128 PB 虚拟空间），但仅当地址超出 47 位时才用第 5 级，避免无谓访存。绝大多数应用无感。
- **PCID 标配**：x86-64 上 PCID 默认启用，配合 KPTI 缓解大幅降低进程/态切换的 TLB 损失；新硬件还出现了 **LAM**（Linear Address Masking，让指针高位放 tag 不触发翻译错误）等扩展。
- **THP 默认 madvise**：主流发行版默认 `enabled=madvise`、`defrag=defer+madvise`，把激进大页交给应用决定——正是多年延迟毛刺教训的沉淀。
- **folio 重构持续推进**：内核内存管理正从"以 4K struct page 为中心"迁移到 **folio**（一组连续页的抽象），统一大页/小页处理、减少管理开销，对上层透明，但让大页相关代码路径更高效。
- **maple tree 管理 VMA**：6.1 起 VMA 不再用红黑树而用 maple tree，降低 mmap 锁竞争、提升地址空间操作的扩展性。

参见 [L05 物理内存管理与回收](./L05-精通-物理内存管理与回收.md)（页框从哪来、怎么回收）、[L06 OOM 与内存诊断](./L06-精通-OOM-与内存诊断.md)（RSS/PSS、内存度量与排障），以及跨专题 [cloud-native C06 资源管理](../cloud-native/C06-精通-Scheduling-与资源管理.md)、[golang G22 pprof](../golang/G22-精通-Go-pprof-性能剖析.md)。

## 练习题

1. 写一段程序 malloc 2 GB 但只每隔 1 MB 写一个字节，预测并实测它的 RSS 大约是多少？为什么不是 2 GB 也不是几 KB？（提示：每次写触碰一个 4 KB 页）
