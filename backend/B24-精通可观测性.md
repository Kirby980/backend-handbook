## 引言：监控 vs 可观测

```
监控（monitoring）：你知道**该看什么**，搭仪表盘看
可观测（observability）：系统行为**可被探测**——能回答你没预设的问题
```

监控告诉你"CPU 80%"；可观测让你能查"为什么这 100 个用户慢，他们有什么共同点"。后端工程师不仅要让代码工作，要让它**可解释**。本章拆开三柱、OTel、SLI/SLO、告警最佳实践。

## 第一章：三柱

### 1.1 Logs（日志）

- 事件流：发生了什么
- 结构化 JSON（参考 G30）
- 适合：debug、审计、合规
- 代价：存储 + 检索

### 1.2 Metrics（指标）

- 聚合数值：QPS、延迟、错误率、CPU
- 时序数据库存储（Prometheus、InfluxDB）
- 适合：dashboard、告警、容量规划
- 代价：低（聚合数据）

### 1.3 Traces（追踪）

- 一个请求跨多服务的完整路径
- span 树状结构 + 时间戳
- 适合：分布式系统排障、性能定位
- 代价：高（每请求大量数据，常采样）

### 1.4 三者关系

- **traceID**：贯穿三柱
- log 含 traceID → 从 trace 跳到日志
- metric label 含错误码 → 找到错误 trace
- 这是 OTel 的核心理念：统一关联

## 第二章：Metrics

### 2.1 四种类型

**Counter**：单调递增（请求数、错误数）
```
http_requests_total{method="GET", status="200"} 12345
```

**Gauge**：可增可减（当前并发、内存使用）
```
goroutines_count 24
memory_bytes 134217728
```

**Histogram**：分布（延迟分桶）
```
http_duration_bucket{le="0.1"} 1000
http_duration_bucket{le="0.5"} 1200
http_duration_bucket{le="1.0"} 1250
http_duration_bucket{le="+Inf"} 1260
http_duration_sum 145.2
http_duration_count 1260
```

**Summary**：客户端算分位数（已被 Histogram 大部分取代）

### 2.2 RED 方法

服务监控的 "RED":
- **Rate**：每秒请求数
- **Errors**：错误率
- **Duration**：延迟分布

每个 endpoint 三个指标 → 大多问题能 cover。

### 2.3 USE 方法

资源监控的 "USE":
- **Utilization**：使用率
- **Saturation**：饱和度（队列、等待）
- **Errors**：错误

CPU、内存、磁盘、网络都按这套。

### 2.4 四个黄金信号（Google SRE）

- Latency
- Traffic
- Errors
- Saturation

每个服务都该有这四个 dashboard。

### 2.5 PromQL 例子

```promql
# QPS
rate(http_requests_total[5m])

# error rate
rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m])

# p99 latency
histogram_quantile(0.99, sum(rate(http_duration_bucket[5m])) by (le))

# 多维度切
sum by (endpoint) (rate(http_requests_total[5m]))
```

### 2.6 cardinality 陷阱

```
http_requests_total{user_id="42"}   ← N 用户 = N 个序列
```

每个 label 组合是一个独立时序——百万级 cardinality 把 Prometheus 撑爆。

**绝不**把 user_id、IP、URL（含参数）当 label。label 值应是低基数（method、status、endpoint 名）。

### 2.7 Native Histograms（Prometheus 3.0+）

经典直方图（classic histogram）要预先定义 bucket 边界，每个 bucket 是一条独立时序，cardinality 高且无法跨服务聚合（bucket 边界必须完全一致）。

**Prometheus 3.0** (2024-11) 把 **native histograms** 推到 GA：

- **指数增长 bucket，无需手动定义**——一个时序就能精确表达完整分布
- bucket 数随数据自适应；存储/传输都比 classic histogram 省一个量级
- 任意百分位计算更准（不再受边界影响）
- 可跨服务聚合（边界不再需要约定）
- Go SDK：`prometheus_client_golang` v1.18+ 支持
- 启用：`--enable-feature=native-histograms`（仍标记为 experimental，但生产已可用）

**Prometheus 3.0 其他亮点**：

- **UTF-8 默认开启**——metric / label name 可含 `.`、中文等非 ASCII 字符；OpenTelemetry metrics 不再需要转 underscore
- **OTLP 接收**：原生接收 OpenTelemetry metrics（`/api/v1/otlp/v1/metrics`），不再要 OTel Collector 中转
- **Remote Write 2.0**：用 string interning，CPU/内存/带宽各降 60-90%
- **Agent 模式 GA**：纯抓取转发，不存盘
- 全新 Web UI（PromLens 风格 tree view、metrics explorer）

> 参考：[Prometheus 3.0 release blog](https://prometheus.io/blog/2024/11/14/prometheus-3-0/)。

## 第三章：Logs

### 3.1 级别

```
DEBUG → INFO → WARN → ERROR → FATAL
```

生产通常 INFO 起；DEBUG 在故障时按需开。

### 3.2 结构化

JSON，含必要字段：
```json
{
  "time": "2026-05-12T10:30:00Z",
  "level": "ERROR",
  "msg": "db query failed",
  "service": "user",
  "trace_id": "abc123",
  "user_id": 42,
  "query_type": "user_lookup",
  "error": "connection refused",
  "duration_ms": 5023
}
```

### 3.3 聚合栈

- **ELK**：Elasticsearch + Logstash + Kibana
- **Loki**：Grafana 的"轻量 ES"
- **Datadog / Splunk / New Relic**：商业全家桶
- **CloudWatch Logs**（AWS）/ **Cloud Logging**（GCP）

### 3.4 采样

INFO 日志可采样（如 1%）减成本。**ERROR 永不采样**。

详见 G30。

### 3.5 不该 log

- 密码、token、session ID
- 完整信用卡号
- 个人身份信息（PII）依合规
- 大 payload（限制长度）

## 第四章：Distributed Tracing

### 4.1 概念

```
request → service A → service B → DB
                    → service C → external API
```

trace = 整个请求的树；每个 box 是 span。

### 4.2 span 字段

```json
{
  "trace_id": "abc",
  "span_id": "1",
  "parent_span_id": null,
  "name": "GET /api/users/42",
  "service": "api-gateway",
  "start_time": "...",
  "duration_ms": 250,
  "attributes": { "user_id": "42", "http.status": 200 },
  "events": [ ... ],
  "status": "OK"
}
```

子 span 的 `parent_span_id` 指向父。组装成 tree。

### 4.3 传播

通过 HTTP header / gRPC metadata 把 trace context 传给下游：

```
traceparent: 00-abc123-span1-01
```

W3C Trace Context 标准。

### 4.4 采样

每请求生成 trace 数据量大。常见策略：

- **head-based**：入口决定（如 1% 请求 trace）
- **tail-based**：执行完后决定（如所有错的、慢的 trace）

OpenTelemetry Collector 支持 tail sampling。

### 4.5 后端

- **Jaeger**：CNCF，开源
- **Tempo**：Grafana 出，配 Loki 友好
- **Zipkin**：早期开源
- **Datadog APM**、**New Relic**：商业
- **AWS X-Ray**、**GCP Cloud Trace**

## 第五章：OpenTelemetry

### 5.1 一个 API 全部三柱

```
应用代码 → OTel SDK → OTLP 协议 → OTel Collector → 各后端
```

不绑特定 vendor——换 Jaeger / Tempo / Datadog 后端而无需改代码。

### 5.2 三种 instrumentation

**A. 自动**
```bash
# Java
java -javaagent:otel-agent.jar -jar app.jar
# Python
opentelemetry-instrument python app.py
```
自动监控常用库（HTTP server / client、DB driver、Kafka）。

**B. 库提供**
```go
import "go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp"

handler := otelhttp.NewHandler(myHandler, "my-route")
```

**C. 手动**
```go
ctx, span := tracer.Start(ctx, "compute")
defer span.End()
// ...
span.SetAttributes(attribute.Int("result", x))
```

### 5.3 Collector

中间层：从应用收数据 → 处理（filter、sample、enrich）→ 转发到后端。

```yaml
receivers: { otlp: { protocols: { grpc: {} } } }
processors: { batch: {}, attributes: { actions: [...] } }
exporters: { jaeger: {...}, prometheus: {...}, loki: {...} }
```

应用只发到 collector，不用知道后端是什么。

### 5.5 OpenTelemetry 是 2026 的事实标准

不只是"又一个 SDK"——OTel 已经是 logs / metrics / traces 三大支柱**协议层**的统一标准：

- **CNCF Graduated 项目**（2024-09 毕业），与 K8s、Prometheus、Envoy 同级
- **Traces SDK**：v1.0（2021-02 起稳定）
- **Metrics SDK**：v1.0（2023-02 起稳定）
- **Logs SDK**：v1.0（2024 年内稳定，2025 全语言对齐）
- **OTLP 协议**：所有主流后端（Tempo、Jaeger v2、Honeycomb、Datadog、New Relic、Grafana Cloud、Splunk、Elastic）原生接收
- **Prometheus 3.0** 直接接收 OTLP metrics（见 §2.7）
- **Jaeger v2** 整个换成 OTel Collector 内核

实际选型建议（2026）：

| 需求 | 选 |
|---|---|
| 全新项目埋点 | **直接用 OpenTelemetry SDK + OTel Collector**——别再单独引 Jaeger client、Prometheus client |
| 现有 Jaeger / Zipkin client | 用 OTel Collector 接收旧协议，统一往后端转 OTLP |
| 数据存储 | Traces → Tempo / Jaeger v2；Metrics → Prometheus 3 / Mimir / VictoriaMetrics；Logs → Loki / OpenSearch |
| 自托管全套 | Grafana stack：Grafana + Loki + Tempo + Mimir + Prometheus + Alloy（OTel Collector distro） |
| eBPF 自动埋点 | Pixie（K8s）、Beyla（HTTP/gRPC 自动 trace） |

> 参考：[OpenTelemetry 官网](https://opentelemetry.io/)、[OTel CNCF graduation](https://www.cncf.io/announcements/2024/09/24/opentelemetry-becomes-the-second-largest-cncf-project/)。

## 第六章：SLI / SLO / SLA

### 6.1 定义

- **SLI**（Service Level Indicator）：度量值——如"成功 request 比例"
- **SLO**（Objective）：目标——如"99.9% 成功"
- **SLA**（Agreement）：合同——违反赔钱

### 6.2 错误预算

99.9% 一个月允许失败：
```
30 天 × 24 × 60 = 43200 分钟
0.1% = 43.2 分钟
```

可以"花掉"这 43 分钟——快速发版、激进迁移。用完了暂停 feature 工作专注稳定。

### 6.3 选 SLI

好的 SLI：
- 直接反映用户体验
- 客户端可见
- 用错误率 + 延迟二者，不是 CPU

例：
```
- 99% 请求 < 500ms
- 99.9% 请求成功 (status < 500)
- 95% 写后立刻可读
```

### 6.4 不要追求 100%

100% SLO 不现实 + 浪费——99.9% 已经很好。允许小故障让团队有时间改进。

## 第七章：告警

### 7.1 What to alert on

- SLO 即将违反（错误预算燃烧率高）
- 关键 metric 异常（数据库挂、关键 dependency down）
- 关键路径错误率突增
- 容量预警（磁盘 80%）

### 7.2 不该 alert

- CPU 高（除非配合用户影响）
- 单实例事件（K8s 自愈）
- 内部 retry / circuit breaker 触发（这是设计的）
- 噪音 metric

每个告警都该是"有人必须立刻看"的级别。

### 7.3 告警疲劳

告警太多 → 都忽视。SRE 经验：

- 每班最多 1-2 个告警
- 不可处理的告警删
- 告警必有 runbook（怎么处理）

### 7.4 多级

- **P0 / page**：立即响应（电话 / 短信）
- **P1 / ticket**：工作时间响应
- **P2 / log**：仅记录，事后看

## 第八章：Dashboard

### 8.1 设计原则

- **能讲故事**：从上到下 = 由问题到细节
- **少而精**：5-10 个 panel，太多看不过来
- **一目了然**：阈值线、颜色编码

### 8.2 黄金 dashboard

每个服务都该有：

1. RED 三件套（rate、errors、duration）
2. 资源利用（CPU、内存）
3. 依赖健康（DB、cache、下游）
4. 业务关键 metric（用户、订单、营收）

### 8.3 Grafana

事实标准。数据源：Prometheus、Loki、Tempo、ES 等。

```
变量化 dashboard：选 service / env → 全 dashboard 切换
```

## 第九章：故障排查工作流

### 9.1 4 步法

1. **现象**：什么有问题？（用户 / 监控）
2. **影响范围**：哪些用户 / 服务受影响
3. **假设**：可能原因
4. **验证**：metric / log / trace 数据支持哪个

### 9.2 工具流

```
告警 → dashboard 看大盘
   → traces 找具体慢请求
   → logs 看错误细节
   → 修复或回滚
```

### 9.3 事后

- **postmortem**：blameless（不怪人，怪系统）
- 5 whys 找根因
- 改进 action items 实施
- 累积 wisdom

## 第十章：成本管理

### 10.1 可观测性数据爆炸

100 服务 × 100 metric × 100 维度 = 1 百万 series → 几 TB / 月。

### 10.2 减成本

- metric：降 cardinality（去掉 user_id label）
- log：采样 + retention（30 天热 + 1 年冷）
- trace：tail sampling（仅错 / 慢）
- 选合适存储层级（hot / warm / cold）

### 10.3 平衡

可观测性是保险——太省可能事故时摸不着头脑。但全 retention 烧钱。**每月审视成本 + 价值**。

## 第十一章：生产级最佳实践

1. **OTel 从 day 1**：避免后期改造。
2. **traceID 贯穿三柱**：log、metric、trace 关联。
3. **RED + USE + 四黄金信号** dashboard。
4. **SLO + 错误预算**：数据驱动决策。
5. **告警精简**：可处理才报警。
6. **runbook 每个告警**：处理步骤清晰。
7. **postmortem 文化**：blameless + 学到东西。
8. **chaos engineering**：验证可观测性是否捕获故障。
9. **成本 monthly review**：不要烧钱在没看的 metric。
10. **演练事件响应**：定期来一次。

## 第十二章：常见陷阱清单

### ❌ 陷阱 1：高 cardinality label
metric 系列爆。

### ❌ 陷阱 2：log everything DEBUG
存储成本 + 关键日志被淹。

### ❌ 陷阱 3：告警每分钟来一个
忽视。

### ❌ 陷阱 4：trace 全采样
TB 级数据。1-5% + tail 错的全采。

### ❌ 陷阱 5：dashboard 几十个 panel
信息超载。

### ❌ 陷阱 6：log 含 PII / secret
合规风险。

### ❌ 陷阱 7：SLO 100%
不可能 + 团队疲于救火。

## 参考答案

**练习 1**：
```go
import (
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp"
    sdktrace "go.opentelemetry.io/otel/sdk/trace"
    "go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc"
)

func setup() {
    exp, _ := otlptracegrpc.New(ctx)
    tp := sdktrace.NewTracerProvider(
        sdktrace.WithBatcher(exp),
        sdktrace.WithSampler(sdktrace.TraceIDRatioBased(0.01)),
    )
    otel.SetTracerProvider(tp)
}

// server
handler := otelhttp.NewHandler(myMux, "api")
http.ListenAndServe(":8080", handler)

// client
client := http.Client{Transport: otelhttp.NewTransport(http.DefaultTransport)}
req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
client.Do(req)   // trace context 自动注入 header
```

**练习 2**：每 label 值组合 = 一个独立时序。`{user_id="42"}, {user_id="43"}, ...` 1 百万用户 = 1 百万系列 → 内存爆炸、查询慢、磁盘满。label 值应来自小集合（method、status、enum）。

**练习 3**：30 天 = 43200 分钟。0.1% = 43.2 分钟。可分若干小故障或一次较大故障。

**练习 4**：
1. **现象**：哪个 endpoint 慢？看 dashboard p99 → 找突变点
2. **范围**：所有用户还是少数？某地区？某 client 版本？
3. **假设**：可能 DB 慢 / 下游服务慢 / GC 抖 / 流量飙升
4. **验证**：
   - DB metric：QPS / latency
   - 下游 service health
   - trace 看具体慢请求各段耗时
   - GC log + heap
   - 输入流量曲线

trace 是关键：找到慢请求 trace ID → 直接看哪一段。

**练习 5**：head sampling 入口随机决定 → 大多"正常"trace 被采，错误 / 慢的也按随机比例被丢。tail sampling 等执行完根据特征采（错的、慢的、含特定属性的）→ 信号量大；问题相关 trace 几乎 100% 保留。
