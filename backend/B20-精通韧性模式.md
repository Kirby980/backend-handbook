## 引言：分布式系统永远在出错

```
99.9% 单服务可用 × 调 10 个服务 = 99% 整体
99.9% × 100 = 90%
```

每多一个依赖，整体可用性下降。**期望失败、设计韧性**是分布式系统的核心思维。本章拆开熔断、重试、超时、Bulkhead、降级、隔离这套韧性工具箱。

## 第一章：超时（Timeout）

### 1.1 最基础也最被忽视

```python
# 反例
requests.get(url)   # 默认无超时 → 可能挂几小时
```

每次外部调用必须有超时。

### 1.2 三类 timeout

- **Connect timeout**：建 TCP 连接
- **Read timeout**：读取响应字节
- **Total timeout**：整个 request 上限（推荐主要用这个）

### 1.3 设值

| 层 | 经验值 |
|---|---|
| Cache read | 100-500 ms |
| DB query | 1-3 s |
| 内部 service | 1-5 s |
| External API | 10-30 s |
| 上层 API（user-facing）| 30 s |

每层应**小于其调用方**——给上层留 retry 余地。

### 1.4 配 context

```go
ctx, cancel := context.WithTimeout(parentCtx, 5*time.Second)
defer cancel()
db.QueryContext(ctx, ...)
```

context 传播 timeout——下游也知道剩多少时间。

### 1.5 没设 timeout 的后果

- goroutine / 线程泄漏
- 连接池耗尽
- 上游也跟着卡（雪崩）

## 第二章：重试（Retry）

### 2.1 何时该 retry

- **临时性失败**：网络抖、5xx、连接 reset、超时
- **幂等操作**：GET / PUT / DELETE / 带 idempotency-key 的 POST
- **底层 retry**：HTTP client / gRPC framework 内部 retry 比应用层更高效

### 2.2 不该 retry

- **业务失败**：400、401、403、404、422
- **非幂等且没去重**：POST 创建可能重复
- **服务已熔断状态**：retry 无用还压垮

### 2.3 指数退避 + 抖动

```python
def retry(fn, attempts=4, base=0.1, cap=10):
    for i in range(attempts):
        try:
            return fn()
        except Retriable:
            if i == attempts - 1: raise
            wait = min(cap, base * (2 ** i)) * (0.5 + random.random())
            time.sleep(wait)
```

- **指数**：失败越多等越久
- **抖动**：防"thundering herd"——同时大量 client 重试

### 2.4 Retry budget

防止 retry 风暴：

```
正常请求 1 + 重试 0.1 = 1.1
失败率高时 retry 自动减少
```

Envoy、gRPC retry budget 内置。

### 2.5 复合 retry 灾难

```
client retry × LB retry × service retry × DB retry = 几何级别放大
```

只在一层 retry！通常在最外层（client）+ 临时性失败位置。

## 第三章：Circuit Breaker（熔断器）

### 3.1 状态机

```
       Closed (正常)
          ↓ 失败率 > 阈值
        Open (拒绝所有请求)
          ↓ 经过冷却时间
       Half-Open (允许少量探测)
          ↓ 成功 → Closed
          ↓ 失败 → Open
```

### 3.2 实现

```go
import "github.com/sony/gobreaker"

cb := gobreaker.NewCircuitBreaker(gobreaker.Settings{
    Name:        "user-service",
    MaxRequests: 5,                              // half-open 探测数
    Interval:    60 * time.Second,
    Timeout:     30 * time.Second,                // open 持续时间
    ReadyToTrip: func(counts gobreaker.Counts) bool {
        return counts.ConsecutiveFailures > 5
    },
})

result, err := cb.Execute(func() (any, error) {
    return userClient.Get(id)
})
```

### 3.3 优点

- 减少对挂掉服务的进一步压力（让它恢复）
- 立即失败比慢失败好（保护上游资源）
- 半开探测自动恢复

### 3.4 与 retry 配合

```python
try:
    cb.execute(lambda: retry(fn))
except CircuitOpen:
    return fallback()
```

retry 处理偶发；breaker 处理持续故障。

### 3.5 实现库

- Go：`sony/gobreaker`、`afex/hystrix-go`
- Java：Resilience4j（Hystrix 已停止）
- Node：opossum
- Python：pybreaker
- Service mesh：Envoy outlier detection（无需应用代码）

## 第四章：Bulkhead（隔离）

### 4.1 概念

船舱隔离——一舱进水不影响其他舱。系统层面把资源分组，故障局部化。

### 4.2 线程池隔离

```python
user_pool = ThreadPoolExecutor(max_workers=20)
order_pool = ThreadPoolExecutor(max_workers=20)

# 慢的 order 服务不会占用 user 服务的线程
```

### 4.3 连接池隔离

```python
db_pool_a = ...  # 给写
db_pool_b = ...  # 给读 / 报表
```

报表慢查询不会占用主业务连接。

### 4.4 K8s 资源隔离

```yaml
resources:
  limits: { cpu: 1000m, memory: 1Gi }
  requests: { cpu: 500m, memory: 512Mi }
```

每 pod 资源上限——单 pod 不影响节点上其他。

### 4.5 网络隔离

Service Mesh 限制服务间流量上限：
- 一个 service 不能耗尽集群带宽
- 故障域可控

## 第五章：降级（Graceful Degradation）

### 5.1 概念

部分功能失败时，**保留核心、降级非核心**，而不是整页 500。

### 5.2 典型场景

- 推荐服务挂 → 返回"热门" fallback
- 个性化失败 → 返回默认页
- 搜索后端慢 → 关键词高亮不再
- 评论加载失败 → 评论区显示"暂时不可用"，文章主体仍显示

### 5.3 实现

```python
def get_homepage(user_id):
    try:
        recs = recommendation_service.get(user_id, timeout=1)
    except (Timeout, CircuitOpen):
        recs = trending_service.get()   # fallback
    
    return render(user, recs)
```

### 5.4 feature flag 配合

```python
if feature.is_enabled("recommendations"):
    try: recs = rec_service.get()
    except: recs = []
```

故障时人工 / 自动关闭 feature。

## 第六章：背压（Backpressure）

详见 B21。这里先点睛：

下游处理不过来时，**让上游慢下来**而非堆积。
- 队列满了 → block 或 drop
- 限流 → 拒绝过量请求
- 流式系统 → 暂停上游

## 第七章：Idempotency 与重试安全

### 7.1 重试的前提

只有**幂等**操作能安全重试。否则重复扣款 / 重复发邮件。

### 7.2 实现幂等

**A. Idempotency key**：
```
POST /payments
Idempotency-Key: uuid
```
server 记 key 24h；重复 key → 返回上次结果。

**B. 业务唯一约束**：
```sql
INSERT INTO orders (request_id, ...) VALUES (?, ...)
ON CONFLICT (request_id) DO NOTHING;
```

**C. 状态机**：
```
order.status: pending → paid → shipped
重复 "mark paid" → 已 paid 不变
```

## 第八章：超时分配（Hierarchical Timeout）

### 8.1 总 budget

用户请求总 30 秒。这 30 秒在下游怎么分？

```
API gateway:           30s
  → service A          20s (留 10s 给其他)
    → service B        5s
    → service C        5s
  → service D          5s
  → service E          5s
```

每层 timeout 应小于父——给父留处理时间。

### 8.2 deadline 传播

gRPC、context.Context 跨服务带 deadline。下游知道：

```go
// service A 收到 context.Deadline() = "10:30:25"
// 调用 service B 之前
ctx, cancel := context.WithDeadline(ctx, time.Now().Add(remaining))
```

不浪费 budget。

### 8.3 抢救式 retry

如果 budget 还有 5 秒，但某次调用 2 秒失败 → retry 一次（3 秒）OK。
如果只剩 1 秒 → 不要 retry。

```python
remaining = ctx.deadline - now
if attempts < max and remaining > min_for_retry:
    retry()
```

## 第九章：监控与可观测

### 9.1 关键 metric

- **request rate**：QPS
- **error rate**：错误百分比
- **latency**：p50 / p95 / p99
- **circuit breaker state**
- **retry count**
- **timeout count**

### 9.2 SLO

Service Level Objective："99% 请求 < 500ms"。基于错误预算（error budget）规划开发节奏：
- 错误预算用完 → 暂停 feature 工作，先 fix
- 错误预算充足 → 可以激进发布

### 9.3 chaos engineering

定期注入故障：
- 杀 pod
- 注入延迟
- 断网
- DB 慢

验证 retry / fallback / circuit breaker 真的工作。Netflix Chaos Monkey、Gremlin、LitmusChaos 等工具。

## 第十章：生产级最佳实践

1. **每个外部调用 timeout + retry + circuit breaker**：三件套。
2. **timeout 分级**：父 > 子。
3. **retry 仅幂等 + 退避抖动**。
4. **service mesh（Istio / Linkerd）**：免应用代码自动处理。
5. **Bulkhead 隔离慢/快路径**：互不影响。
6. **降级 fallback**：核心功能可独立。
7. **chaos engineering**：故障下能跑才算韧性。
8. **观测 SLO + error budget**：数据驱动。
9. **不要复合 retry**：选一层。
10. **idempotency key 在公开 API**：让 client 安全 retry。

## 第十一章：常见陷阱清单

### ❌ 陷阱 1：无 timeout
client 默认 ∞。

### ❌ 陷阱 2：retry 风暴
多层 retry 把 1 个请求放大到 8 个 → 雪上加霜。

### ❌ 陷阱 3：retry 非幂等
重复扣款、重复邮件。

### ❌ 陷阱 4：retry 同步阻塞
重试期间占用资源。改 async。

### ❌ 陷阱 5：breaker 永远 open
半开探测条件错误。

### ❌ 陷阱 6：fallback 路径无测试
"应该有 fallback"——出事才发现 fallback 自己也挂。

### ❌ 陷阱 7：没演练
看 PPT 学了模式 → 真实故障来时还是慌。

## 参考答案

**练习 1**：
```python
import random, time, functools
def resilient(timeout=5, attempts=3, base=0.1, retriable=(Timeout, ConnError)):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kw):
            for i in range(attempts):
                try:
                    return fn(*args, timeout=timeout, **kw)
                except retriable as e:
                    if i == attempts - 1: raise
                    wait = base * (2 ** i) * (0.5 + random.random())
                    time.sleep(wait)
        return wrapper
    return deco
```

**练习 2**：B、C、D 串行 → 时间叠加。预算：
- 每个 3s 留 1s buffer
- 或按重要性分配（关键的多给）

如果可以**并行**：每个独自 8s，整体 8s（最慢决定）。

**练习 3**：
- **retry**：偶发故障（网络抖、瞬时 5xx）—— 短期波动
- **circuit breaker**：持续故障（服务挂、依赖宕）—— 长期问题；retry 此时无效还有害

两者互补：retry 在 breaker closed 时生效；breaker open 时直接失败。

**练习 4**：
- 顶部搜索框降级为静态 placeholder "搜索暂时不可用"
- 主页推荐用 fallback（编辑精选 / trending）
- 文章列表用 cache 数据
- 用户行为还能正常（不依赖搜索）

不要整页 500。

**练习 5**：
- **杀 pod**：测试 K8s 自愈
- **CPU / memory 限制**：测试资源约束
- **网络延迟**：注入 latency 模拟跨 DC
- **网络丢包 / 分区**
- **DNS 解析失败**
- **磁盘满**
- **时钟漂移**（NTP）

工具：Chaos Mesh、LitmusChaos。

## 小结

| 模式 | 解决 |
|---|---|
| Timeout | 不卡死等 |
| Retry | 临时故障 |
| Circuit breaker | 持续故障保护 |
| Bulkhead | 故障隔离 |
| 降级 | 部分可用比全挂好 |
| Backpressure | 下游限速反向 |
| Idempotency | retry 安全 |
| Chaos | 验证韧性 |
