## 引言：解耦的力量

```
service A → API call → service B → API call → service C
```

同步链路 = 任一服务慢，全链路慢；任一服务挂，全链路挂。改成：

```
service A → publish event → message broker → service B, C, D 各自异步消费
```

发布即返回；下游各自处理；A 不知道也不关心谁消费。这就是消息队列的核心价值。本章拆开 Kafka、RabbitMQ、NATS、SQS 的差异，讲清何时用哪个。

---

## 第一章：消息中间件解决什么

### 1.1 五大场景

1. **异步化**：写完即返回，不等下游处理
2. **解耦**：生产者不依赖具体消费者
3. **削峰**：突发流量进队列，下游按自己节奏消费
4. **可靠传递**：消费失败可重试
5. **广播**：一个事件 N 个下游同时收

### 1.2 不适合的场景

- 实时双向通信（RPC、WebSocket）
- 需要保证立即看到结果的同步操作
- 强一致跨服务事务（用 Saga 但理解最终一致）

## 第二章：核心概念

### 2.1 Topic / Queue

- **Topic**：发布订阅模式的"频道"（Kafka、NATS、SNS）
- **Queue**：点对点（RabbitMQ、SQS）

很多系统同时支持两种语义。

### 2.2 Producer / Consumer

- producer 发布消息
- consumer 订阅 / 拉取处理

### 2.3 Partition

把一个 topic 切成多个 partition：
- 并行消费（每 partition 一个 consumer）
- 顺序仅在 partition 内保证

Kafka 核心概念。RabbitMQ 用 queue + sharding 模拟。

### 2.4 Consumer Group

多 consumer 共享 group → 一条消息只分给组内一个 consumer。配合 partition 实现"水平扩展"。

### 2.5 Offset

每 consumer 在 partition 中的位置。commit offset 后下次从该位置开始。

## 第三章：交付语义

### 3.1 三种保证

- **At-most-once**：可能丢失，不会重复
- **At-least-once**：不会丢失，可能重复
- **Exactly-once**：不丢不重（昂贵）

### 3.2 真实情况

- "exactly-once" 跨系统几乎不可能（端到端）；只在特定 broker 内可行（Kafka 事务）
- **默认期待 at-least-once + 消费端幂等**

### 3.3 实现幂等消费

```python
def handle(msg):
    if cache.exists(f"processed:{msg.id}"):
        return   # 已处理
    process(msg)
    cache.set(f"processed:{msg.id}", "1", ttl=86400)
    ack(msg)
```

或基于 DB 唯一约束：

```sql
INSERT INTO processed_events (id) VALUES (?)
ON CONFLICT DO NOTHING;
-- 若 affected_rows == 0，已处理
```

## 第四章：Apache Kafka

### 4.1 核心模型

- broker 集群
- topic 分多 partition
- 每 partition 是不可变追加日志（log）
- consumer 按 offset 读

### 4.2 特性

- **超高吞吐**：百万消息/秒/集群
- **持久化**：消息按 retention 保留（默认 7 天，可永久）
- **多消费者独立**：consumer group 独立 offset
- **顺序保证**：partition 内有序

### 4.3 适合

- 事件流（用户行为、订单变更）
- 日志聚合
- 实时数据管道（→ Spark / Flink）
- CDC（Debezium 把 binlog 推 Kafka）
- 微服务事件总线

### 4.4 不适合

- 复杂路由 / 过滤
- 小规模轻量场景（运维复杂）
- 严格 FIFO 跨整 topic（仅 partition 内）

### 4.5 关键配置

**生产者**：
- `acks=all`：等所有 ISR 副本写入；可靠性最强
- `enable.idempotence=true`：去重
- `compression.type=lz4`：节省带宽

**消费者**：
- `enable.auto.commit=false`：手动 commit 防丢失
- `isolation.level=read_committed`：仅读已提交事务消息

**broker**：
- `min.insync.replicas=2`：至少 2 副本同步
- `replication.factor=3`：3 副本

### 4.6 partition 设计

- partition 数决定最大并行度
- 一开始多设（事后加 partition 麻烦——消息分布变）
- 单 broker 不要超过几千 partition
- key → hash → partition（保证同 key 顺序）

### 4.7 KRaft 模式 —— ZooKeeper 时代的终结（Kafka 4.0+ 默认）

> **2026 年新建 Kafka 集群，不应该再装 ZooKeeper。**

时间线：

- **Kafka 2.8** (2021)：KRaft 模式 early access
- **Kafka 3.3** (2022 / KIP-833)：KRaft **production ready**（新集群可用）
- **Kafka 3.5** (2023)：ZooKeeper 模式正式 deprecated
- **Kafka 4.0** (2025)：**ZooKeeper 完全移除**，KRaft 成为唯一模式

**KRaft（Kafka Raft）做了什么**：

- 用 Raft 共识协议在 controller 节点之间复制集群元数据，**取代 ZooKeeper**。
- 集群只剩一种进程（broker），**部署、运维、监控、版本管理统一**——少一套分布式系统要维护。
- **元数据吞吐与扩展能力大幅提升**：百万级 partition 不再是 ZK znode 的瓶颈。
- 故障切换更快——controller 选主完全在 KRaft quorum 内完成，不再依赖外部 ZK。

**迁移路径**：

| 现状 | 升 4.0 之前要做的 |
|---|---|
| Kafka 3.3+ KRaft 模式 | 直接滚动升 4.0 |
| Kafka 3.3–3.9 ZK 模式 | 先迁 KRaft（在线迁移工具），再升 4.0 |
| Kafka < 3.3 | 先升到 3.9.x，再迁 KRaft，再升 4.0 |

**Java 版本要求**：Kafka 4.0 broker / Connect / 工具要 **Java 17+**；客户端 + Streams 要 **Java 11+**。

### 4.8 KIP-848 —— 新一代消费组协议

旧 rebalance 协议有个根本问题：任一 consumer 加入 / 退出 / 崩溃，**整个 group 全停**（"stop-the-world rebalance"），所有 partition 全部 revoke 再重新分配。在 K8s 滚动重启或自动扩缩时，延迟尖刺非常痛。

**KIP-848** 把 partition 分配从 group leader 移到 broker 端，**新成员增量获得 partition、其他成员不需要 revoke 全部**——彻底告别 stop-the-world。Kafka 4.0 服务端**默认开启**；客户端通过 `group.protocol=consumer` 选择性 opt-in。

**注意**：一旦 consumer group 用了新协议，**只能降级到 Kafka 3.4.1 或更新**，不可回到更老的 3.x。生产启用前要规划清楚。

> 参考：[Apache Kafka 4.0 Release Notes](https://kafka.apache.org/40/getting-started/upgrade/)、[KIP-833](https://cwiki.apache.org/confluence/display/KAFKA/KIP-833%3A+Mark+KRaft+as+Production+Ready)、[KIP-848](https://cwiki.apache.org/confluence/display/KAFKA/KIP-848%3A+The+Next+Generation+of+the+Consumer+Rebalance+Protocol)。

## 第五章：RabbitMQ

### 5.1 模型

```
Producer → Exchange → Queue → Consumer
                    ↑
              Binding（路由规则）
```

四种 Exchange 类型：
- **Direct**：按 routing key 完全匹配
- **Topic**：按 pattern 匹配（`user.*.created`）
- **Fanout**：广播到所有 binding 的 queue
- **Headers**：按 header 匹配

### 5.2 特性

- **灵活路由**
- **传统 AMQP**：精细 ack、reject、requeue
- **优先级队列、TTL、死信**
- **管理 UI** 友好

### 5.3 适合

- 复杂路由需求
- 任务分发（celery、sidekiq 后端）
- 中小规模异步任务
- 需要严格"消息确认"语义

### 5.4 不适合

- 海量吞吐（百万 QPS）
- 长期持久化事件流
- 重放历史消息（消费后即删）

### 5.5 关键配置

- `prefetch_count`：消费者每次拉多少 unacked
- `durable=true`：queue 持久化
- `persistent=true`：消息持久化
- 死信 exchange：失败消息进死信

## 第六章：NATS

### 6.1 模型

- 极简：发布订阅
- 默认无持久化（fire-and-forget）
- JetStream（add-on）提供持久化 + 类似 Kafka 的 stream

### 6.2 特性

- **极快**：百万消息/秒
- **轻量**：单二进制几 MB
- **简洁 API**
- **请求-响应**：内置 RPC pattern
- **集群 + 多区域**

### 6.3 适合

- 微服务内部消息（轻量 RPC + pub/sub）
- 边缘 / IoT
- 实时游戏 / 协同
- 不需重放历史

### 6.4 JetStream

加 persistence + stream + KV + Object store。变得像"Kafka 替代品"，更易用但生态较小。

## 第七章：云托管

### 7.1 AWS SQS

- 简单 queue
- standard（at-least-once + 不保证顺序）vs FIFO
- 长轮询（最长 20s）
- visibility timeout
- 死信队列内建
- 按使用计费

适合：低运维 + 简单异步任务。

### 7.2 AWS SNS + SQS

SNS 广播 → 多个 SQS queue 订阅。fan-out 经典模式。

### 7.3 AWS Kinesis

类 Kafka，AWS 托管。集成 Lambda / Firehose 友好。

### 7.4 GCP Pub/Sub

类似 Kinesis。订阅模型 + 自动 ack/retry。

### 7.5 Cloud vs 自建 Kafka

- 自建：灵活、便宜（大规模）、复杂运维
- 云托管：低运维、贵、有限制

中小规模优先托管；超大规模 + 团队有能力时自建。

### 7.6 Kafka 兼容的现代替代品

2026 年的另一个趋势是**完全兼容 Kafka 协议、但底层重写**的产品：

- **Redpanda**：C++ 实现 Raft + 单进程部署，无 ZooKeeper / 无 JVM。低延迟（p99 < 10ms），单机吞吐高于 Kafka。完全实现 Kafka API（Producer/Consumer/Connect）。
- **Apache Pulsar**：分层存储（broker 无状态 + BookKeeper 持久化），原生多租户、地理复制。Kafka API（KoP）兼容。
- **WarpStream**：完全 stateless brokers + S3 对象存储后端。比传统 Kafka 便宜 5-10x（适合冷数据/审计/可放宽延迟的场景）。

**选型简则**：

| 需求 | 选 |
|---|---|
| 已有 Kafka 团队、生态依赖 Kafka 工具 | **Apache Kafka 4.0 (KRaft)** |
| 极致低延迟 + 简化运维 | **Redpanda** |
| 多租户 + 地理复制 + 长存储 | **Pulsar** |
| 海量数据 + 成本敏感 + 可接受秒级延迟 | **WarpStream** |

## 第八章：典型架构

### 8.1 事件驱动微服务

```
user-service → "user.created" event → Kafka topic
                                       ├→ email-service (发欢迎邮件)
                                       ├→ analytics (统计)
                                       └→ recommendation (推荐冷启动)
```

每下游独立消费 + 独立 offset。

### 8.2 任务队列（worker pool）

```
API → 推送任务 → RabbitMQ → N 个 worker 消费处理
```

celery、sidekiq、bull 等都是这模式。

### 8.3 CDC 管道

```
PostgreSQL → Debezium 监听 WAL → Kafka → 多下游
                                          ├→ Elasticsearch (搜索)
                                          ├→ Redis (cache 同步)
                                          └→ ClickHouse (OLAP)
```

业务无感知；多副本数据靠 binlog 自动一致。

### 8.4 Outbox 模式

```
应用事务: 
  INSERT INTO orders ...
  INSERT INTO outbox (event_type, payload)
COMMIT

后台 worker:
  SELECT * FROM outbox WHERE not_published
  publish to Kafka
  UPDATE outbox SET published_at = now()
```

业务 + 事件原子保证（参考 B09）。

### 8.5 Saga 编排

```
Order Created → Kafka topic
              → Payment Service: 扣款 → Payment Succeeded
              → Inventory Service: 减库存 → Inventory Reserved
              → 所有 success → Mark Order Confirmed
              → 任一 fail → 编排补偿
```

## 第九章：可靠性陷阱

### 9.1 消息丢失

可能位置：
- producer → broker：网络丢；用 `acks=all`
- broker 内：副本丢；min ISR
- broker → consumer：消费后没 commit；ack 后做事
- consumer 处理失败：可重试 + 死信

### 9.2 重复消费

可能：
- consumer 处理完 → commit 前挂 → 重启后再消费
- broker rebalance → consumer 重新读
- producer retry 后 broker 已写

→ **必须幂等**。

### 9.3 顺序问题

- 多 partition + 多 consumer = 全局无序
- 严格顺序 → 单 partition + 单 consumer（吞吐受限）
- 部分顺序 → 按 key 分 partition（同 key 顺序，跨 key 无）

### 9.4 消息堆积

下游处理慢 → broker 累积。监控 lag：

- Kafka：`kafka-consumer-groups --describe`
- 应用层：每 consumer report processed_offset

报警阈值：lag > 10000 或 latency > N 分钟。

### 9.5 死信

n 次重试失败的消息进 dead letter queue。人工分析或自动告警。

## 第十章：选型对比

| 维度 | Kafka | RabbitMQ | NATS | SQS |
|---|---|---|---|---|
| 吞吐 | 极高 | 中 | 高 | 中 |
| 持久化 | 内置 | 内置 | JetStream | 内置 |
| 顺序 | partition 内 | queue 内 | 弱 | FIFO 模式 |
| 路由 | key | 复杂 exchange | 简单 | 无 |
| 重放 | ✅（按 offset） | ❌ | ✅ JetStream | ❌ |
| 运维 | 重 | 中 | 轻 | 托管 |
| 适合 | 事件流、日志 | 任务、复杂路由 | 微服务通信 | AWS 简单任务 |

### 10.1 选型流程

```
需要重放历史 / 多消费组独立位置？
   → Kafka（或 NATS JetStream）
需要复杂路由（pattern matching、多级过滤）？
   → RabbitMQ
极致延迟 + 轻量？
   → NATS
只想 SQS 简单 + 已在 AWS？
   → SQS
```

## 第十一章：生产级最佳实践

1. **消费者幂等**：永远假设可能重复。
2. **手动 commit / ack**：处理成功后再 commit。
3. **死信队列**：失败消息可分析。
4. **监控 lag**：及时报警。
5. **Outbox 模式**：业务 + 事件原子。
6. **schema evolution**：avro / protobuf + schema registry。
7. **partition 数预留**：后期改难。
8. **key 设计**：保证业务"必须有序"的消息同 key。
9. **生产者 acks=all** + **broker 多副本**：可靠优先。
10. **消费者 graceful shutdown**：处理中的消息完成再退。

## 第十二章：常见陷阱清单

### ❌ 陷阱 1：自动 commit
处理失败也 commit 了 → 丢消息。改手动。

### ❌ 陷阱 2：不幂等
重复消费导致重复扣款。

### ❌ 陷阱 3：阻塞消费
慢消费者卡死 partition。增 partition + worker；或异步处理。

### ❌ 陷阱 4：消息超大
> 1MB → broker 配置可能拒；用对象存储 + 消息引用。

### ❌ 陷阱 5：schema 演进破坏
加必填字段没 schema registry → 旧 consumer 崩。

### ❌ 陷阱 6：没死信策略
失败消息无限重试 → 阻塞整个 partition。

### ❌ 陷阱 7：跨 broker 事务幻想
exactly-once 跨多系统几乎不可能。设计幂等。

## 参考答案

**练习 1**：
```
order-service:
  事务 [创建 order + 写 outbox(event_type=OrderCreated)]
  
outbox-publisher:
  outbox → Kafka topic "orders.created"

消费方:
  email-service 消费 "orders.created" → 发邮件
  inventory-service 消费 → 减库存
  scoring-service 消费 → 算分

各自幂等 + 各自 offset。
```

**练习 2**：
- 加 partition + worker：5s × 100 / 1 partition = 500s；4 partition + 4 worker = 125s
- 异步处理：消息 dispatch 后立即 ack；worker 内部加自己 worker pool
- 拆分消息：把大任务拆小

**练习 3**：
- Kafka 内部事务保证 producer 写 + offset commit 原子
- 但**端到端**："消费者处理副作用 + commit offset" 不是原子
- 如果副作用是写另一个外部系统（DB），与 Kafka offset commit 之间仍可能崩
- 解决：consumer 端幂等 + outbox

**练习 4**：
- producer 端用 idempotence
- broker 用持久化
- consumer 端：处理前写 dedup 表 → 处理 → ack
```python
inserted = db.execute("INSERT INTO sent_sms (message_id) VALUES (?) ON CONFLICT DO NOTHING", msg.id)
if inserted:
    sms.send(msg.phone, msg.text)
ack(msg)
```
即使消息重发，dedup 表保证不重发短信。

**练习 5**：
- **选 RabbitMQ 反例**：你只需要简单 fan-out + 极致吞吐 → Kafka 更合适
- **选 Kafka 反例**：任务队列 + 复杂路由 + 几千 QPS → RabbitMQ 更简单
