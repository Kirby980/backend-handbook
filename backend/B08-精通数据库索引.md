## 引言：慢查询的第一嫌疑人

```sql
SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 10;
```

100 万行表，第一次跑 8 秒，加索引后 5 毫秒——快 1600 倍。索引是后端工程师的"性能瑞士军刀"。但**滥用索引也是性能杀手**：写入变慢、内存吃紧、规划器选错。本章拆开索引数据结构、使用规则、陷阱。

---

## 第一章：索引是什么

### 1.1 类比

表的 row 像图书馆的书；索引像书的目录卡片。没卡片要逐一翻；有卡片直接按字母跳。

### 1.2 物理形态

每个索引是磁盘上独立的数据结构（典型 B-tree），存储 (key → row pointer)。

### 1.3 代价

- **空间**：每索引可能占表本身大小的 10-50%
- **写入慢**：INSERT/UPDATE/DELETE 要同时维护索引
- **规划器开销**：多索引让优化器选择路径变复杂

**索引不是越多越好**——只在常 query 的列上加。

---

## 第二章：B-Tree

### 2.1 结构

B-Tree（实际多数 DB 用 B+Tree）是平衡多路搜索树：

```
        [50]
       /     \
    [20,40]   [70,80]
   / |  |  \  /  |  | \
 ...叶子层（有序双链表）
```

性质：
- 每节点有 N 个 key 和 N+1 个孩子
- 所有叶节点深度相同（balanced）
- 叶节点按 key 顺序链接（范围查询 O(范围)）
- 查找 O(log N)；100 万行约 20 步

### 2.2 PostgreSQL / MySQL 默认

`CREATE INDEX idx_name ON users(name);` 默认 B-Tree。

### 2.3 适合的查询

- 等值：`WHERE name = 'Alice'`
- 范围：`WHERE age > 18`
- 前缀：`WHERE name LIKE 'Al%'`（**前缀**才用得上）
- 排序：`ORDER BY name`（与索引方向一致）

### 2.4 不适合

- `WHERE LOWER(name) = 'alice'`（函数包裹列）→ 索引失效
- `WHERE name LIKE '%ce'`（开头通配符）→ 索引失效
- `WHERE name <> 'Alice'`（不等于）→ 索引基本无效

## 第三章：复合索引

### 3.1 多列联合

```sql
CREATE INDEX idx_user_status ON orders(user_id, status, created_at);
```

把多列拼为一个 key。**列顺序至关重要**——按"等值 → 范围 → 排序"考虑：

- 等值条件优先
- 范围条件其次
- 排序方向匹配

### 3.2 最左前缀

复合索引 `(a, b, c)` 可用于：
- `WHERE a = ?`
- `WHERE a = ? AND b = ?`
- `WHERE a = ? AND b = ? AND c = ?`
- `WHERE a = ? AND b > ? AND c = ?`（b 范围后 c 不参与索引）
- `WHERE a = ? ORDER BY b, c`

**不**能用于：
- `WHERE b = ?`（跳过 a）
- `WHERE c = ?`（跳过 a, b）

### 3.3 选择性

定义：`不同值数 / 总行数`。性别（0.5）选择性低；UUID（接近 1）选择性高。

**高选择性列放前面**——让索引快速缩小范围。

例外：复合索引的"等值条件"必须放前，无论选择性。

### 3.4 设计实例

```sql
-- 业务：列出某 user 最近 10 个 paid 订单
SELECT * FROM orders
WHERE user_id = 42 AND status = 'paid'
ORDER BY created_at DESC LIMIT 10;

-- 最优索引
CREATE INDEX idx_orders ON orders(user_id, status, created_at DESC);
```

3 列恰好对应 query 的等值-等值-排序。

## 第四章：覆盖索引

### 4.1 含义

如果索引包含 query 需要的所有列，**不需要回表**——直接从索引返回。

```sql
CREATE INDEX idx_user_name ON users(user_id, name);
SELECT name FROM users WHERE user_id = 42;   -- 仅查 name → 覆盖
```

### 4.2 性能

回表多一次 I/O（叶子 → 主表）。覆盖索引省这次 I/O，热点查询提升明显。

### 4.3 PostgreSQL 的 INCLUDE

```sql
CREATE INDEX idx_user ON users(user_id) INCLUDE (name, email);
```

`INCLUDE` 列**不参与索引 B-tree 排序键**，但存在叶子上，覆盖查询时可用——比单纯加列更省空间、不影响树结构。

### 4.4 MySQL InnoDB 主键索引

InnoDB 主键是聚集索引（clustered）——叶节点直接存整行。所以按主键查永远是覆盖查询。其他索引叶节点存主键值（要回表）。

## 第五章：Hash、GIN、BRIN 等

### 5.1 Hash

```sql
CREATE INDEX idx_h ON users USING HASH (email);
```

仅等值查询。优势：O(1) 查找；劣势：不支持范围、排序。

通常 B-Tree 已经够好，hash 索引现实少用。**PostgreSQL 9.6 之前 hash 索引不支持崩溃恢复**——避坑。

### 5.2 GIN（Generalized Inverted Index）

倒排索引。适合：

- 全文搜索 `tsvector`
- JSONB 字段
- 数组成员

```sql
CREATE INDEX idx_tags ON posts USING GIN (tags);
SELECT * FROM posts WHERE 'go' = ANY(tags);
```

### 5.3 GiST

适合**空间** / **范围**数据（如 PostGIS、tsrange、ip range）。

```sql
CREATE INDEX idx_loc ON places USING GIST (location);
```

### 5.4 BRIN（Block Range Index）

仅存"块范围最小最大值"。适合**有序大表**（时间序列）：

```sql
CREATE INDEX idx_ts ON metrics USING BRIN (timestamp);
```

索引极小（KB 级 vs B-Tree 的 GB）；适合扫描大范围。

### 5.5 Partial Index（部分索引）

```sql
CREATE INDEX idx_active ON users (last_login) WHERE active = true;
```

只为满足条件的行建索引——小、快。常用于"软删除"、状态机。

### 5.6 Expression Index

```sql
CREATE INDEX idx_lower_email ON users (LOWER(email));
SELECT * FROM users WHERE LOWER(email) = 'alice@x.com';
```

让函数化查询也能走索引。

## 第六章：EXPLAIN

### 6.1 查看执行计划

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 42;

EXPLAIN ANALYZE SELECT ...   -- 实际执行 + 统计
```

PostgreSQL 输出：

```
Index Scan using idx_orders_user_id on orders  (cost=0.42..8.44 rows=1 width=...)
  Index Cond: (user_id = 42)
```

MySQL：
```
EXPLAIN SELECT ...
+----+-------------+--------+------+---------------+-----------+
| id | select_type | table  | type | key           | rows      |
+----+-------------+--------+------+---------------+-----------+
|  1 | SIMPLE      | orders | ref  | idx_user_id   |  10       |
```

### 6.2 关键字段

| 字段 | 含义 |
|---|---|
| **type** (MySQL) / **Node Type** (PG) | 扫描方式：const > ref > range > index > ALL |
| **rows** | 估算行数 |
| **key** | 实际用的索引 |
| **Extra** / **Filter** | 额外信息（Using filesort、Using temporary 是警告）|

### 6.3 红旗

- `Seq Scan`（PG）/ `type: ALL`（MySQL）：全表扫
- `Using filesort`：排序未走索引
- `Using temporary`：用了临时表
- rows 估算与实际差大 → 统计信息过期，ANALYZE 表

## 第七章：索引失效场景

### 7.1 函数包裹

```sql
WHERE YEAR(created_at) = 2026     -- ❌ 失效
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'   -- ✅
```

### 7.2 隐式类型转换

```sql
-- user_id INT
WHERE user_id = '42'   -- 看 DB 处理；MySQL 部分版本失效
```

### 7.3 OR 子句

```sql
WHERE a = 1 OR b = 2
```

需要 a、b 各自有索引，且 query planner 选 index_merge 才用得上。否则可能全表扫。

### 7.4 NULL 处理

```sql
WHERE col IS NULL
```

部分索引（含 NULL）能用；很多 DB 默认 B-tree 不索引 NULL。可用 `WHERE col IS NOT NULL` 的 partial index。

### 7.5 != 与 <>

不等于条件几乎用不上索引（要扫除"等于"外的所有）。改正向条件或加复合索引。

### 7.6 数据倾斜

```sql
WHERE status = 'active'   -- 99% 行都是 active
```

planner 觉得"扫全表更快"——不走索引。这通常是对的判断。

## 第八章：索引维护

### 8.1 统计信息

PostgreSQL `ANALYZE`、MySQL `ANALYZE TABLE` 更新表统计信息。统计过期 → planner 选错。

自动 vacuum / autoanalyze 默认开启；大批量更新后建议手动跑一次。

### 8.2 索引膨胀

频繁 UPDATE/DELETE 导致索引页内空闲——B-Tree 不自动合并。

```sql
-- PostgreSQL
REINDEX INDEX idx_foo;
REINDEX TABLE foo CONCURRENTLY;   -- 不锁表

-- MySQL
OPTIMIZE TABLE foo;
```

### 8.3 监控未用索引

```sql
-- PostgreSQL: idx_scan = 0 的索引可能没用
SELECT * FROM pg_stat_user_indexes WHERE idx_scan = 0;
```

未用索引浪费空间 + 拖慢写入。定期清理。

### 8.4 索引上线

大表加索引可能锁很久。生产用 `CONCURRENTLY`：

```sql
CREATE INDEX CONCURRENTLY idx_foo ON tbl (col);
```

不锁表但慢，且失败要 `DROP INDEX CONCURRENTLY`。

## 第九章：典型设计模式

### 9.1 主键

用合适的主键。InnoDB 主键即聚集索引——选择影响整表性能。

- 自增 int：插入快（追加到末尾）
- UUID：高写入冲突低，但分页"乱"

UUIDv7 / ULID（带时间戳的有序 UUID）兼顾安全和有序——现代选择。

### 9.2 反规范化字段加索引

```sql
SELECT * FROM orders WHERE user_id = ? AND status IN ('paid', 'shipped');

-- 设计：加 paid_status 布尔字段
CREATE INDEX idx_orders_paid ON orders(user_id) WHERE status IN ('paid', 'shipped');
```

partial index 进一步缩小。

### 9.3 软删除 + 索引

```sql
CREATE INDEX idx_active_users ON users(email) WHERE deleted_at IS NULL;
```

只索引活用户，索引小，查询快。

### 9.4 排序字段

业务常按 created_at DESC——索引也要 DESC：

```sql
CREATE INDEX idx_orders_created ON orders(user_id, created_at DESC);
```

否则 ORDER BY 需要反向扫，仍可走但代价高。

## 第十章：何时**不**加索引

1. 表小（< 10000 行）：全表扫够快
2. 数据倾斜严重（一个值占 90%+）：planner 不走索引
3. 列频繁更新：每次更新都改索引
4. 仅一次性查询：建索引代价 > 节省
5. 高写入低查询表：日志表通常少索引

---

## 第十一章：生产级最佳实践

1. **慢查询日志开启**：`pg_stat_statements` / MySQL slow log。
2. **每个 FK 列加索引**：JOIN 性能基础。
3. **复合索引按"等值-范围-排序"**。
4. **覆盖索引保护热点 query**。
5. **partial index 处理常态 WHERE**：节省空间。
6. **定期 ANALYZE + REINDEX**：维护新鲜统计 + 减膨胀。
7. **CONCURRENTLY 加索引**：避免锁表。
8. **监控未用索引**：定期清理。
9. **避免 SELECT \***：少返回 = 多机会走覆盖。
10. **大表分区前先索引**：分区是最后手段。

## 第十二章：常见陷阱清单

### ❌ 陷阱 1：函数包裹列
```sql
WHERE LOWER(email) = 'x'   -- 索引失效
```

### ❌ 陷阱 2：复合索引列顺序错
`(status, user_id)` 用于 `WHERE user_id = ?` → 半失效（要扫所有 status）

### ❌ 陷阱 3：忽略统计信息
ANALYZE 没跑 → planner 估算错。

### ❌ 陷阱 4：误以为 IN 走索引
`WHERE id IN (...)` 通常能走，但**大量 IN（万级）** 可能改全表扫。

### ❌ 陷阱 5：UUID 主键插入慢
随机 UUID 让 B-Tree 插入触发频繁页分裂。用 UUIDv7 或 bigint 自增。

### ❌ 陷阱 6：加太多索引
- 每索引一份维护成本
- 写入变 2-5 倍慢
- 内存 buffer pool 被挤

### ❌ 陷阱 7：索引列定义不一致
`WHERE varchar_col = 42` → 隐式转换 → 部分 DB 失效。

## 第十三章：练习题

**练习 1**：以下 SQL 想加索引：
```sql
SELECT * FROM orders WHERE customer_id = ? AND created_at > ? ORDER BY created_at DESC;
```

**练习 2**：解释 PostgreSQL `EXPLAIN ANALYZE` 输出中 `Seq Scan` 出现意味着什么。

**练习 3**：表 1 亿行，加 `CREATE INDEX idx ON tbl (col)` 时锁表多久？怎么改善？

**练习 4**：以下 query 为何索引失效？修复。
```sql
WHERE DATE(created_at) = '2026-05-12'
```

## 参考答案

**练习 1**：`(customer_id, created_at DESC)`。等值 + 范围 + 排序一起覆盖；DESC 配合 ORDER BY。如果 SELECT 字段不多还可加 INCLUDE 形成覆盖索引。

**练习 2**：全表扫——索引没用上或不存在。可能：
- 没匹配索引
- planner 估算"扫全表更便宜"（数据倾斜）
- ANALYZE 信息过期
查 EXPLAIN 看具体原因。

**练习 3**：
- 默认 `CREATE INDEX` 锁写（可能分钟级）
- PG `CONCURRENTLY` 不锁写但慢、可能失败
- MySQL Online DDL（5.6+）默认 inplace + 不阻塞写
- 实在很大用 pt-online-schema-change 或 gh-ost

**练习 4**：`DATE()` 函数包裹列 → 索引失效。改：
```sql
WHERE created_at >= '2026-05-12' AND created_at < '2026-05-13'
```

**练习 5**：
```sql
CREATE INDEX idx_active ON users (email) WHERE deleted_at IS NULL;
```
仅活用户进入索引。查询 `WHERE deleted_at IS NULL AND email = ?` 命中此 partial index——索引极小、查询快。同时 `deleted_at IS NULL` 是大多数 query 的条件。

## 小结

| 知识点 | 关键记忆 |
|---|---|
| B-Tree | 等值/范围/前缀/排序 |
| 复合索引 | 列顺序 = 等值 → 范围 → 排序 |
| 覆盖索引 | 不回表；包含查询所有列 |
| 特殊索引 | Hash / GIN / GiST / BRIN / Partial / Expression |
| EXPLAIN | Seq Scan = 红旗；rows 估算靠 ANALYZE |
| 失效 | 函数包裹 / 类型转换 / OR / 数据倾斜 |
| 维护 | ANALYZE + REINDEX + CONCURRENTLY |
| 数量 | 不是越多越好；写入会变慢 |
