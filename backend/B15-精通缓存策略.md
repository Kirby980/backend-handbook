## 引言：缓存让一切变快

```
DB 查询：50 ms
Redis 查询：0.5 ms
内存命中：0.0001 ms
```

每加一层 cache，速度提升 100x。但缓存有代价：一致性、复杂度、雪崩风险。"There are only two hard things in CS: cache invalidation and naming things"——这章重点讲缓存模式 + 失效策略 + 雪崩防护。

## 第一章：缓存的层次

```
浏览器 cache         ← HTTP Cache-Control
   ↓
CDN                  ← 静态资源 + edge
   ↓
反向代理 cache       ← Nginx / Varnish
   ↓
应用进程内 cache     ← in-memory LRU
   ↓
分布式 cache         ← Redis / Memcached
   ↓
DB query cache       ← PostgreSQL shared_buffers
   ↓
磁盘
```

每层命中越靠上越快。设计目标：让请求尽量早命中。

## 第二章：缓存模式

### 2.1 Cache-Aside（Lazy Loading）

```python
def get_user(id):
    val = cache.get(f"user:{id}")
    if val: return val
    val = db.query(id)
    cache.set(f"user:{id}", val, ttl=300)
    return val
```

最常见。读时按需缓存。

优点：
- 简单
- 容忍 cache 故障（回退到 DB）

缺点：
- 首次 miss 慢
- DB 写更新后 cache 仍是旧值（直到 TTL 或显式删）

### 2.2 Write-Through

```python
def update_user(id, data):
    db.update(id, data)
    cache.set(f"user:{id}", data)
```

写时同步更新 cache。

优点：
- cache 永远是最新
- 读不 miss（首次写后就在）

缺点：
- 写延迟增加
- 写未读字段也缓存（浪费）

### 2.3 Write-Behind（Write-Back）

```python
def update_user(id, data):
    cache.set(f"user:{id}", data)
    queue.publish("user_update", {id: id, data: data})   # 异步入 DB
```

写到 cache 即返回；后台 worker 异步刷 DB。

优点：
- 写极快
- DB 写入可批量化

缺点：
- cache 故障 → 数据丢
- 一致性最弱
- 复杂度高

适用：监控数据、计数器、不太重要的状态。

### 2.4 Refresh-Ahead

定期主动刷新 cache（不等 TTL）。

```python
@scheduler.cron("*/5 * * * *")
def refresh_hot_users():
    for id in hot_user_ids:
        cache.set(f"user:{id}", db.query(id))
```

热点数据保持永远是新。

## 第三章：失效策略

### 3.1 TTL（Time To Live）

```python
cache.set(key, val, ttl=3600)
```

简单。但 TTL 时间内的 stale 数据无法立刻刷新。

### 3.2 主动失效

写 DB 时显式删 cache：

```python
def update_user(id, data):
    db.update(id, data)
    cache.delete(f"user:{id}")
```

下次读 miss → 重新加载新值。比 write-through 简单（不计算新 cache 值）。

### 3.3 LRU / LFU 驱逐

cache 容量满时按策略淘汰：
- **LRU**：最久未用
- **LFU**：最少使用
- **FIFO**：先进先出
- **Random**

Redis maxmemory-policy 配置：
```
maxmemory 4gb
maxmemory-policy allkeys-lru
```

### 3.4 Tag-based / Group invalidation

按标签批量失效：

```
cache.set("user:42", data, tags=["user", "user:42"])
# ...
cache.invalidate_tag("user:42")   # 所有相关 cache 失效
```

但 Redis 没原生支持，要应用层实现（如用 set 存 tag → keys）。

## 第四章：缓存雪崩

### 4.1 现象

大量 cache 同时过期 → 流量瞬间打到 DB → DB 过载 → 服务挂。

```
12:00:00 cache.set 1000 个热点, ttl=3600
13:00:00 全部同时过期 → 1000 个请求同时 miss → DB CPU 100%
```

### 4.2 解决

**A. 随机化 TTL**
```python
cache.set(key, val, ttl=3600 + random.randint(-600, 600))
```
分散到不同时间点过期。

**B. 永不过期 + 后台刷新**
```python
cache.set(key, val)   # 无 TTL
# 后台定期刷新
```

**C. 多级 TTL**
```python
cache.set(key, val, ttl=3600)        # 主 TTL
cache.set(key + ":bak", val, ttl=86400)   # 备份
```
主过期 → 用备份 → 后台异步刷新。

## 第五章：缓存穿透

### 5.1 现象

请求查询**不存在的 key** → cache 永远 miss → 每次打 DB。

```
GET /user/999999999  # 不存在
→ cache miss
→ db.query → not found
→ 返回 404
→ 下次请求重复
```

恶意攻击：随机 ID 不断请求。

### 5.2 解决

**A. 缓存空值**
```python
val = db.query(id)
if val is None:
    cache.set(key, "__NULL__", ttl=60)   # 短 TTL
else:
    cache.set(key, val, ttl=3600)
```

**B. Bloom filter**
应用启动加载所有合法 ID 到 bloom filter。请求来先查 filter——不存在直接返回 404 不打 DB。

**C. 限流**
对 404 高的 IP 限速。

## 第六章：缓存击穿

### 6.1 现象

**单个**热点 key 过期 → 瞬间大量并发请求 miss → 都去打 DB（thundering herd）。

```
12:00:00 cache "user:hot" 过期
12:00:00.001 100 个请求 → cache miss → 100 个 DB query
```

### 6.2 解决

**A. 互斥锁（single-flight）**
```python
def get_with_lock(key):
    val = cache.get(key)
    if val: return val
    with redis.lock(f"lock:{key}", timeout=5):
        val = cache.get(key)    # double-check
        if val: return val
        val = db.query(...)
        cache.set(key, val)
        return val
```

仅一个请求实际打 DB；其他等。

**B. 不过期 + 异步刷新**
热点永远在 cache；后台 cron 刷新。

**C. 提前刷新**
TTL 还有 10% 时主动续期：
```python
if cache.ttl(key) < 60:  # 快过期
    refresh_async(key)
return cache.get(key)
```

## 第七章：一致性策略

### 7.1 强一致很难

cache 与 DB 双写很难保证原子：
- 先写 DB 再 set cache：DB 成功、cache 失败 → 不一致
- 先 set cache 再写 DB：cache 成功、DB 失败 → cache 有但 DB 没有
- 先删 cache 再写 DB：删除成功、DB 失败 → 下次读会重置 cache 为旧值

### 7.2 常用 pattern

**先更 DB 后删 cache**：
```python
db.update(id, data)
cache.delete(key)
```

简单稳健。极端情况下：
- DB 成功 + cache 删除失败 → cache 仍是旧值；下个 TTL 周期自动修复
- 并发读写：A 删 cache → B 读 miss → B 读 DB 拿旧值 → A 写 DB → B set cache 旧值 → 不一致

修：**double delete**——先删，写 DB，sleep 一会，再删一次。

**Cache-aside + 短 TTL**：5-60 秒 TTL。允许短暂不一致；定期自愈。

**通过 CDC 同步**：监听 DB binlog，事件触发 cache invalidation。强大但复杂。

## 第八章：CDN 缓存

### 8.1 边缘缓存

静态资源（JS、CSS、图片）放 CDN：
- 用户就近访问
- 减少 origin 压力
- 命中通常 99%+

### 8.2 控制

```
Cache-Control: public, max-age=31536000, immutable
```

`immutable` 让 client 永不 revalidate。配合文件名哈希（app.abc123.js）实现可控更新。

### 8.3 Surrogate-Control

```
Cache-Control: max-age=60                       # 浏览器
Surrogate-Control: max-age=3600                 # CDN
```

CDN 持有更长，浏览器短——保证用户改动 60s 内可见。

### 8.4 Purge

部署新版后主动通知 CDN 失效：
- Cloudflare、Fastly 提供 API
- 或文件名带 hash，新文件 = 新 URL

## 第九章：进程内 cache

### 9.1 何时用

- 极热数据（< 1ms 都嫌慢）
- Redis 也撑不住的极端 QPS
- 单实例独立数据

### 9.2 实现

Go：
```go
import "github.com/hashicorp/golang-lru/v2"
cache, _ := lru.New[string, *User](10000)
cache.Add(id, user)
val, ok := cache.Get(id)
```

Python：`functools.lru_cache`。Java：Caffeine。

### 9.3 风险

- 跨实例不一致（A 实例 cache 还在用 B 实例已删的版本）
- 实例重启丢
- 内存压力

通常配合 Redis：进程内 cache（L1） + Redis（L2）。

## 第十章：监控

### 10.1 关键 metric

- **Hit rate**：> 90% 才算"有意义"
- **Latency p50/p99**：cache 不应 > 1-5ms
- **Eviction rate**：高 → 容量不够
- **Memory usage**：接近上限要警惕
- **Connection / queue**：饱和告警

## 第十一章：生产级最佳实践

1. **cache-aside 是默认**：简单 + 容错。
2. **TTL 随机化**：防雪崩。
3. **热 key 加 lock 或预刷新**：防击穿。
4. **空值缓存**：防穿透。
5. **写后删 cache（不是 update）**：简单稳健。
6. **Redis maxmemory + LRU policy**：防 OOM。
7. **监控 hit rate**：< 80% 调优。
8. **多级 cache（L1 进程内 + L2 Redis）**：极致延迟。
9. **CDN 静态 + immutable**：边缘命中。
10. **不缓存所有东西**：低频数据不值。

## 第十二章：常见陷阱清单

### ❌ 陷阱 1：所有 TTL 一样
集中过期 → 雪崩。

### ❌ 陷阱 2：忘 set cache
某分支忘了写 cache → miss 持续。

### ❌ 陷阱 3：cache 当主存
丢数据。Redis 持久化是辅助。

### ❌ 陷阱 4：cache 包含敏感数据
session token 不应 log 化。

### ❌ 陷阱 5：写 DB 失败仍 set cache
不一致。先 DB 再 cache，DB 错就 return。

### ❌ 陷阱 6：cache value 过大
Redis 单 key 100MB → 网络 + 序列化都慢。拆。

### ❌ 陷阱 7：高频读慢 query 没缓存
"我以为 DB 够快"——加缓存 100x 提升。

## 参考答案

**练习 1**：
```python
import random
def get_user(id):
    key = f"user:{id}"
    val = cache.get(key)
    if val == "__NULL__": return None
    if val is not None: return val
    
    # 击穿防护
    lock_key = f"lock:{key}"
    if not redis.set(lock_key, "1", nx=True, ex=5):
        time.sleep(0.05); return get_user(id)   # 等别人
    try:
        val = cache.get(key)
        if val is not None: return val if val != "__NULL__" else None
        val = db.query(id)
        if val is None:
            cache.set(key, "__NULL__", ttl=60)
        else:
            cache.set(key, val, ttl=3600 + random.randint(-300, 300))
        return val
    finally:
        redis.delete(lock_key)
```

**练习 2**：删 cache 比更新 cache 更稳健。原因：
- 计算新 cache value 可能出错
- 并发 update 时计算顺序不可控
- 删除是幂等的
- 下次读 miss 自动刷新

更新 cache 的好处：避免 miss 延迟。但风险大于收益，多数场景"删"更好。

**练习 3**：
1. **互斥锁**：只一个 request 打 DB，其他等
2. **永不过期 + 后台刷新**：cron 定期 refresh
3. **TTL 临近 → 提前异步刷新**：用户感知不到过期

**练习 4**：Bloom filter 能"100% 说 key 不存在"或"可能存在"。请求来时先查 filter——不存在直接 404 不打 DB；存在再走 cache → DB。恶意随机 ID 请求被 filter 直接挡住。

**练习 5**：
- 文件名带 hash：`app.abc123.js`。新版本 = 新文件名 = 新 URL，浏览器自动重取
- HTML 用 `Cache-Control: no-cache`：每次 revalidate
- CDN API purge 关键路径
- 渐进发布（10% → 100%）

## 小结

| 模式 | 何时用 |
|---|---|
| Cache-aside | 默认 |
| Write-through | 写后立刻可读 |
| Write-behind | 极致写性能 + 容忍丢失 |
| Refresh-ahead | 热点永新 |

| 问题 | 解 |
|---|---|
| 雪崩 | TTL 随机化 |
| 击穿 | 互斥锁 / 预刷新 |
| 穿透 | 空值缓存 / Bloom filter |
| 一致性 | 写 DB → 删 cache + 短 TTL |
