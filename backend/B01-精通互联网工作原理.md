## 引言：从浏览器输入到响应返回

```
用户在浏览器输入: https://api.example.com/users/42
```

短短一行 URL，背后涉及：DNS 解析、TCP 三次握手、TLS 握手、HTTP 协议、可能的 CDN/load balancer、服务器路由、数据库查询、HTTP 响应、TCP 关闭。每一步都可能成为瓶颈或 bug 源头。后端工程师需要**整条链路都看得见**。本章把这条链路拆开讲清楚。

## 第一章：分层模型

### 1.1 OSI 七层 vs TCP/IP 四层

实际工程中我们用 **TCP/IP 模型**：

| TCP/IP 层 | 主要协议 |
|---|---|
| **应用层** | HTTP、HTTPS、gRPC、DNS、SSH、SMTP |
| **传输层** | TCP、UDP、QUIC |
| **网络层** | IP（v4/v6）、ICMP |
| **链路层** | Ethernet、Wi-Fi、ARP |

每一层处理特定关注点：链路层管硬件，网络层管路由，传输层管端到端可靠性，应用层管业务语义。

### 1.2 封装

每一层把上层数据加上自己的头部：

```
应用层数据 → +TCP头 → +IP头 → +Ethernet头 → 物理网线
```

接收方反向拆解。这种"分层 + 封装"让协议解耦，每层可独立演进。

## 第二章：DNS——把名字变成地址

### 2.1 为什么需要

人记得住 `api.example.com`，记不住 `34.117.59.81`。DNS 是分布式的"域名 → IP"目录。

### 2.2 解析流程

```
1. 浏览器 → 本地 DNS 缓存
2. 操作系统 → resolver（通常 ISP 或 8.8.8.8）
3. resolver → 根 DNS（.）→ TLD（.com）→ 权威 DNS（example.com）
4. 返回 A/AAAA 记录的 IP
```

### 2.3 记录类型

| 类型 | 含义 |
|---|---|
| **A** | 域名 → IPv4 |
| **AAAA** | 域名 → IPv6 |
| **CNAME** | 别名 → 另一域名 |
| **MX** | 邮件服务器 |
| **TXT** | 任意文本（SPF、DKIM、域名验证） |
| **NS** | 该域的权威服务器 |
| **SOA** | 域起始信息（管理员、TTL 等） |
| **SRV** | 服务定位（端口 + 主机） |

### 2.4 TTL 与缓存

每条记录有 TTL（生存时间）。DNS 改动后需要等 TTL 过期才全网生效。

- 短 TTL（60-300s）：方便切换、影响 query 量
- 长 TTL（86400s+）：减少 query、变更慢

生产建议：常变的入口短 TTL，稳定记录长 TTL。

### 2.5 命令行工具

```bash
dig api.example.com         # 完整解析
dig +short api.example.com  # 仅地址
dig MX example.com          # 指定类型
nslookup api.example.com
host api.example.com
```

排查 DNS 问题第一步：从不同地点 `dig` 看是否一致；本地 cache 用 `dig +trace` 或 `systemd-resolve --flush-caches`。

## 第三章：IP——网络层

### 3.1 IPv4 与 IPv6

- IPv4：32 位，约 43 亿地址，已耗尽
- IPv6：128 位，"无限" 地址。截至 2026 年，Google 测得 **IPv6 占比已突破 50%**（2026-03 首次过半，日常在约 45%-50% 波动），主要驱动是移动网络（中国、印度、美国电信运营商已默认 IPv6 first）

现代服务必须**双栈**（dual-stack）—— 同时支持 v4/v6。云上 K8s 集群默认双栈也已成事实标准。

### 3.2 子网

CIDR 表示：`192.168.1.0/24` = 256 个地址（前 24 位是网络，后 8 位是主机）。

| 后缀 | 主机数 |
|---|---|
| /32 | 1 |
| /24 | 256 |
| /16 | 65536 |
| /8 | 16M |

### 3.3 路由

IP 包在每个 router hop 时查路由表选下一跳。`traceroute` 显示路径：

```bash
traceroute api.example.com
1  192.168.1.1     1.2 ms
2  10.0.0.1        5.3 ms
3  isp-gw.com      12.0 ms
...
```

每个 hop 增加一些延迟（10-50ms 跨大洲）。

### 3.4 MTU

最大传输单元：Ethernet 默认 1500 字节。包大于 MTU 被分片（fragment）。分片是性能杀手——丢一片整包重传。

PMTU discovery 让 TCP 协商避免分片。在容器/隧道环境 MTU 常被错配（如 VXLAN 减 50 字节）。

## 第四章：TCP——可靠传输

### 4.1 三次握手

```
客户端 → SYN → 服务端
客户端 ← SYN+ACK ← 服务端
客户端 → ACK → 服务端
连接建立
```

3 个包，1.5 个 RTT。**每次建立 TCP 连接都付这个成本**——也是为什么 HTTP keep-alive 重要。

### 4.2 可靠保证

- **顺序**：包按顺序交付
- **完整**：丢包重传
- **流控**：sliding window 避免压垮接收方
- **拥塞控制**：探测网络容量（slow start、congestion avoidance）

### 4.3 关键参数

- **MSS**（max segment size）：每包数据上限，常 1460 字节
- **rwnd**：接收方告知发送方"我能再收多少"
- **cwnd**：发送方根据网络探测出的窗口

### 4.4 四次挥手 / TIME_WAIT

```
A → FIN → B
A ← ACK ← B
A ← FIN ← B
A → ACK → B
A 进入 TIME_WAIT 2*MSL（通常 60s-120s）
```

TIME_WAIT 是为了处理可能延迟到达的旧包。问题：**短连接服务**会累积大量 TIME_WAIT 端口，可能耗尽端口（65535 - reserved）。

调优：
- 用 keep-alive 减少新连接
- `net.ipv4.tcp_tw_reuse=1`（Linux）
- 用更大的端口范围

### 4.5 head-of-line blocking

TCP 按序交付——丢一个包，后面 100 个包都要等重传。这是 HTTP/2 在 TCP 上仍受限的根本原因（QUIC/HTTP3 改用 UDP 解决）。

## 第五章：UDP

### 5.1 无连接、无序、不重传

UDP 极简：发包就完，不管收没收到、顺序对不对。

| 特性 | TCP | UDP |
|---|---|---|
| 可靠 | ✅ | ❌（应用自己处理） |
| 有序 | ✅ | ❌ |
| 流控 | ✅ | ❌ |
| 开销 | 高 | 低 |

### 5.2 用途

- DNS（小包查询）
- 视频/语音（丢几帧无所谓）
- 游戏（实时性 > 完整性）
- DHCP、SNMP、NTP
- **QUIC**（HTTP/3 底层）

## 第六章：HTTP/1.1

### 6.1 文本协议

```
GET /users/42 HTTP/1.1
Host: api.example.com
User-Agent: curl/8.0

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 32

{"id":42,"name":"Alice"}
```

简单、易调试（telnet 都行）。

### 6.2 关键特性

- **keep-alive**：默认开启，复用 TCP 连接
- **pipelining**：可流水线发请求，但实际很少用（head-of-line 问题）
- **chunked transfer encoding**：流式传输不预知长度的内容

### 6.3 限制

- 文本格式 = 解析开销大
- 同时多请求要多 TCP 连接（浏览器一般 6 个/域名）
- 头部不压缩

## 第七章：HTTP/2

### 7.1 二进制 + 多路复用

HTTP/2 是 HTTP/1.1 的"传输层升级"——语义相同（同样的 method/status/header），但底层格式完全不同。

```
单个 TCP 连接
├── stream 1: GET /a
├── stream 3: GET /b
├── stream 5: GET /c
└── ...
```

并发流（stream），无队头阻塞（HTTP 层面）。

### 7.2 HPACK 头部压缩

重复的头（Cookie、User-Agent）只发一次，之后引用索引。大幅减小开销。

### 7.3 Server Push

服务端可主动推送资源（如 HTML 引用的 CSS）。**实际上已废弃**（Chrome 移除支持）—— 因为难配置且收益不大。

### 7.4 仍受 TCP 层 head-of-line 限制

HTTP/2 解决了 HTTP 层的 head-of-line，但 TCP 丢包仍阻塞整个连接上的所有 stream。

## 第八章：HTTP/3 与 QUIC

### 8.1 QUIC 是什么

Google 开发，IETF 标准化的"UDP 上的可靠流协议"。

特性：
- 基于 UDP，每个 stream 独立
- TLS 1.3 内置（一次握手）
- 0-RTT 重连（已知服务器的连接秒重建）
- 连接迁移（IP 变了不掉线）

### 8.2 HTTP/3 = HTTP over QUIC

```
应用 ── HTTP/3
       ├── QUIC（UDP）
       └── TLS 1.3
```

### 8.3 优势

- 无 TCP head-of-line
- 弱网下显著好（移动、跨洲）
- 切换 Wi-Fi/4G 不断线

### 8.4 普及（2026 现状）

- **HTTP/3 标准**：[RFC 9114](https://datatracker.ietf.org/doc/html/rfc9114)（2022-06）；底层 QUIC v1 [RFC 9000](https://datatracker.ietf.org/doc/html/rfc9000)（2021-05）。
- **浏览器**：Chrome / Edge（2020-11+）、Firefox（2021-04+）、Safari（默认开启）—— 95%+ 主流浏览器原生支持。
- **网络流量**：2026-05 时 Cloudflare 全网约 **21%** 请求走 HTTP/3，仍略低于 HTTP/1.x（约 **29%**）；HTTP/2 约 **50%** 最多；W3Techs 测得 25-34% 网站支持 HTTP/3。
- **CDN / 大流量站**：Cloudflare、Google、Akamai、Fastly、AWS CloudFront、Facebook 全部默认开启。
- **后端架构典型模式**：Browser ──HTTP/3──> CDN/Edge ──HTTP/2 或 HTTP/1.1──> Origin。**绝大多数后端服务自己不必直接说 HTTP/3**——让 CDN/反向代理处理。
- **运行中的工作**：QUIC v2、Multipath QUIC（手机切 Wi-Fi/4G 时同时用多路径）、MASQUE / WebTransport。

## 第九章：协议选择指南

| 场景 | 推荐 |
|---|---|
| Browser → Edge | HTTP/3 → fallback HTTP/2 |
| API 网关 → 微服务 | HTTP/2（gRPC）或 HTTP/1.1 |
| 内部服务之间 | gRPC over HTTP/2 |
| 浏览器实时双向 | WebSocket / Server-Sent Events |
| 移动 app 实时 | gRPC 或 WebSocket |
| 大文件下载 | HTTP（CDN）|
| 视频/语音 | WebRTC（基于 UDP）|
| 物联网低带宽 | MQTT / CoAP |

## 第十章：常见网络问题与排查

### 10.1 慢

**DNS 慢**：`dig api.com` 看耗时；考虑应用层 DNS cache。
**TCP 建连慢**：远端，跨大洲；用 CDN、keep-alive。
**TLS 握手慢**：~1-2 RTT；启用 session resumption、0-RTT、HTTP/3。
**TCP 拥塞**：包丢失导致 cwnd 缩；BBR 算法比 CUBIC 好。
**应用慢**：profile 服务端代码。

### 10.2 不通

- DNS 解析失败：检查 NS records、resolver 配置
- TCP 不通：防火墙、安全组、路由
- TLS 握手失败：证书过期、TLS 版本不匹配、SNI 配置
- HTTP 错：看 status code，4xx 客户端、5xx 服务端

### 10.3 工具

```bash
ping host                # ICMP，测连通
traceroute / mtr host    # 看路由
dig / nslookup name      # DNS
nc -zv host port         # TCP 端口连通
curl -v https://...      # HTTP 调试
tcpdump / wireshark      # 抓包
ss -tlnp                 # 看监听端口
netstat -an              # 连接状态
```

## 第十一章：生产级最佳实践

1. **TLS 必备**：HTTPS 不是 optional；用 Let's Encrypt 免费。
2. **启用 HTTP/2**：现代 server 默认开（前提 TLS）。
3. **keep-alive 必开**：避免反复 TCP 建连。
4. **DNS TTL 因变化频率选**：CDN 入口短，记录稳定的长。
5. **资源用 CDN**：静态资源离用户近 = 快。
6. **IPv6 双栈**：尤其面向移动用户。
7. **Health check 用 TCP/HTTP**：不要 ping（不准）。
8. **超时和重试链路全设**：DNS 1s、TCP 5s、HTTP 30s 等。
9. **大文件 chunked 或分片**：不阻塞内存。
10. **抓包能力**：每个工程师会用 tcpdump 或 wireshark。

## 第十二章：常见陷阱清单

### ❌ 陷阱 1：DNS 不缓存
每个请求都重解析 → 慢。本地或 SDK 层加 cache。

### ❌ 陷阱 2：忽视 TIME_WAIT
高 QPS 短连接 → 端口耗尽。改长连接或调内核参数。

### ❌ 陷阱 3：MTU 错配
容器/隧道下默认 1500 但实际可能 1450 → 包丢、性能差。

### ❌ 陷阱 4：以为 HTTP/2 解决一切
TCP 层 head-of-line 仍存在；高丢包率下 HTTP/3 更优。

### ❌ 陷阱 5：DNS 改了立刻生效
TTL 没过 → 部分用户仍走旧 IP。

### ❌ 陷阱 6：客户端不验证证书
"忽略 TLS"绕开调试问题 → 中间人攻击门户大开。

### ❌ 陷阱 7：用 `0.0.0.0` 监听暴露公网
本应只内网监听。`127.0.0.1` 限本机；`0.0.0.0` 监听所有接口。

## 参考答案

**练习 1**：
1. DNS 解析 example.com → IP
2. TCP 三次握手到 IP:443
3. TLS 握手协商密钥与证书验证
4. HTTP/2 GET / 请求
5. 服务器返回 HTML
6. 解析 HTML，并发请求 CSS/JS/图片
7. 浏览器渲染

**练习 2**：理论上 3600 秒后全球生效。实际：客户端 OS、resolver、应用各自缓存可能不严格遵守 TTL，可能数小时仍有少数请求走旧 IP。**关键 cutover 前几天就降 TTL 到 60s**。

**练习 3**：HTTP/2 多个 stream 复用一个 TCP 连接。TCP 保证顺序——丢一个包，后续所有 stream 的包都要等重传完才能交付应用层。HTTP/3 用 UDP+QUIC 让每个 stream 独立解决。

**练习 4**：
- DNS 查询（小包，丢了重发）
- 视频通话（实时 > 完整）
- 游戏（位置同步快过完整）
- DHCP / SNMP / NTP / VoIP / QUIC

**练习 5**：
- 改长连接（HTTP keep-alive、gRPC）
- 加连接池
- 内核：`net.ipv4.tcp_tw_reuse=1`，`net.ipv4.ip_local_port_range` 扩大
- 横向：加 client 实例分担

## 小结

| 知识点 | 关键记忆 |
|---|---|
| OSI/TCP-IP | 分层 + 封装 |
| DNS | 名字 → IP；TTL 决定生效速度 |
| IP | v4 耗尽，必须双栈 |
| TCP | 三次握手；可靠 + 有序；TIME_WAIT 陷阱 |
| UDP | 简单 + 快；应用自己处理可靠性 |
| HTTP/1.1 | 文本；keep-alive；同时多连接 |
| HTTP/2 | 二进制 + 多路复用；TCP 层 HOL |
| HTTP/3 | QUIC/UDP；无 HOL；0-RTT |
| 工具 | dig/traceroute/curl/tcpdump |
