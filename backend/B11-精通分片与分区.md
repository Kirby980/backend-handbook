## 引言：一台机器装不下

```
PostgreSQL 主表 5TB
查询 P99 8 秒
内存 buffer pool 命中率 30%
```

加索引、升硬件，到一定规模都救不了——数据量本身超过单机能力。这时分片（sharding）登场。但分片是工程复杂度最大的决策之一——一旦做了几乎不能回头。本章讲清何时该分、分什么键、跨片 query 处理、resharding 工程化。

---

## 第一章：分区 vs 分片

### 1.1 名词区分

- **Partition（分区）**：单库内把表拆为多个物理子表
- **Shard（分片）**：跨多个独立 DB 实例
- 有时混用

技术上分区在单机内还有事务支持；分片跨机器一般失去 ACID 跨片保证。

### 1.2 何时需要

判定信号：
- 单表 > 1TB 或 > 10 亿行
- 写入 QPS > 单机上限
- 内存 buffer pool 装不下热数据
- 单库 backup / migration / DDL 超时

如果都不是 → **不要分片**。分片复杂度极高，先穷尽优化（索引、缓存、读副本、归档）。

## 第二章：分区策略

### 2.1 Range Partition

按值范围：
```sql
-- PostgreSQL
CREATE TABLE events (id BIGSERIAL, ts TIMESTAMP, ...)
PARTITION BY RANGE (ts);

CREATE TABLE events_2026_01 PARTITION OF events
FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

CREATE TABLE events_2026_02 PARTITION OF events
FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

适合时间序列。老分区可直接 DROP 归档。

### 2.2 List Partition

按枚举值：
```sql
PARTITION BY LIST (region);
CREATE TABLE users_us PARTITION OF users FOR VALUES IN ('US');
CREATE TABLE users_eu PARTITION OF users FOR VALUES IN ('EU', 'UK');
```

适合多租户、按区域。

### 2.3 Hash Partition

按哈希：
```sql
PARTITION BY HASH (user_id);
CREATE TABLE users_0 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE users_1 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 1);
...
```

均匀分布，但跨多分区查询慢。

### 2.4 优势

- query planner 自动选 partition（partition pruning）
- 每分区独立 vacuum / index
- DROP partition 比 DELETE 快很多
- 索引按分区独立，更小、更快

## 第三章：分片键

### 3.1 选择标准

**高频查询的"筛选条件"**：让大多数 query 只命中一个分片。

- 电商：`user_id` 或 `tenant_id`
- 社交：`user_id`
- 多租户 SaaS：`tenant_id`
- 时间序列：`timestamp`（range）

### 3.2 反例

- **小的枚举值**（性别、国家 top 5）：分布不均，热点严重
- **频繁更新的字段**：值变了要移动数据
- **不参与查询的字段**：无意义

### 3.3 复合分片键

```
shard_key = (tenant_id, user_id)
```

主分片 by tenant_id（大客户独占），细分 by user_id。

### 3.4 数据倾斜

少数 key 占大多数数据 → 某分片远大于其他。

例：Twitter 名人粉丝爆炸。解法：
- 把 hot key 单独分片（手工调配）
- 加 random suffix 把一个 key 散到多片
- 应用层聚合多片结果

## 第四章：分片方案

### 4.1 Hash 分片

```
shard_id = hash(user_id) % N
```

均匀分布。问题：**N 改变时数据要重新洗牌**。

### 4.2 Range 分片

```
[0,    1000):    shard_0
[1000, 5000):    shard_1
[5000, 10000):   shard_2
```

适合范围查询（`WHERE user_id BETWEEN 100 AND 500`）。问题：热点（最新 ID 都在一个分片）。

### 4.3 Directory 分片

外部"路由表" `user_id → shard_id`。灵活、可重新分配。代价：每次查询多一跳路由查询；路由表本身高可用复杂。

### 4.4 一致性哈希（consistent hashing）

```
ring 范围 [0, 2^32)
每节点占一段
hash(key) → 顺时针找下一个节点
```

加节点只影响相邻段——而非全部洗牌。配合"虚拟节点"分担热点。Cassandra、Redis Cluster、CDN 都用这思路。

## 第五章：跨片 Query

### 5.1 单片查询（推荐）

```sql
-- 已知 user_id
SELECT * FROM orders WHERE user_id = 42 AND status = 'paid';
```

路由器直接打到 user_id 所在的片——快。

### 5.2 多片 fan-out

```sql
-- 没 user_id 维度的查询
SELECT * FROM orders WHERE status = 'paid' AND created_at > NOW() - INTERVAL '1 day';
```

要打所有 N 个分片合并结果。延迟受最慢分片影响。

```
T_fanout = max(T_shard_1, T_shard_2, ..., T_shard_N) + merge_overhead
```

### 5.3 跨片 JOIN

不能直接 JOIN。要么：
- 应用层做：分别查再 merge
- 把两个表用相同分片键（colocated）
- 反规范化（小表 broadcast 到所有片）

### 5.4 全局唯一 ID

```
auto_increment    ← 不能用（多个分片各自 1, 2, 3...）
UUID              ← 全局唯一但无序
Snowflake (twitter)  ← 时间戳 + 机器 ID + 序列
ULID / UUIDv7     ← 有序 + 唯一
```

Snowflake 算法：

```
| 1 bit sign | 41 bit timestamp | 10 bit machine | 12 bit sequence |
```

每秒 4096 个 ID/机器；41 bit 时间够 69 年。

### 5.5 跨片事务

几乎不可能。如果业务跨片：
- 用 saga（B09）
- 设计 schema 让事务永远在一片内
- 接受最终一致性

## 第六章：Resharding

### 6.1 必然发生

业务增长 → 数据加 → 已分片不够。或者 hot key 出现要拆。

### 6.2 难点

- 大量数据要迁移
- 迁移期间双写或 stop-the-world
- 应用要切新路由

### 6.3 主流方案

**双写 + 反向迁移**：
1. 应用同时写新旧两套
2. 后台 worker 把旧数据迁到新片
3. 读切到新片
4. 旧片下线

**Vitess、Cassandra 内置 resharding**：
- 自动加节点 → 自动分配 token range
- 后台数据流式迁移
- 透明 routing

### 6.4 选 N 时考虑余量

直接选最终需要的分片数 + 留余量。改 N 远比改 schema 难。Cassandra 文档建议从一开始就用足够多虚拟节点（256 / 节点）。

## 第七章：实际产品

### 7.1 PostgreSQL

- 内置分区（PARTITION BY）
- 第三方分片：Citus、Postgres-XL
- Cloud：Aurora、Cloud SQL 不天然支持跨机分片，要应用层

### 7.2 MySQL

- 内置分区
- Vitess（YouTube 开源）：MySQL 上的分片层；ProxySQL 路由
- Cloud：PlanetScale 商业版 Vitess

### 7.3 MongoDB

- 内置 sharding：`sh.shardCollection()`
- mongos 路由
- 自动 balancer

### 7.4 Cassandra

- 天生分布式
- 一致性哈希 + 虚拟节点
- 各节点对等

### 7.5 CockroachDB / TiDB / YugabyteDB

- NewSQL：SQL 接口 + 自动分片 + 跨片事务
- 性能权衡：跨片事务有 Raft 共识开销
- 适合"想要 SQL + 全球分布"的场景

## 第八章：替代方案

分片前先考虑：

### 8.1 垂直分片

按表拆：user 表在 DB A，order 表在 DB B。简单但有上限（一个表撑爆仍要水平分）。

### 8.2 读副本

写主库 + N 个读副本。读 QPS 解决；写不行。

### 8.3 缓存层

Redis 挡 90% 读 → 主库压力锐减。

### 8.4 归档冷数据

只在热表保留 90 天数据；老数据迁到 cold storage（S3 + Athena）。

### 8.5 用列式 DB 做分析

OLTP（PostgreSQL）+ OLAP（ClickHouse / BigQuery）。分析 query 走 OLAP，主库轻松。

## 第九章：生产级最佳实践

1. **能不分片就不分片**：复杂度极高。
2. **选分片键 = 选 hot query 的等值条件**。
3. **预估 N 留足余量**：reshard 成本高。
4. **全局 ID 用 Snowflake 或 UUIDv7**：避免 hotspot。
5. **跨片 JOIN 避免**：colocate 或反规范化。
6. **路由层独立**：Vitess、Citus、ProxySQL。
7. **监控 shard 大小 + QPS 倾斜**：发现 hot key 早。
8. **数据归档先于分片**：先减少存量。
9. **业务设计天然分片友好**：每个 query 都带 user_id / tenant_id。
10. **NewSQL（CockroachDB / TiDB）作为后路**：跨片事务需求高时。

## 第十章：常见陷阱清单

### ❌ 陷阱 1：过早分片
表 100 万行就分片 → 复杂度 vs 收益不划算。

### ❌ 陷阱 2：分片键不在 query
没 user_id 维度查询全部 fan-out → 慢。

### ❌ 陷阱 3：忽略数据倾斜
一个大客户独占 70% 数据 → 单片爆。

### ❌ 陷阱 4：跨片事务幻想
"我用 2PC"——慢、复杂、单点。改 saga 或重新设计。

### ❌ 陷阱 5：AUTO_INCREMENT
跨片冲突。一开始就用全局 ID。

### ❌ 陷阱 6：reshard 时 stop-the-world
数 TB 数据移动要数天。提前规划双写 + 平滑切换。

### ❌ 陷阱 7：路由层单点
所有流量经过一个 proxy → 它挂全挂。HA 部署 + 客户端缓存路由。

## 参考答案

**练习 1**：`user_id`（B2C）或 `tenant_id`（B2B SaaS）。前提：90% query 已知该值。

**练习 2**：所有分片 fan-out。改善：
- 加二级索引（仍要 fan-out，但只返回 ID）
- 用专用时间序列分片（按 created_at range）
- 或者把热点最新订单存 Elasticsearch 做查询

**练习 3**：传统 hash mod N：N 改时所有 key 重新映射。一致性哈希让 key 落在环上 → 加节点只影响相邻 key（约 1/N 数据）。配合虚拟节点（每节点占 256 个虚拟点）让加节点的 1/N 数据分布到原有所有节点（均匀）。

**练习 4**：
- 把粉丝 fanout 改成 fan-in（读时从 followee 拉，而非写时推到 follower）
- hot user 单独分片
- 用专用消息队列异步处理
- 接受最终一致（粉丝不必同时看到）

**练习 5**：单机 PostgreSQL 事务 commit 仅本地 fsync（~1ms）。CockroachDB 跨片事务用 Raft 共识——commit 要 majority 副本确认（典型 3 节点跨 region 几十 ms）。代价换来的是分布式 ACID + 高可用。
