## 引言：不是银弹

```
"我们要拆微服务！"
6 个月后：30 个服务、跨团队 API 协调灾难、分布式事务难题、本地开发起 docker-compose 卡死
```

微服务能解决"大单体"的某些问题，但代价是分布式复杂度。本章讲清何时拆、按什么边界拆、服务发现、API gateway、监控、事务、何时回头合并。

---

## 第一章：单体 vs 微服务

### 1.1 单体

一个代码库、一个二进制、一个 DB。

优点：
- 简单
- 本地开发起 5 秒
- 跨模块函数调用纳秒级
- 事务跨模块仍是 ACID
- 重构容易（IDE 全局重命名）

缺点（"大"的时候）：
- 任意改动重新部署整个
- 团队互踩
- 单一技术栈
- 单点故障

### 1.2 微服务

多服务、独立部署、独立 DB（理想）、通过 API 通信。

优点：
- 独立部署、独立扩展
- 团队边界清晰
- 多技术栈
- 局部故障不影响整体

缺点：
- 分布式系统复杂度
- 网络延迟 + 失败
- 事务跨服务难
- 运维成本高（监控、CI/CD、服务发现）
- 本地开发难（30 个服务起不来）

### 1.3 哪个先

**默认单体**。规模到了再拆。Martin Fowler 的 "monolith first" 原则。

拆分信号：
- 团队 > 5 个
- 部署频率冲突（A 想发 100 次/天，B 谨慎月发）
- 子系统资源需求差异大（A 内存敏感、B CPU 密集）
- 子系统失败域要隔离

## 第二章：服务边界

### 2.1 按业务能力（推荐）

```
- User Service       用户、认证
- Product Service    产品目录
- Order Service      订单
- Payment Service    支付
- Inventory Service  库存
- Notification Service 通知
```

每服务对应一个**业务领域**。DDD（Domain-Driven Design）的 bounded context。

### 2.2 反例：按技术分层

```
- Web Service
- Business Logic Service
- Data Access Service
```

每请求要跨 3 个服务 → 延迟翻倍、可用性下降、改一处要改三处。

### 2.3 一个服务的合理规模

经验：**两披萨团队**（5-8 人）能独立负责。

判定：
- 一个服务一周能从 0 重写
- 单服务代码 < 几万行
- 单 service repo 单 CI 跑完 < 10 分钟

### 2.4 数据所有权

每服务**独占自己的数据**——其他服务通过 API 访问，不直连 DB。

```
❌ Order Service 直接 SELECT * FROM users
✅ Order Service 调 User Service API
```

否则 schema 变更要协调 N 个服务 = 单体。

## 第三章：服务间通信

### 3.1 同步：REST / gRPC

```
service A --HTTP--> service B
```

优点：直观、易调试。
缺点：B 慢则 A 卡；B 挂则 A 失败。

### 3.2 异步：消息队列

```
service A --publish event--> Kafka --consume--> service B
```

优点：解耦、削峰。
缺点：最终一致；调试复杂。

### 3.3 混合策略

- 用户面 query → 同步（用户等响应）
- 业务事件 / 后续处理 → 异步（不阻塞）

例：下单 API 同步返回订单 ID；扣库存、发邮件、记账 → 异步。

### 3.4 服务间 ID 引用

不要互相借用对方 entity：

```
❌ Order { user: User }   // 通过 API 拉整个 user 对象
✅ Order { user_id: string }  // 只存 ID；需要 user 详情时再调
```

## 第四章：服务发现

### 4.1 静态配置

```
USER_SERVICE_URL=http://10.0.0.42:8080
```

简单但脆——IP 变就要改配置。

### 4.2 DNS

```
USER_SERVICE_URL=http://user-service.svc.cluster.local
```

K8s 中 Service 自动配 DNS。同时 LB。

### 4.3 服务注册中心

- Consul、Etcd、Zookeeper
- 服务启动注册自己 → client 查询拿到列表
- 心跳检测健康

### 4.4 Service Mesh

Istio、Linkerd 等 sidecar 模式：

```
app → sidecar → 网络 → sidecar → app
```

sidecar 负责服务发现 + 负载均衡 + mTLS + 熔断 + 重试 + observability。应用无感知。

代价：复杂部署、额外延迟、运维负担。

### 4.4 sidecar 之后：Ambient Mesh & eBPF（2026 主流走向）

经典 sidecar 模型问题：每 pod 一个 Envoy → CPU/内存翻倍、启动竞态、版本升级要重启所有 pod、p99 延迟有 IPC 开销。

**Istio Ambient Mesh**（2024-11 GA in v1.24）把数据平面拆两层：

- **L4 节点代理 ztunnel**：每节点一个 DaemonSet，负责 mTLS + L4 路由。**所有 pod 自动入网格，零 sidecar**。
- **L7 命名空间代理 waypoint**：仅在需要 L7 特性（重试、HTTP 路由、policy）的 namespace 部署 Envoy waypoint。按需付费式。

**实测收益**（来自 Istio 官方与 Solo.io 客户）：

- pod 数量减少 40-50%（不再一对一 sidecar）
- 启动 / 重启时无 sidecar 竞态
- p99 略降（少一次本地 IPC）
- 升级控制平面无需重启业务 pod

**eBPF / Cilium 路线**：

- Cilium **Service Mesh**（无 sidecar）走 eBPF + Envoy
- Cilium **CNI** 取代 kube-proxy 的 iptables（百万规则可扩展）
- **Cilium Gateway API** 实现取代 Ingress Nginx
- 可观测性：**Hubble** + Tetragon（运行时安全）

**K8s Gateway API**（v1.0 GA，2023-10）：

- Ingress 的下一代，**已 GA**
- 角色清晰分层：Gateway（运维）vs HTTPRoute（开发）
- 原生支持 method / header / weight 路由，不再依赖 vendor annotation
- 实现：Istio、Cilium、Envoy Gateway、Kong、HAProxy、Contour 都已 conformant
- **2026 新建集群应直接用 Gateway API**，老 Ingress 可继续用但新 feature 都在 Gateway API

> 参考：[Istio Ambient GA 公告](https://istio.io/latest/blog/2024/ambient-reaches-ga/)、[Cilium Service Mesh](https://cilium.io/use-cases/service-mesh/)、[Kubernetes Gateway API](https://gateway-api.sigs.k8s.io/)。

## 第五章：API Gateway

### 5.1 角色

```
        Client
          ↓
       API Gateway
       /    |    \
      A     B     C
```

统一入口处理：
- 认证
- 限流
- 路由
- 协议转换（gRPC ↔ REST、版本兼容）
- 监控统一
- TLS 终止

### 5.2 产品

- **Kong**、**Tyk**：开源
- **AWS API Gateway**、**GCP API Gateway**：托管
- **Envoy + control plane**：自己 build
- **Apollo Router**（GraphQL 联邦）

### 5.3 Backend for Frontend (BFF)

不同前端（web、iOS、Android）不同需求 → 每前端自己的 gateway。聚合下游服务的数据，按需返回。

### 5.4 gateway 反模式

把业务逻辑塞 gateway → gateway 变胖、跨团队修改。Gateway 保持薄。

## 第六章：分布式事务

### 6.1 跨服务事务难

```
1. order service 创建订单
2. payment service 扣款（失败）
3. 怎么"撤销"步骤 1？
```

ACID 不再适用。

### 6.2 Saga

每步本地事务 + 补偿。详见 B09 / B17。

### 6.3 Outbox 模式

业务变更 + 事件发布原子。详见 B09。

### 6.4 设计避免跨服务事务

**Aggregate design**：把强一致需求放同一服务/同一 DB。
**Eventual consistency**：用户接受短暂不一致（订单状态 1 秒后变 paid 而不是即时）。

## 第七章：失败处理

### 7.1 假设失败必然发生

每次调用都会：
- 超时
- 失败
- 部分成功
- 重复

### 7.2 关键模式

- **Timeout**：每调用必设
- **Retry**：仅幂等 + 退避
- **Circuit Breaker**：连续失败时熔断
- **Bulkhead**：隔离失败影响域
- **Fallback**：降级响应

详见 B20 韧性模式。

### 7.3 chaos engineering

故意注入故障（杀 pod、注入延迟、断网）测试系统韧性。Netflix Chaos Monkey 是经典。

## 第八章：版本与演进

### 8.1 服务版本

每服务独立版本，每 API 独立版本。一个服务能同时跑多 API 版本（路径前缀 `/v1/`、`/v2/`）。

### 8.2 兼容性

新版 API 必须**向后兼容**旧 client（一段时间）。否则要协调所有 client 同时升级——单体的劣势重现。

非破坏性变更：加可选字段、加 endpoint。
破坏性变更：删字段、改类型 → 新 endpoint / 新版本。

### 8.3 消费者驱动契约

Pact 等工具让 consumer 写"我期待 producer 提供什么" → producer CI 验证不破坏。

### 8.4 schema registry

protobuf / avro 配合 schema registry → CI 检测破坏性变更阻塞。

## 第九章：本地开发

### 9.1 起 N 个服务的痛苦

30 个服务 + docker-compose 起 → 笔记本撑不住。

### 9.2 方案

**A. Mock 上下游**
本地仅运行你改的服务，mock 上游和下游。

**B. 共享 staging 环境**
你的服务连共享 staging 的其他服务。但多人同时改同一服务时冲突。

**C. Telepresence**
本地服务"代理"K8s 集群里的位置——其他流量走 K8s，你这服务走本地。

**D. Skaffold / Tilt**
针对开发优化的 K8s 工具，监听文件变化快速热更新。

## 第十章：可观测性

详见 B24。微服务下：

- **分布式追踪**必备（一个用户请求跨 10 服务）
- **结构化日志 + traceID**
- **每服务独立 dashboard + 整体大盘**

trace 是微服务调试的命脉。没 trace 等于黑盒。

## 第十一章：何时拆 / 何时合

### 11.1 拆

- 团队 > 8 人 + 不同方向
- 部署节奏冲突
- 子系统 SLA / 扩展需求差异大
- 失败要隔离

### 11.2 合并

- 团队 < 5 人
- 服务边界划得太细（几个 service 总一起改）
- 跨服务事务太多
- 分布式复杂度超过收益

**有勇气把过度拆分的服务合并回去**——这不是失败，是工程成熟。

### 11.3 真实案例

- Segment：曾把所有事件处理拆 N 个微服务，后来合并回大单体（performance + 运维痛）
- Amazon Prime Video：一篇博客讲他们把流媒体监控从分布式 lambda 改回单体节省 90%

## 第十二章：生产级最佳实践

1. **monolith first**：先单体，证明业务，再拆。
2. **按业务能力拆**：DDD bounded context。
3. **每服务独占 DB**：API 是唯一边界。
4. **同步 + 异步混合**：用户面同步，事件异步。
5. **服务网格 mTLS**：内部默认加密。
6. **API gateway 单一入口**：统一认证 / 限流 / 监控。
7. **分布式追踪从 day 1**：OpenTelemetry。
8. **schema 契约 + CI 检测**。
9. **每服务独立 CI/CD**：独立部署是核心好处。
10. **chaos engineering 演练**：故障下行为可预测。

## 第十三章：常见陷阱清单

### ❌ 陷阱 1：分布式单体
N 个服务但部署必须一起、强同步调用 → 拥有所有微服务缺点没好处。

### ❌ 陷阱 2：DB 共享
多服务直连同一 DB → schema 变化协调灾难。

### ❌ 陷阱 3：N+1 RPC
service A 循环调 service B → 性能崩。改批量 endpoint。

### ❌ 陷阱 4：分布式事务用 2PC
慢 + 复杂 + 单点。改 saga。

### ❌ 陷阱 5：拆得太细
"function-as-a-service"风格 → 调用链 50+ 跳。

### ❌ 陷阱 6：版本兼容性忽视
单方升级破坏所有下游。schema 检测必备。

### ❌ 陷阱 7：缺乏 trace
出问题不知哪个服务慢。每个微服务项目首要装 OTel。

## 第十四章：练习题

**练习 1**：电商系统按业务能力拆服务，给出至少 5 个服务名 + 各自职责。

**练习 2**：用户下单要更新 order + 扣库存 + 扣余额。同步还是异步？

**练习 3**：解释为什么"每服务独占 DB"重要。

**练习 4**：何时该把两个微服务合并回单服务？

**练习 5**：API gateway 应该做什么、不应该做什么？

## 参考答案

**练习 1**：
- **User**：用户信息、登录、权限
- **Catalog**：商品目录、搜索
- **Cart**：购物车
- **Order**：订单生命周期
- **Payment**：支付与对账
- **Inventory**：库存
- **Shipping**：物流
- **Notification**：邮件 / 短信 / push

每服务有自己 DB、独立部署、API 通信。

**练习 2**：混合：
- 同步：order 创建（用户等响应）
- 异步：发出 `OrderCreated` 事件 → inventory / payment / notification 分别消费处理
- 一致性：用 Saga 编排；失败补偿

**练习 3**：原因：
- schema 变化各服务独立——不需跨团队协调
- 数据访问 = API 边界（强制契约）
- 服务故障域隔离（DB 挂只影响一个服务）
- 各服务选最合适的 DB（user 用 PG、产品搜索用 ES、订单用 PG）

**练习 4**：
- 团队规模缩小（5 人维护 5 个服务）
- 两服务总一起改（边界划错）
- 跨它们的事务太多（强一致需求高）
- 性能损失大（频繁 RPC）
- 部署复杂度 > 业务收益

**练习 5**：
**应该**：
- TLS 终止
- 认证 / token 验证
- 限流
- 路由
- 监控 / log 聚合
- 简单聚合（fan-in 多服务响应）

**不应该**：
- 业务逻辑
- DB 访问
- 复杂数据转换（除简单 protocol 桥接）
- 状态管理

## 小结

| 知识点 | 关键记忆 |
|---|---|
| 何时拆 | 团队多 + 部署冲突 + 失败隔离需求 |
| 边界 | 按业务能力（DDD） |
| 数据 | 每服务独占 DB |
| 通信 | 同步 REST/gRPC + 异步 MQ |
| 服务发现 | DNS / 注册中心 / mesh |
| 事务 | Saga / Outbox / 设计避免跨服务 |
| 失败 | timeout + retry + circuit breaker |
| 监控 | 分布式 trace 必备 |
| 反模式 | 分布式单体、共享 DB、过度拆分 |
