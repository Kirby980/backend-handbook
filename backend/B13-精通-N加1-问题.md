## 引言：性能杀手中的第一名

```python
for user in User.objects.all():       # 1 次 query
    print(user.profile.bio)            # 每次 trigger 1 query → N 次
```

100 个 user → 101 次 DB query。每次 5ms → 整页 500ms+。N+1 是后端常见的"沉默的性能 bug"——逻辑正确，看不出错，但慢得离谱。本章把各种 N+1 模式、检测方法、修复方案讲透。

---

## 第一章：N+1 的定义

### 1.1 形态

```
1 次 query 取主集合（N 个项）
N 次 query 取每项的关联数据
合计 N+1 次 query
```

### 1.2 出现场景

- ORM 懒加载（lazy loading）
- 模板 / 视图层渲染时按需取数据
- API 内部循环调用其他 API
- GraphQL 无 dataloader
- 缓存 miss 时未批量回源

### 1.3 影响

```
N = 100, 每 query 5ms (含网络 RTT) → 500ms
N = 1000 → 5 秒
N = 10000 → 50 秒（实际多半超时）
```

不仅慢，还产生大量 DB 连接 / 客户端线程 / 日志条目。

## 第二章：典型场景

### 2.1 ORM 懒加载

**Django**：
```python
for user in User.objects.all():
    print(user.posts.count())   # N 次
```

**Rails**：
```ruby
User.all.each do |u|
  puts u.posts.count
end
```

**SQLAlchemy**：
```python
users = session.query(User).all()
for u in users:
    print(u.profile.bio)   # 默认 lazy → N 次
```

**GORM**：
```go
var users []User
db.Find(&users)
for _, u := range users {
    db.Model(&u).Related(&u.Posts)   // N 次
}
```

### 2.2 模板触发

```
{% for user in users %}
  {{ user.profile.full_name }}    ← 模板里访问 profile 触发 lazy load
{% endfor %}
```

view 层只看见 user 列表；模板暗暗触发 N 次 query。

### 2.3 跨服务 API

```python
def list_orders():
    orders = order_service.list()     # 1 次
    return [
        { **order, "user": user_service.get(order["user_id"]) }   # N 次
        for order in orders
    ]
```

每订单触发一次 user-service 调用。

### 2.4 GraphQL

```graphql
{ users { name posts { title } } }
```

resolver：
```js
User.posts = (user) => db.posts.find({user_id: user.id})   // N 次
```

### 2.5 缓存层

```python
for id in user_ids:
    user = cache.get(f"user:{id}")
    if not user:
        user = db.query(id)    # 缓存 miss → DB
        cache.set(...)
```

冷启动 → N 次 DB 查询。

## 第三章：解决方案

### 3.1 Eager loading（预加载）

ORM 提供"一次性把关联也查回"的方式。

**Django**：
```python
User.objects.prefetch_related('posts').all()   # 2 query
# 或
User.objects.select_related('profile').all()   # JOIN，1 query
```

`select_related` 用 JOIN（one-to-one、many-to-one）；`prefetch_related` 用单独 IN query 再 Python 端组装（many-to-many、one-to-many）。

**Rails**：
```ruby
User.includes(:posts).all
```

**SQLAlchemy**：
```python
session.query(User).options(joinedload(User.profile))
session.query(User).options(selectinload(User.posts))
```

**GORM**：
```go
db.Preload("Posts").Find(&users)
```

### 3.2 手写 batch query

```python
users = User.objects.all()
user_ids = [u.id for u in users]
posts = Post.objects.filter(user_id__in=user_ids)
posts_by_user = defaultdict(list)
for p in posts:
    posts_by_user[p.user_id].append(p)
for u in users:
    u.posts = posts_by_user[u.id]
```

不依赖 ORM 特殊语法，明确两个 query。

### 3.3 JOIN

```sql
SELECT u.*, p.*
FROM users u
LEFT JOIN posts p ON p.user_id = u.id
WHERE u.created_at > NOW() - INTERVAL '7 days';
```

一次 query 返回 user × post 笛卡尔积；应用端按 user_id 分组。但**大量重复 user 字段**——网络 + 解析开销大。一对少（每 user 1-10 post）合适；一对多（1-1000）不行。

### 3.4 DataLoader

GraphQL 主流方案（参考 B06）。也适用于任何"按 key 批量读"的场景：

```js
const userLoader = new DataLoader(async (ids) => {
    const users = await db.users.findByIds(ids);
    return ids.map(id => users.find(u => u.id === id));
});

// 多次 loader.load(id) 在同一 tick 合并为一次批量查询
```

### 3.5 批量缓存

```python
ids = [1, 2, 3, ..., 100]
cached = redis.mget([f"user:{id}" for id in ids])
miss_ids = [id for id, v in zip(ids, cached) if v is None]
if miss_ids:
    miss_users = db.query("SELECT * FROM users WHERE id IN %s", miss_ids)
    redis.mset({f"user:{u.id}": serialize(u) for u in miss_users})
```

mget / mset 批量化所有 cache 操作。

### 3.6 反规范化

```sql
-- 加 user 表 post_count 字段
SELECT id, name, post_count FROM users;   -- 一次 query 拿到一切
```

需要 trigger / 后台 worker 维护字段。参考 B10。

## 第四章：检测

### 4.1 DB query 计数

```python
# Django
from django.db import connection
print(len(connection.queries))   # 看每 request 多少 query
```

```ruby
# Rails 开发 mode logs each query
ActiveRecord::Base.logger = Logger.new(STDOUT)
```

100+ query 渲染一页 → 立刻看到。

### 4.2 ORM-specific 工具

- **Django Debug Toolbar**：显示每页 query 数 + 时间
- **Rails Bullet**：自动检测 N+1 并警告
- **SQLAlchemy zoo**：query event listener
- **Hibernate Statistics**

CI 集成 + 阈值告警。

### 4.3 APM

Datadog、New Relic、Sentry：在 trace 视图看一个 endpoint 产生多少 DB call。span 树直接显示循环模式。

### 4.4 慢查询日志

虽然单 query 快，但累计调用多 → `pg_stat_statements` 看 calls 列：

```sql
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY calls DESC
LIMIT 20;
```

某 query calls 数百万次 → N+1 嫌疑。

## 第五章：变种

### 5.1 N+1+N

```python
for user in users:
    for post in user.posts:
        print(post.comments.count())
```

100 user × 50 post = 5000+ 调用。

修：嵌套 prefetch
```python
User.objects.prefetch_related('posts__comments').all()
```

### 5.2 cache miss N+1

cache hit rate 高 → 看不出问题；冷启动一开 → 突然慢。要 batch loading 或 lock 防雪崩。

### 5.3 RPC N+1

服务 A 循环调服务 B 单个查询。改 B 提供批量 endpoint：

```
GET /users?ids=1,2,3,4,5
```

### 5.4 ETL N+1

数据管道里每行触发 lookup。改预加载全量 lookup map。

## 第六章：何时 N+1 不是问题

### 6.1 N 很小（< 5-10）

每页只显示 5 个项目 → 6 次 query × 2ms = 12ms。不值得优化。

### 6.2 关联数据极冷

99% 用户不展开看 → 不要预加载所有 → 反而浪费。

### 6.3 已在缓存

每个 lookup hit Redis < 1ms → 100 次也仅 100ms。可接受。

但仍**值得监控**——一旦 N 增长或 cache miss 暴涨，立刻爆。

## 第七章：生产级最佳实践

1. **ORM 默认 lazy → 容易 N+1**：习惯性加 prefetch / includes / preload。
2. **CI 检测 query count**：每 endpoint 设阈值。
3. **APM 看 span 树**：直观发现循环 query。
4. **GraphQL 必 DataLoader**：每请求新建。
5. **缓存层 mget / mset 批量化**。
6. **RPC 批量 endpoint**：内部 service 提供 `BatchGet`。
7. **反规范化频繁字段**：post_count 等避免 COUNT(*)。
8. **JOIN vs prefetch 选合适**：少关联用 JOIN；多关联用 prefetch。
9. **N+1 测试**：核心 endpoint 单独覆盖 query count 测试。
10. **教育团队识别模式**：code review 中盯 for loop + db。

## 第八章：常见陷阱清单

### ❌ 陷阱 1：模板内触发懒加载
view 准备了数据但模板访问其他字段触发 N+1。

### ❌ 陷阱 2：API 序列化时
DRF / json marshaller 访问关联字段。要在序列化前 prefetch。

### ❌ 陷阱 3：select_related vs prefetch_related 用错
反过来用 → JOIN 笛卡尔积爆炸 或 prefetch 不需要的关联。

### ❌ 陷阱 4：N+1 fixed 后忘验证
"应该修好了"——必跑测试或看 query log 数。

### ❌ 陷阱 5：批量 endpoint 上限
batch get 100 ID 一次 → 没问题；10000 → SQL `IN` 列表太长。分批。

### ❌ 陷阱 6：缓存 + N+1 双重坑
缓存 hit 时快；miss 时狂打 DB。引入 single-flight 或预热。

### ❌ 陷阱 7：DataLoader 跨请求共享
缓存污染（用户 A 看到 B 的数据）。每请求新建 loader。

## 参考答案

**练习 1**：
反例：
```python
posts = Post.objects.all()[:100]
for p in posts:
    print(p.author.name)   # 100 次 query
```
修：
```python
posts = Post.objects.select_related('author').all()[:100]   # 1 次 JOIN
```

**练习 2**：是。修：
```go
var posts []Post
db.Preload("Author").Find(&posts)
```

**练习 3**：每层用 DataLoader：
```js
{
    User: { orders: (u, _, {l}) => l.ordersByUser.load(u.id) },
    Order: { items: (o, _, {l}) => l.itemsByOrder.load(o.id) },
    OrderItem: { product: (i, _, {l}) => l.productById.load(i.productId) },
}
```
每层一次批量查询，总共 4 次 query。

**练习 4**：
```sql
SELECT u.*, p.*
FROM users u
LEFT JOIN posts p ON p.user_id = u.id
WHERE u.id IN (1,2,...,100);
```
不一定好：
- 每行重复 user 字段（user 100 字段 × 50 post = 大量冗余流量）
- 一对多变笛卡尔积
- 应用端要分组解构

平均每 user 0-10 post 用 JOIN OK；一对多巨大用 prefetch。

**练习 5**：
- 中间件记录每 request 的 query count
- 测试中 assert：`assert query_count(view) < 10`
- 或用 Bullet（Rails）/ nplusone（Django）等自动检测库 + 失败 CI
