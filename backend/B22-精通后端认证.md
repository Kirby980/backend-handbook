## 引言：认证 ≠ 授权

```
Authentication（认证 / authn）：你是谁？
Authorization（授权 / authz）：你能做什么？
```

后端工程师必须分清。本章讲清后端认证的几大主流方案——session、JWT、OAuth 2.0、OIDC、SAML、API key、mTLS——以及它们的适用场景、安全陷阱。

## 第一章：基本流程

### 1.1 注册 / 登录 / 持久会话

```
1. 注册：用户提交 username + password
2. 后端 hash 密码存 DB（bcrypt）
3. 登录：验证密码 → 颁发 "凭据"
4. 后续请求带凭据 → 后端验证
5. 退出：使凭据失效
```

"凭据"形式是本章核心区别。

### 1.2 密码存储——基础铁律

**永远不要明文存密码**。永远 hash + salt：

```python
import bcrypt
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(cost=12))
# 验证
bcrypt.checkpw(input.encode(), hashed)
```

bcrypt / scrypt / argon2id 都是慢 hash，专门防暴力破解。**不要用 MD5、SHA-256 等快 hash**——GPU 几秒破解。

## 第二章：Session-based Auth

### 2.1 流程

```
1. 登录验证 → 生成 random session ID（如 64 字节）
2. server 把 session ID + user 信息存 Redis/DB
3. 返回 Set-Cookie: session=ID
4. 后续请求自动带 Cookie
5. server 查 Redis → 拿到 user 信息
6. 退出：删 Redis 记录 + 清 cookie
```

### 2.2 优点

- 简单
- server 完全控制（随时可吊销）
- ID 是 opaque——不含用户信息（即使泄露也只是 session）

### 2.3 缺点

- 每请求查 store（Redis 通常）
- 多服务共享 session store
- 横向扩展时 sticky session 麻烦

### 2.4 Cookie 配置

```
Set-Cookie: session=xyz;
            HttpOnly;            ← JS 不能读（防 XSS 偷）
            Secure;              ← 仅 HTTPS
            SameSite=Lax;        ← 防 CSRF
            Max-Age=86400;
            Path=/
```

### 2.5 CSRF 防护

session cookie 在跨站请求中自动发——攻击者诱导用户访问恶意站点触发 transfer。防御：
- `SameSite=Strict` 或 `Lax`
- CSRF token（form + header）
- 验证 Origin / Referer header

### 2.6 适合场景

- 传统 web app（render HTML 在 server）
- 同域应用
- 中小规模

## 第三章：Token-based Auth (JWT)

### 3.1 JWT 结构

```
header.payload.signature
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsImlhdCI6MTYwMH0.signature
```

Base64-encoded JSON：
```json
header:    {"alg": "HS256", "typ": "JWT"}
payload:   {"sub": "42", "iat": 1600, "exp": 1700, "role": "admin"}
signature: HMAC(base64(header) + "." + base64(payload), secret)
```

### 3.2 流程

```
1. 登录 → server 签发 JWT（包含 user_id、过期等）
2. client 存 token（localStorage / cookie）
3. 后续请求带 Authorization: Bearer <token>
4. server 验证签名 + exp → 信任 payload
5. 不需查 store（无状态）
```

### 3.3 优点

- 无状态——server 无需 session store
- 跨服务传递（微服务里用户身份贯穿）
- 可包含权限信息

### 3.4 缺点

- **不能直接吊销**——签出后到 exp 一直有效
- 大（200-1000 字节）
- 误用安全风险大

### 3.5 算法

- **HS256**：HMAC + 共享 secret（对称）
- **RS256 / ES256**：私钥签名 + 公钥验证（非对称）

微服务用 RS256：发布者持私钥；所有服务用公钥验证（公钥可放 JWKS endpoint）。

### 3.6 JWT 陷阱

**A. `alg: none`**：早期实现接受 "无签名"——攻击者改 payload 不被发现。规范修正，但**库要校验 alg**。

**B. 密钥过弱**：HS256 secret 短或简单 → 离线破解。

**C. 存 localStorage**：XSS 偷走。HttpOnly cookie 更好。

**D. 没过期**：终身有效 → 泄漏永远有效。设短 exp（5-60 分钟）+ refresh token。

**E. 信任未签名 payload**：忘了 verify 直接 decode。

### 3.7 何时 JWT 何时 Session

- **JWT**：API、SPA、移动 app、跨服务 / 跨域
- **Session**：单 domain web app、需要即时吊销

混合：access token (JWT, 15min) + refresh token (opaque, store DB, 7 day)。refresh token 可吊销。

## 第四章：Refresh Token 模式

### 4.1 双 token

```
登录:
  access_token  = JWT (15 min)
  refresh_token = random opaque (7 day, 存 DB)

15min 后:
  client → POST /token/refresh + refresh_token
  server → 新 access_token + (可能新 refresh_token)
```

### 4.2 旋转 refresh token

每次 refresh 发新的 + 作废旧的。检测 reuse：若旧 token 再次出现 → 视为被盗用，撤销整个 session 链。

## 第五章：OAuth 2.0

### 5.1 解决的问题

**第三方访问用户数据，但不交出密码**。

例：让 Spotify 读取你的 Twitter（不需告诉 Spotify Twitter 密码）。

### 5.2 四个角色

- **Resource Owner**：用户
- **Client**：第三方 app（Spotify）
- **Authorization Server**：颁发 token（Twitter 的 auth server）
- **Resource Server**：拥有数据的 server（Twitter API）

### 5.3 Authorization Code Flow（最常用）

```
1. Client → 重定向用户到 Twitter 授权页
2. 用户登录 + 同意
3. Twitter → 重定向回 Client 的 callback URL + 带 code
4. Client → 用 code + client_secret 换 token（后端 to 后端）
5. Client → 用 token 调 Twitter API
```

`client_secret` 不暴露到浏览器——所以需要后端。

### 5.4 PKCE（Proof Key for Code Exchange）

公开 client（SPA、移动 app）没有 server 存 client_secret。PKCE 替代：

```
1. Client 生成 code_verifier (随机)
2. code_challenge = SHA256(code_verifier)
3. Auth request 携带 code_challenge
4. 换 token 时携带 code_verifier
5. Auth server 比对 hash 匹配才发 token
```

防中间人偷 code 后换 token。**所有 OAuth 2.0 公开 client 必须用 PKCE**。

### 5.5 其他 flow

- **Client Credentials**：服务到服务，无用户参与
- **Resource Owner Password**：用户给 client 密码（已废弃，仅遗留）
- **Implicit**：浏览器直接拿 token（已废弃，安全问题多）
- **Device Code**：电视、IoT 等无键盘设备

### 5.6 OAuth 2.1 —— 把"最佳实践"变成"必须"

**OAuth 2.1**（IETF 草案，2026 初稳定，配套 [RFC 9700](https://datatracker.ietf.org/doc/rfc9700/) Security BCP 已发布）不是革命，而是把过去十年安全教训正式整合：

| 变化 | 含义 |
|---|---|
| **PKCE 强制**（不只是 SPA / mobile，所有 Authorization Code flow 都要） | 防 code interception |
| **Implicit grant 移除** | 浏览器直接拿 token 的旧模式彻底废弃 |
| **Resource Owner Password (ROPC) grant 移除** | 不再允许应用代用户存密码 |
| **Refresh token 必须 rotation 或 sender-constrained** | 一次性使用，或绑定到 client key |
| **Redirect URI 严格匹配** | 不再允许通配符 |

**MCP（Model Context Protocol，Anthropic 2024 提出）等新协议直接以 OAuth 2.1 为基础**——这是新生态的事实标准。

### 5.7 DPoP（RFC 9449）—— 让 token 不再是"无记名支票"

普通 OAuth 2.0 的 access token 是 **bearer token**：谁拿到谁能用，被偷 = 全部权限被偷。DPoP 把 token **绑定到 client 持有的 keypair**：

1. Client 启动时生成 keypair（不用持久化，进程级临时密钥即可）
2. 请求 token 时带一个 DPoP proof JWT（含 `htm`/`htu`/`iat`/`jti`、用 private key 签名）
3. AS 把 token 与 jwk 公钥绑定（jkt thumbprint 写进 access token）
4. 之后**每个 API 请求都要带新的 DPoP proof JWT**，证明"我还有 private key"
5. RS 验证 proof 公钥与 token 内 jkt 匹配

效果：**token 被偷也用不了**——攻击者没有对应的 private key。比 mTLS 简单（不需要证书 PKI），比 bearer 安全。

```
Authorization: DPoP eyJhbGciOi...   ← access token
DPoP: eyJhbGciOiJFUzI1NiIsImp3ay...  ← per-request proof JWT
```

银行 / 开放银行 / 健康数据 API 已经普遍要求 DPoP（FAPI 2.0 把它列为可选 sender-constraining 机制之一，与 mTLS 并列）。

> 参考：[RFC 9449 OAuth 2.0 DPoP](https://www.rfc-editor.org/rfc/rfc9449.html)、[OAuth 2.1 draft](https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/)、[RFC 9700 OAuth Security BCP](https://datatracker.ietf.org/doc/rfc9700/)。

### 5.6 token 类型

- **access token**：调 API
- **refresh token**：换新 access token
- **id token**（OIDC）：用户身份信息

### 5.7 scope

```
?scope=read:profile write:tweets
```

权限粒度。用户授权时可见 client 申请的范围。

## 第六章：OpenID Connect (OIDC)

### 6.1 OAuth 2.0 的扩展

OAuth 2.0 是**授权协议**，OIDC 是基于它的**认证协议**。

OIDC 在 OAuth 2.0 上加：
- **id_token**：JWT 含用户身份
- **userinfo endpoint**：拿用户信息
- 标准化 scope（openid、profile、email）

### 6.2 流程

```
1. Client → 重定向到 Authorization Server (含 scope=openid)
2. 用户登录
3. 回调 + code
4. Client 换 token：拿到 access_token + id_token
5. 解码 id_token → 拿到 user_id / email / name
```

id_token 是 JWT，可本地验证。

### 6.3 SSO

Google / GitHub / Microsoft 都是 OIDC provider。Client app 信任 Google 的 id_token → 用户用 Google 账号登录任何 app。

## 第七章：API Key

### 7.1 简单

```
Authorization: Bearer sk_live_abc123
# 或
X-API-Key: abc123
```

server 查 DB → 找到对应 user / app。

### 7.2 用途

- 服务到服务调用
- B2B API
- 测试 / dev

### 7.3 安全

- **永不暴露前端**（除非显式公开 key）
- **定期 rotate**
- **不同环境不同 key**
- **每 key 限定权限 + 限流**

## 第八章：mTLS

### 8.1 双向 TLS

详见 B03。服务端验证客户端证书 → 不需要密码 / token。

### 8.2 适合

- 内部微服务
- 高安全 API（金融、医疗）

### 8.3 与 OAuth 配合

mTLS 确认机器身份；OAuth 确认用户身份。同时用——双重保护。

## 第九章：SAML

### 9.1 企业 SSO

XML-based，older than OIDC。仍在企业广泛使用：
- Okta、Azure AD、ADFS
- IT 团队习惯

### 9.2 流程

```
1. 用户访问 SP（Service Provider）
2. SP 重定向到 IdP（Identity Provider）
3. 用户在 IdP 登录
4. IdP 返回 SAML Assertion（XML 签名）
5. SP 验证签名 → 信任用户身份
```

### 9.3 vs OIDC

- SAML：XML、企业、SOAP 时代遗产
- OIDC：JSON、现代 web/移动 first

新项目用 OIDC；对接企业客户可能仍要 SAML。

## 第十章：多因素认证（MFA）

### 10.1 因素

- **knowledge**：密码、PIN
- **possession**：手机、硬件 key
- **inherence**：指纹、人脸

### 10.2 实现

**TOTP**（time-based one-time password）：Google Authenticator 等。RFC 6238。
**SMS OTP**：发短信。**不推荐**——SIM swap 攻击。
**WebAuthn / FIDO2**：硬件 key（YubiKey）/ 平台认证（Touch ID）。最安全。
**Push notification**：app 弹通知点确认。

### 10.3 Passkeys —— 2025 年走向主流的密码替代品

> **2026 年新建消费级产品的认证方案，应该把 passkey 作为 primary 路径，密码作为 fallback。**

**Passkey** 是建立在 **WebAuthn (W3C) + CTAP (FIDO Alliance) = FIDO2** 协议栈之上的一种 credential。和"硬件 YubiKey"不同，passkey 是**可同步、可跨设备使用**的：

- 苹果通过 iCloud Keychain 在用户的 Apple 设备间端到端加密同步
- Google 通过 Google Password Manager 在 Android / Chrome 间同步
- Microsoft 通过 Authenticator 在 Windows / 跨设备同步
- 1Password / Dashlane / Bitwarden 等也实现了独立的同步

**对后端的影响：你的认证 endpoint 多了一组 WebAuthn registration / assertion 路径**：

```
POST /webauthn/register/options    → 返回 challenge + RP info
POST /webauthn/register/verify     → 验证 attestation，存 credential ID + public key
POST /webauthn/login/options       → 返回 challenge + allowed credential IDs
POST /webauthn/login/verify        → 验证 assertion 签名，对 challenge + counter
```

**关键存储项**（每个 user 可能多个）：

| 字段 | 用途 |
|---|---|
| `credentialID` | 客户端登录时回传的句柄 |
| `publicKey` | COSE 编码的公钥，用于验证签名 |
| `signCount` | 防回放（同步 passkey 可能始终为 0，要按文档判断） |
| `transports` | usb / nfc / ble / internal / hybrid，UI 提示用 |
| `aaguid` | 创建该 passkey 的 authenticator 标识，用于风控 / 报表 |

**2025-2026 关键事实**：

- 全球 passkey 累计 **5 亿个**；69% 的用户至少有一个 passkey
- Top 100 网站中 **48%** 已支持 passkey
- 企业部署率约 **87%**
- 监管推动：NIST SP 800-63-4（2025-07）正式承认 syncable passkey 达到 AAL2；UAE 央行要求 2026-03 前所有银行**全面取消 SMS / email OTP**
- 实测：Google 上 passkey 登录成功率 **93% vs 密码 63%**；TikTok 报 **97%** passkey 成功率

**实现库**：

- **服务端 Go**：[`github.com/go-webauthn/webauthn`](https://github.com/go-webauthn/webauthn)
- **服务端 Node**：[`@simplewebauthn/server`](https://simplewebauthn.dev/)
- **服务端 Python**：[`webauthn`](https://github.com/duo-labs/py_webauthn)
- **托管方案**：Auth0、Hanko、Stytch、Authsignal 都有 passkey-first SDK

**陷阱清单**：

1. **同步 passkey 的 `signCount` 始终是 0**——别把它当唯一防回放手段，应同时检查 challenge 一次性与时间窗。
2. **跨平台的"hybrid transport"**（手机扫桌面 QR 登录）需要前端正确处理；Chrome / Safari 的具体行为差异要测。
3. **passkey 创建后不能"导出私钥"**——如果用户全部设备丢失要有 recovery 流程（备份码、邮件回收链接、客服 KYC）。
4. **企业账号 + 设备绑定**场景：选 attested device-bound passkey（不可同步的硬件 passkey），别选 syncable。

> 参考：[FIDO Alliance Passkeys](https://fidoalliance.org/passkeys/)、[WebAuthn Level 3 W3C 规范](https://www.w3.org/TR/webauthn-3/)、[passkeys.dev](https://passkeys.dev/)。

### 10.4 实现 TOTP

```python
import pyotp
secret = pyotp.random_base32()
totp = pyotp.TOTP(secret)
print(totp.now())   # 6 位数字，30 秒变一次
print(totp.verify("123456"))
```

存 secret 与 user 关联；验证时比对。

## 第十一章：典型架构

### 11.1 SPA + API

```
浏览器 (React) → API
- 登录: POST /login → 返回 JWT
- 后续: Authorization: Bearer <jwt>
- token 存 HttpOnly cookie 或内存（避 localStorage）
- refresh token 路径 /refresh
```

### 11.2 微服务

```
Gateway (验证 JWT) → service A, B, C (信任 user_id header)
```

Gateway 集中验证。服务内部通过 mTLS + propagated user_id。

### 11.3 移动 app

```
App → /oauth/authorize (PKCE) → backend
拿到 token 后存系统 keychain
后续 API 调用带 token
```

### 11.4 第三方接入（你提供 OAuth）

```
你是 GitHub 角色
其他 app 调你的 /oauth/authorize → 用户授权 → 回调
其他 app 拿 token → 调你的 API
```

实现 OAuth 2.0 server 复杂——优先用 Auth0、Keycloak、Ory、Okta。

## 第十二章：生产级最佳实践

1. **密码用 bcrypt/argon2id**：never MD5 / SHA。
2. **HTTPS 全程**：HSTS preload。
3. **Cookie HttpOnly + Secure + SameSite**。
4. **JWT 短 exp + refresh token**：15min + 7d。
5. **JWT 验签必检 alg**：不允许 `none`。
6. **公开 client 用 PKCE**。
7. **MFA 高价值账户**：TOTP / WebAuthn。
8. **限流 + lockout**：登录失败多次锁账户。
9. **不自己实现 OAuth server**：用 Auth0 / Keycloak / Ory。
10. **日志认证事件**：登录、失败、refresh、退出。

## 第十三章：常见陷阱清单

### ❌ 陷阱 1：密码明文 / 弱 hash
立即修：bcrypt + cost ≥ 12。

### ❌ 陷阱 2：JWT in localStorage + XSS
XSS 偷走全部。HttpOnly cookie。

### ❌ 陷阱 3：JWT alg=none 接受
让任何人伪造 token。必须 reject。

### ❌ 陷阱 4：忘了 token 过期
泄漏永久。短 exp + refresh。

### ❌ 陷阱 5：refresh token 不旋转
被盗后无限刷新。每次换新 + 检测重用。

### ❌ 陷阱 6：OAuth state 参数缺失
CSRF 风险。state 是随机值，回调验证。

### ❌ 陷阱 7：SMS MFA
SIM swap 攻击。用 TOTP / WebAuthn。

## 参考答案

**练习 1**：JWT 是无状态的——server 仅验签 + exp。一旦签出，到 exp 前永远有效。即使用户退出、改密码也有效。
解决：
- 短 exp（5-15 min）+ refresh token（可吊销）
- 维护 token 黑名单（部分丧失无状态优势）
- jti 在 token 中 → revoke list 记录被吊销的 jti
- 用户改密码时旋转 server signing key（全部 token 失效，过激）

**练习 2**：
```
verifier = random_string(43)
challenge = base64url(sha256(verifier))

# 1. 跳转授权
redirect to /authorize?
  client_id=...&
  redirect_uri=...&
  response_type=code&
  code_challenge=<challenge>&
  code_challenge_method=S256&
  state=<random>

# 2. 回调拿 code

# 3. 换 token
POST /token
  grant_type=authorization_code
  code=<code>
  code_verifier=<verifier>     ← 这里证明你是 step 1 的人
  client_id=...
  redirect_uri=...

# auth server 算 sha256(code_verifier) 与 step 1 的 challenge 对比
```

**练习 3**：
- **HttpOnly cookie**：安全（XSS 偷不到），但需配合 CSRF 保护
- **内存变量**：刷新页面丢——配合 refresh token
- **不要 localStorage**：JS 可读 = XSS 可偷

推荐：access token 内存 / HttpOnly cookie；refresh token HttpOnly cookie。

**练习 4**：
- OAuth 2.0：授权协议（让 third party 访问我数据）
- OIDC：基于 OAuth 2.0 的认证扩展（确认用户是谁）

OIDC = OAuth 2.0 + id_token + standardized scopes（openid, profile, email）。可以用 OAuth 但不实现 OIDC（仅授权不身份）；OIDC 必包含 OAuth。

**练习 5**：
```python
key = f"login_fail:{username}"
fails = redis.incr(key)
if fails == 1: redis.expire(key, 3600)

if fails > 5:
    raise AccountLocked

# 验证密码
if password_correct:
    redis.delete(key)   # 成功清零
    return token
else:
    return error
```
更严谨：fail 来源 IP + username 组合限制；锁定时间指数增长；通知用户邮箱。

## 小结

| 方案 | 适合 |
|---|---|
| Session | 同域 web app |
| JWT | API、跨服务、SPA |
| OAuth 2.0 | 第三方授权 |
| OIDC | 身份联合（SSO） |
| API Key | 服务到服务 |
| mTLS | 内部服务 + 高安全 |
| SAML | 企业 SSO（老） |

铁律：
- 密码 bcrypt
- HTTPS only
- Cookie HttpOnly + Secure + SameSite
- Token 短 exp + refresh
- MFA 必备高价值账户
