## 引言：处理不过来怎么办

```
请求 QPS：10k/s
服务能力：3k/s
```

剩下 7k/s 怎么办？三种选择：
1. **排队**：buffer 起来 → 队列爆 + 延迟暴涨
2. **拒绝**：超限返 429 → 用户体验差但稳
3. **降速上游**：背压让生产者慢下来

无脑加 buffer 是最差选择。本章讲清限流算法、背压机制、自适应负载控制。

## 第一章：限流算法

### 1.1 Fixed Window

```
1 分钟内最多 100 次
```

```python
key = f"rate:{user}:{minute}"
count = redis.incr(key)
if count == 1: redis.expire(key, 60)
if count > 100: reject
```

简单但有"边界突发"问题：59 秒 100 次 + 1 秒后 100 次 = 1.0 秒内 200 次。

### 1.2 Sliding Window

```python
key = f"rate:{user}"
now = time.time()
redis.zremrangebyscore(key, 0, now - 60)
redis.zadd(key, {req_id: now})
if redis.zcard(key) > 100: reject
```

用 sorted set 记每次请求时间。无边界突发，但 ZSET 内存占用大。

### 1.3 Token Bucket

```
bucket 容量 100
每秒补 10 个 token
请求消耗 1 token
没 token → 拒绝
```

允许 burst（最多 100 个瞬时）+ 平均 10/s。

```go
import "golang.org/x/time/rate"
lim := rate.NewLimiter(10, 100)   // rate=10/s, burst=100
if !lim.Allow() { reject }
```

最常用。

### 1.4 Leaky Bucket

```
bucket 满了请求溢出（拒绝）
bucket 以固定速率漏（处理）
```

平滑输出，但不允许 burst。适合下游对突发敏感的场景（如调外部 API）。

### 1.5 总结

| 算法 | 允许 burst | 实现复杂度 |
|---|---|---|
| Fixed Window | ❌ 边界突发 | 简单 |
| Sliding Window | ✅ | 中 |
| Token Bucket | ✅ | 中 |
| Leaky Bucket | ❌ | 中 |

默认用 Token Bucket。

## 第二章：限流的维度

### 2.1 全局限流

```
全 service 1000 QPS 上限
```

防整体过载。但单个恶意 IP 仍可能用尽配额。

### 2.2 按 API 路径

```
/login   10 QPS
/search  100 QPS
/static  无限
```

按代价或重要性分级。

### 2.3 按用户 / API key

```
免费用户 100 req/h
付费用户 10000 req/h
```

公开 API 标配。

### 2.4 按 IP

```
单 IP 60 req/min
```

防恶意。但 NAT 后多用户共享 IP 误伤。

### 2.5 按 user + action

```
单 user 修改密码 5 次/小时
```

防暴力。

### 2.6 组合

```
单 IP 1000 QPS
单 user 100 QPS
全局 10000 QPS
```

多层叠加。任一超限拒绝。

## 第三章：限流响应

### 3.1 HTTP 429

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1652345700
```

`Retry-After` 告诉 client 多久再来；其他 header 让 client 看到 quota。

### 3.2 信息 header

GitHub API 标准：

```
X-RateLimit-Limit: 5000
X-RateLimit-Remaining: 4990
X-RateLimit-Reset: 1652345700
X-RateLimit-Used: 10
```

client 可主动避免超限。

### 3.3 软 vs 硬

- **硬限**：超过直接拒绝
- **软限**：超过给警告（log、metric）不拒绝

公开 API 通常硬限；内部服务可能软限早预警。

## 第四章：分布式限流

### 4.1 问题

3 个 service 实例，每个限流 100 QPS → 全局变成 300 QPS。

### 4.2 集中限流

每实例打 Redis 共享计数：

```python
key = f"rate:user:{id}"
count = redis.incr(key)
if count == 1: redis.expire(key, 60)
if count > 100: reject
```

代价：每请求多 1 个 Redis 调用。

### 4.3 限流 sidecar

Envoy Rate Limit Service：每 sidecar 把请求转给中心限流服务决策。

### 4.4 全局 limiter 高可用

中心限流服务自己挂 → 全部 reject 或全部允许？fail-open（允许）+ 监控 是常见选择。

### 4.5 客户端节流

client-side rate limit：知道自己配额，主动控制不超。比 server 拒绝更省资源。

## 第五章：背压（Backpressure）

### 5.1 概念

下游说"我处理不过来了"，**上游就该慢下来**——而非继续推数据。

### 5.2 显式背压

**HTTP/2 flow control**：接收方告知发送方"我能再收 N 字节"。
**gRPC streaming**：window 控制。
**Reactive Streams**（Java、Node）：`request(N)` 显式拉模式。

### 5.3 隐式背压

阻塞 channel：

```go
ch := make(chan Job, 10)
// 生产者:
ch <- job   // buffer 满了阻塞
```

生产者被阻塞 = 自动慢下来。

### 5.4 没背压的灾难

- 队列无限 buffer → 内存爆
- 上游不停发 → 下游延迟无穷大
- 没人意识到问题，直到 OOM

### 5.5 限流 vs 背压

- 限流：在入口拒绝
- 背压：在内部传递"慢下来"信号

两者互补：入口限流防外部洪水；内部背压防内部失衡。

## 第六章：队列管理

### 6.1 有界 vs 无界

- 无界：内存爆
- 有界：满了怎么办——丢、阻塞、报错

### 6.2 满时策略

- **Block**：生产者等（背压）
- **Drop oldest**：扔老的（典型 metrics 流）
- **Drop newest**：扔新的
- **Reject**：返回错误给生产者

### 6.3 优先级队列

```
高优先：付费用户、健康检查
中：普通业务
低：批量任务、统计
```

资源紧张时优先服务高优先级。Linkerd、Envoy 支持。

### 6.4 LIFO vs FIFO

- FIFO：公平但老消息高延迟
- LIFO：新消息低延迟（适合可丢弃的状态更新）

## 第七章：自适应并发控制

### 7.1 概念

不硬编码 max_concurrency = 100，而是**根据延迟实时调整**。

### 7.2 算法

- **AIMD**（Additive Increase, Multiplicative Decrease）：成功 +1、失败 ÷2
- **Vegas**：基于 RTT 变化判断
- **Gradient**：监控延迟梯度

### 7.3 实现

```python
class AdaptiveLimiter:
    def __init__(self):
        self.limit = 10
    
    def adjust(self, success_rate, p99_latency):
        if p99_latency > target:
            self.limit = max(1, self.limit // 2)
        elif success_rate > 0.99:
            self.limit += 1
```

Netflix Concurrency Limits 库实现完整。

### 7.4 优点

- 不需手工调参
- 自动适应不同负载 / 硬件
- 服务出问题自动降速

## 第八章：实战场景

### 8.1 API gateway 限流

```yaml
# Kong / Tyk / 自实现
- per ip:     1000/min
- per user:   100/min
- per route:
    /api/expensive: 10/min
    /api/cheap:     1000/min
```

### 8.2 数据库连接池

```
max_connections: 20
queue_timeout: 5s
```

连接满 + 5s 没拿到 → 失败。防止瞬时洪水把 DB 拖死。

### 8.3 消息队列消费者

```
consumer concurrency: 10
prefetch: 100
```

每 consumer 同时处理 10 个；预取 100 条到内存。下游慢时 prefetch 自动暂停（背压）。

### 8.4 调外部 API

```python
lim = rate.NewLimiter(rate.Limit(10), 5)   # 10/s, burst 5
for req in requests:
    lim.Wait(ctx)
    external_api.call(req)
```

防止打爆人家。

## 第九章：监控指标

### 9.1 limiter metric

- **allow / deny rate**
- **current concurrency**
- **wait time**（如果是阻塞模式）
- **queue depth**

### 9.2 SLO 关联

429 / 503 计入"错误率"——但有意拒绝是好事，不是 bug。
区分：业务错（5xx）vs 保护性拒绝（429）。

### 9.3 告警

- deny rate > 5% → 容量不够
- queue depth 增长趋势 → 下游瓶颈
- 自适应 limit 降到底 → 服务病了

## 第十章：生产级最佳实践

1. **入口必限流**：每 API、每用户、每 IP 多层。
2. **429 + Retry-After + X-RateLimit-***：让 client 文明退避。
3. **token bucket 默认**：burst 友好。
4. **有界 buffer + 满时 reject**：永远不要无界队列。
5. **背压传递**：channel 阻塞、HTTP/2 flow control。
6. **client-side limiter**：节省双方资源。
7. **自适应并发**：免调参 + 自动应对。
8. **优先级**：保护核心路径。
9. **chaos test 限流**：故意压测验证。
10. **限流 metric + 告警**：知道发生了什么。

## 第十一章：常见陷阱清单

### ❌ 陷阱 1：无界 queue
"加 buffer 就行"——内存爆 + 延迟无穷。

### ❌ 陷阱 2：限流粒度太粗
全局 1000 QPS → 一个用户能占用 800。按 user 限。

### ❌ 陷阱 3：fail-closed limiter
Redis 挂了 → 所有请求被拒。多数场景 fail-open 更好。

### ❌ 陷阱 4：retry-after 没设
429 但没说何时再来 → client 立刻重试 → 雪上加霜。

### ❌ 陷阱 5：sliding window 用 list
内存爆。用 ZSet 或滚动 hash。

### ❌ 陷阱 6：限流忘了 health check
内部 monitor 调用被限流 → 误判服务挂。豁免内部路径。

### ❌ 陷阱 7：硬编码并发
固定 10 个 worker → 机器升级了仍 10 个；坏天气仍 10 个崩。自适应。

## 参考答案

**练习 1**：
```python
import time, threading
class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate = rate
        self.capacity = capacity
        self.tokens = capacity
        self.last = time.time()
        self.lock = threading.Lock()
    def allow(self):
        with self.lock:
            now = time.time()
            self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
            self.last = now
            if self.tokens >= 1:
                self.tokens -= 1
                return True
            return False
```

**练习 2**：1 分钟窗口在 :59 秒 100 次 OK；:00 秒下个窗口又 100 次。这 2 秒内 200 次——超出名义"100/min"上限。Sliding window 通过移动窗口避免此问题。

**练习 3**：
- 集中限流：所有实例 Redis 共享 counter
- 或：限流 sidecar（Envoy + ratelimit service）
- 或：单个 API gateway 入口限
- 简单版：每实例限 (全局 / 实例数)——但实例数变化时不准

**练习 4**：
- Consumer prefetch 调小（如 10 而非 1000）
- Consumer 单线程处理慢下游
- Consumer 不 ack 直到下游成功 → broker 不 push 新消息（背压）
- 监控 lag，超阈值告警

**练习 5**：
- 读 `Retry-After` header
- 指数退避 + 抖动
- 如果是用户操作 → 提示用户"操作过于频繁，请稍后重试"
- 如果是后台任务 → 进入退避循环
- 不要无限 retry → 失败 N 次进死信
