## 引言：先规范，再选择反规范

规范化（normalization）是关系数据库的奠基理论——Codd 在 1970s 提出。目标：消除冗余、避免异常。但严格规范化的数据库在某些查询场景慢——这时反规范化（denormalization）回头加一些冗余换性能。本章讲清两者的边界、何时该 break the rule。

---

## 第一章：规范化范式

### 1.1 1NF（第一范式）

**每个字段是原子值**——不存数组、不存复合值。

```
反例:
order_id | items
1        | "apple, banana, cherry"   ← ❌

修:
order_items 表
order_id | item_name
1        | apple
1        | banana
1        | cherry
```

### 1.2 2NF（第二范式）

**1NF + 非主键字段完全依赖主键**（不能只依赖主键的一部分）。

```
反例:
(order_id, product_id) | order_date | product_name
组合主键，但 product_name 只依赖 product_id 一部分

修:
order(order_id, order_date)
order_item(order_id, product_id)
product(product_id, product_name)
```

### 1.3 3NF（第三范式）

**2NF + 没有传递依赖**——非主键字段不依赖其他非主键。

```
反例:
employee(emp_id, dept_id, dept_name)
dept_name 依赖 dept_id（不是 emp_id）

修:
employee(emp_id, dept_id)
department(dept_id, dept_name)
```

### 1.4 BCNF（Boyce-Codd）

3NF 的更严格版——所有依赖的左侧必须是超键（candidate key）。

实践中 3NF 已经"够好"；BCNF 偶尔需要拆分得更细。

### 1.5 4NF, 5NF, 6NF

理论上有，实践极少需要。

### 1.6 经验法则

**"主键 → 整行；行内每个字段都依赖且仅依赖主键"** —— 这一句话覆盖 BCNF。

## 第二章：规范化的好处

### 2.1 无冗余

```
反例（非规范化）:
order(id, customer_id, customer_name, customer_email, ...)
```

100 万订单 → customer_name 重复 100 万次。客户改名要更新所有订单——慢、容易漏。

### 2.2 一致性

唯一事实来源——name 只在 customer 表，其他地方 JOIN。

### 2.3 避免异常

- **插入异常**：还没下订单的客户怎么存？
- **更新异常**：改一处漏改另一处
- **删除异常**：删订单意外删了客户信息

## 第三章：反规范化

### 3.1 为什么需要

规范化代价：JOIN 多。每次显示订单要 JOIN customer、product、address、shipping——4 个表 join 在大数据下慢。

反规范化：复制数据到一处，读取无 JOIN。

### 3.2 典型场景

**1. 读频繁、写较少**
```
order(id, customer_id, customer_name_snapshot, ...)
```
order 发生时拷贝 customer_name。即使 customer 改名，老订单仍显示当时名字（这反而是业务需求——审计、对账）。

**2. 聚合预计算**
```
user(id, name, post_count, follower_count, like_count)
```
每次显示用户不必 `COUNT(*)`，直接读字段。

**3. 时间序列汇总**
```
daily_stats(day, user_id, login_count, action_count)
```
每天 cron 把当天数据汇总；查月度仅 30 行。

### 3.3 三种反规范化方式

**A. 字段复制**：customer_name 直接放 order
**B. 派生字段**：full_name = first + last（trigger 维护）
**C. 汇总表**：写两次原表 + 一次汇总

### 3.4 维护策略

- **App 应用层维护**：业务代码同时写两处
- **DB 触发器**：UPDATE customer 时自动更新 order.customer_name_snapshot
- **后台 worker**：异步重算汇总
- **CDC（change data capture）**：监听 binlog，推流更新

## 第四章：何时反规范化

### 4.1 判定信号

- 同一 JOIN query 占 CPU 主导（pprof / explain analyze 看）
- 用户列表加载慢（要 join 太多表）
- 排行榜 / 实时统计需求
- 写少读多的列

### 4.2 不要反规范化时

- 数据频繁变（同步成本超过 JOIN 收益）
- 一致性要求高（医疗、金融账户）
- query 还能优化（加索引、调 schema）
- 表行数小（< 10 万）

### 4.3 渐进式

1. **先规范化**：清晰的数据模型
2. **加索引 + 优化 query**：90% 性能问题解决
3. **缓存层**（Redis、Memcached）：90% 剩下问题解决
4. **才考虑 schema 反规范化**：最后手段

## 第五章：典型反规范化模式

### 5.1 物化视图（Materialized View）

```sql
-- PostgreSQL
CREATE MATERIALIZED VIEW user_stats AS
SELECT user_id, COUNT(*) AS post_count
FROM posts GROUP BY user_id;

REFRESH MATERIALIZED VIEW user_stats;   -- 定期刷新
```

DB 内置反规范化。`CONCURRENTLY` 避免锁。

### 5.2 计数器表

```sql
post_likes(post_id, user_id)         -- 明细
post_stats(post_id, like_count)      -- 计数器

-- INSERT trigger
UPDATE post_stats SET like_count = like_count + 1 WHERE post_id = ?;
```

### 5.3 快照字段

```sql
invoices(
    id,
    customer_id,
    customer_name_at_invoice,     -- 快照
    customer_address_at_invoice,
    ...
)
```

法务 / 合规要求：单据生成时的客户信息不能跟着改。

### 5.4 宽表（wide table）

报表场景一张表上百列。每行一条事实，所有维度直接平铺。OLAP 数据库（ClickHouse、BigQuery）擅长。

### 5.5 时间序列分桶

```sql
metrics_5min(timestamp_bucket, metric, value)
metrics_1hour(timestamp_bucket, metric, value)
metrics_1day(timestamp_bucket, metric, value)
```

按精度分表，查询选最合适粒度。

## 第六章：NoSQL 与"天生反规范"

### 6.1 MongoDB 嵌入文档

```json
{
  "_id": "order_123",
  "customer": {
    "id": "user_42",
    "name": "Alice",
    "address": { ... }
  },
  "items": [
    { "product_id": "p1", "name": "Book", "price": 20 }
  ]
}
```

整个 order + 内嵌客户 + 内嵌商品。读一次拿到全部——无 JOIN。

代价：customer.name 改要更新所有 order 文档；或选择不同步（接受漂移）。

### 6.2 DynamoDB 设计

围绕 access pattern 设计 schema。一个表里多种实体共享（single table design）。极端反规范化但 query 极快。

### 6.3 文档 vs 关系

- 文档（嵌入）：写多读多但**关系简单**、读模式固定
- 关系（规范）：复杂关联、ad-hoc 查询、强一致

不少业务两者结合：MongoDB 存物料、PostgreSQL 存事务。

## 第七章：JSON 字段——折中

### 7.1 PostgreSQL jsonb / MySQL JSON

```sql
CREATE TABLE events (
    id BIGSERIAL,
    type TEXT,
    metadata JSONB
);

INSERT INTO events (type, metadata) VALUES
('click', '{"page": "home", "user_id": 42}');

SELECT * FROM events WHERE metadata->>'user_id' = '42';
```

### 7.2 用处

- 半结构化数据（每个 event 字段不同）
- 频繁变 schema 的字段（演进无成本）
- 灵活的过滤（GIN 索引）

### 7.3 不要滥用

- 关键字段（订单金额、用户 ID）放 JSON 失去类型安全 + 难索引
- 仅 metadata / extension / 自定义字段塞 JSON

## 第八章：生产级最佳实践

1. **先 3NF，再考虑反规范**：90% 业务 3NF 够好。
2. **优化顺序：query → 索引 → 缓存 → schema 反规范**。
3. **反规范有维护成本**：成本 > 收益再做。
4. **快照字段**：审计、合规场景必备。
5. **物化视图代替部分汇总**：DB 内置维护。
6. **JSON 字段限定 metadata**：不要塞业务关键字段。
7. **NoSQL 不是"快"的银弹**：访问模式必须匹配。
8. **聚合表用后台 worker 维护**：避免同步事务延迟。
9. **schema migration 用工具**（Flyway、Liquibase、Atlas）。
10. **每次反规范都文档化**：注释 + ADR 说明为什么。

## 第九章：常见陷阱清单

### ❌ 陷阱 1：过度规范化
20 个表 join 显示一个简单页面。规范化也要适度。

### ❌ 陷阱 2：过早反规范
没 profile 就动 schema → 增加复杂度 + 无明显收益。

### ❌ 陷阱 3：复制字段不同步
反规范字段没有维护机制 → 数据漂移。

### ❌ 陷阱 4：JSON 滥用
所有字段塞 JSON → 失去关系优势 + 索引困难。

### ❌ 陷阱 5：单表设计 NoSQL 不懂
DynamoDB 单表设计需要先想 access pattern；不懂直接套关系思维 → 设计崩坏。

### ❌ 陷阱 6：物化视图忘了刷新
查询历史数据混入 stale 数据。

### ❌ 陷阱 7：嵌入文档过大
MongoDB 文档 16MB 上限；嵌入数千子文档容易踩雷。

## 参考答案

**练习 1**：违反 3NF——dept_name 和 dept_manager 依赖 dept_id 而非 employee.id。修：
```
employee(id, name, dept_id)
department(dept_id, dept_name, dept_manager)
```

**练习 2**：应该。理由：
- 订单是历史事实——客户改名后不应回溯
- 法务/审计需要"开票时的客户名"
- 减少 JOIN
代价：客户改名时不需同步老订单（这就是想要的行为）。

**练习 3**：
- **同步 UPDATE**：每次点赞 `UPDATE post SET like_count = like_count + 1 WHERE id=?`——锁竞争重
- **Redis 计数 + 后台批量回写**：高频累积在 Redis，每分钟刷 DB
- **insert-only + 后台聚合**：写 `post_likes` 明细，物化视图或汇总表定期 refresh
- **CRDT/分片计数器**：极高并发用 sharded counter

**练习 4**：
- 文档结构丰富 + 嵌套
- 访问模式固定（按 id 查整个文档）
- schema 频繁变
- 不需要复杂跨实体 JOIN
- 单条文档 < 16MB

否则关系 DB 更合适。

**练习 5**：反规范化是**在规范化基础上**的优化。先理解规范 → 知道哪里有冗余风险 → 才能选择性引入冗余并有意识维护。盲目反规范 = 数据乱。

## 小结

| 知识点 | 关键记忆 |
|---|---|
| 1NF/2NF/3NF/BCNF | 主键依赖、消除传递 |
| 规范优点 | 无冗余、一致、避免异常 |
| 反规范触发 | 读频繁 + JOIN 慢 + 聚合 |
| 维护方式 | 应用 / 触发器 / 后台 / CDC |
| 物化视图 | DB 内置反规范 |
| 快照字段 | 审计/合规需要历史值 |
| JSON 字段 | 限于半结构化 metadata |
| NoSQL | 天生反规范；要懂 access pattern |
