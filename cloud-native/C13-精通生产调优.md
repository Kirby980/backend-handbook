## 引言：从 10 节点到 1000 节点会撞到什么

```bash
# 10 节点集群——一切看起来都很美好
$ kubectl get nodes | wc -l
10
$ kubectl top nodes
NAME       CPU(cores)   MEMORY(bytes)
node-01    320m         2.3Gi
...
```

10 节点时，你可以把所有 Pod 一股脑塞进 Deployment，DNS 用默认 CoreDNS，PDB 不设，节点上随便起 100 个 Pod，etcd 单实例都跑得欢。然后业务起飞，扩到 100 节点——CoreDNS 开始 timeout、apiserver QPS 飙红、节点拉镜像 30 分钟、滚动升级一打开就有 Pod CrashLoopBackOff。再扩到 1000 节点——etcd watch cache miss、apiserver list 整个 nodes 接口超时、cluster autoscaler 一次扩 200 个节点结果 50 个调度不上。

这是规模化路上每个团队都会撞的墙。**Kubernetes 是个反规模友好的系统**——它的设计假设是"中等规模、强一致、声明式"，每一项都和"千节点+ 高吞吐"有张力。本章把 1000 节点级集群的调优要点一次拆开：节点池、镜像、DNS、控制面、Pod 启动、资源规划、升级、多集群、容量、灾备、混沌。

2026 年 5 月，生产 K8s 的几条事实：

| 维度 | 单集群上限（社区推荐） | 实践常见上限 |
|---|---|---|
| 节点数 | 5000 | 单集群 2000-3000 优雅，4000+ 必须深度调优 |
| Pod 数 | 150000 / 集群、110 / 节点 | 250/节点（big node） |
| 命名空间数 | 10000 | 5000+ 时 list 命名空间已慢 |
| Service 数 | 5000+ | iptables 模式建议 < 5k，IPVS 可上 20k |
| 控制面 etcd | 1 raft cluster | 多集群联邦更现实 |

上限不是"硬墙"，而是"沼泽"——越往后每一项指标都要换更深的调优才能稳。下文按"从下到上"（节点 → 镜像 → 网络 → 控制面 → 工作负载）拆开。

## 第一章：节点池策略——异构集群的基石

### 1.1 为什么要分池

把所有节点丢进同一个池子，10 节点没事；100 节点开始出问题：

- 推理任务（高内存）和 web 服务（低 CPU）抢同一台机器
- spot 实例随时被回收，把 etcd 这种状态服务也卷走
- GPU 节点空跑——CPU 任务被调度上去，GPU 浪费
- 高优先级任务被低优先级任务挤——QoS 不够细

**节点池**（node pool / nodegroup）是 1000 节点起步的第一原则：把节点按"用途"分桶，每桶独立扩缩、独立污点、独立 taint。

### 1.2 典型分池

```yaml
# 生产典型 5-6 个池
节点池：
  - system          # kube-system + 关键 DaemonSet；on-demand；不被业务用
  - general         # web / API 服务；on-demand + spot 混合
  - batch           # 批处理 / Job；纯 spot
  - memory          # Redis / Elasticsearch 等内存型；高 MEM 机型
  - gpu             # ML 推理 / 训练；H100 / A100 / L4
  - infra           # ArgoCD / Vault / Prometheus 等平台组件
```

每池一份 ASG / MIG / VMSS / node group。AKS 叫 nodepool、EKS 叫 nodegroup、GKE 叫 node pool。

### 1.3 Spot + On-Demand 混合

Spot（aws）/ Preemptible（gcp）/ Spot VM（azure）——比 on-demand 便宜 60-90%，但**可能被回收**（aws 通知 2 分钟、gcp 30 秒、azure 30 秒）。

混合原则：

```yaml
# Karpenter NodePool 范例
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["c", "m"]
        - key: karpenter.k8s.aws/instance-cpu
          operator: In
          values: ["4", "8", "16"]
        - key: topology.kubernetes.io/zone
          operator: In
          values: ["us-east-1a", "us-east-1b", "us-east-1c"]
      taints: []
  limits:
    cpu: "1000"
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 30s
```

关键策略：

1. **关键服务（无状态但高 SLA）**：on-demand 占 30-50%，spot 占 50-70%，topologySpreadConstraints 强制跨可用区
2. **批处理 / Job**：100% spot；失败重跑无所谓
3. **数据面 / etcd / Redis Cluster master**：100% on-demand；spot 回收会导致状态丢失
4. **GPU 节点**：尽量 on-demand 或 1y reservation；spot GPU 抢手且回收频繁

### 1.4 Spot 中断处理

aws-node-termination-handler、karpenter 的 disruption controller、gcp 的 node-problem-detector——都做同一件事：

```
1. 监听云厂商 metadata endpoint
2. 收到 2min 中断通知
3. cordon 节点（不再调度）
4. drain 节点（驱逐 Pod，触发 PDB）
5. 等 Pod 在别处启动
6. 节点被云回收
```

```yaml
# aws-node-termination-handler 关键配置
apiVersion: helm.cattle.io/v1
kind: HelmChart
metadata:
  name: aws-node-termination-handler
spec:
  set:
    enableSpotInterruptionDraining: "true"
    enableRebalanceMonitoring: "true"
    enableRebalanceDraining: "true"
    nodeSelector.karpenter.sh/capacity-type: spot
```

**Pod 必须 graceful shutdown**——SIGTERM 后 30s 内退出，PDB 配合 minAvailable 防止同时驱逐过多。

### 1.5 专用节点：GPU / 内存型

GPU 节点用污点隔离：

```yaml
# Node taint（机型层面）
nvidia.com/gpu=present:NoSchedule
```

```yaml
# Pod 声明 toleration + resource request
apiVersion: v1
kind: Pod
metadata:
  name: inference
spec:
  tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule
  containers:
    - name: model
      image: registry/llama:latest
      resources:
        limits:
          nvidia.com/gpu: 1
          memory: 24Gi
```

没声明 `nvidia.com/gpu` 的 Pod 不会被调度到 GPU 节点——GPU 不会被 web 服务白白占着跑。

内存型同理：

```yaml
# Node label
node-role.kubernetes.io/memory-optimized=true

# Pod 用 nodeSelector / nodeAffinity 选过去
spec:
  nodeSelector:
    node-role.kubernetes.io/memory-optimized: "true"
```

### 1.6 污点的三种 effect

| effect | 含义 | 典型场景 |
|---|---|---|
| `NoSchedule` | 新 Pod 不调度上来；已在的不动 | GPU 隔离 |
| `PreferNoSchedule` | 软约束；尽量不调度 | spot 节点优先级 |
| `NoExecute` | 立刻驱逐已在节点上但没声明 toleration 的 Pod | 节点维护 |

`NoExecute` 是危险动作——`kubectl taint node foo node.kubernetes.io/unschedulable:NoExecute` 会立刻驱逐节点上所有 Pod。维护场景搭配 `tolerationSeconds` 给业务时间：

```yaml
tolerations:
  - key: node.kubernetes.io/unschedulable
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 300   # 5 分钟内 ok 留着，超时驱逐
```

### 1.7 Karpenter vs Cluster Autoscaler

2026 年 5 月：

| 维度 | Cluster Autoscaler | Karpenter |
|---|---|---|
| 工作方式 | 调 ASG / MIG 接口扩容 | 直接调云 EC2/VMSS API 起节点 |
| 节点选型 | 预设 ASG 机型 | 按 Pod 需求动态选机型（best-fit） |
| 扩容速度 | 60-120s（要走 ASG） | 20-40s（绕过 ASG） |
| 缩容 | 节点空了就 kill | consolidation 主动合并低利用率节点 |
| 多云 | 支持多家 | 主要 AWS（v1 GA），Azure GA（经 AKS NAP）；GCP 无原生 Karpenter，使用 Cluster Autoscaler / NAP |
| 复杂度 | 简单（成熟 5 年+） | 中等（需理解 NodePool / NodeClaim） |

**2026 年共识**：AWS 上 Karpenter 已成主流，cluster autoscaler 仅在传统多云或对 ASG 严重依赖的项目里继续用。Azure/GCP 上 cluster autoscaler 仍是默认。

## 第二章：镜像优化——别让 Pod 启动卡在 ImagePull

### 2.1 ImagePull 是 Pod 启动的最大瓶颈

```
Pod 创建到 Running 的时间分解（典型）：
- API server 接受 Pod: 50ms
- 调度: 50-500ms
- kubelet 拉镜像: 5s - 10min（看镜像大小 / 网络）
- 启动容器: 1-5s
- readinessProbe 通过: 1-30s
```

**镜像拉取经常占总启动时间的 80%+**。1000 节点集群，每天滚动升级几十次——每次 100MB 镜像 × 1000 节点 = 100GB 流量从仓库下载。除了带宽成本，单节点 30s+ 启动延迟会让滚动升级慢得无法忍受。

### 2.2 image preload：把热镜像预下到所有节点

```yaml
# 用 DaemonSet 在每节点预拉镜像
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: image-preloader
spec:
  selector:
    matchLabels:
      app: image-preloader
  template:
    metadata:
      labels:
        app: image-preloader
    spec:
      tolerations:
        - operator: Exists           # 所有节点都跑
      initContainers:
        - name: pull-app-image
          image: registry.internal/api-server:v1.42.0
          command: ["true"]          # 只拉镜像，不真跑
        - name: pull-sidecar
          image: registry.internal/envoy:v1.30
          command: ["true"]
      containers:
        - name: pause
          image: registry.k8s.io/pause:3.9
          resources:
            requests:
              cpu: 1m
              memory: 8Mi
```

initContainer 完成 → kubelet 把镜像存在节点 / containerd layer cache 里。后续 Pod 拉镜像直接命中本地（containerd `imagePullPolicy: IfNotPresent`）。

更高级的做法：

- **k8s-image-prefetcher / spegel**：用 P2P 在节点间共享镜像层（spegel 用 IPFS + containerd mirror，对热镜像几乎零下载流量）
- **dragonfly2 / kraken**：CNCF / Uber 的 P2P 镜像分发，规模化首选
- **lazy pulling**：containerd snapshotter `stargz` / `nydus`——按需懒加载 layer，大镜像启动快 5-10x

```yaml
# containerd config.toml 启 stargz
version = 2
[plugins."io.containerd.grpc.v1.cri".containerd]
  default_runtime_name = "runc"
  snapshotter = "stargz"

[plugins."io.containerd.snapshotter.v1.stargz"]
  root_path = "/var/lib/containerd-stargz-grpc"
```

把镜像转 estargz 格式后推到仓库，节点首次拉只下载启动需要的 layer——LLM 模型镜像（10GB+）通常能从 5min 缩到 30s。

### 2.3 imagePullSecrets 与 ServiceAccount

```yaml
# 私有仓库认证
apiVersion: v1
kind: Secret
metadata:
  name: regcred
type: kubernetes.io/dockerconfigjson
data:
  .dockerconfigjson: <base64 of ~/.docker/config.json>
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: default
imagePullSecrets:
  - name: regcred
```

把 imagePullSecrets 绑到 namespace 默认 SA → 该 ns 下所有 Pod 自动用这个 secret。**别每个 Pod 写一遍**——容易漏。

ECR / GCR / ACR 的 短期 token：

```yaml
# AWS ECR 用 IRSA + ecr-credential-provider，让 kubelet 自动续期
apiVersion: kubelet.config.k8s.io/v1
kind: CredentialProviderConfig
providers:
  - name: ecr-credential-provider
    matchImages:
      - "*.dkr.ecr.*.amazonaws.com"
    defaultCacheDuration: 12h
    apiVersion: credentialprovider.kubelet.k8s.io/v1
```

kubelet 进程内调 provider 续期 token——比手工管 Secret 优雅得多。

### 2.4 私有 registry mirror

```yaml
# containerd config——镜像走私有 mirror
[plugins."io.containerd.grpc.v1.cri".registry.mirrors."docker.io"]
  endpoint = ["https://registry-mirror.internal", "https://registry-1.docker.io"]

[plugins."io.containerd.grpc.v1.cri".registry.mirrors."registry.k8s.io"]
  endpoint = ["https://registry-mirror.internal/registry.k8s.io", "https://registry.k8s.io"]

[plugins."io.containerd.grpc.v1.cri".registry.configs."registry-mirror.internal".auth]
  username = "kube"
  password = "<token>"
```

主流方案：

- **Harbor**：CNCF 毕业项目，企业级 registry + 镜像扫描 + 复制
- **Distribution / registry:2**：官方简单 registry，做 pull-through cache 一流
- **AWS ECR Pull Through Cache** / **GCP Artifact Registry remote repo**：托管方案，零运维

Pull-through cache 是规模化必备——`registry.internal` 收到请求时，先看本地有没有；没有就去上游（docker.io）拉一份缓存到本地。1000 节点拉同一个镜像，docker.io 那边只看到 1 次请求。

### 2.5 imagePullPolicy 的隐藏陷阱

```yaml
spec:
  containers:
    - name: app
      image: registry/app:latest   # ← tag 是 latest
      imagePullPolicy: Always       # 默认 Always
```

**问题**：每次 Pod 创建都去 registry 验证 manifest digest——延迟、流量、配额浪费。

```yaml
- image: registry/app:v1.42.0       # ← 具体版本号
  imagePullPolicy: IfNotPresent     # 显式
```

**铁律**：

1. 生产镜像**永远不要用 `latest`**——用 immutable tag（git commit / semver）
2. `imagePullPolicy` 显式设 `IfNotPresent`
3. 如果一定要 latest，用 `imagePullPolicy: Always` 但接受额外延迟

实际更稳的做法：用 `image: registry/app@sha256:abc...` 钉死 digest——保证整集群跑一份一致的 image，绕过 tag 漂移。

### 2.6 镜像构建优化

```dockerfile
# 多阶段构建：build → distroless
FROM golang:1.23-alpine AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download             # ← 先 mod download；代码改不动这一层
COPY . .
RUN CGO_ENABLED=0 go build -o app -ldflags="-s -w" ./cmd/server

FROM gcr.io/distroless/static-debian12
COPY --from=builder /src/app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]
```

- 多阶段 → 最终镜像不含编译器、源码、缓存（仅二进制）
- `-ldflags="-s -w"` → 去 debug 信息，二进制小 30%
- distroless / scratch → 无 shell，攻击面小，镜像 < 20MB
- 层顺序：变化频率从低到高（COPY 依赖在前，COPY 业务代码在后）

镜像越小 → 拉得越快 → 启动越快 → 扩缩响应越快。详细见 **C01 精通 Docker 与 OCI**。

## 第三章：DNS 性能——CoreDNS 是隐形瓶颈

### 3.1 为什么 DNS 决定 1000 节点集群的稳定性

K8s 每个 Pod 默认 DNS 配置：

```
# /etc/resolv.conf in Pod
nameserver 10.96.0.10            # kube-dns ClusterIP
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5 timeout:1
```

`ndots:5` 是个**坑**——任何 DNS 查询，如果点数 < 5，会先尝试拼接 search domain。比如 `redis.cache.svc.cluster.local`（4 个点）会被先解析为：

```
redis.cache.svc.cluster.local.default.svc.cluster.local      # miss
redis.cache.svc.cluster.local.svc.cluster.local              # miss
redis.cache.svc.cluster.local.cluster.local                  # miss
redis.cache.svc.cluster.local                                # hit!
```

**每次查询发 4 个请求**。如果业务还要查公网域名（如 `api.openai.com`），ndots:5 让它先拼 search domain 全部失败再去公网——延迟、CoreDNS 压力、kube-proxy 转发表压力都翻 4 倍。

1000 节点 × 100 Pod × 几百 QPS DNS → CoreDNS 实例直接打满。

### 3.2 NodeLocal DNSCache：每节点缓存层

```
        ┌──────────────────┐
   Pod ─→ NodeLocal DNS    │  (cache hit return)
        │  169.254.20.10   │
        └────────┬─────────┘
                 │ miss
                 ↓
        ┌──────────────────┐
        │ CoreDNS          │
        │ 10.96.0.10       │
        └──────────────────┘
```

每节点起一个 DaemonSet，监听虚地址 `169.254.20.10`，缓存解析结果。**绕过 kube-proxy iptables/IPVS**——直接 hostNetwork 与 Pod 通信，延迟 < 1ms，命中率 90%+。

部署：

```bash
# upstream coredns ClusterIP
KUBEDNS=$(kubectl get svc -n kube-system kube-dns -o jsonpath='{.spec.clusterIP}')

# 下载 manifest
wget https://raw.githubusercontent.com/kubernetes/kubernetes/master/cluster/addons/dns/nodelocaldns/nodelocaldns.yaml

# 替换占位
sed -i "s/__PILLAR__LOCAL__DNS__/169.254.20.10/g" nodelocaldns.yaml
sed -i "s/__PILLAR__DNS__DOMAIN__/cluster.local/g" nodelocaldns.yaml
sed -i "s/__PILLAR__DNS__SERVER__/${KUBEDNS}/g" nodelocaldns.yaml

kubectl apply -f nodelocaldns.yaml
```

```yaml
# 同时把 Pod 的 DNS 指向 NodeLocal
spec:
  dnsPolicy: ClusterFirst
  dnsConfig:
    nameservers:
      - 169.254.20.10
    options:
      - name: ndots
        value: "1"               # ← 改 ndots 减少拼 search
```

NodeLocal DNSCache 之后，集群层面 CoreDNS QPS 降 10-20x，DNS 延迟 p99 从 50ms 降到 < 2ms。

### 3.3 ndots: 1 的影响

把 ndots 从 5 改 1 后：

- `redis.cache.svc.cluster.local` (4 点 ≥ 1) → 直接查这个 FQDN，**不**拼 search
- `redis` (0 点 < 1) → 拼 search domain
- `api.openai.com` (2 点 ≥ 1) → 直接查公网，**不**拼 search

**好处**：公网域名 + 跨 namespace 服务调用大幅加速。
**风险**：写 `redis-master`（0 点）这种短名时**不会**自动加 namespace；必须写 FQDN 或 `redis-master.cache`。

业务代码里强制用 FQDN：

```go
const RedisHost = "redis-master.cache.svc.cluster.local"
```

或者只在 cluster-internal 高频调用的 Pod 上单独设 ndots: 1，其他保持默认。

### 3.4 CoreDNS 调优

默认部署常常只起 2 个 CoreDNS Pod——1000 节点根本不够。

```yaml
# CoreDNS Deployment
spec:
  replicas: 6                    # 至少；用 autoscaler 动态扩
  template:
    spec:
      containers:
        - name: coredns
          resources:
            limits:
              cpu: 1
              memory: 512Mi
            requests:
              cpu: 200m
              memory: 256Mi
          args:
            - -conf
            - /etc/coredns/Corefile
```

```corefile
# Corefile 调优
.:53 {
    errors
    health {
        lameduck 5s
    }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
        ttl 30                   # 缓存 30s
    }
    prometheus :9153
    forward . /etc/resolv.conf {
        max_concurrent 1000      # 默认 1000
        prefer_udp
    }
    cache 30                     # cache plugin 缓存 30s
    loop
    reload
    loadbalance                  # 多 A 记录轮询
    log . {
        class denial error       # 只记错误，正常查询不打日志
    }
}
```

用 HPA：

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: coredns
  namespace: kube-system
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: coredns
  minReplicas: 6
  maxReplicas: 30
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```

或用 `cluster-proportional-autoscaler` 按节点数线性扩。

### 3.5 监控指标

```promql
# QPS
sum(rate(coredns_dns_requests_total[1m])) by (zone)

# 命中率
sum(rate(coredns_cache_hits_total[1m])) /
sum(rate(coredns_cache_requests_total[1m]))

# NXDOMAIN 比例（异常高 = 业务在查不存在的域名）
sum(rate(coredns_dns_responses_total{rcode="NXDOMAIN"}[1m])) /
sum(rate(coredns_dns_responses_total[1m]))

# p99 延迟
histogram_quantile(0.99,
  sum(rate(coredns_dns_request_duration_seconds_bucket[5m])) by (le, zone))
```

**告警阈值**（生产参考）：

- QPS 单 Pod > 5000 → 扩容
- 命中率 < 70% → 调 TTL 或排查异常请求
- NXDOMAIN > 5% → 排查 ndots / 错误域名
- p99 > 50ms → 上 NodeLocalDNS / 扩 CoreDNS

## 第四章：控制面性能——API Server / etcd

### 4.1 API Server 限流：APF（API Priority and Fairness）

K8s 1.20+ 默认开启 APF，把请求分成不同 priority + flow，避免单一客户端把 apiserver 打挂。

```yaml
# 查看默认 priority level
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: PriorityLevelConfiguration
metadata:
  name: workload-high
spec:
  type: Limited
  limited:
    nominalConcurrencyShares: 100
    limitResponse:
      type: Queue
      queuing:
        queues: 64
        handSize: 6
        queueLengthLimit: 50
```

关键参数：

- `nominalConcurrencyShares`：分配给这个 priority 的"并发份额"（不是绝对数）
- `queues` × `queueLengthLimit`：等待队列总长

业务客户端默认走 `workload-low` / `workload-high`。系统组件走 `system` / `node-high`。看自己请求被分到哪个 level：

```bash
$ kubectl get --raw='/debug/api_priority_and_fairness/dump_priority_levels'
```

### 4.2 客户端 QPS 限制

```go
import "k8s.io/client-go/rest"

config := &rest.Config{...}
config.QPS = 50                    // 持续 QPS
config.Burst = 100                 // 突发上限

clientset, _ := kubernetes.NewForConfig(config)
```

默认 `QPS=5 Burst=10` —— 跑 Operator 时几个 reconcile 一起就限流了。**生产 Operator 调到 50/100 起步**，重型 Reconcile 上 100/200。

但要**适度**——所有 controller 都开高 QPS 会把 apiserver 自己打挂。社区共识：

| 集群规模 | apiserver QPS 总和 |
|---|---|
| 100 节点 | 500-1000 |
| 500 节点 | 2000-4000 |
| 1000 节点 | 5000-10000 |

超过后用 APF FlowSchema 把"乱写代码的 controller"压到低优先级。

### 4.3 etcd 调优

etcd 是 K8s 唯一的状态存储——一切 K8s 对象（Pod / Service / Secret / CR）都在 etcd 里。1000 节点集群 etcd db 通常 5-10GB。

```bash
# 必须用 SSD（NVMe 最好）
# 关键 IOPS：写 > 5000，fsync 延迟 < 10ms

# 检查 fsync p99
$ etcdctl --endpoints=$ETCD_ENDPOINTS endpoint status -w json | jq '.[].Status.dbSize'
```

调优三件套：

```yaml
# 1. db 大小上限（默认 2GB，规模化提到 8GB）
--quota-backend-bytes=8589934592

# 2. 心跳与选举（默认对千兆网 ok；跨 region 要调）
--heartbeat-interval=250        # ms
--election-timeout=2500         # ms

# 3. 自动压缩（K8s apiserver 已配，etcd 自身确认）
--auto-compaction-retention=5   # 保留 5 小时历史 revision
```

```bash
# 定期 defrag —— etcd 在 compaction 后空间不会自动回收
$ etcdctl --endpoints=$ETCD_ENDPOINTS defrag --command-timeout=60s
```

**生产建议**：

1. etcd 跑在独立节点（控制面专用，不与业务混跑）
2. 至少 3 节点 raft，跨可用区
3. 监控 `etcd_server_proposals_failed_total`、`etcd_disk_wal_fsync_duration_seconds`
4. 备份：etcd snapshot 每小时跑一次，存 S3 / GCS
5. 重要操作前手动 snapshot

```bash
# 备份
$ ETCDCTL_API=3 etcdctl snapshot save backup.db \
    --endpoints=$ETCD_ENDPOINTS \
    --cacert=$CA --cert=$CERT --key=$KEY
$ aws s3 cp backup.db s3://etcd-backups/$(date +%Y%m%d-%H%M%S).db

# 恢复（灾难时）
$ etcdctl snapshot restore backup.db \
    --data-dir=/var/lib/etcd-restored
```

### 4.4 Watch Cache：list 之痛

apiserver 对 etcd 的 watch 通过内置 cache 加速：

```
client.LIST(Pods) → apiserver
                    ├─ resourceVersion=0 → 读 cache（快）
                    ├─ resourceVersion=N → 读 etcd 历史（慢）
                    └─ resourceVersion=N&fieldSelector=... → 后置过滤
```

陷阱：

- **`fieldSelector` 不在 cache index 里**——所有 Pod 都被读出再过滤；千节点集群 LIST 整个 cluster Pods 占 100MB+ 内存
- **`?limit=500&continue=...` 分页**也走 etcd（不走 cache）
- **`resourceVersion=""`（强一致 list）** → 直接打 etcd，规模化禁用

社区做的 `ConsistentListFromCache` (K8s 1.31+) 已让一些 list 走 cache 强一致——但默认行为仍保守。

```bash
# 看 cache 命中率
$ kubectl get --raw='/metrics' | grep apiserver_storage_list

apiserver_storage_list_total{resource="pods"} 102
apiserver_storage_list_evaluated_objects_count{resource="pods"} 153000
apiserver_storage_list_returned_objects_count{resource="pods"} 240
```

153000 评估、240 返回——意味着客户端要 240 个对象但服务端遍历了 15w 个再过滤。**优化**：

1. controller / operator 用 `labelSelector` 而非 `fieldSelector`
2. 不用 `?fieldSelector=spec.nodeName=xyz`——这是经典反模式（list pods on node 该走 node-local kubelet API）
3. informer 默认带 indexer——别每个事件都 LIST 一遍

### 4.5 大对象 Watch 风暴

```
单个 ConfigMap 改一次 → 整个 cluster 所有 informer watch 到 → 全网风暴
```

特别是：

- 大 ConfigMap（>1MB）频繁更新
- 全集群 watch ConfigMap（如 fluentd 的配置）
- 同步 Secret 触发 SA token refresh

**对策**：

```yaml
# 1. controller 用 namespace-scoped informer
informerFactory := informers.NewSharedInformerFactoryWithOptions(
    client, time.Minute,
    informers.WithNamespace("app"),   // 只 watch 一个 namespace
)

# 2. ConfigMap 大块内容塞 immutable
apiVersion: v1
kind: ConfigMap
metadata:
  name: large-config
immutable: true                  # 不可改；触发 watch 全部走一次然后再也不变
data:
  large.yaml: |
    ... 1MB ...
```

immutable ConfigMap / Secret 是 K8s 1.21+ 稳定特性——一旦创建不能改，必须删除重建。对"大块只读配置"场景非常合适。

## 第五章：Pod 启动优化——从分钟级到秒级

### 5.1 启动时间分解

```
T0: kubelet 收到 Pod
T1: 创建 Pod sandbox (pause container)              ~100ms
T2: 拉 image                                         5s - 10min
T3: init container 1 ... N 顺序执行                  N × 1-30s
T4: 主容器 + sidecar 启动                            1-10s
T5: readinessProbe 通过                              0-30s
T6: 加入 Service Endpoints                          1-5s
```

千节点滚动升级：**T2 + T3 + T5 占 95%+**。

### 5.2 减少 sidecar

历史上每个 Pod 容易塞一堆 sidecar：

```yaml
# 反例：Pod 里有 5 个 sidecar
- envoy（mesh）
- fluentbit（日志）
- prometheus-exporter
- vault-agent
- istio-proxy
```

每个 sidecar：

- 占 200-500MB 内存（envoy / istio-proxy 是大头）
- 启动慢（envoy bootstrap ~3s）
- 升级要重启整个 Pod

**2026 年趋势**：

1. **Ambient Mesh**（Istio Ambient / Cilium Mesh）：把 sidecar 从 Pod 抽到节点（ztunnel + waypoint），mesh 升级与业务解耦。详见 **C10 精通 Service Mesh**
2. **DaemonSet 化日志**：Fluent Bit / Vector 一个节点一份，所有 Pod 共享，省 N × 100MB 内存
3. **eBPF 替代 sidecar metric exporter**：cAdvisor、kube-state-metrics、Pixie 等
4. **K8s 1.28+ native sidecar containers**（1.28 alpha → 1.29 beta → 1.33 GA）：sidecar 作为特殊 init container 跑，与主容器并行但生命周期独立

```yaml
# K8s 1.33+ native sidecar（GA）
spec:
  initContainers:
    - name: envoy
      image: envoyproxy/envoy:v1.30
      restartPolicy: Always       # ← 这个字段让它成为 sidecar
      ports: [{containerPort: 15000}]
  containers:
    - name: app
      image: app:v1
```

`restartPolicy: Always` 在 initContainer 里把它转成 sidecar——和主容器并行，但 Pod 退出时优雅停止。

### 5.3 减少 init container

init container 顺序串行。每个 1s 启动 → 5 个 = 5s 延迟。**能用 entrypoint 脚本搞定的，别上 init container**：

```yaml
# 反例
initContainers:
  - name: chown
    image: busybox
    command: ["chown", "-R", "1000:1000", "/data"]
  - name: chmod
    image: busybox
    command: ["chmod", "750", "/data"]
  - name: migrate
    image: app:v1
    command: ["./migrate"]

# 正解：直接合到一个 init container 或主进程 prestart
initContainers:
  - name: prepare
    image: app:v1
    command:
      - sh
      - -c
      - |
        chown -R 1000:1000 /data &&
        chmod 750 /data &&
        ./migrate
```

省去镜像切换 + 容器创建开销。

### 5.4 readinessProbe 调优

```yaml
readinessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 0          # 0！让 probe 立刻开始
  periodSeconds: 1                # 每秒一次
  timeoutSeconds: 1
  successThreshold: 1
  failureThreshold: 3
```

老套路把 `initialDelaySeconds: 30` —— **慢了 30s**。正确做法：

1. `initialDelaySeconds: 0`
2. `periodSeconds: 1`（生产建议；不会增加 apiserver 压力，probe 是 kubelet 本地的）
3. 应用本身在 ready 前返回 503/404；ready 后返回 200
4. 用 **startupProbe** 处理"启动慢但 ready 后快"的情况

```yaml
startupProbe:
  httpGet: {path: /healthz, port: 8080}
  failureThreshold: 30            # 30 × 5s = 150s 启动上限
  periodSeconds: 5
readinessProbe:
  httpGet: {path: /healthz, port: 8080}
  periodSeconds: 1
  failureThreshold: 3
```

startupProbe 不通过前不跑 readiness/liveness。这样 JVM / Python 这种慢启动应用不会被 livenessProbe 杀掉。

### 5.5 Service Endpoints 加入延迟

Pod ready 不等于 Endpoints 同步。EndpointSlice controller 监听 Pod 事件，写 EndpointSlice，kube-proxy 监听 EndpointSlice 写 iptables/IPVS——**整条链路 1-5s**。

```yaml
# Service spec.publishNotReadyAddresses 用于 StatefulSet headless
# 但生产 service 默认要等 ready
spec:
  publishNotReadyAddresses: false
```

**优化**：

- Cilium / kube-proxy IPVS 模式更新比 iptables 模式快 10x（IPVS 用 hash 表，iptables 是 O(n) 遍历）
- Endpoint Slice 是 K8s 1.21+ 默认（旧的 Endpoints 单对象规模大时性能差）
- 升级时 `terminationGracePeriodSeconds: 60` + `preStop sleep 5` 给 endpoints 同步窗口

```yaml
spec:
  terminationGracePeriodSeconds: 60
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["sleep", "5"]    # 让 SIGTERM 前 endpoints 先摘除
```

## 第六章：资源规划——基线、突发、与可用区

### 6.1 Requests vs Limits 决定 QoS

```yaml
# Guaranteed（最稳，最容易被资源 schedule）
resources:
  requests:
    cpu: 1
    memory: 1Gi
  limits:
    cpu: 1
    memory: 1Gi

# Burstable（最常用）
resources:
  requests: { cpu: 100m, memory: 256Mi }
  limits:   { cpu: 500m, memory: 512Mi }

# BestEffort（什么都不设，最易被驱逐）
resources: {}
```

| QoS | 节点资源紧张时驱逐顺序 | 适用 |
|---|---|---|
| Guaranteed | 最后 | 关键服务、有 SLA |
| Burstable | 中间 | 通用业务 |
| BestEffort | 最先 | 后台任务、能容忍中断 |

**生产铁律**：

1. 所有 Pod 必须有 `resources.requests`——否则调度器无法做容量决策
2. CPU **不设 limit**（设了反而被 cgroup throttle 拖慢，2022 后社区共识）
3. Memory **必设 limit**——OOM kill 比 OOM 全节点更好
4. 关键路径 Pod 用 Guaranteed

### 6.2 HPA + KEDA 联动

HPA（K8s 内置）按 CPU / Memory / 自定义 metric 扩缩；KEDA（CNCF）扩展为按"事件源"扩缩（Kafka、SQS、Redis、Prometheus）。

```yaml
# KEDA ScaledObject——按 Kafka lag 扩缩
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: kafka-consumer
spec:
  scaleTargetRef:
    name: kafka-consumer
  minReplicaCount: 3
  maxReplicaCount: 100
  pollingInterval: 30
  cooldownPeriod: 300
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka.kafka:9092
        consumerGroup: my-group
        topic: events
        lagThreshold: "1000"
```

KEDA 内部生成 HPA + ExternalMetric——你只管业务指标，KEDA 负责协议转换。**2026 年趋势**：KEDA 几乎是事件驱动伸缩的事实标准。

HPA 与 KEDA 不冲突——KEDA 包了 HPA，业务只写 KEDA ScaledObject。

```yaml
# HPA 行为参数（防抖）
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300    # 5min 内不再缩
    policies:
      - type: Percent
        value: 25                        # 一次最多缩 25%
        periodSeconds: 60
  scaleUp:
    stabilizationWindowSeconds: 0
    policies:
      - type: Percent
        value: 100
        periodSeconds: 30
      - type: Pods
        value: 10
        periodSeconds: 30
    selectPolicy: Max
```

防抖策略：扩容快、缩容慢——避免流量波动导致 Pod 反复创建/销毁。

### 6.3 可用区分散

```yaml
spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule          # 强约束
      labelSelector:
        matchLabels:
          app: api-server
    - maxSkew: 1
      topologyKey: kubernetes.io/hostname
      whenUnsatisfiable: ScheduleAnyway         # 软约束
      labelSelector:
        matchLabels:
          app: api-server
```

`topologySpreadConstraints` 让 Pod 在不同维度（zone / host / rack）分散。**两层**：

1. zone 强约束：3 个 zone 跑 3+ 副本，每 zone 数量差 ≤ 1
2. host 软约束：尽量不挤在同一台机器

**反例**：单 zone 跑全部副本 → AZ 故障 → 服务全挂。AWS us-east-1 2017、2021、2023 多次大故障都跑出来这个教训。

### 6.4 PDB（PodDisruptionBudget）

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-server
spec:
  minAvailable: 80%                # 至少保持 80% Pod 在
  # 或 maxUnavailable: 1
  selector:
    matchLabels:
      app: api-server
```

PDB 影响"自愿中断"（kubectl drain、cluster autoscaler、Karpenter consolidation）。**非自愿中断**（节点故障）不受 PDB 保护——那是 Pod 反亲和 + 多副本的事。

千节点集群必须给所有关键 Deployment 配 PDB。否则一次大规模节点升级会同时驱逐 100+ 个副本。

```bash
# 看 PDB 状态
$ kubectl get pdb
NAME          MIN AVAILABLE   ALLOWED DISRUPTIONS   AGE
api-server    80%             2                     30d
```

`ALLOWED DISRUPTIONS` = 0 说明此刻不允许驱逐——drain 节点时会被阻塞。

## 第七章：升级策略——一边跑一边换轮子

### 7.1 滚动升级的几个旋钮

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 25%            # 旧 Pod 一次最多停多少
      maxSurge: 25%                  # 新 Pod 一次最多多多少
```

`maxUnavailable` + `maxSurge` 决定升级速度与冗余。生产典型：

- 关键服务：`maxUnavailable: 0` + `maxSurge: 25%`（永远不少于 replicas，最多多 25%）
- 一般服务：`maxUnavailable: 25%` + `maxSurge: 25%`（容忍少 25%）

`maxUnavailable: 0` 升级**必须有足够资源**——否则新 Pod 调度不上去，升级卡住。

### 7.2 K8s 集群本身的升级

K8s 集群升级路径（一次只能跳一个小版本）：

```
1.30 → 1.31 → 1.32 → 1.33
```

升级顺序：

```
1. 升 etcd（如果有变更）
2. 升控制面（apiserver / controller-manager / scheduler）
3. 升 worker 节点（kubelet / kube-proxy）
4. 升插件（CNI / coredns / metrics-server）
```

每一步：

- 控制面：先升一个，看 1-2 小时，再升其他
- worker 节点：**滚动**升级，每次升 5-10%（取决于 PDB 与冗余度）

托管 K8s（EKS / GKE / AKS）控制面云厂商升；worker 节点用户自己升或开自动升级。

### 7.3 Surge Nodes：避免缩容卡死

worker 节点升级时，cluster autoscaler / Karpenter 通常"先起新版本节点，drain 旧节点"。旧节点 drain 时如果 Pod 没地方去（资源紧）→ 卡死。

**对策**：

```yaml
# Karpenter Disruption
spec:
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 60s
    budgets:
      - nodes: "20%"             # 同时只升 20% 节点
      - schedule: "0 9 * * mon-fri"
        duration: 8h
        nodes: "0"               # 工作时间禁止任何 disruption
```

- 控制并发：`nodes: "20%"` 避免雪崩
- 时间窗口：业务高峰不操作

EKS managed node group：

```yaml
# Karpenter / EKS API call
$ aws eks update-nodegroup-version \
    --cluster-name prod \
    --nodegroup-name general \
    --kubernetes-version 1.33 \
    --release-version 1.33.1-202405xx
```

EKS 会按 `maxUnavailable` 滚动；自己 drain & 拉起。

### 7.4 Blue-Green / Canary 集群升级

更激进的方法：开一个新集群，把流量逐步从老切到新。

```
集群 A (1.31) ─┐
               ├─ Global LB / 多集群 mesh ─┐
集群 B (1.33) ─┘                            └─ 用户
```

- 集群 B 跑 7 天观察
- 把 10% / 50% / 100% 流量切到 B
- 集群 A 下线

适用场景：

- 跨多个 minor 版本（1.27 → 1.33 这种"补课"）
- 重大组件换（CNI 换、container runtime 换）
- 合规审计要求"新集群"

**代价**：要 2x 资源、要多集群联通（mesh / Submariner / Karmada）。

## 第八章：多集群——超越单集群上限

### 8.1 为什么要多集群

```
单集群极限（2026 实践）：
- ~2000 节点稳定运营
- ~3000 节点深度调优
- ~5000 节点需要严苛的客户端纪律
```

超过这个规模必须拆。其他要拆的理由：

- **故障域隔离**：一个集群故障不影响所有业务
- **合规分区**：金融 / 医疗强制数据隔离
- **多 region 部署**：低延迟 + 灾备
- **多云 / 混合云**：AWS + GCP + 自建 IDC
- **生产 / 预发 / 测试分离**

### 8.2 多集群方案对比

| 方案 | 用途 | 复杂度 | 2026 状态 |
|---|---|---|---|
| **Karmada** | 多集群编排（CNCF Incubating） | 高 | 1.13+，国内大厂用得多 |
| **Cluster API** | 集群生命周期（创建/升级/删除） | 中 | 1.x GA，主流方案 |
| **Submariner** | 跨集群 Pod / Service 网络 | 中 | 0.18+，GA |
| **Crossplane** | 跨云控制面（IaC + K8s 风格） | 中 | v1.16+，主流 |
| **Argo CD ApplicationSet** | 多集群 GitOps 部署 | 低 | 成熟 |
| **Istio Multi-Primary** | 多集群 mesh + 跨集群流量 | 高 | 1.x GA |

**典型组合**：

```
Cluster API     → 创建集群 / 升级集群
Karmada / Argo  → 部署应用到多集群
Istio / Cilium  → 跨集群网络 / mTLS
Crossplane      → 管理云资源（DB / S3 / VPC）
```

### 8.3 Karmada：多集群联邦

```yaml
# Karmada PropagationPolicy
apiVersion: policy.karmada.io/v1alpha1
kind: PropagationPolicy
metadata:
  name: api-server
spec:
  resourceSelectors:
    - apiVersion: apps/v1
      kind: Deployment
      name: api-server
  placement:
    clusterAffinity:
      clusterNames:
        - cluster-us-east
        - cluster-eu-west
        - cluster-ap-southeast
    replicaScheduling:
      replicaSchedulingType: Divided
      replicaDivisionPreference: Weighted
      weightPreference:
        staticWeightList:
          - targetCluster:
              clusterNames: [cluster-us-east]
            weight: 50
          - targetCluster:
              clusterNames: [cluster-eu-west]
            weight: 30
          - targetCluster:
              clusterNames: [cluster-ap-southeast]
            weight: 20
```

应用一次声明，Karmada 把 100 副本按权重 50/30/20 分发到三个集群。地域故障时自动 failover 到其他集群。

### 8.4 Cluster API：把集群当 K8s 对象管

```yaml
# Cluster API 创建集群
apiVersion: cluster.x-k8s.io/v1beta1
kind: Cluster
metadata:
  name: my-cluster
spec:
  clusterNetwork:
    pods: {cidrBlocks: ["10.244.0.0/16"]}
    services: {cidrBlocks: ["10.96.0.0/12"]}
  controlPlaneRef:
    apiVersion: controlplane.cluster.x-k8s.io/v1beta1
    kind: KubeadmControlPlane
    name: my-cluster-cp
  infrastructureRef:
    apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
    kind: AWSCluster
    name: my-cluster-aws
```

- Cluster API 控制集群生命周期（CRUD）
- Provider（AWS / GCP / Azure / OpenStack）实现具体 IaaS 调用
- 升级、扩容、回滚都是声明式

**这是"基础设施即 K8s 资源"的最完整实现**。CNCF Cluster API 项目 2026 年已 GA 多年，是托管 K8s 控制面（EKS Anywhere / OCP / Rancher）的底座。

### 8.5 Submariner：跨集群 Pod 通信

```bash
# 三个集群互联
$ subctl join broker-info.subm --clusterid us-east-1
$ subctl join broker-info.subm --clusterid eu-west-1
$ subctl join broker-info.subm --clusterid ap-southeast-1
```

Submariner 在节点上跑 gateway Pod，用 IPsec / Wireguard 隧道把不同集群 Pod CIDR 路由起来。Pod 直接用对方 Pod IP 访问；Service 通过 ServiceImport / MultiCluster DNS（`<svc>.<ns>.svc.clusterset.local`）发现。

```yaml
apiVersion: multicluster.x-k8s.io/v1alpha1
kind: ServiceExport

  name: api
  namespace: prod
# 把这个 service export 出去，其他集群可以通过 api.prod.svc.clusterset.local 访问
```

适合场景：

- 跨集群数据库 replication
- 跨集群 mesh
- 灰度迁移

## 第九章：容量规划与成本

### 9.1 容量规划三层

```
集群层：节点数量、规格、可用区
节点层：单节点 Pod 密度、IP 数量、存储 IOPS
Pod 层：requests / limits、HPA 上下界
```

### 9.2 节点选型

| 工作负载 | 推荐机型（AWS） | 原因 |
|---|---|---|
| 通用 web | c6i / m6i.large-2xlarge | 平衡 CPU / 内存 |
| 数据库 / Redis | r6i / r7i | 高内存 |
| 计算密集 / ML 推理 CPU | c6i / c7g (ARM) | 高 CPU / 低成本 |
| GPU 推理 | g5 / g6e | 性价比 |
| GPU 训练 | p4 / p5（H100） | 高性能 |
| 批处理 | spot c / m 系列 | 廉价 |

**机型多样性**是 spot 稳定的关键——Karpenter 配多种 instanceType，单一机型被回收时切其他。

```yaml
requirements:
  - key: karpenter.k8s.aws/instance-family
    operator: In
    values: ["c6i", "c6a", "c7i", "m6i", "m6a", "m7i"]   # ← 6 种
```

### 9.3 单节点 Pod 密度

```bash
# 默认上限 110 Pods / node
$ kubectl get node node-01 -o jsonpath='{.status.allocatable}'
{"cpu":"7910m","memory":"30Gi","pods":"110"}
```

提到 250 / 节点的影响：

- IP 池：每节点 250 个 Pod IP（EKS 默认 vpc-cni 容量有限制；要开 prefix delegation）
- 容器运行时压力：containerd 管 250 个容器
- kubelet 心跳与 status 上报
- 节点上 DaemonSet（CNI、kube-proxy、log agent）资源

```yaml
# kubelet config
maxPods: 250
podPidsLimit: 4096
```

**实际经验**：

- 小节点（2-4 vCPU）：50-100 Pod
- 中节点（8-16 vCPU）：100-150 Pod
- 大节点（32+ vCPU）：150-250 Pod

太密集会让单节点故障爆炸半径变大——3-5 个中等节点比 1 个大节点更稳。

### 9.4 Cluster Autoscaler 与 Karpenter 选型

```yaml
# Karpenter 优势
- 启动节点快（< 60s）
- 按 Pod 需求挑机型（best-fit binpacking）
- 主动 consolidation（合并低利用率节点）

# Cluster Autoscaler 优势
- 多云成熟
- 与现有 ASG / MIG 集成无缝
- 概念简单
```

2026 年 5 月 AWS 上 90%+ 的新集群直接用 Karpenter。Azure 也已 GA（经 AKS NAP），正逐步普及；GCP/GKE 无原生 Karpenter，仍依赖 Cluster Autoscaler / NAP。

### 9.5 成本可视化

```yaml
# KubeCost / OpenCost：拿 Prometheus 指标算每 namespace / workload 的成本
apiVersion: helm.cattle.io/v1
kind: HelmChart
metadata:
  name: kubecost
spec:
  chart: cost-analyzer
  repo: https://kubecost.github.io/cost-analyzer/
  set:
    kubecostProductConfigs.clusterName: prod-us-east
    prometheus.server.persistentVolume.size: 100Gi
```

KubeCost 把 EC2 单价 + Pod 实际用量 = $ / namespace / workload / label。

**典型成本浪费**：

- requests 过高（10x 实际用量）→ 节点空跑
- 没有 HPA → 流量低谷期 100% 资源浪费
- spot 用得不够（应该 70% spot 却用了 100% on-demand）
- 跨 zone 流量费（同 zone 内 Pod 通信免费，跨 zone $0.01/GB）

```bash
# 跨 zone 流量
$ kubectl exec -n monitoring prom-0 -- curl -s ...
# 用 KubeCost 的 "network_costs" 算
```

把 Pod 反亲和改 `topology.kubernetes.io/zone preferred` 而非 required → 同 zone 通信优先 → 流量费降 50-80%。

## 第十章：灾备——把"备份"变成"演练"

### 10.1 灾备的几个等级

| 级别 | RPO | RTO | 方案 |
|---|---|---|---|
| L1 | 24h | 8h | 每日 etcd snapshot，手工恢复 |
| L2 | 1h | 1h | Velero 定时备份，半自动恢复 |
| L3 | 5min | 15min | 跨 region 异步复制（etcd + 应用层） |
| L4 | < 1min | < 5min | 多 region active-active |

### 10.2 Velero：备份与恢复

```bash
# 安装
$ velero install \
    --provider aws \
    --bucket velero-backups \
    --backup-location-config region=us-east-1 \
    --snapshot-location-config region=us-east-1 \
    --secret-file credentials-velero

# 立即备份某 namespace
$ velero backup create app-backup-2026-05-14 \
    --include-namespaces app \
    --include-cluster-resources=false

# 定时备份
$ velero schedule create daily-app \
    --schedule="0 1 * * *" \
    --include-namespaces app \
    --ttl 720h
```

Velero 备份内容：

1. K8s 对象（YAML）→ 推到 S3
2. PV 数据 → 走 CSI snapshot 或 restic

```bash
# 恢复
$ velero restore create --from-backup app-backup-2026-05-14

# 跨集群恢复（迁移）
# 1. 老集群 backup → S3
# 2. 新集群 install velero 指向同一 S3
# 3. velero restore
```

**生产建议**：

1. 每周做一次**真实恢复演练**——不演练的备份等于没备份
2. 备份要存**不同 region** / 不同账号——勒索 / 误删 / 账号被入侵
3. PVC 也要备份，不仅是 YAML

### 10.3 跨 region / 跨云

```
方案 A：跨 region 主备（异步复制）
  region-1 主集群 → 持续 etcd snapshot / 应用层复制 → region-2 standby
  region-1 故障 → DNS 切到 region-2

方案 B：跨 region active-active
  两个 region 都接生产流量
  跨 region 数据同步（CRDB / Spanner / DynamoDB Global Table / Aurora Global）
  无状态服务在两 region 同时跑
```

主备简单但 RTO 高（DNS TTL + 数据 catch-up + 验证）。Active-active 复杂（数据一致性）但 RTO 接近 0。

### 10.4 混合云

```
本地 IDC (OpenStack / VMware)  ─┐
                                 ├─ 统一控制（Anthos / EKS Anywhere / OCP）
公有云 (AWS / GCP / Azure)     ─┘
```

混合云典型驱动：

- 数据合规：客户数据必须本地
- 成本：稳定基线本地 + 突发上云
- 渐进迁移：传统应用本地，新应用云上

工具：

- **Anthos / EKS Anywhere / Azure Arc**：把本地 K8s 接入云控制台
- **Crossplane**：跨云资源统一 API
- **GitOps（ArgoCD / Flux）**：用一套 Git 仓库部署到多集群

### 11.1 为什么要混沌

### 11.3 混沌实验的纪律

混沌**不是**"乱杀机器看热闹"。规范流程：

1. **假设**：写下"我假设杀 30% Pod 时 SLO 不受影响"
2. **稳态指标**：定义 SLO（错误率 < 0.5%、p99 < 200ms）
3. **爆炸半径**：从 dev 开始 → staging → prod 1% 流量 → 全量
4. **应急熔断**：实验中 SLO 跌破立刻终止
5. **回顾**：失败的实验是最有价值的——补 PDB、加副本、修代码

**禁忌**：

- 周末 / 节假日不做
- 业务高峰不做
- 没有 on-call 不做
- 没准备好回滚不做

### 11.4 GameDay

每季度组织一次 GameDay：选定场景（如"主 region 全挂"），团队不预演直接演。期间观察：

- 监控是否能及时发现
- runbook 是否到位
- 跨团队协作流程
- 自动化是否真的工作

GameDay 暴露的 bug 远多于平时的 ad-hoc 演习。

## 第十二章：陷阱清单

### 1. PSP 已删除——但旧配置仍 reference

K8s 1.25 移除了 PodSecurityPolicy。升级到 1.25+ 后，旧的 PSP YAML、绑定的 ClusterRole / RoleBinding 不会自动清理。残留的 RBAC 引用导致 admission 报错。**对策**：升级前把所有 PSP 改成 Pod Security Admission（PSA） + Kyverno / Gatekeeper。

### 2. apiserver 限流没监控

APF 把请求扔队列里 → 客户端等待 → 慢得感觉像 hang。**监控**：

```promql
apiserver_flowcontrol_dispatched_requests_total
apiserver_flowcontrol_rejected_requests_total
apiserver_flowcontrol_request_wait_duration_seconds
```

`rejected` 上升 = 容量不够，要扩 apiserver 或调 FlowSchema。

### 3. CoreDNS NXDOMAIN 流量

业务代码错配 `redis://redis-master:6379` 但实际 service 叫 `redis-master.cache`——`ndots:5` + search domain 拼接 → 几千 QPS NXDOMAIN。CoreDNS 上日志爆炸、压力翻倍。**对策**：

- 强制业务用 FQDN
- ndots: 1
- CoreDNS 加 `nxdomain_cache` 缓存 NXDOMAIN 短期不重查

### 4. PDB 与 maxUnavailable 冲突

```yaml
# PDB
minAvailable: 100%

# Deployment
maxUnavailable: 25%
```

PDB 不让你停任何 Pod，但 Deployment 想滚动升级 → 升级 forever 卡死。**对策**：minAvailable 必须 < 100%，留出滚动窗口。

### 5. node-pressure eviction

节点磁盘满 / 内存紧 → kubelet 主动驱逐 Pod。**默认阈值**：

```yaml
evictionHard:
  memory.available: 100Mi
  nodefs.available: 10%
  nodefs.inodesFree: 5%
  imagefs.available: 15%
```

10% 节点磁盘空闲就驱逐——大节点（500GB）下 50GB 才算够。**调整**：

```yaml
evictionHard:
  nodefs.available: 5%    # 25GB 才驱逐
  imagefs.available: 10%
```

但同时要清理：定期 `crictl rmi --prune` 清不用的镜像。

### 6. Karpenter consolidation 误杀

`WhenEmptyOrUnderutilized` 会主动停"低利用率"节点合并到其他节点。低 traffic 时段所有节点都低利用率 → 一次干掉一半节点 → 流量回来调度不上。**对策**：

```yaml
disruption:
  budgets:
    - nodes: "10%"           # 一次最多 disrupt 10%
    - schedule: "0 0 * * *"  # 0-8 点禁止 disruption
      duration: 8h
      nodes: "0"
```

### 7. cluster autoscaler 与 HPA 拉锯

CA 看节点利用率扩容；HPA 看 Pod CPU 扩容。两者节奏不同步：

```
高峰：HPA 想扩 100 Pod → 节点不够 → CA 扩 5 节点 → 1min 起来 → Pod 调度上 → 业务 ok
低谷：HPA 想缩到 10 Pod → 但旧节点上还有 Pod → CA 等 Pod 全走 → 几分钟后才缩节点
```

**优化**：

- CA 的 `--scale-down-delay-after-add=10m`：扩容后 10min 内不缩
- CA 的 `--scale-down-unneeded-time=15m`：节点空闲 15min 才缩
- 用 Karpenter 替代 → consolidation 比 CA 智能

### 8. metric-server / Pod metric 延迟

HPA 决策依赖 metric-server，metric-server 拉取节点 cAdvisor → 60s 延迟很正常。**对策**：

```yaml
# metric-server 参数
- --kubelet-preferred-address-types=InternalIP
- --metric-resolution=15s          # 默认 60s，调到 15s
```

更激进：用 Prometheus Adapter 替代 metric-server，把所有自定义指标喂给 HPA。

### 9. etcd db 满

```bash
$ etcdctl endpoint status
# DB_SIZE: 2.1 GB (default quota: 2 GB)
# IS_LEARNER: false
# ALARMS: [NOSPACE]   # ← 报警
```

`NOSPACE` 后整个 etcd 停止写入 → apiserver 写入全失败。**对策**：

```bash
# 1. 紧急压缩
$ etcdctl compact $(etcdctl endpoint status -w json | jq -r '.[].Status.header.revision')

# 2. defrag
$ etcdctl defrag

# 3. 取消报警
$ etcdctl alarm disarm

# 4. 长期：调大 quota，配置 auto-compaction
--quota-backend-bytes=8589934592
--auto-compaction-mode=periodic
--auto-compaction-retention=1h
```

### 10. CrashLoopBackOff 雪崩

某个 ConfigMap 改坏 → 所有依赖 Pod 一起 Crash → 反复重启 → kubelet 拉镜像、apiserver watch 风暴。**对策**：

- 关键 ConfigMap 改前先 dry-run
- 用 OPA / Kyverno 在 admission 阶段拦截
- argo Rollouts / Flagger 渐进发布（10% → 50% → 100%）

### 11. Pod 与节点版本不匹配

K8s 升级 1.31 → 1.32，kubelet 在 1.32 节点但有些 Pod 还按 1.31 的 API 定义。少数 deprecated API 删除时 Pod 启动失败。**对策**：

- 升级前用 `kubectl convert` / `kube-no-trouble (kubent)` 扫描所有 YAML
- staging 集群先升级 1-2 周

### 12. ServiceAccount token 过期

K8s 1.24+ 取消 auto-mount 长期 token，改成投影卷 token（1h 过期，kubelet 自动续）。老代码读 `/var/run/secrets/kubernetes.io/serviceaccount/token` 一次然后缓存 → 1h 后 401。**对策**：

```yaml
serviceAccountToken:
  audience: api
  expirationSeconds: 3600
  path: token
```

每次调 API 重读 token 文件——或者用 client-go，它自动处理。

### 13.3 Karpenter v1 GA

2024 年底 Karpenter v1 GA：

- AWS GA、Azure GA（经 AKS NAP）；GCP/GKE 无原生 Karpenter，使用 Cluster Autoscaler / NAP
- NodePool / NodeClaim 两层 CRD 取代旧 Provisioner
- consolidation 默认开
- 与 Cluster Autoscaler 互不替代但 AWS 上 Karpenter 已成主流

### 13.4 eBPF 全面接管

```
2020:  CNI 还是 Calico / Flannel / Weave
2024:  Cilium 上来占近 40%
2026:  Cilium 主流，eBPF 接管 kube-proxy / service mesh / observability
```

eBPF 收益：

- 性能：跳过 iptables 长链
- 灵活：动态加载内核态 filter，无需重启
- 可观测：从 syscall 到 HTTP 全 stack 看到
- 安全：Tetragon / Falco 运行时检测

### 13.5 Ambient Mesh

Istio Ambient（1.24 GA，2024-11）让 mesh 从 Pod 抽到节点：

```
Pod  ──→ ztunnel (per-node L4 mTLS)
           ↓
        waypoint (per-namespace L7 policy)  ← 可选
           ↓
        目标 Pod
```

- 业务 Pod 不再注入 sidecar
- mesh 升级不重启业务
- 资源开销降 70%
- L7 能力按需在 waypoint 启用

详见 **C10 精通 Service Mesh**。

### 13.6 KEDA + Karpenter 联动

```
事件源（Kafka lag / SQS / Prometheus）
    ↓
KEDA → 触发 HPA 扩 Pod
    ↓ Pod pending
Karpenter 立刻 provision 节点
    ↓ 60s
Pod scheduled & ready
```

事件突发 → Pod 数瞬间从 10 涨到 200 → Karpenter 自动起 20 个节点。低谷 → Karpenter consolidation 自动缩。

这是"真正弹性"的体感——比 ASG + CA 快 5-10x。

**练习 5**：

```go
package main

import (
    "context"
    "log/slog"
    "time"
    corev1 "k8s.io/api/core/v1"
    "k8s.io/client-go/informers"
    "k8s.io/client-go/kubernetes"
    "k8s.io/client-go/rest"
    "k8s.io/client-go/tools/cache"
)

func main() {
    config, err := rest.InClusterConfig()
    if err != nil { panic(err) }
    config.QPS = 100
    config.Burst = 200

    client, _ := kubernetes.NewForConfig(config)

    factory := informers.NewSharedInformerFactoryWithOptions(
        client,
        time.Minute,
        informers.WithNamespace("app"),
    )
    cmInformer := factory.Core().V1().ConfigMaps().Informer()
    cmInformer.AddEventHandler(cache.ResourceEventHandlerFuncs{
        AddFunc: func(obj interface{}) {
            cm := obj.(*corev1.ConfigMap)
            slog.Info("cm added", "name", cm.Name)
        },
        UpdateFunc: func(_, obj interface{}) {
            cm := obj.(*corev1.ConfigMap)
            slog.Info("cm updated", "name", cm.Name)
        },
    })

    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()
    factory.Start(ctx.Done())
    factory.WaitForCacheSync(ctx.Done())
    // informer 内部自动 watch 重连；不需要手工处理
    <-ctx.Done()
}
```

informer 内置 ListAndWatch 循环——watch 断开后自动重新 list + watch。

**练习 8**：`minAvailable: 100%` 意味着永远不能少于当前副本数 → 任何驱逐都被拒绝。

cluster autoscaler 缩容时：

- 选一个低利用率节点
- drain 节点（先 cordon，然后 evict 上面所有 Pod）
- PDB 拒绝 evict → drain 失败 → CA 报 `pod_disruption_budget` 错误
- 节点永远缩不掉，CA 一直试

正解：`minAvailable: 90%` 或 `maxUnavailable: 1`，留出滚动 / 驱逐窗口。

**练习 9**：3 节点 etcd（raft）要求多数派可用。1 节点磁盘满：

- 该节点写入失败 → 不能给 raft 投票 → 但仍有 2/3 节点正常 → **集群可以继续读写**（多数派满足）
- 但 etcd 报 NOSPACE 告警，apiserver 状态会异常

恢复：

```bash
# 在满的节点上：
$ etcdctl compact $(rev)
$ etcdctl defrag --command-timeout=60s
$ etcdctl alarm disarm

# 长期：扩 disk + 设 --auto-compaction-retention
```

## 结语

1000 节点 K8s 不是"10 节点 × 100"——每一项指标都要换更深的思考：

- **节点池**让异构变可控
- **镜像优化**让启动变快
- **DNS / 控制面**让规模变稳
- **资源规划 / 升级 / 灾备**让运行变长
- **多集群 / 混沌**让系统变韧

最重要的一条：**不演练的方案等于没方案**。备份要演、升级要演、跨集群切换要演。每次演练都会暴露 1-2 个不知道的坑——这些坑就是真正生产故障的提前预演。
