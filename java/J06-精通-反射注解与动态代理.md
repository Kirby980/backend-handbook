# 精通反射、注解与动态代理

> 反射 + 注解 + 动态代理是 Java 框架的"三件套"——Spring、MyBatis、各种 ORM 和序列化库全靠它们。理解这三者，才能看懂 Spring 的 IOC/AOP（[J22](./J22-精通-Spring-IOC容器.md)/[J23](./J23-精通-Spring-AOP.md)）到底在干什么。本篇打通这条线。
>
> **📅 基准：Java 17/21。**

---

## 一、反射是什么

**反射（Reflection）** 是在**运行时**动态获取类的信息（字段、方法、构造器、注解）并操作对象的能力——即使编译期不知道具体类型，运行时也能"照镜子"看清并调用。

正常调用是编译期确定的：`new User().getName()`。反射是运行时确定的：拿到一个 `Class` 对象，运行时问它"有哪些方法"、"创建一个实例"、"调用某方法"。

这是框架"通用"的根基——Spring 不知道你的业务类长什么样，但能用反射创建它、注入它、调用它。

---

## 二、获取 Class 对象的三种方式

一切反射从 `Class` 对象开始：

```java
// ① 类字面量（编译期已知，最快，不触发初始化）
Class<User> c1 = User.class;

// ② 对象的 getClass()（运行时）
Class<?> c2 = user.getClass();

// ③ Class.forName(全限定名)（运行时按名字加载，会触发类初始化）
Class<?> c3 = Class.forName("com.example.User");
```

- 每个类在 JVM 中只有**一个 Class 对象**（由类加载器加载，见 [J16 类加载](./J16-精通-类加载与双亲委派.md)）。
- `Class.forName` 常用于加载驱动/按配置名加载类（如老式 JDBC `Class.forName("com.mysql.cj.jdbc.Driver")`）。

---

## 三、反射核心 API

```java
Class<?> clazz = User.class;

// 创建实例（无参构造）
User u = (User) clazz.getDeclaredConstructor().newInstance();

// 访问字段（包括私有）
Field f = clazz.getDeclaredField("name");
f.setAccessible(true);     // 突破 private 封装
f.set(u, "Alice");
Object v = f.get(u);

// 调用方法（包括私有）
Method m = clazz.getDeclaredMethod("setAge", int.class);
m.setAccessible(true);
m.invoke(u, 18);
```

- `getXxx()` 只拿 public（含继承）；`getDeclaredXxx()` 拿本类所有（含 private，不含继承）。
- `setAccessible(true)` 可突破访问控制（private 也能改）——强大但破坏封装，且受模块系统/安全限制。
- 反射创建实例：旧的 `clazz.newInstance()` 已废弃，用 `getDeclaredConstructor().newInstance()`。

---

## 四、反射的代价与应用

**代价**：
- 反射调用比直接调用**慢**（涉及方法查找、访问检查、装箱、无法被部分 JIT 优化），虽然现代 JVM 已优化不少。
- 破坏封装、绕过编译期检查，错误推迟到运行时。

**应用**（框架基石）：
- **Spring IOC**：反射创建 Bean、注入依赖。
- **MyBatis/ORM**：反射把结果集映射到对象字段。
- **JSON 库（Jackson/Gson）**：反射读写字段做序列化/反序列化。
- **JUnit**：反射找到 `@Test` 方法并调用。

所以反射的"慢"在框架启动/配置阶段可接受；热点路径上框架会用缓存（缓存 Method/Field）、或字节码生成替代反射来提速。

---

## 五、注解

**注解（Annotation）** 是给代码加的元数据，本身不影响逻辑，靠工具/框架在编译期或运行时读取它来做事。

### 5.1 元注解（注解的注解）

| 元注解 | 作用 |
|---|---|
| `@Retention` | 保留策略：SOURCE（源码丢弃）/ CLASS（编译进 class 不进运行时）/ **RUNTIME**（运行时可反射读取） |
| `@Target` | 能标注在哪（类/方法/字段/参数...） |
| `@Documented` | 是否进 javadoc |
| `@Inherited` | 子类是否继承父类的该注解 |

### 5.2 自定义注解 + 运行时读取

```java
@Retention(RetentionPolicy.RUNTIME)   // 必须 RUNTIME 才能被反射读到
@Target(ElementType.METHOD)
public @interface Log { String value() default ""; }

// 使用
@Log("用户查询") void query() {}

// 反射读取
Method m = clazz.getMethod("query");
if (m.isAnnotationPresent(Log.class)) {
    Log log = m.getAnnotation(Log.class);
    System.out.println(log.value()); // "用户查询"
}
```

**关键**：要在运行时通过反射读取注解，注解必须是 `@Retention(RUNTIME)`。Spring 的 `@Autowired`、`@Transactional`、`@RequestMapping` 都是 RUNTIME 注解 + 反射读取实现的。

## 六、JDK 动态代理

**动态代理**：运行时动态生成一个代理类，在调用真实方法前后插入逻辑（这正是 AOP 的实现基础）。

JDK 动态代理**基于接口**：

```java
interface UserService { void save(); }
class UserServiceImpl implements UserService {
    public void save() { System.out.println("save"); }
}

// 代理逻辑
InvocationHandler handler = (proxy, method, args) -> {
    System.out.println("before"); // 前置增强
    Object result = method.invoke(target, args); // 调真实方法
    System.out.println("after");  // 后置增强
    return result;
};

UserService proxy = (UserService) Proxy.newProxyInstance(
    target.getClass().getClassLoader(),
    target.getClass().getInterfaces(),  // ← 必须有接口
    handler);
proxy.save(); // before → save → after
```

- 核心是 `Proxy.newProxyInstance` + `InvocationHandler`。
- JVM 运行时生成一个实现了目标接口的代理类，所有方法调用都转发到 `handler.invoke`。
- **限制：必须基于接口**——代理对象是接口的实现，目标类没接口就用不了。

---

## 七、CGLIB 动态代理

**CGLIB** 通过**继承目标类、字节码生成子类**来代理，**不需要接口**：

```java
Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(UserServiceImpl.class); // 目标类（无需接口）
enhancer.setCallback((MethodInterceptor) (obj, method, args, proxy) -> {
    System.out.println("before");
    Object r = proxy.invokeSuper(obj, args); // 调父类（真实）方法
    System.out.println("after");
    return r;
});
UserServiceImpl proxy = (UserServiceImpl) enhancer.create();
```

- 生成目标类的**子类**，重写方法插入增强。
- **限制：不能代理 final 类/final 方法**（无法被继承/重写）。

---

## 八、JDK vs CGLIB

| 维度 | JDK 动态代理 | CGLIB |
|---|---|---|
| 实现 | 基于接口，实现接口生成代理 | 基于继承，生成子类 |
| 前提 | 目标类**必须有接口** | 无需接口 |
| 限制 | 只能代理接口方法 | 不能代理 final 类/方法 |
| 依赖 | JDK 内置 | 需引入 CGLIB（Spring 已内置 ASM） |

**Spring AOP 怎么选**（高频考点）：
- 目标类**实现了接口** → 默认用 **JDK 动态代理**。
- 目标类**没有接口** → 用 **CGLIB**。
- Spring Boot 2.x+ 默认强制用 CGLIB（`proxyTargetClass=true`），避免"只能注入接口类型"的困扰。

详见 [J23 Spring AOP](./J23-精通-Spring-AOP.md)。

## 陷阱清单

- **注解忘了 `@Retention(RUNTIME)`**：反射读不到（默认是 CLASS，不进运行时）。
- **JDK 动态代理代理无接口的类**：必须有接口，否则用 CGLIB。
- **CGLIB 代理 final 类/方法**：无法继承/重写，代理失效。
- **反射 `setAccessible(true)` 滥用**：破坏封装，且模块化（JPMS）下可能被拒，有安全风险。
- **热点路径大量反射**：慢。框架会缓存 Method/Field 或用字节码生成替代。
- **`clazz.newInstance()`**：已废弃（异常处理有缺陷），用 `getDeclaredConstructor().newInstance()`。
- **Spring AOP 自调用失效**：类内部方法 a() 调 b()，b 上的 @Transactional 不生效——因为没走代理对象（见 [J24](./J24-精通-Spring事务与循环依赖.md)）。

---

## 2026 现状

- **GraalVM 原生镜像的挑战**：原生镜像在构建期做静态分析，反射/动态代理需要**显式配置元数据**（reachability metadata），否则运行时失败。这推动框架（Spring 6/Boot 3）改用**编译期处理（AOT）+ 生成代码**减少运行时反射，见 [J25 Spring Boot](./J25-精通-SpringBoot自动配置.md)。
- **字节码生成替代反射**：高性能场景用 ByteBuddy、ASM 或 `MethodHandle`/`invokedynamic`（比反射快）替代传统反射。
- **记录类 + 反射**：Record（[J28](./J28-精通-Java版本特性演进.md)）的组件可反射访问，序列化库已适配。
- **模块系统限制**：JPMS（Java 9+）下，跨模块反射访问需要 `opens`，`setAccessible` 不再无条件可用。

## 练习题

1. 获取 Class 对象有哪三种方式？它们有什么区别？

<details><summary>参考答案</summary>

三种方式：①**类字面量** `User.class`——编译期已知类型时使用，最高效，且**不会触发类的初始化**（只是拿到 Class 引用）；②**对象的 `getClass()`** `user.getClass()`——运行时通过已有实例获取其实际类型的 Class（注意拿到的是真实运行时类型，多态下可能是子类）；③**`Class.forName("全限定名")`**——运行时根据类的字符串名字动态加载，常用于按配置/名字加载类（如旧式 JDBC 驱动加载），它**会触发类的初始化**（执行静态代码块、静态变量赋值），可用重载 `forName(name, initialize, loader)` 控制是否初始化。区别核心：`.class` 编译期、不初始化；`getClass()` 靠实例、得到运行时真实类型；`forName` 靠字符串名、默认会初始化类。每个类在同一类加载器下只有一个 Class 对象。

</details>

2. 反射有哪些性能代价？为什么框架大量使用反射却仍能接受？

<details><summary>参考答案</summary>

代价：①反射调用比直接调用慢——需要运行时查找方法/字段、做访问权限检查、参数装箱拆箱，且部分调用难以被 JIT 充分内联优化；②破坏封装（setAccessible 绕过 private）、绕过编译期类型检查，错误推迟到运行时；③代码可读性和可维护性下降。框架仍大量使用且可接受的原因：①反射主要发生在**启动/配置阶段**（如 Spring 扫描类、创建 Bean、解析注解），这是一次性的，不在高频请求路径上，慢一点可接受；②框架对热点路径做了优化——缓存解析出来的 Method/Field 对象避免重复查找，或用字节码生成（CGLIB/ByteBuddy/ASM）、MethodHandle 等替代反射来提速；③反射换来的是框架的通用性和解耦（框架无需知道业务类细节就能操作它），这个收益远大于可控的性能成本。现代趋势（GraalVM AOT）则进一步用编译期生成代码减少运行时反射。

</details>

3. 自定义注解要在运行时被反射读取，必须满足什么条件？举例说明注解如何驱动框架行为。

<details><summary>参考答案</summary>

必须用元注解 `@Retention(RetentionPolicy.RUNTIME)` 声明保留策略为 RUNTIME，注解信息才会保留到运行时、能被反射 API（`isAnnotationPresent`、`getAnnotation`）读取。默认保留策略是 CLASS（编译进 class 文件但运行时不可见），SOURCE 则编译后就丢弃（如 @Override 只在编译期检查）。还应用 `@Target` 限定可标注的位置。驱动框架行为的例子：Spring 的 `@Transactional`（RUNTIME 注解）——框架在创建 Bean 时通过反射扫描方法上是否有 @Transactional，有则用动态代理为该方法织入事务逻辑（开启事务、提交/回滚）；`@RequestMapping` 让 Spring MVC 反射读取 URL 映射、建立路由表；`@Autowired` 让容器反射找到字段/构造器并注入依赖；JUnit 的 `@Test` 让框架反射找出测试方法并执行。模式都是"注解标记 + 运行时反射读取 + 据此执行增强逻辑"，这正是反射 + 注解组合的威力。

</details>

4. JDK 动态代理和 CGLIB 动态代理有什么区别？各自有什么限制？

<details><summary>参考答案</summary>

**JDK 动态代理**：基于接口实现，运行时用 `Proxy.newProxyInstance` 生成一个实现了目标接口的代理类，所有接口方法调用都转发到 `InvocationHandler.invoke`，在其中插入增强逻辑并通过反射调用真实方法。限制：**目标类必须实现接口**，且只能代理接口中声明的方法（代理对象类型是接口）。**CGLIB 动态代理**：基于继承，用字节码技术（ASM）在运行时生成目标类的**子类**，重写其方法并插入增强（通过 MethodInterceptor），调用 `invokeSuper` 执行父类原方法。优点是**不需要接口**，能代理普通类。限制：**不能代理 final 类**（无法被继承）和 **final/private/static 方法**（无法被重写）。两者对比：JDK 是 JDK 内置、面向接口；CGLIB 需依赖库（Spring 已内置）、面向继承、能力更广但有 final 限制。

</details>

5. Spring AOP 在什么情况下用 JDK 动态代理，什么情况下用 CGLIB？

<details><summary>参考答案</summary>

Spring AOP 的默认选择逻辑：如果目标 Bean **实现了至少一个接口**，Spring 默认使用 **JDK 动态代理**（生成接口的代理）；如果目标类**没有实现任何接口**，Spring 自动改用 **CGLIB**（生成子类代理）。但可以通过配置强制使用 CGLIB：设置 `proxyTargetClass=true`（如 `@EnableAspectJAutoProxy(proxyTargetClass=true)`）。实际上 **Spring Boot 2.x 及以后默认就把 proxyTargetClass 设为 true、统一用 CGLIB**，原因是 JDK 代理只能按接口类型注入/使用（代理对象只实现接口、不是具体类），容易出现"期望注入实现类却失败"或只能用接口引用的困扰；统一用 CGLIB 生成子类代理，既能代理有接口的也能代理没接口的，行为更一致。需要注意 CGLIB 不能代理 final 类/方法。无论哪种代理，都存在"自调用失效"问题——同一个类内部方法直接调用另一个带 @Transactional/@Async 的方法不会走代理、增强失效，需通过代理对象调用或自注入解决。

</details>

6. 为什么 Spring 的 `@Transactional` 在同一个类的方法内部自调用时会失效？

<details><summary>参考答案</summary>

因为 `@Transactional` 的事务能力是通过**动态代理**实现的：Spring 为目标 Bean 生成一个代理对象，外部调用先经过代理对象，代理在调用真实方法前后织入开启事务、提交/回滚的逻辑。容器里注入和被外部调用的都是这个**代理对象**。但当类内部一个方法 `a()` 直接调用本类另一个方法 `b()`（b 上有 @Transactional）时，这个调用是通过 `this.b()` 进行的——`this` 指向的是**原始目标对象本身，而不是代理对象**，因此绕过了代理，b 上的事务增强逻辑根本没机会执行，事务失效。解决办法：①把 b 拆到另一个 Bean 中、通过注入的代理调用；②自注入（注入自己的代理引用，用代理调 b）；③通过 `AopContext.currentProxy()` 拿到当前代理对象再调用（需开启 exposeProxy）。本质问题是"自调用没走代理"，这也是为什么理解动态代理对理解 Spring AOP/事务至关重要。

</details>
