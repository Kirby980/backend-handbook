# 精通并发容器

> 并发场景下，`HashMap`/`ArrayList` 不安全，`Collections.synchronizedXxx` 又是全表锁性能差。`java.util.concurrent` 提供了一系列高性能并发容器：`ConcurrentHashMap`、`CopyOnWriteArrayList`、各种 `BlockingQueue`。本篇讲清它们的原理、取舍和适用场景。
>
> **📅 基准：Java 17/21。** ConcurrentHashMap 已在 [J02](./J02-精通-HashMap与ConcurrentHashMap.md) 详讲，本篇侧重其他并发容器。

---

## 一、并发容器全景

| 普通容器（不安全） | 同步包装（全表锁、慢） | 并发容器（推荐） |
|---|---|---|
| HashMap | Collections.synchronizedMap | **ConcurrentHashMap** |
| ArrayList | Collections.synchronizedList | **CopyOnWriteArrayList** |
| HashSet | synchronizedSet | CopyOnWriteArraySet / ConcurrentHashMap.newKeySet |
| TreeMap | — | **ConcurrentSkipListMap**（有序） |
| LinkedList(队列) | — | **ConcurrentLinkedQueue** / BlockingQueue |

并发容器用更细粒度的锁（锁桶）、CAS、写时复制等技术，在保证线程安全的同时大幅提升并发性能，是多线程场景的正确选择。

---

## 二、ConcurrentHashMap

详见 [J02](./J02-精通-HashMap与ConcurrentHashMap.md)，这里补充并发容器视角的两个特性：

- **弱一致性迭代器**：遍历时不抛 `ConcurrentModificationException`（不像 HashMap 的 fail-fast，见 [J01](./J01-精通-集合框架与List源码.md)），它反映的是"创建迭代器那一刻或之后某个时刻"的状态，是弱一致的（fail-safe）——容忍遍历期间的并发修改。
- **size() 弱一致**：用 baseCount + CounterCell 分段累加（类似 [LongAdder](./J13-精通-CAS与原子类.md)），size 是估算值，并发下不保证瞬时精确。
- **原子复合方法**：`putIfAbsent`、`computeIfAbsent`、`merge` 保证复合操作原子，是并发计数/缓存填充的正确姿势（避免"先查后写"的竞态）。

---

## 三、CopyOnWriteArrayList

**写时复制（Copy-On-Write）**：读不加锁，写时复制一份新数组、改完再把引用指过去。

```java
// 写：加锁 + 复制新数组
public boolean add(E e) {
    synchronized (lock) {
        Object[] newArr = Arrays.copyOf(array, len + 1); // 复制
        newArr[len] = e;
        array = newArr;  // 原子替换引用（array 是 volatile）
    }
}
// 读：无锁，直接读当前数组引用
public E get(int i) { return (E) array[i]; }
```

特点：
- **读完全无锁、极快**；写加锁且要复制整个数组、开销大。
- **弱一致迭代**：迭代器拿的是某一刻的数组快照，遍历期间的修改看不到，但绝不抛异常（fail-safe）。
- **适用：读多写极少**（如监听器列表、配置、白名单）。**不适合写频繁/大数据量**（每次写复制全数组，内存和性能双输）。

---

## 四、阻塞队列 BlockingQueue

`BlockingQueue` 是**生产者-消费者模式**的核心：队列满时 `put` 阻塞，队列空时 `take` 阻塞。

```java
BlockingQueue<Task> q = new ArrayBlockingQueue<>(100);
// 生产者
q.put(task);   // 满则阻塞等待
// 消费者
Task t = q.take(); // 空则阻塞等待
```

| 实现 | 特点 |
|---|---|
| **ArrayBlockingQueue** | 有界数组，一把锁（公平可选） |
| **LinkedBlockingQueue** | 链表，默认无界（危险），读写两把锁吞吐高 |
| **SynchronousQueue** | 不存元素，put 必须等 take（直接传递） |
| **PriorityBlockingQueue** | 无界、按优先级出队 |
| **DelayQueue** | 元素到期才能取（延迟队列，见 [S14](../system-design/S14-精通-设计延迟队列与定时任务.md)） |
| **LinkedTransferQueue** | 高性能，transfer 直接传递 |

阻塞队列是线程池工作队列（[J11](./J11-精通-线程池.md)）和生产者消费者的基础。`offer/poll`（非阻塞带超时）、`put/take`（阻塞）、`add/remove`（满/空抛异常）三组 API 语义不同，注意区分。

---

## 五、ConcurrentLinkedQueue

**无锁队列**：基于 CAS（[J13](./J13-精通-CAS与原子类.md)）实现的非阻塞队列，不加锁靠自旋 CAS 入队/出队。

- 高并发下吞吐高（无锁，无阻塞）。
- **非阻塞**：队列空时 `poll` 返回 null（不阻塞），需要阻塞语义用 BlockingQueue。
- `size()` 要遍历计算（O(n)、弱一致），别频繁调用。

适合不需要阻塞、追求高吞吐的并发队列场景。

---

## 六、ConcurrentSkipListMap

并发的**有序** Map（相当于并发版 TreeMap），底层是**跳表（Skip List）**而非红黑树。

- 为什么用跳表不用红黑树：跳表的并发实现比红黑树简单（红黑树的旋转再平衡在并发下难处理），用 CAS 就能实现无锁/低锁的并发有序结构。
- 有序、支持范围查询（`subMap`、`headMap`），key 按自然序/Comparator 排序。
- 对应 `ConcurrentSkipListSet`（有序并发 Set）。

需要"并发 + 有序 + 范围查询"时用它。

---

## 七、为什么不用同步包装类

`Collections.synchronizedMap/List` 只是给每个方法套一层 `synchronized`（**全表/全集合一把锁**）：

- 所有操作串行，并发度极低（一个线程读，其他读写全等）。
- 复合操作仍不安全（如遍历时要手动 synchronized 整个迭代过程，否则 ConcurrentModificationException）。

而 ConcurrentHashMap 锁桶（细粒度）、CopyOnWriteArrayList 读无锁——并发性能远超同步包装类。所以**多线程优先用 JUC 并发容器，而非 synchronizedXxx**。

---

## 八、常见考点

- **弱一致迭代器 vs fail-fast**：并发容器是弱一致（fail-safe，遍历快照、不抛异常）；普通容器是 fail-fast（遍历中改抛异常）。
- **CopyOnWrite 适用场景**：读多写极少。写多会因复制全数组而性能崩。
- **阻塞队列三组 API**：`add/remove`（抛异常）、`offer/poll`（返回特殊值/带超时）、`put/take`（阻塞）。
- **ConcurrentHashMap key/value 不能 null**（见 [J02](./J02-精通-HashMap与ConcurrentHashMap.md)）。

---

## 陷阱清单

- **多线程用同步包装类**：全表锁、并发度低、复合操作仍要手动加锁。用 JUC 并发容器。
- **CopyOnWriteArrayList 用于写频繁场景**：每次写复制全数组，内存和性能双输。只适合读多写极少。
- **LinkedBlockingQueue 不指定容量**：默认无界，任务堆积 OOM（同 [J11](./J11-精通-线程池.md) 线程池坑）。
- **频繁调 ConcurrentLinkedQueue.size()**：O(n) 遍历且弱一致，别用它判空，用 `isEmpty()`。
- **以为并发容器的复合操作天然原子**：单方法原子，但"先查后写"组合仍要用 putIfAbsent/computeIfAbsent。
- **阻塞队列 API 混用**：add 满了抛异常、offer 返回 false、put 阻塞，语义不同别用错。
- **依赖并发容器 size 精确值**：弱一致估算，并发下不精确。

---

## 2026 现状

- **ConcurrentHashMap 仍是并发 Map 主力**，原子复合方法（computeIfAbsent/merge）是并发计数、本地缓存的标准写法。
- **虚拟线程下的队列**：海量虚拟线程（[J28](./J28-精通-Java版本特性演进.md)）做生产者消费者时，阻塞队列依旧适用且虚拟线程阻塞代价低；但也可考虑结构化并发等新模型。
- **不可变 + 并发**：现代设计偏好不可变数据结构 + 并发容器，减少显式锁。
- **CopyOnWrite 仍是监听器/配置等读多写少场景的简单可靠选择**。

## 练习题

1. 为什么多线程场景推荐用 ConcurrentHashMap 而不是 `Collections.synchronizedMap`？

<details><summary>参考答案</summary>

因为两者的锁粒度和并发性能差距巨大。`Collections.synchronizedMap` 只是把底层 HashMap 的每个方法用 synchronized 包一层，**整个 Map 共用一把锁**——任何时刻只有一个线程能操作它，所有读写都串行化，并发度极低（一个线程在 get，其他所有读写都得等），高并发下成为瓶颈；而且它的复合操作（如遍历、先查后写）仍不安全，遍历时必须手动 synchronized 整个迭代过程，否则会 ConcurrentModificationException。而 ConcurrentHashMap（JDK8）采用 **CAS + synchronized 锁单个桶** 的细粒度锁：不同桶的操作可以完全并发，读操作几乎无锁（靠 volatile 保证可见性），并发度等于桶数量，吞吐远高于全表锁；还提供 putIfAbsent/computeIfAbsent 等原子复合方法。所以多线程下应优先用 ConcurrentHashMap，synchronizedMap 只是历史遗留的简单包装。

</details>

2. CopyOnWriteArrayList 的原理是什么？它适合和不适合什么场景？

<details><summary>参考答案</summary>

原理是"写时复制（Copy-On-Write）"：读操作完全不加锁，直接读取当前的数组引用（数组引用是 volatile，保证可见性）；写操作（add/set/remove）则加锁，先把整个底层数组**复制一份新的**，在新数组上做修改，改完用新数组原子地替换旧引用。这样读和写操作在不同数组上进行，读永远不会被写阻塞、也不会读到写到一半的中间状态。适合场景：**读多写极少**，如事件监听器列表、配置项、黑白名单——这些数据读取频繁但很少变更，读无锁带来极高读性能。不适合场景：**写频繁或数据量大**——因为每次写都要复制整个数组，写多时会产生大量数组拷贝和垃圾对象，内存占用和性能都很差；大数组的复制开销也很高。此外它的迭代器是弱一致的（拿的是某一刻的快照，看不到之后的修改，但不抛异常）。所以用它前要确认确实是读多写少。

</details>

3. BlockingQueue 在生产者-消费者模式中起什么作用？put/take、offer/poll、add/remove 三组 API 有什么区别？

<details><summary>参考答案</summary>

作用：BlockingQueue 是生产者-消费者模式的核心枢纽——生产者把任务/数据放入队列，消费者从队列取出处理，二者通过队列解耦、独立运行。它的"阻塞"特性自动协调速度：当队列满时生产者的 put 会阻塞等待（防止生产过快撑爆），队列空时消费者的 take 会阻塞等待（避免空轮询），从而实现自然的流量控制和线程协作，无需手动 wait/notify。三组 API 区别（应对队列满/空的不同策略）：①**add/remove/element**——队列满时 add 抛 IllegalStateException、空时 remove 抛 NoSuchElementException（异常风格）；②**offer/poll/peek**——满时 offer 返回 false、空时 poll 返回 null（返回特殊值，不抛异常），还有带超时的重载 `offer(e, time, unit)`/`poll(time, unit)`（限时等待）；③**put/take**——满时 put 一直阻塞直到有空间、空时 take 一直阻塞直到有元素（阻塞风格，最常用于生产者消费者）。选择取决于你希望队列满/空时是抛异常、返回特殊值、还是阻塞等待。

</details>

4. 并发容器的"弱一致性迭代器"和普通容器的 fail-fast 有什么区别？

<details><summary>参考答案</summary>

**fail-fast（快速失败）**是 HashMap、ArrayList 等普通（非线程安全）容器的机制：用迭代器遍历时，如果检测到容器结构被修改（通过 modCount 校验），立即抛出 ConcurrentModificationException，目的是尽早暴露"遍历中被并发/意外修改"的错误，避免基于不一致数据继续运行（见 J01）。**弱一致性迭代器（weakly consistent / fail-safe）**是并发容器（ConcurrentHashMap、CopyOnWriteArrayList、ConcurrentLinkedQueue 等）的特性：迭代器创建后反映的是"创建时或之后某个时刻"的容器状态，遍历期间允许其他线程并发修改容器，迭代器**不会抛 ConcurrentModificationException**；它可能看到也可能看不到遍历开始后发生的修改（不保证实时一致，故称"弱一致"），但保证遍历过程不报错、能安全完成。区别本质：fail-fast 是"发现并发修改就报错"（面向单线程安全检测），弱一致是"容忍并发修改、遍历快照不报错"（面向并发可用性）。所以并发容器可以边遍历边被其他线程修改而不崩溃，代价是读到的可能不是最新全貌。

</details>

5. ConcurrentSkipListMap 为什么用跳表而不是红黑树来实现并发有序 Map？

<details><summary>参考答案</summary>

ConcurrentSkipListMap 需要提供"并发安全 + 有序（支持范围查询）"的 Map。普通的有序 Map（TreeMap）用红黑树，但红黑树在并发环境下很难高效实现：红黑树为保持平衡，插入/删除时需要做旋转和重新着色，这些操作会涉及多个节点的结构调整，在并发修改下要锁住较大范围或处理复杂的并发再平衡，难以做到无锁或细粒度锁，实现复杂且性能差。而**跳表（Skip List）**是一种用多层链表实现的有序结构，插入/删除只需要修改局部相邻节点的指针、不需要全局再平衡，天然适合用 CAS 做无锁/低锁的并发修改——每层链表的指针更新可以用 CAS 原子完成，实现并发安全相对简单且高效。跳表的查询/插入/删除平均也是 O(log n)，和红黑树同级。所以 JUC 选择用跳表实现并发有序 Map/Set。代价是跳表有额外的多层索引节点、空间占用略高，但换来了优良的并发性能和实现简洁性。它支持有序遍历和 subMap/headMap/tailMap 等范围操作。

</details>

6. 为什么不要频繁调用 ConcurrentLinkedQueue 的 size() 方法？

<details><summary>参考答案</summary>

因为 ConcurrentLinkedQueue 是基于 CAS 的无锁链表队列，它**没有维护一个实时的元素计数字段**（维护精确计数会引入竞争、违背其无锁高并发的设计目标）。所以它的 `size()` 方法需要**从头到尾遍历整个链表来逐个计数**，时间复杂度是 O(n)，队列越大越慢；而且由于遍历期间其他线程可能正在并发增删，遍历得到的结果是**弱一致的、不精确的**（只是某个时刻的近似值）。如果在高并发或大队列场景频繁调用 size()，会带来显著的性能开销且结果还不可靠。正确做法：判断队列是否为空用 `isEmpty()`（它只需检查头节点、O(1)，不必遍历），而不是 `size() == 0`；如果业务确实需要精确且高频的计数，应考虑用其他带计数的结构（如配合 AtomicInteger 自行维护，或用其他队列实现）。总之 ConcurrentLinkedQueue 的 size() 是"能用但慢且不准"，应尽量避免在热点路径调用。

</details>
