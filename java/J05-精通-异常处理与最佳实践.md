# 精通异常处理与最佳实践

> 异常处理看似简单，却藏着不少面试点：受检异常和非受检异常怎么分？`finally` 里有 `return` 会怎样？`try-with-resources` 的"抑制异常"是什么？为什么"用异常做流程控制"是反模式？本篇讲透异常机制和工程实践。
>
> **📅 基准：Java 17/21。**

---

## 一、异常体系

所有异常的根是 `Throwable`，分两大支：

```
Throwable
├── Error              —— 严重错误，程序无法处理（OutOfMemoryError、StackOverflowError）
└── Exception
    ├── RuntimeException —— 非受检异常（NPE、IndexOutOfBounds、IllegalArgument...）
    └── 其他 Exception   —— 受检异常（IOException、SQLException...）
```

- **Error**：JVM 层面的严重问题（内存溢出、栈溢出），应用通常**不应捕获**，捕了也无力回天。
- **Exception**：程序可处理的异常，又分受检和非受检。

---

## 二、受检异常 vs 非受检异常

| 维度 | 受检异常（Checked） | 非受检异常（Unchecked / RuntimeException） |
|---|---|---|
| 例子 | IOException、SQLException | NPE、IllegalArgumentException、IndexOutOfBounds |
| 编译器 | **强制处理**（try-catch 或 throws 声明） | 不强制 |
| 语义 | 可预期、可恢复的外部问题 | 编程错误，应通过修复代码避免 |
| 父类 | Exception（非 RuntimeException 分支） | RuntimeException |

- **受检异常**：编译器强制你处理（要么 catch，要么 throws 往上抛）。设计意图是"调用者必须意识到并处理"。
- **非受检异常**：通常是 bug（空指针、参数非法），不强制处理——应该靠修代码避免，而不是到处 catch。

**争议**：受检异常是 Java 特有设计，实践中常被诟病（导致样板 try-catch、或被随意 `catch(Exception e){}` 吞掉）。现代框架（Spring）倾向把受检异常包装成非受检异常向上抛；Go/Kotlin/C# 都没有受检异常。

---

## 三、try-catch-finally 机制

```java
try {
    // 可能抛异常
} catch (SpecificException e) {
    // 处理（先 catch 子类，再 catch 父类）
} finally {
    // 无论是否异常都执行（用于释放资源）
}
```

要点：
- **catch 顺序**：子类异常在前、父类在后（否则父类先捕获，子类 catch 永远不可达，编译报错）。
- **finally 几乎总会执行**——即使 try/catch 里有 return，finally 也会在 return 前执行。**例外**：`System.exit()`、JVM 崩溃、死循环、线程被杀。
- **finally 里别写 return / 别抛异常**：会**覆盖** try 里的 return 值或异常，导致原异常丢失（高频坑，见第八节）。

---

## 四、try-with-resources

Java 7 引入，自动关闭资源，替代手写 finally：

```java
// 旧写法：繁琐且易错
BufferedReader br = null;
try {
    br = new BufferedReader(new FileReader("f"));
    ...
} finally {
    if (br != null) br.close(); // 还得判空、close 还可能抛异常
}

// try-with-resources：自动关闭
try (BufferedReader br = new BufferedReader(new FileReader("f"))) {
    ...
} // 自动调用 br.close()，无论是否异常
```

- 资源类需实现 `AutoCloseable`（或 `Closeable`）接口。
- 多个资源按声明的**逆序**关闭。
- **抑制异常（suppressed）**：如果 try 块抛了异常，关闭资源时又抛异常，则关闭的异常被"抑制"（附加到主异常的 `getSuppressed()` 上），主异常正常抛出——避免了旧写法中 close 异常覆盖业务异常的问题。

---

## 五、异常链

捕获异常后重新抛出时，要**保留根因（cause）**，否则丢失原始堆栈：

```java
try {
    ...
} catch (SQLException e) {
    throw new ServiceException("查询用户失败", e); // ✅ 传入 cause，保留根因
    // throw new ServiceException("查询用户失败"); // ❌ 丢了 SQLException 的堆栈
}
```

- 通过构造器或 `initCause()` 传入 cause，形成异常链。
- 打印时会显示 "Caused by: ..."，能追到最底层根因。**包装异常时务必带上 cause**。

---

## 六、异常的性能

创建异常对象的主要开销是**填充栈轨迹（fillInStackTrace）**——要遍历当前调用栈，较慢。

- **不要用异常做正常流程控制**：如用异常表示"没找到"、循环退出。异常应只用于"异常"情况。
- 极高频路径上的异常可考虑覆盖 `fillInStackTrace()` 返回自身（不填栈）来优化，但属特殊优化，慎用。
- `catch` 本身在无异常时几乎零开销（现代 JVM）；开销在"抛出 + 创建异常对象"。

---

## 七、最佳实践

- **早抛晚捕（throw early, catch late）**：在错误发生点尽早抛出（带足够上下文），在能真正处理的高层统一捕获。
- **不要吞异常**：`catch (Exception e) {}` 空捕获是大忌，问题被掩盖。至少要记日志或重新抛。
- **catch 要具体**：catch 具体异常类型，别一律 `catch (Exception e)`。
- **自定义异常**：业务异常自定义（如 `BusinessException`），携带错误码/上下文，便于统一处理（如 Spring 的全局异常处理器 `@ControllerAdvice`）。
- **日志 + 抛出二选一**：要么记录日志、要么向上抛，别又记又抛导致日志重复。
- **finally 只做清理**：不要在 finally 里 return 或抛异常。

---

## 八、常见考点

```java
// finally 覆盖 return（经典坑）
int f() {
    try { return 1; }
    finally { return 2; } // 返回 2！finally 的 return 覆盖了 try 的
}

// finally 修改返回值（基本类型不受影响）
int g() {
    int x = 1;
    try { return x; }      // 返回值 1 已确定
    finally { x = 2; }     // 改 x 不影响已确定的返回值，仍返回 1
}
```

- `finally` 的 return 会覆盖 try 的 return 和异常——**永远不要在 finally 写 return**。
- 多异常合并 catch（Java 7+）：`catch (IOException | SQLException e)`。
- 空指针：Java 14+ 的 **Helpful NullPointerExceptions** 会精确指出是哪个变量为 null，排查更方便。

---

## 陷阱清单

- **finally 里 return / throw**：覆盖 try 的返回值或异常，原异常丢失。finally 只做清理。
- **空 catch 吞异常**：`catch(Exception e){}` 掩盖问题，排查无门。至少记日志。
- **catch 父类在前**：子类 catch 不可达，编译错误。子类在前父类在后。
- **重新抛异常不带 cause**：丢失根因堆栈。包装时传入原异常。
- **catch (Exception) 一把抓**：连不该处理的也吞了。catch 具体类型。
- **用异常做流程控制**：性能差且语义混乱。异常只用于异常情况。
- **手写 close 不判空/不防 close 异常**：用 try-with-resources。
- **catch Error**：Error 通常不可恢复（OOM），不应捕获处理。

---

## 2026 现状

- **Helpful NullPointerExceptions**（Java 14+）：NPE 消息精确到具体变量/方法，极大改善排查体验。
- **受检异常争议持续**：现代 Java 实践和框架普遍倾向"少用受检异常、包装成非受检向上抛"；Lambda/Stream 中受检异常很别扭（需包装），进一步推动这一趋势。
- **`@ControllerAdvice` / 全局异常处理**：Spring 体系下业务异常统一在全局处理器转换为标准响应，是生产标配。
- **结构化并发**（Java 21+ 预览/演进）：让并发任务的异常传播更清晰（子任务异常能聚合到父作用域），见 [J29](./J29-精通-Java版本特性演进.md)。

## 练习题

1. 受检异常和非受检异常有什么区别？各举例。为什么现代实践倾向少用受检异常？

<details><summary>参考答案</summary>

受检异常（Checked，继承 Exception 但不属 RuntimeException 分支，如 IOException、SQLException）：编译器**强制**调用者处理——要么 try-catch，要么用 throws 声明继续上抛，否则编译不过；语义上代表可预期、可能需要恢复的外部问题。非受检异常（Unchecked，RuntimeException 及其子类，如 NullPointerException、IllegalArgumentException、IndexOutOfBoundsException）：编译器不强制处理，语义上通常是编程错误（bug），应通过修正代码来避免，而非到处捕获。现代实践倾向少用受检异常的原因：①受检异常导致大量样板 try-catch 或 throws 传染，代码冗长；②常被开发者用空 catch 吞掉，反而更危险；③在 Lambda/Stream 中无法直接抛受检异常，需要丑陋的包装；④Go、Kotlin、C# 等都没有受检异常也运行良好。因此 Spring 等框架普遍把受检异常包装成非受检异常向上抛，由全局异常处理器统一处理。

</details>

2. `finally` 块一定会执行吗？如果 try 和 finally 里都有 return 会怎样？

<details><summary>参考答案</summary>

finally **几乎总会执行**——即使 try 或 catch 里有 return、throw，finally 也会在方法真正返回/抛出之前执行（常用于释放资源）。但有例外：①try 中调用了 `System.exit()`（JVM 直接退出）；②JVM 崩溃、断电；③执行 finally 的线程被杀死或进入死循环。如果 try 和 finally 里都有 return：**finally 的 return 会覆盖 try 的 return**，方法最终返回 finally 里的值，且 try 中原本要返回的值或要抛的异常都被丢弃。例如 `try{return 1;}finally{return 2;}` 返回 2。这是个危险陷阱：finally 的 return/throw 会吞掉 try 的返回值和异常（包括业务异常），导致问题被掩盖。所以最佳实践是**绝不在 finally 里写 return 或 throw**，finally 只做资源清理。另外注意：若 finally 只是修改一个基本类型局部变量，不影响 try 中已确定的返回值（返回的是值的副本）。

</details>

3. try-with-resources 相比手写 try-finally 关闭资源有什么优势？什么是"抑制异常"？

<details><summary>参考答案</summary>

优势：①**简洁**——在 `try(...)` 中声明实现了 AutoCloseable 的资源，JVM 自动在 try 结束（无论正常还是异常）时调用其 close()，无需手写 finally + 判空 + close；②**正确处理多资源**——多个资源按声明的逆序自动关闭；③**避免异常覆盖**——这正是"抑制异常"要解决的问题。**抑制异常（suppressed exception）**：在旧的 try-finally 写法里，如果 try 块抛了业务异常，而 finally 里 close() 又抛了异常，则 close 的异常会覆盖掉业务异常，导致真正的根因丢失。try-with-resources 改进了这点：当 try 块已经抛出异常、关闭资源时再抛异常，关闭的异常会被"抑制"——附加到主（业务）异常的 suppressed 列表中（可通过 `Throwable.getSuppressed()` 获取），而主异常正常向上抛出。这样既保留了主异常作为根因，又不丢失关闭时的异常信息。

</details>

4. 为什么捕获异常后重新抛出时要保留 cause（异常链）？

<details><summary>参考答案</summary>

因为如果重新抛出时不传入原始异常作为 cause，原异常的类型和堆栈信息就会丢失，排查问题时只能看到上层包装异常，无法定位最底层的真正原因。保留 cause（通过 `new XxxException(msg, e)` 构造器或 `initCause(e)`）会形成异常链，打印堆栈时显示 "Caused by: ..." 一直追溯到根因异常及其发生位置。例如 DAO 层抛 SQLException，Service 层捕获后抛 `new ServiceException("查询失败", e)`：带上 e 时，日志能看到 ServiceException → Caused by: SQLException → 具体 SQL 错误的完整链路；不带 e 时只能看到 "查询失败" 这一句，根本不知道是连接超时、SQL 语法错还是约束冲突。所以包装并重新抛出异常时，必须把原异常作为 cause 传入，保留完整的诊断信息。

</details>

5. 为什么说"用异常做流程控制"是反模式？异常的性能开销主要在哪？

<details><summary>参考答案</summary>

"用异常做流程控制"（如用抛异常表示"查无数据""循环结束""校验未通过"等正常分支）是反模式，原因：①**性能**——异常的主要开销在创建异常对象时调用 `fillInStackTrace()` 填充栈轨迹，需要遍历当前调用栈，开销不小；在高频路径上频繁抛异常会显著拖慢性能。②**语义混乱**——异常应表示"异常/意外"情况，用它表达正常业务分支会让代码意图不清、可读性差、难以维护。③**破坏控制流**——异常会跨多层栈跳转，使流程难以跟踪。正确做法是用返回值、Optional、状态码等表达正常分支，异常只用于真正异常的情况。性能补充：catch 块在不发生异常时几乎零开销（现代 JVM），真正的开销在"抛出 + 构造异常对象（填栈）"；极端高频场景如必须用异常可重写 fillInStackTrace 不填栈，但属特殊优化、应谨慎。

</details>

6. catch 多个异常时为什么子类异常要写在父类前面？

<details><summary>参考答案</summary>

因为 catch 块是按顺序匹配的：当异常发生时，JVM 从上到下依次检查每个 catch 能否捕获该异常（是否是其声明类型或子类型），匹配到第一个就执行、不再往下看。如果把父类异常（如 Exception）写在前面、子类（如 IOException）写在后面，那么任何 IOException 都会先被前面的 `catch(Exception e)` 捕获，后面的 `catch(IOException e)` 永远不可能被执行到——这是一段"不可达代码"。Java 编译器会直接报错（"exception IOException has already been caught"），强制你把更具体的子类异常放在前面、更宽泛的父类放在后面，保证每个 catch 都有意义、能精确处理对应的异常类型。Java 7+ 还支持用 `|` 合并捕获多个无继承关系的异常（`catch (IOException | SQLException e)`）以减少重复。

</details>
