# 精通泛型与类型擦除

> Java 泛型是"编译期的把戏"——它在编译后被**擦除**，运行时并不存在。理解类型擦除，才能解释一堆看似奇怪的限制：为什么不能 `new T[]`？为什么 `List<String>` 和 `List<Integer>` 的 `getClass()` 相同？通配符的 `extends`/`super` 又该怎么选？本篇讲透。
>
> **📅 基准：Java 17/21。** 对照 [Go 泛型](../golang/G09-精通-Go-泛型-类型参数与约束.md)（Go 是真泛型、运行时保留类型），差异很大。

---

## 一、为什么需要泛型

泛型（Generics，Java 5 引入）解决"类型安全"和"消除强制转换"：

```java
// 没有泛型：运行时才暴露错误
List list = new ArrayList();
list.add("hello");
Integer i = (Integer) list.get(0); // 编译通过，运行时 ClassCastException

// 有泛型：编译期就报错
List<String> list = new ArrayList<>();
list.add("hello");
Integer i = list.get(0); // ❌ 编译失败，提前拦截
```

泛型把类型检查从运行时提前到**编译期**，并省去强制转换。本质是给编译器更多类型信息做检查。

---

## 二、类型擦除

**这是 Java 泛型的核心机制。** Java 泛型是"伪泛型"——泛型信息只存在于编译期，编译后会被**擦除（Type Erasure）**，字节码里没有泛型：

- 无界类型参数 `<T>` 擦除为 `Object`。
- 有界类型参数 `<T extends Comparable>` 擦除为上界 `Comparable`。
- 编译器在擦除后，在需要的地方**自动插入强制转换**。

```java
// 源码
class Box<T> { T value; T get() { return value; } }

// 擦除后（概念上）
class Box { Object value; Object get() { return value; } }
// 调用处 String s = box.get(); 编译器插入 (String) 转换
```

**为什么用擦除**：Java 5 引入泛型时为了**向后兼容**——擦除后泛型代码和老的非泛型代码字节码一致，老代码不用改、JVM 不用改。代价是丢失了运行时类型信息（这正是 Go/C# 真泛型与 Java 的根本差异）。

---

## 三、类型擦除的证据与影响

擦除导致一系列"奇怪"现象，都是高频考点：

```java
// ① 运行时类型相同：泛型参数被擦除
List<String> ls = new ArrayList<>();
List<Integer> li = new ArrayList<>();
System.out.println(ls.getClass() == li.getClass()); // true！都是 ArrayList.class

// ② 不能 new 泛型数组 / 泛型实例
T[] arr = new T[10];      // ❌ 编译错误：擦除后不知道 T 是什么
T t = new T();            // ❌ 同理

// ③ 不能对泛型参数做 instanceof
if (obj instanceof List<String>) {} // ❌ 运行时没有 String 信息

// ④ 不能有泛型的静态字段、不能 catch 泛型异常
// ⑤ 重载冲突：擦除后签名相同
void f(List<String> a) {}
void f(List<Integer> a) {} // ❌ 擦除后都是 f(List)，方法重复
```

绕过办法：传 `Class<T>` 反射创建（`clazz.newInstance()`）、用 `Array.newInstance(clazz, n)` 创建泛型数组、用通配符 `instanceof List<?>`。

## 四、桥方法

类型擦除会破坏多态，编译器用**桥方法（bridge method）**修复。看一个例子：

```java
class Node<T> {
    T data;
    void set(T data) { this.data = data; }
}
class StringNode extends Node<String> {
    @Override
    void set(String data) { super.set(data); } // 重写
}
```

`Node<T>` 擦除后是 `void set(Object)`，而 `StringNode.set(String)` 签名不同，**本来不构成重写**。为保持多态，编译器在 `StringNode` 里自动生成一个**桥方法**：

```java
void set(Object data) { set((String) data); } // 编译器生成的桥方法，转调真正的方法
```

这样通过 `Node` 引用调 `set(Object)` 时，会经桥方法转到 `set(String)`，多态正确。桥方法对开发者透明，但反射/调试时能看到它（`isBridge()`）。

## 五、通配符

类型参数有继承的"不变性"问题：`List<String>` **不是** `List<Object>` 的子类型（即使 String 是 Object 子类）。通配符解决"灵活接收不同泛型实参"：

| 通配符 | 含义 | 能读 | 能写 |
|---|---|---|---|
| `<?>` 无界 | 任意类型 | 读为 Object | 只能写 null |
| `<? extends T>` 上界 | T 或其子类 | 读为 T | 不能写（除 null） |
| `<? super T>` 下界 | T 或其父类 | 读为 Object | 能写 T 及其子类 |

```java
List<? extends Number> nums; // 可指向 List<Integer>、List<Double>
Number n = nums.get(0);      // ✅ 读出来是 Number
nums.add(1);                 // ❌ 不能写：不知道具体是 List<Integer> 还是 List<Double>

List<? super Integer> sink;  // 可指向 List<Integer>、List<Number>、List<Object>
sink.add(1);                 // ✅ 能写 Integer
Object o = sink.get(0);      // 读出来只能当 Object
```

---

## 六、PECS 原则

通配符怎么选，记 **PECS：Producer Extends, Consumer Super**（生产者用 extends，消费者用 super）：

- **你从集合里读数据（集合是生产者）→ 用 `? extends T`**：因为你只读、读出来当 T 用。
- **你往集合里写数据（集合是消费者）→ 用 `? super T`**：因为你只写，写 T 进去安全。

JDK 的 `Collections.copy` 是经典示范：

```java
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    // src 是生产者（读）→ extends；dest 是消费者（写）→ super
}
```

记忆：**读 extends、写 super；既读又写就用确定类型**。

## 七、泛型方法与边界

```java
// 泛型方法：<T> 声明在返回值前
public static <T extends Comparable<T>> T max(List<T> list) {
    T best = list.get(0);
    for (T t : list) if (t.compareTo(best) > 0) best = t;
    return best;
}
```

- `<T extends Comparable<T>>` 给 T 加**上界约束**，T 必须实现 Comparable，才能调 `compareTo`（否则擦除到 Object 没有该方法）。
- 多个边界用 `&`：`<T extends A & B>`。
- 泛型方法的类型参数由调用时实参**自动推断**，通常不用显式指定。

---

## 八、常见限制与坑

- **基本类型不能做类型参数**：`List<int>` ❌，要用包装类 `List<Integer>`（涉及自动装箱开销，见 [J01 集合](./J01-精通-集合框架与List源码.md) 相关）。
- **数组协变 vs 泛型不变**：数组是协变的（`Integer[]` 是 `Object[]` 子类型），但这不安全（`Object[] a = new Integer[1]; a[0]="x";` 运行时 `ArrayStoreException`）；泛型设计成**不变**正是为了编译期堵住这个洞。所以**不要混用泛型和数组**。
- **不能创建泛型数组**：`new List<String>[10]` ❌（擦除 + 协变会破坏类型安全）。
- **静态成员不能用类的类型参数**：静态成员不依附实例，没有 T。

---

## 陷阱清单

- **以为运行时能拿到泛型类型**：擦除后没有，`getClass()` 看不到泛型实参；需要类型信息要传 `Class<T>`。
- **`new T()` / `new T[]`**：擦除后不知道 T，编译失败。用反射或传 Class。
- **`List<String>` 当 `List<Object>` 用**：泛型不变，编译错误。需要协变用 `? extends`。
- **PECS 用反**：从集合读却用 super、往集合写却用 extends，导致读写受限。读 extends、写 super。
- **泛型数组**：`new T[]`、`new List<String>[]` 不允许，易踩坑。
- **重载擦除冲突**：`f(List<String>)` 和 `f(List<Integer>)` 擦除后签名相同，编译报错。
- **基本类型做泛型参数**：`List<int>` 不合法，用 Integer（注意装箱开销）。

---

## 2026 现状

- **类型擦除仍是 Java 泛型的根基**，短期不会变（兼容性约束）。这是与 Go（真泛型、运行时保留）、C#（具体化泛型）的本质区别。
- **Project Valhalla**：长期演进项目，目标包括"具体化泛型（reified generics）"和值类型（value/primitive classes），未来可能让泛型支持基本类型、保留运行时类型信息，但尚未进入正式 LTS，关注后续进展。
- **`var` 与泛型**：Java 10 的 `var` 配合菱形 `<>` 让泛型声明更简洁，但不改变擦除本质。
- **泛型 + Stream/Record**：现代 Java 大量用泛型（Stream、Optional、Record 组件），理解擦除有助于排查相关编译错误。

## 练习题

1. 什么是类型擦除？Java 为什么采用类型擦除来实现泛型？

<details><summary>参考答案</summary>

类型擦除是指 Java 泛型的类型信息只存在于**编译期**，编译成字节码后泛型参数被"擦除"掉：无界类型参数 `<T>` 被替换为 `Object`，有界 `<T extends X>` 被替换为上界 `X`，编译器再在需要的地方自动插入强制类型转换。所以运行时并不存在 `List<String>` 这种类型，只有 `List`。Java 采用擦除的根本原因是**向后兼容**：泛型是 Java 5 才加入的，为了让泛型代码与之前大量的非泛型（裸类型）代码在字节码层面兼容、老代码无需修改、JVM 也无需改动，就选择了擦除——擦除后泛型类和原来的非泛型类字节码一致。代价是丢失了运行时泛型类型信息，导致不能 `new T()`、不能对泛型做 instanceof、`getClass()` 拿不到泛型实参等限制。这与 Go、C# 的"具体化泛型"（运行时保留类型）形成对比。

</details>

2. 为什么 `List<String>` 和 `List<Integer>` 的 `getClass()` 相同？为什么不能 `new T[]`？

<details><summary>参考答案</summary>

因为类型擦除：编译后 `List<String>` 和 `List<Integer>` 的泛型参数都被擦除，运行时都只是 `ArrayList`（同一个 Class 对象），所以 `ls.getClass() == li.getClass()` 为 true——运行时根本区分不出泛型实参。不能 `new T[]`（或 `new T()`）的原因也是擦除：创建数组/对象需要在运行时知道确切的类型来分配内存和做类型检查，但 T 在运行时已被擦除成 Object（或上界），JVM 不知道 T 到底是什么，因此编译器直接禁止 `new T[]` 和 `new T()`。绕过办法：传入 `Class<T> clazz` 参数，用反射 `Array.newInstance(clazz, n)` 创建泛型数组、用 `clazz.getDeclaredConstructor().newInstance()` 创建实例，把运行时类型信息显式传进来。

</details>

3. 什么是桥方法（bridge method）？它解决什么问题？

<details><summary>参考答案</summary>

桥方法是编译器为了在类型擦除后保持泛型的多态（方法重写）而自动生成的方法。问题背景：当子类重写父类的泛型方法时，擦除会让签名对不上——例如 `Node<T>` 的 `set(T)` 擦除成 `set(Object)`，而子类 `StringNode extends Node<String>` 写的是 `set(String)`，两者签名不同，按 Java 规则本不构成重写，多态会失效（通过 `Node` 引用调用时找不到子类方法）。为修复这一点，编译器在子类中自动生成一个**桥方法** `set(Object o) { set((String) o); }`，它的签名与父类擦除后的方法一致，内部强转后转调子类真正的 `set(String)`。这样通过父类引用调用 `set(Object)` 时经桥方法正确分发到子类方法，多态得以保持。桥方法对开发者透明，但可通过反射 `Method.isBridge()` 检测到。

</details>

4. 解释通配符 `? extends T` 和 `? super T` 的区别，以及 PECS 原则。

<details><summary>参考答案</summary>

`? extends T`（上界通配符）：表示"T 或 T 的某个子类型"，但具体是哪个子类未知。因此可以安全地**读取**（读出来一定是 T 或其父类型，按 T 用），但**不能写入**（除 null）——因为不知道实际是 `List<Integer>` 还是 `List<Double>`，写任何具体值都可能类型不符。`? super T`（下界通配符）：表示"T 或 T 的某个父类型"。因此可以安全地**写入** T 及其子类型（它们一定是该父类型的实例），但**读取**只能当作 Object（不知道确切上层类型）。**PECS 原则**（Producer Extends, Consumer Super）：如果一个泛型集合是数据的"生产者"（你从中读数据），用 `? extends T`；如果是"消费者"（你往里写数据），用 `? super T`。例如 `Collections.copy(List<? super T> dest, List<? extends T> src)`：src 提供数据是生产者用 extends，dest 接收数据是消费者用 super。记忆口诀：读用 extends、写用 super、既读又写用确定类型。

</details>

5. 数组是协变的而泛型是不变的，这分别意味着什么？为什么泛型要设计成不变？

<details><summary>参考答案</summary>

**数组协变**：`Integer[]` 是 `Object[]` 的子类型，可以把 `Integer[]` 赋给 `Object[]` 引用。但这不安全——`Object[] arr = new Integer[3]; arr[0] = "hello";` 编译能过，运行时抛 `ArrayStoreException`（因为实际是 Integer 数组却存了 String），即把类型错误推迟到了运行时。**泛型不变**：`List<Integer>` **不是** `List<Object>` 的子类型，二者无继承关系，不能互相赋值。泛型设计成不变正是为了**在编译期堵住数组协变留下的类型漏洞**：如果泛型也协变，`List<Object> l = new ArrayList<Integer>(); l.add("x");` 就会在运行时出错；不变性让编译器在编译期就拒绝这种赋值，把错误提前暴露。需要"协变"灵活性时，用通配符 `? extends`（只读）显式表达，既灵活又安全。这也是"不要混用泛型和数组"建议的由来。

</details>

6. 以下代码为什么编译不过？`void f(List<String> a){}` 和 `void f(List<Integer> a){}`。

<details><summary>参考答案</summary>

因为类型擦除后这两个方法的签名变成完全相同。`List<String>` 和 `List<Integer>` 在擦除后都变成裸类型 `List`，于是 `f(List<String>)` 和 `f(List<Integer>)` 都擦除成 `f(List)`——两个方法有了相同的名字和相同的参数类型（擦除后），构成方法重复定义（duplicate method），编译器报错 "name clash: both methods have same erasure"。也就是说，泛型参数的不同不能作为方法重载的区分依据，因为运行时它们无法区分。要解决只能改方法名（如 `fStr`、`fInt`），或改用其他参数区分。这是类型擦除带来的一个典型限制，常作为面试陷阱题出现。

</details>
