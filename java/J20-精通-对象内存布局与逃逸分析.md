# 精通对象内存布局与逃逸分析

> 一个 Java 对象在内存里到底长什么样？为什么说"对象不一定都在堆上"？逃逸分析、栈上分配、标量替换是 JIT 的重要优化。本篇打通对象内存布局和逃逸分析，串起 [J08 锁](./J08-精通-synchronized与volatile.md)（对象头）、[J15 内存](./J15-精通-JVM运行时内存结构.md)（堆）、[J17 GC](./J17-精通-垃圾回收算法.md)。
>
> **📅 基准：Java 17/21（HotSpot，64 位）。**

---

## 一、对象的内存布局

HotSpot 中，一个普通对象在堆中的内存布局分三部分：

```mermaid
flowchart LR
    subgraph 对象
        H[对象头 Header<br>Mark Word + 类型指针]
        D[实例数据 Instance Data<br>各字段值]
        P[对齐填充 Padding<br>补齐到8字节倍数]
    end
    style H fill:#fff9c4
    style D fill:#c8e6c9
    style P fill:#e1bee7
```

1. **对象头（Header）**：存运行时元数据（见第二节）。
2. **实例数据（Instance Data）**：对象真正的字段内容（含父类继承的字段）。
3. **对齐填充（Padding）**：HotSpot 要求对象大小是 **8 字节的整数倍**，不足则填充补齐（无实际含义，只为内存对齐提升访问效率）。

---

## 二、对象头

对象头包含两到三部分：

| 部分 | 内容 | 大小（64 位） |
|---|---|---|
| **Mark Word** | 运行时数据：hashCode、GC 分代年龄、锁标志位、锁信息 | 8 字节 |
| **类型指针（Klass Pointer）** | 指向方法区/元空间该类的元数据（这对象是哪个类的实例） | 4 字节（压缩指针开启）/ 8 字节 |
| **数组长度** | 仅数组对象有，记录数组长度 | 4 字节 |

- **Mark Word** 是复用的（不同锁状态存不同内容，靠锁标志位区分）——这正是 [J08 synchronized 锁升级](./J08-精通-synchronized与volatile.md) 的存储基础。
- **类型指针**让 JVM 知道对象属于哪个类（从而找到类的方法、字段定义）。

---

## 三、对象大小计算

经典考点：一个空对象多大？

- `new Object()`：对象头 = Mark Word(8) + Klass Pointer(4，压缩指针) = 12 字节，对齐填充到 **16 字节**。
- 含字段的对象：对象头 + 各字段大小 + 对齐。字段大小：boolean/byte=1、char/short=2、int/float=4、long/double=8、引用=4（压缩指针）。

例：一个有一个 int 字段的对象 = 头 12 + int 4 = 16 字节（刚好对齐，无填充）。

JOL（Java Object Layout）工具可以打印对象的实际内存布局，面试可提。

---

## 四、压缩指针 CompressedOops

64 位 JVM 的对象引用本应是 8 字节，但 HotSpot 默认开启 **压缩指针（Compressed Ordinary Object Pointers）**，把引用压成 **4 字节**：

- **为什么省内存**：64 位下引用占 8 字节，对象多时引用开销巨大。压缩指针利用对象 8 字节对齐的特性（地址低 3 位总是 0），用 4 字节存储"对象编号"再左移 3 位还原地址，相当于能寻址 32GB（2^32 × 8）。
- **效果**：引用、类型指针都从 8 字节降到 4 字节，显著节省内存、提升缓存命中。
- **32GB 限制**：堆超过 32GB 时压缩指针失效（4 字节寻址不够），引用退回 8 字节。**所以堆要么设 < 32GB（享受压缩指针），要么明显大于 32GB**——设成 33GB 反而因失去压缩指针，可用内存可能不如 31GB（一个反直觉的调优坑）。

## 五、对象的创建过程

`new` 一个对象的完整步骤（高频考点）：

1. **类加载检查**：检查类是否已加载、解析、初始化，没有则先类加载（见 [J16](./J16-精通-类加载与双亲委派.md)）。
2. **分配内存**：在堆中划出对象所需大小的内存（方式见第六节）。
3. **初始化零值**：把分配的内存空间初始化为零值（保证字段不赋值也能用默认值，如 int=0）。
4. **设置对象头**：填充 Mark Word、类型指针（这对象属于哪个类、GC 年龄、锁状态等）。
5. **执行 `<init>`**：调用构造方法，按代码给字段赋真正的值、执行构造逻辑。

注意"初始化零值"在构造方法之前——这就是为什么字段不显式赋值也有默认值。

---

## 六、内存分配方式

第 2 步"分配内存"有两种方式 + TLAB 优化：

- **指针碰撞（Bump the Pointer）**：堆内存规整（用标记-整理/复制，无碎片）时，用一个指针划分已用和空闲，分配就是指针往后挪。简单高效。
- **空闲列表（Free List）**：堆内存不规整（用标记-清除，有碎片，如 CMS）时，维护一个空闲块列表，分配时找合适的块。
- **TLAB（Thread Local Allocation Buffer）**：并发分配内存要保证线程安全（否则两个线程可能分到同一块）。TLAB 给**每个线程在 Eden 预分配一小块私有缓冲区**，线程在自己的 TLAB 里分配对象（无需同步），TLAB 用完再向堆申请新的。这大幅减少了分配时的锁竞争，是高并发下对象分配快的关键。

---

## 七、逃逸分析

**逃逸分析（Escape Analysis）** 是 JIT 的优化技术：分析一个对象的作用域，判断它会不会"逃逸"出当前方法或线程。

- **不逃逸**：对象只在方法内部使用，方法结束就没用了（如局部变量 new 的临时对象）。
- **方法逃逸**：对象被作为返回值返回、或赋给外部变量，逃出了方法。
- **线程逃逸**：对象被其他线程访问（如赋给静态字段、实例字段被其他线程读）。

```java
// 不逃逸：sb 只在方法内用，没返回也没给外部
String concat(String a, String b) {
    StringBuilder sb = new StringBuilder();  // 可被优化
    sb.append(a).append(b);
    return sb.toString();   // 返回的是 String，sb 本身没逃逸
}
```

JIT 通过逃逸分析，对"不逃逸"的对象做激进优化（见下节）。

---

## 八、逃逸分析的优化

基于逃逸分析，JIT 可做三种优化：

| 优化 | 做法 | 收益 |
|---|---|---|
| **栈上分配** | 不逃逸的对象直接在**栈**上分配（随栈帧出栈自动销毁） | 减少堆分配和 GC 压力 |
| **标量替换** | 把不逃逸对象**拆散成一个个标量字段**（不创建整个对象），直接用局部变量代替 | 彻底不创建对象、字段可放寄存器 |
| **锁消除** | 不逃逸（线程私有）的对象上的锁，直接消除（见 [J08](./J08-精通-synchronized与volatile.md)） | 省掉无意义的加解锁 |

- **栈上分配/标量替换**让"对象不一定在堆上"——不逃逸的对象可能根本不进堆（被标量替换掉），随方法结束自动消失，**不需要 GC**。这是"逃逸分析能减轻 GC 压力"的原因。
- HotSpot 实际更多用**标量替换**（比纯栈上分配更彻底）。
- 默认开启（`-XX:+DoEscapeAnalysis`），是 JIT（[J21](./J21-精通-字节码与执行引擎.md)）的重要优化。

所以面试题"对象一定分配在堆上吗？"——**不一定**，逃逸分析可能让它栈上分配或被标量替换。

## 陷阱清单

- **以为对象一定在堆上**：逃逸分析可让不逃逸对象栈上分配/标量替换，不进堆、不用 GC。
- **堆设成 32~40GB**：超过 32GB 压缩指针失效，引用变 8 字节，可用内存反而可能不如 31GB。要么 < 32GB，要么远大于。
- **忽略对象头开销**：每个对象有 12~16 字节头，海量小对象时对象头开销可观（用基本类型数组/对象池优化）。
- **以为构造方法最先执行**：分配内存、零值初始化、设对象头都在构造方法之前。
- **以为对象内存是连续紧凑无浪费**：有对齐填充（补齐 8 字节倍数）。
- **依赖 identity hashCode 还想要偏向锁**：调用对象 hashCode 会占用 Mark Word，影响锁状态（见 [J08](./J08-精通-synchronized与volatile.md)）。

---

## 2026 现状

- **逃逸分析 + 标量替换是 JIT 标配优化**，C2/Graal 编译器对热点代码自动应用，开发者无感但受益。
- **Project Valhalla（值类型/原始类）**：长期演进中，目标让"值类型"对象**无对象头、可内联存储**（像基本类型一样紧凑），从根本上消除小对象的对象头开销和间接寻址——会显著改变对象内存布局，关注其进入 LTS。
- **压缩指针仍是默认**：64 位 JVM 默认开启，32GB 是经典调优分界线。
- **Foreign Memory API（Java 21）**：提供堆外内存的安全访问，对需要精确内存布局的高性能场景（如序列化、堆外缓存）是 Unsafe 的现代替代。

## 练习题

1. 一个 Java 对象在内存中的布局分哪几部分？对象头里存了什么？

<details><summary>参考答案</summary>

HotSpot 中普通对象的内存布局分三部分：①**对象头（Header）**——存放运行时元数据，包含两到三块：**Mark Word**（8 字节，存 hashCode、GC 分代年龄、锁标志位和锁信息，是复用的、不同锁状态存不同内容，是 synchronized 锁升级的存储基础）、**类型指针 Klass Pointer**（指向方法区/元空间中该类的元数据，告诉 JVM 这个对象是哪个类的实例；开启压缩指针时 4 字节，否则 8 字节）、以及**数组长度**（仅数组对象才有，4 字节，记录数组元素个数）。②**实例数据（Instance Data）**——对象真正存储的字段内容，包括自身定义的和从父类继承来的所有字段（按一定规则排列，HotSpot 会做字段重排以节省空间）。③**对齐填充（Padding）**——HotSpot 要求对象的总大小必须是 8 字节的整数倍，如果对象头加实例数据后不是 8 的倍数，就用填充补齐（没有实际数据含义，纯为内存对齐以提升访问效率）。例如 `new Object()` = 8（Mark Word）+ 4（压缩类型指针）= 12 字节，填充到 16 字节。

</details>

2. 什么是压缩指针？为什么堆大小不建议设置在 32GB 附近？

<details><summary>参考答案</summary>

压缩指针（Compressed Oops）是 64 位 HotSpot 的默认优化：64 位系统下对象引用本应占 8 字节，对象多时引用开销巨大。压缩指针利用"对象按 8 字节对齐、地址低 3 位恒为 0"的特性，用 **4 字节存储一个对象编号（去掉低 3 位）**，使用时左移 3 位还原成真实地址，从而把引用和类型指针从 8 字节压缩到 4 字节，显著节省内存、提升 CPU 缓存命中率。由于用 4 字节（2^32 个编号）× 8 字节对齐，可寻址范围约为 2^35 = 32GB。**堆超过 32GB 时压缩指针就会失效**（4 字节编号不够用），引用退回 8 字节。这带来一个反直觉的调优坑：如果把堆从 31GB 调到 33GB，看似增大了，但因为失去了压缩指针，所有引用和类型指针都变回 8 字节、内存占用大增，实际可用的有效内存可能**反而比 31GB 还少**、对象更占空间、缓存效率下降。所以建议堆大小**要么设在 32GB 以下**（充分享受压缩指针带来的内存和性能收益），**要么设得明显大于 32GB**（如 48GB 以上，确保增加的容量能弥补失去压缩指针的损失），而**避免设在 32GB ~ 约 40GB 这个尴尬区间**。

</details>

3. new 一个对象的完整过程是怎样的？为什么字段不赋值也有默认值？

<details><summary>参考答案</summary>

new 一个对象的步骤：①**类加载检查**——检查这个类是否已被加载、解析、初始化过，如果没有则先触发类加载流程（见 J16）；②**分配内存**——根据对象大小在堆中划分出一块内存（规整内存用"指针碰撞"、不规整用"空闲列表"，并发用 TLAB 减少竞争）；③**初始化零值**——把分配到的内存空间全部初始化为零值（数值类型为 0、boolean 为 false、引用为 null）；④**设置对象头**——在对象头里填入 Mark Word（GC 年龄、锁状态等）和类型指针（标明属于哪个类）；⑤**执行 `<init>` 构造方法**——按照代码给字段赋真正的初值、执行构造逻辑，对象才算完全创建好。**字段不赋值也有默认值**的原因正是第③步"初始化零值"：在构造方法执行之前，JVM 已经把对象所占内存清零（赋予各类型的零值）。所以即使你在代码里没有显式给某个成员字段赋值，它也已经是该类型的默认值（int=0、boolean=false、对象引用=null），不会是随机的脏数据。这与局部变量不同——局部变量不会自动赋零值，必须显式初始化后才能使用，否则编译报错。

</details>

4. 什么是 TLAB？它解决了什么问题？

<details><summary>参考答案</summary>

TLAB（Thread Local Allocation Buffer，线程本地分配缓冲区）是 HotSpot 在 Eden 区为对象分配做的并发优化。问题背景：堆是所有线程共享的，多个线程同时在堆（Eden）上分配对象时，如果直接用一个全局指针做"指针碰撞"分配，会出现竞争——两个线程可能同时拿到同一个空闲地址、分配到重叠内存，必须加同步（如 CAS 或锁）来保证分配的原子性，而对象分配是极其高频的操作，频繁同步会成为性能瓶颈。TLAB 的解决办法：**给每个线程在 Eden 中预先分配一小块私有的缓冲区（TLAB）**，线程创建对象时优先在自己的 TLAB 里分配——因为这块缓冲区是线程私有的，分配时只需移动自己 TLAB 内的指针、**完全不需要和其他线程同步**，速度极快；当一个线程的 TLAB 用完了，再向堆（Eden）申请一块新的 TLAB（这一步才需要同步，但频率低得多）。这样把"每次分配都要全局同步"变成"绝大多数分配在私有 TLAB 内无锁完成、偶尔申请新 TLAB 才同步"，大幅减少了分配时的竞争，是高并发下对象创建依然高效的关键。可用 `-XX:+UseTLAB`（默认开启）控制。

</details>

5. 什么是逃逸分析？基于它 JIT 能做哪些优化？

<details><summary>参考答案</summary>

逃逸分析（Escape Analysis）是 JIT 编译器的一种分析技术，用于判断一个对象的作用域/动态范围——即这个对象是否会"逃逸"出创建它的方法或线程。分几种情况：**不逃逸**（对象只在方法内部使用，方法结束就不再被引用）、**方法逃逸**（对象被作为返回值返回、或被赋给外部可访问的变量，逃出了当前方法）、**线程逃逸**（对象被其他线程访问，如赋给静态字段或被其他线程读取的实例字段）。基于逃逸分析的结果，JIT 对"不逃逸"的对象可以做三种优化：①**栈上分配**——把不逃逸的对象直接分配在栈上（栈帧里），随方法调用结束、栈帧弹出而自动销毁，无需进堆、不增加 GC 负担；②**标量替换**——把一个不逃逸的对象拆解成它的各个成员字段（标量），不再创建完整对象，而是用一组独立的局部变量来代替这些字段（这些标量甚至可以直接分配到 CPU 寄存器），相当于对象"消失"了，比栈上分配更彻底，HotSpot 实际更多用这种；③**锁消除**——如果加锁的对象经分析确定不会被其他线程访问（线程私有、不逃逸），那这个锁就没有意义，JIT 直接把锁消除掉（如方法内局部 StringBuffer 的 synchronized）。这些优化默认开启（-XX:+DoEscapeAnalysis），对热点代码自动生效，能显著减少堆分配、GC 压力和无谓的锁开销，开发者无感但受益。

</details>

6. "Java 对象一定分配在堆上吗？"请回答并解释。

<details><summary>参考答案</summary>

**不一定。** 虽然通常我们说 Java 对象在堆上分配（这是默认和主要情况），但由于 JIT 编译器的**逃逸分析**优化，并非所有对象都会真正进入堆。当逃逸分析判定一个对象"不逃逸"（只在方法内部使用，既不作为返回值、也不赋给外部变量、更不被其他线程访问）时，JIT 可以对它做：①**栈上分配**——把对象直接分配在当前方法的栈帧上，随方法结束、栈帧出栈而自动销毁，根本不进入堆；②更彻底的**标量替换**——干脆不创建这个对象，而是把它的字段拆成一个个独立的局部变量（标量），直接用这些局部变量（可能放在寄存器里）参与运算，对象在运行时层面"不存在"了。这两种优化的对象都不在堆上、也就不需要 GC 去回收它们，从而减轻了堆分配压力和 GC 负担。所以正确的回答是："对象**大多数**分配在堆上，但不是绝对——经逃逸分析判定不逃逸的对象，可能被栈上分配或标量替换，从而不在堆上分配、不需要 GC。"这也解释了为什么逃逸分析能优化性能：大量短命的、不逃逸的临时对象（如方法内的局部 StringBuilder、临时包装对象）被优化掉后，堆压力和 Minor GC 频率都会下降。（注意：这是 JIT 在运行期对热点代码的优化，解释执行或未被优化时对象仍在堆上。）

</details>
