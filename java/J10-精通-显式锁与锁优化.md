# 精通显式锁与锁优化

> `synchronized`（[J08](./J08-精通-synchronized与volatile.md)）够用，但不够灵活。`ReentrantLock`、读写锁、`StampedLock` 提供了可中断、超时、公平、读写分离、乐观读等高级能力。本篇讲清这些显式锁的取舍，以及死锁/活锁/饥饿这些并发"病症"的防治。
>
> **📅 基准：Java 17/21。** 显式锁基于 [AQS](./J09-精通-AQS原理.md)。

---

## 一、Lock 接口与 ReentrantLock

`Lock` 接口提供比 synchronized 更细的控制：

```java
ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
    // 临界区
} finally {
    lock.unlock(); // ⚠️ 必须在 finally 手动释放
}
```

`ReentrantLock`（可重入锁，基于 AQS）的核心方法：

| 方法 | 作用 |
|---|---|
| `lock()` | 加锁（阻塞直到拿到） |
| `unlock()` | 释放锁（必须手动，放 finally） |
| `tryLock()` | 尝试加锁，立即返回 true/false（不阻塞） |
| `tryLock(time, unit)` | 限时尝试，超时返回 false |
| `lockInterruptibly()` | 可中断地加锁（等待时能响应中断） |
| `newCondition()` | 创建条件变量（见 [J09](./J09-精通-AQS原理.md)） |

这些正是 synchronized 没有的：**可尝试、可超时、可中断、可公平、多条件**。

---

## 二、ReentrantLock vs synchronized

| 维度 | synchronized | ReentrantLock |
|---|---|---|
| 实现 | JVM 内置（monitor） | JDK 代码（AQS） |
| 释放 | 自动（出块/异常） | **手动 unlock**（忘记会死锁） |
| 可中断 | ❌ | ✅ lockInterruptibly |
| 超时 | ❌ | ✅ tryLock(timeout) |
| 尝试加锁 | ❌ | ✅ tryLock |
| 公平锁 | ❌（非公平） | ✅ 可选公平 |
| 条件变量 | 一个（wait/notify） | 多个（Condition） |
| 性能 | 优化后很好 | 相近 |

**选择**：默认用 `synchronized`（简单、自动释放、不易出错、JVM 持续优化）；**只有需要可中断/超时/尝试/公平/多条件时才用 `ReentrantLock`**。注意 ReentrantLock 必须 finally unlock，忘记就是死锁。

## 三、ReentrantReadWriteLock

读写锁把锁分成**读锁（共享）**和**写锁（独占）**，适合**读多写少**：

```java
ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
Lock readLock = rwLock.readLock();
Lock writeLock = rwLock.writeLock();
```

规则（"读读共享，读写/写写互斥"）：

| | 读锁 | 写锁 |
|---|---|---|
| **读锁** | ✅ 兼容（多读并发） | ❌ 互斥 |
| **写锁** | ❌ 互斥 | ❌ 互斥 |

- 多个线程可同时持有读锁（并发读）；写锁独占（写时不能读也不能写）。
- 底层用 AQS 一个 int 的高 16 位记读锁数、低 16 位记写锁数（见 [J09](./J09-精通-AQS原理.md)）。
- **锁降级**：持有写锁时可以获取读锁，再释放写锁，"降级"为读锁（保证数据可见性的平滑过渡）；但**不支持锁升级**（持读锁直接拿写锁会死锁）。
- **写饥饿**：读多时写线程可能一直拿不到锁，需注意。

适合缓存、配置等读远多于写的场景。读多写少且追求更高性能可看 StampedLock。

---

## 四、StampedLock

Java 8 引入，比读写锁更快，核心是**乐观读（optimistic read）**：

```java
StampedLock sl = new StampedLock();
long stamp = sl.tryOptimisticRead();   // 乐观读：不加锁，拿一个版本戳
int x = data;                          // 读数据
if (!sl.validate(stamp)) {             // 校验期间有没有被写
    stamp = sl.readLock();             // 被写过则升级为悲观读锁
    try { x = data; } finally { sl.unlockRead(stamp); }
}
```

- **乐观读不加锁**：先读，再校验期间有没有写发生；没写就直接用（零锁开销），有写才退化为悲观读锁重读。
- 读多写极少时性能远超 ReentrantReadWriteLock（避免了读锁的 CAS 开销）。
- **代价/限制**：**不可重入**、不支持 Condition、用错（如忘了 validate）易出 bug，API 比读写锁难用。适合性能敏感的读多写少场景。

## 五、死锁

**死锁**：两个或多个线程互相持有对方需要的锁，永久等待。

```java
// 线程1：先 lockA 再 lockB
synchronized (A) { synchronized (B) { } }
// 线程2：先 lockB 再 lockA  ← 加锁顺序相反
synchronized (B) { synchronized (A) { } }
// 线程1 持 A 等 B，线程2 持 B 等 A → 死锁
```

死锁的**四个必要条件**（缺一不可，破坏任一即可避免）：

1. **互斥**：资源同一时刻只能被一个线程占用。
2. **持有并等待**：持有一个资源的同时等待另一个。
3. **不可剥夺**：资源不能被强行抢走，只能主动释放。
4. **循环等待**：存在线程环形等待链（A 等 B、B 等 A）。

**避免方法**：
- **破坏循环等待（最常用）**：所有线程**按固定全局顺序加锁**（如总是先 A 后 B）。
- **破坏持有并等待**：一次性申请所有锁。
- **破坏不可剥夺**：用 `tryLock(timeout)`，拿不到就释放已持有的锁重试。

**检测**：`jstack` 能直接检测并打印死锁（"Found one Java-level deadlock"），见 [J19 调优排查](./J19-精通-JVM调优与故障排查.md)。

## 六、活锁与饥饿

- **活锁（Livelock）**：线程没阻塞，但一直"重试-失败-重试"，互相谦让导致谁都进行不下去（像两人过道互相让路反复同向）。解法：引入随机退避。
- **饥饿（Starvation）**：某线程长期抢不到资源（如低优先级线程、非公平锁下的排队线程、读写锁的写线程）。解法：公平锁、合理优先级。

死锁是"卡死不动"，活锁是"忙而无进展"，饥饿是"个别线程拿不到"。

---

## 七、锁的最佳实践

- **unlock 放 finally**：`lock()` 后立刻 `try`，`unlock()` 放 `finally`，否则异常时锁不释放 → 死锁。
- **缩小锁范围**：只锁真正需要互斥的代码，别把 IO/耗时操作锁进去。
- **固定加锁顺序**：多锁场景按全局一致顺序加锁，防死锁。
- **优先 tryLock 超时**：关键路径用 `tryLock(timeout)` 避免无限等待，拿不到可降级/重试。
- **能不共享就不共享**：用 ThreadLocal（[J14](./J14-精通-ThreadLocal.md)）、不可变对象（[J03](./J03-精通-String与不可变设计.md)）、局部变量减少锁需求。
- **读多写少用读写锁/StampedLock**。

---

## 八、常见考点

- **ReentrantLock 可重入**：同一线程可重复 lock（state 累加），但 lock 几次就要 unlock 几次。
- **lock() 不在 try 外还是 try 内**：`lock()` 应在 try **之前或 try 第一行**，确保只有成功加锁才会 unlock（避免没拿到锁却 unlock 抛异常）。常见写法是 lock() 后紧跟 try。
- **公平锁构造**：`new ReentrantLock(true)`。
- **synchronized 也可重入**，但不能中断/超时。

---

## 陷阱清单

- **忘记 unlock / unlock 不在 finally**：异常时锁不释放，造成死锁。
- **lock() 写在 try 内第一行之后**：若 lock 抛异常仍执行 unlock 会出错；规范是 lock() 紧贴 try。
- **读写锁锁升级**：持读锁直接获取写锁会死锁（不支持升级）；只支持降级（写→读）。
- **死锁：加锁顺序不一致**：多锁不按固定顺序加，循环等待死锁。统一顺序。
- **StampedLock 当可重入锁用**：它不可重入，重入会死锁。
- **StampedLock 乐观读忘了 validate**：读到不一致数据。乐观读后必须校验。
- **锁范围过大**：把耗时 IO 锁进临界区，并发度骤降。
- **用 ReentrantLock 却不需要它的高级特性**：徒增手动释放的出错风险，简单场景用 synchronized。

---

## 2026 现状

- **虚拟线程优先用 ReentrantLock**：Java 21 虚拟线程在 synchronized 中阻塞早期会 pin 住载体线程；在 ReentrantLock 等 AQS 锁上阻塞则能正确卸载，所以虚拟线程场景推荐显式锁（见 [J11](./J11-精通-线程池.md)、[J29](./J29-精通-Java版本特性演进.md)）。
- **StampedLock 在高读并发场景流行**：读多写少的缓存/计数等用乐观读获得接近无锁的性能。
- **死锁排查工具成熟**：jstack/Arthas/JFR 能快速定位死锁与锁竞争热点（见 [J19](./J19-精通-JVM调优与故障排查.md)）。
- **更倾向无锁/不可变**：现代并发设计趋向用不可变数据、并发容器（[J12](./J12-精通-并发容器.md)）、CAS（[J13](./J13-精通-CAS与原子类.md)）减少显式锁。

## 练习题

1. ReentrantLock 相比 synchronized 多了哪些能力？什么时候应该用 ReentrantLock？

<details><summary>参考答案</summary>

ReentrantLock 相比 synchronized 多了：①**可中断加锁**（lockInterruptibly）——等待锁时能响应中断，避免一直阻塞；②**超时获取**（tryLock(time, unit)）——限时等待，超时返回 false，可避免死等；③**非阻塞尝试**（tryLock()）——立即返回是否拿到，拿不到可做别的；④**公平锁**（构造传 true）——可选严格 FIFO；⑤**多个条件变量**（newCondition）——一个锁可建多个 Condition 实现精确唤醒。但代价是必须手动 unlock（要放 finally，忘记会死锁），不像 synchronized 自动释放。选择原则：默认用 synchronized（简单、自动释放、不易出错、JVM 优化后性能与 Lock 相近）；只有当确实需要上述高级特性之一（可中断、超时、尝试、公平、多条件）时才用 ReentrantLock。不要为了"听起来高级"而在简单互斥场景用 ReentrantLock，徒增手动释放出错的风险。

</details>

2. ReentrantReadWriteLock 的读写规则是什么？什么是锁降级？为什么不支持锁升级？

<details><summary>参考答案</summary>

读写规则："读读共享，读写/写写互斥"——多个线程可同时持有读锁（并发读），但写锁是独占的：持有写锁时其他线程既不能读也不能写；有线程持读锁时，写锁也拿不到。适合读多写少场景。**锁降级**：指一个线程持有写锁的同时去获取读锁，然后释放写锁，从而"降级"为只持有读锁。这样做的意义是保证数据修改后的可见性平滑过渡——在写完数据、还没释放写锁时就先拿到读锁，能确保降级后这段时间内自己能读到刚写的数据、且不被其他写线程插入修改。ReadWriteLock 支持锁降级（写→读）。**不支持锁升级**（读→写）的原因：如果允许持有读锁时直接申请写锁，当多个线程都持有读锁并都想升级为写锁时，每个都要等其他读锁释放，而大家都不释放（都在等升级），就会**死锁**。所以读写锁禁止升级——要写必须先释放读锁再竞争写锁。

</details>

3. StampedLock 的"乐观读"是怎么回事？它和读写锁相比有什么优劣？

<details><summary>参考答案</summary>

StampedLock 的乐观读（tryOptimisticRead）：读取前不加任何锁，只获取一个"版本戳（stamp）"，然后直接读数据，读完调用 `validate(stamp)` 校验在这期间是否有写操作发生——如果没有写（validate 返回 true），说明读到的数据是一致的，直接使用，全程零锁开销；如果有写（validate 返回 false），则退化为获取悲观读锁（readLock）重新读取。优势：在读多写极少的场景，乐观读几乎不加锁、没有读写锁那种读锁的 CAS/状态修改开销，吞吐和性能远高于 ReentrantReadWriteLock。劣势/限制：①**不可重入**（重入会死锁）；②不支持 Condition；③ API 复杂、易用错（如忘记 validate 就用了可能不一致的数据、stamp 管理麻烦）；④乐观读期间读到的数据可能是不一致的中间态，必须 validate 后才能信任。所以 StampedLock 适合性能敏感、读远多于写、且能正确处理乐观读模式的场景，普通场景用 ReentrantReadWriteLock 更安全易用。

</details>

4. 死锁产生的四个必要条件是什么？实践中最常用的避免方法是什么？

<details><summary>参考答案</summary>

四个必要条件（同时满足才会死锁，破坏其一即可避免）：①**互斥**——资源同一时刻只能被一个线程占用；②**持有并等待**——线程持有至少一个资源的同时，又在等待获取被其他线程占用的资源；③**不可剥夺**——资源不能被强行夺走，只能由持有者主动释放；④**循环等待**——存在一个线程等待环（如 T1 持 A 等 B、T2 持 B 等 A）。实践中最常用的避免方法是**破坏"循环等待"**：让所有线程按照一个**固定的全局顺序**获取锁（例如总是先锁 A 再锁 B，绝不出现先 B 后 A），这样就不会形成环形等待链，简单有效。其他方法：破坏"持有并等待"（一次性申请所有需要的锁，要么全拿到要么都不拿）；破坏"不可剥夺"（用 tryLock 带超时，拿不到第二把锁就释放已持有的锁、退避重试）。检测上可用 jstack 直接发现 Java 级死锁。

</details>

5. 死锁、活锁、饥饿有什么区别？

<details><summary>参考答案</summary>

三者都是并发中线程无法正常推进的问题，但表现不同。**死锁（Deadlock）**：两个或多个线程互相持有对方需要的资源并永久等待，所有相关线程都**完全卡住、不再执行**（如 T1 持 A 等 B、T2 持 B 等 A）。**活锁（Livelock）**：线程并没有阻塞，仍在不停地执行和重试，但因为不断地互相响应/谦让导致谁都无法真正前进——比如两个线程检测到冲突都主动退让再重试，结果一直同步地退让、永远成功不了（类比两人在走廊相遇，都往同一侧让、反复同步）。活锁是"忙碌但无进展"，CPU 在转。解决常用随机化退避（引入随机等待时间打破同步）。**饥饿（Starvation）**：某个或某些线程长期得不到所需资源而无法执行，但其他线程在正常运行——比如低优先级线程总被高优先级抢占、非公平锁下排队线程一直被插队、读写锁读多时写线程长期拿不到写锁。解决用公平锁、合理设置优先级、避免长期独占。简记：死锁=都卡死不动；活锁=都在动但没进展；饥饿=个别线程长期得不到资源。

</details>

6. 使用 ReentrantLock 有哪些最佳实践？为什么 unlock 一定要放在 finally？

<details><summary>参考答案</summary>

最佳实践：①**unlock 必须放在 finally 中**，且 lock() 紧贴 try 之前/之首；②缩小锁的范围，只锁真正需要互斥的代码，别把耗时 IO 放进临界区；③多锁场景按固定全局顺序加锁防死锁；④关键路径用 tryLock(timeout) 避免无限等待；⑤只在需要其高级特性时才用，否则用 synchronized；⑥可重入但 lock 几次就要 unlock 几次。**unlock 放 finally 的原因**：ReentrantLock 不像 synchronized 会在退出代码块或抛异常时自动释放锁，它需要程序员显式调用 unlock。如果不放在 finally 里，一旦临界区代码抛出异常，unlock 就不会被执行，这个锁将永远不被释放——后续所有想获取该锁的线程都会永久阻塞，造成死锁。放在 finally 保证无论临界区正常结束还是异常退出，锁都一定会被释放。标准范式是：`lock.lock(); try { /*临界区*/ } finally { lock.unlock(); }`，且 lock() 要在 try 外或紧贴 try（确保只有真正加锁成功才会在 finally 执行 unlock，避免没拿到锁却调 unlock 抛 IllegalMonitorStateException）。

</details>
